# Работа с Claude на проекте VibeTradingBotV5

Этот документ описывает **концепцию работы** с Claude (в чате и в Claude Code) на этом проекте. Это фундамент — на нём строятся операционные сценарии (`.claude/flow/playbook.md`), агенты (`.claude/agents/`), скиллы (`.claude/skills/`) и принятие решений (`.claude/adr/`).

## Базовые принципы

### Принцип 1. Чат — для мышления, Claude Code — для исполнения

- **Чат** (claude.ai): обсуждение, проектирование, ревью, разбор. Здесь принимаются решения.
- **Claude Code** (CLI): чтение, изменение, создание файлов в репозитории. Здесь решения исполняются.

Содержательные решения принимаются в чате. Файлы меняются в Claude Code. Из чата в Claude Code знание переносится через **черновики**: я в чате выдаю готовый текст артефакта, ты передаёшь его в Claude Code с задачей "адаптируй под текущее состояние репо и сохрани".

### Принцип 2. Знания живут в файлах, не в истории чата

История любого чата — расходный материал. Файлы в репозитории — постоянная память.

Любое значимое решение, паттерн, наблюдение, конвенция должны быть зафиксированы в одном из мест:
- **ADR** — для архитектурных решений с альтернативами.
- **Спецификация** (`docs/spec/`, временно `docs/domain/`, `docs/api/`) — для описания текущего состояния системы.
- **Скилл** (`.claude/skills/`) — для переиспользуемых процедур и знаний.
- **Промпт агента** (`.claude/agents/`) — если влияет на поведение конкретной роли.
- **`CLAUDE.md`** — для проектных конвенций, применяемых всегда.
- **`pipeline-evolution-log.md`** — для изменений самого пайплайна работы (агенты, скиллы, процессы).

Если решение принято и не зафиксировано — оно потеряно.

### Принцип 3. Иерархия источников правды

При противоречиях между документами / кодом — побеждает источник **выше** в иерархии (см. CLAUDE.md, раздел "Source of truth hierarchy"). Это правило строгое и применяется во всех сессиях, во всех чатах, всеми агентами.

Конфликты внутри одного уровня — выносятся на обсуждение и фиксируются как ADR.

### Принцип 4. Связное обновление документации

Любое изменение модели, процесса или ключевой концепции **автоматически** влечёт проверку и обновление всех связанных документов. Это **не отдельная процедура**, а базовое поведение Claude Code на этом проекте.

В частности:
- Принят ADR → проверяем, какие спецификации требуют обновления, обновляем в той же сессии.
- Изменена модель → проходим по всем документам, ссылающимся на модель, обновляем.
- Появился новый термин → добавляем в `GLOSSARY.md` (когда создан).
- Изменился промпт агента или скилл → запись в `pipeline-evolution-log.md`.
- Принятие ADR / обновление спецификации, закрывающее пункт из `.claude/planning/backlog.md` → пункт перемещается в раздел «Закрытые» с датой и ссылкой на ADR или коммит.
- Появление нового открытого вопроса в ходе работы → пункт сразу заводится в `.claude/planning/backlog.md`, не остаётся в чате или в комментарии к коду.

Knowledge Curator в конце каждой сессии должен проверять, не осталось ли связных обновлений без внимания. Пропуск связного обновления = **незавершённая работа**.

### Принцип 5. Claude Code не коммитит сам

Все изменения остаются в working tree. Коммиты делает человек после ревью через IDEA. Это даёт возможность откатить или скорректировать любое изменение перед фиксацией в истории.

## Поэтапная миграция документации

Проект унаследовал несколько поколений документации. Главные источники сейчас — `docs/domain/` и `docs/api/`. Они **остаются** на своих местах, не удаляются и не помечаются deprecated сразу.

**Целевое место** для всей актуальной документации — `docs/spec/`. Туда мы переносим темы постепенно, адаптируя их под структуру и связи новой документации.

**Правила миграции:**

1. Новые спецификации создаются только в `docs/spec/`.
2. Существующая тема переезжает в `docs/spec/` целиком, не "наполовину". Полумиграции запрещены — создают путаницу.
3. Когда тема перенесена и адаптирована — соответствующий файл в `docs/domain/` помечается на первой строке:

[MIGRATED → docs/spec/<новый-путь>] — этот файл больше не источник правды, см. новое расположение.

   Сам файл при этом не удаляется (история, ссылки извне).
4. С момента пометки `[MIGRATED]` — файл становится **приоритета 5** (только справка), независимо от исходного приоритета.
5. **Структура `docs/spec/`** зафиксирована в [ADR-0002](adr/0002-spec-document-standard.md). Шесть жанровых
   каталогов: `models/`, `lifecycle/`, `processes/`, `integrations/`,
   `references/`, `invariants/`. Шаблоны для каждого — в
   `docs/spec/_templates/`. Полные правила (имена файлов, frontmatter,
   стиль ссылок, размер документов, что допустимо в spec) — в ADR-0002.
   При работе с документами в `docs/spec/` автоматически активируется
   скилл `spec-document-workflow`, обеспечивающий соблюдение стандарта.

Эта же логика применима к `docs/api/`, если решим её переносить.

## Команда агентов

Стартовый состав (детали — в `.claude/agents/`):

- **architect** — структура, слои, абстракции. KPI: поддерживаемость и расширяемость.
- **domain-expert** — доменная модель торговли (сделки, ордера, позиции, стратегии). KPI: чистота доменного слоя.
- **risk-engineer** — системные/технические риски (failure modes, race conditions, timeouts). KPI: что произойдёт в худшем случае.
- **trading-risk-officer** — финансовый смысл решений (sizing, stops, regime-awareness). KPI: предотвращение финансово бессмысленных решений.
- **knowledge-curator** — фиксация решений в правильных местах, проверка связных обновлений. KPI: ничего ценного не остаётся незафиксированным.

Состав эволюционирует через сценарии 2-3 в `playbook.md`. Все изменения — через `pipeline-evolution-log.md`.

## Скиллы

Скиллы — переиспользуемые знания и процедуры в `.claude/skills/`. Активируются автоматически по триггеру в `description`.

Скиллы НЕ заменяют:
- ADR (обоснование решений).
- Спецификации (описание системы).
- CLAUDE.md (общие конвенции).

Скиллы — это **как делать на практике** конкретные задачи. Эволюционируют через сценарии 4-5 в `playbook.md`.

## ADR — архитектурные решения

ADR хранятся в `.claude/adr/`. Индекс — `.claude/adr/README.md`. Шаблон — `.claude/adr/0000-template.md`.

**Правила ADR:**

- ADR **append-only**. Принятый ADR не редактируется задним числом.
- Если решение пересмотрено — создаётся новый ADR со статусом `Supersedes ADR-NNNN`. Старый помечается `Superseded by ADR-MMMM`.
- ADR должен содержать: контекст, решение, альтернативы (с причиной отказа), последствия (включая список затронутых документов).
- ADR создаётся для значимых решений: трудно отменить, есть альтернативы, влияет более чем на один модуль/документ. Для мелких выборов ADR избыточен.

## Project Knowledge в claude.ai

В claude.ai создан Проект "VibeTradingBotV5". К нему прикреплены ключевые файлы:
- `CLAUDE.md`
- `.claude/working-with-claude.md`
- `.claude/flow/playbook.md`
- `docs/README.md`
- `.claude/adr/README.md`
- `.claude/project-instructions.md` (опционально — для прозрачности; основная функция файла — резервная копия для Custom Instructions Проекта)
- (по мере появления) `docs/GLOSSARY.md`, `docs/ROADMAP.md`

**Все чаты по проекту создаются внутри этого Проекта.** Тогда любая новая сессия со мной автоматически видит эти файлы.

Содержимое поля **Custom Instructions** Проекта хранится в репозитории как `.claude/project-instructions.md`. При обновлении инструкций — правишь файл, коммитишь, копируешь обновлённый текст в claude.ai вручную. Это резервная копия и история изменений в одном лице.

**Дисциплина обновления Project Knowledge:**

При обновлении любого прикреплённого к Проекту файла — после коммита в репозитории необходимо обновить файл в Project Knowledge (через интерфейс claude.ai). Иначе будущие чаты будут работать со старой версией.

Knowledge Curator должен напоминать об этом, если затронут файл из списка выше.

## Knowledge capture rules (обязательно для всех агентов)

В системные промпты **всех** агентов вшита инструкция: при принятии решения или обнаружении паттерна — предложить, где его задокументировать. Это распределённая ответственность, не только Curator.

Конкретно:
- Решение с альтернативами → ADR.
- Новый паттерн / процедура → скилл.
- Новый термин → GLOSSARY.md.
- Уточнение проектной конвенции → CLAUDE.md или соответствующий скилл.
- Изменение в пайплайне работы → pipeline-evolution-log.md.
- Описание модели или процесса → спецификация (`docs/spec/`).

Если место неочевидно — агент спрашивает явно, не молчит.
