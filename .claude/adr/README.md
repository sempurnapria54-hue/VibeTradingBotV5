# Architecture Decision Records

Журнал значимых архитектурных решений на проекте.

## Что такое ADR

ADR — короткий документ, фиксирующий **одно** архитектурное решение с обоснованием. Принципы:

- **Append-only.** Принятый ADR не редактируется задним числом.
- **Одно решение — один ADR.** Не смешивать.
- **С альтернативами.** Если альтернатив не было — это не ADR, это просто факт.
- **С последствиями.** Что меняется в коде / документации.

## Когда создавать ADR

Создавай ADR для решений, которые:
- Трудно отменить.
- Имеют альтернативы.
- Влияют более чем на один модуль или документ.
- Будут влиять на проект дольше нескольких недель.

Не создавай ADR для:
- Мелких выборов реализации.
- Конвенций — это в `docs/conventions/` или CLAUDE.md.
- Описания текущего состояния — это в спецификации.

## Статусы ADR

- **Proposed** — обсуждается, не принято.
- **Accepted** — принято, действует.
- **Superseded by ADR-NNNN** — заменено другим ADR. Старый остаётся для истории.
- **Deprecated** — больше не действует, но и замены нет (редко).

Изменение статуса (например, на `Superseded`) — единственное допустимое изменение принятого ADR.

## Алгоритм работы с ADR

**Принцип append-only:** принятый ADR — снимок решения на момент принятия. Содержание не редактируется задним числом.

**Что считается редактированием (запрещено):**

- Изменение Decision, Context, Alternatives, Consequences по существу.
- Обновление технических ссылок на пути файлов при переезде целевых файлов.

**Что НЕ считается редактированием (разрешено):**

- Изменение Status (Proposed → Accepted, Accepted → Superseded by N, и т.д.).
- Исправление опечаток без изменения смысла.
- Физическое перемещение/переименование файла (содержание не меняется).
- Добавление примечаний в строго определённый блок (см. ниже).

### Два типа примечаний

**1. Технические примечания** — разрешены в любом статусе. Назначение: навигационные / ссылочные пометки, не меняющие решение. Формат — фиксированный блок в конце документа:

```
## Примечания

### Технические
- [YYYY-MM-DD] Файлы, на которые ссылается этот ADR, частично
  переехали (см. ADR-NNNN). Актуальные пути — в CLAUDE.md.
```

Каждая запись датируется и не редактируется после добавления (append-only внутри append-only).

**2. Содержательные примечания** — разрешены **только** в статусах Superseded и Deprecated. Назначение: ретроспективные комментарии после того, как решение устарело. «Почему пришлось пересматривать», «что не учли», «какой опыт получили».

```
### Содержательные
- [YYYY-MM-DD] Решение пересмотрено в ADR-NNNN. Главный фактор —
  не учли X.
```

Также append-only, датированы. Не отменяют само решение — комментируют задним числом.

### Битые ссылки после переезда целевых файлов

Ссылки внутри принятого ADR не обновляются. Они остаются как есть — это часть исторического контекста. Читатель ориентируется по CLAUDE.md и `docs/README.md` для актуальных путей. Опционально — техническое примечание с указанием на переезд.

### При крупных рефакторингах

1. ADR переезжают физически согласно решению из ADR о рефакторинге.
2. Тела ADR не редактируются.
3. В блок «Технические примечания» добавляется запись со ссылкой на ADR о рефакторинге.
4. ADR о рефакторинге в Consequences явно перечисляет все ADR, которых коснулся переезд.

Полный пример применения этого алгоритма — ADR-0003 (раздел Decision, подраздел «Расширение алгоритма работы с ADR»).
