# ADR-0009: Стратегия миграции `docs/domain/`

**Статус:** Proposed
**Дата:** 2026-05-15
**Контекст:** Операционный план миграции legacy-документации `docs/domain/` в `docs/spec/`.
**Связанные ADR:** ADR-0002 (стандарт документа `docs/spec/`), ADR-0003 (разделение `docs/` и `.claude/`), ADR-0006 (принципы спецификации), ADR-0007 (структура `docs/spec/`), ADR-0008 (журнал open-questions).

## Context

Проект унаследовал legacy-документацию в `docs/domain/`: 20 содержательных файлов, ~25430 строк суммарно. Документация описывает доменные модели, процессы, статусы, integration с OKX, оркестрацию сделок.

ADR-0002 ввёл `docs/spec/` как целевую спецификацию и обозначил миграцию как поэтапную. Но **детального плана миграции** не было. Принцип «тема целиком, маркер `[MIGRATED]`» — недостаточный план для 25K+ строк legacy.

В этом цикле проектирования зафиксированы:

- **ADR-0006** — принципы организации содержания спецификации (что считается бизнес-объектом, локальным или кросс-модельным инвариантом, и т.д.).
- **ADR-0007** — структура `docs/spec/`: подкаталоги, полный список model-документов (13 core + 3 runtime), структура integration.
- **ADR-0008** — журнал open-questions как новый артефакт для фиксации концептуальных и рабочих вопросов.

Эти три ADR закрепили **что мы строим** в результате миграции. ADR-0009 закрепляет **как и в каком порядке** мы это делаем.

Перед проектированием стратегии были проведены две разведки:

- **Инвентарь legacy `docs/domain/`:** 20 содержательных файлов, ~25430 строк, кластеризация по содержанию (9 кластеров).
- **Каталог именованных моделей:** 154 модели с тремя источниками (доменная документация, Java-код, Flyway-миграции). Выявлены ~55 documented-only моделей (есть в доке, нет в коде) и ~35 code-only классов (есть в коде, нет в доке).

Обработка расхождений «дока vs код» при миграции строится на проектном принципе «документация — источник истины, код подтягивается» (`working-with-claude.md`, Принцип 6 — добавляется при применении пакета ADR-0006..0009).

## Decision

Десять подразделов.

### 1. Шесть фаз миграции

Миграция делится на шесть последовательных фаз.

**Фаза 1: миграция домена.** Восемь кластеров (см. §2), 13 core + 3 runtime моделей, 1 lifecycle, 6 processes, ~5 invariants. В начале фазы создаются `docs/spec/MODELS.md` (реестр канонических имён, стартует с заглушками) и `.claude/planning/migration-tracker.md` (чеклист прогресса миграции). `docs/conventions/terminology.md` создаётся до старта фазы 1 как часть Этапа 4 (он не зависит от миграции). По окончании: все мигрируемые legacy-документы `docs/domain/` помечены `[MIGRATED → ...]`, целевые spec-документы созданы, `docs/spec/MODELS.md` наполнен (или содержит стартовые заглушки для документов, ещё не созданных), `.claude/planning/migration-tracker.md` отражает завершённые кластеры. Маршруты legacy-документов:

- `docs/domain/models/mapping/okx/` → фаза 2 (см. §1 «Фаза 2»).
- `docs/domain/Открытые вопросы по движку.md` → фаза 3 (переносится в журнал по ADR-0008).
- `docs/domain/models/Справочник по доменным моделям.md` → фаза 1, особым маршрутом: содержание распределяется между `docs/spec/MODELS.md` (имена), соответствующими model-документами (содержание), и при необходимости `docs/conventions/terminology.md` (если есть фрагменты, попадающие в терминологические соглашения) — см. §9.
- `docs/domain/models/Strategy API examples.md` → фаза 1, кластер C5, как сопровождающий материал к Strategy.md (см. §2).
- Остальные ~16 legacy-файлов → фаза 1, по кластерам (см. §2).

**Фаза 2: миграция integration-маппингов OKX.** `docs/domain/models/mapping/okx/*` → `docs/spec/integrations/okx/{models,mapping}/`. Структура зафиксирована в ADR-0007 §2. Включает: описание внешних DTO OKX, маппинг DTO ↔ домен, конкретные таблицы резолва статусов (по ADR-0006 §3).

**Фаза 3: обработка корневого backlog.** `docs/domain/Открытые вопросы по движку.md` — 13 пронумерованных вопросов про runtime-движок. Все вопросы переносятся в `.claude/questions/open-questions.md` и проходят процедуру разбора по ADR-0008. К моменту фазы 3 часть вопросов может быть уже разрешена в ADR, принятых при фазах 1-2; остаток классифицируется и обрабатывается. После переноса исходный документ помечается `[MIGRATED → .claude/questions/open-questions.md]`.

**Фаза 4: реорганизация `docs/api/`.** Отдельная задача. Жанр API остаётся самостоятельным (не сливается с `integrations/`). Решение по форме реорганизации — отдельный ADR при старте фазы 4. До того момента `docs/api/` остаётся как есть.

**Фаза 5: цикл ревью смигрированной документации.** Итеративная фаза. После фаз 1-4 у нас есть полная карта: домен в `docs/spec/`, integrations в `docs/spec/integrations/`, API в финальной форме. Ревью проходит по всей этой карте: формируются Q-N в журнале по неясным местам, разбираются, при необходимости создаются недостающие документы или уточняются существующие. Фаза заканчивается в состоянии **насыщения**: после очередного цикла ревью не появляются новые Q-N групп «вопросы, требующие решения» и «рабочая задача» (по ADR-0008 §4).

**Фаза 6: упразднение legacy.** Проверка, что все legacy-файлы `docs/domain/` помечены `[MIGRATED → ...]`. Проверка, что в `docs/spec/`, в коде, в CLAUDE.md нет ссылок на `docs/domain/`. Удаление `docs/domain/` целиком одним коммитом. Обновление CLAUDE.md и `docs/README.md` (иерархия источников упрощается: `docs/spec/` становится единственным первоуровневым). Техническое примечание в ADR-0003 о завершении миграции.

Фазы выполняются строго последовательно: каждая следующая стартует только после завершения предыдущей.

### 2. Восемь кластеров фазы 1

Кластеризация — из `migration-inventory-2026-05-15.md`, с добавлением C-NEW по результатам `model-catalog-2026-05-15.md`. Порядок выбран снизу-вверх по зависимостям, с группировкой однотипных моделей для батчинга.

**Кластер C-NEW: Exchange + Instrument (фундамент).**
- Legacy-источники: фрагменты `Справочник по доменным моделям.md`, `Статусы торговых сущностей.md`, `Расчёт индикаторов и рыночных данных.md`. Модели существуют как ссылки во множестве legacy-документов (через FK в Balance, Order, Position, IndicatorValue и др.), но отдельных model-документов в legacy нет — в spec заводятся впервые.
- Целевые документы: `docs/spec/models/core/Exchange.md`, `Instrument.md`.
- Зависимости: нет.
- Обоснование первенства: все остальные модели ссылаются на Exchange и Instrument через FK. Без них в spec — все последующие модели имеют забегающие ссылки на legacy.

**Кластер C4: Balance.**
- Legacy-источники: `Balance.md`, фрагменты `Статусы торговых сущностей.md`.
- Целевые: `docs/spec/models/core/Balance.md`.
- Зависимости: Exchange (C-NEW).
- Обоснование: после C-NEW первый «торговый» кластер. Маленький и почти самодостаточный, тестирует процедуру миграции на простом случае.

**Кластер C2: Order, AlgoOrder, Position (однотипные торговые сущности).**
- Legacy-источники: `Order.md`, `AlgoOrder.md`, `Position.md`, фрагменты `Статусы торговых сущностей.md`, `Сервисные команды.md §12` (дубль).
- Целевые: `docs/spec/models/core/Order.md`, `AlgoOrder.md`, `Position.md`.
- Зависимости: Exchange, Instrument (C-NEW). Через FK ссылаются на Deal — допустимая забегающая ссылка (см. §5).
- Обоснование: однотипные торговые сущности. Хорошо батчируются по общим паттернам (external snapshot, status resolver упоминаются как роли).

**Кластер C6: Market data.**
- Legacy-источники: `Расчёт индикаторов и рыночных данных.md`.
- Целевые: 4 model-документа (`IndicatorValue.md`, `MarketStructure.md`, `MarketPhase.md`, `MarketPriceData.md`) + 1 process (`market-data-jobs.md`).
- Зависимости: Instrument (C-NEW).
- Обоснование: 4 однотипных результата Job'ов — батчируются. Process-документ market-data-jobs — относительно изолирован.

**Кластер C5: Strategy.**
- Legacy-источники: `Strategy.md` (3080 строк, самый большой документ legacy), `Strategy API examples.md` (как сопровождающий материал, не самостоятельный документ).
- Целевые: `docs/spec/models/core/Strategy.md` (один большой документ; включает все strategy-config parts как вложенные модели, по ADR-0006 §1).
- Зависимости: Instrument (C-NEW). Ссылается на Deal — допустимая забегающая ссылка.
- Обоснование: к моменту C5 есть опыт миграции 7 model-документов однотипных кластеров. Strategy декомпозиция применяется по проверенному шаблону.

**Кластер C1: Deal + FSM + DealContext + DealActionState.**
- Legacy-источники: `Deal.md`, `Жизненный цикл сделки.md`, `FSM этапы сделки.md`.
- Целевые: `docs/spec/models/core/Deal.md`, `docs/spec/lifecycle/Deal.md`, `docs/spec/models/runtime/DealContext.md`, `DealActionState.md`. Возможны invariants — состав определяется по ходу миграции.
- Зависимости: Exchange, Instrument, Order, AlgoOrder, Position, Balance, Strategy, MarketData — все в spec к моменту C1.
- Обоснование: корневой агрегат и оркестратор. К этому моменту все зависимости описаны.

**Кластер C7: Calculator + Risk + Command (самый связный).**
- Legacy-источники: `Калькуляторы действий стратегии.md`, `Оценка рисков.md`, `Сервисные команды.md`.
- Целевые: `docs/spec/models/runtime/ServiceCommand.md`, `docs/spec/processes/strategy-action-calculator.md`, `risk-validator.md`, `service-command-executor.md`. Возможны invariants — состав определяется по ходу миграции.
- Зависимости: все остальные кластеры в spec.
- Обоснование: самый связный кластер фазы 1. К этому моменту вся остальная картина в spec, описывать на готовом фоне.

**Кластер C8: Audit (финал).**
- Legacy-источники: `Аудит и история исполнения.md`, фрагменты `Статусы торговых сущностей.md` (общие правила резолвера → `status-resolution.md`).
- Целевые: `docs/spec/processes/audit.md`, `docs/spec/invariants/status-resolution.md`, `anomaly-classification.md` (если ещё не создан в более раннем кластере).
- Зависимости: ServiceCommand (C7), все основные модели.
- Обоснование: естественный финал — описывает фиксацию истории всего, что описано ранее.

Грубая оценка по сессиям: C-NEW — 2-3, C4 — 2-3, C2 — 4-6 (батчинг), C6 — 4-5, C5 — 5-7 (большой документ), C1 — 5-7, C7 — 5-7, C8 — 3-4. Суммарно: ≈30-42 сессии. Это ориентир, может скорректироваться.

### 3. Единица миграции — двухуровневая

**Уровень кластера** — единица планирования и итогового состояния. Один кластер — один пункт в backlog как задача миграции. Кластер начат → кластер закрыт. По завершении кластера применяется финальная проверка — см. §8.

Маркеры `[MIGRATED]` ставятся **на каждый legacy-файл сразу после его полного разбора** — то есть когда всё содержание файла распределено по созданным spec-документам, и файл перестал быть источником правды. Ждать конца кластера не нужно. К моменту завершения кластера все legacy-файлы кластера должны быть помечены — это часть финальной проверки (§8).

Это согласуется с правилом из `working-with-claude.md`: тема переезжает в `docs/spec/` целиком, не «наполовину». Тема в данном случае — содержание legacy-файла; полный разбор файла — естественный момент маркировки.

**Уровень spec-документа** — единица одной сессии. Один spec-документ — одна сессия по скиллу `spec-document-workflow` (по ADR-0002). Кластер — серия таких сессий, скоординированных скиллом `spec-cluster-migration` (см. §10).

Соотношение: один legacy-файл может породить несколько spec-документов (например, `Deal.md` legacy → `models/core/Deal.md` + `lifecycle/Deal.md` + фрагмент в `models/runtime/DealContext.md`). Один spec-документ может собирать материал из нескольких legacy-файлов (например, `models/core/Order.md` собирает из `Order.md` + фрагментов `Статусы торговых сущностей.md`).

### 4. Пять hard gates готовности кластера

Перед стартом миграции кластера проверяется чек-лист из пяти hard gates. Если хотя бы один gate не пройден — кластер не стартует, открываются задачи на закрытие gap'ов.

**Gate 1: все зависимости кластера присутствуют в `docs/spec/`.**

Если кластер C-X использует модели, описанные в spec — соответствующие model-документы существуют. Допускается забегающая ссылка по правилу §5.

**Gate 2: карта legacy-источников зафиксирована.**

Известно, какие именно legacy-файлы и какие разделы внутри них — материал для этого кластера. Не «примерно где-то в processes/», а конкретно.

**Gate 3: карта целевых spec-документов зафиксирована.**

Известно, какие spec-документы создаются в рамках кластера. Полный список с указанием жанра (model core / runtime, lifecycle, process, invariant).

**Gate 4: критические концептуальные вопросы закрыты.**

Не все open-questions — только те, без которых **невозможно описать структуру** документов кластера. Знак критичности: ответ влияет на поля документов, не на пояснения. Поля — основа структуры, заглушками не закрываются.

Закрытие — это Q-N в журнале со статусом `Resolved` и заполненным `resolution`. Альтернатива: явное подтверждение, что критичных вопросов нет.

**Gate 5: проанализировано влияние на следующие кластеры в очереди.**

Составлен явный список ожидаемых влияний: что от решений, принимаемых в текущем кластере, потребуется при миграции следующих. Список — рабочий артефакт Этапа 1 миграции (рядом с картой источников и картой целевых документов).

Критерий прохождения gate: каждое влияние в списке либо неблокирующее (зафиксировано как ожидание, не требует действий до старта), либо закрыто — как Q-N со статусом `Resolved` или как явное решение, зафиксированное в чате/ADR.

Если в списке остаются блокирующие влияния без закрытия — gate не пройден, кластер не стартует.

Все пять gates обязательные. Soft-категории нет.

### 5. Допустимая забегающая ссылка

В ходе фазы 1 могут возникать ссылки на ещё не существующие spec-документы. Например, при миграции C2 (Order/AlgoOrder/Position) ссылки на Deal как контейнер — Deal в spec появится только в C1.

Забегающая ссылка **допустима**, если:

- Ссылается на **роль или будущий документ** в общих формулировках («контейнер Deal», «integration-документация биржи»).
- Не содержит inline-ссылку на конкретный путь, который ещё не существует.
- Не описывает структуру / контракт того, на что ссылается — только упоминает.

**Синтаксис.** Забегающая ссылка — прозаическое упоминание имени бизнес-объекта (или роли) в тексте, без markdown-link и без inline-code (`` ` ``). Примеры: «передаётся в контейнер Deal», «маппинг описан в integration-документации биржи», «инициируется Risk-валидатором». Не пример: «передаётся в `Deal`» — inline-code сигнализирует ссылку на класс/документ, её ставить нельзя до создания целевого документа.

**Идентификация при ревью.** Knowledge Curator определяет забегающие ссылки по списку имён бизнес-моделей из `docs/spec/MODELS.md`: упоминание известного имени в spec-документе кластера, целевой документ для которого ещё не создан, — забегающая ссылка. После миграции зависящего кластера ссылки уточняются на полноценные markdown-link.

После миграции зависящего кластера — забегающие ссылки **уточняются**. Knowledge Curator при ревью кластера проверяет наличие забегающих ссылок в созданных документах. При миграции кластера, описывающего цель забегающей ссылки, ссылка обновляется на конкретную (это часть Gate 1 проверки следующего кластера, который описывает ранее упоминаемые сущности).

Эта механика отличается от inline-ссылок на Q-N (ADR-0008): inline-ссылка на Q-N — это **открытый вопрос**; забегающая ссылка — это **зависимость от будущего документа**. Они не пересекаются по природе и обрабатываются разными механизмами.

### 6. Принцип качества миграции

Цель миграции — устранить накопление legacy-слоёв и привести документацию в единое состояние истины. Сокращения скоупа и снижение порога качества **не применяются**.

Допустимое ускорение — **батчинг однотипных документов** в рамках одной сессии:

- 4 market-data моделей в C6 (`IndicatorValue.md`, `MarketStructure.md`, `MarketPhase.md`, `MarketPriceData.md`) — единый паттерн результата Job, можно мигрировать пакетом за 1-2 сессии.
- 3 трейдинговых сущности в C2 (`Order.md`, `AlgoOrder.md`, `Position.md`) — общие паттерны (external snapshot, status resolver), частичный батчинг возможен.
- 4 mapping-документа фазы 2 (OKX) — шаблонные, идеальный батчинг.

Батчинг не означает **слияние** документов или **снижение индивидуального качества** каждого. Это только техника сокращения накладных расходов на сессию (одна установочная диалог, одна передача в Claude Code, один цикл ревью).

**Не допускается** в рамках миграции:

- Перенос open-questions в журнал без классификации (по ADR-0008, классификация обязательна при добавлении).
- Упрощение реструктуризации legacy («оставить структуру как есть, поменять только заголовки»).
- Пропуск ревью каждого spec-документа в IDEA.
- Пакетный перевод вопросов в `Resolved` без обоснования в поле `resolution`.

### 7. Процедура работы с open-questions при миграции

Применение ADR-0008 при миграции каждого документа из `docs/domain/`:

1. **Этап выписки.** Claude Code при миграции legacy-документа выписывает все встроенные open questions из исходного документа в structured отчёт с контекстом вокруг каждого. Не классифицирует.

2. **Сессия классификации в чате.** Каждый вопрос получает Q-N и заводится в журнал. Классификация присваивается по ADR-0008 §4 (одно из 7 значений).

3. **Исключение для очевидных случаев.** Если вопрос буквально отвечается уже принятым ADR / разделом spec — заводится сразу со статусом `Resolved`, classification `obsolete-by-decision`, идёт в раздел «Closed» с заполненным `resolution`. Это единственный случай, когда вопрос не задерживается в `Added`.

4. **Inline-ссылки в новых spec-документах.** Если описание неполно из-за нерешённого вопроса — в spec-документе добавляется короткая ссылка «см. Q-NNN». Сама формулировка вопроса — только в журнале (по ADR-0008 §6).

5. **Commit миграции.** Содержит ссылку на новые Q-N: «Open-questions из <legacy-файл> перенесены в журнал: Q-NNN..Q-MMM».

6. **Knowledge Curator контроль.** Knowledge Curator при ревью проверяет, что все open-questions из исходного документа перенесены в журнал. Механизм проверки — сверка с structured-отчётом Этапа 1 миграции (см. чек-лист в скилле `spec-cluster-migration`, Этап 4). Иначе миграция не считается завершённой.

7. **Ревью групп Q-N — отдельная сессия.** Сами разборы концептуальных вопросов и подтверждение устаревания — не в составе миграционной сессии. Это отдельная сессия (или серия), задача на ревью заводится в backlog с перечислением целевых Q-N.

### 8. Завершение кластера

При завершении каждого кластера выполняется финальная проверка:

- Все legacy-файлы кластера помечены `[MIGRATED → docs/spec/...]` на первой строке с указанием новой локации.
- Все целевые spec-документы созданы и приняты (прошли чек-лист Сценария 7 из playbook).
- `docs/spec/MODELS.md` обновлён: заглушки для бизнес-моделей кластера заменены ссылками на созданные model-документы.
- `.claude/planning/migration-tracker.md` обновлён: кластер помечен как завершённый, отмечены ссылки на коммиты и созданные spec-документы.
- Журнал open-questions пополнен (если в ходе возникли вопросы): новые Q-N имеют статус, классификацию, контекст.
- Inline-ссылки «см. Q-NNN» в новых spec-документах оправданы открытыми вопросами в журнале (не «забыли»).
- Забегающие ссылки помечены или зафиксированы для уточнения при миграции зависящего кластера.
- Knowledge Curator подтвердил завершённость: связные обновления не пропущены.
- Backlog-пункт кластера переведён в «Закрытые» с датой и ссылками на commits.

Только после прохождения всех пунктов кластер считается завершённым.

### 9. Три артефакта работы с терминологией и прогрессом миграции

Зафиксированное в более ранних черновиках ADR-0009 решение «единый `docs/GLOSSARY.md` с тремя функциями» пересмотрено до принятия пакета. Функции разделены на три артефакта с разной природой и разной судьбой после фазы 1:

**1. `docs/conventions/terminology.md` — терминологические соглашения.**

Содержит правила выбора слов при письме на проекте: «доменная модель», «aggregate root», «core vs runtime», «хранимая модель» и подобные. Не зависит от миграции — создаётся вне фаз, в составе Этапа 4. Соседствует с CodeStyle.md и TechRadar.md (по жанру — convention о написании текста проекта, аналогично convention о написании кода).

Стартовое содержание — ~4 соглашения, накопленные в принципах концепции и в пакете ADR. Растёт по мере введения новых соглашений проектом.

**2. `docs/spec/MODELS.md` — реестр канонических имён моделей.**

Содержит ~16 entries — имена 13 core + 3 runtime моделей со ссылками на model-документы. Стартует с заглушками в начале фазы 1; заглушки заменяются ссылками по мере миграции кластеров.

Функции:

- Навигационная точка входа в `docs/spec/`.
- Источник списка имён для идентификации забегающих ссылок Knowledge Curator'ом (см. §6).
- Прогресс миграции по моделям виден напрямую через состояние заглушек.

Расположение и роль зафиксированы в ADR-0007 §3.

**3. `.claude/planning/migration-tracker.md` — чеклист прогресса миграции.**

Рабочий артефакт процесса (по ADR-0003 — в `.claude/`, не в `docs/`). Содержит:

- Список 8 кластеров фазы 1 со статусами (planned / in-progress / done).
- Список 6 сквозных концепций (kill-switch, orphan, freshness, reconcile, FSM сделки, anomaly) со ссылками на целевые spec-документы (invariant / process / lifecycle), создаваемые при миграции соответствующих кластеров.
- Ссылки на коммиты завершения кластеров.

Соседствует с backlog.md (оба про планирование). Живёт в фазе 1 активно; в фазах 2-5 — обновляется при работе с соответствующими кластерами. Дальнейшая судьба пересматривается по завершении фазы 5 (отдельный backlog-пункт).

**Сквозные концепции системы.**

Kill-switch, orphan, freshness, reconcile, FSM сделки, anomaly — получают собственные spec-документы по жанрам (invariant / process / lifecycle) при миграции соответствующих кластеров. Отдельного «глоссария концепций» проект не создаёт; в migration-tracker.md они присутствуют только как пункты чеклиста с ссылкой на целевой spec-документ.

**Правило «новый термин — куда фиксировать»:**

- имя бизнес-модели (Deal, Order, Position, ServiceCommand и подобные) → `docs/spec/MODELS.md` + соответствующий model-документ;
- терминологическое соглашение («как правильно писать») → `docs/conventions/terminology.md`;
- сквозная концепция (kill-switch, freshness, orphan и подобные) → соответствующий invariant/process/lifecycle-документ в `docs/spec/`. Отдельного глоссария концепций нет.

### 10. Скилл `spec-cluster-migration` и Сценарий 9

**Скилл `spec-cluster-migration`** — операционная процедура миграции кластера. Создаётся в `.claude/skills/spec-cluster-migration/SKILL.md`.

Структура скилла на верхнем уровне:

- **Этап 1: первоначальный анализ.** Скилл проводит разбор кластера в чате: какие legacy-источники, какие целевые spec-документы, какие зависимости (с проверкой их присутствия в spec), какие критические open-questions. Результат — рабочий артефакт сессии (например, в `.claude/notes/migration-cluster-<id>-readiness.md`), не идёт в Project Knowledge.

- **Этап 2: проверка готовности.** На основе результатов анализа — проверка 5 hard gates (см. §4). Если gate не пройден — открывается задача на закрытие, кластер не стартует.

- **Этап 3: миграция.** Последовательность создания spec-документов в кластере. Внутрикластерные связные обновления. Применение скилла `spec-document-workflow` для каждого документа. Применение ADR-0008 для open-questions (см. §7).

- **Этап 4: финализация.** Финальная проверка (см. §8). Маркеры `[MIGRATED]`. Обновление `docs/spec/MODELS.md` (заглушки бизнес-моделей кластера → ссылки на созданные model-документы). Обновление `.claude/planning/migration-tracker.md` (отметка завершения кластера, ссылки на spec-документы и коммиты). Закрытие backlog-пункта кластера. Сверка перенесённых Q-N со structured-отчётом Этапа 1: каждый найденный open-question получил Q-N в журнале.

Полный текст скилла создаётся после принятия ADR-0009 как отдельный артефакт.

**Сценарий 9 в playbook** — короткий указатель для человека.

Создаётся в `.claude/flow/playbook.md` как Сценарий 9 «Запуск миграции кластера». Структура аналогична другим сценариям: когда, цепочка действий (открыть backlog-пункт, активировать скилл `spec-cluster-migration`, далее по скиллу), подводные камни.

Сценарий 9 — указатель **где смотреть процедуру** (в скилле). Сама процедура — не дублируется в playbook.

**Backlog-пункт кластера** — содержит только короткую формулировку задачи:

```text
Кластер C2: миграция Order, AlgoOrder, Position.
```

Никаких чек-листов, источников, зависимостей в самой задаче. Все детали формируются скиллом на Этапе 1 как рабочий артефакт сессии.

## Alternatives

**По единице миграции:**

- *Вариант: файл-за-файлом.* Отброшен. Один legacy-файл содержит материал для нескольких spec-документов (например, `Deal.md` legacy → core/Deal.md + lifecycle/Deal.md + фрагмент в runtime/DealContext.md). Файл закрыт, spec-документы не закрыты. Маркеры `[MIGRATED]` ставятся преждевременно.
- *Вариант: spec-документ-за-документом.* Отброшен в чистом виде. Legacy-файл фигурирует в нескольких spec-документах. Долго и непрозрачно, какой статус у legacy.
- *Выбран: двухуровневая механика (кластер + spec-документ).*

**По порядку кластеров:**

- *Вариант: от корня (Deal сначала, дальше остальное).* Отброшен. C1 требует все остальные кластеры как контекст. Описать Deal без Order/Position/Strategy в spec — писать в вакууме.
- *Вариант: от простого к сложному без учёта зависимостей.* Отброшен. Размер слабо коррелирует со связностью. Опыт миграции маленького Balance не переносится на сложный Strategy так же эффективно, как опыт миграции однотипных Order/AlgoOrder/Position.
- *Выбран: снизу-вверх по зависимостям с группировкой однотипных для батчинга.*

**По форме закрепления критериев готовности:**

- *Вариант: чек-лист в backlog-пункте каждого кластера.* Отброшен. Дублирование в 8 пунктах. Backlog становится местом для процедуры, не для задач.
- *Вариант: чек-лист только в ADR.* Отброшен. ADR — статичный документ, не активный инструмент. Чек-лист в ADR без операционализации в скилле — будет пропускаться.
- *Вариант: чек-лист только в playbook.* Отброшен. Playbook — памятка для человека. Без скилла Claude не «увидит» чек-лист автоматически.
- *Выбран: gates в скилле как операционная процедура, короткий указатель в playbook (Сценарий 9), backlog содержит только формулировку задачи, ADR содержит формулировки gates как источник истины.*

**По числу ADR на эту работу:**

- *Вариант: один большой ADR на всю стратегию (включая принципы, структуру, журнал, миграционный план).* Отброшен. ADR должны быть «одно решение — один документ». Здесь — десятки решений, что разрушает принцип.
- *Вариант: много мелких ADR (отдельный на каждое решение).* Отброшен. Взаимозависимости. При корректировке одного — нужно править несколько ADR (append-only ограничивает).
- *Выбран: четыре связанных ADR (0006, 0007, 0008, 0009). Структурные решения (0006, 0007, 0008) — постоянные, переживут миграцию. Стратегический ADR (0009) — план фазы 1, со временем теряет актуальность.*

**По расщеплению функций глоссария на три артефакта:**

- Единый `docs/GLOSSARY.md` с тремя функциями (соглашения + реестр имён + чеклист миграции). Отброшен: три разные функции при разной природе дают концептуальную неопрятность; после миграции непонятно, что делать с файлом.
- Расщепить на два артефакта (соглашения отдельно, реестр + чеклист вместе). Отброшен: реестр имён — постоянный навигационный артефакт, чеклист миграции — временный рабочий артефакт. Объединение оставляет ту же концептуальную неопрятность.
- *Выбран: три артефакта с разной природой и судьбой (см. §9).*

## Consequences

### Артефакты, которые создаются после принятия ADR-0009

После принятия пакета ADR-0006..0009 выполняются следующие действия:

- `.claude/skills/spec-cluster-migration/SKILL.md` — скилл миграции кластера (структура из §10).
- `.claude/flow/playbook.md` — добавляется Сценарий 9 «Запуск миграции кластера».
- `docs/conventions/terminology.md` — создаётся в Этапе 4 (до старта фазы 1) с ~4 стартовыми терминологическими соглашениями.
- `docs/spec/MODELS.md` — создаётся в начале фазы 1 со стартовыми заглушками (13 core + 3 runtime моделей).
- `.claude/planning/migration-tracker.md` — создаётся в начале фазы 1 с 8 кластерами и 6 сквозными концепциями.
- `.claude/questions/open-questions.md` — пустой журнал по ADR-0008 (без entry на старте; первые Q-N появятся при миграции первого кластера).
- `.claude/templates/documents/open-questions-journal.md` — шаблон (по ADR-0008).
- `.claude/skills/open-questions-workflow/SKILL.md` — скилл (по ADR-0008).

Обновления существующих файлов:

- `.claude/working-with-claude.md` — упоминание журнала, скилла миграции, новых правил.
- `CLAUDE.md` — навигационные обновления.

- Пункт: «Привести `docs/spec/models/AnomalyReport.md` к стандарту ADR-0002» (существующий пункт, перемещается в фазу 1 как часть кластера C-NEW или C1 — решается при миграции).

- Пункт: «Фаза 3: обработка корневого `docs/domain/Открытые вопросы по движку.md`».
- Пункт: «Фаза 4: реорганизация `docs/api/` — отдельный ADR при старте».
- Пункт: «Фаза 5: цикл ревью смигрированной документации».
- Пункт: «Фаза 6: упразднение `docs/domain/`».

### Грубая оценка объёма работы фазы 1

- Сессий миграции: ≈30-42 (см. §2). Грубая, может скорректироваться.
- Человеческого времени: ≈20-50 часов суммарно.
- Календарно: ≈2-5 недель при темпе 2-3 часа в день; ≈2-3 месяца при темпе 1 час в день.
- Что входит в оценку: сессии миграции + сессии классификации open-questions + ревью.
- Что НЕ входит: фазы 2-6 (отдельно).

### Что выходит за рамки фазы 1

- Миграция OKX-маппингов (фаза 2).
- Обработка корневого backlog движка (фаза 3).
- Реорганизация `docs/api/` (фаза 4).
- Цикл ревью с заполнением gap'ов (фаза 5).
- Упразднение legacy (фаза 6).

### Связь с другими ADR

- **ADR-0002** (стандарт документа). Сохраняется в силе. Применяется к каждому создаваемому spec-документу. Чек-лист сценария 7 уточняется (правило inline-ссылок «см. Q-NNN» — см. ADR-0008).
- **ADR-0003** (разделение `docs/` и `.claude/`). Сохраняется в силе. Новые артефакты (скилл миграции, журнал) живут в `.claude/` по правилам ADR-0003.
- **ADR-0006** (принципы спецификации) — источник истины по применению критериев при миграции каждого документа.
- **ADR-0007** (структура `docs/spec/`) — источник истины по расположению создаваемых документов и финальной структуре.
- **ADR-0008** (журнал open-questions) — источник истины по работе с вопросами при миграции.
