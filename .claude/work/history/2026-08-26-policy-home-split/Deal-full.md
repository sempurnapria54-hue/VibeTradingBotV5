# Deal

## На какой вопрос отвечает этот файл

Что это за торговая модель `Deal` (lifecycle root и runtime graph
сделки): структура, енумы, runtime graph, итоговый PnL.

Статусы и переходы — в `docs/lifecycles/Deal.md`.

## Назначение

`Deal` — lifecycle root и runtime graph торговой сделки. Фиксирует,
что система начала сопровождать торговый сценарий по конкретному
`Instrument`, по pinned `StrategyDetail`, в ожидаемом направлении,
с FSM-статусом, причиной создания, причиной завершения и итоговым
profit/loss.

`Deal` **не** является биржевой сущностью: нет external id, нет
external status, OKX mapping-документ не нужен. `Deal` **не**
отвечает за: сырые exchange responses, историю команд, историю
изменений сущностей, подробный entry context, risk-check details,
свежие market/calculation data, raw fills archive, полную финансовую
отчётность.

Java-класс `com.example.tradingbot.domain.model.aggregate.deal.Deal`,
расширяет `Auditable`.

| `entryStepType` | `EntryStepType` | Тип entry-step (`ENTRY`/`GRID_ENTRY`/null; не управляет FSM). |
| `shutdownReason` | `ShutdownReason` | Причина graceful shutdown / controlled close (если запущен). Не заменяет `closeReason`. |
| `closeReason` | `CloseReason` | Итоговая бизнес-причина завершения. |
| `plannedRiskAmount` | `BigDecimal` | **Заявленный плановый риск сделки (`R`)** — **сумма** плановых рисков её **живых и исполнившихся** ног входа (`Order.plannedRiskAmount`), каждый посчитан при постановке своей ноги; снятые ноги в сумму не входят. **Знаменатель R-мультипликатора** (см. §«Плановый риск», §«Предикат отбора слагаемых»). Не write-once: производная проекция ног, пересчитывается целиком при изменении их состава или состояния. |
| `incurredRiskAmount` | `BigDecimal` | **Взятый риск сделки (на входе)** — сколько из заявленного действительно встало под удар: Σ по ногам входа `plannedRiskAmount_i × (accumulatedFillSize_i / plannedSizeContracts_i)` (H3 `DOCS_CHECK_16`). Не знаменатель R-мультипликатора — измеритель разрыва «заявлено ↔ взято». **Частичным выходом не уменьшается** (см. §«Взятый риск»). Не write-once, производная проекция. |
| `currentRiskAmount` | `BigDecimal` | **Неотработанная доля взятого на входе риска** — какая часть взятого ещё не отыграна выходом: `incurredRiskAmount × (Position.externalSize / Σ accumulatedFillSize_i)`. Уменьшается частичным выходом, при полном — ноль. **Риском «под ударом сейчас» не является** — уровня актуального стопа формула не содержит (решение держателя П10, вариант 1). Потребитель — **сопровождение**, не отчёт (решение держателя, `GAPS_CLOSE_16`). Не write-once, производная проекция. |
| `protectionRelievedRiskAmount` | `BigDecimal` | **Риск, снятый защитой** — насколько актуальный стоп уменьшил взятый риск: `incurredRiskAmount −` риск при **актуальном** уровне стопа. Пересчитывает писатель защиты (`CreateAlgoOrderExecutor` / place-нога `REPLACE`) своей транзакцией. Заведено решением держателя П10 (вариант 3) — величину «риск под ударом» несёт эта пара чисел, а не `currentRiskAmount` в одиночку. Не write-once, производная проекция. |
| `plannedRiskCurrency` | `String` | Валюта планового риска — **одна на все четыре числа** (та же, что у `resultProfitCurrency` — иначе отношение не считается). Источник значения у писателя — **расчётная валюта инструмента** (`Instrument.externalSettlementCurrency`, `docs/decisions/instrument-currencies-home.md`); у всех ног сделки она одна, поэтому суммирование валюту не смешивает. |
| `resultProfit` | `BigDecimal` | Итоговый PnL (см. ниже). |
| `resultProfitCurrency` | `String` | Валюта результата (для `ETH-USDT-SWAP` обычно `USDT`). Источник — **расчётная валюта инструмента** (тот же дом, что у `plannedRiskCurrency`); валюта, пришедшая от биржи, — проверяемый признак, не источник (§«Валюта результата: один авторитет»). |
| `billsWindowBegin` | `OffsetDateTime` | **Нижняя граница окна линковки bills** — собственное поле сделки; пишет **единственный** писатель `SubmitOrderExecutor` (`Order.externalCreatedAt` первой отправленной ноги, H9 `DOCS_CHECK_16`; см. §«Окно линковки bills»). |
| `billsWindowEnd` | `OffsetDateTime` | **Верхняя граница окна линковки bills** — заполняет наблюдатель факта закрытия (вторая нога `REFRESH_POSITION_COMMAND`). Пусто = факт закрытия не добыт → привязка ждёт. |
| `closeOutcome` | `CloseOutcome` | **Торговый исход закрытия** (`NORMAL_EXIT` / `LIQUIDATION` / `FORCED_REDUCTION` / `UNDETERMINED`) — признак отбора для отчёта. Пишет финализация (штатная и аварийная) из `Position.externalCloseType`; техническая тропа FSM на значение не влияет. Пусто = признак **неприменим** (тропа закрытия без входа); `UNDETERMINED` = операнд не добыт (§«Признаки отбора для отчёта»). |
| `reconciliationStatus` | `ReconciliationStatus` | **Статус сверки разбивки** (`NOT_RUN` / `MATCHED` / `MISMATCHED`) — признак отбора для отчёта. Свойство числа, а не членства в популяции: сделка остаётся в популяции при любом значении. Пусто = признак неприменим (тропа закрытия без входа). |
| `breakdownIncomplete` | `BreakdownCompleteness` | **Полнота разбивки** (`COMPLETE` / `INCOMPLETE_BY_WINDOW` / `NOT_ASSESSED`) — сделка длиннее окна доступности движений выбранного конвейера добычи. Отделяет «сверка звенит по дефекту» от «звенит по построению»; `NOT_ASSESSED` = сравнение не выполнялось, операнды не добыты. Пусто = признак неприменим (тропа закрытия без входа). |
| `riskBenchmarkAvailability` | `RiskBenchmarkAvailability` | **Почему знаменатель `R` пуст или непуст** (`AVAILABLE` / `NOT_APPLICABLE` / `MISSING`) — признак отбора для отчёта, разводит две природы пустоты `plannedRiskAmount` (H13 `DOCS_CHECK_16`). Пишут финализация (штатная и аварийная) и — для `NOT_APPLICABLE` на тропах закрытия без входа — `MarkDealClosedExecutor` (решение держателя П9); пусто до терминала. |
| `orders` | `List<Order>` | Ordinary orders сделки (attached protection — внутри `Order`). |
| `algoOrders` | `List<AlgoOrder>` | Standalone algo-orders сделки. |
| `position` | `Position` | Текущая позиция (≤1 на `Deal`). |

## Енумы

- **`Status`**: `PRECHECK`, `ENTRY_SUBMITTED`, `ENTRY_FINALIZED`,
  `PROTECTION_SWITCHED`, `MANAGING`, `EXIT_PENDING`, `CLOSED`,
  `ERROR`, `EMERGENCY_CLOSED`. Описывает бизнес-этап сделки, **не**
  статус `Order`/`AlgoOrder`/`Position`/command execution/exchange
  ACK. Значения, группы, переходы — в `docs/lifecycles/Deal.md`.
- **`EntryReason`**: `STRATEGY` (создана `EntryScannerJob` по
  условиям), `MANUAL`, `RECOVERY` (восстановление существующего
  runtime risk), `UNKNOWN` (fallback, не для normal flow).
- **`EntryStepType`**: `ENTRY`, `GRID_ENTRY` (или null, если создана
  не через strategy entry-step). Комбинации с `entryReason` — в
  lifecycle/справке. Подробный entry context — в аудите, не в `Deal`.
- **`ShutdownReason`**: `STRATEGY_DELETED`, `MARKET_DATA_EXPIRED`
  (только если policy решила завершать сделку controlled-exit, не
  при любом stale), `MANUAL_STOP`, `RISK_POLICY`, `EXCHANGE_HOLD`,
  `UNKNOWN`. Заполняется только при реальном запуске graceful
  shutdown (см. lifecycle).
- **`CloseReason`**: `ENTRY_CONDITION_EXPIRED` (candidate закрыт в
  PRECHECK до live risk), `STRATEGY_EXIT`, `TAKE_PROFIT`,
  `STOP_LOSS` (включая fixed и trailing SL; конкретный механизм — в
  `Order`/`AlgoOrder`/`DealActionState`/audit), `TIME_STOP`,
  `RISK_CONTROL` (штатное risk-control завершение, включая risk-block
  в PRECHECK), `MANUAL_CLOSE`, `EMERGENCY_CLOSE` (только для
  `EMERGENCY_CLOSED`), `UNKNOWN`. Не используются:
  `ENTRY_RISK_BLOCKED`, `TRAILING_STOP`. Описывает бизнес-причину, не
  технический механизм закрытия позиции.

- **`CloseOutcome`** (шаг 7, узел F `DOCS_CHECK_12`) — **торговый** исход
  закрытия, ось отбора для отчёта:
  - `NORMAL_EXIT` — позицию закрыли мы (стоп, тейк, стратегийный выход,
    ручное закрытие) либо биржевое событие вне ликвидационного контура
    (`externalCloseType` `1`–`2`);
  - `LIQUIDATION` — позицию принудительно закрыла биржа по марже
    (`3`–`4`);
  - `FORCED_REDUCTION` — принудительное сокращение (ADL) (`5`–`6`);
  - `UNDETERMINED` — исход **не определён: операнд не добыт** (H2
    `GAPS_CLOSE_13`; половина «пришёл вне перечня `1..6`» снята H5
    `DOCS_CHECK_15` — такая запись не проходит границу интеграции и до
    признака не доезжает). Значение, а не пустота:
    сделка остаётся в популяции и счётна отдельной корзиной. Пустой
    `closeOutcome` означает другое — признак **неприменим** (тропа
    закрытия без входа); см. §«Признаки отбора для отчёта».

  Отличается от `CloseReason` намеренно: `closeReason` — **бизнес-причина**
  завершения сделки (и она не имеет значения под ликвидацию), `closeOutcome`
  — **рыночный факт** того, кто и почему закрыл позицию. Смешивать их нельзя:
  на `closeReason` фильтровать нечем — `ENTRY_CONDITION_EXPIRED`
  переиспользована двумя тропами, а ликвидация в нём не выражается вовсе.
- **`ReconciliationStatus`** (шаг 7, узел F `DOCS_CHECK_12`) — исход
  контроля целостности разбивки:
  - `NOT_RUN` — сверка **не была обязана** и не выполнялась: ветвь
    аварийного терминала с **пустым окном движений** (запись закрытия не
    добыта, H21 `DOCS_CHECK_14` — на ветви с добытой записью сверка
    гоняется). Ветка «пустой операнд epsilon» **снята** (H2
    `DOCS_CHECK_15`): при наступившей обязанности нерезолвимый операнд
    допуска уводит сделку ошибочной тропой, а не даёт `NOT_RUN` с
    успешным терминалом — иначе значение снова означало бы и «не были
    обязаны», и «были обязаны, операнда не нашлось»;
  - `MATCHED` — **общее расхождение по сделке** (`Δ = Σ|Δᵢ|` по четырём
    парам) в пределах epsilon — допуск один на сделку, пер-парных якорей
    нет (H9 `GAPS_CLOSE_13`; пер-парная редакция «все четыре пары сошлись
    / хотя бы одна разошлась» снята H4 `DOCS_CHECK_14`: это другой,
    более слабый предикат — `Σ|Δᵢ| ≥ max|Δᵢ|`, и он давал `MATCHED`
    сделке с четырьмя расхождениями по 40 % допуска каждое);
  - `MISMATCHED` — общее расхождение сверх epsilon; **какие** пары
    разошлись — состав отчёта, не предиката;
  **Третьего значения нет — решение держателя** (`GAPS_CLOSE_16`). H6
  `DOCS_CHECK_16` предлагал завести `OPERAND_MISSING` — «сверка была
  обязана, операнд допуска не резолвился»; предложение **отклонено**, и
  ратифицированная клауза H10 `DOCS_CHECK_14` остаётся в силе: различение
  несёт **терминальный статус** (`CLOSED` ↔ `EMERGENCY_CLOSED`), а не
  значение признака и не новая колонка.

  > **Цена решения названа и с позицией С3 она уменьшилась.** Довод H6 был
  > не пуст: терминал различает исход только на паре терминалов и
  > **вырождается внутри `EMERGENCY_CLOSED`**, где сверка тоже бывает
  > обязана (ветвь (a), H21 `DOCS_CHECK_14`), а статус константен. Случая
  > «были обязаны, операнда не нашлось» **больше не существует**: ветка
  > снята вместе с журнальным кодом (решение держателя, позиция С3
  > `GAPS_CLOSE_16`), нерезолвимый операнд до финализатора не доезжает —
  > его ловит детектирующий контур отказом операции. Поэтому `NOT_RUN`
  > внутри `EMERGENCY_CLOSED` несёт **один** смысл: сверка не была обязана.
- **`RiskBenchmarkAvailability`** (шаг 7, H13 `DOCS_CHECK_16`, решение
  пользователя) — **почему знаменатель `R` пуст или непуст**, поле
  `riskBenchmarkAvailability`:
  - `AVAILABLE` — `plannedRiskAmount` непуст: знаменатель определён;
  - `NOT_APPLICABLE` — входа **не было по построению**: три тропы закрытия
    без входа (`PRECHECK`-истечение, риск-блок, отмена неисполненного
    входа без движения средств — `docs/rules/deal-without-operations.md`).
    Нормальная популяция, аномалией не является;
  - `MISSING` — **операции были, знаменателя нет**: ни одна нога входа
    планового риска не несёт при состоявшихся операциях (позиция создана
    вне приложения). Аномалия; сопровождается `AnomalyReport`
    `PLANNED_RISK_MISSING` (§«Операции были, а `R` пуст»).

  Признак **разводит две природы пустоты** `plannedRiskAmount`, которые до
  этого склеивались в одном фильтре, — тем же ходом, каким шаг развёл
  «не проверяли» и «проверили, всё в порядке» у трёх соседних признаков.

  **Писателей три, и третий — исполнитель закрытия** (H8 `DOCS_CHECK_17`,
  решение держателя П9, вариант A): `AVAILABLE` / `MISSING` пишут два
  финализатора, **`NOT_APPLICABLE` — `MarkDealClosedExecutor` той же
  транзакцией**, на тропах закрытия без входа (финализатор выхода там не
  работает, и писателя у значения не было). Ветка `NOT_APPLICABLE` у
  финализатора выхода **снята как недостижимая**. Пусто — до терминала.

  **Это выводит признак из-под ратифицированного клейма** «признаки на
  тропах закрытия без входа не пишутся — это их значение» (H3
  `GAPS_CLOSE_13`): клейм остаётся верным для `closeOutcome`,
  `reconciliationStatus` и `breakdownIncomplete`, а
  `riskBenchmarkAvailability` из-под него выведен явно — иначе популяция
  «входа не было по построению» перестаёт быть адресуемой значением одного
  поля, ради чего признак и заводился.
- **`BreakdownCompleteness`** (шаг 7, H4 `GAPS_CLOSE_13`) — полнота
  разбивки, поле `breakdownIncomplete`:
  - `COMPLETE` — **возраст нижней границы окна на момент добычи** не
    превышает глубины доступности движений (операнд — H20
    `DOCS_CHECK_15`);
  - `INCOMPLETE_BY_WINDOW` — превышает: часть строк недобываема
    выбранным конвейером добычи;
  - `NOT_ASSESSED` — сравнение **не выполнялось**: нижняя граница окна не
    добыта либо добыча движений не выполнялась. Не то же, что
    `COMPLETE`: «не проверяли» и «проверили, всё в порядке» разведены
    (`docs/rules/absent-value-semantics.md`).

`entryReason`/`entryStepType` не управляют FSM. `shutdownReason`
(почему перевели в graceful shutdown — не значит, что закрылась) и
`closeReason` (итоговая причина завершения) — разные поля.

## Итоговый PnL (resultProfit)

Первоисточник правила — здесь (`Deal` владеет полем,
`.claude/decisions/rule-source-of-truth.md`); источник данных числа и
разбивки — `docs/decisions/result-profit-source.md`:

- **Число** `resultProfit` = **net realized P&L**, берётся **готовым** из
  positions-history (`realizedPnl = pnl + fee + fundingFee + liqPenalty`,
  посчитан биржей), **плюс cross-ccy-слагаемое** Σ(`amount` ×
  `appliedRate`) по строкам `DealCashFlow`, у которых **`rateStatus =
  APPLIED` и тип вне списка исключений биржи и категория — экономическая
  (не `OTHER`)** — предикат области **конъюнктивный**, полный, не
  сокращение (H11 `GAPS_CLOSE_13`; протянут в место истины H2
  `DOCS_CHECK_14` — редакция с одним `rateStatus` пускала в числитель `R`
  любое прилинкованное движение в чужой валюте вне экономики сделки, и
  такие строки не ловятся ни одной парой сверки; редакция «по строкам
  чужой `ccy`» снята ещё раньше H9 `DOCS_CHECK_11`: она захватывает
  строки с пустым `appliedRate` — `RATE_UNAVAILABLE` /
  `SETTLE_CURRENCY_UNAVAILABLE` — и обнуляет всю сумму, а на чистой тропе
  `CLOSED` число обязано быть непустым). Биржевой
  net считается в settle-ccy и издержку вне неё не содержит — без
  слагаемого число завышалось бы молча; реш.5
  `docs/decisions/pnl-finalization-mechanics.md`,
  `docs/models/mapping/DealCashFlow.md` §«Число — в settle-ccy»). **Не**
  через fills/`TradeFill` и **не** через
  `BalanceContainer` diff. `REFRESH_BALANCE_COMMAND` после выхода нужен для
  актуального account snapshot, не для PnL сделки.
- **Категорийная разбивка** (торговая комиссия / funding / rebate /
  ликвидационный штраф) — из bills (`DealCashFlow`); сумма bills-flows
  сверяется с net из positions-history (контроль целостности). В `Deal`
  разбивка не хранится (см. ниже).
- **Формула одна на обе тропы** (H12 `DOCS_CHECK_10`). `EMERGENCY_CLOSED`
  best-effort **по доступности** числа, а не по его составу: когда net
  доступен, аварийный терминал применяет то же cross-ccy-слагаемое
  (`docs/components/MarkDealEmergencyClosedExecutor.md` §«Состав числа»).
  Иначе отсутствие слагаемого давало бы **направленное смещение вверх**
  ровно в той корзине, которая и так смещена.
- Для **чистого** terminal `CLOSED` `resultProfit` и
  `resultProfitCurrency` обязательны; для аварийного `EMERGENCY_CLOSED`
  число — **best-effort**: если net доступен — оно считается **по той же
  формуле** (net + cross-ccy-слагаемое, см. пункт выше), иначе
  `resultProfit = null` c маркером «неисчислимо» (**не ноль**;
  `docs/lifecycles/Deal.md` §«Терминальный контракт финализации»; DEAL-Q2
  закрыт). На `EMERGENCY_CLOSED` `null` = «число не достать» (отличимо от
  нуля). Формулировка «фактический realized net» здесь **снята** (H18
  `DOCS_CHECK_11`): best-effort относится к доступности числа, не к его
  составу, и прежняя редакция читалась как «на аварийной тропе слагаемого
  нет».
- `resultProfit = 0` допустим только как **результат расчёта** (net вышел
  нулевым), **не** как молчаливый fallback при ошибке. Если временно нельзя
  посчитать — добыча и финализация ретраятся бюджетом своих **системных
  действий** (`REFRESH_DEAL_CONTEXT_ACTION` / `FINALIZE_DEAL_EXIT_ACTION`,
  `docs/models/domain/other/DealActionState.md`); при исчерпании сделка
  уходит ошибочной тропой к терминалу — всегда доходит до терминала, не
  зависает живым риском (**DEAL-Q2, закрыт**, `docs/lifecycles/Deal.md`
  §«Терминальный контракт финализации»).
- **Расчёт и запись (N7).** Число вычисляет и **пишет прямо на `Deal`**
  `FinalizeDealExitExecutor` (net из **`Position.externalRealizedProfit`** —
  положения закрытия, приземлённого второй ногой `REFRESH_POSITION_COMMAND`,
  — плюс разбивка из `DealCashFlow` + сверка; в одной транзакции с
  продвижением своего исполнения — durable-носитель числа = само поле
  `Deal`, рестарт-safe). `MarkDealClosedExecutor` **ассертит** непустоту и
  ставит терминал `CLOSED` (число не пишет). Step-6 писал
  интерим-placeholder `ZERO` (граница 6 ↔ 7); шаг 7 его снял (реальный
  net). Механика — `docs/decisions/pnl-finalization-mechanics.md` реш.2.

## Валюта результата: один авторитет

**Авторитет — расчётная валюта инструмента** (H10 `DOCS_CHECK_10`, решение
пользователя; **дом — поля самого `Instrument`**
(`externalSettlementCurrency`), H6 `DOCS_CHECK_11`,
`docs/decisions/instrument-currencies-home.md`; прежняя атрибуция дома
JSONB-навесу `InstrumentExternalRules` **снята** — вариант «дом — навес»
выписан в §Альтернативы решения и отвергнут). Прежде носителей было
названо два — она же и `Position.externalResultCurrency` (валюта записи
positions-history), — и число складывалось из net'а «в валюте записи
источника» с cross-ccy-слагаемым «в расчётной валюте инструмента»: при
расхождении носителей **складывались разные валюты молча**.

- **Один источник на оба поля.** `resultProfitCurrency` и
  `plannedRiskCurrency` берутся из **одного** места — иначе требование
  «валюты обязаны совпадать, иначе отношение не считается» ничем не
  обеспечено. Это и есть довод выбора: авторитетом назначен носитель,
  который у обоих полей уже общий, известен **до входа** и от исхода
  сделки не зависит.
- **Валюта от биржи — проверяемый признак, не источник.**
  `Position.externalResultCurrency` сверяется с расчётной валютой
  инструмента; не совпало → `AnomalyReport` с кодом
  `RESULT_CURRENCY_MISMATCH` (`severity = NON_CRITICAL`, ставит
  финализатор — `docs/components/FinalizeDealExitExecutor.md`). **Расчёт
  не блокируется:** число считается и записывается, терминал проходит —
  реакция симметрична `SETTLE_CURRENCY_VIOLATION` на cross-ccy-движении и
  инварианту «сделка всегда доходит до терминала».
- **Почему пометка, а не controlled error на границе.** Валидация
  `PositionCloseResult` требует лишь «`ccy` заполнен и парсится» и
  усиливать её до отказа нельзя: отказ на границе оставил бы сделку без
  терминала. Проверка живёт **после** приземления факта, где отказывать
  уже не нужно.
- **Самоприменимость.** Проект дважды чинил этот класс на bills (мёртвый
  guard; пустой операнд сравнения) и записал «валюта — проверяемый
  атрибут», но к валюте net'а правило не применял. Здесь применено.

### Ветка «операнд пуст»

Расчётная валюта — **новое поле самой сущности `Instrument`** (не
JSONB-навеса: атрибуция навесу снята H6 `DOCS_CHECK_11`), которое пишет
**тропа заведения инструмента** — она ходит на биржу и заполняет валюты
оттуда (H10 `DOCS_CHECK_12`,
`docs/decisions/instrument-currencies-home.md` §«Писатель — тропа
заведения»). Бэкфилла ветка не подразумевает: до конца фазы 1 заведённых
инструментов нет (`.claude/rules/pre-launch-schema-changes.md`). Ветка
достижима, когда валюта **не резолвилась при заведении** (ответ источника
неполон), и на популяции «позиция создана вне приложения», которая
риск-преконтроль не проходила. Задана по образцу
`FEE_RATE_UNAVAILABLE` (`docs/components/models/RiskCheckResult.md`) —
**реджект там, где риск ещё не взят; пометка там, где отказывать нельзя**:

| Точка | Операнд пуст ⇒ |
|---|---|
| Вход (`RiskValidator`, писатель `plannedRiskCurrency`) | **реджект** `SETTLE_CURRENCY_UNAVAILABLE` — сделка не открывается. Подставить `USDT` «по контуру» нельзя: это то же подставленное число, выглядящее фактом, из-за которого отвергнут fallback ставки |
| Запись движения (`RefreshBillsExecutor`, cross-ccy guard) | строка **персистится и линкуется**, guard не выполняется, `appliedRate` не считается; `AnomalyReport` `SETTLE_CURRENCY_UNAVAILABLE` |
| Финализация (`resultProfitCurrency`) | берётся `Position.externalResultCurrency` как единственный доступный факт + `AnomalyReport` `SETTLE_CURRENCY_UNAVAILABLE`. Это **явная деградация с пометкой**, а не второй молчаливый источник |

Реджект на входе делает две нижние ветки практически недостижимыми для
сделок, открытых **нашим** входом: они остаются для сделок вокруг позиции,
созданной вне приложения (риск-преконтроль на этой популяции не работал).
Ветки «для сделок, живых на момент ввода» нет — до конца фазы 1 таких
сделок не существует (`.claude/rules/pre-launch-schema-changes.md`).

**Смежное:** дом расчётной валюты — поля самого `Instrument`
(`docs/decisions/instrument-currencies-home.md`); `CCY-Q2` закрыт H6
`DOCS_CHECK_11`, имена полей окончательные.

## Плановый риск (`R`)

**`plannedRiskAmount` — знаменатель R-мультипликатора** (H9,
`GAPS_CLOSE_7`). Шаг 7 персистит числитель (`resultProfit`) и обязан
персистить знаменатель: без него отношение «сколько R заработала сделка» не
считается, а система в торговом смысле **и есть** распределение
R-мультипликаторов [Tharp гл.6 с.144-146].

- **Что это за число — сумма по ногам входа** (H6/H11 `DOCS_CHECK_15`,
  решение пользователя). Слагаемое хранится **на ноге**
  (`Order.plannedRiskAmount`) и есть убыток на **её** стопе, посчитанный
  при постановке **этой** ноги, — та же величина `risk amount`, которую
  считает `RiskValidator` (`|entry − stop| × contracts × ctVal +
  commissions`, `docs/decisions/per-trade-risk-policy.md` §«Закрытая форма
  сайзинга»). Прогнозная комиссия в слагаемое **входит** — иначе
  знаменатель отличался бы от величины, под которую подбирался размер.
  На `Deal` живёт **Σ по живым и исполнившимся ногам входа** — предикат
  отбора слагаемых записан ниже (H2 `DOCS_CHECK_16`, редакция — решение
  держателя), а не подразумевается фразой «ноги входа».
- **Почему сумма, а не снимок первой ноги.** Сетка и добор в фазе 1
  включены фактически (подтверждено пользователем), то есть многоногий
  вход — рабочий режим. Write-once-число на `Deal` при нём оставалось бы
  риском **первой** ноги и молча выдавалось бы за риск сделки: занижение
  знаменателя в λ раз растягивает **все** R-мультипликаторы, λ
  коррелировано с числом ног, и выборка перестаёт быть из одного
  распределения. Побочно портился `BiggestLoss` — делитель размера позиции
  [Vince гл.1 с.17]. Той же правкой восстанавливается тождество
  омиссионного члена epsilon: оно верно **поногово**, а не в агрегате
  (`docs/models/domain/core/Order.md` §«Плановый риск и его операнды»).
- **Кто и когда пишет.** Исполнитель `CREATE_ORDER_COMMAND` входного действия
  (`docs/components/CreateOrderExecutor.md`) — в одной транзакции с созданием
  сущности входа: пишет слагаемое на ногу **и** пересчитывает сумму на
  `Deal`. Риск-преконтроль и создание идут **одним проходом**
  (`docs/rules/risk-validator-scope.md`: `RiskValidator` вызывается после
  расчёта цены/размера и **до** создания команды), поэтому durable-слота
  между проходами не нужно. Сумма пишется **производной, но
  персистируемой**: фильтр и отчёт обязаны быть выразимы запросом без
  join'а по `orders` (§«Признаки отбора для отчёта»), а `join` на лету
  правило отбора запрещает.
- **Чем доезжает — полями `CreateOrderCommandPayload`** (H5
  `DOCS_CHECK_10`). «Durable-слот не нужен» отвечало на другую ось —
  где число живёт **между** проходами; канал **внутри** прохода не был
  назван, а ни один существующий RVO метрику не несёт (единственный
  числовой слот `RiskCheckResult.actualValue` на happy-path не
  существует: в фазе 1 валидатор строит только `BLOCKED`-результаты).
  Четыре числа (`plannedRiskAmount`, `plannedRiskCurrency`,
  `plannedEntryPrice`, `plannedSizeContracts`) едут payload'ом — тем же
  путём, что цена и размер; разбор альтернатив —
  `docs/components/CreateOrderExecutor.md` §«Канал доставки».
- **Write-once переехал на ногу; сумма на сделке — не write-once**
  (H6/H11 `DOCS_CHECK_15`). Слагаемое `Order.plannedRiskAmount` пишется при
  постановке своей ноги и **не переписывается**: трейлинг двигает стоп, но
  риск ноги — риск **на её входе**, бенчмарк измерения [Tharp гл.9
  с.234-236]; текущее состояние защиты знаменателя не даёт. Поле `Deal`
  при этом **обязано** двигаться — не потому, что бенчмарк перестал быть
  входным, а потому, что состав слагаемых растёт: новая нога входа
  добавляет **новый принятый на входе риск**, и сумма его учитывает.
  - **Определение сведено, а не переопределено.** Ратифицированное «`R` —
    риск, под который сайзились» (H24 `GAPS_CLOSE_14`,
    `docs/decisions/per-trade-risk-policy.md` §Асимметрия) сохраняется —
    оно переехало на **уровень ноги**, где и было верно. На уровне сделки
    `R` читается как «суммарный риск, под который сайзились её входы».
    Прежняя формулировка «снимок, сделанный **один раз** при входе» снята:
    она описывала одноногую рамку.
  - **Двух чисел «риск первой ноги» и «сумма» не заводится.** Вариант
    рассмотрен и отвергнут: у первого числа не названо потребителя —
    R-мультипликатор считается от того, чем сделка рисковала, а не от
    того, чем начинала. *(Отказ касается **этой** пары. Пара
    «заявленный ↔ взятый» — другая ось, и она заведена: §ниже.)*

### Предикат отбора слагаемых (H2 `DOCS_CHECK_16`; редакция — решение держателя)

**Какие строки `orders` входят в сумму, прежде записано не было.** Отбор
существовал только как фраза «ноги входа», а её недостаточно: при REPLACE
входной ноги (штатный режим, `docs/decisions/replace-not-amend.md`) в
таблице остаются **две** строки с непустым `planned_risk_amount` —
отменённая и замещающая, — и обе проходят по любому прочтению «нога входа».

**Предикат — бизнес-тип, состояние ноги и страховочный конъюнкт:**

```text
слагаемые Deal.plannedRiskAmount =
  строки orders сделки, у которых
    type ∈ {ENTRY, ENTRY_ATTACHED_STOP_LOSS}       — бизнес-тип
    И status ∈ isLive() ∪ {COMPLETED}              — живая либо исполнившаяся
    И planned_risk_amount НЕПУСТ                   — страховка (цена ниже)
```

**Отбирает бизнес-тип** (решение держателя). Из трёх согласованных форм
(`docs/models/domain/core/Order.md` §«Предикат "нога входа"») предикатом
назначен **`Type`**: он называет роль ноги прямо, читается человеком без
знания того, какой преконтроль гонялся, и живёт в той же строке, что и
отбираемое слагаемое. `positionReducingOnly` остаётся **намерением**,
уходящим на биржу, предикатом отбора не служит.

**Снятая нога не считается вовсе** (решение держателя). Второй конъюнкт
стоит на **состоянии** ноги, а не на причине её снятия: в сумму входят
живые (`CREATED` / `PENDING` / `ACTIVE` / `PARTIALLY_COMPLETED`,
`Order.isLive()`) и исполнившиеся (`COMPLETED`); всякая снятая
(`CANCELED`) выпадает независимо от `closeReason`.

- **`closeReason = REPLACED_BY_STRATEGY` предикатом отбора не служит.**
  Прежняя редакция вычитала из суммы **только** замещённые — и оставляла в
  ней ногу, снятую `CANCELED_BY_STRATEGY` / `KILL_SWITCH` /
  `CONDITION_EXPIRED` / `MANUAL_CANCEL`, то есть заявленный риск, который
  стратегия **отозвала**. Замещённая нога выходит из суммы **тем же
  конъюнктом по состоянию** (REPLACE снимает ногу, `closeReason`
  проставляется вместе с терминальным `CANCELED`), поэтому отдельного
  вычитания не требуется, а обхода цепочки `replacesInternalId` — тем
  более.
- **Почему отозванный риск не в знаменателе.** `R` — риск, под который
  сайзились и который **стоял**. Снятая заявка не стояла: за неё сделка не
  рисковала ни минуты. Оставить её в сумме — раздуть знаменатель кратно
  числу перевыставлений и отмен, ровно тем механизмом растяжения
  R-мультипликаторов, против которого сумма и вводилась, и искажение
  коррелировано с манерой перевыставления, а не с торговым качеством.
- **Частично исполнившаяся и затем снятая нога** из **заявленного**
  выходит тоже, а взятый ею риск учитывает **второе** число (§ниже), где
  она входит своей исполненной долей. Разведение по двум полям и делает
  предикат простым: одному полю не приходится обслуживать обе природы.
- **Нога в `ERROR` в сумму не входит** — она не живая и не исполнившаяся.
  Следствие названо явно: заявленный риск ноги, ушедшей в `ERROR`
  (`MISSING_AFTER_REFRESH`, `UNKNOWN_EXTERNAL_STATUS`,
  `EXCHANGE_INVARIANT_VIOLATION`, `docs/lifecycles/Order.md`
  §«ERROR-переходы»), из знаменателя выпадает, а её исполненная доля — если
  наблюдалась — остаётся во взятом риске. Сделка с такой ногой идёт
  safety-каскадом и в отчёт попадает помеченной, поэтому знаменатель без
  этого слагаемого не выдаётся за нормальный.
- **Отбор идёт по наблюдённому состоянию, не по намерению.** Пока отмена не
  подтверждена refresh'ем (`docs/rules/ack-not-runtime-truth.md`), нога
  остаётся живой и остаётся в сумме. Это не дефект: знаменатель следует
  фактам, а сумма пересчитывается **целиком** тем же исполнителем, который
  проставит терминальный статус (`docs/components/CancelOrderExecutor.md`).

**Третий конъюнкт — страховка, и её цена названа** (решение держателя).
Непустота `planned_risk_amount` — **производная** первых двух форм: у
reduce-only-ноги риск-преконтроль не гоняется
(`CreateOrderActionExecutor.isRiskCreating` = `isNotTrue(positionReducingOnly)`),
шесть чисел не производятся, колонка пуста по построению. Пока инвариант
`Type = REDUCE_ONLY ⇔ positionReducingOnly = true` держится, конъюнкт исход
**не меняет никогда**; он стоит в предикате именно на случай, когда
инвариант **не** держится, — чтобы в сумму не попало слагаемое-пустота.

> **Цена: рассогласование пары носителей гасится молча, обеими сторонами.**
> `Type ∈ {ENTRY, …}` при `positionReducingOnly = true` ⇒ колонка пуста ⇒
> ногу выбрасывает **страховочный** конъюнкт. `Type = REDUCE_ONLY` при
> `positionReducingOnly = false` ⇒ преконтроль гонялся, число есть ⇒ ногу
> выбрасывает **типовой** конъюнкт, и реально принятый риск исчезает из
> знаменателя. В обоих направлениях предикат **не поднимает тревогу**, а
> тихо уменьшает выборку — то есть маскирует нарушение инварианта ровно
> там, где оно измеримо. Поэтому обнаружение рассогласования **не
> возлагается на предикат отбора** и живёт отдельным механизмом (§ниже),
> а реакция на обнаруженное — **отказ операции**, а не пометка.

**Три формы отбирают одно множество и связаны инвариантом**
(`docs/models/domain/core/Order.md` §«Предикат "нога входа"»): бизнес-тип;
`positionReducingOnly = false`; непустота `plannedRiskAmount`. Предикатом
отбора назначена **первая**, третья добавлена страховкой, вторая в отборе
не участвует.

- **Побочный дефект снят тем же ходом.** Прежде attached-SL отменённой
  ноги мог уйти в `ERROR`, предикат селекции защиты давал ноль элементов
  при непустом `plannedRiskAmount_i`, и **чисто закрывшаяся** сделка
  уходила ошибочной тропой. Снятая нога в сумму не входит — её `stop_i` не
  запрашивается.

### Обнаружение рассогласования пары носителей (`Type` ↔ `positionReducingOnly`)

Предикат отбора нарушение инварианта **гасит** (§выше), поэтому носитель
обнаружения нужен отдельный, и он не один: превентивный — на входе,
детектирующий — на пересчёте.

| Контур | Где стоит | Что делает |
|---|---|---|
| **Превентивный** | валидация состава шага стратегии (дельта `CODE`, `.claude/work/backlog.md` §Шаг 7) | не выпускает действие, у которого `orderType = REDUCE_ONLY` при `positionReducingOnly = false` либо наоборот. Закрывает штатный путь появления пары |
| **Детектирующий** | те же три исполнителя, что пересчитывают суммы (`CreateOrderExecutor`, `RefreshOrderExecutor`, `CancelOrderExecutor`) | при пересчёте сверяет пару на ногах сделки **до** применения предиката отбора: расхождение становится фактом, а не молчаливым исключением ноги |

**Почему одного превентивного мало.** Он закрывает путь, которым пара
создаётся **приложением**, и ничего не говорит о строках, попавших в
таблицу иначе (правка данных, миграция, нога, заведённая до ввода
валидации). Знаменатель `R` при этом уже искажён, а искажение по
построению беззвучно.

**Реакция детектирующего контура — отказ операции** (решение держателя
`GAPS_CLOSE_16`). Обнаружив рассогласование пары на ноге сделки, исполнитель
пересчёта **не продолжает работу**: он бросает исключение
non-retryable-класса (`VALIDATION_ERROR` по классификации
`docs/components/ServiceCommandExecutor.md`), строка исполнения уходит в
`FAILED`, сделка — **ошибочной тропой** (`ERROR` → `ErrorHandler`), а
перехваченное оркестратором исчерпание бюджета даёт **полный холд
инструмента** (`docs/rules/instrument-hold.md` §«Форма реакции на исчерпание
бюджета попыток»). Журнального отчёта под это не заводится и нового кода
тоже: реактивную запись производит последовательность холда, код —
`RETRY_BUDGET_EXHAUSTED`.

> **Цена названа и принята держателем.** Рассогласование пары — дефект
> данных, а не рыночное событие, и реакция на него **несоразмерна ущербу**:
> сделка получает аварийный терминал, слот инструмента остаётся занятым до
> его постановки, торговля по инструменту встаёт **до ручного разбора**
> (снятие холда — вручную). Отвергнутая альтернатива — журнальный
> `AnomalyReport` с продолжением пересчёта — оставляла бы торговлю живой, но
> и сделку с искажённым знаменателем — тоже живой. Держатель выбрал
> **остановку**: искажённый знаменатель не должен продолжать накапливаться,
> пока причину не разобрали.

**Реакция одна на оба направления** рассогласования: и «тип входной, числа
нет», и «тип reduce-only, число есть» — один и тот же отказ. Разделять их
нечем и незачем: оба означают, что инвариант нарушен, а какой стороной —
вопрос разбора, не реакции.

### Взятый риск — второе число (`incurredRiskAmount`, H3 `DOCS_CHECK_16`)

Решение пользователя: **два разных поля** — заявленный (заполняется при
создании ноги) и фактически взятый (обновляется по исполнению ног).

| Поле | Что измеряет | Момент | Предикат / формула |
|---|---|---|---|
| `plannedRiskAmount` | **заявленный** риск — бенчмарк, «риск, под который сайзились» | вход | Σ `Order.plannedRiskAmount` по **живым и исполнившимся** ногам входа (§выше) |
| **`incurredRiskAmount`** | **взятый** риск — сколько из заявленного действительно встало под удар | вход | Σ по ногам входа, отобранным **тем же предикатом**, что и первое число, включая страховочный конъюнкт непустоты `planned_risk_amount` (§«Предикат отбора слагаемых»): `plannedRiskAmount_i × (accumulatedFillSize_i / plannedSizeContracts_i)`; слагаемое ноги с `plannedSizeContracts_i = 0` — **ноль**, не деление |
| **`currentRiskAmount`** | **неотработанная доля** взятого на входе риска — какая часть взятого ещё не отыграна выходом | сейчас | `incurredRiskAmount × (Position.externalSize / Σ accumulatedFillSize_i по ногам входа)`; слагаемых нет ⇒ поле **пусто**; слагаемые есть, а `Σ accumulatedFillSize_i = 0` ⇒ поле **ноль** (риск заведомо ещё не взят — значение по проверенному факту, `docs/rules/absent-value-semantics.md`) |
| **`protectionRelievedRiskAmount`** | **риск, снятый защитой** — насколько актуальный стоп уменьшил взятый риск | сейчас | `incurredRiskAmount −` риск при актуальном уровне стопа (`AlgoOrder.condition.trigger.stopLoss.value` действующей защиты; операнд уже persisted); защиты нет ⇒ поле **пусто** |

- **Величина «риск под ударом» несёт пара чисел, а не третье поле в
  одиночку** (H7 `DOCS_CHECK_17`, решение держателя П10: варианты 1 + 3).
  Стоп в контуре **двигается** тремя механизмами (перенос в безубыток,
  трейлинг, risk-weakening replace), а формула третьего числа уровня стопа не
  содержит — поэтому:
  - клейм «сколько взятого ещё **стоит под ударом**» с `currentRiskAmount`
    **снят**: поле честно называется неотработанной долей взятого на входе
    риска;
  - обещанную величину несёт **отдельное число** `protectionRelievedRiskAmount`,
    пересчитываемое **писателем защиты**.

  **Что отвергнуто и почему.** Ввод рыночной цены и актуального стопа прямо в
  формулу третьего числа (вариант 2) превратил бы событийно-пересчитываемую
  проекцию в **функцию времени** и сломал названное этим же доком свойство
  «пересчёт идемпотентен и от порядка не зависит»; оба числа новой пары
  остаются **событийными**. Вариант «не персистить третье поле» переоткрывал
  решение держателя `GAPS_CLOSE_16` («полей три»), вариант «вывести поле из
  популяции потребителей риск-бюджета» лишал `RISK-Q3` названного
  кандидата-операнда.
- **Вырожденные операнды разведены явно** (H6 `DOCS_CHECK_17`, решение
  держателя П2, вариант D). Страховочный конъюнкт непустоты `planned_risk_amount`,
  выписанный у первого числа, распространяется на **все три** формулы: без
  него `null`-слагаемое отравляет сумму там, где инвариант «шесть или ни
  одного» не удержался. Отдельно разведены две природы вырожденного
  знаменателя третьего числа: **слагаемых нет** (пусто — по правилу
  `absent-value-semantics.md`) и **слагаемые есть, филлов нет** (ноль — риск
  ещё не взят; это неприменимость по построению тропы, а не «не знаем»).
  Достижимость второй ветки: `accumulated_fill_size` в `V6` **nullable**,
  а `Position` может быть `ACTIVE` при `externalSize = 0`
  (`docs/models/domain/core/Position.md` §Live risk).
- **Знаменатель R-мультипликатора остаётся заявленным** (решение
  пользователя; бенчмарк `docs/decisions/per-trade-risk-policy.md`
  §Асимметрия **не переоткрывается**). Второе поле — измеритель
  расхождения «заявлено ↔ взято», а не замена бенчмарка.
- **Полей четыре, и каждое отвечает на свой вопрос** (три — решение
  держателя по итогам inspection частичного выхода; четвёртое —
  `protectionRelievedRiskAmount`, решение держателя П10). Частичный выход
  показал, что
  «взятый риск» и «риск, стоящий под ударом сейчас» — **разные величины**:
  первая входная и не отматывается, вторая уменьшается с каждым
  reduce-only-выходом.
  - **`incurredRiskAmount` частичным выходом не уменьшается.** Он
    фиксирует, сколько заявленного встало под удар **на входе**: риск был
    понесён, между входом и частичным выходом позиция стояла целиком, и
    исход этого отрезка реализовался. Уменьшать его задним числом значило
    бы стирать факт и делать R-мультипликаторы сделок со скейл-аутом
    несравнимыми с прямыми [Tharp гл.6 с.144-146] — тот же механизм, из-за
    которого сумма заменила снимок первой ноги.
  - **`currentRiskAmount` уменьшается** и при полном выходе обращается в
    ноль. Его потребитель — **сопровождение**, не отчёт: у закрытой сделки
    он нулевой по построению и в выборку `R` не входит. Кандидат-потребитель
    назван: правило агрегации лимита при многоногом входе
    (`.claude/work/questions/open-questions.md` §`RISK-Q3`, вариант (в) —
    риск-бюджет как расходуемый ресурс: остаток = лимит − текущий).
  - **Колонок операндов не добавляется:** `Position.externalSize` и
    `accumulatedFillSize` персистятся; операнд четвёртого числа (уровень
    актуального стопа на строке защиты) — тоже.
- **Что оно чинит.** Неисполненная нога (grid-уровень, до которого цена не
  дошла; `CONDITION_EXPIRED`) своё слагаемое в заявленном сохраняет —
  заявка была, — но во взятом даёт **ноль**. Прежде разрыв был вычислим
  только постфактум «в аналитике» и **не персистился**, а искажение он
  даёт направленное: у сетки, набирающей против движения, доля
  неисполненных ног максимальна на **выигрышных** сделках ⇒ систематическое
  занижение правого хвоста распределения `R` и ожидаемости [Tharp гл.6
  с.144-146, с.158-159]. Теперь величина искажения — **поле**, а не
  реконструкция.
- **Колонок операндов не добавляется:** `accumulatedFillSize` персистится
  (`V6`, `orders.accumulated_fill_size`), `plannedSizeContracts` —
  write-once на ноге.
- **Все четыре — производные проекции, пересчитываемые целиком.**
  Инкрементального накопления нет: значение всегда равно формуле по
  текущему состоянию, поэтому пересчёт идемпотентен и от порядка не
  зависит — свойство сохраняется и у четвёртого числа, потому что его
  операнд (уровень актуального стопа) **событийный**, а не рыночный.
  Пересчитывает **тот исполнитель, который меняет операнд**, своей
  же транзакцией:

  | Триггер | Исполнитель | Какие поля |
  |---|---|---|
  | создана новая нога входа | `CreateOrderExecutor` (ратифицировано H6/H11 `GAPS_CLOSE_15`) | **две суммы** — `plannedRiskAmount` и `incurredRiskAmount` (H5 `DOCS_CHECK_17`, решение держателя П1) |
  | наблюдены исполнение / терминальный статус ноги **входа** | `RefreshOrderExecutor` | обе входные суммы |
  | нога входа отменена / замещена | `CancelOrderExecutor` | обе входные суммы |
  | **наблюдена позиция** — живая либо из истории | `RefreshPositionExecutor` | **только `currentRiskAmount`** — входные поля от размера позиции не зависят |
  | **поставлена / замещена защита** | `CreateAlgoOrderExecutor`, place-нога `REPLACE` | **только `protectionRelievedRiskAmount`** (решение держателя П10) |

  **Reduce-only-нога входные поля не двигает** — она не входит в
  множество слагаемых (§«Предикат отбора слагаемых»); её исполнение
  меняет `Position.externalSize`, и через него — только `currentRiskAmount`.

  **Третье число пишет только тот, кто наблюдает позицию** (H5
  `DOCS_CHECK_17`, решение держателя П1). `CreateOrderExecutor` его **не
  пересчитывает**: в момент создания ноги исполненного объёма по ней ещё
  нет, а `Position.externalSize` не менялся — пересчёт дал бы либо то же
  значение, либо деление `0/0`. Отдав третье поле наблюдателю позиции, у
  которого знаменатель непуст по построению тропы, ветку вырожденного
  знаменателя делаем **недостижимой**, а не обрабатываемой. Счётный довод
  против обратного варианта («писать все три + ветка нуля»): поле,
  читаемое сопровождением в том же проходе, где создана нога, обнулялось
  бы в пусто — то есть теряло значение ровно тогда, когда сопровождение
  принимает решение о доборе. Формулировка совпадает с
  `docs/decisions/pnl-finalization-mechanics.md` §Следствия («на `Deal`
  той же транзакцией пересчитывает **две суммы**»).

  - **Момента наблюдения не оказалось ⇒ значение берётся из истории**
    (решение держателя П1, вход сверх перечня). Названная цена варианта —
    «между созданием ноги и первым наблюдением позиции третье поле несёт
    прежнее значение» — снимается тем, что **наблюдение позиции не
    ограничено live-ногой**: `REFRESH_POSITION_COMMAND` при not-found
    эскалирует на `positions-history` и материализует позицию **из записи
    закрытия** (`docs/components/RefreshPositionExecutor.md`
    §«Evidence-cycle: live → positions-history»). Сделка, чью позицию не
    застали живой между тиками оркестратора — тропа быстрого стопа и
    ликвидации, — третье число всё равно получает, тем же писателем и по
    тому же операнду.
  - **Отдельного механизма под этот вход не вводится:** нога 2 уже идёт
    безусловно при not-found ноги 1, и это ратифицировано H9
    `DOCS_CHECK_10`. Известное ограничение адресации записи из истории
    (позиция вокруг чужого риска — операнда нижней границы окна нет)
    остаётся тем же и здесь: у такой сделки третье число не появляется, и
    это записано, а не замаскировано суррогатом.

  Персистируются все четыре (а не считаются запросом) по уже названному
  доводу: фильтр и отчёт обязаны быть выразимы запросом **без join'а** по
  `orders` (§«Признаки отбора для отчёта»). У `currentRiskAmount` и
  `protectionRelievedRiskAmount` довод другой — их читает **сопровождение**
  в проходе оркестратора, где `DealContext` уже собран; персист здесь ради
  однородности набора и наблюдаемости, а не ради фильтра.
- **Валюта одна на все четыре числа** — `plannedRiskCurrency` (расчётная
  валюта инструмента); вторая валютная колонка не заводится.
  - **Чего сумма не покрывает — названо.** Риск, выросший **без новой
    ноги** (risk-weakening replace: основная standalone-защита
    переоткрывается дальше от входа — разрешённый класс действия,
    `docs/rules/risk-validator-scope.md`), в `R` не входит: слагаемые
    write-once на ногах, а замещается не нога, а защита. Это **та же ось**,
    что уже названа H24 `GAPS_CLOSE_14`: бенчмарк — риск, под который
    сайзились. Отдельного признака под неё в шаге 7 не заводится, и посылка
    «ослабление защиты конфигурируемо стратегиями фазы 1» остаётся
    **непроверенной** (владелец — `trading-specialist`). **Наблюдаемым это
    движение всё же становится** — с обратным знаком и без входа в `R`:
    `protectionRelievedRiskAmount` пересчитывается писателем защиты, поэтому
    risk-weakening replace виден как **уменьшение снятого защитой риска**
    (решение держателя П10). *(Оговорка «реально
    понесённый `R` вычислим постфактум и реализуется на шаге ожидаемости»
    сужена H3 `DOCS_CHECK_16`: доля **неисполненного объёма** больше не
    ждёт шага ожидаемости — она персистится полем `incurredRiskAmount`
    (§ниже). Ослабление защиты без новой ноги этим полем **не** покрывается
    и остаётся на шаге ожидаемости.)*
- **`R` — риск заявленный, не взятый; разрыв персистится рядом.** Число
  считается по **заявленной** цене входа и **заявленному** размеру, а
  сделка несёт риск по фактической цене исполнения и фактически
  исполненному объёму. Расхождение систематическое по обеим осям
  (проскок входа; частичное исполнение), поэтому вместе с `R` персистятся
  его операнды — **`plannedEntryPrice`** (reference-цена входа, по которой
  считался риск; для market-входа это `ORDER_MARKET_REFERENCE_PRICE`
  калькулятора, на биржу не отправляемая) и **`plannedSizeContracts`**
  (заявленный размер). Имена полей предварительные.
  - **Дом операндов — нога входа, и это `Order`** (H3 `DOCS_CHECK_11`;
    `RISK-Q4` закрыт 2026-08-20): reference-цена и заявленный
    размер — атрибуты **ноги**, а при многоногом входе их несколько; на
    `Deal` write-once-поле оставило бы число первой ноги и молча выдавало
    его за сделку. **Тем же ходом туда переехал и сам риск** (H6/H11
    `DOCS_CHECK_15`): держать риск и его операнды на разных уровнях
    значило разорвать тождество, которое их связывает.
  - **Входной тропы алго-ордером не существует** (`RISK-Q4`, inspection по
    коду): `AlgoOrder.ConditionType` несёт семь значений, все
    protective/closing, входного нет; вход — ordinary `Order`
    (`ENTRY` / `ENTRY_ATTACHED_STOP_LOSS`). Поэтому колонки
    `planned_entry_price` / `planned_size_contracts` живут **только в
    `orders`** (`docs/models/domain/core/Order.md` §Персистентность);
    вторая пара колонок в `algo_orders` была бы мёртвой схемой с живым
    именем. Условие возврата вопроса записано в
    `docs/models/domain/core/AlgoOrder.md` §Назначение.
  - **Знаменатель `R` на `Deal` остаётся — но как сумма, а не как
    единственный носитель** (уточнено H6/H11 `DOCS_CHECK_15`; прежняя
    редакция «переезжают только операнды сравнения» снята).
    `plannedRiskAmount`/`plannedRiskCurrency` живут **и** на ноге
    (слагаемое, write-once), **и** на сделке (сумма, поддерживаемая
    актуальной). Дублирования смысла нет: у ноги — принятый ею риск, у
    сделки — принятый ею суммарно.
  - **Зачем.** Фактически взятый риск вычислим из уже имеющегося:
    стоп — абсолютный ценовой уровень, рассчитанный от рантайм-цены и
    политики риска, на бирже он не плывёт; цена исполнения и объём
    входа читаются финализацией входа (`avgPx`, `accFillSz`). Не хватало
    **второй половины сравнения** — того, против чего решение
    принималось: reference-цена market-входа не персистилась нигде
    (`CreateOrderExecutor` кладёт `Order.price` только при
    `sendPriceToExchange`), и разрыв «заявлено ↔ взято» был неизмерим
    даже постфактум.
  - **Поправка живёт в аналитике, не в поле.** `plannedRiskAmount`
    остаётся тем числом, под которое подбирался размер (решение
    пользователя, `GAPS_CLOSE_10`); альтернатива «писать в поле риск по
    факту входа» отвергнута — поле сменило бы смысл и появлялось бы на
    такт позже, завися от добычи фактов входа. Взамен разрыв становится
    **наблюдаемым**: (`avgPx` − `plannedEntryPrice`) и (`accFillSz` −
    `plannedSizeContracts`) считаются по persisted-данным.
  - **Смежное:** мониторинг slippage сигналов против исполнений — условие
    валидности утверждения «система работает» [Kaufman гл.21 PDF
    с.1913-1914]; поправка на проскок **выхода** отложена отдельно
    (`docs/decisions/per-trade-risk-policy.md` §«Без поправки на
    проскок»).
- **Почему не реконструкция.** Формально `R` восстановим через append-only
  REPLACE-цепочку (`docs/decisions/replace-not-amend.md` §4) + `avgPx`/
  `accFillSz` + `ctVal` — но это join через три носителя, прогнозная комиссия
  в него уже не входит, и получается не то число, под которое сайзились.
- **Незакрытый смежный вопрос — про лимит, не про знаменатель.**
  Знаменатель при многоногом входе **определён** (сумма по ногам, H6/H11
  `DOCS_CHECK_15`). Открытым остаётся другое: **правило агрегации лимита**
  риска — он проверяется **по действию**, и должен ли существовать
  сделочный/портфельный потолок, шаг 7 не решает (`RISK-Q3`,
  `.claude/work/questions/open-questions.md`). Две оси разведены явно:
  знаменатель — про измерение результата, лимит — про допуск к взятию
  риска; исход `RISK-Q3` состав знаменателя не меняет.

Детальный breakdown (fees, fundingFee, gross/netProfit, entry/exit
fills, average prices, partial exits) в `Deal` не хранится: число берётся
готовым из positions-history, категорийная разбивка живёт как `DealCashFlow`
(bills), пофилловая детализация — вне фазы 1 (**OKX-Q1 закрыт**: persisted
`TradeFill` не вводится).

## Рамка R-выборки

**Выборки как хранимого объекта не существует** (узел F `DOCS_CHECK_12`,
решение пользователя). Отбор сделок для отчёта — **параметры эндпоинта**,
который дёргает фронт; фильтры суть значения полей сделки. **Сделка
пишется всегда**, независимо от терминала, и **из популяции ничего не
выводится**: нет ни «выведена из R-выборки», ни «исключена как
непроверенная» — есть значения признаков, по которым потребитель отчёта
фильтрует сам.

Прежняя редакция трактовала выборку как множество с предикатом членства и
на этом строила решения «включить / вывести». Ось «включать ли аварийные»
от этого распадалась неверно: две сделки с **одинаковым рыночным исходом**
попадали в разные популяции в зависимости от технической тропы FSM (H18
`DOCS_CHECK_12`), а левый хвост распределения — ликвидации, то есть ровно
худшие исходы, — усекался, из-за чего `BiggestLoss` (делитель размера
позиции) становился ненаблюдаемым, а ожидаемость систематически
завышалась.

### Признаки отбора для отчёта

**Каждый фильтруемый признак — поле сделки, а не вывод на лету.** Признак,
вычисляемый запросом «по дороге», фильтром эндпоинта быть не может: его
нельзя ни проиндексировать, ни воспроизвести, ни объяснить в отчёте.

| Признак | Поле | Значения |
|---|---|---|
| Торговый исход закрытия | `closeOutcome` | `NORMAL_EXIT` / `LIQUIDATION` / `FORCED_REDUCTION` / `UNDETERMINED` |
| Статус сверки разбивки | `reconciliationStatus` | `NOT_RUN` / `MATCHED` / `MISMATCHED` |
| Структурная неполнота разбивки | `breakdownIncomplete` | `COMPLETE` / `INCOMPLETE_BY_WINDOW` / `NOT_ASSESSED` |
| Природа пустоты знаменателя `R` | `riskBenchmarkAvailability` | `AVAILABLE` / `NOT_APPLICABLE` / `MISSING` |

- **`closeOutcome` — торговый факт, не техническая тропа.** Пишется
  финализацией (штатной и аварийной) из `Position.externalCloseType`
  (`docs/models/domain/core/Position.md`): `1,2` — штатный выход;
  `3,4` — ликвидация; `5,6` — принудительное сокращение (ADL);
  **операнд пуст — `UNDETERMINED`** (H2 `GAPS_CLOSE_13`; половина «вне
  `1..6`» снята H5 `DOCS_CHECK_15` — такая запись не проходит контракт на
  границе интеграции и до финализаторов не доезжает; стейл-редакция снята
  H18 `DOCS_CHECK_16`).
  Ликвидация, пришедшая **чистой** тропой `EXIT_PENDING → CLOSED`, и
  ликвидация через `ERROR → EMERGENCY_CLOSED` получают **одно и то же**
  значение — путь-зависимость снята.
- **`reconciliationStatus` — свойство числа, а не членства.** `NOT_RUN`
  ставится там, где сверка **не была обязана**: аварийный терминал на
  ветви с пустым окном движений (H21 `DOCS_CHECK_14`). Ветка «пустой
  операнд epsilon» из состава `NOT_RUN` **выведена** (H2 `DOCS_CHECK_15`):
  при наступившей обязанности она даёт ошибочный терминал.
  `MISMATCHED` — расхождение сверх epsilon.
  **`EMERGENCY_TERMINAL_UNVERIFIED` перестаёт означать «выведена из
  выборки»**: факт, который этот код нёс, теперь и есть значение
  `NOT_RUN`, а сама сделка остаётся в популяции.
- **Неполнота разбивки — она же неполнота числа, и она уводит терминал**
  (H11 `DOCS_CHECK_17`, решение держателя П11, вариант 3). Источник
  неполноты у разбивки и у `resultProfit` **общий**: cross-ccy-слагаемое
  числа суммируется по тем же строкам. Усечение направленное — вычитаемая
  издержка уменьшается, число **завышается**, — поэтому такая сделка
  чистого `CLOSED` не получает: предикат «`breakdownIncomplete =
  INCOMPLETE_BY_WINDOW` **либо** есть cross-ccy-строка без
  `rateStatus = APPLIED`» уводит её **ошибочной тропой** к
  `EMERGENCY_CLOSED`. **Пятого признака (полноты числителя) не заводится** —
  предикат собран из уже существующих фактов, новой колонки нет.
- **`breakdownIncomplete` — структурная, а не дефектная неполнота** (H23
  `DOCS_CHECK_12`). Окно добычи движений конечно со стороны источника,
  горизонт удержания сделки ничем не ограничен; у сделки длиннее окна
  часть строк недобываема **выбранным конвейером добычи** (`7d` →
  `bills-archive` `3m`; deep-архив источника в конвейер не входит — H27
  `GAPS_CLOSE_13`), поэтому Σ`amount` заведомо не сойдётся с net. Признак
  отделяет «сверка звенит по дефекту» от «сверка звенит по построению» —
  без него контроль, срабатывающий на каждом объекте своей популяции,
  эквивалентен погашенному.

**Значение при недобытом операнде — явное, не благоприятное** (H2, H4
`GAPS_CLOSE_13`; правило — `docs/rules/absent-value-semantics.md`). Два
признака вычисляются сравнением, чьи операнды сами могут быть не добыты,
и «не проверяли» обязано отличаться от «проверили, всё в порядке»:

| Признак | Операнд не добыт | Значение | Сигнал |
|---|---|---|---|
| `closeOutcome` | `Position.externalCloseType` пуст (записи нет) | `UNDETERMINED` | журнальный `AnomalyReport` (`kind = EVENT`) |
| `breakdownIncomplete` | `billsWindowBegin` пуст либо добыча движений не выполнялась | `NOT_ASSESSED` | журнальный `AnomalyReport` (`kind = EVENT`) |
| `reconciliationStatus` | **строки нет** — операнд допуска резолвится всегда, нерезолвимый до признака не доезжает (позиция С3 `GAPS_CLOSE_16`) | — | — |

- **`UNDETERMINED` — не «сделки не было» и не «штатный выход».**
  Прежняя формулировка предиката («`3..6` ⇒ …, иначе — штатный выход»)
  отправляла сделку с **недобытым** фактом закрытия в самую
  благоприятную корзину: она оставалась в выборке под чужим ярлыком, а
  корзина `NORMAL_EXIT` заражалась форсированными исходами. Счётность
  «неопределённых» обеспечена тем же механизмом, что у остальных трёх, —
  `group by close_outcome`.
- **Недостача обязательного поля источника — нарушение контракта
  интеграции, и обнаруживается оно на границе** (H5 `DOCS_CHECK_15`,
  решение пользователя; прежде — у финализатора, H7/H10
  `DOCS_CHECK_14`). Обязательные поля добытой записи (`type` внутри
  `1..6`, правые операнды четырёх пар, `realizedPnl`, `ccy`, резолвимый
  `direction`) проверяются **в слое интеграции**, там, где ответ впервые
  разбирается; нарушение — `ExternalInvariantViolationException`
  (`docs/models/mapping/PositionCloseResult.md` §«Контракт записи
  проверяется здесь»). Реакция — **полный биржевой холд** (`HoldScope.
  EXCHANGE` + `ReactionClass.FULL`, kill-switch, снятие вручную) плюс
  ошибочная тропа сделки; поднимает её общий контур перехвата, не
  финализатор. Класс реакции задан не радиусом наблюдаемого ущерба (он мал
  — отчётный признак одной закрытой сделки), а **неизвестностью радиуса
  поражения** (`docs/rules/error-handling-policy.md` §«Нарушение контракта
  интеграции — радиус по неизвестности поражения»). Триггер зарегистрирован
  в `docs/rules/exchange-hold.md` §«Что переводит в HOLD».
  **Следствие для признака:** до финализатора запись с `type` вне перечня
  не доезжает, поэтому `UNDETERMINED` несёт ровно один смысл — **записи
  нет вовсе** (позиция не заводилась либо не найдена); холда этот случай
  не вызывает.
- **Обязанная и невыполненная сверка ⇒ ошибочный терминал — независимо от
  того, чей операнд недостаёт** (H2 `DOCS_CHECK_15`, решение
  пользователя). Принцип формулируется через **обязанность**, а не через
  природу причины: обязанность наступила и не исполнена. Различение
  выражено **терминальным статусом сделки**: «должны были посчитать и не
  посчитали» ⇒ ошибочный терминал; «должны были и посчитали» ⇒ успешный
  терминал (`MATCHED`/`MISMATCHED`); «не должны были» ⇒ успешный терминал
  независимо от посчитанного (`NOT_RUN`). Третьего значения признака под
  «были обязаны, операнда не нашлось» **не заводится** (H6
  `DOCS_CHECK_16` отклонён решением держателя, §Енумы) — и различать
  больше нечего: самой ветки не осталось (позиция С3 `GAPS_CLOSE_16`).
  **Операнд «должны были посчитать»** — составной durable-предикат из
  существующих полей (новой колонки нет): запись закрытия добыта
  (`Position.externalRealizedProfit` непуст — поле обязательно на границе,
  поэтому его непустота ⟺ запись добыта) **и** окно движений закрыто
  (`Deal.billsWindowEnd` непуст).
  - **Что под это подпадает после переноса валидации.** Правые операнды
    пар до финализатора недостающими не доезжают (граница их не
    пропускает), а операнд допуска с Р3 `GAPS_CLOSE_16` резолвится всегда:
    и `ctVal` (H5 `DOCS_CHECK_16`), и уровень стопа (Р3) персистятся
    write-once на ноге по инварианту «шесть или ни одного»
    (`docs/components/FinalizeDealExitExecutor.md` §epsilon). **Живого
    случая под эту ветку не осталось, и сама ветка снята** — решение
    держателя, позиция С3 `GAPS_CLOSE_16` (вариант a): вместе с ней снят
    журнальный код `RECONCILIATION_OPERAND_MISSING`. Нарушение инварианта
    «шесть или ни одного» — тот же класс, что рассогласование пары
    носителей, и реакция у него одна: **отказ операции** детектирующим
    контуром (§«Обнаружение рассогласования пары носителей»), не доводящий
    пустой операнд до расчёта. Биржевой холд по этому классу по-прежнему
    **не поднимается**: недостача наша, радиус ущерба локализован сделкой.
  - **Почему не `NOT_RUN` + успешный терминал.** Тогда `NOT_RUN` снова
    означал бы и «не были обязаны», и «были обязаны, операнда не
    нашлось», а компенсирующий различитель (терминальный статус) на этом
    случае не срабатывал бы — то есть «не проверяли» и «не должны были»
    опять делили бы одно значение, вопреки правилу, заведённому этим же
    шагом (`docs/rules/absent-value-semantics.md`).
  - Форма пустого значения несобытийных полей у источника (`"0"` против
    пустой строки) — рантайм-посылка того же прогона, что знак/горизонт
    `fundingFee`; после переноса валидации на границу она стала **несущей**
    (`docs/models/mapping/PositionCloseResult.md` §«Контракт записи
    проверяется здесь»).
- **`breakdownIncomplete` — енум из трёх значений, не `Boolean`** (H4
  `GAPS_CLOSE_13`; операнд — H20 `DOCS_CHECK_15`): `COMPLETE` — возраст
  нижней границы окна **на момент добычи** не превышает глубины
  источника; `INCOMPLETE_BY_WINDOW` — превышает; `NOT_ASSESSED` —
  сравнение не выполнялось, потому что операнд не добыт. Третье состояние
  заведено значением, а не пустотой: `Boolean` + `NULL` дал бы
  трёхзначную логику в фильтре, где `false` («разбивка полна») и «не
  оценивалась» неразличимы для потребителя, не пишущего `IS NULL`.
  **Аварийный терминал считает признак тем же сравнением, что штатный**
  (не подставляет `INCOMPLETE_BY_WINDOW` безусловно): «заведомо неполна»
  — свойство разбивки, а не результат измерения.

**Тропы закрытия без входа — признаки неприменимы, и пустота есть их
значение** (H3 `GAPS_CLOSE_13`). На тропах, где терминал `CLOSED`
ставится в обход финализации (истечение условия входа в `PRECHECK`,
риск-блок `RISK_CONTROL` в `PRECHECK`, отмена неисполненного входа из
`ENTRY_SUBMITTED`), события, о котором признак, **не было**: позиция не
открывалась, разбивку сверять не с чем, закрывать было нечего. Пустота
здесь однозначна и второго прочтения не имеет — «не определено» под неё
не заводится (`docs/rules/absent-value-semantics.md` §«Разграничение — по
тропе, а не по полю»). Писателя признаков эти тропы **не получают**:
`MARK_DEAL_CLOSED_COMMAND` пишет ноль, валюту и терминал, признаки
оставляет пустыми — это их ратифицированное значение, а не пропуск.

**Принудительный эпизод внутри сделки отдельным полем не выражается**
(H5 `GAPS_CLOSE_13`). `closeOutcome` — проекция **последнего** закрытия
источника; сделка, где принудительное сокращение произошло в середине, а
последним закрытием было наше, числится `NORMAL_EXIT`. Факт **полной**
ликвидации / принудительного закрытия несёт **`closeOutcome`
(`LIQUIDATION` / `FORCED_REDUCTION`) — единственный носитель, на любой
тропе** (H22 `DOCS_CHECK_14`): прежний клейм «закрытие позиции биржей
доводит сделку до `EMERGENCY_CLOSED`» **снят** — такого маршрутизирующего
правила нет ни в одном handler-доке (цитируемая цель ссылки его не несла),
ликвидация штатно проходит и чистой тропой `EXIT_PENDING → CLOSED`, и
`closeOutcome` пишется на обеих. Названная цена: **частичный**
принудительный эпизод, за которым последовал наш выход, отдельно не
счётен.

**След эпизода — посылка, а не факт** (H13 `DOCS_CHECK_15`, решение
пользователя). Прежняя редакция утверждала: «его след остаётся строками
категории `LIQ_PENALTY` в разбивке и покрыт четвёртой парой сверки». Это
**перемаркировано в посылку**, и проверка внесена в реестр предусловий
`CODE` (`docs/decisions/pnl-finalization-mechanics.md` §«Предусловия
`CODE`», п. 10) — то есть **гейт открыт**, цена пометки принята осознанно.

- **Почему посылка, а не факт.** `type` `3,4` — ликвидация, `5,6` —
  **ADL**: он закрывает позицию против контрагента, а не через страховой
  фонд, и ликвидационный штраф в нём не обязателен. Если при ADL
  `liqPenalty` нулевой и bill-записи штрафа нет, **частичный** ADL следа
  не оставляет вовсе: все три признака отбора чистые, эпизод невидим.
- **Направление ущерба — правый хвост.** ADL по конструкции выбирает
  прибыльные позиции с высоким плечом, то есть его жертва — выигрышная
  сделка, у которой отняли часть размера в лучший момент [Tharp гл.6
  с.158-159]. Систематическое невидимое усечение правого хвоста занижает
  ожидаемость — тем же механизмом, каким усечение левого её завышало.
- **Грунт двусторонний, и это существенно.** Корпус **явно объявляет ADL
  пробелом** и запрещает достраивать («∅ Ликвидационные каскады
  крипто-перпетуалов… auto-deleveraging (ADL)… из общих знаний не
  достраиваем», `microstructure.md` §9; дубль `risk-and-sizing.md` §14).
  Отсюда следует не то, что клауза неверна, а то, что она **не могла быть
  выведена** — то есть является достройкой. Обратное утверждение («при ADL
  штрафа нет») из источника тоже не выводится и в док не вносится.
- **Чем проверяется.** Фикстура §AG1 на реальном ответе источника: даёт ли
  `type` `5,6` записи категории `LIQ_PENALTY` в bills. Это **условие
  корректности названной цены**, а не калибруемая величина, — тот же
  класс, что уже гейтящая посылка `AG3.4`.

Ограничение записано, а не замаскировано — но теперь названо и его
**статус**.

**Конструкция фильтров живёт на стороне API и фронта**, в модели шага 7 её
нет: модель обязана лишь **нести признаки полями**, чтобы фильтр был
выразим запросом.

**Что остаётся верным из прежней рамки:**

- **Сделка без состоявшихся операций — не исход системы.** Признак —
  `docs/rules/deal-without-operations.md` (H7 `DOCS_CHECK_12`, там же
  составной предикат по тропам). **Отдельным полем он не
  материализуется** (H6 `GAPS_CLOSE_13`); **назначенного операнда отбора
  у отчёта нет** (H20 `DOCS_CHECK_14`): прежняя запись «для отбора его
  несёт `status` вместе с `closeReason`» была **ложной** — `closeReason`
  две тропы не различает (`ENTRY_CONDITION_EXPIRED` носят и
  PRECHECK-истечение без операций, и отмена входа из `ENTRY_SUBMITTED`,
  где заявка стояла на бирже и могла частично исполниться), а
  терминальный `status` фазу закрытия не хранит. **Определение популяции
  — за потребителем отчёта, решается на шаге фронта:** фильтрация идёт по
  полям сделки и её дочерних сущностей, и их достаточно — выбор
  конкретного операнда (и конструкция фильтров) делается там, не в
  модели шага 7. Составной предикат дом-дока остаётся тем, чем и был, —
  **ветвлением внутри действия** (потребитель 1), где нужен факт движения
  средств на бирже; фильтр отчёта его не использует. Несостоявшиеся входы относятся к оси
  «частота возможностей», а не к распределению R [Tharp гл.6 с.130-133]:
  включённые нулём они размывали бы ожидаемость к нулю, включённые как
  `unknown` — искажали бы частоту. **Счётчик частоты покрывает только
  входы, дошедшие до создания `Deal`;** пропуски на уровне скана (инструмент
  под холдом выпадает из выборки) им не считаются — это форвард фазы 3
  (`docs/decisions/pnl-finalization-mechanics.md` §«Форвард-фокус»).
- **Неисчислимые (`resultProfit = null`) считаются поштучно.**
  `RESULT_PROFIT_UNAVAILABLE` — отчёт природы `kind = EVENT`, анкера не
  имеет и по разным сделкам одного инструмента **не схлопывается**
  (`docs/models/domain/other/AnomalyReport.md` §Енумы, `Kind`). Счётность
  обеспечена структурно, а не соглашением.

**Разрешимость выборки при пропускной способности контура фазы 1** (один
инструмент, одна активная сделка) — **форвард на фазу 3** вместе с осью
упущенных возможностей (H24 `DOCS_CHECK_12`,
`docs/decisions/pnl-finalization-mechanics.md` §«Форвард-фокус»).

### Операции были, а `R` пуст (H23 `DOCS_CHECK_11`)

Обратный случай к «есть `R`, но операций не было»: числитель есть,
знаменателя нет. Достижим он **только** для позиций, созданных **вне
приложения** (решение пользователя): наш риск-преконтроль пишет
`plannedRiskAmount` на каждом входном действии, поэтому сделка,
рождённая нашим входом, без знаменателя не бывает. Остаются
`EntryReason.RECOVERY` / `MANUAL` / `UNKNOWN` — сделки, поднятые вокруг
чужой позиции.

**Переезд риска на ногу смысла кода не меняет** (проверено при закрытии
H6/H11 `DOCS_CHECK_15`). `Deal.plannedRiskAmount` — сумма по живым и исполнившимся ногам входа
(§«Предикат отбора слагаемых»), поэтому её пустота
означает ровно прежнее: **ни одна нога входа планового риска не несёт**, то
есть входа нашего риск-преконтроля не было.
Пустая сумма и сумма-ноль различимы: слагаемых нет ⇒ поле пусто (не
`ZERO`) — подстановка нуля запрещена тем же правилом, что и везде
(`docs/rules/absent-value-semantics.md`). `PLANNED_RISK_MISSING`
(`kind = EVENT`) остаётся тем же кодом с тем же предикатом.

**Две природы пустоты разведены признаком, а не оставлены потребителю**
(H13 `DOCS_CHECK_16`, решение пользователя). Пустой `plannedRiskAmount`
означал **и** «входа не было по построению» (три тропы закрытия без
входа — нормальная популяция), **и** «операции были, знаменателя нет»
(эта секция — аномалия). Единственное названное поле-фильтр склеивало
нормальную популяцию с аномальной, и это ровно тот класс, ради разведения
которого шаг завёл `UNDETERMINED`, `NOT_ASSESSED` и `NOT_RUN`, — правило
«не проверяли ≠ проверили, всё в порядке»
(`docs/rules/absent-value-semantics.md`) к четвёртому полю того же шага
применено не было. Признак — енум
**`riskBenchmarkAvailability`** (§Енумы), четвёртый в ряду признаков
отбора, пишется теми же двумя финализаторами.

Отвергнутая альтернатива названа: записать операнд отбора конъюнкцией
`planned_risk_amount is null AND close_outcome is not null` — колонки не
добавляет, но связность растёт (потребителю отчёта нужно знать связь двух
полей вместо чтения одного), а фильтр отчёта обязан быть выразим значением
поля (§«Признаки отбора для отчёта»).

- **Это аномалия, а не рабочий режим.** Реакция — **жёсткий выход**:
  контур фазы 1 позициями извне не управляет, и попытка вести такую
  сделку означала бы риск, размер которого система не назначала.
- **Инвариант, который нельзя потерять: такие сделки обязаны быть
  счётными.** Молча выпасть из отчёта они не могут — иначе популяция,
  outcome-коррелированная по построению (чужие позиции всплывают из
  рестартов, расхождений и аварий), омиссией воспроизводит то самое
  смещение, ради устранения которого отвергнут drop null'ов. Счёт
  обеспечивается тем же механизмом, что у `unknown`'ов, — журнальным
  отчётом природы `kind = EVENT` (`PLANNED_RISK_MISSING`). Из популяции
  сделка при этом **не выводится**: отсутствие знаменателя — свойство
  строки (пустой `plannedRiskAmount`), по которому потребитель отчёта
  фильтрует сам (§«Признаки отбора для отчёта»).
- **Детализация — шаг 8** (`AnomalyJob`): код отчёта, момент детекции и
  форма жёсткого выхода. Шаг 7 фиксирует популяцию, реакцию и
  требование счётности; механику ставит шаг 8.

Провенанс числа и довод «`null` ≠ ноль» — `docs/decisions/
pnl-finalization-mechanics.md` реш.3.

## Окно линковки bills (`billsWindowBegin` / `billsWindowEnd`)

Границы окна, по которому `RefreshBillsExecutor` матчит движения к сделке,
— **собственные поля `Deal`**; из чужих колонок
(`Position.externalModifiedAt`) окно **не реконструируется** — та колонка
писалась обеими ногами `REFRESH_POSITION_COMMAND` и предиката «запись
закрытия добыта» не выражала (узел 1 `DOCS_CHECK_8`;
`docs/decisions/command-action-boundary.md` §7). Заполняет **наблюдатель
факта**, write-once:

- `billsWindowBegin` — **`Order.externalCreatedAt` первой отправленной
  ноги сделки; писатель один — `SubmitOrderExecutor`, всегда при
  постановке** (H9 `DOCS_CHECK_16`, решение пользователя). Прежняя
  конструкция — три писателя (live-нога `REFRESH_POSITION_COMMAND` с
  `cTime` позиции, нога 2 на create-тропе с `cTime` записи
  positions-history, условно `SubmitOrderExecutor`) — **снята целиком**;
  разбор ниже.
- `billsWindowEnd` — `uTime` записи закрытия positions-history; пишет
  **вторая нога** `REFRESH_POSITION_COMMAND` в одной транзакции с полями
  положения закрытия на `Position`. Писатель у верхней границы был и
  остаётся один.

### Верхних границ две, и у них разные роли (Р7 `GAPS_CLOSE_16`, решение держателя)

Развилка `FEE-Q2` закрыта вариантом 3: **величины две, и обе законны**.

| Величина | Чем является | Носитель | Кто потребитель |
|---|---|---|---|
| **подвижная** | **текущее время** момента запроса | не персистится — `now()` на проходе | верхняя граница **запроса к источнику**: `RefreshBillsExecutor` тянет `[billsWindowBegin, now]` |
| **неподвижная** | `uTime` записи закрытия positions-history | `Deal.billsWindowEnd` (write-once, как и было) | **линковка** строк к сделке, предикат **обязанности сверки**, **один из двух** операндов признака полноты (составной предикат — решение держателя П4 валидации `GAPS_CLOSE_17`) |

**Что это меняет.** Добыча перестаёт ждать записи закрытия: окно запроса
определено **всегда**, поэтому звено выходной тропы завершимо на любом
проходе, и дефект «звено с недостижимым условием завершения расходует
бюджет» закрыт **без** гейта эмиссии (гейт остаётся тропным, H7
`DOCS_CHECK_16`).

**Разделение ролей — точное:**

- **завершение звена** = страницы диапазона `[begin, now]` добыты и
  персистированы (дедуп по `UNIQUE(exchange_id, external_bill_id)`);
- **линковка** (`deal_cash_flows.deal_id`) идёт **только** по неподвижной
  границе и только когда она непуста. Провизорной линковки нет — значит
  нет и отлинковки, а монотонная политика перезаписи
  (`docs/models/domain/other/DealCashFlow.md` §«Политика перезаписи при
  повторной записи»: заполненное не обнуляется) **не нарушается**.

**Цена двойной линковки посчитана — линковка не двойная, двойная добыча:**

- **перекрывающиеся перезапросы.** Каждый проход тянет диапазон заново до
  `now`; лишних строк не появляется (дедуп по паре ключей), но растут
  трафик и число страниц. Это плата за завершимость звена;
- **строки за неподвижной границей.** Проход, случившийся после закрытия
  позиции, но до приземления записи, добывает движения с `ts >`
  будущего `billsWindowEnd`. Они персистятся **несвязанными** и такими
  остаются: линковка их не подберёт. Популяция несвязанных строк — уже
  описанный форвард-слот (движения аккаунта вне сделки, шаг 8), новой
  сущности не появляется;
- **Операнд `breakdownIncomplete` — составной: верхняя отметка есть
  позднейший из двух моментов** (H20 `DOCS_CHECK_15`, решение пользователя;
  форма операнда — **решение держателя П4** валидации `GAPS_CLOSE_17`,
  вариант C):

  ```text
  max(t_добычи, billsWindowEnd) − billsWindowBegin   против глубины конвейера
  ```

  Недобываемость строки определяется тем, насколько давно она произошла, —
  отсюда возраст нижней границы; а **позднейший** из двух моментов делает
  операнд **монотонным и не зависящим от тропы**: какой бы из двух ни
  оказался старше, отметка не уезжает назад. Цена — один лишний конъюнкт.

  **Что отвергнуто.** Одноместный `t_добычи − billsWindowBegin`
  (предложение владельца, вариант A) на аварийной тропе ошибается
  консервативно, но остаётся тропа-зависимым; возврат к
  `billsWindowEnd − billsWindowBegin` (вариант B) **переоткрывал** H20
  `DOCS_CHECK_15` и возвращал снятый **благоприятный** сдвиг — сделка с уже
  недобываемыми строками получала `COMPLETE`.

  `Deal.billsWindowEnd` при этом остаётся операндом **обязанности сверки** —
  и, с этим решением, **одним из двух** операндов признака полноты; ветка
  «добыча не выполнялась» (пустота границы означает отсутствие разбивки)
  сохраняется. Прежняя формулировка («считается против неподвижной границы;
  подвижная величина в него не входит вовсе») противоречила
  `docs/components/FinalizeDealExitExecutor.md` §«Структурная неполнота».

**Почему подвижная не персистится.** Она не факт, а параметр запроса:
воспроизводить её незачем — что именно добыто, видно по самим строкам и их
`ts`. Колонки под неё не заводится.

### Почему у нижней границы один писатель (H9 `DOCS_CHECK_16`)

**Что было не так.** Поле объявлялось write-once при **трёх** писателях, а
правило разрешения конкуренции не было записано **нигде**: mapping-док
ссылался на «порядок задан там же», то есть сюда, и здесь его не было.
Вторая опора — посылка «конкуренции нет по построению, тропа определена
отсутствием предыдущих наблюдений» — **ложна** в ветке дефолта `AG1.5`, где
`SubmitOrderExecutor` пишет границу **всегда** при постановке, то есть до
всякого наблюдения позиции.

**Что решено.** Писатель один, безусловно:
`Deal.billsWindowBegin = Order.externalCreatedAt` первой отправленной ноги
(`docs/components/SubmitOrderExecutor.md` §«Нижняя граница окна линковки
bills»). Ни live-нога, ни нога 2 `REFRESH_POSITION_COMMAND` этого поля
больше не касаются.

- **Развилка снимается вместе с зависимостью от рантайм-факта.** Вопрос
  §AG1.5 «штампуется ли entry-fee раньше `cTime` позиции» для этой границы
  **закрыт конструкцией**: `externalCreatedAt` ордера не позже комиссии его
  же исполнения (комиссия входа возникает при филле, филл — не раньше
  постановки), значит окно накрывает entry-fee при любом ответе источника.
- **Цена названа:** переоткрыта условная ветка H27 `DOCS_CHECK_10` — она
  становится безусловной. Довод безопасности более широкого окна уже был
  записан и принят: лишних движений оно не захватывает, потому что активная
  сделка на инструмент одна (тот же инвариант слота, что держит верхнюю
  границу).
- **Ограничение подтропы «позиция создана вне приложения» не новое:**
  отправленной ноги там нет, значит нет и операнда границы, — но та же
  подтропа уже не адресуема по временной оси запроса positions-history
  (`docs/components/RefreshPositionExecutor.md` §«Известное ограничение»).
  Выбор писателя её достижимости не меняет.

**Механизм write-once — условный `UPDATE`, не `updatable = false`.** Строка
`deals` существует раньше значения (сделка заводится, границы окна приходят
позже наблюдением факта), поэтому JPA-запрет обновления колонки сделал бы
поле незаписываемым вовсе; это отличает `deals.bills_window_*` от
`orders.planned_*`, которые садятся той же вставкой, что и строка
(`docs/models/domain/core/Order.md` §Персистентность). Guard — условие
`where bills_window_begin is null` в обновлении. При единственном писателе
он охраняет не конкуренцию писателей, а повторную постановку ног той же
сделки.

`billsWindowEnd` пуст (факт закрытия не добыт) → **привязка bills ждёт**,
окно не закрывается; исчерпание бюджета добычи → ошибочная тропа + холд
инструмента. **Цена решения:** после терминала линковка запрещена
(`docs/models/domain/other/DealCashFlow.md` §«Линковка») ⇒ неподобранные к
этому моменту движения не подберутся никогда — разбивка неполна, сверка
даёт `AnomalyReport` при, возможно, верном числе.

## Runtime graph

`Deal` содержит runtime graph: `orders` (см.
`docs/models/domain/core/Order.md`), `algoOrders` (см.
`docs/models/domain/core/AlgoOrder.md`), `position` (см.
`docs/models/domain/core/Position.md`, ≤1 на `Deal`). Live risk сделки —
вычисляемо (см. lifecycle), отдельным boolean-полем не хранится.

В runtime graph **не** входят и в `Deal` не хранятся:
`DealActionState`, `Exchange`, `Instrument`, `StrategyDetail`,
`BalanceContainer`, `TradeFill` archive, raw exchange facts,
`CalculationContext`, `MarketPriceData`, `IndicatorValue`,
`MarketStructure`, `MarketPhase` runtime data, audit/history, pending
`ServiceCommand`. Также не хранятся `marketPhaseId` (фаза входа
выводится через `StrategyDetail.marketPhaseType`), `openedAt`/
`closedAt`/`errorAt` (даты записи — `Auditable`; торговые моменты —
через `Order`/`Position`/audit). `TradeFill` из перечня носителей
**убран** (H14, `GAPS_CLOSE_6`): persisted `TradeFill` в проекте не
вводится (§выше, OKX-Q1 закрыт). Окно линковки bills из чужих носителей
больше не собирается — его границы суть собственные поля сделки (§«Окно
линковки bills» выше; `docs/models/domain/other/DealCashFlow.md`
§«Линковка к `Deal`»).

## Персистентность

Хранится в БД (entity `DealEntity`, таблица `deals`), наследует
audit-поля (`AuditableEntity`). Runtime graph (`orders`/`algoOrders`/
`position`) — отдельные таблицы по `deal_id`, не cascade-коллекции этой
строки. Категорийная разбивка P&L (`DealCashFlow`) — тоже **отдельная
таблица `deal_cash_flows` по `deal_id`** (не поле `Deal`; число
`resultProfit`/`resultProfitCurrency` — поля `Deal`, разбивка — строки
`deal_cash_flows`; `docs/models/domain/other/DealCashFlow.md`). Ограничения
схемы:

- `id` — identity (autoincrement).
- `internal_id`, `instrument_id`, `strategy_detail_id`, `status`,
  `direction` — `NOT NULL`; `entry_reason`, `entry_step_type`,
  `shutdown_reason`, `close_reason`, `planned_risk_amount`,
  `incurred_risk_amount`, `current_risk_amount`,
  `protection_relieved_risk_amount`, `planned_risk_currency`,
  `result_profit`, `result_profit_currency`, `bills_window_begin`,
  `bills_window_end`, `close_outcome`, `reconciliation_status`,
  `breakdown_incomplete`, `risk_benchmark_availability` — nullable
  (`planned_risk_*` / `incurred_risk_amount` / `current_risk_amount` пусты
  до постановки входа, `protection_relieved_risk_amount` — до постановки
  защиты; `bills_window_*` — до наблюдения фактов
  открытия/закрытия; признаки отбора — до финализации).
- **Колонки шага 7 — `ALTER`, в `V6`/`V9` их нет** (H21, `DOCS_CHECK_8`;
  типы дописаны H13 `DOCS_CHECK_14` по общему правилу
  `docs/rules/persistence-representation.md` §«Строковые колонки»):
  `planned_risk_amount` (`numeric(36,18)` — **заявленная** сумма плановых
  рисков живых и исполнившихся ног входа, H6/H11 `DOCS_CHECK_15` + H2
  `DOCS_CHECK_16`; не write-once), **`incurred_risk_amount`**
  (`numeric(36,18)` — **взятый на входе** риск, H3 `DOCS_CHECK_16`; не
  write-once), **`current_risk_amount`** (`numeric(36,18)` —
  **неотработанная доля** взятого на входе риска, уменьшается частичным
  выходом; решение держателя `GAPS_CLOSE_16`; не write-once),
  **`protection_relieved_risk_amount`** (`numeric(36,18)` — **риск, снятый
  защитой**; решение держателя П10 валидации `GAPS_CLOSE_17`; не
  write-once), `planned_risk_currency` (`varchar(64)` — одна на все четыре
  числа),
  `bills_window_begin`,
  `bills_window_end` (обе `timestamptz`) **плюс признаки отбора для
  отчёта** (узел F
  `DOCS_CHECK_12`) — `close_outcome` (`varchar(64)`),
  `reconciliation_status` (`varchar(64)`), `breakdown_incomplete`
  (`varchar(64)` — енум `BreakdownCompleteness`, не `boolean`: третье
  состояние «не оценивалось» заведено значением, H4 `GAPS_CLOSE_13`),
  **`risk_benchmark_availability`** (`varchar(64)` — енум
  `RiskBenchmarkAvailability`, H13 `DOCS_CHECK_16`: две природы пустоты
  знаменателя разведены значением, а не оставлены потребителю отчёта) —
  добавляются миграцией шага 7. **Длины строковых колонок — единая норма
  `varchar(64)`** (H18 `DOCS_CHECK_15`; прежняя категоризация по типу
  значения схлопнута —
  `docs/rules/persistence-representation.md` §«Строковые колонки:
  длины»). Полная schema-дельта
  шага — `docs/decisions/pnl-finalization-mechanics.md` §Следствия.
  Перечень здесь — **место истины** схемы сущности
  (`docs/rules/persistence-representation.md` §«Место истины схемы»).
- **Индекс отбора для отчёта** — по (`status`, `close_outcome`): выборка
  отчёта фильтрует по терминалу и торговому исходу, и без индекса она
  растёт линейно по истории закрытых сделок. Остальные два признака
  низкоселективны и в индекс не идут. **Прежний `ix_deal_status`
  дропается той же миграцией** (H28 `GAPS_CLOSE_13`): (`status`) —
  префикс нового индекса, то есть выборку активных сделок за проход
  оркестратора он обслуживает; вторая структура на непрунимой таблице
  платится стоимостью записи без выигрыша чтения.
- `internal_id` — `updatable = false` (неизменен после создания).
- **`bills_window_begin` / `bills_window_end` — write-once условным
  `UPDATE`, не `updatable = false`** (H9 `DOCS_CHECK_16`): строка `deals`
  создаётся раньше, чем наблюдается факт границы, поэтому JPA-запрет
  обновления сделал бы колонки незаписываемыми. Guard — `where
  bills_window_begin is null` (соотв. `bills_window_end`) в обновлении.
  Разбор — §«Почему у нижней границы один писатель».
- Enum-поля (`status`, `direction`, `entry_reason`, `entry_step_type`,
  `shutdown_reason`, `close_reason`, `close_outcome`,
  `reconciliation_status`, `breakdown_incomplete`,
  `risk_benchmark_availability`) хранятся строкой
  (имя enum); enum — только в домене (codestyle: enum'ы — в доменном
  слое).

Ключевые индексы/constraints (миграция
`V9__create_deal_finalization_states.sql`):

- **`uk_deal_active_instrument`** — частичный уникальный индекс
  `on deals (instrument_id) where status not in ('CLOSED',
  'EMERGENCY_CLOSED')`. DB-уровень инварианта «одна незакрытая сделка на
  инструмент» — **defense-in-depth** к app-gatekeeper'у (`EntryScannerJob`/
  `DealOpeningService`; см. `docs/rules/trading-constraints.md`). Предикат
  «активная/незакрытая» = любой `Status` **кроме** `CLOSED` и
  `EMERGENCY_CLOSED`: `PRECHECK`, `ENTRY_SUBMITTED`, `ENTRY_FINALIZED`,
  `PROTECTION_SWITCHED`, `MANAGING`, `EXIT_PENDING` **и `ERROR`** считаются
  активными — сделка в `ERROR` всё ещё блокирует новую сделку по
  инструменту, пока не дойдёт до терминала `CLOSED`/`EMERGENCY_CLOSED`.
- **`ix_deal_status`** `on deals (status)` — support-индекс под горячую
  выборку активных сделок за проход оркестратора (`DealOrchestratorJob`).
  **Снимается миграцией шага 7** (H28 `GAPS_CLOSE_13`): его роль
  принимает префикс индекса отбора (`status`, `close_outcome`).
- **`ix_deal_instrument_status`** `on deals (instrument_id, status)` —
  support-индекс под gatekeeper входа по инструменту (`EntryScannerJob`/
  `DealOpeningService`). Таблица `deals` не пруним — индексы по
  `status`/`instrument_id` держат выборку активных дешёвой по мере роста
  истории закрытых сделок.
- **Benign insert-race:** вставку новой сделки `EntryScannerJob` делает в
  try/catch — конкурентная вставка, нарушающая `uk_deal_active_instrument`,
  ловится как benign skip (лог по инструменту, не фатальная ошибка прохода),
  а не как сбой. Гонку между двумя проходами закрывает DB-инвариант, приложение
  её не эскалирует.

## Границы с DealActionState / DealContext

- `DealActionState` **не** поле `Deal`: persisted строка **исполнения
  действия** (оба вида — STRATEGY и SYSTEM; recovery/retry/idempotency,
  для STRATEGY — связь `StrategyAction → runtime target`). Связь:
  `Deal.id → DealActionState.dealId → strategyActionId | systemActionType
  → (targetEntityType, targetEntityId)`.
- `DealContext` **не** часть модели `Deal`: процессный runtime-context
  одного прохода FSM (добавляет `Exchange`, `Instrument`, pinned
  `StrategyDetail`, последний persisted `BalanceContainer`, список строк
  исполнений).

Полные модели — `docs/models/domain/other/DealActionState.md`,
`docs/components/models/DealContext.md`; FSM-handlers (материализованы) —
`docs/components/` (`PrecheckHandler` … `ErrorHandler`,
`.claude/decisions/fsm-handler-as-component.md`); правила сборки —
`docs/processes/deal-management.md`.
