## Входные решения (зафиксированы)

1. **Цель теста — сырьё.** Тесты бьют в сырой клиент (`OkxRestClient`)
   + сырые интеграционные DTO (`OkxApiResponse<T>`, типизированные
   `*OkxResponse`/`*OkxRequest`), а не в нашу границу
   (`IntegrationService` / снапшоты / мапперы / `OkxProxyController`).
   Прокси-граничный пилот снимается; его дизайн-контент переносится.
2. **Интеграционные DTO — худые.** `integration.model` держит только
   используемые поля; `codestyle` §«Неиспользуемый код» в силе, карваута
   на полное зеркало биржи нет. Тесты проверяют используемые поля +
   поведение/коды ошибок, не каждое возможное поле биржи. Следствие:
   doc-sync (напр. `OkxTickerResponse` ↔ `market-price-data.md`) —
   **подрезка дока под худой код**, не расширение кода под док (задача
   `integrator` по `api-docs-completion`).
3. **Источник набора запросов — манифест**
   `docs/integrations/okx/coverage-manifest.md` (полон, провенанс
   офдок). Контур покрывает каждый запрос в периметре (строки
   `есть-док`/`создан`/`обновлён`); `вне-периметра`/`сознательно-вне`
   исключены. Новый манифест не заводить.
4. **На каждый запрос — прямой кейс + широкий негатив** через
   порождающую методологию (ниже), не фиксированный список.
5. **Гейт достижимости прямого кейса** (ниже).
6. **Сложные запросы — через цепочки предусловий**
   (close-position требует исполненного ордера → позиции).
7. **Артефакты и поток:** манифест → план (таблица на кейс) →
   Postman-коллекция 1:1 с планом → аппрув пользователя → код-тесты,
   покрывающие весь план → бланк отчёта (таблицы как в плане) → прогон →
   фиксация расхождений с апидоками → по успеху правка апидоков + отметка
   в отчёте. Коллекция — **ревью/аппрув-артефакт**; код-тесты —
   **исполнитель**; существуют оба.

## Что меняется концептуально (было → стало)

| Аспект | Было (граничный) | Стало (сырьё) |
|---|---|---|
| Цель теста | граница: `IntegrationService`/снапшоты/`ExchangeAck` через `OkxProxyController` | сырой клиент `OkxRestClient` + сырые DTO `OkxApiResponse<T>` |
| Проверки полей | на mapped DTO / `*ExternalSnapshot` / `ExchangeAck` | на сырых DTO источника (используемые поля + коды ошибок) |
| Полнота покрытия | «каждый запрос клиентского слоя» | **манифест** (периметр) ∩ сырой клиент (см. ниже) |
| Негатив | ad-hoc (несущ. id, фейк-ключ) | **порождающая методология** категорий |
| Достижимость прямого кейса | не формализована | **гейт достижимости** (отказ + причина) |
| Исполнитель прогона | Postman-коллекция | **код-тесты** (коллекция → ревью/аппрув) |
| Surface-gap | прокси не выводит поле/эндпоинт → gap | большинство gap'ов **растворяется** (бьём в сырой клиент); остаётся client-coverage-gap |
| Возврат расхождений в апидоки | находка → `integrator` | стыковка с `api-docs-completion` (по развилке C) |

**Растворение прокси-surface-gap'ов.** Прежние «surface-расхождения
прокси» (свечи не на прокси; сырой `getOrder` ниже прокси; адаптер-
инварианты на снапшоте не выведены) были артефактом проверки **через
mapped-границу**. Против сырого клиента + сырого DTO они наблюдаемы
напрямую: candle-методы есть на клиенте; `getOrder` — метод клиента;
сырой DTO несёт поля, которые снапшот ронял. Этот пласт уходит из
концепции; остаётся только client-coverage-gap (ниже).

## Манифест ∩ сырой клиент (покрытие)

Решения 1 и 3 пересекаются: цель — сырой клиент, набор — периметр
манифеста. Периметр манифеста **шире** того, что реализует
`OkxRestClient` (много строк `создан`/`обновлён` задокументированы, но
метода в клиенте нет: `account/config`, `order-precheck`, `mark-price`,
`price-limit`, `funding-rate`, `position-tiers`, `server-time`,
`insurance-fund`, batch-операции и пр.).

Разрешение: контур кроссит **периметр манифеста** с **поверхностью
сырого клиента**:

- строка периметра, реализованная в клиенте → прямой кейс + негатив;
- строка периметра **без** метода клиента → **client-coverage-gap**:
  явно фиксируется (в периметре, в клиенте не подключён), запрос **не
  выдумывается**. Это новый аналог прежнего surface-gap, поднятый с
  уровня прокси на уровень клиента.

`OkxRestClient` сейчас несёт ~22 метода (instruments, candles ×2,
ticker, pending/history orders+algo, fills ×2, getOrder, getPositions,
place/cancel order, closePosition, getAlgoOrder, place/cancel(+advance)
algos, getBalance, диагностический сырой getAccountConfig).

## Порождающая методология негатива (решение 4)

Не фиксированный список — **процедура вывода** применимых негативных
категорий по типу запроса; тестировщик добавляет свои кейсы.

**Категории-генераторы:**

- **битый параметр (значение)** — нечисло там, где число; неверный
  формат (битый `instId`); вне диапазона;
- **имя параметра/поля** — неизвестный/опечатанный ключ параметра;
- **значение вне домена** — неизвестный `side`/`ordType`/`instType`;
  нулевой/отрицательный размер;
- **отсутствие обязательного** — пропуск обязательного параметра/поля;
- **несуществующий идентификатор** — фейковый `ordId`/`algoId`/`instId`;
- **дубль идентификатора** — повторный `clOrdId`/`algoClOrdId`;
- **удаление удалённого / отмена отменённого** — cancel уже отменённого,
  get отменённого, close несуществующей позиции;
- **дата-фильтр из будущего / вне окна** — `after`/`before`-якорь в
  будущем либо за окном хранения;
- **авторизация** — пустые/битые креды (кейс I3), недостаточный
  permission;
- **состояние-конфликт** — reduce-only без позиции и т. п.

**Процедура вывода для запроса:**

1. перечислить параметры запроса и требуемое состояние;
2. на каждый — инстанцировать применимые категории (read-only GET →
   несущ. id, битый параметр, вне-окна фильтр, неизвестный ключ,
   пропуск обязательного, auth; write POST → плюс значение вне домена,
   пропуск обязательного поля тела, дубль id, состояние-конфликт,
   отмена-отменённого для cancel/close);
3. скрестить с **документированными кодами ошибок** контракта (у
   `integrator`);
4. тестировщик добавляет суждение-кейсы.

Негатив без состояния — дешёвый слой, гоняется первым (сохраняется из
прежней концепции).

## Гейт достижимости прямого кейса (решение 5)

Часть эндпоинтов отдаёт архивные сущности с задержкой/окном
(`orders-history-archive` 3м, `fills-archive` async 3м+, закрытые
позиции ~30д — `integration-okx.md` §Известные ограничения). Прямой
(happy) кейс такого эндпоинта требует сущности, существующей в окне, —
в свежем рантайме (demo-аккаунт, текущая сессия) она может быть
**недостижима**.

**Процедура гейта** — на каждый прямой кейс оценить достижимость
предусловия в рантайме контура (с учётом архивных окон, async-задержек,
~30д-позиций, истории, которой у свежего аккаунта нет):

- достижим → прямой кейс остаётся (возможно, через цепочку
  предусловий);
- недостижим → **отказ от прямого кейса**, покрытие только негативом,
  **явное указание отказа + причины** в плане (шапка кейса) и в отчёте
  прогона. Ожидание недостижимого прямого кейса не выдумывается
  (симметрично «источниковый дефицит — эскалация; незадокументированное
  не выдумывается»).

## Миграция пилота

Прокси-граничный пилот (`.claude/tests/source-api/okx/pilot-plan.md`
+ `pilot-collection.postman_collection.json` + `pilot-environment...`)
**снимается** (цель ушла с прокси-границы). Переносится дизайн-контент:

- **дизайн кейсов** — негативный слой (N1/N2), цепочка ордера (C),
  trailing/И-2 (advance-cancel), пустые креды (I3), prod read-only блок;
- **цепочки предусловий** — граф (live-цена → place → get → cancel →
  проверка отменённого; A0→A4 trailing);
- **карта surface-gap'ов** — переосмысляется: прокси-gap'ы растворяются,
  выжившее фиксируется как client-coverage-gap;
- **закрытая нога amend** — REPLACE-only (`replace-not-amend`); amend в
  клиенте нет; будущий REPLACE-тест гейтится приземлением
  REPLACE-оркестрации (`backlog.md` §Хвост шага 4).

Под сырьё пилот **регенерируется** (или расширяется до полного периметра
манифеста ∩ клиент) как первый план новой концепции.
