### A1. Суррогат нижней границы окна линковки живёт в шести носителях и отсутствует в доме окна

**Вопрос.** `Deal.md` объявлен домом окна линковки движений тремя носителями,
но не содержит ни поля `externalCreatedAt`, ни клаузы «пустая граница
подставляется суррогатом». Предикат линковки (исполнимая спецификация) и три
компонента на этот суррогат опираются как на несущий операнд. Читатель,
реализующий шаг 7 по `Deal.md`, построит другое окно, чем задаёт
`cash-flow-linkage.json`.

**Цитаты (носители).**

| Носитель | Что утверждает |
|---|---|
| `docs/models/domain/aggregate/Deal.md:23-51` | таблица полей: `billsWindowBegin`, `billsWindowEnd`, `billsFetchedThrough`; `externalCreatedAt` отсутствует |
| `docs/models/domain/aggregate/Deal.md:221-240` | «Границ **две**…»; «**У нижней границы один писатель** — отправка первой входной заявки сделки… второго кандидата на него нет»; суррогат не упомянут |
| `docs/models/domain/aggregate/Deal.md:262-291` | инвентарь `NOT NULL`/nullable и таблица write-once guard'ов; `external_created_at` не назван |
| `docs/spec/cash-flow-linkage.json:10,21-29,120-139` | `lowerBound = coalesce(deal.billsWindowBegin, deal.externalCreatedAt)`; два примера прогоняют именно суррогатную ветку |
| `docs/components/RefreshBillsExecutor.md:21-39,80-83` | «Нижняя граница: поле либо суррогат»; §Связи: «Окно линковки — `docs/models/domain/aggregate/Deal.md`» |
| `docs/components/DealOpeningService.md:20-25` | пишет `Deal.externalCreatedAt`; «Поле служит нижней границей окна линковки bills, когда `billsWindowBegin` пуст (`docs/models/domain/aggregate/Deal.md`)» — атрибуция в док, клаузы не содержащий |
| `docs/components/EntryScannerJob.md:46-56` | «биржевой момент… служит нижней границей окна линковки движений, когда собственной границы ещё нет» |
| `docs/models/domain/other/Auditable.md:29-39` | «Экземпляр — момент создания сделки: он служит нижней границей окна линковки движений» |
| `docs/models/domain/other/DealCashFlow.md:74-88,102-107` | предикат линковки описан без суррогата; §Связи: «Окно линковки — там же» (в `Deal.md`) |

**Проверка отрицательной посылки.** «Поля нет в `Deal.md`» —
`grep -rn "externalCreatedAt|external_created_at" docs/`: в `Deal.md` ни
одного вхождения; клауза о суррогате есть только в перечисленных выше
файлах. Колонка при этом **существует** (`Deal.md:258` «наследует поля
аудита» + `Auditable.md:41-48` «набор бинарен: либо все шесть колонок, либо
ни одной»), то есть дефект — не отсутствие носителя, а отсутствие знания в
доме.

**Достижимость суррогатной ветки проверена.** Для сделки с
`entryReason = RECOVERY` `SubmitOrderExecutor` не вызывается никогда
(`DealTranche.md:108-113`: транш без объявления, ведётся safety-тропой), то
есть `billsWindowBegin` пуст навсегда и суррогат — единственная граница.
Вариант «снять суррогат» на этой тропе оставляет окно нерезолвимым.

**Целевой док.** `docs/models/domain/aggregate/Deal.md` (§Структура +
§«Окно линковки движений») — правка существующего дока; при выборе
варианта 2 — правки `cash-flow-linkage.json`, `RefreshBillsExecutor.md`,
`DealOpeningService.md`, `EntryScannerJob.md`, `Auditable.md`.

**Ожидаемый владелец.** `solution-designer` (конструкция концепции: состав
полей агрегата и предикат окна). Курационная половина (свести пересказ к
ссылке) — `knowledge-curator`.

**Трассировка.** Открыл `Deal.md` целиком → §«Окно линковки движений»
перечисляет две границы и одного писателя → §Связи `DealCashFlow.md` и

суррогатной ветки на тропе `RECOVERY`.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|

### A2. Ключ живого системного исполнения: дом ключей и компонент называют разные наборы полей

**Вопрос.** `idempotency-via-unique.md` объявляет модель местом истины для
состава ключа. `DealActionState.md` называет ключ системной таблицы без
транша и явно ограничивает транш стратегийными исполнениями;
`FinalizeDealEntryExecutor.md` называет ключ **с** траншем. Расхождение
касается схемы, которая едет в миграцию шага, и решает, может ли сетка
консолидировать вход двух траншей одновременно.

**Цитаты (носители).**

|---|---|
| `docs/rules/idempotency-via-unique.md:16-18` | «Ключевые UNIQUE-инварианты сущности фиксируются в её модели. Модель — место истины» |
| `docs/models/domain/other/DealActionState.md:96-109` | «в стратегийной ссылка на узел обязательна, в **системной — тип системного действия**»; «**Транш входит в состав ключа стратегийных исполнений**» (о системных — молчание) |
| `docs/models/domain/other/DealActionState.md:38` | `dealTrancheId` обязателен «у стратегийных»; «Пусто у системных исполнений **уровня сделки**» — обязательность у системных исполнений уровня транша не задана |
| `docs/components/FinalizeDealEntryExecutor.md:41-44` | «частичный ключ живого исполнения (`deal_id`, `deal_tranche_id`, `system_action_type`)» |

| `docs/components/TrancheExitPendingHandler.md:29-31` | добыча системным действием «состояние заявок **транша**» — второй потраншевый системный потребитель |

**Проверка достижимости коллизии.** Сетка материализует N траншей в
`PRECHECK` (`DealOpeningService.md:27-32`), каждый идёт своим входом
независимо (`DealActiveHandler.md:31-33`), поэтому два транша в
`ENTRY_SUBMITTED` одновременно — штатное, а не редкое состояние; при ключе
без транша второе живое исполнение `FINALIZE_DEAL_ENTRY_ACTION` не
заводится.

**Целевой док.** `docs/models/domain/other/DealActionState.md` (§Инварианты +
строка `dealTrancheId` таблицы). Второй носитель
(`FinalizeDealEntryExecutor.md`) после правки сводится к ссылке.

**Ожидаемый владелец.** `solution-designer` (состав ключа — конструкция);
`code-writer` — форма частичного индекса.

**Трассировка.** Читал `DealActionState.md` → заметил асимметрию «транш в
ключе только у стратегийных» при потраншевом `FINALIZE_DEAL_ENTRY_ACTION`
→ открыл `SystemActionExecutor.md` (подтвердил потраншевость) → открыл
`FinalizeDealEntryExecutor.md` за писателем ребра → нашёл встречный состав
ключа → проверил одновременность на грид-примере спеки покрытия.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| 1. Достаточность существующего: ключ без транша, `FINALIZE_DEAL_ENTRY_ACTION` — уровня сделки | Одна консолидация на сделку, подтверждающая вход всех траншей разом | Ломает `SystemActionExecutor.md:52-54` и потраншевое ребро `ENTRY_SUBMITTED → ENTRY_FINALIZED`: транши входят в разные моменты, общая консолидация подтверждала бы неналитый вход. Счётный неверный исход |
| 2. (крен) Транш в ключ системных исполнений; `dealTrancheId` обязателен у системных действий траншевой области, пуст у сделочных | Ключ `(deal_id, deal_tranche_id, system_action_type)` среди живых, partial-index по nullable-колонке | След: колонка + индекс (уже существующая колонка, меняется только состав ключа).
