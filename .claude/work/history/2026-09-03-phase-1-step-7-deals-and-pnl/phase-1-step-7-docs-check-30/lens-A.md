# Блокирует выход в CODE

## A1. Восстановленная сделка, чью позицию сняли до первого прохода, не доходит **ни до одного** терминала

**Вопрос.** `positionObserved` истинен у **всякой** сделки с
`entryReason = RECOVERY` по построению, поэтому `episodesComplete`
требует у неё непустых эпизодов безусловно. Строку эпизода заводит только
добыча позиции ближайшим проходом; если позицию закрыли вне приложения
**до** этого прохода, ветка добычи «не найдена → живую строку закрыть»
закрывать нечего и строку не заводит. Эпизодов нет и не будет ⇒
`graphComplete` ложен навсегда ⇒ `riskProvenAbsent` ложен ⇒
`transitionAllowed` ложен и для `CLOSED`, и для `EMERGENCY_CLOSED`.
Сделка висит активной вечно. Ровно эту популяцию корпус называет
**законной тропой штатного терминала**.

**Грунт (торговый).** Не нужен: развилка о механике модели, не о рынке.

**Цитаты (носители).**

- `docs/spec/deal-context-load.json` — `positionObserved`
  (`entryFilled || deal.entryReason == 'RECOVERY'`), `episodesComplete`
  (`episodesAllLoaded && (episodesPresent || !positionObserved)`), нота
  величины («у восстановленной сделки заявки не было, **а эпизод есть**»),
  пример 7 «восстановленная сделка… пустые эпизоды не проходят»;
- `docs/spec/deal-lifecycle.json` — `riskProvenAbsent`
  (`graphComplete && …`), `transitionAllowed` (оба терминала требуют
  `riskProvenAbsent`);
- `docs/lifecycles/Deal.md:219-225` — «Штатный терминал доступен ей, когда
  риск снялся раньше, чем его застал проход… **живого эпизода нет**…
  и сделка сворачивается штатно»;
- `docs/lifecycles/Deal.md:201` — «Сделка всегда доходит до терминала и не
  зависает живым риском»;
- `docs/components/DealOpeningService.md` §«Эпизод позиции сервис не
  заводит» — «на входе у неё состояние «на бирже позиция есть, локальной
  строки у сделки нет»»;
- `docs/components/RefreshPositionExecutor.md` §«Обход внутри одной
  команды» — ветка «не найдена → живую строку закрыть → нога 2»; нога 2
  адресует «строку закрытую и без положения закрытия» — строк нет;
- `docs/concept.md` §П1 (потолок обеспечен механизмом), §«Что это за
  система» («всегда доходит до финала: зависшего живого риска не бывает»).

**Мутационная проба (обе стороны, `SPEC_DIR=target/probe-lensA`).**
Проба C (`deal-context-load`): состояние `RECOVERY` + `episodes: []` +
`position.externalSize: 0` — ожидание `positionObserved: true`,
`episodesComplete: false`, `graphComplete: false` **сошлось**. Пробы D и E
(`deal-lifecycle`): то же состояние на рёбрах `ACTIVE → CLOSED` и
`ERROR → EMERGENCY_CLOSED` — ожидание `riskProvenAbsent: false`,
`transitionAllowed: false` **сошлось** на обоих. Прогон: 453 примера, все
сошлись. Каталог удалён.

**Почему гейтит.** Тропа объявлена законной и приземляется в код как
«сделка сворачивается штатно»; исполнимая форма её запирает. Писателю
кода нечего реализовывать: любой выбор (обойти гейт, завести суррогатный
эпизод, ослабить `episodesComplete`) — проектное решение, а не деталь.
Направление ошибки — зависший активный слот инструмента: новых сделок по
нему не завести никогда (`uk_deal_active_instrument`).

**Уровень пробела.** Концепция-стык: контракт между сборщиком контекста
(удостоверитель пустоты эпизодов), тропой восстановления (кто заводит
строку эпизода) и гейтом терминала.

**Целевой док.** `docs/spec/deal-context-load.json` (`episodesComplete`)
плюс один из: `docs/components/RefreshPositionExecutor.md` (кто заводит
строку при отсутствующей позиции) либо `docs/lifecycles/Deal.md`
§«Куда приходит восстановленная сделка».

**Ожидаемый владелец.** `solution-designer`.

**Трассировка.** Открывал `docs/lifecycles/Deal.md` (тропы
восстановления) → `DealOpeningService.md` (кто заводит эпизод) →
`RefreshPositionExecutor.md` (ветка «позиция не найдена») →
`deal-context-load.json` (`episodesComplete`, пример 7) →
`deal-lifecycle.json` (`riskProvenAbsent`) → пробы C/D/E.

**Варианты.**

| Вариант | Что делает | Цена (правки / контекстная связность) |
|---|---|---|
| **Достаточность существующего носителя** — прочесть `episodesPresent` как уже покрытый | ничем не покрыт: удостоверитель `positionObserved` тождественно истинен у `RECOVERY`, третьей ветви нет | 0 правок / — ; **отвергается**: проба C показывает ложь предиката |
| **(а) добыча заводит строку закрытого эпизода и при отсутствующей позиции** (первая нога: «не найдена, локальной строки нет» → завести строку эпизода со статусом закрытого по данным истории) | строка появляется, `episodesPresent` истинен, обе тропы терминала открыты | правка `RefreshPositionExecutor.md` + пример в `deal-context-load.json`; связность низкая — факт добывается там же, где остальные. Риск: истории может не быть (эпизод чужой), тогда строка без положения закрытия и `allCloseRecordsFetched` ложен ⇒ число недоступно ⇒ **аварийный** терминал, а не штатный |
| **(б) третья ветвь удостоверителя**: пустые эпизоды законны у `RECOVERY`, если живой позиции нет и добыча позиции отработала | предикат перестаёт быть тотально-истинным на `RECOVERY` | правка `episodesComplete` + новый операнд «добыча позиции отработала» (носителя сегодня нет — durable-факт добычи есть только у движений, `billsFetchedThrough`); связность высокая: операнд обязан быть durable, иначе рестарт вернёт ложь |
| **(в) снять клаузу «штатный терминал доступен ей»** — восстановленная сделка всегда идёт аварийным терминалом | одна тропа вместо двух; но `riskProvenAbsent` требует `graphComplete` и на аварийном ребре — сделка всё равно висит | правка одного пассажа `Deal.md`; **исход не чинит**: проба E показывает, что аварийное ребро закрыто тем же конъюнктом |
| **(г) переструктурировать**: вынести `graphComplete` из `riskProvenAbsent` в отдельный гейт применения ребра, оставив терминалу право закрываться на усечённом графе | развязывает A1 и A5 одним ходом | сущность/вторая ось: гейт применения ребра — новый уровень; **переоткрывает** охрану, введённую последним закрытием |

**Ярлык исхода.** `варианты-с-креном` — крен на **(а)**: минимальный след
среди работающих (правка одного дока + пример), не заводит ни поля, ни
операнда, и сохраняет обе тропы. Счётный довод против (б): у него нет
существующего durable-носителя операнда.

**Ярлык дефицита.** `работа` (проектирование внутри концепции; из
`docs/concept.md` выводится, что тропа обязана существовать, но не какая
из трёх).

## A2. У `Deal.closeReason` нет писателя и момента, а наследование причины траншем стои́т на перечне, который с ним не пересекается

**Вопрос.** Причина закрытия транша объявлена наследуемой: «транш
получает **то же** значение, которое уводит в выход саму сделку», и это
подпёрто клеймом «у сделки оно к этому моменту уже определено… пустым
`closeReason` сделки на этом ребре не бывает» с указателем на
`docs/lifecycles/Deal.md`. В указанном доме такой клаузы нет: его
§«Причина сворачивания» перечисляет значения **`ShutdownReason`**
(`STRATEGY_DELETED`, `RISK_POLICY`, `EXCHANGE_HOLD`,
`MARKET_DATA_EXPIRED`), а `CloseReason` — другой перечень
(`ENTRY_CONDITION_EXPIRED`, `STRATEGY_EXIT`, `TAKE_PROFIT`, `STOP_LOSS`,
`TIME_STOP`, `RISK_CONTROL`, `EMERGENCY_CLOSE`, `UNKNOWN`), и модель прямо
разводит эти два поля («`closeReason` не заменяет»). Перечни не
пересекаются ни одним значением. Ни один док не называет компонент и
момент, которые пишут `Deal.closeReason` на штатной тропе; тот же дефект
у `Deal.shutdownReason` — он объявлен пассивным залогом («Заполняется…»,
«переводятся в graceful shutdown»), что `writer-named-for-every-value.md`
запрещает поимённо.

**Грунт (торговый).** Не нужен.

**Цитаты (носители).**

- `docs/models/domain/aggregate/Deal.md:34` — поле `closeReason` без
  писателя и момента (соседние строки :39, :43, :44, :45, :32 писателя
  называют);
- `docs/models/domain/aggregate/Deal.md:89-94` — перечень `CloseReason` без
  писателей по значениям;
- `docs/models/domain/aggregate/Deal.md:33`, `:84-87` — `shutdownReason` и
  `ShutdownReason` тем же пассивным залогом;
- `docs/lifecycles/Deal.md:140-160` — §«Причина сворачивания»: таблица
  событий → `ShutdownReason`; поле в заголовке не названо; писателя нет;
- `docs/lifecycles/DealTranche.md:150-159` — таблица терминальных рёбер
  транша со значением «**причина сделки**» и клеймом «У сделки оно к
  этому моменту уже определено… (`docs/lifecycles/Deal.md`)»;
- `docs/components/DealExitPendingHandler.md:53-54` — «**подтвердить**
  причину закрытия» (подтверждает, не пишет);
- `docs/components/FinalizeDealExitExecutor.md:11-13` — «**Читает:**…
  причина закрытия определена»;
- `docs/components/MarkDealClosedExecutor.md` — о `closeReason` сделки не
  говорит вовсе (пишет число, валюту, признак, счётчик, базу);
- `docs/components/MarkDealEmergencyClosedExecutor.md:9-11` — «пишет
  аварийный терминал **с причиной**» — единственный намёк на писателя,
  значение не названо;
- `docs/lifecycles/Strategy.md:32-33` — «открытые сделки **переводятся** в
  graceful shutdown (`Deal.shutdownReason = STRATEGY_DELETED`)» — пассивный

- `docs/rules/writer-named-for-every-value.md` — нарушенное правило

**Верификация атрибуции.** Клейм `DealTranche.md:157-158` проверен
чтением цели: в `docs/lifecycles/Deal.md` нет ни клаузы «пустым
`closeReason` сделки на этом ребре не бывает», ни перечня значений
`CloseReason` по событиям сворачивания. Битая кросс-ссылка.

**Почему гейтит.** Писателю кода нужно поставить `deals.close_reason` и

сделки и уровнем транша плюс отображение «инициатор выхода → значение».

**Целевой док.** `docs/lifecycles/Deal.md` (новая клауза «писатель и

**Ожидаемый владелец.** `solution-designer`.

## A3. Запрет набора риска в окне сворачивания энфорсится **только на статусном ребре**; risk-creating действие, статус не двигающее, не гейтится ничем

**Вопрос.** Дом запрета объявляет: «Пока сделка в координированном
выходе, **ни один** её транш не берёт новый риск», и называет энфорсеры
«по статусу транша, поимённо». Все названные энфорсеры — статусные:
`PRECHECK` не отправляет вход, `MANAGING` не применяет ветвь
переоткрытия, исполнимая форма — предикат ребра
(`to == 'ENTRY_SUBMITTED' && deal.status == 'EXIT_PENDING'`). Но
risk-creating действие транша в `MANAGING` статуса **не двигает**: добор
и `REPLACE` с увеличением размера оставляют транш в `MANAGING` (ребро

## A4. Каскад сворачивания в транш описан циклом, а вторая из двух законных форм полного выхода энфорсера порядка не имеет

**Вопрос — две сцепленные половины одного хода.**

**(а) Порядок.** Инвариант объявлен общим для обоих уровней: «Сначала
отменяются живые входные заявки, потом закрывается экспозиция». На тропе
явного действия он энфорсится стадиями (`ExitActionExecutor`: «живые
входные заявки есть → отмена; нет → закрытие», область «этих заявок» у
выхода сделки — заявки **всех** траншей). На второй законной форме —
условие-переход, эмитент `DealExitPendingHandler` — такого гейта нет: шаг
2 «Полное закрытие нетто-экспозиции» обоснован только законностью уровня
(«выходят все транши»), а собственных отмен агрегат не делает («Агрегат
заявок за транши не снимает»). Живую входную заявку транша снимает только
`TrancheExitPendingHandler`, то есть транш **в статусе выхода**.

**(б) Как транш `MANAGING` попадает в статус выхода под каскадом.** У
обработчика сопровождения выходные проверки называют два триггера: «сработал
его шаг выхода» либо «экспозиция схлопнулась и переоткрытие запрещено».
Статуса сделки среди них нет. Дом запрета в строке `MANAGING` объясняет
переход тем, что «экспозиция обнулена **приписанным закрытием уровня
сделки**» — то есть закрытием, которое по (а) обязано произойти **после**
снятия входных заявок. Круг: закрытие ждёт снятия заявок, снятие ждёт
статуса выхода, статус выхода ждёт закрытия.

**(в) Строка «прочие нетерминальные» неверна для двух статусов.** Она
обещает «своим штатным выходом каскадом» всем прочим, но в матрице транша
из `ENTRY_FINALIZED` объявлены только `PROTECTION_SWITCHED`/`MANAGING`, а
из `PROTECTION_SWITCHED` — только `MANAGING`. Рёбер в выход и в терминал у
них нет.

**Грунт (торговый).** Не нужен: класс ущерба назван самим правилом
(«исполнившись после закрытия, такая заявка **открывает позицию
заново**»).

**Цитаты (носители).**

- `docs/rules/exit-teardown-order.md:9-12` — инвариант и его область
  («действует на обоих уровнях»); `:13-20` — довод («полное закрытие
  перестаёт быть финальным»); `:23-26` — таблица двух уровней;
  `:70-74` — таблица энфорсеров (строка `MANAGING` и строка «прочие

## A5. «Аварийный терминал приходит на усечённом графе» — основание трёх конструкций, опровергаемое их же спекой

**Вопрос.** Три конструкции последнего закрытия обоснованы одним и тем же
доводом: аварийный терминал приходит на **усечённой загрузке**, где
доступность итога ложна при законном числе. Довод опровергается соседним
конъюнктом той же спеки: `riskProvenAbsent` содержит `graphComplete`, и
`transitionAllowed` требует его для **обоих** терминалов. На усечённом
графе аварийное ребро не применяется вовсе — значит, состояние, которым
довод обоснован, для этого ребра недостижимо. Два примера спеки
(«аварийный терминал приходит на сделку с УЖЕ финализированным числом» и
парный к нему) стоя́т на `graphComplete: false`, то есть на состоянии,
где ребро запрещено, и `transitionAllowed` в них не проверяется.

**Грунт (торговый).** Не нужен.

**Цитаты (носители).**

- `docs/spec/deal-lifecycle.json` — `riskProvenAbsent`
  (`graphComplete && …`), `transitionAllowed`;
- `docs/spec/deal-lifecycle.json` — нота `emergencyTerminalContract`:
  «доступность пересчитывается каждым проходом и **на усечённой загрузке
  ложна**»; нота `benchmarkAvailabilityOnTerminal`: «аварийный терминал,
  приходящий на усечённом, пересчитывать её не вправе»;
- `docs/spec/deal-lifecycle.json` примеры 26 и 27 (`graphComplete: false`,
  нота примера 26 «аварийный терминал **приходит на усечённом**»);
- `docs/lifecycles/Deal.md:184-195` — «доступность пересчитывается каждым
  проходом и на усечённой загрузке ложна»;
- `docs/lifecycles/Deal.md:310-334` — та же посылка у третьей строки
  таблицы писателей («терминал пересчитывал все четыре признака **на
  усечённом графе**»);
- `docs/components/MarkDealEmergencyClosedExecutor.md` — трижды: «на
  проходе с усечённой загрузкой она ложна при том, что число законно»;
  «они записаны на полном графе, **а он приходит на усечённом**»;
  «застревала бы… на каждом проходе с усечённой загрузкой».

**Мутационная проба (обе стороны).** Проба A: аварийное ребро,
`resultProfitFinalized: true`, `graphComplete: false`, остальное чисто —
ожидание `emergencyTerminalContract: true`, `riskProvenAbsent: false`,
`transitionAllowed: false` **сошлось**. Проба B: то же на
`graphComplete: true` — `riskProvenAbsent: true`, `transitionAllowed: true`
**сошлось**. То есть контракт третьего дизъюнкта на усечённом графе не
работает не потому, что он неверен, а потому, что до него не доходит.

**Что остаётся верным.** Третий дизъюнкт и охранная ветвь признаков **не
вакуумны**: `resultAvailable` ложен и при полном графе — через
`allCloseRecordsFetched`, `flowsComplete` (на аварийной тропе звено добычи
движений не эмитится вовсе) и `rateBlocking`. То есть конструкции нужны, а
**названное основание у них ложное**.

**Почему гейтит.** Основание — не украшение: им обоснован выбор
дискриминатора ветки («ключ ветки — доступность итога, не добытость
положений закрытия») и отказ гейтить аварийную тропу терминальностью
траншей («по той же цене»). Писатель кода, читающий «терминал приходит на
усечённом графе», реализует аварийный контур как работающий при неполной
загрузке — а спека его запрёт (проба A). Расхождение дока с исполнимой
формой на тропе, которая по построению обязана доходить до финала.

**Уровень пробела.** Доказательство (пример стои́т на состоянии,
недостижимом для проверяемого ребра) поверх носителя (три дока несут одну
ложную посылку).

**Целевой док.** `docs/lifecycles/Deal.md` §«Терминальный контракт
финализации» + `docs/spec/deal-lifecycle.json` (ноты
`emergencyTerminalContract`, `benchmarkAvailabilityOnTerminal`, примеры
26/27) + `docs/components/MarkDealEmergencyClosedExecutor.md`.

**Ожидаемый владелец.** `solution-designer`.

**Трассировка.** Читал `Deal.md` §«Терминальный контракт» → сверял с

## A6. Охрана полнотой графа не введена терминалу транша, хотя он читает те же загружаемые коллекции

**Вопрос.** Последнее закрытие ввело охрану полнотой графа «симметрично
всем читателям агрегатов по загружаемым коллекциям». Терминал **сделки**
её получил (`riskProvenAbsent`). Терминал **транша** — нет: у
`deal-tranche-lifecycle` в операндах `graphComplete` отсутствует, а
`terminalContract = !trancheRiskBearing` считается по агрегатам
`trancheHasLiveEntryOrder` (`any` над `orders`) и
`trancheHasLiveProtection` (`any` над `protections`). Недогруженная живая
заявка или живая защита делают оба агрегата ложными молча, транш уходит в
`CLOSED`, и обработчика у него больше нет («Терминальный статус
обработчика не имеет») — живая сущность остаётся на бирже без
наблюдателя FSM.

**Грунт (торговый).** Не нужен.

**Цитаты (носители).**

- `docs/spec/deal-tranche-lifecycle.json` — блок `operands` (`graphComplete`
  отсутствует), `terminalContract`, `transitionAllowed`;
- `docs/spec/protection-coverage.json` — `trancheRiskBearing`,
  `trancheHasLiveEntryOrder` (`op: any` над `orders`),
  `trancheHasLiveProtection` (`op: any` над `protections`);
- `docs/spec/deal-lifecycle.json` — `riskProvenAbsent`, нота операнда
  `graphComplete`: «Охрана **СИММЕТРИЧНА** охране результата… и охране
  торгового исхода… на недогруженном графе «живых заявок нет» ложно
  молча — направление ошибки разрешающее»;
- `docs/spec/deal-context-load.json` — `coverageAnswerDistorted`,
  `exitAnswerDistorted` (направления искажения при неполноте названы, но
  для транша гейта нет);
- `docs/components/DealTrancheStateMachine.md` — «Терминальный статус
  обработчика не имеет»;
- `docs/lifecycles/DealTranche.md:106-136` — терминал транша и его
  контракт;
- `.claude/work/questions/open-questions.md` §CTX-Q1 — та же зона, вердикт
  «не гейтит» стои́т на направлении искажения у **правила сопоставления**
  (там оно запрещающее); у живых заявок и защит направление
  **противоположное**, и этим вердикт не покрыт.

**Почему гейтит.** Направление ошибки разрешающее: транш закрывается,
неся живую защиту или живую входную заявку. Довод, которым охрана введена
у сделки, дословно применим к траншу; несимметричность делает клейм
«симметрично всем читателям» ложным и оставляет писателю кода выбор без
записанного основания.

**Уровень пробела.** Концепция-стык: симметрия охраны — свойство пары
«сборщик контекста ↔ все читатели агрегатов», не одного читателя.

**Целевой док.** `docs/spec/deal-tranche-lifecycle.json`
(`terminalContract` / `transitionAllowed` + операнд) и
`docs/lifecycles/DealTranche.md` §«Терминал транша».

**Ожидаемый владелец.** `solution-designer`.

**Трассировка.** Сверял конъюнкты `riskProvenAbsent` с конъюнктами
`terminalContract` → выписал операнды обеих спек → проверил, какие
агрегаты читает `trancheRiskBearing` → сверил с нотой симметрии в
`deal-lifecycle.json` → сверил с вердиктом CTX-Q1 (покрывает другое
направление).

**Варианты.**

| Вариант | Что делает | Цена (правки / контекстная связность) |
|---|---|---|
| **Достаточность существующего носителя** — терминал сделки всё равно поймает (`dealRiskBearing` пересчитается по всем траншам, включая закрытые) | ловит **сделку**, не транш: транш уже терминален, обработчика нет, живая заявка не снимается никем; сделка при этом висит | 0 / — ; исход хуже, чем у охраны |
| **(а) добавить `graphComplete` конъюнктом в `terminalContract`** | симметрия восстановлена одним конъюнктом | операнд + конъюнкт + 1 падающий пример; связность низкая — признак берётся готовым с контекста, как у сделки |
| **(б) охрана на уровне машины транша** (не применять переход, если контекст неполон) | одна точка на все рёбра транша, не только терминал | § правила + клауза в `DealTrancheStateMachine.md`; больший след, но покрывает и переоткрытие, чей гейт `reopenPermitted` читает те же агрегаты |
| **(в) явно записать ограничение** — «терминал транша не охраняется полнотой; риск покрывается терминалом сделки» | 0 механики | цена **отложенная**: закрытый транш со снятой защитой — состояние, из которого выход только через поиск нарушений инвариантов; сравнение по правилу «записать против закрыть сразу» не в пользу записи |

**Ярлык исхода.** `варианты-с-креном` — крен на **(а)**: минимальный след,
дословно тот же ход, что уже сделан у сделки.

**Ярлык дефицита.** `работа`.
