# Проработка К-1 (расширенная развилка): универсальный REPLACE вместо AMEND

## На какой вопрос отвечает этот файл

Каков результат проработки варианта (г) развилки К-1 (`DOCS_CHECK_4`)
— запрет AMEND как доменной операции целиком и единый replace-путь
ремоделирования — против baseline (а) (узкий запрет только для
TRAILING_*): анализ по граням, семантика REPLACE, дельта правок,
крен. На валидацию пользователю; `GAPS_CLOSE_3` / `DOCS_CHECK_5` —
после валидации.

## Контекст

К-1 (`DOCS_CHECK_4`): концепция предлагает амендный путь ремодела
trailing, неисполнимый на бирже (И-3). Финализации по (а)/(б)/(в) не
было — пользователь расширил развилку вариантом **(г)**: AMEND
уходит из доменного словаря для **всех** типов (ордера и algo);
любое ремоделирование — универсальным путём replace (создать новый,
закрыть старый). Продуктовые вводные (входы, не предмет спора):
мультибиржевость впереди; amend биржеспецифичен, replace универсален;
REPLACE-only проще в поддержке и аудите; двойственность amend/replace
оценена как сложный путь; решить сейчас, не переделывать потом.

Роль: `solution-designer`; консультации — `integrator` (биржевая
фактура), торговая грань — по дистилляту. Ступень — Предложение:
ничего не финализируется.

## Сверка вводных с биржевой фактурой (integrator)

- **Amend неоднороден уже внутри одной биржи.** OKX: `amend-order`
  амендит ordinary orders; `amend-algos` — только Stop/Trigger;
  advance-семья (trailing/iceberg/twap) не амендится вовсе (И-3,
  офдок). То есть «матрица амендуемости» существует не только между
  биржами, но и между типами сущностей одной биржи — вводная о
  сложности дуальности подтверждается фактурой ещё до второй биржи.
- **Place + cancel — универсальные примитивы.** Оба у OKX
  задокументированы для обеих семей (`order.md`, `algo-order.md`;
  cancel advance — с пометкой И-2). Атомарного cancel-replace
  эндпоинта у OKX нет (поверхность — манифест) — окно между ногами
  управляется на нашей стороне **при любом** исходе развилки.
- **Rate-limit (OKX, контракты):** ноги replace тратят лимиты
  **разных** вёдер (place 60 req/2s и cancel 60 req/2s по
  User+Instrument; algo: order-algo 20 req/2s и cancel-algos
  20 orders/2s) — против одного ведра amend. Аккаунт-уровневый
  fill-ratio-лимит (`account-rate-limit.md`) считает **place и amend
  одинаково** (cancel бесплатен) → на аккаунт-уровне replace не
  дороже amend; на endpoint-уровне нагрузка размазывается. Каденс
  бота — свечной тик, единицы инструментов: на порядки ниже
  потолков. **Цена реальна, но нематериальна** для фазы 1; чувствительна
  только для HFT-каденса, которым бот не является.

## Scope: все AMEND, включая amend-order — подтверждается

Сужать (оставить amend ординарным ордерам) не предлагаю:

1. Остаточный amend сохраняет дуальность — ровно то, что (г)
   устраняет; универсальность домена ломается одной оставленной
   веткой.
2. Entry-ордера replace-безопасны: защитного окна нет (позиции ещё
   нет), цена — race на исполнение (ниже) и очередь (ниже).
3. Attached protection выражается без amend: до fill родителя —
   replace родительского ордера вместе с attach-настройками (окна
   защиты нет — позиции нет); после fill attached материализуется
   в standalone algo (`AttachedAlgoOrderStateResolver`) — дальше
   обычный algo-replace.
4. Единственный сильный аргумент за остаточный amend — атомарность
   защитного ремодела — закрывается порядком ног + reduce-only
   (ниже), который придётся строить в любом случае (трейлинг уже не
   амендится на OKX).

## Торговая грань: окно без защиты → порядок ног по риск-классу

Т-1 генерализуется: под (г) каждый защитный ремодел — две операции.
Грунт: позиция на плечевом перпе без стопа — путь к руине
(неограниченная ответственность без стопов → разорение с
вероятностью → 1 при бесконечной игре [Vince, введение, с. 6]; гэп
проходит промежуточные уровни [там же]).

**Правило порядка ног — по риск-классу действия (предложение):**

- **Protective (`positionReducingOnly = true`):**
  **place-new → подтверждение фактом (REFRESH) → cancel-old
  (`REPLACED_BY_STRATEGY`)**. Окна без защиты нет вообще; в окне —
  **двойная reduce-only защита**, безопасная по построению:
  reduce-only не может увеличить позицию (`reduce-only-invariant`:
  «бот строит exits на reduce-only-ордерах»); при сработке обеих на
  гэпе вторая закрывает остаток либо отклоняется на нулевой позиции;
  conditional/trigger algo маржу не морозят (`algo-order.md`:
  активы при постановке не морозятся). Это **обобщение уже принятого
  паттерна** `ProtectionSwitchedHandler` (standalone main protection
  подтверждена active → attached снята) на все защитные ремоделы.
- **Risk-creating (entry, не reduce-only):**
  **cancel-old → подтверждение терминала (REFRESH, вкл. разбор
  fill-race) → place-new**. Перекрытие недопустимо (двойной
  риск-объём); окно без живой entry — упущенный вход, не риск.
  Fill-race разрешается фактами: cancel вернул «уже исполнен» →
  ремодел неактуален (`SKIPPED`); частичное исполнение → отмена
  остатка, новая сущность на пересчитанный остаток (калькулятор
  работает от контекста; эджи — CODE).

Риск-класс действия уже есть в модели (`positionReducingOnly`
выводится из назначения — `Strategy.md`) — новое поле не требуется.

**Ключевое для сравнения с (а):** окно-менеджмент (порядок ног,
двойная reduce-only защита) обязателен **и в baseline (а)** —
трейлинг-ремодел на OKX уже только replace (И-3), биржи без amend —
тем более. (а) не избавляет от паттерна — лишь сужает его
применение, оставляя вторую (амендную) ветку навсегда.

## Очередь / приоритет лимитных ордеров

Корпус тезисов о приоритете очереди не несёт (дистиллят
`microstructure.md` — очередь не покрыта; единственное упоминание —
блокчейн-мемпул, не наш кейс). **Предполагаю** (инженерно, помечено):
ремодел почти всегда меняет **цену** — а смена цены теряет место в
очереди и при amend (перестановка на новый уровень); приоритет
сохраняет только amend с уменьшением размера на той же цене —
краевой кейс, не паттерн стратегии. Класс стратегии — свечной
тренд-фоллоинг, вход от уровней с офсетом (`StrategyPricePlacement`),
не борьба за очередь маркет-мейкера. **Нерелевантно классу
стратегии**; чувствительность к очереди появилась бы только с
HFT/MM-стратегиями, которых в роадмапе нет.

## Семантика REPLACE в домене

### Под-развилка (г-1)/(г-2): команда или оркестрация

- **(г-1) `REPLACE_ORDER`/`REPLACE_ALGO_ORDER` как
  `ServiceCommandType`:** один executor делает обе ноги. Против
  канона: команда трогает **две** сущности («одна команда — одна
  простая операция», `command-lifecycle`; гранулярность CMD-Q3);
  безопасный порядок требует подтверждения ноги **фактом**, не ACK
  («ACK не runtime truth») → внутри executor'а пришлось бы либо
  секвенсить по ACK (нарушение инварианта в защитно-критичном
  месте), либо встроить refresh-цикл и продублировать
  submit/cancel/refresh-дисциплины (жирный executor). Прецедент F1
  (мульти-вызов внутри команды) — про **read**-цикл одной сущности,
  не про две write-операции.
- **(г-2) REPLACE как оркестрация атомарных команд:** канон уже
  говорит ровно это — «составные процессы (graceful shutdown,
  protection switch, safety-flow) раскладываются на атомарные
  команды и переходы FSM» (`command-lifecycle`), «protection switch
  … собираются из существующих команд — отдельных типов под них
  нет» (`ServiceCommand.md`), «replace-flow собирается отдельными
  атомарными командами вне этого executor'а»
  (`AmendAlgoOrderExecutor.md`). Последовательность ног идёт через
  существующие `CREATE_*`/`SUBMIT_*`/`REFRESH_*`/`CANCEL_*`,
  секвенсится FSM по фактам («одна актуальная команда за проход»),
  recovery после рестарта — штатный (`DealActionState` + facts).

**Крен — (г-2).** Уточнение терминологии к постановке: REPLACE
живёт как операция **доменного словаря стратегии/действий**
(`StrategyActionType: CREATE / REPLACE / CANCEL`), а не как значение
`ServiceCommandType`; командный enum остаётся атомарным,
`AMEND_ORDER`/`AMEND_ALGO_ORDER` из него **уходят** (19 → 17
значений). «AMEND из доменного словаря уходит» выполняется; буква
«доменная команда называется REPLACE» трансформируется в «доменное
действие REPLACE» — расхождение с постановкой проговорено, не
замолчано.

### Identity, lifecycle, аудит

- **Новая сущность** с новым `internalId` (= новый
  `clOrdId`/`algoClOrdId`) — вся существующая submit-retry
  дисциплина по stable client id сохраняется без изменений.
- **Связь цепочки:** `replacesInternalId` на новой сущности
  (указатель на предшественника; nullable). Обратная ссылка не
  хранится — выводится запросом (append-only след, сущности-звенья
  неизменяемы).
- **Старая сущность:** `Status = CANCELED`,
  `closeReason = REPLACED_BY_STRATEGY` — у `AlgoOrder` это значение
  **уже есть** («стратегия заменила другим algo-order»); у `Order` —
  добавить симметрично. Новых статусов lifecycle не требуется.
- **Аудит:** amend мутирует параметры на месте (история — только в
  audit-слое); replace оставляет неизменяемую цепочку сущностей —
  след самодокументируется (подтверждает продуктовую вводную «проще
  для аудита»; согласуется с `audit-not-runtime-source`).

### Strategy-actions и валидация

- `actionType`: `CREATE / AMEND / CANCEL` → `CREATE / REPLACE /
  CANCEL`; REPLACE-action несёт ту же палитру настроек, что CREATE
  (полное новое желаемое состояние) — как AMEND сейчас.
- Правила валидации 6/7: «ORDER/ALGO_ORDER REPLACE/CANCEL ссылаются
  на … CREATE». `targetActionKey` без изменений.
- **Резолюция цели по цепочке (новое правило):** REPLACE/CANCEL
  через `targetActionKey` ссылаются на CREATE-action; рантайм
  резолвит **актуальную** сущность как последнее звено цепочки
  замещений от target-action (через `DealActionState` target-action
  → сущность → вперёд по `replacesInternalId`). При AMEND вопрос не
  существовал (identity не менялась) — при REPLACE правило
  обязательно.

### DealActionState и фабрика

REPLACE-action ведёт себя как CREATE-надмножество: порождает новую
сущность (`target` = новая) плюс cancel-нога по старой. Новых
статусов `DealActionStateStatus` не предлагаю: фабрика выводит
следующую команду **из фактов** (новой нет → `CREATE_*`; не
отправлена → `SUBMIT_*`; новая ACTIVE и старая жива → `CANCEL_*`
старой с reason `REPLACED_BY_STRATEGY`; старая терминальна →
`COMPLETED`) — в духе «пересобирает нужную команду по status +
target + exchange facts». Для entry-порядка — зеркально
(cancel-нога первой). Старая сущность резолвится из
`DealContext.actionStates` по цепочке (см. резолюцию выше).
*Альтернатива*, если на CODE вывод из фактов окажется мутным, —
явные фазы replace на `DealActionState`; решать на CODE, концепцию
не блокирует.

### Executors / payloads

`AmendOrderExecutor` + `AmendOrderCommandPayload`,
`AmendAlgoOrderExecutor` + `AmendAlgoOrderCommandPayload` —
**удаляются** (вместе с `newTrailingPrice` — ядро К-1). Новых
executors **нет** (ноги — существующие). `cancelOnFail`/`reqId`
амендные тонкости уходят вместе с амендом.

## Сравнение с baseline (а)

| Ось | (а) узкий запрет TRAILING_* | (г) REPLACE-only |
|---|---|---|
| Дуальность ремодела | остаётся навсегда (amend жив для ordinary + Stop/Trigger) | уходит — один путь |
| Мультибиржевость | матрица «что амендуемо где» течёт в домен/валидацию | place+cancel есть везде; матрицы нет |
| Окно защиты | паттерн нужен только trailing-ремоделу | паттерн по умолчанию, закрыт place-first + reduce-only (нужен и в (а)) |
| Очередь лимиток | сохраняется в краевом кейсе (size-down) | теряется; нерелевантно классу стратегии |
| Rate-limit | 1 вызов, 1 ведро | 2 вызова в разных вёдрах; аккаунт-уровнево равно |
| Аудит ремодела | мутация на месте + audit-слой | append-only цепочка сущностей |
| Дельта концепции сейчас | ~3-4 дока (оговорки) | ~12 доков + дельта кода на CODE |
| Сложность навсегда | две ветки исполнения | одна ветка |

## Итог — на валидацию пользователю

**Крен — принять (г) в форме (г-2):**

1. **(г) против (а)-baseline:** дуальность уходит, домен
   универсален; цены ((окно — закрыто порядком ног и reduce-only,
   причём паттерн обязателен и в (а); rate-limit — нематериален;
   очередь — нерелевантна классу стратегии)) приемлемы и оплачены
   аргументированно. Рекомендую (г).
2. **Форма (г-2):** REPLACE — действие доменного словаря стратегии
   (`StrategyActionType.REPLACE`), исполняемое оркестрацией
   существующих атомарных команд; `AMEND_*` уходят из
   `ServiceCommandType` (17 значений); отдельной REPLACE-команды нет
   — это буквальное следование уже принятому канону командного слоя.
   (Альтернатива (г-1) — REPLACE-команда с двумя write-ногами —
   отвергается: ломает гранулярность и втягивает ACK-секвенс либо
   жирный executor.)
3. **Торговое правило порядка ног:** protective — place-new →
   подтверждение фактом → cancel-old (двойная reduce-only защита в
   окне — безопасна, обобщение protection-switch); entry —
   cancel-old → подтверждение (fill-race по фактам) → place-new.

После валидации: `GAPS_CLOSE_3` (дельта выше + закрытие К-1/Т-1 и
И-3-следствий) → подтверждающий `DOCS_CHECK_5`.

## Исход валидации (2026-06-11)

**Чистая валидация** — крен принят пользователем без правки по
существу, все три пункта: (1) полный scope (г), вкл. `amend-order`;
(2) форма (г-2) — REPLACE как `StrategyActionType`, `AMEND_*` сняты
из `ServiceCommandType` (19 → 17), отдельной REPLACE-команды нет;
(3) порядок ног по риск-классу. Дельта исполнена на `GAPS_CLOSE_3`
(2026-06-11); рационал и отвергнутые альтернативы зафиксированы —
`docs/decisions/replace-not-amend.md`. К-1/Т-1 и следствие И-3
закрыты; подтверждение — `DOCS_CHECK_5`.
