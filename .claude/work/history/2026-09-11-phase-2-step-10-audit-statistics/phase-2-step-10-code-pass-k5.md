# Кодовый заход K5 шага 10 фазы 2 — чистка журнала

## На какой вопрос отвечает этот файл

Чем предъявлен кодовый заход по компоненту K5 шага 10 фазы 2.

## Единица работы и её заходы

Единица — **один кодовый заход** по одному компоненту реестра
(`.claude/rules/session-work-unit.md`). Компонент — K5
(`audit-statistics: чистка журнала`), позиции 8 и 33 дельты `CODE`.

**Почему K5.** Естественный следующий назван заходом K4 и снапшотом v199:
его предмет — **единственный писатель снятия** у момента разрыва, и он же
второй потребитель оси `journalRetentionProfile`, которая до сервиса уже
доезжает. Альтернатива (K7/K8, выборки чтения) приводит второе отображение
схемы на классы и первого читателя строк состояния — то есть больший заход.
K10 по-прежнему не берётся одной единицей (Д1215).

| Заход | Состояние |
|---|---|
| кодовый заход K5 (корпусный) | `записан` — §«Классификация правки по родам» |

Раунда критики и доработки у единицы этого рода нет: корпус она меняет одной
партией, а исход её правок мерит не чтение, а прогон — реактор, тесты модуля,
двенадцать мутационных проб кода и живой прогон одиннадцати утверждений SQL с

### Чего заход НЕ строил, и почему это названо

- **Джобы пересчёта агрегатов (K6) нет.** Чистка область пересчёта сужает
  **косвенно** — двигая вперёд самую раннюю уцелевшую строку, — а сам отбор
  пересчёта живёт у своего дома и приедет со своим компонентом, у которого
  ещё и своя тропа к базе агрегатов.
- **Экспортёра метрик и правил алерта (K9) нет.** Порог по паре по-прежнему
  лежит снимком в памяти с захода K4; чистка ни одной экспортируемой величины
  не производит.
- **Предела журнального окна чтения заход не вводит.** Это величина
  конфигурации **читающей** поверхности (K7), и приезжает она с тем, кто окно
  и проверяет; вводить её сейчас значило бы завести число без читателя.
- **Ручного триггера у джобы нет** — по доводу сервиса, а не по забывчивости:
  поверхность объявлена только читающей. Отсюда же нет `@EnableAsync`.
- **Живого прогона на стенде нет.** Проверены схема и запросы на одноразовом
  Postgres 16; стенд от дерева кода отстаёт с захода K1, и ограничение то же,
  что у K2-K4, — оно не сузилось.
- **Ключа конфигурации в манифесте сервиса заход не заводит.** Величины чистки
  читаются с умолчаниями из `application.yaml` формой `${VAR:умолчание}`;
  манифестный ключ завёл бы **второй** носитель того же числа, а калибровка
  владельцем добавит переменную окружения тем же ходом, что и назначит
  значение.

## Чем предъявлено, а не прочитано

### Живой прогон одиннадцати утверждений SQL

Одноразовый Postgres 16; **запросы берутся из тела репозиториев**, а не
переписываются в пробнике: сборщик извлекает их по имени метода и связывает
именованные параметры литералами (несвязанный параметр — отказ сборки).
Нативные идут как есть; **два чтения — запросы по отображению, и сборщик
переводит их в SQL по `@Table`/`@Column` самих сущностей**, своей копии имён не
держа. Что перевод идёт именно за отображением, доказано отдельной мутацией
(M-SQL-8: атрибут переставлен на чужую колонку — красными стали три
утверждения). Цепочка журнала применяется так же, как её применяет Flyway.

```bash
export MSYS_NO_PATHCONV=1
CT=k5probe
CHAIN=services/audit-statistics/src/main/resources/db/migration/audit/V1__audit_baseline.sql
docker rm -f "$CT" >/dev/null 2>&1
docker run -d --name "$CT" -e POSTGRES_PASSWORD=probe postgres:16 >/dev/null
until docker exec "$CT" pg_isready -U postgres >/dev/null 2>&1; do sleep 1; done
docker exec -i "$CT" psql -U postgres -v ON_ERROR_STOP=1 -q <<'SQL'
create role audit login password 'probe-audit';
create role statistics login password 'probe-statistics';
create database audit owner audit;
SQL
sed 's/[$]{statisticsRole}/statistics/g' "$CHAIN" > tmp-audit.sql
docker cp tmp-audit.sql "$CT":/tmp/audit.sql >/dev/null
docker exec "$CT" psql -U audit -d audit -v ON_ERROR_STOP=1 -q -f /tmp/audit.sql
py tmp-k5-probe-build.py
docker cp tmp-k5-probe.sql "$CT":/tmp/probe.sql >/dev/null
docker exec "$CT" psql -U audit -d audit -q -f /tmp/probe.sql
```

Сценарий: шесть строк журнала, из них **у одной оси времени расходятся**
(произошла раньше глубины, принята позже неё); три порции удаления подряд
порцией в две строки; четыре строки состояния — подписанная с разрывом раньше
границы, **снятая с подписки** с позднейшим моментом наблюдения и разрывом
ровно на границе, третья с разрывом позже границы и строка **соседней
группы**.

| Проба | Что утверждает | Исход |
|---|---|---|
| П1 | первая порция удалила ровно две строки, третья старая жива — порция ограничена | `true` |
| П2 | вторая порция добрала остаток: старых не осталось | `true` |
| П3 | третья порция не удалила ничего — отбор исчерпан | `true` |
| П4 | строка, **произошедшая** раньше глубины и **принятая** позже неё, уцелела | `true` |
| П5 | самый ранний момент приёма уцелевших — новая граница ряда | `true` |
| П6 | позднейший момент наблюдения взят и по строке, **снятой с подписки** | `true` |
| П7 | разрыв раньше границы погашен | `true` |
| П8 | разрыв **ровно на границе** не погашен: сравнение строгое | `true` |
| П9 | разрыв позже границы не погашен | `true` |
| П10 | строка соседней группы не тронута | `true` |
| П11 | у правленой пары не тронуты момент обновления, момент наблюдения, признак подписки, флаг остановки и момент последнего принятого | `true` |

**Утверждения непусты по построению.** Первая редакция пробника сравнивала
момент напрямую, и у погашенной колонки сравнение давало **пустоту**, а не
ложь: две мутации (`M-SQL-4`, `M-SQL-5`) прошли зелёными. Каждое утверждение
обёрнуто `coalesce(…, false)`, а исходом «красный» считается всё, что не `t`.
Это дефект **пробника**, найденный мутацией и ею же закрытый, — ровно то, ради
чего мутационная проба и ставится.

**Мутационные пробы SQL идут по ИСХОДНИКУ, а не по пробнику** — правится тело
репозитория, пробник пересобирается из него заново:

| Проба | Что нейтрализовано | Что упало |
|---|---|---|
| M-SQL-1 | отбор по глубине снят — удаляется что попало | П2, П3, П4, П5 |
| M-SQL-2 | порция снята — проход правит без предела | П1 |
| M-SQL-3 | глубина отсчитывается по моменту происшествия, а не приёма | П2, П3, П4, П5, П8 |
| M-SQL-4 | момент, равный границе, гасится | П8 |
| M-SQL-5 | снятие перестало фильтровать по группе | П10 |
| M-SQL-6 | чистка двигает момент обновления — величину чужого писателя | П11 |
| M-SQL-7 | позднейший момент наблюдения берётся только по подписанным парам | П6 |
| M-SQL-8 | отображение атрибута уехало на чужую колонку — перевод идёт за ним | П6, П8, П9 |

Контроли до мутаций и после восстановления — зелёные.

**Названное ограничение живого прогона.** Это Postgres 16 в одноразовом
контейнере, а не стенд и не образ окружения (PostgreSQL 17 с TimescaleDB);
брокера в прогоне нет вовсе, и объёма, на котором порционность имела бы цену,
тоже: порция проверена **пределом отбора**, а не нагрузкой.

### Замер, снявший тип скалярного чтения с догадки

**Оба чтения границы сперва были написаны нативными — и это был дефект,
найденный замером, а не чтением.** У нативного скалярного запроса тип
результата выводится из метаданных JDBC, а не из отображения; замер драйвером
показал, чем он выводится на самом деле:

```bash
docker run -d --name k5type -p 15432:5432 -e POSTGRES_PASSWORD=probe postgres:16
docker exec -i k5type psql -U postgres -q \
  -c "create table t (m timestamptz); insert into t values (now());"
jshell --class-path "<postgresql-42.7.8.jar>" /tmp/k5type.jsh
```

Выдача: `sqlType=93 columnClassName=java.sql.Timestamp`,
`getObject=java.sql.Timestamp`. То есть драйвер объявляет `min(timestamptz)`
кодом **93** (`TIMESTAMP`), а не 2014 (`TIMESTAMP_WITH_TIMEZONE`), и отдаёт
`java.sql.Timestamp` — **без смещения**. Объявленный `OffsetDateTime` держался
бы на преобразовании, которого никто не назначал, а ошибка пришла бы
**смещением времени**, то есть тихо: граница полноты уехала бы на часовой пояс
машины, и клейм «журнал полон по событиям, произведённым после X» стал бы
ложен в разрешающую сторону.

**Оба чтения переписаны запросами по отображению** (`@Query` без
`nativeQuery`), где тип берётся из самой сущности и выводить его неоткуда.
Записи остались нативными: им нужны `limit` в подзапросе удаления и форма
обновления, которых у отображения нет. Прецедента нативного скалярного чтения
в дереве не было ни одного — этот был бы первым.

**Разбора самого запроса по отображению ни один тест не делает, и это
названо:** контекста с фабрикой сущностей в тестах модуля нет (проба
подключений поднимает только источники данных). Имена сущности и атрибутов при
этом сверяет **сборщик пробника**: неразобранная сущность и атрибут вне
отображения — отказ сборки, а M-SQL-8 показывает, что сверка идёт за
отображением, а не за копией имён. Остаток — синтаксис HQL; он падает при
старте сервиса, то есть громко.

повторный вызов проходил у невозвращённого замка — тест мерил reentrancy, а не
отпускание. Обе пробы переписаны на второй поток (планировщик и бьёт своим), и
мутация стала красной. Класс тот же, что корпус называет у подменённого
предиката (`.claude/rules/codestyle.md` §«Тесты доменных моделей»): проба,

## Решения захода

| # | Развилка | Что отвергнуто | Почему выбрано так |
|---|---|---|---|
| Д1249 | ось отсчёта глубины — **момент приёма** (`recorded_at`) | момент происшествия (`occurred_at`) — читается естественнее и покрыт своим индексом | на оси приёма стои́т **чужой** клейм: отбор пересчёта агрегатов утверждает, что у всякой удалённой строки момент приёма меньше самого раннего уцелевшего. На оси происшествия он ложен — событие, доставленное с опозданием, ушло бы раньше принятой прежде него соседки. Ось внесена в дом величины тем же ходом |
| Д1250 | критерий снятия момента разрыва — **нижняя граница полноты**, а не глубина | «разрыв старше глубины» — так короче и так стои́т в трёх носителях деталей | так говорит дом (`docs/models/domain/other/AuditRecord.md` §«Момент разрыва вместо признака разрыва — решение, а не форма записи», `docs/spec/audit-journal.json`), а сокращение строже: граница не раньше глубины, и по глубине предикат непрерывности остался бы ложным у пары, чьей дыры в обещаемом ряду уже нет. Три носителя сведены к дому |
| Д1251 | сравнение с границей **строгое** (`<`) | нестрогое (`<=`) | момент, равный границе, лежит на её краю, и удержанный разрыв обещает **меньше**, а погашенный — больше. Направление ошибки выбрано в сторону меньшего обещания; пробой оно закреплено (П8, M-SQL-4) |
| Д1252 | пустая ось — **проход не идёт**, плюс предупреждение | пусто ⇒ чистить (умолчание в сторону работы); пусто ⇒ падать при старте | удаление необратимо: чистить по значению, которого никто не назначал, значило бы терять журнал по недоразумению. Падение старта уронило бы **читающую** поверхность из-за величины, которая ей не нужна. Предупреждение отличает дефект развёртывания от назначенного `UNBOUNDED` |
| Д1253 | нижняя граница полноты — **отдельный носитель** (`JournalCompletenessService`) | посчитать её внутри чистки; отложить до K7 и написать там заново | читателей у величины двое, и второй (выборки чтения) отдаёт её с **каждой** выдачей чисел. Вторая реализация той же свёртки разошлась бы с первой молча (`.claude/rules/policy-home.md`); дом формы при этом остаётся спекой, а класс — её единственным носителем в коде |
| Д1254 | размер порции — **константа кода**, а не величина конфигурации | вынести в конфигурацию, как окно реле outbox у `strategies` | исход прохода от неё не зависит: проход идёт, пока старее глубины ничего не остаётся. У окна реле предмет другой — оно ограничивает **объём работы тика**. Дом довода — компонент-док, и заход его исполняет |
| Д1255 | признак конца прохода — **неполная порция** | «пока удалено больше нуля» | исход тот же, а лишний пустой запрос на каждый проход не делается: полная порция означает, что подходящих строк было не меньше её размера |
| Д1256 | своя копия `JobExecutionGuard` у модуля | вынести охрану в общую библиотеку (четвёртая копия в дереве) | библиотека к базе не ходит и инфраструктуры не держит; охрана — три десятка строк без предмета для расхождения, а зависимость на общий артефакт стала бы обязательной для всех сервисов (`.claude/rules/codestyle.md` §«Новый модуль монорепозитория»). Копия объявлена, а не заведена молча |
| Д1257 | форма конфигурации чистки объявлена **на точке входа**, а не в своей `@Configuration` | завести `JournalCleanupConfig` ради регистрации | конфигурация-владелец бывает у формы, которая что-то **настраивает** (клиент брокера, подключения); у чистки настраивать нечего, и пустой класс был бы носителем без предмета. Форма встала рядом с осями окружения — по тому же признаку |
| Д1258 | ключа конфигурации в манифесте сервиса заход не заводит | положить `JOB_JOURNAL_CLEANUP_DEPTH_DAYS` в манифест сразу | число тогда стояло бы в двух местах, а `${VAR:умолчание}` уже принимает его от владельца. Калибровка добавит переменную тем же ходом, что и назначит значение |
| Д1259 | **скалярные чтения границы — запросами по отображению, записи — нативными** | оставить оба чтения нативными, как соседние запросы модуля; объявить возвращаемым типом `java.sql.Timestamp` | замер драйвером: `min(timestamptz)` объявлен кодом 93 (`TIMESTAMP`) и отдаётся `java.sql.Timestamp` **без смещения**, а тип нативного скаляра выводится из метаданных JDBC. Ошибка пришла бы смещением времени, то есть тихо, и в разрешающую сторону. У запроса по отображению тип берётся из сущности; записям же нужны `limit` в подзапросе и форма обновления, которых у отображения нет |
