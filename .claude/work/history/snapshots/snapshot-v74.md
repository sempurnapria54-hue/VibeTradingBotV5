## Живой контекст: что открыто по развилке (валидация 3)

1. **Подтверждённый факт звена — по пяти действиям** (§6 проработки).
   `FINALIZE_DEAL_EXIT_ACTION` и `FINALIZE_DEAL_ERROR_ACTION` выводимы из
   `Deal` (число/статус). Решений требуют: `FINALIZE_DEAL_ENTRY_ACTION` —
   **носитель факта не назван** (доки описывают запись как
   «консолидированный результат входа», поля не называя; крен — статус
   строки действия с записанной клаузой); `REFRESH_DEAL_CONTEXT_ACTION` —
   нужна **метка подтверждения** (refresh не меняет данных, если факт не
   изменился; крен — метка на строке-владельце по принципу «свежесть
   измеряется»), и она **упирается в узел 7**, который открыт.
2. **Развязки `KILL_SWITCH_ACTION`** (§7): scope-уровневый kill-switch
   (`fireInstrument`/`fireExchange` каскадом по сделкам) против
   deal-scoped строки — крен «строка на каждую сделку каскада» с двумя
   названными дырами (одно событие размазано по N строк; при холде без
   живых сделок строки нет вовсе); **три счётчика** (серия-триггер
   инструмент-scope / внутренний `kill-switch.max-teardown-attempts` =
   3 / бюджет действия) — крен «два уровня остаются, действие —
   **учётная обёртка**, не оркестратор» (иначе аварийный teardown
   становится loop-driven вопреки `action-orchestration-vs-command.md`);
   терминальный контракт при исчерпании — `FAILED` не транслируется в
   тропу сделки и **не поднимает новую реакцию холда** (иначе рекурсия);
   лимит из конфига **не резолвится** политикой, ключуемой типом
   команды, — kill-switch не команда (крен — политика per action type,
   уточняет, а не отменяет «per command»).
3. **`StrategyActionType` под суффиксным правилом** — крен «не трогать»
   (вид узла авторского дерева, другая ось), но значения **persisted**
   (`strategy_actions.action_type`) и видны во внешнем Strategy API ⇒
   решение за пользователем.

## Живой контекст: находки, живущие независимо от развилки

- **Дефект ключа шага 4.** `UNIQUE(deal_id, strategy_action_id)` +
  единственный резолв `findByDealIdAndStrategyActionId`: второй ноге
  грида некуда лечь, `attemptCount` общий, `target` перетирается.
  Чинится этой правкой (В2.6).
- **Пустая секция retry-конфига (новое, §5.2).** Механизм построен
  (`ServiceCommandRetryProperties`, `@ConfigurationPropertiesScan`,
  чтение живьём), но секции `service-command-retry` **нет ни в одном
  конфиге** ⇒ `getPolicy` возвращает `null`, `canRetry` падает **NPE** —
  и падает в **catch-ветке** `ServiceCommandExecutor.execute`, подменяя
  исходную ошибку и не доводя retry-учёт. Пункт `CODE`.
