# Дизайн реактивных холдов L3/L4-CRITICAL (шаг 6) — отчёт

## На какой вопрос отвечает этот файл

Как устроена реактивная реакция CRITICAL-холда уровней L3 (инструмент) /
L4 (биржа) на шаге 6: локус решения, последовательность с привязкой к
`AnomalyReport` и kill-switch, enforcement и каскад, достаточность модели
`AnomalyReport`. Отчёт для валидации пользователем; доки/код в этом заходе
не правятся.

## Контекст и главный рефрейм

Прежний `CODE` шага 6 отложил подсистему холдов целиком (deferral D2),
оставив `KillSwitchExecutor` без эмитента. Обоснование D2 опиралось на то,
что **вся** реакция холда зависит от шага 8 (`AnomalyJob` ops) и backlog
п.9 (status-lifecycle). Это смешало два разных контура:

- **Реактивный контур (этот дизайн, шаг 6).** Триггерится конкретной
  сделкой в проходе оркестратора: handler классифицировал CRITICAL,
  оркестратор координирует холд + журнал + kill-switch. Строится на уже
  описанном: модель/lifecycle `AnomalyReport` (доки есть), `KillSwitchExecutor`
  (код есть), терминал `ERROR` сделки (код есть), graceful-shutdown
  `EXCHANGE_HOLD`/`RISK_POLICY` (енумы `Deal.ShutdownReason` уже есть),
  сериализация прохода advisory-локом D-M1 (`OrchestratorPassLock`, код есть).
- **Проактивный контур (остаётся шаг 8).** `AnomalyJob` по расписанию +
  `TradeRuleValidator` широко сканируют расхождение локального и биржевого
  состояния; численные пороги («серия неудач подряд» — STRUCT-Q1)
  калибруются бэктестом.

Вывод: реактивный enforcement холда **построяем сейчас**; в шаг 8 уходит
только проактивная детекция и численные пороги. D2 в части реактивного
контура снимается этим дизайном. Единственная требуемая сверка модели —
`AnomalyReport` (см. §8).

## Границы захода

- Только severity = `CRITICAL`, уровни L3/L4. `NON_CRITICAL` и уровни L1/L2
  — вне захода.
- Численные пороги срабатывания и проактивный детектор аномалий — шаг 8.
- Авто-снятие холда не проектируется (его нет как сущности; снятие —
  только ручное).
- Доки (`instrument-hold.md` / `exchange-hold.md` / `error-handling-policy.md`
  и др.) и код в этом заходе **не правятся** — устаревший deferral в доках
  снимется общим `SYNC_DOCS_FROM_CODE`.

## 1. Локус и координатор

### Кто что делает

| Роль | Кто | Что |
|---|---|---|
| Классификация CRITICAL + увод **своей** сделки в `ERROR` + сигнал | FSM-handler | возвращает `DealTransition`: `MARK_DEAL_ERROR` (своя сделка → `ERROR`) **и** `holdSignal` |
| Решение и оркестрация реакции (над сделкой) | оркестратор-проход (`DealOrchestratorJob`) → `SafetyHoldCoordinator` | идемпотентность, порядок шагов, диспатч исполнителям |
| Исполнение | `Instrument/ExchangeDataService` (HOLD), `AnomalyReportService` (журнал + слепки), `ServiceCommandExecutor`→`KillSwitchExecutor` (kill-switch) | атомарные операции |

### Сигнал

`DealTransition` расширяется опциональным `HoldSignal`:

```text
HoldSignal { Scope scope; String code; }   Scope ∈ { INSTRUMENT(L3), EXCHANGE(L4) }
```

Severity не носим — в этом контуре она по определению `CRITICAL` (граница
захода). Handler, обнаруживший CRITICAL-условие, возвращает транзишн, где
одновременно: команда `MARK_DEAL_ERROR` (своя сделка уходит в `ERROR`
существующим механизмом) **и** `holdSignal{scope, code}`. Сигнал — это
«подними холд scope», а не «закрой мою сделку»: вторую часть делает
обычный терминал сделки (§9).

### Где принимается решение

В проходе оркестратора, в `DealOrchestratorJob.processDeal`, **после**
`applyTransition` (своя сделка переведена в `ERROR`): если
`transition.getHoldSignal()` присутствует — проход делегирует сигнал
`SafetyHoldCoordinator` (новый сервис «над сделкой»). Координатор —
держатель решения; HOLD-статус, `AnomalyReport`, kill-switch исполняют
сервисы. Решение на уровне прохода, а не внутри handler'а, потому что
handler видит только свою сделку, а холд — инструмент-/биржа-широкий
(особенно каскад L4).

### Идемпотентность «один раз на инструмент/биржу»

- Проход сериализован advisory-локом D-M1 (`OrchestratorPassLock`) → двух
  параллельных проходов нет → межпроходных гонок нет.
- Внутри прохода координатор **перед** действием читает текущий HOLD-статус
  scope: instrument уже в safety-HOLD (L3) / exchange уже в HOLD (L4) →
  пропуск (реакция уже идёт/прошла).
- **HOLD ставится первым** (до `AnomalyReport`/kill-switch) → следующий
  сигнал того же scope в том же проходе видит HOLD и пропускается. Анкер
  идемпотентности и enforcement-гейт — одно и то же поле. Это и есть
  «идемпотентно по статусу HOLD» из сида.
- Межпроходно: scope в HOLD больше не триггерит (холд держится до ручного
  снятия). Возобновление прерванной краш-ем реакции (полуготовый отчёт) —
  по `AnomalyReport.status` (механика lifecycle уже описана; проактивный
  подъём — шаг 8).

### Замечание о конкурентности с `EntryScannerJob`

`EntryScannerJob` крутится на своём расписании под собственным in-memory
`JobExecutionGuard`, **не** под advisory-локом прохода. Поэтому HOLD,
выставленный в проходе, для сканера действует со следующего скана
(eventually consistent в пределах тика). Сходимость гарантируют: (а)
kill-switch fire-all снимает риск немедленно вне зависимости от порядка;
(б) HOLD-гейт действует на все последующие сканы/проходы; (в) gatekeeper
«одна сделка на инструмент» закрывает окно по триггерному инструменту
(сделка-триггер ещё активна в `ERROR`).

## 2. Последовательность L3 (инструмент)

Привязка к существующему lifecycle `AnomalyReport`
(`CREATED → IN_PROGRESS → KILL_SWITCH_EXECUTED → COMPLETED`), kill-switch
встроен между слепками:

1. **Идемпотентность.** Инструмент уже в safety-HOLD → пропуск.
2. **HOLD инструмента первым.** Enforcement-гейт поднят немедленно (и это
   анкер идемпотентности): новые входы/наращивание по инструменту
   блокированы до того, как начнётся teardown.
3. **`AnomalyReport` `CREATED`.** `exchangeId`, `instrumentId`,
   `severity=CRITICAL`, `code`, `scope=INSTRUMENT`; `internalBefore` (БД:
   активная `Deal`+граф, `Position`, pending `Order`/`AlgoOrder`, статус
   инструмента) + `externalBefore` (биржа: позиции, pending orders, active
   algos по instId, orphan-сущности).
4. `status → IN_PROGRESS`.
5. **Scoped kill-switch (команда, скоуп инструмент).** `EXECUTE_KILL_SWITCH`
   по инструменту: close позиции первым → cancel orders → cancel algo-защит
   **последними** → безусловный финальный close (порядок владеет
   `KillSwitchExecutor`, §6).
6. `status → KILL_SWITCH_EXECUTED`.
7. **`internalAfter` + `externalAfter`** (повторное чтение БД + биржи; факт
   снятия — через `REFRESH_*`, ACK не truth). Остаточный риск частичного
   kill-switch виден в `externalAfter`.
8. `status → COMPLETED`.
9. **Enforcement в силе.** Инструмент в safety-HOLD → `EntryScannerJob`
   пропускает; normal-flow по инструменту гейтится. Сделка-триггер уже в
   `ERROR` → `ErrorHandler` доводит её до `EMERGENCY_CLOSED` своим
   терминальным путём на следующих проходах (§9).

Замечание о порядке «HOLD первым vs before-слепок». HOLD ставится до
создания отчёта, поэтому `internalBefore` фиксирует статус инструмента уже
`HOLD` (первый шаг реакции). Риск-картина (позиции/ордера) в before-слепке
— **до** kill-switch, что и нужно для записи инцидента.

## 3. Последовательность L4 (биржа) + каскад

Та же форма, скоуп — биржа:

1. **Идемпотентность.** Биржа уже в HOLD → пропуск.
2. **HOLD биржи первым.** Один биржа-уровневый гейт **каскадно** блокирует
   входы по всем инструментам биржи (enforcement читает статус биржи живьём
   — §7; per-instrument записей не делаем).
3. **`AnomalyReport` `CREATED`.** `exchangeId`; `instrumentId` = инструмент,
   на котором обнаружено нарушение (если определим), иначе `null`;
   `scope=EXCHANGE`; before-слепки шире — все активные сделки/позиции/ордера
   биржи.
4. `status → IN_PROGRESS`.
5. **Exchange-scoped kill-switch.** Флэтит **все** инструменты биржи с live
   risk — итерация по инструментам, `EXECUTE_KILL_SWITCH` на каждый (порядок
   «защиту последней» — внутри каждого). Это шире текущего per-deal
   `KillSwitchExecutor` → роль `KillSwitchService` (backlog п.7); см.
   build-surface §11.
6. `status → KILL_SWITCH_EXECUTED`.
7. after-слепки (БД + биржа).
8. `status → COMPLETED`.

### Каскад и ручное снятие

- HOLD биржи — одно поле. Enforcement читает его (§7): для входа по
  инструменту проверяется статус его биржи; HOLD → пропуск. Блок каскадит
  на все инструменты **без** per-instrument записей.
- **Ручное снятие на уровне биржи — одно действие.** Снять HOLD биржи →
  каскадно отпускает всё (enforcement читает статус биржи живьём). Поэтому
  L4-реакция **не** пишет per-instrument холды — иначе один un-hold не
  отпустил бы всё. L4 ставит только биржа-уровневый гейт.
- Per-instrument холды L3, выставленные отдельными инцидентами, независимы и
  снимаются индивидуально.

## 4. Kill-switch: скоуп, «защиту последней», командная природа

- **Скоуп по уровню.**
  - L3 (инструмент): kill-switch по одному инструменту — граф сделки +
    orphan/foreign live risk на instId. Текущий `KillSwitchExecutor`
    работает по `dealContext.deal`-графу + close по instId; финальный
    безусловный `closeBestEffort(instId)` ловит позицию вне локального графа
    → доминирующий риск инструмента покрыт. (Ограничение: orders/algos вне
    локального графа индивидуально не отменяются — для L3 приемлемо, позицию
    закрываем с `autoCxl` + финальный close.)
  - L4 (биржа): kill-switch по **всем** инструментам биржи →
    `KillSwitchService` (backlog п.7) оркеструет per-instrument команды.
- **«Защиту последней»** живёт **внутри** каждого kill-switch
  (`KillSwitchExecutor`): close позиции → cancel orders → cancel algo-защит
  последними → безусловный финальный close. Координатор порядок не
  переписывает — он вызывает команду, которая им владеет; для L4 — по разу
  на инструмент, порядок сохраняется внутри каждого.
- **Команда, не действие-оркестрация** (`action-orchestration-vs-command`):
  аварийный тормоз доводит teardown сам, синхронно, **не завися от живости
  петли**. Координатор вызывает его как команду (через `ServiceCommandExecutor`
  по типу — единый маршрут командного слоя; retry-anchor'а нет, исполнитель
  best-effort), а не как многопроходный FSM-секвенс. Это и оправдывает
  командный статус в реакции на инцидент.
- **Эмитент `EXECUTE_KILL_SWITCH`** = `SafetyHoldCoordinator`. Это тот
  «тонкий эмиттер», который, по заметке `CODE`-сверки, подключает
  hold-подсистема (удалённый орфан `DealFsmSupport.killSwitchCommand()`
  заменяется эмиссией из координатора, теперь с реальным вызывающим).

## 5. Enforcement держимого холда

Две поверхности — новые сделки и сделки в полёте:

- **Новые сделки.** `EntryScannerJob` сейчас сканирует
  `instrumentDataService.findByStatus(ACTIVE)` и **не** смотрит на биржу.
  Enforcement: сканер пропускает (а) инструменты в safety-HOLD, (б)
  инструменты, чья биржа в HOLD (каскад L4). → правка фильтра сканера
  (build-surface §11).
- **Сделки в полёте.** Сделка на held-scope не должна порождать новый риск.
  Существующий дизайн уже это контемплирует: `Deal.ShutdownReason`
  содержит `EXCHANGE_HOLD` и `RISK_POLICY`, а `docs/lifecycles/Deal.md`
  §graceful shutdown предписывает `Exchange/Instrument/Account HOLD →
  shutdownReason = EXCHANGE_HOLD`. Enforcement для активных сделок =
  **graceful-shutdown по held-scope**: handler видит scope-HOLD → controlled
  close live risk → терминал с `shutdownReason=EXCHANGE_HOLD` (или
  `RISK_POLICY` для L3). Normal-flow гейтится, safety/reduce/refresh
  разрешены — ровно как `exchange-hold.md`/`instrument-hold.md`.
- **Комплементарность с kill-switch.** L4 kill-switch (fire-all, команда)
  снимает live risk немедленно; per-deal graceful-shutdown (ведомый петлёй)
  затем орднунг-доводит каждую сделку до терминала. Kill-switch убирает риск
  быстро, петля подтверждает фактами и закрывает сделки. Порядок обработки
  сделок в проходе при этом неважен: риск снят командой вне зависимости от
  порядка, гейт действует на последующие проходы.

## 6. Связь с терминалом `ERROR` и «действие vs команда»

- **Терминал сделки vs реакция холда — два независимых трека.** Сделка-
  триггер уходит в свой `ERROR` (handler `markError`, существующая
  механика) → `ErrorHandler` доводит до `EMERGENCY_CLOSED` (close → cancel →
  cancel algo последней → подтверждение `REFRESH_*` → терминал). Реакция
  холда — отдельный инструмент-/биржа-широкий трек, координируемый над
  сделкой. Треки комплементарны и безопасно перекрываются (оба снижают
  риск; idempotent/best-effort).
- **action vs command.** Per-deal `ErrorHandler` — **действие**, ведомое
  петлёй (постепенно, подтверждает `REFRESH_*`); оно может опираться на
  петлю, т.к. немедленный риск уже снят командой. Kill-switch реакции —
  **команда** (самодостаточный fire-all teardown, не зависит от живости
  петли) — корректно для аварийного тормоза в инциденте.

## 7. Сверка модели `AnomalyReport` на достаточность

Единственная требуемая сверка. Поля сейчас: `id`, `internalId`, `exchangeId`
(req), `instrumentId` (nullable), `status`, `severity`(CRITICAL/NON_CRITICAL),
`code`, `message`, 4 jsonb-слепка. Lifecycle: `CREATED → IN_PROGRESS →
KILL_SWITCH_EXECUTED → COMPLETED → ERROR`.

| Что нужно реактивному пути | Несёт ли модель | Вердикт |
|---|---|---|
| Носитель before/after слепков (БД+биржа) | `internalBefore/After`, `externalBefore/After` | ✅ достаточно |
| Встроенный kill-switch между слепками | статус `KILL_SWITCH_EXECUTED` между before/after | ✅ достаточно (lifecycle ровно так и описан) |
| Severity-политика (CRITICAL → торговля заблокирована до ручного разбора) | `severity` | ✅ достаточно (policy-кнобом) |
| Привязка к бирже/инструменту | `exchangeId`(req), `instrumentId`(nullable) | ✅ достаточно |
| **Уровень L3/L4 / скоуп инструмент-vs-биржа** | только косвенно через `instrumentId=null` | ⚠ **недостаточно** — рекомендую дополнить |
| **Привязка к результату kill-switch** | статус `KILL_SWITCH_EXECUTED` + `externalAfter` (остаточный риск виден) | ◑ достаточно для журнала; явный residual-флаг — опционально/форвард |
| **Статус ручного разбора** | `Status` отражает только авто-обработку | ⚠ не моделируется — развилка (§10) |

**Рекомендуемое дополнение (`scope`/`level`).** `instrumentId=null`
перегружен: он `null` и когда «инструмент не определён», и потенциально для
L4. L4-инцидент при этом может называть инструмент (нарушение обнаружено на
инструменте X, эскалирует до холда биржи). Поэтому скоуп из `instrumentId`
**не выводится однозначно**. Рекомендую явный enum-поле `scope`/`level`
(`INSTRUMENT` / `EXCHANGE`): малое дополнение, снимает неоднозначность,
прямо определяет, какой гейт трогают координатор и un-hold.

**Привязка к kill-switch** — через `status` + `externalAfter` (частичный
успех = остаточный риск в слепке; политика частичного успеха — открытый
ANOM-Q2). Отдельное поле не обязательно; явный residual-risk маркер —
опционален.

**Статус ручного разбора** — `Status`-енум трекает только авто-обработку:
`COMPLETED` = авто-реакция завершена, **не** «человек разобрал». Снятие
холда живёт на статусе инструмента/биржи, не в `AnomalyReport`, и сейчас
ничто не связывает «инцидент разобран, холд снят (кем/когда)» с отчётом.
Это развилка (§10, развилка C).

## 8. Найденные расхождения доки↔код / доки↔доки

Доки в этом заходе не правим — фиксирую находки для последующего
`SYNC_DOCS_FROM_CODE` и для валидации.

- **A. `Exchange.Status` не имеет `HOLD`.** `exchange-hold.md` и
  `error-handling-policy.md` (уровень 4) опираются на `Exchange.Status =
  HOLD` как точку enforcement, но енум `Exchange.Status` в коде —
  `CREATED/PENDING/ACTIVE/CLOSED/ERROR`, **без `HOLD`**. Enforcement L4
  сейчас невозможен — нужна материализация (§10, развилка B).
- **B. `Instrument.Status.HOLD` — онбординг, не safety.** Енум-значение
  есть, но его javadoc: «придержан (**не вовлекается в онбординг**)».
  `instrument-hold.md` трактует `Instrument.Status=HOLD` как safety-паузу
  торговли. Это **конфляция двух смыслов** на одном поле. Перевод
  `ACTIVE → HOLD` к тому же теряет «был ACTIVE» (нужно для восстановления
  при un-hold). См. §10, развилка B.
- **C. Бесстоповая позиция — L3 или L4? → РЕШЕНО (`trading-specialist`,
  2026-06-23): L3 (инструмент).** `instrument-hold.md` §Триггеры числит
  «обнаруженную бесстоповую risk-creating позицию» триггером **уровня 3**
  (инструмент). `risk-creating-entry-protection.md` §2 и `backlog.md` §Шаг 6
  пишут: «нарушение постфактум → реакция **уровня 4** (холд биржи)». Прямое
  расхождение: одно явление подшито под две разные категории error-градации —
  «нарушение риск-политики» (L3) vs «нарушение инварианта системы» (L4).
  **Решение владельца по риск-семантике — L3**, с обоснованием:
  - *Радиус поражения локализован на инструменте.* Неограниченная
    ответственность (risk of ruin при неограниченном убытке = 1 —
    дистиллят `risk-and-sizing.md` §7, §12) живёт на одной позиции одного
    инструмента; при isolated-марже (наш инвариант — non-isolated сама есть
    L4) убыток не перетекает на другие инструменты. Биржа/контракт/прочие
    инструменты работоспособны.
  - *Критерий L4 у самой политики — радиус за пределы инструмента.* Примеры
    L4 (`>1 позиции на инструмент`, `не-isolated маржа`) структурны и
    биржа-/аккаунт-широки (модель состояния площадки неверна / cross-перетёк).
    Бесстоповая позиция не такова: состояние понятно (позиция есть, стопа
    нет), замкнуто на инструменте → L3-категория «финансовая/риск-ошибка,
    локализованная на инструменте».
  - *Ярлык «инвариант» описывает силу пре-трейд гарда (`PRECHECK` держит
    всегда), а не скоуп реакции.* Скоуп реактивного холда трекает радиус
    живого риска. Стоп задаёт границу R позиции (Tharp гл. 9, дистиллят §9);
    его отсутствие — провал риск-дисциплины на одной сделке, не коррупция
    биржа-широких допущений.
  - *Пропорциональность.* Instrument-scoped реакция (close позиции + cancel
    её ордеров + холд инструмента + `AnomalyReport`) полностью покрывает
    живой риск; флэтить всю биржу — несоразмерно.

  **Предусловия / границы для `CODE`:** (1) L3 условен на isolated-марже;
  при cross-марже единичный бесстоповый убыток способен ликвидировать
  аккаунт → L4 (у нас non-isolated сама L4-инвариант, посылка — isolated).
  (2) Системный L4-путь сохраняется, но он **проактивный и отдельный**: если
  скан шага 8 найдёт много бесстоповых позиций / структурно обойдённый гард
  (control-plane failure неизвестного скоупа) — это другая находка, легитимно
  L4. Реактивный контур шага 6 поднимает L3 на одну обнаруженную позицию.
  **`SYNC_DOCS`:** выровнять `risk-creating-entry-protection.md` §2 и
  `backlog.md` §Шаг 6 с L3; `instrument-hold.md` остаётся как есть.
- **D. Enforcement холдов нигде не подключён в коде.** Грепом: ни одной
  ссылки на safety-`Instrument.Status.HOLD`/`Exchange.HOLD` в торговом
  пути; `EntryScannerJob` биржу не читает вовсе. Подтверждает: реактивный
  enforcement — чистый build, не правка.
- **E. Java-модели `AnomalyReport` нет** — только доковый каркас
  (модель+lifecycle). «Переиспользуем» = переиспользуем спеку; код модели
  (entity/repo/dataservice/mapper/миграция) надо материализовать.

## 9. Развилки и рекомендации

### Развилка A — где принимается решение реакции
- (a, рекоменд.) В проходе оркестратора (`DealOrchestratorJob` →
  `SafetyHoldCoordinator`), сигнал из `DealTransition`. Над сделкой,
  идемпотентно по HOLD, под advisory-локом прохода.
- (b) Внутри FSM-handler'а. Отвергнуто: handler видит только свою сделку,
  каскад L4 ему не виден.
- **Крен (a).** Прямо соответствует сиду «решение на оркестраторе».

### Развилка B — точка enforcement (материализация статусов)
Минимально нужно для построяемости (то место, где дизайн касается backlog
п.9):
- (b1, рекоменд.) **Отдельный safety-hold маркер**, ортогональный
  онбординг-`Status`: на `Instrument` и на `Exchange` (поле/флаг +,
  опц., timestamp/ссылка на `AnomalyReport`). Онбординг-`Instrument.Status`
  не перетирается → un-hold чисто восстанавливает к `ACTIVE`; на `Exchange`
  не плодим перегрузку. Enforcement читает маркер.
- (b2) **Переиспользовать `Instrument.Status.HOLD` + добавить
  `Exchange.Status.HOLD`.** Дешевле по полям, но (1) конфляция онбординг-HOLD
  и safety-HOLD на инструменте, (2) `ACTIVE→HOLD` теряет прежний статус для
  восстановления.
- **Крен (b1)** — чистое разделение смыслов, корректный un-hold; снимает
  находки §8.A/§8.B. Полная модель координации статусов остаётся backlog
  п.9; здесь — минимальный safety-маркер + его чтение. Это хвост
  пользователя/владельца (продуктовый scope статус-модели).

### Развилка C — где живёт статус ручного разбора
- (c1, рекоменд.) **`AnomalyReport` остаётся авто-журналом**; «ещё
  заблокировано» — источник правды на safety-hold маркере (§B); операция
  un-hold (шаг 9 / backlog п.9) back-референсит снятые отчёты. Аудит-поля
  ручного снятия (кем/когда) добираются при постройке операции un-hold.
- (c2) Добавить в `AnomalyReport` manual-resolution статус/поля
  (`REVIEWED`/`RESOLVED` + `resolvedBy`/`resolvedAt`).
- **Крен (c1)** для scope шага 6: гейт-маркер — источник «заблокировано»,
  `AnomalyReport` не раздувается ролью, которой у него по дизайну нет
  (он — журнал инцидента). Форвард-заметка о возможном аудит-поле — к
  операции un-hold.

### Развилка D — момент координации в проходе
- (d1, рекоменд.) **Немедленно** по сигналу (внутри `processDeal` после
  applyTransition). Риск снимается ASAP; HOLD-гейт встаёт для остатка
  прохода.
- (d2) Сбор сигналов и реакция в конце прохода. Отвергаемо: задерживает
  снятие риска без выгоды (kill-switch fire-all делает порядок benign).
- **Крен (d1).**

## 11. Резюме

Реактивный CRITICAL-холд L3/L4 построяем на шаге 6 на уже описанном:
сигнал в `DealTransition` → решение в проходе оркестратора (идемпотентно по
HOLD, под advisory-локом) → `SafetyHoldCoordinator`: HOLD первым →
`AnomalyReport` со встроенным kill-switch между before/after-слепками →
enforcement (сканер-фильтр + graceful-shutdown), для L4 — каскад одним
биржа-гейтом и одним ручным un-hold. Снятие — только ручное. Модель
`AnomalyReport` достаточна как носитель слепков и kill-switch; рекомендуется
добавить явный `scope`/`level` (снять неоднозначность L3/L4). В шаг 8
остаётся только проактивный детектор (`AnomalyJob`/`TradeRuleValidator`) и
численные пороги. Развилки A/B/C/D — на валидацию (хвост пользователя по B
— продуктовый scope статус-модели; §8.C **разрешена владельцем
`trading-specialist`: бесстоповая позиция = L3, инструмент**).
Финальный аппрув дизайна и переход к `CODE`-инкременту холдов — за
пользователем.
