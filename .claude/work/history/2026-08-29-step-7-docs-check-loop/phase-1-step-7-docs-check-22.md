# Блокирует выход в `CODE`

## Узел «операнд базы риска» — C2 + C3 + C4

Три находки об одном объекте: что такое база риска, чем она ограничена и
на что реагирует. Одним изменением не закрываются, но держателю
предъявляются вместе — каждая по отдельности даёт неполную картину.

### C2. Счётная таблица worst-case считает размер формулой, которой система не пользуется

- **Вопрос.** Таблица, на которой стоит решение держателя «кэп не
  вводится», выводит контракты **только** из поактного лимита риска.
  `SizeCalculator` берёт `min(alloc-derived, risk-derived)`, где
  `alloc-derived = база риска × allocationPercents/100 ÷ (entryPrice ×
  ctVal)`, а `allocationPercents` — доля с create-реджектом вне `[0;100]`.
  Значит нотинал одного акта **уже** ограничен базой риска, и две из трёх
  строк таблицы арифметически недостижимы.
- **Пересчёт** (исходные — те же: `ctVal = 0.1`, цена 3000, база 10 000,
  поактный лимит 1 %, `allocationPercents = 100`; alloc-derived = 33):

| Дистанция стопа | risk-derived | В таблице дока | Фактически (`min`) | Нотинал | Плечо |
|---|---|---|---|---|---|
| 3.0 % | 11 | 11 / 3 300 / 0.33× | 11 | 3 300 | 0.33× — строка верна |
| 0.5 % | 66 | 66 / 19 800 / ~2× | **33** | **9 900** | **≈1×** |
| 0.1 % | 333 | 333 / 99 900 / ~10× | **33** | **9 900** | **≈1×** |

- **Что уцелевает.** R-отношение: при 0.1 %-стопе фактический риск ноги
  9.9, гэп в 1 % (≈99) остаётся ≈10R. **Что падает** — корпусный тест,
  которым раздел обоснован: при нотинале ≤ базы для обнуления счёта нужен
  ход 100 %, то есть поактно тест [Carver ST гл.9 с.180-181] **проходит**,
  а раздел утверждает обратное. Падают две строки перечня четырёх дыр.
- **Что остаётся настоящей дырой** (и это надо записать вместо снятого):
  кэп **поактный, не сделочный** — веер из `N` ног даёт до `N ×` базы
  нотинала; и `allocationPercents` — число автора стратегии с одной лишь
  структурной валидацией, без системного потолка. Система несёт кэп, но
  не назначает его.
- **Грунт.** [Carver ST гл.9 с.180-181], [Kaufman гл.23 PDF с.2036-2037],
  [Vince гл.2 с.30-31] — все три уже процитированы разделом; находка не
  оспаривает грунт, а показывает, что вывод сделан по неверному операнду.
- **Цитаты (носители).** `docs/decisions/per-trade-risk-policy.md:797-856`
  (перечень четырёх дыр + счётная таблица), `:1223-1228` (отклонение кэпа
  нотинала); `docs/components/SizeCalculator.md` §«Вход (open/increase)»,
  §«Сайзинг под поактный лимит риска» («Лимит риска — связывающий потолок
  **над желаемым объёмом**»); `docs/models/domain/aggregate/Strategy.md:550`,
  `:652-655`.
- **Целевой док.** `docs/decisions/per-trade-risk-policy.md`
  §«Worst-case открывающего входа».
- **Ожидаемый владелец.** `trading-specialist`; держательская половина —
  ниже.
- **Трассировка.** Линза C, проход по формулам: перепроверяла счётную
  таблицу → числа не сошлись с `SizeCalculator` → проверила верхнюю
  границу `allocationPercents` → пересчитала три строки. Верифицировано
  CC независимо — V2, V3.
- **Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| **(a)** пересчитать таблицу, переформулировать дыру как «сделочного кэпа нет, поактный есть» | восстанавливает истинность раздела; решение «кэп не вводится» остаётся в силе, но на верной картине | ноль по коду и схеме. Цена — раздел перестаёт быть аргументом «тут дыра размером 10×» |
| **(b)** (a) + системный потолок на `allocationPercents` (глобальный конфиг, как `globalSimultaneousRiskPerDealPercent`) | превращает существующий кэп из числа автора в guard системы; носитель того же класса уже принят | одна провизорная величина + код реджекта; отсекает конфигурации, сознательно берущие полный нотинал |
| **(c)** (a) + сделочный кэп нотинала (Σ по живым ногам ≤ `M ×` база риска) | закрывает названный остаток (веер ног) | вторая провизорная величина; **переоткрывает** решение держателя C5 `DOCS_CHECK_21` |
| **(d)** оставить как есть | ноль правок | раздел, на который ссылаются пять мест, несёт неверную арифметику и ложную строку «кэпа нет»; решение по C5 остаётся стоящим на неверных числах |

- **Ярлык дефицита.** (a) — дефицита нет; (b)/(c) — `подтверждение`.
  Находка **составная**: проектная половина исполнима владельцем.

### C3. База лимитов движется под сделкой от изъятия маржи, а не только от просадки

- **Вопрос.** База риска — свободный остаток расчётной валюты, режим
  маржи — isolated, значит открытие позиции **изымает маржу из свободного
  остатка**. Правая часть **одновременного** лимита (`% ×` база текущая) и
  база **кумулятивного** (`min(снимок, текущая)`) падают на величину
  заблокированной маржи при нулевом убытке — тем сильнее, чем теснее стоп.
- **Счётно.** База 10 000, `strategySimultaneousRiskPerDealPercent = 1 %`,
  `N_overlap = 1`. Нога с нотиналом 9 900 при `leverage = 3` изымает ≈3 300
  ⇒ база 6 700 ⇒ правая часть = 67, тогда как `liveRiskNow` ≈ 99. Лимит
  нарушен **сразу после филла собственной первой ноги**; всякое следующее
  risk-creating действие блокируется. При `leverage = 1` блокируется всё.
- **Что ломается по существу.** Статическая проверка create
  `N_overlap × riskPerActionPercent ≤ strategySimultaneousRiskPerDealPercent`
  сравнивает **проценты**, то есть считает базу постоянной по вееру («сумма
  вырождается в произведение»). При изымаемой марже произведение неверно, и
  веер, прошедший create как выполнимый, в рантайме недостижим — клейм «что
  проверка ловит: веер, который не поместится **никогда**» получает
  зеркальный, неназванный отказ. Первым упирается многоногий вход, объявленный
  рабочим режимом фазы 1.
- **Грунт.** Корпус разводит риск-бюджет и маржинальную загрузку на **два**
  неравенства: [Vince гл.8 с.96, ф.8.08] (маржинальное неравенство рядом с
  f-неравенством), [Carver AFTS тактика 4, PDF с.636-637] (маржа —
  отдельный процесс со своим порогом), [Kaufman гл.23 PDF с.2028,
  2091-2092] (резервы). Проект свёл их в одно, не назвав этого.
- **Посылка, помеченная непроверенной.** «Открытие isolated-позиции
  уменьшает `availBal` строки расчётной валюты» — прямого утверждения нет
  ни в `BalanceContainer.md`, ни в `docs/integrations/okx/contracts/balance.md`
  (там только пример payload'а). Верификация CC (V4) это подтвердила:
  посылка из носителей не выведена. Проверка — `integrator`.
- **Цитаты (носители).** `docs/decisions/per-trade-risk-policy.md:196-229`,
  `:301-305`, `:584-607`, `:637-663`;
  `docs/rules/trading-constraints.md` §«Режим маржи: isolated»;
  `docs/models/domain/core/BalanceContainer.md` §«`Balance` (currency-level,
  раздел модели)»; `docs/components/RiskValidator.md:151-165`.
- **Целевой док.** `docs/decisions/per-trade-risk-policy.md` §«Три лимита
  внутри уровня „риск на сделку“» и §«Валидация — в двух точках».
- **Ожидаемый владелец.** `trading-specialist`; проверка посылки —
  `integrator`.
- **Трассировка.** Линза C, проход по направлению ошибки: проверяла, куда
  ошибается `min(снимок, текущая)` → доминирующий драйвер «текущей» не
  убыток, а изъятие маржи → прогнала через статическую проверку → грепом
  `маржа|margin|заморож` по четырём докам убедилась, что связь нигде не

- **Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| **(a)** назвать ограничение записью: база включает изъятую маржу; веер `N_overlap` в рантайме может не пройти; статическая проверка это не ловит | цена названа, ничего не строится | автор стратегии узнаёт об отказе только реджектом; направление отказа **консервативное**, то есть допустимое |
| **(b)** правая часть лимитов — от базы **до** изъятия маржи под собственную сделку (`база + маржа живого эпизода`) | восстанавливает объявленный смысл «процент депозита под ударом» | новое чтение поля позиции в горячем пути; вопрос, чем считать маржу при многоэпизодности |

### C4. «Сжимается в просадке» — только в реализованной; на открытой просадке потолок неподвижен

- **Вопрос.** Обоснование секции — анти-мартингейл («риск сжимается при
  падении» [Tharp гл.12 с.283-285]). Операнд — база риска, из которой
  плавающая переоценка **сознательно исключена** тем же доком. Следствие,
  нигде не названное: пока сделка жива, её собственный убыток нереализован,
  и потолок на него не реагирует **никогда**. Мартингейльная форма —
  добор/грид **против** движения внутри эпизода — остаётся вне реакции
  ровно того контроля, который заведён против неё.
- **Единственная строка, где сужение признано, его не называет
  ограничением:** «сделка, потерявшая часть депозита **реализованными
  убытками**» — прилагательное стоит, вывод не сделан.
- **Носитель операнда уже есть.** `Position.externalUnrealizedProfit`
  персистится (колонка в `V6`), маппится из `upl` и в риск-контуре
  **читателя не имеет** — то есть первая позиция перебора (достаточность
  существующего носителя) даёт непустой ответ.
- **Грунт.** [Tharp гл.12 с.283-285]; [Carver ST гл.9 с.187-189] —
  пересчёт капитала идёт по P&L, а не по свободному кэшу; [Vince гл.8
  с.89-91]; [Harris гл.28 с.556-562].
- **Цитаты (носители).** `docs/decisions/per-trade-risk-policy.md:637-663`,

## B3. `Σ(amount − externalFee)`: область определения при пустом вычитаемом не задана, клейм безопасности сильнее установленного

- **Вопрос.** Левый операнд первой пары сверки — `Σ(amount − externalFee)`.
  `externalFee` **nullable**, его пустота ратифицирована как значение, и
  конвенции «пусто = 0» у bills-записи, в отличие от positions-history,

  вычитаемом — не сказано ни в одном носителе. Рядом стои́т клейм «Суперсет
  безопасен для суммы-сверки **и realized-слагаемого** при любой
  гранулярности».

  схлопывается к нулю ⇒ `Δ₁ = |pnl|` ⇒ `MISMATCHED` детерминированно, а в
  боевом режиме — `Exchange.HOLD` после **каждой** сделки. Ошибка не
  ловится ни одной из четырёх пар: вторая при этом сходится.

   оказалась неверной (плечо ≈1×, а не ~10×), — то есть на **менее**
   тревожной картине, чем предполагалось. Вопрос численного риск-аппетита.
2. **C4 — расширять ли операнд кумулятивного потолка на открытую
   просадку?** Проектная половина (оговорка «сжатие — по реализованной

   ратифицированный вариант (б) ответа на C7 `DOCS_CHECK_21`. Вопрос: должен

3. **C5 — какие ценовые базы триггера защиты разрешены стратегиям до

# Рекомендация

**Прогнать `GAPS_CLOSE_22`.** Порядок закрытия — по классу дефекта, а не
по номерам находок:

1. **Сначала — четыре развилки держателя** (§«Вынос пользователю»): три из
   них составные, и проектные половины C2/C4 можно закрывать параллельно с
   ожиданием ответа; C5 без ответа не закрывается вовсе.
2. **Затем — узел «операнд базы риска» (C2 + C3 + C4) целиком**, одним
   заходом: три находки об одном объекте, и правка любой из них меняет
   картину для остальных двух.
3. **Пропагация уже принятого** (C1, A1, A3, B4, B5, N1, N2) — механическая,
   но именно она дала семь из одиннадцати гейтящих. Закрытие обязано
   пройти **внутрифайловым** свипом: новый подкласс этого прогона — правка,
   дошедшая до одного пассажа файла и не дошедшая до другого пассажа **того
   же файла** (B4, B5, A3). Греп по термину находит первое вхождение;
   нужен проход по **всем** вхождениям предмета, а не по первому.
4. **Операнды без операционного значения** (B1, B3, C5) — каждый требует
   назвать носитель, а не переформулировать клаузу.
5. **N4 закрывается до B6** — B6 зависимая: её целевой док определяется
   исходом N4.

**Чего делать не надо.** Не заводить новый перечень носителей в §3
процесса: подкласс «тот же файл, другой пассаж» покрывается уже
существующим требованием «перечень, а не счёт» и «проход по клеймам
полноты» — не хватало не перечня, а **исполнения внутри файла**.
