## Пробелы

### H1 — Гидрация ставки: владелец не назван; «seam не двинулся» ложно для `RiskValidator` [F-A1, F-A2]. Тип: name-level + несогласованность. **ГЕЙТИТ.**

`InstrumentExternalRules.md:105-111`: «Ставка подгружается в модель **при
материализации** спец-запросом по `externalFeeGroupId`… Аксессоры делегируют в
подгруженный `TradeFeeRate`» — пассивный залог, **владельца нет**.

Материализаций **две** (`InstrumentExternalRulesDataService.md:25-26`): читают
`CalculationContextFactory` (кладёт в `CalculationContext`) и `RiskValidator`
(**напрямую**). Естественный дом гидрации — `InstrumentExternalRulesDataService`
(единственная граница domain↔persistence) — **о `TradeFeeRate` не знает вовсе**
(греп по файлу пуст, верифицировано CC); его §Использование (`:26-29`)
перечисляет цели чтения без ставки — док stale относительно шага 7.

**Отягчающее (F-A2):** реш.4 `pnl-finalization-mechanics.md:123-124` —
«`SizeCalculator`/**`RiskValidator`** читают taker-ставку из **уже
присутствующего** `CalculationContext.instrumentExternalRules`»; то же
`per-trade-risk-policy.md:98-99`. Но `RiskValidator.md:17` — сигнатура
`validate(CalculatedStrategyAction, DealContext)`; `:23` — «валидатор сам читает
через `InstrumentExternalRulesDataService.findByInstrumentId`»; **`CalculationContext`
у него нет** (`CalculationContext.md:10-11` — собирается фабрикой внутри
`StrategyActionCalculator`). Верифицировано CC (V2/V3).

**Почему гейтит:** если гидрация лежит в фабрике, прямое чтение `RiskValidator`
отдаёт негидрированный навес → `takerFeeRate()` = null → `FEE_RATE_UNAVAILABLE`
блокирует **каждый** risk-creating вход.

Доки должны задать: кто гидрирует, каким запросом, и что **обе** тропы чтения
отдают гидрированный инстанс. Отдельно: навес — JSONB на `instruments`, ставка —
реляционная `trade_fee_rates`, ключ лежит **внутри JSONB**; опора codestyle

сущностей и на навес механически не переносится.

### H2 — Знак ставки не сведён с формулой `+ commissions` → позиция больше положенной [F-B3]. Тип: несогласованность. **ГЕЙТИТ.**

- `contracts/trade-fee.md:111-112`: «`maker`/`taker`: **отрицательное значение =
  комиссия**, положительное = ребейт» — раздел озаглавлен «**критично для P&L**».
- `TradeFeeRate.md:53`: «Сырая ставка taker-комиссии (знак: минус = комиссия)»;
  `:103` — «`takerFeeRate()` / `makerFeeRate()` — числовые аксессоры **сырых**
  строк» ⇒ аксессор отдаёт знаковое сырое значение.
- `RiskValidator.md:30` / `SizeCalculator.md:60` / `per-trade-risk-policy.md:89`:
  «`|entry − stop| × contracts × ctVal **+ commissions**`»;
  `per-trade-risk-policy.md:87`: «бюджет = `riskPerTradePercent ×
  externalAvailableEquity **− прогнозная_комиссия**».

`abs`/модуля на этом пути **нет нигде** (верифицировано CC, V8). Композиция как
написано: `commissions` = notional × (отрицательная ставка) → отрицательна →
`+ commissions` **уменьшает** убыток на стопе, а `бюджет − (отрицательное)`
**увеличивает** бюджет. Оба члена смещают в одну сторону — **позиция больше
положенной**. Это дословно тот отказ, ради недопущения которого доки отвергают
fallback (`RiskValidator.md:106-108`: «заниженный прогноз → бюджет свободнее →
позиция больше положенной… тихое оптимистичное смещение, которое не видно ни в
одном логе»).

Документированные защиты не ловят: валидация проверяет только parseable numeric
(`mapping/TradeFeeRate.md:64-69`) — отрицательное парсится; `FEE_RATE_UNAVAILABLE`
срабатывает только на `null` (`RiskCheckResult.md:66-68`). Прецедент явной
нормализации знака в проекте есть (`mapping/Position.md:44,122` — `abs(pos)` →
`externalSize`, знак → `direction`); для ставки клаузы нет.

Доки должны задать, где снимается знак (нормализация в снапшоте/аксессоре либо
`commissions = |rate| × notional × 2` в формуле) — **одним** местом, без дубля.

### H3 — Холд по несвежести блокирует защиту и reduce-only partial exit; «сделки доживают» неверно [F-T1]. Тип: несогласованность (внутри одного файла) + торговая. **ГЕЙТИТ.**

`exchange-hold.md` противоречит сам себе:
- `:10-11` — «Что блокируется — **одинаково для любого триггера**»; `:16-17` —
  блок-сет `SUBMIT_ORDER` / **`SUBMIT_ALGO_ORDER`**; `:38-40` — «Также `HOLD`
  блокирует… **normal-flow TP/SL/trailing actions**, pyramid/scaling»;
- `:59` (новый триггер) — «холд блокирует **вход** (`SUBMIT_*`), не мешая
  `REFRESH_*` / `CANCEL_*` / `CLOSE_POSITION`, и **сделки доживают**».

Но `SUBMIT_ALGO_ORDER` — не только вход: `EntryFinalizedHandler.md:32` — main
protection ставится `CREATE_ALGO_ORDER` → **`SUBMIT_ALGO_ORDER`**;
`ManagingHandler.md:48-49` — `PROTECTION_ADJUSTMENT` / `PARTIAL_EXIT` /
`GRID_MANAGEMENT` идут теми же командами. Верифицировано CC (V11/V11b).

Отсюда под fee-холдом: (а) сделка в `ENTRY_FINALIZED` **не может поставить
`MAIN_PROTECTION`** и висит на временной attached-защите; (б) **reduce-only
partial exit заблокирован** — при том, что собственное обоснование холда
(`exchange-hold.md:77-80`) гласит: «оставляет возможность… **снижать риск**».

**Почему это новое:** блок-сет спроектирован под прежний триггер (safety-каскад
= биржа сломана; блокировать всё защитимо). `GAPS_CLOSE_3` подключил к нему
триггер, срабатывающий на **исправной** бирже — устарело **справочное** число
для сайзинга, а деградирует **боевой** контур управления позицией.

Различение, которого не хватает, в проекте **уже сформулировано**:
`risk-validator-scope.md:14-19,48` делит те же типы команд по **направлению
риска** (risk-creating vs reduce-only exit-flow); `exchange-hold.md` делит по
**типу команды**.

**Грунт [C]:** «Вход почти не важен: случайный вход прибылен с хорошими выходами
и сайзингом» [Tharp гл.8 с.200-202]; «Нет системы, пока не знаешь worst-case
выход в момент входа» [Tharp гл.9 с.234-236]. Жертвовать управлением выходом
ради точности сайзинга входа — инверсия приоритета корпуса.

**Почему гейтит:** доки утверждают обе ветки (`:38-40` vs `:59`) — CODE обязан
выбрать.

### H4 — Класс холда по несвежести не определён: реакция противоречит L4, тропа недоступна, снятие не задано [F-A4, F-A5]. Тип: несогласованность + name-level. **ГЕЙТИТ.**

`error-handling-policy.md:58-59` (уровень 4): «→ **холд биржи** + **kill-switch**
+ `AnomalyReport`; снятие **вручную**». `exchange-hold.md:93` сам себя объявляет:
«exchange-HOLD = **уровень 4**». Но тропа несвежести (`:52-60`) не несёт ни
kill-switch, ни `AnomalyReport`, ни ручного снятия — и прямо говорит «сделки
доживают». Верифицировано CC (V6).

**Тропа тоже не сходится:** L4-холд достигается через `HoldSignal` на
`DealTransition` от handler'а → `SafetyHoldCoordinator` в проходе
`DealOrchestratorJob` (`SafetyHoldCoordinator.md:22-27`), реакция —
`KillSwitchService.fireExchange` = «**каскадный sweep** по всем активным»
(`KillSwitchService.md:26`). У синк-джобы нет ни сделки, ни `DealTransition`, ни
места в проходе — документированной тропой она воспользоваться не может; а
воспользовавшись — расплющила бы биржу, противореча «сделки доживают».

**Снятие [F-A5]:** в `exchange-hold.md` **нет раздела о снятии вообще**
(верифицировано CC, V7 — заголовки: Правило / Что переводит в HOLD / DISABLED /
Почему / Связанное). При этом `instrument-hold.md:47-48` — «Снятие вручную… **как
и exchange-холд уровня 4**» — приписывает `exchange-hold.md` конвенцию, которой
тот не содержит → **битая кросс-ссылка** (сама по себе находка по
§«Верификация атрибуции»); конвенция живёт в `error-handling-policy.md:59`.
Существо: несвежесть **самоизлечима** (чтение восстановилось → возраст < порога).
Ручное снятие → одна транзиентная поломка требует человека; авто-снятие → первый
самоснимающийся L4-холд против конвенции. Не сказано ни то, ни другое.

Доки должны задать: несвежесть — это L4 (→ kill-switch + `AnomalyReport` +
ручное снятие) или **новый, более слабый класс холда** (тогда это новый концепт
со своим домом, реакцией и снятием).

### H5 — `modifiedAt` как измеритель свежести не следует из JPA auditing → ложный холд после 24 ч здоровой работы [F-B2]. Тип: несогласованность. **ГЕЙТИТ.**

- `Auditable.md:28-29`: «Системные `createdAt`/`modifiedAt`… **проставляются
  persistence-слоем (JPA auditing)**».
- `TradeFeeRate.md:67-69`: «**Значение совпало** → **обновить `modifiedAt`**
  последней строки, новую не плодить».
- `TradeFeeRate.md:75-78`: «**Прямой измеритель свежести** — `modifiedAt`
  двигается при **каждом успешном** чтении… Отдельный счётчик отказов не нужен».

JPA auditing (`@LastModifiedDate`) проставляет метку на **изменении** сущности.
Путь «значение совпало» по определению ничего не меняет → сущность не dirty →
UPDATE не выпускается → `modifiedAt` не двигается. Принудительный touch **нигде
не задан** (греп `touch|принудительн|dirty` по `docs/` пуст — верифицировано CC,
V10); прецедент показывает, что проект такие вещи проговаривает явно:
`InstrumentExternalRulesDataService.md:20-21` — «запись через load-modify
строки-владельца (**чтобы audit-поля обновлялись штатным JPA auditing**)».

**Отказ на дефолтной тропе, а не в углу:** ставка меняется редко
(`TradeFeeRate.md:80-81` — «единицы строк в год») ⇒ «значение совпало» —
практически **единственный** путь. Если touch не выпускает UPDATE, `modifiedAt`
замирает на времени создания, и через 24 ч **полностью здоровой** работы возраст
превышает порог → холд биржи, вход блокируется. Дефект даёт не «тихо сломанный
измеритель», а **ложноположительную остановку торговли**.

Свойство несущее и растиражировано в 4 доках (`TradeFeeRate.md:75-78,94-96`;
`InstrumentExternalRulesSyncJob.md:109-111`; `exchange-hold.md:52-54`;
`pnl-finalization-mechanics.md:154-157`); если оно не выполняется, обоснование
«счётчик отказов не нужен» лишается опоры.

**Спорно (помечено субагентом):** можно возразить, что «обновить `modifiedAt`» —
императив, а способ — деталь `code-writer`. Контрдовод: доки не просто
предписывают действие, а **выводят из него свойство** и на этом свойстве строят
решение (нет счётчика) и триггер холда; свойство из механизма owner-дока не
следует.

FUTURES-инструмент в scope либо матчится на SWAP-группу по голому `groupId` →

### H9 — Резолв `CashFlowCategory`: объявленная ось ≠ механизм; нет приоритета при комбинированной записи; нет ветки нуля [F-B4]. Тип: несогласованность + name-level. **ГЕЙТИТ корректность разбивки.**

- `mapping/DealCashFlow.md:90-92` (ветка после H2): «**комиссия / rebate** — по

Три проблемы:
1. **Заявленная ось расходится с механизмом** (`type`/`subType` vs знак

   категорийная ось (единственный смысл `DealCashFlow`, `:10-14`) вырождается.
3. **Нет ветки нуля** — тест «минус/плюс» не покрывает `externalFee` = 0

Ровно тот сценарий, ради которого H2 возвращал `fee` в used: **число** комиссии
починено, **присвоение категории** в комбинированном случае осталось незаданным.

гранулярности» верен для сумм, но **не для категории**. Плюс: область
суммирования для «realized-pnl-слагаемое = `amount` − `externalFee`»
(`mapping/DealCashFlow.md:79-81`) без исключения `FUNDING`-строк втянет funding.

**Намерение при этом торгово верно** (подтверждено линзой C: известная несвежая

### H11 — Путь «значение совпало» не задаёт, что ещё обновляется; подрывает `level`-датчик и историю [F-B6]. Тип: name-level. **НЕ ГЕЙТИТ** (сцеплен с H5).

### H12 — Довод «~5 bp против стопа 1-2%» на неустановленной посылке и не той величине [F-T2]. Тип: провизор. **НЕ ГЕЙТИТ.**

`pnl-finalization-mechanics.md:153` / `InstrumentExternalRulesSyncJob.md:123-124`
отвергают (C) чтение-на-входе доводом «цена свежести ~5 bp против стопа 1-2%».
Греп: «1-2%» встречается **только** в этих двух местах — как аргумент, нигде как
свойство системы; напротив, `risk-creating-entry-protection.md:51-53` —
«Численного хвоста нет… Конкретные расстояния стопа — отдельная ось». И величина
не та: раз-на-тик рискует не **уровнем** ставки (~5 bp), а **дрейфом между
тиками** (порядка 1 bp при часовом такте). **Вывод (A′) обе поправки переживает**
[C: при стопе 1% комиссия ≈9% риск-бюджета, дрейф ≈2% от него] — довод верен, но
по другой причине, чем записан; при сдвиге геометрии (тесный стоп/скальпинг) док
не даёт чем перевывести вывод. Грунт: «Тесные стопы: транзакционные издержки
**взрываются**» [Tharp гл.9 с.242-243].

### H13 — Taker-консерватизм подан как бесплатный [F-T3]. Тип: торговая. **НЕ ГЕЙТИТ. Cross-cutting** (шаг ожидаемости / фаза 2).

`per-trade-risk-policy.md:90`, `pnl-finalization-mechanics.md:174-175`,
`SizeCalculator.md:61-62`, `TradeFeeRate.md:54` — «по taker (worst-case) →

входы в модели есть (`RiskValidator.md:63` — `PriceMode.EXPLICIT`) и
`makerFeeRate()` хранится и не используется. **Грунт — источник говорит:**
«издержки (**равный вред от занижения и завышения**)» [Kaufman гл.1, PDF
с.114-119] — прямо против рамки «завышение = бесплатно»; «Ожидаемость ×
возможности = ценность системы» [Tharp гл.6 с.142,156-157].

### H14 — Epsilon на Σ|amount| слепнет с ростом оборота [F-T4]. Тип: провизор (форма, не калибровка). **НЕ ГЕЙТИТ.**

`pnl-finalization-mechanics.md:186-194` заявляет, что якорь на `|net|` «ломался с
обоих концов», и новый чинит это; `mapping/DealCashFlow.md:134-135` — «Величина
провизорна… **якорь — нет**». Но конец «глотает дыру» не починен — **переехал**:
допуск = 0.005 × Σ|amount| растёт линейно с числом движений, тогда как охраняемая
ошибка (межэндпоинтное округление) растёт как N × 0.01. **[C, арифметика —
предполагаю]:** при N ≥ 200 движений целое пропавшее движение проходит молча;
N в сотнях реалистичен (funding 3×/сутки + partial-филлы grid) — т. е. сверка
слепнет на grid/partial, целевом семействе бота. Свойство **формы**, а форма
объявлена непровизорной. **Радиус ограничен** (epsilon гонит только
`AnomalyReport`, не число и не терминал, `:180-184`) ⇒ «монитор слепнет», а не
«число неверно».

### H15 — Цена пропуска сделки оценена в ~0; для холда занижена на порядки [F-T5]. Тип: торговая (качество решения). **НЕ ГЕЙТИТ.**

Рамка «пропуск дёшев» повторена в 4 местах (`RiskValidator.md:109-111`,
`per-trade-risk-policy.md:111-112`, `pnl-finalization-mechanics.md:166-167`,
`InstrumentExternalRules.md:113-120`): «цена реджекта — пропуск **одной** сделки;
цена fallback'а — тихо превышенный риск на **каждой**». Для **реджекта**
асимметрия защитима. Но той же рамкой обосновано **холд**-решение — а холд не
«одна сделка»: остановка входов **по всей бирже** на всё время поломки,
неограниченно, плюс деградация живых сделок (H3). Альтернативы с корректно
оценённой ценой (холд scope=инструмент; торговля по последней известной ставке с
аномалией) не взвешивались. **Грунт — источник говорит:** «весь годовой профит
часто делает **одна сделка — её нельзя пропустить**» [Tharp гл.6 с.158-159; гл.11
с.279].

### H17 — Направление H6 «добор числа» на непроверенном допущении о null-популяции [F-T7]. Тип: торговая. **НЕ ГЕЙТИТ. Cross-cutting** (шаг ожидаемости / фаза 2).

(индекс ≠ ключ), H8 (голый `groupId` + FUTURES), H9 (резолв категории).
**Не гейтят — 9:** H10-H18; из них **cross-cutting/форвард — 3** (H13, H16, H17).

**Находки кучкуются в четырёх узлах, а не рассыпаны:**

1. **Гидрация (H1)** — H1 прошлого прогона закрыт **не до конца**: дом ставки
   переехал, поверхность чтения доспецифицирована только для `SizeCalculator`.
   Несущий довод `GAPS_CLOSE_3` («seam не двинулся, обе линзы признали валидным»)
   верифицируем наполовину. Тот же класс молчаливого отказа, ради которого
   гейтили CODE, — слоем ниже.
2. **Холд по несвежести (H3, H4, H5, H6)** — новый триггер подключён к
   блок-сету, спроектированному под **другой** триггер. Прежний означал «биржа
   сломана» (блокировать всё защитимо); новый срабатывает на **исправной** бирже
   и снимает у живых сделок main protection, ремодел трейлинга и reduce-only
   partial exit — при том, что доки в том же файле обещают «сделки доживают» и
   «оставляем возможность снижать риск». Плюс H5: измеритель, на котором триггер
   стоит, из своего механизма не следует ⇒ холд может сработать после 24 ч
   **здоровой** работы. Это **самый тяжёлый узел** и, вероятно, настоящая
   product/policy-развилка.
3. **Ось резолва (H7, H8)** — пара (instType, groupId) **заявлена** единообразно
   в 6 доках, но **не применена**: индекс на сырой колонке против запроса по
   доменному enum; матч по голому `groupId`; контур SWAP/FUTURES против чтения
   `instType=SWAP`.
4. **Число vs категория (H2, H9)** — оба про «починили одно, не свели с другим»:
   H2 — ставка добыта, но её **знак** не сведён с формулой риска (тихо большая
   позиция); H9 — комиссия посчитана, но **присвоение категории** при
   комбинированной записи не задано (категорийная ось вырождается).

**Торговый синтез — крен двойной.** `GAPS_CLOSE_3` последовательно выбирал
консервативную ветку (taker-always, реджект вместо fallback, холд вместо тихой
торговли) и **всюду оценивал цену консерватизма в ноль**. Корпус эту оценку не
поддерживает дважды: «издержки — равный вред от занижения и завышения» [Kaufman
гл.1, PDF с.114-119] и «весь годовой профит часто делает одна сделка — её нельзя
пропустить» [Tharp гл.6 с.158-159; гл.11 с.271-279]. Возник **новый крен —
пессимистичный, по оси возможностей** (H13, H15: недосайзинг на maker-входах,
пропуск входов под холдом). Он **не отменяет** прежний **оптимистичный крен по
оси исходов** (H6-null-drop прошлого прогона, N11, гэп-проскок TR2) — тот жив и
пополнился четвёртым, условным механизмом (H16: cross-ccy число помечается, но
не корректируется). Две группы искажают измеряемую ожидаемость **на разных осях
и в разные стороны** — они не гасят друг друга, а делают сравнение
бэктест↔live двусторонне несопоставимым. Прежняя формулировка форвард-фокуса
(«конвергенция трёх оптимистичных смещений») его теперь **недоописывает**.

**Исход: `DOCS_CHECK_4` НЕ чист → `GAPS_CLOSE_4`.** Гейт `CODE` не снят.
Владельцы: `solution-designer` (узлы 1-2, H7) + `integrator` (H8, H9 — с
пересечением с рантайм-кейсом §AG3.5) + `knowledge-curator` (H10, H11, H18).
Эскалации к пользователю — 4 (см. §Эскалации); тяжёлая — класс холда.

**Рантайм-фикстура §AG1.5 — по-прежнему рано** (порядок «чистый `DOCS_CHECK` →
рантайм» не выполнен). Отметить: **RQ-1** (покрытие `feeGroup[]`) прямо питает
предикат свежести — при частичном покрытии выпавшая из ответа группа протухает,
пока остальные освежаются, и «возраст актуальной строки» при N группах
неоднозначен (побочная находка линзы A, свёрнута в H4/H5-узел).
