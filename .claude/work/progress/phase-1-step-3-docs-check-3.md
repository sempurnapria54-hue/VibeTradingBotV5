## Находки и эскалации

### Н1. Ключевание результатов по идентичности: доки несут старую схему, точная схема не задана

- **Вопрос.** Decision
  `docs/decisions/market-data-result-identity-keying.md` решил:
  `IndicatorValue`/`MarketStructure` ключуются идентичностью
  считаемого (тип + `timeframe` + canonical-`params`), ссылка на
  настройку из результата убирается; правка доков — «на этом же шаге
  реализации». Шаг наступил, а (а) `IndicatorValue.md`,
  `MarketStructure.md`, `IndicatorJob.md`, `MarketStructureJob.md`,
  `market-data-calculation.md` всё ещё несут поле
  `setting: Strategy*Setting` и `UNIQUE(…, *_setting_id, …)` —
  ссылку на реляционный `id`, которого у JSONB-настроек нет;
  (б) точная схема идентичности (канонизация `params`, состав
  `UNIQUE`, как результат адресуется доменно) не задана нигде.
- **Ожидаемый владелец:** `solution-designer` (концепт:
  персистентность, топология моделей).
- **Кто ответил + трассировка:** `solution-designer`. Surface —
  `concept-review` (стадия 2, модели). Открыл:
  `market-data-result-identity-keying.md` (owner-док направления —
  клауза «точная схема … при построении кластеров» найдена),
  `strategy-tree-persistence.md` §Следствия (сверка: следствие Н3
  ревизии сформулировано так же), `persistence-representation.md`
  (дефолт: params — JSONB у владельца),
  `Strategy.md` §Настройки (настройки иммутабельны, адресуются по
  `key`). Рассуждение: направление решено и переоткрытию не
  подлежит; осталась конструкция — где живёт «идентичность» и чем
  ключуется строка результата.
- **Ответ.** Подтвердить пробел; доки результата/джоб/процесса
  переписываются по выбранной схеме на `GAPS_CLOSE_3`.
- **Варианты** (схема идентичности):
  1. **Реестр конфигураций** — отдельная таблица
     `indicator_configs` / `market_structure_configs`
     (тип + `timeframe` + canonical-`params`, UNIQUE по
     канонической форме); результаты ключуются
     `UNIQUE(instrument_id, config_id, candle_timestamp /
     window_end_at)`. Канонизация считается один раз при регистрации
     конфигурации; FK компактен; «считается раз и шарится» выражено
     структурно.
  2. **Inline-идентичность** — колонки `type`, `timeframe`,
     `params_canonical` (JSONB/text) прямо на строке результата +
     UNIQUE по ним (или по hash-колонке). Без новой таблицы, но
     канонизация/сравнение в каждом значении, ключ широкий.
  3. **Hash-колонка** — как (2), но UNIQUE по
     `(instrument_id, identity_hash, timestamp)`; компактно, зато
     идентичность нечитаема и есть (теоретический) риск коллизий.
  **Крен — (1):** структурно повторяет смысл решения (конфигурация —
  самостоятельная сущность шаринга), дешевле по хранению и индексам;
  не противоречит `persistence-representation.md` (реестр — не
  «части одного владельца», FK на него ссылаются → реляционная
  строка по букве правила).
- **Целевой док.** Правка `IndicatorValue.md`, `MarketStructure.md`,
  `IndicatorJob.md`, `MarketStructureJob.md`,
  `market-data-calculation.md`; схема — дополнением к
  `market-data-result-identity-keying.md` (направление уже там).
- **Ярлык исхода:** `варианты-с-креном`.
- **Ярлык дефицита:** `подтверждение` (выбор схемы — концепт-категория
  на R1, фиксируется только валидацией пользователя).
- Гейтит `CODE`: без схемы хранения значений писать код шага нельзя.

### Н2. Checkpoint джоб — упомянут, держатель не задан

- **Вопрос.** `IndicatorJob.md` §Идемпотентность и
  `market-data-calculation.md` говорят «checkpoint по последнему
  рассчитанному timestamp», но где живёт checkpoint (отдельное
  persisted-состояние? вычисляется?) — не задано. Шаг конструирует
  jobs → по функциональному порогу структура нужна.
- **Ожидаемый владелец:** `solution-designer` (держатели
  runtime-состояния).
- **Кто ответил + трассировка:** `solution-designer`. Surface —
  `concept-review` (стадия 2, компоненты). Открыл:
  `market-data-freshness.md` («состояние свежести в БД не
  хранится»), `CandleGroup.md` (прецедент явных границ
  `actualLast…` — но там границы и есть рабочая модель группы),
  модели результатов (уникальный ключ несёт timestamp). Рассуждение:
  результат сам несёт `candle_timestamp` / `window_end_at` →
  «последний рассчитанный timestamp» выводим запросом
  `max(timestamp)` по идентичности; отдельный держатель дублировал
  бы данные и ломался бы на рестарте в середине пачки (ср.
  реконсиляцию `count` у `CandleGroup`).
- **Ответ.** Checkpoint — **производный** (запрос max по таблице
  результатов на инструмент + идентичность), отдельная
  checkpoint-модель не заводится. Job на тике: взял max → досчитал
  от него по закрытым свечам. Это согласуется с идемпотентностью и
  «не храним runtime-состояние свежести».
- **Варианты.** (1) производный checkpoint — крен; (2) отдельная
  persisted checkpoint-модель — отвергается (дубль, рассинхрон).
- **Целевой док.** Уточнение в `IndicatorJob.md` (и по аналогии в
  job-доках структуры/фазы) + строка в `market-data-calculation.md`.
- **Ярлык исхода:** `выводимо-R1`.

### Н4. Для каких статусов стратегий считаются данные — формулировки расходятся

- **Вопрос.** `IndicatorJob.md` / `MarketPhaseJob.md` — «читает
  активные/готовящиеся стратегии»; `market-data-freshness.md` —
  «для `DELETED`-стратегий новые данные не считаются» (исключён
  только `DELETED`); lifecycle `Strategy.md`: `INACTIVE` блокирует
  только новые сделки, открытые сопровождаются по pinned detail —
  а сопровождение читает индикаторы для шагов. «Активные/
  готовящиеся» (читается как `ACTIVE`+`CREATED`) исключает
  `INACTIVE` — противоречие с потребностью открытых сделок.
- **Ожидаемый владелец:** `solution-designer` (конструкция
  концепции; выводимо из решённого).
- **Кто ответил + трассировка:** `solution-designer`. Surface —
  `concept-review` (стадия 2, сверка job-доков с owner-доками
  правила и lifecycle — обе клаузы найдены и процитированы выше).
  Рассуждение: правило свежести — сквозной источник истины;
  lifecycle даёт потребителя данных у `INACTIVE` (открытые сделки);
  `CREATED` нужен для готовности к активации (warmup).
- **Ответ.** Выводимо: jobs считают для всех стратегий **кроме
  `DELETED`** (как в правиле). Формулировку job-доков привести к
  «стратегии кроме `DELETED`» (или явному перечню
  `CREATED`/`ACTIVE`/`INACTIVE`) — правка формулировки, не смысла
  правила.
- **Варианты.** Альтернатива «считать только `ACTIVE`+`CREATED`»
  отвергается: рвёт сопровождение открытых сделок `INACTIVE`-
  стратегий (lifecycle прямо обещает их вести).
- **Целевой док.** Правка `IndicatorJob.md`, `MarketPhaseJob.md`
  (и проверить `MarketStructureJob.md` — там перечня нет, добавить
  единообразно).
- **Ярлык исхода:** `выводимо-R1`.

  candle_timestamp)`, т.е. ряд по штампам (история). Один из двух:
  upsert одной строки или история с «актуальный = последний».
- **Ожидаемый владелец:** `solution-designer`.
- **Кто ответил + трассировка:** `solution-designer`. Surface —

  по timestamp осмысленны только при истории.
- **Ответ.** Выводимо: хранится **история**, «актуальный» —
  последний по `candle_timestamp` (его и отдаёт
  `MarketPhaseService.getLatestPhase`). Формулировку «один

- **Варианты.** Upsert одной строки отвергается: ломает

  моделями.
- **Целевой док.** Правка `MarketPhase.md` (+ та же формулировка в
  `MarketPhaseJob.md` «сохраняет новый актуальный результат» — уже
  корректна, выровнять модель под неё).
- **Ярлык исхода:** `выводимо-R1`.

### Н6. Точка отсчёта устаревания структуры не задана (и торговый нюанс долгоживущих уровней)

- **Вопрос.** `MarketStructure.md`: «Актуальность проверяется через
  `…expirationDuration` и `confirmedAt` / `windowEndAt`» — от какого
  из двух полей меряется устаревание, не задано (у индикатора —
  `candleTimestamp`, у фазы — `candleTimestamp`/`confirmedAt`, тоже
  двойственно). Торговый нюанс рядом: уровни S/R живут дольше окна
  расчёта — устаревание по времени расчёта может пометить ещё
  валидный уровень как expired.
- **Ожидаемый владелец:** торговое ядро → `trading-specialist`,
  точка отсчёта в модели → `solution-designer`.
- **Кто ответил + трассировка:** `trading-specialist` +
  `solution-designer`. Surface — `concept-review`. Specialist (по
  дистилляту microstructure/strategy-patterns): источник прямого
  правила «когда уровень мёртв» не даёт (помечаю как «предполагаю»,
  не «источник говорит»); валидность уровня — вопрос пробоя/
  переподтверждения, а наша конструкция и так **перерасчитывает**
  структуру регулярно — expiration здесь ловит не «смерть уровня»,
  а «расчёт остановился» (нет свежих данных). Значит торгово
  корректная точка отсчёта — момент последних данных расчёта.
  Designer: это `windowEndAt` (конец окна свечей); `confirmedAt` —
  про look-ahead-подтверждение, не про свежесть.
- **Ответ.** Устаревание структуры меряется от `windowEndAt`;
  `confirmedAt` остаётся гейтом «можно использовать» (без
  look-ahead). Для фазы — аналогично: свежесть от
  `candleTimestamp`, использование — от `confirmedAt`. Семантику
  «expiration = остановка перерасчёта, не смерть уровня» — строкой
  в правило свежести.
- **Варианты.** Отсчёт от `confirmedAt` отвергается: давно

### ТР1 (= IND-Q1). Надёжность биржевого объёма для OBV / volume-условий

- **Вопрос.** Открытый вопрос IND-Q1 (владелец — шаг 3): OBV и
  `VOLUME_FILTER_PASSED` опираются на биржевой объём; wash trading —
  стандартная манипуляция, крипто-специфика фейкового объёма острая.
  Как учитывать манипулируемость объёма при расчёте и использовании

  гл. 12, с. 259-260, 269-270]; «⚠/∅»-разметка пробелов корпуса —

### ТР2. OBV: сравнение абсолютного значения с константой нестабильно

- **Вопрос.** OBV — кумулятивный индикатор: абсолютное значение
  зависит от точки старта расчёта (глубины загруженной истории).
  Условие `INDICATOR_COMPARE` «OBV vs `CONSTANT`» даёт нестабильную
  семантику (перезагрузка истории/другая глубина → другой уровень
  OBV при той же динамике). Доки (`IndicatorValue.md` — `ObvValue.obv`;
  контракт авторинга) использование OBV не ограничивают.
- **Ожидаемый владелец:** `trading-specialist`.
- **Кто ответил + трассировка:** `trading-specialist`. Surface —
  `trading-review` (адверсариальный проход по торговой корректности
  модели значений). Дистиллят `strategy-patterns.md`: объёмные
  индикаторы (OBV и др.) у Kaufman используются в трендовой/
  сигнальной интерпретации, интрадей-паттерны и фильтрация низкого
  объёма [Kaufman, гл. 12, PDF с. 1003-1005] — про сравнение
  абсолютного уровня OBV с константой источник не говорит;
  кумулятивная природа OBV и зависимость от точки старта —
  «предполагаю» (математическое свойство, не требующее источника).
- **Ответ.** Выводимая рекомендация: per-`ruleType` контракт (он
  дозаполняется инкрементально — `Strategy.md` §Контракт авторинга)
  при реализации OBV-операнда должен допускать для OBV
  относительные формы (`CROSSED_ABOVE`/`CROSSED_BELOW` против
  другой серии/своей скользящей, динамика), а не абсолютный
  compare с `CONSTANT`. Финальная роль OBV — вместе с ТР1.
- **Варианты.** (1) ограничить контракт (крен); (2) разрешить
  абсолютный compare, риск на авторе стратегии — отвергается
  (нестабильность не видна автору).
- **Целевой док.** Пометка в `IndicatorValue.md` (OBV) сейчас;
  правило контракта — при реализации OBV-`ruleType` (инкрементальный
  контракт), связка с IND-Q1.
- **Ярлык исхода:** `выводимо-R1`.
