## Как проверялось

Каждая гейтящая находка перепроверена **своим** ходом: цели открыты и
прочитаны (атрибуция не принята на веру), числа пересчитаны собственными
командами, заявленное прогоном — исполнено. Временные каталоги и скрипты
проб удалены; рабочее дерево возвращено к исходным 171 staged-файлам
закрытия `_28` (`git status --porcelain | wc -l` до и после — 171;
по `docs/ src/ tools/` — 104).

Средовые оговорки соблюдены: `py` (не `python`/`python3`); подмена в
мутанте проверялась грепом **до** прогона; `LC_ALL=C.UTF-8` перед
`grep -P`; `\b` вокруг кириллицы не использовался; отрицательные клеймы
собраны счётом (`| wc -l`), не `| head`.

**Базовые прогоны (мои):** `bash tools/spec-run.sh` → 20 спек, 387
примеров, `ВСЕ ПРИМЕРЫ СОШЛИСЬ`; инвентарь — 20 спек / **350** величин /

### E1. Четыре копии закрытой формы риска на стопе — **подтверждена**

Прочитаны все четыре выражения; клейм дома и `includes` всех 20 спек
проверены счётом.

| Носитель | Выражение (прочитано) |
|---|---|
| `order-sizing.perContractRisk` | `(abs(entryPrice − stopPrice) + takerFeeRate·(entryPrice + stopPrice))·contractValue` |
| `stop-distance.lossAtStopPerUnit` | `signedStopDistance + stopDistanceFloor` — знаковая, без клэмпа, без `contractValue` |
| `deal-risk-numbers.legRiskAtCurrentStop` | знаковая, без клэмпа, на `accumulatedFillSize·plannedContractValue` |
| `risk-limits.livePositionRiskAtStop` | знаковая с `max(0, …)`, на `position.externalSize·contractValue` |

Клейм-нота `perContractRisk` («ДОМ ФОРМЫ — эта спека… подключает через
includes») прочитана дословно. `grep '"includes"' docs/spec/*.json`:
`order-sizing` **не подключает никто** (девять спек с `includes`, ни в
одной его нет). Расхождение обработки знака и клэмпа — счётное, читается
прямо из четырёх выражений: `abs()` против знаковой без клэмпа против
знаковой с `max(0, …)`. Три разных числа под одним именем — подтверждено.

### E3. Пятнадцать инвариантов переживают замену константой — **подтверждена прогоном**

обязан быть пример, где он не ноль» в корпусе нет — проверено чтением.

### E4. Нулевая доля аллокации — **подтверждена, переформулирована**

Фактика воспроизведена целиком:

- `where` предиката прочитан: `… (allocationPercents < 0 || allocationPercents > 100)`
  — граница `< 0`. **Проба:** ужесточение до `<= 0` во временной копии →
  `ВСЕ ПРИМЕРЫ СОШЛИСЬ`, ни один из 387 примеров границу не трогает.
- **Проба сайзинга (моя, результат дословно совпал):** синтетический
  пример с `allocationPercents: 0` →
  `entryContracts ожидалось 0, получено 0.01` — ровно `minSize`.
- **Проба знаменателя:** `expectRefusal` на `bindingStopDistance` →
  `java.lang.ArithmeticException: Division by zero`, прогон обрывается,
  итоговой строки нет, rc=1.
- Носители сверены: `docs/rules/strategy-validation.md:69-76`
  («**Доля, которой действие объявлено, положительна**» — только
  `closeFractionPercents`), `docs/models/domain/aggregate/Strategy.md:267-272`
  (единственный указатель диапазона ведёт в этот предикат),
  `StrategyOrderActionApiModel.java:26-29` (`@Positive` `@DecimalMax("100")`),
  греп `allocationPercents` по `src/main` — поля нет ни в одном валидаторе.

**Переформулировка (достижимость).** Следствия (2) и (3) стоя́т на
состоянии, которого система **не допускает**: `@Positive` на api-модели —
единственная дверь в домен (`StrategyOrderAction.allocationPercents`
заполняется только через `apiToDomain`). По действующему правилу
`.claude/processes/roadmap-step-execution.md:172` §«Там, где код уже
написан, достижимость проверяется и по нему» это не самостоятельные
находки, а **цена** следствия (1). Гейтинг держится **одним** доводом, и
он верен: на `CODE` ведёт док, клауза положительности названа только у
`closeFractionPercents`, и исполнитель, приводящий валидацию к корпусу,
не имеет основания сохранить `@Positive` — то есть разомкнёт границу.
Формулировка «три следствия сразу» завышена; довод остаётся гейтящим.

# Дубли

1. **`G1` ≡ `F-P2` — один предмет.** Оба о том, что счёт адресного долга
   записан в двух носителях (`backlog.md:533-534` — 123;
   `docs/concept.md:553` — 178) и что копия команды в бэклоге есть
   пересказ политики вне дома. Целевой док и крен совпадают («снять
   копию, сослаться на дом»). Разошлись только классом: `G1` —
   гейтящая, `F-P2` — «прочее». **Сводится в один пункт**; надстройка
   `G1` (позиционная форма и расширение предмета в `docs/concept.md`
   §Ссылки) — надмножество. По гейтингу права F: доводом
   «исполнитель-курационник закроет задачу по 123» находка не мешает
   **писать код**. Рекомендую класс `F-P2`, объём `G1`.

2. **`E4` ≡ `F-P5` — один предмет, противоположные вердикты.** Оба:
   `allocationOutOfRange.where` = `< 0` пропускает ноль, api-модель
   строже (`@Positive`). `F-P5` не гейтит («код строже — неверного входа
   система не примет»), `E4` гейтит по трём следствиям. **Сведено
   выше:** следствия (2) и (3) недостижимы при действующем коде и по
   правилу `roadmap-step-execution.md:172` находкой не являются;
   следствие (1) — корпус ведёт на `CODE`, клауза положительности
   названа только у `closeFractionPercents` — остаётся и **гейтит**.
   Один пункт, один крен: `E4 (a)` и `F-P5 (A)` совпадают.

3. **`E2` ⊃ `E4` частично.** Мутационное доказательство `E4` («ни один
   пример границу не трогает») есть частный случай `E2`
   (`allocationOutOfRange` зелен на константе `0`). Падающий пример,
   которого требует `E2`, закрывает половину `E4` тем же ходом.

4. **`E2` ≡ `E3` — один ход.** Подтверждаю формулировку линзы: одно
   правило («предикат/инвариант засчитывается только с фальсифицирующим
   примером») плюс доводка **25** экземпляров (10 + 15). Разделять
   бессмысленно. `E5` (невыразимость отказа при нулевом знаменателе) —
   хвост `E4`, не самостоятельный ход.

**Смежное, но не дубль** (закрывать рядом, не сливать):

- `B-P4` «Обязательности, живущие в коде и не записанные в корпусе» —
  тот же класс, что `E4`/`F-P5`, но **обратного направления** (код
  строже корпуса против корпуса, который разрешает больше кода). Оба
  сходятся на `docs/rules/strategy-validation.md`.
- `B5` «Делитель четырёх потолков назван тремя носителями по-разному» —
  тот же класс, что `E1` (одна форма, несколько редакций), другой
  предмет.
- `lens-D:298` строит вариант на симметрии с `DEAL_GRAPH_INCOMPLETE` как
  с существующим — второй клейм, стоящий на гейте, которого нет в
  предписании (`F1`).

**Самые тяжёлые по существу** (в порядке цены ошибки):

1. **`E1`** — четыре неэквивалентных дома одной формы риска на стопе. На
   стопе за безубытком `abs()` даёт положительное число, знаковая —
   отрицательное, клэмп — ноль; какое попадёт в код, решает то, какой
   файл исполнитель открыл первым.
2. **`F1`** — входного fail-fast гейта полноты графа нет в единственном
   предписании исполнителю, притом что на нём уже стоя́т два чужих
   клейма. Разрешающая ошибка потолка.
3. **`E2` + `E3`** — 25 предикатов и инвариантов, каждый из которых мог
   бы не ловить ничего, а корпус остался бы зелёным. Проверено прогоном
   с рабочим контролем.
4. **`F2`** — исполнимая и неверная инструкция о писателе write-once FK;
   ошибка неисправима на месте, связь ретроспективно невосстановима.
5. **`G2`** — конвенция имён расколота ровно перед `CODE`, который
   заводит четыре новых DTO; исправление потом — переименование по всем
   потребителям.
