## Разборы (трейл R1)

### PROC-Q1 — `PositionContext` (knowledge-curator)

**Вывод:** вариант 1 — рудимент, не материализовать.

**Основание.** Зафиксированные инварианты: `Deal.position` ≤1
(`docs/models/domain/aggregate/Deal.md` §Структура), «не более одной
позиции на инструмент» (`docs/rules/trading-constraints.md`).
«Состояние позиций по инструменту» при ≤1 позиции вырождается в
0..1 — это уже поле `activePosition` в `CalculationContext`.
Источник-противоречие («Калькуляторы» §4 vs «ЖЦ сделки» §5.3)
разрешается приоритетом инварианта, зафиксированного в канон:
lifecycle-док прав, поле архивной модели — рудимент.

**Варианты:** (1) рудимент — снять поле; (2) самостоятельный RVO
(мультипозиционный контекст). Вариант 2 имел бы смысл только при
пересмотре инварианта «одна позиция на инструмент» — это продуктовое
решение, не текущее состояние.

**Эскалация-guard:** если будущая политика разрешит >1 позицию —
вопрос возвращается как продуктовый.

**Материализация при валидации:** убрать поле `positionContext` из
`docs/components/models/CalculationContext.md` (строку-пометку),
закрыть PROC-Q1 в `open-questions.md` (история закрытия — пометка,
decision-файл не нужен: применение зафиксированного инварианта, не
новое решение — аналог закрытия STRAT-Q5 по дефолту).

### DEAL-Q3 — размещение `DealActionState` (knowledge-curator)

**Вывод:** вариант 1 — `docs/models/domain/other/DealActionState.md`
+ отдельный `docs/lifecycles/DealActionState.md`.

**Основание.** По `classify-type` §«Компонент vs доменная модель»:
`domain/other` = прочая хранимая модель «без торговой бизнес-логики:
свечи, индикаторы, аудит». `DealActionState` — операционная machinery
(retry/idempotency/recovery-состояние выполнения action), не торговая
бизнес-сущность в смысле PnL — сам вопрос это констатирует. Прямой
прецедент: `AnomalyReport` — операционная модель в `domain/other` со
своим lifecycle. Lifecycle оправдан: настоящий FSM-статус
(`PLANNED → CREATED → SUBMITTED → COMPLETED / RETRY_PENDING / FAILED /
SKIPPED`) с владельцами переходов (executor'ы + retry-policy + FSM);
по критерию «через какие состояния проходит объект, кто управляет» —
один объект = один файл.

**Варианты:** (2) `domain/aggregate` — отказ: aggregate = торговые
сущности (`Deal`, `Strategy`); связь с сопровождением сделки не
делает операционный state торговым. (3) статусы разделом модели —
отказ: переходы многовладельческие (executor / RetryPolicyService /
FSM-recovery), это содержание lifecycle, не атрибут.

**Остаточная доля:** доменное представление (`RuntimeTarget` объект
vs инлайн-поля) — `code-writer` на `CODE` (в БД в любом случае JSONB
по `persistence-representation.md`). Содержание модели чуть шире —
см. DEAL-Q1 (designer предлагает включить system actions).

**Материализация при валидации:** файлы модели и lifecycle — при
ближайшей потребности (шаг 4), сейчас фиксируется только решение о
размещении; закрыть DEAL-Q3.

### CMD-Q1 — гранулярность executor'ов/payload'ов (knowledge-curator)

**Вывод:** подтвердить рабочее решение прохода 2 как правило:
file-per-executor; payload'ы — один файл с разделами; четыре
refresh-executor'а без отдельных секций не заводятся.

**Основание.** Перепись `docs/components/`: 15 executor-файлов + 7
handler-файлов уже живут file-per-X — структура устоялась, дублей и
неудобств за 8 дней не выявлено. Прецедент:
`.claude/decisions/fsm-handler-as-component.md` («Java-класс-исполнитель
→ компонент», «компонент 1:1 с элементом структуры допустим»).
Payload'ы — данные, не исполнители; по критерию гранулярности моделей
(«раздел — если не имеет ценности вне родителя») payload вне команды
ценности не имеет → один файл `ServiceCommandPayload.md` с разделами.
Refresh-executor'ы без секций в источнике — «методы заводим по
потребности» (codestyle §Неиспользуемый код, перенос принципа).

**Варианты:** группировка по семантике (CREATE_*/SUBMIT_*/...) —
отказ: ломает соответствие «файл = Java-класс» для компонентов,
осложняет ссылки; payload'ы отдельными файлами — отказ: 9+ мелких
файлов без самостоятельной ценности.

**Материализация при валидации:** короткий decision
`.claude/decisions/executor-payload-file-granularity.md`
(подтверждение прецедента с альтернативами), снять пометку
«гранулярность под вопросом — CMD-Q1» из executor-файлов, закрыть
CMD-Q1.

### ENUM-Q1 — `RISK_CONTROL` vs `ENTRY_RISK_BLOCKED` (trading-specialist + knowledge-curator)

**Вывод:** подтвердить `RISK_CONTROL`; `ENTRY_RISK_BLOCKED`
окончательно отвергнуть.

**Реплика trading-specialist.** `closeReason` — ось бизнес-причины,
не этапа. Risk-block в `PRECHECK` и risk-управляемое закрытие позже —
одна бизнес-причина «риск-контроль»; этап кодируется статусной
историей/`entryStepType`, не причиной. Отдельный `ENTRY_RISK_BLOCKED`
дублирует ось этапа внутри оси причины — таксономическая избыточность.
Аналитика «сколько кандидатов убито на входе» выводима:
`closeReason = RISK_CONTROL` + отсутствие `ENTRY_SUBMITTED` в истории.
(Семантическое суждение по модели, не корпусное — дистиллят не
требовался.)

**Реплика knowledge-curator.** Приоритет источников: risk-док §8.1 —
нормативный и новее, прямо запрещает `ENTRY_RISK_BLOCKED`; аудит-док
старше, черновой, сам себя помечает («или другое согласованное
значение»). `docs/lifecycles/Deal.md` и `Deal.md` уже фиксируют
`RISK_CONTROL`. Migration-triad п.3: знаем — кладём.

**Материализация при валидации:** decision
`docs/decisions/close-reason-risk-control.md` (подтверждение +
отвергнутая альтернатива), закрыть ENUM-Q1; `Deal.md`/`lifecycles`
не меняются (уже верны).

### RISK-Q1 — структура `RiskSettings` (trading-specialist)

**Вывод:** вариант 1 с уточнением — не отдельный RVO сейчас.
Per-trade риск живёт в `StrategyDetail` (`riskPerTradePercent`,
`targetRiskRewardRatio`) и не дублируется; «RiskSettings»
переосмысляется как **глобальная risk policy уровня счёта**,
материализуемая на шаге 5 вместе с риск-движком.

**Корпусное основание.** Риск двухслоен: ставка на сделку — слой
стратегии; риск программы/счёта — системный слой (vol target и
капитал-пересчёт [Carver ST, гл. 9, с. 175-189]; business risk и
exposure caps поверх позиций [Kaufman, гл. 24, PDF с. 2188-2195];
worst-case как отправная точка [Vince, введение, с. 6]). Состав
будущей policy (кандидаты, фиксируются на шаге 5): лимиты потерь
счёта (дневной/общий), ликвидационный буфер инварианта «ликвидация
за стопом», лимит одновременных сделок, worst-case guards (RISK-Q2).
Архивный комментарий «из StrategyDetail или глобальной risk policy»
подтверждает ту же двухслойность.

**Варианты:** (2) самостоятельный RVO сейчас — отказ: структуру
диктует риск-движок шага 5, фиксировать спекулятивно нечего;
дублирование полей StrategyDetail в RVO — рассинхрон.

**Пользовательский хвост:** численные значения лимитов (риск-аппетит)
— на шаге 5.

**Материализация при валидации:** пометку в
`CalculationContext.md`/`RiskValidator.md` сменить с «структура —
RISK-Q1» на «глобальная risk policy — структура на шаге 5»; RISK-Q1
закрыть (переформулировка ушла в шаг 5 как вход, отдельный вопрос не
нужен — шаг 5 владеет составом policy по построению).

### STRAT-Q4 — percent-anchor (trading-specialist)

**Вывод:** зафиксировать контрактный паттерн «каждое percents-поле
имеет якорь: либо соседним enum-полем (где выбор авторский), либо
фиксированным якорем, документированным per-ruleType». Для
действующих мест:

- `StrategyPricePlacement.percents` — якорь уже выражен `baseType`
  (RANGE_LOW/HIGH, SWING_LOW/HIGH, SUPPORT/RESISTANCE, ENTRY_PRICE,
  MARKET_PRICE) + `offsetSide`. Зафиксировать как образец паттерна,
  ничего не менять.
- `StopLossSettings.distancePercents` — якорь уже выражен
  `calculationType` (ENTRY_PRICE_PERCENT / ATR_PERCENT /
  MARKET_STRUCTURE_BUFFER_PERCENT). Не менять.
- `PROFIT_PERCENTS_REACHED` / `LOSS_PERCENTS_REACHED` — фикс-якорь:
  **изменение цены от средней цены входа позиции в направлении
  сделки** (% цены, не % ROE/маржи).
- `RANGE_BREAKOUT_CONFIRMED.percents` — фикс-якорь: буфер от
  пробиваемой границы диапазона (% цены границы).
- `TrailingSettings` — % цены (callback — биржевой параметр),
  `activationProfitPercents` — как PROFIT_*: % цены от входа.

**Корпусное основание.** Якорь «% цены», а не «% ROE»: при
динамическом плече (решение 2026-06-04) ROE-якорь делает условие
недетерминированным для автора — один и тот же ход цены даёт разный
ROE в зависимости от вычисленного плеча сделки; авторский контракт
должен быть предсказуем. Канонический способ мерить результат сделки
— R-мультипликаторы от начального риска [Tharp, гл. 6, с. 144-146];
выражение `PROFIT_R_REACHED` — кандидат будущего инкремента контракта
(после материализации стопов в рантайме), сейчас не вводим
(per-`ruleType` контракт дозаполняется инкрементально — принятая
политика `strategy-condition-authoring-contract.md`).

**Варианты:** (а) фикс-якоря (рекомендовано); (б) авторское поле
`anchorType` у профит/лосс-условий (вход/предыдущая свеча/хай) —
отказ сейчас: расширение по требованию, не превентивно; (в) ROE-якорь
— отказ (см. выше).

**Пользовательский хвост:** подтвердить, что фикс-якорей достаточно
для авторинга первых стратегий (это продуктовый интерфейс).

**Материализация при валидации:** дозаполнить per-`ruleType` контракт
в `Strategy.md` §Условия (якоря PROFIT_/LOSS_/RANGE_BREAKOUT) +
паттерн якоря в `strategy-condition-authoring-contract.md`; закрыть
STRAT-Q4.

### OKX-Q1 — persisted `TradeFill` (trading-specialist)

**Вывод:** вариант 1 по существу — `TradeFill` как persisted-факт
нужен; срок материализации — шаг 7 («Сделки и P&L»), раньше не
требуется (агрегация в `Order`/`AlgoOrder`/`Position` достаточна для
шагов 3-6).

**Корпусное основание.** «Реальная торговля = тестированная
торговля»: мониторинг slippage сигналов против исполнений обязателен
— без него нет основания утверждать, что система работает [Kaufman,
гл. 21, PDF с. 1913-1914]; издержки — главный предсказуемый параметр
дизайна, их фактическое измерение требует гранулярности исполнений
[Carver ST, гл. 12, с. 225-235]; измерение системы в R-мультипликаторах
требует точных entry/exit цен [Tharp, гл. 6, с. 144-152]. Агрегация
теряет: времена/цены отдельных исполнений, maker/taker (`execType`),
структуру partial fills — невосстановимо позже (OKX держит fills 3
мес). Идемпотентность по `billId`/`tradeId` упрощается персистенцией.

**Связь с OKX-Q3 (реплика):** fills и bills — два слоя одного
финализационного контура: fills = исполнение (slippage, fee
breakdown, средние цены), bills = денежный итог (включая funding).
Материализовать одним заходом на шаге 7.

**Варианты:** (2) остаться на агрегации навсегда — отказ: теряет
несобираемые данные для оценки качества исполнения; (3) материализовать
сейчас — отказ: до шага 7 потребителя нет, спекулятивная модель.

**Пользовательский хвост:** подтвердить срок (шаг 7; альтернатива —
шаг 4 вместе с REFRESH-контуром, если захочется собирать факты
раньше).

**Материализация при валидации:** OKX-Q1 закрывается решением
«да, на шаге 7»; стаб `mapping/TradeFill.md` и пометки остаются до
шага 7; план шага 7 пополняется.

### OKX-Q3 — bills как источник `DealCashFlow` (trading-specialist)

**Вывод:** вариант 1 по существу — bills-контур обязателен для
корректного итогового PnL перпа; материализация (`DealCashFlow` +
executor) — на шаге 7, одним заходом с `TradeFill` (OKX-Q1).

**Корпусное основание.** Funding — реальная компонента результата
перпа, не привязанная к ордерам; ближайший корпусный аналог —
carry/roll yield как полноправная составляющая доходности [Carver
AFTS, стратегии 10-11; Kaufman, гл. 13]; funding перпов — помеченный
пробел корпуса (∅ risk-and-sizing §14), биржевая механика OKX
документирована в наших контрактах (`account-bills.md`: subType
173/174). «Ошибки упущения — все издержки учтены?» [Kaufman, гл. 1,
заповедь 5, PDF с. 110-112]. Для свинговых сделок funding (каждые 8ч)
накапливается в значимую долю результата; PnL только по fills
систематически смещён.

**Следствие при принятии:** правило `Deal.md` §Итоговый PnL
уточнится: расчёт — fills facts (исполнение) **+ bills cashflow**
(funding/rebate); формула финализации — `resultProfit =
sum(DealCashFlow.amount)` по окну сделки с кросс-чеком против
fills-расчёта (расхождение = anomaly). Это правка канона — только
после валидации.

**Варианты:** (2) PnL только через fills — отказ: систематическое
смещение; (3) отложить решение — отказ: решение «как считаем
resultProfit» уже определяет модель шага 7, тянуть нечего.

**Пользовательский хвост:** подтвердить продуктовую трактовку
«resultProfit включает funding/rebate» (итог = что заработал счёт).

   либо удалить — финал на шаге 5. **Set-leverage — на каждую
   сделку**, перед отправкой entry (после расчёта плеча, до
   `SUBMIT_*`): иначе вычисленный риск не реализуется — позиция
   откроется под старым плечом и ликвидационная цена не та, инвариант
   «ликвидация за стопом» нарушен молча. Верификация после установки
   (ack + refresh) — несоответствие блокирует вход. Worst-case
   обоснование: ни одна позиция не должна обнулять счёт при
   максимальном мыслимом движении [Carver ST, гл. 9, с. 180-181];
   готовиться от worst-case [Vince, введение, с. 6].
2. **`externalLeverage` (OKX `lever` из спецификации) = биржевой
   максимум плеча** — тот же факт, что rules-поле
   `externalMaxLeverage`, из того же источника: прямой дубль. При
   материализации спецификации (INSTR-Q1) остаётся **одно** поле
   «биржевой потолок плеча» в спецификации; до того носитель потолка —
   `externalLeverage` на `Instrument` (единственный персистентный).
3. **`HOLD` к плечу не привязывать.** После снятия наших потолков
   нарушение = вычисленное плечо > биржевой максимум; это свойство
   конкретной сделки, не инструмента → штатный `BLOCKED` риск-проверки
   (`RiskCheckCode.EXCHANGE_MAX_LEVERAGE_EXCEEDED` уже есть), не
   статус инструмента. `HOLD` остаётся для биржевых событий
   (backlog п.9).

**Реплика solution-designer:** дубль `externalLeverage` ↔
`externalMaxLeverage` схлопывается конструкцией INSTR-Q1 (спецификация
JSONB на `Instrument` — поле потолка одно по построению); отдельного
решения не требуется.

**Пользовательский хвост:** подтвердить направление (set-leverage
на каждую сделку; судьба `leverage`-поля финализуется на шаге 5).

**Материализация при валидации:** зафиксировать set-leverage-требование
и роль полей короткими правками в `Instrument.md`/`trading-constraints.md`
(пометки «вход шага 5»), INSTR-Q2 закрыть с переносом остатка
(механика executor'а set-leverage) в шаг 4/5.

### DEAL-Q1 — persisted retry-state финализации (solution-designer)

**Вывод:** вариант «расширить `DealActionState` на системные
действия» — единый носитель retry-state для strategy- и
lifecycle/system-actions.

**Конструкция.** `strategyActionId` становится nullable; добавляется
дискриминатор системного действия (enum вида `SystemActionType`:
финализационные REFRESH_FILLS / FINALIZE_DEAL_EXIT / MARK_DEAL_CLOSED /
EMERGENCY_FINALIZATION); уникальность: `UNIQUE(deal_id,
strategy_action_id)` для стратегических + `UNIQUE(deal_id,
system_action_type)` для системных (частичные индексы). Семантика
модели честно расширяется: «runtime-состояние выполнения **действия
сделки**» (стратегического или системного).

**Основание из решённого.** (а) Архив сам закладывал системные
цели: `RuntimeTarget.entityType` включает `DEAL`/`BALANCE`/`NONE` —
бессмысленные для чисто стратегических действий. (б) Retry-механизм
один: `Retryable`/`RetryPolicyService` уже описывают флоу через
статусы `DealActionState` (`RETRY_PENDING`/`FAILED`); вторая
retry-сущность дублирует механизм. (в) Recovery-канал один:
`lifecycles/Deal.md` — FSM восстанавливается по `DealActionState`;
финализационный recovery идёт тем же каналом без расширения списка
runtime-sources. (г) Аудит не runtime-source — соблюдено.

**Варианты:** (2) отдельный `DealFinalizationState` (1:1 с Deal) —
чистая семантика, но второй носитель retry + второй recovery-source +
дублирование механизма; (3) finalization-state JSONB-полем на строке
`Deal` — дефолт persistence-representation формально применим, но
`Deal` сознательно не хранит operational state (вынесено в
`DealActionState` решением границ модели) — ломает принятую границу.

**Связка с DEAL-Q3:** размещение/lifecycle от расширения не меняются
(`domain/other` + lifecycle); содержание модели дополняется системной
осью. DEAL-Q2 (поведение при исчерпании retry) не предрешается —
остаётся пользовательским.

**Пользовательский хвост:** выбор варианта (это настоящая
концепт-развилка — R1 подаёт варианты + рекомендацию).

**Материализация при валидации:** decision
`docs/decisions/deal-action-state-system-actions.md` (или фиксация в
будущей модели `DealActionState.md` на шаге 4); закрыть DEAL-Q1.

### INSTR-Q1 — снапшот-концепция и `InstrumentExternalRules` (solution-designer)

**Вывод:** вариант 2 — переосмыслить как persisted-проекцию снапшота
**с ренеймом** от «rules» к «specification»-семантике; персистентный
дом справочных полей — **JSONB-навес на строке `Instrument`**
(дефолт `persistence-representation.md`), не самостоятельная таблица.

**Конструкция.**
- Единая граница спецификации: `InstrumentExternalSnapshot` — один
  транзиентный снапшот питает и биржевые поля `Instrument`
  (`externalStatus`/`externalLeverage` — уже так в шаге 1), и
  персистентную спецификацию при её материализации. Отдельный
  boundary `InstrumentExternalRulesExternalSnapshot` упраздняется
  (дубль границы).
- Персистентная проекция: вложенный объект на `Instrument` (рабочее
  имя `InstrumentExternalSpecification`; финальное — на
  материализации), JSONB на строке `instruments`: FK извне на rules
  нет, читается только с инструментом (`CalculationContext` грузит в
  составе контекста) — ровно профиль «навешанного на каркас».
  Нормализованные enum'ы (`InstrumentType`/`ContractType`/`Status`)
  едут внутри объекта (десериализация в типизированный класс — по
  правилу).
- «Snapshot»-нейминг для persisted-модели отвергнут: омонимия с
  транзиентной снапшот-границей (`*ExternalSnapshot` = boundary, не
  хранимое). «Rules» отвергнут: поля — факты спецификации биржи
  (sizes, ctVal, max leverage), не правила системы.
- `InstrumentExternalRulesSyncJob` концептуально остаётся (обновляет
  спецификацию на инструменте), переименование вслед за моделью.
- Дубль потолка плеча схлопывается по построению (см. INSTR-Q2).

**Варианты:** (1) самостоятельная persisted-таблица rules — осознанное
исключение из правила персистентности понадобилось бы при FK извне
или независимом цикле жизни — ни того, ни другого нет (sync-job
обновляет поле владельца так же легко); (3) ничего не решать до шага
sizing — отказ: решение уже выводимо из принятого правила
персистентности + снапшот-границы, фронт-лоад снимает блокер с
будущего шага. Материализация по-прежнему **не сейчас** (округление/
sizing/риск — поздние шаги; backlog п.9): фиксируется концепт-вход.

**Пользовательский хвост:** выбор варианта (концепт-развилка).

**Материализация при валидации:** decision
`docs/decisions/instrument-specification-not-rules.md` (конструкция +
отвергнутые), пометки INSTR-Q1 в `Instrument.md`/`mapping/*`/
`InstrumentExternalRules.md` свернуть на ссылку на decision; закрыть
INSTR-Q1 (исполнение — на шаге материализации).

### ORCH-Q1 — владелец оркестрации онбординга (solution-designer)

**Вывод:** вариант 2 оформленный — `CandleJob` остаётся владельцем
переходов `CandleGroup.Status` (уже так по lifecycle); вводится
**лёгкий компонент-координатор онбординга инструмента** (один класс,
без per-status handler'ов; рабочее имя `InstrumentOnboardingService`,
финальный нейминг — `CODE`), владелец записи `Instrument.Status`:
`CREATED → SYNC → CANDLES_LOADING` по ходу онбординга и
`CANDLES_LOADING → ACTIVE` по готовности всех групп; вызывается из
онбординг-потока и из тика `CandleJob`.

**Основание из решённого.** Онбординг-путь — линейный, 3 перехода с
простыми триггерами (спецификация синхронизирована; все группы
ACTIVE); ветвистость (HOLD, ERROR-recovery, повторный онбординг)
отложена (backlog п.9). Полный orchestrator + handler-per-status по
образцу Deal оправдан там, где per-status логика ветвиста и
многоучастна (9 статусов, 3 типа проверок, стратегия/риск) — для 3
линейных переходов это оверинжиниринг. Провизорный seam в коде шага 1
(`CandleJob.refreshInstrumentReadiness`) — фактически уже вариант 2
минус выделенный компонент: решение канонизирует его и выносит
владение статусом из джобы-производителя.

**Варианты:** (1) orchestrator + handlers по образцу Deal — отказ
сейчас, **якорь пересмотра**: материализация периферийных статусов
(backlog п.9) — если логика разветвится, паттерн в проекте уже есть;
(3) событийная модель — отказ: новый механизм без прецедента в
системе ради 3 переходов (против «появляются от потребности», радар
событий не вводил); (4) оставить в `CandleJob` навсегда — отказ:
смешивает производителя данных с владельцем статуса инструмента
(нарушает однонаправленность ответственности — джоба свечей не
должна владеть онбордингом).

**Пользовательский хвост:** выбор варианта (концепт-развилка).

**Материализация при валидации:** компонент-док
`docs/components/InstrumentOnboardingService.md` + правки указателей
в `lifecycles/Instrument.md`, `candle-loading.md` (снять «владелец —
открытый вопрос»); перенос кода из seam — на ближайшем `CODE`-касании
(шаг 3 стартует с runtime-прогона); закрыть ORCH-Q1 (заодно
распарковывается cross-cutting «warmup → plannedCandleStartDate»,
ждавший владельца, — его берёт координатор+`CandleJob` связка, деталь
шага 3).
