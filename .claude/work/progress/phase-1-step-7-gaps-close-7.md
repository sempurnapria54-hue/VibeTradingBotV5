## Узел 1 — Добыча положения закрытия (H1, H2, H3)

**Решение материализовано:** positions-history добывается **второй ногой
evidence-cycle `REFRESH_POSITION`** (live `/account/positions` → при
not-found `/account/positions-history` по `posId`), результат
**приземляется полями на `Position`**. Отдельная команда
`REFRESH_POSITIONS_HISTORY` **не вводится** (целевой состав 18 → **17**).

Поля на `Position`: `externalRealizedProfit`, `externalResultCurrency`,
`externalCloseType` (+ переиспользуются `externalAverageEntryPrice`,
`externalModifiedAt`, `externalId`). Состав ограничен полями с **названным
потребителем** — см. H22.

### H1 — операнд `end` окна линковки bills

Обе границы окна берутся из дат, **уже лежащих на `Deal`/`Position`**:
`begin` = `Position.externalCreatedAt`; `end` = `Position.externalModifiedAt`
(`uTime` записи закрытия, приземлённой ногой 2); нет записи —
`Deal.modifiedAt`.

**Записан несущий довод, который прежде подразумевался:** точность окна
сверху обеспечивает **инвариант «одна активная сделка на инструмент»**, а не
сама граница. Пока сделка удерживает слот, второй сделки по инструменту не
существует ⇒ движения по `instId` позже `begin` принадлежат ей однозначно.

**Записано условие исполнимости:** линковка выполняется, **пока сделка
удерживает слот** (статус вне `CLOSED`/`EMERGENCY_CLOSED`). После терминала
слот освобождён — окно + `instId` перестают быть однозначными, отложенная и
повторная добыча bills по этому окну **не выполняется**; добор числа за
терминалом (реш.3) обязан нести собственную адресацию. Без этого условия
аварийная и отложенная тропы снова открывали бы окно вверх.

## Узел 6 — формула комиссии (H10)

Записана **закрытая форма**:

```text
contracts ≤ budget / ( ctVal × ( |entryPrice − stopPrice|
                               + rate × (entryPrice + stopPrice) ) )
```

- **Фиксированная точка не подбирается** — точки нет, есть решение
  уравнения. Прежние две формы («вычесть комиссию из бюджета» / «прибавить к
  убытку») совпадают ровно в ней, поэтому заявление об эквивалентности
  становится **верным**. Итеративный подбор отвергнут (то же число дороже +
  провизорный порог сходимости).
- **Каждая нога — по своей цене** (вход по цене входа, выход по цене стопа):
  направленная асимметрия снята, шорты больше не сайзятся крупнее.

## Узел 7, первая половина — носитель метки свежести (H11) + H26

**Измеритель переехал на `Instrument.externalModifiedAt`** (колонка
строки-владельца); собственные `refreshCount` / `confirmedAt` навеса
**сняты**.

**Разбор достаточности связки (а не допущение):**

1. Опереться на **системный** `modifiedAt` действительно нельзя — его двигает
   JPA auditing при любой правке инструмента. Но `externalModifiedAt` —
   **другое поле с другим писателем**: биржевые `external*` пишет код,
   производящий данные. На строке `instruments` таких писателей два —
   онбординговый `SYNC` и `InstrumentExternalRulesSyncJob`, — и **оба читают
   тот же эндпоинт** `/public/instruments`. Посторонними правками метка не
   двигается.
2. **Dirty-проблема не воспроизводится:** метку пишет код **явно** на каждом
   успешном чтении, и сама эта запись делает строку dirty. Счётчик-двигатель
   (как `TradeFeeRate.refreshCount`) не нужен.
3. Три вопроса находки закрываются структурно: nullability и начальное
   состояние — колонкой и миграцией (`instruments.external_modified_at` есть
   с `V1`), выживание при перезаписи JSONB — тем, что метка живёт **вне**
   JSON.

**Уточнение конвенции записано явно:** `/public/instruments` собственной
метки обновления не отдаёт, поэтому для таких источников
`externalModifiedAt` = **момент успешного подтверждения ответом источника**.
Без этой записи поле читалось бы как «биржа что-то изменила».

**Альтернатива пользователя (отдельная таблица) — отвергнута с доводом:**
она решает те же три вопроса дороже (миграция + переписывание DataService и
гидрации) и оправдана лишь если измеритель надо **отвязать** от факта
модификации строки-владельца — а писатель у навеса и у метки один. Вернуться,
если у навеса появится второй писатель со своим тактом.

- `InstrumentExternalRules.md:81-82,:151-186,:60-83` — **правлено**.
- `InstrumentExternalRulesSyncJob.md:78-82,:133-143` — **правлено**.
- `mapping/InstrumentExternalRules.md:35-51,:88-102` — **не требует
  правки**: клауза о переносе счётчика не нужна — счётчика нет (парная

## Узел 8 — вход в safety-статусы (H13) + H14

**Множества входа зафиксированы:**

| Целевой статус | Множество входа |
|---|---|
| `ENTRY_BLOCKED` | только `ACTIVE` |
| `TRADE_BLOCKED` | любой статус |
| `CLOSED` / `ERROR` | любой статус |

Довод записан: мягкий класс запрещает **новые входы**, а они и так возможны
только из `ACTIVE`; жёсткий — реакция на аварию, которая застаёт инструмент в
любом состоянии, и ограничение входа сделало бы реакцию **пропускаемой**.
Смежный угол закрыт следствием: широкий радиус мягкой реакции онбординговые
статусы не затрагивает.

## Узел 9 — тропа отказа добычи (H15)

**Нового якоря не заводится** — попытки считает существующий механизм
`StrategyAction` (`DealActionState`); finalization-строка `FETCH_*` не
вводится.

**Асимметрия троп записана явно** (`pnl-finalization-mechanics.md` §5a) —
прежде она нигде не была зафиксирована, хотя кодировать надо именно её:

| Тропа | Отказ добычи | Реакция |
|---|---|---|
| Штатная | не смогли прочитать | ретрай/провал по счётчику; исчерпание — ошибочной тропой в `ERROR` |
| Аварийный терминал | **жёсткий** отказ чтения | приравнивается к «недоступно» → пустой результат → **терминал всё равно** |

Довод: на штатной тропе сделка живая, ждать безопасно; на аварийном терминале
ждать нельзя — трактовка жёсткого отказа как провала уводит
`MARK_DEAL_EMERGENCY_CLOSED` в `FAILED`, фабрика молчит, и сделка зависает в
`ERROR` вопреки инварианту.

**Bills не гейтят выход** — разбивка best-effort, её отсутствие даёт
`AnomalyReport`, а не удержание в `EXIT_PENDING`.

- `pnl-finalization-mechanics.md:48` — **правлено** (+§5a).
- `ServiceCommand.md:40-44` — **правлено**: оговорка «системная команда может
  не нести анкера» ограничена cleanup'ом; добывающие команды штатной тропы
  идут под `DealActionState` (CODE-пункт).
- `ExitPendingHandler.md:36-43` — **правлено** (выходная проверка).
- `MarkDealEmergencyClosedExecutor.md:37-42` — **правлено**.
- `DealFinalizationCommandFactory.md:28-33` — **не требует правки**:

## Предложения владельцу (проработаны, в доки не записаны)

### П1. Узел 3 (H5) — несостоявшаяся сделка в `ERROR` + `ENTRY_CONDITION_EXPIRED`

Выбор пользователя **исполним**, но требует трёх довесков — иначе он
воспроизводит ту же перегрузку маркера на другом терминале:

1. **`ERROR` — не терминал.** Единственный выход — `ERROR →
   EMERGENCY_CLOSED`. Значит фактический терминал не-сделки —
   `EMERGENCY_CLOSED`, и различителем работает **пара** (`status`,
   `closeReason`): (`EMERGENCY_CLOSED`, `ENTRY_CONDITION_EXPIRED`) против
   (`EMERGENCY_CLOSED`, `EMERGENCY_CLOSE`). Клауза «`EMERGENCY_CLOSE` — только
   для `EMERGENCY_CLOSED`» этому не мешает (она односторонняя).
2. **Правило добора обязано фильтровать не-сделки.** На `EMERGENCY_CLOSED`
   `resultProfit = null` означает «неисчислимо» и подлежит добору (реш.3); у
   не-сделки число не подлежит добору никогда. Фильтр — по `closeReason`
   (`ENTRY_CONDITION_EXPIRED` / риск-блок в `PRECHECK` из добора исключены),
   иначе механизм добора будет вечно гоняться за не-сделками — ровно то, что
   нашла линза C.
3. **`ErrorHandler` нуждается в раннем выходе.** Сегодня `ERROR` означает
   «авария, risk может быть жив; разрешены safety/recovery». У кандидата
   live risk не возникал вовсе, и прогонять по нему safety-flow
   (`REFRESH_POSITION`, `CANCEL_*`) незачем. Нужен явный ранний переход к
   терминалу для тропы «live risk не возникал».

**R-выборка решается сама** (побочный выигрыш H9): у не-состоявшейся сделки
`plannedRiskAmount` **пуст** — вход не ставился, писатель не отработал.
Значит R-выборка = сделки с непустым `plannedRiskAmount`, и не-сделки
выпадают **структурно**, без нового признака.

**Вторая PRECHECK-тропа (риск-блок) — предлагаю туда же**, с
`closeReason = RISK_CONTROL`: обе тропы — «сделка не состоялась, live risk не
возникал», и разводить их разными терминалами значит заводить два правила там,
где работает одно.

**Цена, которую надо принять сознательно:** `ERROR` действительно
перегружается — он перестаёт значить только «авария». Альтернатива —
отдельный терминал/признак «не состоялась» (крен линзы C) — онтологически
честнее, но вводит новое значение, чего решение пользователя избегает.

### П2. Узел 4 (H6) — адресация записи парой (`posId` + окно сделки)

- Запись positions-history адресуется **парой**: `posId` **и** попадание
  `uTime` записи в окно сделки. Переиспользованный через ~30 дней `posId`
  чужую запись больше не отдаёт — её отсекает окно.
- **H7 закрывается следствием, а не отдельным решением:** если пара
  **обязательна**, фолбэк «по `instId` без `posId`» отпадает сам — пара не
  собирается. На аварийной тропе без локальной `Position` запись не
  адресуется ⇒ число «неисчислимо» (существующий, торгово честный исход).
  Это ровно крен линзы C по H7.
- **Инвариант N11 переформулируется:** «ровно одна финализированная запись на
  **пару**», а не на `posId`. Множественная запись по паре остаётся
  controlled external error — но теперь она означает реальное нарушение, а не
  штатную вторую сделку по инструменту, то есть перестаёт гасить площадку.
- **§AG1.5 всё равно расширять вторым эпизодом** по тому же инструменту
  (H6-(а)): без него режим переиспользования не измерен, а только обезврежен.
- Окно для адресации — `[Position.externalCreatedAt, момент чтения]`;
  однозначность держит тот же инвариант слота, что и в узле 1.

### П3. Носитель расчётной валюты инструмента (нужен узлу 2)

| Вариант | Оценка |
|---|---|
| **(а) колонка `instruments.external_settle_currency` + поле `Instrument.externalSettleCurrency`** | **крен** |
| (б) поле навеса `InstrumentExternalRules.externalSettleCurrency` | против |
| (в) отдельная таблица | отпадает вместе с решением H11 |

**За (а):** расчётная валюта — часть **идентичности** инструмента (она вшита
в `instId` `ETH-USDT-SWAP`) и не меняется; она нужна **вне** риск-преконтроля
— на записи bills, тогда как навес объявлен «правилами инструмента для
преконтроля/сайзинга»; решение H11 уже поставило несущий измеритель на
**колонку** владельца, и прятать рядом ещё одно несущее свойство в JSON —
шаг назад. Плюс `InstrumentExternalRules` **прямо объявляет**, что на
base/quote/settle не претендует: вариант (б) требует отменить эту клаузу.

**Против (а) и ответ:** `Instrument.md` §«Биржевое воплощение» говорит, что
справочные поля спецификации на домене не хранятся. Клауза снимается
**адресно** для settle-ccy: «не храним» было следствием **отсутствия
потребителя**, а не принципа — потребитель появился (cross-ccy guard).
