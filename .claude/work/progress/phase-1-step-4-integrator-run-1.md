# Интегратор, прогон 1: доукомплектация OKX под шаг 4

## На какой вопрос отвечает этот файл

Каков результат первого прогона `integrator` — сверка и
доукомплектация command-relevant OKX-доков под шаг 4 и скан
возможностей по командам (на валидацию в чат).

## Контекст

Первый прогон `integrator` (`.claude/agents/integrator.md`) сразу
после материализации тулинга (агент, процесс
`api-docs-completion`, скилл `integration-okx`). Скоуп — шаг 4
(команды и их lifecycle): command-relevant контракты и нативные
модели OKX (write-команды + 5 refresh: order / algo-order /
position / balance / fills и смежное). Ступень — **Предложение**:
ничего не финализируется, всё ниже — на валидацию.

Хвосты других шагов не трогались: OKX-Q1/Q2/Q3 (шаг 7), WS/OKX-Q4
(рубеж), order-precheck/positions-history (шаги 5/7) — только
помечены в скане как форвард.

## Метод и реальность инструментов

Источник правды по правилу роли — официальный веб-док OKX
(`https://www.okx.com/docs-v5/en/`). На прогоне выяснилось:
**официальный док — JS-SPA, наивный `WebFetch` ненадёжен** —
суммаризатор конфабулировал, вернув несуществующие пути
`amend-order-algo` / `cancel-order-algo`. Реальные пути
(`amend-algos` / `cancel-algos`) подтверждены кросс-чеком (WebSearch
+ совпадение с нашими доками). Вывод занесён в скилл как известное
ограничение и в дисциплину: факты кросс-чекать, в док писать только
подтверждённое; неподтверждаемое чистым чтением SPA — оформлять
находкой «требует подтверждения», не фиксировать.

В скоупе — 5 сущностей; по каждой контракт + нативная модель уже
существуют (материализованы миграцией из архива, выверены через
`DOCS_CHECK_1..3`). Сверка с верифицированной спекой:

| Сущность | Контракт | Нативная модель | Вердикт сверки |
|---|---|---|---|
| order | `contracts/order.md` | `OkxOrderResponse.md` | **Соответствует.** Endpoints/лимиты/ACK/пагинация совпадают со спекой; attached TP/SL покрыты в response-инвентаре. |
| algo-order | `contracts/algo-order.md` | `OkxAlgoOrderResponse.md` | **Соответствует, кроме одного — см. Часть 2** (cancel-путь для trailing). |
| position | `contracts/position.md` | `OkxPositionResponse.md` | **Соответствует.** `close-position` ACK без `ordId`, подтверждение через `REFRESH_POSITION` — верно. |

## Часть 2. Находка-расхождение (Предложение, требует подтверждения)

**И-1. Cancel-путь для trailing-stop algo (`move_order_stop`).**

- **Что в нашем доке:** `contracts/algo-order.md` перечисляет
  `move_order_stop` (trailing) среди create-типов и указывает
  cancel всех algo через `POST /trade/cancel-algos`
  (`CANCEL_ALGO_ORDER`).
- **Что говорит спека (кросс-чек, 2 источника):** OKX делит algo на
  две семьи — *ordinary* (trigger / oco / conditional) → `cancel-algos`
  и *advance* (iceberg / twap / **trailing**) → `cancel-advance-algos`.
  То есть trailing-stop, вероятно, **не отменяется через `cancel-algos`**
  — нужен `cancel-advance-algos`.
- **Последствие, если верно:** `CANCEL_ALGO_ORDER`, маршрутизированный
  на `cancel-algos`, провалит отмену trailing-stop algo. В шаге 4 это
  латентно (использует ли единственная стратегия фазы 1 trailing —
  открытый вопрос; защита сейчас — TP/SL через conditional/oco), но
  **контракт-док описывает вероятно неверный путь**.
- **Статус:** не финализировано. SPA-чтение официального дока
  ненадёжно; находка корпусно подтверждена сторонними клиентами, но
  **не** чистым чтением официального дока. На валидацию: подтвердить
  по официальному доку и решить — (а) если trailing в скоупе фазы 1:
  `CANCEL_ALGO_ORDER`-исполнитель ветвит cancel-путь по типу algo
  (advance → `cancel-advance-algos`); (б) если trailing вне скоупа
  фазы 1: пометить `move_order_stop` форвардом и сузить контракт до
  фактически используемых ordinary-типов. **Крен:** (б) —
  фаза 1 защищается TP/SL, trailing не нужен; убрать риск неверного
  пути сужением скоупа дешевле, чем заводить ветвление под
  неиспользуемый тип.

## Часть 3. Скан возможностей (команды vs поверхность OKX)

Сверка command-layer против поверхности API. С уважением к принятым
решениям: отвергнутое по вкусу/scope не перевыносится без новой
фактуры. Каждый кандидат — с ярлыком владельца-шага.

| # | Возможность OKX (не используется) | Релевантность командам | Владелец / горизонт | Предложение |
|---|---|---|---|---|
| В-1 | `POST /trade/cancel-all-after` (dead-man's switch: авто-снятие всех ордеров по таймауту без heartbeat) | серверная страховка для `EXECUTE_KILL_SWITCH` / потери связи | safety/kill-switch кластер = **backlog п.7 / `AnomalyJob` (шаг 8)** | **Форвард.** Не тащить в шаг 4; передать владельцу safety-кластера как кандидат на серверную страховку поверх явного kill-switch. |
| В-2 | `POST /trade/order-precheck` (серверная пре-валидация влияния ордера на счёт) | прямо релевантно `PrecheckHandler` / преконтролю | **шаг 5 (Риск-преконтроль, HOLD)** | **Форвард.** Кандидат: преконтроль может опираться на/дополняться биржевым precheck. Передать владельцу шага 5. |
| В-3 | `GET /account/positions-history` (история закрытых позиций) | P&L / агрегирование в `Deal` | **шаг 7 (Сделки и P&L)** | **Форвард.** Смежно с `OKX-Q*` шага 7; не трогаем сейчас. |
| В-4 | Batch-write: `batch-orders` / `cancel-batch-orders` / `cancel-advance-algos` (до 20 операций в одном HTTP) | эффективность множественных операций | **portfolio (шаг 3+)** | **Отложить, низкий приоритет.** Конфликтует с принятой гранулярностью «одна команда на сущность» (смежно CMD-Q3). Новой фактуры под пересмотр гранулярности нет; в фазе 1 (1 стратегия / 1 инструмент) выгоды нет. Не перевыношу как пересмотр. |
| В-5 | `stpMode` / `stpId` (self-trade prevention на place-order) | риск/исполнение submit | **сознательно не используется** (помечено в `OkxOrderResponse.md`) | **Не предлагаю.** Деление зафиксировано как неиспользуемое; новой фактуры нет. |

Внутри-скоупных (шаг 4) возможностей, которые стоило бы добавить
сейчас, скан **не выявил**: attached TP/SL (`attachAlgoOrds`) уже
смоделирован (`AttachedProtectionPayload` +
`AttachedAlgoOrderStateResolver`); evidence-cycle покрывает
pending/history/archive звенья. Всё содержательное — форвард к
владельцам будущих шагов.
