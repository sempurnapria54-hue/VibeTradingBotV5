## Пробелы по типам (концептный фокус)

### 1. Несогласованности между доками

- **К1. «Активные/готовящиеся стратегии» vs `Strategy.Status`.**
  `IndicatorJob.md` («читает активные/готовящиеся стратегии») и
  `MarketPhaseJob.md` («настройки активных/готовящихся стратегий»)
  используют термин «готовящиеся», которого нет в lifecycle:
  статусы — `CREATED` / `ACTIVE` / `INACTIVE` / `DELETED`
  (`docs/lifecycles/Strategy.md`). Явно задано только «для
  `DELETED` новые значения не считаются»
  (`market-data-freshness.md`). По каким статусам jobs реально
  считают данные — не задано: `CREATED` (вероятно да — активационная
  проверка «можно ли рассчитать индикаторы» требует расчёта до
  активации), `INACTIVE` (не задано: считать ради мгновенной
  реактивации vs не считать ради экономии). Содержательная политика
  → эскалация Э2.

### 2. Name-level без структуры (где структура нужна шагу 3)

- **К2. Схема identity-keying результатов — центральный пробел
  шага.** Решение `docs/decisions/market-data-result-identity-keying.md`
  зафиксировало направление: результаты ключуются идентичностью
  считаемого (тип + `timeframe` + canonical-`params`), ссылка на
  настройку (`strategy_indicator_setting_id`) из результата уходит;
  «точная схема — при построении кластеров результатов»; «текущие
  доки `IndicatorValue`/`MarketStructure` (и job-доки) пока несут
  старый `UNIQUE` — он переписывается на этом же шаге реализации».
  Шаг реализации индикаторного кластера — **этот**. `IndicatorValue`
  конструируется и получает схему хранения в шаге 3 → по
  функциональному порогу доки обязаны задать: состав идентичности и
  новый `UNIQUE`; канонизацию `params` (стабильная сериализация для
  сравнения/уникальности); судьбу поля `setting:
  StrategyIndicatorSetting` в модели (при identity-keying результат
  на настройку не ссылается); checkpoint `IndicatorJob` («по
  последнему рассчитанному timestamp» — теперь per идентичность);
  проверку из решения «прежнее по-настройке ключевание ничем не
  держалось». Конструкция → кандидат на делегирование
  `solution-designer` в `GAPS_CLOSE_1`: по правилу срока — живой
  потребитель, текущий шаг выигрывает. MarketStructure-часть той же
  правки — под Э1.

- **К3. Warmup-derive: «кратно period» без формулы.** Strategy.md
  §IndicatorParams: эффективный `warmup = override ?? derived`,
  «настоящий derive — у реализаций индикаторов (шаг 3)»; для
  рекурсивных (EMA/RSI/ATR) derive описан как «кратно `period`» без
  множителя, MACD — «от старшего периода» без формулы. Потребители
  числа: candle-loading (глубина истории) и `IndicatorJob` (пропуск
  разгонной зоны). Грань «доки vs деталь реализации CODE» →
  эскалация Э3. Торговый штрих — ТР2.

- **К4. `Candle.volume` nullable vs volume-индикаторы.**
  `Candle.md` §Персистентность: `volume` — **nullable**; OBV
  (`ObvValue`) и будущие volume-условия требуют объём каждой свечи.
  Поведение расчёта при `NULL` не задано (пропуск свечи / трактовка
  как 0 / ошибка расчёта / гейт на группу). Поведение ветвится по
  значению поля → доки должны задать. Разбор вместе с IND-Q1 (Э4) —
  это про целостность входа, IND-Q1 — про доверие к значениям.

### 3. Неотвеченные вопросы

- **IND-Q1 (владелец — шаг 3, срок настал).** Надёжность биржевого
  объёма (wash trading) для `VOLUME_FILTER_PASSED` и OBV. Механику
  расчёта не гейтит (формула OBV известна); гейтит роль объёма в
  условиях и, возможно, состав сохраняемого. Требует интернет-добора
  крипто-специфики (пробел корпуса ∅ — `microstructure.md` §9) —
  вход пользователя. Эскалация Э4.

- **К5. Парковка «вход стратегии в candle-loading» повисла.**
  `candle-loading.md` §«Глубина под прогрев»: как warmup-горизонт
  стратегии перекладывается в `Instrument.plannedCandleStartDate` —
  «запарковано (всплывёт вместе с владельцем оркестрации,
  ORCH-Q1)»; смежно: «созданы `CandleGroup` по нужным таймфреймам»
  (`lifecycles/Instrument.md`) — кто определяет набор ТФ, name-level.
  ORCH-Q1 отложен на конец фазы → якорь распарковки уехал. Сам
  расчёт шага 3 не гейтится (считаем по тем свечам, что есть;
  warmup-зона просто сдвигает первое сохранённое значение), но
  end-to-end «значения, запрошенные стратегией» (новая стратегия
  объявила ТФ/warmup — история должна подъехать) упирается в
  парковку. Эскалация Э5: минимальная связка в шаге 3 vs
  перепарковка на новый якорь vs ручная политика Фазы 1.

## Торговые находки (фокус `trading-review`)

### Содержательные

- **ТР1 (= материал IND-Q1/Э4).** Объём — самый манипулируемый вход
  кластера. Источник говорит: wash trades / «paint the tape» —
  стандартный приём [Harris, гл. 12, с. 259-260, 273-274];
  крипто-специфика фейкового объёма — ∅ пробел корпуса
  (`microstructure.md` §9). Предполагаю: OBV/объём как
  единственное основание ENTRY ненадёжен, как вспомогательный
  фильтр — приемлем; политика — в разборе IND-Q1. Сюда же К4:
  nullable объём = тихая деградация volume-индикаторов, если
  политика NULL не задана.

- **ТР2 (= торговая сторона К3).** Несошедшийся рекурсивный
  индикатор — систематически смещённые значения: EMA/RSI/ATR
  сходятся асимптотически, при warmup = `period` ранние значения
  зависят от seed'а. Модель уже страхует механикой («сохраняются
  только значения после warmup-зоны» — `IndicatorJob.md` §Warmup),
  вопрос только в **величине** эффективного warmup. Прямого тезиса
  в дистилляте нет — «предполагаю» (математика сходимости
  экспоненциального сглаживания); консервативный множитель для
  рекурсивных — содержание Э3.

### Положительная сверка (модель корпусу соответствует)

- Только закрытые свечи, без look-ahead, на всех уровнях (правило
  производящей стороны `confirm=1`, расчёты по закрытым) —
  фундаментальная гигиена данных расчёта.
- Freshness-гейтинг: data-dependent действия не выполняются по
  протухшим данным; jobs не трогают `Strategy.Status`
  (`market-data-freshness.md`) — разделение административного
  разрешения и runtime-готовности.
- Immutable params + шаринг результата по идентичности — расчёт
  детерминирован, без скрытой подгонки на лету (анти-meddling, ср.
  [Carver ST, гл. 12, с. 231-233] — сверено ещё на шаге 2).
- Волатильность через ATR/Bollinger bandwidth без отдельной
  сущности — достаточный минимум для стопов/фаз Фазы 1.

## Эскалации

Разбор — по одной за раз, в порядке номеров:

1. **Э1 (гейт охвата, стадия 0).** Входят ли в шаг 3 кластеры
   `MarketStructure`/`MarketPhase` (jobs + модели + сервисы) или
   только индикаторный? За узкое чтение — формулировка шага
   («Индикаторы»). За широкое: `market-data-calculation` — один
   кластер из трёх jobs с цепочкой зависимостей (Structure ←
   optional IndicatorValue; Phase ← IndicatorValue + Structure); ни
   один другой шаг фазы структуру/фазу не несёт; шаг 7
   (`EntryScannerJob` выбирает `StrategyDetail` по фазе) потребует
   готовую фазу — без неё end-to-end цикл фазы не соберётся.
   Рекомендация: включить весь кластер производных рыночных данных
   в шаг 3 (иначе у структуры/фазы нет шага-дома).
2. **Э2 (К1).** По каким статусам стратегий jobs считают данные:
   `CREATED` — считать (нужно для активационной готовности)?
   `INACTIVE` — считать (мгновенная реактивация) или нет (экономия
   расчёта)? Зафиксировать состав и поправить термин
   «активные/готовящиеся» в job-доках.
3. **Э3 (К3).** Где фиксируются derive-формулы эффективного warmup
   per тип: в доках до `CODE` (таблица формул в §IndicatorParams /
   job-доке) или инвариантом «derived ≥ create-минимум» с формулами
   в коде. Рекомендация: короткая таблица формул в доках —
   потребители числа (candle-loading depth) концептуальные, не
   кодовые.
4. **Э4 (IND-Q1 + К4).** Роль объёма: ограничение до
   вспомогательного фильтра vs полноправный вход; политика
   `volume = NULL` при расчёте OBV/volume-условий; нужен
   интернет-добор крипто-специфики wash trading (вход пользователя).
5. **Э5 (К5).** Судьба парковки «warmup/набор ТФ стратегии →
   plannedCandleStartDate/CandleGroup»: минимальная связка в
   шаге 3 / перепарковка на новый якорь (без ORCH-Q1) / ручная
   политика Фазы 1 (plannedCandleStartDate задаётся при создании
   инструмента с запасом). Рекомендация: ручная политика Фазы 1 +
   перепарковка автоматики, оркестрацию в шаг 3 не тянуть.
