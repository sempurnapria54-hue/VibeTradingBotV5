## Пробелы по типам (концептный фокус)

### 1. Несогласованности между доками

- **Н1. Статусная политика расчёта: «активные/готовящиеся» vs
  `Strategy.Status`; полубитая ссылка.** `IndicatorJob.md` («читает
  активные/готовящиеся стратегии») и `MarketPhaseJob.md`
  («настройки активных/готовящихся стратегий») используют термин
  «готовящиеся», которого нет в lifecycle (`CREATED` / `ACTIVE` /
  `INACTIVE` / `DELETED` — `docs/lifecycles/Strategy.md`);
  `MarketStructureJob.md` статусы не упоминает вовсе (асимметрия).
  Явно задано только «для `DELETED` не считаются». Верификация
  атрибуции: `market-data-calculation.md` §Условия запуска подвешивает
  обе клаузы («jobs не меняют статус»; «для DELETED не считаются») на
  ссылку «(правило — `market-data-freshness.md`)» — правило свежести
  содержит только первую; источник DELETED-клаузы —
  `docs/lifecycles/Strategy.md`. По каким статусам jobs реально
  считают (`CREATED`? `INACTIVE`?) — не задано, а поведение по ним
  ветвится.

### 2. Name-level без структуры (где структура нужна шагу 3)

- **Н2. Схема identity-keying результатов — центральный пробел
  шага.** `docs/decisions/market-data-result-identity-keying.md`
  зафиксировал направление (ключ = тип + `timeframe` +
  canonical-`params`; ссылка на настройку из результата уходит) и
  явно отложил схему на «шаг реализации кластеров» — это **этот**
  шаг. `IndicatorValue` и `MarketStructure` конструируются и
  получают схему хранения в шаге 3 → по функциональному порогу доки
  обязаны задать: состав идентичности и новые `UNIQUE`; канонизацию
  `params` (стабильная сериализация); судьбу полей `setting` в
  моделях (при identity-keying результат на настройку не ссылается;
  поля `timeframe`/`params` в моделях отсутствуют); checkpoint
  `IndicatorJob` per идентичность; переформулировку статус-фильтра
  (Н1) в терминах идентичностей («идентичность запрошена хотя бы
  одной стратегией в считающем статусе»); представление наследников
  `IndicatorValue` (7 подтипов) и `MarketPriceLevel`
  (реляционно/JSONB — модель несёт `id`, дефолт правила
  `persistence-representation.md` тянет к JSONB; FK извне не
  документированы); проверку из решения «прежнее по-настройке
  ключевание ничем не держалось». Старый `UNIQUE(…, *_setting_id, …)`
  несут: `IndicatorValue.md`, `MarketStructure.md`,
  `IndicatorJob.md`, `MarketStructureJob.md`,
  `market-data-calculation.md` §Условия. `MarketPhase` решением не
  затронут (контейнер реляционный).

- **Н3. Warmup-derive: «кратно period» без формулы.** `Strategy.md`
  §IndicatorParams: эффективный `warmup = override ?? derived`,
  create-минимумы заданы (окно/рекурсивные → `period`; MACD →
  `slow + signal`; стохастик — сумма окон; OBV → 1), «настоящий
  derive — у реализаций индикаторов (шаг 3)»; для рекурсивных
  (EMA/RSI/ATR) — «кратно `period`» без множителя. Потребители
  числа: candle-loading (глубина истории — концептуальный
  потребитель) и `IndicatorJob` (пропуск разгонной зоны). Грань
  «доки vs деталь реализации CODE» не выбрана. Торговая сторона —
  ТР2.

- **Н6. Семантика классификации фазы — params без семантики
  (новая).** `MarketPhaseParams` несёт `algorithmType`
  (`STRUCTURE_ONLY` / `INDICATORS_ONLY` / `STRUCTURE_AND_INDICATORS`),
  `minTrendScore`, `minRangeScore`, `confirmationBars` — но нигде не
  задано: что такое «score», из чего он считается по каждому
  `algorithmType` (какие входы из `IndicatorValue` / `MarketStructure`
  и как сворачиваются), что именно подтверждает `confirmationBars`,
  как выбирается `Type` (`BULL_TREND`/`BEAR_TREND`/`RANGE`/`UNKNOWN`)
  и откуда берётся `confidenceScore` модели. В отличие от формул
  индикаторов (общеизвестная математика) классификация фазы —
  **наш собственный алгоритм**, общеизвестного канона нет;
  `MarketPhase` конструируется в этом шаге, поведение ветвится по
  params → доки должны задать контракт семантики. Торговая сторона —
  ТР3.

- **Н7. Optional `IndicatorValue`-вход структуры не выражен моделью
  (новая).** `MarketStructureJob.md` («может использовать
  `IndicatorValue` как фильтр шума») и цепочка процесса
  («Candles + optional IndicatorValue → MarketStructureJob»)
  объявляют индикаторный вход, но концепция не выражает, **какой**
  индикатор и **чьей настройкой** он запрошен:
  `StrategyMarketStructureSetting` индикаторных ссылок не несёт, а
  `Destiny` (`MARKET_PHASE` / `ENTRY_CONDITION` / `ACTION_PRICE` /
  `PROTECTION` / `EXIT_CONDITION`) значения «под структуру» не имеет
  — настройку индикатора «для фильтра шума структуры» сейчас нельзя
  объявить. Либо вход выражается (расширение `Destiny` /
  внутренняя производная идентичность из `MarketStructureParams`),
  либо опциональная зависимость снимается из доков.

- **Н8. Якорь свежести результата неоднозначен (новая, мелкая).**
  `MarketStructure.md`: «актуальность проверяется через …
  `expirationDuration` и `confirmedAt` / `windowEndAt`»;
  `MarketPhase.md`: «… `candleTimestamp` / `confirmedAt`» — от
  какого из двух полей меряется возраст, не задано;
  `MarketDataExpirationChecker.md` анкер тоже не фиксирует. Для
  `IndicatorValue` поле одно (`candleTimestamp`) — неоднозначности
  нет.

### 3. Неотвеченные вопросы

- **Н4 (= IND-Q1 + политика NULL-объёма).** Надёжность биржевого
  объёма (wash trading) для OBV / `VOLUME_FILTER_PASSED` — открытый
  вопрос со сроком «шаг 3». Смежно (поведение ветвится по значению
  поля): `Candle.volume` — **nullable** (`Candle.md`
  §Персистентность), а OBV и volume-условия требуют объём каждой
  свечи; поведение расчёта при `NULL` (пропуск свечи / 0 / ошибка /
  гейт) не задано. Торговая сторона — ТР1.

- **Н5 (парковка warmup → `plannedCandleStartDate` без якоря; +
  расширение).** `candle-loading.md` §«Глубина под прогрев»: перенос
  warmup-горизонта стратегии в `Instrument.plannedCandleStartDate`
  «запарковано (всплывёт вместе с владельцем оркестрации, ORCH-Q1)»
  — но ORCH-Q1 отложен на конец фазы, якорь распарковки уехал.
  Расчёту шага это не мешает (считаем по имеющимся свечам), но
  end-to-end «значения, запрошенные стратегией» (новая стратегия
  объявила ТФ/warmup → история должна подъехать) упирается в
  парковку. **Расширение перепрогона:** объявленный вход глубины
  сформулирован только через индикаторы («эффективный `warmup` +
  `timeframe` каждой `StrategyIndicatorSetting`»), тогда как при
  охвате Э1 истории требуют и структура (`lookbackBars`,
  `swingLookbackBars`), и фаза (`confirmationBars`) — их в формуле
  входа нет. Смежно name-level: «созданы `CandleGroup` по нужным
  таймфреймам» (`lifecycles/Instrument.md`) — кто определяет набор
  ТФ.

## Торговые находки (фокус `trading-review`)

### Содержательные

- **ТР1 (= Н4).** Объём — самый манипулируемый вход кластера.
  Источник говорит: wash trades / «paint the tape» — стандартный
  приём блефа [Harris, гл. 12, с. 259-260, 273-274];
  крипто-специфика фейкового объёма — пробел корпуса ∅
  (`microstructure.md` §9). Предполагаю: объём как единственное
  основание ENTRY ненадёжен, как вспомогательный фильтр — приемлем.
  Сюда же: nullable объём без политики NULL = тихая деградация
  volume-индикаторов.

- **ТР2 (= Н3).** Несошедшийся рекурсивный индикатор —
  систематически смещённые значения: EMA/RSI/ATR сходятся
  асимптотически, при warmup = `period` ранние значения зависят от
  seed'а. Механика уже страхует («сохраняются только значения после
  warmup-зоны» — `IndicatorJob.md`), вопрос в **величине**
  эффективного warmup. Прямого тезиса в дистилляте нет —
  «предполагаю» (математика сходимости экспоненциального
  сглаживания); корпус оперирует EWMA-span'ами без
  warmup-множителей.

- **ТР3 (= Н6, новая).** Режимная классификация — вершина каскада
  шага (по фазе выбирается `StrategyDetail`, от неё зависит вся
  торговля) и при этом самое слабое концептуальное звено: источник
  говорит — опознать боковик трудно, адаптивные техники «не решают
  всё» [Kaufman, гл. 17, PDF с. 1529-1532]; формальная рамка
  тренд-vs-шум — efficiency ratio [Kaufman, гл. 1, PDF с. 98-107];
  перформанс правил падает в режиме высокой волатильности [Carver
  AFTS, стратегия 13, PDF с. 293-295]. Пока семантика скоров не
  задана (Н6), торговую корректность классификатора проверить
  нельзя — это и есть находка: модель не выражает торговое правило,
  по которому собирается торговать.

### Положительная сверка (модель корпусу соответствует)

- Только закрытые свечи, без look-ahead, на всех уровнях (правило
  производящей стороны `confirm=1`; расчёты по закрытым; инвариант
  повторён в процессе и в job-доках).
- `confirmedAt` / `confirmationBars` у структуры и фазы —
  анти-look-ahead подтверждение, согласуется с дисциплиной
  «подтверждённый сигнал, не экстраполяция».
- Freshness-гейтинг: data-dependent действия не выполняются по
  протухшим данным; jobs не трогают `Strategy.Status`
  (`market-data-freshness.md`).
- Immutable params + шаринг результата по идентичности — расчёт
  детерминирован, без подгонки на лету (анти-meddling: параметры
  системы как источник оборота = meddling [Carver ST, гл. 12,
  с. 231-233]).
- `UNKNOWN`-фолбэк у структуры и фазы + матрица `UNKNOWN → NO_TRADE`
  (`PhaseEntryPolicy.isAllowedFor`) — «не уверен → не торгуй»,
  корректная страховка классификатора.

## Эскалации (маршрут через владельцев, с трассировкой)

Прогон — обкатка маршрута: вопросы маршрутизированы владельцам
инлайн (одна сессия, роли = стойки агент-доков); пользователю в
этом прогоне ничего не выносится на содержательное закрытие
(режим обкатки пайплайна). Исходы:

1. **Н1 → `solution-designer`.** Surface: `concept-review`
   (открыты: оба job-дока, процесс §Условия запуска,
   `market-data-freshness.md` — клаузы DELETED там нет,
   `lifecycles/Strategy.md` — источник истины по статусам).
   Работа владельца: политика **выводима из канона** — `CREATED`
   считать (активационная готовность «можно ли рассчитать» требует
   расчёта до активации — процесс §Активация); `INACTIVE` считать
   (lifecycle: «блокирует **только** новые сделки» + открытые сделки
   сопровождаются по pinned detail и их step'ы требуют свежих данных
   — иначе marketDataExpiredSetting принудительно закрывал бы их,
   противореча lifecycle); `DELETED` — не считать (явно).
   **Исход: решение подготовлено (R1)** — статусная политика
   CREATED/ACTIVE/INACTIVE = считать, DELETED = нет; формулировка
   финализируется в терминах идентичностей вместе с Н2; правка
   термина «готовящиеся» в job-доках + переподвес ссылки в процессе.
   На валидацию пользователю — на `GAPS_CLOSE_2`.

2. **Н2 → `solution-designer`.** Surface: `concept-review` (открыты:
   decision identity-keying — направление и явная отложка «на этом
   шаге»; обе модели; job-доки; `persistence-representation.md` —
   дефолты представления; `strategy-tree-persistence` — прецедент).
   Работа владельца: конструкторская задача, не быстрый ответ —
   опора есть (направление решено, прецеденты персистентности
   стоят), объём: состав ключей, канонизация `params`, судьба
   `setting`-полей, checkpoint, представление подтипов и
   `MarketPriceLevel`, статус-фильтр в терминах идентичностей.
   **Исход: принято владельцем в работу** — блокер шага → решается
   сейчас, R1-пакет (схема + альтернативы) готовится на
   `GAPS_CLOSE_2`. Остатка пользователю на этом прогоне нет.

3. **Н3 → `trading-specialist` + `solution-designer` (смешанная;
   торговое — первым, как ограничение).** Specialist (грунт:
   дистиллят `strategy-patterns` §3, `system-design` §4 — корпус
   оперирует EWMA-span'ами, точного warmup-множителя не несёт):
   требование — для рекурсивных типов эффективный warmup строго
   больше create-минимума `period`, множитель консервативный;
   величина — «предполагаю» (математика сходимости), помечена
   **неуверенность**. Designer: потребитель числа концептуальный
   (candle-loading depth) → крен к короткой таблице derive-формул в
   доках + инвариант «derived ≥ create-минимум»; альтернатива
   (формулы только в коде) оставлена как вариант.
   **Исход: варианты + крен подготовлены (R1)** — на валидацию на
   `GAPS_CLOSE_2`.

4. **Н4 → `trading-specialist`.** Surface: `trading-review`/ТР1
