## C1. Терминала у встроенной защиты отменённого родителя с нулевым наливом не производит никто: `CANCEL_BY_PARENT` стои́т за условием, которое опровергнуто наблюдением того же закрытия

**Вопрос.** Кто и по какому предикату переводит встроенную защиту в
терминал, когда родитель отменён при **нулевом** наливе, — если
наблюдение источника говорит, что элемент `attachAlgoOrds` **остаётся** в
теле отменённого родителя?

**Грунт (торговый, добыт контуром).**
`.claude/tests/source-api/okx/plan.md:934-942` (цепочка C17a, RUN
2026-08-30): «После отмены родителя `attachAlgoOrds[0]` **сохраняется в
теле отменённого родителя** с прежними значениями и пустыми
`failCode`/`failReason`». То есть операнд `attachedInSnapshot` у
отменённого родителя **истинен**.

**Цитаты (носители).**

- `docs/spec/order-lifecycle.json:62` — `missingAttachedOutcome`:
  `... if(parentStatus == 'CANCELED', if(parentAccumulatedFillSize > 0,
  'SEARCH_MORE', 'CANCEL_BY_PARENT'), ...)`. Величина по построению
  вычисляется только при **отсутствии** защиты в снапшоте (имя, нота
  `:61`, таблица `docs/lifecycles/Order.md:67-81`).
- `docs/spec/order-lifecycle.json:56` — `attachedBecomesActive =
  attachedInSnapshot && isNull(failCode) && parentAccumulatedFillSize > 0`;
  при нулевом наливе ложна, и защита остаётся `PENDING` (нота `:51`: «До
  налива защита принята биржей, но не материализована — это `PENDING`»).
- `docs/spec/order-lifecycle.json:300-313` — парный контрпример
  `CANCEL_BY_PARENT` объявляет состояние `"attachedInSnapshot": false` при
  `parentStatus: CANCELED`; ровно это состояние C17a опровергает.
- `docs/lifecycles/Order.md:79` — строка `CANCEL_BY_PARENT` таблицы
  исходов; `docs/models/domain/core/Order.md:187` — единственный
  производитель `PARENT_ORDER_CANCELED` назван «исполнитель добычи
  родителя **на исходе `CANCEL_BY_PARENT`**».
- `docs/spec/protection-coverage.json` — `isLive` для `ATTACHED` =
  `in(status,'PENDING','ACTIVE')`; `trancheHasLiveProtection` = `any
  isLive`; `trancheRiskBearing = trancheExposure > 0 ||
  trancheHasLiveEntryOrder || trancheHasLiveProtection`.
- `docs/spec/deal-lifecycle.json` — `riskProvenAbsent = graphComplete &&
  !hasLiveEpisode && !dealRiskBearing && !anyLiveOrder &&
  exposureReconciled`; `docs/components/MarkDealClosedExecutor.md:60-62` —
  «Терминал ставится **только после подтверждённого отсутствия живого
  риска и терминальности всех траншей**».
- `docs/components/MarkDealClosedExecutor.md:39` — тропа «**отмена
  неисполненного входа** из отправленного входа транша» объявлена одной из
  трёх штатных троп закрытия без входа.
- `src/main/java/.../okx/resolve/OkxAttachedAlgoOrderStateResolver.java:29-46`
  — действующий код исполняет **снятую** редакцию (`nonNull(snapshot) →
  ACTIVE`, `resolveMissing` только при `snapshot == null`); он подтверждает
  механизм: ветвь `resolveMissing` достижима лишь при отсутствии элемента.

**Почему гейтит.** Цепочка замкнута и счётна: элемент присутствует ⇒
`missingAttachedOutcome` не вычисляется ⇒ `CANCEL_BY_PARENT` и
`PARENT_ORDER_CANCELED` не производятся никем; `attachedBecomesActive`
ложна при нулевом наливе ⇒ статус остаётся `PENDING`; `PENDING` входит в
`isLive` ⇒ `trancheRiskBearing` истинен ⇒ транш не терминален и
`riskProvenAbsent` ложен ⇒ штатный терминал не ставится. Сделка,
отменившая неисполненный вход, **зависает с ненулевым признаком живого
риска** — состояние, которое `docs/concept.md` §«Что это за система»
объявляет несуществующим («зависшего живого риска у системы не бывает») и
которое держит слот инструмента `uk_deal_active_instrument`. Тропа —
одна из трёх штатных троп закрытия без входа, то есть не краевая.

**Уровень пробела.** Концепция-стык: контракт между резолвером встроенной
защиты, предикатом живости, предикатом живого риска транша и гейтом
терминала. Плюс вложенный уровень доказательства: несущий контрпример
спеки стои́т на состоянии, опровергнутом грунтом того же закрытия.

**Целевой док.** `docs/spec/order-lifecycle.json` (форма

`docs/lifecycles/Order.md` §«Отсутствие встроенной защиты в снапшоте» и
§«Живость подтверждается наливом родителя» + строка производителя
`docs/models/domain/core/Order.md`.

**Ожидаемый владелец.** `integrator` (первым: предмет — трактовка факта

## C2. Пятый источник цикла добычи заявки не дошёл до трёх носителей и не имеет ни одной per-source формы

## C3. Формулировка исхода `SEARCH_MORE` шире формулы: терминал `COMPLETED` у родителя даёт `PROTECTION_LOST` на защите, которую источник материализовал живой

**Вопрос.** Почему дискриминатор налива введён **только** в ветвь
`CANCELED`, если наблюдённый факт («при непустом наливе защита
материализуется живой самостоятельной заявкой») от статуса терминала не
зависит, а док прямо утверждает более широкую популяцию?

**Цитаты (носители).**

- `docs/lifecycles/Order.md:76` — «Две популяции: родитель живой — **либо
  родитель терминален с непустым наливом**, и тогда защита материализована
  самостоятельной живой заявкой».
- `docs/spec/order-lifecycle.json:62` — формула даёт `SEARCH_MORE` при
  терминале только для `CANCELED`; `COMPLETED` (налив непуст по
  определению статуса) уходит в
  `if(positionLive && !standaloneProtectionExists, 'PROTECTION_LOST',
  'ANALYSE_HISTORY')`.
- `docs/spec/order-lifecycle.json:230-251` (примеры «родитель исполнен,
  позиция жива, отдельной защиты нет — покрытие потеряно» и «…отдельная
  защита есть») — оба **не несут** операнда `parentAccumulatedFillSize`
  вовсе.
- `docs/lifecycles/Order.md:77` — исход `PROTECTION_LOST`: «Защита и
  сделка — в `ERROR`»; `docs/models/domain/core/Order.md:190` — тот же
  исход даёт `closeReason = PROTECTION_LOST`;
  `docs/rules/external-status-resolution.md:52-60` — реакция на этот класс
  — `Exchange.TRADE_BLOCKED`, ступень 2, kill-switch flatten.
- `.claude/tests/source-api/okx/plan.md:956-978` — факт сформулирован без
  оговорки о статусе: «при непустом наливе встроенная защита
  **материализуется самостоятельной живой conditional-заявкой** на
  налитый объём», «судьба защиты от инициатора терминала не зависит».

**Почему гейтит.** Ветвь `COMPLETED` — самая частая тропа (вход налился
целиком). Если элемент `attachAlgoOrds` в снапшоте истории отсутствует
хотя бы в одном режиме ответа, исход `PROTECTION_LOST` объявляет
потерянным покрытие, которое живо на бирже: заявка + сделка в `ERROR` и
биржевая ступень 2 с flatten по ложному факту — та самая ошибка, ради
которой правился соседний дизъюнкт. Если же элемент присутствует всегда
(как наблюдено у отменённого), то оба примера `COMPLETED` стоя́т на
недостижимом состоянии и доказательства не несут. Корпус не отвечает,
какая из двух ветвей верна, — и в обеих формулировка `:76` расходится с
формулой.

**Уровень пробела.** Предмет/концепция-стык (популяция дискриминатора) с
вложенным уровнем доказательства (два примера без операнда, на
непроверенной достижимости).

**Целевой док.** `docs/spec/order-lifecycle.json` (`missingAttachedOutcome`
+ примеры) и `docs/lifecycles/Order.md` §«Отсутствие встроенной защиты в
снапшоте».

**Ожидаемый владелец.** `integrator` (достижимость состояния —
факт источника), затем `solution-designer`.

**Трассировка.** Сверка прозы `:76` с `expr` формулы построчно →

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| **Достаточность существующего** | Оставить: `COMPLETED` покрыт `standaloneProtectionExists` | Ложно: операнд объявлен как «**отдельная основная** защита существует» (`order-lifecycle.json`, операнды), то есть наш `AlgoOrder`; материализованная запись доменной строкой `AlgoOrder` не является (`docs/models/domain/core/Order.md:145-150`). Цена — ложный `PROTECTION_LOST` |
| **A. Цена — ветвь `ERROR`-родителя обязана быть выписана явно (иначе поглощается) |
| **B. консервативный по направлению: лишний поиск дешевле ложного
`PROTECTION_LOST`.

**Ярлык дефицита.** `грунт` для B/C (нужен прогон: несёт ли снапшот

## C4. Ветвь ноги 1 рефреша позиции «позиции нет и локальной строки нет» не имеет дискриминатора популяции — и на своей объявленной популяции не адресуема

**Вопрос.** Чем ограничена ветвь, заводящая строку **закрытого** эпизода,
если её условие («живая позиция не найдена, живой строки нет») истинно у
всякой сделки между отправкой входной заявки и её филлом?

**Цитаты (носители).**

- `docs/components/RefreshPositionExecutor.md:17-36` — ветвление первой
  ноги; четвёртая ветвь: «не найдена, живой строки нет → эпизодов у сделки
  нет вовсе: завести строку **ЗАКРЫТОГО** эпизода по записи истории →
  нога 2».
- `docs/components/RefreshPositionExecutor.md:54-68` — «Она достижима у
  **восстановленной** сделки…»; и далее: «**Записи истории нет** (эпизод
  чужой либо старше окна) — строка **всё равно заводится**, но без
  положения закрытия, и звено не завершается … сделка уходит **аварийным**
  терминалом».
- `docs/components/SystemActionExecutor.md:44-51` — «Звенья — добывающие
  команды по известным сущностям сделки: **позиция**, заявки, условные
  заявки, баланс, движения средств. **Состав цикла един для всех троп**;
  разводится гейт звена. Звено добычи **движений** эмитится только на
  выходной тропе» — разведён гейт только у движений; звено позиции
  эмитится и до филла.
- `docs/components/TrancheEntrySubmittedHandler.md:25-29` — выходные
  проверки статуса «вход отправлен» включают «позиция открыта», то есть
  проход в этом статусе факты позиции добывает.
- **Вторая половина, на объявленной популяции:**
  `docs/components/RefreshPositionExecutor.md:76-94` — запись истории
  адресуется «инструментом и **временным окном от времени создания первой
  отправленной ноги входа**», и тут же: «**Известное ограничение:** у
  позиции вокруг чужого риска отправленной ноги входа нет, значит нет и
  операнда нижней границы — подтропа **не адресуема**».
- **Соседний исполнитель тот же операнд имеет:**
  `docs/components/RefreshBillsExecutor.md:21-36` — нижняя граница =
  `Deal.billsWindowBegin`, иначе **суррогат** `Deal.externalCreatedAt`;
  `docs/models/domain/aggregate/Deal.md:426-441` — дом решения о суррогате
  («Без суррогата восстановленная сделка осталась бы без окна … это было
  бы благоприятное умолчание»); `docs/components/DealOpeningService.md:87-90,
  106-115` — на тропе восстановления `Deal.externalCreatedAt` пишется
  биржевым моментом детектора и назван «единственный операнд нижней
  границы окна линковки».

**Почему гейтит.** Два счётных исхода.

1. **Ложное срабатывание.** У штатной сделки в статусе «вход отправлен»
   живой позиции ещё нет, строки эпизода тоже нет ⇒ ветвь заводит
   **фантомную строку закрытого эпизода** без положения закрытия. Дальше
   `closeRecordFetched` ложен навсегда (`docs/spec/deal-result.json`),
   `allCloseRecordsFetched` ложен, `resultAvailable` ложен ⇒ итог сделки
   недоступен, `waitContinues` до исчерпания бюджета, затем
   `errorPathRequired` ⇒ холд инструмента полной формы и аварийный
   терминал с «неисчислимо» (`docs/rules/pnl-reconciliation.md:106-131`).
   Ошибка направлена в разрешающую сторону по наблюдаемости результата:
   каждая штатная сделка теряет число.
2. **Несрабатывание на объявленной популяции.** У восстановленной сделки
   операнд нижней границы отсутствует по прямому заявлению того же дока,
   то есть ветвь, заведённая ради неё, записи не адресует; а рядом, у
   исполнителя движений, для того же класса операнда суррогат существует и
   назван домом. Две стороны одного стыка отвечают на «чем заменяется
   пустая нижняя граница» по-разному.

**Уровень пробела.** Концепция-стык: дискриминатор популяции связывает
эмиттер звена (`SystemActionExecutor`), исполнитель добычи позиции,
предикат доступности итога и суррогат нижней границы, чей дом —
`Deal.md`. Правка одного носителя пробел не закрывает.

**Целевой док.** `docs/components/RefreshPositionExecutor.md` (условие
ветви и адресация) + `docs/models/domain/aggregate/Deal.md` (дом операнда
нижней границы: распространяется ли суррогат на окно адресации записи
истории) + при выборе гейта — `docs/components/SystemActionExecutor.md`.

**Ожидаемый владелец.** `solution-designer` (конструкция дискриминатора);
`integrator` — по вопросу, чем адресуется запись истории при отсутствии
отправленной ноги.

**Трассировка.** Читал `RefreshPositionExecutor.md` целиком → искал гейт
звена позиции в `SystemActionExecutor.md`, `fsm-execution-layering.md`,
`deal-management.md`, `command-lifecycle.md`, `DealContext.md` (гейта нет,
разведён только гейт звена движений) → проверил достижимость статуса
«вход отправлен» по `TrancheEntrySubmittedHandler.md` → сверил операнд
нижней границы с `RefreshBillsExecutor.md` и домом в `Deal.md` →
`DealOpeningService.md` на предмет того, чем заполнена восстановленная
сделка.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| **Достаточность существующего носителя** | Считать, что ветвь и так ограничена словом «эпизодов у сделки нет вовсе» | Не ограничивает: у сделки до филла эпизодов тоже нет вовсе. Существующего различителя в тексте ветви нет; ближайший durable-факт — `Deal.entryReason = RECOVERY` — в ветви не назван |
| **A. Гейт по durable-признаку тропы: ветвь работает только при `entryReason = RECOVERY`** | Дискриминатор — уже существующая колонка (`docs/models/domain/aggregate/Deal.md`), нового поля не заводится | След минимальный (правка клаузы). Цена: тропа «наша сделка, эпизод схлопнулся и запись не наблюдалась» ветвью не покрывается — но она и не заявлена ветвью |
| **B. Гейт по факту операций: ветвь работает, только если по сделке были операции на бирже** | Дискриминатор — признак «операций по сделке не было» (`docs/rules/deal-without-operations.md`), уже используемый обоими терминалами | След тот же; покрывает и восстановленную (риск живой ⇒ операции есть), и схлопнувшийся эпизод. ## C5. Кто заводит строку эпизода на тропе материализации — нога 1 или нога 2: три носителя расходятся

**Вопрос.** Какая нога команды рефреша позиции создаёт строку эпизода,
впервые увиденного закрытым, и какая наполняет положение закрытия и
двигает верхнюю границу окна линковки?

**Цитаты (носители).**

- `docs/components/RefreshPositionExecutor.md:23-25` и `:62-64` — строку
  заводит **нога 1**, и «положение закрытия — из той же записи», то есть
  нога 1 же его и наполняет.
- `docs/lifecycles/Position.md:16-20` — «**Вторая нога** статус не меняет
  … она **наполняет положения закрытия** на строках эпизодов и двигает
  верхнюю границу окна линковки»; `:58-59` — «Позиция, впервые увиденная
  уже закрытой, заводится **второй ногой** сразу закрытой — из записи
  истории».
- `docs/models/mapping/PositionCloseResult.md:53-59` — «**материализация**
  … и **вторая нога** заводит её из записи истории».
- `docs/models/domain/core/Position.md:54-57` — «Поля положения закрытия
  пишет **вторая нога** рефреша позиции … и **той же транзакцией** нога
  двигает верхнюю границу окна линковки движений».

**Почему гейтит.** Верхняя граница окна линковки движений привязана к
транзакции наполнения положения закрытия. Если положение наполняет нога 1
(редакция дока исполнителя), а границу двигает нога 2 (редакция дома
модели), то у эпизода, материализованного ногой 1, граница окна не
двигается: строки движений после этого момента в окно не попадают,
левые стороны пар сверки и слагаемое чужой валюты считаются по усечённой
популяции. Направление — заниженный/недосчитанный результат при внешне
полном числе. Плюс `writer-named-for-every-value.md:9-10` требует
однозначного актора у каждого значения; здесь их два.

**Уровень пробела.** Носитель: истина верна хотя бы в одном месте, дефект
— в согласии носителей (три против одного, дом не назван).

**Целевой док.** `docs/components/RefreshPositionExecutor.md` (привести к
дому) либо `docs/lifecycles/Position.md` + `docs/models/domain/core/Position.md`
+ `docs/models/mapping/PositionCloseResult.md` — в зависимости от того,
какая редакция признаётся верной; дом стыковой истины («что делает каждая
нога») по `.claude/rules/carrier-levels.md` — уровень правила/жизненного
цикла, не док деталей.

**Ожидаемый владелец.** `solution-designer`.

**Трассировка.** Сверял четыре носителя пофайлово после того, как ветвь
ноги 1 (C4) заявила наполнение положения закрытия; проверил привязку
верхней границы окна к транзакции в `Position.md` и в
`PositionCloseResult.md:69`.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| **A. Верна редакция «нога 2»** | Нога 1 только заводит строку (статус закрытый, полей положения нет); нога 2 по своему предикату «строка закрыта и положения не несёт» её наполняет и двигает границу | След — правка двух пассажей в доке исполнителя. Цена: лишний проход по той же записи истории в рамках одной команды (обрыв на первом успешном источнике этого не запрещает) |
| **B. Верна редакция «нога 1»** | Нога 1 заводит и наполняет; нога 2 такие строки не подбирает | След — правка трёх носителей, включая дом модели. Цена: движение верхней границы окна обязано быть перенесено в ту же транзакцию, иначе окно молча не двигается — то есть правка тянет за собой дом окна |
| **C. Развести носители: тропа материализации — отдельное звено** | Ни нога 1, ни нога 2, а самостоятельный шаг | Больший след (новое звено, новая строка исполнения) без счётной выгоды; выписан ради оси структурной свободы |

**Крен — A.** Меньший след и совпадает с тремя носителями из четырёх; при
B правка тянет дом окна линковки, то есть уходит на уровень выше.

## C6. `Position.CloseReason.UNKNOWN` — производителя нет ни в доке, ни в спеке, ни в коде

**Вопрос.** Кто и в какой момент пишет `UNKNOWN` в `Position.closeReason`?

**Цитаты (носители).**

- `docs/models/domain/core/Position.md:97-107` — таблица производителей;
  строка `UNKNOWN`: «fallback, когда причину безопасно определить не
  удалось» — пассивный залог, компонент не назван
  (`docs/rules/writer-named-for-every-value.md:23-25`: «Пассивный залог
  писателя не называет … Нет подлежащего-компонента — требование не
  выполнено»).
- `docs/spec/external-status-resolution.json` — `closeReasonCandidate` для
  `POSITION` даёт только `EXTERNAL_CLOSE` либо `null`: ветвь
  `resolvedStatus == 'CANCELED'` (единственный источник `UNKNOWN` через
  `coalesce(cancelIntentReason,'UNKNOWN')`) у позиции недостижима —
  `resolvedStatus` для `POSITION` возвращает `ACTIVE` либо `CLOSED`.
- `docs/models/mapping/Position.md:91-95` — `UNKNOWN` прямо назван
  **не используемым** как requested reason.
- Код: `LC_ALL=C.UTF-8 grep -rn "CloseReason.UNKNOWN" src/main` — четыре
  вхождения, все у `AttachedAlgoOrder`, `AlgoOrder` и `Order`; у
  `Position` — ни одного.
- Тот же файл, `:114-124`, снимает `UNKNOWN_EXTERNAL_STATUS` **ровно по
  этому доводу** («производителя у него нет нигде»), то есть довод в
  таблице уже применён — к соседней строке и не к этой.

**Почему гейтит.** Пограничный, но гейтит по `docs/concept.md` П3
(«у каждого значения назван писатель») и по правилу-энфорсеру: значение
перечня без достижимого писателя — «описание состояния, в которое система
не умеет попасть», и оно **приглашает выдумать тропу** — тот самый довод,
которым в этом же файле снято соседнее значение. Писатель кода, увидев
значение в перечне, обязан либо реализовать fallback (и получить причину
без объяснимого происхождения — нарушение П3), либо не реализовать (и
оставить в енуме мёртвую константу).

**Уровень пробела.** Носитель (перечень разошёлся с фактикой писателей),
не доказательство: сама истина — «производителя нет» — в корпусе уже
выражена соседней строкой.

**Целевой док.** `docs/models/domain/core/Position.md` §Енумы
(таблица производителей) + `docs/models/mapping/Position.md` §«Close reason
при close-position»; при снятии — CODE-дельта в `.claude/work/backlog.md`
рядом с уже стоящим пунктом «Снять значения без производителя»
(`backlog.md:215-223`).

**Ожидаемый владелец.** `solution-designer` (снятие значения перечня),
`knowledge-curator` — за перенос в CODE-дельту.

**Трассировка.** Проходил три таблицы производителей (`Order`,
`AlgoOrder`, `Position`) построчно, сверяя каждое значение с формой
`closeReasonCandidate` в спеке и с грепом по `src/main`; `UNKNOWN` у
`Position` — единственное значение, не сошедшееся ни с одним из трёх
источников.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| **Достаточность существующего** | Оставить как страховку «на всякий случай» | Отвергается прямой клаузой того же файла: «оставленное оно приглашало бы выдумать тропу» (`docs/models/domain/core/Order.md:118-122` — тот же довод у `CONDITION_EXPIRED`). Цена — значение без объяснимого происхождения в персистентной колонке |
| **A. Снять `UNKNOWN` из `Position.CloseReason`** | Перечень сводится к четырём значениям с производителями | След — правка перечня + строка CODE-дельты (в коде значение не используется, миграция не нужна: `.claude/rules/pre-launch-schema-changes.md`). Цена — при появлении новой тропы придётся заводить значение заново |
| **B. Назвать производителя явно** | Например: резолвер позиции при `ERROR`-статусе — по симметрии с `AttachedAlgoOrder` (`OkxAttachedAlgoOrderStateResolver` пишет `UNKNOWN` на `ERROR`) | След — та же одна строка, но требует, чтобы у позиции ветвь `ERROR` резолвером производилась; сегодня `ERROR` позиции производит слой интеграции при нарушении инварианта и ставит `EXCHANGE_INVARIANT_VIOLATION`, то есть места для `UNKNOWN` нет. Цена — либо вторая ветвь `ERROR`, либо ложный писатель |
| **C. Записать явное «состояние недостижимо, и чем»** | Законный исход по `writer-named-for-every-value.md:47-50` | След наименьший; цена — значение остаётся в енуме и в колонке, а недостижимость приходится держать прозой |

**Крен — A.** Симметрично уже принятому снятию `UNKNOWN_EXTERNAL_STATUS`
в том же перечне и тем же доводом; меньший след из закрывающих.

**Ярлык исхода.** `варианты-с-креном`.
**Ярлык дефицита.** `работа`.
