## Решённая рамка (не переоткрывать)

- `MarketPhase.Type` определяется авторскими условиями по образцу
  `StrategyCondition`; по фазе выбирается `StrategyDetail`.

## Сквозная рамка (три наблюдения поверх подвопросов)

**1. Редизайн — это унификация, не новая подсистема.** До: у фазы
свой бэспоук-движок скоринга, отдельный от грамматики условий. После:
классификация фазы переиспользует **ту же** авторскую грамматику
(`StrategyCondition`/`StrategyConditionRule`/`StrategyConditionOperand`)
и **тот же** `StrategyConditionEvaluator`. Это снимает целую
подсистему скоринга и убирает дубль грамматики — *выводимо из
codestyle* (DRY, «неиспользуемого/дублирующего кода быть не должно»).

**2. Направление зависимости (инвариант от циклов).** Цепочка jobs —
Indicator → Structure → **Phase** → EntryScanner. Фаза вычисляется из
индикаторов и структуры; правила фазы поэтому **не могут** ссылаться
на `MARKET_PHASE` (само-референция/цикл) и на runtime-источники сделки
(`POSITION`/`ORDER`/`ALGO_ORDER`/`BALANCE`/`DEAL`) — на момент
классификации сделки нет, фаза считается per-инструмент×настройка до
выбора детали. Это даёт **контекстно-суженный whitelist операндов и
ruleType** для условий фазы (подвопрос 1).

**3. Сдвиг владения торговым смыслом.** Раньше «что считать трендом»
проектировал алгоритм системы (формула score). Теперь это композирует
**автор стратегии** из грунтованных корпусом примитивов (ER, свинговая
структура, подтверждение баром, консервативный UNKNOWN — все из части
1.1, *источник говорит*). Роль `trading-specialist` сжимается с
«спроектировать формулу скоринга» до «дать меню грунтованных
операндов/предикатов, из которых автор собирает правило». Пороги
становятся **авторскими константами в условиях** — это усиливает уже
зафиксированное «значение порогов = численный риск-аппетит = хвост
пользователя» (1.2 прежнего файла): хвост не исчезает, он переезжает
из полей params в литералы операндов.

## Подвопрос 1. Носитель правил

**Что нужно.** Как `StrategyMarketPhaseSetting` несёт правила
определения фазы: структура авторинга, операнды, отображение набора
правил на `MarketPhase.Type` (одно правило на тип? приоритет при
нескольких срабатываниях? дефолт `UNKNOWN`).

### Опорная находка: операндный пул уже на месте

`StrategyMarketPhaseSetting` **уже** несёт
`indicatorSettings: List<StrategyIndicatorSetting>` и
`marketStructureSettings: List<StrategyMarketStructureSetting>` (см.
`Strategy.md` §StrategyMarketPhaseSetting). Под редизайн они становятся
**операндным пулом** правил фазы — ровно как detail-level настройки
служат пулом для entry-условий. Меняется только `params:
MarketPhaseParams` (подвопрос 2). *Выводимо из established* — структура
уже есть, переиспользуется.

### Развилка 1 — как набор правил отображается на `Type`

- **(A) Упорядоченный список клауз `(condition → type)`, first-match
  wins, fallthrough = `UNKNOWN`** — **крен·рекомендация**.
  `phaseRules: List<StrategyMarketPhaseRule>`, каждая клауза `{ level,
  type, condition: StrategyCondition }`. Проверяются по `level` ASC;
  первая, чьё `condition` истинно, задаёт свой `type`; ни одна не
  сработала → `UNKNOWN`. Параллелит `StrategyCondition.rules` (тоже по
  `level` ASC) и стандартную decision-table-семантику «первое
  совпавшее правило выигрывает». `UNKNOWN` **не авторится** — это
  безопасный неявный fallthrough (согласуется с матрицей `UNKNOWN →
  NO_TRADE` и инвариантом детали «UNKNOWN → явная NO_TRADE-деталь»:
  потребитель полон, продюсер всегда достижим в UNKNOWN). Несколько
  клауз на один `type` допустимы и полезны (разные паттерны
  свидетельства → одна фаза).
- **(B) `Map<MarketPhase.Type, StrategyCondition>` + фикс-приоритет
  типов** — отвергается: Map теряет порядок, при срабатывании двух
  типов нужен отдельный тайбрейк-приоритет; нельзя выразить два разных
  способа быть одним типом; жёстче и беднее (A).
- **(C) Список как (A), но `UNKNOWN` авторится явной финальной
  catch-all-клаузой** — допустимо как опция поверх (A), но не дефолт:
  неявный fallthrough безопаснее (автор не может «забыть» UNKNOWN и
  оставить дыру).

### Эскиз модели (на валидацию)

```
StrategyMarketPhaseSetting:
  timeframe: TimeFrame
  phaseRules: List<StrategyMarketPhaseRule>          // ← заменяет params: MarketPhaseParams (тип распускается, подвопрос 2)
  indicatorSettings: List<StrategyIndicatorSetting>          // операндный пул, без изменений
  marketStructureSettings: List<StrategyMarketStructureSetting>   // операндный пул, без изменений
  expirationDuration: Duration

StrategyMarketPhaseRule:
  level: Integer                 // порядок проверки ASC; первая истинная клауза выигрывает
  type: MarketPhase.Type         // какой фазе соответствует клауза (BULL_TREND/BEAR_TREND/RANGE)
  condition: StrategyCondition   // та же грамматика; операнды — по key из пула настройки
```

Имя элемента — `StrategyMarketPhaseRule` (консистентно с
`StrategyMarketPhaseSetting`). **Коллизия терминов:** внешняя
клауза (`StrategyMarketPhaseRule`, condition→type) и внутреннее
правило условия (`StrategyConditionRule`) обе зовутся «rule».
Альтернатива без коллизии — `StrategyMarketPhaseClause` /
`phaseClauses`. *Минорный designer-выбор; крен — `…Rule` ради
слой-консистентности, но помечаю коллизию.*

### Контекстный whitelist операндов и ruleType (из сквозной рамки п.2)

Условие клаузы фазы — полноценный `StrategyCondition`, но **в
суженном контексте классификации**:

- **Разрешённые `sourceType`:** `INDICATOR` (по `indicatorKey` из пула),
  `MARKET_STRUCTURE` (по `structureKey` из пула), `PRICE`, `CONSTANT`,
  `TIME` (если понадобится).
- **Запрещённые `sourceType`:** `MARKET_PHASE` (цикл), `POSITION`,
  `ORDER`, `ALGO_ORDER`, `BALANCE` (нет runtime-контекста сделки).
- **Разрешённые `ruleType`:** сравнивающие (`INDICATOR_COMPARE`,
  `PRICE_COMPARE`, `CROSSOVER`), структурно-эффективностные
  (`RANGE_BREAKOUT_CONFIRMED`, `TREND_CHANGED`,
  `EFFICIENCY_BELOW_THRESHOLD`, `VOLUME_FILTER_PASSED`, `CANDLE_CLOSED`)
  + предложенный `MARKET_STRUCTURE_IS` (подвопрос 5).
- **Запрещённые `ruleType`:** жизненный цикл сделки/позиции
  (`NO_OPEN_POSITION`, `NO_ACTIVE_DEAL`, `ENTRY_ORDER_FINALIZED`,
  `POSITION_OPENED`, `ATTACHED_STOP_LOSS_EXISTS`,
  `MAIN_PROTECTION_EXISTS`, `PROFIT_PERCENTS_REACHED`,
  `LOSS_PERCENTS_REACHED`) и `MARKET_PHASE_IS` (цикл).

Whitelist проверяется create-валидацией (400) — параллельно
существующему per-`ruleType` контракту авторинга
(`strategy-condition-authoring-contract.md`). *Выводимо из established*
(контекстное сужение grammar, та же линия валидации).

**Крен подвопроса 1:** вариант (A) — упорядоченный first-match-список
клауз `{ level, type, condition }` с неявным `UNKNOWN`-fallthrough;
операндный пул — уже существующие `indicatorSettings`/
`marketStructureSettings`; контекстный whitelist на create.

## Подвопрос 2. Судьба `MarketPhaseParams`

Текущее: `algorithmType` (`STRUCTURE_ONLY`/`INDICATORS_ONLY`/
`STRUCTURE_AND_INDICATORS`), `minTrendScore`, `minRangeScore`,
`confirmationBars`.

### Что уходит безусловно (*выводимо из редизайна*)

- **`algorithmType` — удаляется.** Какие источники свидетельства питают
  фазу, теперь выражается тем, **какие операнды автор пишет** в
  условиях: только структурные операнды ≈ прежний `STRUCTURE_ONLY`,
  только индикаторные ≈ `INDICATORS_ONLY`, оба ≈ комбинация. Информация
  enum'а **субсумируется** авторскими условиями — поле избыточно.
- **`minTrendScore` / `minRangeScore` — удаляются.** Скоринга нет;
  планка свидетельства выражается **конкретными сравнениями в
  условиях** (напр. `EFFICIENCY_BELOW_THRESHOLD` с `percents`,
  `INDICATOR_COMPARE` ER vs `CONSTANT`). «Риск-циферблат» переезжает в
  литералы операндов (сквозная рамка п.3) — свойство «пороги = хвост
  пользователя» сохраняется и усиливается.

### Развилка 2 — судьба `confirmationBars` / анти-whipsaw (перепрогон после валидации)

**Что разошлось на валидации.** Прошлый крен был **(A) сохранить
фаза-уровневый дебаунс полем `minPhaseHoldBars`**. Дообучение входа:
(i) не была рассмотрена опция «персистентность задаётся параметром
самого индикатора-операнда» (вариант B рассматривался только в
дорогой форме «руками в каждой клаузе»); (ii) приемлемость остаточного
whipsaw была подана как инженерный дефицит, тогда как это
**продуктово-рисковое решение пользователя** — и пользователь его
**принял**: отдельного фаза-уровневого дебаунса не держим, устойчивость
целиком на уровне операндов.

**Зафиксированный вход (хвост пользователя, не переоткрывается).**
Остаточный перескок решения фазы на стыке режимов **приемлем** — это
риск-аппетит автора стратегии, не инженерный регулятор системы.
Следствие: фаза-уровневый дебаунс **снимается**.

Тогда вопрос сужается до: *достижима ли операнд-уровневая
персистентность и требует ли она добавления поля?*

### Осуществимость опции 1 — персистентность на индикаторе-операнде

Разбор модели индикатора (`StrategyIndicatorSetting` = `{ key, type,
params }`; `IndicatorParams` = база `timeframe`/`warmup` + математика по
типу — `Strategy.md` §IndicatorParams). Различаю **два** механизма
анти-whipsaw, которые прошлая проработка смешала:

1. **Сглаживание (smoothing) — УЖЕ достижимо без добавлений.** Период
   индикатора *и есть* горизонт сглаживания/персистентности; длиннее
   период → меньше дребезг. Более того, у ряда индикаторов горизонт
   подтверждения **уже стоит в сигнатуре**: `period` (EMA/RSI/ATR/
   Bollinger), `signalPeriod` (MACD — сглаживание линии), `dPeriod` +
   `smoothPeriod` (Stochastic — сглаживание %K). Это ровно опция 1
   пользователя в её работающей форме: горизонт описан **один раз на
   индикаторе**, переиспользуется всеми клаузами по `key`, без правки
   каждой клаузы. *Источник говорит* на компромисс лаг↔ложные сигналы
   (длиннее окно → меньше ложных смен режима) [Kaufman, дистиллят
   `strategy-patterns.md` §1/§4]; *предполагаю·инженерное* — что
   удлинение окна снижает частоту флипов (математическое свойство
   сглаживания, не торговое утверждение).
   *Исключение:* OBV (`enabled`) сглаживающего параметра не несёт
   (кумулятивен) — согласуется с ТР2 (OBV стабилизируют относительной
   формой, не абсолютным сравнением).

2. **Дискретное подтверждение (hold-N-bars гистерезис перехода) — НЕ
   достижимо сейчас, и на индикатор-*значение* не садится.**
   Подтверждение — свойство **перехода состояния** (пересечение
   порога/смена знака), а не сырого значения: «подтвердить EMA(20)» вне
   сравнения смысла не имеет. *Предполагаю·инженерное.* На сырой
   индикатор-операнд hold-N-bars навесить нельзя без того, чтобы
   индикатор начал отдавать дебаунс-производную серию (что и есть просто
   ещё одно сглаживание → п.1). Поэтому если автору нужен именно
   дискретный hold-N-bars поверх индикаторного сравнения (не сглаживание
   периодом) — это **добавление**, и оно садится не на индикатор, а на
   сравнивающее правило → **под-развилка ниже**.

**Вывод осуществимости:** операнд-уровневая персистентность **в базовой
форме уже достижима** — (а) сглаживающими периодами индикаторов
(переиспользуются по `key`), (б) для структурных клауз —
`breakoutConfirmationBars` структуры (клаузы на `RANGE_BREAKOUT_CONFIRMED`
наследуют подтверждение). Добавлять для базы редизайна **ничего не
нужно**. Возражение «руками в каждой клаузе» снято: подтверждение живёт
на операнде/структуре, не в клаузе.

### Под-развилка — нужен ли дискретный hold-N-bars (если да, куда)

Возникает, только если автору мало сглаживания и нужен дискретный
гистерезис на чисто-индикаторном сравнении.

- **(S1) `confirmationBars` на сравнивающем правиле** (`INDICATOR_COMPARE`/
  `CROSSOVER`/`PRICE_COMPARE`): «сравнение истинно, продержавшись N
  закрытых баров» — **крен под-развилки**, *если* потребность возникнет.
  Семантический дом — переход состояния (зеркалит `breakoutConfirmationBars`
  структуры). Дешевле отвергнутого «руками»: первоклассное поле правила,
  не отдельное правило в каждой клаузе. Применимо и к фазовым, и к
  entry-условиям единообразно.
- **(S2) Поле подтверждения на индикатор-настройке, реюз по `key`** —
  отвергается для дискретного подтверждения: подтверждение сырого
  значения семантически не определено (схлопывается в сглаживание =
  период, п.1). Для сглаживания добавка не нужна (уже есть периоды).
- **Дефолт под-развилки — не добавлять (S0).** По принципу
  «инфраструктура от потребности, не превентивно»: hold-N-bars не
  вносится, пока конкретная стратегия не упрётся в недостаточность
  сглаживания. Тогда — инкрементом по контракту авторинга (как
  `MARKET_STRUCTURE_IS`/OBV-ТР2), вариантом S1. **Не блокер редизайна.**

### Пересобранный крен подвопроса 2

- `algorithmType` + `minTrendScore` + `minRangeScore` удаляются
  (без изменений к прошлому разбору).
- **`confirmationBars` удаляется тоже** — фаза-уровневого дебаунса нет
  (принятый риск-аппетит пользователя). Анти-whipsaw — операнд-уровневый:
  сглаживающие периоды индикаторов (реюз по `key`) + структурный
  `breakoutConfirmationBars`. Добавлять ничего не нужно.
- Дискретный hold-N-bars — **не вносим** (S0); при доказанной
  потребности — на сравнивающее правило (S1), инкрементом, не на фазу и
  не на индикатор-значение.

### Судьба типа `MarketPhaseParams` (досверка)

При снятом дебаунсе у `MarketPhaseParams` **не остаётся ни одного поля**:
`algorithmType`, `minTrendScore`, `minRangeScore`, `confirmationBars` —
все ушли. **Тип распускается целиком без остатка**, JSONB-колонка
`params` со строки `strategy_market_phase_settings` исчезает,
`StrategyMarketPhaseSetting` не несёт ни `params`, ни `minPhaseHoldBars`.
*Выводимо из codestyle* (не держать пустую обёртку). Это подтверждает
оговорку прошлой проработки «если дебаунс убрать — исчезает целиком».

**Крен подвопроса 2:** все четыре поля `MarketPhaseParams` удаляются,
тип распускается **без остатка**; анти-whipsaw полностью операнд-уровневый
(сглаживающие периоды индикаторов + структурный `breakoutConfirmationBars`),
ничего добавлять не нужно; дискретный hold-N-bars — отложенный инкремент
на сравнивающее правило (S1) по потребности, не дефолт.

## Подвопрос 3. Исполнение в job

Текущий `MarketPhaseJob`: читает настройки, читает `IndicatorValue` +
`MarketStructure`, применяет `MarketPhaseParams` (`algorithmType`),
сохраняет `MarketPhase`, «может сохранять score».

### Развилка 3 — кто оценивает правила

- **(A) Переиспользовать `StrategyConditionEvaluator` + тонкий
  доменный `MarketPhaseClassifier`** — **крен·рекомендация**.
  `MarketPhaseClassifier` владеет циклом first-match по `level`
  (stateless, без дебаунса — подвопрос 2); истинность каждой клаузы делегирует
  `StrategyConditionEvaluator` (он **уже** оценивает `StrategyCondition`
  по готовым `IndicatorValue`/`MarketStructure`/`MarketPriceData`,
  возвращает true/false — `StrategyConditionEvaluator.md`). Job остаётся
  тонким: читает данные → зовёт классификатор → персистит. Зеркалит
  арх-оболочку структуры (1.3 прежнего файла: аналитик — выделенный
  доменный компонент, job тонкий; *выводимо из codestyle* — rich-домен,
  логика не в job).
- **(B) `MarketPhaseClassifier` со своей реализацией оценки условий**,
  независимой от `StrategyConditionEvaluator` — отвергается: дублирует
  evaluator, две грамматики дрейфуют, ломает DRY (сквозная рамка п.1).
- **(C) Цикл инлайн в теле job** — отвергается: толстый job, нарушает
  rich-домен/тонкий-job (codestyle, 1.3).

### Контракт (на валидацию)

```
MarketPhaseJob:
  1. читает StrategyMarketPhaseSetting (статусы кроме DELETED — без изменений)
  2. собирает контекст оценки: готовые IndicatorValue + MarketStructure + MarketPriceData
     инструмента на закрытой свече (без Position-фактов — whitelist гарантирует ненужность)
  3. зовёт MarketPhaseClassifier.classify(...)
  4. персистит актуальный MarketPhase

MarketPhaseClassifier.classify(
    phaseRules,                 // упорядоченные клаузы
    evaluationContext           // indicator/structure/price, без deal-контекста
) -> (type: MarketPhase.Type, confirmedAt: OffsetDateTime)
   // first-match по level ASC через StrategyConditionEvaluator.evaluate(condition, context);
   // ни одна клауза → UNKNOWN
```

> Обновлено перепрогоном развилки 2: фаза-уровневого дебаунса нет —
> классификатор stateless (чистый first-match), `priorPhases`/чтение
> истории под дебаунс убраны. Суть подвопроса 3 (классификатор поверх
> переиспользуемого evaluator, тонкий job) не пересматривается.

**Замечания designer (не блокеры):** сигнатура
`StrategyConditionEvaluator` в доках полностью не зафиксирована —
переиспользование под фазу требует контекст-объекта, **не требующего**
`Position`-фактов (whitelist это гарантирует); уточнить контракт
evaluator при реализации. (Анти-whipsaw — на операндах: сглаживающие
периоды индикаторов + структурный `breakoutConfirmationBars`, подвопрос
2; классификатору состояние истории не нужно.)

**Крен подвопроса 3:** вариант (A) — тонкий **stateless**
`MarketPhaseClassifier` (чистый first-match) поверх переиспользуемого
`StrategyConditionEvaluator`; job тонкий.

## Подвопрос 4. `confidenceScore` при детерминированной модели

Сейчас `MarketPhase.confidenceScore: BigDecimal` = выигравший score.
При булевых условиях исход бинарен (клауза совпала / нет) — непрерывной
уверенности нет.

### Кто потребляет поле сейчас

Никто. `StrategyConditionEvaluator` читает `MarketPhase` для
`MARKET_PHASE_IS`/`TREND_CHANGED` — по `Type`, не по `confidenceScore`.
`EntryScannerJob` выбирает деталь по `Type`. `SIGNAL_SCORE_REACHED` и
источник `SIGNAL` **удалены** (`strategy-signal-is-entry-condition.md`)
— потребителя фазового score нет. *Выводимо из established.*

### Развилка 4

- **(A) Удалить `confidenceScore`** — **крен·рекомендация**.
  Детерминированная условная модель не даёт непрерывной уверенности;
  поле никем не потребляется; сохранить его — значит **фабриковать**
  score, что редизайн как раз убирает. Заодно убирается «может сохранять
  score» из `MarketPhaseJob`. *Предполагаю·инженерное:* у булева исхода
  нет магнитуды — это математико-инженерное свойство, не торговое
  утверждение.
- **(B) Сохранить поле, переопределив смысл** (`level` совпавшей
  клаузы / маржа превышения порогов / доля корроборирующих клауз) —
  отвергается: все варианты синтетичны, не грунтованы и
  реинтродуцируют скоринг через чёрный ход, противореча посылке
  редизайна.
- **(C) Оставить поле nullable, заполнять только если будущая «мягкая»
  клауза даст магнитуду** — отвергается сейчас: спекулятивно, нет
  потребности; вернуться, если появится grammar с непрерывным исходом.

**Крен подвопроса 4:** вариант (A) — `confidenceScore` удаляется из
`MarketPhase` и из контракта job. (Это правка природы поля модели — на
Предложении идёт предложением, канон правится после валидации.)

## Подвопрос 5. Ссылка на `MarketStructure`

**Переживает ли проработка Н3-структуры под условную модель?** — Да,
полностью. *Выводимо из established* (часть 1.1/1.3 прежнего файла,
помеченная «вероятно выживает»): `MarketStructure` остаётся
**вычисляемым шаримым результатом** (`MarketStructureJob` → свинг-пивоты
/ кластеризация уровней по `minTouches` / пробой с буфером и
подтверждением → `Type` + `MarketPriceLevel[]`). `MarketStructureParams`
(`lookbackBars`, `minTouches`, `swingLookbackBars`, …) и
`MarketStructureAnalyzer` **не затронуты** — редизайн распускает только
`MarketPhaseParams`, не `MarketStructureParams`. Меняется лишь то, **как
фаза потребляет структуру**: не входом в скоринг, а **операндом
условия** (`MARKET_STRUCTURE` по `structureKey` из
`marketStructureSettings` пула) — ровно как уже делают entry-условия.

### Под-пробел — как условие тестирует `MarketStructure.Type`

Естественное правило фазы — «структура `UPTREND` → фаза `BULL_TREND`».
Грамматика **уже** несёт `sourceType: MARKET_STRUCTURE` и
`RANGE_BREAKOUT_CONFIRMED`, но **нет** способа проверить сам **`Type`
структуры** равенством: есть `MARKET_PHASE_IS` (для фазы), нет
аналога для структуры; что именно резолвит `MARKET_STRUCTURE`-операнд
(цену уровня vs `Type`) — недоопределено.

- **(A) Зеркальный `ruleType` `MARKET_STRUCTURE_IS`** (operator +
  `MARKET_STRUCTURE`-операнд + `CONSTANT`-`ENUM` валиден по
  `MarketStructure.Type`) — **крен·рекомендация**. Прямой параллель
  `MARKET_PHASE_IS`, самоописателен, минимальная добавка; ложится в
  инкрементальный per-`ruleType` контракт авторинга.
- **(B) Типизированный селектор на `MARKET_STRUCTURE`-операнде** (атрибут:
  `TYPE` vs цена уровня), включающий `INDICATOR_COMPARE`-подобное
  равенство — мощнее, но усложняет операнд (новое поле-селектор,
  пересекается с уже существующим использованием `structureKey` под
  цену уровня в placement); рассмотреть, если понадобится сравнивать и
  другие атрибуты структуры. Не дефолт.

Это **per-`ruleType` контракт-инкремент** (дозаполняется при реализации,
как `RANGE_BREAKOUT_CONFIRMED`/OBV-ТР2) — **не блокер** редизайна:
правила фазы могут стартовать на индикаторных операндах +
`RANGE_BREAKOUT_CONFIRMED`, `MARKET_STRUCTURE_IS` добавляется
инкрементом.

**Крен подвопроса 5:** `MarketStructure` выживает как вычисляемый
результат, на который правила фазы ссылаются операндом; под-пробел
«тест `MarketStructure.Type`» закрывается зеркальным `MARKET_STRUCTURE_IS`
(вариант A) инкрементальным контрактом.
