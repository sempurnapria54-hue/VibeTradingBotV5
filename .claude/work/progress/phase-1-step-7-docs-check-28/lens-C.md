### C1. Валюта результата на тропе закрытия без входа: спека гасит её безусловно, исполнитель и контракт терминала — пишут

**Вопрос.** Пишется ли `Deal.resultProfitCurrency` на тропах закрытия без
входа, когда расчётная валюта резолвится? Исполнимая форма и
компонент-док дают противоположные ответы на одном и том же состоянии.

**Цитаты (носители).**

- `docs/spec/deal-result.json:83-86` — `resultProfitCurrency`,
  `expr: "if(hadEntry, settleCurrency, null)"`.
- `docs/spec/deal-result.json:284-292` — пример «тропа закрытия без
  входа»: `hadEntry: false`, **`settleCurrency: "USDT"`** (валюта
  резолвится), `expect.resultProfitCurrency: null`.
- `docs/components/MarkDealClosedExecutor.md:28-33` — таблица рёбер: на
  трёх тропах закрытия без входа «этот исполнитель: **ноль плюс валюта**».
- `docs/components/MarkDealClosedExecutor.md:37-38` — «Валюта пишется,
  **только если резолвится**; не резолвится — ноль без валюты плюс
  журнальный отчёт».
- `docs/spec/deal-lifecycle.json:74-76` — note `cleanTerminalContract`:
  «валюта — кроме троп закрытия без входа, **где она пишется, только если
  резолвится**».
- `docs/models/domain/aggregate/Deal.md:206` — «**Валюта результата — один
  авторитет:** расчётная валюта инструмента» (условия по тропе нет).

**Целевой док.** `docs/spec/deal-result.json` §`resultProfitCurrency` и
пример «тропа закрытия без входа» — либо
`docs/components/MarkDealClosedExecutor.md` §«Терминальное ребро» +
note `cleanTerminalContract` в `docs/spec/deal-lifecycle.json`. Что именно
правится — предмет развилки ниже.

**Ожидаемый владелец.** `solution-designer` (конструкция значения на
терминальном ребре; граница источника не затронута).

**Трассировка.** Открыл `MarkDealClosedExecutor.md` целиком → таблица
рёбер называет писателя числа и валюты на тропах без входа. Открыл
`deal-result.json` (дом формы) → `resultProfitCurrency` условен по
`hadEntry`. Проверил, не спасает ли пример-исключение: грепом
`hadEntry` по `deal-result.json` — единственный пример с `hadEntry:false`
несёт **резолвимую** `settleCurrency` и ожидает `null`, то есть спека
покрывает ровно спорное состояние и решает его против компонента.
Проверил третий носитель — `Deal.md:206` даёт валюту без условия по тропе,
то есть стоит на стороне компонента. Проверил, не гасит ли расхождение
контракт перехода: `cleanTerminalContract`
(`expr: notNull(resultProfit) && (notNull(resultProfitCurrency) || !hadEntry)`)
**пермиссивен** — пропускает оба исхода, поэтому прогон спецификаций
расхождения не ловит и не поймает (315 примеров сошлись). Расхождение
живёт между `expr` спеки и прозой компонента.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| (а) правится спека: `resultProfitCurrency = settleCurrency` безусловно | валюта пишется всегда, когда резолвится; `!hadEntry` перестаёт быть условием | правка одного `expr` + правка одного примера; **след — клауза в одном доке** (минимальный по шкале). Контекстная связность не растёт. Цена: «валюта при нулевом числе» надо признать осмысленной — она называет, в чём выражен ноль |
| (б) правится компонент и note контракта: на тропах без входа валюта не пишется | спека остаётся; `MarkDealClosedExecutor.md` таблица и клауза, note `cleanTerminalContract`, `Deal.md:206` сводятся к «валюта только у вошедшей сделки» | правка трёх носителей (§ правила по шкале). Цена: ноль без валюты у **всей** популяции закрытия без входа — теряется различение «ноль в USDT» и «ноль неизвестно в чём»; журнальный отчёт из клаузы `MarkDealClosedExecutor.md:38` становится недостижим (нерезолвимость перестаёт быть отличимым случаем) — это уже вторая правка, не названная в варианте |
| (в) развести носители: валюта результата и валюта, в которой выражен ноль — разные величины | у не вошедшей сделки пишется расчётная валюта инструмента как справка, `resultProfitCurrency` пуст | колонка / поле (больший след). Цена: вторая колонка ради популяции, где числа нет; «валюта нуля» потребителя пока не имеет |

**Крен — (а).** Счётная разница на стороне (б): она делает недостижимой
уже записанную ветку «валюта не резолвится ⇒ ноль без валюты плюс
журнальный отчёт» (`MarkDealClosedExecutor.md:37-38`), то есть обменивает
наблюдаемое различение на молчание — направление разрешающее по
`docs/concept.md` §П1 следствие 4. (а) — минимальный след по шкале
`.claude/rules/design-simplicity.md`.

**Ярлык исхода.** `варианты-с-креном`.

**Ярлык дефицита.** Дефицита нет — ответ выводится из концепции
(различимость «не проверяли» / «проверили»), закрывается CC.

### C2. Реакция на расхождение сверки поднимает ступень и заводит отчёт без машинного кода причины

**Вопрос.** Какой `code` несёт сигнал блокировки и отчёт, поднимаемые
терминальным исполнителем при `reconciliationStatus = MISMATCHED` в боевом
режиме допуска? Поле обязательно у обоих носителей, значение не назвал ни
один док.

**Цитаты (носители).**

- `docs/components/models/HoldSignal.md:21` — `| code | String | Машинный
  код причины; попадает в отчёт. |` (поле структуры, не опциональное).
- `docs/components/models/HoldSignal.md:29-35` — «**Значения `code` заводят
  тропы-производители, каждое — в своём доме.** Реестра кодов у сигнала нет
  и закрытого перечня здесь не ведётся» + пример `LOSS_STREAK_LIMIT_REACHED`.
- `docs/models/domain/other/AnomalyReport.md:30` — `| code | String | да |
  Машинно-читаемый код аномалии. |` (обязательное поле).
- `docs/components/HoldService.md:27` — строка «исполнители терминального
  ребра | **при расхождении сверки** в боевом режиме допуска, после
  коммита терминала | мягкую биржевую ступень» — **кода нет**, при том что
  соседние строки 28 и 29 коды называют (`LOSS_STREAK_LIMIT_REACHED`,
  `MANUAL_HALT_REQUESTED`).
- `docs/rules/exchange-hold.md:35` — строка триггера «расхождение сверки
  P&L за калиброванным допуском … ⇒ `Exchange.HOLD` + `AnomalyReport` +
  ручной разбор» — **кода нет**; соседняя строка 36 (серия убытков) код
  называет.
- `docs/rules/pnl-reconciliation.md:176-197` (§«Реакция на расхождение») —
  таблица режимов и §«Актор — исполнитель терминального ребра»: код не
  назван нигде в доме политики.
- `docs/components/MarkDealClosedExecutor.md:55-59` и
  `docs/components/MarkDealEmergencyClosedExecutor.md:90-92` — оба
  исполнителя зовут блокировку по этой тропе, кода не несут.
- Контраст того же файла: `docs/components/MarkDealClosedExecutor.md:88-89`
  — по серии убытков «Сигнал несёт машинный код причины
  `LOSS_STREAK_LIMIT_REACHED`».

**Целевой док.** `docs/rules/pnl-reconciliation.md` §«Реакция на
расхождение» — дом тропы-производителя по правилу
`HoldSignal.md:29`; указатели в `docs/components/HoldService.md` §«Кто
зовёт» и `docs/rules/exchange-hold.md` §«Ступень 1 — мягкий холд».

**Ожидаемый владелец.** `solution-designer` (значение принадлежит
продуктовой тропе реакции; интеграционной границы нет).

**Трассировка.** Проверял мандат «коды отказа зарегистрированы ли в своих
домах-перечнях». Грепом `машинн\w* код|код причины|перечень кодов` по
`docs/` собрал все носители кодов. Обнаружил, что реестра кодов
сознательно нет (`HoldSignal.md:29-31`), то есть проверка сводится к «у
каждой тропы-производителя код назван в её доме». Прошёл тропы шага 7:
серия убытков — назван в трёх местах; ручная остановка — назван; **тропа
расхождения сверки — не назван нигде**, при том что она поднимает ту же
ступень тем же сигналом от тех же исполнителей. Отдельно проверил, не
поглощён ли вопрос открытым: `docs/rules/error-handling-policy.md:37-38` и
`docs/rules/manual-halt.md:79-81` объявляют открытым перечень **HTTP**-кодов
внешней поверхности — другой предмет, эту дыру не покрывает.
Проверил `RiskValidator.md:55-75` — там перечень кодов реджекта преконтроля
ведётся полностью, то есть конвенция «код называется» в корпусе живая.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| (а) назвать код в доме тропы (например `PNL_RECONCILIATION_MISMATCH`) | `pnl-reconciliation.md` §«Реакция на расхождение» получает строку с кодом; `HoldService.md:27` и `exchange-hold.md:35` — указатель | правка клаузы в одном доке + два указателя; минимальный след по шкале. Контекстная связность нулевая: код читается там же, где тропа |
| (б) завести один код на «наш счёт под подозрением» и различать причины полем отчёта | один код на обе строки ступени 1, разведение уходит в `AnomalyReport.message`/снимки | цена названа самим корпусом и отрицательна: `AnomalyReport.md:71-79` держит ключ дедупа `STATE` на тройке «объект + `code` + `severity`» — общий код схлопнул бы расхождение сверки и серию убытков в **одно состояние**, и второе основание на той же бирже не завело бы строки |
| (в) завести реестр кодов отдельным носителем | закрытый перечень всех `code` в одном доке | переоткрывает ратифицированное `HoldSignal.md:29-31` («реестра кодов у сигнала нет») — выписано, не выбрано; след — новый файл-перечень плюс обязанность вести его при каждой новой тропе |

**Крен — (а).** (б) счётно ломает дедуп отчётов состояния, (в)
переоткрывает принятое ради того, что (а) закрывает правкой одной клаузы.

**Ярлык исхода.** `варианты-с-креном`.

**Ярлык дефицита.** Дефицита нет — конструкция выводима, конкретная
строка-значение кода деталью держателя не является.

### C3. Резолв `Deal.closeOutcome` из сырого типа закрытия не определён: ни перечня, ни резолвера, ни ветки неизвестного значения

значение под неё не производится.

### C4. Сверка на аварийной тропе: исход пишется, актора расчёта нет

**Вопрос.** Кто считает сверку на аварийной тропе? Дом политики назначает
её финализации выхода, а финализация выхода на этой тропе не эмитится;
аварийный терминал объявлен **писателем исхода**, но не тем, кто исход
производит.

**Цитаты (носители).**

- `docs/rules/pnl-reconciliation.md:121-122` — «**Гоняет сверку финализация
  выхода** на штатной тропе; на аварийной — если движения уже добыты».
- `docs/components/MarkDealEmergencyClosedExecutor.md:49-51` — «Симметрия не
  с штатным терминалом, а со **штатной тропой**: там те же четыре пишет
  финализация выхода …, **а на аварийной финализации не было** — писателем
  остаётся терминал».
- `docs/components/MarkDealEmergencyClosedExecutor.md:60` — «статус сверки |
  `NOT_RUN`, когда обязанность не наступила …, **иначе исход сверки**» —
  ветка «иначе» производителя не называет.
- `docs/components/SystemActionExecutor.md:58-62` — таблица финализации:
  «аварийная тропа | **ребро в ошибку и аварийный терминал** — два отдельных
  исполнения» (звена расчёта числа/сверки в аварийном действии нет).
- `docs/components/FinalizeDealExitExecutor.md:97-99` — «финализация выхода
  **не работает** ни на тропах закрытия без входа, ни на аварийной».
- Достижимость ветки «иначе» проверена, а не предположена:
  `docs/rules/pnl-reconciliation.md:87-97` — тропа «исчерпание бюджета
  добычи курса» уводит к аварийному терминалу **после** того, как добыча
  движений выполнялась, то есть `duty.flowsFetched` истинен;
  `docs/spec/pnl-reconciliation.json:136-152` — `dutyArisen` при этом может
  быть истинным, и `notRun = !dutyArisen` ложен.

**Целевой док.** `docs/rules/pnl-reconciliation.md` §«Что сверяется, когда,
кем» (клауза «Гоняет сверку…») и
`docs/components/MarkDealEmergencyClosedExecutor.md` §«Признаки отбора».

**Ожидаемый владелец.** `solution-designer` (распределение обязанности
между исполнителями финализации; границы источника нет).

**Трассировка.** Проверял мандат «у каждого писателя — достижимый момент
вызова». По штатной тропе цепочка сходится: `SystemActionExecutor` эмитит
звено расчёта → `FinalizeDealExitExecutor` считает и пишет → терминальное
ребро. По аварийной открыл `SystemActionExecutor.md` — в аварийном действии
звеньев два, и расчётного среди них нет; открыл
`FinalizeDealExitExecutor.md` — он сам называет аварийную тропу как ту, где
не работает; открыл `MarkDealEmergencyClosedExecutor.md` — он пишет исход
сверки, но раздел называется «Признаки отбора» и глагол везде «пишет», а не
«считает» (в отличие от `FinalizeDealExitExecutor.md` §Сверка, где сказано
«Сверяются четыре пары … Для допуска дочитываются операнды планового риска
по каждой ноге входа»). Проверил, не поглощена ли ветка предикатом:
`notRun` тотален только при `!dutyArisen`; достижимая тропа с истинным
`dutyArisen` на аварийном терминале названа самим домом политики (ожидание
курса → исчерпание бюджета). Значит ветка «иначе исход сверки» достижима и
операнда не имеет.

**Варианты.**

| Вариант | Что делает | Названная цена |
|---|---|---|
| (а) достаточность существующего: считает аварийный терминал сам | к обязанностям `MarkDealEmergencyClosedExecutor` добавляется расчёт четырёх пар и допуска | правка клаузы в двух доках; след минимальный. Цена — контекстная связность: терминал обязан читать ноги входа с плановыми числами (операнд омиссионного члена), то есть знать объём загрузки прохода, от чего `DealContextService.md:124-129` уходит намеренно; плюс расчёт встаёт в транзакцию терминала, а `pnl-reconciliation.md:185-189` уже требует держать реакцию **вне** неё |
| (б) отдельное звено расчёта в аварийном действии, симметрично штатному | аварийное действие получает третье звено «расчёт числа и сверка», исполняемое тем же `FinalizeDealExitExecutor`, но по аварийному дискриминатору | § правила + строка таблицы `SystemActionExecutor.md`. Цена: имя исполнителя («финализация **выхода**») перестаёт описывать популяцию; аварийный контур получает вторую точку отказа — ровно то, чего избегает `deal-lifecycle.json:79-81` («терминальность траншей на этой тропе не гейт: строка транша стала бы второй точкой отказа аварийного контура») |
| (в) сверка на аварийной тропе не гоняется вовсе; статус — `NOT_RUN` | клауза `pnl-reconciliation.md:121-122` («на аварийной — если движения уже добыты») снимается; ветка «иначе» исчезает | правка клаузы в одном доке — минимальный след. Цена **счётная и запрещающая-наоборот**: `MarkDealEmergencyClosedExecutor.md:80-86` уже обосновал, что аварийная корзина обязана быть счётной по этим признакам, а `NOT_RUN` определён как «сверка **не была обязана**» — на тропе с добытыми движениями это ложный ярлык, то есть подмена факта умолчанием (`docs/concept.md` §П1 следствие 4) |
| (г) составной актор: считает тот, кто последним приземлил операнд (добыча движений), терминал только читает | расчёт уезжает в `RefreshBillsExecutor` | сущность/компонент не добавляется, но `RefreshBillsExecutor.md:129-134` §Границы прямо объявляет обратное («Заголовочное число сделки не пишет»); переоткрывает принятое разделение «добыча наполняет — финализация консолидирует» |

**Крен — (б).** Единственный, который не ломает уже названную цену
соседнего носителя: (а) втягивает объём загрузки в терминал, (в) ставит
ложный ярлык на достижимой популяции, (г) переоткрывает разделение
ролей. Названная цена (б) — вторая точка отказа — снимается тем, что
звено расчёта на аварийной тропе **не гейтит** терминал (число
best-effort, `deal-lifecycle.json:79-81`), в отличие от штатного.

**Ярлык исхода.** `варианты-с-креном`.

**Ярлык дефицита.** Дефицита нет — выводится из концепции (различимость
«не были обязаны» и «были обязаны, никто не посчитал»), закрывается CC.
