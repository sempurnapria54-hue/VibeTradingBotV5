# Развилки ре-базы source-api на сырьё

## На какой вопрос отвечает этот файл

Какие развилки открыты по ре-базе контура тестов API источника на сырьё
и какие у них варианты.

Концепция и план правок — `.claude/work/progress/source-api-rebase.md`.

> **РЕШЕНО.** A → **A2**, B → **B1 + passthrough** (профиль-гейт
> structural no-prod, создание demo-сущностей + teardown), C → **C3**;
> prod вне контура. Финал и обоснование — decision
> `.claude/decisions/source-api-target-rebase.md`. Ниже — варианты с
> отклонёнными альтернативами (рабочая проработка).

## A. Подключение коллекции — как Postman достаёт сырой ответ

Коллекция под ре-базой — **ревью/аппрув-артефакт** (человек читает,
аппрувит план как конкретные исполнимые запросы; вторая роль — ручной
prod-read-only прогон на поднятом app). Чтобы остаться поверхностью
ревью **того же**, что гонит исполнитель, коллекция должна бить в
**сырьё** (сырой DTO/биржевой ответ), не в снапшот-границу.

Контур уже несёт два инвариант-свойства: **кредов в Postman нет**
(подпись/креды — на стороне app), **demo/prod — профилем поднятого
app**, не тумблером в Postman.

- **A1. Прямой вызов OKX из Postman (подпись в Postman).** Pre-request
  JS считает HMAC-SHA256, реальные креды в окружении Postman, запрос на
  base-URL OKX напрямую.
  - + сырой биржевой JSON, app в тракте нет, новый код app не нужен,
    коллекция самодостаточна;
  - − переписывает подпись в Postman (дубль `OkxSigningInterceptor`,
    дрейф); **возвращает креды в Postman** (откат инвариант-правила,
    регресс безопасности); demo/prod — тумблером в Postman; **не
    прогоняет нашу сериализацию request-DTO и биндинг response-DTO**
    (отдаёт литеральный OKX-JSON, мимо `OkxApiResponse<T>`).

- **A2. Тонкий raw-passthrough через app (типизированный, на метод
  клиента).** Новый контроллер зовёт `OkxRestClient` напрямую и отдаёт
  **сырой** `OkxApiResponse<T>` / типизированный DTO (без
  `IntegrationService`→снапшот-маппинга). App подписывает и сериализует
  request-DTO.
  - + прогоняет реальные подпись + сериализацию request-DTO + биндинг
    response-DTO (= ровно тот сырой слой, на который мы переезжаем);
    кредов в Postman нет; demo/prod — профилем (оба инварианта
    сохранены); прецедент — диагностический сырой `getAccountConfig()`;
  - − нужен raw-passthrough контроллер (диагностическая поверхность под
    тесты — мягкое трение с `codestyle` §«Неиспользуемый код», но
    прокси уже существует ровно как тест-поверхность, `getAccountConfig`
    — прецедент); ограничен поверхностью клиента (строка периметра без
    метода клиента → client-coverage-gap).

- **A3. Универсальный signed raw-passthrough через app.** Один эндпоинт:
  app подписывает и форвардит произвольный путь+тело на OKX, отдаёт
  сырое тело.
  - + подпись + профиль на стороне app (кредов в Postman нет); кроет
    любой эндпоинт периметра даже без метода клиента;
  - − мимо типизированного клиента и наших DTO (литеральный OKX-JSON) —
    не прогоняет «сырой клиент + сырой DTO»; покрытие A1 при
    безопасности A2.

**Рекомендация — A2.** Единственный вариант, прогоняющий ровно новую
цель (сырой клиент + сырые DTO) и сохраняющий оба инвариант-свойства
контура (кредов в Postman нет; demo/prod — профилем); есть прецедент.
Строку периметра без метода клиента фиксируем client-coverage-gap'ом
(дисциплина решения 3), а не тянем A3. Связка с B: если код-тесты бьют в
**тот же** passthrough, проходной слой работает на оба артефакта и
держит коллекцию↔код-тесты 1:1 по механике.

## B. Слой код-тестов — исполнитель прогона

Под ре-базой исполнитель — **код-тесты** (решение 7), коллекция — только
ревью/аппрув. Код-тесты **живые**: бьют в demo, ставят реальные ордера,
делают teardown. Существующий прецедент в `src/test` —
`OkxAckDeserializationTest` / `OkxReadDtoDeserializationTest` (JUnit 5 +
AssertJ, **офлайн**, биндинг DTO без сети).

- **B1. `@SpringBootTest` интеграционные тесты в `src/test`.** JUnit 5 +
  AssertJ (существующий стек), профиль `test` (demo-креды из Vault test),
  autowire `OkxRestClient` (либо passthrough через MockMvc/
  TestRestTemplate), цепочки упорядоченными тестами, teardown в
  `@AfterEach`/try-finally; тег `@Tag("source-api-live")` + выключены по
  умолчанию (opt-in), чтобы дефолтный CI (офлайн unit-тесты) не стрелял
  реальными demo-ордерами. Бланк отчёта = таблицы плана (колонка «факт»)
  → `history`.
  - + переиспользует устоявшийся стек JUnit/AssertJ/Spring + расположение
    и прецедент `src/test`; реальные подпись+DTO; teardown по жизненному
    циклу; тег/профиль изолируют живые тесты;
  - − живые тесты в `src/test` требуют дисциплины изоляции (тег +
    профиль + opt-in), иначе риск выстрела demo-ордерами в CI;
    упорядоченные stateful-цепочки чуть неуклюжи в JUnit
    (`@TestMethodOrder` или единый цепочечный тест).

- **B2. Newman (прогон Postman-коллекции из CLI) как исполнитель.**
  - + один артефакт (коллекция = ревью + исполнитель);
  - − противоречит решению 7 (исполнитель — код-тесты); проверки/
    teardown/цепочки слабее в Postman JS; тяжелее в сопровождении.

- **B3. Отдельный раннер (модуль / main-метод / скрипт).**
  - + полная изоляция от unit-CI;
  - − переизобретает то, что даёт `@SpringBootTest` + тег; новая инфра в
    сопровождение.

**Рекомендация — B1**, с autowire `OkxRestClient` in-process (чистейшая
верность цели «сырой клиент + сырой DTO»; коллекция — через A2-passthrough
для человекочитаемого повтора); JUnit 5 + AssertJ; `@Tag` + opt-in
профиль-гард; teardown по жизненному циклу; бланк отчёта = таблицы плана
в `history`. Под-выбор: in-process autowire (чистейшая цель, механика
отличается от коллекции) **vs** через passthrough по MockMvc (механика
идентична коллекции, чуть менее «сырая»). Крен — autowire; если важнее
коллекция↔код-тесты 1:1, бить в тот же passthrough (см. связку с A).

## C. Сверка апидоков — как расхождения прогона возвращаются в апидоки

Прогон находит расхождения «апидок (из офдока) ↔ реальность биржи».
Канонический случай — **A3-находка**: офдок говорит `cancel-advance-algos`
выведен (changelog 2025-04-24), а demo-прогон показал его **живым**
(`coverage-manifest.md`, `algo-order.md`). Провенанс манифеста сейчас
бинарен (`офдок`/`сторонний`) — рантайм-подтверждённого факта,
**противоречащего** офдоку, записать нечем.

- **C1. Маршрутизация находкой к `integrator` (текущий этап «разбор
  находок»); он правит апидоки по `api-docs-completion`.** Провенанс не
  трогаем.
  - + минимально; сохраняет разделение ролей; переиспользует
    существующий этап;
  - − оставляет противоречие офдок↔рантайм (A3) без честной пометки
    провенанса: рантайм-факт либо выдаёт себя за офдок, либо теряется.

- **C2. `tester` правит апидоки напрямую.** — **Отклонено**: ломает
  разделение ролей (`integrator` ведёт интеграционное знание, `tester`
  потребляет).

- **C3. Формализованная стыковка + рантайм-провенанс.** `integrator`
  остаётся владельцем (как в C1), но: (a) раздел «расхождения» отчёта
  прогона — явный вход/триггер `api-docs-completion` («рантайм-
  расхождение»); (b) в легенду манифеста — значение провенанса
  `рантайм` / `подтверждён-прогоном`, чтобы живой факт (особенно против
  офдока) фиксировался честно; (c) шапка `external-source-sync` несёт
  пометку рантайм-расхождения рядом с датой офдок-сверки.
  - + честно закрывает A3; чистая стыковка контур↔контур; разделение
    ролей сохранено;
  - − трогает легенду манифеста + `api-docs-completion` (ограниченная
    правка).

**Рекомендация — C3** (C1 — лёгкий запасной). A3 уже ждёт и C1 записать
его честно не может; рантайм-провенанс — минимальная честная починка,
заодно чисто сшивающая два контура. Если правку манифеста/провенанса
хочется отложить — C1 маршрутизирует сейчас, C3 формализует позже; но
A3 на руках, поэтому C3 оправдан сразу.

## Сводка рекомендаций

| Развилка | Рекомендация | Одной строкой |
|---|---|---|
| A | **A2** | типизированный raw-passthrough через app: ровно сырьё + кредов в Postman нет + demo/prod профилем |
| B | **B1** | `@SpringBootTest`+JUnit5/AssertJ в `src/test`, autowire клиента, тег+opt-in, teardown по циклу |
| C | **C3** | `integrator`-владелец + рантайм-провенанс манифеста + триггер `api-docs-completion` (честно ловит A3) |

Связка A2+B: код-тесты через тот же passthrough → проходной слой на оба
артефакта, коллекция↔код-тесты 1:1.
