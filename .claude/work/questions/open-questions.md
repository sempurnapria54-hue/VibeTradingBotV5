### ORCH-Q1. Владелец оркестрации онбординга инструмента и загрузки свечей

Кто драйвит переходы `Instrument.Status`
(`CREATED → SYNC → CANDLES_LOADING → ACTIVE`) и `CandleGroup.Status`
(`BACKFILL`/`SYNC`/`CHECK`/`REPAIR`/`ACTIVE`/`ERROR`) и координирует
их между собой. Не решено при выносе процесса `candle-loading`
(2026-05-30). Поглощает вопрос, поднятый при закрытии `GAPS_CLOSE_2`
(владелец записи `Instrument.Status` был оставлен деталью `CODE`).

Варианты: (1) отдельный orchestrator-компонент + per-status
handler'ы по образцу FSM сделки (`docs/components/DealStateMachine.md`
+ handler'ы); (2) оркестрация внутри `CandleJob` + лёгкий координатор
инструмента; (3) событийная модель; (4) иное. До решения владелец
**не материализуется**: семантика переходов и координации зафиксирована
в lifecycle-доках, оркестрация описана процессом `candle-loading`
без привязки к компоненту-владельцу.

Горизонт (взвешивание срока, 2026-06-06): отложен — узкий
онбординг-кусок несёт провизорный seam шага 1 (`CandleJob`); широкое
мультиисточниковое владение `Instrument.Status` (FSM, AnomalyJob и
пр.) — отдельная ось (backlog п.9). Решать к концу фазы / когда
осядет ось владения статусом.
Связано: `docs/processes/candle-loading.md`,
`docs/lifecycles/Instrument.md`, `docs/lifecycles/CandleGroup.md`,
`docs/components/CandleJob.md`.

### CMD-Q4. Перечисление неизвестных live orders/algo по инструменту

Контекст: CMD-Q3 закрыт (steer, 2026-06-10) — refresh-набор по одной
команде на сущность, bulk-команды сняты
(`docs/decisions/refresh-evidence-cycle-ownership.md`).

Снятие bulk-команд оставляет **дыру** (подтверждена при чистке, не
достраивается): per-entity `REFRESH_*` покрывает только **известные**
сущности сделки. Перечисления **неизвестных** live orders/algo по
инструменту command-layer больше не предоставляет:

- `PrecheckHandler` — входная проверка «нет чужих live orders/algo» на
  инструменте перед входом;
- `AnomalyJob` (шаг 8) — orphan orders/algo (на бирже, нет в БД), хвосты
  после cleanup, чужой live risk;
- `ErrorHandler` / `ExitPendingHandler` — неизвестные live-хвосты.

(`REFRESH_POSITION` уже инструмент-скоупный — позиции-orphan покрыты; дыра
только по orders/algo.)

Варианты: (1) инструмент-скоупный exchange-read **вне command-layer** (read
в `IntegrationService`, дёргается job'ами/handler'ами для сверки/orphan-скана,
не `ServiceCommand`); (2) вернуть узкую scoped bulk-scan операцию (не
per-deal-команду); (3) иное по проработке anomaly / precheck-cleanliness.

**Precheck-часть закрыта (`GAPS_CLOSE_1` шага 6, 2026-06-22, вариант (1);
вариант (2) отвергнут):** инструмент-скоупный exchange-read вне
command-layer — `docs/components/IntegrationService.md`
§«Инструмент-скоупный read», `docs/components/PrecheckHandler.md`.
**Остаток — orphan-скан шага 8** (`AnomalyJob`: чужие сущности при уже
открытой сделке и по неведомым инструментам); владелец —
`solution-designer` / шаг 8.

**Смежный вход (REPLACE-only, 2026-06-11):** при проработке
Precheck/AnomalyJob учесть легитимное **окно двойной reduce-only
защиты** во время REPLACE-ремодела (protective-порядок: новая
поставлена, старая ещё не отменена) — намерение видно из
`DealActionState` / цепочки `replacesInternalId`; не флагать
аномалией (`docs/decisions/replace-not-amend.md` §Следствия).
Связано: `docs/decisions/refresh-evidence-cycle-ownership.md`,
`docs/components/PrecheckHandler.md`, `docs/components/AnomalyJob.md`,
`docs/components/ServiceCommandExecutor.md`,
`docs/components/IntegrationService.md`.

### OKX-Q2. Persisted `TradeFillsArchive` и async-флоу выгрузки

OKX endpoint'ы `POST/GET /trade/fills-archive` дают доступ к fills
старше 3 месяцев и до ~2 лет через двухшаговый async-флоу (генерация
файла → polling state → скачивание `fileHref`). На первом этапе ни
executor, ни persisted-сущность `TradeFillsArchive` не введены. Не
решено: нужен ли async-executor под архив (с long-running polling
state) и persisted-модель `TradeFillsArchive`.

**Обоснование пересобрано (`GAPS_CLOSE_4`, вслед за `GAPS_CLOSE_2`).**
Прежняя опора («текущий runtime использует только `RefreshFillsExecutor`
за последние 3 месяца») устарела: `REFRESH_FILLS` и её executor **сняты**
(N12) — число P&L идёт из positions-history, разбивка из bills
(вторая нога `REFRESH_POSITION` / `REFRESH_BILLS`), order-fill-метрики
(`accFillSz`/`avgPx`) — из `REFRESH_ORDER`. ⇒ runtime фазы 1 **не читает
fills вообще** — ни 3d, ни 3m (`docs/integrations/okx/coverage-manifest.md`:
⚪ не-runtime, контракты справочно).

Вопрос это **не закрывает, а сужает**: отпадает мотив «архив как
продолжение runtime-контура fills» (его больше нет), остаётся чистый
вопрос **off-band-аудита**. Пофилловый аудит вынесен за фазу 1 при
закрытии OKX-Q1 (`docs/decisions/result-profit-source.md` §«Персист
fills») — это отложение, не отказ; решения «нужен ли архив вообще» ни
один decision не несёт. Де-факто действует вариант (3).

Цитаты источника (архив, `Запрос генерации файла из архива сделок REST.md`):
- «**последние 3 месяца** — берёшь обычным `GET /api/v5/trade/fills-history`;
  **старше 3 месяцев и до ~2 лет** — через архив: сначала **POST
  (запросить генерацию)**, потом **GET (взять ссылку на файл)**.»
- «`result=false`, OKX пишет, что файл может генерироваться **долго
  (порядка десятков часов)**.»

Варианты: (1) materialize `TradeFillsArchive` с lifecycle
(`REQUESTED → ONGOING → FINISHED|FAILED`) + executor; (2) держать
архив вне runtime (off-band tool для аудита); (3) отложить до явной
потребности. До решения контракт endpoint'ов и поля responses
зафиксированы в `docs/models/integrations/okx/OkxFillsArchiveResponse.md` и
`docs/integrations/okx/contracts/fills-archive.md`.
Связано: `docs/models/integrations/okx/OkxFillsArchiveResponse.md`,
`docs/integrations/okx/contracts/fills-archive.md`,
`docs/decisions/result-profit-source.md` (OKX-Q1 закрыт — persisted `TradeFill`
не вводится).

### OKX-Q4. WS-каналы OKX — отдельный заход

В архивном источнике WS-каналы покрыты только обзорной таблицей: имена
(`account`, `positions`, `orders`, `balance_and_position`, `tickers`,
`candle<bar>`, `instruments`, `algo-orders`, `algo-advance`) и краткое
назначение. Детального описания протокола подписок, push-сообщений,
матчинга `orders` events с runtime-фактами — нет. Текущая миграция
покрывает REST. WS — отдельный заход.

Цитаты источника (архив, `okx_api_for_trading_bot_v5.md`):
- «WS канал `orders` **не даёт начальный snapshot**. Он начинает слать
  события **только при изменениях**.»
- WS-каналы фигурируют в обзорной таблице операций без отдельных
  файлов; в каждом REST-файле есть короткая WS-заметка («WS — основной
  realtime-канал», «REST — fallback»).

Варианты: (1) выделить кластер `docs/integrations/okx/ws/` или ввести
`docs/integrations/okx/rules/okx-ws-channels.md` (один файл = один канал
либо один файл = все каналы) — после сбора реальных push-примеров;
(2) держать WS-альтернативу пометками внутри существующих
`okx-*-mapping.md`, без отдельных файлов. До решения WS-каналы описаны
только короткой пометкой в mapping-файлах; в `okx-service-urls.md`
зафиксированы base URL public/private/business.
Связано: `docs/integrations/okx/contracts/service-urls.md`,
`docs/integrations/okx/rules/ws-limits.md`,
`docs/models/mapping/Order.md` (примеры WS-альтернатив).

Статус (GAPS_CLOSE_1, 2026-05-29): шаг 1 — REST-first (WS отложен),
поэтому OKX-Q4 **шаг 1 не блокирует**. Якорь пересмотра — рефакторинг
на микросервисы (архитектурный рубеж роадмапа). Контрактные доки
рыночных данных приведены к REST-first
(`docs/integrations/okx/contracts/market-price-data.md`,
`docs/models/mapping/MarketPriceData.md`).

### STRAT-Q4. percent-anchor: «−N% относительно чего»

деталь реализации соответствующего `ruleType` / placement.

### IND-Q1. Надёжность биржевого объёма для volume-условий (wash trading) (владелец — шаг 3)

**Книжная часть закрыта (2026-06-09)** решением
`docs/decisions/volume-condition-semantics.md`: объёмное условие —
подтверждающий фильтр, не единственное основание `ENTRY`; OBV — только
относительные формы.

**Остаётся открытой крипто-часть.** Крипто-специфика надёжности
**спот-объёма CEX** (накрутка / фейковый объём на нерегулируемых биржах,
надёжность по площадкам/ликвидности) — в корпусе **∅**, подтверждено
прямой вычиткой сырых книг
(`.claude/library/trading/distilled/microstructure.md` §9): крипту
застали только Kaufman (2019) / Carver AFTS (2023), обе трактуют её как
торгуемый инструмент (Carver — через регулируемые фьючерсы), достоверности
спот-объёма не касаются. **Эскалация:** корпусу не хватает
крипто-микроструктурного источника по интегритету объёма — подбор
источника в **контуре дообучения (в чате)**; до него крипто-часть не
закрывается. Внешний (не-книжный) добор зафиксирован в snapshot v37 §ТР1,
в корпусные тезисы не вносился.

**Якорь — фаза 4.** Крипто-надёжность спот-объёма CEX решается в **фазе
4** (анализ рынка + заведение новых инструментов), где встаёт продуктовый
подбор инструмента/площадки и заводится будущий аналитик торгового
совета. До фазы 4 крипто-микроструктурный источник **не добирается**:
(1) в фазе 1 инструмент и стратегия задаются пользователем **вручную** —
острый случай накрутки объёма под ручным контролем пользователя;
(2) объёмное условие уже ограничено ролью **подтверждающего фильтра** (не
единственное основание `ENTRY`, `docs/decisions/volume-condition-semantics.md`)
— даунсайд прикрыт. Книжный контур дообучения корпуса (подбор
крипто-микроструктурного источника) запускается **к фазе 4**.

Находка ТР1 `DOCS_CHECK_5` (= ТР4 `DOCS_CHECK_8`, торговый фокус
`trading-review`). Затрагивает авторинг стратегии (чек-лист СТ-1,
применён на `CODE` шага 2; архив —
`.claude/work/history/2026-06-05-phase-1-step-2-strategy/tasks-phase-1-step-2-strategy.md`).
Связано: `docs/decisions/volume-condition-semantics.md`,
`docs/models/domain/aggregate/Strategy.md` (§Условия),
`docs/models/domain/other/IndicatorValue.md` (OBV),
`docs/components/IndicatorJob.md`.

### STRUCT-Q1. Калибровка числовых порогов структуры рынка (ER-порог тренда, k-толеранс) (владелец — фаза 2)

Закрывающий батч шага 3 (D2/D3, 2026-06-09) вынес два числовых порога
резолвера структуры из захардкоженных констант в `MarketStructureParams`
(per-конфиг): `trendEfficiencyThreshold` (ER ≥ порога → тренд vs диапазон,
D2) и `levelToleranceAtrMultiplier` (k в толерансе кластеризации = k·ATR,
D3). **Подход** грунтован корпусом (ER-дискриминация тренд/шум [Kaufman
гл. 1 «Measuring Noise», гл. 17 KAMA]; свинг-фильтр/толеранс относительно
волатильности [Kaufman гл. 5, гл. 8]), но **числовые значения — нет**:
корпус не даёт ни бинарной ER-отсечки (ER используется континуально в
KAMA), ни конкретного k. Значения — **пользовательский хвост**, калибруются
на **бэктест-гейте фазы 2** (анализ робастности: широкая зона успеха, не
пик — [Kaufman гл. 21]).

До калибровки резолвер применяет **провизорные консервативные дефолты**
(ER-порог 0.30; k 0.5), если поля не заданы в `MarketStructureParams`;
числом в канон не зашиваются (в доках помечать «value: бэктест»). Находки
ТВ1/ТВ3 торговой валидации шага 3 (`trading-review`).

Связано: `docs/models/domain/aggregate/Strategy.md` (§MarketStructureParams),

### PHASE-Q1. «Липкость» / гистерезис фазы при stateless-резолве (владелец — `trading-review`)

Трек D (2026-06-10) сделал `MarketPhase` **stateless — вычисляется на лету,
не персистится** (`docs/decisions/market-phase-stateless.md`). Резолв на
лету по текущим индикаторам/структурам не даёт **гистерезиса/
подтверждаемости** фазы: у границы режимов фаза может перескакивать тик за
тиком. Сейчас анти-whipsaw — только операнд-уровневый (сглаживающие периоды
индикаторов, структурный `breakoutConfirmationBars`,
`docs/decisions/market-phase-conditional-classification.md` §Анти-whipsaw).

Не решено: нужна ли фазе **отдельная подтверждаемость / гистерезис** поверх
операнд-уровневого сглаживания (hold-N-баров на смену фазы и т. п.), и если
да — как выразить без хранимого состояния истории фаз (источник истории —
готовая структура, не фаза; см. «дверь на будущее» в
`docs/models/domain/aggregate/Strategy.md` §StrategyMarketPhaseRule).
Приемлемость остаточного перескока как численный риск-аппетит автора уже
принята пользователем, но stateless-переход вопрос обостряет.

**Торговый грунт (trading-review пост-D, ТВ-1/ТВ-2).** Корпус: режим
флип-флопит при слишком отзывчивом дискриминаторе (одиночная быстрая MA
«дёргается» — Carver AFTS стр. 5), а анти-whipsaw встроен в **конструкцию
дискриминатора** (медленный кроссовер; KAMA — адаптивная скорость EMA из
efficiency ratio, Kaufman гл. 17), не в отдельный stateful-дебаунс ярлыка
режима. ⇒ операнд-уровневый механизм модели корпусно-грунтован; жёсткий гейт
«не выражает торговое правило» не срабатывает. Если гистерезис понадобится —
опоры ввода: **KAMA-адаптивная скорость** входов / документированный
инкремент **`confirmationBars`** на сравнивающее правило
(`docs/decisions/market-phase-conditional-classification.md` §Анти-whipsaw),
не stateful debounce. Смягчающий фактор (ТВ-2): перескок фазы влияет только
на выбор детали при **входе** — открытые сделки идут по pinned detail, не
«треплются» (`docs/lifecycles/Strategy.md`). Полный разбор —
`.claude/work/history/2026-06-10-phase-1-step-3-derived-market-data/phase-1-docs-check-post-revision-d.md` §Торговый фокус.

Владелец — торговый ревью (`trading-review`) со специалистом; горизонт — по
ходу торговой проработки фазы. До решения дополнительный гистерезис не
вводится (S0), анти-whipsaw остаётся операнд-уровневым.
Связано: `docs/decisions/market-phase-stateless.md`,
`docs/decisions/market-phase-conditional-classification.md`,
`docs/models/domain/aggregate/Strategy.md` (§StrategyMarketPhaseRule),
`docs/components/MarketPhaseResolver.md`.

### PNL-Q1. Измеримость искажений измеряемой ожидаемости (владелец — `trading-specialist`)

Узел 10 `DOCS_CHECK_7` (H16-H18) целиком. Три места, где система **не может
измерить** собственное искажение; не обсуждалось, в `GAPS_CLOSE_7` сознательно
не закрывалось.

1. **Провенанс ликвидации/ADL наблюдается и выбрасывается** (H16).
   **Основная часть закрыта** узлом F `GAPS_CLOSE_12`: провенанс доносится
   на `Deal` полем `closeOutcome` (`NORMAL_EXIT` / `LIQUIDATION` /
   `FORCED_REDUCTION`), пишется финализацией из `Position.externalCloseType`
   (`docs/models/domain/aggregate/Deal.md` §«Признаки отбора для отчёта») —
   то есть вариант (а) исполнен по факту, как признак отбора для отчёта.
   **Снят с активации** (`GAPS_CLOSE_12`): активировавший его вариант H18
   «сменить дискриминатор выборки» отпал вместе с самой выборкой — выборки
   как хранимого объекта не существует.
   **Остаток пункта:** нужен ли сверх `closeOutcome` ещё и `triggerPx`
   (цена триггера ликвидации/ADL) как носитель измеримости отказа инварианта
   «ликвидация за стопом» (`STOP_LOSS_TOO_CLOSE_TO_LIQUIDATION`) — сегодня
   поле из маппинга выведено. Корпус здесь объявляет **дыру**
   (`risk-and-sizing.md` §∅ ликвидационные каскады, `microstructure.md`).
   Остаточные варианты: (а) вернуть `triggerPx` в used с названным
   потребителем; (б) слепок в `AnomalyReport` аварийного терминала;
   (в) явно признать эту ось неизмеримой.
2. **Цена реакции измерима у реджекта и структурно неизмерима у холда**
   (H17), хотя больше она именно у холда. Реджект оставляет строку `Deal`;
   инструмент под холдом «выпадает из скана **самой выборкой**»
   (`EntryScannerJob`) — следа нет вовсе, а холд дороже по трём осям (радиус
   до аккаунта, длительность до ручного снятия, невидимость). Клетка
   «возможности × пессимистично» не «незаполнена», а **непополняема** при
   текущей структуре. Грунт: «ожидаемость × возможности = ценность системы;
   сравнение валидно при **полном использовании возможностей**» [Tharp гл.6
   с.142, 156-157; гл.11 с.271-275]. Варианты: (а) счётчик пропусков скана в
   разрезе (инструмент, причина) — ставится там, где сейчас «выпадает
   выборкой»; (б) заводить `Deal` и сразу закрывать; (в) признать ось
   неизмеримой явным решением.
3. **Сверка bills↔net — единственный детектор N11-недосчёта — неблокирующая
   и без агрегатной эскалации** (H18). Асимметрия: несвежести ставки (влияет
   лишь на прогноз комиссии будущего входа) дан sticky-холд с ручным снятием,
   а неверному `resultProfit` (портит измеренную ожидаемость **всей**
   системы) — самая слабая реакция реестра; по собственному критерию
   «радиус ущерба ограничивает реакцию»
   (`docs/rules/error-handling-policy.md`) соотношение должно быть обратным.
   **Зависимая от N11:** гейтит, если рантайм покажет «OKX не агрегирует /
   запись читается послайсово»; при «агрегирует» — вопрос качества
   мониторинга.
   **Уточнён H21 `DOCS_CHECK_12`:** уровень не назначен **и в самой
   error-политике** — независимо от исхода N11. То есть вопрос не сводится к
   рантайм-факту: `PNL_RECONCILIATION_MISMATCH` не имеет ни уровня
   внутренней градации, ни агрегатного триггера, ни лестницы эскалации.
   **Вариант (в) снят** (`GAPS_CLOSE_12`, узел F): «пометка вместо
   исключения» больше не вариант — она **данность**, поле
   `Deal.reconciliationStatus` (`NOT_RUN`/`MATCHED`/`MISMATCHED`); из
   популяции ничего не выводится. Остаётся вопрос **реакции** на
   расхождение. Варианты: (а) агрегатный триггер (K расхождений подряд /
   доля за окно → мягкий запрет входов по scope через `HoldService` —
   реакция уже есть, новая только провизорная величина K); (б) блокировать
   терминал (отвергнуто справедливо — инвариант «сделка всегда доходит до
   терминала»); (г) явно записать, что уровня «лог» достаточно, с названной
   ценой (сколько искажённых чисел допустимо и почему это не обесценивает
   `EVENT`-журнал).

**Частичное движение (H26 `DOCS_CHECK_10`, решение пользователя).** Средняя
цена **фактического выхода** заведена полем
`Position.externalCloseAveragePrice` — но **не** по этому вопросу, а по

### RISK-Q3. Лимит риска на сделку при многоногом входе (`GRID_ENTRY`/пирамидинг) (владелец — `trading-specialist`)

H8 `DOCS_CHECK_7`. Лимит риска проверяется **по действию**, а не по сделке:
`RiskValidator` считает risk amount из `sizeContracts` **рассчитанного
действия**, агрегата по позиции/сделке нет. `GRID_ENTRY` в контуре фазы 1
подтверждён и по докам, и по коду (верификация V11 отчёта), а
`risk-validator-scope.md` прямо держит «scaling / pyramiding order,
увеличивающий позицию» в контуре валидации. Следствие: N доборов копят риск
кратно лимиту, каждый по отдельности проходя проверку.

Несущая посылка отказа от guard'а экспозиции
(`docs/decisions/per-trade-risk-policy.md`: «агрегатной экспозиции нет —
торгуется один инструмент, и единственная позиция ограничена самим лимитом
риска на сделку») при доборах **не держится**: доборы делают позицию не
единственной по риску, оставаясь внутри одного инструмента.

**Ограничение «в фазе 1 торгуется один инструмент» вопрос не закрывает**
(H8 `DOCS_CHECK_10`, решение пользователя). Оно чинит посылку по радиусу
**между сделками**; `RISK-Q3` — тот же класс с радиусом **внутри одной
сделки**, и многоногий вход целиком укладывается в один инструмент. Один
класс, два радиуса; разбирать разумно вместе, но закрытие одного
автоматически не закрывает второй.

Грунт: «перебор риска хуже недобора… цена отклонения от пика асимметрична и
огромна» [Vince гл.1 с.9, рис.1-1; с.18]; «главные причины провала на
здоровой системе: … переплечо» [Tharp гл.6 с.145-146]. Для шага 7 конкретно:
`resultProfit` — число **на сделку**, а `R` при N доборах не определён ⇒
R-мультипликатор искажён.

Варианты: (а) считать risk amount **по позиции после действия** (метрика уже
названа в `RiskValidator.md`, но отложена на фазу 3 — нужен её per-deal
срез); (б) явно **вывести `GRID_ENTRY`/scaling из контура фазы 1** по образцу
выноса FUTURES — ратифицировать сужение, а не оставлять умолчанием;
(в) риск-бюджет **на сделку** как расходуемый ресурс (`Deal` держит остаток),
каждое risk-creating действие списывает — заодно даёт правило агрегации для
`Deal.plannedRiskAmount`.

**Поле планового риска вопрос не закрывает** (`GAPS_CLOSE_7`, H9): оно даёт
знаменателю слот, а не правило агрегации при доборах.
Связано: `docs/components/RiskValidator.md`, `docs/components/SizeCalculator.md`,
`docs/rules/risk-validator-scope.md`,
`docs/decisions/per-trade-risk-policy.md`,
`docs/models/domain/aggregate/Deal.md` §«Плановый риск».

### FEE-Q1. Слот подгружаемой ставки комиссии в `InstrumentExternalRules` (владелец — `solution-designer` + `code-writer`)

H12 `DOCS_CHECK_7`. У гидрированной ставки **нет объявленного слота**:
§Структура навеса поля под неё не несёт, а §«Ставка комиссии» говорит, что
`InstrumentExternalRulesDataService` «кладёт её в возвращаемый инстанс» и что
«на навесе ставка не персистится». Объявленный механизм персистенции при
этом сериализует **весь бин** в JSONB и заменяет JSON целиком.

Счёт: как только слот появится и модель будет сохранена после чтения, ставка
уедет в `external_rules` и превратится в «копию на каждом инструменте» —
ровно то, ради недопущения чего ставку вынесли в свою таблицу
(`docs/models/domain/other/TradeFeeRate.md` §«Масштаб модели»).

Варианты: (1) transient-слот с явной записью в §Структура (и с гарантией, что
конвертер его не сериализует); (2) **не класть в модель вовсе** —
`DataService` отдаёт пару/RVO, аксессоры ставки переезжают на потребителя, и
«не персистится» становится свойством **структуры**, а не дисциплины;
(3) запретить сохранять прочитанный инстанс.

**Давление снижено, но вопрос жив** (`GAPS_CLOSE_7`, H11): требование
«синк делает read-modify и переносит счётчик» отпало вместе со снятыми
`refreshCount`/`confirmedAt` навеса — то есть сценарий «сохранили прочитанный
инстанс» стал реже, но структурного запрета так и нет.

**Шага 7 не гейтит** (H26/H7 `DOCS_CHECK_11`). `DOCS_CHECK_11` переклассифицировал
вопрос в мягко-гейтящий на том основании, что шаг 7 добавляет **третьего
читателя ставки** (омиссионный член epsilon у финализатора) и каждый новый
читатель повышает шанс сохранить прочитанный инстанс. Решение по H7 это
основание сняло: ожидаемая комиссия считается из persisted-операндов сделки,
и **финализатор `TradeFeeRate` не читает вовсе**
(`docs/decisions/pnl-finalization-mechanics.md` реш.5 §epsilon). Читателей
ставки по-прежнему двое; вопрос возвращается к прежней классификации —
не-гейтящий, владелец прежний.

Связано: `docs/models/domain/other/InstrumentExternalRules.md` §«Ставка
комиссии», `docs/components/InstrumentExternalRulesDataService.md`,
`docs/models/domain/other/TradeFeeRate.md`.

### RISK-Q4. Дом операндов планового риска: `Order` против `AlgoOrder` (владелец — `solution-designer`) — **ГЕЙТИТ `CODE` шага 7**

H3 `DOCS_CHECK_11`. Решение пользователя: дом `plannedEntryPrice` /
`plannedSizeContracts` — **сущность ноги входа**, по тому, **кто фактически
исполнился**; на `Deal` они не живут (write-once поле оставило бы число
первой ноги и молча выдавало его за сделку — радиус `RISK-Q3`).

Развилка **внутри** решения не закрыта: колонки идут в `orders`, в
`algo_orders` или **в обе**. Вход через `AlgoOrder` возможен (условный
вход), поэтому «только `orders`» не очевиден; «обе» дублирует пару колонок
и требует правила, какая из них читается при агрегации по сделке.

**Расширение (H11 `DOCS_CHECK_12`): у алго-тропы входа нет писателя
операндов планового риска.** Единственный названный писатель —
`CreateOrderExecutor`; `CreateAlgoOrderExecutor` о плановом риске не
упоминал вовсе, при том что `docs/rules/risk-validator-scope.md` **прямо
включает** `CREATE_ALGO_ORDER_COMMAND` в множество валидируемых
risk-creating действий, а `AlgoOrder.md` ратифицирует, что операнды —
атрибуты алго-строки, «если вход исполнился алго-ордером». Цена, если
`RISK-Q4` разрешится как `algo_orders` либо «обе»: вход, исполненный
алго-ордером, оставляет `Deal.plannedRiskAmount` пустым → финализатор
ставит `PLANNED_RISK_MISSING` → сделка объявляется «созданной вне
приложения» и получает **жёсткий выход**, будучи открытой самой системой.
Ветка-детектор чужих позиций срабатывала бы на собственных — тем чаще, чем
чаще стратегия входит алго-ордером.

**Под-развилка того же узла:** `AlgoOrder.md` §Назначение перечисляет
применения «standalone SL/TP, OCO, trailing, partial exit» — **входа среди
них нет**, тогда как §«Операнды планового риска» и `risk-validator-scope.md`
вход алго-ордером предполагают. Один из двух носителей неверен, и какой —
содержание этого вопроса. Проверяемый факт, который его закрывает: порождает
ли стратегийный слой **входную** `CREATE_ALGO_ORDER_COMMAND`.

**Что от ответа НЕ зависит:** назначение писателя. Оно ратифицировано H5
`DOCS_CHECK_12` как **per-leg** (каждый CREATE-executor пишет операнды на
свою сущность, той же транзакцией) и верно при любом исходе — открыт только
**состав таблиц**.

От ответа зависит **состав schema-дельты шага 7**
(`docs/decisions/pnl-finalization-mechanics.md` §Следствия), поэтому вопрос
гейтит `CODE`.

### ANOM-Q3. Перекрытие разных `code` на одном ключе анкера (владелец — `solution-designer`) — **ГЕЙТИТ `CODE` шага 7**

H15 `DOCS_CHECK_11`. Пока групповой анкер идемпотентности `STATE`-отчётов
был **мёртв** (ключ содержал nullable `instrument_id`, а NULL'ы в UNIQUE
различны), вопрос был теоретическим и стоял хвостом шага 8. Решение по H15
внесло идентификацию группы в ключ и анкер **оживило** — тем самым
немедленно материализовав перекрытие: `FEE_RATE_STALE` и
`FEE_GROUP_KEY_STALE` делят ключ (`exchangeId`, `INSTRUMENT_GROUP`,
`NON_CRITICAL`, `feeGroupKey`), а `code` в ключ не входит ⇒ **второй факт
подавляется первым**. Подавление факта — не идемпотентность.

Варианты: (1) добавить `code` в ключ — прямо отвергнуто H15 `DOCS_CHECK_9`
(«ось не та: различать надо природу, а не тип»), требует пересмотра того
довода в новых обстоятельствах; (2) свести оба факта к **одному коду**
несвежести с уточнением в слепке; (3) признать подавление сознательным —
требует названной цены (какой из двух фактов теряется и чем это грозит).
Связано: `docs/models/domain/other/AnomalyReport.md` §Инварианты структуры /
§Персистентность, `docs/rules/idempotency-via-unique.md`.

### ANOM-Q4. Анкер негрупповых `STATE`-отчётов с `instrument_id = null` (владелец — `solution-designer`)

Хвост H15 `DOCS_CHECK_11`. Групповой радиус анкер получил (ключ без
nullable-колонок). У негруппового индекса ключ прежний — (`exchange_id`,

### HOLD-Q2. Статус онбординга после ручного снятия жёсткой блокировки (владелец — `solution-designer`)

Смежный угол H13 `DOCS_CHECK_7`. `GAPS_CLOSE_7` зафиксировал множества входа:
`ENTRY_BLOCKED` — только из `ACTIVE`; `TRADE_BLOCKED`/`CLOSED`/`ERROR` — из
**любого** статуса. Отсюда: жёсткая блокировка может застать инструмент в

поэтому вопрос узкий: чем должно быть снятие — возвратом в **прежний**
статус (нужен носитель «откуда пришли»), возвратом в `CANDLES_LOADING` с
перепроверкой готовности групп, или запретом снимать блокировку, пока
онбординг не завершён.

Пересекается с ORCH-Q1 (владелец записи `Instrument.Status` и координация с
`CandleGroup.Status`) — решать, вероятно, вместе.
Связано: `docs/models/domain/core/Instrument.md` §Енумы,
`docs/lifecycles/Instrument.md` §Охват, `docs/rules/instrument-hold.md`

### PHASE-Q2. Размещение `MarketPhase` после перехода в вычисляемое значение (классификация)

протухшая метка coverage-gap в `source-api-testing.md`), но
конфликтует с принципом `structure.md` «скиллы самодостаточны —
не ссылаются на справочники и другие скиллы».

Варианты:

- **A. Статус-кво**: самодостаточность сохраняется, дубли
  остаются. Платим контекстом и риском рассинхрона.
- **B. Ослабить принцип точечно**: разрешить скиллу ссылаться на
  канон, когда канон и так в контексте читателя. Кейсы:
  `classify-type` → таблица `structure.md` (инжектится в каждую
  сессию); фокус-скиллы → стойка в `reviewer.md` (reviewer всегда
  читает свой файл роли). Экономия без реальной потери
  самодостаточности; принцип в `structure.md` уточняется
  оговоркой.
- **C. Дубли с меткой канона**: дубль остаётся, но помечается
  «копия, канон — X»; правка канона обязана обновить копии
  (проверка на ревью). Снимает рассинхрон, не экономит контекст.
- **D. B + C гибрид**: B — где канон гарантированно в контексте;
  C — для тестового кластера (скиллы этапов используются порознь,
  канон `test-design` не всегда загружен).

Крен CC: **D** — B закрывает classify-type и фокус-скиллы без
потери самодостаточности по факту, C страхует тестовый кластер от
повторного рассинхрона; чистый B для тестового кластера заставил
бы каждый этап тянуть `test-design` целиком (15 KB) ради пары
правил.
