# Тип знания: тест-планы API источника

## На какой вопрос отвечает этот файл

Почему per-source тест-планы и библиотека кейсов контура тестов API
источника живут в `.claude/tests/{testType}/{source}/`.

## Контекст

С материализацией контура тестов API источника (роль `tester`,
процесс `.claude/processes/source-api-testing.md`) появился новый
род знания — **тест-план проверки API источника**: кейсы, цепочки
по графу предусловий, teardown, среда. Он отвечает на вопрос,
которого нет в таблице размещения (`.claude/rules/structure.md`):
«**как проверяем API источника X?**».

Тип сперва (создание контура) размещён в
`docs/integrations/{name}/tests/` — как продуктовое знание об
источнике, рядом с контрактами. На аппруве пилота (2026-06-12)
решение **пересмотрено**: тест-план — **артефакт проверочной
деятельности (область пайплайна)**, не продуктовый факт об
источнике. Продуктовые доки источника (`contracts/`, `rules/`,
нативные модели) — источник истины об API; план — проверка **над**
ними, рабочий артефакт контура. Его дом — `.claude/` (инфраструктура
работы), не `docs/`.

## Принятое решение

Новый тип знания: **`.claude/tests/{testType}/{source}/`** —
per-source тест-планы и библиотека кейсов.

- **`{testType}`** — уровень на вырост под будущие типы тестов;
  текущий контур — **`source-api`** (проверка API источника через
  клиентский слой). Доменные автотесты кода (`src/test`, шаг 10) —
  другой `{testType}`, когда дойдут, не смешиваются с `source-api`
  в одном уровне.
- **`{source}`** — источник (`okx` и далее), как в
  `docs/integrations/{name}/`.
- Имя файла — kebab-case по теме. Отвечает на вопрос «как проверяем
  API источника `{source}`?».

Сопутствующее:

- **Шаблон плана/кейса** — доковый шаблон
  `.claude/templates/docs/test-plan.md` (тир `templates/docs/`,
  существующий тип) — без изменений.
- **Отчёты прогонов** — `history` (датированные) — без изменений;
  не `tests/` (там — планы, не прогоны).

## Альтернативы

- **A. `docs/integrations/{name}/tests/`** (продуктовое знание об
  источнике, рядом с контрактами) — первоначальное размещение.
  Отклонено на аппруве пилота: тест-план — артефакт **проверочной
  деятельности** (пайплайн), не продуктовый факт об источнике;
  продуктовые доки (`contracts/`/`rules/`/модели) — источник истины
  об API, план — проверка над ним. Инструменты контура (роль,
  скиллы, процесс, шаблон) уже живут в `.claude/` — план-артефакт
  органичен рядом, не в `docs/`.
- **B. Source-agnostic корень `.claude/tests/` (плоско, без
  `{source}`).** Отклонено: план привязан к контрактам конкретного
  источника и регрессит вместе с ними; source-agnostic ядра у плана
  тестов API источника нет.
- **C. Плоско `.claude/tests/{source}/` (без `{testType}`).**
  Отклонено: уровень `{testType}` нужен на вырост — доменные
  автотесты шага 10 — иной тип проверки, не должны лечь в один
  уровень с `source-api`.
- **D. `docs/models/integrations/{name}/tests/`** (под `models/`).
  Отклонено по тому же доводу, что контракты не кладутся под
  `models/` (`.claude/decisions/model-layer-ontology.md`,
  альтернатива B): план проверки — не модель.

## Следствия

- `.claude/rules/structure.md` — строка типа перенесена из секции
  `docs/integrations/...` в секцию `.claude/...`.
- Каталог наполняется через процесс
  `.claude/processes/source-api-testing.md` (этап DESIGN); первый
  файл — пилотный план `.claude/tests/source-api/okx/pilot-plan.md`.
- Планы — файлы знания: раздел «На какой вопрос отвечает этот файл»
  обязателен (вопрос плана — «как проверяем API `{source}` в
  таком-то скоупе?»).
