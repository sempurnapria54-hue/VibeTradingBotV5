# Стратегия миграции cross-cutting кластеров

## На какой вопрос отвечает этот файл

Как мигрируем сущность, у которой часть знания относится к другим
кластерам.

## Контекст

Миграция архивных торговых сущностей (Balance, Position, Order,
AlgoOrder, Deal, Strategy). Архивные файлы каждой сущности содержали
разрозненные упоминания cross-cutting компонентов: command-подсистема
(`ServiceCommand`, executors, `ServiceCommandFactory`), resolver/
mapper-компоненты, `RiskValidator`, jobs (`EntryScannerJob`,
`IndicatorJob`, `MarketStructureJob`, `MarketPhaseJob`, `AnomalyJob`,
`ReconciliationJob`, `DealOrchestratorJob`), калькуляторы,
FSM-handlers, `DealStateMachine`, RVO (`DealContext`,
`CalculationContext`, `RiskValidationResult`,
`*External*`-snapshot-родственники), market-data модели, аудит. Из
одного архивного файла сущности полное знание о таких компонентах не
собирается — упоминания частичные.

Развилка поднята при миграции Balance (BAL-Q6: считать ли
entity-specific executor/checker/mapper владением Balance или частью
command-подсистемы). Решение применено ко всей серии.

## Принятое решение

При миграции сущности размещается только то, чем сущность владеет:
модель, lifecycle, владельческие правила, mapping в
`docs/models/mapping/<Сущность>.md` (под-разделом per-source) и
source-specific факты в `docs/integrations/{name}/`. Cross-cutting
(компоненты, RVO, jobs, command-подсистема, calc/risk-слой,
anomaly/safety, аудит и подобное), которые текущая сущность задевает
лишь частично, паркуются в `.claude/work/questions/tasks/<задача>.md`
как форвард-заметки.

Доменное существо cross-cutting, видимое в текущем источнике, при этом
фиксируется в файлах владельца — например, статус-таблица resolver'а
живёт в `docs/lifecycles/` владельца и
`docs/models/mapping/<Сущность>.md` (раздел статус-резолвера), а
`docs/components/<Resolver>.md` не создаётся до миграции
resolver-кластера.

Решение опирается на тот же принцип владения, что
`rule-source-of-truth.md` (первоисточник = владелец) и
`master-index-not-fixated.md` (агрегатор разбирается по владельцам);
здесь критерий владения дополняется условием полноты источника: пока
полная картина cross-cutting не собирается из текущего файла, его док
не материализуется.

## Альтернативы

- **B. Создавать тонкие доки компонентов из частичного обзора.**
  Отказались: тонкие доки из неполной картины разрастаются и
  пересобираются при следующей миграции — повторная работа, риск
  рассинхронизации между upgrade-проходами.
- **C. Останавливать миграцию сущности до миграции всех её зависимых
  кластеров.** Отказались: миграция превращается в дерево без понятного
  корня — у любого узла есть зависимости в других кластерах, начать
  невозможно.

## Следствия

- Стратегия применяется к остальным миграциям (Deal management,
  calc/risk-слой, command-подсистема, market-data/timeseries,
  anomaly/safety, аудит, API-кластер OKX).
- Форвард-заметки в `.claude/work/questions/tasks/<задача>.md` —
  указания «при миграции X учесть Y», а не «нерешённые вопросы». При
  миграции соответствующего cross-cutting кластера форвард-заметки
  разбираются. Судьба форвард-заметок после закрытия задачи (где они
  живут, пока соответствующий кластер не мигрирован) — отдельный
  методологический вопрос, разбирается отдельно.
- Пункт backlog «Активно использовать `docs/components/`»
  сформулирован преждевременно: `docs/components/` будет заполняться
  при миграции владельцев соответствующих компонентов. При закрытии
  задачи миграции 6 торговых сущностей этот метод-пункт из backlog
  снимается (выполнено сейчас — см. `.claude/work/backlog.md`).
- Скиллы классификации не меняются: решение касается времени
  материализации дока при миграции (когда создавать), а не определения
  области / типа / темы фрагмента. Cross-cutting фрагмент остаётся
  кандидатом на фиксацию своего типа (компонент / RVO / процесс) — он
  не «не-кандидат» в смысле `recognize-knowledge.md` и не новый тип в
  `classify-type.md`; меняется только размещение во времени.
