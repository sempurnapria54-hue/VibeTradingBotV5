# Издатель токенов окружения — имя хоста окружения

## На какой вопрос отвечает этот файл

Почему издатель токенов окружения закреплён на имени хоста окружения, а ключи
подписи сервисы берут по внутреннему адресу провайдера.

## Контекст

Каждый сервис сверял издателя токена с внутренним адресом провайдера
(`http://platform-identity-service:8080/realms/vibetrading`), а провайдер
выводил адреса из запроса (`hostname.strict: false`). Пока токен брал только
сервис внутри кластера, издатель совпадал. Маршрут к провайдеру снаружи
(`.claude/decisions/environment-ingress-controller.md`) эту посылку снял:
токен, взятый браузером или дымом через ингресс, несёт издателя
`https://<хост окружения>/realms/vibetrading`, и периметр отверг бы каждый
токен человека. Тот же токен периметр пересылает владельцам, и каждый из них
проверяет подпись и издателя сам (`docs/architecture/contracts.md`,
контекст тенанта в вызове).

## Решение (solution-designer, 2026-09-30)

- **Провайдер строит адреса и издателя от закреплённого имени**
  `https://<хост окружения>` (`deploy/base/data/keycloak.yaml`, значение
  патчит оверлей — проекция оси «имя хоста ингресса»); внутренние адреса
  остаются рабочими (`backchannelDynamic`), о схеме запроса он узнаёт из
  заголовков X-Forwarded-*, которые ставит контроллер.
- **Сервис сверяет издателя с именем хоста окружения, а ключи берёт по
  внутреннему адресу.** В манифесте каждого сервиса `OIDC_ISSUER_URI`
  собирается из оси `ingressHost` (`https://$(PLATFORM_INGRESS_HOST)/realms/…`),
  и рядом стои́т адрес ключей
  `SPRING_SECURITY_OAUTH2_RESOURCESERVER_JWT_JWKSETURI`. При обоих свойствах
  Boot собирает декодер по адресу ключей и добавляет проверку издателя
  (`OAuth2ResourceServerJwtConfiguration#jwtDecoderByJwkKeySetUri`, линия
  4.0.0 сверена по исходнику). Кода сервисов правка не касается.
- Дом описания — `docs/architecture/platform.md` §Безопасность.

## Отвергнутые альтернативы

- **Издатель, выводимый из адреса запроса.** Токен браузера и служебный токен
  несли бы разных издателей, и каждый владелец принимал бы обоих — правкой
  кода у восьми сервисов и вторым издателем, которого проверка не различает.
- **Сервисы ходят к провайдеру через имя хоста окружения.** Имя `.invalid`
  внутри кластера не резолвится, сертификат самоподписанный, и каждому
  сервису понадобился бы выход к контроллеру — исходящий периметр
  прикладных сервисов открылся бы ради ключей, лежащих в том же пространстве
  имён.
- **Закрепить издателя на внутреннем адресе.** Провайдер отправлял бы браузер
  на адрес, которого снаружи нет, — тропа входа человека рвалась бы на
  первой переадресации.

## Цена

- **Ветвь декодера у развёрнутого сервиса другая, чем у его чёрного ящика:**
  ящик задаёт только адрес издателя на стаб, и Boot собирает декодер
  обнаружением издателя, а в окружении — по адресу ключей с проверкой
  издателя. Проверка издателя есть в обеих, различается тропа добычи ключей;
  сведение — работа ящиков, и дыма `E1.4` на развёрнутой ветви.
- **Провайдер доверяет заголовкам X-Forwarded-*** от всякого, кто до него
  доходит; до него доходят только контроллер и поимённые сервисы окружения
  (сетевые политики).
- **Не проверено на стенде**, как и контроллер: сверку оживит первый токен,
  выданный провайдером стенда браузерному клиенту.
