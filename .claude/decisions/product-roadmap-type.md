# Продуктовый роадмап как отдельный тип знания

## На какой вопрос отвечает этот файл

Почему тип «роадмап» устроен так, а не иначе (оси решения: scope,
принцип ценности, уровни детализации, источник наполнения,
размещение, тулинг, связь с backlog, отслеживание прогресса).

## Контекст

До этого решения не было устойчивой точки фиксации продуктового
видения: куда движется бот по бизнес-ценности и в каком статусе
каждый шаг. Backlog (`.claude/work/backlog.md`) отражал активную
миграционную работу (cross-cutting кластеры из архива), а не
продуктовый путь вперёд. Snapshot фиксирует срез состояния, но не
направление. `open-questions.md` накапливает развилки, но не
выстраивает их в последовательность.

Возникла потребность зафиксировать продуктовый путь как
самостоятельную сущность с отслеживанием прогресса.

## Принятое решение

Вводится новый тип знания — **«роадмап»**, размещается в
`.claude/work/roadmap/`. Главный файл — таблица фаз; на каждую
фазу — отдельный детальный файл с таблицей шагов.

Состав решения — ниже по развилкам.

### Scope роадмапа — только продукт

В роадмап входят способности с бизнес-ценностью (что бот умеет
делать как торговый продукт). Пайплайн/инфраструктура работы
(методология фиксации знания, миграции из архива и т. п.) в
роадмап не входит — у пайплайна свои механизмы (`decisions/`,
`backlog.md`, snapshot).

**Альтернативы.**
- **Пайплайн-роадмап** (только инфраструктура). Отклонено: у
  пайплайна нет «движения вперёд по фазам», его развитие реактивно
  — от потребностей продукта.
- **Оба слоя в одном роадмапе.** Отклонено: разные природы (продукт
  — бизнес-ценность; пайплайн — обеспечение), смешивание размывает
  принцип отслеживания.

### Принцип ценности

В роадмапе фиксируются только способности с бизнес-ценностью.
Обеспечивающая инфраструктура (перцепция, исполнение, риск,
аудит) строится **внутри той способности, которой впервые нужна**,
не выносится в безценностные фазы.

Поэтому в роадмапе нет «Фазы 0» (инфраструктурной): первая фаза
сразу даёт ценность — «полноценная торговля одной стратегией»,
все обеспечивающие подсистемы рождаются внутри неё.

**Альтернативы.**
- **Фаза 0 (фундамент / инфраструктура).** Отклонено: фаза без
  ценности на финише — это не milestone продукта; правильнее
  строить инфраструктуру inline, под конкретную ценность.

### Уровни детализации

- **Верхний уровень.** Фазы — бизнес-способности. Главный файл
  роадмапа.
- **Детальный уровень.** Шаги реализации внутри фазы — детальный
  файл фазы.
- **Глубже шаги заранее не дробятся.** Подзадачи и детализация
  рождаются в процессе исполнения шага (см.
  `.claude/processes/roadmap-step-execution.md`), не пишутся
  превентивно. Роадмап — карта, не ТЗ.

### Источник наполнения

Содержание роадмапа — продуктовое видение пользователя. Не текущее
состояние кода, не backlog миграций, не накопленные открытые
вопросы. Backlog и open-questions могут стать входами для шага,
когда шаг берётся в работу, — но не определяют, какие фазы и шаги
есть в роадмапе.

### Размещение типа — `.claude/work/roadmap/`

Классификация **по назначению** (как `backlog.md`): это
планирование, относится к пайплайн-области (`.claude/work/`),
несмотря на то, что предмет планирования — продукт.

**Альтернативы.**
- **`docs/roadmap/`** (по предмету: продукт). Отклонено: `docs/`
  — описание продукта как он есть (модели, lifecycles, процессы,
  правила). Роадмап — план движения, это другой жанр.
- **`.claude/work/roadmap/roadmap.md`** (как продуктовое решение).
  Отклонено: роадмап — живой инструмент с изменяющимися
  статусами, а decision — фиксация принятого выбора в моменте.

### Тулинг docs-first

Агенты целостности концепции, ревьюеры доков и подобный тулинг
**не выносится** в отдельную «Фазу 0» и не в отдельный трек.
Тулинг рождается в под-шаге 1 процесса исполнения (см.
`.claude/processes/roadmap-step-execution.md`) — по потребности
конкретного шага.

**Альтернативы.**
- **Фаза 0 — тулинг.** Отклонено по принципу ценности (см. выше).
- **Отдельный методологический трек параллельно роадмапу.**
  Отклонено: тулинг бессмысленно проектировать без конкретной
  потребности; он созревает на конкретном шаге.

### Связь роадмап ↔ backlog

Роадмап и backlog связаны, не дублируются.

- **Роадмап** — план продуктового движения (фазы + шаги).
- **Backlog** — активная исполнительная работа (миграции,
  cross-cutting задачи, методологические ревизии).
- Когда шаг роадмапа берётся в работу, через процесс исполнения
  (`.claude/processes/roadmap-step-execution.md`) он порождает
  конкретные задачи в backlog. Backlog шире роадмапа — в нём
  живут и пайплайн-задачи, не относящиеся к продуктовым шагам.

**Альтернативы.**
- **Поглощение** (роадмап вместо backlog или наоборот).
  Отклонено: backlog шире, включает пайплайн; роадмап только
  продуктовый.
- **Независимость** (роадмап и backlog никак не связаны).
  Отклонено: тогда нет механизма перехода «шаг роадмапа → задача
  в работу».

### Отслеживание прогресса

Статус-таблицы живут в самом роадмапе (главный файл — статус фазы;
детальный файл фазы — статус шага). Пользователь хочет видеть и
отслеживать движение по фазам и шагам — это первично.

- **Статус фазы** — ролляп статусов её шагов (см. ниже скилл).
- **Статус шага** — из канонического набора, определённого в
  процессе исполнения шага.
- **Ведение прогресса** — отдельный скилл
  `.claude/skills/update-roadmap-progress.md`.

**Альтернативы.**
- **Роадмап чистый, прогресс только в `work/progress/` +
  snapshot.** Отклонено: теряется видимость продуктового движения
  одной таблицей; нужно скакать по нескольким файлам.

## Формат типа

- **Главный файл** `.claude/work/roadmap/roadmap.md` — таблица
  фаз: `Фаза | Описание | Статус`.
- **Детальный файл фазы** `.claude/work/roadmap/phase-1.md` —
  таблица шагов: `# | Шаг | Статус`.
- Под-шаги шага заранее не дробятся; детализация рождается в
  исполнении (см. процесс).
- Шаблон в `.claude/templates/` пока не выносим — формат покажет
  себя на практике, вынесем если понадобится повторное
  применение к новым фазам.

## Канонический набор статусов

Канонический набор статусов **шага** живёт в одном месте —
`.claude/processes/roadmap-step-execution.md`. Скилл ведения
прогресса валидирует значения по этому источнику.

Канонический набор статусов **фазы** (ролляп):
- `HOLD` — все шаги в `HOLD`;
- `DONE` — все шаги в `DONE`;
- `IN_PROGRESS` — иначе.

## Следствия

- `.claude/rules/structure.md` — добавлена строка для
  `.claude/work/roadmap/` (вопрос: «Куда движется продукт по
  бизнес-ценности и в каком статусе каждый шаг?»).
- `.claude/skills/classify-type.md` — добавлен тип «роадмап» в
  перечне типов пайплайн-области.
- Созданы файлы:
  - `.claude/work/roadmap/roadmap.md` — главный (фазы 1-5 +
    архитектурный рубеж).
  - `.claude/work/roadmap/phase-1.md` — детальный (10 шагов).
  - `.claude/processes/roadmap-step-execution.md` — процесс
    docs-first исполнения шага.
  - `.claude/skills/update-roadmap-progress.md` — скилл ведения
    прогресса.
- `.claude/work/backlog.md` — короткая пометка про связь с
  роадмапом.
- Сверка backlog/open-questions с роадмапом (где сейчас находимся
  по карте) — отдельная будущая активность, в этом проходе не
  выполняется.
