# Писатель онбордингового статуса инструмента

## На какой вопрос отвечает этот файл

Почему онбординговый статус инструмента пишет каталог пересчётом по
группам свечей, а не отдельный оркестратор?

## Контекст

Вопрос ORCH-Q1 держал владельца переходов `Instrument.Status` и их
координации с `CandleGroup.Status` открытым с фазы 1; lifecycle описывал
только путь `SYNC → CANDLES_LOADING → ACTIVE`, периферию (`HOLD`, `ERROR`,
повторный онбординг, `CLOSED`) откладывал, а процесс загрузки свечей называл
построенный пересчёт готовности «провизорным seam'ом». Построенное в
`services/market-data` к шагу 12 фазы 2:

- `InstrumentCatalogService` — единственный писатель статуса: заведение в
  `SYNC` (синк листинга) и пересчёт готовности (`refreshReadiness`, его зовёт
  `CandleJob` последним ходом прохода); статус — чистая функция статусов
  групп, двусторонняя популяция кандидатов;
- статусы групп пишут `CandleLoader` под `CandleJob` (шаги цикла, триггер
  хвоста) и `MarketDataDemandService` (рождение `CREATED`, возврат к
  `BACKFILL`);
- у `HOLD`, `ERROR`, `CLOSED` инструмента писателя нет ни одного; читает
  `CLOSED` только проход срезов (исключение из популяции).

## Решение (solution-designer, 2026-09-30)

1. **Писатель статуса — каталог, координация — вывод по группам тем же
   тиком, что группы двигает.** Оркестратора нет; lifecycle это объявляет,
   «провизорность» снята.
2. **`HOLD` и `ERROR` инструмента недостижимы, как `CREATED`.** Придерживать
   у онбординга нечего — сбор идёт только под требование, исключение из
   торговли держит ступень ядра; застрявший онбординг выражен `ERROR`
   группы, инструмент остаётся в `CANDLES_LOADING`.
3. **Выхода из `ERROR` группы нет.** Статус пишет только ответ площадки;
   повтор получил бы тот же ответ, приём дыры требует реестра пропусков.
   Возврат — по первой встреченной группе в `ERROR`.
4. **`CLOSED` и повторный онбординг — фаза 6** (сбор по всему листингу);
   в фазе 2 торговлю по ушедшему инструменту останавливает гейт свежести.
   Вводящий писатель обязан вывести периферийный статус из пересчёта.
5. **Запись строки целиком обеими тропами принята с ценой:** окно —
   миллисекунды между чтением и записью внутри тропы, потерянный итог
   восстанавливает следующий тик своей тропы.

## Отвергнутые альтернативы

- **Оркестратор с обработчиком на статус по образцу сделки.** У рёбер
  инструмента нет действия, кроме записи статуса, и нет решения, кроме
  функции групп; обработчики вели бы ту же функцию большим следом
  (`.claude/rules/design-simplicity.md`).
- **Событие о сдвиге группы и подписчик-координатор.** Клиента брокера у
  `market-data` нет, производный статус своей же базы получил бы окно
  рассогласования, а читатель события — только сам сервис.
- **Отдельный тик готовности.** Гадал бы, когда группы сдвинулись; тот, кто
  двигает, знает это точно.
- **`ERROR` инструмента при группе в `ERROR`.** Второй носитель факта
  группы; инструмент ушёл бы из листинга поверхности, и проекция ядра по
  нему устарела бы, не сказав почему.
- **Операция поверхности «вернуть группу в цикл».** Повтор на неустранимой
  дыре исчерпал бы бюджет снова; ценность — только у приёма пропуска, а его
  спроектировать не на чем, пока случай не встречен.
- **Писатель `CLOSED` в фазе 2 по исчезновению из листинга.** Одним
  заказчиком уход закрыт гейтом свежести; популяция и повторный онбординг —
  предмет сбора по всему листингу.
- **Точечная запись статуса и спецификации сейчас.** Окно и исход не
  оправдывают правки двух троп; пересчитывается при появлении перекрытия с
  чтением площадки внутри окна.

## Цена

- Инструмент с неустранимой дырой площадки выпадает из торговли бессрочно,
  разбор — ручной, мимо поверхности.
- Ушедший из листинга инструмент тратит чтения на проходах сбора до фазы 6.
- Ручной запуск синка поверх тика свечей может на один тик вернуть статус
  или спецификацию к застанному.
