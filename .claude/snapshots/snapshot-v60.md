## Дизайн холдов — согласованные решения

**Суть рефрейма:** прежний D2 отложил холды целиком, смешав два контура.
Реактивный CRITICAL-холд L3/L4 **построяем сейчас** (стоит на уже описанном:
дока модели `AnomalyReport`, `KillSwitchExecutor` в коде, терминал `ERROR`,
`Deal.ShutdownReason`, сериализация прохода D-M1). В шаг 8 остаётся только
**проактивный** детектор (`AnomalyJob`/`TradeRuleValidator`) и численные
пороги.

- **Локус (развилка A выбрана ранее):** handler классифицирует CRITICAL →
  уводит свою сделку в `ERROR` → поднимает `HoldSignal{scope, code}`; решение
  и оркестрация реакции — на оркестраторе (`SafetyHoldCoordinator` над
  сделкой, решение в проходе `DealOrchestratorJob`). Один раз на
  инструмент/биржу, идемпотентно (`TRADE_BLOCKED` первым + D-M1). Исполняют
  сервисы — `AnomalyReport`, holds, kill-switch; оркестратор только
  координирует.
- **Последовательность (L3 и L4 одной формы):** `TRADE_BLOCKED` scope первым →
  `AnomalyReport` CREATED (before-слепки БД+биржа) → kill-switch встроен между
  слепками (close→cancel→защиту последней→безусловный close) → after-слепки →
  COMPLETED → enforcement.
- **L3 = инструмент, L4 = биржа** для всех трёх (hold, слепки, flatten). **L4
  — каскад** одним биржа-гейтом на все инструменты; ручной un-hold одним
  действием отпускает всё (per-instrument холды для L4 не пишем).
- **B — статус-модель (решение пользователя):** новый `Status.TRADE_BLOCKED` у
  **инструмента и биржи**. Заморозка только из `ACTIVE` (`ACTIVE →
  TRADE_BLOCKED`); ручная разморозка `TRADE_BLOCKED → ACTIVE`. Из других
  статусов не стартует (неактивное не торгуем). Онбординг-`HOLD` инструмента
  на safety **не** переиспользуется (снята конфляция онбординг↔safety).
  `ERROR → SYNC` (инстр.) / `ERROR → PENDING` (биржа) — восстановление из
  собственной ошибки, отдельная ветка, к заморозке отношения не имеет.
- **C — статус разбора (решение c1):** не вводим. `TRADE_BLOCKED → ACTIVE` =
  «разобрано и отпущено»; `AnomalyReport` — авто-журнал без `RESOLVED`/
  `resolvedBy/At`. Причина: поддержку ведёт лично пользователь; при появлении
  не-его поддержки — вернуть как потребность.
- **§8.C — бесстоповая позиция = L3** (подтверждено `trading-specialist`).
  Опоры: риск локализован на одной позиции/инструменте (isolated-маржа не
  каскадит); критерий L4 политики — радиус за пределы инструмента (cross-маржа
  / >1 позиции), чему бесстоповость не отвечает; «инвариант» — про силу
  пре-трейд гарда, не скоуп реакции. **Предусловия:** L3 условен на
  isolated-марже (cross-маржа → был бы L4); проактивный L4-путь (паттерн «много
  бесстоповых / обойдён гард» = control-plane failure) сохраняется отдельно —
  **шаг 8**; реактивный контур шага 6 поднимает L3 на одну обнаруженную
  позицию.
- **`AnomalyReport`:** модель уже описана докой — **переиспользуем**, не
  создаём. Носитель before/after-слепков + встроенного kill-switch. Дополнить
  явным `scope`/`level` (INSTRUMENT/EXCHANGE) вместо вывода из
  `instrumentId=null`. Java-модели нет (только дока) — материализуется в
  `CODE`-заходе.
