## Живой контекст: открыто по развилке (валидация 4)

**Одна позиция — окно консолидации входа** (§6.3). Между `COMPLETED`
строки `FINALIZE_DEAL_ENTRY_ACTION` и переводом статуса проходит минимум
один проход петли (статус двигает handler по выходным проверкам, а
завершённые строки ключ не держит) ⇒ может завестись второе исполнение
консолидации. Порчи данных нет — команда атомарна по клаузе «повтор с
нуля безопасен»; цена — лишний повтор. Варианты: (i) закрыть окно
транзакцией — цена: статус двигает не handler, исключение из «стадии из
фактов» и из конструкции handler'а; **(ii) принять повтор — крен**;
(iii) сузить предикатом эмиссии — цена: знание выходных проверок в двух
местах.

**Гейтится другим узлом:** §6.4 — метка подтверждения для
`REFRESH_DEAL_CONTEXT_ACTION` (refresh не меняет данных, если факт не
изменился) упирается в **узел 7** `DOCS_CHECK_8`, который открыт.

**Не развилки:** §5.2 — пустая секция `service-command-retry` (дефект
кода, пункт `CODE`); §2.2 — переименование `StrategyActionType` (решено,
условие проверено).

## Живой контекст: находки, живущие независимо от развилки

- **Дефект ключа шага 4.** `UNIQUE(deal_id, strategy_action_id)` +
  единственный резолв `findByDealIdAndStrategyActionId`: второй ноге
  грида некуда лечь, `attemptCount` общий, `target` перетирается.
  Чинится этой правкой.
- **Пустая секция retry-конфига.** Механизм построен и читается живьём,
  но секции `service-command-retry` нет ни в одном конфиге ⇒ `getPolicy`
  возвращает `null`, `canRetry` падает **NPE** в **catch-ветке**
  `ServiceCommandExecutor.execute`, подменяя исходную ошибку и не
  доводя retry-учёт. Пункт `CODE`.
- **Потребителей Strategy API в репозитории нет** (проверено на
  валидации 3): контроллер есть, тесты его не дёргают, клиента нет ⇒
  переименование `StrategyActionType` = миграция значений одной колонки
  + правка примера + свип по коду.
