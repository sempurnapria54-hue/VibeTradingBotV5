# Формат отчёта фокуса ревью

## На какой вопрос отвечает этот файл

Каков формат отчёта фокуса ревью (структура, набор полей находки,
принципы верификации находок)?

## Применение

Общий формат для **всех фокусов** роли `reviewer` на статусах
`CONCEPT_REVIEW` и `REVIEW` машины шага
(`.claude/processes/roadmap-step-execution.md`). Скиллы фокусов держат
**процедуру обхода**; формат отчёта и находки — здесь, в скиллах не
дублируется.

**Область — всякий перечень вариантов, не только находка фокуса:**
перебор владельца при закрытии находки или в дайджесте решений несёт те
же обязательные поля и проходит те же принципы верификации.

**Потребители полей берут их из отчёта, не реконструируют:** закрытие
идёт по списку носителей находки
(`.claude/rules/edit-kind-obligations.md` §«Прочие обязанности закрытия»),
дайджест решений — по полям находки. Непроставленное поле не
«подразумевается» — оно теряется.

Разбор находок — автономный (`.claude/processes/question-delegation.md`):
владелец по карте решает сам и фиксирует решение в дайджесте
(`.claude/work/decision-digest.md`); держателю выносится только дефицит
`подтверждение`.

## Артефакт

Отчёт фокуса — файл в `work/progress/` шага:
`phase-<N>-step-<M>-review-<фокус>.md`; у ревью концепции —
`phase-<N>-step-<M>-concept-review.md`. При закрытии шага переезжает в
`history/` вместе с хроникой.

## Структура отчёта

- **Охват.** Что проверялось (дельта шага: файлы, классы, доки), что вне
  охвата и почему.
- **Находки.** Каждая — с полным набором полей (§ниже).
- **Открытые вопросы держателю.** Пункты с дефицитом `подтверждение` —
  только они доходят до держателя; остальное закрывается автономно.
- **Сводка.** Сколько находок, агрегация по ярлыкам и владельцам;
  счётные строки — пересчётом по телу после его закрытия
  (`.claude/rules/self-description-form.md`).

Полные выводы грепов в отчёт не вклеиваются: команда поиска — блоком кода,
её вывод — нет; в отчёте остаются заключение и точки (`файл:строки`).

## Набор полей находки

Поля проставляются по **каждой** находке. Поля «варианты» и «дефицит»
пустыми молча не остаются: отсутствие пишется явно («развилки нет»,
«дефицита нет — закрыто прогоном»).

- **Вопрос** — суть находки.
- **Носители** — перечень носителей дефекта с точками (`файл:строки` или
  файл + §секция). **Обязательно на каждой находке:** закрытие проходит по
  этому списку, отмечая каждый носитель — правлено / не требует правки —
  почему.
- **Целевой носитель** — адрес правки (правка существующего дока или
  кода / новый `decision`). Обязателен, даже когда очевиден.
- **Ожидаемый владелец** — роль по **природе вопроса** из карты владельцев
  (`.claude/processes/question-delegation.md`), не по фокусу-источнику.
- **Посылка** — достроенный контекст, если он есть, с пометкой «из
  носителя не выведена» (`.claude/agents/reviewer.md` §Поведение).
- **Варианты** — если развилка: перечень вариантов и позиция (крен) с
  обоснованием, либо явно «крена нет». Форма и верификация перебора —
  §Принципы верификации находок.
- **Ярлык исхода** — **обязателен на каждой находке**: `выводимо` /
  `варианты-с-креном` / `принято-в-работу` / `неразрешимо-владельцем`.
  `варианты-с-креном` без двух и более перечисленных вариантов запрещён.
- **Ярлык дефицита** (только если фокус не закрыл) — `грунт` (не хватает
  внешнего знания) / `работа` (нужно проектирование) / `подтверждение`.
  Что считается `подтверждение` — `.claude/processes/question-delegation.md`
  §«Критерий один: выводится ли ответ из концепции»; вынос несёт запись
  самопроверки (там же, §«Вынос проходит самопроверку, и она
  записывается»).

## Принципы верификации находок

Обязательны с обеих сторон: фокусу при генерации находки и владельцу при
проработке (`.claude/skills/design-fork.md`).

### Проверка посылок и клеймов

- **Отрицательная посылка верифицируется до того, как стать доводом.**
  «Поля/метода/значения X нет» — клейм о полноте: проверяется грепом по
  дереву кода или чтением носителя, не памятью.
- **Перечень существующего устанавливается по коду, не по обходу
  owner-доков.** Носитель без owner-дока — тоже носитель.
- **Посылка перебора называется явно** и помечается **непроверенной**,
  если утверждает устройство, не выведенное из носителя.
- **Клейм разбирается против инвариантов объемлющего уровня.** Ветка,
  запрещённая ратифицированным инвариантом, вариантов не порождает:
  снимается либо выносится явно с пометкой «переоткрывает инвариант X».
- **Несущий пример проверяется на достижимость.** Класс отказа, штатно
  поглощаемый уровнем ниже, до точки решения не доходит и примером не
  служит.
- **«Подтверждено-ОК» называет уровень сверки** — состав слагаемых /
  предикат области / операнды.

### Состав перебора

- **Первая позиция перебора — достаточность существующего носителя.**
  Прежде чем вводить новую структуру, находка называет, чем различение
  выражено сегодня и чего этому носителю не хватает; если ничем —
  пишется явно.
- **Достаточность проверяется на поверхности потребления, не в модели.**
- **Ось структурной свободы обязательна.** Наравне с «починить внутри»
  выносится «переструктурировать» — с пометкой «переоткрывает принятое»
  (выписать не значит выбрать).
- **Совмещение двух природ в одном носителе открывает вариант «развести
  носители»** — цена называется и взвешивается.
- **На развилке «пусто или ноль» обязателен предикатный третий вариант**
  (`docs/rules/absent-value-semantics.md`).
- **Находки сверяются на общий ход до выноса.** Закрываемые одним
  изменением выносятся **одной** развилкой; проверка — по совпадению
  **правки**, не темы.
- **Развилка собирается из находок всех фокусов.** Нашедший альтернативу
  фокус вносит её наравне с нашедшим дефект.

### Цена варианта

- **Перечень вариантов самонесущий: цена варианта — в его же строке.**
  Форма — таблица «вариант | что делает | названная цена».
- **Оценка цены — проверяемая величина, не риторика.** «Цена ≈ 0»
  принимается, только если названо, из чего складывается и чем
  проверяется.
- **Второе измерение цены — контекстная связность:** сколько мест обязаны
  знать внешний контекст для корректного вызова.
- **Продуктовый scope не оценивается агентом как цена** — вариант
  выписывается с пометкой «цена — продуктовое решение держателя»
  (дефицит `подтверждение`).
- **«Записать ограничение как известное» сравнивается с «закрыть сразу»
  явной ценой обеих сторон**, включая цену закрытия потом.

### Выбор варианта

- **Минимальный след — норма; бо́льший след называет счётную разницу**
  (`.claude/rules/design-simplicity.md`). Шкала следа: правка клаузы →
  явное ограничение → § правила → значение енума / признак → колонка /
  поле / индекс → сущность / компонент / вторая ось. При равенстве
  выигрывает меньший.
- **Гейт не ставится на невыясненном.** Находка, гейтящая только при
  одном исходе соседней развилки, — **зависимая**, не гейтящая.

### Классификация и направление правки

- **Дефект записи и продуктовая ось разводятся в находке.** Ложная запись
  чинится курационно и от продуктового выбора не зависит.
- **Направление синхронизации доков и кода — docs←code.** Код, прошедший
  `CODE` с зелёным реактором, — истина; расхождение либо пробел `DOCS`,
  либо находка по коду, и находка называет, какое из двух. Клейм о
  **фактическом** устройстве кода при расхождении — дефект дока.
