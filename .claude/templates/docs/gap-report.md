# Формат gap-отчёта DOCS_CHECK

## На какой вопрос отвечает этот файл

Каков формат gap-отчёта `DOCS_CHECK_N` (структура отчёта, набор полей
находки, узлы, сборка эскалаций)?

## Применение

Общий формат для **всех линз** ревью под-шага `DOCS_CHECK_N`
(`concept-review`, `trading-review`, будущие) и для CC-оркестратора,
собирающего отчёт. Скиллы линз держат **процедуру обхода** (как искать);
формат отчёта и находки — здесь, в скиллах не дублируется. Дайджест чата
обязан **брать поля из отчёта, а не реконструировать** (правило «Дайджест
отчёта `DOCS_CHECK_N`» в `.claude/chat/chat-project-instructions.md`):
непроставленное поле = пустая колонка дайджеста — оно не
«подразумевается», оно **теряется**.

## Артефакт

Gap-отчёт — progress-файл активной задачи (название итерации включает
номер `N`, по образцу
`.claude/work/progress/phase-<N>-step-<M>-docs-check-<K>.md`).

## Структура отчёта

- **Охват.** Какие доки проверялись, какие были вне охвата (и почему).
- **Стадия остановки.** На какой стадии обход остановился: гейт стадии 0 /
  после процессов (стадия 1) / прошёл все стадии (стадия 2).
- **Пробелы по типам.** Списком: несогласованности; name-level без
  структуры; неотвеченные вопросы.
- **Блокирующие открытые вопросы.** Из `open-questions.md`, со ссылками.
- **Эскалации.** Пункты, дошедшие до чата (product/policy-остаток), и
  спорные случаи.
- **Сводка.** Сколько пробелов, сколько эскалаций; **агрегация находок по
  ярлыкам исхода и дефицита**; чисто или нужен следующий
  `DOCS_CHECK_{N+1}` после `GAPS_CLOSE_N`.

## Набор полей находки

**Поля проставляются по каждой находке, не только по эскалируемой.**
Минимум по типам находок:

- **Ярлык исхода — обязателен всегда**, на каждой находке. Без
  исключений: находка без ярлыка не отчитана.
- **Цитаты (носители) — обязательны на каждой находке.** Закрытие стоит
  на этом списке (см. поле ниже).
- **Ожидаемый владелец — обязателен на каждой гейтящей находке.** Гейт —
  это заявка на работу; работа без адресата не начнётся. Владелец берётся
  по **природе вопроса** из карты владельцев
  (`.claude/processes/question-delegation.md`), в том числе
  `trading-specialist` для торговых находок — независимо от того, какая
  линза находку surface-ила.
- **Ярлык дефицита** — на находках, которые прогон не закрыл.
- **Флаг действия CC** — на каждой находке (опора аудита автономии).

Прочие поля (варианты, целевой док, трассировка) — по применимости, но их
отсутствие проговаривается, а не молчит.

Фиксированный набор полей:

- **Вопрос** — суть пробела.
- **Цитаты (носители)** — перечень носителей дефекта с точками
  (`файл:строки` или файл + §секция), по которым находка утверждает
  дефект. **Обязателен на каждой находке:** закрытие находки на
  `GAPS_CLOSE_N` обязано пройти по её собственному списку цитат и
  отметить каждую — правлено / не требует правки — почему
  (`.claude/processes/roadmap-step-execution.md` §3); находка без списка
  цитат оставляет это правило без входа.
- **Ожидаемый владелец** — кого даёт карта владельцев по природе вопроса
  (`.claude/processes/question-delegation.md`).
- **Кто ответил + трассировка** — фактический владелец; кто surface-ил
  (агент/фокус); что владелец открыл (какие доки; в частности —
  сверялся ли с owner-доком, источником истины по затронутому концепту),
  как рассуждал, к чему пришёл.
- **Ответ** — что владелец вывел/предложил.
- **Варианты** — если развилка: варианты + крен с обоснованием, либо явно
  «крена нет — настоящий product/policy-выбор пользователя». **Состав
  вариантов собирается из находок всех линз, чьи находки вошли в узел**
  (§ниже), с проверкой оси структурной свободы (§ниже).
- **Целевой док** — куда трансформируется ответ (правка существующего
  дока / новый `decision`); финальное размещение — штатным потоком на
  `GAPS_CLOSE_N`.
- **Ярлык исхода** — `выводимо-Предложение` / `варианты-с-креном` /
  `принято-в-работу` (design-задача) / `неразрешимо-владельцем`.
  Связка ярлык → сомнение/эскалация по ступеням —
  `.claude/processes/question-delegation.md` §«Определение сомнения».
- **Ярлык дефицита** (только если не закрыто) — `грунт` (не хватает
  внешнего знания) / `работа` (нужно проектирование) / `подтверждение`
  (величину/поле неоткуда зафиксировать).
- **Флаг действия CC** — что CC сделал с находкой: `предложил` /
  `финализировал` / `завёл открытый вопрос` / `эскалировал`. Опора для
  независимого аудита автономии в дайджесте чата (правило «Дайджест
  аудитит автономию CC» в `.claude/chat/chat-project-instructions.md`):
  по флагу видно, сработал ли CC в рамках ступени владельца или превысил
  её. Аудит заодно ловит мисклассификацию сомнения — закрытую молча живую
  развилку, не помеченную сомнением.

## Сборка эскалации из узла — по всем линзам узла

Находки кучкуются в **узлы** (одна развилка, вскрытая с разных сторон).
Когда узел эскалируется, действует правило:

**Состав вариантов собирается из находок ВСЕХ линз, чьи находки в узел
вошли** — не одной, даже если она вскрыла узел первой или дала самую
тяжёлую находку. Линза, нашедшая **альтернативу**, вносит её в эскалацию
наравне с линзой, нашедшей **дефект**.

Механика: перед выпуском эскалации — пройти по списку находок узла и
проверить, что каждая, предлагающая или подразумевающая **иной вариант
ответа**, представлена в §Варианты. Находка узла, не давшая варианта, —
тоже фиксируется («вклад — постановка/довод, варианта не несёт»), чтобы
пропуск было видно.

**Кейс, на котором правило выведено (`DOCS_CHECK_4`, шаг 7 фазы 1).**
Узел «класс холда по несвежести» собран из линз A и C, а варианты взяты
только из A — «L4 целиком vs новый более слабый класс». Линза C той же
кучей нашла третий вариант — **scope = инструмент** (H15: цена пропуска
для холда занижена, альтернативы с корректной ценой не взвешивались), и в
эскалацию он **не попал**. Пользователь на слепом проходе выбрал именно
его. То есть **существенное расхождение слепого прохода было вызвано
дефектом сборки эскалации, а не незнанием CC**: вариант в отчёте лежал,
до пользователя не доехал. Цена ошибки — обнулённый счёт гейта
делегирования плюс лишняя итерация.

**Почему это не лечится «внимательнее читать».** Дефект структурный:
линзы независимы, узел собирает CC, и при сборке естественно тянуть
варианты оттуда же, откуда взята формулировка узла. Поэтому проверка —
отдельный шаг с явным списком, а не установка на аккуратность.

## Ось структурной свободы при генерации вариантов

Прежде чем чинить находку внутри существующей структуры, проверить:
не является ли развилкой **сам выбор структуры** — новый компонент,
новая сущность, новый радиус, другая модель угроз. Если да — вариант
«переструктурировать» выносится в §Варианты наравне с вариантами
«починить внутри», даже когда чинящий вариант выглядит достаточным.

**Кейс, на котором правило выведено (`DOCS_CHECK_5`, шаг 7 фазы 1).**
Сверка слепого прохода дала четыре расхождения одного класса:
пользователь выбирал **переструктурирование**, линза чинила внутри
существующей онтологии, и вариант «переструктурировать» в набор не
попадал (новый компонент; новый радиус; новая сущность; другая модель
угроз). Дефект структурный, не «фантазии не хватило»: линза по
построению ищет минимальную правку против существующих доков, и ось
«а верна ли сама структура» без явного шага не открывается.

Та же проверка — обязанность **конструктивного владельца** при
проработке развилки (`.claude/skills/design-fork.md`): ось нужна с обеих
сторон машины, не только линзе.

## Гейт не ставится на невыясненном

**Находка не гейтит под допущением.** Если находка гейтит только при
одном из открытых вариантов соседней находки — она не гейтящая, а
**зависимая**: фиксируется с явной записью «гейтит, если <узел>
разрешится как <вариант>».

Гейт означает «CODE нельзя начинать, пока не закрыто». Утверждать это
можно, только когда посылка **установлена**. Иначе гейт наследует
неопределённость посылки и создаёт ложную работу: закрывать будут то,
чего при другом исходе узла не существует.

**Кейс (`DOCS_CHECK_4`, шаг 7 фазы 1).** H6 («`Exchange.HOLD` нет в
енуме») был помечен **ГЕЙТИТ** — но гейтил он **только** под допущением
«холд по несвежести = холд биржи». Класс холда при этом разбирался в
**открытом** H4 того же прогона. Пользователь выбрал scope = инструмент —
и H6 испарился: писателя `Exchange.HOLD` шаг 7 не вводит вовсе, а
`Instrument.Status.HOLD` в енуме уже есть. Гейт был поставлен на посылке,
которую сам отчёт держал открытой.

Правильная запись такой находки: «**зависимая от H4.** Гейтит, если H4
разрешится как «холд биржи»: писателю статуса не из чего его выставить.
При «scope = инструмент» — не применима».
