# Шаблон: тест-план интеграции

## На какой вопрос отвечает этот файл

Каков формат докового файла тест-плана контура тестов API источника.

## Назначение

Универсальный шаблон тест-плана и кейсов контура тестов API
источника, **один на все источники**. Вход для `tester` на этапе
DESIGN (`.claude/skills/test-design.md`). Готовый план кладётся в
`.claude/tests/{testType}/{source}/`.

Скоуп контура — **сырьё** (сырой клиент + сырые DTO), demo/non-prod
(prod вне контура). Обоснование —
`.claude/decisions/source-api-target-rebase.md`.

## Структура плана: метод → кейсы → таблица

План построен **по методам сырого клиента**, прямой маппинг на код
(**класс на метод, тест на кейс**):

- **метод сырого клиента — заголовок** (`## Mn. method — путь (раздел)`);
- **кейс — подзаголовок** (`### Mn.k …`): прямой кейс / **каждый**
  негатив / **каждый** вариант типа-дискриминатора / цепочка —
  отдельным подзаголовком;
- **в каждом кейсе — своя таблица** (строка = запрос кейса).

Эти же таблицы — **бланк отчёта прогона** (durable): на RUN заполняется
колонка «Факт + наблюдения», структура метод → кейсы → таблица не
пересобирается (`test-run`).

## Форма плана (скелет)

- **На какой вопрос отвечает этот файл** — «Как проверяем API источника
  `{name}` на уровне сырья (такой-то скоуп)?».
- **Скоуп** — что покрывает план. Для новой биржи — **весь периметр
  манифеста ∩ сырой клиент**: каждый запрос в периметре
  (`docs/integrations/{name}/coverage-manifest.md`, строки `есть-док`/
  `создан`/`обновлён`), прямой кейс (если достижим) + **негатив на
  каждый запрос (вкл. write/мутацию)** + **каждый вариант типа-
  дискриминатора**. Плюс триггер (новая биржа / новый эндпоинт /
  изменение контракта / разовый).
- **Инвариант полноты** — раздел-перечень: in-perimeter ∩ клиент
  (метод ↔ строка манифеста ↔ варианты) и client-coverage-gap'ы (строки
  периметра без метода клиента). Сверяется с колонкой покрытия манифеста.
- **Среда** — demo/non-prod (test-профиль, demo-креды). Prod вне
  контура: prod-кейсов и prod-read-only блока **нет**.
- **Негативный слой (без состояния)** — дешёвые кейсы, гоняются первыми.
- **Цепочки (по графу предусловий)** — связные последовательности;
  выход кейса = предусловие следующего; stateful-кейс создаёт реальную
  demo-сущность.
- **Чистота биржи** — после прогона ни висящих ордеров, ни позиций, ни
  иных созданных сущностей. Достигается teardown'ом **в каждом кейсе**.
- **client-coverage-gap'ы / вариант-gap'ы** — строки периметра без
  метода клиента и варианты, которые клиент собрать не может, помеченные
  явно (запрос не выдумывается).

## Форма кейса (скелет)

**Кейс — подзаголовок `###` метода, тело — одна таблица.** Кейс
самодостаточен: ставит своё предусловие (создаёт сущность), проверяет
своё и **оставляет биржу чистой**.

- **Шапка кейса** — объект (сырой метод клиента или цепочка),
  предусловие-состояние, среда (demo), **пометка достижимости** (прямой
  кейс достижим? если нет — отказ + причина, покрытие только негативом);
  для варианта — какой именно (`ordType=limit`, `conditionType=OCO_FULL`,
  семья cancel).
- **Тело — таблица, строка = запрос кейса.** Колонки: запрос (сырой
  метод клиента + параметры) | проверки (на **сыром DTO**:
  `OkxApiResponse<T>` — `code`/`msg`/`data[].sCode`, типизированный
  `*OkxResponse`/`*Ack`; используемые поля + коды ошибок) | ожидаемый
  результат (из контракта источника — ACK-семантика, код ошибки, факт
  состояния; незадокументированное не выдумывается) | **Факт +
  наблюдения (RUN)** (заполняется на RUN; до прогона пусто — это и есть
  бланк отчёта).
- **Негатив — на каждый запрос, по порождающей методологии**
  (`test-design`), включая write/мутацию: применимые категории (битый
  параметр, имя ключа, значение вне домена, несущ. id, дубль, отмена
  отменённого, фильтр вне окна, auth, состояние-конфликт) с ожидаемым
  кодом ошибки.
- **Вариант типа-дискриминатора — отдельным кейсом.** На каждый
  поддерживаемый клиентом вариант (`ordType`, `conditionType`, семья
  cancel) — прямой кейс варианта + применимый негатив. Вариант, который
  клиент собрать не может, — вариант-gap (не выдумывается).
- **Teardown кейса** — завершающие строки той же таблицы: что снимает
  поставленное кейсом состояние (отмена/закрытие), чтобы после кейса
  биржа была чистой.
- **Цена ордера — с биржи, минимальный риск.** Кейс, ставящий лимитный
  ордер, не берёт цену «из воздуха»: live-цена тянется сырым `getTicker`
  (отдельной строкой кейса), ордер ставится **заведомо неисполнимым**.
  Где нужен факт исполнения (fill/позиция) — минимальный **market**-ордер
  на demo с обязательным teardown (закрытие позиции).
