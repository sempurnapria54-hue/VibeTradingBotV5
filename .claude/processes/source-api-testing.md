# Тестирование API источника

## На какой вопрос отвечает этот файл

Как устроен процесс тестирования API внешнего источника.

## Назначение

Оркестрация контура тестов API источника — живой проверки API
внешнего источника через наш клиентский слой. Координирует четырёх
участников; собственное содержание — последовательность этапов,
входы/выходы между участниками, условия запуска (условие
материализации процесса — собственная оркестрация, см.
`.claude/decisions/process-materialization-criterion.md`).

Скоуп контура — **граница с биржей** (`IntegrationService` /
`OkxRestClient` / `OkxProxyController`), не торговый домен. Доменные
автотесты (`src/test`) — шаг 10 Фазы 1, тот же владелец (`tester`),
вне этого процесса.

## Участники

- **`tester`** — автор: строит план (`test-design`), прогоняет
  (`test-run`), чинит забракованное. Ступень — Предложение.
- **`integrator`** — консультант-хранитель интеграционного знания:
  контракты, ACK-семантика, коды ошибок, конфликты/пробелы спеки.
  Дёргается front-load, итеративно.
- **`reviewer`** (фокус `test-review`) — адверсариальный критик
  плана и отчёта.
- **Пользователь** — аппрув плана; решения с prod-эффектом /
  реальными деньгами; хвост находок, не закрываемый владельцами.

## Этапы

1. **DESIGN.** `tester` составляет план и кейсы (`test-design`) по
   контрактам источника. Консультации `integrator` по контрактам —
   итеративно, front-load до фиксации кейсов. Выход — тест-план в
   `.claude/tests/{testType}/{source}/` (поле «фактический
   результат» пустое).

2. **REVIEW плана.** `reviewer` (`test-review`) — осмысленность
   кейсов, покрытие границ/ошибок, корректность графа предусловий,
   наличие teardown. Петля с `tester` до прохождения: браковка →
   правит автор → перепроверка.

3. **APPROVE.** Отревьюенный план — пользователю. На ступени
   Предложение — план целиком, с разбором (аргументация, варианты,
   что сказал интегратор по ходу консультаций; формат —
   `.claude/processes/question-delegation.md`, валидация
   Предложения). **Прогон до аппрува не запускается.**

4. **RUN.** Прогон по утверждённому плану (`test-run`): кейсы в
   порядке цепочек, дешёвый негативный слой первым, teardown.
   Выход — отчёт прогона (ожидание vs факт + наблюдения).
   Write-операции — только demo; prod — только read-only.

5. **REVIEW отчёта.** `reviewer` (`test-review`) — качество
   фиксации, полнота наблюдений, обоснованность вердиктов. Петля с
   `tester`.

6. **Разбор находок.** Маршрутизация по владельцам:
   - расхождение «контракт-док ↔ реальность биржи» → `integrator`
     (правка интеграционных доков `docs/integrations/{name}/`);
   - баг нашего клиентского слоя → `backlog.md`;
   - наблюдение-знание → штатное размещение
     (`recognize-knowledge` → классификаторы → `place-knowledge`);
   - незадокументированное поведение биржи → находка `integrator` /
     эскалация, не выдумка.
   Отчёт прогона — в `history` (датированный).

DESIGN-only заход (пилот, обкатка формы) останавливается после
этапа 3: план уходит на аппрув, RUN/разбор — отдельным заходом.

## Триггеры

- **новая биржа** — полный план по всем контрактам источника;
- **новый эндпоинт** — точечное расширение существующего плана;
- **изменение контракта** — регрессия затронутого;
- **разовый запуск по запросу пользователя.**

Гранулярность построения по триггеру — `test-design`
(§«Гранулярность по триггеру»).
