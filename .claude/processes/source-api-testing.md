# Тестирование API источника

## На какой вопрос отвечает этот файл

Как устроен процесс тестирования API внешнего источника.

## Назначение

Оркестрация контура тестов API источника — живой проверки API
внешнего источника на уровне **сырья** (сырой клиент + сырые DTO).
Координирует четырёх участников; собственное содержание —
последовательность этапов, входы/выходы между участниками, условия
запуска (условие материализации процесса — собственная оркестрация, см.
`.claude/decisions/process-materialization-criterion.md`).

Скоуп контура — **сырьё биржевого запроса/ответа**: сырой клиент
(`OkxRestClient`) + сырые интеграционные DTO (`OkxApiResponse<T>`,
типизированные `*OkxResponse`/`*OkxRequest`), не наша граница
(`IntegrationService` / снапшоты / мапперы) и не торговый домен.
Обоснование переезда — `.claude/decisions/source-api-target-rebase.md`.
Доменные автотесты (`src/test` доменного слоя) — шаг 10 Фазы 1, тот же
владелец (`tester`), вне этого процесса.

Контур — **demo/non-prod**. Prod вне контура: prod-кейсов нет,
prod-read-only блока нет; прод пользователь проверяет ад-хок вручную
коллекцией вне контура.

## Участники

- **`tester`** — автор: строит план (`test-design`), пишет и прогоняет
  код-тесты (`test-code`), по желанию собирает справочную коллекцию
  (`test-collection`),
  чинит забракованное. Ступень — Предложение.
- **`integrator`** — консультант-хранитель интеграционного знания:
  контракты, ACK-семантика, коды ошибок, конфликты/пробелы спеки,
  правка апидоков по расхождениям прогона (C3). Дёргается front-load,
  итеративно.
- **`reviewer`** (фокус `test-review`) — адверсариальный критик плана,
  код-тестов и отчёта.
- **Пользователь** — аппрув **плана**; хвост находок, не закрываемый
  владельцами. (Коллекция аппрув-артефактом не является — решение
  держателя 2026-08-31, `.claude/decisions/collection-not-approval-artifact.md`.)

## Этапы

1. **DESIGN.** `tester` составляет план и кейсы (`test-design`) —
   **источник набора запросов — манифест покрытия**
   (`.claude/tests/{testType}/{source}/coverage-manifest.md`), весь in-perimeter
   периметр через `/raw`. Структура — **метод → кейсы → таблица** (класс на метод,
   тест на кейс). Правила построения кейсов (прямой кейс + широкий
   порождающий негатив на каждый запрос вкл. write/мутацию,
   вариант-покрытие по каждому in-perimeter варианту
   типа-дискриминатора, гейт достижимости, цепочки, teardown, цена с
   биржи) — канонически в `test-design`. **Инвариант полноты:** каждый
   in-perimeter запрос манифеста покрыт — под `/raw` тело конверта
   строится руками, наличие типизированного метода клиента роли не
   играет; прежняя метка `client-coverage-gap` снята
   (`source-api-target-rebase.md`, раздел D). Консультации `integrator` —
   итеративно, front-load. Выход — тест-план в
   `.claude/tests/{testType}/{source}/` (поле «факт» пустое); **колонка
   покрытия манифеста переводится в «в плане»** для методов, покрытых
   планом (см. ниже).

2. **REVIEW плана.** `reviewer` (`test-review`) — покрытие по манифесту,
   соблюдение правил построения (чек-лист — в `test-review`). Петля с
   `tester` до прохождения.

3. **APPROVE.** Отревьюенный план — пользователю (ступень Предложение,
   разбор по `.claude/processes/question-delegation.md`). Аппрув — **на
   план**. **Код-тесты и прогон до аппрува плана не запускаются.**

   **Коллекция аппрув-артефактом не является** (решение держателя
   2026-08-31, `.claude/decisions/collection-not-approval-artifact.md`):
   исполнитель прогона — код-тесты, а коллекция была бы третьей записью
   того же знания, которую никто не прогоняет. Строится по желанию как
   выводимая справка (`.claude/skills/test-collection.md`), предметом
   ревью и аппрува не служит, и её отсутствие прогон не гейтит.

4. **CODE-тесты.** По утверждённому плану `tester` пишет
   `@SpringBootTest`-код-тесты (`test-code`), бьющие в A2-passthrough;
   покрывают весь план
   (класс на метод, тест на кейс). REVIEW код-тестов (`test-review`) —
   петля с `tester`. По прохождении ревью **колонка покрытия манифеста
   переводится в «в коде»** — но только для строк, **все** кейсы которых
   покрыты (код-тестом либо делегированием цепочке, см. §«Колонка
   покрытия в манифесте»); строка с хотя бы одним непокрытым кейсом
   остаётся «в плане».

5. **RUN.** Прогон код-тестов на demo/non-prod (`test-run`):
   профиль-гейт (на prod не идут); дисциплина прогона (порядок
   цепочек, дешёвый негатив первым, реальные demo-сущности, teardown)
   — в `test-run`. Выход — бланк отчёта (таблицы плана + колонка
   «факт») с ожиданием vs факт + наблюдения.

   **Исход-перечень пишет сам прогон, и пишет персистентно.** Кейс, чей
   исход есть перечень (справочник, набор пар, состав записи), зовёт
   `persistObservation` и кладёт перечень в `observations/<КЕЙС>.md`;
   ячейка плана несёт указатель и мощность, не сам перечень. Лог
   носителем наблюдаемости не является: слот, закрытый фактом из лога,
   закрыт не был. **Ветвь пропуска — тоже исход:** кейс, пропущенный
   assumption'ом, пишет строку «прогон был, событие не наступило» до
   пропуска, иначе «не гонялся» и «гонялся и промахнулся» в данных не
   различаются.

6. **REVIEW отчёта.** `reviewer` (`test-review`) — качество фиксации,
   полнота наблюдений, обоснованность вердиктов. Петля с `tester`.

7. **Разбор находок.** Маршрутизация по владельцам:
   - расхождение «апидок ↔ реальность биржи» → раздел «расхождения»
     отчёта = вход/триггер `api-docs-completion` (C3): `integrator`
     правит апидоки, рантайм-факт фиксируется провенансом `рантайм` /
     `подтверждён-прогоном`, в шапке `external-source-sync` — пометка;
   - баг сырого клиента / адаптера → `backlog.md`;
   - наблюдение-знание → штатное размещение
     (`recognize-knowledge` → классификаторы → `place-knowledge`);
   - незадокументированное поведение биржи → находка `integrator` /
     эскалация, не выдумка.
   Отчёт прогона — в `history` (датированный).

DESIGN-only заход (обкатка формы) останавливается после этапа 3: план
уходит на аппрув, CODE/RUN/разбор — отдельным заходом.

## Колонка покрытия в манифесте

Манифест покрытия (`.claude/tests/{testType}/{source}/coverage-manifest.md`)
несёт **колонку статуса покрытия контуром** — чек-лист инварианта
полноты. Метки по стадии (цветные — эмодзи-кружок + слово):

*Адрес манифеста исправлен `GAPS_CLOSE_27` (F10 `DOCS_CHECK_27`): шесть
живых носителей адресовали его как `docs/integrations/{name}/coverage-manifest.md`
— такого файла не существовало. Манифест лежит рядом с планом, который
его потребляет, по тому же доводу, по которому туда переехал реестр
предусловий (`code-preconditions.md` §«Почему реестр здесь, а не в
`docs/`»).*

- 🔴 **не в плане** — in-perimeter запрос, ещё не покрыт планом;
- 🟡 **в плане** — кейсы в утверждённом/строящемся плане (этап DESIGN),
  код-тестов на **все** кейсы строки нет;
- 🟢 **в коде** — есть прошедшие ревью код-тесты **на все кейсы плана по
  этой строке** (этап CODE-тесты);
- ⚪ **не-runtime** — эндпоинт в периметре доков, но runtime фазы 1 его не
  вызывает: контракт держим справочно, покрытия контуром не требуем;
- **—** — вне периметра (не покрывается).

Прежняя метка ⚪ `coverage-gap` («в периметре, но клиент метод не
строит») снята: под `/raw` покрывается каждая in-perimeter строка
(`source-api-target-rebase.md`, раздел D). Метка ⚪ `не-runtime` — другая и
живая (строки `Fills 3d` / `Fills 3m`); в легенде она числится с
`GAPS_CLOSE_6`.

**Гранулярность метки — строка манифеста (операция/метод), не кейс.**
Колонка отвечает на вопрос «покрыта ли операция», а не «прогнан ли
кейс»: покейсное покрытие читается в плане контура, а полнота гейтящих
слотов — в реестре предусловий шага
(`.claude/tests/{testType}/{source}/code-preconditions.md`). Уровень
клейма называется явно, потому что метка стоит на строке, а читают её
как утверждение о периметре.

**Продвижение по стадиям** ведёт `tester` синхронно с этапами:
DESIGN покрыл метод → 🟡 в плане; код-тесты на **все** кейсы строки
прошли ревью → 🟢 в коде. Колонка — source-agnostic поверхность
инварианта: пустых in-perimeter строк без метки быть не должно.

**Откат метки обязателен, и он — часть того же продвижения.** Строка, на
которой появились **непокрытые** кейсы (прирост плана на уже покрытом
методе, новый содержательный кейс от чужого шага), возвращается
**🟢 → 🟡**; причина отката пишется в её «Примечание» поимённо — какие
именно кейсы. Без отката прирост невидим: метка ставится один раз и
навсегда утверждает покрытие, которого больше нет.

**«Непокрытый» ≠ «нет код-теста со своим идентификатором».** Кейс покрыт,
если выполнено **одно из двух**: (а) на него есть прошедший ревью
код-тест, либо (б) он **делегирован цепочке** — тело кейса в плане
начинается строкой `Покрыт <идентификаторы звеньев>`, и названные звенья
код-тестами покрыты. Делегирование — штатная форма плана (прямой кейс
write-операции часто исполняется звеном цепочки, а не отдельным
запросом), и грепом по идентификатору кейса оно **не видно**: покрывающее
звено несёт другой идентификатор. Проверка «нет код-теста» без этой
половины даёт ложные откаты — ровно это произошло при первом применении
правила: `M18.3`, `M20.2`, `M21.2` откатили строки, покрытые цепочками
`Cmarket` и `M19*.cancel`.

**Уровень механической проверки клаузы (б) назван.** Записанная команда
(`coverage-manifest.md` §Легенда) проверяет **наличие** строки
`Покрыт …`, но не то, что названные звенья действительно покрыты
код-тестами. Механически вторая половина не выражается: план пишет звено
как `M19trailing.cancel`, тест — как `M19.trailing`, и греп по имени
звена даёт ноль. Поэтому вторая половина — **предмет ревью** (`tester`
пишет делегирование, `reviewer` на `test-review` проверяет, что звено
существует и покрыто), а не предмет грепа. Клейм команды сужен до
проверяемого: она отделяет делегированные кейсы от вовсе непокрытых, а
не подтверждает делегирование.

Класс, на котором правило записано (F5 `DOCS_CHECK_28`): манифест OKX
стоял на 100 % 🟢 при **16** непокрытых кейсах плана, из них 9 — гейтящих
`CODE`.

**Раздел без таблицы — дефект манифеста, а не «нечего покрывать».**
Манифест читается как поверхность полноты; пустой раздел утверждает
полноту, которой нет, и **клейм полноты его не видит**: «пустых строк
нет» выполняется у раздела без строк тривиально.

**Целостность манифеста проверяется инвентарём, а не процентом.** Тело
манифеста — перечень операций; у перечня контролируется **число
объектов**, а не объём текста. Проверка — две оси, обе поднимают дефект
до кода возврата:

```bash
M=.claude/tests/source-api/okx/coverage-manifest.md
P=.claude/tests/source-api/okx/plan.md
# (а) раздел-эндпоинт с заголовком, но без таблицы
awk '/^## /{ if (sec!="" && rows==0 && sec ~ /\(`\/api\/v5\//) print "ДЕФЕКТ: раздел без таблицы — " sec
            sec=$0; rows=0; next }
     /^\| /{ rows++ }
     END { if (sec!="" && rows==0 && sec ~ /\(`\/api\/v5\//) print "ДЕФЕКТ: раздел без таблицы — " sec }' "$M"
# (б) инвентарь: пути in-perimeter строк манифеста == пути методов плана
awk -F'|' '/^\| / && NF>=7 { v=$5; gsub(/^[ \t]+|[ \t]+$/,"",v)
    if (v=="Покрытие"||v=="—") next
    p=$3; gsub(/^[ \t]+|[ \t]+$/,"",p); gsub(/`/,"",p); sub(/^[A-Z+]+ /,"",p); print p }' "$M" | sort -u > /tmp/m.paths
grep -oE '^## [A-Za-z]+[0-9]+\..*(GET|POST\+GET|POST) /api/v5/[a-z-]+/[a-z-]+' "$P" \
  | grep -oE '/api/v5/[a-z-]+/[a-z-]+' | sed 's|/api/v5||' | sort -u > /tmp/p.paths
diff /tmp/m.paths /tmp/p.paths
```

Обе оси молчат на действительном состоянии и обе срабатывают на
состоянии до `GAPS_CLOSE_28`: первая называет `## Trade` и
`## Public Data`, вторая перечисляет 28 пропавших эндпоинтов. Ось (б)
существенна отдельно от (а): она сверяет манифест с **внешним** для него
операндом (перечень методов плана), поэтому ловит и потерю строк внутри
непустого раздела, где ось (а) молчит.

**Прогонять — при переезде или переписывании манифеста и при заходе по
триггеру** (§Триггеры). Класс, против которого проверка заведена: рерайт
файла под целевой **процент** сокращения снёс две таблицы целиком,
заголовки разделов оставил, а собственный счётчик манифеста уехал вместе
с потерянным абзацем легенды — противоречить остатку стало нечему.
Факт, дату и провенанс держит сам пострадавший носитель —
`.claude/tests/source-api/okx/coverage-manifest.md`
§«Что было не так до 2026-08-30».

## Триггеры

- **новая биржа** — полный план по **всему in-perimeter периметру
  манифеста** через `/raw` (прямой кейс + негатив на каждый запрос +
  каждый вариант типа-дискриминатора); инвариант полноты сверяется по
  колонке покрытия манифеста;
- **новый эндпоинт** — точечное расширение существующего плана; новый
  in-perimeter запрос → требование покрытия;
- **изменение контракта** — регрессия затронутого;
- **разовый запуск по запросу пользователя.**

Гранулярность построения по триггеру — `test-design`
(§«Гранулярность по триггеру»).
