# Процесс: доукомплектация апидоков

## На какой вопрос отвечает этот файл

Как интеграционные доки внешнего источника доводятся до полного
покрытия продуктового периметра по официальной документации источника
и как сканируется поверхность API под потребителя.

## Назначение

Процесс приводит интеграционные доки источника
(`docs/integrations/{name}/`, `docs/models/integrations/{name}/`) к
**полному покрытию продуктового периметра**: дополняет существующие
доки и заводит недостающие по официальной документации источника,
фиксирует покрытие манифестом, затем сканирует поверхность API против
потребителя и предлагает, чем его дополнить. Владелец процесса —
`integrator` (`.claude/agents/integrator.md`).

Процесс **source-agnostic**: описывает последовательность, не специфику
площадки. Входные точки официального дока, command-relevant разделы,
конвенции и ограничения конкретного источника живут в **скилле
интеграции** этого источника (для OKX —
`.claude/skills/integration-okx.md`).

## Два скоупа

Процесс работает с двумя разными скоупами — не путать:

- **Продуктовый периметр** — границы докачки. Полное покрытие
  поверхности источника в пределах того, что нужно продукту (для
  торгового бота — Trading / Account / Market+Public data / Funding по
  потребности). Применяется к этапам докачки (шаги 2-4): покрываем
  **весь** периметр, не только текущий шаг роадмапа.
- **Скоуп текущего шага** — границы скана. Потребитель, под который
  ищем возможности (сейчас потребитель — command-layer шага 4).
  Применяется только к скану возможностей (шаг 5), не к докачке.

## Порядок

Жёсткий порядок: **корпус → манифест → скан → предложения**. Скан
возможностей и предложения — только **после** полного покрытия
периметра, подтверждённого манифестом. Сканировать частичный корпус
нельзя — предложения должны опираться на полную картину поверхности.

## Шаги

### 1. Вход — периметр и потребитель

На вход — (а) продуктовый периметр источника (что покрываем докачкой
полностью) и (б) текущий потребитель со скоупом шага (под кого сканируем
возможности). Периметр и состав «вне периметра» — содержательное
решение, при неоднозначности выносится на валидацию.

### 2. Манифест покрытия источника

Полная карта поверхности API источника — **все** разделы / группы
эндпоинтов официального дока, не только покрытые. Манифест — отдельный
док в папке источника (`docs/integrations/{name}/coverage-manifest.md`).
Каждая строка (раздел / endpoint) несёт **статус**:

- `есть-док` — уже задокументирован;
- `создан` / `обновлён` — заведён / дополнен в этом прогоне;
- `пробел` — в периметре, ещё не задокументирован (к заведению; если
  заведение в прогоне не выполнено — с причиной, напр. источниковый
  дефицит);
- `вне-периметра` — вне продуктового периметра, док не заводим (с
  причиной);
- `сознательно-вне` — в периметре, но отложено решением (с причиной и,
  если есть, якорем — открытый вопрос / шаг-владелец).

Полнота покрытия проверяется **по манифесту**, не на доверии: пустой
строки быть не должно — каждый раздел поверхности либо покрыт, либо
явно вне периметра / отложен с причиной.

**Провенанс каждой строки.** Источник правды — официальный док
источника. Сторонние списки эндпоинтов (SDK-клиенты, агрегаторы)
используются **только как скелет манифеста и для кросс-чека**, не как
факт. Каждая строка несёт провенанс:

- `офдок` — подтверждено официальной документацией источника;
- `сторонний` — пока только из стороннего источника, официальным
  доком не подтверждено (кандидат на подтверждение или на статус
  «требует подтверждения»).

Расхождение «сторонний vs официальный док» (путь, метод, наличие
эндпоинта) — **находка**, не молчаливый выбор в пользу одного из них.

### 3. Сверка с официальным источником и докачка (полное покрытие)

По манифесту — сверка с официальной документацией и докачка **всего
периметра** (не скоупа шага):

- **дополнить** существующие доки недостающими полями / endpoint'ами /
  лимитами / семантикой;
- **создать недостающие** — контракты, нативные модели, правила
  источника.

Содержание дистиллируется из официального дока и несёт **указатели на
его разделы** (дисциплина пометки `integrator`: «официальный док
говорит» с указателем vs «предполагаю»). При конфликте «свежий
официальный док vs наш док/архив» — побеждает официальный док,
расхождение оформляется правкой/находкой. **Неподтверждаемое** чистым
чтением официального дока — оформляется находкой «требует
подтверждения», в док как факт не пишется.

### 4. Размещение — через куратора

Интегратор предлагает содержание; раскладку по структуре
(`docs/integrations/{name}/...`, `docs/models/integrations/{name}/`),
именование, раздел «На какой вопрос отвечает» выполняет
`knowledge-curator` штатным потоком размещения. Фактологическая
дистилляция (поля, endpoints, лимиты с указателями) на ступени
Предложение ложится в доки напрямую через куратора — это перенос факта,
не выбор; неоднозначное/конфликтное идёт на валидацию.

### 4a. Самоподдержка актуальности (свежесть корпуса)

Корпус — дистиллят волатильного источника; актуальность
поддерживается перевыкачкой, не хранением выгрузок:

- **Когда:** при каждом заходе интегратора по источнику и по явной
  задаче «актуализируй».
- **Как:** перевыкачка официального дока (канал чтения — в скилле
  источника) + дифф против манифеста и затронутых доков. Сырая
  выкачка — временный рабочий материал прогона, в репозиторий не
  коммитится (решение B — `.claude/decisions/integrator-agent.md`
  §Канал и хранение).
- **Дрейф фактов** (поле/путь/лимит изменились) — правка дока;
  **дрейф выборов** (изменение, затрагивающее принятое решение) —
  предложение на валидацию по ступени.
- **Шапка синхронизации:** каждый интеграционный контракт-док несёт
  раздел «Внешний источник правды» (источник, процедура синка, дата
  последней сверки) по правилу
  `.claude/rules/external-source-sync.md`; дата обновляется при
  сверке.

### 5. Скан возможностей (после полного корпуса)

Только после того как корпус полон и зафиксирован манифестом — сверка
**потребителя** по скоупу шага (сейчас — command-layer) против **полной**
поверхности API из манифеста: какие операции/поля/режимы площадка
предоставляет, но потребитель не использует. Результат — предложения
«чем ещё дополнить» в формате **Предложения**, на валидацию (не
финализируются интегратором).

**С уважением к принятым решениям.** Отвергнутые альтернативы не
перевыносятся без новой фактуры источника: отвергнутое по
вкусу/scope-решению (пример — CMD-Q3: bulk-refresh-команды сняты
сознательно) возвращается только при появлении новой фактуры, не как
пересмотр уже сделанного выбора. Скан опирается на неиспользуемую
возможность API, а не на ревизию решённого.
