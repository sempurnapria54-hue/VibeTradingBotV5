# Исполнение шага роадмапа (docs-first)

## На какой вопрос отвечает этот файл

Как устроен процесс исполнения одного шага продуктового
роадмапа.

## Назначение

Процесс описывает последовательность под-шагов, через которые
проходит каждый шаг роадмапа от старта до завершения. Подход —
**docs-first**: концепция в `docs/` доводится до целостности
**до** написания кода; код пишется по проработанной концепции и
при отклонении синхронизирует доки.

## Под-шаги

Один шаг роадмапа исполняется по следующей последовательности.

### 1. Tooling (создать агенты/скиллы под потребность)

Если для исполнения шага нужны новые агенты, скиллы или процессы
— создаются здесь. По потребности шага, не превентивно. Если
ничего нового не нужно — под-шаг проходится без артефактов.

**Статус шага:** `TOOLING`.

### 2. Проверка целостности концепции доков

Сквозной обход документации, релевантной шагу: модели, lifecycles,
процессы, правила, словарь. Цель — найти пробелы в концепции
(несогласованности, пустоты, неотвеченные вопросы), которые
помешают писать корректный код.

Помимо концептного фокуса (`concept-review`) проверка включает
**торговый фокус** (`trading-review`) — адверсариальный проход по
торговой корректности модели. Торговые находки — отдельная
категория пробелов в том же gap-отчёте, не отдельная петля (см.
«Торговая категория в петле» ниже).

**Статус шага:** `DOCS_CHECK_N`, где N — номер итерации (1, 2, ...).

### 3. Закрытие пробелов концепции

По каждому найденному пробелу: открытый вопрос (если ещё не
заведён) → обсуждение → решение → правка доков.

**Закрытие находки — по её собственному списку цитат.** Закрытие
любой находки `DOCS_CHECK_N` обязано пройти по списку цитат самой
находки из отчёта и отметить каждую цитату: правлено / не требует
правки — почему. Это отдельный явный шаг закрытия, не отчёт «по
узлу»: перечень носителей берётся из отчёта, а не собирается
заново. Список цитат — обязательное поле каждой находки
(`.claude/templates/docs/gap-report.md` §«Набор полей находки»).

**Отчёт закрытия называет по каждой находке, кто фактически ответил.**
Поле заполняется на закрытии, потому что в отчёте прогона его нет по
построению: прогон **находит**, отвечает **закрытие**
(`.claude/templates/docs/gap-report.md` §«Набор полей находки»,
`.claude/skills/design-fork.md` §4). Это вход сверки «ожидаемый владелец
= ответивший»: расхождение — сигнал мис-роутинга, и сводится оно в
дайджесте `GAPS_CLOSE_N`
(`.claude/chat/chat-project-instructions.md`), а не прогона, где вторая
сторона сверки отсутствует.

**Сверка «ожидаемый = ответивший» ведётся пофайндингово, против ярлыка
дефицита.** Ключ сверки по каждой находке — её собственный ярлык дефицита
из отчёта прогона: `подтверждение` (величину, scope или продуктовое
намерение неоткуда взять, кроме как у пользователя) ⇒ ожидался
**пользователь**; `работа` / `грунт` ⇒ ожидался **штатный владелец** по
карте. Сводная формулировка в прозе («мис-роутинга нет — все находки с
дефицитом `подтверждение` ушли пользователю, остальные штатным
владельцам») сверкой **не является** и её не заменяет: она проверяема
только пересчётом по телу — как и счётные строки сводки прогона
(`.claude/templates/docs/gap-report.md` §«Структура отчёта»). Сводка,
расходящаяся с собственной пофайндинговой таблицей, — **дефект отчёта**.

Кейс, на котором записано: отчёт закрытия утверждал «мис-роутинга нет —
все находки с дефицитом `подтверждение` ушли пользователю», тогда как
ярлык `подтверждение` стоял на **семи** находках прогона, а пользователю
ушли **семнадцать**; десять из них несли дефицит `работа`, то есть
проектный ход владельца. Расхождение видно только пересчётом — в прозе
формула выглядела состоятельной.

**Ответивший называется ролью — тем же словарём, что ожидаемый владелец:**
роль из карты владельцев (`.claude/processes/question-delegation.md`) либо
**пользователь**. Ответ, фактически произведённый CC, называется **ролью, в
которой CC отработал** — чью работу он выполнил, — а не словом «CC».
Категория «CC» роли не называет, поэтому сверка «ожидаемый = ответивший»
на ней невыполнима: сравнивать не с чем, и мис-роутинг не детектируется ни
в одну сторону. Кейс, на котором записано: в отчёте закрытия ответивший
назван категориями «пользователь / CC», ожидаемый владелец — ролью, и
сверка владельцев (стадия, ради которой дайджест закрытия и существует)
оказалась выполнима на трёх позициях из двадцати девяти.

**Флаг действия CC ставится и в отчёте закрытия — по каждой позиции.**
Набор значений тот же, что в отчёте прогона (`предложил` /
`финализировал` / `завёл открытый вопрос` / `эскалировал`;
`.claude/templates/docs/gap-report.md` §«Флаг действия CC»), плюс значение
**`разместил в рамках принятого`** — для случаев именования и размещения,
где решение уже принято, а CC выбирает только носитель и имя. Эти случаи
обязаны **отличаться** от финализации, а не сваливаться с ней в одну
категорию. Без флага молчаливая финализация детектируется только
вычитыванием прозы исходов: аудиту автономии на стадии закрытия опереться
не на что — при том что расходуется автономия именно на закрытии. Позиция
без флага не отчитана, как и в прогоне.

**`разместил в рамках принятого` не покрывает выбор — разделитель по
однозначности исхода.** Значение означает **размещение** и валидации не
ждёт, поэтому граница проходит не по тому, «внутри принятого решения ли
работа», а по тому, **определяет ли решение держателя исход однозначно**:

- решение определяет исход однозначно, CC выбирает только носитель, имя
  и место — **`разместил в рамках принятого`**, валидации не требует;
- решение оставляет альтернативы, и CC выбирает из них — **`предложил`**,
  позиция **ждёт валидации** и идёт в счёт гейта делегирования наравне с
  остальными предложениями.

Формула «хвост внутри принятого решения» разделителем **не является**:
хвост принятого решения бывает и однозначным, и развилочным, и второе
регулярно проходит под флагом размещения — то есть выбор попадает в
канон, не будучи ни разу предъявлен на валидацию. Признак развилки тот же,
что в `.claude/processes/question-delegation.md` §«Калибровка: что выдаёт
живую развилку»: названы альтернативы, не отметаемые принципом.

Кейс, на котором записан разделитель: в одном закрытии под флагом
размещения прошли выбор формулировки определения величины из двух
названных опций, состав реакции при нерезолвимом операнде (включая
решение **не** поднимать биржевой холд) и назначение ветки «предикат
селекции дал не ровно один элемент» — три выбора среди альтернатив,
поданные как размещение.

**Правка, выходящая за находку на уровне решения, помечается флагом
«расширение» — в момент правки.** Выход за список цитат уже отмечается на
уровне **файла** («вне списка цитат») и так и остаётся. Не отмечался
уровень **решения**: правка, которая **снимает или назначает правило**, а
не проводит уже принятое, в строке исхода ничем не отличалась от
остальных.

Признак, по которому расширение опознаётся: правка снимает действующую
политику **как следствие** решения, принятого про другое, — форма «раз
выбрано X, то Y больше не выразимо, значит Y снимается». Это крен среди
альтернатив, поданный как вывод на принципе, и он обязан быть видимым
**сразу**, а не при аудите. Рядом с флагом — **одна строка о том, из чего
следствие выведено**.

Оба флага — действие CC и «расширение» — про **видимость в момент
действия**, а не про пересмотр задним числом: аудиту, которому нечего
читать, остаётся реконструкция, а реконструкция и есть то место, где
итерация теряет время.

**Оба флага — обязательные поля отчёта закрытия, на каждой позиции.**
Требование то же, что уже действует для ярлыка исхода, целевого дока и
крена в отчёте прогона (`.claude/templates/docs/gap-report.md`), и
распространяется на закрытие целиком: пустое поле — **дефект отчёта**, а
не «неприменимо». Отсутствие расширения записывается **явно**
(«расширения нет — правка проводит принятое»), как и отсутствие развилки в
прогоне. Молчание в этих двух полях неотличимо от пропуска, а цена у
пропуска несимметричная: снятая политика и молчаливая финализация видны
только по флагу, и без него обнаруживаются следующим прогоном как находка.

Кейс, на котором записана обязательность: в одном закрытии флаг действия
стоял на **пяти** позициях из двадцати одной, а флаг «расширение» — один
раз при **четырёх** непомеченных кандидатах (сужение ратифицированной
клаузы о субъекте состояния на радиусе биржи — в тексте названо
«сужена», флага нет; снятие довода, которым держалась прежняя топология;
назначение области действия единой нормы длин — «прежние миграции не
ретрофитятся»; назначение ветки нерезолвимого предиката).

**Политикоменяющее закрытие завершается свипом по терминам старой
политики.** Если закрытие **меняет политику** (снимает или заменяет
правило, а не доуточняет структуру), список цитат находки — необходимый,
но **не достаточный** вход. Такое закрытие обязано завершиться
**свип-грепом по терминам снимаемой политики** по **всем живым
носителям** — `docs/` **и** рабочим файлам (`.claude/work/backlog.md`,
`open-questions.md`, `questions/tasks/*`, roadmap `phase-N.md`,
`progress/`), — с **отметкой каждого попадания** в отчёте: правлено /
не требует правки — почему. Термины берутся из **снимаемой** формулировки
(её ключевые слова), а не из новой, и их обычно **несколько**: политика
живёт в нескольких словах (например «kill-switch» и «ручное снятие» —
два разных термина одной снятой реакции).

**Терминологический свип отчитывается пофайловой таблицей — той же формы,
что структурный.** По каждому свипу: перечень терминов, по которым шёл
греп, и таблица «файл (§секция) → исход» с отметкой **каждого** попадания
грепа — правлено (что именно) / не требует правки — почему. Вывод-итог
(«живых попаданий не осталось», «все носители приведены») таблицу **не
заменяет**: по нему не видно ни какой файл осмотрен, ни что в нём
изменилось, то есть он непроверяем — а непроверяемая отметка равна
отсутствующей (§«Исполненное правило от неисполненного отличается следом в
отчёте» ниже). Итог остаётся, но строкой **под** таблицей.

Кейс, на котором записана форма: требование действовало, а пофайлово
отчитан был **один** свип из пяти — остальные четыре несли только вывод
«живых попаданий оси не осталось».

**Свип покрывает и доки уровня, на который переехала собственность.**
Когда закрытие переносит владение чем-либо на другой уровень (перечень
команд — с handler'а на действие, метрику — с одного компонента на
другой), свип обязан покрыть **оба** конца переноса: носители, откуда
собственность ушла, **и** носитель уровня, куда она пришла. Свип «по
терминам снимаемой политики» первый конец находит сам, второй — нет: на
принимающем уровне старых терминов может не быть вовсе.

Кейс (H3 `DOCS_CHECK_10`): закрытие H3 `GAPS_CLOSE_9` записало принцип
«состав команд-звеньев — собственность действия, не handler'а» и вычистило
перечни из **семи** handler-доков — но не дошло до дока самого действия
(`SystemActionExecutor.md`), где осталась клауза «состав конкретного цикла
задаёт handler-контекст», то есть ровно отменённая топология в носителе
принимающего уровня. Три линзы следующего прогона подняли это как гейт.

**Правка, вводящая поле или тропу чтения, завершается свипом по
структурным носителям.** Существующие свипы — «по терминам снимаемой
политики» и «по уровню, на который переехала собственность» — ищут
**текст**. Поле, которого нет, текстом не находится по определению:
недостаёт **структуры**. Поэтому закрытие, которое вводит поле, колонку,
операнд или тропу чтения, обязано пройти по фиксированному перечню
структурных носителей и отметить каждый:

- §Структура доменной модели;
- §Персистентность (тип, nullability, ключи, индексы);
- **schema-дельта шага** (перечень, который сам себя объявляет полным);
- состав `*ExternalSnapshot` и used/unused нативного инвентаря источника;
- mapping-таблицы (native → snapshot → domain), включая счёт цепочки;
- инвентарь **читателей** у владельца данных (кто теперь читает и через
  что), если введена тропа чтения.

Признак применимости — закрытие называет новое имя (`plannedEntryPrice`,
`rateStatus`, `externalInstrumentId`) либо фразу «резолвится через …».
Кейс, на котором правило записано: прогон, где **восемь из восьми**
гейтящих находок оказались класса «решение ратифицировано, довод есть,
владелец есть, целевой док есть — а поля, писателя, тропы чтения или
операнда нет», и **три** из них нарушали правило, записанное тем же
прогоном, который их внёс.

**Структурный свип отмечается пофайлово в отчёте закрытия — отдельным
разделом, симметрично терминологическому.** Отчёт `GAPS_CLOSE_N` несёт
§«Свипы по структурным носителям» рядом с §«Свипы по терминам снимаемой
политики»: по каждому свипу — что вводится правкой, перечень пройденных
носителей и исход **по каждому** (правлено / не требует правки —
почему). Структурных правок в итерации не было — это пишется явно;
отсутствующий раздел читается как «не применимо», а не как «не
проведено».

**Отдельный проход — по носителям с клеймом полноты**, затронутым
правкой. Клейм полноты — формулировка, которая сама объявляет перечень
исчерпанным: «счёт цепочки N = N = N», «четыре суммы», «перечень
закрытый», «перечень сквозной», «это и есть единственное, что выходит».
Такой носитель не просто отстаёт после правки — он **запрещает**
писателю искать дальше, превращая пропуск в инструкцию. Поэтому клеймы
проходятся списком и отмечаются поимённо, а не покрываются попутно
внутри свипа по структуре.

**Исполненное правило от неисполненного отличается следом в отчёте.**
Свип без пофайловой отметки считается непроведённым — как и
терминологический: правило, существующее без следа, ничем не отличается
от пропущенного, и это уже воспроизводилось.

Кейс, на котором записана отчётность: прогон, где терминологические
свипы были отмечены пофайлово **шесть раз**, а структурных не
задокументировано **ни одного** — при том, что правило структурного
свипа действовало. Цена — **восемь** находок одного класса «перечень,
объявляющий себя полным, не пересчитан после правки»: счёт цепочки
маппинга, реестр областей суммирования, реестр предусловий `CODE`,
закрытый перечень зовущих сервис, клейм «производителей такого рода в
шаге нет», §Персистентность двух новых таблиц, реестр граничных
снапшотов, mapping-таблица сущности. Терминологический свип ищет
**текст** и недостающую **структуру** не находит никогда — поэтому один
проведённый свип не засчитывается за другой.

**Отложенный хвост проверяется на сцепленность с тем, что шаг
поставляет.** Прежде чем отложить хвост на следующий шаг, проверяется:
не зависит ли от него артефакт, который поставляет **текущий** шаг. Два
хвоста, отложенных порознь, могут вместе обнулять guard, вводимый сейчас
— и тогда шаг отгружает мёртвый механизм, считая его работающим.

Признак: хвост отложен, но артефакт, который от него зависит, входит в
дельту **этого** шага. Обратная сторона того же правила: починка одного
из сцепленных хвостов может **немедленно активировать** второй, который
до неё был теоретическим, — поэтому при закрытии хвоста проверяется, что
именно он оживляет.

**Разведочный режим guard'а называет условие выхода и его носителя.**
Если шаг отгружает контроль с заведомо пустым конфигом, порогом «по
умолчанию» или неоткалиброванной величиной, закрытие обязано назвать:
**что** выводит его из разведочного режима, **кто/что** это фиксирует и
**к чему привязан срок** (гейт `CODE`, прогон, шаг роадмапа). «Проявится
само» описывает **процедуру разведки**, а не режим работы: без условия
выхода разведочный режим становится постоянным, а контроль,
срабатывающий на каждом объекте, эквивалентен погашенному.

**Ревизия used/unused инвентаря источника сверяется с правилом
`Auditable`.** Поля времени создания и обновления, отдаваемые источником,
в unused не выводятся — у них структурный носитель, а не прикладной
потребитель, и обычный критерий «потребителя нет» к ним неприменим.
Правило и кейс — `docs/models/domain/other/Auditable.md` §«Ревизия
инвентаря источника»; читается ролью-владельцем инвентарей
(`.claude/agents/integrator.md` §Компетенция).

**На слепой проход выносится только то, у чего есть пользовательский
хвост.** Находка, в которой пользователь не участвует — дефицит `работа`
или `грунт`, владелец штатный (`solution-designer` / `integrator` /
`code-writer` / `knowledge-curator`), — **на проход не выносится**: она
идёт владельцу, к пользователю возвращается **результатом**. Ярлык
`варианты-с-креном` сам по себе основанием для выноса **не является** —
он говорит, что развилка есть, а не что она пользовательская;
пользовательской её делает ярлык дефицита `подтверждение` (величину, scope
или продуктовое намерение неоткуда взять, кроме как у пользователя).

Цена ошибки в обе стороны разная и обе реальны: невынесенное
пользовательское решение закрывается за пользователя (потеря — та, ради
которой заведён слепой проход), а вынесенное **не**-пользовательское тратит
проход пользователя на работу владельца и создаёт видимость, будто выбор
был продуктовым.

**«Не выносится» — про очередь, не про исключение навсегда.** Находка со
штатным владельцем на проход не выносится **до** проработки владельца;
после неё она возвращается к пользователю **на валидацию** результата, и
на ступени `Предложение` эта валидация и идёт слепым проходом — против
выбора владельца как ключа сверки. Порядок: находка → владелец →
проработка (решение либо варианты с выбором) → слепой проход → сверка.
Развилка без штатного владельца (дефицит `подтверждение`) идёт
пользователю **напрямую**: сверять проходу не с чем, и проход по ней не
нужен. Поведенческий слайс для чата — правила «Делегирование развилок по
владельцам» и «Слепой проход по вопросам и сверка пакетом» в
`.claude/chat/chat-project-instructions.md`; счётное следствие — ответы,
полученные без проработки владельца, в счёт гейта не идут ни в одну
сторону (`.claude/processes/question-delegation.md` §«Гейт повышения»).

Кейсы (`GAPS_CLOSE_10`, шаг 7 фазы 1): H11 (носитель курса cross-ccy)
вынесена **ошибочно** — дефицит `грунт`, владелец `integrator`, и
пользователь ответил догадкой, а не решением; H19 и H23 тем же фильтром
**отсеяны** правильно (правило переноса таблицы и тип колонки — работа
владельца, ярлык `варианты-с-креном` при этом стоял у обеих).

**Владелец, помеченный «первым», отрабатывает до выноса находки на
решение.** Пометка «первым» (`.claude/templates/docs/gap-report.md`
§«Ожидаемый владелец») — про **порядок**, а не про состав адресатов:
названный ею владелец проверяет посылку находки **до** того, как находка
попадёт на решение, а не после него. Находка, чью посылку назначенный
владелец не проверил, выносится в проход **помеченной непроверенной**, а
не как готовая развилка: у готовой развилки посылка установлена, и
пользователь выбирает из вариантов, а не из вариантов плюс неизвестного
грунта.

Кейс: находка несла дефицит `грунт`, ушла на решение как готовая развилка,
а сверка назначенного владельца отложилась на после — то есть дефицит был
зафиксирован в отчёте и при выносе проигнорирован.

**Невалидированный крен переживает закрытие итерации.** Крен находки,
который на `GAPS_CLOSE_N` не был ни принят, ни отвергнут (остался
предложением в §«Не закрыто»), **переносится в отчёт следующей итерации**
явной строкой — с пометкой, что носители под него не правились. Иначе
находка воспроизводится по построению, а прогон тратится на её
переоткрытие.

Кейс (H2 `DOCS_CHECK_10`): крен H8 `DOCS_CHECK_9` (предикат эмиссии
bills-звена) остался невалидированным, носители не тронуты — и две
независимые линзы следующего прогона пришли к тому же варианту заново.

Кейс, на котором правило выведено (H1 `DOCS_CHECK_6`, шаг 7 фазы 1):
закрытие H2 `GAPS_CLOSE_5` сняло kill-switch с тропы несвежести и прошло
по списку цитат находки корректно — но свип «сверх списка» шёл **по
одному термину и только по `docs/`**. В результате отвергнутую политику
пронесли два носителя вне списка: хвост решения
(`pnl-finalization-mechanics.md` реш.4) и **CODE-инструкция в
`backlog.md`** — то есть прямое предписание исполнителю следующего
под-шага. Три независимые линзы подняли это на следующем прогоне.
Диагноз структурный: список цитат описывает **известных** носителей
дефекта, а политика расползается по носителям, которых линза не читала;
рабочие файлы при этом опаснее доков — они адресованы исполнителю.

Кейс, на котором выведено правило закрытия по цитатам (шаг 7 фазы 1): класс дефекта
«обоснование верно для части носителей, а дано безусловно»
повторился три прогона подряд — `GAPS_CLOSE_3` («seam не двинулся»
— ложно для `RiskValidator`), `GAPS_CLOSE_4` («испарился» — ложно
для писателя статуса; «закрыт» — второй носитель не тронут;
«индекс совпадает с ключом» — ложно по одной из осей; ось
категории приведена в модели и mapping, но не в native). Диагноз
структурный, не «невнимательность»: закрытие отчитывалось по узлу,
а находка называет носители поимённо — перечень цитат самой
находки при закрытии не перепроверялся. Природа та же, что у
сборки эскалации по всем линзам узла
(`.claude/templates/docs/gap-report.md`): перечень надо брать из
отчёта, а не собирать заново.

**Статус шага:** `GAPS_CLOSE_N`, где N — номер итерации.

### 4. Итерация под-шагов 2-3

Чередовать проверку и закрытие пробелов до тех пор, пока
проверка не пройдёт чисто (новых пробелов не выявлено). После
чистой проверки — переход к под-шагу 5 по гейту `CODE`
(см. «Гейты»).

**Сбор внешнего грунта не ждёт чистого прогона.** По умолчанию
проверочные прогоны против источника (контур
`.claude/processes/source-api-testing.md`) идут после чистого
`DOCS_CHECK` — перед `CODE`. Но находка, у которой **единственный**
блокер — ярлык дефицита `грунт` (не хватает внешнего факта, а не
проектирования и не решения пользователя), этим порядком образует петлю:
факт собирается после чистого прогона, а прогон без факта чистым не
станет. Такие находки выносятся на сбор грунта **сразу**, не дожидаясь
чистоты остальных: их закрытие ничего в концепции не двигает, оно только
подставляет недостающее число или подтверждает поведение источника.

Признак петли: находка несёт `грунт` **без** сопутствующего `работа` или
`подтверждение`. Несёт вместе с ними — грунт собирается в общем порядке
(сначала проектное решение, потом проверка его посылок).

Кейс (`DOCS_CHECK_10`, шаг 7 фазы 1): четыре находки ждали рантайм-факта
источника (оси адресации истории позиций; инвентарь типов bill; поведение
`realizedPnl` при cross-ccy-издержке; эндпоинт котировки), при том что
сама фикстура была запланирована «после чистого прогона». Порядок при этом
**нигде не был записан** — он накопился практикой и в носители процесса не
попадал; правило вводится вместе с исключением.

### Торговая категория в петле (под-шаги 2-4)

Торговые находки (фокус `trading-review` роли `reviewer`) идут той
же машиной `DOCS_CHECK_N` / `GAPS_CLOSE_N` — отдельная категория
находок, не отдельная петля.

- **Приоритет по тяжести, не по категории.** Торговые находки
  ложатся в существующие оси: блокирующее / неблокирующее,
  содержательное / гигиена. Внутри содержательного торговое
  **ведёт**: его правки переформируют модель, поэтому после
  торговой правки концептная проверка прогоняется заново (рябь).
- **Гейтинг `CODE`.** Содержательно-блокирующее гейтит переход к
  `CODE`, включая ключевой кейс «модель не выражает нужное торговое
  правило» (жёсткий гейт). Гигиена / name-level / торговые заметки
  на будущие фазы — не гейтят.
- **Два касания торговли во времени:**
  - *конструктив* — торговый специалист
    (`.claude/agents/trading-specialist.md`) по ходу
    проектирования: на торговой развилке отвечает и предлагает
    торгово-обоснованные варианты (front-load, чтобы не закреплять
    торгово-наивные решения);
  - *критика* — торговый фокус ревьюера в петле: адверсариальный
    проход, валидирует результат, в том числе предложенное
    специалистом и выбранное пользователем (независимость от
    автора).
- **Применение — по текущему шагу роадмапа**, изолированно.
  Forward-находки, упирающиеся в ещё незрелые шаги, паркуются как
  **cross-cutting** — поднимаются рано, не решаются до своего шага
  (штатно — открытый вопрос с пометкой шага-владельца).

### 5. Код

Пишется код по проработанной концепции: написание (`code-writer`)
+ ревью-итерации адверсариального ревьюера по фокусам
(`conventions` / `performance` / `disaster`; фокус `security`
деактивирован до шага «Безопасность» Фазы 1, см.
`.claude/skills/security-review.md`) + аппрув.
Синхронизация доков в этот под-шаг **не входит** — она вынесена в
отдельный под-шаг `SYNC_DOCS_FROM_CODE` (ниже): пока код не
утверждён, неясно, к чему приводить доки.

Аппрув `CODE` — зафиксированный исход адверсариальных фокусов, не
устное согласие (см. «Гейты»).

**Статус шага:** `CODE`.

### 6. Синхронизация доков под утверждённый код

После аппрува `CODE` доки приводятся к утверждённому коду.
Направление — **docs←code**: утверждённый код считается истиной
(вопрос «код или доки неверны» снят аппрувом). Сверка полная:
добавления, изменения, удаления. Проход одиночный (без `_N`):
аппрув уже зафиксировал истину, итерировать не по чему.

Внутри под-шага:

- **детект расхождений** — фокус `divergence` адверсариального
  ревьюера (`.claude/skills/divergence-review.md`): список
  add / change / remove;
- **реконсиляция** — `knowledge-curator`: добавления идут штатным
  потоком размещения; изменения и удаления —
  `.claude/skills/reconcile-knowledge.md`.

**Аппрув `SYNC_DOCS_FROM_CODE` — зафиксированный исход `divergence`.**
Синхронизация считается выполненной, только когда `divergence`-фокус
адверсариального ревьюера **прогнан с зафиксированным исходом** (список
add / change / remove в отчёте) и расхождения реконсилированы. «Доки ок
на глаз» / сверка автором синхронизацией **не является** — детект
расхождений ведёт независимый фокус, не автор кода.

**Статус шага:** `SYNC_DOCS_FROM_CODE`.

### 6a. Пост-хок концепт-гейт для CODE-инкрементов

**Концепт-инкремент, въехавший через CODE, требует пост-хок
концепт-гейта.**

Концепт/контракт-инкремент — новая семантика контракта или модели
сверх утверждённой концепции шага; признак: сопровождается решением с
обоснованием или закрывает ранее открытый концепт-пробел (а не просто
добавляет поля). В норме такой инкремент проектируется
(`solution-designer`) и проходит концепт-гейт (`DOCS_CHECK`) **до**
CODE.

Если инкремент по необходимости вошёл уже на под-шаге CODE — он
миновал концепт-гейт: `DOCS_CHECK` идёт по докам *до* CODE, а на
`SYNC_DOCS_FROM_CODE` активен только `divergence` (механическая сверка
код↔доки, концепт не проверяет).

**Remedy:** после `SYNC_DOCS_FROM_CODE`, когда доки приведены к коду,
прогнать `concept-review` по обновлённым докам — прежде чем шаг уходит
в `DONE`. Концепт ревьюится на доках, раз на коде его проверить нельзя.
Прогон идёт по машине под-шагов 2-3: найдены пробелы — закрыть узким
`GAPS_CLOSE` и перепрогнать, пока концепт-проверка пост-sync доков не
пройдёт чисто; только тогда шаг уходит в `DONE`.

**Применимость — по наличию концепт-инкремента.** Если на CODE вошли
только поля/механика без новой контрактной семантики (нет
сопровождающего решения и не закрыт концепт-пробел) — пост-хок гейт не
нужен, `SYNC_DOCS_FROM_CODE` → `DONE` напрямую. Признак-триггер —
решение с обоснованием или закрытый концепт-пробел, въехавшие на CODE.

**Статус шага:** прогон ведётся как `DOCS_CHECK_N` (concept-review по
пост-sync докам), при находках — `GAPS_CLOSE_N`; продолжает сквозную
нумерацию итераций шага.

### 7. Завершение шага

После того как код утверждён, доки синхронизированы **и пройден
пост-хок концепт-гейт** (§6a, если на CODE вошёл концепт-инкремент) —
шаг переходит в `DONE` по гейту `DONE` (см. «Гейты»).

**Статус шага:** `DONE`.

## Гейты

Канон гейтов процесса; под-шаги 4, 5 и 7 ссылаются сюда.

**Гейт `CODE` — чистый `DOCS_CHECK`.** Статус шага не переводится на
`CODE`, пока соответствующий прогон `DOCS_CHECK` не прошёл **чисто**
(без открытых находок и расхождений). Чистый проход `DOCS_CHECK` —
обязательное условие гейта концепции. Прогон не чист → шаг остаётся в
пред-`CODE` статусе до закрытия находок (узкий `GAPS_CLOSE_N`) и
повторного чистого прогона.

**Аппрув `CODE` — зафиксированный исход фокусов, не устное согласие.**
Аппрув под-шага `CODE` — это **не** «ок» от `code-writer` (автора),
самопроверки на глаз или устного согласия пользователя, а **прогнанные
адверсариальные ревьюер-фокусы** (`conventions` / `performance` /
`disaster`) **с зафиксированным исходом** (отчёт фокуса в истории шага)
**и закрытыми находками**. Независимость обязательна: автор кода свой код
не аппрувит. Без зафиксированного исхода фокусов под-шаг `CODE` не
завершён, как бы ни выглядел код «на глаз».

**Гейт `DONE` — зафиксированный исход адверсариального ревью.**
Статус **не** переводится в `DONE`, пока не выполнены **все** условия
с **зафиксированным исходом** (отчёты фокусов в истории шага), а не
устным согласием автора/пользователя:

1. аппрув `CODE` пройден (фокусы прогнаны независимым ревьюером,
   находки закрыты — см. выше);
2. `SYNC_DOCS_FROM_CODE` — `divergence`-фокус прогнан, расхождения
   реконсилированы (аппрув под-шага 6);
3. пост-хок концепт-гейт §6a пройден (если на `CODE` въехал
   концепт-инкремент).

Нет зафиксированного исхода любого из них → шаг **остаётся в пред-`DONE`
статусе** до прогона фокуса и закрытия находок. Устное «ок» гейт не
закрывает. Если шаг уже помечен `DONE` мимо этого условия — статус
**откатывается** в пред-`DONE` до фактического прохождения гейтов
(статус отражает реально пройденное, не намерение).

## Фиксация статуса — часть каждого под-шага

Завершение **любого** под-шага включает перевод статуса шага в
роадмапе через `.claude/skills/update-roadmap-progress.md` (новая
итерация / следующий под-шаг / шаг закрыт). Под-шаг **не считается
завершённым**, пока статус не проставлен в `phase-<N>.md` и не
пересчитан ролляп фазы в `roadmap.md`.

Это часть работы под-шага, не отдельное напоминание и не действие «по
сигналу»: закрыл под-шаг (например, выпустил gap-отчёт `DOCS_CHECK_N`
или закрыл эскалации `GAPS_CLOSE_N`) — сразу прогнал
`update-roadmap-progress`. Производящий артефакт скилл (фокусы
`reviewer`, `code-writer` и т. п.) сам статус не ведёт — оркестрацию
держит этот процесс.

Источник истины для статусов шага роадмапа. Скилл ведения

таблицы фаз в `.claude/work/roadmap/` ссылаются сюда.

`DOCS_CHECK_N` / `GAPS_CLOSE_N` обычно — под-шаги 2-3 (до CODE), но та
же машина переиспользуется **пост-CODE** как пост-хок концепт-гейт
(под-шаг 6a) для концепт-инкрементов, въехавших через CODE: прогон
идёт после `SYNC_DOCS_FROM_CODE` по приведённым докам, нумерация
итераций сквозная.

## Конец фазы

В конце каждой фазы — отдельные шаги **«Тесты»** и **«Фронт»**.
Оба исполняются по этому же процессу (docs-first), как любые
другие шаги. Зрелость фронта — атрибут самого шага (простой для
прогонов до архитектурного рубежа; полноценный после).
