# Написание код-тестов

## На какой вопрос отвечает этот файл

Как именно написать код-тесты (исполнитель прогона) контура тестов API
источника по утверждённому плану.

## Когда применять

Этап **CODE-тесты** процесса
`.claude/processes/source-api-testing.md` — после аппрува плана +
коллекции. Роль — `tester`.

## Назначение и границы

По **утверждённому** плану строятся `@SpringBootTest`-код-тесты —
**исполнитель** прогона контура (коллекция — ревью/аппрув-артефакт,
не исполнитель). Покрывают весь план: каждый кейс плана → код-тест.
Скилл **пишет** код-тесты; ревью — `reviewer` (`test-review`), прогон —
`test-run`. Скоуп — **сырьё** (сырой клиент + сырые DTO).

## Ключевые правила

- **Фреймворк — JUnit 5 + AssertJ** (существующий стек, прецедент —
  `src/test/.../integration/model/okx/response/*DeserializationTest`).
  `@SpringBootTest` с профилем `test` (demo-креды из Vault test).

- **Механика — тот же A2-passthrough, что и коллекция.** Код-тест бьёт
  в raw-passthrough (MockMvc / `TestRestTemplate` по поднятому контексту),
  получает **сырой** `OkxApiResponse<T>` / типизированный DTO, проверяет
  его AssertJ. Механика 1:1 с коллекцией — код-тест проверяет то же, что
  ревьюится в коллекции.

- **Расположение и изоляция.** Живые тесты — отдельным пакетом
  `src/test/java/.../integration/sourceapi/{source}/`, **не** смешивать с
  офлайн unit-тестами биндинга DTO. Метка `@Tag("source-api-live")`.
  Структура зеркалит коллекцию: один тест(-метод) = один кейс плана
  (метка кейса `N1`/`C1`/`A3` — в имени теста).

- **Профиль-гейт — структурный no-prod.** Код-тесты активны на
  **non-prod** и на **prod не идут** (гард по активному профилю: профиль
  prod → тест пропускается; любой другой → выполняется). Это не «opt-in
  off by default» — это структурное исключение prod (интерим, «пока»).

- **Создание реальных demo-сущностей.** Stateful-кейсы **создают**
  реальные сущности на demo (ордера/позиции/algo) — иначе stateful-
  запросы (getOrder / cancel / close-position) не проверить.

- **Teardown обязателен в каждом кейсе.** Каждый кейс оставляет биржу
  чистой: teardown по жизненному циклу (`@AfterEach` / try-finally),
  покрывает **все** созданные кейсом состояния (отмена/закрытие). После
  кейса — ни висящих ордеров, ни позиций, ни algo. Teardown идёт даже
  при провале тела теста.

- **Гейт достижимости.** Где сущность создать нельзя (архивные окна —
  `orders-history-archive`, `fills-archive`, ~30д-позиции) — прямого
  кейса нет (по плану), покрытие только негативом; отказ + причина
  отражены (план → отчёт).

- **Порядок прогона.** Дешёвый негатив без состояния — первым; затем
  цепочки по графу предусловий (упорядоченно — `@TestMethodOrder` или
  единый цепочечный тест).

- **Цена ордера — live с сырого `getTicker`, минимальный риск.** Ставя
  ордер, тест берёт live-цену сырым ticker и формирует заведомо
  неисполнимую цену (минимальный риск даже на demo).

- **Незадокументированное не выдумывается.** Если факт расходится с
  ожиданием, а спека не задаёт нормы — тест фиксирует факт + наблюдение,
  помечает находкой интегратору; вердикт не подгоняется.

## Бланк отчёта

Код-тест даёт автоматический вердикт (pass/fail) **и** питает бланк
отчёта (`test-run`): таблицы плана с заполненной колонкой «факт» +
наблюдения. Автоматический pass/fail не отменяет фиксацию факта в бланке
(полнота отчёта отвязана от ступени).

## Вход / Выход

- **Вход:** утверждённый тест-план + коллекция
  (`.claude/tests/{testType}/{source}/`); A2-passthrough; сырые DTO.
- **Выход:** код-тесты в `src/test/java/.../integration/sourceapi/{source}/`
  (`@Tag("source-api-live")`, профиль-гейт, teardown в каждом кейсе),
  покрывающие весь план.
