# Написание код-тестов

## На какой вопрос отвечает этот файл

Как именно написать код-тесты (исполнитель прогона) контура тестов API
источника по утверждённому плану.

## Когда применять

Этап **CODE-тесты** процесса
`.claude/processes/source-api-testing.md` — после аппрува **плана**.
Роль — `tester`.

## Назначение и границы

По **утверждённому** плану строятся `@SpringBootTest`-код-тесты —
**исполнитель** прогона контура (коллекция — необязательная справка,
не исполнитель, и аппрув-артефактом не является). Покрывают весь план: каждый кейс плана → код-тест.
Скилл **пишет** код-тесты; ревью — `reviewer` (`test-review`), прогон —
`test-run`. Скоуп — **сырьё** (сырой клиент + сырые DTO).

## Ключевые правила

- **Фреймворк — JUnit 5 + AssertJ** (существующий стек, прецедент —
  `src/test/.../integration/model/okx/response/*DeserializationTest`).
  `@SpringBootTest` с профилем `test` (demo-креды из Vault test).

- **Механика — A2-passthrough.** Код-тест бьёт
  в `POST /api/proxy/okx/raw` (под Spring Boot 4 — JDK `HttpClient` по
  `@LocalServerPort`; `TestRestTemplate` в SB4 удалён), получает **сырой**
  ответ OKX (`{code, msg, data}` как JsonNode) и ассертит сырые поля
  AssertJ.

- **Расположение и изоляция.** Живые тесты — отдельным пакетом
  `src/test/java/.../integration/sourceapi/{source}/`, **не** смешивать с
  офлайн unit-тестами биндинга DTO. Метка `@Tag("source-api-live")`.
  Структура зеркалит план **метод → кейсы**: **класс на метод сырого
  клиента, тест-метод на кейс** (прямой / каждый негатив / каждый
  вариант / цепочка). Метка кейса (`M2.1`/`Climit.place`/`Acond.cancel`)
  — в имени теста. Покрытие — весь план: каждый кейс → тест-метод, вкл.
  негатив на каждый запрос (write тоже) и каждый вариант типа-
  дискриминатора.

- **Профиль-гейт — структурный no-prod.** Код-тесты активны на
  **non-prod** и на **prod не идут** (гард по активному профилю: профиль
  prod → тест пропускается; любой другой → выполняется). Это не «opt-in
  off by default» — это структурное исключение prod (интерим, «пока»).

- **Создание реальных demo-сущностей.** Stateful-кейсы **создают**
  реальные сущности на demo (ордера/позиции/algo) — иначе stateful-
  запросы (getOrder / cancel / close-position) не проверить.

- **Teardown обязателен в каждом кейсе.** Каждый кейс оставляет биржу
  чистой: teardown по жизненному циклу (`@AfterEach` / try-finally),
  покрывает **все** созданные кейсом состояния (отмена/закрытие). После
  кейса — ни висящих ордеров, ни позиций, ни algo. Teardown идёт даже
  при провале тела теста. Teardown-хелперы (`*Quietly`, глушат ошибки) —
  **попытка sweep'а**, не авторитет возврата (см. sweep+halt ниже).

- **Throttle + rate-limit.** Все запросы к бирже идут воронкой через
  `raw()`: перед каждым — пауза-троттл (пол ≥1с, **per-case override**
  выше), измеряется глобально, поэтому покрывает и стык между тестами
  (отдельная между-тестовая пауза не нужна). Rate-limit-ответ OKX
  (HTTP 429 / rate-limit-коды) → backoff + повтор. Троттл — единственный
  пейсер поллинга (не складывается наивно с poll-интервалом).

- **Осадка — per-case таймаут.** Адаптивный поллинг
  (wait-until-condition) до per-case таймаута (дефолт ~25с; медленным
  кейсам — длиннее). Троттл (≥1с) и poll-таймаут (≥25с) — два разных
  per-case числа, разные цели; дефолты подкручиваются на прогоне.

- **Модель безопасности — sweep + halt (инвариант восстановления).**
  Verify.end единый для сущностей (ордера/позиции/algo) и настроек
  (`acctLv`/`leverage`/`posMode`): невозврат к старту → **жёсткий фейл**
  (не глушится) + **принудительный sweep** (снять/закрыть сущность;
  настройку — re-set к снапшоту); если sweep не вычистил → **halt
  прогона** (последующие кейсы абортятся). Находка C3 (невосстановимое
  состояние) логируется **в любом случае**. Авторитет «вернулось ли» —
  Verify.end, не teardown-хелперы.

- **Формат ошибки — кейс + запрос + ошибка.** Каждый путь фейла
  (assertion, исключение `raw()`, таймаут поллинга, halt) несёт в
  сообщении метку кейса/шага (`M19tr.place`), запрос к бирже
  (method/path/body/query) и саму ошибку (что не сошлось / тело ответа
  OKX). Механизм: ответ несёт породивший запрос, «текущий кейс» — в
  контексте теста.

- **Гейт достижимости.** Где сущность создать нельзя (архивные окна —
  `orders-history-archive`, `fills-archive`, ~30д-позиции) — прямого
  кейса нет (по плану), покрытие только негативом; отказ + причина
  отражены (план → отчёт).

- **Порядок прогона — детерминированный по структуре плана.** Классы и
  методы упорядочены `@Order`: класс на эндпоинт (M1–M21 → TG → AG → MG →
  PG, 1..60), метод на кейс (по порядку плана внутри эндпоинта); orderers
  включены в `src/test/resources/junit-platform.properties`
  (`ClassOrderer`/`MethodOrderer` = `OrderAnnotation`). Порядок
  воспроизводим (один и тот же каждый раз), что делает **halt** осмысленным:
  «дальше не идём» = всё, что после в этом порядке. Дешёвые no-state
  негативы естественно идут раньше write-цепочек по нумерации эндпоинтов.

- **Цена ордера — live с сырого `getTicker`, минимальный риск.** Ставя
  ордер, тест берёт live-цену сырым ticker и формирует заведомо
  неисполнимую цену (минимальный риск даже на demo).

- **Незадокументированное не выдумывается.** Если факт расходится с
  ожиданием, а спека не задаёт нормы — тест фиксирует факт + наблюдение,
  помечает находкой интегратору; вердикт не подгоняется.

## Бланк отчёта

Код-тест даёт автоматический вердикт (pass/fail) **и** питает бланк
отчёта (`test-run`): таблицы плана с заполненной колонкой «факт» +
наблюдения. Автоматический pass/fail не отменяет фиксацию факта в бланке
(отчёт полный всегда, независимо от режима).

## Вход / Выход

- **Вход:** утверждённый тест-план
  (`.claude/tests/{testType}/{source}/`); A2-passthrough; сырые DTO.
- **Выход:** код-тесты в `src/test/java/.../integration/sourceapi/{source}/`
  (`@Tag("source-api-live")`, профиль-гейт, teardown в каждом кейсе),
  покрывающие весь план.
