# spec-document-migration

Процедура миграции существующего документа из legacy-локаций
(`docs/domain/`, `docs/deprecated/`) в `docs/spec/`. Покрывает
переработку содержания под стандарт ADR-0002, разделение по жанрам
при необходимости, и связные обновления.

**Статус скилла:** первая версия после одного пилотного кейса
(AnomalyReport, 2026-05-15). Ожидается итерация после 2-3 следующих
миграций — паттерны декомпозиции, таксономия развилок, чек-листы
ревизии могут уточняться.

## Когда активируется

- Перенос документа из `docs/domain/` в `docs/spec/`.
- Перенос документа из `docs/deprecated/` в `docs/spec/`.
- Любая миграция, где исходник вне `docs/spec/`, цель — внутри
  `docs/spec/`, и содержание требует переработки под стандарт.

## Когда НЕ активируется

- Создание нового документа сразу в `docs/spec/` без legacy-предка —
  это [`spec-document-workflow`](../spec-document-workflow/SKILL.md).
- Редактирование существующего документа в `docs/spec/` — тоже
  `spec-document-workflow`.
- Физическое перемещение файла (`git mv`) без переработки содержания —
  это refactor, не миграция.

## Базовая модель работы

Миграция — это не правка файла, а **переработка**. Исходник написан до
ADR-0002, содержит смешанные жанры, Java-сниппеты, rationale-блоки,
addenda. Целевой документ — другой по структуре. Цель не «привести в
соответствие правкой», а **переразложить содержание** по жанрам и
правилам стандарта.

Поэтому миграция — трёхэтапный процесс:

1. **Анализ исходника** — структурированный отчёт от Claude Code в чат.
   Не правки, а инвентаризация: что есть, куда уезжает, что
   дублирует ADR, что выпадает.
2. **Развилки решаются в чате** — пользователь принимает решения
   по неоднозначным блокам, опираясь на отчёт.
3. **Исполнение** — Claude Code пишет целевые документы, проставляет
   MIGRATED-маркер, обновляет backlog. По завершении исполнения
   активируется `spec-document-workflow` для финального чек-листа на
   целевых документах.

Анализ и развилки **обязательны**. Попытка «сразу написать целевой
документ» по исходнику пропускает решения, которые должен принять
пользователь, и теряет содержание.

## Процедура

### Шаг 1. Анализ исходника

Запросить у Claude Code структурированный отчёт по 6 разделам.
Промпт-шаблон:

> Задача — анализ, не правка. Ничего не менять в файлах, не запускать
> git. Прочитай:
>
> 1. `<путь к исходнику>`
> 2. Все ADR в `.claude/adr/`, на которые ссылается исходник или
>    которые касаются предметной области документа.
> 3. `.claude/adr/0002-spec-document-standard.md` — стандарт.
> 4. Шаблоны жанров из `.claude/templates/documents/`, релевантные
>    предполагаемому жанру (или нескольким, если ожидается разделение).
> 5. `.claude/planning/backlog.md` — для проверки затронутых пунктов.
>
> Отчёт по разделам:
>
> **1. Инвентарь содержания исходника.** Разбить документ на смысловые
> блоки (не по заголовкам — по смыслу). Для каждого блока:
> имя / содержание / жанр (structure / lifecycle / rationale / metadata /
> duplicate / other) / куда уезжает / риск потери (high/medium/low).
>
> **2. Что уже зафиксировано в связанных ADR** про предмет документа.
> Цель — выявить, что **не** нужно повторять в spec.
>
> **3. Расхождения исходника с ADR-0002.** Для каждого: где
> нарушение / какое правило / как чинится.
>
> **4. Расхождения исходника с шаблонами целевых жанров.** Какие
> разделы шаблона отсутствуют, какие разделы исходника не предусмотрены.
>
> **5. Затронутые пункты backlog.** Что закроется, обновится, появится
> как новый пункт.
>
> **6. Открытые вопросы и развилки.** То, что требует решения
> пользователя ДО исполнения. Формат: вопрос / контекст / варианты с
> тезисом за каждый.
>
> НЕ предлагать финальные тексты, НЕ править файлы.

### Шаг 2. Решение развилок в чате

Пользователь и Claude разбирают каждый открытый вопрос из Раздела 6.
Решения фиксируются в чате, не в файлах.

Типичные классы развилок (наблюдённые на AnomalyReport):

- **Разделение по жанрам.** Сохранять исходник одним документом или
  разбивать по жанрам ADR-0002. По умолчанию — разбивать (жанры в
  стандарте принципиальны). Сохранение в одном документе требует
  обоснования.
- **Rationale-блоки в исходнике.** Что-то из «зачем нужна модель»
  принадлежит ADR (если уже зафиксировано), что-то остаётся в spec
  как описание назначения. Граница — принадлежит ли утверждение
  «истории решения» или «текущему состоянию».
- **Дублирование с ADR.** Куски, повторяющие то, что есть в ADR —
  удаляются из spec, заменяются ссылкой или вообще не упоминаются.
- **«Что не включается» как активный сигнал.** Списки «не включаем X, Y, Z»
  могут оставаться в spec как конструктивный сигнал, либо считаться
  частью ADR. Решение — по полезности сигнала.

### Шаг 3. Исполнение

Передать в Claude Code исполнительский пакет:

- Концептуальные решения по развилкам (буквально, не «по духу»).
- Инвентарь — таблица «что куда уезжает», используется как страховка
  от потерь.
- Список целевых документов с путями.
- Связные обновления:
  - закрыть/обновить пункты backlog;
  - проставить MIGRATED-маркер на исходник (формат — см. ниже);
  - проверить, не нужно ли обновить ADR-индекс / Project Knowledge
    (обычно нет, но явно проверить).
- Чек-лист самопроверки (стандарт ADR-0002 + специфика миграции).
- Указание `git add`, **не коммитить**.

После исполнения активируется `spec-document-workflow` для финального
чек-листа на каждом целевом документе.

### Шаг 4. Ревью пользователем

Пользователь получает от Claude Code сводку и тексты целевых
документов. Сверка по инвентарю — каждый блок исходника нашёл место,
ничего не выпало. Точечные правки — отдельной итерацией Claude Code,
не «по ходу».

## MIGRATED-маркер на исходнике

После того как все целевые документы написаны и зафиксированы —
исходник помечается на первой строке:

```markdown
> **[MIGRATED → <путь1>, <путь2>, ...]** — этот документ больше не источник правды.
```

Если миграция разделила исходник на несколько целевых документов
(например, model + lifecycle) — в маркере перечисляются **все**
целевые документы, не только первый.

Сам файл исходника не удаляется — остаётся в legacy-локации с
маркером.

## Чек-лист исполнения

Прогнать перед `git add`.

**По каждому целевому документу:**

- [ ] Документ соответствует чек-листу `spec-document-workflow`
  (frontmatter, имя, жанр, отсутствие Java-сниппетов и addenda, стиль,
  размер).
- [ ] `related_adrs` включает ADR, к которым относится исходник.

**Связные обновления:**

- [ ] Пункт backlog про эту миграцию закрыт с обновлённой
  формулировкой и датой.
- [ ] Новые открытые вопросы (если появились) занесены в backlog.
- [ ] Backlog-пункты, активированные миграцией (по факту использования
  в качестве первого кейса) — переведены в подходящий приоритет.

**Маркер на исходнике:**

- [ ] Если у исходника был старый MIGRATED-маркер (миграция не первая
  итерация) — он обновлён, перечисляет все актуальные целевые документы.
- [ ] Если маркера не было — он проставлен в требуемом формате.

**Финальная страховка от потерь:**

- [ ] Каждая строка таблицы инвентаря из пакета шага 3 нашла место в
  одном из целевых документов или была явно удалена с обоснованием
  (duplicate / уже в ADR / запрещено стандартом).

## Подводные камни

**1. «Сразу написать целевой документ» без анализа.** Соблазн —
исходник вроде понятен. Запрещено. Анализ ловит то, что
переработке без него пропускают: дублирования с ADR, скрытые
жанровые смешения, потерянные при беглом чтении сигналы.

**2. Точечная правка вместо переработки.** Соблазн — «здесь Java
заменю таблицей, тут frontmatter добавлю, и достаточно». Это не
миграция, это косметика. Если содержание не переразложено по жанрам и
правилам ADR-0002 — миграция не сделана.

**3. Слепое доверие к самоотчёту Claude Code.** Сводка от Claude Code
о проделанной работе — это самоотчёт. Перед коммитом — пользователь
запрашивает тексты целевых документов и сверяет с инвентарём. Иначе
выпадения остаются незамеченными.

**4. Парный «migrated-from»-маркер в целевом документе.** Соблазн —
дописать в spec-документ «мигрировано из ...». Запрещено по ADR-0002
§5. Связь — только через `related_adrs` в frontmatter и через
односторонний маркер на исходнике.

**5. Спор о жанре «по удобству».** Соблазн — оставить динамику в model
ради «удобства одного файла». ADR-0002 жанровое разделение
принципиально. Аргумент удобства неприемлем.
