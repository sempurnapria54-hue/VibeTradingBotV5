# Скилл: миграция кластера документов

Этот скилл описывает **процедуру** миграции одного кластера legacy-документов в `docs/spec/`. Для конкретного кластера — состав, порядок и обоснование берутся из [ADR-0009 §2](../../adr/0009-domain-migration-strategy.md) и `.claude/planning/migration-tracker.md`.

Скилл оркестрирует миграцию. Для каждого документа кластера вызывается [`spec-document-migration`](../spec-document-migration/SKILL.md).

## Когда активируется

- Старт миграции нового кластера.
- Миграция следующего документа внутри уже начатого кластера.
- Проверка готовности кластера к закрытию (hard gates).
- Финализация кластера (обновление связанных артефактов).

## Когда НЕ активируется

- Миграция отдельного документа вне кластерного контекста —
  [`spec-document-migration`](../spec-document-migration/SKILL.md).
- Создание нового документа в `docs/spec/` без legacy-предка —
  [`spec-document-workflow`](../spec-document-workflow/SKILL.md).
- Обновление трекера или MODELS.md вне миграционной сессии —
  работайте с этими файлами напрямую по их собственным правилам.

## Базовая модель работы

Кластер — единица батчинга миграции. Содержит связанные legacy-документы (по зависимостям, по общему предмету, по однотипным паттернам). Состав каждого кластера и обоснование первенства — в ADR-0009 §2.

Миграция кластера — последовательная миграция всех его документов с контролем зависимостей и проверкой готовности на финале. Один документ кластера = один вызов `spec-document-migration`. Документы внутри кластера мигрируются по очерёдности, диктуемой зависимостями: сначала те, на которые ссылаются остальные.

Кластер считается завершённым, когда:
- Все документы кластера имеют статус `done` в трекере (MIGRATED-маркер проставлен).
- Все hard gates пройдены (см. ниже).
- Связанные артефакты обновлены (MODELS.md, трекер, backlog).

## Процедура

### Этап 1. Подготовка кластера

Перед стартом первого документа кластера:

1. **Прочитать ADR-0009 §2** для целевого кластера: legacy-источники, целевые spec-документы (планируемые), зависимости, обоснование первенства.
2. **Проверить готовность зависимостей.** Все кластеры, от которых зависит текущий, должны быть в статусе `done` в трекере. Если зависимости не готовы — старт текущего кластера откладывается, либо явно решается, как обрабатывать забегающие ссылки на ещё немигрированные модели (см. §5 ADR-0009).
3. **Открыть migration-tracker.md** и поставить статус кластера `in-progress` (если ещё не стоит).
4. **Определить порядок документов внутри кластера.** Если в кластере один документ — порядок очевиден. Если несколько — порядок определяется зависимостями между документами. Часто порядок неявно следует из ADR-0009 §2; если не следует — порядок выбирается рабочим путём, фиксируется в чате до старта.
5. **Открыть журнал** `.claude/questions/open-questions.md` — он понадобится по ходу миграции для фиксации неразрешённых блоков.

### Этап 2. Миграция документов кластера

Для каждого документа кластера, в выбранном порядке:

1. **Запустить миграцию документа** через скилл `spec-document-migration`. Его процедура (анализ → развилки → исполнение) применяется к этому конкретному документу.
2. **При появлении забегающей ссылки** в целевом spec-документе (упоминание модели из ещё немигрированного кластера) — оформить по синтаксису ADR-0009 §5: прозаическое упоминание имени без markdown-link и без inline-code. Knowledge Curator при ревью идентифицирует забегающие ссылки по списку имён в MODELS.md (по ADR-0009 §6).
3. **При появлении неразрешённого блока в legacy-документе** — завести Q-N в журнале (через скилл `open-questions-workflow`). Source = путь к legacy-файлу + фрагмент. Documенту это **не блокирует завершение** — частичная миграция допустима; MIGRATED-маркер не ставится до закрытия всех Q-N по документу.
4. **После завершения миграции документа** — обновить трекер: статус документа `done` (или остаётся `in-progress`, если есть открытые Q-N). Перечислить созданные целевые spec-документы.
5. **Обновить MODELS.md** — для каждой бизнес-модели, целевой spec-документ которой создан в этой миграции, заменить заглушку на ссылку (по правилам скилла `spec-models-registry`).
6. **Перейти к следующему документу** кластера.

### Этап 3. Проверка hard gates перед закрытием кластера

Кластер не закрывается, пока не пройдены пять hard gates по [ADR-0009 §8](../../adr/0009-domain-migration-strategy.md):

1. **Все документы кластера в статусе `done`** в трекере. MIGRATED-маркеры проставлены.
2. **Все целевые spec-документы существуют** и проходят чек-лист `spec-document-workflow` (стандарт ADR-0002, frontmatter, размер, отсутствие запрещённых элементов).
3. **MODELS.md обновлён**: заглушки для бизнес-моделей кластера заменены ссылками на созданные model-документы.
4. **Open-questions, открытые по ходу миграции, — в журнале**. Те, что заблокировали финализацию документов — закрыты или сознательно оставлены открытыми (с явным решением, что они не блокируют закрытие кластера).
5. **Влияния на последующие кластеры зафиксированы**. Список ожидаемых влияний (что новые модели/спецификации означают для соседних кластеров) — пройден; все блокирующие влияния закрыты как Q-N (Resolved) или решением в чате/ADR.

Если хотя бы один gate не пройден — кластер остаётся `in-progress`. Возвращаемся к Этапу 2 для довоза.

### Этап 4. Финализация кластера

После прохождения всех hard gates:

1. **Трекер**: статус кластера `done`. Указать дату завершения и (опционально) ссылку на коммит финализации.
2. **MIGRATED-маркеры на legacy-файлах**: проставить маркер только на те legacy-файлы, чьи фрагменты этим кластером полностью разнесены. Для shared-файлов (распадающихся по нескольким кластерам) маркер ставится только когда **все** фрагменты файла мигрированы — возможно, через несколько кластеров. До этого момента такие файлы остаются в `in-progress` в трекере. См. также скилл [`spec-document-migration`](../spec-document-migration/SKILL.md), раздел «MIGRATED-маркер на исходнике».
3. **MODELS.md**: финальная сверка — все бизнес-модели кластера имеют ссылки на model-документы.
4. **Backlog**: закрыть пункт «миграция кластера X», если такой был. Обновить пункт «миграция фазы 1», если все её кластеры завершены.
5. **Журнал**: пройтись по Q-N, заведённым в этом кластере. Те, что разрешены ходом миграции, — закрыть с Resolution. Остальные — оставить открытыми с понятным статусом для следующих кластеров или для отдельного разбора.
6. **Связные обновления**: если миграция кластера затронула другие spec-документы (например, добавила forward-ссылки или закрыла их), — пройтись по затронутым документам, подтвердить корректность.
7. **Knowledge Curator** в конце сессии — общая проверка консистентности (см. Сценарий 8 в playbook).

## Hard gates подробнее

См. полную формулировку — [ADR-0009 §8](../../adr/0009-domain-migration-strategy.md). Кратко:

- **Gate 1**: документы → MIGRATED.
- **Gate 2**: spec-документы → стандарт ADR-0002.
- **Gate 3**: MODELS.md → актуальные ссылки.
- **Gate 4**: журнал → без блокирующих Q-N.
- **Gate 5**: влияния на следующие кластеры → закрыты или явно неблокирующие.

Gate 5 операционализируется списком: для каждого следующего кластера в очерёдности — какие моменты текущего кластера могут на него повлиять (новые модели, изменения семантики, новые инварианты). Каждый пункт списка — закрыт ADR/spec-разделом, или существует как Q-N (с осознанным «не блокирует закрытие»).

## Забегающие ссылки

При миграции часто возникает упоминание модели из ещё немигрированного кластера. Это **штатно**, не ошибка. По ADR-0009 §5:

- Упоминать модель прозаически: «связана с Order через FK», не `[Order](models/core/Order.md)`.
- Не использовать `Order` в inline-коде с подразумеванием существующего документа.
- При миграции упоминающего кластера → Curator идентифицирует ссылку по MODELS.md и помечает как забегающую.
- Когда упоминаемый кластер мигрирует — забегающие ссылки на его модели становятся обычными ссылками (отдельным проходом или при следующем ревью).

## Работа с журналом

По ходу миграции в журнале могут появляться Q-N (через скилл `open-questions-workflow`). Типичные случаи:

- **Неразрешённый блок** в legacy-документе при миграции. Source: путь + фрагмент.
- **Концептуальное противоречие** между legacy и ADR.
- **Развилка по жанру** целевого документа, не разрешённая в чате.
- **Отсутствующая модель**, упомянутая в legacy без описания.

Q-N не блокирует продолжение миграции документа — продолжается частичная миграция. Q-N блокирует **финализацию документа** (MIGRATED-маркер) и, если блокирующих много, может блокировать закрытие кластера (gate 4).

## Чек-лист завершения кластера

Прогнать перед переключением на следующий кластер.

**По каждому документу кластера:**

- [ ] MIGRATED-маркер проставлен на legacy-файле.
- [ ] Целевые spec-документы созданы и проходят `spec-document-workflow`.
- [ ] Q-N, заведённые при миграции этого документа, либо закрыты, либо явно оставлены открытыми с осознанным решением.

**По кластеру в целом:**

- [ ] Трекер: статус кластера `done`.
- [ ] MODELS.md: все бизнес-модели кластера имеют ссылки.
- [ ] Все 5 hard gates по ADR-0009 §8 пройдены.
- [ ] Backlog: пункты по этому кластеру обновлены (закрыты или переформулированы).
- [ ] Knowledge Curator: общая проверка консистентности (Сценарий 8 playbook).

## Подводные камни

**1. Старт без проверки готовности зависимостей.** Соблазн — взять кластер в работу, надеясь, что зависимости подтянутся. Запрещено: при работе появятся forward-ссылки без понимания, штатные они или критические. Зависимости должны быть `done` или должен быть явный план обработки.

**2. Параллельная миграция нескольких документов кластера.** Соблазн — гнать сразу два документа в чате. Запрещено: документы внутри кластера обычно зависят друг от друга, параллельная работа создаёт несогласованности. Последовательно.

**3. Полное завершение кластера без проверки hard gates.** Соблазн — выглядит как готово, ставим `done`. Запрещено: каждый gate проверяется явно. Особенно gate 5 — он легко пропускается.

**4. Откладывание обновления MODELS.md «на потом».** Соблазн — давайте сначала все документы напишем, потом ссылки добавим. Запрещено: Curator не сможет работать с забегающими ссылками. MODELS.md обновляется после каждой завершённой миграции документа.

**5. Дублирование состава кластера в скилле.** Соблазн при правке скилла — добавить «вот наши 8 кластеров с составом». Запрещено: источник состава — ADR-0009 §2 и трекер. Скилл описывает процедуру, не данные.

**6. Игнорирование Q-N как «маленькие неточности».** Соблазн — продолжать миграцию, не заводя Q-N. Запрещено: незаведённый Q-N — потерянное наблюдение. Завести легко (через `open-questions-workflow`), не заводить — теряем системную память.
