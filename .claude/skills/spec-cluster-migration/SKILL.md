# Скилл: миграция кластера документов

Этот скилл описывает процедуру миграции одного кластера
legacy-документов в `docs/spec/`. Состав кластера и порядок
прохождения внутри — в `.claude/planning/migration-tracker.md`.
Скилл оркестрирует миграцию; для каждого legacy-документа кластера
вызывается [`spec-document-migration`](../spec-document-migration/SKILL.md).

## Когда активируется

- Старт миграции нового кластера.
- Миграция следующего документа внутри уже начатого кластера.
- Проверка готовности кластера к закрытию (hard gates).
- Финализация кластера (обновление связанных артефактов).

## Когда НЕ активируется

- Миграция отдельного legacy-документа вне кластерного контекста —
  [`spec-document-migration`](../spec-document-migration/SKILL.md).
- Создание нового документа в `docs/spec/` без legacy-предка —
  [`spec-document-workflow`](../spec-document-workflow/SKILL.md).
- Обновление трекера или MODELS.md вне миграционной сессии —
  работайте с этими файлами напрямую по их собственным правилам.

## Базовая модель работы

Кластер — единица батчинга миграции. Содержит набор
legacy-документов, объединённых по тематической связи или по
последовательности прохождения. Миграция кластера — последовательная
миграция всех его legacy-документов с проставлением MIGRATED-маркера
на каждом. **Кластер закрыт, когда все его legacy-документы имеют
MIGRATED-маркер.**

Кластер не требует, чтобы все упоминания сущностей внутри были
полностью описаны. Если в legacy-документе упоминается сущность
без содержательного описания — заводится Q-N (этим занимается
`spec-document-migration`). **Открытые Q-N не блокируют закрытие
кластера**: они привязаны к сущности, не к legacy-документу и не
к кластеру.

Документы-заглушки в `docs/spec/` (заполнено определение и связи,
остальное помечено как «появится при содержательной миграции») —
валидное промежуточное состояние. Заглушка регистрируется в
`docs/spec/MODELS.md` сразу. Кластер не обязан превращать все
заглушки в полные документы — это происходит при миграции
содержательного источника, который может быть в другом кластере.

## Процедура

### Этап 1. Подготовка кластера

Перед стартом первого документа кластера:

1. **Прочитать состав кластера** в
   `.claude/planning/migration-tracker.md`: список
   legacy-документов кластера, текущий статус каждого.
2. **Определить порядок прохождения legacy-документов внутри
   кластера.** Порядок либо указан в трекере, либо выбирается
   рабочим путём (обычно — от более автономных документов к
   более связным). Решение фиксируется в чате до старта.
3. **Поставить статус кластера `in-progress`** в трекере
   (если ещё не стоит).
4. **Открыть журнал** `.claude/questions/open-questions.md` —
   он понадобится по ходу миграции для заведения и закрытия Q-N.

### Этап 2. Миграция документов кластера

Для каждого legacy-документа кластера, в выбранном порядке:

1. **Запустить миграцию документа** через скилл
   [`spec-document-migration`](../spec-document-migration/SKILL.md).
   Его алгоритм (прочитать → классифицировать упоминания →
   разнести по spec-документам или Q-N → закрыть существующие
   Q-N по созданным сущностям → MIGRATED-маркер) применяется к
   этому конкретному legacy-документу.
2. **После завершения миграции legacy-документа** — обновить
   трекер: статус legacy-документа `done`, перечислить
   созданные/дополненные spec-документы.
3. **Для модели со статусами — проверить парный lifecycle-документ.**
   Если у мигрированной модели есть поле статуса (enum) и между
   статусами есть переходы — у неё должен быть создан парный
   lifecycle-документ `docs/spec/lifecycle/<Имя>.md` (таблица
   переходов, кто триггерит, доменные запреты с обоснованием,
   инварианты поведения). Если переходов нет — lifecycle не
   создаётся, в model достаточно раздела «Статусы».
4. **Перейти к следующему legacy-документу** кластера.

### Этап 3. Проверка hard gates перед закрытием кластера

Кластер не закрывается, пока не пройдены три gates:

1. **Все legacy-документы кластера имеют MIGRATED-маркер.**
   Содержимое каждого разнесено: содержательные упоминания — в
   целевые spec-документы (созданные или дополненные),
   упоминания без описания — в Q-N журнала.
2. **Все целевые spec-документы валидны.** Каждый созданный
   или дополненный документ в `docs/spec/` проходит чек-лист
   [`spec-document-workflow`](../spec-document-workflow/SKILL.md):
   корректный frontmatter, корректный жанр и имя файла,
   отсутствие запрещённых элементов, размер. Документы-заглушки
   (заполнено определение и связи, остальное явно помечено)
   считаются валидными — это штатное промежуточное состояние.
3. **Все Q-N, заведённые в ходе миграции кластера, имеют
   корректную classification и source.** Classification —
   `missing-model` / `missing-process` / `missing-invariant` /
   `concept`. Source — путь к legacy-файлу + фрагмент. Открытые
   Q-N не блокируют закрытие; пропускаются только Q-N без
   classification или без source.

Если хотя бы один gate не пройден — кластер остаётся
`in-progress`. Возвращаемся к Этапу 2 для довоза.

### Этап 4. Финализация кластера

После прохождения всех hard gates:

1. **Трекер**: статус кластера `done`. Указать дату завершения.
2. **Статус целевых spec-документов**: если документ был создан
   как заглушка и в ходе кластера дополнен до полноты —
   обновить frontmatter `status` с `wip`/`draft` на `current`.
   Если документ остаётся в промежуточном состоянии (часть
   разделов помечена как «появится при содержательной
   миграции») — статус не повышается, соответствующий Q-N
   остаётся открытым.
3. **Backlog**: закрыть пункт «миграция кластера X», если такой
   есть. Обновить пункт «миграция фазы 1», если все её кластеры
   завершены.
4. **Журнал**: пройтись по Q-N, заведённым в этом кластере. Те,
   что разрешены ходом миграции, — должны быть уже закрыты на
   этапе создания соответствующего документа (этим занимается
   `spec-document-migration`). Открытые Q-N оставляются как
   есть — они привязаны к сущностям, не к кластеру.
5. **Knowledge Curator** в конце сессии — общая проверка
   консистентности.

## Чек-лист завершения кластера

Прогнать перед переключением на следующий кластер.

**По каждому legacy-документу кластера:**

- [ ] MIGRATED-маркер проставлен на legacy-файле.
- [ ] Целевые spec-документы созданы/дополнены и проходят
  `spec-document-workflow`.
- [ ] Для каждой модели со статусами (enum) и переходами между
  ними — создан парный lifecycle-документ. Для модели со
  статусом без переходов lifecycle отсутствует — это штатно.

**По журналу Q-N:**

- [ ] Каждый Q-N, заведённый в этой сессии, имеет classification
  и source.
- [ ] Q-N о сущностях, для которых в этой сессии создан целевой
  документ, — закрыты с резолюцией (это работа
  `spec-document-migration`, здесь только проверяется).

**По кластеру в целом:**

- [ ] Трекер: статус кластера `done`.
- [ ] Целевые model-документы (включая заглушки) зарегистрированы
  в `docs/spec/MODELS.md`.
- [ ] Backlog: пункты по этому кластеру обновлены.
- [ ] Knowledge Curator: общая проверка консистентности.

## Подводные камни

**1. Параллельная миграция нескольких документов кластера.**
Соблазн — гнать сразу два legacy-документа в чате. Запрещено:
документы внутри кластера обычно связаны, параллельная работа
создаёт несогласованности (например, дублирование Q-N по одной
сущности из разных источников). Последовательно.

**2. Полное завершение кластера без проверки gates.** Соблазн —
выглядит как готово, ставим `done`. Запрещено: каждый gate
проверяется явно. Особенно gate 3 (Q-N classification) —
пропускается легко, потому что Q-N выглядят «уже заведено, и
хорошо».

**3. Создание документа-заглушки и забыть про MODELS.md.**
Заглушка — это валидный документ. Он регистрируется в реестре
сразу. Откладывание регистрации создаёт расхождение между
`docs/spec/` и реестром.

**4. Дублирование состава кластера в скилле.** Соблазн при
правке скилла — добавить «вот наши 8 кластеров с составом».
Запрещено: источник состава — `.claude/planning/migration-tracker.md`.
Скилл описывает процедуру, не данные.

**5. Игнорирование Q-N как «маленькие неточности».** Соблазн —
продолжать миграцию, не заводя Q-N. Запрещено: незаведённый
Q-N — потерянное наблюдение. Завести легко (через
`open-questions-workflow`).

**6. Промоушн статуса заглушки в `current` без оснований.**
Соблазн — кластер завершён, повысим статусы всех созданных
документов. Запрещено: документ-заглушка остаётся в
`wip`/`draft`, пока структурные поля не заполнены. Промоушн —
только когда документ заполнен по существу.

## Связанные документы и скиллы
