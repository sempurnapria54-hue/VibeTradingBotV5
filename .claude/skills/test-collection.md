# Построение тест-коллекции

## На какой вопрос отвечает этот файл

Как именно построить исполняемую тест-коллекцию (Postman) по
тест-плану.

## Когда применять

Этап **DESIGN** процесса
`.claude/processes/source-api-testing.md`, вместе с построением
плана (`test-design`). Роль — `tester`. Коллекция строится на
DESIGN, **до запуска**.

## Назначение и границы

По тест-плану строится исполняемая Postman-коллекция (v2.1) —
материализация кейсов плана в запросы через **A2 raw-passthrough**
(единственный generic `POST /api/proxy/okx/raw`). Скоуп — **сырьё**:
сырой ответ OKX (`OkxApiResponse<JsonNode>`). Коллекция — **ревью/аппрув-
артефакт** (человек читает и аппрувит план как конкретные исполнимые
запросы; вторичная роль — ручной повтор). **Исполнитель прогона — не
коллекция, а код-тесты** (`test-code`), бьющие в тот же passthrough
(механика 1:1). Скилл **строит** коллекцию; не ревьюит (`test-review`)
и не прогоняет.

## A2 raw-passthrough

Под ре-базой на сырьё (`.claude/decisions/source-api-target-rebase.md`
§D) все запросы идут через **единственный** generic-эндпоинт app
`POST /api/proxy/okx/raw` (конверт `{method, path, query, body, signed}`
→ `OkxRestClient.dispatch`): он отдаёт **сырой**
`OkxApiResponse<JsonNode>` (`b.code`/`b.msg`/`b.data[]`), **без**
`IntegrationService`→снапшот-маппинга. Тело запроса строится руками по
контракту — типизированного прокси-метода на эндпоинт не требуется.

## Ключевые правила

- **Через A2-passthrough, не прямой вызов OKX.** Подпись и креды — на
  стороне app (signing interceptor): в Postman подпись **не считается**,
  кредов в Postman **не нужно**. Та же поверхность, что бьют код-тесты.

- **demo/non-prod — профилем поднятого app.** Тот же passthrough-путь;
  base URL — переменной (`base_url`). Окружение — шаблон с `base_url`,
  **кредов в шаблон не класть**. Контур — demo/non-prod; ад-хок повтор
  коллекции на prod-поднятом app — дело пользователя **вне контура**.

- **Структура — папка на метод, запрос/под-папка на кейс.** Коллекция
  зеркалит структуру плана **метод → кейсы**: 1 папка коллекции =
  1 метод плана (`## Mn`); внутри — запрос на кейс (`### Mn.k`), а
  многозапросный кейс (цепочка) = под-папка с запросами-шагами. Папки/
  кейсы с write — помечать: на demo — **реальные ордера/algo/позиции**.

- **Вариант и негатив — отдельными пунктами.** Каждый вариант типа-
  дискриминатора (`ordType`/`conditionType`/семья cancel) и **каждый**
  негатив (вкл. write/мутацию) — отдельный запрос-пункт в папке метода,
  с проверкой ожидаемого исхода. Вариант-gap — помечается в описании,
  запрос не выдумывается.

- **Подпись кейсом плана.** Каждый запрос несёт в имени/описании метку
  своего кейса плана (`M2.1`, `Climit.place`, `Acond.cancel`, …).

- **Per-request — проверки на сыром JSON.** Проверки ставятся на
  **сырых полях JSON** ответа OKX (`OkxApiResponse<JsonNode>`:
  `b.code`/`b.msg`/`b.data[i].<field>`) — по используемым полям +
  статус-код; реджект — per-element `b.data[i].sCode` и top-level
  `b.code`. Не каждое возможное поле биржи — используемые + коды ошибок.

- **Проверки кодируют ожидание плана.** Где открытая находка делает
  поведение иным — фейл проверки по дизайну **показывает находку**. Где
  вердикт частично неизвестен (рантайм-снятие) — проверка кодирует
  гипотезу, её фейл = сигнал находки на разбор.

- **Цена ордера — live с сырого `getTicker`, минимальный риск.**
  Коллекция сперва тянет live-цену сырым ticker через passthrough,
  кладёт `last` в переменную и от неё формирует **заведомо неисполнимую**
  цену ордера. Под сырьё — прямой запрос, surface-gap'а нет.

- **Цепочка переменных.** id из write-ответа (`ordId`/`algoId` из
  `data[0]`) сохраняется в переменную коллекции и потребляется
  зависимыми запросами — без ручной вставки. Stable client id
  (`clOrdId`/`algoClOrdId`) генерится pre-request-скриптом.

- **Negative-кейсы — по плану.** Запросы порождённого негатива (битый
  параметр, несущ. id, дубль, отмена отменённого, фильтр вне окна, …)
  идут отдельными пунктами с проверкой ожидаемого кода ошибки.

- **Полнота — весь in-perimeter.** Под `/raw` тело конверта строится
  руками, поэтому материализуется каждая in-perimeter строка манифеста —
  прежняя метка `client-coverage-gap` (строка без метода клиента) **снята**
  (`source-api-target-rebase.md` §D): под `/raw` недостижимых через клиент
  строк нет.

## Общий жизненный цикл с планом

Коллекция — поверхность ревью наравне с планом. Ревьюится
(`test-review`), аппрувится и правится **вместе с планом**. Прогон
(RUN) — код-тестами по утверждённой паре план + коллекция.

## Вход / Выход

- **Вход:** тест-план (`.claude/tests/{testType}/{source}/`); generic
  `/raw` источника (пути, параметры, сырые response-формы); сырой ответ
  (`OkxApiResponse<JsonNode>`).
- **Выход:** Postman-коллекция (v2.1) + шаблон окружения (`base_url`,
  без кредов) в `.claude/tests/{testType}/{source}/`.
