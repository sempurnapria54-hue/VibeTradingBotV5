# Определение типа

## На какой вопрос отвечает этот файл

Как определить тип знания фрагмента.

## Когда применять

Шаг 3 процесса классификации знания: после того как определена
область, до определения темы.

## Метод

Тип знания определяется через вопрос, на который отвечает
фрагмент. Перечень типов с соответствующими им вопросами —
ниже.

## Перечень типов знания

Список всех типов, которые сейчас используются в проекте, с
вопросом, на который каждый отвечает. Список ведётся внутри
скилла. При появлении нового типа — обновляется здесь.

### Типы пайплайн-области

- **Базовые правила проекта** — «каковы базовые правила
  проекта?» (живёт в `CLAUDE.md`).
- **Снимок состояния** — «где мы сейчас и как сюда пришли?»
  (`snapshots/`).
- **Правило** — «какое у нас правило?» (`rules/`).
- **Шаблон** — «каков формат файла такого-то типа?»
  (`templates/`).
- **Скилл** — «как именно делать X?» (`skills/`).
- **Агент** — «что делает Claude в роли X?» (`agents/`).
- **Решение** — «почему мы решили так, а не иначе?»
  (`decisions/`).
- **Наблюдение** — «что я наблюдал / разведал?» (`notes/`).
- **Методологический процесс** — «как устроен этот
  методологический процесс?» (`processes/`).
- **Планируемая задача** — «что мы планируем сделать?»
  (`work/backlog.md`).
- **Роадмап** — «куда движется продукт по бизнес-ценности и в
  каком статусе каждый шаг?» (`work/roadmap/`). Главный файл —
  таблица фаз; детальный файл фазы — таблица шагов. Scope —
  только продукт; пайплайн вне. См.
  `.claude/decisions/product-roadmap-type.md`.
- **Активная задача** — «на каком шаге мы в этой операции?»
  (`work/progress/`).
- **Общие открытые вопросы** — «что мы ещё не решили?»
  (`work/questions/open-questions.md`).
- **Локальные вопросы задачи** — «что неясно по этой
  конкретной активной задаче?» (`work/questions/tasks/`).
- **История** — «что мы уже сделали?» (`work/history/`).

### Типы продуктовой области

- **Торговая модель с биржевым воплощением (domain/core)** — «что
  это за торговая модель?» (`docs/models/domain/core/`).
- **Aggregate без биржевой привязки (domain/aggregate)** — «что это
  за сущность без биржевой привязки, нужная для торговли?»
  (`docs/models/domain/aggregate/`).
- **Прочая хранимая модель (domain/other)** — «что это за прочая
  хранимая модель?» (`docs/models/domain/other/`).
- **Нативная модель источника** — «какие поля у нативной модели
  источника?» (`docs/models/integrations/{name}/`).
- **External snapshot** — «какая структура нормализованного
  граничного объекта?» (`docs/models/externalSnapshot/`; файл —
  только при самостоятельном содержании).
- **Mapping между слоями** — «как сущность переходит между слоями
  и как резолвится её статус?» (`docs/models/mapping/<Сущность>.md`;
  per-source — подразделами).
- **Модель хранимого слоя (скаффолд)** —
  «что это за модель хранимого слоя?» (`docs/models/persistence/`).
- **Модель API нашего сервиса (скаффолд)** — «что это за модель API
  нашего сервиса?» (`docs/models/api/`).
- **Lifecycle** — «через какие состояния проходит этот объект,
  кто управляет?» (`docs/lifecycles/`).
- **Продуктовый процесс** — «как устроен этот процесс?»
  (`docs/processes/`).
- **Компонент** — «кто выполняет?» (`docs/components/`).
- **Продуктовое правило** — «какое правило действует в
  системе?» (`docs/rules/`).
- **Словарная статья** — «что означает этот термин?»
  (`docs/dictionary/`).
- **Продуктовое решение** — «почему мы решили так, а не
  иначе?» (`docs/decisions/`).
- **Контракт источника** — «каков контракт и какие лимиты у этой
  операции источника?» (`docs/integrations/{name}/contracts/`).
- **Правило источника** — «какое правило источника (инварианты,
  adapter-константы, конвенции)?» (`docs/integrations/{name}/rules/`).
- **Runtime value object** — «что это за runtime-объект?»
  (`docs/components/models/`).

## Признаки для различения близких типов

### Правило vs наблюдение

- **Правило** — повторяющееся применение, обязательность,
  действует впредь. Идёт в `.claude/rules/` (для пайплайна) или
  `docs/rules/` (для системы).
- **Наблюдение** — разовость, фиксация факта в моменте, не
  обязывает. Идёт в `.claude/notes/`.
- Сомневаешься — в `notes/`. Если потом подтвердится как
  правило — оформим через decision и перенесём.

### Решение vs правило

- **Решение** — есть выбор, рассматривались альтернативы,
  выбор нужно объяснить. Идёт в `decisions/` (пайплайн или
  продукт по смыслу).
- **Правило** — тривиально, альтернативы не обсуждались,
  просто фиксируем как «делаем так». Идёт в `rules/`.

### Продуктовое знание: модель vs процесс vs lifecycle vs правило vs словарь

- **Модель** — «что это?» про объект. Layer определяет место:
  доменная — `docs/models/domain/core/` (торговая с биржевым
  воплощением), `docs/models/domain/aggregate/` (без биржевой
  привязки), `docs/models/domain/other/` (прочая хранимая);
  нативная модель источника — `docs/models/integrations/{name}/`;
  external snapshot — `docs/models/externalSnapshot/`;
  persistence-проекция — `docs/models/persistence/`; модель нашего
  API — `docs/models/api/`. См.
  `.claude/decisions/model-layer-ontology.md`. Имя совпадает с
  Java-классом (где применимо).
- **Lifecycle (`docs/lifecycles/`)** — «через какие состояния
  проходит объект, кто и при каких событиях их меняет». Один
  объект = один файл lifecycle.
- **Mapping (`docs/models/mapping/<Сущность>.md`)** — «как сущность
  переходит между слоями» (native ↔ snapshot ↔ domain ↔ request) и
  «как резолвится её статус». Один файл = одна сущность; источники
  подразделами.
- **Процесс (`docs/processes/`)** — «как устроен этот процесс»:
  загрузка свечей, расчёт индикаторов и т. п. Поток шагов,
  участники, входы/выходы.
- **Правило (`docs/rules/`)** — «какое правило действует в
  системе»: инварианты, бизнес-правила. Не описывает объект
  целиком, фиксирует ограничение или норму поведения.
- **Словарная статья (`docs/dictionary/`)** — «что означает
  этот термин». Короткое определение. Для терминов-классов —
  определение + ссылка на `docs/models/domain/...`.

Если фрагмент тянет на несколько типов — разнести по местам,
каждая часть в свой файл. Если части неразрывны — положить в
основной тип, в других оставить ссылки.

### Компонент vs доменная модель

- **Компонент** (`docs/components/`) — Java-класс-исполнитель:
  сервис, валидатор, job, фабрика, оркестратор, resolver,
  executor. Выполняет работу (поведение).
- **Торговая модель с биржевым воплощением** (`docs/models/domain/core/`)
  — `Position`, `Order`, `AlgoOrder`, `BalanceContainer`.
- **Aggregate без биржевой привязки** (`docs/models/domain/aggregate/`)
  — `Deal`, `Strategy`.
- **Прочая хранимая модель** (`docs/models/domain/other/`) — без
  торговой бизнес-логики: свечи, индикаторы, аудит и т. п.
- Компонент не описывает бизнес — он работает с ним.

### Компонент vs процесс

- **Процесс** описывает, как идёт поток: вход, шаги, выход, кто
  запускает.
- **Компонент** описывает исполнителя: за что отвечает, какие у
  него границы.
- Поведенческие правила взаимодействия между компонентами живут
  в процессе, не в компоненте.
- **Материализация процесса как файла — не автоматическая.** Когда
  фрагмент опознан как кандидат в процесс (поток/оркестрация над
  несколькими сущностями, координация джобы — в т. ч. встроенный в
  другую задачу), при размещении прогоняется двухусловный критерий
  (собственное содержание про оркестрацию сверх lifecycle одной
  модели / точка композиции для других процессов). Если ни одно
  условие не выполнено — отдельный `docs/processes/<X>.md` не
  создаётся, содержание распределяется по владельцам (см.
  «Первоисточник правила» выше). Применение критерия —
  `place-knowledge`; обоснование —
  `.claude/decisions/process-materialization-criterion.md`.

### FSM-handler vs раздел lifecycle

- **FSM-handler** (per-status, Java-класс-исполнитель 1:1 с
  состоянием FSM) — компонент (`docs/components/<Handler>.md`).
  Привязка к статусу не делает handler частью структуры
  объекта-владельца — это исполнитель.
- **Механика самого статуса** (назначение, инварианты, переходы,
  recovery-переходы) — раздел lifecycle объекта-владельца
  (`docs/lifecycles/<Object>.md`), со ссылкой на handler-компонент.
- **Общая конструкция handler'а** (паттерн вроде «3 типа проверок»)
  — раздел оркестратора FSM в `docs/components/<StateMachine>.md`,
  не в lifecycle.
- Связь односторонняя: lifecycle ссылается на handler; handler на
  lifecycle не ссылается.
- Обоснование — в `.claude/decisions/fsm-handler-as-component.md`.

### Модель vs раздел внутри модели (гранулярность)

- **Отдельный файл** `docs/models/<Name>.md` — если объект
  **самостоятельная бизнес-сущность**.
- **Раздел внутри модели-родителя** — если объект не имеет ценности
  вне родителя.
- **Снапшоты** (`*ExternalSnapshot`) — не сущности, а external-поля
  модели + механизм обновления; описываются внутри модели.
- **Енумы** — раздел в модели, которой принадлежит атрибут. Енум,
  используемый несколькими моделями, размещается по критерию
  первоисточника (ниже).
- **Слой модели.** Самостоятельная domain-модель раскладывается по
  поддерево `docs/models/domain/`: торговая с биржевым воплощением →
  `core`; aggregate без биржевой привязки → `aggregate`; прочая
  хранимая (свечи, индикаторы, аудит) → `other`. Нативные модели
  источника, snapshot, mapping, persistence, rest — отдельные слои
  (см. `.claude/decisions/model-layer-ontology.md`, supersede
  `models-core-vs-other.md`).
- Обоснование и прогон по торговым сущностям — в
  `.claude/decisions/model-granularity.md`.

### Первоисточник правила: кто им владеет

Одно правило может ложиться сразу в несколько мест. Первоисточник —
**владелец** правила; остальные места дают короткое упоминание со
ссылкой, без повтора формулировки.

- **сущность** (`docs/models/domain/...` / `docs/lifecycles/`) —
  формула, атрибут, поведение конкретного объекта (формула live risk
  → `Position`; `resultProfit` → `Deal`);
- **сквозной слой** (`docs/rules/`) — правило про несколько сущностей
  без единственного владельца (запрет partial close; «ACK не runtime
  truth»);
- **mapping-слой** (`docs/models/mapping/<Сущность>.md`) — правило
  про преобразование между слоями (native ↔ snapshot ↔ domain ↔
  request) и статус-резолвинг;
- **правило источника** (`docs/integrations/{name}/rules/`) —
  инвариант или конвенция конкретного источника;
- **процесс** (`docs/processes/`) — правило имеет смысл только в
  контексте процесса;
- **компонент** (`docs/components/`) — правило про поведение
  конкретного исполнителя.
- Обоснование — в `.claude/decisions/rule-source-of-truth.md`.

### Знание источника vs доменное

- **Нативная модель источника** (`docs/models/integrations/{name}/`)
  — описывает поля DTO / модели API конкретного источника
  (инвентарь, used/unused). **Доменная модель**
  (`docs/models/domain/...`) — описывает бизнес-сущность, не
  привязанную к источнику.
- **Mapping между слоями** (`docs/models/mapping/<Сущность>.md`) —
  «как сущность переходит между слоями»; per-source детали в
  подразделах.
- **Контракт источника** (`docs/integrations/{name}/contracts/`) —
  endpoint'ы, лимиты, ACK-семантика. **Правило источника**
  (`docs/integrations/{name}/rules/`) — инварианты, adapter-константы,
  конвенции, специфичные для источника (например `tdMode=isolated`,
  OKX `reduceOnly` invariant). **Сквозное правило** (`docs/rules/`)
  — не зависит от источника.
- Source-specific факт не живёт в доменной модели — только в
  `docs/integrations/{name}/` и `docs/models/integrations/{name}/`.
  Обоснование — `.claude/decisions/model-layer-ontology.md`
  (supersede `client-layer-docs.md`).

### Runtime value object vs доменная/нативная модель / компонент

- **Runtime value object (`docs/components/models/`)** — носитель
  данных runtime-слоя: не persisted, без identity, без lifecycle
  (`CalculationContext`, `DealContext`, `MarketPriceData`,
  `Calculated*`, `RiskValidationResult`).
- **vs доменная модель** — доменная persisted и имеет identity /
  жизненный цикл; RVO — нет.
- **vs нативная модель источника** — RVO не привязан к конкретному
  источнику; нативная модель источника описывает поля API источника.
- **vs компонент** — RVO это структура (данные), компонент —
  исполнитель (поведение). Связь односторонняя: компонент знает про
  RVO, RVO про компонент не знает.
- Обоснование — в `.claude/decisions/runtime-value-object.md`.

## Пометка

Скилл в обкатке. Признаки и перечень типов дополняются по
ходу — через накопление открытых вопросов и оформление
решений.
