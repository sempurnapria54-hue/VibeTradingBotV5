# Ревью тестов

## На какой вопрос отвечает этот файл

Как именно сделать адверсариальное ревью тест-плана, коллекции,
код-тестов и отчёта прогона (фокус `test`).

## Когда применять

Этапы **REVIEW плана/коллекции**, **REVIEW код-тестов** и **REVIEW
отчёта** процесса `.claude/processes/source-api-testing.md`. Фокус роли
`reviewer` (`.claude/agents/reviewer.md`). В отличие от прочих фокусов
ревьюера, привязан не к под-шагу роадмапа, а к этапам процесса
тестирования API источника.

## Назначение и границы

Адверсариальный проход свежим взглядом. Цель — найти проблему, а не
подтвердить корректность. Что находит — **не чинит, не размещает, не
решает**: формулирует замечание и возвращает автору (`tester`).

## Применения

### Ревью тест-плана и коллекции (вместе)

План и построенная по нему коллекция ревьюятся вместе — общий жизненный
цикл, замечания правят оба.

- **Полнота покрытия по манифесту (инвариант полноты)** — план
  перечисляет **каждый** in-perimeter запрос (`есть-док`/`создан`/
  `обновлён`); пропущенная строка периметра = находка. Под `/raw` тело
  строится руками — наличие метода клиента роли не играет
  (`source-api-target-rebase.md` §D).
  **Колонка покрытия манифеста** согласована с планом (методы плана →
  «в плане»/«в коде»); расхождение = находка.
- **Применён ли порождающий негатив на КАЖДЫЙ запрос** — на каждый
  запрос, **включая write/мутацию** (place/cancel/close), выведены
  применимые негативные категории (битый параметр, имя ключа, значение
  вне домена, несущ. id, дубль, отмена отменённого, фильтр вне окна,
  auth, состояние-конфликт), скрещены с документированными кодами ошибок;
  не голый happy path. Запрос без негатива = находка.
- **Вариант-покрытие по типу-дискриминатору** — запрос с
  `ordType`/`conditionType`/семьёй cancel покрыт по **каждому in-perimeter
  варианту** (прямой + негатив); под `/raw` вариант достижим телом
  конверта. Пропущенный вариант = находка.
- **Соблюдён ли гейт достижимости** — недостижимый прямой кейс (архивные
  окна) помечен отказом + причиной, покрыт негативом; ожидание не
  выдумано.
- **Цель — сырьё.** Проверки стоят на **сырых полях JSON** ответа OKX
  (`OkxApiResponse<JsonNode>`: `b.code`/`b.msg`/`b.data[i].sCode`/
  `b.data[i].<field>`), не на снапшоте/`ExchangeAck`/типизированном DTO.
  Запрос идёт через A2-passthrough — generic `/raw` (подпись/креды не в
  Postman).
- **Осмысленность кейсов** — кейс проверяет реальный риск, не тавтологию.
- **Корректность графа предусловий** — выход кейса даёт предусловие
  следующего; цепочка не опирается на отсутствующее состояние.
- **Teardown в каждом кейсе** — самодостаточен, оставляет биржу чистой;
  покрывает все созданные кейсом состояния, не отложен в общий финал.
- **Форма «метод → кейсы → таблица» и соответствие план ↔ коллекция** —
  метод = заголовок, кейс = подзаголовок + своя таблица (класс на метод,
  тест на кейс); коллекция зеркалит структуру (папка на метод, запрос/
  под-папка на кейс), один-к-одному.
- **Цена с биржи, минимальный риск** — live-цена сырым `GET /market/ticker`
  через `/raw`, ордер заведомо неисполнимый; цена не «из воздуха».

### Ревью код-тестов

Код-тесты (`test-code`) — поверхность ревью наравне с планом.

- **Покрытие плана** — каждый кейс плана → код-тест; механика бьёт в тот
  же A2-passthrough, что коллекция (1:1).
- **Профиль-гейт** — структурный no-prod (на prod не идут); `@Tag`
  изолирует живые тесты от офлайн unit-тестов.
- **Teardown по жизненному циклу** — `@AfterEach`/try-finally чистит
  созданное даже при провале тела; после теста биржа чистая.
- **Проверки на сырых полях JSON** (`OkxApiResponse<JsonNode>`:
  `b.code`/`b.data[i].sCode`/`b.data[i].<field>`) — AssertJ по
  используемым полям + кодам ошибок, не подгонка под текущее поведение
  (фейл по дизайну = находка).

### Ревью отчёта прогона

- **Качество фиксации** — по каждому кейсу видно ожидание, факт, вердикт;
  факт не подогнан под ожидание.
- **Полнота наблюдений** — зафиксированы расхождения и неожиданности, не
  только pass/fail; раздел «расхождения с апидоками» заполнен (вход C3).
- **Обоснованность вердиктов** — вердикт следует из факта;
  незадокументированное помечено находкой, не закрыто выдумкой.

## Петля с tester

Ревью — петля: браковка → правит **автор** (`tester`) → перепроверка.
Ревьюер не правит сам. Неоднозначное (спорная классификация замечания,
пробел спеки) уходит маршрутом эскалации процесса — к интегратору;
пользователю — только дефицит `подтверждение`.
