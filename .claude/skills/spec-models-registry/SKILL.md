# Скилл: работа с реестром канонических имён моделей

Реестр имён бизнес-моделей живёт в `docs/spec/MODELS.md`. Этот
скилл описывает правила работы с реестром: формат записей,
операции, границы содержания, связи с другими артефактами.

Полный список моделей (текущий состав) — в самом `MODELS.md`.
Этот скилл сюда состав не дублирует.

## Назначение MODELS.md

Три функции:

1. **Навигационная точка входа в `docs/spec/`.** При заходе в
   spec первое, что видит читатель — карту моделей: имя + короткое
   описание + ссылка на model-документ (когда мигрирован).
2. **Реестр канонических имён для Knowledge Curator.** Curator при
   ревью использует MODELS.md как авторитетный список имён
   бизнес-моделей: упоминание имени в документе, у которого
   целевой model-документ ещё не создан — забегающая ссылка
   (по ADR-0009 §6).
3. **Источник прогресса миграции по моделям.** Стартовое состояние —
   все entries как заглушки (только имя + описание). По мере
   миграции кластера соответствующие entries получают ссылки на
   созданные model-документы. Прогресс по моделям виден напрямую.

Прогресс по кластерам и сквозным концепциям — отдельный артефакт
`.claude/planning/migration-tracker.md`, не в MODELS.md.

## Структура файла
Реестр канонических имён моделей
[короткая шапка: назначение + ссылка на этот скилл]
Core

<Имя> — <одна короткая фраза-описание>. [Ссылка после миграции]
<Имя> — <одна короткая фраза-описание>. [Ссылка после миграции]
...

Runtime

<Имя> — <одна короткая фраза-описание>. [Ссылка после миграции]
...
Два раздела: Core и Runtime, по делению ADR-0006 §1 (см. также
`docs/conventions/terminology.md`). Внутри раздела — алфавитный
порядок имён.

## Формат записи

Одна запись = одна строка списка. Структура:

- **Имя модели** (bold, точное PascalCase-имя).
- Тире.
- Одна короткая фраза-описание (1-2 коротких предложения).
- Если модель мигрирована — ссылка на model-документ в формате
  markdown link.

Пример заглушки (до миграции):

Strategy — конфигурация торгового алгоритма: правила входа, выхода, риск-менеджмента.


Пример после миграции:

Strategy — конфигурация торгового алгоритма: правила входа, выхода, риск-менеджмента. См. models/core/Strategy.md.
Жёсткое правило: первое слово после имени и тире — начало
определения. Должно отвечать на «что это» без отсылок.

## Правила формата (что класть в описание, что нет)

**В описание идёт:**

- Что модель собой представляет в системе (одна-две короткие
  фразы).
- Ключевая роль или поведение, если оно определяет суть модели
  (например, «корневой агрегат торговой логики», «не persisted —
  пересобирается из контекста»).

**В описание НЕ идёт:**

- **Перечисление полей или вложенных моделей.** Это уровень
  model-документа.
- **Примеры значений или типов.** Это тоже уровень
  model-документа (например, конкретные значения enum'ов,
  список возможных статусов).
- **Ссылки на ADR.** Реестр — это «карта моделей», не «карта
  решений». Ссылки на ADR живут в model-документах, где уместен
  раздел «История решений».
- **Технические детали реализации.** JPA-аннотации, JSONB-структура,
  имена таблиц — это уровень технической документации, не реестра.

**Язык.** Используем «хранимое» вместо «persisted», «доменная
модель» вместо «entity» (по конвенциям `docs/conventions/terminology.md`).

## Операции

### Добавление новой модели в реестр

Применяется, если в проекте появляется новая бизнес-модель
(см. правило B1 в `working-with-claude.md` Принцип 4).

1. Определи, к какому разделу относится: Core (по тесту ADR-0006 §1 —
   хранимое, имеет identity, переживает рестарт) или Runtime
   (живёт в рамках операции/цикла).
2. Сформулируй одну короткую фразу-описание по правилам выше.
3. Добавь строку в соответствующий раздел в алфавитном порядке.
4. Если соответствующий model-документ ещё не создан — запись
   остаётся заглушкой (без ссылки). Если документ создан в той же
   сессии — добавь ссылку сразу.

### Обновление заглушки на ссылку (после миграции модели)

Применяется при миграции кластера, когда соответствующий
model-документ создан.

1. Найди запись модели в нужном разделе.
2. В конец описания добавь ссылку:  
   `См. [`models/core/<Имя>.md`](models/core/<Имя>.md).`
   (или `models/runtime/` для runtime-моделей).
3. Описание модели обычно остаётся как было (короткая фраза). Если
   при миграции оказалось, что описание неточное или устарело —
   обнови.

### Удаление модели из реестра

Применяется редко — если модель упразднена в проекте (а не просто
переименована или поглощена другой).

1. Убедись, что упразднение зафиксировано ADR.
2. Удали строку из реестра.
3. Проверь, что в `docs/spec/` нет model-документа упразднённой
   модели (или он перемещён в `docs/deprecated/` по правилам
   проекта).

### Переименование модели

1. Изменение имени модели должно быть зафиксировано ADR (это
   значимое решение, влияющее на всю кодовую базу и
   документацию).
2. В реестре — обновить имя в записи, переместить в алфавитный
   порядок по новому имени.
3. Связные обновления — все упоминания старого имени в других
   spec-документах, в коде, в названиях файлов.

## Границы — что НЕ идёт в реестр

- **Терминологические соглашения** («доменная модель», «aggregate
  root» и подобные) → `docs/conventions/terminology.md`.
- **Сквозные концепции** (kill-switch, orphan, freshness, reconcile,
  FSM сделки, anomaly) → собственные spec-документы по жанрам
  (invariant / process / lifecycle). В реестр моделей не идут —
  это не модели.
- **Имена джоб, сервисов, executor'ов, фабрик, валидаторов,
  резолверов** → упоминаются в process-документах как роли, не как
  модели. В реестре отсутствуют.
- **Вложенные модели** (по ADR-0006 §1: модели, существующие
  только в составе другого бизнес-объекта, например
  StopLossSettings внутри Strategy) → разделами внутри
  model-документа бизнес-объекта-контейнера. В реестре отдельной
  строкой не появляются.
- **Прогресс миграции по кластерам и концепциям** →
  `.claude/planning/migration-tracker.md`.
- **Открытые вопросы по моделям** →
  `.claude/questions/open-questions.md`.

## Связи с другими артефактами

- **`docs/conventions/terminology.md`** — соглашения о именовании
  и деление Core vs Runtime.
- **`.claude/working-with-claude.md` Принцип 4** — правило «новый
  термин — куда фиксировать»: имя бизнес-модели идёт в MODELS.md
  + model-документ.
- **`.claude/adr/0007-spec-structure.md` §3** — обоснование
  расположения MODELS.md в корне `docs/spec/` и его функций.
- **`.claude/adr/0009-domain-migration-strategy.md` §6, §9** —
  роль реестра при миграции, использование Curator'ом для
  идентификации забегающих ссылок.
- **Скилл `spec-cluster-migration`** (создаётся позже) — при
  финализации кластера обновляет MODELS.md, ссылается на этот
  скилл за правилами формата.
- **Knowledge Curator** — при ревью проверяет: используются ли в
  spec-документах имена из реестра, есть ли модели, упомянутые
  в spec, но не в реестре, и наоборот.

## Что не покрывает этот скилл

- **Структура и наполнение model-документов** — за это отвечает
  `spec-document-workflow` (стандарт документа `docs/spec/` по
  ADR-0002) и шаблоны model.
- **Принципы деления core / runtime** — формальный критерий в
  ADR-0006 §1, расширенное объяснение в
  `docs/conventions/terminology.md`.
- **Процедура миграции кластера целиком** — скилл
  `spec-cluster-migration` (создаётся позже).
