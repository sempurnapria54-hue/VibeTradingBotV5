# Построение тест-плана

## На какой вопрос отвечает этот файл

Как именно построить тест-план и кейсы по сырью API источника.

## Когда применять

Этап **DESIGN** процесса
`.claude/processes/source-api-testing.md`. Роль — `tester`.

## Назначение и границы

Построение тест-плана и кейсов контура тестов API источника на базе
универсального шаблона (`.claude/templates/docs/test-plan.md`). Скоуп —
**сырьё биржевого запроса/ответа** через единственный generic-эндпоинт
`POST /api/proxy/okx/raw` (`OkxRestClient.dispatch` под капотом,
`source-api-target-rebase.md` §D): ассерты — по **сырым полям JSON**
ответа OKX (`OkxApiResponse<JsonNode>`: `b.code`, `b.data[i].sCode`,
`b.data[i].<field>`). Наша граница (снапшоты/мапперы), типизированные DTO
и домен — **вне контура** (продуктовый слой / отдельные юнит-тесты).
Контур — **demo/non-prod** (prod вне контура).

Скилл строит план; он его **не ревьюит** (это `reviewer`, фокус
`test-review`), не материализует в коллекцию (`test-collection`), не
пишет код-тесты (`test-code`) и не прогоняет (`test-run`).

## Известный скелет

- **Полнота покрытия — по манифесту.** Источник набора запросов —
  манифест покрытия источника (`docs/integrations/{name}/coverage-manifest.md`,
  провенанс офдок). План перечисляет **каждый запрос в периметре**
  (строки `есть-док`/`создан`/`обновлён`); `вне-периметра` /
  `сознательно-вне` исключены. Новый манифест не заводится.

- **Весь in-perimeter — через `/raw`.** Тело конверта `{method, path,
  query, body, signed}` строится **руками по контракту**, поэтому
  покрывается **каждая** in-perimeter строка манифеста — наличие
  типизированного метода клиента роли не играет. Прежняя метка
  `client-coverage-gap` («в периметре, но клиент метод не строит →
  покрыть нельзя») **снята** (`source-api-target-rebase.md` §D): под
  `/raw` таких нет. На каждую in-perimeter строку — прямой кейс (если
  достижим, см. гейт) + негатив.

- **На каждый запрос — прямой кейс + широкий негатив. Негатив — на
  КАЖДЫЙ запрос, включая write/мутацию** (place / cancel / close), не
  только read. Прямой кейс — happy path операции (при достижимом
  предусловии). Негатив — по порождающей методологии (ниже).

- **Вариант-покрытие по типу-дискриминатору.** Запрос с полем-
  дискриминатором, по которому ветвится поведение или семья
  (`ordType` ordinary order — limit / market; `conditionType` → `ordType`
  algo — conditional / oco / move_order_stop; семья cancel — ordinary
  `cancel-algos` / advance `cancel-advance-algos`), покрывается **по
  каждому in-perimeter варианту**: прямой кейс варианта + применимый к
  нему негатив. Под `/raw` тело конверта строится руками, поэтому вариант
  достижим независимо от того, собирает ли его типизированный клиент —
  прежний **вариант-gap** (из-за типизации прокси) **снят**. Ограничение
  множества — продуктовый периметр (вне-периметра матрицу биржи не тащим),
  не возможности клиента.

- **Инвариант полноты.** Каждый in-perimeter запрос манифеста покрыт
  контуром (через `/raw`). Новый in-perimeter запрос → требование
  покрытия (прямой + негатив, по вариантам). Чек-лист инварианта —
  **колонка статуса покрытия в манифесте** (см. процесс контура,
  стадии «в плане» / «в коде»; метка `coverage-gap` снята).

- **Форма — метод → кейсы → таблица.** Структура плана: **метод сырого
  клиента — заголовок** (`## Mn. method`), **кейс — подзаголовок**
  (`### Mn.k …`: прямой / каждый негатив / каждый вариант / цепочка),
  **в каждом кейсе — своя таблица** (строка = запрос кейса: проверки +
  ожидание). Цель формы — **прямой маппинг на код: класс на метод, тест
  на кейс**. Детальная форма — `.claude/templates/docs/test-plan.md`.

- **Кейс несёт предусловие-состояние на бирже.** Операция требует
  состояния, в котором её осмысленно проверять: `getOrder` —
  исполненного/живого ордера; cancel несуществующего — **отсутствия**
  ордера (негатив). Stateful-кейс **создаёт реальную demo-сущность**
  (ордер/позицию/algo) — иначе её не проверить.

- **Цепочки по графу предусловий, не плоская матрица.** Выход одного
  кейса — предусловие следующего: `place → проверка place → getOrder на
  этом ордере → cancel → проверка cancel → негативный getOrder на
  отменённом`. Сложные запросы (close-position) — через цепочку
  (исполненный ордер → позиция → close).

- **Негатив без состояния — отдельный дешёвый слой, гоняется первым.**
  Не требует постановки состояния (cancel несуществующего, getOrder по
  фейку), даёт быстрый сигнал до дорогих цепочек.

- **Teardown в каждом кейсе.** Кейс самодостаточен и **обязан оставлять
  биржу чистой**: teardown проектируется внутри кейса (вместе с
  цепочкой), не общим финалом. После любого кейса — ни висящих ордеров,
  ни позиций, ни иных созданных сущностей.

- **Цена ордера — с биржи, минимальный риск.** Кейс, ставящий ордер, не
  берёт цену «из воздуха»: live-цена снимается с биржи **сырым
  `GET /market/ticker` через `/raw`** (`b.data[0].last`/`ask`/`bid`),
  ордер ставится от неё **заведомо неисполнимым, с минимальным риском**.
  Под `/raw` достижим — surface-gap'а нет.

- **Консультации интегратора — front-load, итеративно.** Предусловия,
  ACK-семантика, документированные коды ошибок, конфликты/пробелы спеки
  — у `integrator` до фиксации кейса. Незадокументированное не
  выдумывается; помечается пробелом / находкой интегратору.

## Порождающая методология негатива

Не фиксированный список — **процедура вывода** применимых негативных
категорий по типу запроса; тестировщик добавляет свои кейсы.

**Категории-генераторы:**

- **битый параметр (значение)** — нечисло там, где число; неверный
  формат (битый `instId`); вне диапазона;
- **имя параметра/поля** — неизвестный / опечатанный ключ;
- **значение вне домена** — неизвестный `side`/`ordType`/`instType`;
  нулевой / отрицательный размер;
- **отсутствие обязательного** — пропуск обязательного параметра/поля;
- **несуществующий идентификатор** — фейковый `ordId`/`algoId`/`instId`;
- **дубль идентификатора** — повторный `clOrdId`/`algoClOrdId`;
- **удаление удалённого / отмена отменённого** — cancel отменённого,
  get отменённого, close несуществующей позиции;
- **дата-фильтр из будущего / вне окна** — `after`/`before`-якорь в
  будущем либо за окном хранения;
- **авторизация** — пустые / битые креды, недостаточный permission;
- **состояние-конфликт** — reduce-only без позиции и т. п.

**Процедура вывода для запроса:** (1) перечислить параметры и требуемое
состояние; (2) на каждый — инстанцировать применимые категории
(read-only GET → несущ. id, битый параметр, вне-окна фильтр, неизвестный
ключ, пропуск обязательного, auth; write POST → плюс значение вне
домена, пропуск обязательного поля тела, дубль id, состояние-конфликт,
отмена-отменённого для cancel/close); (3) скрестить с документированными
кодами ошибок контракта (у `integrator`); (4) добавить суждение-кейсы.

## Гейт достижимости прямого кейса

Часть эндпоинтов отдаёт архивные сущности с задержкой/окном
(`orders-history-archive` 3м, `fills-archive` async 3м+, закрытые
позиции ~30д — `integration-okx.md` §Известные ограничения). Прямой
кейс такого эндпоинта требует сущности в окне, недостижимой в свежем
demo-рантайме.

На каждый прямой кейс — оценить достижимость предусловия в рантайме
контура (архивные окна, async-задержки, ~30д-позиции, история свежему
аккаунту недоступная):

- достижим → прямой кейс остаётся (возможно, через цепочку);
- недостижим → **отказ от прямого кейса**, покрытие только негативом,
  **явное указание отказа + причины** в шапке кейса (и далее в отчёте).
  Ожидание недостижимого прямого кейса не выдумывается.

**Исполняемые типы — достижимость через исполнение.** Где прямой кейс
требует факта исполнения (fill, открытая позиция), а тип запроса
**исполняем** (market-ордер), достижимость берётся **исполнением**:
минимальный реальный market-ордер на demo → fill → позиция → зависимые
прямые кейсы (`getFills` / `getFillsHistory` / `getPositions` /
`closePosition` / `getOrderHistory` с filled) → teardown (закрытие
позиции). Это снимает отказ по достижимости для fills/позиций. Отказ
остаётся только там, где исполнение невозможно или окно архивное и
недостижимо на свежем demo (3м-архивы, ~30д-позиции, история, которой у
свежего аккаунта нет).

## Гранулярность по триггеру

- **новая биржа** → полный план по **всему in-perimeter периметру
  манифеста** (через `/raw`);
- **новый эндпоинт** → точечное расширение существующего плана;
- **изменение контракта** → регрессия затронутого.

## Вход / Выход

- **Вход:** манифест покрытия (`docs/integrations/{name}/coverage-manifest.md`,
  источник набора), контракты (`docs/integrations/{name}/contracts/`),
  правила (`docs/integrations/{name}/rules/`), поверхность сырого
  клиента (`OkxRestClient`), скоуп прогона (триггер), консультации
  интегратора.
- **Выход:** тест-план в `.claude/tests/{testType}/{source}/` по
  шаблону — кейсы (прямой + негатив), цепочки, teardown, пометки
  достижимости; среда — demo/non-prod; поле «факт» пустое до RUN.
