# Построение тест-плана

## На какой вопрос отвечает этот файл

Как именно построить тест-план и кейсы по контрактам источника.

## Когда применять

Этап **DESIGN** процесса
`.claude/processes/source-api-testing.md`. Роль — `tester`.

## Назначение и границы

Построение тест-плана и кейсов контура тестов API источника по
контрактам источника на базе универсального шаблона
(`.claude/templates/docs/test-plan.md`). Скоуп — **API биржи через
наш клиентский слой**; домен (Deal, FSM, executors) вне охвата.

Скилл строит план; он его **не ревьюит** (это `reviewer`, фокус
`test-review`) и не прогоняет (это `test-run`). Исполняемую
Postman-коллекцию по плану строит отдельный скилл
`test-collection` (тот же этап DESIGN, та же роль `tester`).

## Известный скелет

Алгоритм построения (форма деталей снимается с первого пилота, см.
«Доработка»):

- **Полнота покрытия.** План перечисляет **всю** интеграционную
  поверхность источника — каждый запрос клиентского слоя к источнику
  — и заводит осмысленный кейс на каждый. Не подмножество: пропуск
  запроса — пробел плана, а не выбор объёма (объём режется только
  триггером, см. «Гранулярность по триггеру»).

- **Форма — таблица на кейс.** Один кейс = одна отдельная таблица,
  каждый запрос кейса = строка таблицы (с его проверками и
  ожиданием). Детальная форма — `.claude/templates/docs/test-plan.md`.

- **Кейс несёт предусловие-состояние на бирже.** Операция требует
  состояния, в котором её осмысленно проверять: `getPosition` —
  исполненного ордера; amend/replace — живого неисполненного
  ордера; cancel несуществующего — **отсутствия** ордера
  (негативный кейс).

- **План строится цепочками по графу предусловий, не плоской
  матрицей.** Выход одного кейса — предусловие следующего:
  `place → проверка place → на этом же ордере getOrder → cancel →
  проверка cancel → негативный getOrder на отменённом`. Одно
  состояние обслуживает несколько кейсов — цепочка экономит
  постановку состояния.

- **Негативные кейсы без состояния — отдельный дешёвый слой,
  гоняются первыми.** Не требуют постановки состояния (cancel
  несуществующего, getOrder по фейковому id), стоят дёшево, дают
  быстрый сигнал до дорогих цепочек.

- **Teardown в каждом кейсе.** Каждый кейс самодостаточен и **обязан
  оставлять биржу чистой**: teardown проектируется внутри кейса
  (вместе с его цепочкой), а не общим финальным шагом. После любого
  кейса — ни висящих ордеров, ни позиций, ни иных сущностей.

- **Цена ордера — с биржи, минимальный риск.** Кейс, ставящий ордер,
  не берёт цену «из воздуха»: live-цена снимается с биржи (ticker /
  mark), ордер ставится от неё **заведомо неисполнимым, с минимальным
  риском** — цель проверить интеграцию, не потерять деньги (критично
  на prod). Зависимость-**предусловие**: интеграция отдаёт live-цену
  через прокси. Нет такого эндпоинта — surface-gap, закрываемый при
  регенерации (или заводимый находкой): кейс его помечает, цену не
  выдумывает.

- **Два уровня кейсов:** эндпоинт-кейсы (happy path / ошибки /
  границы / ACK-семантика одной операции) и цепочки (связные
  последовательности по графу предусловий).

- **Консультации интегратора — front-load, итеративно.** Предусловия,
  ACK-семантика, документированные коды ошибок, конфликты/пробелы
  спеки берутся у `integrator` (`.claude/agents/integrator.md`) до
  фиксации кейса. Незадокументированное поведение — не выдумывается;
  помечается как пробел / находка интегратору.

## Гранулярность по триггеру

Объём построения — по триггеру процесса:

- **новая биржа** → полный план по **всей интеграционной поверхности**
  источника (кейс на каждый запрос клиентского слоя);
- **новый эндпоинт** → точечное расширение существующего плана;
- **изменение контракта** → регрессия затронутого (пересобирается
  только задетая цепочка / кейс).

## Вход / Выход

- **Вход:** контракты источника (`docs/integrations/{name}/contracts/`),
  правила источника (`docs/integrations/{name}/rules/`), скоуп
  прогона (триггер), консультации интегратора.
- **Выход:** тест-план в `.claude/tests/{testType}/{source}/` по
  шаблону `.claude/templates/docs/test-plan.md` — кейсы, цепочки,
  teardown, среда (demo / prod read-only); поле «фактический
  результат» пустое до RUN.

## Доработка

Процедура и детальные поля кейса/плана дорабатываются по ходу;
форма снимается с первого пилотного плана. Спекулятивную процедуру
здесь не фиксируем.
