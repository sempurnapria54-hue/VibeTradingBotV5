# Сквозная проверка концепции

## На какой вопрос отвечает этот файл

Как именно сделать сквозную проверку концепции доков под
конкретный шаг роадмапа.

## Когда применять

Под-шаг `DOCS_CHECK_N` процесса
`.claude/processes/roadmap-step-execution.md`. Цель — найти
пробелы в концепции, которые помешают писать корректный код
**этого** шага. Не аудит концепции в целом, не проверка «модели
вообще» — проверка под потребность кода шага.

Закрытие найденных пробелов — отдельный под-шаг (`GAPS_CLOSE_N`),
не часть этой процедуры.

## Вход

- Номер фазы и шага роадмапа.
- Краткая формулировка шага (из `phase-N.md`).
- Понимание, какой код будет писаться на под-шаге `CODE` — это
  определяет, какие модели/процессы/правила релевантны и насколько
  глубоко.

## Порог глубины — функциональный

Фиксируется ровно то, что нужно коду этого шага. Решение по
каждой модели / процессу / правилу принимается **по полям и
поведению**, которое код шага реально трогает, а не «модель
целиком да/нет».

### Тест по полю / структуре

Глубина «нужны типы / nullability / структура / ограничения»
включается, если код шага хотя бы одно из:

- **конструирует или заполняет инстанс** модели;
- **читает конкретные поля** или ветвится по их значениям;
- **маппит из/в внешнее представление** (например, OKX DTO →
  доменная модель или обратно);
- **(persisted) пишет схему хранения** (тогда обязательны типы,
  nullability, ограничения, индексы — то, что попадает в
  миграцию).

### Когда хватает name-level

Если модель в коде шага:

- только **упоминается** (имя в комментарии, в сигнатуре в
  качестве типа без чтения полей);
- **передаётся насквозь** (параметр/поле, не разбирается);
- **объявлена «на потом»** (placeholder под будущий шаг),

— достаточно name-level (модель существует, имя такое-то).
Структура, типы, nullability откладываются до того шага, который
эти поля действительно трогает.

### Гранулярность — по полю, не по модели

Один и тот же объект может попадать в разные пороги по разным
полям: одно поле код шага читает (нужны тип/nullability), второе
только передаётся насквозь (хватает name-level). Это нормально;
фиксируется в отчёте по полям.

## Типы пробелов

При обходе доков фиксируем три типа пробелов:

1. **Несогласованности между доками** — одно и то же утверждается
   по-разному в разных местах; формула/набор полей/правило
   расходятся; ссылка ведёт в файл, где описано не то.

2. **Name-level без структуры (там, где нужна структура).**
   Модель / процесс / правило упоминается по имени, но структуры
   (полей, состояний, шагов, формулировки), которая нужна коду
   шага по функциональному порогу, нет.

3. **Неотвеченные вопросы.** Открытый вопрос из
   `.claude/work/questions/open-questions.md` или из локальных
   вопросов прошлых задач (`.claude/work/questions/tasks/`,
   архивные `tasks-*.md`), который блокирует написание кода
   шага.

## Сверка с `open-questions.md`

Отдельным проходом — пройти по `open-questions.md`. По каждому
открытому вопросу: блокирует ли он код этого шага? Если да —
помечается в gap-отчёте как блокер, со ссылкой на вопрос.

Незаблокированные открытые вопросы не выписываются — они уже
живут в своём файле и сюда не дублируются.

## Шаги обхода

1. **Определить охват.** По формулировке шага собрать список
   релевантных доков: модели (`docs/models/...`), lifecycles
   (`docs/lifecycles/`), процессы (`docs/processes/`), компоненты
   (`docs/components/` — executors, сервисы; `docs/components/models/`
   — компонентные модели), правила (`docs/rules/`), словарь
   (`docs/dictionary/`), интеграции (`docs/integrations/{name}/`),
   mapping (`docs/models/mapping/`). Что код шага реально затронет —
   то и в охват. Что не затронет — вне охвата (помечается, но не
   проверяется).

2. **Проход по охвату.** По каждому доку в охвате — применить
   функциональный порог к содержанию: достаточно ли того, что
   есть, для кода шага. Найденное фиксировать в отчёт как пробел
   соответствующего типа.

3. **Сверка с открытыми вопросами.** Отдельный проход по
   `open-questions.md` (см. выше).

4. **Сформировать gap-отчёт** (см. ниже «Выход»).

## Размещение знания — не здесь

`concept-review` помечает пробел, но **не решает**, где его
закрывать (тип дока, файл, новый или существующий). Это работа
штатного потока на под-шаге `GAPS_CLOSE_N`:

- `.claude/skills/recognize-knowledge.md` — опознать кандидат;
- `.claude/skills/classify-area.md`,
  `.claude/skills/classify-type.md`,
  `.claude/skills/classify-theme.md` — определить
  область / тип / тему;
- `.claude/skills/place-knowledge.md`, `.claude/rules/structure.md`
  — разместить;
- развилки «отдельный файл или раздел»: для моделей —
  `.claude/decisions/model-granularity.md`; для процессов —
  `.claude/decisions/process-materialization-criterion.md`;
  компонент vs процесс — `.claude/decisions/component-vs-process.md`.

В gap-отчёте — формулировка пробела и его тип, но не
предписание места.

## Эскалация

Неоднозначные случаи — в чат, решает пользователь на под-шаге
`GAPS_CLOSE_N`:

- блокер или не блокер для шага (когда функциональный порог
  трактуется на грани);
- насколько глубоко достаточно (когда «name-level» и «структура»
  оба правдоподобны);
- спорная классификация пробела (несогласованность vs
  name-level vs открытый вопрос).

Не угадывать — выписать в отчёт с пометкой «эскалация», движение
по разрешению идёт через чат.

## Выход

Gap-отчёт — progress-файл активной задачи (название итерации
включает номер `N`, например
`.claude/work/progress/phase-1-step-1-docs-check-1.md`).

Структура отчёта:

- **Охват.** Какие доки проверялись, какие были вне охвата (и
  почему).
- **Пробелы по типам.** Списком: несогласованности; name-level
  без структуры; неотвеченные вопросы.
- **Блокирующие открытые вопросы.** Из `open-questions.md`, со
  ссылками.
- **Эскалации.** Спорные случаи, ожидающие решения в чате.
- **Сводка.** Сколько пробелов, сколько эскалаций, чисто или
  нужен следующий `DOCS_CHECK_{N+1}` после `GAPS_CLOSE_N`.

После сборки отчёта — короткое сообщение в чат: путь к отчёту,
сводка, рекомендация (`GAPS_CLOSE_N` нужен / шаг готов к `CODE`).

## Связи

- Процесс шага роадмапа — `.claude/processes/roadmap-step-execution.md`.
- Скилл ведения прогресса роадмапа —
  `.claude/skills/update-roadmap-progress.md`.
- Каркас классификации (для `GAPS_CLOSE_N`) —
  `.claude/processes/knowledge-classification.md`.

## Пометка

Скилл новый, обкатывается на под-шаге `DOCS_CHECK_1` шага 1
Фазы 1. Уточнения формулировок (особенно функционального порога
и типов пробелов) — по итогам первых прогонов.
