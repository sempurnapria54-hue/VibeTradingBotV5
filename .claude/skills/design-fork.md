# Проработка развилки конструктивным владельцем

## На какой вопрос отвечает этот файл

Как именно конструктивный владелец прорабатывает развилку/находку до
вариантов с креном.

## Когда применять

Под-шаг `GAPS_CLOSE_N` (и подготовка эскалаций на `DOCS_CHECK_N`):
находка или узел gap-отчёта маршрутизированы владельцу по карте
(`.claude/processes/question-delegation.md`) — концепт →
`solution-designer` (первый носитель скилла), торговые →
`trading-specialist`, интеграционные → `integrator`. Процедура общая;
опора и эвристики §ниже — концептные, у других владельцев своя опора
(корпус, офдок).

Роль задаёт стойку и границы; этот скилл — рабочую процедуру. Что
владелец **финализирует**, а что предлагает — ступень категории
(`question-delegation.md`), скилл ступень не меняет.

## Вход

- Находка/узел из gap-отчёта: формулировка + **список цитат
  (носителей)** + вклады всех линз узла
  (`.claude/templates/docs/gap-report.md`).
- Owner-док затронутого концепта (источник истины по нему).

## Шаги

### 1. Грунт

Открыть owner-док и **каждую цитату находки** (не пересказ линзы).
Собрать, на чём стоит текущая редакция: какое решение/прецедент её
породили (`decisions/`), не сменился ли контекст этого решения.

### 2. Генерация альтернатив

Собрать варианты ответа. Обязательные проверки состава:

- **Ось структурной свободы** (`.claude/templates/docs/gap-report.md`
  §«Ось структурной свободы»): не является ли развилкой **сам выбор
  структуры** — новый компонент, новая сущность, новый радиус, другая
  модель угроз. Вариант «переструктурировать» — в набор наравне с
  «починить внутри», даже когда чинящий вариант выглядит достаточным.
  Ось обязательна с обеих сторон машины: линза проверяет её при
  генерации вариантов находки, владелец — при проработке.
- **Вклады других линз узла** — уже предложенные альтернативы входят в
  набор, не пересобираются заново.

### 3. Крен

По каждому отвергаемому варианту — **чем** отвергнут:

- **принципом-отбрасывателем** (правило, инвариант, зафиксированное
  решение — с указателем) → вариант отброшен, исход `выводимо`;
- **суждением** (цена, вкус, оценка вероятности) → вариант остаётся в
  наборе, исход `варианты-с-креном`; суждение помечается явно.

Нет принципа ни у одного отбрасывания — крена нет: явная запись
«настоящий product/policy-выбор пользователя». Формула «X верно по
существу, чинится Y» — крен, не вывод
(`question-delegation.md` §Калибровка).

### 4. Заполнение находки

Поля «Кто ответил + трассировка» (что открывал, как рассуждал),
«Ответ», «Варианты», «Целевой док» — по формату
`.claude/templates/docs/gap-report.md`. Трассировка обязана называть
owner-док и пройденные цитаты.

## Эвристики (концепт-владелец)

Переносимые приёмы при генерации и переоценке вариантов (кейсы —
иллюстрации, не часть правила):

1. **Где может жить свойство.** Прорабатывая размещение механизма,
   рассматривай его как **свойство операнда/входа**, а не только
   отдельным полем или повтором в каждой единице. Свойство, заданное
   раз на входе и переиспользуемое, часто снимает мнимую развилку
   «поле vs руками в каждой единице». *(Кейс: persistence фазы через
   период индикатора-операнда.)*
2. **Риск-аппетит не закрывается инженерным дефолтом.** Если крен
   отвергает вариант по «недопустимости остаточного риска» (whipsaw,
   перескок, просадка) — это кандидат на **вынос пользователю** как
   риск-хвост, не молчаливый инженерный дефолт; приемлемость
   остаточного риска — продуктово-рисковое решение пользователя (на
   смешанной развилке — связка с `trading-specialist`). *(Кейс:
   фаза-дебаунс.)*
3. **Контекст крена мог устареть.** Прорабатывая или переоценивая,
   сверяй, **на каком контексте держится** прежний крен или прежнее
   отвержение варианта. Если зафиксированный decision сменил этот
   контекст (основание рухнуло) — переоценивай **с нуля**, не тащи
   старый крен. *(Кейс: «ER внутри аналитика» после редизайна фазы.)*
4. **Аналогия-прецедент требует структурной сверки.** Прежде чем
   перенести крен по аналогии с существующим решением — проверь
   **структурное совпадение**; прецедент применим только при нём.
   *(Кейс: составное событие ≠ одно сравнение.)*
5. **Маркер/базовый тип — не только «есть ли поведение».** Решая,
   вводить ли общий базовый/маркер-тип над семейством (payload'ы,
   события, команды), взвешивай не только наличие у типа поведения, но
   и **эргономику сигнатур** (единый тип в сигнатурах потребителей —
   один контракт вместо N перегрузок/дженериков) и **запас на
   расширение** (разные будущие воплощения семейства — напр. другие
   биржевые модели). Отказ «база без поведения ценности не несёт» —
   неполный критерий: маркер-база может окупаться сигнатурами и
   расширяемостью при пустом поведении. *(Кейс: базовый
   `ServiceCommandPayload`.)*
6. **Цена варианта раскладывается во времени.** Цена не единая величина
   «здесь и сейчас»: разделяй **цену сейчас** (что придётся сделать в
   этой правке) и **цену, откладываемую за границу фазы** (операционная
   нагрузка, обслуживание, объём, которые наступают позже). Откладываемое
   называется **явно вместе с границей** («ретеншен — фаза 3»), а не
   растворяется в общем доводе против варианта: иначе будущая нагрузка
   срабатывает отбрасывателем сегодня, хотя решать её сегодня не нужно.
   *(Кейс: объём строк повторяющихся системных действий — ретеншен подан
   доводом против «копить строки», хотя выносится за фазу 1.)*
