# spec-document-workflow

Процедура работы с документами в `docs/spec/`. Покрывает создание новых
документов и обновление существующих. Обеспечивает соблюдение
стандарта, зафиксированного в ADR-0002.

## Когда активируется

- Создание нового документа в `docs/spec/`.
- Обновление существующего документа в `docs/spec/`.
- Ревью соответствия существующего документа стандарту.

## Когда НЕ активируется

- Миграция документа из `docs/domain/` в `docs/spec/` — для этого
  планируется отдельный скилл `spec-document-migration`. До его создания
  миграцию выполнять с этим скиллом, но действовать осторожно (не
  ограничиваться им).
- Работа с любыми файлами **вне** `docs/spec/` (включая `docs/domain/`,
  `.claude/adr/`, `.claude/planning/`).
- Редактирование шаблонов в `docs/spec/_templates/` (это отдельная
  задача, требующая согласования через ADR).

## Базовые принципы (выжимка из ADR-0002)

- **Один факт — одно место.** Документ не повторяет то, что описано в
  другом — он ссылается через markdown-link с относительным путём.
- **Документ = текущее состояние.** Никаких addenda («Дополнение
  после ...»), никаких разделов «Открытые вопросы» (они в backlog).
  При изменении правится тело документа.
- **Жанровая чистота.** Один документ — один жанр. Не смешивать модель
  с процессом, маппинг с lifecycle.
- **Контракт, не реализация.** Никаких Java-сниппетов. Структура —
  таблицами полей. SQL DDL — в Flyway-миграциях, не здесь.

Полный стандарт — в `.claude/adr/0002-spec-document-standard.md`. При
неоднозначности всегда смотри ADR.

## Процедура

### Шаг 1. Определить ситуацию

Это **создание** нового документа или **обновление/ревью** существующего?

- Файл по целевому пути не существует → создание.
- Файл существует → обновление или ревью.

### Шаг 2. Определить жанр

Шесть жанров:

| Жанр | Что описывает | Папка |
|---|---|---|
| **model** | Структура доменной модели (поля, типы, инварианты структуры) | `docs/spec/models/` |
| **lifecycle** | Динамика модели (жизненный цикл, переходы, кто меняет) | `docs/spec/lifecycle/` |
| **process** | Оркестрация, jobs, шаги executor-flow | `docs/spec/processes/` |
| **integration-mapping** | Маппинг внешней системы на доменные структуры | `docs/spec/integrations/<exchange>/` |
| **reference** | Стабильные справочники, архитектурные паттерны | `docs/spec/references/` |
| **invariant** | Правило, пересекающее несколько моделей или процессов | `docs/spec/invariants/` |

Если документ не подходит ни под один жанр — стоп. Это сигнал, что либо
жанр выбран неправильно, либо документ смешивает жанры. Разбираться с
пользователем, не выкручиваться.

### Шаг 3a. Создание нового документа

1. **Скопировать шаблон** из `docs/spec/_templates/<genre>.md` в целевой
   путь. Не писать с нуля.
2. **Определить имя файла:**
   - PascalCase, если документ описывает один конкретный класс. Имя
     файла = имя класса (`Order.md`, `AlgoOrder.md`,
     `DealOrchestratorJob.md`).
   - kebab-case в остальных случаях (`exception-policy.md`,
     `algo-order-mapping.md`, `order-deal-action-state-sync.md`).
   - Русские имена, пробелы, кириллица — запрещены.
3. **Заполнить frontmatter:**
   - `status`: обычно `draft` для нового документа, `wip` если основные
     положения уже зафиксированы, `current` если документ полностью
     готов.
   - `last_review`: текущая дата.
   - `related_adrs`: список ADR, касающихся документа.
   - `related_models`, `related_processes`: опционально, для cross-links.
4. **Заполнить тело** по полученному содержанию. Сохранить структуру
   шаблона — обязательные разделы не удалять, опциональные удалить, если
   не применимы.
5. **Проверить связные документы** (см. шаг 5).
6. **Пройти чек-лист** (см. шаг 6).

### Шаг 3b. Обновление существующего документа

1. **Прочитать документ полностью.** Не править вслепую — изменение
   может затронуть разделы, на которые ссылается другая часть документа.
2. **Проверить соответствие шаблону:**
   - Открыть `docs/spec/_templates/<genre>.md` для жанра документа.
   - Сверить структуру (frontmatter, обязательные разделы).
   - Если документ устарел относительно шаблона — это сигнал. Не править
     молча: либо привести в соответствие в той же сессии (если изменение
     невелико), либо завести задачу в `.claude/planning/backlog.md`.
3. **Внести изменения в тело документа.** Никаких addenda. Если нужно
   зафиксировать дельту относительно прошлого состояния — это работа для
   ADR, не для документа спецификации.
4. **Обновить frontmatter:**
   - `last_review`: на текущую дату — **если изменение значимое**
     (изменение содержания, добавление/удаление разделов, изменение
     структуры). Косметика (опечатки, форматирование) — `last_review`
     не трогаем.
   - `related_adrs`: добавить новые ADR, если они касаются документа.
   - `status`: при необходимости перевести (например, `wip` → `current`).
5. **Проверить связные документы** (см. шаг 5).
6. **Пройти чек-лист** (см. шаг 6).

### Шаг 4. Ревью соответствия существующего документа

Если задача — проверить документ на соответствие стандарту, без правок:
сразу к шагу 6 (чек-лист). Найденные несоответствия — либо адресовать в
той же сессии (с согласия пользователя), либо завести задачу в backlog.

### Шаг 5. Связные документы

При любом значимом изменении пройтись по следующему списку:

- **Другие spec-документы.** Если изменение в `models/Order.md` касается
  поля, упомянутого в `lifecycle/Order.md` или в
  `integrations/okx/order-mapping.md` — обновить и их.
- **ADR.** Если изменение мотивировано новым решением — оно должно быть
  ADR. Если ADR ещё нет — поднять руку пользователю.
- **Backlog (`.claude/planning/backlog.md`).**
  - Если изменение **закрывает** пункт из backlog — переместить пункт в
    раздел «Закрытые» с датой и ссылкой на коммит/ADR.
  - Если в процессе всплыл **новый открытый вопрос** — завести в backlog
    с понятным приоритетом и источником.
- **Pipeline-evolution-log.** Записывается **только** если изменение
  касается самого пайплайна работы (агенты, скиллы, процессы), не
  содержательной спецификации.

### Шаг 6. Чек-лист соответствия (обязательно)

Прогнать на каждом создании/обновлении. Несоответствие — либо исправить,
либо явно поднять руку пользователю.

**Frontmatter и метаданные:**

- [ ] Frontmatter присутствует и заполнен (`status`, `last_review`,
      `related_adrs`).
- [ ] `last_review` обновлён, если изменение значимое.
- [ ] `status` соответствует реальному состоянию документа.

**Расположение и имя:**

- [ ] Файл лежит в правильной папке для своего жанра.
- [ ] Имя файла соответствует правилам: PascalCase для классов,
      kebab-case иначе. Без пробелов, без кириллицы.

**Содержание:**

- [ ] Документ описывает **один** жанр (нет смешения «модель + процесс»
      или «маппинг + lifecycle»).
- [ ] Нет дублирования с другими spec-документами. Если факт уже описан
      где-то — здесь ссылка, не повтор.
- [ ] Нет Java-сниппетов классов/методов/аннотаций. Структура моделей —
      таблицей полей.
- [ ] Нет SQL DDL. Структура БД — в Flyway-миграциях.
- [ ] Нет addenda-разделов («Дополнение после Q2-Q8», «Уточнение
      после ...» и подобные).
- [ ] Нет встроенных «Открытых вопросов» — они в `.claude/planning/backlog.md`.

**Стиль:**

- [ ] Кросс-ссылки — markdown-link с относительным путём
      (`[Order](../models/Order.md)`), не inline-code.
- [ ] Заголовки без нумерации (`# Order`, не `# 01. Order`).
- [ ] Mermaid-диаграммы inline, длинные примеры (>30 строк) — в
      `references/`.

**Размер:**

- [ ] Размер документа ≤1000 строк.
- [ ] Если >1000 строк: добавить запись в раздел «Документы под пересмотр
      размера» в `.claude/planning/backlog.md` с указанием пути, количества
      строк, даты и возможных направлений декомпозиции.

**Связное обновление:**

- [ ] Связные spec-документы проверены и обновлены при необходимости.
- [ ] Если закрыт пункт backlog — он перемещён в «Закрытые».
- [ ] Если появился новый открытый вопрос — он занесён в backlog.

## Подводные камни

**1. Документ смешивает жанры.** Самая частая ошибка миграции. Признак:
в одном файле есть и структура модели, и описание процесса, и куски
маппинга. Решение — разнести по соответствующим папкам, не пытаться
сохранить «удобство одного файла».

**2. Дублирование «для наглядности».** Соблазн повторить инвариант,
описанный в другом документе, «чтобы читателю было удобно». Запрещено.
Только ссылка.

**3. Java-сниппет для иллюстрации структуры.** Соблазн: «вот так это
выглядит в коде». Запрещено. Таблица полей.

**4. Addenda как способ зафиксировать изменение.** Соблазн: дописать
раздел «Дополнение после ADR-0NNN» в конце документа. Запрещено.
Правится тело документа, история — в ADR.

**5. «Открытые вопросы» внутри документа.** Соблазн: «здесь не до конца
ясно, оставлю TODO». Запрещено. Открытый вопрос — в backlog с понятным
приоритетом и источником.

**6. Слепое следование шаблону.** Шаблон — основа, не догма. Если для
конкретного документа какой-то опциональный раздел не применим — удалить.
Если нужен новый раздел, не предусмотренный шаблоном — добавить, но
проверить, не сигнал ли это к расширению шаблона (тогда задача в
backlog).

**7. Изменение `last_review` на каждое касание.** Только при значимых
изменениях содержания. Косметика — не основание.

## Связанные документы

- `.claude/adr/0002-spec-document-standard.md` — полный стандарт.
- `docs/spec/_templates/` — шаблоны жанров.
- `.claude/flow/playbook.md`, Сценарий 7 — операционная процедура с точки зрения
  пользователя.
- `.claude/planning/backlog.md` — куда заводить открытые вопросы и пункты на
  пересмотр размера.
