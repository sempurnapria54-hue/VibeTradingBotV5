## Принятые концептуальные решения

Из v2 без изменений — все 11 пунктов (двухсессионная модель, иерархия
источников правды, поэтапная миграция, связное обновление, no-commit
от Claude Code, стандарт `docs/spec/`, ADR-0001 reconcile, ADR-0003
разделение `docs/`/`.claude/`, версионированные снимки, backlog как
синхронизация, терминология «доменная модель»).

Новые решения, накопленные в этом цикле проектирования (детальные
формулировки уйдут в ADR-0006..0009):

12. **Принципы спецификации (→ ADR-0006).** Критерий бизнес-объекта
    vs вложенной модели. Критерий локального vs кросс-модельного
    инварианта. Распределение статусных таксономий по жанрам.
    Двухуровневый резолвер биржевых статусов (общий контракт —
    invariant; конкретные таблицы — integration). Addenda при
    миграции вмерживаются в основной текст.

13. **Структура `docs/spec/` (→ ADR-0007).** Жанры spec-документов
    (model, lifecycle, process, integration, reference, invariant)
    с уточнением: model делится на `core/` (persistent, имеют
    identity, переживают рестарт) и `runtime/` (транзитные).
    Структура integration: `docs/spec/integrations/<exchange>/{models,mapping}/`
    зафиксирована заранее, применяется в фазе 2. Глоссарий —
    `docs/GLOSSARY.md` в корне, исключение из `references/` по
    соображениям видимости.

14. **Журнал open-questions (→ ADR-0008).** Новый артефакт —
    `.claude/questions/open-questions.md`. Структура entry с
    11 полями (id, title, formulation, source, added, status,
    classification, context, related, notes, resolution).
    Статусы — `Added`/`In-progress`/`Resolved`. Classification —
    7 значений (concept, missing-model, contradiction, structural,
    legacy-bug, obsolete-by-decision, obsolete-by-context). Условия
    устаревания — 3. Knowledge Curator при закрытии Q-N
    автоматически проверяет, есть ли висящие inline-ссылки на
    этот Q-N в `docs/spec/`, и при наличии заводит задачу в backlog.

15. **Стратегия миграции `docs/domain/` (→ ADR-0009).** Миграция
    разделена на 6 фаз (см. ниже). В фазе 1 — 8 кластеров.
    Единица миграции — двухуровневая: кластер как единица
    планирования и итогового состояния; spec-документ как единица
    одной сессии. Перед стартом кластера — 5 hard gates готовности.
    Принцип качества миграции: без сокращений скоупа, только
    батчинг однотипных документов. Принцип «связной зависимости» —
    допустима «забегающая ссылка» на роль/будущий документ в
    общих формулировках, без указания конкретного пути и без
    описания структуры.

## План работы: шесть фаз

- **Фаза 1.** Миграция домена. 8 кластеров. Финальный результат —
  ≈28 spec-документов + глоссарий.
- **Фаза 2.** Миграция `docs/domain/models/mapping/okx/` в
  `docs/spec/integrations/okx/{models,mapping}/`.
- **Фаза 3.** Обработка корневого `docs/domain/Открытые вопросы по
  движку.md` (вопросы переносятся в журнал и проходят процедуру
  разбора).
- **Фаза 4.** Реорганизация `docs/api/` (отдельной задачей; жанр API
  остаётся самостоятельным).
- **Фаза 5.** Цикл ревью смигрированной документации: формирование
  Q-N в журнале по неясным местам, ответы, заполнение gap'ов и
  уточнение существующих документов. Итеративная, заканчивается на
  «насыщении».
- **Фаза 6.** Упразднение legacy: проверка `[MIGRATED]` маркеров,
  зачистка ссылок на legacy, удаление `docs/domain/`, обновление
  CLAUDE.md и `docs/README.md`, техническое примечание в ADR-0003.

## Восемь кластеров фазы 1 (порядок)

1. **C-NEW** — Exchange + Instrument (фундамент).
2. **C4** — Balance.
3. **C2** — Order, AlgoOrder, Position (однотипные торговые сущности,
   батчинг).
4. **C6** — Market data (4 однотипных результата Job'ов + 1 process,
   батчинг моделей).
5. **C5** — Strategy (корневая конфигурация; самый большой документ).
6. **C1** — Deal + FSM + DealContext + DealActionState (корневой
   агрегат).
7. **C7** — Calculator + Risk + Command (самый связный).
8. **C8** — Audit (финал).

Порядок строится снизу вверх по зависимостям: листья → корневые
агрегаты → связные слои. Однотипные модели идут вместе для батчинга.

Грубая оценка: ≈25-35 сессий миграции, ≈20-50 часов человеческого
времени, ≈2-5 недель календарно при темпе 2-3 часа в день.

## Что решено НЕ делать (расширение из v2)

Из v2 без изменений. Добавляется:

- **Не дробить стратегию миграции на много маленьких ADR.** Один
  стратегический ADR-0009 + три структурных (0006/0007/0008).
- **Не сокращать качество ради скорости.** Принцип качества миграции:
  батчинг — да; сокращение скоупа, отложенная классификация
  open-questions, пропуск ревью — нет.
- **Не описывать runtime services и executors (RefreshOrderExecutor,
  KillSwitchService и т.п.) как отдельные spec-документы.** Они
  упоминаются как роли в process-документах.
- **Не вести параллельный backlog по фазам / кластерам.** Один общий
  backlog с короткими формулировками задач на кластеры.
- **Не хранить чек-листы готовности в backlog.** Процедура — в скилле,
  данные кластера формируются на первом этапе миграции как рабочий
  артефакт сессии.
- **Не запускать цикл ревью смигрированной документации до полной
  миграции домена + integrations + API.** Цикл ревью (фаза 5) —
  после фаз 1-4.
