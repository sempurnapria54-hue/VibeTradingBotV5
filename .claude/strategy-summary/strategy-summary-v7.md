## Редизайн пайплайна (новый сюжет v7)

### Концепция целевого пайплайна

**Роли:**

- **Пользователь** — формулирует задачи, принимает решения, делает ревью результатов. Источник целеполагания и арбитр развилок.
- **Чат** — обсуждает суть, классифицирует материал по маркерам (через какой слой/трекер он проходит, какой агент его смотрит), готовит короткие промпты для Claude Code. **НЕ пишет содержательные тексты репозитория** (ADR, спецификации, скиллы, README) — это работа Claude Code. Чат проводит ретроспективы пайплайна. Запускает проверку консистентности Project Knowledge (Сценарий 8 playbook).
- **Claude Code** — знает проект (репо доступно), читает файлы, пишет файлы, делает git add. На любой неопределённости — **останавливается**, заводит вопрос в открытый список (`.claude/questions/open-questions.md`), **не додумывает**. Коммит не делает — коммитит человек после IDEA-ревью.

**Базовый цикл:**

```
задача (от пользователя)
  → работа Claude Code
  → стоп с вопросами (если есть неопределённость)
  → разбор в чате (содержание + классификация по маркерам)
  → правки правил пайплайна (если выяснилось, что правило отсутствует или неточно)
  → продолжение работы Claude Code
```

Цикл не предполагает, что чат пишет что-то в репозиторий. Чат — это конструктор задач и правил. Репозиторий — рабочая среда Claude Code.

### Мета-приём "вопросы-маркеры"

Каждый артефакт проекта идентифицируется характеристическим вопросом. Артефакты делятся на две категории:

**Процессные слои знания** (CLAUDE.md → Process layers). Устойчивые категории знания — куда кладут новое:

- Specification — *что есть в системе?* → `docs/spec/` (+ legacy `docs/domain/`, `docs/api/`)
- ADR — *почему выбрано это, а не другое?* → `.claude/adr/`
- Convention — *как принято в проекте?* → `docs/conventions/`
- Skill — *как выполняется операция?* → `.claude/skills/`
- Agent — *какая роль смотрит на это?* → `.claude/agents/`

**Трекеры состояния** (CLAUDE.md → Trackers). Снимки текущего состояния — куда сводят то, что есть сейчас:

- Strategy snapshot — *где мы сейчас и как сюда пришли?* → `.claude/strategy-summary/`
- Open questions journal — *что ещё не решено?* → `.claude/questions/open-questions.md`
- Backlog — *что в работе?* → `.claude/planning/backlog.md`
- Migration tracker — *где мы в миграции?* → `.claude/planning/migration-tracker.md`
- Pipeline evolution log — *как менялся пайплайн?* → `.claude/pipeline-evolution-log.md`

Подчинённые индексы повторяют приём для своего уровня (`.claude/agents/README.md` — каждый агент через свой характеристический вопрос).

Назначение приёма — навигация без перечитывания. По вопросу из задачи сразу видно, какой артефакт затрагивается; по списку маркеров видно, какой роли передаётся вопрос.

## Состав пакета ADR-0006..0009

Без изменений после v6. Все четыре в статусе Proposed, в режиме as-if-Accepted, ожидают V2 dry-run.

### ADR-0006: принципы спецификации (Proposed)

Четыре принципа организации содержания spec-документов:

1. **Декомпозиция моделей.** Один бизнес-объект — один model-документ. Вложенные модели — разделами внутри. Критерий бизнес-объекта (identity, независимый жизненный цикл, способность быть субъектом операций, смысл в отрыве). Дополнительное деление: core vs runtime.
2. **Инварианты: локальные vs кросс-модельные.** Локальные — внутри model/lifecycle/process документа модели. Кросс-модельные — в `invariants/`. Операционализированный тест разделения.
3. **Статусные таксономии** (после Правки 1 итерации 1). Для любой модели со статусами — пара документов: model-документ содержит enum и семантику; lifecycle-документ той же модели — переходы и инварианты поведения. Структурные запреты не пишутся (отсутствие = запрет); явно пишутся только доменные запреты с обоснованием. Двухуровневый резолвер биржевых статусов.
4. **Addenda при миграции.** Запрещено добавлять "дополнения после миграции" отдельными разделами. Нерешённые остатки → журнал Q-N.

### ADR-0007: структура `docs/spec/` (Proposed)

Подкаталоговая структура: `models/core/`, `models/runtime/`, `lifecycle/`, `processes/`, `integrations/<exchange>/{models,mapping}/`, `references/`, `invariants/`. `MODELS.md` в корне как реестр имён и навигационная точка входа. `docs/api/` остаётся самостоятельным жанром.

### ADR-0008: журнал open-questions (Proposed, после Правки 2 итерации 1)

- Структура entry: 11 полей.
- Статусы: Added → Resolved.
- Classification: **10 значений** — 9 содержательных + 1 служебная.
- Три условия устаревания.
- Шаблон в `.claude/templates/documents/`. Скилл `open-questions-workflow`.

### ADR-0009: стратегия миграции `docs/domain/` (Proposed)

Шесть последовательных фаз: миграция домена (8 кластеров) → OKX-маппинги → обработка открытых вопросов движка → реорганизация `docs/api/` → цикл ревью → упразднение legacy. Восемь кластеров фазы 1. Единица миграции — двухуровневая (кластер + spec-документ). Пять hard gates готовности кластера. Скилл `spec-cluster-migration` и Сценарий 9 в playbook.

## Структура артефактов знаний

### Источники правды о системе (`docs/`)

- **`docs/spec/`** — целевая спецификация, главный приоритет.
  - `MODELS.md` — реестр канонических имён бизнес-моделей. Отражение созданных model-документов, не гейт.
  - `models/core/`, `models/runtime/` — спецификации бизнес-моделей по природе.
  - `lifecycle/` — динамика моделей. Для любой модели со статусами и переходами — обязательный парный документ.
  - `processes/` — оркестрация (Job, executor-flow).
  - `invariants/` — кросс-модельные правила.
  - `references/` — стабильные справочники и архитектурные паттерны.
  - `integrations/<exchange>/` — описания внешних интеграций и маппинги.
- **`docs/conventions/`** — конвенции проекта (`terminology.md`; `code-style.md`, `tech-radar.md` ожидают миграции из codex).
- **`docs/domain/`** — текущая живая спецификация (legacy, постепенно мигрирует). Источник правды по темам, не перенесённым в `docs/spec/`.
- **`docs/api/`** — документация по API. Самостоятельный жанр, фаза 4 миграции в плане.

- **Не переписывать `.claude/flow/playbook.md` превентивно.** Сначала проба, потом пересмотр сценариев на её основе. Текущие 10 сценариев работают, дополнительный риск переписывания их "под концепцию" без проверки выше выгоды.
- **Чат не пишет содержательные тексты репозитория.** ADR, спецификации, скиллы, README — пишет Claude Code. Чат формулирует, классифицирует, готовит промпт. Это часть редизайна, не запрет на детальные обсуждения в чате.
- **Claude Code не додумывает на неопределённости.** Останавливается, заводит вопрос в открытый список, ждёт разбора в чате. (Правило в процессе фиксации — место решается отдельно.)

## Как использовать этот документ

Snapshot — навигационный. Используется:

- Чтобы понять, в каком состоянии проект на 2026-05-18 после сессии редизайна пайплайна.
- Чтобы новая сессия (проба переразложения `spec-document-migration`) видела текущую картину без перечитывания всех обсуждений этой серии.
- Как индекс будущих задач (проба переразложения → масштабирование → пересмотр playbook → V2 dry-run миграции).

Не редактируется задним числом. Если состояние изменится значимо (после пробы переразложения, после решения о масштабировании, после пересмотра playbook) — создаётся следующая версия.

История эволюции пайплайна — `../pipeline-evolution-log.md`.
История архитектурных решений — `../adr/`.
Чеклист прогресса миграции — `../planning/migration-tracker.md`.
Открытые вопросы — `../questions/open-questions.md`.
Навигация по слоям и трекерам — `../../CLAUDE.md` (секции Process layers и Trackers).
