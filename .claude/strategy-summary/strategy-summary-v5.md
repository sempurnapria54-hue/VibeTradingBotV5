## Контекст на текущий момент

Проект — VibeTradingBotV5. Алгоритмический торговый бот на Java 21 + Spring Boot 3 + PostgreSQL, поддерживает биржу OKX, архитектура рассчитана на расширение до нескольких бирж. Состояние кода: 357 Java-файлов, тесты пустые, содержательная работа над кодом не начата.

## Принятые концептуальные решения

Полный список действующих решений проекта на текущий момент.

1. **Двухсессионная модель работы.** Чат — для проектирования и решений. Claude Code — для исполнения. Решения фиксируются в чате, артефакты в репозиторий идут через Claude Code.

2. **Иерархия источников правды.** При расхождениях побеждает источник выше: `docs/spec/` → `docs/domain/`/`docs/api/` → код + ADR + conventions → прочие docs → архивы. Конфликты между уровнями — через ADR.

3. **Поэтапная миграция документации.** `docs/domain/` мигрирует в `docs/spec/` по фазам и кластерам. Структура `docs/spec/` зафиксирована в ADR-0002 и ADR-0007.

4. **Связное обновление документации.** Любое изменение модели, процесса, концепции автоматически влечёт проверку и обновление связанных документов. Knowledge Curator проверяет в конце сессии.

5. **Claude Code не коммитит сам.** Коммиты делает человек через IDEA после ревью.

6. **Стандарт документа `docs/spec/`** (ADR-0002): шесть жанров (model, lifecycle, process, integration-mapping, reference, invariant), frontmatter, размер документа ≤1000 строк, запрет Java-сниппетов и addenda. Скилл `spec-document-workflow` обеспечивает соблюдение стандарта.

7. **ADR-0001: модель reconcile через AnomalyReport.** Аномалии при сверке внутреннего состояния с биржей фиксируются как `AnomalyReport`.

8. **ADR-0003: разделение `docs/` и `.claude/`.** Продуктовая документация (что бот делает) — в `docs/`. Артефакты процесса работы (как мы работаем с Claude) — в `.claude/`.

9. **Версионированные снимки стратегии.** `strategy-summary-vN.md` — навигационная точка входа для новой сессии. Не редактируется задним числом. При значимых изменениях создаётся следующая версия. Snapshot — самостоятельный документ, не отсылается к предыдущим версиям.

10. **Backlog как механизм синхронизации.** `.claude/planning/backlog.md` — единый список открытых задач и тем для проработки. Закрытые задачи помечаются `✅ DONE` с датой и ссылкой, не удаляются.

11. **Терминология: «доменная модель» вместо «entity».** Объект предметной области торговли — доменная модель. Слово «entity» в проектной речи не используется (тянет JPA-смысл).

12. **Принципы спецификации (ADR-0006).** Один бизнес-объект — один model-документ. Вложенные модели — разделами внутри. Деление моделей на core (хранимые, имеют identity, переживают рестарт) и runtime (транзитные, живут в рамках операции). Инварианты: локальные vs кросс-модельные. Статусные таксономии и резолвер биржевых статусов.

13. **Структура `docs/spec/` (ADR-0007).** Подкаталоги: `models/core/`, `models/runtime/`, `lifecycle/`, `processes/`, `integrations/<exchange>/{models,mapping}/`, `references/`, `invariants/`. В корне `docs/spec/` — `MODELS.md` как навигационная точка входа.

14. **Журнал open-questions (ADR-0008).** Каталог концептуальных и рабочих вопросов проекта. Файл `.claude/questions/open-questions.md`, шаблон `.claude/templates/documents/open-questions-journal.md`, скилл `open-questions-workflow`. Структура entry (11 полей), статусы Added/Resolved, классификация (7 содержательных + 1 служебная `unclassified`), три условия устаревания.

15. **Стратегия миграции `docs/domain/` (ADR-0009).** Шесть последовательных фаз: миграция домена (8 кластеров) → OKX-маппинги → обработка открытых вопросов движка → реорганизация `docs/api/` → цикл ревью → упразднение legacy. Единица миграции двухуровневая (кластер + spec-документ). Пять hard gates готовности кластера. Синтаксис забегающей ссылки. Скилл `spec-cluster-migration` и Сценарий 9 в playbook.

16. **Принцип 6: документация — источник истины, код подтягивается.** На проекте код отстаёт от документации, не наоборот. Доменная документация описывает целевое состояние; код реализует постепенно. При миграции дока — источник истины; documented-only модели мигрируются как валидные spec-документы; code-only классы — реализационный слой, упоминаются как роли в process-документах.

17. **Формат общения при содержательных решениях** (Принцип 13 project-instructions). При обсуждении решений Claude использует формат: короткое описание вопроса (контекст из жизни) → список вариантов → короткая рекомендация → ждать выбор пользователя. Применяется для содержательных развилок, не для рутинных вопросов.

18. **Пакет ADR принимается разом.** ADR-0006..0009 переводятся в Accepted в конце Этапа 4 (после стресс-теста), не по одному. До этого индекс `.claude/adr/README.md` не обновляется частично. Это страхует от ситуации, когда часть пакета принята, а потом по результатам теста нужно править уже принятые ADR.

19. **Открытые концептуальные вопросы заводятся естественно при миграции.** Не предзаводятся по плану. Q-N появляется в журнале из материала legacy при миграции соответствующего кластера. Природа моделей, структура отсутствующих моделей, противоречия между источниками — всё это обнаруживается по ходу разбора legacy-документов.

20. **Расщепление функций единого глоссария на три артефакта.** Принято в этой сессии. Единый `docs/GLOSSARY.md` с тремя функциями (терминологические соглашения + реестр имён моделей + чеклист миграции) разнесён на три независимых артефакта с разной природой и судьбой:
    - `docs/conventions/terminology.md` — терминологические соглашения. По жанру convention, не зависит от миграции. Соседствует с code-style.md и tech-radar.md (когда они будут мигрированы из codex).
    - `docs/spec/MODELS.md` — реестр канонических имён бизнес-моделей. По жанру навигационная точка входа в `docs/spec/`, размещён в корне как осознанное исключение из жанровой структуры. Создаётся в начале фазы 1, наполняется по ходу миграции кластеров.
    - `.claude/planning/migration-tracker.md` — рабочий артефакт процесса по ADR-0003, чеклист прогресса миграции. Соседствует с backlog.md. Рассматривается на пересмотр после фазы 5.
    
    Сквозные концепции (kill-switch, freshness, anomaly, reconcile, FSM сделки) в отдельный артефакт не идут — мигрируют в соответствующие spec-документы по жанрам (invariant / process / lifecycle) при миграции своих кластеров. Применено к Proposed-ADR-0007 §3 и ADR-0009 §9.

21. **Правило «новый термин — куда фиксировать»** (Принцип 4 working-with-claude.md). При появлении нового термина — определи его тип и зафиксируй в соответствующем артефакте:
    - **Имя бизнес-модели** (Deal, Order, Position, ServiceCommand и подобные) → `docs/spec/MODELS.md` + соответствующий model-документ в `docs/spec/models/core/` или `docs/spec/models/runtime/`.
    - **Терминологическое соглашение** («как правильно писать в проекте»: «доменная модель» вместо «entity», «хранимая модель», «aggregate root» и подобные) → `docs/conventions/terminology.md`.
    - **Сквозная концепция** (kill-switch, orphan, freshness, reconcile, FSM сделки, anomaly и подобные) → соответствующий invariant/process/lifecycle-документ в `docs/spec/`.
    
    Отдельного «глоссария концепций» проект не создаёт.

22. **Терминологическое соглашение «domain-only / external-only»** заменяет «orphan». Domain-only — сущность зафиксирована во внутреннем состоянии системы, но отсутствует на бирже. External-only — сущность существует на бирже, но отсутствует во внутреннем состоянии. Зеркальные типы, различающиеся стороной присутствия. При встрече «orphan» в legacy — конкретизировать тип. Обнаружение, классификация и реакция на рассинхронизацию — не в terminology.md, а распределяется по соответствующим spec-документам при миграции (или появляется как Q-N в журнале по ходу разбора).

23. **Частичная миграция как штатное состояние.** Документ может быть мигрирован не целиком за одну итерацию. Логика поведения:
    - При обнаружении неразобранных блоков в legacy-документе → заводится Q-N в журнале (через скилл `open-questions-workflow`), source указывает на конкретный фрагмент.
    - MIGRATED-маркер на legacy-документ не ставится, пока хотя бы один блок не разнесён или хотя бы один Q-N по этому документу остаётся открытым.
    - В трекере документ остаётся в статусе `in-progress`.
    - При разрешении Q-N — локальный довоз только этого блока в целевой spec-документ. Файл не переоткрывается для миграции с нуля.
    - Когда все блоки разнесены и все Q-N закрыты — финализация (MIGRATED-маркер, статус `done`).
    
    Зафиксировано в скилле `spec-document-migration` (раздел «Базовая модель работы», «MIGRATED-маркер на исходнике»).

24. **Shared-файлы при миграции кластера.** Legacy-документ, распадающийся по нескольким кластерам, получает MIGRATED-маркер только когда все его фрагменты разнесены — возможно, через несколько кластеров. До этого момента документ остаётся `in-progress` в трекере, целевые spec-документы накапливаются по мере миграции каждого фрагмента. Зафиксировано в скиллах `spec-document-migration` (раздел «Маркер для shared-файлов») и `spec-cluster-migration` (Этап 4, пункт 2).

25. **Терминологические замены при миграции.** При переработке legacy-документа в целевой spec-документ применяются канонические термины из terminology.md:
    - entity / сущность / domain object → доменная модель.
    - persisted (в русском тексте) → хранимое.
    - orphan / orphan-сущность → domain-only или external-only (требует уточнения типа).
    - persistent/transient JPA → core/runtime (по тесту ADR-0006 §1).
    
    Прямые замены применяются автоматически. Замены с неоднозначным контекстом порождают Q-N в журнале. Список замен растёт по мере добавления соглашений в terminology.md. Зафиксировано в скилле `spec-document-migration` (раздел «Терминологические замены при миграции»).

26. **MODELS.md и migration-tracker.md пересматриваются после фазы 5.** Их роль на длинной дистанции (после завершения миграции) не определена окончательно:
    - migration-tracker полностью теряет миграционную роль — после миграции прогресс отслеживать нечего.
    - MODELS.md формально остаётся как навигационная точка входа и реестр имён, но содержательно становится беднее.
    
    После фазы 5 (цикл ревью) принимается решение: оставить, реструктурировать или упразднить. Backlog-пункт зафиксирован. terminology.md пересмотром не затрагивается — живёт независимо от миграции.

## Состав пакета ADR-0006..0009

Все четыре в статусе Proposed. Перевод в Accepted — после стресс-теста.

### ADR-0006: принципы спецификации (Proposed)

Четыре принципа организации содержания spec-документов:

1. **Декомпозиция моделей.** Один бизнес-объект — один model-документ. Вложенные модели — разделами внутри документа бизнес-объекта. Критерий бизнес-объекта: независимый жизненный цикл, identity, способность быть субъектом операций, смысл в отрыве. Дополнительное деление: core vs runtime по природе persistence.

2. **Инварианты: локальные vs кросс-модельные.** Локальные — внутри model-документа (инвариант одной модели). Кросс-модельные — в `invariants/` (правило, пересекающее несколько моделей или процессов). Операционализированный тест разделения.

3. **Статусные таксономии.** Внутри model-документов фиксируются собственные статусные перечисления модели. Двухуровневый резолвер биржевых статусов (по примеру OKX): exchange-status в integration-mapping → domain-status в model-документе.

4. **Addenda при миграции.** Запрещено добавлять «дополнения после миграции» отдельными разделами. Любое уточнение вмерживается в основной текст документа; нерешённые остатки уходят в журнал Q-N.

### ADR-0007: структура `docs/spec/` (Proposed)

Подкаталоговая структура `docs/spec/`:

- `models/core/` и `models/runtime/` — раздельные подкаталоги по природе модели (ADR-0006 §1).
- `integrations/<exchange>/{models,mapping}/` — для фазы 2 (OKX и далее). Models — описание внешних DTO биржи. Mapping — таблицы соответствия DTO ↔ домен.
- `lifecycle/`, `processes/`, `invariants/`, `references/` — жанровые подкаталоги.
- `MODELS.md` в корне `docs/spec/` — реестр канонических имён бизнес-моделей, навигационная точка входа. Размещение в корне — осознанное исключение из жанровой структуры (после правок этой сессии — раздел §3 переписан).
- `docs/api/` остаётся самостоятельным жанром, не сливается с `integrations/`.

После правок этой сессии: единый `docs/GLOSSARY.md` отсутствует как артефакт; функции распределены на три файла (MODELS.md в `docs/spec/`, terminology.md в `docs/conventions/`, migration-tracker.md в `.claude/planning/`).

### ADR-0008: журнал open-questions (Proposed)

Артефакт `.claude/questions/open-questions.md` — каталог концептуальных и рабочих вопросов проекта.

- Структура entry: 11 полей (id, title, status, classification, source, added, related, formulation, context, notes, resolution).
- Статусы: Added → Resolved (один переход).
- Classification: семь содержательных (`missing-model`, `concept`, `contradiction`, `obsolete-candidate`, `process`, `decision-needed`, `obsolete-by-decision`) + служебная `unclassified`.
- Три условия устаревания (потеря актуальности по факту, дубль, разрешение вне журнала).
- Шаблон `.claude/templates/documents/open-questions-journal.md`.
- Скилл `open-questions-workflow` создаётся вместе с принятием ADR (создан в этой сессии).

### ADR-0009: стратегия миграции `docs/domain/` (Proposed)

Шесть последовательных фаз миграции:

1. **Миграция домена** — 8 кластеров, фундаментальные модели → торговые сущности → стратегии → сделки → калькуляторы/риски/команды → аудит. Порядок зафиксирован по зависимостям.
2. **Миграция OKX-маппингов** — `docs/domain/models/mapping/okx/*` → `docs/spec/integrations/okx/{models,mapping}/`.
3. **Обработка `Открытые вопросы по движку.md`** — корневой документ legacy, состоящий полностью из открытых вопросов; полный перенос в журнал.
4. **Реорганизация `docs/api/`** — отдельный ADR при старте фазы.
5. **Цикл ревью смигрированной документации** — итеративная фаза, заканчивается в состоянии насыщения (по операционализированным условиям).
6. **Упразднение `docs/domain/`** — удаление папки целиком.

Восемь кластеров фазы 1. Единица миграции — двухуровневая (кластер + spec-документ). Пять hard gates готовности кластера. ## Что решено НЕ делать

- **Не создавать единый `docs/GLOSSARY.md`.** Функции расщеплены на три артефакта.
- **Не создавать отдельный «глоссарий концепций».** Сквозные концепции мигрируют в соответствующие spec-документы по жанрам при миграции своих кластеров.
- **Не предзаводить Q-N в журнале по плану миграции.** Q-N появляются естественно при работе с конкретным legacy-материалом.
- **Не принимать пакет ADR по одному.** Все четыре ADR пакета принимаются разом после стресс-теста.
- **Не заводить отдельных backlog-пунктов на разведку persistence конкретных моделей** (DealActionState, MarketPriceData). Эти вопросы встанут естественно при миграции C1/C7/C6 как Q-N со classification `missing-model`.
- **Не использовать термин «orphan» как канонический.** Используется пара «domain-only / external-only».
- **Не создавать отдельный invariant-документ для domain-only/external-only.** Это терминологическое соглашение, концепция обнаружения и реакции распределяется по соответствующим spec-документам при миграции (или появляется как Q-N).
- **Не использовать слово «entity» как канонический термин.** Используется «доменная модель».
- **Не править ADR-0006 §1 на «торговые сущности» вместо persistence-критерия.** Буквальная формулировка ADR-0006 (persistence-критерий) остаётся; интуитивное расширение в terminology.md описывает как ось работает на практике. Правка ADR — кандидат на следующую ретроспективу, если на практике возникнет реальное противоречие.
- **Не создавать отдельный скилл для terminology.md.** Объём правил мал, формат стабильный. Если терминология разрастётся — пересмотреть.
- **Не предзаявлять целевые spec-документы в migration-tracker.** Они появляются по факту создания при миграции, не как план.
- **Не дублировать состав кластеров в скилле `spec-cluster-migration`.** Источник состава — ADR-0009 §2 и трекер; скилл описывает процедуру, не данные.

## Как использовать этот документ

Snapshot — навигационный. Используется:

- Чтобы понять, в каком состоянии проект на 2026-05-16 после завершения Этапа 4 в репозитории.
- Чтобы новая сессия (стресс-тест) видела текущую картину без перечитывания всех обсуждений.
- Как индекс будущих задач (стресс-тест, принятие пакета, старт первого кластера).

Не редактируется задним числом. Если состояние изменится значимо (после стресс-теста, после перевода ADR в Accepted, после первого кластера) — создаётся следующая версия.

История архитектурных решений — `../adr/`.
Чеклист прогресса миграции — `../planning/migration-tracker.md`.
