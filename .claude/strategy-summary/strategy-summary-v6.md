## Принятые концептуальные решения

Сохраняются все 26 решений snapshot v5 + новые решения итерации 1 (продолжается сквозная нумерация).

27. **Lifecycle-документ для моделей со статусами** (ADR-0006 §3 после Правки 1). Для любой модели со статусами выделяется пара документов: model-документ содержит enum и семантику статусов; lifecycle-документ той же модели содержит таблицу переходов, доменные запреты с обоснованием, инварианты поведения, обработку сбоев. Если у модели нет переходов — lifecycle не создаётся. Структурные запреты переходов не пишутся явно (отсутствие = запрет). Прецедент AnomalyReport — пример корректного применения.

28. **Алгоритм миграции «заглушка + Q-N».** Единица миграции — один legacy-документ. Каждое упомянутое имя классифицируется по тестам типа сущности (модель / реализационный класс / значение / процесс / invariant / integration / reference). Содержательное описание → создаём/дополняем целевой документ. Пустое упоминание имени → Q-N в журнале с classification `missing-<тип>`. Заглушка (документ с заполненными определением и связями, но без структурных полей) — валидное состояние; сопровождается открытым Q-N о содержательном пробеле. Markdown-ссылка на несуществующий документ запрещена — прозаическое упоминание + Q-N. Зафиксировано в скиллах `spec-document-migration` и `spec-cluster-migration`.

29. **MODELS.md — отражение, не гейт.** Реестр обновляется как следствие создания model-документа (включая заглушку), не предшествует ему. При классификации имени по тестам типа сущности проверяется содержание legacy, не наличие в реестре. Дрейф флагируется только в одну сторону: документ существует в `docs/spec/models/`, имени нет в реестре. Обратная ситуация (имя упомянуто, в реестре нет) — штатное состояние по алгоритму миграции (имя может прозвучать раньше документа, с Q-N отслеживающим пробел). Зафиксировано в скиллах `spec-models-registry`, `spec-document-migration` и в проверках knowledge-curator.

30. **Семейство classification `missing-*`** (ADR-0008 §4 после Правки 2). Помимо `missing-model` введены `missing-process` (процесс упомянут, описания нет) и `missing-invariant` (кросс-модельное правило упомянуто, описания нет). Типичная судьба у всех трёх одинаковая: довоз содержания из другого legacy → создание соответствующего документа → автоматическое закрытие Q-N. Список classification — 10 значений (9 содержательных + 1 служебная `unclassified`).

31. **Режим as-if-Accepted для пакета Proposed-ADR во время итеративной доводки.** Пакет Proposed-ADR считается стабильным снапшотом на время итерации. Правки тела ADR накапливаются в журнале `.claude/notes/adr-drafts/adr-fixes-iteration-N.md`, не применяются по ходу итерации. В конце итерации правки применяются разом, журнал удаляется, следующая итерация начинается на новом снапшоте. Правки инфраструктуры (скиллы, агенты, шаблоны) применяются сразу — они не тестируются в качестве части пакета ADR. Зафиксировано в working-with-claude.md.

32. **Принцип самостоятельности скиллов и агентов.** Правила, по которым кк применяет действия, живут в скиллах и промптах агентов. ADR — обоснование решений, не источник для применения. Скилл не содержит «по ADR-NNNN §X» как ссылку на правило, которое нужно применить — правила записываются в самом скилле, ADR упоминается для контекста. При изменении правила правится скилл/агент; ADR обновляется как обоснование задним числом, не как источник применения. Зафиксировано в working-with-claude.md.

33. **Методология итеративной доводки через dry-run.** Цикл: dry-run прогон → анализ отчёта отдельной сессией кк → группировка пробелов в пакеты (приоритет B → A повторные → A одиночные → C → E → D) → обработка пакетов по очереди (отдельная сессия чата на формулировку, отдельная сессия кк на применение) → правки Proposed-ADR в журнал, не применяются по ходу → финальная сессия итерации (применение журнала, snapshot, лог) → следующий dry-run при необходимости. Итерации до насыщения (тест перестаёт находить значимое; 3-4 итерации без насыщения — сигнал к содержательному пересмотру концепции). Зафиксировано в Сценарии 10 playbook.

## Состав пакета ADR-0006..0009

Все четыре в статусе Proposed. Перевод в Accepted — после насыщения цикла dry-run → доводка.

### ADR-0006: принципы спецификации (Proposed)

Четыре принципа организации содержания spec-документов:

1. **Декомпозиция моделей.** Один бизнес-объект — один model-документ. Вложенные модели — разделами внутри. Критерий бизнес-объекта (identity, независимый жизненный цикл, способность быть субъектом операций, смысл в отрыве). Дополнительное деление: core vs runtime.

2. **Инварианты: локальные vs кросс-модельные.** Локальные — внутри model/lifecycle/process документа модели. Кросс-модельные — в `invariants/`. Операционализированный тест разделения.

3. **Статусные таксономии** (после Правки 1). Для любой модели со статусами — пара документов: model-документ содержит enum и семантику; lifecycle-документ той же модели — переходы и инварианты поведения. Структурные запреты не пишутся (отсутствие = запрет); явно пишутся только доменные запреты с обоснованием. Двухуровневый резолвер биржевых статусов (общий контракт в invariant + конкретные таблицы маппинга в integration-документации).

4. **Addenda при миграции.** Запрещено добавлять «дополнения после миграции» отдельными разделами. Нерешённые остатки → журнал Q-N.

### ADR-0007: структура `docs/spec/` (Proposed)

Подкаталоговая структура: `models/core/`, `models/runtime/`, `lifecycle/`, `processes/`, `integrations/<exchange>/{models,mapping}/`, `references/`, `invariants/`. `MODELS.md` в корне как реестр имён и навигационная точка входа. `docs/api/` остаётся самостоятельным жанром.

### ADR-0008: журнал open-questions (Proposed, после Правки 2)

- Структура entry: 11 полей.
- Статусы: Added → Resolved.
- Classification: **10 значений** — 9 содержательных + 1 служебная.
  - Вопросы, требующие решения: `concept`, `missing-model`, `missing-process`, `missing-invariant`, `contradiction`.
  - Рабочая задача: `structural`.
  - Кандидаты на устаревание: `legacy-bug`, `obsolete-by-decision`, `obsolete-by-context`.
  - Служебная: `unclassified`.
- Три условия устаревания (содержательное решение зафиксировано / контекст исчез / некорректно сформулирован).
- Шаблон в `.claude/templates/documents/`. Скилл `open-questions-workflow`.

### ADR-0009: стратегия миграции `docs/domain/` (Proposed)

Шесть последовательных фаз: миграция домена (8 кластеров) → OKX-маппинги → обработка открытых вопросов движка → реорганизация `docs/api/` → цикл ревью → упразднение legacy. Восемь кластеров фазы 1. Единица миграции — двухуровневая (кластер + spec-документ). Пять hard gates готовности кластера. Скилл `spec-cluster-migration` и Сценарий 9 в playbook.

### Источники правды о системе (`docs/`)

- **`docs/spec/`** — целевая спецификация, главный приоритет.

## Что решено НЕ делать

Сохраняются все пункты v5, плюс новые в итерации 1.

- **Не создавать единый `docs/GLOSSARY.md`.** Функции расщеплены на три артефакта.
- **Не создавать отдельный «глоссарий концепций».** Сквозные концепции мигрируют в соответствующие spec-документы по жанрам.
- **Не предзаводить Q-N в журнале по плану миграции.** Q-N появляются естественно при работе с конкретным legacy-материалом.
- **Не принимать пакет ADR по одному.** Все четыре ADR пакета принимаются разом после насыщения dry-run.
- **Не заводить отдельных backlog-пунктов на разведку persistence конкретных моделей.** Эти вопросы встанут естественно при миграции как Q-N со classification `missing-model`.
- **Не использовать термин «orphan» как канонический.** Пара «domain-only / external-only».
- **Не создавать отдельный invariant-документ для domain-only/external-only.**
- **Не использовать слово «entity» как канонический термин.** «Доменная модель».
- **Не править ADR-0006 §1 на «торговые сущности» вместо persistence-критерия.**
- **Не создавать отдельный скилл для terminology.md.**
- **Не предзаявлять целевые spec-документы в migration-tracker.**
- **Не дублировать состав кластеров в скилле `spec-cluster-migration`.**
- **Не выносить определение «модель = поля + локальные инварианты» в terminology.md.** Определение модели остаётся внутри тестов типа сущности в скилле `spec-document-migration`. terminology.md — для канонических форм слов, не для определений жанров.
- **Не сохранять забегающие ссылки как штатный механизм.** Прозаические упоминания имён без markdown-ссылки заменены на алгоритм «заглушка + Q-N» через ADR-0009 §5 (после применения правок итерации). Markdown-ссылка на несуществующий документ остаётся запрещённой; до создания документа — Q-N в журнале + прозаическое упоминание.
- **Не править Proposed-ADR по ходу итерации.** Правки накапливаются в журнале `adr-fixes-iteration-N.md`, применяются разом в конце итерации.
- **Не считать «расхождение скилла с ADR» автоматическим сигналом править ADR.** Если расхождение — это естественная эволюция инфраструктуры под практику, обновляется ADR как обоснование. Если ADR содержательно верен, а скилл ошибся — правится скилл. Решение принимается per-case, не по умолчанию в одну сторону.

## Как использовать этот документ

Snapshot — навигационный. Используется:

- Чтобы понять, в каком состоянии проект на 2026-05-18 после итерации 1 доводки пакета ADR-0006..0009.
- Чтобы новая сессия (V2 dry-run) видела текущую картину без перечитывания всех обсуждений итерации.
- Как индекс будущих задач (V2 dry-run, принятие пакета, старт первого кластера).

Не редактируется задним числом. Если состояние изменится значимо (после V2, после принятия пакета, после первого кластера) — создаётся следующая версия.
