# Codestyle

## На какой вопрос отвечает этот файл

Как мы пишем код (конвенции написания).

## Назначение

Конвенции написания кода проекта. Опора `code-writer` при письме и
фокуса `conventions-review` при проверке кода.

## Принципы

- **DDD** — проектируем от доменной модели.
- **Clean Code** — код читается как проза.
- **Гибкость и переиспользуемость** — без преждевременной
  абстракции, но с расчётом на расширение.
- **Rich-доменные модели** — бизнес-логика живёт на доменных моделях,
  не размазана по сервисам. Поток: вход из внешнего слоя → маппинг в
  домен → выполнение логики на домене → при необходимости маппинг
  обратно. На моделях интеграции, граничных снапшотов, персистентности
  и api бизнес-логика не выполняется; допустима только структурная
  валидация своего слоя.
- **Lombok** — убираем boilerplate, но не прячем за ним
  бизнес-логику.

## Поля и доступ к ним

- Все поля классов — `private`.
- Доступ к полям — только через аннотации Lombok (`@Getter`,
  `@Setter`, конструкторы), не через вручную написанные
  геттеры/сеттеры/конструкторы-аксессоры. Руками пишем только
  методы с логикой (бизнес-методы домена, фабрики-парсеры
  граничных DTO), а не голые аксессоры, которые сгенерировал бы
  Lombok.
- `@Value` уже делает поля `private final` (через `@FieldDefaults`)
  — явный `private` на полях `@Value`-классов не пишем.

## Примитивы и обёртки

- На **контрактной поверхности** (публичные методы сервисов,
  мапперов, доменных моделей) параметры и возвращаемые типы — это
  обёртки (`Long`, `Integer`, `Boolean`, `Double`, ...), не
  примитивы.
- Поля, доступные через Lombok-аксессоры, — тоже обёртки (чтобы
  геттер/сеттер не работал с примитивом).
- На call-site и в `return` конвертацию делает автобоксинг — явный
  `X.valueOf(...)` не пишем (он избыточен, раз контракт уже принимает/
  возвращает обёртку). Меняем контракт на обёртку — лишние обёртки в
  местах вызова убираем.
- Исключения (остаются примитивами):
  - `static final`-константы — нужны как compile-time constant
    (индексы, `@Column(precision = …, scale = …)` и т. п.);
  - приватные чисто-арифметические хелперы и локальная арифметика
    внутри метода;
  - компоненты вспомогательных `record`-value-объектов;
  - перегрузки/индексы библиотечных API, требующих примитив
    (`List.get(int)`, `IntStream` / `mapToLong`);
  - **обратное направление того же исключения — явная обёртка,
    разводящая перегрузку**: `assertEquals(Integer.valueOf(2), x)`
    выбирает перегрузку `(Object, Object)`, и без неё пустое значение
    дало бы NPE вместо падения ассерта. Запрет снимает **избыточную**
    обёртку — ту, которую и так поставил бы автобоксинг; здесь она
    несущая.

## Нейминг по слоям

Одна сущность проходит слои с суффиксом слоя. Пример для
`Instrument`:

| Слой | Класс |
|---|---|
| Домен | `Instrument` |
| Доменный снапшот ответа биржи | `InstrumentExternalSnapshot` |
| Интеграция (сырой ответ источника) | `Instrument{Exchange}Response` (например `InstrumentOkxResponse`) — **суффикс, не префикс** |
| Persistence | `InstrumentEntity` |
| API нашего сервиса | `InstrumentApiResponse` |
| Сообщение внутренней шины | `InstrumentMessage` (§«Слой сообщения: внутренняя шина») |

В домене — полные слова, без сокращений.

**Маркер источника — суффикс, и это не вкусовая развилка.** Вся таблица
выше строится одним способом: имя сущности впереди, маркер слоя в конце
(`InstrumentEntity`, `InstrumentApiResponse`, `InstrumentExternalSnapshot`).
Префиксная форма (`OkxInstrumentResponse`) ломает **систематичность**:
имя сущности уезжает в середину, и слой перестаёт читаться по хвосту.
Пакет `integration.external.api.model.okx.response` источник и так называет, поэтому
префикс к тому же его дублирует.

**Конвенция была расколота ровно пополам** — семь классов суффиксом,
семь префиксом, и в доках так же, — а объявлена только одна.
`GAPS_CLOSE_29` свёл обе стороны к объявленной; момент выбран потому, что
`CODE` шага 7 заводит новые DTO источника, и переименование после него
стоило бы дороже (`.claude/rules/naming.md` §«Разведение уровней
абстракции»: смена способа разведения задним числом — переименование по
всем потребителям).


## Слои (зоны ответственности)

Слоя «Client» нет — граница с биржей называется **Integration**
(пакет `integration`, класс `IntegrationService` и его реализации
`{Exchange}IntegrationService`).

**Сам пакет `integration` разделён**, и раскладку держит §«Слой сообщения:
внутренняя шина»; здесь она не пересказывается. Коротко: синхронный вызов
чужой поверхности — `integration.internal.api` у соседа по монорепозиторию
и `integration.external.api` у системы вне его; сообщение через брокер —
`integration.internal.event` со своими моделями `*Message`.

| Слой | Принимает / отдаёт | Зовёт | Чего не видит |
|---|---|---|---|
| Controller | api ↔ domain | Service | integration DTO, `OkxRestClient` |
| Service | domain | IntegrationService, DataService | — |
| IntegrationService | domain ↔ integration DTO | `OkxRestClient` | — |
| DataService | domain ↔ persistence | Repository | — |
| Job (`domain.jobs`) | domain | Service, доменные хелперы | — |
| Писатель факта (`integration.internal.event`) | domain → message → строка outbox | маппер, DataService | — |
| Публикатор шины (`integration.internal.event`) | message → брокер | `KafkaTemplate` | domain |
| Слушатель шины (`integration.internal.event`) | брокер → message → domain (маппером) | Service, DataService | — |
| `OkxRestClient` | чистый HTTP + подпись + DTO | — | domain |
| Repository | интерфейсы-запросы (нативные — через аннотации) | — | — |

- Controller принимает api, делает `apiToDomain`, дальше работает
  только с domain; integration DTO и `OkxRestClient` ему недоступны.
- Service принимает domain, держит прикладную логику.
- IntegrationService — единственная граница domain ↔ integration DTO.
- **Константы источника границу тоже не переходят.** `Constants.<Источник>`
  читают слои, которые с источником и говорят: `integration` и мапперы.
  Доменный слой источникового литерала не знает — ни в поле, ни в
  сравнении, ни в тернарнике: иначе граница проведена для DTO и открыта
  для значений, а при втором источнике доменный код молча остаётся с
  чужим словарём.

  **Объявленного долга на этой границе больше нет.** Сторона заявки —
  доменный перечень `Order.Side` (`docs/models/domain/core/Order.md`), а
  перевод в словарь площадки делает коннектор на своей границе
  (`docs/models/mapping/Order.md`). Прежде поле было `String` с литералом
  источника, и это стоя́ло названным долгом; условие возврата сработало на
  шаге 3 фазы 2, когда `Order` переехал в общую библиотеку, чей критерий
  устойчивости такое поле нарушает по построению.
- DataService — единственная граница domain ↔ persistence.
- **Шина — единственная граница domain ↔ message**, и проходится она
  маппером: доменный код формы сообщения не строит и в сигнатурах её не
  держит (§«Слой сообщения: внутренняя шина»).

### Идентичность наружу — `internalId`, не id из БД

- API-слой не отдаёт наружу `id` сущности из БД. Внешний
  идентификатор — `internalId`.
- Это касается и тела ответа, и path-параметров, и ссылок на
  связанные сущности: в api-моделях вместо `id`/FK-`id` —
  `internalId` своей сущности и `internalId` связанной (например,
  `exchangeInternalId`, `instrumentInternalId`); резолв
  `internalId` ↔ `id` связанной сущности делает Service.
- Path-параметры контроллеров — `internalId` (строка), сервисы
  читают через `getRequiredByInternalId`.
- Внутри (domain ↔ persistence, связи между сущностями) ссылки
  по-прежнему по числовому `id` — это деталь хранения, наружу не
  выходит.

### Джобы

- Джобы (`@Scheduled`) живут в отдельном пакете `domain.jobs`; их
  фасады — в `domain.jobs.facade`.
- Кроме расписания, джоба триггерится вне расписания через
  контроллер. Такой запуск — **асинхронный** (не блокирует ответ
  HTTP) и идёт **через фасад**: Controller → `{Job}Facade`
  (`@Async`) → Job. Приложение помечается `@EnableAsync`.
- **Каждая джоба — с выключателем и CRON в конфиге.** Период тика —
  `@Scheduled(cron = "${...}")` из конфигурации (не хардкод); плюс
  булев флаг `enabled` (тоже в конфиге, через `@ConfigurationProperties`):
  при `false` запланированный и ручной (через фасад) тик ничего не
  делают. Тело джобы вынесено в приватный `run()`, метод `@Scheduled`
  проверяет `enabled` и делегирует.
- **Тик живости соединения — джоба, но не всех четырёх требований.**
  Периодический тик, который **не производит работы** (пульс потока в
  браузер), живёт в `domain.jobs` и несёт выключатель, как всякая джоба,
  но **ручного фасада и защиты от перекрытия у него нет, и это
  объявлено, а не забыто**: догонять ему нечего — пропущенный тик
  бессмыслен по построению, а `fixedDelay` следующий тик до конца
  текущего не запускает. **Признак класса механический, и он о РАБОТЕ, а не
  о записи: пропущенный тик не оставляет невыполненной работы** — следующий
  производит тот же исход актуальным моментом.

  **Прежняя редакция признака** («тик не меняет состояния ни в базе, ни у
  соседа») снята расширением: она описывала первый встреченный кейс, а не
  предмет класса. Тик, чей единственный след — **отметка собственного
  момента**, перезаписываемая следующим тактом, работы не производит, хотя
  в базу и пишет; чистка по глубине не производит её тоже — следующий проход
  удаляет всё, что старше глубины, включая пропущенное. Джоба, чей
  пропущенный тик оставляет **невосполненный ряд** (свечи, индикаторы,
  агрегаты за окно), в класс не попадает и несёт все четыре требования.

  **Экземпция снимает две обязанности, и доводы у них РАЗНЫЕ.** Признак
  работы («пропущенный тик не оставляет невыполненной работы») снимает
  **ручной фасад**: догонять нечего, значит и запускать вне расписания
  нечего. **Защиту от перекрытия снимает не он, а ПАРА: форма такта плюс
  отсутствие второго запускающего.** `fixedDelay` не пускает следующий
  запуск **по расписанию** до конца текущего, а ручной фасад есть второй
  источник запуска — с ним перекрытие возможно при любой форме такта.
  Отсюда механический признак: охраны нет только у джобы, у которой **и**
  такт `fixedDelay`, **и** фасада нет; джоба с CRON её не наследует,
  сколько бы верен ни был у неё признак работы, — расписание бьёт
  независимо от того, кончился ли предыдущий проход. *(Кейс: джоба чистки
  по глубине унаследовала экземпцию соседнего тика целиком, имея CRON и
  проход, удаляющий ограниченными порциями.)*

  **Второй довод бывает свой у сервиса, и он старше общего.** У сервиса,
  чья поверхность объявлена **только читающей**, ручной фасад завёл бы
  входящую точку записи — то есть снял бы клейм инвентаря; тогда фасада нет
  у **всех** его джоб, независимо от класса тика.

  **Что у такого тика обязано быть вместо них — операнд живости.** Тик,
  бьющийся по расписанию независимо от того, живо ли наблюдаемое, мерит
  собственный планировщик и о предмете не сообщает ничего; молчание
  тогда неотличимо от тишины. Поэтому тик живости обязан проверять
  живость **наблюдаемого** и молчать, когда её нет. *(Кейс: пульс потока
  в браузер бился и при мёртвом потребителе тем — то есть показывал
  живую картину в ровно том состоянии, против которого заведён.)*

  **Операнда живости мало: такт обязан ДОСТАТЬСЯ тику.** `@Scheduled`-методы
  сервиса делят один поток планировщика — `spring.task.scheduling.pool.size`
  по умолчанию равен единице, — и пока сосед его держит, тик не исполняется
  вовсе. У джобы, **производящей продукт**, это задержка работы, наблюдаемая
  через её собственный выход; у **измерителя** — это задержка **измерения**, и
  голодающий тик наблюдателю неотличим от состояния наблюдаемого. Поэтому у
  сервиса, среди джоб которого есть измеритель, **размер пула планировщика
  выводится из числа его `@Scheduled`-методов** и объявляется величиной
  конфигурации сервиса. Признак механический — **измеритель среди джоб**, а не
  число джоб само по себе: сервису, у которого измерителя нет, правило не
  предписывает ничего.

  **Признак измерителя — ПАРА, и обе половины читаются по ВЫХОДУ тика.**

  - **Выход тика есть измерение о ЧУЖОМ состоянии**, а не собственный продукт
    джобы: возраст последнего принятого события, счёт ненаблюдённых проходов,
    признак живости потребителя — против свечей, индикаторов, опубликованных
    строк и синхронизованной ставки, которые джоба сама и производит.
  - **Голодание тика это измерение подменяет:** по выходу нельзя отличить
    «тик не исполнялся» от «наблюдаемое в таком состоянии». Молчание уходит
    либо в «наблюдаемое мертво» (возраст растёт одинаково в обоих случаях),
    либо в «наблюдаемое здорово» (счётчик стои́т на нуле, потому что двигают
    его только состоявшиеся проходы).

  **Джоба, производящая продукт, в признак не попадает, и довод не в жанре, а
  в ВЕРНОСТИ ВЫВОДА:** её пропущенный тик оставляет продукт действительно
  отсутствующим или устаревшим, и читатель, заключивший «данных нет, входить
  нельзя» либо «ставка стара», прав независимо от причины. У измерителя тот же
  читатель заключает о **наблюдаемом** — и ошибается.

  **Прежняя редакция признака** — приложение через экспортируемый наблюдателю
  окружения ряд — снята этой. Она называла первый встреченный случай, а не
  предмет: сервис, у которого экспорта метрик не построено вовсе, получал
  «измерителя нет» **по построению**, то есть применимость правила
  оказывалась свойством инфраструктуры наблюдения, а не свойством джобы. Ряд
  делает неразличимость видимой **снаружи**; создаёт её форма выхода.
  *(Кейс: контурная джоба safety-сети, чей чистый проход обнулял уже нулевой
  счётчик слепоты bulk-`update`'ом без момента, а несостоявшийся не двигал
  счётчика вовсе. Обе стороны читались одинаково — «наблюдение идёт, аномалий
  нет», — и предел слепоты считал только СОСТОЯВШИЕСЯ проходы; при этом
  калибровка предела была переведена в время дословно и выведена из такта,
  которого тик мог не получить.)*

  **Вывод числа обязан иметь охрану, иначе он держится совпадением.** Пул и
  число джоб лежат в разных файлах, и четвёртая джоба, заведённая без правки
  пула, вернула бы голодание молча. Охрана — проба, которая **считает**
  `@Scheduled`-методы дерева и сверяет счёт с объявленным числом; без неё
  инвариант не мерится ничем. *(Кейс: тик живости приёма — единственный
  писатель и durable-момента, и рядов экспорта — делил один поток с чисткой
  журнала и почасовым пересчётом агрегатов, а порог возраста был откалиброван
  от такта, которого тик мог не получить.)*

  **Пул больше единицы делает проходы сервиса ОДНОВРЕМЕННЫМИ, и это
  проверяется, а не подразумевается.** Охрана ниже запрещает перекрытие джобы
  **с самой собой** и о соседях не знает; ход, поднимающий пул, обязан пройти
  пары джоб сервиса и назвать по каждой, что общего они пишут и чем разведены.
- **Защита от конкурентного выполнения.** Тик идёт через
  `JobExecutionGuard.runExclusively(jobName, run)`: пока один запуск
  джобы активен, перекрывающий (затянувшийся предыдущий тик или ручной
  триггер параллельно расписанию) пропускается. Guard — in-memory на
  инстанс; распределённый лок (ShedLock и т. п.) — на мультиинстансе
  после архитектурного рубежа.

## Слой сообщения: внутренняя шина

**Правило (решение держателя, 2026-09-12).**

**`integration` — граница с чужой СИНХРОННОЙ поверхностью, и делится она по
собеседнику: `internal` — соседний сервис монорепозитория, `external` —
система за его пределами. То, что едет СООБЩЕНИЕМ через брокер, живёт своим
слоем `integration.internal.event`: у него свои модели с суффиксом
`Message`, свой пакет и свои мапперы, а домен его форм не видит.**

### Раскладка пакетов

    <сервис>
    ├── integration
    │   ├── internal
    │   │   ├── event       шина: писатель факта, публикатор, слушатель,
    │   │   │   │           чтец конверта, смещения, ребаланс, отказ
    │   │   │   └── model   формы сообщения — `*Message`
    │   │   └── api         синхронный вызов соседа по монорепозиторию
    │   │       └── model   формы его запроса и ответа
    │   └── external
    │       └── api         синхронный вызов системы вне монорепозитория
    │           └── model   формы источника
    └── mapping             мапперы сервиса, в том числе message ↔ domain

Мапперы живут в общем `mapping` сервиса, а не внутри слоя: конвенция «один
маппер на сущность» ведёт счёт по сущности, а не по тому, какую границу она
сегодня пересекает.

### Признак деления механический, и осей у него две

- **Собеседник** — сервис монорепозитория (`internal`) либо система вне его
  (`external`). Читается по коду: адрес соседа приезжает конфигурацией
  `neighbours.*`, адрес внешнего — своей.
- **Транспорт** — синхронный вызов чужой поверхности (`api`) либо сообщение
  через брокер (`event`).

Ни одна ось не выводится из другой, и обе читаются по коду, а не по замыслу.
**У брокера собеседника нет вовсе** — есть тема, и потому шина попадает в
`internal` не по адресу получателя, а по тому, что темы монорепозитория
заводит он сам.

**Вызов соседа остаётся интеграцией, и это названо, а не умолчано.** Сосед —
чужой процесс с собственным контрактом: его ответ приезжает **его** формой, а
не доменной моделью вызывающего. Деление `internal`/`external` эту границу не
снимает — оно говорит, **чья** поверхность за ней.

### Модели слоя — с суффиксом `Message`

Форма, которая едет сообщением, есть модель слоя наравне с `*Entity` и
`*ApiResponse` (§«Нейминг по слоям»): `DealOpenedMessage`,
`StrategyActivatedMessage`, `AuditEventMessage`.

**Доменного класса на проводе не бывает.** У rich-модели предикаты — методы,
и сериализатор вывел бы их полями; потребитель обопрётся на то, что увидит.
Обратное направление того же запрета: форма сообщения **бизнес-логики не
исполняет** — она структура, и её единственная работа состоит в том, чтобы
пережить сериализацию.

### Домен формы сообщения не строит и не читает

Перевод domain ↔ message делает маппер, а форму никогда не держит доменный
код — ни на приёме, ни на публикации:

- **`domainToMessage` у производителя**, `messageToDomain` у потребителя;
  когда форм несколько, цель называется в имени
  (`domainToDealOpenedMessage`). Фабрика вида `XxxMessage.of(доменная
  модель)` на самой форме — дефект: она ставит сборку провода в доменный
  слой и прячет границу.
- **Доменный сервис принимает доменные значения.** Слушатель распаковывает
  сообщение и передаёт дальше то, что домен понимает, — модель либо её
  идентичность. Доменный сервис с параметром `*Message` в сигнатуре есть та
  же граница, проведённая на слой глубже, чем объявлено.
- **Доменный сервис и ОТДАЁТ доменные значения.** Производитель зовёт
  писателя факта — бин слоя шины с методом на класс события и доменными
  аргументами (`coreEventWriter.dealOpened(tenantId, deal, …)`); маппер
  зовёт писатель, а не домен. Иначе форма проходит **через** доменный код
  транзитом: имени её в сигнатурах не видно, а значение лежит в аргументе.

**Признак механический: доменное имя не встречается в сигнатурах слоя
домена и не возникает у него в выражениях.** Мерится грепом по двум осям —
импорт пакета форм в `**/domain/**` и слово `Message` в его теле; обе оси
обязаны быть пусты.

*(Кейс, на котором записано: писатель outbox жил в `domain.event`, принимал
уже собранное содержимое параметром `Object` и строил конверт сам. Имени
формы в сигнатуре не было — параметр `Object`, — но класс и называл
`EventEnvelopeMessage`, и сериализовал содержимое. Транзит же проходил
через семь доменных сервисов, каждый из которых звал маппер и передавал
результат дальше.)*

**У маппера формы сообщения непокрытая цель — ОШИБКА, а не умолчание.** Общий
дефолт мапперов (`unmappedTargetPolicy = IGNORE`) заведён под слои, где часть
полей цели законно пуста; у формы сообщения пустое поле есть **потерянный
факт у читателя на другой стороне провода**, и замечает он его в проде, а не
при сборке. Поэтому у такого маппера (либо у такого метода — `@BeanMapping`)
политика ужесточается до `ERROR`: поле, забытое при расширении содержимого,
роняет компиляцию.

### Общие формы — один носитель на обе стороны провода

Форма, которую пишет один сервис и читает другой, живёт в общем артефакте
`services/common/model` (пакет `com.example.tradingbot.message`), а не копией
у каждой стороны: две записи одной формы расходятся первой же правкой
(`.claude/rules/carrier-levels.md`). Форма, у которой читатель — тот же
сервис (прочитанное сообщение у потребителя), остаётся в его
`integration.internal.event.model`.

**Перечень классов события остаётся в домене.** Enum'ы объявляются только в
доменном слое (§«Слои моделей и enum'ы»), а `CoreEventType` и
`StrategyEventType` называют доменные происшествия; на проводе они едут
именем, и разбор имени в значение делает граница.

**Исключение одно, и оно предъявлено, а не выведено.** Содержимое активации
определения стратегии несёт **снимок доменного дерева** целиком: зеркало
этого дерева в слое сообщения было бы вторым носителем одной формы и
разошлось бы с первым при первом расширении каталога условий. Поэтому
`common/model/message` зависит от `domain-model` — ровно одной зависимостью и ровно
ради этого снимка.

### Что правило снимает

Класс «имя пакета перестало предписывать». Пока у сервиса один вид границы,
слово «интеграция» значит «то, что снаружи», и различать нечего. Как только
видов два, слово покрывает оба, и по имени пакета нельзя сказать, с кем класс
говорит: рядом лежат слушатель брокера, клиент соседа и биржевой контур, а
объявленная зона ответственности у них разная.

**Замер, на котором правило стои́т** (2026-09-12): у `audit-statistics` пакет
`integration` состоял из кода брокера **целиком** — 9 файлов из 9; у
`trading-core` тот же пакет держал 2 файла брокера, 7 клиентов соседей, 9
файлов биржевого контура и 11 форм чужих ответов. Слоя сообщения при этом не
существовало ни у одного сервиса: слушатели читали запись брокера **прямо в
доменную модель**, а доменные сервисы-производители собирали форму провода
фабриками на ней самой — то есть граница была объявлена для DTO источника и
открыта для шины.

### Чего правило НЕ означает

- **Не делит сам домен.** Доменные модели, джобы и сервисы остаются там, где
  были; меняется раскладка границы, а не то, что за ней.
- **Не запрещает слушателю знать конверт.** Заголовки, смещения, ребаланс и
  обработка отказа — предмет слоя шины, и они его не покидают.
- **Не требует формы сообщения там, где её читателя нет.** Значение, живущее
  только в памяти прохода, остаётся доменным; признак применимости — что у
  формы есть **читатель на другой стороне провода**.
- **Не отменяет §«Неизменяемое значение, пересекающее сериализацию».** Форма
  сообщения под него попадает по построению: у неё читатель есть всегда.

### Цена принята и названа

- **Границ у сервиса стало две вместо одной, и выбор делает пишущий.** Оси
  механические, но прогона у них нет: класс, положенный в `internal.api`
  вместо `internal.event`, не поймает ни один инструмент корпуса.
- **Сообщение проходит лишний перевод.** Слушатель собирает форму, маппер
  переводит её в домен — там, где прежде был один ход. Взамен момент приёма,
  инвариант полноты и разбор заголовков перестали жить в одном классе.
- **Общий артефакт форм зависит от доменного.** Зависимость одна и названа
  выше; она делает `common/model/message` непереносимым в чужой репозиторий без
  `domain-model` — цена принята за единственность носителя формы определения.

## Выборка данных: не тянем сущность ради одного поля

- Если из сущности нужно одно-два поля (типичный случай — резолв
  `id` ↔ `internalId` связанной сущности) — тянем **проекцию** этих
  полей запросом репозитория (`select e.field …`), а не всю сущность
  ради последующего `.getField()`.
- Резолв одного поля оформляется методом `getRequired<Field>By<Key>`
  в соответствующем `DataService` поверх проекции репозитория, не
  `getRequiredBy…().get<Field>()` на полной сущности.
- **Правило проекции адресует ЧТЕНИЕ ПОЛЯ, а не вызов предиката.** Когда
  нужен не `.getField()`, а **вопрос к модели** (`order.isLive()`,
  `tranche.isCovered()`), старше §«Вложенность и rich-модели»: предикат
  остаётся на модели, а сущность грузится целиком. Обратное — вынести
  предикат в сервис ради проекции — размазывает бизнес-логику по слоям,
  против чего заведено само правило rich-моделей. Дорогая загрузка
  лечится **пакетностью** (`findAllBy…In` плюс раскладка в памяти), а не
  переносом предиката.
- **Потенциально большие выборки — только ограниченным окном или
  пагинацией.** Запрос, который может вернуть много строк (например,
  все свечи группы — минутные за годы кладут БД), не делаем «вытащить
  всё»: грузим ограниченное недавнее окно (`Pageable` / `LIMIT`,
  `find…OrderBy…Desc(…, Pageable)` + реверс) либо переосмысливаем
  логику, чтобы тяжёлого запроса не было вовсе. Если нужно несколько
  сущностей из БД — через пагинацию/окно, не безлимитным `findAll`-подобным
  чтением.

## Вложенность и rich-модели

- Глубокая вложенность `if` плохо читается. Снижаем её **guard-clause**
  (ранний `return`) или объединением условий — «тело» метода держим
  неглубоким.
- Проверки состояния и бизнес-инварианты сущности живут **в самой
  модели** (rich-модель), не в сервисе: вместо
  `Objects.equals(x.getStatus(), Status.FOO)` в сервисе — предикат
  `x.isFoo()` на модели; сложное условие — отдельным методом модели,
  возвращающим `Boolean`.
- Если проверка опирается только на саму модель и её данные —
  предпочитаем объединить в одно условие/метод модели (меньше
  ветвлений). Если проверка затрагивает не только модель (внешние
  сервисы, сторонние данные) — раскладываем ранними `return`-guard'ами,
  оставляя тело неглубоким.
- Предикат модели проверяет её собственные данные. Если для проверки
  нужны связанные сущности (например, группы свечей инструмента) —
  грузим их в эту модель спец-запросом (`join fetch`), а проверку
  делаем методом модели, а не тащим коллекцию параметром через сервис.

## Неиспользуемый код

- Метода, который никто не вызывает (репозиторный запрос, метод
  сервиса/маппера, приватный хелпер), в коде быть не должно. Методы
  заводим по потребности, не превентивно, и удаляем, когда они
  перестают использоваться.
- Исключение — Lombok-аксессоры и свойства `@ConfigurationProperties`:
  их «использование» идёт через биндинг конфигурации / доступ к
  модели, не обязательно прямым вызовом.

## Схема БД

- **Имена таблиц — во множественном числе** (snake_case):
  `strategies`, `strategy_order_actions`, не `strategy_order_action`.
  Правило общее для всех таблиц проекта.
- FK-колонки и имена constraint'ов/индексов остаются в единственном
  числе (`instrument_id`, `fk_strategy_action_step`,
  `uk_strategy_internal_id`).

### Применённая миграция неизменяема — включая комментарии

**Файл миграции, уже накатанный на любую живую базу, не правится ни в
одном байте.** Flyway держит контрольную сумму **всего файла**, поэтому
правка комментария роняет валидацию ровно так же, как правка DDL, — а
падает она при старте приложения, то есть у того, кто миграции не трогал.

**Это не противоречит «новое знание правит прошлое на месте»**
(`docs/concept.md` П4): то правило о **знании**, а миграция — применённый
факт, а не описание. Устаревший комментарий внутри применённой миграции
правится **новой** миграцией (если он живёт в БД — `comment on`), либо не
правится вовсе: его читают в git, как и всякую историю.

**Что делать, когда расхождение уже случилось:** сверить, менялся ли DDL.
Менялся только текст — привести контрольные суммы в
`flyway_schema_history` к локальным (это и делает `flyway repair`) и
доприменить изменённые `comment on`. Менялся DDL — пересоздать базу: до
прод-рубежа таблицы пусты и терять нечего
(`.claude/rules/pre-launch-schema-changes.md`).

*(Кейс: правка §-адреса в комментарии двух применённых миграций — правка
доковой ссылки, к схеме отношения не имеющая, — уронила старт профиля
`test` на `FlywayValidateException` и стоила отдельного разбора.)*

## Слои моделей и enum'ы

- Enum'ы объявляются **только в доменном слое**.
- В остальных слоях (api, persistence, integration DTO)
  соответствующие поля — `String`. Конвертацию String ↔ enum на
  границах делает MapStruct автоматически (`name()` / `valueOf`).
- В БД enum хранится строкой (значение = `name()` доменного
  enum); persistence-поле — `String` без `@Enumerated`.

## Auditable по слоям

Если доменная модель наследует базовый `Auditable`, то аналогичные
базовые типы заводятся **в каждом слое отдельно, с постфиксом
слоя**, и каждый слой наследует свой:

| Слой | Базовый тип |
|---|---|
| Домен | `Auditable` |
| Persistence | `AuditableEntity` |
| API | `AuditableApiResponse` |

Доменный базовый тип в других слоях не переиспользуется. Системные
audit-поля проставляет persistence (JPA auditing); биржевые
`external*` — код, производящий данные.

## Маппинг

- Только **MapStruct**, ручного маппинга нет.
- Один mapper на сущность.
- **Имена методов отражают слои-участники** (источник → цель):
  `apiToDomain`, `domainToApi`, `domainToPersistence`,
  `persistenceToDomain`, `integrationToSnapshot`, `snapshotToDomain`,
  `domainToMessage`, `messageToDomain`, `messageToApi`
  и аналогичные. Суффикс слоя в имени метода — `Persistence` (не
  `Entity`), `Integration` (не `Client`), `Message` (не `Event`).
  Когда форм у одного направления несколько, цель называется в имени
  (`domainToDealOpenedMessage`): перегрузка по типу возврата невозможна,
  а `domainToMessage` во множественном числе перестаёт адресовать.
- Цепочка `api → domain → …` обязательна **даже при 1:1** (не
  срезаем слой).
- integration/OKX DTO наружу не отдаём; доменный слой работает
  только с доменными моделями.
- Маппинг — на границах: контроллер `apiToDomain` → домен;
  `DataService` — domain ↔ persistence; `IntegrationService` —
  domain ↔ integration DTO.
- **Без избыточных `@Mapping`.** Когда имена полей источника и цели
  совпадают — `@Mapping(target = "x", source = "x")` не ставим,
  полагаемся на маппинг по имени. `@Mapping` оставляем только там,
  где имена различаются, нужен `qualifiedByName`/выражение или
  явный `ignore`. Непокрытые целевые поля гасим на уровне маппера
  `unmappedTargetPolicy = ReportingPolicy.IGNORE`, а не списком
  `@Mapping(..., ignore = true)` для каждого совпадающего поля.
- **Обновление сущности из снапшота — маппером, не вызывающим
  кодом.** Перенос полей `*ExternalSnapshot` → доменную сущность (при
  `REFRESH`-контуре и т. п.) делает маппер методом
  `updateFromSnapshot(snapshot, @MappingTarget entity)` (MapStruct,
  `@BeanMapping(nullValuePropertyMappingStrategy = IGNORE)` — не
  затирать существующие значения null'ами). Исполнитель/сервис не
  копирует поля сущности вручную (`setX(snapshot.getX())`).
- **Резолв доменного статуса — не в маппере, а в вызывающем коде.**
  Перевод внешнего статуса в доменный (`*ExternalStatusResolver`),
  применение `closeReason` write-once и ERROR-обработка
  (controlled exceptions) — это интерпретация фактов и оркестрация,
  остаётся в исполнителе/сервисе. Маппер делает только перенос
  данных, доменных решений не принимает.

## Неизменяемое значение, пересекающее сериализацию

**У значения, которое кто-то будет ЧИТАТЬ из JSON, форма обязана
собираться без скрытых механизмов.** `@Value` (и `@Value` + `@Builder`)
не даёт ни пустого конструктора, ни инструкции по сборке: сериализатор
восстанавливает такое значение только при удачном стечении обстоятельств
— зарегистрированном модуле имён параметров и флаге компиляции
`-parameters`, — а на другом сериализаторе, чужой аннотации или без флага
падает. Отказ приходит в рантайме, у **читателя**, и написан он в файле,
которого писатель не открывал.

Признак применимости механический: у значения есть **читатель**, а не
только писатель. Пересекает провод между сервисами, ложится в JSONB,
уезжает событием — правило действует. Живёт только в памяти прохода
(контекст, результат исполнения, сигнал) — не действует, там `@Value`
остаётся дефолтом.

Две законные формы, и выбор между ними — по цене переименования:

- **запись (`record`)** — когда аксессоры зовёт только наш новый код:
  сериализатор собирает её по канонической форме, ничего сверх не
  требуя, и неизменяемость сохраняется;
- **бин** (`@Getter @Setter @NoArgsConstructor @AllArgsConstructor`) —
  когда `getXxx()` уже зовут существующие потребители (замороженный
  донор, соседний сервис): запись переименовала бы аксессоры по всем
  вызовам, и цена перевешивает.

**Что НЕ является решением:** `@Jacksonized`. Он выпускает аннотацию
Jackson 2, а на HTTP-проводе проекта работает Jackson 3 (в дереве
зависимостей лежат оба, конвертеры Spring выбирают третий) — аннотация
будет **молча проигнорирована**, и дефект останется, выглядя закрытым.

*(Кейсы, на которых записано: `ExchangeAck` — писался коннектором и не
разбирался никем, пока у него не появился первый читатель; разбор упал на
первой же команде площадке. `RetryError` — тот же класс в навесе JSONB:
отказ пришёл бы на тропе ПОВТОРА, то есть ровно тогда, когда что-то уже
пошло не так.)*

## Пин значения, пересекающего провод: слово или символ

**Значение перечня, по которому ветвится ЧУЖОЙ сервис, проба писателя пинит
СЛОВОМ провода; прочие значения того же перечня — символом.** Слово провода —
литерал (`"HARD"`); символ — само значение перечня (`HoldRung.SOFT.name()`).

**Признак применения механический: есть ли у слова ветвящийся потребитель.**
Потребитель ветвится, когда сравнивает поле с этим словом **у себя** —
литералом в тексте запроса либо в коде своего сервиса. Есть такое сравнение —
пин словом; нет — пин символом. Признак читается по коду потребителя, а не по
важности значения.

**Довод у слова: обе стороны символьного пина уезжают вместе.** Символ мерит
**принадлежность перечню**, поэтому переименование значения правит и
производителя, и пин одной правкой — проба остаётся зелёной. Предикат
потребителя лежит литералом **в другом сервисе** и молча перестаёт совпадать:
счётчик встаёт на нуле, а ноль от «таких событий не было» в отчёте не
отличается ничем.

**Признак переоценивается правкой ЧУЖОГО сервиса, и это несущее следствие.**
Ветвящийся потребитель появляется и исчезает не у писателя: сегодня значение
пинится символом законно, а завтра сосед заводит по нему предикат — и та же
константа становится дефектом, хотя её никто не трогал. Поэтому обязанность
лежит на **вводящем предикат**: ход, заводящий у потребителя сравнение со
словом провода, тем же заходом переводит пин у писателя на слово. Прогона у
этой обязанности нет, и она названа остатком ниже.

**Обратная сторона — тоже правило, а не послабление.** Слово провода там, где
потребитель не ветвится, читается как клейм «по этому значению кто-то
ветвится»: следующий писатель прочтёт из блока то, чего нет, а предмет пробы
подменится — вместо принадлежности перечню она начнёт мерить несуществующий
стык.

**Стои́т пин у ПИСАТЕЛЯ формы.** Он тот, чья правка слово меняет. Охрана у
потребителя — другого класса: сверка литералов его запроса со значениями
перечней, прочитанными у построенного публикатора. **Проба формы у
потребителя журнала есть, но предмет у неё другой** — имена заголовков
конверта, а не литералы значений; сверки литералов сегодня нет ни у одного
потребителя.

**Остаток назван: признака не мерит ни один прогон.** Ветвящегося потребителя
ищут грепом по чужому сервису, и правило — вместе с обязанностью вводящего
предикат — держится дисциплиной пишущего. Кандидат охраны, её оживитель и
перечень слов, у которых обязанность сегодня не исполнена, —
`.claude/work/backlog.md` §«Слова провода, по которым ветвится потребитель, у
четырёх компонентов терминала не запинены».

*(Кейс: в одном блоке констант два одинаковых случая были решены двумя
способами без названного различия — жёсткая ступень пинилась словом, мягкая
тоже, хотя ветвящегося потребителя у мягкой нет; блок при этом сам объявлял
признак, которому не отвечал.)*

## Lombok

- `@Getter` / `@Setter` / `@NoArgsConstructor` / `@AllArgsConstructor`
  — для DTO / api / domain.
- `@Value` — для immutable.
- `@Builder` — где уместно.
- `@UtilityClass` — для классов-констант и статических хелперов;
  **живёт в пакете `util`** (`util.Constants`, `util.IndicatorMath`,
  `domain.util.DomainMath` и т. п.), не в доменных/сервисных пакетах.
  Требование механическое и держится в общих артефактах тоже: в
  библиотеке, чьё содержимое целиком доменное, `util` — последний сегмент
  пакета, а не отдельное дерево.
- `@Data` **не использовать** (особенно на доменных моделях).
- Lombok не скрывает бизнес-логику: сложные методы пишем явно.

## Новый модуль монорепозитория

- **Конфигурация Lombok — одна, в корне репозитория.** Новый модуль
  своей не заводит и наследует корневую. Причина не в удобстве: Lombok
  ищет конфигурацию вверх от файла-исходника, и модуль, заведённый вне
  области действия корневой, молча получает **умолчание капитализации** —
  у полей вида `kPeriod` меняются имена аксессоров, и ломается не он, а
  его потребитель. Дефект этого класса ловится только сборкой: имя
  аксессора не написано ни в одном файле, его производит процессор.
- **Библиотека на classpath — её `spring-boot-*` автоконфиг-модуль
  подтянут?** Boot 4 разнёс автоконфигурации по модулям
  (`spring-boot-starter-restclient`, `spring-boot-jackson2`,
  `spring-boot-starter-flyway`, `spring-boot-kafka`, …); без модуля бин или
  фича молча не активируется, и компиляция этого не ловит. Особо коварны
  автоконфиги без инжектируемого бина (Flyway): они не падают, а просто
  ничего не делают. Проверяется контекстным тестом модуля, а не чтением
  `pom.xml`.
- **Модуль включается в реактор корневого `pom.xml`.** Сборка «только
  этого дерева» через `-f <дерево>/pom.xml` разрешала бы его зависимости
  из локального репозитория, то есть проверяла бы предыдущую сборку;
  точечный прогон — `mvn -o -am -pl <модуль> test`.
- **Зависимость, добавленная в общий артефакт, становится обязательной
  для всех сервисов.** Поэтому в `services/common/**` её вводят по предъявленной
  потребности (компилятор не собрал без неё), а не превентивно, и
  называют причину рядом с объявлением.

## Константы

- Магические числа и строки → в константы (исключение —
  лог-сообщения).
- Дом констант — один класс `util.Constants` с множеством вложенных
  классов; константа кладётся во вложенный класс по теме (например:
  цена/точность, коды ошибок, имена полей запроса, заголовки).
- Локальные технические константы, осмысленные только внутри одного
  класса (индексы позиционного разбора, коэффициенты алгоритма),
  допустимо держать рядом с кодом — выносим «по необходимости», по
  теме.

## Форматирование

- Пустая строка после объявления класса.
- Импорты не схлопывать (без `*`).
- Аннотации пирамидкой: по длине строки, короткая сверху → длинная
  снизу.
- Статические методы — статический импорт, без имени класса, если
  нет конфликта. Применяется в том числе к утилитным предикатам:
  `Objects.isNull` / `nonNull`, `CollectionUtils.isEmpty` /
  `isNotEmpty`, `BooleanUtils.isFalse` / `isTrue`,
  `StringUtils.isBlank` / `isNotBlank` — импортируем статически и
  зовём без имени класса.
- Исключение — `Objects.equals`: статический импорт `equals`
  конфликтует с унаследованным `Object.equals`, поэтому вызываем с
  именем класса (`Objects.equals(a, b)`).

## Строгие правила

- Не объявлять несколько переменных через запятую.
- Фигурные скобки всегда: `if` / `else` / `for` / `while` / `do`.
- `Objects.equals(a, b)` вместо `a.equals(b)` — **когда получатель может
  быть пустым**. Запрет адресован null-небезопасности получателя, а не
  форме записи: `КОНСТАНТА.equals(x)` и `Enum.VALUE.equals(x)` пусты быть
  не могут по построению и **исключением не являются — они и есть
  безопасная форма**. Признак механический: слева литерал, константа,
  значение перечня **либо выражение, выведенное из них** (`Type.class`,
  `Enum.VALUE.name()`) — форма законна; слева переменная, поле или
  результат вызова **на них** — `Objects.equals`.

  **Клауза о выведенном выражении добавлена свипом дельты шага 10 фазы 2**
  и прежнюю редакцию признака заменяет. Та говорила «результат вызова —
  `Objects.equals`» без оговорки, и под неё попадало
  `Enum.VALUE.name().equals(x)` — конструкция, чей получатель пуст быть не
  может ровно по тому же построению, что и `Enum.VALUE`: признак расходился
  с предикатом, который сам же объявляет («получатель может быть пустым»).
  Что осталось дефектом, не изменилось: `переменная.getName().equals(x)` —
  результат вызова **на переменной**, и форма там `Objects.equals` (свип
  нашёл шесть таких точек в дельте шага, все правлены).
  *(Замер, на котором записано: из 123 вызовов `x.equals(…)` в `donor/src/main`
  122 несли слева константу и один — переменную. Буквальное чтение
  объявляло бы дефектом 122 верных места и прятало бы единственное
  настоящее.)*
- `CollectionUtils.isNotEmpty` / `isEmpty` вместо ручных проверок
  коллекций.
- Null-check только `Objects.isNull` / `Objects.nonNull`. Запрет
  `== null` / `!= null` **везде**: `if`, тернарники, присваивания,
  составные условия.
- Запрет прямых отрицаний (`!flag`, `!Objects.equals(...)`,
  `!"CONST".equals(...)`) → `BooleanUtils.isFalse` / `isTrue`.
- Стримы, результат которых может изменяться, собираем в изменяемую
  коллекцию: `.collect(Collectors.toList())`, не `.toList()`
  (последний возвращает неизменяемый список).
- В именах методов нет слова `New`: `save<Class>`, не
  `saveNew<Class>`. Касается всех методов.
- **Не использовать deprecated API** (классы/методы/константы) —
  подбирать актуальную замену (например,
  `HttpStatus.UNPROCESSABLE_CONTENT` вместо устаревшего
  `UNPROCESSABLE_ENTITY`,
  `ObjectMapper.setDefaultPropertyInclusion` вместо
  `setSerializationInclusion`). Проверка — компиляция с
  `-Dmaven.compiler.showDeprecation=true` без предупреждений в нашем
  коде.
- Метод вида `getRequiredById` / `getRequiredByInternalId`
  (вернуть сущность из репозитория или кинуть ошибку, если не
  найдена) располагается в соответствующем `DataService`, не в
  прикладном `Service`. Service при необходимости делегирует в
  `DataService`.
- В сервисах не заводим внутренние классы и рекорды — выносим
  отдельными типами.

## Контроллеры / API

- Swagger-аннотации + валидация.
- **Каждое поле api-модели — со Swagger-аннотацией с описанием
  назначения поля** (`@Schema(description = "...")`).
- API наружу отдаёт `internalId`, не `id` из БД (см. «Идентичность
  наружу»). Path-параметры — `internalId` (строка).
- `@RequestParam` — ок, но при более чем двух параметрах →
  `@ParameterObject`.
- API-пути: от общего к частному (слева → справа).

## Логирование

- Ошибки внешних API логируем с контекстом: endpoint, параметры
  (без секретов), `code` / `msg`.
- Секреты (`apiKey` / `secret` / `passphrase`) **никогда** не
  логируем.

## Доменные модель-классы

- Поясняющий javadoc — на класс и на **все** поля.
- Javadoc покрывает вложенные классы и **значения вложенных
  enum'ов** (каждая константа enum — со своим пояснением).

## Обработка ошибок

Полная error-политика — `docs/rules/error-handling-policy.md`.
Кратко для кода:

- **Внешняя поверхность — единый глобальный `@ControllerAdvice` + единый
  error-DTO** (не per-endpoint). FSM/оркестрация наружу не торчат.
- **Async-фасад ручного триггера джобы** отвечает только за запуск: чистый
  запуск → `202`; проблема при запуске (вкл. отказ блокировки «уже бежит»)
  → `409`. Исход работы джобы наружу не транслируется — уходит во
  внутреннюю градацию.
- **Внутренняя градация (4 уровня)** — лог / ретрай / холд инструмента /
  холд биржи (`docs/rules/error-handling-policy.md`,
  `docs/rules/instrument-hold.md`, `docs/rules/exchange-hold.md`,
  `docs/rules/runtime-error-classification.md`).
- Документирование ошибок на контроллере (`@ApiResponses`) — **по
  конвенции** (§«Контроллеры / API»), не отдельным правилом на эндпоинт.
- **Конкретный набор HTTP-кодов** и политика 409-vs-идемпотентности —
  **провизорны** (хвост пользователя); ретро-майоры шагов 2/4 (500 вместо
  422/409, невыровненные коды реджектов — `.claude/work/backlog.md`)
  закрываются в одном месте по этой политике.

## Тесты доменных моделей

- **Тест подменяет СОСТОЯНИЕ модели, а не её предикаты.** Собрать модель
  настоящими полями (налив, статус, состав заявок) и дать предикату
  посчитаться — единственная форма, при которой тест проверяет
  проверяемое. Подменённый предикат (анонимный подкласс с
  переопределённым `isCovered()`, мок доменной модели) проверяет
  исполнителя **против модели, которой в проде не существует**: правка
  самого предиката такой тест не роняет, и он молча перестаёт что-либо
  охранять.
- Мок допустим для **коллабораторов** (сервисы, репозитории, границы) —
  у них своя проверка; доменная модель мокается только там, где её
  конструирование стоило бы больше, чем даёт тест, и это называется в
  javadoc теста.

*(Кейс: тест детектора инварианта покрытия подменял `isRiskBearing()` и
`isCovered()`. Когда предикат детектора был исправлен — добавлена третья
конъюнкта, — тест этого не заметил: он спрашивал подменённые ответы, а не
модель.)*

## Наполнение

Итеративно, как `tech-radar`: возникла конвенция в коде — **владелец
дома решает и записывает**, решение уходит в
`.claude/work/decision-digest.md` пакетом на чтение с правом вето
постфактум. Владелец — `code-writer`: дом обслуживает его письмо, и
карта владельцев отдаёт ему детали уровня кода
(`.claude/processes/question-delegation.md`). Спекулятивных правил не
вносим — правило заводится на встреченный случай, не на воображаемый.

**Пробел конвенции держателя не требует, и маршрут через чат снят**
(решение держателя 2026-09-04). Он не меняет поведения кода, не
упирается ни в численную величину риск-аппетита, ни в продуктовый
scope — то есть не относится ни к одному классу, который режим автономии
оставляет держателю. Прежний маршрут был остатком доавтономного порядка
и держал находки фокуса `conventions` в очереди вместо закрытия.
