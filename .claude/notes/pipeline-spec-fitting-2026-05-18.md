# Примерка метамоделей пайплайна к форме spec-документа

**Дата:** 2026-05-18 (текущая системная дата: 2026-05-19; файл назван по дате,
указанной в задаче).
**Автор:** аналитический разбор (research-only, без правок продуктивных
файлов).

## Цель

Проверить гипотезу: у пайплайна (артефактов работы над проектом) есть
полноценное измерение со всеми пятью процессными слоями, в т.ч. L-SPEC.
Конкретно — проверить, ложится ли содержание пяти известных метамоделей
пайплайна в форму spec-документа (по стандартам ADR-0002, ADR-0006, ADR-0007
и шаблонам в `.claude/templates/documents/`).

Это **отчёт о примеримости**, не реализация. Файлов не перемещаю, каталогов
не создаю, реорганизации не предлагаю. Развилки фиксирую как открытые
вопросы.

Образец формата spec-документа — `docs/spec/models/core/AnomalyReport.md`
+ `docs/spec/lifecycle/AnomalyReport.md` (единственная пара полностью
оформленных документов на момент анализа), плюс шаблоны
`.claude/templates/documents/model.md`, `lifecycle.md`, `process.md`,
`invariant.md`, `reference.md`, `integration-mapping.md`.

## Метамодель 1. Q-N как сущность

### Собранное содержание

**Идентичность.**
- Стабильный `id` вида `Q-NNN`; не меняется при перемещении между разделами
  Open/Closed.

**Поля entry (11).**

| Поле | Тип | Изменяемость | Комментарий |
|---|---|---|---|
| `id` | `Q-NNN` | стабильный | identity entry |
| `title` | строка | редактируем | без потери истории |
| `formulation` | текст | редактируем | буквальная формулировка |
| `source` | текст | редактируем | legacy-файл/обсуждение/работа |
| `added` | дата | фиксированная | дата заведения |
| `status` | enum {Added, Resolved} | меняется ОДИН раз | переход терминален |
| `classification` | enum (10 значений) | меняется (reclassification), история в `notes` | при добавлении ≠ `null`, при закрытии ≠ `unclassified` |
| `context` | 1–3 абзаца | редактируем | контекст вокруг вопроса |
| `related` | список Q-N | редактируем | кросс-связи |
| `notes` | список датированных записей | **append-only** | старые не редактируются |
| `resolution` | текст | заполняется ОДИН раз | при переходе в Resolved |

**Статусы и переход.**
- `Added` — активное состояние.
- `Resolved` — финальное; перемещает entry из раздела «Open» в «Closed».
- Один переход Added → Resolved, обратного нет.
- Сигнал «вопрос в активном разборе» — датированная запись в `notes`, не
  отдельный статус.

**Классификация (10 значений).**
- Содержательные (9): `concept`, `missing-model`, `missing-process`,
  `missing-invariant`, `contradiction`, `structural`, `legacy-bug`,
  `obsolete-by-decision`, `obsolete-by-context`.
- Служебная (1): `unclassified` — временная, при добавлении.
- Семейство `missing-*` — общий паттерн «имя есть, описания нет», закрывается
  автоматически при создании целевого spec-документа.

**Правила перехода в Resolved.**
- `classification` ≠ `unclassified`.
- `resolution` заполнено.
- Перемещение entry из «Open» в «Closed».
- Связные обновления (backlog, inline-ссылки в spec через Knowledge Curator).

**Условия устаревания (3).**
- Условие 1 (содержательное решение зафиксировано) → `obsolete-by-decision`.
- Условие 2 (контекст исчез) → `obsolete-by-context`.
- Условие 3 (некорректная формулировка) → `legacy-bug`.

**Связи с другими артефактами.**
- С backlog — задача на разбор группы Q-N (со ссылкой на Q-N).
- С spec-документами — inline-ссылка «см. Q-NNN».
- С Knowledge Curator — авто-завод backlog-задач при закрытии Q-N с
  висящими ссылками.
- С `spec-document-migration` — связное закрытие `missing-*` при создании
  целевого документа.

### Попытка переложения в spec-форму

Q-N разворачивается на пару model + lifecycle, по аналогии с
AnomalyReport.

**Model-документ `Q-N (open question)`:**

- Frontmatter (`status: current`, `last_review`, `related_adrs:
  [ADR-0008]`) — применим без натяжки.
- Раздел «Поля» — таблица 11 полей entry. Прямой аналог таблицы полей
  AnomalyReport.
- Раздел «Статусы» — enum `{Added, Resolved}` с семантикой.
- Раздел «Значения classification» — таблица 10 значений с семантикой
  (как «Значения Severity» в AnomalyReport).
- Раздел «Инварианты структуры»:
  - `id` стабилен.
  - `notes` append-only.
  - `resolution` non-null ⇔ `status = Resolved`.
  - При `status = Resolved` → `classification ≠ unclassified`.
  - При reclassification — датированная запись в `notes`.
- Раздел «Связи» — backlog-задачи, inline-ссылки в spec, Knowledge Curator.

**Lifecycle-документ `Q-N — жизненный цикл`:**

- Раздел «Жизненный цикл» — линейная цепочка Added → Resolved (с веткой
  «зайти сразу в Resolved» для `obsolete-by-decision`, по аналогии с
  записью «зайти сразу в Resolved» в skill).
- Раздел «Статусы и переходы» — таблица перехода с условиями (как у
  AnomalyReport).
- Раздел «Кто триггерит переходы» — пользователь (через скилл
  `open-questions-workflow`), миграционный поток (через
  `spec-document-migration` для `missing-*`), Knowledge Curator (связные
  обновления).
- Раздел «Инварианты поведения»:
  - id не меняется при перемещении.
  - notes append-only.
  - Перемещение Open → Closed синхронно с переходом status.
- Раздел «Доменные запреты» — обратный переход Resolved → Added запрещён.
- Раздел «Обработка сбоев» — практически пуст (нет понятия сбоя у entry).

### Что лезет и что не лезет

**Лезет без натяжки:**
- Frontmatter.
- Таблица полей.
- Таблица значений enum (status, classification).
- Инварианты структуры.
- Связи.
- Жизненный цикл, переходы, кто триггерит, инварианты поведения.

**Пустое/искусственное:**
- «Обработка сбоев» в lifecycle — содержания нет.
- «Персистентность» в model (опциональный раздел) — entry хранится в
  markdown-файле, маппинг тривиален; раздел просто отсутствует.

**Не помещается в текущий шаблон:**
- **Условия устаревания (3).** В текущем lifecycle-шаблоне условие
  перехода — поле колонки таблицы. Здесь же условия многоуровневые
  («одно из трёх + сопоставимое classification + явное обоснование»). По
  букве шаблона лезет, но «расплющивается» — теряется блочный характер.
  Решение: добавить раздел «Условия терминального перехода» (по аналогии
  с «Доменные запреты переходов»).
- **Семантика семейства `missing-*` как паттерна.** Это не про значение
  enum, это про связь classification ↔ ответный артефакт (создание
  целевого spec-документа закрывает Q-N). В текущем model/lifecycle
  шаблоне такому смыслу нет раздела; ближайшее место — «Связи». Часть
  содержания естественнее живёт в process-документе («Процесс закрытия
  Q-N при создании целевого spec-документа») — а это уже отдельный
  жанр.

### Дополнительные жанры

- Process-документ `Закрытие Q-N missing-* при создании целевого
  документа`: триггер — создание model/process/invariant документа в
  `docs/spec/`, шаги, эффекты. Это нормальный process-жанр.
- Process-документ `Связное обновление spec и backlog при закрытии Q-N`
  (Knowledge Curator).

Оба — нормальные process-документы PIPELINE; ничего нового изобретать
не нужно.

## Метамодель 2. MIGRATED-маркер

### Собранное содержание

**Что это.** Однострочная пометка на первой строке legacy-файла:

```markdown
> **[MIGRATED → <путь1>, <путь2>, ...]** — этот документ больше не источник правды.
```

**Правила постановки.**
- Ставится **на первую строку** legacy-документа.
- Условие постановки: **все** упоминания в legacy разнесены (содержательные
  — в целевые spec-документы, без описания — в Q-N в журнале).
- В маркере перечисляются **все** целевые документы.
- Сам legacy-файл не удаляется — остаётся с маркером.

**Особые случаи.**
- **Открытые Q-N не блокируют маркер.** Q-N относится к сущности, не к
  legacy-документу. Маркер ставится, когда legacy-документ свою задачу
  выполнил.
- **Shared-файлы.** Если фрагменты файла распределены по разным сессиям
  миграции — маркер ставится только когда **все** фрагменты разнесены;
  до этого статус в трекере `in-progress`, целевые документы
  накапливаются в трекере.
- **Парный «migrated-from»-маркер в целевом документе запрещён.** Связь
  только односторонняя.

**Дополнительно (из ADR-0002 §5).** Тот же формат был зафиксирован раньше
как «маркер миграции» в стандарте spec-документа.

### Попытка переложения в spec-форму

**Через model.** Не работает.
- Identity отсутствует (маркер — это строка в файле, не самостоятельный
  объект с идентификатором).
- Полей нет: одна строка с двумя «слотами» (список путей + фиксированный
  суффикс).
- Жизненного цикла нет: маркер либо есть, либо нет; других состояний
  нет, переходов нет.

**Через lifecycle.** Не работает по той же причине.

**Через invariant.**
- Можно сформулировать как «инвариант legacy-документа после полной
  миграции»: «У всякого legacy-файла, чьё содержание полностью
  разнесено, первая строка содержит MIGRATED-маркер канонического
  формата, перечисляющий все целевые spec-документы». Это утверждение
  ложится в шаблон invariant как одна формулировка.
- Минус: invariant в текущей трактовке (ADR-0006 принцип 2) — это
  правило, **пересекающее** несколько доменных моделей или процессов.
  Здесь субъект — артефакт документации, а не доменная модель. По форме
  лезет, по содержанию — за пределами текущего скоупа invariant.

**Через reference.**
- «Справочник формата маркеров миграции» — близко. Шаблон reference
  допускает свободную форму. Разделы: формат, правила постановки,
  особые случаи, обратные ссылки.
- Минус: reference в текущей трактовке — стабильный архитектурный
  паттерн / справочник, общий для нескольких документов. Технически
  подходит, но содержание узкое (один маркер) — reference тут начинает
  выглядеть как «format-spec», не reference.

**Через process.**
- Можно описать «Постановка MIGRATED-маркера» как процедуру: триггер,
  шаги, обработка особых случаев. Шаблон process применим.
- Но это уже не **сам маркер**, а **процедура работы с ним**. Метамодель
  маркера (формат + правила) — отдельная вещь от метамодели процедуры
  его постановки.

### Что лезет и что не лезет

**Лезет без натяжки:**
- Описание формата строки можно дать в любом из жанров inline-кодом.
- Процедура постановки и особые случаи помещаются в process-документ.

**Пустое/искусственное:**
- Поля, статусы, переходы, инварианты структуры, связи — у самого маркера
  ничего нет.

**Не помещается:**
- **Сам маркер как самостоятельная единица описания.** Это не модель, не
  процесс, не invariant в смысле ADR-0006, не reference в типовом
  понимании. Это **формат-строка с правилами постановки** — отдельный
  жанр.

### Дополнительные жанры

Кандидат на новый жанр L-SPEC PIPELINE:

- **`format`** (или `syntax`, или `marker`) — спецификация
  однострочного/коротко-форматного артефакта. Разделы: каноническая
  форма (синтаксис), грамматика слотов, правила постановки, особые
  случаи, обратные ссылки.

Альтернатива без нового жанра: распределить содержание между invariant
(«правило существования маркера») и process («процедура постановки»).
Минус — потеря целостности описания: «где живёт формат?» не имеет
канонического места.

## Метамодель 3. Spec-документ-заглушка

### Собранное содержание

**Что это.** Документ в `docs/spec/`, у которого заполнено только то, что
было в исходном legacy (хотя бы определение и связи), остальные разделы
шаблона — помечены «описание появится при миграции содержательного
источника» или удалены. Заглушка — **валидное** промежуточное состояние,
не «ошибка».

**Три состояния документа (по
`spec-document-migration/SKILL.md`).**
- **«Заглушка с обвязкой»** — заполнено определение и связи; нет
  структурных полей. Сопровождается открытым Q-N `missing-<тип>`.
- **«Заполнен по существу, не по всему шаблону»** — норма, Q-N нет.
- **«Полностью заполнен»** — идеал.

**Правила.**
- Документ-заглушка регистрируется в `docs/spec/MODELS.md` сразу
  (для model-документов).
- Ссылки на заглушку — обычные markdown-ссылки (заглушка существует как
  файл).
- Markdown-ссылки на ещё не созданные документы — запрещены (для
  отсутствующих — Q-N + прозаическое упоминание).
- Q-N резолвится по конкретному содержательному пробелу, не по полноте
  документа в целом.

### Попытка переложения в spec-форму

**Это не самостоятельная сущность.** «Заглушка» — это **значение поля
«состояние»** у метамодели 4 (Spec-документ как артефакт). Аналог:
`Order.Status` — не отдельная модель, а enum у Order.

**Если всё же попробовать как самостоятельный spec-документ.**
- Model — пустой почти весь шаблон: identity нет, полей нет, инварианты
  структуры пусты, связи описываются через ссылку на «Spec-документ» как
  родительский артефакт.
- Lifecycle — три состояния можно описать как enum {stub, substantive,
  complete}, переходы — через «миграция доносит содержание». Но subject
  перехода — не «заглушка», а «документ»; «заглушка» меняет своё
  значение, потому что меняется значение поля у документа-родителя.

Получается рекурсивная зависимость: чтобы говорить о «заглушке», нужно
говорить о «документе». Это аргумент за тем, чтобы заглушка была
**разделом** в спецификации метамодели 4, а не отдельным spec-документом.

### Что лезет и что не лезет

**Лезет:**
- Описание трёх состояний — как enum в model-документе родительского
  артефакта (Spec-документ).
- Переходы между состояниями — как раздел в lifecycle-документе
  родительского артефакта.

**Не помещается как отдельный документ:**
- В отдельном model — нет identity, нет полей.
- В отдельном lifecycle — нет subject'а в смысле «модель, у которой есть
  жизненный цикл».

### Дополнительные жанры

Жанра не нужно — метамодель не самостоятельна. **Это раздел внутри
метамодели «Spec-документ как артефакт»** (см. ниже §«Состояния
наполненности» в раскладке для метамодели 4).

## Метамодель 4. Spec-документ как артефакт

### Собранное содержание

**Frontmatter (поля).**
- `status` — enum {`draft`, `wip`, `current`, `deprecated`}.
- `last_review` — дата.
- `related_adrs` — список ID ADR.
- `related_models` — опционально, список имён моделей.
- `related_processes` — опционально, список имён процессов.

**Жанры (6, ADR-0002 §1, ADR-0007 §1, §2).**
- `model` (с подкаталогами `core/` и `runtime/`).
- `lifecycle`.
- `process`.
- `integration-mapping` (с подкаталогами `models/` и `mapping/` под биржей).
- `reference`.
- `invariant`.

Каждый жанр имеет собственный шаблон в
`.claude/templates/documents/<genre>.md`.

**Структурные правила (ADR-0002 §2, §3).**
- Один факт — одно место (атомарность).
- Документ = карта текущего состояния (без addenda).
- Жанровая чистота (один документ — один жанр).
- Контракт, не реализация (нет Java-сниппетов, нет SQL DDL).
- Открытые вопросы — в `.claude/questions/`, не внутри документа. В
  spec — только inline-ссылка «см. Q-NNN».

**Имена файлов (ADR-0002 §5).**
- PascalCase для документов, описывающих один класс
  (`Order.md`).
- kebab-case иначе (`exception-policy.md`).
- Без пробелов, без кириллицы.
- Без нумерации в заголовках и именах.

**Стиль и навигация (ADR-0002 §5).**
- Кросс-ссылки — markdown-link с относительным путём.
- Inline-code для ссылок запрещён.
- Mermaid inline; длинные примеры — в `references/`.

**Технические запреты (ADR-0002 §6).**
- Java-сниппеты — запрещены.
- SQL DDL — запрещены.
- Длинные справочники в теле — запрещены.
- Размер документа — мягкий cap 1000 строк.

**Расположение (ADR-0007 §4).**
- `docs/spec/` + подкаталоги по жанрам.
- `docs/spec/MODELS.md` — навигационное исключение.

**Контроль (ADR-0002 §7).**
- Уровень 1: шаблон.
- Уровень 2: скилл `spec-document-workflow`.
- Уровень 3: ревью человека (Сценарий 7 в playbook).

### Попытка переложения в spec-форму

Естественный разворот: model + lifecycle. По аналогии с AnomalyReport.

**Model-документ `Spec-документ`:**

- Frontmatter (`related_adrs: [ADR-0002, ADR-0006, ADR-0007]`).
- Раздел «Поля» — таблица полей frontmatter (status, last_review,
  related_adrs, related_models, related_processes) + path/имя + жанр.
- Раздел «Статусы» — enum значений `status` (draft/wip/current/deprecated).
- Раздел «Состояния наполненности (вне frontmatter)** — три состояния из
  метамодели 3 (заглушка с обвязкой, по существу, полностью заполнен).
  Это «второе измерение состояния» документа.
- Раздел «Жанры» — таблица 6 жанров с их назначением и каталогом.
  Аналог «полиморфных подтипов» в spec.
- Раздел «Инварианты структуры»:
  - Атомарность.
  - Жанровая чистота.
  - Нет Java/SQL/addenda/встроенных open-questions.
  - Markdown-ссылки только на существующие документы.
  - Размер ≤ 1000 строк (мягкий cap).
- Раздел «Связи»:
  - С ADR (через `related_adrs`).
  - С MODELS.md (для model-документов).
  - С шаблонами в `.claude/templates/documents/`.
  - С Q-N (через inline-ссылки).
  - С backlog (через сигналы превышения cap).

**Lifecycle-документ `Spec-документ — жизненный цикл`:**

- Цепочка draft → wip → current → deprecated.
- Параллельная цепочка по полноте: stub → substantive → complete
  (свободная, не привязанная к статусу).
- Кто триггерит: автор/Claude (создание, наполнение), значимая правка
  (обновление last_review), новое ADR/несоответствие
  стандарту (status-переходы).
- Инварианты поведения:
  - Frontmatter всегда заполнен.
  - last_review обновляется только при значимой правке.
  - При закрытии Q-N — связные обновления (через Knowledge Curator).

### Что лезет и что не лезет

**Лезет без натяжки:**
- Frontmatter (его поля → поля spec-документа артефакта-документа: самореференция работает).
- Таблица полей.
- Enum status.
- Жанры как enum.
- Инварианты структуры.
- Связи.
- Lifecycle с переходами.

**Пустое/искусственное:**
- «Обработка сбоев» в lifecycle — нет понятия сбоя у документа.
- «Персистентность» — markdown-файл, тривиально.

**Не помещается в текущий шаблон:**
- **Правила имён файлов и расположения.** В текущем model-шаблоне нет
  раздела «синтаксис имени» или «правила расположения». Это естественно:
  у доменной модели имя класса задаёт код, у документа имя задают
  правила оформления. Ближайшее место — «Инварианты структуры», но это
  про **содержание**, а не про **именование артефакта**.
- **Стилевые правила (markdown-ссылки, заголовки без нумерации,
  inline-code запрещён).** Это **convention**, не свойства модели.
  Сейчас они зафиксированы в ADR-0002 как часть «стандарта», а должны
  жить либо в `docs/conventions/` (как convention о написании
  документов), либо в новом разделе «Правила оформления» внутри
  model-документа Spec-документа.
- **Контроль соблюдения стандарта (3 уровня).** Это **процесс**, не
  свойство документа. Может разойтись на несколько артефактов: шаблон
  (как формат), скилл (как процедура), playbook-сценарий (как
  пользовательская процедура). Все три уже существуют — но их связка как
  единая «трёхуровневая страховка» — это метарегистр, который сам по
  себе не лезет в model.
- **Подтипы (6 жанров) с разными шаблонами.** Это полиморфизм, как у
  Order/AlgoOrder/Position или у полиморфного DTO в integration. По
  ADR-0006 принцип 1 — это «один бизнес-объект (Spec-документ) с
  разделами для каждого подтипа». Лезет, но раздувает документ. Альтернатива
  — отдельный model-документ на каждый жанр (модель документа жанра
  model, модель документа жанра lifecycle и т.д.). Это уже шесть
  spec-документов вместо одного.

### Дополнительные жанры

- **`convention`** — правила оформления (стиль, markdown-ссылки, имена
  файлов). Уже существует как `docs/conventions/` для продуктовых
  правил; для пайплайна — соответствующий аналог. Не требует нового
  жанра spec, требует разнесения содержания.
- Полиморфизм 6 жанров — внутри одного model-документа разделами; либо
  6 model-документов (по аналогии с расщеплением `Order` / `AlgoOrder` /
  `Position`).

## Метамодель 5. ADR как артефакт

### Собранное содержание

**Структура (по `adr.md` и `.claude/adr/README.md`).**
- Заголовок: `ADR-XXXX: <название>`.
- Метаданные: Дата, Статус.
- Разделы: Контекст, Решение, Альтернативы, Последствия, Связи,
  Заметки (опционально).
- Frontmatter в текущем шаблоне **отсутствует** — структура задаётся
  заголовками markdown.

**Статусы (4).**
- `Proposed` — обсуждается.
- `Accepted` — принято, действует.
- `Superseded by ADR-NNNN` — заменено другим ADR.
- `Deprecated` — больше не действует, замены нет.

**Принципы.**
- Append-only: содержание не редактируется задним числом.
- Одно решение — один ADR.
- С альтернативами обязательно (иначе это не ADR).
- С последствиями обязательно.

**Допустимые/недопустимые правки.**
- Запрещено: правка Decision, Context, Alternatives, Consequences по
  существу; обновление путей в технических ссылках.
- Разрешено: смена Status, исправление опечаток, физическое перемещение
  файла, добавление примечаний в фиксированный блок.

**Два типа примечаний.**
- **Технические** — разрешены в любом статусе. Назначение —
  навигационные/ссылочные пометки. Append-only, датированы.
- **Содержательные** — разрешены ТОЛЬКО в Superseded и Deprecated.
  Назначение — ретроспективные комментарии. Append-only, датированы. Не
  отменяют решение.

**Связи (поле Связи в шаблоне).**
- Supersedes ADR-NNNN.
- Superseded by ADR-MMMM.
- Related ADR-XXX.
- Driven by — обсуждение/требование.

**Имена файлов.**
- `NNNN-имя.md` (с нумерацией) — исключение из правила «без нумерации»
  для spec.

**Расположение.**
- `.claude/adr/`.

### Попытка переложения в spec-форму

Естественный разворот: model + lifecycle.

**Model-документ `ADR`:**

- Frontmatter (`related_adrs: []` — ADR об ADR; интересный случай
  самореференции; на практике пусто).
- Раздел «Поля»:

| Имя | Тип | Обязательно | Описание |
|---|---|---|---|
| `number` | `NNNN` | да | стабильный номер, входит в имя файла |
| `title` | строка | да | короткое название решения |
| `date` | дата | да | дата принятия |
| `status` | enum (4) | да | см. раздел «Статусы» |
| `context` | текст | да | ситуация |
| `decision` | текст | да | принятое решение |
| `alternatives` | список | да, ≥1 | отвергнутые варианты с обоснованием |
| `consequences` | список | да | что меняется |
| `links` | подмодель | опц. | Supersedes / Superseded by / Related / Driven by |
| `technical_notes` | список датированных записей | append-only | разрешены в любом статусе |
| `contentful_notes` | список датированных записей | append-only, ТОЛЬКО в Superseded/Deprecated | ретроспективные комментарии |

- Раздел «Статусы» — enum 4 значения с семантикой.
- Раздел «Подмодели»:
  - `Link` (вложенная) — поля {kind: enum {Supersedes, SupersededBy,
    Related, DrivenBy}, target: ADR-NNNN | url}.
  - `Note` (вложенная) — поля {kind: enum {Technical, Contentful}, date,
    text}.
- Раздел «Инварианты структуры»:
  - `alternatives` непуст.
  - `decision`, `context`, `consequences` непусты.
  - Append-only на всё тело, кроме `status` и блока заметок.
  - `contentful_notes` непуст ⇒ `status ∈ {Superseded, Deprecated}`.
- Раздел «Связи»:
  - С другими ADR через `links`.
  - С затронутыми документами через `consequences` (списком путей).

**Lifecycle-документ `ADR — жизненный цикл`:**

- Цепочка: Proposed → Accepted → Superseded by N | Deprecated.
- Кто триггерит:
  - Автор (создаёт Proposed).
  - Решение по итогам обсуждения (Proposed → Accepted).
  - Принятие ADR-N, заменяющего этот (Accepted → Superseded by N).
  - Утрата актуальности без замены (Accepted → Deprecated).
- Инварианты поведения:
  - Append-only на содержательные разделы после Accepted.
  - Технические примечания — в любом статусе.
  - Содержательные примечания — только в Superseded/Deprecated.
  - Файл не удаляется; статус Superseded не удаляет старый ADR.
- Обработка сбоев — пуста.

### Что лезет и что не лезет

**Лезет без натяжки:**
- Поля.
- Статусы (enum).
- Инварианты структуры (append-only, обязательность разделов).
- Связи (через подмодель `Link`).
- Lifecycle с переходами.
- Подмодель `Note` с дискриминатором (Technical/Contentful) — аналогично
  полиморфным семействам в integration mapping.

**Пустое/искусственное:**
- «Обработка сбоев» — нет.
- «Персистентность» — нет.

**Не помещается в текущий шаблон:**
- **Append-only как принцип на уровне всего документа.** Это не
  «инвариант структуры» (структура полей) и не «инвариант поведения»
  (FSM модели) — это **policy** редактирования артефакта. Ближе к
  convention о работе с артефактом, чем к свойству самой модели.
  Текущий шаблон lifecycle принимает append-only как инвариант
  поведения, но это натяжка.
- **«Что считается редактированием / что не считается».** Это
  операционные правила, ближе к скиллу, чем к spec-документу.
- **Битые ссылки после переезда — не обновляются.** Это правило работы с
  артефактом, не свойство артефакта. Снова convention/skill.
- **Когда создавать ADR vs CLAUDE.md vs convention.** Это решение о
  размещении знания, не часть метамодели ADR. Скорее всего, должно
  жить в `working-with-claude.md` или отдельном процессе.

### Дополнительные жанры

- **Process-документ `Принятие ADR`** — триггер, шаги (от Proposed до
  Accepted), связные обновления (индекс в README.md, ссылки в
  CLAUDE.md). Это стандартный process-жанр.
- **Convention** — правила редактирования (append-only, битые ссылки не
  правятся). См. метамодель 4 — общий convention о работе с
  документацией пайплайна.

## Сводный анализ

### Сколько ложится в текущий формат spec-документа

| Метамодель | model | lifecycle | Дополнительно | Итог |
|---|---|---|---|---|
| 1. Q-N как сущность | ✅ | ✅ | + process для связного закрытия | **ложится** |
| 2. MIGRATED-маркер | ❌ | ❌ | требует жанра format/syntax или разнесения по invariant+process | **не ложится** в текущие жанры; нужен новый или гибридное решение |
| 3. Spec-документ-заглушка | — | — | это раздел метамодели 4, не самостоятельный документ | **не самостоятельная единица** |
| 4. Spec-документ как артефакт | ⚠️ | ⚠️ | стиль, имена и контроль уходят в convention/skill | **ложится с оговорками**: часть содержания не помещается, требует разнесения |
| 5. ADR как артефакт | ✅ | ⚠️ | append-only-policy не лезет как инвариант, уходит в convention/skill | **ложится с оговорками** |

**В сухом остатке:**

- **2 из 5** ложатся чисто в model + lifecycle (Q-N, ADR — последний с
  одной оговоркой про append-only-policy).
- **1 из 5** ложится с серьёзными оговорками (Spec-документ): половина
  содержания (стилевые правила, имена файлов, контроль) уходит за
  пределы spec-формата.
- **1 из 5** не ложится вообще (MIGRATED-маркер): требует нового жанра
  либо разнесения.
- **1 из 5** оказывается не самостоятельной метамоделью (заглушка): это
  раздел внутри метамодели «Spec-документ».

### Альтернативные жанры PIPELINE-spec

По итогам примерки вырисовываются такие жанры (если идти по
гипотезе L-SPEC PIPELINE):

- **model** — структура артефакта (как у Q-N, ADR, Spec-документа). По
  аналогии с PRODUCT model. **3 метамодели** (1, 4, 5).
- **lifecycle** — жизненный цикл артефакта. **3 метамодели** (1, 4, 5).
- **process** — операции над артефактами (закрытие Q-N, миграция,
  принятие ADR, связные обновления). Часть содержания каждой
  метамодели уходит сюда.
- **format / syntax / marker** — спецификация короткоформатного
  артефакта (MIGRATED-маркер). **1 метамодель** (2). Нового жанра в
  PRODUCT spec нет; для PIPELINE — обоснованный кандидат.
- **convention (вне spec)** — правила оформления, имена, стиль,
  append-only-policy. **Куски из метамоделей 4 и 5.** Это **не** жанр
  L-SPEC, это convention-слой пайплайна (по аналогии с
  `docs/conventions/` в PRODUCT).

### Метамодели, не ложащиеся ни в один жанр (даже расширенный)

Чистых «нелезущих» нет, но есть **частичное нелезание**:

- Кусок «контроль соблюдения стандарта» (метамодель 4, ADR-0002 §7) —
  это **метарегистр** трёх уровней контроля. Не модель, не процесс, не
  invariant. Может стать reference, но это натяжка.
- Кусок «append-only как policy на артефакт» (метамодели 4 и 5) — это
  правило редактирования. Естественнее жить в convention/skill, чем в
  spec.
- Кусок «когда создавать ADR / когда convention / когда CLAUDE.md» — это
  правило размещения знания. Естественнее жить в
  `working-with-claude.md`.

Эти куски — **общая convention пайплайна**, не L-SPEC. Они выходят
из L-SPEC естественно, как стиль и tech-radar выходят из PRODUCT-spec.

### Возможная шестая метамодель

В ходе разбора всплыли ещё кандидаты, **не упомянутые** в исходной пятёрке,
но имеющие ту же природу:

- **Backlog как артефакт** — список задач со статусами, разделами «Open»
  и «Закрытые», правилами связности с Q-N. Полная аналогия с Q-N: model
  + lifecycle.
- **Migration-tracker как артефакт** — записи legacy-документов со
  статусами (planned / in-progress / done), кластерами, фазами.
  Model + lifecycle.
- **MODELS.md как артефакт** — реестр имён моделей с состояниями entry
  (stub / linked). Model + lifecycle (близко к метамодели 3 как разделу
  внутри метамодели 4 — отношения «реестр vs документ»).
- **Skill как артефакт** — описание процедуры с фронтматтером
  (name, description), разделами, правилами активации. Model.

Все четыре кандидата идут по тому же паттерну, что Q-N и ADR (model +
lifecycle). Это **усиливает** гипотезу о наличии L-SPEC PIPELINE с
ядром «модель артефакта + lifecycle артефакта», но **не меняет** вывод:
жанровая палитра шире 6 жанров PRODUCT-spec (нужен format/marker и
явная convention-сторона).

## Вердикт по гипотезе

**Промежуточная позиция: гипотеза требует пересмотра.**

Не полное подтверждение и не полный отказ. Конкретно:

**Что подтверждается.**

- Ядро метамоделей пайплайна (Q-N, ADR, Spec-документ; а также внешние
  кандидаты — backlog, migration-tracker, MODELS.md, skill) **естественно
  раскладывается** на пару model + lifecycle, как продуктовые модели.
- Шаблоны `model.md` и `lifecycle.md` применимы почти без правок:
  поля, статусы, переходы, инварианты, связи — всё на месте.
- Принципы ADR-0006 (атомарность, локальные vs кросс-модельные
  инварианты, расщепление model/lifecycle) на этом материале работают.

**Что требует пересмотра.**

- **Не каждая «метамодель» — самостоятельный spec-документ.**
  Spec-документ-заглушка — раздел внутри метамодели Spec-документа, а не
  отдельный артефакт. Слепая фиксация «5 метамоделей = 5 spec-документов»
  даст перегруженный реестр и расщеплённое описание.
- **Жанровая палитра шире 6 жанров PRODUCT-spec.** MIGRATED-маркер не
  лезет ни в один из текущих жанров. Кандидат на новый жанр —
  `format` / `marker` / `syntax`. Без него — гибридное разнесение по
  invariant + process с потерей целостности описания.
- **Стиль / имена / append-only-policy / контроль — не L-SPEC, а
  convention пайплайна.** Их попытка сидеть в L-SPEC растягивает
  стандарт документа за пределы «контракт, не реализация» (ADR-0002).
  Пайплайн нуждается **в собственном convention-слое** (аналог
  `docs/conventions/` для PRODUCT), не только в L-SPEC.

**Что НЕ подтверждается.**

- Утверждение «у PIPELINE есть полноценный L-SPEC, и метамодели чисто
  ложатся в форму spec-документа» — слишком сильное. Чисто ложатся **не
  все**, а часть содержания **выходит** за рамки spec в convention-
  слой и (опционально) в новый жанр.

**Итого: PIPELINE действительно получает L-SPEC, но:**

1. Не как линейный набор «5 метамоделей = 5 spec-документов» —
   состав документов другой (несамостоятельные метамодели уходят
   разделами; некоторые дополнительные метамодели всплывают
   попутно).
2. С расширенной жанровой палитрой (как минимум 6 жанров PRODUCT +
   `format/marker` для коротких форматов).
3. **Параллельно** с явным convention-слоем пайплайна, куда
   уходят правила оформления, имена, стили, append-only-policy,
   контроль.

Без convention-слоя гипотеза вырождается в раздувание L-SPEC до
«стандарта работы в проекте», что размывает границу «контракт, не
реализация» в самом spec.

- **OQ-PIPE-4.** Метамодель `Spec-документ` имеет 6 жанров с разными
  шаблонами — это один model-документ с разделами по подтипам или 6
  отдельных model-документов? Аналог в PRODUCT — полиморфные семейства
  (один документ по ADR-0002 §6: «один документ на семейство»). Прямое
  применение даёт раздутый документ.
- **OQ-PIPE-5.** Шестая (и далее) метамодель — backlog, migration-tracker,
  MODELS.md, skill — это часть L-SPEC PIPELINE или отдельные сущности
  процесс-слоя? Все идут по паттерну model + lifecycle. Прежде чем
  расширять состав, нужен критерий, что вообще входит в L-SPEC PIPELINE.
- **OQ-PIPE-6.** Жанр lifecycle для метамоделей-артефактов — даёт ли он
  ценность за пределами «нарисовать FSM по статусам»? У AnomalyReport
  lifecycle несёт «кто триггерит» и «обработка сбоев», что
  содержательно. У ADR / Q-N — раздел «обработка сбоев» пуст,
  «кто триггерит» — короткий список. Возможно, lifecycle для
  PIPELINE-артефактов схлопывается в раздел внутри model.
- **OQ-PIPE-7.** Отношение L-SPEC PIPELINE к существующим артефактам:
  ADR (`.claude/adr/`), skill (`.claude/skills/`), playbook (`.claude/flow/`).
  Эти артефакты сейчас **сами являются** объектами, которые L-SPEC
  PIPELINE должен был бы описывать. Возникает самореферентность:
  ADR-NNNN об ADR-артефакте; skill `spec-document-workflow` об
  spec-документе. Это работающая, но непривычная структура — её
  следует осмыслить отдельно.
