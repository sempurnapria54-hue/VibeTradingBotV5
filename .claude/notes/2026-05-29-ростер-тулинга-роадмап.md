# Ростер тулинга для шага роадмапа

## На какой вопрос отвечает этот файл

Какой состав тулинга нужен для исполнения шага роадмапа, в каком
порядке артефакты материализуются и как устроен каждый.

## Контекст

Тулинг роадмапа спроектирован в чате 2026-05-29 в начале
исполнения шага 1 Фазы 1. Заметка фиксирует состав целиком, чтобы
решения не потерялись.

**Подход (а), переписан (2026-05-30).** Состав фиксируется сейчас
целиком; файлы артефактов создаются **стабами сразу** и
наполняются по ходу. Стаб = раздел «На какой вопрос отвечает этот
файл» + назначение и границы + известный скелет (вход/выход,
принцип) + явная пометка «процедура/наполнение дорабатывается по
ходу, форма снимается с первого реального использования».
Спекулятивную процедуру в стаб не пишем.

Не стабим сейчас (наполнять нечем):

- **тестовые артефакты шага 10** (`testing-strategy`, `test-writer`,
  `test-review`) — наполнять нечем до шага 10.

Привязка к процессу — `.claude/processes/roadmap-step-execution.md`
(под-шаги `TOOLING` → `DOCS_CHECK_N` → `GAPS_CLOSE_N` → `CODE` →
`SYNC_DOCS_FROM_CODE` → `DONE`).

## Код (под-шаг `CODE`)

### `tech-radar` — правило. Стаб.

**Стаб.** `.claude/rules/tech-radar.md` (2026-05-30).

**На какой вопрос отвечает:** «Что используем при написании кода?»
Стэк (Java 21, Spring Boot 3, PostgreSQL — расширяется) + библиотеки
/ техники со статусом по модели tech radar (`adopt` / `trial` /
`assess` / `hold`). Наполняется итеративно через чат, форма с первых
записей. Детали — в стабе.

### `codestyle` — правило. Стаб.

**Стаб.** `.claude/rules/codestyle.md` (2026-05-30).

**На какой вопрос отвечает:** «Как мы пишем код?» Конвенции
написания (именование, слои, обработка ошибок, идиомы,
форматирование, разбиение на классы/пакеты). Наполняется итеративно
через чат. Детали — в стабе.

### `code-writer` — роль-агент. Стаб.

**Стаб.** `.claude/agents/code-writer.md` (2026-05-30).

**Суть.** Автор кода. Пишет по `tech-radar` + `codestyle`, опирается

**Стаб.** `.claude/skills/find-code-examples.md` (2026-05-30).

**Суть.** Пост-код-скилл: после написания кода подбирает примеры из

## Сквозное

### Адверсариальный ревьюер — роль-агент с фокусами

**Суть.** Одна роль-агент, не несколько отдельных. Ревьюит по
фокусам, переключая фокус по запросу или по контексту шага.

**Статус.** Создана 2026-05-29: `.claude/agents/reviewer.md`.
Реестр фокусов ведётся там.

**Фокусы:**

- **концепция** — `concept-review` (создан), активен, `DOCS_CHECK_N`;
- **безопасность** — `security-review` (стаб, деактивирован до шага
  «Безопасность»), `CODE`;
- **конвенции** — `conventions-review` (стаб), `CODE`;
- **производительность** — `performance-review` (стаб), `CODE`;
- **устойчивость к сбоям** — `disaster-review` (стаб), `CODE`;
- **расхождения** — `divergence-review` (стаб), `SYNC_DOCS_FROM_CODE`;
- **тесты** — `test-review` (отложен), шаг 10.

## Принятый дизайн (сводка решений из чата)

- **Состав фиксируется целиком; файлы артефактов — стабами сразу**
  (подход (а), переписан 2026-05-30). Наполнение по ходу, форма с
  первого реального использования. Не стабим только то, что
  наполнять нечем: тестовые артефакты
  шага 10.
- **Тулинг кода и тулинг тестов — на разных под-шагах фазы.** Код —
  на `CODE`. Тесты — на шаге 10. Разделение по моменту реальной
  потребности.
- **Синхронизация доков вынесена из `CODE` в отдельный под-шаг
  `SYNC_DOCS_FROM_CODE`.** `CODE` = написание + ревью-итерации
  (фокусы) + аппрув; SYNC = docs←code после аппрува (детект
  `divergence-review` → реконсиляция curator / `reconcile-knowledge`).
  См. процесс.
- **`tech-radar` и `codestyle` наполняются через чат итеративно**,
  без заранее заданной формы. Форма вырастает по первым записям.
- **`code-writer` опирается на код-шаблоны** тира
  `.claude/templates/code/` (абстрактные паттерны). Подбор примеров
  из реального кода (`find-code-examples`) — пост-код-фаза для доков,
  не написание. Единый слой «референс-доков» — закрыт (REF-Q1,
  `.claude/decisions/code-templates-vs-examples.md`).
- **Ревью — одна роль-агент с переключаемыми фокусами**, не
  несколько отдельных агентов. На каждом фокусе — отдельный скилл.
- **`concept-review` помечает пробелы, но не размещает знание.**
  Размещение — штатный поток (`recognize-knowledge` → классификаторы
  → `place-knowledge` / `structure`) на под-шаге `GAPS_CLOSE_N`.
  См. сам скилл.

## Срок жизни заметки

Заметка живёт до материализации всех артефактов. Стабы созданы
2026-05-30; остаются отложенными тестовые артефакты шага 10. По мере наполнения стабов содержательной
процедурой и закрытия отложенных — статусы в сводной карте
обновляются. Когда вся карта проставлена и наполнена, заметка
сворачивается / переезжает в архив; решения переезжают в сами
артефакты, где для этого есть место. Точка свёртки — по факту, не
заранее.
