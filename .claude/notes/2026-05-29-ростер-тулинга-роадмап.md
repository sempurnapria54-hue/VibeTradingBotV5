порядке артефакты материализуются и как устроен каждый.

## Контекст

Тулинг роадмапа спроектирован в чате 2026-05-29 в начале
исполнения шага 1 Фазы 1. Заметка фиксирует состав целиком,
чтобы решения не потерялись; файлы артефактов создаются на тех
под-шагах, где они нужны (подход (а)). Исключение —
`concept-review`: нужен сразу для `DOCS_CHECK_1` шага 1,
создан 2026-05-29 вместе с этой заметкой.

Привязка к процессу — `.claude/processes/roadmap-step-execution.md`
(под-шаги `TOOLING` → `DOCS_CHECK_N` → `GAPS_CLOSE_N` → `CODE`).

## Концепт-чек

### `concept-review` — скилл

**Статус.** Создан 2026-05-29: `.claude/skills/concept-review.md`.

**Суть.** В самом скилле. Здесь не дублируем.

## Код (под-шаг `CODE`)

### `tech-radar` — правило/док. Отложен.

**На какой вопрос отвечает:** «Что используем при написании
кода?»

**Содержание.** Стэк (Java 21, Spring Boot 3, PostgreSQL —
расширяется по мере появления выбора) + библиотеки / техники со
статусом по модели tech radar:

- `adopt` — используем по умолчанию;
- `trial` — пробуем в этом шаге, оцениваем;
- `assess` — на радаре, ещё не пробовали;
- `hold` — отказались / временно не используем.

**Как наполняется.** Итеративно через чат: появилась развилка по
библиотеке — обсудили — записали запись в `tech-radar` со
статусом. Шаблон записей не фиксируется заранее; вырастает по
первым записям.

**Когда материализуется.** На под-шаге `CODE` первого шага, где
пишется код (шаг 1 Фазы 1, если код там будет).

### `codestyle` — правило. Отложен.

**На какой вопрос отвечает:** «Как мы пишем код?»

**Содержание.** Конвенции написания: именование, слои, обработка
ошибок, идиомы, форматирование, разбиение на классы / пакеты.

**Как наполняется.** Итеративно через чат, как `tech-radar`.

**Когда материализуется.** На под-шаге `CODE` первого шага с
кодом.

### `code-writer` — роль-агент. Отложен.

**На какой вопрос отвечает:** «Что делает Claude в роли автора
кода?»

**Суть.** Автор кода. Пишет по `tech-radar` (выбор технологий) +
`codestyle` (стиль написания). Дополнительно опирается на
example-скилл, который смотрит в референс-доки (живые примеры
кода из проекта или подсобранные).

**Референс-доки.** Создаются через чат **первый раз** перед
`CODE` (см. маркер в backlog) и растут итеративно по мере
накопления примеров. Статических шаблонов кода не держим —
example-based подход.

**Когда материализуется.** На под-шаге `CODE` первого шага с
кодом.

### `security-review` — ревью-фокус. Отложен.

**Фокус.** Секреты и ключи (в т. ч. ключи OKX), валидация входов
(API наш и потребление чужого), безопасность ордеров (что мы
посылаем на биржу).

**Реализация.** Один из фокусов адверсариального ревьюера
(см. ниже «Сквозное»), не отдельный агент.

**Когда материализуется.** На под-шаге `CODE` первого шага с
кодом.

### `conventions-review` — ревью-фокус. Отложен.

**Фокус.** Соответствие написанного кода правилам в `codestyle` и
`tech-radar`.

**Реализация.** Один из фокусов адверсариального ревьюера.

**Когда материализуется.** На под-шаге `CODE` первого шага с
кодом.

## Тесты (шаг 9)

### `testing-strategy` — правило. Отложен.

**На какой вопрос отвечает:** «Какая у нас стратегия тестирования?»

**Содержание.** Уровни (unit / integration / e2e), что в scope
тестирования и что — вне; тест-данные (как готовим, где живут);
цель покрытия.

**Когда материализуется.** На шаге 9 (Тесты) фазы.

### `test-writer` — скилл. Отложен.

**На какой вопрос отвечает:** «Как именно писать тесты?»

**Суть.** Критический разбор системы (что может сломаться,
какие границы / инварианты) → подбор релевантных кейсов из
стратегии, заданной `testing-strategy`. Не «покрытие ради
покрытия», а целевой выбор кейсов.

**Когда материализуется.** На шаге 9 фазы.

### `test-review` — ревью-фокус. Отложен.

**Фокус.** Покрытие, осмысленность тестов (не тавтологии вроде
`mock.method() → assertEquals(mock.method())`), границы.

**Реализация.** Один из фокусов адверсариального ревьюера.

**Когда материализуется.** На шаге 9 фазы.

## Сквозное

### Адверсариальный ревьюер — роль-агент с фокусами

**Суть.** Одна роль-агент, не четыре отдельных. Ревьюит
концепцию / безопасность / конвенции / тесты, переключая
фокус по запросу или по контексту шага.

**Статус.** Создана 2026-05-29: `.claude/agents/reviewer.md`.
Активен только концептный фокус.

**Фокусы:**

- **концепция** — скилл `concept-review` (создан 2026-05-29),
  **активен**;
- **безопасность** — `security-review` (отложен, под-шаг `CODE`);
- **конвенции** — `conventions-review` (отложен, под-шаг `CODE`);
- **тесты** — `test-review` (отложен, шаг 9).

**Подключение остальных фокусов.** `DOCS_CHECK_N` теперь
прогоняется ролью reviewer с фокусом `concept-review` (не прямым
применением скилла). Фокусы безопасности и конвенций
подключаются на под-шаге `CODE` первого шага с кодом, фокус
тестов — на шаге 9.

## Принятый дизайн (сводка решений из чата)

- **Состав фиксируется сейчас целиком, файлы — по
  потребности.** Подход (а): ростер ниже + файлы артефактов на
  тех под-шагах, где они нужны. `concept-review` — единственное
  исключение (нужен сразу для `DOCS_CHECK_1`).
- **Тулинг кода и тулинг тестов — на разных под-шагах фазы.**
  Код — на `CODE` (первый шаг с кодом). Тесты — на шаге 9
  фазы. Разделение по моменту реальной потребности, не по
  концептуальной близости.
- **`tech-radar` и `codestyle` наполняются через чат
  итеративно**, без заранее заданной формы. Форма вырастает по
  первым записям.
- **`code-writer` — example-based**, не template-based. Базируется
  на референс-доках, которые тоже растут итеративно. Маркер
  «приложить референс-доки перед `CODE`» — в backlog.
- **Ревью — одна роль-агент с переключаемыми фокусами**, не
  четыре отдельных агента. На каждом фокусе — отдельный скилл
  (`concept-review`, `security-review`, `conventions-review`,
  `test-review`). Концептный фокус уже выделен в скилл; остальные
  — при материализации роли-агента.
- **`concept-review` помечает пробелы, но не размещает знание.**
  Размещение — штатный поток (`recognize-knowledge` → классификаторы
  → `place-knowledge` / `structure`) на под-шаге `GAPS_CLOSE_N`.
  См. сам скилл.

## Срок жизни заметки

Заметка живёт до материализации всех артефактов. По мере
создания каждого — статус в сводной карте обновляется
(`отложен` → ссылка на файл). Когда вся карта проставлена
ссылками, заметка переезжает из активного состояния в архив /
сворачивается; решения переезжают в сами артефакты, где для
этого есть место (тех-радар, codestyle, агент). Точка свёртки —
по факту, не заранее.
