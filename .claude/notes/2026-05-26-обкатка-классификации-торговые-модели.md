- **Отброшено как не-знание:** implementation checklist (ALG §18),
  legacy-навигация и legacy decision-log ссылки (STR §33.1/33.2/§38),
  негативные «что не храним» списки (свёрнуты в границы моделей).

### Что сработало гладко
- **Шаг 1 (распознавание):** материал уже отфильтрован; правило про
  отрицательные формулировки («не храним…», «нет lifecycle…»)
  отработало единообразно — позитив в модель, отрицание сворачиваю.
- **Шаг 2 (область):** мгновенно, всё продукт.
- **Шаг 3 (тип):** модель/lifecycle/правило/команда различимы для
  основной массы.

### Где скрипит (по убыванию остроты)
1. **NQ-A. Гранулярность модели для вложенных/value/snapshot классов.**
   Самый громкий скрип батча. Condition-дерево (AlgoOrder),
   ~30-классовое дерево Strategy, все `*ExternalSnapshot`, `Balance`
   в контейнере, `AttachedAlgoOrder` в Order. `naming.md` +
   «один файл = одна сущность» буквально → ~50 файлов. Нужен критерий
   «агрегат-корень → документ; value/snapshot/params/enum → внутри
   родителя или в поддереве». **Кандидат в новый открытый вопрос.**
2. **Q2 (дублированное правило — первоисточник).** Подтверждено мощно;
   снапшот v6 говорил «Q2 отложен до появления торговых сущностей в
   `docs/`» — этот батч и есть тот материал. Самые повторяемые
   правила и число документов:
   - partial-close запрещён / только reduce-only: **5 док.**
     (Position, Order, AlgoOrder, Deal, Strategy).
   - не хранить strategyActionId / связь через DealActionState:
     **4 док.** (Order, AlgoOrder, Deal, Strategy).
   - resultProfit через REFRESH_FILLS, не balance diff: **3 док.**
     (Balance, Position, Deal).
   - positionReducingOnly vs OKX reduceOnly: **3 док.**
   - ACK не runtime truth: **3 док.** (Position, Order, AlgoOrder).
   - формула live risk: **2 док.** (Position, Deal) — плюс
     внутридокументный дубль в Deal (§2, §10.3, §12.3).
   - external-status через resolver / unknown→exception→ERROR/HOLD:
     **2 док.** (Order, AlgoOrder).
   - ServiceCommand — runtime object, не persisted queue:
     Deal + Strategy (+ B8/F1).
   - **Внутридокументные дубли:** Deal §3.4 ≈ §11 (граница
     DealContext); BalanceContainer «не гарантия свежести» ×3.
   - **Гипотеза критерия:** первоисточник = документ объекта, который
     *владеет/энфорсит* правило; остальные ссылаются. live risk →
     Position (владеет формулой); resultProfit → Deal (владеет полем);
     partial-close → `docs/rules/` (нет единственного владельца);
     reduce-only intent → спорно (Strategy intent vs runtime-поле
     Order/AlgoOrder).
3. **Q1 (инвариант объекта: в его doc или в `docs/rules/`).** Богатый
   материал и более чёткая гипотеза разделителя — **охват**:
   - один объект → его модель/lifecycle: «макс. одна Position на
     Deal», terminal-инварианты Deal, эффекты статусов Strategy;
   - кросс-объектное/сквозное → `docs/rules/`: partial-close (5 док.),
     ACK-not-truth (3 док.), Exchange HOLD command-lists, adapter
     boundary, error→ERROR/HOLD таксономия. partial-close — самый
     чистый экспонат «сквозное → rules».
   - B3 (Strategy.INACTIVE) подтвердился как тройная развилка
     (модель/lifecycle vs rules vs компонент-решатель).
4. **NQ-D. Компонент vs модель/процесс.** Скрип первой обкатки
   (K1/B11/D3), теперь с большой свежей популяцией: *StatusResolver,
   *Executor, *Checker, *Calculator, RiskValidator, RiskBlockResolver,
   ServiceCommandFactory, *Job. **Важно:** в текущей `structure.md`
   **есть** тип `docs/components/` («кто выполняет?», PascalCase) —
   он закрывает «куда класть исполнителя». Остаётся судейский вопрос
   границы «компонент vs процесс vs раздел модели». Тип `components/`
   стоит явно задействовать (первая обкатка его не упоминала).
5. **NQ-C. Lifecycle: отдельный файл или раздел модели.** Системно:
   Order, AlgoOrder, AttachedAlgoOrder, Position, Deal, Strategy — у
   всех есть статусы; у Order/AlgoOrder/AttachedAlgoOrder в коде явные
   FSM-переходы. Критерий: тривиальный набор (Position ACTIVE/CLOSED/
   ERROR) → раздел модели? богатая FSM (Deal, AlgoOrder) → свой
   lifecycle? Обобщает G1/B12/E4 первой обкатки.
6. **Q3 (правило, неотделимое от процесса).** Умеренный новый
   материал: таксономия exchange-исключений (процесс error-handling
   vs rules), 12-пунктная валидация стратегии (неотделима от операции
   сохранения), evidence-cycle refresh («пустой data=[] не финал»).
