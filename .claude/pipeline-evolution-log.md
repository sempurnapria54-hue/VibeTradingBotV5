## 2026-05-16 — Этап 4: артефакты и правки пайплайна для миграции `docs/domain/` → `docs/spec/`

Завершён Этап 4 подготовки к миграции legacy-документации. Создана инфраструктура артефактов, скиллов и правил, поддерживающая работу над миграцией. Перевод пакета ADR-0006..0009 в Accepted откладывается до стресс-теста (отдельная сессия после обновления Project Knowledge).

### Содержательные решения сессии

- **Расщепление функций единого `docs/GLOSSARY.md` на три артефакта.** Решение принято в начале сессии при ревью плана Этапа 4. Единый файл с тремя функциями (терминологические соглашения + реестр имён моделей + чеклист миграции) разнесён по трём независимым артефактам с разной природой и судьбой:
  - `docs/conventions/terminology.md` — терминологические соглашения, не зависят от миграции.
  - `docs/spec/MODELS.md` — реестр канонических имён бизнес-моделей, навигационная точка входа в `docs/spec/`.
  - `.claude/planning/migration-tracker.md` — рабочий артефакт прогресса миграции, рассматривается на упразднение после фазы 5.
  
  Решение применено к Proposed-ADR-0007 §3 и ADR-0009 §9 (правки до перевода в Accepted).

- **Правило «новый термин — куда фиксировать»** (Принцип 4 working-with-claude.md). Имя бизнес-модели → MODELS.md + model-документ. Терминологическое соглашение → terminology.md. Сквозная концепция → соответствующий invariant/process/lifecycle-документ. Отдельного «глоссария концепций» проект не создаёт.

- **Терминологическое соглашение «domain-only / external-only»** заменяет «orphan». Концепция «рассинхронизации домена и биржи» по обнаружению, классификации и реакции — не в terminology.md, а распределяется по соответствующим spec-документам при миграции (или появляется как Q-N в журнале по ходу разбора).

- **Частичная миграция как штатное состояние.** Документ может быть мигрирован не целиком за одну итерацию — неразобранные блоки уходят в журнал Q-N. MIGRATED-маркер ставится только когда все блоки разнесены и все Q-N закрыты. После разрешения Q-N — локальный довоз, не переоткрытие миграции.

- **Shared-файлы при миграции кластера.** Legacy-документ, распадающийся по нескольким кластерам, получает MIGRATED-маркер только когда все его фрагменты разнесены, возможно через несколько кластеров.

## 2026-05-15 — Уточнение правила «чат vs Claude Code»

Расширено правило разделения работы между чатом и Claude Code в
обратном направлении. Существующая формулировка (правило 11
project-instructions, Принцип 1 working-with-claude, таблица в
playbook) покрывала «не задавай пользователю вопросы, требующие
чтения репо — отдай в Claude Code». Не покрывала симметричное:
**прикрепление файлов в чат — это доставка материала, не
делегирование анализа чату**.

Прецедент — сессия миграции AnomalyReport + создание скилла
`spec-document-migration` (2026-05-15). В одной сессии Claude
трижды попытался выполнить анализ файлов в чате после того, как
пользователь прикрепил их вручную; правильное поведение
восстанавливалось только после прямых указаний пользователя.

Правка точечная, без ADR (по аналогии с открытым пунктом
«Определение принятия ADR» в backlog — мелкие уточнения
существующих правил выполняются без формального ADR).

Затронуты три файла из Project Knowledge: project-instructions.md,
working-with-claude.md, playbook.md. Требуется обновление PK в
claude.ai человеком + Сценарий 8 (глубокая проверка консистентности)
в исходном чате.

## 2026-05-15 — Создан скилл `spec-document-migration`

Стартовая версия после пилотного кейса миграции AnomalyReport
(`docs/spec/models/AnomalyReport.md` + `docs/spec/lifecycle/AnomalyReport.md`,
закрыто в backlog тем же днём).

Скилл фиксирует трёхэтапную процедуру миграции (анализ-отчёт от
Claude Code → решение развилок в чате → исполнение), формат
промпта-анализа, требования к MIGRATED-маркеру и страховку от потерь
содержания через инвентарь.

Триггер активации: миграция документа из legacy-локаций (`docs/domain/`,
`docs/deprecated/`) в `docs/spec/`. Граница с `spec-document-workflow`:
последний работает с документами, уже находящимися в `docs/spec/`;
новый — с переездами в `docs/spec/`. На целевых документах после
исполнения миграции активируется `spec-document-workflow` для финального
чек-листа.

Помечен как первая версия после одного пилотного кейса — ожидается
итерация после 2-3 следующих миграций.

Связное обновление: пункт «Создание скилла `spec-document-migration`»
из Later переведён в Закрытые backlog. Граница с соседним скиллом
описана в обоих скиллах (после доработки `spec-document-workflow` на

## 2026-05-14 — терминологическая правка: entity → доменная модель

Зафиксировано предпочтение термина «доменная модель» (или «модель»)
вместо «entity» во всех контекстах проекта. Причина: «entity» в
Spring/Java-проекте нагружено JPA-аннотацией `@Entity`, что создаёт
двусмысленность между доменной моделью и персистентной сущностью.

Не все доменные модели проекта персистентны (DealContext,
CalculationContext — не имеют таблиц). Термин «доменная модель»
покрывает оба случая без подразумеваемой персистентности.

Триггер: пользователь обратил внимание на нагруженность термина
«entity» в обсуждении стандарта структуры docs/spec/.
