# Концепция тестирования

## На какой вопрос отвечает этот файл

Что хотим получить от тестирования системы и зачем, где границы этого
предмета.

## Носитель намерения держателя

Здесь — намерение держателя по теме «тестирование»: материал от 2026-09-12,
граница пересмотрена его же решением 2026-09-16. Док меняется только решением
держателя; всё, чем это намерение исполняется, — уровни разложены по
предметам, стабы, управление временем, обвязка сквозных, состав сценариев,
среда прогона, место документов кейсов, включение в реактор — живёт у
дизайн-прохода (`.claude/decisions/test-contour-design-pass.md`) и в доках
по факту, а не здесь. Порядок работы тестового шага — три под-шага `CODE` —
держит машина шага (`.claude/processes/roadmap-step-execution.md`
§«Конец фазы»).

## Что доказываем и зачем

Систему, не модули: чёрный ящик каждого сервиса плюс сквозные тесты через
API. Цель — рефакторить сервисы без опаски; позже наборы встраиваются в
пайплайн GitLab.

Тесты не должны закреплять хранение против цели рефакторинга: при
проверках по базе различается, где схема — контракт (журнал аудита, факты
статистики), а где рабочая внутренность.

## 1. Чёрный ящик сервиса

Каждый сервис отдельно.

- **Входы:** вызовы API, потреблённые события, ответы внешних систем
  (стабы), конфигурация и **время** — джоба по расписанию есть вход,
  которым управляет тест.
- **Выходы:** ответы API, опубликованные события, исходящие вызовы, **база
  сервиса**. **Отсутствие выхода — тоже выход:** «риск-гейт отказал»
  утверждается как «ни ордера, ни события», а не остаётся непроверенным.

## 2. Юнит-тесты — только чистая логика

Юниты пишутся только на чистую логику с комбинаторным входом:
риск-математика, размер позиции, переходы FSM, парсеры, календарь и время.
Через стабильные интерфейсы, без моков внутренностей. Проводка,
репозитории, оркестрация — только чёрный ящик.

Существующий набор реактора ревьюется этим критерием: тест, закрепляющий
структуру, — под снос, когда его поведение покрыл ящик. Снимается он
**последним** под-шагом `CODE` и не раньше, чем ящик покрыл его поведение;
ни один существующий тест до этого не удаляется.

## 3. Интеграционные — только против биржи, только коннектор

Термин держателя: «интеграционные» здесь — против биржи; контейнеры базы и
Kafka — субстрат чёрного ящика, не интеграционные. **Это частный случай
уровня 1:** чёрный ящик коннектора против двух мишеней.

- Против **стаба** с записанными ответами реальной площадки —
  детерминированно, в каждом пайплайне.
- Против **живой площадки** — demo-окружение источника, тестовый профиль,
  тестовый аккаунт биржи — по расписанию и по запросу, не в каждом
  пайплайне: это детектор дрейфа API площадки. Записи для стаба берутся из
  этих прогонов.

Обе формы — чёрный ящик самого коннектора: отдельной тест-обращённой
поверхности у сервиса не появляется.

## 4. Сквозные — два набора

- **Ядро** против стаба биржи — в каждом пайплайне, широкие сценарии.
- **Дым** против тестового аккаунта биржи — по расписанию и перед выходом
  на живого; узкий: выставил → исполнилось/отменилось → видно в журнале и
  агрегатах.

Площадка — локальный стенд сейчас; тот же набор переезжает на кластер как
есть.

## Границы

- **Предмет — построенные сервисы фазы 2 в их итоговом составе** (после
  раздела `audit-statistics` шагом 11).
- **Работа с источником — внутри трёх уровней, а не рядом с ними**
  (§«Пересмотр границы»).
- **Demo-прогоны в пайплайн не входят.** Их предусловие — ключи
  demo-окружения и распечатанный Vault; держатель предоставляет их к
  под-шагу 3 `CODE` тестового шага фазы 2.
- **Нагрузочное тестирование и генератор (эмулятор) сбоев — не предмет
  тестового шага фазы 2:** держатель отнёс их к концу фазы 6. Парковка со
  своим триггером — `.claude/work/backlog.md` §«Нагрузочные прогоны и
  генератор сбоев — конец фазы 6».
- **«Как» — предмет дизайн-прохода шага, не концепции:** стабы, управление
  временем, обвязка сквозных, состав сценариев; за ними — перечень
  предметов по уровням, среда прогона, место документов кейсов, включение
  в реактор.

## Пересмотр границы (решение держателя, 2026-09-16)

**Оговорка «контур API источника — свой процесс» снята.** Три уровня
покрывают **всё построенное фазой 2, включая интеграцию с источником**:
работа с OKX проверяется как чёрный ящик `connector-okx` на demo-окружении —
как у любого другого сервиса. **Отдельный контур со своей тест-обращённой
поверхностью (`/raw`-passthrough) в сервисах не строится.** Контур фазы 1
снят вместе с донором; переиспользуемое взято материалом для кейсов
коннектора (`.claude/decisions/source-api-contour-retired.md`).

Пересмотр адресует границу, данную 2026-09-15 вместе с машиной шага; три
уровня, порядок трёх под-шагов `CODE` и предмет — построенные сервисы фазы 2
в итоговом составе — не меняются.
