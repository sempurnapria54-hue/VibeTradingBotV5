# 5. # 6. Q5. Можно ли автоматически переводить ERROR -> CLOSED после kill-switch

Статус: `DECIDED`

---

## Проблема

Если сделка находится в `ERROR`, это означает, что обнаружено аварийное состояние:

```text
сломаны инварианты;
есть опасное расхождение БД и биржи;
потеряна защита;
есть неизвестный live risk;
процесс сопровождения не может безопасно продолжаться обычным FSM-flow.
```

При этом kill-switch / safety-flow может снять весь риск:

```text
позиция закрыта;
ordinary orders отменены;
algo-orders отменены;
attached protection больше не влияет на риск;
live risk отсутствует;
финальные факты подтверждены refresh/history.
```

Нужно решить, можно ли после этого автоматически переводить сделку:

```text
ERROR -> CLOSED
```

или сделка должна оставаться в `ERROR` для ручного разбора.

---

## Финальное решение

Не переводим аварийную сделку напрямую:

```text
ERROR -> CLOSED
```

Вместо этого добавляем отдельный terminal-статус:

```text
EMERGENCY_CLOSED
```

Финальная семантика:

```text
ERROR
  -> авария обнаружена;
  -> обычная strategy/FSM-логика заблокирована;
  -> разрешены только safety / recovery / refresh / kill-switch действия.

EMERGENCY_CLOSED
  -> авария была;
  -> kill-switch или safety-flow снял весь live risk;
  -> отсутствие риска подтверждено фактами;
  -> сделка терминально завершена, но не считается нормальным CLOSED.
```

---

## Почему не ERROR -> CLOSED

`CLOSED` должен означать нормальное завершение сделки.

Например:

```text
STOP_LOSS;
TAKE_PROFIT;
STRATEGY_EXIT;
TIME_STOP;
MANUAL;
обычный graceful shutdown.
```

Если переводить аварийную сделку в `CLOSED`, есть риск скрыть важный факт:

```text
сделка закрылась не штатно,
а через аварийный safety-flow / kill-switch.
```

Это плохо для:

```text
аудита;
расследования инцидентов;
аналитики качества стратегии;
отчётов по стабильности FSM;
поиска проблем в интеграции с биржей.
```

Поэтому аварийный финал должен быть отдельным статусом.

---

## Почему не оставлять навсегда в ERROR

Если kill-switch уже снял весь риск, то сделка фактически больше не требует runtime-сопровождения.

Оставлять её навсегда в `ERROR` неудобно:

```text
orchestrator будет постоянно видеть аварийную сделку;
нужно будет вручную отличать “риск ещё живой” от “риск уже снят”;
сложнее строить списки активных проблем;
сложнее отделить pending emergency от завершённой emergency-сделки.
```

Поэтому `ERROR` оставляем для состояния:

```text
авария есть или была обнаружена,
но safety-flow ещё не доказал отсутствие live risk.
```

А `EMERGENCY_CLOSED` используем для состояния:

```text
авария была,
но риск уже снят и подтверждён.
```

## Обновлённая модель Deal.Status

```java
public enum Status {

    /**
     * Сделка создана, но entry order ещё не создан / не отправлен.
     */
    PRECHECK,

    /**
     * Entry order создан или отправлен, ждём подтверждения входа.
     */
    ENTRY_SUBMITTED,

    /**
     * Вход подтверждён: entry order финализирован, позиция открыта.
     */
    ENTRY_FINALIZED,

    /**
     * Temporary attached protection заменена на standalone main protection.
     *
     * Этот статус условный и используется только если switch реально нужен.
     */
    PROTECTION_SWITCHED,

    /**
     * Позиция сопровождается по стратегии.
     */
    MANAGING,

    /**
     * Выход инициирован, нужно дочистить риск и подтвердить закрытие.
     */
    EXIT_PENDING,

    /**
     * Сделка нормально закрыта.
     */
    CLOSED,

    /**
     * Обнаружена авария.
     *
     * Обычная strategy/FSM-логика заблокирована.
     * Разрешены только safety / recovery / refresh / kill-switch действия.
     */
    ERROR,

    /**
     * Аварийная сделка завершена после safety-flow / kill-switch.
     *
     * Live risk отсутствует:
     * - position закрыта или отсутствует;
     * - ordinary orders не live;
     * - algo-orders не live;
     * - attached protection больше не влияет на риск;
     * - финальные факты подтверждены refresh/history.
     *
     * Это terminal-статус, но не нормальный CLOSED.
     */
    EMERGENCY_CLOSED
}
```

---

## Допустимый переход

Новый допустимый переход:

```text
ERROR -> EMERGENCY_CLOSED
```

Переход разрешён только после safety-flow / kill-switch и финального подтверждения фактов.

Типовой flow:

```text
ERROR
  -> EXECUTE_KILL_SWITCH
  -> REFRESH_POSITION
  -> REFRESH_PENDING_ORDERS
  -> REFRESH_ALGO_ORDERS
  -> REFRESH_FILLS / REFRESH_ORDER_HISTORY / REFRESH_ALGO_ORDER_HISTORY
  -> проверка отсутствия live risk
  -> EMERGENCY_CLOSED
```

Недопустимый переход:

```text
ERROR -> CLOSED
```

---

## Инварианты перехода ERROR -> EMERGENCY_CLOSED

Переход разрешён только если подтверждено:

```text
1. На бирже нет активной позиции по инструменту сделки
   или позиция имеет размер 0.

2. В локальной БД Position закрыта
   или приведена к состоянию, соответствующему биржевому факту.

3. Live ordinary orders отсутствуют.

4. Live algo-orders отсутствуют.

5. Attached protection отсутствует
   или больше не влияет на риск.

6. Нет pending orders, которые могут открыть или увеличить риск.

7. Нет больше одной позиции по инструменту.

8. Kill-switch / safety-команды зафиксированы в истории исполнения.

9. Финальные exchange snapshots / refresh facts сохранены
   в аудите, истории или safety report.

10. Сделка больше не требует runtime-сопровождения FSM.
```

Если хотя бы один пункт не подтверждён:

```text
сделка остаётся в ERROR;
FSM / orchestrator продолжает safety-flow;
или требуется ручной разбор.
```

## Связь с CloseReason

`EMERGENCY_CLOSED` — это статус сделки.

`Deal.closeReason` остаётся причиной фактического закрытия позиции / сделки.

Примеры:

```text
Deal.status = EMERGENCY_CLOSED
Deal.closeReason = EMERGENCY_STOP
```

или:

```text
Deal.status = EMERGENCY_CLOSED
Deal.closeReason = RISK_CONTROL
```

Если аварийное закрытие было вызвано конкретной причиной shutdown:

```text
Deal.shutdownReason = MARKET_DATA_EXPIRED
Deal.closeReason = EMERGENCY_STOP
Deal.status = EMERGENCY_CLOSED
```

или:

```text
Deal.shutdownReason = STRATEGY_DELETED
Deal.closeReason = EMERGENCY_STOP
Deal.status = EMERGENCY_CLOSED
```

Важно:

```text
shutdownReason объясняет, почему был запущен shutdown / safety-flow.
closeReason объясняет, почему позиция фактически закрылась.
status показывает terminal-состояние сделки.
```

---

## Поведение FSM в ERROR

`ERROR` — это не обычный торговый статус.

В `ERROR` запрещено:

```text
проверять обычные strategy steps;
создавать новые entry/grid orders;
делать data-dependent protection adjustment;
делать partial exit по обычным strategy conditions;
продолжать MANAGING-flow.
```

В `ERROR` разрешены только действия, связанные с безопасностью и восстановлением:

```text
REFRESH_POSITION;
REFRESH_PENDING_ORDERS;
REFRESH_ALGO_ORDERS;
REFRESH_ORDER_HISTORY;
REFRESH_ALGO_ORDER_HISTORY;
REFRESH_FILLS;
CANCEL_ORDER;
CANCEL_ALGO_ORDER;
CLOSE_POSITION;
EXECUTE_KILL_SWITCH;
MARK_DEAL_ERROR;
финальная фиксация EMERGENCY_CLOSED.
```

---

## Поведение после EMERGENCY_CLOSED

`EMERGENCY_CLOSED` — terminal-статус.

После перехода в `EMERGENCY_CLOSED` обычный `DealOrchestratorJob` больше не сопровождает сделку как активную.

Если позже будет найден live risk по такой сделке или инструменту, это уже не обычная FSM-задача.

Это зона:

```text
AnomalyJob / ReconciliationJob
```

Такой случай должен создавать anomaly report, потому что invariant нарушен:

```text
сделка terminal,
но live risk снова обнаружен.
```

---

## Аудит и история

Переход в `EMERGENCY_CLOSED` должен быть хорошо виден в timeline.

Минимально нужно зафиксировать:

```text
1. Почему сделка попала в ERROR.
2. Какие инварианты были нарушены.
3. Почему был запущен kill-switch / safety-flow.
4. Какие команды были выполнены:
   - cancel orders;
   - cancel algo-orders;
   - close position;
   - refresh facts.
5. Какие snapshots были до safety-flow.
6. Какие snapshots были после safety-flow.
7. Кто/что инициировал переход в EMERGENCY_CLOSED.
8. Почему live risk считается снятым.
```

`EMERGENCY_CLOSED` не должен скрывать аварийность.

Он должен явно показывать:

```text
сделка закрыта аварийно,
риск снят,
нужен разбор причины ERROR по истории.
```

---

## Итоговое правило

```text
ERROR -> CLOSED не разрешаем.

Добавляем Deal.Status.EMERGENCY_CLOSED.

ERROR означает:
  авария обнаружена;
  обычная strategy/FSM-логика заблокирована;
  risk может быть ещё живым;
  разрешён только safety-flow.

EMERGENCY_CLOSED означает:
  авария была;
  kill-switch / safety-flow снял live risk;
  отсутствие риска подтверждено фактами;
  сделка терминально завершена, но не считается нормальным CLOSED.
```

# 6. Q6. Что делать в PRECHECK, если entry condition больше не актуален

Статус: `DECIDED`

---

## Проблема

`EntryScannerJob` может создать `Deal` в статусе `PRECHECK`, потому что на момент сканирования рынка условия входа были выполнены.

Но между созданием `Deal` и обработкой `PRECHECK` в FSM рынок мог измениться:

```text
цена ушла;
свеча закрылась иначе;
MarketPhase изменилась;
индикаторное условие больше не выполняется;
range / breakout condition больше не актуален;
risk/precheck уже не разрешает вход.
```

Нужно решить, что делать, если:

```text
Deal уже создан,
но ENTRY / GRID_ENTRY condition больше не true.
```

---

## Финальное решение

Выбираем вариант:

```text
Закрывать Deal без ошибки.
```

Если сделка находится в `PRECHECK`, entry condition больше не актуален, и по сделке ещё не создан live risk, то сделку закрываем штатно:

```text
Deal.status = CLOSED
Deal.closeReason = ENTRY_CONDITION_EXPIRED
```

Это не авария и не `ERROR`.

Это нормальная рыночная ситуация:

```text
EntryScannerJob увидел возможность входа,
но к моменту PRECHECK окно входа уже устарело.
```

---

## Новое значение Deal.CloseReason

Добавляем новое значение в `Deal.CloseReason`:

```java
public enum CloseReason {

    /** Закрытие по stop-loss. */
    STOP_LOSS,

    /** Закрытие по take-profit. */
    TAKE_PROFIT,

    /** Закрытие по правилу стратегии. */
    STRATEGY_EXIT,

    /** Закрытие по time-stop. */
    TIME_STOP,

    /** Закрытие по risk control. */
    RISK_CONTROL,

    /** Аварийное закрытие. */
    EMERGENCY_STOP,

    /** Закрытие вручную. */
    MANUAL,

    /**
     * Deal был создан как candidate на вход,
     * но до создания live risk условие входа перестало быть актуальным.
     *
     * Используется только для раннего закрытия сделки в PRECHECK,
     * когда entry order ещё не создан / не отправлен,
     * позиции нет и live risk отсутствует.
     */
    ENTRY_CONDITION_EXPIRED,

    /** Причина не определена. */
    UNKNOWN
}
```

---

## Почему не ERROR

`ERROR` означает аварийное состояние:

```text
сломаны инварианты;
есть опасное расхождение БД и биржи;
есть неизвестный live risk;
обычный FSM-flow не может безопасно продолжаться.
```

Но исчезновение entry condition в `PRECHECK` — это обычная ситуация живого рынка.

Пример:

```text
EntryScannerJob:
  RSI > 50
  price пробил RANGE_HIGH
  MarketPhase = BULL_TREND
  Deal создан в PRECHECK

Через несколько секунд:
  price вернулась в range
  breakout больше не подтверждён
  ENTRY condition больше не true
```

Это не поломка системы.

Поэтому не нужно засорять `ERROR` такими сделками.

---

## Почему не оставаться в PRECHECK

Можно было бы оставить сделку в `PRECHECK` до timeout/retry, но это хуже для первого этапа.

Минусы такого подхода:

```text
будут копиться candidate-deals;
нужна отдельная timeout policy;
нужно решать, сколько ждать возврата condition;
PRECHECK начнёт превращаться в очередь ожидания сигнала;
можно случайно открыть сделку по старому входному контексту.
```

На первом этапе проще и безопаснее:

```text
condition устарел до появления live risk
  -> Deal закрываем без ошибки
  -> следующий вход найдёт новый EntryScannerJob
```

---

## Главный инвариант

Закрывать `Deal` без ошибки можно только если по сделке ещё не создан live risk.

Обязательные условия:

```text
1. Deal.status = PRECHECK.

2. Entry order ещё не создан
   или точно не отправлен на биржу.

3. Position отсутствует.

4. Live ordinary orders отсутствуют.

5. Live algo-orders отсутствуют.

6. Attached protection отсутствует
   или существует только как локальная неотправленная часть entry order,
   которая не создаёт live risk.

7. DealActionState не содержит materialized target,
   который уже может влиять на биржу или риск.

8. Нет exchange facts, указывающих,
   что entry order был отправлен или позиция появилась.
```

Если хотя бы одно условие не выполнено, простое закрытие запрещено.

---

## Что делать, если live risk уже появился

Если в `PRECHECK` или при recovery обнаружилось, что live risk уже создан, то `ENTRY_CONDITION_EXPIRED` больше не применим.

Например:

```text
entry order уже отправлен;
order найден на бирже;
position появилась;
algo-order уже отправлен;
есть live attached protection;
есть DealActionState с materialized RuntimeTarget, который уже влияет на биржу.
```

Тогда нельзя просто закрыть `Deal` как candidate.

Нужно идти через recovery / safety flow:

```text
refresh facts;
понять фактическое состояние order / position / algo-orders;
перейти в ENTRY_SUBMITTED или ENTRY_FINALIZED, если факты подтверждают вход;
или cancel / close / kill-switch, если состояние опасное;
или ERROR / EMERGENCY_CLOSED, если аварийный сценарий уже случился.
```

---

## Поведение PRECHECK handler

В `PRECHECK` handler нужно добавить отдельную ветку.

Flow:

```text
PRECHECK handler
  -> входные проверки
  -> найти ENTRY / GRID_ENTRY step
  -> проверить MarketDataExpirationChecker.checkForStep(...)
  -> если данные устарели или отсутствуют:
       применить StrategyStep.marketDataExpiredSetting
  -> если данные свежие:
       проверить StrategyCondition
  -> если StrategyCondition false:
       проверить, что live risk ещё не создан
       если live risk отсутствует:
           Deal.status = CLOSED
           Deal.closeReason = ENTRY_CONDITION_EXPIRED
       если live risk есть или состояние неизвестно:
           перейти в recovery / safety flow
  -> если StrategyCondition true:
       продолжить обычный PRECHECK flow
```

## Связь с EntryScannerJob

`EntryScannerJob` по-прежнему отвечает за первичный поиск входа.

Он создаёт `Deal`, только если на момент сканирования:

```text
Strategy active;
market data fresh;
MarketPhase подходит;
StrategyDetail выбрана;
ENTRY / GRID_ENTRY condition выполнен;
risk/invariant pre-checks не запрещают создание candidate Deal.
```

Но `EntryScannerJob` не гарантирует, что condition останется true до момента обработки `PRECHECK`.

Поэтому `PRECHECK` имеет право повторно проверить entry condition перед созданием live risk.

## Связь с entryReason / entryStepType

Если candidate Deal закрывается из-за устаревшего условия входа, его entry metadata остаётся полезной.

Пример:

```text
Deal.entryReason = STRATEGY
Deal.entryStepType = ENTRY
Deal.status = CLOSED
Deal.closeReason = ENTRY_CONDITION_EXPIRED
```

или:

```text
Deal.entryReason = STRATEGY
Deal.entryStepType = GRID_ENTRY
Deal.status = CLOSED
Deal.closeReason = ENTRY_CONDITION_EXPIRED
```

Это показывает:

```text
Deal был создан по strategy entry-step,
но вход не дошёл до live risk,
потому что condition устарел в PRECHECK.
```

# 7. Q7. Кто валидирует CLOSED после закрытия сделки

Статус: `DECIDED`

---

## Проблема

Изначальный вопрос был сформулирован так:

```text
Кто валидирует CLOSED после закрытия сделки?
```

Но такая формулировка неточная.

`CLOSED` — это terminal-статус.

Если сделка уже находится в `CLOSED`, обычная FSM больше не должна её сопровождать и периодически проверять через отдельный `ClosedHandler`.

Правильный вопрос:

```text
Где выполняется финальная проверка отсутствия live risk перед переводом сделки в terminal-статус?
```

---

## Финальное решение

Финальную проверку выполняет handler предыдущего нетерминального статуса.

Штатная ветка:

```text
EXIT_PENDING
  -> ExitPendingHandler
  -> финальная проверка закрытия и отсутствия live risk
  -> CLOSED
```

Аварийная ветка:

```text
ERROR
  -> ErrorHandler
  -> safety-flow / kill-switch
  -> финальная проверка отсутствия live risk
  -> EMERGENCY_CLOSED
```

`CLOSED` и `EMERGENCY_CLOSED` — terminal-статусы.

Для них отдельные FSM handlers не нужны.

---

## Правило по handlers

Для каждого нетерминального `Deal.Status` должен быть отдельный handler.

```text
PRECHECK            -> PrecheckHandler
ENTRY_SUBMITTED     -> EntrySubmittedHandler
ENTRY_FINALIZED     -> EntryFinalizedHandler
PROTECTION_SWITCHED -> ProtectionSwitchedHandler
MANAGING            -> ManagingHandler
EXIT_PENDING        -> ExitPendingHandler
ERROR               -> ErrorHandler
```

Для terminal-статусов handler не нужен:

```text
CLOSED              -> terminal, handler не нужен
EMERGENCY_CLOSED    -> terminal, handler не нужен
```

---

## CloseHandler переименовываем

`CloseHandler` переименовываем в:

```text
ExitPendingHandler
```

Причина:

```text
название handler должно соответствовать статусу сделки, который он обрабатывает.
```

`CloseHandler` звучит так, будто он работает со сделкой, которая уже находится в `CLOSED`.

Но по финальной модели закрывающая логика должна выполняться до terminal-статуса:

```text
EXIT_PENDING -> CLOSED
```

Поэтому корректное название:

```text
ExitPendingHandler
```

---

## Семантика EXIT_PENDING

`EXIT_PENDING` означает:

```text
решение о выходе уже принято,
но сделка ещё не закрыта окончательно.
```

На этом этапе нужно:

```text
закрыть позицию, если она ещё открыта;
отменить live ordinary orders;
отменить live algo-orders;
проверить attached protection;
загрузить fills/history;
обновить position/order/algo facts;
убедиться, что live risk отсутствует;
зафиксировать closeReason;
перевести Deal в CLOSED.
```

То есть `ExitPendingHandler` — это handler финализации штатного закрытия.

Он не сопровождает уже закрытую сделку.

---

## Семантика CLOSED

`CLOSED` означает:

```text
штатная ветка закрытия завершена;
позиция закрыта или отсутствует;
live ordinary orders отсутствуют;
live algo-orders отсутствуют;
attached protection больше не влияет на риск;
финальные факты подтверждены;
сделка больше не требует runtime-сопровождения FSM.
```

После перехода в `CLOSED` обычная FSM сделку не обрабатывает.

Если после `CLOSED` найден live risk, это не задача `ExitPendingHandler` и не задача отдельного `ClosedHandler`.

Это зона:

```text
AnomalyJob / ReconciliationJob
```

---

## Семантика ERROR

`ERROR` означает:

```text
обнаружена авария;
обычная strategy/FSM-логика заблокирована;
risk может быть живой;
нужен safety-flow / recovery / kill-switch.
```

`ErrorHandler` не выполняет обычные strategy steps.

Он выполняет только safety/recovery-логику:

```text
refresh facts;
cancel live orders;
cancel live algo-orders;
close position;
execute kill-switch;
verify no live risk;
перевести Deal в EMERGENCY_CLOSED, если risk снят и подтверждён.
```

---

## Семантика EMERGENCY_CLOSED

`EMERGENCY_CLOSED` означает:

```text
аварийный сценарий завершён;
kill-switch / safety-flow снял live risk;
отсутствие live risk подтверждено фактами;
сделка terminal, но не считается штатно закрытой.
```

После перехода в `EMERGENCY_CLOSED` обычная FSM сделку не сопровождает.

Если после `EMERGENCY_CLOSED` найден live risk, это глобальная аномалия.

---

## Инварианты перед CLOSED

`ExitPendingHandler` может перевести сделку:

```text
EXIT_PENDING -> CLOSED
```

только если подтверждено:

```text
1. Position закрыта или отсутствует.

2. Live ordinary orders отсутствуют.

3. Live algo-orders отсутствуют.

4. Attached protection отсутствует
   или больше не влияет на риск.

5. Нет pending orders, которые могут открыть или увеличить риск.

6. Fills/history загружены настолько,
   насколько нужно для финализации сделки.

7. closeReason определён.

8. Финальные exchange facts / refresh facts подтверждены.

9. Deal больше не требует runtime-сопровождения FSM.
```

Если хотя бы один пункт не подтверждён:

```text
сделка остаётся в EXIT_PENDING;
ExitPendingHandler продолжает refresh / cancel / close flow;
или переводит сделку в ERROR, если штатная финализация невозможна безопасно.
```

---

## Инварианты перед EMERGENCY_CLOSED

`ErrorHandler` может перевести сделку:

```text
ERROR -> EMERGENCY_CLOSED
```

только если подтверждено:

```text
1. Safety-flow / kill-switch выполнен или больше не требуется,
   потому что live risk уже отсутствует.

2. Position закрыта или отсутствует.

3. Live ordinary orders отсутствуют.

4. Live algo-orders отсутствуют.

5. Attached protection отсутствует
   или больше не влияет на риск.

6. Нет pending сущностей, которые могут создать или увеличить риск.

7. Финальные exchange facts подтверждены.

8. В аудите видна причина ERROR и действия safety-flow.

9. Сделка больше не требует runtime-сопровождения FSM.
```

Если хотя бы один пункт не подтверждён:

```text
сделка остаётся в ERROR;
ErrorHandler продолжает safety-flow;
или требуется ручной разбор.
```

---

## Зона AnomalyJob

Если по инструменту нет активных сделок, но на бирже есть live entities, это не зона FSM конкретной сделки.

Примеры:

```text
по инструменту нет активной Deal,
но на бирже есть live position;
```

```text
по инструменту нет активной Deal,
но на бирже есть live ordinary order;
```

```text
по инструменту нет активной Deal,
но на бирже есть live algo-order;
```

```text
Deal уже CLOSED,
но live risk снова найден;
```

```text
Deal уже EMERGENCY_CLOSED,
но live risk снова найден.
```

Это зона:

```text
AnomalyJob / ReconciliationJob
```

`AnomalyJob` должен:

```text
создать anomaly report;
зафиксировать exchange/internal snapshots;
при необходимости запустить kill-switch по инструменту;
заблокировать инструмент до разбора, если риск критичный.
```

---

## Почему не нужен ClosedHandler

`ClosedHandler` не нужен, потому что `CLOSED` — terminal-статус.

Если добавить handler для `CLOSED`, смешаются две ответственности:

```text
FSM сопровождение активной/закрывающейся сделки;
глобальная проверка аномалий после terminal-состояния.
```

Финальная проверка должна выполняться до перехода в `CLOSED`:

```text
ExitPendingHandler
  -> проверил отсутствие live risk
  -> поставил CLOSED
```

А всё, что найдено после `CLOSED`, относится к глобальной аномалии:

```text
AnomalyJob
```

---

## Почему не нужен EmergencyClosedHandler

`EMERGENCY_CLOSED` тоже terminal-статус.

Если аварийный risk уже снят и подтверждён, обычная FSM больше не должна сопровождать сделку.

Финальная проверка выполняется до перехода:

```text
ErrorHandler
  -> safety-flow / kill-switch
  -> проверил отсутствие live risk
  -> поставил EMERGENCY_CLOSED
```

Если после `EMERGENCY_CLOSED` снова найден live risk, это не продолжение FSM.

Это нарушение terminal-инварианта и зона `AnomalyJob`.

---

## Итоговое правило

```text
Финальную проверку закрытия выполняет handler предыдущего нетерминального статуса.

Штатная ветка:
  EXIT_PENDING -> ExitPendingHandler -> CLOSED

Аварийная ветка:
  ERROR -> ErrorHandler -> EMERGENCY_CLOSED

CloseHandler переименовываем в ExitPendingHandler.

Для terminal-статусов CLOSED и EMERGENCY_CLOSED отдельные FSM handlers не нужны.

Если по инструменту нет открытых сделок, но на бирже есть live entities,
или terminal-сделка снова имеет live risk,
это зона AnomalyJob / ReconciliationJob.
```

```text
   EXIT_PENDING -> ExitPendingHandler;
   ERROR -> ErrorHandler.

4. Указать, что CLOSED handler не нужен.

5. Указать, что EMERGENCY_CLOSED handler не нужен.

6. В ExitPendingHandler описать финальные проверки перед CLOSED.

7. В ErrorHandler описать финальные проверки перед EMERGENCY_CLOSED.
```

### Сервисные команды

Новые `ServiceCommandType` не требуются.

Для штатной финализации используются существующие команды:

```text

REFRESH_PENDING_ORDERS;
REFRESH_ALGO_ORDERS;
REFRESH_FILLS;
REFRESH_ORDER_HISTORY;
REFRESH_ALGO_ORDER_HISTORY;
CANCEL_ORDER;
CANCEL_ALGO_ORDER;

```

Для аварийной финализации используются существующие команды:

```text

REFRESH_ALGO_ORDERS;
REFRESH_FILLS;

CANCEL_ALGO_ORDER;
CLOSE_POSITION;
EXECUTE_KILL_SWITCH;
MARK_DEAL_ERROR;
финальная фиксация EMERGENCY_CLOSED.
```

В command-layer нужно только уточнить:

```text
MARK_DEAL_CLOSED относится к штатному CLOSED.
EMERGENCY_CLOSED фиксируется аварийным safety/finalization flow.
Новые ServiceCommandType на уровне Q7 не вводим.
```

### Аудит и история исполнения

Нужно обновить:

```text
1. Для CLOSED фиксировать штатную финализацию:
   - решение о выходе;
   - cancel/close commands;
   - финальные refresh/history facts;
   - closeReason;
   - переход EXIT_PENDING -> CLOSED.

2. Для EMERGENCY_CLOSED фиксировать аварийную финализацию:

   - финальные refresh/history facts;
   - переход ERROR -> EMERGENCY_CLOSED.

3. В отчётах отделять:
   CLOSED — штатный terminal-финал;
   EMERGENCY_CLOSED — аварийный terminal-финал.
```

### AnomalyJob / ReconciliationJob

Нужно учесть:

```text
1. Если по инструменту нет активной Deal, но на бирже есть live entities,
   это anomaly.

2. Если Deal terminal, но найден live risk,
   это anomaly.

3. AnomalyJob не является handler'ом Deal.Status.

4. AnomalyJob работает на уровне системных инвариантов,

```

# 8. Q8. Нужен ли отдельный ACKED-статус для command execution

Статус: `DECIDED`

---

## Проблема

В command-layer есть несколько разных уровней фактов:

```text
1. StrategyAction выбран стратегией / FSM.
2. Runtime-сущность создана локально в БД.
3. Команда отправки / изменения / отмены была выполнена или могла быть выполнена.
4. Биржа могла вернуть технический ACK.
5. Refresh / search / history подтвердили фактическое состояние.
```

Нужно решить:

```text
нужен ли отдельный ACKED-статус;
нужен ли CONFIRMED;
какой статус считать успешным terminal-состоянием action.
```

---

## Финальное решение

Фиксируем:

```text
ACKED не добавляем.
CONFIRMED не используем в DealActionStateStatus.
Успешный terminal-статус action — COMPLETED.
```

Финальный набор `DealActionStateStatus`:

```text
PLANNED
CREATED
SUBMITTED
COMPLETED
RETRY_PENDING
FAILED
SKIPPED
```

Главное правило:

```text
ACK от биржи не является runtime-truth для FSM.

Runtime-truth строится на refresh / search / history facts.

DealActionStateStatus.COMPLETED ставится только тогда,
когда refresh / search / history подтвердили нужный финальный факт по action.
```

---

## Зачем нужен DealActionState

`DealActionState` нужен FSM, чтобы понимать:

```text
какой StrategyAction уже начал выполняться;
какая runtime-сущность по нему создана;
можно ли продолжать;
нужно ли делать submit / refresh / retry;
action уже завершён, сломан или больше не нужен.
```

Стратегия содержит действия:

```text
StrategyStep
  -> StrategyAction
```

Но биржевые runtime-сущности не хранят `strategyActionId`:

```text
Order      не хранит strategyActionId
AlgoOrder  не хранит strategyActionId
Position   не хранит strategyActionId
```

Поэтому связь хранится отдельно:

```text
Deal + StrategyAction
  -> DealActionState
     -> RuntimeTarget(entityType, entityId)
```

Пример:

```text
Deal #100
StrategyAction #55 main-stop-loss
  -> DealActionState
       strategyActionId = 55
       target = RuntimeTarget(ALGO_ORDER, 777)
       status = COMPLETED
```

Смысл:

```text
action стратегии main-stop-loss материализован
в конкретный AlgoOrder #777,
и нужный финальный факт по нему подтверждён refresh/search/history.
```

---

## Финальная модель DealActionStateStatus

```java
public enum DealActionStateStatus {

    /**
     * Action запланирован, но runtime-сущность ещё не создана
     * и команда ещё не отправлялась.
     *
     * Обычно target = null.
     */
    PLANNED,

    /**
     * Локальная runtime-сущность создана в БД.
     *
     * Например:
     * - CREATE_ORDER создал Order;
     * - CREATE_ALGO_ORDER создал AlgoOrder.
     *
     * На этом этапе ещё нет подтверждённого факта на бирже.
     */
    CREATED,

    /**
     * Команда отправки / изменения / отмены была выполнена
     * или могла быть выполнена.
     *
     * Это не означает, что биржевой факт подтверждён.
     * После SUBMITTED всегда нужен refresh / search / history.
     *
     * Важный кейс:
     * если был timeout после отправки, мы не знаем,
     * дошёл запрос до биржи или нет.
     * Поэтому перед повтором нужно искать факт по clientOrderId / algoClOrdId.
     */
    SUBMITTED,

    /**
     * Action успешно завершён.
     *
     * Ставится только после refresh / search / history,
     * когда подтверждён нужный финальный факт.
     *
     * Это успешный terminal-статус action.
     */
    COMPLETED,

    /**
     * Action временно не выполнен, но будет повторён по retry policy.
     *
     * Например:
     * - сетевой сбой;
     * - timeout;
     * - временная ошибка биржи;
     * - неизвестный результат, который требует safe retry flow.
     */
    RETRY_PENDING,

    /**
     * Action не удалось выполнить после допустимого количества попыток
     * или ошибка неретраибельная.
     *
     * После FAILED FSM решает, что делать дальше:
     * - recovery;
     * - ERROR;
     * - safety-flow;
     * - kill-switch.
     */
    FAILED,

    /**
     * Action больше не нужен из-за изменения состояния сделки.
     *
     * Это не ошибка.
     *
     * Примеры:
     * - old attached protection уже отсутствует;
     * - order уже cancelled/filled;
     * - protection switch не требуется;
     * - step потерял смысл после refresh facts.
     */
    SKIPPED
}
```

---

## Почему не добавляем ACKED

`ACKED` означает только:

```text
биржа технически приняла запрос
или вернула успешный ответ на команду.
```

Но ACK не отвечает на вопросы:

```text
order реально active?
order уже filled?
order cancelled?
position появилась?
algo-order реально pending?
cancel действительно применился?
```

Вся runtime-политика проекта строится на refresh/search/history.

Поэтому:

```text
ACK не является runtime-truth.
ACK не должен двигать FSM дальше.
ACK не нужен как DealActionStateStatus.
```

На первом этапе ACK не обязательно хранить даже в `ServiceCommandExecutionHistory` отдельным полем.

Если позже понадобится диагностика, можно добавить:

```text
exchangeResponseSnapshot
rawExchangeResponse
exchangeAckSnapshot
```

Но это будет audit/debug-расширение, а не источник runtime-логики.

---

## Почему убираем CONFIRMED

Раньше рассматривалась модель:

```text
SUBMITTED -> CONFIRMED -> COMPLETED
```

Но при разборе выяснилось, что `CONFIRMED` и `COMPLETED` начинают дублировать друг друга.

Если refresh/search/history уже подтвердили нужный финальный факт, то для конкретного action больше не нужен отдельный промежуточный статус.

Поэтому упрощаем:

```text
SUBMITTED -> COMPLETED
```

Где:

```text
COMPLETED = refresh / search / history подтвердили нужный финальный факт по action.
```

---

## Что считается COMPLETED для разных action

### CREATE_ORDER

```text
PLANNED -> CREATED -> SUBMITTED -> COMPLETED
```

`COMPLETED` означает:

```text
Order создан локально;
отправка обработана;
refresh/search/history подтвердили нужный факт по order.
```

Например:

```text
order active;
order filled;
order cancelled;
order финализирован и позиция/история подтверждают результат.
```

Конкретный expected fact зависит от этапа FSM.

---

### CREATE_ALGO_ORDER

```text
PLANNED -> CREATED -> SUBMITTED -> COMPLETED
```

`COMPLETED` означает:

```text
AlgoOrder создан локально;
отправлен или найден на бирже;
refresh подтвердил нужное состояние.
```

Например для основной защиты:

```text
protective algo-order active/pending;
он соответствует ожидаемым параметрам;
он связан с нужной сделкой / инструментом / позицией.
```

---

### CANCEL_ORDER

```text
PLANNED -> SUBMITTED -> COMPLETED
```

`COMPLETED` означает:

```text
refresh/search/history подтвердили,
что ordinary order больше не live
или уже находится в допустимом terminal-состоянии.
```

---

### CANCEL_ALGO_ORDER

```text
PLANNED -> SUBMITTED -> COMPLETED
```

`COMPLETED` означает:

```text
refresh/search/history подтвердили,
что algo-order больше не live
или больше не влияет на риск.
```

---

### AMEND_ORDER / AMEND_ALGO_ORDER

```text
PLANNED -> SUBMITTED -> COMPLETED
```

`COMPLETED` означает:

```text
refresh/search/history подтвердили,
что runtime-сущность приведена к ожидаемому состоянию.
```

Если direct amend небезопасен или невозможен, это относится к отдельному вопросу про direct amend / safe replace.

---

### CLOSE_POSITION

```text
PLANNED -> SUBMITTED -> COMPLETED
```

`COMPLETED` означает:

```text
refresh/history подтвердили,
что position закрыта или размер позиции = 0.
```

---

## Пример: MAIN_PROTECTION на пальцах

Есть сделка:

```text
Deal.status = ENTRY_FINALIZED
```

Это значит:

```text
entry order исполнен;
позиция открыта;
нужно привести позицию к состоянию основной защиты.
```

В стратегии есть step:

```text
StrategyStepType = MAIN_PROTECTION
```

Важно:

```text
MAIN_PROTECTION — это не обязательно один action.
Это пакет actions, который должен привести защиту позиции к целевому состоянию.
```

Пример actions внутри step:

```text
Action A: create-main-protection
  -> создать standalone main protection

Action B: cancel-attached-protection
  -> отменить старую temporary attached protection
```

Конкретные actions берём из pinned `StrategyDetail`, а не придумываем в handler'е.

```text
EntryFinalizedHandler
  -> StrategyDetail.stepsByStatus[ENTRY_FINALIZED]
  -> StrategyStep MAIN_PROTECTION
  -> StrategyStep.actions
```

---

## Action A: создать основную защиту

```text
StrategyAlgoOrderAction key = create-main-protection
```

DealActionState:

```text
PLANNED
  -> action нужен, но runtime algo-order ещё не создан

CREATED
  -> локальный AlgoOrder создан в БД

SUBMITTED
  -> algo-order отправлен на биржу или мог быть отправлен

COMPLETED
  -> refresh/search/history подтвердили,
     что main protection active/pending и соответствует ожиданиям
```

Схема:

```text
StrategyAction create-main-protection
  -> DealActionState PLANNED
  -> CREATE_ALGO_ORDER
  -> DealActionState CREATED + RuntimeTarget(ALGO_ORDER, algoOrderId)
  -> SUBMIT_ALGO_ORDER
  -> DealActionState SUBMITTED
  -> REFRESH_ALGO_ORDERS / REFRESH_ALGO_ORDER
  -> DealActionState COMPLETED
```

---

## Action B: отменить старую attached protection

```text
StrategyAction key = cancel-attached-protection
```

Этот action тоже должен быть описан в стратегии, если стратегия хочет выполнять switch защиты.

Он не должен выполняться раньше, чем новая main protection стала безопасной.

Порядок контролирует `EntryFinalizedHandler`:

```text
если create-main-protection != COMPLETED
  -> cancel-attached-protection выполнять нельзя

если create-main-protection = COMPLETED
  -> можно выполнять cancel-attached-protection
```

DealActionState для cancel action:

```text
PLANNED
  -> action нужен, но cancel ещё не выполнялся

SUBMITTED
  -> команда cancel была выполнена или могла быть выполнена

COMPLETED
  -> refresh/search/history подтвердили,
     что attached protection больше не live
     или больше не влияет на риск
```

Если старой attached protection нет или её не нужно отменять:

```text
cancel-attached-protection -> SKIPPED
```

---

## Кто управляет порядком actions внутри step

Стратегия задаёт:

```text
что хотим сделать
```

Например:

```text
create-main-protection;
cancel-attached-protection.
```

FSM handler задаёт:

```text
когда это безопасно делать;
можно ли переходить дальше;
можно ли action считать SKIPPED;
нужно ли идти в ERROR / safety-flow.
```

То есть `EntryFinalizedHandler` не придумывает actions сам.

Он исполняет actions из стратегии, но применяет safety-order:

```text
сначала создать и подтвердить main protection;
только потом отменять temporary attached protection.
```

---

## Когда MAIN_PROTECTION step считается завершённым

`DealActionStateStatus.COMPLETED` относится к конкретному action.

Он не означает, что весь `StrategyStep` завершён.

`MAIN_PROTECTION step` считается завершённым уровнем handler'а, когда выполнены условия step-level:

```text
1. Все обязательные actions step имеют terminal-состояние:
   - COMPLETED;
   - или SKIPPED, если action больше не нужен.

2. Основная защита позиции active/pending и подтверждена refresh/search/history.

3. Temporary attached protection снята
   или больше не влияет на риск,
   если strategy-flow требовал switch.

4. Нет дублирующей конфликтующей защиты.

5. Позиция безопасна для дальнейшего сопровождения.
```

После этого handler решает, куда переводить `Deal`:

```text
ENTRY_FINALIZED -> PROTECTION_SWITCHED
```

если реально был switch защиты.

Или:

```text
ENTRY_FINALIZED -> MANAGING
```

если switch не нужен.

---

## Как это ложится на структуру проекта

Общая схема:

```text
StrategyStep MAIN_PROTECTION
  -> содержит StrategyAction list

EntryFinalizedHandler
  -> берёт actions из pinned StrategyDetail
  -> проверяет freshness через MarketDataExpirationChecker
  -> проверяет StrategyCondition
  -> для каждого action смотрит DealActionState
  -> вызывает StrategyActionCalculator
  -> создаёт ServiceCommand через ServiceCommandFactory

ServiceCommandExecutor
  -> выполняет CREATE / SUBMIT / REFRESH / CANCEL
  -> обновляет runtime-сущности Order / AlgoOrder / Position
  -> обновляет DealActionState

EntryFinalizedHandler
  -> проверяет step-level инварианты
  -> переводит Deal дальше
```

---

## Что не делает DealActionStateStatus

`DealActionStateStatus` не отвечает за:

```text
переход Deal.status;
решение, завершён ли весь StrategyStep;
выбор следующего StrategyStep;
расчёт цены / размера / риска;
исполнение REST-запроса;
аудит;
проверку глобальных аномалий.
```

За это отвечают другие слои:

```text
Deal.status transition
  -> FSM handler

StrategyStep completion
  -> FSM handler по facts/action states

Price/size/risk
  -> StrategyActionCalculator

REST/API execution
  -> ServiceCommandExecutor / concrete Executor

Audit/timeline
  -> ServiceCommandExecutionHistory / EntityHistory

Global anomalies
  -> AnomalyJob / ReconciliationJob
```

---

## Что делать с ServiceCommandExecutionHistory

На первом этапе ACK от биржи не обязателен как отдельная persisted-модель.

`ServiceCommandExecutionHistory` хранит минимальный технический результат команды:

```text
CREATED / IN_PROGRESS / SUCCESS / FAILED / RETRY_PENDING / SKIPPED
command payload snapshot;
result snapshot, если нужен;
RetryError, если была ошибка.
```

Raw exchange response / ACK можно добавить позже, если понадобится для диагностики.

Но runtime-логика не должна зависеть от raw ACK.

---

```text

  refresh / search / history подтвердили нужный финальный факт по action.

```

## Impact matrix

```text
6. Уточнить:
   raw ACK / exchange response можно добавить позже в историю,
   но на первом этапе это не обязательная persisted-модель.
```

### FSM этапы сделки

Нужно обновить:

```text
1. FSM не принимает переходы на основании ACK.

2. FSM считает action успешным только при DealActionStateStatus.COMPLETED.

3. Для step-level завершения handler проверяет:
   - обязательные actions COMPLETED;
   - ненужные actions SKIPPED;
   - runtime-сущности находятся в ожидаемом состоянии;
   - stage-level safety-инварианты выполнены.

4. В MAIN_PROTECTION описать:
   - actions берутся из стратегии;
   - create-main-protection и cancel-attached-protection — разные actions;
   - порядок выполнения контролирует EntryFinalizedHandler;
   - cancel old protection разрешён только после подтверждённой main protection.
```

### Жизненный цикл сделки

Нужно обновить:

# 9. Q9. ServiceCommand persisted entity или runtime object

> Статус: `DECIDED`
>
> Приоритет: `MUST_DECIDE_BEFORE_CODE`
>
> Финальное решение: `ServiceCommand` остаётся runtime object. Отдельную persisted-таблицу / durable queue для `ServiceCommand` на первом этапе не вводим.

---

# 1. Проблема

Нужно решить, чем является `ServiceCommand` в архитектуре управления сделкой:

```text
1. Runtime object, который создаётся FSM / ServiceCommandFactory и сразу передаётся executor'у.
2. Persisted entity, которая живёт в БД как очередь команд.
3. Гибридная модель, где часть команд runtime, а часть persisted.
```

От этого зависят:

```text
схема БД;
retry policy;
recovery после рестарта;
orchestration flow;
граница ответственности DealActionState;
будет ли у нас полноценная durable command queue;
как позже будет проектироваться история исполнения команд.
```

Ключевой вопрос:

```text
потеряем ли мы важное намерение системы после рестарта,
если ServiceCommand не хранится как отдельная persisted entity?
```

---

# 2. Финальное решение

Выбираем вариант:

```text
ServiceCommand = runtime object
```

`ServiceCommand` создаётся в памяти:

```text
FSM handler
  -> StrategyActionCalculator
  -> ServiceCommandFactory
  -> ServiceCommand
  -> ServiceCommandExecutor
  -> concrete Executor
```

В БД не создаём отдельную таблицу вида:

```text
service_command
```

и не делаем `ServiceCommand` durable queue.

Persisted runtime-state хранится в доменных сущностях:

```text
Deal;
DealActionState;
Order;
AlgoOrder;
Position;
BalanceContainer / BalanceSnapshot, если нужен.
```

Persisted audit/history будет проектироваться отдельно в документе `05. Аудит и история исполнения`.

На уровне Q9 фиксируем только принцип:

```text
история исполнения команд и история изменений сущностей не являются источником runtime-логики FSM.
```

Точную модель истории в Q9 не проектируем.

---

# 3. Главное правило

```text
ServiceCommand не является источником recovery.
```

Источник recovery:

```text
DealContext
DealActionState
Order / AlgoOrder / Position / BalanceContainer
exchange snapshots
refresh/search/history facts
```

После рестарта FSM не ищет pending `ServiceCommand`.

После рестарта FSM делает так:

```text
1. DealOrchestratorJob находит активные Deal.
2. Загружает DealContext.
3. FSM handler смотрит Deal.status.
4. Handler анализирует DealActionState.
5. Handler анализирует runtime-сущности Order / AlgoOrder / Position.
6. При необходимости создаёт refresh-команды.
7. После refresh/search/history фактов создаёт новую runtime ServiceCommand,
   если действие всё ещё актуально.
```

---

# 4. Почему ServiceCommand можно не хранить

`ServiceCommand` не должен быть единственным носителем намерения.

Намерение должно быть восстановимо из:

```text
Deal.status;
pinned StrategyDetail;
StrategyStep;
StrategyAction;
DealActionState.status;
DealActionState.target;
Order / AlgoOrder / Position;
exchange facts.
```

Если команда была создана в runtime, но приложение упало до выполнения, после рестарта FSM снова увидит то же состояние и снова создаст нужную runtime-команду.

Пример:

```text
FSM выбрала StrategyAction create-main-protection
ServiceCommandFactory создала CREATE_ALGO_ORDER
приложение упало до исполнения
```

После рестарта:

```text
Deal.status = ENTRY_FINALIZED
DealActionState отсутствует или PLANNED
AlgoOrder ещё нет
```

FSM снова поймёт:

```text
MAIN_PROTECTION step нужен;
create-main-protection ещё не материализован;
нужно снова создать CREATE_ALGO_ORDER.
```

Потеря runtime-команды не приводит к потере бизнес-намерения.

---

# 5. Почему не persisted ServiceCommand

Persisted `ServiceCommand` фактически превращает command-layer в очередь.

Это сразу добавляет новые вопросы:

```text
кто создаёт command-row;
кто забирает command-row на исполнение;
как блокировать конкурентное исполнение;
как хранить статус команды;
как отличать command status от DealActionState status;
как переисполнять команду после рестарта;
как не выполнить опасную биржевую команду дважды;
как связать command queue с FSM transition;
как чистить старые команды;
как отличить историю команды от самой команды.
```

Для первой версии это избыточно.

У нас уже есть более правильный источник восстановления:

```text
DealActionState + runtime-сущности + exchange facts.
```

Если добавить persisted `ServiceCommand`, появится дублирование статусов:

```text
ServiceCommand.status
DealActionState.status
Order / AlgoOrder / Position.status
future command execution history status
```

Это усложнит модель и создаст риск рассинхрона.

---

# 6. Что именно хранится для runtime recovery

## 6.1. DealActionState

`DealActionState` — операционное состояние action стратегии.

Он нужен FSM для восстановления после рестарта.

Он отвечает на вопросы:

```text
action уже начинали выполнять или нет;
action материализован в Order / AlgoOrder / Position или нет;
какая runtime-сущность является target;
нужен ли retry;
можно ли продолжать выполнение;
action completed / skipped / failed.
```

Ключевой инвариант:

```text
UNIQUE(deal_id, strategy_action_id)
```

Важно:

```text
DealActionState — это не аудит.
DealActionState — это operational state для FSM.
```

## 6.2. Runtime-сущности

FSM и executor'ы опираются на фактическое состояние runtime-сущностей:

```text
Order
AlgoOrder
Position
BalanceContainer
```

`Order`, `AlgoOrder`, `Position` остаются чистыми биржевыми сущностями.

В них не храним:

```text
strategyActionId
strategyActionKey
role стратегии
level стратегии
```

Связь action стратегии с runtime-сущностью хранится отдельно:

```text
DealActionState.strategyActionId
DealActionState.target
```

## 6.3. Exchange facts

После рестарта или неизвестного результата команды FSM должна опираться на факты:

```text
REFRESH_ORDER
REFRESH_PENDING_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_POSITION
REFRESH_FILLS
REFRESH_ALGO_ORDER
REFRESH_ALGO_ORDERS
REFRESH_ALGO_ORDER_HISTORY
```

И только после этого решать, нужна ли новая runtime-команда.

---

# 7. Как выглядит runtime ServiceCommand

`ServiceCommand` остаётся простым объектом:

```java
public class ServiceCommand {

    /** Тип атомарной операции. */
    private ServiceCommandType type;

    /** Сделка, в рамках которой выполняется команда. */
    private Long dealId;

    /** Runtime-состояние action стратегии, если команда связана с action. */
    private Long dealActionStateId;

    /** Параметры выполнения команды. */
    private ServiceCommandPayload payload;
}
```

Он может быть создан много раз в разных проходах FSM.

Это нормально, потому что безопасность обеспечивается не идентичностью объекта `ServiceCommand`, а:

```text
DealActionState;
clientOrderId / algoClOrdId;
local entity state;
exchange lookup before submit/amend/cancel;
idempotent executor logic;
refresh/search/history facts.
```

---

# 8. Retry policy после решения Q9

Retry не хранится как pending `ServiceCommand`.

Retry хранится в `DealActionState`, потому что retry относится к выполнению action стратегии.

Flow retry:

```text
1. Executor попытался выполнить runtime ServiceCommand.
2. Команда завершилась retryable-ошибкой.
3. DealActionState.status = RETRY_PENDING.
4. DealActionState.attemptCount увеличивается.
5. DealActionState.nextRetryAt выставляется по retry policy.
6. После nextRetryAt DealOrchestratorJob снова берёт Deal.
7. FSM заново анализирует факты.
8. Если action всё ещё нужен — создаётся новая runtime ServiceCommand.
```

Важно:

```text
Retry = повторить business/action flow после проверки фактов,
а не переисполнить старый serialized ServiceCommand из БД.
```

История retry-попыток будет отдельно детализироваться в документе `05. Аудит и история исполнения`.

---

# 9. Recovery после рестарта

## 9.1. Общий алгоритм

После рестарта:

```text
DealOrchestratorJob
  -> загружает активные Deal
  -> собирает DealContext
  -> запускает FSM handler
```

FSM handler смотрит:

```text
Deal.status;
DealActionState;
Order / AlgoOrder / Position;
BalanceContainer;
exchange facts после refresh;
```

Если видит, что действие было начато, но результат неизвестен, handler не ищет старую команду.

Он создаёт refresh / search flow:

```text
REFRESH_ORDER
REFRESH_PENDING_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_POSITION
REFRESH_FILLS
REFRESH_ALGO_ORDER
REFRESH_ALGO_ORDERS
REFRESH_ALGO_ORDER_HISTORY
```

После refresh/search/history фактов FSM решает:

```text
action уже выполнен -> DealActionState.COMPLETED
action не выполнен, но всё ещё нужен -> создать новую runtime ServiceCommand
action больше не нужен -> DealActionState.SKIPPED
action опасен / facts противоречат -> ERROR / kill-switch
```

## 9.2. Кейс: команду сгенерировали, но не успели выполнить

```text
FSM выбрала action
-> ServiceCommandFactory создала runtime ServiceCommand
-> приложение упало до исполнения
```

После рестарта FSM не ищет старую команду.

Она снова собирает `DealContext` и смотрит persisted state:

```text
Deal.status;
DealActionState;
runtime-сущности;
exchange facts.
```

Если действие всё ещё актуально, FSM снова создаст runtime `ServiceCommand`.

Итог:

```text
потеря runtime ServiceCommand безопасна,
если бизнес-намерение восстановимо из persisted state.
```

## 9.3. Кейс: CREATE_* выполнили локально, но упали до SUBMIT_*

Пример:

```text
CREATE_ALGO_ORDER
-> AlgoOrder создан в БД
-> DealActionState.target = RuntimeTarget(ALGO_ORDER, algoOrderId)
-> DealActionState.status = CREATED
-> приложение упало
```

После рестарта:

```text
DealActionState.status = CREATED;
DealActionState.target = ALGO_ORDER #777;
AlgoOrder существует локально;
```

FSM понимает:

```text
локальная runtime-сущность уже создана;
нужно продолжить с SUBMIT_ALGO_ORDER.
```

Обязательное правило:

```text
CREATE_* должен сохранять runtime-сущность и DealActionState в одной транзакции.
```

Итог:

```text
безопасно.
```

## 9.4. Кейс: SUBMIT_* отправили на биржу, но упали до сохранения результата

Это самый важный recovery-кейс.

```text
SUBMIT_ALGO_ORDER
-> запрос ушёл на OKX
-> OKX могла создать algo-order
-> приложение упало до сохранения externalId / статуса
```

После рестарта нельзя слепо отправлять второй раз.

Правильный recovery:

```text
1. Локальный AlgoOrder уже есть.
2. У него есть стабильный internalId / algoClOrdId.
3. Перед повторным submit делаем search/refresh на бирже по algoClOrdId.
4. Если algo-order найден:
   - обновляем локальный AlgoOrder из exchange snapshot;
   - DealActionState переводим дальше по фактам.
5. Если algo-order не найден:
   - можно безопасно повторить SUBMIT_ALGO_ORDER.
```

Для ordinary order аналогично:

```text
Order.internalId -> clOrdId
```

Для algo-order:

```text
AlgoOrder.internalId -> algoClOrdId
```

Итог:

```text
безопасно, если у каждой биржевой сущности есть стабильный client id.
```

## 9.5. Кейс: ACK получили, но refresh ещё не делали

```text
OKX вернула success / ordId / algoId
```

Это ещё не runtime-truth для FSM.

После ACK всё равно нужен refresh/search/history:

```text
REFRESH_ORDER;
REFRESH_PENDING_ORDERS;
REFRESH_ORDER_HISTORY;
REFRESH_ALGO_ORDERS;
REFRESH_ALGO_ORDER_HISTORY;
REFRESH_POSITION;
REFRESH_FILLS.
```

`DealActionState` становится `COMPLETED` только после refresh/search/history, когда подтверждён нужный финальный факт.

Итог:

```text
ACK не требует persisted ServiceCommand.
```

## 9.6. Кейс: REFRESH_* сгенерировали, но упали

```text
FSM решила сделать REFRESH_ALGO_ORDERS
-> приложение упало до вызова
```

После рестарта refresh можно создать снова.

Refresh-команды безопасны:

```text
они не создают новый риск;
они читают truth с биржи;
они помогают восстановить локальное состояние.
```

Итог:

```text
безопасно.
```

## 9.7. Кейс: CANCEL_* отправили, но упали до сохранения результата

```text
CANCEL_ALGO_ORDER
-> запрос ушёл на биржу
-> приложение упало
```

После рестарта нельзя считать, что cancel не было.

Правильный recovery:

```text
1. Сначала REFRESH_ALGO_ORDERS / history.
2. Если algo-order уже не live:
   - cancel action -> COMPLETED.
3. Если algo-order ещё live:
   - можно повторить CANCEL_ALGO_ORDER.
4. Если состояние неизвестно:
   - retry через safe refresh/search flow.
```

Итог:

```text
безопасно, если перед повтором CANCEL_* всегда делается refresh/search/history.
```

## 9.8. Кейс: CLOSE_POSITION отправили, но упали

`CLOSE_POSITION` разрешаем только для полного закрытия позиции.

```text
CLOSE_POSITION
-> запрос ушёл на биржу
-> приложение упало
```

После рестарта:

```text
1. Сначала REFRESH_POSITION.
2. Если position size = 0 или position отсутствует:
   - close action -> COMPLETED;
   - можно идти к финализации.
3. Если position всё ещё открыта:
   - можно повторять close по текущему факту.
4. Если состояние противоречиво:
   - ERROR / safety-flow.
```

Для полного закрытия итоговый факт простой:

```text
position отсутствует
или
position size = 0
```

Итог:

```text
безопасно.
```

# 10. Команды, которые не связаны со StrategyAction

Не все команды инициируются стратегией.

Примеры:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_BALANCE
REFRESH_FILLS
EXECUTE_KILL_SWITCH
MARK_DEAL_ERROR
FINALIZE_DEAL_EXIT
MARK_DEAL_CLOSED
```

Для таких команд:

```text
dealActionStateId = null
```

Они всё равно могут исполняться через общий `ServiceCommandExecutor`.

Как именно они будут отражаться в истории исполнения — отдельный вопрос документа `05. Аудит и история исполнения`.

---

# 11. Как это влияет на ServiceCommandFactory

`ServiceCommandFactory` не сохраняет команды в БД.

Он делает только:

```text
StrategyAction / CalculatedStrategyAction
  -> runtime ServiceCommand
```

Или для системных команд:

```text
FSM / handler decision
  -> runtime ServiceCommand
```

`ServiceCommandFactory` не должен:

```text
создавать command-row;
управлять очередью;
выбирать pending commands;
делать retry scheduling;
читать историю исполнения команд для runtime-решений.
```

---

# 12. Как это влияет на ServiceCommandExecutor

`ServiceCommandExecutor` принимает runtime `ServiceCommand`.

Он отвечает за:

```text
выбрать concrete Executor по ServiceCommandType;
передать payload;
обработать результат;
обновить DealActionState, если команда связана с action;
вернуть результат FSM / orchestrator.
```

Запись истории исполнения команд — отдельная зона проектирования документа `05. Аудит и история исполнения`.

На уровне Q9 фиксируем только ограничение:

```text
ServiceCommandExecutor не должен быть worker'ом durable command queue.
```

`ServiceCommandExecutor` не должен:

```text
искать команды в БД;
сам принимать торговые решения;
сам выбирать следующий Deal.status.
```

---

# 13. Что будет, если позже понадобится durable queue

Durable queue можно добавить позже отдельным слоем.

Например:

```text
CommandOutbox
CommandQueue
AsyncCommandTask
```

Но это будет отдельное архитектурное решение.

Текущая модель не блокирует такой переход, потому что:

```text
ServiceCommand уже имеет type + payload;
DealActionState уже хранит recovery state;
executors уже должны быть идемпотентными.
```

Но на первом этапе durable queue не вводим.

---

# 14. Важное уточнение: частичное закрытие позиции

Прямое частичное закрытие позиции через `CLOSE_POSITION` не используем вообще.

Причина:

```text
частичный close сложнее безопасно восстановить после падения;
можно случайно закрыть больше, чем планировалось;
нужна точная привязка к конкретной runtime-сущности и fills.
```

Пример проблемы:

```text
position size = 10 contracts
хотели закрыть 30% = 3 contracts
запрос ушёл на биржу
приложение упало

после рестарта непонятно:
  закрыли 3 или нет;
  был ли partial fill;
  можно ли повторять;
  не закроем ли ещё 30% от остатка.
```

Поэтому:

```text
StrategyPositionAction.CLOSE_PARTIAL запрещён как постоянный инвариант стратегии и системы.
```

Частичный выход должен быть выражен через трассируемую runtime-сущность:

```text
StrategyOrderAction reduce-only;
или StrategyAlgoOrderAction partial TP / reduce-only semantics.
```

То есть:

```text
partial take profit
  -> StrategyAlgoOrderAction

risk reduction by partial reduce
  -> StrategyOrderAction reduceOnly

grid partial exit
  -> StrategyOrderAction / StrategyAlgoOrderAction

phase degradation partial reduce
  -> StrategyOrderAction / StrategyAlgoOrderAction
```

Такой action материализуется в:

```text
Order / AlgoOrder
  -> stable client id
  -> DealActionState
  -> fills/history/refresh
```

И после рестарта можно понять, что реально произошло.

## 14.1. Обновлённое правило по StrategyPositionAction

`StrategyPositionAction` поддерживает только полное закрытие позиции.

```java
public class StrategyPositionAction extends Auditable implements StrategyAction {

    /**
     * Стабильный ключ action внутри StrategyDetail.
     */
    private String key;

    /**
     * Только CLOSE_FULL.
     */
    private StrategyActionType actionType;

    /**
     * Уровень действия.
     */
    private Integer level;
}
```

Для `StrategyPositionAction` разрешён только:

```text
CLOSE_FULL
```

Запрещаем:

```text
CLOSE_PARTIAL
```

Финальное решение:

```text
CLOSE_PARTIAL не поддерживается как direct position action.
Это постоянный инвариант стратегии и приложения, а не временное ограничение первого этапа.
```

## 14.2. Валидация стратегии при создании

На этапе создания стратегии нужно валидировать намерение частично уменьшить позицию.

Правила:

```text
1. StrategyPositionAction.actionType = CLOSE_PARTIAL запрещён.

2. Любое частичное уменьшение позиции должно быть выражено через:
   - StrategyOrderAction;
   - или StrategyAlgoOrderAction.

3. Такой action должен материализоваться в persisted Order / AlgoOrder.

4. У action должен быть stable client id через runtime-сущность:
   - Order.internalId -> clOrdId;
   - AlgoOrder.internalId -> algoClOrdId.

5. Action должен иметь reduce-only semantics,
   если он уменьшает позицию.

6. Размер или доля закрытия должны быть явно заданы:
   - closeFractionPercents;
   - или allocationPercents;
   - или рассчитанный sizeContracts.

7. Action не должен увеличивать позицию.

8. Recovery должен быть возможен через:
   DealActionState -> RuntimeTarget -> Order/AlgoOrder -> fills/history/refresh.
```

Если стратегия пытается создать прямой partial position action:

```text
validation error:
CLOSE_PARTIAL as direct position action is not supported.
Use reduce-only StrategyOrderAction or StrategyAlgoOrderAction.
```

## 14.3. Что считается persisted state при runtime-only ServiceCommand

Так как `ServiceCommand` не хранится как pending entity, критичные намерения должны материализоваться в persisted state.

Для разных типов action это означает:

```text
CREATE_ORDER
  -> Order + DealActionState

CREATE_ALGO_ORDER
  -> AlgoOrder + DealActionState

AMEND_ORDER / CANCEL_ORDER
  -> target Order через DealActionState target action

AMEND_ALGO_ORDER / CANCEL_ALGO_ORDER
  -> target AlgoOrder через DealActionState target action

CLOSE_POSITION full
  -> Position + DealActionState + refresh facts

PARTIAL_EXIT
  -> не CLOSE_POSITION;
  -> Order/AlgoOrder + DealActionState + fills/history/refresh
```

# 11. Q11. AMEND_ALGO_ORDER: direct amend или safe replace

Статус: `OPEN`

Приоритет: `MUST_DECIDE_BEFORE_CODE`

## Почему вопрос актуален

Для изменения protective algo-order есть два принципиально разных механизма:

```text
direct amend
или
safe replace
```

Для protection-сценариев важно не потерять активную защиту позиции.

## Документы, которых касается

* `02. Сервисные команды`
* `FSM этапы сделки`
* `03. Калькуляторы действий стратегии`
* `05. Аудит и история исполнения`

## Варианты

### Вариант A. Direct amend основной механизм

Плюсы:

* проще;
* меньше команд;
* меньше REST-вызовов.

Минусы:

* может быть ограничено биржей;
* если amend дал неизвестный результат, нужна осторожная проверка;
* для защиты позиции direct amend может быть менее безопасен.

### Вариант B. Safe replace основной механизм для protection

```text
1. Создать новый protective algo-order.
2. Подтвердить, что он active.
3. Отменить старый protective algo-order.
```

Плюсы:

* старую защиту не снимаем до подтверждения новой;
* безопаснее для позиции.

Минусы:

* больше команд;
* временно может быть дублирующая защита;
* сложнее recovery.

### Вариант C. Direct amend по умолчанию, safe replace для protection / небезопасных типов

Плюсы:

* гибко;
* не усложняем все сценарии.

Минусы:

* нужна policy выбора механизма.

## Предварительная рекомендация

Для защитных algo-orders безопаснее:

```text
Вариант B или C.
```

Минимально разумно:

```text
direct amend допустим для безопасных сценариев;
safe replace обязателен там, где есть риск потерять protection.
```

## Impact matrix

### Сервисные команды

```text
Описать execution policy для AMEND_ALGO_ORDER.
Если safe replace выбран для protection, описать create-confirm-cancel flow.
```

### FSM этапы сделки

```text
Recovery должен понимать временное состояние с двумя protection algo-orders.
Старую protection нельзя отменять до подтверждения новой.
```

### Калькуляторы действий стратегии

```text
Калькулятор считает параметры новой защиты одинаково,
независимо от direct amend или safe replace.
Различается command-layer flow.
```

### Аудит и история исполнения

```text
Timeline должен показывать, что protection была заменена безопасно:
new protection created -> confirmed -> old protection cancelled.
```

* runtime остаётся безопасным.

Минусы:

### Вариант B. Хранить только explanation/result

Плюсы:

```text
Вариант C.
```

# 16. Q16. Ошибки калькуляторов: exception или error-result

Статус: `OPEN`

Приоритет: `MUST_DECIDE_BEFORE_CODE`

## Почему вопрос актуален

Калькуляторы могут не рассчитать action из-за контролируемых причин:

```text
нет свежей цены;
нет ATR;
нет MarketStructure;
не хватает баланса;
размер меньше minSz;
risk выше лимита.
```

Нужно решить формат возврата ошибки.

## Документы, которых касается

* `03. Калькуляторы действий стратегии`
* `FSM этапы сделки`
* `05. Аудит и история исполнения`

## Варианты

### Вариант A. Бросать controlled exception

Плюсы:

* проще код;
* быстро прерывает flow.

Минусы:

* исключения могут смешать expected business rejection и technical failure.

### Вариант B. Возвращать error-result

Пример:

```java
CalculatedStrategyActionResult {
    boolean success;
    CalculatedStrategyAction value;
    CalculationError error;
}
```

Плюсы:

* хорошо для expected rejection;
* удобно для аудита.

Минусы:

* больше boilerplate.

### Вариант C. Комбинированный подход

```text
expected/domain rejection -> error-result;
technical unexpected failure -> exception.
```

Плюсы:

* разделяет бизнес-отказ и техническую ошибку.

Минусы:

* нужно строго описать границу.

## Предварительная рекомендация

```text
Вариант C.
```
