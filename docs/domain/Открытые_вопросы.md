# 1. Статусы вопросов

```text
OPEN        — вопрос ещё не обсуждали или решение не принято.
DECIDED     — решение принято, но ещё не внесено во все затронутые документы.
APPLIED     — решение внесено во все затронутые документы.
POSTPONED   — вопрос осознанно отложен до реализации / интеграционных тестов / live-прогона.
OBSOLETE    — вопрос больше не актуален из-за уже принятого решения или переименования модели.
```

---

# 2. Приоритеты вопросов

```text
MUST_DECIDE_BEFORE_CODE
  Нужно решить до реализации, иначе будет сложно правильно спроектировать модели / статусы / таблицы / flow.

CAN_USE_DEFAULT
  Можно выбрать простой дефолт сейчас и изменить позже без сильной ломки архитектуры.

POSTPONE_TO_IMPLEMENTATION
  Лучше не решать заранее. Решение зависит от деталей реализации, API биржи, тестов или UI.
```

# 5. Q1. `AMEND_ALGO_ORDER`: direct amend или safe replace для protection-сценариев

Статус: `OPEN`

Приоритет: `MUST_DECIDE_BEFORE_CODE`

## Почему вопрос критичный

Для защитных algo-orders важно не потерять активную защиту позиции.

Есть два механизма:

```text
direct amend;
safe replace: create new protection -> confirm active -> cancel old protection.
```

## Что нужно решить

```text
1. Разрешаем ли direct amend для protective algo-orders.
2. Когда обязателен safe replace.
3. Как FSM должна жить во временном состоянии с двумя protection orders.
4. Как не снять старую защиту до подтверждения новой.
```

```text
FSM этапы сделки
```

# 6. Q2. `ServiceCommandFactory`: создавать цепочку команд сразу или по одной

Статус: `OPEN`

Приоритет: `MUST_DECIDE_BEFORE_CODE`

## Почему вопрос критичный

Для операций есть логическая цепочка:

```text
CREATE_ORDER -> SUBMIT_ORDER -> REFRESH_ORDER
CREATE_ALGO_ORDER -> SUBMIT_ALGO_ORDER -> REFRESH_ALGO_ORDER
```

После Q9 `ServiceCommand` — runtime object, поэтому особенно важно решить, создаём ли исполняемые команды по одной или заранее строим command plan.

## Предварительная рекомендация

```text
Создавать следующую команду после результата предыдущей.
```

Причина:

```text
каждая команда создаётся по актуальным фактам;
проще recovery;
не нужен persisted command queue.
```

## Документы, которых касается

```text
02. Сервисные команды
FSM этапы сделки
01. Жизненный цикл сделки
```

# 7. Q3. Разделять ли `UNKNOWN_RESULT` и `EXCHANGE_TIMEOUT`

Статус: `OPEN`

Приоритет: `CAN_USE_DEFAULT`

## Почему вопрос актуален

Для обеих ситуаций runtime safe retry чаще всего одинаковый:

```text
1. Сначала refresh/search на бирже.
2. Потом повтор только если факт не найден.
```

## Варианты

```text
A. Оставить оба типа ошибок.
B. Объединить в UNKNOWN_RESULT.
C. Оставить оба, но дать им одинаковую safe retry policy.
```

## Предварительная рекомендация

```text
Вариант C.
```

Диагностику сохраняем, runtime logic не усложняем.

```text
02. Сервисные команды
05. Аудит и история исполнения
```

# 9. Q5. Ошибки калькуляторов: exception или error-result

Статус: `OPEN`

Приоритет: `MUST_DECIDE_BEFORE_CODE`

## Почему вопрос критичный

Калькуляторы могут не рассчитать action по ожидаемым причинам:

```text
нет свежей цены;
нет ATR;
нет MarketStructure;
не хватает баланса;
размер меньше minSz;
risk выше лимита;
partial exit не reduce-only.
```

## Предварительная рекомендация

```text
expected/domain rejection -> error-result;
technical unexpected failure -> exception.
```
