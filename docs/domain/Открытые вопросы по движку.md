# Открытые вопросы по движку

> Статус документа: рабочий список вопросов по runtime-движку.
>
> Вопросы по аудиту, истории исполнения и timeline сделки сюда пока не включаем.
> Их будем разбирать отдельно, когда дойдём до документа `05. Аудит и история исполнения`.

---

# 1. Active / Closed semantics по runtime-сущностям

Нужно финализировать единые правила, какие сущности считаются active/live, а какие closed/inactive.

Затрагивает:

```text
Order
AlgoOrder
AttachedAlgoOrder
Position
Deal
BalanceContainer / BalanceSnapshot
```

Зачем нужно:

```text
RefreshExecutor
ExitPendingHandler
ErrorHandler
KillSwitchService
AnomalyJob
DealContextService
```

Ключевой вопрос:

```text
как в одном месте определить: есть live risk или нет?
```

---

# 2. ErrorHandler / safety-flow после Deal.ERROR

Q8 зафиксировал, что при критичных unexpected exceptions или blocking risk после live-risk этапов сделка переходит в `ERROR`.

Нужно детально расписать `ErrorHandler`:

```text
какие refresh-команды запускает первым;
как определяет live risk;
в каком порядке отменяет orders/algo-orders;
когда вызывает CLOSE_POSITION;
когда использует EXECUTE_KILL_SWITCH;
когда можно перейти ERROR -> EMERGENCY_CLOSED;
когда оставаться в ERROR.
```

# 3. AnomalyJob / ReconciliationJob и границы с DealOrchestratorJob

Базовое решение уже есть:

```text
DealOrchestratorJob ведёт известные сделки по FSM.
AnomalyJob ищет глобальные нарушения системных инвариантов.
```

Но нужно точнее расписать политики:

```text
какие аномалии считаются critical;
когда блокируется инструмент;
когда запускается kill-switch;
когда AnomalyJob только пишет report;
как AnomalyJob не конфликтует с DealOrchestratorJob;
что делать с чужими live orders/algo-orders;
что делать, если terminal Deal имеет live risk.
```

# 4. Порядок выполнения нескольких actions внутри одного StrategyStep

Q4 зафиксировал:

```text
ServiceCommandFactory создаёт одну актуальную команду,
а не всю цепочку команд заранее.
```

Нужно детально расписать runtime-порядок:

```text
как сортируются actions;
как используется level;
можно ли выполнять следующий action, если предыдущий RETRY_PENDING;
что делать, если один action BLOCKED risk result;
что делать, если один action TEMPORARY calculation error;
как работает step с 4 TP / grid orders;
как избежать частичного выполнения опасного набора actions.
```

# 5. Refresh baseline для каждого FSM-статуса

Мы договорились, что каждый проход FSM опирается на свежие exchange facts.

Нужно формализовать:

```text
какие refresh-команды обязательны для PRECHECK;
какие для ENTRY_SUBMITTED;
какие для ENTRY_FINALIZED;
какие для PROTECTION_SWITCHED;
какие для MANAGING;
какие для EXIT_PENDING;
какие для ERROR;
какие refresh можно пропустить из-за свежести локального snapshot;
какие refresh обязательны перед retry опасной команды.
```

Цель:

```text
не перегружать биржу лишними запросами,
но не принимать runtime-решения по устаревшим фактам.
```

# 6. Protection policy: когда защита обязательна

Уже зафиксировано:

```text
PROTECTION_SWITCHED используется только если реально нужен switch.
PROTECTION_ESTABLISHED отдельно не вводим.
```

Но нужно отдельно решить:

```text
кто определяет, что позиция достаточно защищена;
может ли StrategyDetail разрешить сопровождение без standalone protection;
какая минимальная защита обязательна после entry;
когда attached protection достаточно;
когда main protection обязательна;
что делать, если защита временно потеряна в MANAGING.
```

Нужно собрать единый validation matrix для создания стратегии:

```text
key / targetActionKey;
совместимость actionType и action kind;
запрет direct partial close;
reduce-only для partial exit;
обязательные price settings;
обязательные indicator / market structure settings;
marketDataExpiredSetting для каждого step;
expirationDuration для используемых settings;
совместимость StrategyStepType и Deal.Status;
валидность phaseEntryPolicy;

```

Результат должен быть пригоден для реализации `StrategyValidator`.

# 11. CalculationError policy: финальный каталог controlled errors

Q3 зафиксировал общий подход:

```text
controlled calculation errors -> error-result;
unexpected exceptions -> INTERNAL_ERROR / EXCHANGE_ERROR / VALIDATION_ERROR.
```

Нужно отдельно собрать каталог controlled calculation errors:

```text
TEMPORARY;
PERMANENT;
какие коды относятся к market data delay;
какие коды относятся к missing indicator;
какие коды относятся к invalid calculated price;
какие коды относятся к missing position facts;
какие retry policy для TEMPORARY;
когда после retry переводить Deal в ERROR.
```
