# 05. Аудит и история исполнения

> Статус документа: каркас.
>
> Эта дока пока не финализирована.
>
> Здесь зафиксированы только текущие договорённости и вопросы, которые нужно прояснить.

---

# 1. Главная идея

Аудит и история исполнения нужны для объяснения:

* какая команда была создана;
* почему она была создана;
* какая стратегия/action к этому привели;
* какая runtime-сущность была создана или изменена;
* какой был snapshot до изменения;
* какой стал snapshot после изменения;
* чем закончилась команда;
* были ли ошибки и retry.

Главное правило:

> Аудит не является источником runtime-логики FSM.
>
> FSM не должна читать историю, чтобы решить, что делать дальше.

Для runtime-восстановления используется:

```text
DealContext
DealActionState
Order / AlgoOrder / Position
Exchange snapshots
```

Для объяснения прошлого используется:

```text
ServiceCommandExecutionHistory
EntityHistory
```

---

# 2. Что уже договорились

## 2.1. Биржевые сущности остаются чистыми

В `Order`, `AlgoOrder`, `Position` не храним:

```text
strategyActionId
role
level стратегии
```

Причина:

* биржевая сущность может меняться несколько раз за сделку;
* один order/algo-order может быть создан, изменён, отменён, восстановлен;
* связь с action стратегии — это история изменений, а не постоянное поле биржевой сущности.

---

## 2.2. Runtime-связь хранится в DealActionState

Для runtime-логики используется `DealActionState`.

Он отвечает на вопрос:

> Какое действие стратегии уже материализовано в какую runtime-сущность?

Это не аудит.

Это operational state для FSM.

---

## 2.3. Аудит хранит цепочку фактов

Аудит отвечает на вопрос:

> Что произошло?

Пример цепочки:

```text
StrategyAction selected
  -> ServiceCommand created
  -> ServiceCommand executed
  -> Order changed
  -> Exchange ack received
  -> Refresh confirmed final state
```

# 3. Возможные сущности аудита

## 3.1. ServiceCommandExecutionHistory

История исполнения сервисных команд.

Примерная модель:

```java
public class ServiceCommandExecutionHistory {

    /**
     * Технический ID записи.
     */
    private Long id;

    /**
     * Сделка, в рамках которой выполнялась команда.
     */
    private Long dealId;

    /**
     * Runtime-состояние action стратегии, если команда связана с action.
     */
    private Long dealActionStateId;

    /**
     * ID action стратегии, если нужно денормализовать для удобства аудита.
     */
    private Long strategyActionId;

    /**
     * Тип команды.
     */
    private ServiceCommandType commandType;

    /**
     * Статус исполнения команды.
     */
    private ServiceCommandExecutionStatus status;

    /**
     * Тип целевой сущности.
     */
    private TargetEntityType targetEntityType;

    /**
     * ID целевой сущности.
     */
    private Long targetEntityId;

    /**
     * Snapshot payload команды.
     */
    private JsonNode commandPayloadSnapshot;

    /**
     * Snapshot результата выполнения.
     */
    private JsonNode resultSnapshot;

    /**
     * Текст ошибки, если команда упала.
     */
    private String errorMessage;

    /**
     * Время начала исполнения.
     */
    private OffsetDateTime startedAt;

    /**
     * Время завершения исполнения.
     */
    private OffsetDateTime finishedAt;
}
```

Пример enum:

```java
public enum ServiceCommandExecutionStatus {

    /**
     * Команда создана, но ещё не начала исполняться.
     */
    CREATED,

    /**
     * Команда исполняется.
     */
    IN_PROGRESS,

    /**
     * Команда успешно выполнена технически.
     */
    SUCCESS,

    /**
     * Команда завершилась ошибкой.
     */
    FAILED,

    /**
     * Команда была пропущена, потому что действие уже выполнено или больше не нужно.
     */
    SKIPPED,

    /**
     * Команда ждёт retry.
     */
    RETRY_PENDING
}
```

## 3.2. EntityHistory

История изменений runtime-сущностей.

Примерная модель:

```java
public class EntityHistory {

    /**
     * Технический ID записи.
     */
    private Long id;

    /**
     * Сделка, если изменение связано со сделкой.
     */
    private Long dealId;

    /**
     * Тип сущности: ORDER / ALGO_ORDER / POSITION / BALANCE / DEAL.
     */
    private TargetEntityType entityType;

    /**
     * ID сущности.
     */
    private Long entityId;

    /**
     * Тип события истории.
     */
    private EntityHistoryEventType eventType;

    /**
     * Команда, которая привела к изменению, если есть.
     */
    private Long serviceCommandExecutionHistoryId;

    /**
     * Snapshot сущности до изменения.
     */
    private JsonNode beforeSnapshot;

    /**
     * Snapshot сущности после изменения.
     */
    private JsonNode afterSnapshot;

    /**
     * Время события.
     */
    private OffsetDateTime eventTime;
}
```

Пример enum:

```java
public enum EntityHistoryEventType {

    /**
     * Сущность создана локально в БД.
     */
    CREATED_LOCAL,

    /**
     * Сущность отправлена на биржу.
     */
    SUBMITTED_TO_EXCHANGE,

    /**
     * Получено подтверждение/ack от биржи.
     */
    EXCHANGE_ACK_RECEIVED,

    /**
     * Сущность обновлена из биржевого snapshot.
     */
    REFRESHED_FROM_EXCHANGE,

    /**
     * Сущность изменена через amend.
     */
    AMENDED,

    /**
     * Сущность отменена.
     */
    CANCELLED,

    /**
     * Сущность исполнена.
     */
    FILLED,

    /**
     * Позиция закрыта.
     */
    CLOSED,

    /**
     * Сущность переведена в ошибочное состояние.
     */
    MARKED_ERROR,

    /**
     * Обновлён snapshot баланса.
     */
    BALANCE_REFRESHED
}
```

# 4. Что история не должна делать

Аудит не должен:

* управлять FSM;
* быть источником решения, какие команды создать;
* заменять `DealActionState`;
* быть единственным источником восстановления после рестарта;
* хранить operational-lock состояние.

Runtime-логика не должна зависеть от чтения исторических таблиц.

---

# 5. Что история должна делать

Аудит должен:

* объяснять, почему появилась команда;
* показывать, какая команда изменила какую сущность;
* хранить payload команды;
* хранить результат команды;
* хранить before/after snapshots сущности;
* помогать разбирать инциденты;
* помогать строить timeline сделки;
* фиксировать REFRESH_BALANCE как команду исполнения;
* фиксировать kill-switch действия;
* фиксировать ошибки и retry.

---

# 6. REFRESH_BALANCE

Баланс не является управляемой торговой сущностью как `Order`, `AlgoOrder`, `Position`.

Но команда обновления баланса должна попадать в историю исполнения команд.

Причина:

* баланс влияет на риск;
* баланс влияет на возможность открытия сделки;
* баланс нужен для объяснения, почему команда была разрешена или отклонена;
* изменение balance snapshot может быть важным для расследования.

Возможные места фиксации:

```text
ServiceCommandExecutionHistory
  -> REFRESH_BALANCE

BalanceHistory / BalanceSnapshotHistory
  -> before/after balance snapshot
```

---

# 7. Связь с DealActionState

`DealActionState` нужен runtime-логике.

Аудит может ссылаться на него, но не заменяет его.

Пример:

```text
DealActionState
  action #123 -> target Order #777

ServiceCommandExecutionHistory
  command CREATE_ORDER
  dealActionStateId = ...
  strategyActionId = 123
  targetEntityId = 777
```

FSM читает `DealActionState`.

Человек или отчёт читает `ServiceCommandExecutionHistory` и `EntityHistory`.

# 9. Предварительная итоговая схема

```text
FSM / StrategyActionInterpreter
  -> создаёт ServiceCommand

ServiceCommandExecutor
  -> создаёт ServiceCommandExecutionHistory
  -> вызывает Executor

Executor
  -> меняет runtime-сущность
  -> пишет EntityHistory
  -> обновляет DealActionState, если команда связана с action

FSM
  -> продолжает работу по DealContext + DealActionState

Audit / Reports
  -> читают ServiceCommandExecutionHistory + EntityHistory
```

# 10. Текущий статус

Эта дока пока не финальная.

Зафиксировано точно:

* аудит не источник runtime-логики FSM;
* `Order`, `AlgoOrder`, `Position` не хранят `strategyActionId`;
* связь action стратегии с runtime-сущностью для FSM хранится в `DealActionState`;
* история должна фиксировать команды и изменения сущностей;
* `REFRESH_BALANCE` должен попадать в историю команд.

Нужно дополнительно спроектировать:

* финальные модели истории;
* enum'ы статусов и событий;
* before/after snapshot формат;
* связь с UI/отчётом сделки;
* retry/audit детализацию.
