# 1. Главная идея

Аудит и история исполнения нужны для объяснения прошлого:

* почему была создана сделка;
* какая стратегия и какой action привели к действию;
* какая runtime-команда выполнялась;
* какая runtime-сущность была создана или изменена;
* чем закончилась попытка исполнения;
* были ли ошибки и retry;
* какие факты подтвердили финальное состояние.

Главное правило:

> Аудит не является источником runtime-логики FSM.
>
> FSM не должна читать историю, чтобы решить, что делать дальше.

Для runtime-восстановления используется:

```text
DealContext
DealActionState
Order / AlgoOrder / Position / BalanceContainer
exchange snapshots
refresh/search/history facts
```

Для объяснения прошлого будет использоваться история исполнения команд и история изменений сущностей, но их финальные модели проектируются отдельно.

---

# 2. Инварианты аудита

* `Order`, `AlgoOrder`, `Position` не хранят `strategyActionId`, `strategyActionKey`, role или level стратегии.
* Runtime-связь `StrategyAction -> runtime entity` хранится в `DealActionState`.
* `DealActionState` — operational state для FSM, а не аудит.
* `ServiceCommand` — runtime object, а не persisted command queue.
* История исполнения команд не должна становиться durable queue.
* История изменения сущностей не должна заменять `DealActionState`.
* Подробный entry context хранится в истории, а не в `Deal`.
* `shutdownReason` должен быть виден в timeline сделки, но не заменяет `closeReason`.
* `CLOSED` и `EMERGENCY_CLOSED` должны различаться в отчётах: штатный terminal-финал и аварийный terminal-финал.
* `ENTRY_CONDITION_EXPIRED` должен отображаться как нормальное закрытие candidate Deal без live risk, а не как авария.
* Direct partial close позиции запрещён. Partial exit должен быть объясним через `Order / AlgoOrder`, fills/history/refresh и `DealActionState`.
* `REFRESH_BALANCE` должен попадать в историю исполнения команд, потому что баланс влияет на risk decisions.

---

# 3. Что аудит не должен делать

Аудит не должен:

* управлять FSM;
* быть источником решения, какие команды создать;
* заменять `DealActionState`;
* быть единственным источником восстановления после рестарта;
* хранить operational-lock состояние;
* быть command queue.

Runtime-логика не должна зависеть от чтения исторических таблиц.

---

# 4. Что аудит должен объяснять

Аудит должен помогать человеку понять:

* почему появился `Deal`;
* какой `entryReason` и `entryStepType` были у сделки;
* почему был запущен graceful shutdown;
* почему сделка попала в `ERROR`;
* как был выполнен safety-flow / kill-switch;
* почему сделка стала `EMERGENCY_CLOSED`;
* какие команды выполнялись;
* какие команды были retryable / failed / skipped;
* какие refresh/search/history facts подтвердили состояние;
* как partial exit был материализован через `Order / AlgoOrder`;
* почему `DealActionState` перешёл в `COMPLETED`, `FAILED`, `SKIPPED` или `RETRY_PENDING`.

# 5. Открытые вопросы

В этой редакции не финализируем модели аудита и flow записи истории.

## 5.1. История исполнения команд

Нужно решить:

1. Нужна ли отдельная запись истории на каждую попытку исполнения команды.
2. Какие статусы должны быть у записи истории исполнения команды.
3. Нужно ли фиксировать command payload snapshot.
4. Нужно ли фиксировать result snapshot.
5. Нужно ли хранить raw response биржи.
6. Где фиксировать exchange ack, если он понадобится для диагностики.
7. Как хранить `RetryError`.
8. Как связывать историю команды с `DealActionState`.
9. Как отражать команды, которые не связаны со `StrategyAction`.
10. Как отражать `REFRESH_*` команды.
11. Как отражать `EXECUTE_KILL_SWITCH`.
12. Нужен ли correlation id / trace id.

## 5.2. История изменения сущностей

Нужно решить:

1. Делать одну общую историю сущностей или отдельные истории для `Order`, `AlgoOrder`, `Position`, `Balance`, `Deal`.
2. Какие изменения сущностей нужно фиксировать.
3. Нужны ли before/after snapshots.
4. Нужен ли external raw snapshot отдельно от internal domain snapshot.
5. Нужен ли diff или достаточно snapshots.
6. Как связывать изменение сущности с command execution.
7. Как фиксировать изменения, которые произошли из refresh, а не из торговой команды.
8. Как показывать такие изменения в timeline.

## 5.3. Timeline сделки

Нужно решить:

1. Какие события показываем человеку.
2. Какие события считаются техническими.
3. Как группировать `CREATE -> SUBMIT -> REFRESH`.
4. Как показывать retry.
5. Как показывать `UNKNOWN_RESULT` / `EXCHANGE_TIMEOUT`.
6. Как показывать graceful shutdown.
7. Как показывать emergency flow / kill-switch.
8. Как показывать recovery после рестарта.
9. Как показывать partial exit через `Order / AlgoOrder / fills`.
10. Как показывать `ENTRY_CONDITION_EXPIRED`.
11. Как показывать `EMERGENCY_CLOSED`.

---

# 6. Текущий статус

Зафиксировано точно:

* аудит не источник runtime-логики FSM;
* `Order`, `AlgoOrder`, `Position` не хранят `strategyActionId`;
* связь action стратегии с runtime-сущностью для FSM хранится в `DealActionState`;
* `ServiceCommand` не является persisted queue;
* `REFRESH_BALANCE` должен попадать в историю исполнения команд;
* модели истории команд и сущностей ещё не финализированы;
* flow записи истории ещё не финализирован.
