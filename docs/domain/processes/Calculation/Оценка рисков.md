# 1. Главная идея

Risk-layer отвечает на вопрос:

```text
можно ли выполнить уже рассчитанное действие стратегии при текущем состоянии сделки, позиции, баланса, инструмента и биржи?
```

Risk-layer не выбирает стратегию, не проверяет торговый сигнал и не исполняет команды.

Общий flow для risk-creating / risk-increasing action:

```text
FSM handler
  -> выбирает StrategyStep
  -> проверяет StrategyCondition
  -> выбирает StrategyAction
  -> StrategyActionCalculator
     -> собирает свежий CalculationContext
     -> считает CalculatedPrice
     -> считает CalculatedSize
  -> RiskValidator
     -> возвращает RiskValidationResult
  -> RiskBlockResolver
     -> если риск BLOCKED, выбирает RiskBlockAction
  -> ServiceCommandFactory
     -> создаёт одну актуальную runtime ServiceCommand, если действие разрешено
```

Главное правило:

```text
RiskValidator вызывается после расчёта цены и размера,
но только для actions, которые создают, увеличивают или ослабляют контроль риска,
и до создания соответствующей торговой ServiceCommand.
```

Exit / cleanup / safety-flow не проходит через `RiskValidator`.
Для таких действий handler выполняет minimal domain / exchange safety checks и invariant checks.

Refresh/search/history команды тоже не проходят через `RiskValidator`, потому что они только обновляют факты.

# 2. Границы ответственности

## 2.1. Strategy-layer

Стратегия хранит настройки риска:

```text
StrategyDetail.riskPerTradePercent
StrategyDetail.maxLeverage
StrategyOrderAction.allocationPercents
StrategyOrderAction.positionReducingOnly
StrategyAlgoOrderAction.closeFractionPercents
StrategyAlgoOrderAction.triggerProfitPercents
```

Стратегия не решает runtime-risk сама.

## 2.2. Calculator-layer

`StrategyActionCalculator` считает:

```text
CalculatedPrice
CalculatedSize
```

Он может вернуть controlled calculation error, если цену или размер безопасно посчитать невозможно.

`StrategyActionCalculator` не возвращает `RiskValidationResult` и не возвращает `CalculatedRiskMetrics`.

Метрики, нужные для решения `ALLOWED / WARNING / BLOCKED`, считаются внутри `RiskValidator` / risk-layer.

Финальное решение о risk-policy принимает не калькулятор, а `RiskValidator`.

## 2.3. RiskValidator

`RiskValidator` проверяет уже рассчитанное действие.

Он отвечает на вопрос:

```text
разрешено ли действие по risk-policy?
```

Для этого `RiskValidator` сам считает или запрашивает нужные risk-метрики на базе:

```text
CalculatedPrice;
CalculatedSize;
DealContext;
BalanceContainer;
Position;
InstrumentExternalRules;
RiskSettings.
```

Примеры метрик:

```text
risk amount;
risk percent от депозита;
estimated leverage;
estimated margin;
notional;
SL distance;
liquidation guard distance;
position exposure после действия.
```

Эти метрики могут попадать в `RiskCheckResult.details`, логи или аудит.

Он не переводит сделку в другой статус и не создаёт команды.

## 2.4. RiskBlockResolver

`RiskBlockResolver` превращает результат проверки риска в понятное действие для handler'а.

Он отвечает на вопрос:

```text
что должен сделать handler, если RiskValidator вернул BLOCKED?
```

## 2.5. FSM / handler

FSM handler исполняет решение:

```text
ALLOWED / WARNING -> продолжить flow
BLOCKED -> применить RiskBlockAction
```

FSM не должна вручную маппить каждый `RiskCheckCode` в статус сделки.

Политика маппинга кодов риска живёт в `RiskBlockResolver`.

# 3. Когда вызывается RiskValidator

`RiskValidator` вызывается не перед каждым техническим действием, а только перед action, который может создать новый риск, увеличить риск или ослабить контроль риска.

Вызывается для `CREATE_ORDER`, `AMEND_ORDER`, `CREATE_ALGO_ORDER`, `AMEND_ALGO_ORDER` только если конкретное рассчитанное действие является risk-creating / risk-increasing / risk-weakening.

Примеры:

```text
entry order, который открывает позицию;
scaling / pyramiding order, который увеличивает позицию;
amend, который увеличивает размер live order;
amend, который ухудшает защиту, например двигает SL дальше от цены входа;
создание защитного algo-order с параметрами, которые не обеспечивают требуемый контроль риска.
```

Не вызывается для exit / cleanup / safety-flow, даже если технически используется `Order` / `AlgoOrder`.

Partial exit через reduce-only `Order` / `AlgoOrder` не является risk-validation flow.
Для него выполняются minimal safety / invariant checks:

```text
order/algo действительно reduce-only;
размер не больше текущей позиции;
target относится к текущей Deal;
направление уменьшает позицию, а не увеличивает;
есть нужные exchange facts / runtime facts.
```

Не вызывается для:

```text
REFRESH_BALANCE
REFRESH_POSITION
REFRESH_ORDER
REFRESH_PENDING_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER
REFRESH_ALGO_ORDERS
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
EXECUTE_KILL_SWITCH
MARK_DEAL_ERROR
MARK_DEAL_CLOSED
FINALIZE_DEAL_EXIT
```

Причина:

```text
refresh/search/history не создают новый риск,
а только обновляют факты, на которых потом строится решение.

CANCEL_ORDER / CANCEL_ALGO_ORDER / CLOSE_POSITION / EXECUTE_KILL_SWITCH
не создают новое торговое намерение, а снимают или локализуют уже существующий риск.

Partial exit через reduce-only Order / AlgoOrder также относится к exit-flow:
он не проходит через RiskValidator, но обязан пройти minimal safety / invariant checks.
```

## 3.1. Минимальные проверки для cleanup / safety commands

Для risk-reducing / cleanup / safety commands `RiskValidator` не вызывается.

К таким командам относятся:

```text
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
EXECUTE_KILL_SWITCH
```

Для них нужны не risk-policy проверки, а минимальные domain / exchange safety checks.

Для `CLOSE_POSITION` проверяем:

```text
позиция существует;
позиция относится к текущей сделке / инструменту;
команда закрывает всю позицию, а не partial;
есть данные, чтобы сформировать exchange request;
свежие exchange facts не доказывают, что позиция уже закрыта.
```

Для `CANCEL_ORDER` / `CANCEL_ALGO_ORDER` проверяем:

```text
сущность существует;
сущность относится к текущей сделке;
сущность live или potentially live;
есть данные, чтобы сформировать exchange request;
если refresh/search/history уже показал terminal state, cancel не нужен.
```

Для `EXECUTE_KILL_SWITCH` проверяем только safety/invariant часть:

```text
какой instrument / exchange account нужно обезопасить;
какие live positions / orders / algo-orders известны;
какие read/safety commands нужно выполнить.
```

Главное правило:

```text
RiskValidator не должен блокировать команды, цель которых — снять live risk.
```

# 4. Базовая модель результата

## 4.1. RiskValidationResult

```java
public class RiskValidationResult {

    /** Итоговое решение risk-layer. */
    private RiskDecision decision;

    /** Детальные результаты отдельных проверок. */
    private List<RiskCheckResult> checks;

    /** Короткое пояснение для логов / будущей истории исполнения. */
    private String comment;
}
```

```java
public enum RiskDecision {

    /** Действие разрешено. */
    ALLOWED,

    /** Есть риск-предупреждения, но действие не блокируется. */
    WARNING,

    /** Действие заблокировано risk-policy. */
    BLOCKED
}
```

## 4.2. RiskCheckResult

```java
public class RiskCheckResult {

    /** Машинный код проверки. */
    private RiskCheckCode code;

    /** Результат конкретной проверки. */
    private RiskCheckStatus status;

    /** Фактическое значение, если проверка числовая. */
    private BigDecimal actualValue;

    /** Короткое пояснение. */
    private String comment;

    /** Дополнительные детали, если нужны для диагностики. */
    private Map<String, Object> details;
}
```

`limitValue` отдельным полем не вводим.

Причина:

```text
не у каждой проверки есть один понятный лимит;
для сложных проверок может быть несколько порогов;
если лимит нужен для диагностики, его можно положить в details.
```

```java
public enum RiskCheckStatus {

    /** Проверка пройдена. */
    PASSED,

    /** Проверка дала предупреждение, но не блокирует действие. */
    WARNING,

    /** Проверка заблокировала действие. */
    BLOCKED
}
```

```java
    TAKE_PROFIT_INVALID_SIDE,

    STOP_LOSS_TOO_CLOSE_TO_LIQUIDATION,

     * Действие partial exit не имеет reduce-only semantics.
     *
     * Это не risk-policy check для RiskValidator, а safety / invariant violation

    PARTIAL_EXIT_NOT_REDUCE_ONLY,

    /**
     * Действие partial exit может открыть или увеличить позицию.
     *
     * Это не risk-policy check для RiskValidator, а safety / invariant violation
     * для exit-flow через reduce-only Order / AlgoOrder.
     */
    PARTIAL_EXIT_INCREASES_POSITION,

    /** Попытка выполнить partial close через StrategyPositionAction / CLOSE_POSITION. */
    DIRECT_PARTIAL_POSITION_CLOSE_FORBIDDEN,

    /** По инструменту обнаружено больше одной позиции. */
    MULTIPLE_POSITIONS_DETECTED,

    /** Состояние позиции неизвестно или противоречиво, поэтому торговое действие небезопасно. */
    POSITION_STATE_UNKNOWN,

    /** Инструмент не находится в торговом состоянии LIVE. */
    INSTRUMENT_NOT_LIVE,

    /** Внешние правила инструмента отсутствуют или неполные. */
    INSTRUMENT_RULES_MISSING,

    /** Расчётные параметры действия внутренне противоречивы. */
    CALCULATED_ACTION_INVALID
}
```

Важно:

```text
Market data expired / missing — это не risk-code первого уровня.
Такие кейсы сначала обрабатываются через MarketDataExpirationChecker
и StrategyStep.marketDataExpiredSetting.
```

# 6. RiskBlockResolver

## 6.1. Назначение

`RiskBlockResolver` нужен, чтобы handler не содержал большой `switch` по всем risk-кодам.

Он получает результат проверки риска и возвращает действие:

```text
RiskValidationResult -> RiskBlockAction
```

## 6.2. Интерфейс

```java
public interface RiskBlockResolver {

    RiskBlockAction resolve(
            DealContext dealContext,
            Deal.Status currentStatus,
            StrategyStep strategyStep,
            StrategyAction strategyAction,
            CalculatedStrategyAction calculatedAction,
            RiskValidationResult riskValidationResult
    );
}
```

## 6.3. Зачем каждый параметр

`dealContext` нужен, чтобы понять фактическое состояние сделки:

```text
есть ли позиция;
есть ли live orders;
есть ли live algo-orders;
есть ли DealActionState;
есть ли active risk.
```

`currentStatus` нужен, чтобы различать `PRECHECK` и этапы, где live risk уже есть или мог появиться:

```text
PRECHECK
ENTRY_SUBMITTED
ENTRY_FINALIZED
PROTECTION_SWITCHED
MANAGING
EXIT_PENDING
ERROR
```

`strategyStep` нужен, чтобы понимать тип шага:

```text
ENTRY
GRID_ENTRY
MAIN_PROTECTION
PROTECTION_ADJUSTMENT
PARTIAL_EXIT
GRID_MANAGEMENT
EXIT
FAIL_SAFE
```

`strategyAction` нужен, чтобы понимать исходное намерение стратегии:

```text
ORDER / ALGO_ORDER / POSITION;
CREATE / AMEND / CANCEL / CLOSE_FULL;
action создаёт/увеличивает риск или является reduce-only exit-flow;
positionReducingOnly / reduce-only intent.
```

`calculatedAction` нужен, чтобы видеть рассчитанную цену, размер, направление, reduce-only intent и другие рассчитанные параметры действия.

`riskValidationResult` нужен, чтобы видеть итоговое решение и конкретные `RiskCheckCode`.

`boolean liveRiskExists` отдельным параметром не передаём.

Причина:

```text
это производное состояние;
RiskBlockResolver должен вывести его из DealContext + currentStatus + runtime-сущностей,
а не доверять отдельному boolean, который можно передать неверно.
```

# 7. RiskBlockAction

```java
public class RiskBlockAction {

    /** Что должен сделать FSM handler. */
    private Type type;

    /** Причина закрытия сделки, если нужно закрыть candidate Deal. */
    private Deal.CloseReason closeReason;

    /** Код ошибки, если сделку нужно перевести в ERROR. */
    private RuntimeErrorCode errorCode;

    /** Короткое пояснение для логов / будущей истории. */
    private String comment;

    public enum Type {

        /** Продолжить выполнение action. */
        CONTINUE,

        /** Продолжить выполнение action, но сохранить предупреждение в логах / будущей истории. */
        CONTINUE_WITH_WARNING,

        /** Закрыть candidate Deal без ошибки, потому что live risk ещё не создан. */
        CLOSE_CANDIDATE_DEAL,

        /** Перевести сделку в ERROR, дальше работает ErrorHandler / safety-flow. */
        MOVE_DEAL_TO_ERROR,

        /** Не выполнять текущий action и запросить refresh фактов. */
        REQUEST_REFRESH,

        /** Пропустить action как больше не актуальный. */
        SKIP_ACTION
    }
}
```

# 8. Политика реакции на BLOCKED

## 8.1. PRECHECK

Если `RiskValidator` вернул `BLOCKED` в `PRECHECK` и live risk ещё не создан:

```text
Deal.status = CLOSED
Deal.closeReason = ENTRY_RISK_BLOCKED
```

Это не авария.

Смысл:

```text
candidate Deal был создан,
но до создания live risk выяснилось, что вход запрещён risk-policy.
```

Если в enum `Deal.CloseReason` ещё нет `ENTRY_RISK_BLOCKED`, его нужно добавить.

Отличие от `ENTRY_CONDITION_EXPIRED`:

```text
ENTRY_CONDITION_EXPIRED
  -> входное условие стратегии стало false до создания live risk

ENTRY_RISK_BLOCKED
  -> условие может быть true, но risk-policy запретила вход до создания live risk
```

## 8.2. ENTRY_SUBMITTED / ENTRY_FINALIZED / PROTECTION_SWITCHED / MANAGING

Если RiskValidator вернул `BLOCKED` для risk-creating / risk-increasing / risk-weakening action на этих этапах:

```text
Deal.status = ERROR
```

Дальше работает:

```text
ErrorHandler
  -> refresh/search/history facts
  -> safety-flow
  -> cancel live orders/algo-orders
  -> close live position if needed
  -> EMERGENCY_CLOSED после подтверждения отсутствия live risk
```

Причина:

```text
на этих этапах live risk уже есть, мог появиться или состояние может быть неизвестным;
безопаснее остановить обычную strategy-логику и передать сделку ErrorHandler.

В `EXIT_PENDING` RiskValidator обычно не вызывается: этот этап относится к cleanup/finalization.
Если cleanup / exit action не проходит minimal safety / invariant checks, это обрабатывается как recovery / ERROR / safety-flow, но не как `RiskValidationResult`.
```

## 8.3. WARNING

Если `RiskValidator` вернул `WARNING`:

```text
action не блокируется;
handler может продолжить flow;
warning фиксируется в логах / будущей истории исполнения.
```

`WARNING` не должен сам переводить сделку в `ERROR`.

## 8.4. ALLOWED

Если `RiskValidator` вернул `ALLOWED`:

```text
ServiceCommandFactory может создать одну актуальную runtime ServiceCommand.
```

# 9. Несколько actions в одном StrategyStep

Если в `StrategyStep` несколько actions, они выполняются последовательно.

Для каждого action:

```text
1. Собрать свежий CalculationContext.
2. Рассчитать price/size.
3. Если action создаёт/увеличивает/ослабляет риск — выполнить RiskValidator.
4. Если action относится к exit / cleanup / safety-flow — выполнить minimal safety / invariant checks.
5. Если RiskValidator вернул ALLOWED / WARNING — создать одну актуальную ServiceCommand.
6. Если minimal checks пройдены — создать одну актуальную exit / cleanup / safety ServiceCommand.
7. Если RiskValidator вернул BLOCKED — остановить выполнение step и применить RiskBlockResolver.
8. Если minimal checks не пройдены — остановить step и перейти в recovery / ERROR / safety-flow по контексту.
```

Правило:

```text
если любое risk-creating действие step заблокировано risk-policy,
не пытаемся продолжить остальные actions этого step.

если любое exit / cleanup / safety действие не прошло minimal checks,
не пытаемся продолжить остальные actions этого step до refresh/recovery.
```

Для `PRECHECK` без live risk это ведёт к закрытию candidate Deal без ошибки.

Для этапов с live risk или потенциальным live risk это ведёт к `ERROR` и safety-flow.

# 10. Связь с CalculationError

`CalculationError` и `RiskValidationResult` — разные вещи.

`CalculationError` означает:

```text
мы не смогли безопасно рассчитать цену / размер / параметры действия.
```

`RiskValidationResult` означает:

```text
мы рассчитали действие, RiskValidator посчитал нужные risk-метрики
и проверил действие по risk-policy.
```

Примеры:

```text
нет ATR для ATR-based SL
  -> CalculationError

размер меньше minSz
  -> RiskCheckCode.SIZE_BELOW_MIN

partial exit не reduce-only
  -> safety / invariant violation: PARTIAL_EXIT_NOT_REDUCE_ONLY

плечо выше лимита
  -> RiskCheckCode.LEVERAGE_EXCEEDED
```

# 11. Связь с unexpected exceptions

Unexpected exceptions не превращаем в `RiskValidationResult`.

Для unexpected exceptions используются runtime error codes:

```text
INTERNAL_ERROR
EXCHANGE_ERROR
VALIDATION_ERROR
```

Правило:

```text
RiskValidationResult — это контролируемый результат проверки риска.
Unexpected exception — это техническая ошибка runtime-flow.
```

Если unexpected exception возникла на границе FSM / DealOrchestratorJob:

```text
Deal -> ERROR
дальше ErrorHandler / safety-flow
```

# 12. Итоговые правила

```text
1. RiskValidator вызывается после расчёта цены и размера.
2. RiskValidator вызывается только для actions, которые создают, увеличивают или ослабляют контроль риска.
3. RiskValidator не вызывается перед refresh/search/history командами.
4. RiskValidator не вызывается для exit / cleanup / safety-flow: reduce-only partial exit, CANCEL_ORDER, CANCEL_ALGO_ORDER, CLOSE_POSITION, EXECUTE_KILL_SWITCH.
5. Для exit / cleanup / safety-flow выполняются minimal domain / exchange safety checks и invariant checks, а не risk-policy validation.
6. RiskValidator не создаёт ServiceCommand.
7. RiskBlockResolver маппит BLOCKED risk result в действие handler'а.
8. FSM handler исполняет RiskBlockAction.
9. PRECHECK + BLOCKED + нет live risk -> CLOSED / ENTRY_RISK_BLOCKED.
```
