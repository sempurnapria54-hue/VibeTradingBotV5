# Управление сделкой на основе стратегии и атомарных сервисных команд

> Модель стратегии: Strategy.md
>
> Связанная дока: `Формирователь цены на основе стратегии`.

---

# 1. Главная идея

Стратегия не управляет сделкой напрямую.

Стратегия описывает:

* **какой шаг** нужно выполнить;
* **при каких условиях**;
* **какое действие** ожидается;
* **над какой сущностью** это действие выполняется.

FSM сделки сопровождает runtime-сделку и решает:

* какой сейчас статус сделки;
* можно ли в этом статусе применять стратегию;
* выполнены ли условия конкретного шага;
* какие `StrategyAction` нужно превратить в команды;
* какие параметры нужны для выполнения команды.

Executor не принимает торговых решений.

Executor получает уже готовую атомарную команду и просто исполняет её.

---

# 2. Ключевое разделение

## 2.1. StrategyAction — верхнеуровневое бизнес-действие

`StrategyAction` отвечает на вопрос:

> Что стратегия хочет сделать?

Примеры:

* создать entry order;
* создать entry order с attached stop-loss;
* создать standalone algo stop-loss;
* создать OCO protection;
* передвинуть stop-loss;
* создать partial take-profit;
* закрыть позицию полностью;
* закрыть позицию частично;
* отменить grid-level;
* перестроить grid-level.

`StrategyAction` не является сервисной командой.

Она не должна знать:

* какой executor её выполнит;
* какой REST endpoint будет вызван;
* какой `ServiceCommandType` будет использован;
* какие конкретные `ordId/algoId` будут получены;
* как именно сохранять результат в БД.

---

## 2.2. ServiceCommand — атомарная runtime-команда

`ServiceCommand` отвечает на вопрос:

> Какую простую операцию нужно выполнить над одной runtime-сущностью?

Примеры:

* создать обычный order в БД;
* разместить обычный order на бирже;
* изменить обычный order;
* отменить обычный order;
* обновить обычный order;
* создать algo-order в БД;
* разместить algo-order на бирже;
* изменить algo-order;
* отменить algo-order;
* обновить algo-order;
* закрыть position;
* обновить position;
* обновить balance;
* финализировать deal;
* выполнить kill-switch.

`ServiceCommand` уже содержит подготовленные параметры выполнения.

---

## 2.3. Executor — технический исполнитель

Executor отвечает на вопрос:

> Как технически выполнить эту команду?

Executor не решает:

* входить ли в сделку;
* выходить ли из сделки;
* двигать ли stop-loss;
* достаточно ли прибыли;
* сломался ли тренд;
* подходит ли текущая фаза рынка.

Executor делает только техническую работу:

* читает нужные данные;
* вызывает биржу, если это биржевая команда;
* сохраняет результат;
* обновляет локальную сущность;
* обеспечивает восстановление после рестарта;
* возвращает результат выполнения.

---

# 3. Общий flow

```text
DealOrchestrator
  -> DealContextService.load(dealId)
  -> DealStateMachine.step(context, event)
     -> StateHandler
        -> StrategyConditionEvaluator
        -> StrategyActionInterpreter
           -> PriceResolver
           -> SizeCalculator
           -> RiskCalculator
           -> ServiceCommandFactory
        -> TransitionResult(commands)
  -> ServiceCommandExecutor.execute(context, commands)
     -> конкретный Executor
  -> DealContextService.load(dealId)
  -> DealService.save(deal)
```

Коротко:

```text
StrategyStep + DealContext
  -> StrategyAction
  -> расчёт параметров
  -> ServiceCommand
  -> Executor
```

Для сущностей, которые создаются на бирже, используется двухфазная модель:

```text
CREATE_* -> SUBMIT_* -> REFRESH_*
```

Где:

* `CREATE_*` — создать локальную сущность в БД;
* `SUBMIT_*` — разместить уже созданную сущность на бирже или восстановить факт размещения;
* `REFRESH_*` — подтвердить фактическое состояние.

---

# 4. Роли компонентов

## 4.1. DealOrchestrator

Отвечает за один цикл сопровождения сделки.

Делает:

1. Загружает `DealContext`.
2. Вызывает FSM.
3. Получает `TransitionResult`.
4. Передаёт команды в `ServiceCommandExecutor`.
5. Перезагружает `DealContext` после выполнения команд.
6. Сохраняет `Deal`.

Не делает:

* не проверяет условия стратегии вручную;
* не считает цены;
* не ходит на биржу напрямую;
* не создаёт ордера сам.

---

## 4.2. DealStateMachine

Отвечает за переходы сделки по статусам.

Делает:

* выбирает handler по `Deal.Status`;
* вызывает входные проверки handler’а;
* вызывает обработку события;
* вызывает выходные проверки handler’а;
* применяет `nextStatus`, если он есть.

Не делает:

* не исполняет команды;
* не вызывает биржу;
* не знает детали REST API.

---

## 4.3. StateHandler

Отвечает за правила конкретного статуса сделки.

Например:

* `PrecheckHandler`;
* `EntrySubmittedHandler`;
* `EntryFinalizedHandler`;
* `ProtectionSwitchedHandler`;
* `ManagingHandler`;
* `ExitPendingHandler`;
* `ErrorHandler`.

Handler решает:

* какие факты обязательны для статуса;
* какие `StrategyStepType` допустимы сейчас;
* нужно ли применять стратегию;
* нужно ли выполнить refresh-команды;
* нужно ли выполнить submit-команды для уже созданных локальных сущностей;
* нужно ли перейти в следующий статус;
* нужно ли перейти в `EXIT_PENDING` или `ERROR`.

Handler не должен сам считать цену или размер.

---

## 4.4. StrategyConditionEvaluator

Отвечает за проверку `StrategyCondition`.

Делает:

1. Берёт rules из condition.
2. Сортирует по `level ASC`.
3. Проверяет каждое rule.
4. Возвращает `true`, только если все rules истинны.

Примеры rules:

* `NO_OPEN_POSITION`;
* `POSITION_OPENED`;
* `ATTACHED_STOP_LOSS_EXISTS`;
* `MAIN_PROTECTION_EXISTS`;
* `PROFIT_PERCENTS_REACHED`;
* `LOSS_PERCENTS_REACHED`;
* `RANGE_BREAKOUT_CONFIRMED`;
* `TREND_CHANGED`;
* `EFFICIENCY_BELOW_THRESHOLD`.

---

## 4.5. StrategyActionInterpreter

Отвечает за интерпретацию `StrategyAction`.

Делает:

1. Получает применимый `StrategyStep`.
2. Берёт его `actions`.
3. Для каждой action проверяет допустимость.
4. Запрашивает расчёт цены у формирователя цены.
5. Запрашивает расчёт размера у size/risk модуля.
6. Маппит action в атомарные `ServiceCommand`.

Важно:

`StrategyActionInterpreter` — это не executor.

Он ничего не отправляет на биржу.

---

## 4.6. PriceResolver

Отдельный модуль расчёта цены.

Делает:

* считает цену limit order;
* определяет market-like политику для market / optimal_limit_ioc;
* считает SL trigger price;
* считает TP trigger price;
* считает trailing active price;
* округляет цену по `tickSz`;
* возвращает готовый результат расчёта.

Подробно описан в отдельной доке: `Формирователь цены на основе стратегии`.

---

## 4.7. ServiceCommandFactory

Создаёт `ServiceCommand` из рассчитанных параметров.

Пример:

```text
StrategyOrderAction CREATE ENTRY
  + resolvedPrice
  + resolvedSize
  -> ServiceCommand CREATE_ORDER
  -> ServiceCommand SUBMIT_ORDER
```

---

## 4.8. ServiceCommandExecutor

Маршрутизирует команду в executor.

Пример:

```text
CREATE_ORDER -> CreateOrderExecutor
SUBMIT_ORDER -> SubmitOrderExecutor
AMEND_ORDER -> AmendOrderExecutor
CANCEL_ORDER -> CancelOrderExecutor
CREATE_ALGO_ORDER -> CreateAlgoOrderExecutor
SUBMIT_ALGO_ORDER -> SubmitAlgoOrderExecutor
CLOSE_POSITION -> ClosePositionExecutor
```

`ServiceCommandExecutor` не принимает торговых решений.

---

# 5. Рекомендуемый ServiceCommandType

```java
public enum ServiceCommandType {

    REFRESH_BALANCE,

    REFRESH_POSITION,
    CLOSE_POSITION,

    CREATE_ORDER,
    SUBMIT_ORDER,
    AMEND_ORDER,
    CANCEL_ORDER,
    REFRESH_ORDER,
    REFRESH_PENDING_ORDERS,
    REFRESH_ORDER_HISTORY,

    CREATE_ALGO_ORDER,
    SUBMIT_ALGO_ORDER,
    AMEND_ALGO_ORDER,
    CANCEL_ALGO_ORDER,
    REFRESH_ALGO_ORDER,
    REFRESH_ALGO_ORDERS,
    REFRESH_ALGO_ORDER_HISTORY,

    REFRESH_FILLS,

    FINALIZE_DEAL_ENTRY,
    FINALIZE_DEAL_EXIT,
    MARK_DEAL_CLOSED,
    MARK_DEAL_ERROR,

    EXECUTE_KILL_SWITCH
}
```

Названия можно доработать, но принцип такой:

> Команда должна описывать простую операцию над одной сущностью или техническую операцию сопровождения.

Для сущностей, которые создаются на бирже, создание делится на две команды:

```text
CREATE_* = создать локальную сущность в БД
SUBMIT_* = отправить локальную сущность на биржу или восстановить факт отправки
```

---

# 6. ServiceCommand должен быть объектом, а не только enum

Одного `ServiceCommandType` недостаточно.

Нужен объект команды:

```java
public class ServiceCommand {

    private ServiceCommandType type;

    private Long dealId;

    private Long instrumentId;

    private Long strategyId;

    private Long strategyDetailsId;

    private Deal.Status sourceDealStatus;

    private StrategyStepType sourceStepType;

    private StrategyActionType sourceActionType;

    private Integer sourceActionLevel;

    private String actionSlotKey;

    private ServiceCommandPayload payload;
}
```

`ServiceCommandType` говорит, что делать.

`payload` говорит, с какими параметрами делать.

`actionSlotKey` нужен для связи команды с конкретным местом стратегии:

```text
deal + роль сущности + stepType + actionType + actionLevel
```

На практике для ordinary order и algo-order основная биржевая идемпотентность строится через:

```text
clientOrderId = internalId
clientAlgoOrderId = internalId
```

# 7. Payload по типам команд

## 7.1. CREATE_ORDER

```java
public class CreateOrderCommandPayload implements ServiceCommandPayload {

    private Order.Type orderType;

    private StrategyTradeDirection strategyDirection;

    private OrderSide side;

    private PositionSide positionSide;

    private String instrumentExternalId;

    private MarginMode marginMode;

    private OrderExecutionType executionType;

    private BigDecimal sizeContracts;

    private BigDecimal price;

    private boolean priceRequiredByExchange;

    private AttachedProtectionPayload attachedProtection;
}
```

Используется для создания локального `Order` в БД.

После `CREATE_ORDER` сам order ещё не обязан существовать на бирже.

Используется для:

* entry order;
* grid entry order;
* ordinary close order, если закрытие делается не через close-position endpoint;
* обычных лимитных ордеров.

---

## 7.2. SUBMIT_ORDER

```java
public class SubmitOrderCommandPayload implements ServiceCommandPayload {

    private Long orderId;

    private String internalOrderId;

    private String clientOrderId;

    private String instrumentExternalId;
}
```

Используется для размещения уже созданного `Order` на бирже.

Важно:

```text
Order.Status = CREATED и externalId = null
```

не означает, что order точно ещё не отправляли на биржу.

Поэтому `SUBMIT_ORDER` должен сначала попытаться найти order на бирже по `clientOrderId`.

Если order найден — локальная БД догоняется до биржи.

Если order не найден — order отправляется на биржу.

---

# 8. StrategyAction -> ServiceCommand

## 8.1. StrategyOrderAction

### CREATE

```text
StrategyOrderAction CREATE
  -> CREATE_ORDER
  -> SUBMIT_ORDER
```

Примеры:

* `ENTRY` -> создать обычный entry order;
* `ENTRY_ATTACHED_STOP_LOSS` -> создать entry order с attached protection;
* grid level -> создать limit order по рассчитанной цене.

`CREATE_ORDER` фиксирует намерение в БД.

`SUBMIT_ORDER` размещает уже созданный order на бирже или восстанавливает факт размещения по `clientOrderId`.

### AMEND

```text
StrategyOrderAction AMEND
  -> AMEND_ORDER
```

Примеры:

* подвинуть цену лимитки;
* перестроить grid-level;
* изменить размер pending order.

### CANCEL

```text
StrategyOrderAction CANCEL
  -> CANCEL_ORDER
```

Примеры:

* снять конкретный grid-level;
* отменить entry order;
* отменить pending order при breakout.

---

## 8.2. StrategyAlgoOrderAction

### CREATE

```text
StrategyAlgoOrderAction CREATE
  -> CREATE_ALGO_ORDER
  -> SUBMIT_ALGO_ORDER
```

Примеры:

* создать stop-loss;
* создать OCO_FULL;
* создать partial take-profit;
* создать trailing stop.

`CREATE_ALGO_ORDER` фиксирует намерение в БД.

`SUBMIT_ALGO_ORDER` размещает уже созданный algo-order на бирже или восстанавливает факт размещения по `clientAlgoOrderId`.

### AMEND

```text
StrategyAlgoOrderAction AMEND
  -> AMEND_ALGO_ORDER
```

Примеры:

* передвинуть stop-loss;
* обновить take-profit;
* перестроить trailing;
* перейти в breakeven.

### CANCEL

```text
StrategyAlgoOrderAction CANCEL
  -> CANCEL_ALGO_ORDER
```

Примеры:

* отменить старую защиту;
* снять partial TP;
* снять trailing при выходе.

---

## 8.3. StrategyPositionAction

### CLOSE_FULL

```text
StrategyPositionAction CLOSE_FULL
  -> CLOSE_POSITION
```

`closeFraction = 1`.

### CLOSE_PARTIAL

```text
StrategyPositionAction CLOSE_PARTIAL
  -> CLOSE_POSITION
```

`closeFraction = closeFractionPercents / 100`.

# 9. Что остаётся в FSM

FSM должна управлять этапами сделки.

Примеры:

## PRECHECK

FSM проверяет:

* есть ли активная стратегия;
* есть ли `StrategyDetails`;
* можно ли торговать в текущей фазе;
* нет ли активной позиции;
* нет ли активного entry order.

Если условия entry-step выполнены:

```text
StrategyOrderAction CREATE
  -> CREATE_ORDER
```

После перезагрузки контекста FSM видит локальный order в БД.

Если order ещё не размещён на бирже:

```text
Order.CREATED
  -> SUBMIT_ORDER
```

После успешного создания локального order сделка может перейти в:

```text
PRECHECK -> ENTRY_SUBMITTED
```

---

## ENTRY_SUBMITTED

FSM не исполняет стратегию, а обновляет факты и доводит entry order до подтверждённого состояния:

```text
REFRESH_ORDER
REFRESH_POSITION
REFRESH_PENDING_ORDERS
```

Если entry order есть в БД, но ещё не подтверждён на бирже:

```text
Order.CREATED + externalId = null
  -> SUBMIT_ORDER
```

При этом `SUBMIT_ORDER` сначала проверяет биржу по `clientOrderId`.

Если вход подтверждён:

```text
ENTRY_SUBMITTED -> ENTRY_FINALIZED
```

---

## ENTRY_FINALIZED

FSM применяет steps типа:

```text
MAIN_PROTECTION
```

Если стратегия говорит создать защиту:

```text
StrategyAlgoOrderAction CREATE OCO_FULL
  -> CREATE_ALGO_ORDER
```

После перезагрузки контекста FSM видит локальный algo-order в БД.

Если algo-order ещё не размещён на бирже:

```text
AlgoOrder.CREATED
  -> SUBMIT_ALGO_ORDER
```

После подтверждения защиты:

```text
CANCEL_ALGO_ORDER или CANCEL_ORDER для attached protection
ENTRY_FINALIZED -> PROTECTION_SWITCHED
```

---

## PROTECTION_SWITCHED

FSM проверяет:

* позиция активна;
* main protection активна;
* attached protection снята.

Если всё хорошо:

```text
PROTECTION_SWITCHED -> MANAGING
```

---

## MANAGING

FSM применяет steps типа:

```text
PROTECTION_ADJUSTMENT
PARTIAL_EXIT
GRID_MANAGEMENT
EXIT
FAIL_SAFE
```

Примеры:

```text
PROTECTION_ADJUSTMENT -> AMEND_ALGO_ORDER
PARTIAL_EXIT -> CREATE_ALGO_ORDER / SUBMIT_ALGO_ORDER или CLOSE_POSITION
GRID_MANAGEMENT -> CREATE_ORDER / SUBMIT_ORDER / AMEND_ORDER / CANCEL_ORDER
EXIT -> CLOSE_POSITION
FAIL_SAFE -> CLOSE_POSITION
```

---

## EXIT_PENDING

FSM не создаёт новые стратегические действия.

Она дочищает сделку:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
CANCEL_ORDER
CANCEL_ALGO_ORDER
REFRESH_FILLS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
FINALIZE_DEAL_EXIT
```

---

## ERROR

FSM не применяет стратегию.

Она вызывает:

```text
EXECUTE_KILL_SWITCH
MARK_DEAL_ERROR
```

---

# 10. Что делает executor

Executor должен быть максимально простым.

## CreateOrderExecutor

Получает `CREATE_ORDER`.

Делает:

* создаёт локальный `Order` в БД;
* выставляет статус `CREATED`;
* привязывает order к `Deal`;
* создаёт attached protection внутри order, если она задана стратегией;
* не ходит на биржу;
* не решает, нужно ли входить.

---

## SubmitOrderExecutor

Получает `SUBMIT_ORDER`.

Делает:

1. Находит локальный `Order`.
2. Если `externalId` уже есть — команда считается выполненной.
3. Если `externalId` пустой — проверяет биржу по `clientOrderId = order.internalId`.
4. Если order найден на бирже — обновляет локальный order из external snapshot.
5. Если order не найден на бирже — отправляет локальный order на биржу.
6. Сохраняет `externalId`, внешний статус и другие внешние поля.

Важно:

```text
Order.CREATED + externalId = null
```

не означает, что order точно не был отправлен на биржу.

Поэтому `SUBMIT_ORDER` всегда должен быть recoverable.

## AmendOrderExecutor

Получает `AMEND_ORDER`.

Делает:

* находит order;
* отправляет amend;
* сохраняет ack/status;
* не решает, хорошая ли новая цена.

## CancelOrderExecutor

Получает `CANCEL_ORDER`.

Делает:

* находит order;
* отправляет cancel;
* сохраняет ack/status;
* не решает, надо ли снимать сетку.

## CreateAlgoOrderExecutor

Получает `CREATE_ALGO_ORDER`.

Делает:

* создаёт локальный `AlgoOrder` в БД;
* выставляет статус `CREATED`;
* привязывает algo-order к `Deal`;
* не ходит на биржу;
* не решает, нужен ли этот SL/TP.

5. Если algo-order не найден на бирже — отправляет локальный algo-order на биржу.
6. Сохраняет `externalId`, внешний статус и другие внешние поля.

# 11. Идемпотентность и восстановление после рестарта

В этой модели не требуется сложная идемпотентность на уровне `StrategyAction`, если соблюдается главный доменный инвариант:

```text
deal + роль сущности + level = одна сущность
```

Примеры:

```text
deal + ENTRY + level 1 = один entry order

deal + GRID_ENTRY + level 1 = один grid order

deal + GRID_ENTRY + level 2 = один grid order

deal + MAIN_PROTECTION + level 1 = один main algo-order

deal + PARTIAL_TAKE_PROFIT + level 1 = один TP1 algo-order
```

## 11.1. CREATE фиксирует намерение в БД

`CREATE_ORDER` и `CREATE_ALGO_ORDER` создают локальную сущность в БД.

Это значит:

* после перезагрузки `DealContext` видит эту сущность;
* FSM не создаёт её повторно;
* следующий шаг FSM — не новый create, а submit или refresh.

Пример:

```text
нет Order
  -> CREATE_ORDER

Order.CREATED
  -> SUBMIT_ORDER
```

## 11.2. SUBMIT является recoverable-командой

Если приложение упало после отправки запроса на биржу, но до сохранения `externalId`, то в БД останется:

```text
Order.CREATED
externalId = null
```

Это состояние нельзя трактовать как "ещё не отправляли".

Правильный алгоритм:

```text
1. Взять clientOrderId = order.internalId
2. Спросить биржу по clientOrderId
3. Если order найден:
   - сохранить externalId
   - обновить статус
   - обновить external snapshot
4. Если order не найден:
   - отправить order на биржу
```

Аналогично для algo-order:

```text
clientAlgoOrderId = algoOrder.internalId
```

## 11.3. REFRESH подтверждает факт

`SUBMIT_*` может получить только ack от биржи.

Финальное подтверждение делается через refresh:

```text
SUBMIT_ORDER
  -> REFRESH_ORDER / REFRESH_PENDING_ORDERS / REFRESH_POSITION

SUBMIT_ALGO_ORDER
  -> REFRESH_ALGO_ORDER / REFRESH_ALGO_ORDERS
```

FSM двигает статус сделки только после подтверждения факта.

## 11.4. Итоговая модель

```text
CREATE = фиксируем намерение в БД
SUBMIT = исполняем на бирже или восстанавливаем факт исполнения
REFRESH = подтверждаем фактическое состояние
```

# 12. Refresh-команды

Команды создания/изменения/отмены часто получают только ack от биржи.

Поэтому подтверждение факта делается через refresh.

Примеры:

```text
CREATE_ORDER
  -> SUBMIT_ORDER
  -> REFRESH_ORDER / REFRESH_PENDING_ORDERS / REFRESH_POSITION
```

```text
CREATE_ALGO_ORDER
  -> SUBMIT_ALGO_ORDER
  -> REFRESH_ALGO_ORDER / REFRESH_ALGO_ORDERS
```

```text
CANCEL_ALGO_ORDER
  -> REFRESH_ALGO_ORDERS / REFRESH_ALGO_ORDER_HISTORY
```

```text
CLOSE_POSITION
  -> REFRESH_POSITION / REFRESH_FILLS
```

FSM двигает статус сделки только после подтверждения факта.

# 13. Итоговая схема

```text
Strategy
  -> StrategyDetails
     -> stepsByStatus[Deal.Status]
        -> StrategyStep
           -> StrategyCondition
           -> StrategyAction

DealStateMachine / StateHandler
  -> проверяет статус и безопасность
  -> проверяет StrategyCondition
  -> выбирает StrategyAction

StrategyActionInterpreter
  -> считает цену через PriceResolver
  -> считает размер через SizeCalculator
  -> собирает ServiceCommand

ServiceCommandExecutor
  -> маршрутизирует команду

Executor
  -> исполняет атомарную операцию
  -> сохраняет результат

CREATE executors
  -> фиксируют намерение в БД

SUBMIT executors
  -> отправляют на биржу или восстанавливают по client id

Refresh executors
  -> подтверждают факты

FSM
  -> двигает Deal.Status по подтверждённым фактам
```

Главное правило:

> Торговое решение принимается на уровне `Deal.Status + StrategyStep + StrategyCondition + StrategyAction`.
>
> Executor только исполняет уже сформированную атомарную команду.

Для создаваемых на бирже сущностей:

```text
CREATE -> SUBMIT -> REFRESH
```
