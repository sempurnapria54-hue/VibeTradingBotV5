# Главная идея

`ServiceCommand` — это атомарная runtime-команда, которую можно передать executor'у.

Стратегия не исполняется напрямую.

FSM не ходит на биржу напрямую.

Executor не принимает торговых решений.

Flow:

```text
StrategyAction
  -> StrategyActionCalculator
  -> рассчитанные параметры
  -> ServiceCommandFactory
  -> ServiceCommand
  -> ServiceCommandExecutor
  -> конкретный Executor
```

`ServiceCommand` отвечает на вопрос:

> Какую простую операцию нужно выполнить над runtime-сущностью?

Executor отвечает на вопрос:

> Как технически выполнить эту операцию?

FSM отвечает на вопрос:

> Зачем эту команду сейчас выполнять и можно ли после её результата перейти дальше?

# Архитектурные инварианты command-layer

Эта часть фиксирует текущие правила command-layer.

* `ServiceCommand` — runtime object, а не persisted entity.
* Pending `ServiceCommand` не хранится в БД и не является durable queue.
* После рестарта FSM заново генерирует runtime-команды по `DealContext`, `DealActionState`, runtime-сущностям и exchange facts.
* `ServiceCommandExecutionHistory` относится к `05. Аудит и история исполнения` и не является источником runtime-логики FSM.
* `CREATE_*` сохраняет runtime-сущность и `DealActionState` в одной транзакции.
* `SUBMIT_*` использует стабильный client id: `Order.internalId -> clOrdId`, `AlgoOrder.internalId -> algoClOrdId`.
* Перед retry `SUBMIT_*` выполняется search/refresh по client id.
* Перед retry `CANCEL_*` выполняется refresh/search/history.
* Перед retry `CLOSE_POSITION` выполняется `REFRESH_POSITION`.
* `ACKED` не вводится как runtime status.
* `CONFIRMED` не используется в `DealActionStateStatus`.
* Успешный terminal-статус action — `COMPLETED`.
* `CLOSE_POSITION` используется только для полного закрытия позиции.
* Direct partial close позиции запрещён как постоянный инвариант стратегии и приложения.
* Partial exit выполняется через reduce-only `Order` / `AlgoOrder` actions с `DealActionState`, stable client id и recovery через fills/history/refresh.
* Graceful shutdown, protection switch и safety-flow собираются из существующих атомарных команд.
* `ServiceCommandFactory` создаёт одну актуальную команду для текущего action/state, а не всю цепочку команд заранее.
* Risk-check выполняется после расчёта цены/размера и до создания торговой команды.
* Если `RiskValidator` вернул блокирующий результат, `ServiceCommandFactory` не создаёт торговую команду для этого action.
* Для risk decisions используется отдельный `RiskBlockResolver`; command-layer не принимает policy-решения по риску сам.
* `EXCHANGE_ERROR` используется как общий код проблем взаимодействия с биржей; отдельные runtime-коды `UNKNOWN_RESULT` / `EXCHANGE_TIMEOUT` не используются в новой политике.
* Unexpected exceptions классифицируются через `INTERNAL_ERROR`, `EXCHANGE_ERROR`, `VALIDATION_ERROR` на границе orchestrator/FSM/executor flow.

# 1. Границы ответственности

## 1.1. Strategy-layer

Стратегия описывает ожидаемые действия:

* создать entry order;
* создать main protection;
* изменить stop-loss;
* отменить grid order;
* закрыть позицию полностью;
* частично уменьшить позицию через reduce-only Order / AlgoOrder action.

Стратегия не знает runtime ID сущностей.

В момент создания стратегии ещё не существует:

* `orderId`;
* `algoOrderId`;
* `positionId`.

Поэтому `StrategyAction` не должен ссылаться напрямую на runtime-сущность.

Для `AMEND` и `CANCEL` стратегия указывает, какое ранее описанное действие стратегии является target.

Для этого используется:

```text
targetActionKey
```

При сохранении стратегии `targetActionKey` валидируется и резолвится во внутреннюю ссылку на target action.

Подробности см. в документе:

```text
Strategy.md
```

## 1.2. FSM-layer

FSM решает:

* какой `Deal.Status` сейчас обрабатывается;
* какие входные проверки пройти;
* какие `StrategyStep` доступны в этом статусе;
* какие `StrategyCondition` выполнены;
* какие `StrategyAction` нужно применить;
* какие `ServiceCommand` нужны;
* можно ли перейти в следующий `Deal.Status`.

FSM не исполняет REST-запросы и не работает с биржей напрямую.

Подробности см. в документе:

```text
FSM этапы сделки
```

## 1.3. Calculator-layer

`StrategyActionCalculator` рассчитывает параметры action:

* цену;
* размер;
* risk-check;
* SL/TP/trailing параметры;
* размер partial exit для reduce-only Order / AlgoOrder;
* reference price для полного закрытия позиции.

Он собирает свежий `CalculationContext`.

Подробности см. в документе:

```text
03. Калькуляторы действий стратегии
```

Risk-check после расчёта отделён от command-layer:

```text
StrategyActionCalculator
  -> CalculatedStrategyAction
  -> RiskValidator
  -> RiskBlockResolver, если risk result BLOCKED
  -> ServiceCommandFactory, только если action разрешён
```

`ServiceCommandFactory` не должен сам решать, является ли риск блокирующим.
Он получает уже разрешённое к выполнению рассчитанное действие либо вообще не вызывается для заблокированного action.

Подробности по risk-layer см. в документе:

```text
Оценка рисков
```


## 1.4. Command-layer

Command-layer превращает рассчитанное действие в атомарную исполняемую команду.

Он отвечает за:

* `ServiceCommand`;
* payload;
* executor routing;
* executor'ы;
* retry policy;
* обновление `DealActionState`;
* безопасный повтор опасных команд;
* `CREATE -> SUBMIT -> REFRESH`.

# 2. Важные принципы

## 2.1. Runtime-связь хранится в DealActionState

`Order`, `AlgoOrder`, `Position` остаются чистыми runtime-сущностями биржи.

В них не храним:

```text
strategyActionId
role
level стратегии
```

Связь хранится отдельно:

```text
StrategyAction.id
  -> DealActionState.strategyActionId
     -> RuntimeTarget
        -> entityType
        -> entityId
```

`StrategyAction.key` нужен для JSON/API и резолва ссылок между actions при сохранении стратегии.

Runtime работает через `strategyActionId`, а не через `strategyActionKey`.

## 2.2. key остаётся только у StrategyAction

`key` не используется в strategy settings:

```text
StrategyIndicatorSetting
StrategyMarketStructureSetting
StrategyMarketPhaseSetting
```

Но `StrategyAction.key` остаётся обязательным, потому что он нужен для `targetActionKey`.

## 2.3. Аудит не источник runtime-логики

Аудит отвечает на вопрос:

> Что произошло и почему?

FSM отвечает на вопрос:

> Что делать дальше?

Поэтому FSM не должна читать историю, чтобы принимать runtime-решения.

Для восстановления используется:

```text
DealContext + DealActionState + runtime-сущности + exchange snapshots
```

## 2.4. Команды должны быть атомарными

Одна команда должна делать одну простую операцию.

Примеры:

```text
CREATE_ORDER
SUBMIT_ORDER
REFRESH_ORDER
CANCEL_ORDER
CREATE_ALGO_ORDER
SUBMIT_ALGO_ORDER
REFRESH_ALGO_ORDER
CLOSE_POSITION
```

Не нужно делать команду вида:

```text
OPEN_FULL_DEAL_AND_PROTECT_POSITION
```

Такой процесс должен быть разложен на атомарные команды и переходы FSM.

```text
entryReason / entryStepType
```

# 4. ServiceCommand

`ServiceCommand` — runtime object. Он не сохраняется как pending entity и не используется как durable command queue.


```java
public class ServiceCommand {

    /**
     * Тип атомарной операции.
     */
    private ServiceCommandType type;

    /**
     * Сделка, в рамках которой выполняется команда.
     */
    private Long dealId;

    /**
     * Runtime-состояние action стратегии.
     *
     * Через него команда связывается с StrategyAction,
     * но сама биржевая сущность не хранит strategyActionId.
     */
    private Long dealActionStateId;

    /**
     * Параметры выполнения команды.
     */
    private ServiceCommandPayload payload;
}
```

Важно:

* `ServiceCommand` не обязан хранить `strategyId` и `strategyDetailId`.
* Если нужно понять происхождение команды, это можно сделать через `DealActionState` и историю исполнения команд.
* Аудит и история не должны быть источником runtime-логики FSM.

# 5. ServiceCommandFactory

## 5.0. Связь с MarketDataExpirationChecker

`ServiceCommandFactory` не проверяет свежесть рыночных данных сам.

Свежесть проверяют `EntryScannerJob` и FSM handler через `MarketDataExpirationChecker`.

Если данные для data-dependent `StrategyStep` устарели и `StrategyStep.marketDataExpiredSetting` запрещает выполнение actions, `ServiceCommandFactory` не должен получить такой action для создания торговой команды.

При этом safety/cleanup-команды остаются допустимыми:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
EXECUTE_KILL_SWITCH
```


`ServiceCommandFactory` создаёт команды из рассчитанных действий стратегии.

Он не проверяет стратегические условия.

Он не рассчитывает цену, размер и риск.

Он не исполняет команды.

Он делает:

* выбирает `ServiceCommandType` по типу action;
* создаёт payload;
* привязывает команду к `dealId`;
* привязывает команду к `dealActionStateId`, если команда относится к action стратегии;
* не создаёт команды, если action нельзя выполнить без target entity.

Пример flow для CREATE order:

```text
StrategyOrderAction(actionType = CREATE)
  -> CalculatedStrategyAction
  -> ServiceCommandFactory
  -> CREATE_ORDER payload
  -> SUBMIT_ORDER payload после локального создания order
```

Пример flow для AMEND algo-order:

```text
StrategyAlgoOrderAction(actionType = AMEND, targetActionKey = main-stop-loss)
  -> target StrategyAction
  -> DealActionState(target StrategyAction.id)
  -> RuntimeTarget(ALGO_ORDER, algoOrderId)
  -> CalculatedStrategyAction
  -> ServiceCommandFactory
  -> AMEND_ALGO_ORDER payload
```

# 6. DealActionState

## 5.1. Актуальное правило после Q4: одна команда за раз

`ServiceCommandFactory` не создаёт всю цепочку команд заранее.

Правило:

```text
один проход FSM / handler
  -> один актуальный action-state
  -> одна актуальная runtime ServiceCommand
```

Пример для order-flow:

```text
DealActionState отсутствует / PLANNED
  -> создать CREATE_ORDER

DealActionState.status = CREATED
  -> создать SUBMIT_ORDER

DealActionState.status = SUBMITTED
  -> создать REFRESH_ORDER / REFRESH_PENDING_ORDERS / REFRESH_ORDER_HISTORY
```

То есть `CREATE_ORDER -> SUBMIT_ORDER -> REFRESH_ORDER` не создаются одним пакетом заранее.
Каждая следующая команда появляется только после того, как FSM заново посмотрела на `DealContext`, `DealActionState`, runtime-сущности и exchange facts.

Для шага стратегии с несколькими actions применяется то же правило:

```text
StrategyStep.actions[0]
  -> довести action до безопасного runtime-состояния
  -> затем перейти к следующему action, если step всё ещё актуален
```

Если action попал в `RETRY_PENDING`, весь step ждёт retry этого action.
FSM не перескакивает к следующим actions этого step, чтобы не получить непредсказуемую смесь частично выполненных действий.

## 5.2. Связь ServiceCommandFactory с risk-layer

Risk-check выполняется до создания торговой команды:

```text
StrategyActionCalculator
  -> CalculatedStrategyAction
  -> RiskValidator
  -> RiskBlockResolver, если BLOCKED
  -> ServiceCommandFactory
```

`ServiceCommandFactory` получает только action, который разрешён к исполнению.
Если риск блокирующий, handler принимает runtime-решение по результату `RiskBlockResolver`, а command-layer не создаёт `CREATE_*`, `SUBMIT_*`, `AMEND_*`, `CANCEL_*` для заблокированного торгового action.

Refresh/cleanup/safety-команды не являются торговыми action-командами и могут создаваться без risk-check:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
EXECUTE_KILL_SWITCH
```


`DealActionState` — runtime-проекция выполнения action стратегии.

Она нужна для восстановления после рестарта.

Она не является аудитом.

```java
public class DealActionState extends Retryable {

    /**
     * Технический ID записи.
     */
    private Long id;

    /**
     * Сделка, в рамках которой выполняется action стратегии.
     */
    private Long dealId;

    /**
     * Action стратегии, с которым связан runtime-state.
     */
    private Long strategyActionId;

    /**
     * Runtime-сущность, в которую материализовался action стратегии.
     *
     * Для ещё не созданной сущности может быть null.
     */
    private RuntimeTarget target;

    /**
     * Текущее состояние выполнения action.
     */
    private DealActionStateStatus status;
}
```

Ключевой инвариант:

```text
UNIQUE(deal_id, strategy_action_id)
```

Важно:

> `strategyActionId` не хранится в `Order`, `AlgoOrder`, `Position`.
>
> Связь action стратегии с runtime-сущностью хранится в `DealActionState`.
>
> `strategyActionKey` в `DealActionState` не хранится, если actions стратегии сохранены отдельными строками и имеют ID.

```java
public enum DealActionStateStatus {

    /** Action ожидает выполнения. */
    PLANNED,

    /** Локальная runtime-сущность создана в БД. */
    CREATED,

    /**
     * Команда отправки / изменения / отмены была выполнена

    FAILED,

    /** Action больше не нужен из-за изменения состояния сделки. */
    SKIPPED
}
```

# 7. StrategyAction.key и targetActionKey

## 7.1. Зачем нужен StrategyAction.key

Для валидации стратегии и ссылок между actions нужно понимать:

> На какое действие стратегии ссылается `AMEND` / `CANCEL`?

Например:

```text
grid-entry-long-1
  -> должен создать Order

cancel-grid-entry-long-1
  -> должен отменить именно Order, созданный action grid-entry-long-1
```

Для этого у каждого action есть явно заданный ключ:

```text
key
```

## 7.2. key задаётся в JSON стратегии

`key` задаётся явно в JSON при создании стратегии.

Он не генерируется автоматически.

## 7.3. Минимальный контракт StrategyAction для command-layer

Это не полная модель всех `StrategyAction`.

Полная модель находится в `Strategy.md`.

Здесь указаны только поля, которые нужны для связи:

```text
StrategyAction -> DealActionState -> ServiceCommand
```

```java
public interface StrategyAction {

    /**
     * Стабильный ключ action внутри StrategyDetail.
     *
     * Задаётся явно в JSON при создании стратегии.
     * Нужен для ссылок между actions и первичной валидации targetActionKey.
     */
    String getKey();
}
```

Для action, который работает с уже созданной runtime-сущностью, добавляется `targetActionKey`.

```java
public interface TargetedStrategyAction extends StrategyAction {

    /**
     * Ключ action, который создал runtime-сущность,
     * над которой нужно выполнить AMEND или CANCEL.
     */
    String getTargetActionKey();
}
```

## 7.4. Правила валидации key / targetActionKey

При создании стратегии валидатор должен проверить:

1. `key` обязателен у каждого `StrategyAction`.
2. `key` уникален в рамках одной `StrategyDetail`.
3. `targetActionKey` должен ссылаться на существующий `action.key` в той же `StrategyDetail`.
4. `targetActionKey` обязателен для `AMEND` и `CANCEL` у `ORDER` / `ALGO_ORDER` actions.
5. `CREATE` не должен иметь `targetActionKey`.
6. `ORDER AMEND` / `ORDER CANCEL` должны ссылаться на `ORDER CREATE`.
7. `ALGO_ORDER AMEND` / `ALGO_ORDER CANCEL` должны ссылаться на `ALGO_ORDER CREATE`.
8. Нельзя ссылаться на action из другой `StrategyDetail`.

## 7.5. Резолв targetActionKey при сохранении стратегии

После валидации стратегия сохраняет actions как отдельные записи.

На этом этапе:

```text
targetActionKey
  -> резолвится в target StrategyAction
```

В Java domain/entity лучше хранить объектную ссылку на target action.

В БД это будет FK.

Runtime уже работает через `strategyActionId`, а не через `strategyActionKey`.

Инвариант стратегии:

```text
UNIQUE(strategy_detail_id, key)
```

## 7.6. Пример target для grid cancel

CREATE actions:

```text
grid-entry-long-1
grid-entry-long-2
grid-entry-short-3
grid-entry-short-4
```

CANCEL actions:

```text
cancel-grid-entry-long-1  -> targetActionKey = grid-entry-long-1
cancel-grid-entry-long-2  -> targetActionKey = grid-entry-long-2
cancel-grid-entry-short-3 -> targetActionKey = grid-entry-short-3
cancel-grid-entry-short-4 -> targetActionKey = grid-entry-short-4
```

Runtime:

```text

  -> имеет target StrategyAction, полученный из targetActionKey при сохранении стратегии
  -> ищет DealActionState(dealId, strategyActionId = target StrategyAction.id)
  -> получает RuntimeTarget
  -> создаёт CANCEL_ORDER / CANCEL_ALGO_ORDER payload с конкретным ID сущности
```

# 8. CREATE -> SUBMIT -> REFRESH

Для сущностей, которые создаются на бирже, используется трёхшаговая схема:

```text
CREATE_* -> SUBMIT_* -> REFRESH_*
```

## 8.1. CREATE

Создаёт локальную сущность в БД.

Пример:

```text
CREATE_ORDER
  -> создать Order в БД
  -> status = CREATED
  -> externalId = null
  -> internalId заполнен
  -> обновить DealActionState.target = RuntimeTarget(ORDER, orderId)
  -> DealActionState.status = CREATED
```

CREATE не ходит на биржу.

Инвариант:

```text
CREATE_* сохраняет runtime-сущность и DealActionState в одной транзакции.
```

## 8.2. SUBMIT

Отправляет локальную сущность на биржу или восстанавливает факт отправки.

Важно:

```text
Order.CREATED + externalId = null
```

не означает, что order точно ещё не отправляли на биржу.

Алгоритм:

```text
1. Найти локальный Order.
2. Взять clientOrderId = order.internalId.
3. Проверить биржу по clientOrderId.
4. Если order найден:
   -> обновить локальную сущность из external snapshot.
5. Если order не найден:
   -> отправить order на биржу.
6. Обновить DealActionState.status.
```

Для algo-order аналогично:

```text
1. Найти локальный AlgoOrder.
2. Взять algoClOrdId = algoOrder.internalId.
3. Проверить биржу по algoClOrdId.
4. Если algo-order найден:
   -> обновить локальную сущность из external snapshot.
5. Если algo-order не найден:
   -> отправить algo-order на биржу.
6. Обновить DealActionState.status.
```

## 8.3. REFRESH

Подтверждает фактическое состояние.

Пример:

```text
SUBMIT_ORDER
  -> REFRESH_ORDER
  -> REFRESH_PENDING_ORDERS
  -> REFRESH_POSITION
```

FSM двигает статус сделки только после подтверждения фактов.

ACK от биржи не является runtime-truth. Runtime-truth строится на refresh/search/history facts.

# 9. Как обновляется DealActionState

## 9.1. CREATE action

```text
PLANNED
  -> CREATED
  -> SUBMITTED
  -> COMPLETED
```

Пояснение:

* `CREATED` — локальная сущность создана в БД.
* `SUBMITTED` — команда отправки была выполнена или могла быть выполнена, но биржевой факт ещё не подтверждён.
* `COMPLETED` — refresh/search/history подтвердили нужный финальный факт, action больше не требует обработки.

## 9.2. AMEND action

`AMEND` action не создаёт новую runtime-сущность.

Он должен изменить сущность, созданную target `CREATE` action.

Алгоритм:

```text
1. Взять target StrategyAction из AMEND action.
2. Найти DealActionState по dealId + target StrategyAction.id.
3. Проверить, что RuntimeTarget.entityType совместим с AMEND-командой.
4. Взять RuntimeTarget.entityId.
5. Создать payload AMEND_ORDER / AMEND_ALGO_ORDER с конкретным ID сущности.
6. Обновить DealActionState текущего AMEND action.
```

Lifecycle AMEND action:

```text
PLANNED
  -> SUBMITTED
  -> COMPLETED
```

## 9.3. CANCEL action

`CANCEL` action не создаёт новую runtime-сущность.

Он должен отменить сущность, созданную target `CREATE` action.

Алгоритм:

```text
1. Взять target StrategyAction из CANCEL action.
2. Найти DealActionState по dealId + target StrategyAction.id.
3. Проверить, что RuntimeTarget.entityType совместим с CANCEL-командой.
4. Взять RuntimeTarget.entityId.
5. Создать payload CANCEL_ORDER / CANCEL_ALGO_ORDER с конкретным ID сущности.
6. Обновить DealActionState текущего CANCEL action.
```

Lifecycle CANCEL action:

```text
PLANNED
  -> SUBMITTED
  -> COMPLETED
```

## 9.4. Retry состояния

Если команда упала, но может быть повторена:

```text
current status
  -> RETRY_PENDING
```

В `Retryable` обновляются:

```text
attemptCount
nextRetryAt
lastError
```

`lastError` — это объект `RetryError`, а не пара строк `lastErrorCode` / `lastError`.

Когда наступает `nextRetryAt`, orchestrator может снова попробовать action.

Если `attemptCount >= maxAttempts`:

```text
RETRY_PENDING -> FAILED
```

Дальше FSM решает по критичности этапа:

```text
безопасно завершить / MARK_DEAL_ERROR / EXECUTE_KILL_SWITCH
```

Если обнаружены неизвестные или чужие live-хвосты на бирже, это anomaly/safety-flow, а не штатный cleanup сделки.

# 11. Retry policy

Retry policy — это техническая политика исполнения команд.

На первом этапе храним её в конфиге приложения, а не в БД.

Причина:

```text
retry policy — это не часть торговой стратегии,
а техническая политика обработки ошибок и неизвестных результатов.
```

## 11.1. Пример application.yml

```yaml
service-command-retry:
  default-policy:
    max-attempts: 3
    initial-delay: 1s
    max-delay: 30s
    backoff: EXPONENTIAL

  policies:
    SUBMIT_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 30s
      backoff: EXPONENTIAL

    SUBMIT_ALGO_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 30s
      backoff: EXPONENTIAL

    REFRESH_ORDER:
      max-attempts: 10
      initial-delay: 500ms
      max-delay: 10s
      backoff: FIXED

    REFRESH_ALGO_ORDERS:
      max-attempts: 10
      initial-delay: 500ms
      max-delay: 10s
      backoff: FIXED

    CANCEL_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 20s
      backoff: EXPONENTIAL

    CANCEL_ALGO_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 20s
      backoff: EXPONENTIAL

    CLOSE_POSITION:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 15s
      backoff: EXPONENTIAL
```

## 11.4.1. Уточнение после Q6 и Q8

Текущий enum выше сохраняется как исторический черновик модели ошибки, но для новой runtime-политики фиксируем более простое правило.

На первом этапе не используем отдельные runtime-коды:

```text
UNKNOWN_RESULT
EXCHANGE_TIMEOUT
```

Вместо них используем общий код:

```text
EXCHANGE_ERROR
```

`EXCHANGE_ERROR` означает проблему взаимодействия с биржей:

```text
timeout;
connection reset;
gateway/API error;
ошибка exchange client;
executor не смог надёжно завершить exchange operation.
```

FSM не строит отдельную ветку по `EXCHANGE_ERROR`.
Каждый проход FSM и так сначала обновляет exchange facts через refresh/search/history, затем анализирует `DealContext`, `DealActionState` и runtime-сущности.

Для unexpected exceptions используем 3 базовых кода:

```java
public enum RuntimeErrorCode {

    /** Баг приложения, NPE, mapper error, unexpected state, внутренняя техническая проблема. */
    INTERNAL_ERROR,

    /** Ошибка взаимодействия с биржей: timeout, gateway/API error, exchange client error. */
    EXCHANGE_ERROR,

    /** Нарушение инварианта/валидации, которое не должно было попасть в runtime. */
    VALIDATION_ERROR
}
```

Retryable по умолчанию:

```text
EXCHANGE_ERROR может быть retryable.
INTERNAL_ERROR и VALIDATION_ERROR по умолчанию non-retryable.
```

## 11.6. Как работает retry

```text
Executor упал
  -> ServiceCommandExecutor ловит ошибку
  -> RetryPolicyService получает policy по ServiceCommandType
  -> увеличивает Retryable.attemptCount
  -> считает nextRetryAt
  -> сохраняет RetryError в lastError
  -> переводит DealActionState в RETRY_PENDING

Если attemptCount >= maxAttempts
  -> DealActionState.status = FAILED
  -> FSM решает, что делать дальше
```

## 11.7. Важное правило для опасных команд

Для команд:

```text
SUBMIT_*
CANCEL_*
CLOSE_POSITION
```

перед повтором обязательно сначала делать refresh/search на бирже.

Причина:

> Предыдущий запрос мог реально выполниться на бирже, даже если сервис не получил ответ.

Примеры:

```text
SUBMIT_ORDER retry
  -> сначала найти order по clientOrderId
  -> если найден, восстановить локальное состояние
  -> если не найден, отправить заново

CANCEL_ORDER retry
  -> сначала refresh order
  -> если уже CLOSED, считать cancel успешным
  -> если ещё active, повторить cancel

CLOSE_POSITION retry
  -> сначала refresh position
  -> если позиции уже нет, считать close успешным
  -> если позиция ещё active, повторить close
```

## 12.1. Order.Status

```java
    /** Ордер закрыт: отменён, финализирован или больше не активен. */
    CLOSED,

    /** Не удалось создать, отправить, обновить или корректно синхронизировать ордер. */
    FAILED
}
```

Важно:

* `ACTIVE` — это не “после fill”, а “активен на бирже”.
* `PARTIALLY_COMPLETED` и `COMPLETED` отвечают за fill-состояния.
* `strategyActionId` должен быть убран из `Order`.

## 12.2. AlgoOrder.Status

```java
public enum Status {

    /** Запись создана локально, ещё не отправляли на биржу. */
    CREATED,

    /** Algo-order отправлен на биржу, но ещё не подтверждён как активный. */
    PENDING,

    /** Algo-order реально активен на бирже. */
    ACTIVE,

    /** Algo-order закрыт: отменён, сработал или больше не активен. */
    CLOSED,

    /** Не удалось создать, отправить, обновить или корректно синхронизировать algo-order. */
    FAILED
}
```

Важно:

* `strategyActionId` должен быть убран из `AlgoOrder`.
* `CloseReason` у `AlgoOrder` нужно расширить.

Рекомендуемый минимум для `AlgoOrder.CloseReason`:

```java
public enum CloseReason {
    TRIGGERED,
    CANCELLED_BY_STRATEGY,
    REPLACED_BY_AMEND,
    POSITION_CLOSED,
    KILL_SWITCH,
    EXCHANGE_CANCELLED,
    UNKNOWN
}
```

## 12.3. AttachedAlgoOrder.Status

```java
public enum Status {
    CREATED,
    ATTACHED,
    ACTIVE,
    CLOSED,
    FAILED
}
```

Комментарий:

> `ATTACHED` нужен отдельно от `ACTIVE`, потому что attached protection может быть привязан к entry order до того, как реально станет активной защитой после fill.

## 12.4. Position.Status

```java
public enum Status {
    ACTIVE,
    CLOSED,
    ERROR
}
```

`Position.CloseReason` в текущей модели уже достаточно подробный.

# 13. Executor'ы

## 13.1. CreateOrderExecutor

Получает `CREATE_ORDER`.

Делает:

* создаёт локальный `Order`;
* ставит статус `CREATED`;
* генерирует `internalId`;
* сохраняет рассчитанные параметры;
* создаёт attached protection внутри order, если она есть;
* обновляет `DealActionState.target = RuntimeTarget(ORDER, orderId)`;
* обновляет `DealActionState.status = CREATED`.

Не делает:

* не ходит на биржу;
* не решает, нужен ли вход;
* не пересчитывает цену;
* не проверяет стратегические условия.

## 13.2. SubmitOrderExecutor

Получает `SUBMIT_ORDER`.

Делает:

1. Загружает локальный `Order`.
2. Если `externalId` уже есть — команда считается выполненной или требует refresh.
3. Если `externalId` пустой — ищет order на бирже по `clientOrderId = order.internalId`.
4. Если order найден — обновляет локальный order из биржевого snapshot.
5. Если order не найден — отправляет order на биржу.
6. Обновляет `DealActionState.status`.

Recoverability:

```text
если приложение упало после отправки на биржу,
но до сохранения externalId,
следующий submit найдёт order по clientOrderId
и восстановит локальное состояние.
```

## 13.3. RefreshOrderExecutor

Получает `REFRESH_ORDER`.

Делает:

* загружает локальный order;
* получает актуальное состояние с биржи;
* обновляет локальный order;
* обновляет статусы исполнения;
* при необходимости обновляет `DealActionState`.

## 13.4. AmendOrderExecutor

Получает `AMEND_ORDER`.

Делает:

* загружает локальный order по `payload.orderId`;
* отправляет amend на биржу;
* сохраняет ack / технический результат;
* дальше факт подтверждается refresh-командой.

Не решает, хорошая ли новая цена.

## 13.5. CancelOrderExecutor

Получает `CANCEL_ORDER`.

Делает:

* загружает локальный order по `payload.orderId`;
* отправляет cancel на биржу;
* сохраняет ack / технический результат;
* дальше факт отмены подтверждается refresh-командой.

## 13.6. CreateAlgoOrderExecutor

Получает `CREATE_ALGO_ORDER`.

Делает:

* создаёт локальный `AlgoOrder`;
* ставит статус `CREATED`;
* генерирует `internalId`;
* сохраняет рассчитанные SL/TP/trailing-параметры;
* обновляет `DealActionState.target = RuntimeTarget(ALGO_ORDER, algoOrderId)`;
* обновляет `DealActionState.status = CREATED`.

Не ходит на биржу.

## 13.7. SubmitAlgoOrderExecutor

Получает `SUBMIT_ALGO_ORDER`.

Делает:

1. Загружает локальный `AlgoOrder`.
2. Если `externalId` уже есть — команда считается выполненной или требует refresh.
3. Если `externalId` пустой — ищет algo-order на бирже по `algoClOrdId = algoOrder.internalId`.
4. Если algo-order найден — обновляет локальное состояние.
5. Если не найден — отправляет algo-order на биржу.
6. Обновляет `DealActionState.status`.

## 13.8. RefreshAlgoOrderExecutor

Получает `REFRESH_ALGO_ORDER`.

Делает:

* загружает локальный algo-order;
* получает актуальное состояние с биржи;
* обновляет локальную сущность;
* при необходимости обновляет `DealActionState`.

## 13.9. AmendAlgoOrderExecutor

Получает `AMEND_ALGO_ORDER`.

Делает:

* загружает локальный algo-order по `payload.algoOrderId`;
* выполняет amend или safe replace;
* сохраняет технический результат;
* факт подтверждается refresh.

## 13.10. CancelAlgoOrderExecutor

Получает `CANCEL_ALGO_ORDER`.

Делает:

* загружает локальный algo-order по `payload.algoOrderId`;
* отправляет cancel на биржу;
* сохраняет технический результат;
* факт отмены подтверждается refresh.

## 13.11. ClosePositionExecutor

Получает `CLOSE_POSITION`.

Делает:

* загружает позицию;
* закрывает позицию полностью;
* сохраняет технический результат;
* дальше факт полного закрытия подтверждается `REFRESH_POSITION` и `REFRESH_FILLS`.

Важно:

```text
ClosePositionExecutor не выполняет partial close.
Частичный выход выполняется через Order / AlgoOrder executor flow.
```

Дополнение после Q5:

```text
ClosePositionExecutor не смешивает закрытие позиции с доменной автоотменой ордеров.
```

Для OKX adapter может технически проставить `autoCxl=true`, но это не часть доменного payload и не источник бизнес-логики.

После выполнения `CLOSE_POSITION` FSM/handler обязан подтвердить факты отдельными refresh-командами:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
```

Только после этих фактов handler решает:

```text
позиция закрыта;
known live orders/algo-orders нужно отменить;
unknown live tails являются anomaly/safety-flow;
можно переходить к финализации выхода.
```

## 13.12. RefreshFillsExecutor

`REFRESH_FILLS` — runtime read-only команда.

На первом этапе отдельную persisted entity `Fill` не вводим.
`RefreshFillsExecutor` загружает fills с биржи, сопоставляет их с известными `Order` / `AlgoOrder` / `Position` facts и обновляет вложенные runtime-сущности.

Правило:

```text
RefreshFillsExecutor не обновляет Deal напрямую.
```

`Deal` обновляет FSM handler по фактам вложенных сущностей после refresh-контура.

`REFRESH_FILLS` должен быть идемпотентным:

```text
повторный вызов не должен задваивать filled size;
повторный вызов не должен задваивать fee;
повторный вызов не должен задваивать realized pnl;
повторный вызов должен приводить локальные факты к состоянию биржи.
```

Один общий executor на первом этапе:

```text
RefreshFillsExecutor
```

Он сам понимает контекст команды и умеет обновлять связанные runtime-сущности без передачи этой ответственности в отдельный сервис.

# 14. Восстановление после рестарта

FSM не должна помнить, на каком действии упал процесс.

После рестарта она заново собирает:

* `DealContext`;
* `DealActionState`;
* runtime-сущности;
* exchange snapshots.

Пример:

```text
StrategyStep GRID_ENTRY:
  action key = grid-entry-long-1
  action key = grid-entry-long-2
  action key = grid-entry-short-3
  action key = grid-entry-short-4
```

При сохранении стратегии эти `key` резолвятся во внутренние `strategyActionId`.

До рестарта создали 2 order.

После рестарта:

```text
DealActionState(strategyActionId для grid-entry-long-1) -> target.entityId = order1, status = CREATED
DealActionState(strategyActionId для grid-entry-long-2) -> target.entityId = order2, status = SUBMITTED
DealActionState(strategyActionId для grid-entry-short-3) -> отсутствует
DealActionState(strategyActionId для grid-entry-short-4) -> отсутствует
```

FSM делает:

```text
grid-entry-long-1 -> submit / refresh
grid-entry-long-2 -> refresh
grid-entry-short-3 -> create
grid-entry-short-4 -> create
```

Для `AMEND` / `CANCEL`:

```text
cancel-grid-entry-long-1
  -> targetActionKey = grid-entry-long-1
  -> при сохранении стратегии targetActionKey резолвится в target StrategyAction
  -> найти DealActionState(dealId, target StrategyAction.id)
  -> получить RuntimeTarget(entityType = ORDER, entityId = order1)
  -> создать CANCEL_ORDER(orderId = order1)
```

Подробные правила recovery по FSM-статусам описаны в документе:

```text
FSM этапы сделки
```

# 15. ServiceCommandExecutionHistory

## 15.0. Что обязательно должно попасть в аудит после Q1–Q4

`ServiceCommandExecutionHistory` должен позволять восстановить timeline по следующим сценариям:

```text
1. graceful shutdown из-за Strategy.DELETED;
2. graceful shutdown из-за MARKET_DATA_EXPIRED;
3. protection switch:
   - main protection created/submitted/refreshed;
   - temporary attached protection cancelled;
4. skip switch:
   - если switch не требовался, это может быть отражено диагностическим событием в timeline;
5. REFRESH_BALANCE как часть risk/sanity-check.
```

Подробная модель timeline и entry context описывается в документе `05. Аудит и история исполнения`.


Формат `ServiceCommandExecutionHistory` детализируется в документе:

```text
Аудит и история исполнения
```

В рамках этой доки фиксируем только принцип:

> История команд нужна для аудита, расследования и timeline сделки.
>
> Runtime-логика FSM работает по `DealActionState + DealContext + runtime-сущностям`.

История не влияет на:

* жизненный цикл сделки;
* выполнение сервисных команд;
* retry policy;
* расчёт цены;
* runtime recovery.

Команда обновления баланса `REFRESH_BALANCE` тоже должна попадать в историю исполнения команд.

Баланс не является управляемой торговой сущностью как `Order`, `AlgoOrder` или `Position`, но сам факт обновления балансового snapshot важен для расследования и timeline.

# 16. Итоговые решения

1. `ServiceCommand` — атомарная команда, а не торговое решение.
2. Стратегия не хранит сервисные команды.
3. FSM выбирает применимые steps/actions и создаёт команды через command-layer.
4. Executor не принимает торговых решений.
5. Для создаваемых на бирже сущностей используем `CREATE -> SUBMIT -> REFRESH`.
6. `CREATE_*` создаёт локальную сущность и не ходит на биржу.
7. `SUBMIT_*` отправляет локальную сущность или восстанавливает факт отправки по client id.
8. `REFRESH_*` подтверждает фактическое состояние.
9. Из `Order` и `AlgoOrder` нужно убрать `strategyActionId`.
10. `DealActionState` хранит runtime-связь action -> entity через `strategyActionId` и `RuntimeTarget`.
11. `DealActionState` наследуется от `Retryable`.
12. Retry-ошибка хранится как объект `RetryError`, а не как отдельные поля `lastErrorCode` / `lastError`.
13. Retry policy храним в application config.
14. Для опасных команд перед retry сначала делаем refresh/search на бирже.
15. История исполнения команд не является источником runtime-логики FSM.
16. `REFRESH_BALANCE` должен попадать в `ServiceCommandExecutionHistory`.

# 17. Инвариант частичного выхода

`CLOSE_POSITION` используется только для полного закрытия позиции.

```text
partial close через CLOSE_POSITION запрещён всегда.
```

Частичное уменьшение позиции выполняется только через трассируемые runtime-сущности:

```text
StrategyOrderAction / StrategyAlgoOrderAction
  -> CREATE_ORDER / CREATE_ALGO_ORDER
  -> SUBMIT_ORDER / SUBMIT_ALGO_ORDER
  -> REFRESH_* / fills / history
  -> DealActionState.COMPLETED
```

Обязательные свойства partial exit action:

* reduce-only semantics;
* stable client id;
* связь через `DealActionState`;
* восстановление через fills/history/refresh;
* запрет на увеличение позиции.

# 18. Дополнение после Q2–Q8

Этот раздел добавлен без удаления существующих решений command-layer.

## 18.1. Risk-result и command-layer

Risk-layer вынесен в отдельный документ `Оценка рисков`.

Command-layer не решает risk-policy самостоятельно.

Flow:

```text
StrategyActionCalculator
  -> CalculatedStrategyAction
  -> RiskValidator
  -> RiskBlockResolver, если BLOCKED
  -> ServiceCommandFactory, если action разрешён
```

Если risk result блокирующий, торговая команда для action не создаётся.
Handler получает результат `RiskBlockResolver` и решает, как двигать `Deal` дальше.

## 18.2. ServiceCommandFactory создаёт одну актуальную команду

`ServiceCommandFactory` не создаёт всю цепочку команд заранее.

```text
CREATE_* -> SUBMIT_* -> REFRESH_*
```

это lifecycle, а не единый пакет команд.

Каждая следующая команда создаётся только после нового анализа:

```text
DealContext;
DealActionState;
runtime entities;
exchange facts;
retry policy;
nextRetryAt.
```

## 18.3. EXCHANGE_ERROR вместо UNKNOWN_RESULT / EXCHANGE_TIMEOUT

`UNKNOWN_RESULT` не используем на первом этапе.
`EXCHANGE_TIMEOUT` отдельно не используем.

Для timeout, connection reset, gateway/API error и других проблем биржи используется общий код:

```text
EXCHANGE_ERROR
```

`ACK` не является runtime-truth.
После `ACK` action может перейти в `SUBMITTED`, но финальный факт подтверждается только через refresh/search/history.

## 18.4. Unexpected exceptions

Unexpected exceptions не превращаем в `CalculationError`.

Для runtime-классификации используем:

```text
INTERNAL_ERROR
EXCHANGE_ERROR
VALIDATION_ERROR
```

Общая реакция:

```text
Deal -> ERROR
дальше ErrorHandler / safety-flow
```

Если ошибка связана с конкретным action:

```text
retryable EXCHANGE_ERROR -> DealActionState.RETRY_PENDING
non-retryable INTERNAL_ERROR / VALIDATION_ERROR -> DealActionState.FAILED
```

## 18.5. CLOSE_POSITION и OKX autoCxl

`CLOSE_POSITION` остаётся доменной атомарной командой полного закрытия позиции.

В payload не добавляем:

```text
autoCancelOrders
autoCxl
```

OKX-specific adapter может технически проставить `autoCxl=true`, но handler всё равно обязан выполнить refresh-контур и отдельно дочистить известные live `Order` / `AlgoOrder`.

## 18.6. REFRESH_FILLS

`REFRESH_FILLS` — runtime read-only команда.

Fill как отдельную persisted entity на первом этапе не храним.

Один executor:

```text
RefreshFillsExecutor
```

Он загружает fills, сопоставляет их с известными `Order` / `AlgoOrder` / `Position` facts и обновляет вложенные runtime-сущности.

`Deal` напрямую не обновляет executor; `Deal` обновляет FSM handler по результатам refresh-фактов.
