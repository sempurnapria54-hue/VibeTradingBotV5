# 02. Сервисные команды

> Статус документа: подробная дока по `ServiceCommand`, payload, executor'ам, `CREATE -> SUBMIT -> REFRESH` и обновлению `DealActionState`.
>
> Связанная дока: `01. Жизненный цикл сделки`.

---

# 1. Главная идея

`ServiceCommand` — это атомарная runtime-команда, которую можно передать executor'у.

Стратегия не исполняется напрямую.

Flow такой:

```text
StrategyAction
  -> StrategyActionCalculator
  -> рассчитанные параметры
  -> ServiceCommandFactory
  -> ServiceCommand
  -> ServiceCommandExecutor
  -> конкретный Executor
```

`ServiceCommand` отвечает на вопрос:

> Какую простую операцию нужно выполнить над runtime-сущностью?

Executor отвечает на вопрос:

> Как технически выполнить эту операцию?

Executor не принимает торговых решений.

# 3. ServiceCommand

`ServiceCommand` должен быть объектом, а не только enum.

Минимальная модель:

```java
public class ServiceCommand {

    /**
     * Тип атомарной операции.
     */
    private ServiceCommandType type;

    /**
     * Сделка, в рамках которой выполняется команда.
     */
    private Long dealId;

    /**
     * Runtime-состояние action стратегии.
     * Через него команда связывается с StrategyAction,
     * но сама биржевая сущность не хранит strategyActionId.
     */
    private Long dealActionStateId;

    /**
     * Параметры выполнения команды.
     */
    private ServiceCommandPayload payload;
}
```

Важно:

* `ServiceCommand` не обязан хранить `strategyId` и `strategyDetailsId`.
* Если нужно понять происхождение команды, это можно сделать через `DealActionState` и историю исполнения команд.
* Аудит и история не должны быть источником runtime-логики FSM.

# 4. DealActionState

`DealActionState` — runtime-проекция выполнения action стратегии.

Она нужна для восстановления после рестарта.

Она не является аудитом.

```java
public class DealActionState {

    /**
     * Технический ID записи.
     */
    private Long id;

    /**
     * Сделка, в рамках которой выполняется action стратегии.
     */
    private Long dealId;

    /**
     * Стабильный ID action из immutable-стратегии.
     */
    private Long strategyActionId;

    /**
     * Тип целевой runtime-сущности.
     */
    private TargetEntityType targetEntityType;

    /**
     * ID runtime-сущности, если action уже материализован.
     */
    private Long targetEntityId;

    /**
     * Текущее состояние выполнения action.
     */
    private DealActionStateStatus status;

    /**
     * Количество попыток исполнения.
     */
    private Integer attemptCount;

    /**
     * Последняя ошибка выполнения.
     */
    private String lastError;
}
```

```java
public enum TargetEntityType {

    /**

     */
    ORDER,

    /**
     * Algo-order: SL / TP / OCO / trailing / trigger.
     */
    ALGO_ORDER,

    /**
     * Position.
     */
    POSITION,

    /**
     * Deal как агрегат.
     */
    DEAL,

    /**
     * Баланс или balance snapshot.
     */
    BALANCE,

    /**
     * Нет конкретной target-сущности.
     */
    NONE
}
```

```java
public enum DealActionStateStatus {

    /**
     * Action ожидает выполнения.
     */
    PLANNED,

    /**
     * Локальная runtime-сущность создана в БД.
     */
    CREATED,

    /**
     * Сущность отправлена на биржу или отправка начата.
     */
    SUBMITTED,

    /**
     * Биржа подтвердила фактическое состояние.
     */
    CONFIRMED,

    /**
     * Action выполнен и больше не требует обработки.
     */
    COMPLETED,

    /**
     * Action не удалось выполнить.
     */
    FAILED,

    /**
     * Action больше не нужен из-за изменения состояния сделки.
     */
    SKIPPED
}
```

Ключевой инвариант:

```text
UNIQUE(deal_id, strategy_action_id)
```

Важно:

> `strategyActionId` не хранится в `Order`, `AlgoOrder`, `Position`.
>
> Связь action стратегии с runtime-сущностью хранится в `DealActionState`.

# 5. CREATE -> SUBMIT -> REFRESH

Для сущностей, которые создаются на бирже, используется трёхшаговая схема:

```text
CREATE_* -> SUBMIT_* -> REFRESH_*
```

## CREATE

Создаёт локальную сущность в БД.

Пример:

```text
CREATE_ORDER
  -> создать Order в БД
  -> status = CREATED
  -> externalId = null
  -> internalId заполнен
  -> обновить DealActionState.targetEntityId
  -> DealActionState.status = CREATED
```

CREATE не ходит на биржу.

---

## SUBMIT

Отправляет локальную сущность на биржу или восстанавливает факт отправки.

Важно:

```text
Order.CREATED + externalId = null
```

не означает, что order точно ещё не отправляли на биржу.

Правильный алгоритм:

```text
1. Найти локальный Order.
2. Взять clientOrderId = order.internalId.
3. Проверить биржу по clientOrderId.
4. Если order найден:
   -> обновить локальную сущность из external snapshot.
5. Если order не найден:
   -> отправить order на биржу.
6. Обновить DealActionState.status.
```

---

## REFRESH

Подтверждает фактическое состояние.

Пример:

```text
SUBMIT_ORDER
  -> REFRESH_ORDER
  -> REFRESH_PENDING_ORDERS
  -> REFRESH_POSITION
```

FSM двигает статус сделки только после подтверждения фактов.

# 7. Executor'ы

## 7.1. CreateOrderExecutor

Получает `CREATE_ORDER`.

Делает:

* создаёт локальный `Order`;
* ставит статус `CREATED`;
* генерирует `internalId`;
* сохраняет рассчитанные параметры;
* создаёт attached protection внутри order, если она есть;
* обновляет `DealActionState.targetEntityId`;
* обновляет `DealActionState.status = CREATED`.

Не делает:

* не ходит на биржу;
* не решает, нужен ли вход;
* не пересчитывает цену;
* не проверяет стратегические условия.

---

## 7.2. SubmitOrderExecutor

Получает `SUBMIT_ORDER`.

Делает:

1. Загружает локальный `Order`.
2. Если `externalId` уже есть — команда считается выполненной или требует refresh.
3. Если `externalId` пустой — ищет order на бирже по `clientOrderId = order.internalId`.
4. Если order найден — обновляет локальный order из биржевого snapshot.
5. Если order не найден — отправляет order на биржу.
6. Обновляет `DealActionState.status`.

Recoverability:

```text
если приложение упало после отправки на биржу,
но до сохранения externalId,
следующий submit найдёт order по clientOrderId
и восстановит локальное состояние.
```

---

## 7.3. RefreshOrderExecutor

Получает `REFRESH_ORDER`.

Делает:

* загружает локальный order;
* получает актуальное состояние с биржи;
* обновляет локальный order;
* обновляет статусы исполнения;
* при необходимости обновляет `DealActionState`.

---

## 7.4. AmendOrderExecutor

Получает `AMEND_ORDER`.

Делает:

* загружает локальный order;
* отправляет amend на биржу;
* сохраняет ack / технический результат;
* дальше факт подтверждается refresh-командой.

Не решает, хорошая ли новая цена.

---

## 7.5. CancelOrderExecutor

Получает `CANCEL_ORDER`.

Делает:

* загружает локальный order;
* отправляет cancel на биржу;
* сохраняет ack / технический результат;
* дальше факт отмены подтверждается refresh-командой.

---

## 7.6. CreateAlgoOrderExecutor

Получает `CREATE_ALGO_ORDER`.

Делает:

* создаёт локальный `AlgoOrder`;
* ставит статус `CREATED`;

* сохраняет рассчитанные SL/TP/trailing-параметры;
* обновляет `DealActionState.targetEntityId`;
* обновляет `DealActionState.status = CREATED`.

Не ходит на биржу.

---

## 7.7. SubmitAlgoOrderExecutor

Получает `SUBMIT_ALGO_ORDER`.

Делает:

1. Загружает локальный `AlgoOrder`.

6. Обновляет `DealActionState.status`.

---

## 7.8. RefreshAlgoOrderExecutor

Получает `AMEND_ALGO_ORDER`.

Делает:

* факт подтверждается refresh.

Получает `CANCEL_ALGO_ORDER`.

Делает:

Получает `CLOSE_POSITION`.

# 8. Восстановление после рестарта

FSM не должна помнить, на каком действии упал процесс.

После рестарта она заново собирает:

* `DealContext`;
* `DealActionState`;
* runtime-сущности;
* exchange snapshots.

Пример:

```text
StrategyStep GRID_ENTRY:
  action #1
  action #2
  action #3
  action #4
```

До рестарта создали 2 order.

После рестарта:

```text
DealActionState(action #1) -> targetEntityId = order1, status = CREATED
DealActionState(action #2) -> targetEntityId = order2, status = SUBMITTED
DealActionState(action #3) -> отсутствует
DealActionState(action #4) -> отсутствует
```

FSM делает:

```text
action #1 -> submit / refresh
action #2 -> refresh
action #3 -> create
action #4 -> create
```

---

# 9. Почему не используем аудит для runtime-логики

Аудит отвечает на вопрос:

> Что произошло и почему?

FSM отвечает на вопрос:

> Что нужно сделать дальше?

Поэтому FSM не должна читать аудит, чтобы принимать runtime-решения.

Для runtime-восстановления используется:

```text
DealActionState + DealContext + runtime-сущности
```

Для истории используется:

```text
ServiceCommandExecutionHistory + EntityHistory
```
