# 02. Сервисные команды

> Статус документа: подробная дока по `ServiceCommand`, payload, executor'ам, `CREATE -> SUBMIT -> REFRESH`, retry policy и обновлению `DealActionState`.
>
> Связанная дока: `01. Жизненный цикл сделки`.

---

# 1. Главная идея

`ServiceCommand` — это атомарная runtime-команда, которую можно передать executor'у.

Стратегия не исполняется напрямую.

Flow такой:

```text
StrategyAction
  -> StrategyActionCalculator
  -> рассчитанные параметры
  -> ServiceCommandFactory
  -> ServiceCommand
  -> ServiceCommandExecutor
  -> конкретный Executor
```

`ServiceCommand` отвечает на вопрос:

> Какую простую операцию нужно выполнить над runtime-сущностью?

Executor отвечает на вопрос:

> Как технически выполнить эту операцию?

Executor не принимает торговых решений.

---

# 2. Важные принципы

## 2.1. Стратегия не знает runtime ID сущностей

Стратегия immutable и описывает ожидаемые действия заранее.

В момент создания стратегии ещё не существует:

* `orderId`;
* `algoOrderId`;
* `positionId`.

Поэтому `StrategyAction` не должен ссылаться напрямую на runtime-сущность.

Для `AMEND` и `CANCEL` стратегия указывает, какое ранее описанное действие стратегии является target.

Для этого используется поле:

```text
targetActionKey
```

При сохранении стратегии `targetActionKey` валидируется и резолвится во внутреннюю ссылку на target action.

---

## 2.2. Runtime-связь хранится в DealActionState

`Order`, `AlgoOrder`, `Position` остаются чистыми runtime-сущностями биржи.

В них не храним:

```text
strategyActionId
role
level стратегии
```

Связь хранится отдельно:

```text
StrategyAction.id
  -> DealActionState.strategyActionId
     -> RuntimeTarget
        -> entityType
        -> entityId
```

`StrategyAction.key` нужен для JSON/API и резолва ссылок между actions при сохранении стратегии.

Runtime работает через `strategyActionId`, а не через `strategyActionKey`.

---

## 2.3. Аудит не источник runtime-логики

Аудит отвечает на вопрос:

> Что произошло и почему?

FSM отвечает на вопрос:

> Что делать дальше?

Поэтому FSM не должна читать историю, чтобы принимать runtime-решения.

Для восстановления используется:

```text
DealContext + DealActionState + runtime-сущности + exchange snapshots
```

# 4. ServiceCommand

`ServiceCommand` должен быть объектом, а не только enum.

```java
public class ServiceCommand {

    /**
     * Тип атомарной операции.
     */
    private ServiceCommandType type;

    /**
     * Сделка, в рамках которой выполняется команда.
     */
    private Long dealId;

    /**
     * Runtime-состояние action стратегии.
     *
     * Через него команда связывается с StrategyAction,
     * но сама биржевая сущность не хранит strategyActionId.
     */
    private Long dealActionStateId;

    /**
     * Параметры выполнения команды.
     */
    private ServiceCommandPayload payload;
}
```

Важно:

* `ServiceCommand` не обязан хранить `strategyId` и `strategyDetailId`.
* Если нужно понять происхождение команды, это можно сделать через `DealActionState` и историю исполнения команд.
* Аудит и история не должны быть источником runtime-логики FSM.

# 5. StrategyAction.key и targetActionKey

## 5.1. Зачем нужен StrategyAction.key

Для валидации стратегии и ссылок между actions нужно понимать:

> На какое действие стратегии ссылается `AMEND` / `CANCEL`?

Например:

```text
grid-entry-long-1
  -> должен создать Order

cancel-grid-entry-long-1
  -> должен отменить именно Order, созданный action grid-entry-long-1
```

Для этого у каждого action есть явно заданный ключ:

```text
key
```

---

## 5.2. key задаётся в JSON стратегии

`key` задаётся явно в JSON при создании стратегии.

Он не генерируется автоматически.

Пример CREATE action:

```jsonc
{
  "actionKind": "ORDER",
  "key": "grid-entry-long-1",
  "actionType": "CREATE",
  "orderType": "ENTRY",
  "direction": "LONG",
  "allocationPercents": 25,
  "level": 1,
  "placement": {
    "baseType": "RANGE_LOW",
    "priceSource": null,
    "offsetSide": "ABOVE",
    "percents": 10
  },
  "attachedProtection": null
}
```

Пример CANCEL action:

```jsonc
{
  "actionKind": "ORDER",
  "key": "cancel-grid-entry-long-1",
  "actionType": "CANCEL",
  "targetActionKey": "grid-entry-long-1",
  "orderType": "ENTRY",
  "direction": "LONG",
  "allocationPercents": null,
  "level": 1,
  "placement": null,
  "attachedProtection": null
}
```

---

## 5.3. StrategyAction

Базово каждый action должен иметь `key`.

```java
public interface StrategyAction {

    /**
     * Стабильный ключ action внутри StrategyDetail.
     *
     * Задаётся явно в JSON при создании стратегии.
     * Нужен для ссылок между actions и первичной валидации targetActionKey.
     */
    String getKey();
}
```

Для action, который работает с уже созданной runtime-сущностью, добавляется `targetActionKey`.

```java
public interface TargetedStrategyAction extends StrategyAction {

    /**
     * Ключ action, который создал runtime-сущность,
     * над которой нужно выполнить AMEND или CANCEL.
     */
    String getTargetActionKey();
}
```

На практике `targetActionKey` можно добавить в конкретные action-модели, где это нужно:

```java
public class StrategyOrderAction implements StrategyAction {

    /**
     * Стабильный ключ action внутри StrategyDetail.
     */
    private String key;

    /**
     * Для AMEND / CANCEL: key action, который создал target order.
     * Для CREATE должен быть null.
     */
    private String targetActionKey;

    // остальные поля action
}
```

```java
public class StrategyAlgoOrderAction implements StrategyAction {

    /**
     * Стабильный ключ action внутри StrategyDetail.
     */
    private String key;

    /**
     * Для AMEND / CANCEL: key action, который создал target algo-order.
     * Для CREATE должен быть null.
     */
    private String targetActionKey;

    // остальные поля action
}
```

---

## 5.4. Правила валидации key / targetActionKey

При создании стратегии валидатор должен проверить:

1. `key` обязателен у каждого `StrategyAction`.
2. `key` уникален в рамках одной `StrategyDetail`.
3. `targetActionKey` должен ссылаться на существующий `action.key` в той же `StrategyDetail`.
4. `targetActionKey` обязателен для `AMEND` и `CANCEL` у `ORDER` / `ALGO_ORDER` actions.
5. `CREATE` не должен иметь `targetActionKey`.
6. `ORDER AMEND` / `ORDER CANCEL` должны ссылаться на `ORDER CREATE`.
7. `ALGO_ORDER AMEND` / `ALGO_ORDER CANCEL` должны ссылаться на `ALGO_ORDER CREATE`.
8. Нельзя ссылаться на action из другой `StrategyDetail`.

---

## 5.5. Резолв targetActionKey при сохранении стратегии

После валидации стратегия сохраняет actions как отдельные записи.

На этом этапе:

```text
targetActionKey
  -> резолвится в target StrategyAction.id
```

И runtime уже работает через `strategyActionId`, а не через `strategyActionKey`.

Упрощённая persistence-модель action может выглядеть так:

```java
public class StrategyActionEntity {

    /**
     * Технический ID action.
     */
    private Long id;

    /**
     * StrategyDetail, которому принадлежит action.
     */
    private Long strategyDetailId;

    /**
     * Явный ключ action из JSON.
     */
    private String key;

    /**
     * Для AMEND / CANCEL: target action, найденный по targetActionKey.
     */
    private Long targetStrategyActionId;
}
```

Инвариант стратегии:

```text
UNIQUE(strategy_detail_id, key)
```

## 5.6. Пример target для grid cancel

CREATE actions:

```text
grid-entry-long-1
grid-entry-long-2
grid-entry-short-3
grid-entry-short-4
```

CANCEL actions:

```text
cancel-grid-entry-long-1  -> targetActionKey = grid-entry-long-1
cancel-grid-entry-long-2  -> targetActionKey = grid-entry-long-2
cancel-grid-entry-short-3 -> targetActionKey = grid-entry-short-3
cancel-grid-entry-short-4 -> targetActionKey = grid-entry-short-4
```

Runtime:

```text
CANCEL action
  -> имеет targetStrategyActionId, полученный из targetActionKey при сохранении стратегии
  -> ищет DealActionState(dealId, strategyActionId = targetStrategyActionId)
  -> получает RuntimeTarget
  -> создаёт CANCEL_ORDER / CANCEL_ALGO_ORDER payload с конкретным ID сущности
```

# 6. DealActionState

`DealActionState` — runtime-проекция выполнения action стратегии.

Она нужна для восстановления после рестарта.

Она не является аудитом.

```java
public class DealActionState extends Retryable {

    /**
     * Технический ID записи.
     */
    private Long id;

    /**
     * Сделка, в рамках которой выполняется action стратегии.
     */
    private Long dealId;

    /**
     * Action стратегии, с которым связан runtime-state.
     */
    private Long strategyActionId;

    /**
     * Runtime-сущность, в которую материализовался action стратегии.
     *
     * Для ещё не созданной сущности может быть null.
     */
    private RuntimeTarget target;

    /**
     * Текущее состояние выполнения action.
     */
    private DealActionStateStatus status;
}
```

Ключевой инвариант:

```text
UNIQUE(deal_id, strategy_action_id)
```

Важно:

> `strategyActionId` не хранится в `Order`, `AlgoOrder`, `Position`.
>
> Связь action стратегии с runtime-сущностью хранится в `DealActionState`.
>
> `strategyActionKey` в `DealActionState` не хранится, если actions стратегии сохранены отдельными строками и имеют ID.

## 6.3. Retryable

`Retryable` — базовый класс для объектов, которые могут повторять выполнение после ошибки.

```java
public abstract class Retryable {

     * Количество уже выполненных попыток.

     * Максимально разрешённое количество попыток.

     */

     * Последняя ошибка retry.
     */

}
```

# 7. CREATE -> SUBMIT -> REFRESH

Для сущностей, которые создаются на бирже, используется трёхшаговая схема:

```text
CREATE_* -> SUBMIT_* -> REFRESH_*
```

## 7.1. CREATE

Создаёт локальную сущность в БД.

Пример:

```text
CREATE_ORDER
  -> создать Order в БД
  -> status = CREATED
  -> externalId = null
  -> internalId заполнен
  -> обновить DealActionState.target = RuntimeTarget(ORDER, orderId)
  -> DealActionState.status = CREATED
```

CREATE не ходит на биржу.

---

## 7.2. SUBMIT

Отправляет локальную сущность на биржу или восстанавливает факт отправки.

Важно:

```text
Order.CREATED + externalId = null
```

не означает, что order точно ещё не отправляли на биржу.

Правильный алгоритм:

```text
1. Найти локальный Order.
2. Взять clientOrderId = order.internalId.
3. Проверить биржу по clientOrderId.
4. Если order найден:
   -> обновить локальную сущность из external snapshot.
5. Если order не найден:
   -> отправить order на биржу.
6. Обновить DealActionState.status.
```

Для algo-order аналогично:

```text
1. Найти локальный AlgoOrder.
2. Взять algoClOrdId = algoOrder.internalId.
3. Проверить биржу по algoClOrdId.
4. Если algo-order найден:
   -> обновить локальную сущность из external snapshot.
5. Если algo-order не найден:
   -> отправить algo-order на биржу.
6. Обновить DealActionState.status.
```

---

## 7.3. REFRESH

Подтверждает фактическое состояние.

Пример:

```text
SUBMIT_ORDER
  -> REFRESH_ORDER
  -> REFRESH_PENDING_ORDERS
  -> REFRESH_POSITION
```

FSM двигает статус сделки только после подтверждения фактов.

# 8. Как обновляется DealActionState

## 8.1. CREATE action

```text
PLANNED
  -> CREATED
  -> SUBMITTED
  -> CONFIRMED
  -> COMPLETED
```

Пояснение:

* `CREATED` — локальная сущность создана в БД.
* `SUBMITTED` — сущность отправлена на биржу или отправка начата.
* `CONFIRMED` — refresh подтвердил факт на бирже.
* `COMPLETED` — action больше не требует обработки.

---

## 8.2. AMEND action

`AMEND` action не создаёт новую runtime-сущность.

Он должен изменить сущность, созданную target `CREATE` action.

Алгоритм:

```text
1. Взять targetStrategyActionId из AMEND action.
2. Найти DealActionState по dealId + targetStrategyActionId.
3. Проверить, что RuntimeTarget.entityType совместим с AMEND-командой.
4. Взять RuntimeTarget.entityId.
5. Создать payload AMEND_ORDER / AMEND_ALGO_ORDER с конкретным ID сущности.
6. Обновить DealActionState текущего AMEND action.
```

Lifecycle AMEND action:

```text
PLANNED
  -> SUBMITTED
  -> CONFIRMED
  -> COMPLETED
```

Пояснение:

* `SUBMITTED` — amend-запрос отправлен.
* `CONFIRMED` — refresh подтвердил новые параметры сущности.
* `COMPLETED` — action завершён.

---

## 8.3. CANCEL action

`CANCEL` action не создаёт новую runtime-сущность.

Он должен отменить сущность, созданную target `CREATE` action.

Алгоритм:

```text
1. Взять targetStrategyActionId из CANCEL action.
2. Найти DealActionState по dealId + targetStrategyActionId.
3. Проверить, что RuntimeTarget.entityType совместим с CANCEL-командой.
4. Взять RuntimeTarget.entityId.
5. Создать payload CANCEL_ORDER / CANCEL_ALGO_ORDER с конкретным ID сущности.
6. Обновить DealActionState текущего CANCEL action.
```

Lifecycle CANCEL action:

```text
PLANNED
  -> SUBMITTED
  -> CONFIRMED
  -> COMPLETED
```

Пояснение:

* `SUBMITTED` — cancel-запрос отправлен.
* `CONFIRMED` — refresh подтвердил, что сущность закрыта/отменена.
* `COMPLETED` — action завершён.

---

## 8.4. Retry состояния

Если команда упала, но может быть повторена:

```text
current status
  -> RETRY_PENDING
```

В `Retryable` обновляются:

```text
attemptCount
nextRetryAt
lastError
```

`lastError` — это объект `RetryError`, а не пара строк `lastErrorCode` / `lastError`.

Когда наступает `nextRetryAt`, orchestrator может снова попробовать action.

Если `attemptCount >= maxAttempts`:

```text
RETRY_PENDING -> FAILED
```

Дальше FSM решает по критичности этапа:

```text

```

# 10. Retry policy

Retry policy — это техническая политика исполнения команд.

На первом этапе храним её в конфиге приложения, а не в БД.

Причина:

```text
retry policy — это не часть торговой стратегии,
а техническая политика обработки ошибок и неизвестных результатов.
```

---

## 10.1. Пример application.yml

```yaml
service-command-retry:
  default-policy:
    max-attempts: 3
    initial-delay: 1s
    max-delay: 30s
    backoff: EXPONENTIAL

  policies:
    SUBMIT_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 30s
      backoff: EXPONENTIAL

    SUBMIT_ALGO_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 30s
      backoff: EXPONENTIAL

    REFRESH_ORDER:
      max-attempts: 10
      initial-delay: 500ms
      max-delay: 10s
      backoff: FIXED

    REFRESH_ALGO_ORDERS:
      max-attempts: 10
      initial-delay: 500ms
      max-delay: 10s
      backoff: FIXED

    CANCEL_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 20s
      backoff: EXPONENTIAL

    CANCEL_ALGO_ORDER:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 20s
      backoff: EXPONENTIAL

    CLOSE_POSITION:
      max-attempts: 5
      initial-delay: 1s
      max-delay: 15s
      backoff: EXPONENTIAL
```

## 10.4. Как работает retry

```text
Executor упал
  -> ServiceCommandExecutor ловит ошибку
  -> RetryPolicyService получает policy по ServiceCommandType
  -> увеличивает Retryable.attemptCount
  -> считает nextRetryAt
  -> сохраняет RetryError в lastError
  -> переводит DealActionState в RETRY_PENDING

Если attemptCount >= maxAttempts
  -> DealActionState.status = FAILED
  -> FSM решает, что делать дальше
```

---

## 10.5. Важное правило для опасных команд

Для команд:

```text
SUBMIT_*
CANCEL_*
CLOSE_POSITION
```

перед повтором обязательно сначала делать refresh/search на бирже.

Причина:

> Предыдущий запрос мог реально выполниться на бирже, даже если сервис не получил ответ.

Примеры:

```text
SUBMIT_ORDER retry
  -> сначала найти order по clientOrderId
  -> если найден, восстановить локальное состояние
  -> если не найден, отправить заново

CANCEL_ORDER retry
  -> сначала refresh order
  -> если уже CLOSED, считать cancel успешным
  -> если ещё active, повторить cancel

CLOSE_POSITION retry
  -> сначала refresh position
  -> если позиции уже нет, считать close успешным
  -> если позиция ещё active, повторить close
```

# 12. Executor'ы

## 12.1. CreateOrderExecutor

Получает `CREATE_ORDER`.

Делает:

* создаёт локальный `Order`;
* ставит статус `CREATED`;
* генерирует `internalId`;
* сохраняет рассчитанные параметры;
* создаёт attached protection внутри order, если она есть;
* обновляет `DealActionState.target = RuntimeTarget(ORDER, orderId)`;
* обновляет `DealActionState.status = CREATED`.

Не делает:

* не ходит на биржу;
* не решает, нужен ли вход;
* не пересчитывает цену;
* не проверяет стратегические условия.

---

## 12.2. SubmitOrderExecutor

Получает `SUBMIT_ORDER`.

Делает:

1. Загружает локальный `Order`.
2. Если `externalId` уже есть — команда считается выполненной или требует refresh.
3. Если `externalId` пустой — ищет order на бирже по `clientOrderId = order.internalId`.
4. Если order найден — обновляет локальный order из биржевого snapshot.
5. Если order не найден — отправляет order на биржу.
6. Обновляет `DealActionState.status`.

Recoverability:

```text
если приложение упало после отправки на биржу,
но до сохранения externalId,
следующий submit найдёт order по clientOrderId
и восстановит локальное состояние.
```

---

## 12.3. RefreshOrderExecutor

Получает `REFRESH_ORDER`.

Делает:

* загружает локальный order;
* получает актуальное состояние с биржи;
* обновляет локальный order;
* обновляет статусы исполнения;
* при необходимости обновляет `DealActionState`.

---

## 12.4. AmendOrderExecutor

Получает `AMEND_ORDER`.

Делает:

* загружает локальный order по `payload.orderId`;
* отправляет amend на биржу;
* сохраняет ack / технический результат;
* дальше факт подтверждается refresh-командой.

Не решает, хорошая ли новая цена.

---

## 12.5. CancelOrderExecutor

Получает `CANCEL_ORDER`.

Делает:

* загружает локальный order по `payload.orderId`;
* отправляет cancel на биржу;
* сохраняет ack / технический результат;
* дальше факт отмены подтверждается refresh-командой.

# 13. Восстановление после рестарта

FSM не должна помнить, на каком действии упал процесс.

После рестарта она заново собирает:

* `DealContext`;
* `DealActionState`;
* runtime-сущности;
* exchange snapshots.

Пример:

```text
StrategyStep GRID_ENTRY:
  action key = grid-entry-long-1
  action key = grid-entry-long-2
  action key = grid-entry-short-3
  action key = grid-entry-short-4
```

При сохранении стратегии эти `key` резолвятся во внутренние `strategyActionId`.

До рестарта создали 2 order.

После рестарта:

```text
DealActionState(strategyActionId для grid-entry-long-1) -> target.entityId = order1, status = CREATED
DealActionState(strategyActionId для grid-entry-long-2) -> target.entityId = order2, status = SUBMITTED
DealActionState(strategyActionId для grid-entry-short-3) -> отсутствует
DealActionState(strategyActionId для grid-entry-short-4) -> отсутствует
```

FSM делает:

```text
grid-entry-long-1 -> submit / refresh
grid-entry-long-2 -> refresh
grid-entry-short-3 -> create
grid-entry-short-4 -> create
```

Для `AMEND` / `CANCEL`:

```text
cancel-grid-entry-long-1
  -> targetActionKey = grid-entry-long-1
  -> при сохранении стратегии targetActionKey резолвится в target strategyActionId
  -> найти DealActionState(dealId, target strategyActionId)
  -> получить RuntimeTarget(entityType = ORDER, entityId = order1)
  -> создать CANCEL_ORDER(orderId = order1)
```

# 14. ServiceCommandExecutionHistory

Формат `ServiceCommandExecutionHistory` будет детализирован в документе `05. Аудит и история исполнения`.

В рамках этой доки фиксируем только принцип:

> История команд нужна для аудита, расследования и timeline сделки.
>
> Runtime-логика FSM работает по `DealActionState + DealContext + runtime-сущностям`.

История не влияет на:

* жизненный цикл сделки;
* выполнение сервисных команд;
* retry policy;
* расчёт цены;
* runtime recovery.

# 15. Итоговые решения

1. Статусы `Order`, `AlgoOrder`, `AttachedAlgoOrder`, `Position` в целом достаточны.
2. Из `Order` и `AlgoOrder` нужно убрать `strategyActionId`.
3. `AlgoOrder.CloseReason` нужно расширить.
4. `Order.Status.ACTIVE` должен означать активность на бирже, а не fill.
5. У каждого `StrategyAction` должен быть обязательный `key`.
6. `key` задаётся явно в JSON стратегии.
7. `key` уникален в рамках одной `StrategyDetail`.
8. Для `AMEND` и `CANCEL` добавляем `targetActionKey`.
9. `targetActionKey` должен ссылаться на существующий `action.key` в той же `StrategyDetail`.
10. При сохранении стратегии `targetActionKey` резолвится в target `strategyActionId`.
11. `DealActionState` хранит runtime-связь action -> entity через `strategyActionId` и `RuntimeTarget`.
12. `DealActionState` наследуется от `Retryable`.
13. Retry-ошибка хранится как объект `RetryError`, а не как отдельные поля `lastErrorCode` / `lastError`.
14. Retry policy храним в application config.
15. `ServiceCommandExecutionHistory` пока не детализируем; это часть доки по аудиту.
