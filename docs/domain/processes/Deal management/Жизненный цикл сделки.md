# 1. Главная идея

Жизненный цикл сделки — это процесс от момента, когда система увидела подходящие условия входа, до полного закрытия сделки и очистки риска.

Сделка управляется не напрямую стратегией и не executor'ами.

Стратегия описывает:

* какие условия должны выполниться;
* какой шаг стратегии применим;
* какие действия ожидаются;
* какие параметры нужны для расчёта цены, размера и риска.

Runtime-слой делает:

* готовит рыночные данные;
* ищет возможность входа;
* создаёт `Deal`;
* сопровождает `Deal` через FSM;
* интерпретирует действия стратегии;
* рассчитывает runtime-параметры действий;
* создаёт сервисные команды;
* исполняет команды через executor'ы;
* восстанавливается после рестарта по фактическому состоянию БД и биржи.

Главное правило:

> Стратегия задаёт ожидаемые действия и привязывает их к этапам сделки.
>
> FSM проверяет фактическое состояние сделки и решает, можно ли применить эти действия сейчас.
>
> `StrategyActionCalculator` рассчитывает runtime-параметры.
>
> `ServiceCommandExecutor` исполняет атомарные команды.

## 1.1. Зафиксированные решения lifecycle / FSM

В эту версию документа встроены принятые решения:

```text
Q1. Strategy.INACTIVE / Strategy.DELETED / market data expired
Q2. entryReason: короткий код в Deal, подробности в `05. Аудит и история исполнения`
Q3. entryStepType: ENTRY / GRID_ENTRY хранится в Deal
Q4. PROTECTION_ESTABLISHED не вводим; PROTECTION_SWITCHED условный
Q5. ERROR -> CLOSED запрещён; добавлен EMERGENCY_CLOSED
Q6. PRECHECK может закрыть candidate Deal с ENTRY_CONDITION_EXPIRED, если live risk ещё не создан
Q7. CLOSED / EMERGENCY_CLOSED — terminal-статусы без handlers; CloseHandler переименовывается в ExitPendingHandler
Q8. ACKED не добавляем; CONFIRMED убираем; успешный terminal-статус action — COMPLETED
Q9. ServiceCommand — runtime object; persisted queue не вводим; direct partial close запрещён
```

Для жизненного цикла сделки это означает:

* `Strategy.INACTIVE` блокирует только новые сделки; уже открытые сделки продолжают сопровождаться по pinned `StrategyDetail`.
* `Strategy.DELETED` блокирует новые сделки и переводит уже открытые сделки в graceful shutdown.
* Устаревшие рыночные данные не меняют `Strategy.Status`; новые сделки не создаются, а открытые сделки обрабатываются через `StrategyStep.marketDataExpiredSetting`.
* `Deal.entryReason` хранит короткую причину создания сделки: `STRATEGY`, `MANUAL`, `RECOVERY`, `UNKNOWN`.
* Подробный entry context хранится в `05. Аудит и история исполнения`, а не в `Deal`.
* `Deal.entryStepType` хранит `ENTRY` / `GRID_ENTRY`, если сделка создана через strategy entry-step.
* `PROTECTION_SWITCHED` используется только если реально выполняется замена temporary attached protection на main protection.
* Если protection switch не нужен, сделка может перейти `ENTRY_FINALIZED -> MANAGING`, если позиция безопасна для сопровождения.
* `ERROR -> CLOSED` запрещён; аварийно завершённая сделка переводится в `EMERGENCY_CLOSED` только после подтверждённого снятия live risk.
* В `PRECHECK`, если entry condition больше не актуален и live risk ещё не создан, сделка закрывается как `CLOSED` с `closeReason = ENTRY_CONDITION_EXPIRED`.
* `CLOSED` и `EMERGENCY_CLOSED` — terminal-статусы; отдельные handlers для них не нужны.
* `DealActionStateStatus.CONFIRMED` не используется; успешный terminal-статус action — `COMPLETED`.
* `ServiceCommand` — runtime object, pending command queue в БД не создаём.
* `CLOSE_POSITION` используется только для полного закрытия позиции; partial exit идёт через reduce-only `Order` / `AlgoOrder`.

# 2. Большие процессы системы

Вокруг сделки есть 4 больших процесса.

```text
1. Расчёт индикаторов и рыночных данных
   -> IndicatorJob
   -> MarketStructureJob
   -> MarketPhaseJob

2. Жизненный цикл сделки
   -> EntryScannerJob
   -> DealOpeningService
   -> DealOrchestratorJob
   -> Deal FSM

3. Калькуляторы действий стратегии
   -> StrategyActionCalculator
      -> PriceCalculator
      -> SizeCalculator
      -> RiskCalculator

4. Сервисные команды
   -> ServiceCommandFactory
   -> ServiceCommandExecutor
   -> конкретные Executor'ы
```

Итоговый flow:

```text
IndicatorJob / MarketStructureJob / MarketPhaseJob
  -> готовят свежие данные рынка

EntryScannerJob
  -> читает активную Strategy
  -> проверяет свежесть данных через MarketDataExpirationChecker
  -> получает MarketPhase по Strategy.marketPhaseSetting
  -> выбирает StrategyDetail по MarketPhase.Type
  -> проверяет ENTRY / GRID_ENTRY conditions
  -> если условия подходят, вызывает DealOpeningService

DealOpeningService
  -> создаёт Deal в статусе PRECHECK
  -> сохраняет pinned StrategyDetail
  -> сохраняет entryReason и entryStepType

DealOrchestratorJob
  -> загружает DealContext
  -> запускает Deal FSM

Deal FSM / StateHandler
  -> проверяет этап сделки
  -> проверяет свежесть данных для конкретного StrategyStep
  -> проверяет StrategyCondition
  -> выбирает StrategyAction

StrategyActionCalculator
  -> получает StrategyAction + DealContext
  -> собирает свежий CalculationContext
  -> вызывает PriceCalculator / SizeCalculator / RiskCalculator
  -> возвращает рассчитанные параметры

ServiceCommandFactory
  -> создаёт ServiceCommand

ServiceCommandExecutor
  -> вызывает конкретный Executor

Executor
  -> исполняет атомарную операцию
  -> сохраняет результат
```

# 3. Зоны ответственности

## 3.1. IndicatorJob / MarketStructureJob / MarketPhaseJob

Эти job'ы готовят данные рынка.

Они не управляют сделкой и не создают `Deal`.

`IndicatorJob` считает `IndicatorValue` по настройкам стратегии.

Источник:

```text
Candles + StrategyIndicatorSetting
```

Правила:

* индикаторы считаются только по закрытым свечам;
* warmup-значения не сохраняются;
* если новых закрытых свечей нет, новый `IndicatorValue` не создаётся;
* старые значения остаются в БД;
* `MarketDataExpirationChecker` считает их устаревшими после `StrategyIndicatorSetting.expirationDuration`;
* если стратегия `DELETED`, новые значения для неё не считаем.

`MarketStructureJob` считает `MarketStructure` и `MarketPriceLevel` по настройкам стратегии.

Источник:

```text
Candles + StrategyMarketStructureSetting
```

Если алгоритму нужно, он может использовать уже посчитанные `IndicatorValue`.

`MarketPhaseJob` считает `MarketPhase` по `StrategyMarketPhaseSetting`.

Источники:

```text
IndicatorValue + MarketStructure + StrategyMarketPhaseSetting
```

Важно:

> Job'ы рыночных данных не меняют `Strategy.Status`.
> Устаревание данных — runtime-состояние, которое проверяет `MarketDataExpirationChecker`.

Данные этих job'ов используют:

* `EntryScannerJob` — для проверки входа;
* `StrategyConditionEvaluator` — для проверки условий в уже открытой сделке;
* `StrategyActionCalculator` — для расчёта цен, размеров и риска.

Подробности см. в документе `04. Расчёт индикаторов и рыночных данных`.

---

## 3.2. EntryScannerJob

`EntryScannerJob` отвечает за поиск возможности создать новую сделку.

Он не выставляет ордера и не открывает позицию.

Он делает:

1. Читает активные стратегии по инструментам.
2. Для каждой стратегии проверяет свежесть данных через `MarketDataExpirationChecker.checkForEntry(strategy)`.
3. Если нужные данные устарели или отсутствуют — новую `Deal` не создаёт.
4. Если данные свежие — получает актуальную `MarketPhase`, рассчитанную по `Strategy.marketPhaseSetting`.
5. По `MarketPhase.Type` выбирает подходящий pinned `StrategyDetail`.
6. Проверяет `phaseEntryPolicy`:
   * если `NO_TRADE` — сделка не создаётся;
   * если `FOLLOW_PHASE` / `CONTRARIAN` / `GRID` — продолжает проверку.
7. Читает свежие данные рынка, нужные для входа:
   * `MarketPriceData`;
   * `IndicatorValue`;
   * `MarketStructure`;
   * `MarketPhase`;
   * balance / risk data, если нужны для предварительной проверки.
8. Проверяет, что по инструменту нет активной сделки, если одновременно разрешена только одна сделка.
9. Проверяет, что по инструменту нет активной позиции, если стратегия требует новый вход.
10. Находит `StrategyStep` с `stepType = ENTRY` или `GRID_ENTRY`.
11. Проверяет `StrategyCondition` выбранного entry-step.
12. Если условия входа выполнены — вызывает `DealOpeningService`.

`EntryScannerJob` передаёт в `DealOpeningService` уже выбранные данные:

* `instrumentId`;
* `strategyDetailId`;
* `marketPhase`;
* `entryReason`;
* `entryStepType`;
* направление сделки, если оно уже определено;
* минимальный entry context для аудита / истории исполнения.

Правила для `entryReason` и `entryStepType`:

```text
если сделка создана по StrategyStepType.ENTRY
  -> entryReason = STRATEGY
  -> entryStepType = ENTRY

если сделка создана по StrategyStepType.GRID_ENTRY
  -> entryReason = STRATEGY
  -> entryStepType = GRID_ENTRY
```

Не делает:

* не создаёт order;
* не создаёт algo-order;
* не открывает позицию;
* не исполняет `StrategyAction`;
* не запускает FSM напрямую;
* не ходит на биржу для выставления ордеров.

Важно:

> Не рынок “дал сигнал”, а `EntryScannerJob` увидел, что текущее состояние рынка подходит под `ENTRY` / `GRID_ENTRY` condition активной стратегии.
>
> `Strategy.Status = ACTIVE` не означает, что можно открыть сделку прямо сейчас.
> Перед созданием `Deal` должны быть свежие данные и выполненные условия входа.

## 3.3. DealOpeningService

`DealOpeningService` отвечает за атомарное создание `Deal`.

Он не принимает торговое решение о входе.

Решение о том, что условия входа подходят, принимает `EntryScannerJob` через проверку `StrategyStep ENTRY` / `GRID_ENTRY`.

`DealOpeningService` получает от `EntryScannerJob` уже выбранные данные:

* `instrumentId`;
* `strategyDetailId`;
* `marketPhase`;
* `entryReason`;
* `entryStepType`;
* направление сделки, если оно уже определено;
* минимальный entry context для аудита / истории исполнения.

`DealOpeningService` делает:

1. Выполняет финальную защитную проверку, что по инструменту всё ещё нет активной сделки.
2. Создаёт `Deal`.
3. Ставит `Deal.Status = PRECHECK`.
4. Сохраняет pinned-связи сделки с инструментом, `StrategyDetail` и фазой рынка.
5. Сохраняет `Deal.entryReason`.
6. Сохраняет `Deal.entryStepType`.
7. Передаёт подробный entry context в аудит / историю исполнения.
8. Возвращает созданную сделку.

Не делает:

* не ищет активную стратегию;
* не выбирает `StrategyDetail`;
* не анализирует индикаторы;
* не проверяет `ENTRY` / `GRID_ENTRY condition`;
* не создаёт order;
* не создаёт algo-order;
* не ходит на биржу;
* не запускает FSM.

Важно:

> Создание `Deal` — часть жизненного цикла сделки.
>
> Но создание `Deal` не является частью FSM.
>
> FSM сопровождает уже созданную сделку.
>
> Подробный `entryContext` не хранится в `Deal`; он фиксируется в `05. Аудит и история исполнения`.

## 3.4. DealOrchestratorJob

`DealOrchestratorJob` сопровождает уже созданные сделки.

Он делает:

1. Находит активные `Deal`.
2. Для каждой сделки загружает `DealContext`.
3. Запускает `DealStateMachine`.
4. Получает `TransitionResult`.
5. Передаёт команды в `ServiceCommandExecutor`.
6. Перезагружает `DealContext` после выполнения команд.
7. Сохраняет новый статус сделки.

Он не делает:

* не считает индикаторы;
* не ищет новые входы;
* не ходит на биржу напрямую;
* не считает цены вручную;
* не исполняет REST-запросы сам.

---

## 3.5. DealStateMachine

`DealStateMachine` управляет статусами сделки.

Она делает:

* выбирает handler по текущему `Deal.Status`;
* запускает входные проверки handler'а;
* выполняет рабочую логику этапа;
* проверяет свежесть данных для конкретного `StrategyStep`;
* проверяет условия стратегии, если этап допускает strategy steps;
* выбирает допустимые `StrategyAction`;
* возвращает команды и новый статус, если переход разрешён.

FSM не делает:

* не создаёт `Deal`;
* не рассчитывает индикаторы;
* не собирает live-цену;
* не исполняет команды;
* не вызывает биржу;
* не строит аудит.

## 3.6. StrategyActionCalculator

`StrategyActionCalculator` рассчитывает runtime-параметры для выбранного действия стратегии.

Он получает:

```text
StrategyAction + DealContext
```

И делает:

1. Собирает свежий `CalculationContext`.
2. Вызывает `PriceCalculator`.
3. Вызывает `SizeCalculator`.
4. Вызывает `RiskCalculator`.
5. Возвращает готовые параметры для `ServiceCommand`.

Важно:

> Рыночные цены, индикаторы, market phase и market structure лучше собирать в runtime внутри калькулятора, а не полагаться на устаревшие данные из `DealContext`.
>
> Если данные, нужные action / step, устарели и `StrategyStep.marketDataExpiredSetting` запрещает выполнение, `StrategyActionCalculator` не должен рассчитывать торговый action.
>
> Safety-команды и cleanup-команды при этом остаются разрешены.

Причина:

```text
DealContext собрали
  -> прошло несколько секунд
  -> цена могла измениться
  -> перед созданием команды нужно пересчитать параметры по свежим данным
```

Подробности см. в документе `03. Калькуляторы действий стратегии`.

# 4. Deal

`Deal` — корневая runtime-сущность сделки.

Она фиксирует, что система начала сопровождать конкретный торговый сценарий по выбранному инструменту и pinned `StrategyDetail`.

```java
public class Deal extends Auditable {

    /**
     * Технический ID сделки.
     */
    private Long id;

    /**
     * Безопасный внешний / межсервисный идентификатор сделки.
     */
    private String internalId;

    /**
     * Инструмент сделки.
     */
    private Long instrumentId;

    /**
     * Pinned detail стратегии, по которой создана сделка.
     */
    private Long strategyDetailId;

    /**
     * Фаза рынка, по которой была выбрана StrategyDetail при создании сделки.
     */
    private Long marketPhaseId;

    /**
     * Текущий статус сделки в FSM.
     */
    private Status status;

    /**
     * Направление сделки: LONG / SHORT.
     */
    private StrategyTradeDirection direction;

    /**
     * Короткая причина создания сделки.
     *
     * Отвечает на вопрос: почему Deal был создан.
     *
     * Подробный entry context не хранится в Deal.
     */
    private EntryReason entryReason;

    /**
     * Тип strategy entry-step, по которому была создана сделка.
     *
     * Допустимые значения:
     * - ENTRY;
     * - GRID_ENTRY;
     * - null, если сделка создана не через strategy entry-step.
     */
    private StrategyStepType entryStepType;

    /**
     * Причина запуска graceful shutdown.
     *
     * Не заменяет closeReason.
     */
    private ShutdownReason shutdownReason;

    /**
     * Причина закрытия сделки, если сделка уже закрывается или закрыта.
     */
    private CloseReason closeReason;

    /**
     * Время открытия сделки в нашей системе.
     */
    private OffsetDateTime openedAt;

    /**
     * Время закрытия сделки в нашей системе.
     */
    private OffsetDateTime closedAt;
}
```

## 4.1. Deal.Status

`Deal.Status` — текущий FSM-статус сделки.

Подробная логика каждого статуса описана ниже в разделе `FSM статусы` и в отдельном документе `FSM этапы сделки`.

```java
public enum Status {

    /**
     * Сделка создана, но entry order ещё не создан / не отправлен.
     */
    PRECHECK,

    /**
     * Entry order создан или отправлен, ждём подтверждения входа.
     */
    ENTRY_SUBMITTED,

    /**
     * Вход подтверждён: entry order финализирован, позиция открыта.
     */
    ENTRY_FINALIZED,

    /**
     * Temporary attached protection заменена на standalone main protection.
     *
     * Этот статус условный и используется только если switch реально нужен.
     */
    PROTECTION_SWITCHED,

    /**
     * Позиция сопровождается по стратегии.
     */
    MANAGING,

    /**
     * Выход инициирован, нужно дочистить риск и подтвердить закрытие.
     */
    EXIT_PENDING,

    /**
     * Сделка нормально закрыта.
     *
     * Terminal-статус.
     */
    CLOSED,

    /**
     * Сделка в аварийном состоянии.
     *
     * Обычная strategy/FSM-логика заблокирована.
     * Разрешены только safety / recovery / refresh / kill-switch действия.
     */
    ERROR,

    /**
     * Аварийная сделка завершена после safety-flow / kill-switch.
     *
     * Live risk отсутствует:
     * - position закрыта или отсутствует;
     * - ordinary orders не live;
     * - algo-orders не live;
     * - attached protection больше не влияет на риск;
     * - финальные факты подтверждены refresh/search/history.
     *
     * Terminal-статус, но не нормальный CLOSED.
     */
    EMERGENCY_CLOSED
}
```

## 4.2. Deal.CloseReason

`CloseReason` фиксирует причину фактического закрытия позиции / сделки.

```java
public enum CloseReason {

    /** Закрытие по stop-loss. */
    STOP_LOSS,

    /** Закрытие по take-profit. */
    TAKE_PROFIT,

    /** Закрытие по правилу стратегии. */
    STRATEGY_EXIT,

    /** Закрытие по time-stop. */
    TIME_STOP,

    /** Закрытие по risk control. */
    RISK_CONTROL,

    /** Аварийное закрытие. */
    EMERGENCY_STOP,

    /** Закрытие вручную. */
    MANUAL,

    /**
     * Candidate Deal был создан, но до создания live risk
     * entry condition перестал быть актуальным.
     *
     * Применяется только в PRECHECK.
     */
    ENTRY_CONDITION_EXPIRED,

    /** Причина не определена. */
    UNKNOWN
}
```

## 4.3. EntryReason

`entryReason` — короткая машинная причина создания сделки.

```java
public enum EntryReason {

    /**
     * Сделка создана по правилу стратегии.
     *
     * Конкретный тип входа хранится отдельно в Deal.entryStepType:
     * ENTRY или GRID_ENTRY.
     */
    STRATEGY,

    /**
     * Ручное создание сделки.
     */
    MANUAL,

    /**
     * Recovery-сценарий, если сделка была восстановлена по фактам.
     */
    RECOVERY,

    /**
     * Причина не определена.
     */
    UNKNOWN
}
```

## 4.4. entryStepType

`entryStepType` показывает, какой именно strategy entry-step создал `Deal`.

Допустимые значения:

```text
ENTRY
GRID_ENTRY
null
```

Правила:

```text
entryReason = STRATEGY, entryStepType = ENTRY
  -> обычная сделка по стратегии

entryReason = STRATEGY, entryStepType = GRID_ENTRY
  -> grid-сделка по стратегии

entryReason = MANUAL, entryStepType = null
  -> ручная сделка

entryReason = RECOVERY, entryStepType = ENTRY / GRID_ENTRY / null
  -> восстановленная сделка, если исходный entry-step известен
```

`entryStepType` не является источником runtime-логики FSM.

Он нужен для API, UI, аналитики и аудита.

## 4.5. ShutdownReason

`shutdownReason` фиксирует, почему был запущен graceful shutdown.

`ShutdownReason` не заменяет `Deal.CloseReason`.

```java
public enum ShutdownReason {

    /**
     * Стратегия была удалена.
     */
    STRATEGY_DELETED,

    /**
     * Рыночные данные устарели или отсутствуют.
     */
    MARKET_DATA_EXPIRED,

    /**
     * Ручная остановка сделки.
     */
    MANUAL_STOP,

    /**
     * Остановка по risk policy.
     */
    RISK_POLICY,

    /**
     * Причина не определена.
     */
    UNKNOWN
}
```

`Deal.CloseReason` остаётся причиной фактического закрытия позиции:

```text
STOP_LOSS
TAKE_PROFIT
STRATEGY_EXIT
TIME_STOP
RISK_CONTROL
EMERGENCY_STOP
MANUAL
UNKNOWN
```

Пример:

```text
shutdownReason = MARKET_DATA_EXPIRED
closeReason = RISK_CONTROL
```

или:

```text
shutdownReason = STRATEGY_DELETED
closeReason = STRATEGY_EXIT
```

# 5. DealContext

`DealContext` — это контекст FSM.

Он отвечает на вопрос:

> Что сейчас известно о сделке?

`DealContext` содержит факты сделки и runtime-состояние, которое нужно FSM для принятия решений по этапам сделки.

Он не должен превращаться в универсальный контейнер всех свежих рыночных данных.

Для критичных расчётов цены, размера, риска и внешних правил инструмента `StrategyActionCalculator` собирает свежий `CalculationContext`.

```java
public class DealContext {

    /**
     * Сделка, которую сейчас сопровождает FSM.
     */
    private Deal deal;

    /**
     * Торговый инструмент сделки.
     */
    private Instrument instrument;

    /**
     * Деталь стратегии, по которой была создана сделка.
     *
     * Это pinned-конфигурация сделки.
     */
    private StrategyDetail strategyDetail;

    /**
     * Контейнер баланса аккаунта.
     */
    private BalanceContainer balanceContainer;

    /**
     * Состояние позиций по инструменту сделки.
     */
    private PositionContext positionContext;

    /**
     * Ordinary orders, связанные со сделкой.
     *
     * Attached protection хранится внутри Order,
     * поэтому отдельное поле AttachedProtection в DealContext не нужно.
     */
    private List<Order> orders;

    /**
     * Algo-orders, связанные со сделкой.
     */
    private List<AlgoOrder> algoOrders;

    /**
     * Runtime-состояние выполнения actions стратегии.
     */
    private List<DealActionState> actionStates;
}
```

## 5.1. PositionContext

```java
public class PositionContext {

    /**
     * Единственная ожидаемая активная позиция по инструменту.
     *
     * Если позиции нет, поле null.
     */
    private Position activePosition;

    /**
     * Все позиции, найденные по инструменту.
     *
     * В норме список пустой или содержит одну позицию.
     */
    private List<Position> positionsByInstrument;

    /**
     * Признак нарушения инварианта:
     * по инструменту найдено больше одной позиции.
     */
    private boolean multiplePositionsDetected;
}
```

## 5.2. Что специально не входит в DealContext

В `DealContext` не включаем как обязательные поля:

```text
Strategy целиком
InstrumentExternalRules / InstrumentSpec как свежие внешние правила
MarketPriceData
IndicatorValue
MarketStructure
MarketPhase как свежий runtime-result
AttachedProtection отдельным полем
```

Пояснения:

* `Strategy` целиком не нужна, потому что сделка работает по pinned `StrategyDetail`.
* Внешние правила инструмента получает `StrategyActionCalculator` прямо перед расчётом.
* `MarketPriceData`, `IndicatorValue`, `MarketStructure`, `MarketPhase` для расчётов собираются в свежий `CalculationContext`.
* `AttachedProtection` не нужен отдельным полем, потому что это вложенная часть `Order`.

Важно:

> FSM принимает решения по фактам из `DealContext`, а не только по `Deal.status`.
>
> Калькуляторы принимают решения по свежему `CalculationContext`, собранному в runtime.

# 6. CalculationContext

`CalculationContext` — рабочий контекст калькуляторов.

Он не заменяет `DealContext`.

Он собирается внутри `StrategyActionCalculator` на базе:

```text
DealContext + StrategyAction + свежие runtime data
```

В него могут входить:

* `Deal`;
* `Instrument`;
* `StrategyDetail`;
* `StrategyAction`;
* `InstrumentExternalRules`;
* `MarketPriceData`;
* `IndicatorValue`;
* `MarketStructure`;
* `MarketPhase`;
* `BalanceContainer`;
* `PositionContext`;
* orders / algo-orders, если нужны для расчёта;
* риск-настройки;
* параметры action;
* направление сделки;
* текущая позиция;
* entry price.

Подробности см. в документе `03. Калькуляторы действий стратегии`.

# 7. DealActionState

`DealActionState` — runtime-состояние выполнения действия стратегии.

Это не аудит.

Это операционная проекция, которая нужна FSM для восстановления после рестарта.

Зачем нужен `DealActionState`:

* `Order`, `AlgoOrder`, `Position` остаются чистыми биржевыми сущностями;
* в них не храним `strategyActionId`;
* в них не храним `role / level` стратегии;
* связь `StrategyAction -> runtime entity` хранится отдельно;
* FSM после рестарта понимает, какие actions уже материализованы, а какие ещё нет.

Базовая идея модели:

```java
public class DealActionState {

    /**
     * Технический ID записи.
     */
    private Long id;

    /**
     * Сделка, в рамках которой выполняется действие стратегии.
     */
    private Long dealId;

    /**
     * Стабильный ID action из immutable-стратегии.
     */
    private Long strategyActionId;

    /**
     * Тип целевой runtime-сущности: ORDER / ALGO_ORDER / POSITION.
     */
    private TargetEntityType targetEntityType;

    /**
     * ID runtime-сущности, если action уже материализован.
     */
    private Long targetEntityId;

    /**
     * Текущее состояние выполнения action.
     */
    private DealActionStateStatus status;

    /**
     * Количество попыток исполнения.
     */
    private Integer attemptCount;

    /**
     * Последняя ошибка, если action не удалось выполнить.
     */
    private String lastError;
}
```

Пример enum:

```java
public enum DealActionStateStatus {

    /**
     * Action ожидает выполнения.
     */
    PLANNED,

    /**
     * Локальная runtime-сущность создана в БД.
     */
    CREATED,

    /**
     * Сущность отправлена на биржу или отправка начата.
     */
    SUBMITTED,

    /**
     * Action выполнен и больше не требует обработки.
     *
     * Ставится только после refresh/search/history,
     * когда подтверждён нужный финальный факт.
     */
    COMPLETED,

    /**
     * Action временно не выполнен, но будет повторён по retry policy.
     */
    RETRY_PENDING,

    /**
     * Action не удалось выполнить после допустимого количества попыток
     * или ошибка неретраибельная.
     */
    FAILED,

    /**
     * Action больше не нужен из-за изменения состояния сделки.
     */
    SKIPPED
}
```

Ключевой инвариант:

```text
UNIQUE(deal_id, strategy_action_id)
```

Важно:

> Это уникальность не в `Order` и не в `AlgoOrder`, а в `DealActionState`.

# 8. ServiceCommand — тезисно

Подробно команды описаны в документе `02. Сервисные команды`.

В жизненном цикле сделки важно понимать только следующее:

```text
StrategyAction
  -> StrategyActionCalculator
  -> рассчитанные параметры
  -> ServiceCommand
  -> Executor
```

`ServiceCommand` — это атомарная runtime-команда.

Важно:

```text
ServiceCommand не является persisted entity.
Pending ServiceCommand не хранится в БД.
После рестарта FSM создаёт новую runtime-команду по DealContext, DealActionState,
runtime-сущностям и exchange facts.
```

`ServiceCommand` может:

* создать локальный order;
* отправить order на биржу;
* обновить order;
* отменить order;
* создать algo-order;
* отправить algo-order на биржу;
* отменить algo-order;
* закрыть позицию;
* обновить баланс;
* обновить позицию;
* финализировать сделку;
* выполнить kill-switch.

Для сущностей, которые создаются на бирже, используется схема:

```text
CREATE_* -> SUBMIT_* -> REFRESH_*
```

Где:

* `CREATE_*` — создать локальную сущность в БД;
* `SUBMIT_*` — отправить локальную сущность на биржу или восстановить факт отправки;
* `REFRESH_*` — подтвердить фактическое состояние.

# 9. FSM статусы

## 9.1. PRECHECK

Назначение:

> Подготовить сделку к созданию entry order.

Источник информации:

* `DealContext`;
* pinned `StrategyDetail`;
* balance snapshot;
* active positions;
* existing orders;
* risk policy;
* instrument settings.

Что проверяет:

* сделка создана корректно;
* есть pinned `StrategyDetail`;
* нет активной позиции, если вход предполагает новую позицию;
* нет конфликтующего entry order;
* торговый режим соответствует проекту;
* используется isolated margin;
* нет признаков borrow / debt;
* хватает доступного баланса;
* риск не превышает лимиты;
* можно создать entry order.

Кто принимает решение:

* `PrecheckHandler` проверяет инварианты этапа;
* `StrategyConditionEvaluator` проверяет условия entry-step;
* `StrategyActionCalculator` проверяет цену, размер и риск действия.

Какие команды возможны:

```text
CREATE_ORDER
SUBMIT_ORDER
REFRESH_BALANCE
REFRESH_POSITION
REFRESH_PENDING_ORDERS
MARK_DEAL_ERROR
```

Когда переход дальше:

```text
PRECHECK -> ENTRY_SUBMITTED
```

Переход разрешён, когда entry order создан локально и/или отправлен на биржу согласно текущему этапу.

Важно:

> Проверка фазы рынка и свежести данных на вход уже была выполнена `EntryScannerJob`.
> В PRECHECK не нужно заново принимать торговое решение.
> Здесь нужны sanity-check и risk-check перед созданием runtime-сущностей.

---

## 9.2. ENTRY_SUBMITTED

Назначение:

> Подтвердить, что entry order отправлен и понять, появилась ли позиция.

Источник информации:

* локальный entry order;
* биржевой order snapshot;
* pending orders;
* position snapshot;
* fills, если нужны для подтверждения исполнения.

Что проверяет:

* entry order существует локально;
* если order уже отправлен — он найден на бирже или в истории;
* если order исполнен — позиция появилась или обновилась;
* attached protection существует, если она должна была быть создана вместе с order;
* нет конфликтующих ордеров.

Какие команды возможны:

```text
SUBMIT_ORDER
REFRESH_ORDER
REFRESH_PENDING_ORDERS
REFRESH_POSITION
REFRESH_FILLS
REFRESH_ORDER_HISTORY
MARK_DEAL_ERROR
```

Когда переход дальше:

```text
ENTRY_SUBMITTED -> ENTRY_FINALIZED
```

Переход разрешён, когда вход подтверждён фактами:

* entry order финализирован;
* позиция открыта;
* known attached protection не потеряна, если она была нужна.

---

## 9.3. ENTRY_FINALIZED

Назначение:

> Подтвердить, что вход завершён, позиция открыта, и определить следующий безопасный путь сопровождения.

На этом этапе стратегия может требовать создать основную standalone-защиту позиции.

Но не каждая стратегия обязана заменять temporary attached protection на standalone main protection.

Источник информации:

* активная позиция;
* фактическая цена входа;
* текущая защита;
* attached protection внутри entry order;
* strategy steps типа `MAIN_PROTECTION`;
* свежие данные для расчёта цены и размера через `StrategyActionCalculator`;
* `DealActionState`;
* exchange facts / refresh results.

Что проверяет:

* позиция активна;
* entry order финализирован;
* требования strategy / risk policy по защите понятны;
* если нужна standalone protection — её можно создать;
* нет уже активной основной защиты того же назначения;
* если protection switch не нужен, позиция уже находится в безопасном состоянии для сопровождения.

Какие команды возможны:

```text
CREATE_ALGO_ORDER
SUBMIT_ALGO_ORDER
REFRESH_ALGO_ORDER
REFRESH_ALGO_ORDERS
CANCEL_ALGO_ORDER
CANCEL_ORDER
REFRESH_POSITION
MARK_DEAL_ERROR
```

Когда переход дальше:

```text
ENTRY_FINALIZED -> PROTECTION_SWITCHED
ENTRY_FINALIZED -> MANAGING
ENTRY_FINALIZED -> ERROR
```

`ENTRY_FINALIZED -> PROTECTION_SWITCHED` используется, если фактически нужен protection switch:

```text
temporary attached protection
  -> заменяется на standalone main protection
  -> attached protection отменяется только после подтверждения main protection
```

`ENTRY_FINALIZED -> MANAGING` разрешён, если protection switch не нужен и позиция безопасна для сопровождения.

Перед переходом в `MANAGING` должен выполняться инвариант:

```text
позиция открыта;
entry order финализирован;
если strategy / risk policy требует защиту — активная защита подтверждена;
если защита не обязательна — это явно разрешено strategy / risk policy.
```

---

## 9.4. PROTECTION_SWITCHED

Назначение:

> Подтвердить, что temporary attached protection больше не является основной активной защитой, а основная защита переведена на standalone main protection.

`PROTECTION_SWITCHED` не означает просто “защита существует”.

Он означает конкретный факт switch-сценария:

```text
temporary attached protection
  -> main protection подтверждена active
  -> temporary attached protection снята или больше не влияет на риск
```

Этот статус не является обязательным для всех сделок.

Источник информации:

* active position;
* active algo-orders;
* attached protection внутри entry order;
* pending orders;
* exchange snapshots;
* `DealActionState`.

Что проверяет:

* позиция активна;
* main protection активна;
* temporary attached protection снята или больше не влияет на риск;
* нет дублирующей конфликтующей защиты;
* нет orphan algo-orders.

Какие команды возможны:

```text
REFRESH_POSITION
REFRESH_ALGO_ORDERS
CANCEL_ALGO_ORDER
CANCEL_ORDER
MARK_DEAL_ERROR
```

Когда переход дальше:

```text
PROTECTION_SWITCHED -> MANAGING
PROTECTION_SWITCHED -> ERROR
```

Переход разрешён, когда сделка защищена и готова к обычному сопровождению.

Если switch не нужен, FSM не должна искусственно переводить сделку в `PROTECTION_SWITCHED`.

---

## 9.5. MANAGING

Назначение:

> Сопровождать открытую позицию по стратегии.

Источник информации:

* позиция;
* ордера;
* algo-orders;
* `DealActionState`;
* свежие market данные;
* свежие indicator данные;
* свежая market structure;
* свежая market phase;
* risk/balance data.

Что проверяет:

* условия переноса SL;
* условия partial exit;
* условия trailing;
* условия grid management;
* условия планового выхода;
* fail-safe условия;
* наличие защиты;
* актуальность live-сущностей;
* свежесть данных для конкретного `StrategyStep` через `MarketDataExpirationChecker`.

Какие strategy steps применимы:

```text
PROTECTION_ADJUSTMENT
PARTIAL_EXIT
GRID_MANAGEMENT
EXIT
FAIL_SAFE
```

Перед проверкой `StrategyCondition` для каждого такого step FSM проверяет:

```text
MarketDataExpirationChecker.checkForStep(dealContext, step)
```

Если данные устарели или отсутствуют, применяется `StrategyStep.marketDataExpiredSetting`:

```text
protectedPositionAction
unprotectedPositionAction
```

Data-dependent actions не выполняются по устаревшим данным.

Refresh / cancel / close / safety commands остаются разрешены.

Какие команды возможны:

```text
AMEND_ALGO_ORDER
CREATE_ALGO_ORDER
SUBMIT_ALGO_ORDER
CANCEL_ALGO_ORDER
CREATE_ORDER
SUBMIT_ORDER
AMEND_ORDER
CANCEL_ORDER
CLOSE_POSITION
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
MARK_DEAL_ERROR
```

Когда переход дальше:

```text
MANAGING -> EXIT_PENDING
MANAGING -> ERROR
```

Переход в `EXIT_PENDING` происходит, когда выход инициирован стратегией, SL/TP/algo сработал или позиция закрывается другим допустимым способом.

---

## 9.6. EXIT_PENDING

Назначение:

> Дочистить сделку после инициированного выхода.

Источник информации:

* position snapshot;
* pending orders;
* algo-orders;
* fills;
* order history;
* algo-order history.

Что проверяет:

* позиция закрыта или закрывается;
* нет активного риска;
* нет live ordinary orders;
* нет live algo-orders;
* история исполнения загружена;
* причина закрытия определена.

Какие команды возможны:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
CANCEL_ORDER
CANCEL_ALGO_ORDER
REFRESH_FILLS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
FINALIZE_DEAL_EXIT
MARK_DEAL_CLOSED
MARK_DEAL_ERROR
```

Когда переход дальше:

```text
EXIT_PENDING -> CLOSED
EXIT_PENDING -> ERROR
```

`CLOSED` возможен, когда риск полностью снят и сделка финализирована.

Если сделка ещё в `PRECHECK`, entry condition больше не актуален и live risk ещё не создан, допустимо раннее штатное завершение:

```text
PRECHECK -> CLOSED
Deal.closeReason = ENTRY_CONDITION_EXPIRED
```

Если live risk уже создан или состояние неизвестно, прямой переход в `CLOSED` запрещён: нужен recovery / safety-flow.

---

## 9.7. CLOSED

Назначение:

> Нормальное terminal-завершение сделки.

`CLOSED` означает, что штатная ветка закрытия завершена:

* position закрыта или отсутствует;
* live ordinary orders отсутствуют;
* live algo-orders отсутствуют;
* attached protection отсутствует или больше не влияет на риск;
* финальные факты подтверждены refresh/search/history;
* closeReason определён.

В этом статусе сделка больше не сопровождается как активная.

Для `CLOSED` отдельный FSM handler не нужен.

Разрешены только:

* чтение;
* отчётность;
* аудит;
* аналитика.

Если после `CLOSED` найден live risk, это зона `AnomalyJob / ReconciliationJob`, а не обычной FSM.

---

## 9.8. ERROR

Назначение:

> Аварийное состояние сделки.

FSM не применяет обычную стратегию.

В `ERROR` запрещено:

```text
проверять обычные strategy steps;
создавать новые entry/grid orders;
делать data-dependent protection adjustment;
делать partial exit по обычным strategy conditions;
продолжать MANAGING-flow.
```

Возможные safety/recovery команды:

```text
EXECUTE_KILL_SWITCH
MARK_DEAL_ERROR
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
```

`ERROR` используется, если:

* нарушены критичные инварианты;
* позиция есть, но защита не может быть восстановлена;
* биржа и БД расходятся опасным образом;
* торговый режим нарушен;
* появились признаки borrow / debt;
* обычный recovery небезопасен.

Из `ERROR` запрещён переход:

```text
ERROR -> CLOSED
```

Допустимый аварийный terminal-переход:

```text
ERROR -> EMERGENCY_CLOSED
```

Только после safety-flow / kill-switch и подтверждения отсутствия live risk.

---

## 9.9. EMERGENCY_CLOSED

Назначение:

> Аварийный terminal-финал после подтверждённого снятия live risk.

`EMERGENCY_CLOSED` означает:

* авария была;
* обычная strategy/FSM-логика была заблокирована;
* kill-switch / safety-flow снял риск;
* отсутствие live risk подтверждено refresh/search/history facts;
* сделка больше не требует runtime-сопровождения FSM.

Для `EMERGENCY_CLOSED` отдельный FSM handler не нужен.

Если после `EMERGENCY_CLOSED` найден live risk, это зона `AnomalyJob / ReconciliationJob`.

# 10. Восстановление после рестарта

После рестарта система не должна восстанавливать старые `ServiceCommand` из БД.

`ServiceCommand` — runtime object, поэтому pending command queue не существует.

После рестарта система не должна помнить, на каком action она упала.

Она должна заново собрать факты:

```text
DealContext
DealActionState
Order / AlgoOrder / Position
Exchange данные
```

И сравнить:

```text
что ожидает pinned StrategyDetail
vs
что уже материализовано в runtime
```

После рестарта нельзя слепо верить только `Deal.status`.

FSM должна проверить факты и при необходимости выполнить безопасный forward recovery.

Пример:

```text
StrategyStep GRID_ENTRY:
  action #1
  action #2
  action #3
  action #4
```

До рестарта были созданы 2 order.

После рестарта:

```text
DealActionState(action #1) -> targetEntityId = order1
DealActionState(action #2) -> targetEntityId = order2
DealActionState(action #3) -> отсутствует
DealActionState(action #4) -> отсутствует
```

FSM делает:

```text
action #1 -> refresh / submit, если нужно
action #2 -> refresh / submit, если нужно
action #3 -> create
action #4 -> create
```

Для `ENTRY_FINALIZED` recovery отдельно проверяет:

```text
1. Нужен ли protection switch по pinned StrategyDetail.
2. Есть ли активная main protection.
3. Есть ли temporary attached protection.
4. Можно ли перейти сразу в MANAGING.
5. Или нужно идти через PROTECTION_SWITCHED.
```

Если switch не нужен и позиция безопасна:

```text
ENTRY_FINALIZED -> MANAGING
```

Если switch нужен, но ещё не завершён:

```text
ENTRY_FINALIZED -> PROTECTION_SWITCHED
```

Если состояние небезопасно:

```text
ENTRY_FINALIZED -> ERROR / safety flow / kill-switch
```

Важно:

> Runtime-логика FSM не строится по аудиту.
>
> Для восстановления используется `DealActionState`, runtime-сущности и exchange facts, а `05. Аудит и история исполнения` остаётся журналом фактов.

# 11. AnomalyJob и kill-switch

`AnomalyJob` не сопровождает сделки по FSM.

Он ищет глобальные нарушения инвариантов:

* сущность есть на бирже, но нет в БД;
* больше одной позиции на инструмент;
* активный риск без защиты;
* чужие live orders по инструменту;
* live algo-orders без связи со сделкой;
* превышение глобального плеча;
* нарушение isolated margin;
* признаки borrow / debt.

Если аномалия критична, может быть инициирован kill-switch.

`DealOrchestratorJob` и `AnomalyJob` не должны смешиваться:

```text
DealOrchestratorJob
  -> ведёт известные Deal по FSM

AnomalyJob
  -> ищет глобальные нарушения системных инвариантов
```

---

# 12. Торговые ограничения проекта

Фиксируем:

* OKX SWAP/FUTURES контур;
* торговля только своими средствами;
* без margin borrow;
* без loan/debt логики;
* isolated margin;
* плечо не выше разрешённого стратегией и глобальной risk policy;
* плечо не выше биржевого лимита из `InstrumentExternalRules`;
* не более одной позиции на инструмент;
* максимум одна активная сделка на инструмент, если будущая политика явно не разрешит иначе;
* `CLOSE_POSITION` используется только для полного закрытия позиции;
* прямой partial close через `StrategyPositionAction.CLOSE_PARTIAL` запрещён как постоянный инвариант стратегии и системы;
* частичное уменьшение позиции выполняется только через reduce-only `Order` / `AlgoOrder` actions с recovery через `DealActionState` + fills/history/refresh.

* `Deal.CloseReason.ENTRY_CONDITION_EXPIRED`.
* Правило runtime-only `ServiceCommand` без persisted command queue.
* Инвариант: direct partial close запрещён; partial exit только через reduce-only `Order` / `AlgoOrder`.


```text
1. Раздел с зафиксированными решениями Q1–Q4.
2. Проверка свежести данных через MarketDataExpirationChecker в EntryScannerJob и FSM.
3. Deal.entryReason.
4. Deal.entryStepType.
5. Deal.shutdownReason.
6. EntryReason.
7. ShutdownReason.
8. Условная семантика PROTECTION_SWITCHED.
9. Возможность ENTRY_FINALIZED -> MANAGING без PROTECTION_SWITCHED.

11. Раздел открытых вопросов после применения Q1–Q4.
```

## Изменено

* `DealActionStateStatus`: удалён `CONFIRMED`, успешный terminal-статус action — `COMPLETED`.
* `ERROR` теперь не может переходить в `CLOSED`; аварийный terminal-финал — `EMERGENCY_CLOSED`.
* Открытые вопросы перенумерованы по критичности после применения Q1–Q9.


```text
1. Strategy.INACTIVE:
   - новые сделки не создаются;
   - открытые сделки продолжают сопровождаться по pinned StrategyDetail.

2. Strategy.DELETED:
   - новые сделки не создаются;
   - открытые сделки переводятся в graceful shutdown;
   - Deal.shutdownReason = STRATEGY_DELETED.

3. EntryScannerJob:
   - перед созданием Deal проверяет MarketDataExpirationChecker.checkForEntry(strategy);
   - передаёт entryReason и entryStepType в DealOpeningService.

4. DealOpeningService:
   - сохраняет entryReason и entryStepType;
   - подробный entry context отправляет в аудит / историю исполнения.

5. ENTRY_FINALIZED:
   - больше не всегда обязан вести в PROTECTION_SWITCHED;
   - может перейти напрямую в MANAGING, если switch не нужен и позиция безопасна.

6. PROTECTION_SWITCHED:
   - теперь описан как условный статус только для фактической замены temporary attached protection на main protection.
```

## Удалено / заменено

```text
1. Упоминание StrategyDetails заменено на StrategyDetail.
2. Упоминания snapshots в названии data-доки заменены на "рыночные данные".
3. Старая обязательная цепочка ENTRY_FINALIZED -> PROTECTION_SWITCHED -> MANAGING заменена на условную:
   - ENTRY_FINALIZED -> PROTECTION_SWITCHED -> MANAGING;
   - ENTRY_FINALIZED -> MANAGING.
```

Другие разделы, модели и комментарии сохранены.
