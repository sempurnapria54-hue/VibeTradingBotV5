# Жизненный цикл сделки

> Статус документа: основная процессная дока.
>
> Документ описывает общий жизненный цикл `Deal`: от поиска входа до закрытия сделки и очистки риска.
>
> Подробный регламент FSM-статусов вынесен в отдельный документ: `FSM этапы сделки`.
>
> Подробности command-layer вынесены в отдельный документ: `Сервисные команды`.
>
> Модель стратегии описана отдельно: `Strategy.md`.

---

# Главная идея

Жизненный цикл сделки — это процесс от момента, когда система увидела подходящие условия входа, до полного закрытия сделки и очистки риска.

Сделка не управляется напрямую стратегией и не управляется напрямую executor'ами.

Стратегия описывает:

* какие условия должны выполниться;
* какой `StrategyStep` применим;
* какие `StrategyAction` ожидаются;
* какие параметры нужны для расчёта цены, размера и риска;
* какие индикаторы, структуры рынка и фаза рынка должны быть заранее подготовлены.

Runtime-слой делает:

* готовит рыночные данные;
* ищет возможность входа;
* создаёт `Deal`;
* сопровождает `Deal` через FSM;
* интерпретирует действия стратегии;
* рассчитывает runtime-параметры действий;
* создаёт сервисные команды;
* исполняет команды через executor'ы;
* восстанавливается после рестарта по фактическому состоянию БД и биржи.

Главное правило:

> Стратегия задаёт ожидаемые действия и привязывает их к этапам сделки.
>
> FSM проверяет фактическое состояние сделки и решает, можно ли применить эти действия сейчас.
>
> `StrategyActionCalculator` рассчитывает runtime-параметры.
>
> `ServiceCommandExecutor` исполняет атомарные команды.

# 1. Общие правила жизненного цикла

## 1.1. Deal создаётся до FSM

`DealOpeningService` создаёт `Deal` в статусе `PRECHECK`.

FSM не создаёт сделку.

FSM сопровождает уже созданную сделку.

## 1.2. Deal работает по pinned StrategyDetail

Когда `EntryScannerJob` нашёл подходящий вход, он уже выбрал `StrategyDetail`.

Эта detail сохраняется в сделке как pinned-конфигурация.

Если стратегия позже стала `INACTIVE` или `DELETED`, уже открытая сделка продолжает жить по pinned `StrategyDetail`, если отдельная политика остановки стратегии не говорит иначе.

Подробности по `Strategy`, `StrategyDetail`, `StrategyStep`, `StrategyCondition` и `StrategyAction` см. в документе:

```text
Strategy.md
```

## 1.3. Deal.status не является единственным источником правды

После рестарта нельзя слепо верить только `Deal.status`.

Нужно собрать `DealContext` и проверить факты:

* есть ли позиция;
* есть ли entry order;
* есть ли active algo-orders;
* какие `DealActionState` уже материализованы;
* что есть на бирже;
* что есть в БД.

Главное правило:

> После рестарта истиной считаются факты из `DealContext`, а не только `Deal.status`.

## 1.4. Runtime recovery должен быть безопасным

После рестарта допускается forward recovery, если этап сделки ещё актуален и восстановление безопасно.

Если фактическое состояние сделки уже ушло дальше, FSM может перейти на более поздний этап.

Если восстановление небезопасно, сделка переводится в `ERROR` или запускается kill-switch.

Подробности по входным/рабочим/выходным проверкам каждого FSM-статуса см. в документе:

```text
FSM этапы сделки
```

## 1.5. Аудит не источник runtime-логики

Аудит и история нужны для расследования и timeline.

FSM не должна читать историю исполнения команд, чтобы понять, что делать дальше.

Runtime-логика строится по:

```text
DealContext
DealActionState
Order / AlgoOrder / Position
exchange snapshots
```

Подробности по истории см. в документе:

```text
Аудит и история исполнения
```

# 2. Большие процессы системы

Вокруг сделки есть 4 больших процесса.

```text
Расчёт индикаторов и рыночных данных
  -> IndicatorJob
  -> MarketStructureJob
  -> MarketPhaseJob

Жизненный цикл сделки
  -> EntryScannerJob
  -> DealOpeningService
  -> DealOrchestratorJob
  -> Deal FSM

Калькуляторы действий стратегии
  -> StrategyActionCalculator
     -> PriceCalculator
     -> SizeCalculator
     -> RiskCalculator

Сервисные команды
  -> ServiceCommandFactory
  -> ServiceCommandExecutor
  -> конкретные Executor'ы
```

Итоговый flow:

```text
IndicatorJob / MarketStructureJob / MarketPhaseJob
  -> готовят свежие данные рынка

EntryScannerJob
  -> читает активную Strategy
  -> читает MarketPhase по Strategy.marketPhaseSetting
  -> выбирает StrategyDetail по MarketPhase.Type
  -> проверяет ENTRY / GRID_ENTRY conditions
  -> если условия подходят, вызывает DealOpeningService

DealOpeningService
  -> создаёт Deal в статусе PRECHECK
  -> сохраняет pinned StrategyDetail

DealOrchestratorJob
  -> загружает DealContext
  -> запускает Deal FSM

Deal FSM / StateHandler
  -> проверяет этап сделки
  -> проверяет StrategyCondition
  -> выбирает StrategyAction

StrategyActionCalculator
  -> получает StrategyAction + DealContext
  -> собирает свежий CalculationContext
  -> вызывает PriceCalculator / SizeCalculator / RiskCalculator
  -> возвращает рассчитанные параметры

ServiceCommandFactory
  -> создаёт ServiceCommand

ServiceCommandExecutor
  -> вызывает конкретный Executor

Executor
  -> исполняет атомарную операцию
  -> сохраняет результат
```

# 3. Как стратегия влияет на runtime

Стратегия не переводит сделку из одного `Deal.Status` в другой напрямую.

Переходы между FSM-этапами делает FSM через входные и выходные проверки фактического состояния.

Влияние стратегии проявляется в трёх местах:

```text
1. Какие условия проверять.
2. Какие actions выполнить.
3. Как рассчитать параметры команд.
```

## 3.1. До FSM стратегия влияет на создание Deal

`EntryScannerJob` использует стратегию до создания сделки:

```text
Strategy
  -> marketPhaseSetting
  -> MarketPhase
  -> StrategyDetail
  -> ENTRY / GRID_ENTRY condition
  -> DealOpeningService
  -> Deal.status = PRECHECK
```

То есть в FSM попадает уже созданная сделка с pinned `StrategyDetail`.

## 3.2. Внутри FSM стратегия влияет через StrategyDetail

FSM handler берёт из `DealContext` pinned `StrategyDetail`:

```text
DealContext.strategyDetail
```

Затем handler смотрит steps, привязанные к текущему статусу сделки:

```text
StrategyDetail.stepsByStatus[Deal.status]
```

Например:

```text
Deal.status = MANAGING

StrategyDetail.stepsByStatus[MANAGING]:
  - PROTECTION_ADJUSTMENT
  - PARTIAL_EXIT
  - GRID_MANAGEMENT
  - EXIT
  - FAIL_SAFE
```

Стратегия говорит:

> В этом статусе сделки вот какие шаги вообще могут быть применены.

## 3.3. StrategyCondition решает, применим ли step

FSM не должна сама знать, когда переносить SL, делать partial exit или закрывать позицию по правилу стратегии.

Она делает так:

```text
handler
  -> берёт StrategyStep для текущего Deal.Status
  -> для каждого StrategyStep проверяет StrategyCondition
  -> если condition true, step применим
```

Пример:

```text
StrategyStep = PROTECTION_ADJUSTMENT

Condition:
  PROFIT_PERCENTS_REACHED >= 1.5
  MAIN_PROTECTION_EXISTS
```

Если condition выполнен, FSM понимает:

> Нужно выполнить actions этого step.

## 3.4. StrategyAction говорит, что именно сделать

После того как `StrategyCondition` прошла, FSM берёт actions:

```text
StrategyStep.actions
```

Пример:

```text
StrategyAlgoOrderAction
  actionType = AMEND
  targetActionKey = main-stop-loss
  stopLossSettings = breakeven / ATR / structure
```

FSM сама не знает, как двигать SL.

Она только видит:

> Стратегия требует изменить algo-order, который был создан action `main-stop-loss`.

Дальше через `DealActionState` находится runtime-сущность:

```text
targetActionKey
  -> target StrategyAction
  -> DealActionState
  -> RuntimeTarget(ALGO_ORDER, algoOrderId)
```

## 3.5. StrategyActionCalculator применяет настройки стратегии

Стратегия влияет на расчёт через поля action и detail:

```text
StrategyOrderAction.placement
StrategyOrderAction.allocationPercents
StrategyAlgoOrderAction.stopLossSettings
StrategyAlgoOrderAction.trailingSettings
StrategyPositionAction.closeFractionPercents
StrategyDetail.riskPerTradePercent
StrategyDetail.maxLeverage
```

FSM не считает цену и размер.

FSM вызывает:

```text
StrategyActionCalculator
  -> PriceCalculator
  -> SizeCalculator
  -> RiskCalculator
```

Только после этого создаётся `ServiceCommand`.

## 3.6. Что стратегия не делает

Стратегия не решает напрямую:

```text
Deal.status = ENTRY_FINALIZED
Deal.status = MANAGING
Deal.status = CLOSED
```

Например переход:

```text
ENTRY_SUBMITTED -> ENTRY_FINALIZED
```

делает не стратегия.

Его делает FSM, когда факты подтверждают:

```text
entry order финализирован
position открыта
нет критичных конфликтов
```

Главная формула:

```text
FSM-статус
  -> выбирает handler

handler
  -> проверяет технические инварианты этапа
  -> берёт StrategyDetail.stepsByStatus[Deal.status]

StrategyCondition
  -> говорит, применим ли step стратегии

StrategyAction
  -> говорит, что нужно сделать

StrategyActionCalculator
  -> считает runtime-параметры

ServiceCommand
  -> исполняет атомарное действие

Exit checks FSM
  -> решают, можно ли перейти на следующий Deal.status
```

# 4. Зоны ответственности

## 4.1. IndicatorJob / MarketStructureJob / MarketPhaseJob

Эти job'ы готовят данные рынка.

Они не управляют сделкой и не создают `Deal`.

### IndicatorJob

`IndicatorJob` считает `IndicatorValue` по настройкам стратегии.

Источник:

```text
Candles + StrategyIndicatorSetting
```

Результат:

```text
IndicatorValue
```

Правила:

* индикаторы считаются только по закрытым свечам;
* warmup-значения не сохраняются;
* `confirmed` не храним;
* если стратегия `DELETED`, новые значения для неё не считаем.

### MarketStructureJob

`MarketStructureJob` считает `MarketStructure` и `MarketPriceLevel` по настройкам стратегии.

Основной источник:

```text
Candles + StrategyMarketStructureSetting
```

Дополнительный источник, если алгоритму нужно:

```text
IndicatorValue
```

Результат:

```text
MarketStructure
  -> List<MarketPriceLevel>
```

### MarketPhaseJob

`MarketPhaseJob` считает `MarketPhase` по `StrategyMarketPhaseSetting`.

Источники:

```text
IndicatorValue + MarketStructure + StrategyMarketPhaseSetting
```

Результат:

```text
MarketPhase
```

Важно:

> `MarketPhase` привязана к `StrategyMarketPhaseSetting`, потому что разные стратегии могут считать фазу рынка по-разному.

Данные этих job'ов используют:

* `EntryScannerJob` — для проверки входа;
* `StrategyConditionEvaluator` — для проверки условий в уже открытой сделке;
* `StrategyActionCalculator` — для расчёта цен, размеров и риска.

Подробности см. в документе:

```text
Расчёт индикаторов и рыночных данных
```

## 4.2. EntryScannerJob

`EntryScannerJob` отвечает за поиск возможности создать новую сделку.

Он не выставляет ордера и не открывает позицию.

Он делает:

1. Читает активные стратегии по инструментам.
2. Для каждой стратегии получает актуальную `MarketPhase`, рассчитанную по `Strategy.marketPhaseSetting`.
3. Проверяет свежесть `MarketPhase` через `StrategyMarketPhaseSetting.maxAgeBars`.
4. По `MarketPhase.Type` выбирает подходящий `StrategyDetail`.
5. Проверяет `phaseEntryPolicy`:

   * если `NO_TRADE` — сделка не создаётся;
   * если `FOLLOW_PHASE` / `CONTRARIAN` / `GRID` — продолжает проверку.
6. Читает свежие данные, нужные для входа:

   * `MarketPriceData`;
   * `IndicatorValue`;
   * `MarketStructure`;
   * `MarketPhase`;
   * balance / risk data, если нужны для предварительной проверки.
7. Проверяет, что по инструменту нет активной сделки, если одновременно разрешена только одна сделка.
8. Проверяет, что по инструменту нет активной позиции, если стратегия требует новый вход.
9. Находит `StrategyStep` с `stepType = ENTRY` или `GRID_ENTRY`.
10. Проверяет `StrategyCondition` выбранного entry-step.
11. Если условия входа выполнены — вызывает `DealOpeningService`.

`EntryScannerJob` передаёт в `DealOpeningService` уже выбранные данные:

* `instrumentId`;
* `strategyDetailId`;
* `marketPhase`;
* `entryStepType`;
* направление сделки, если оно уже определено;
* entry context / reason, если нужно для аудита.

Не делает:

* не создаёт order;
* не создаёт algo-order;
* не открывает позицию;
* не исполняет `StrategyAction`;
* не запускает FSM напрямую;
* не ходит на биржу для выставления ордеров.

Важно:

> Не рынок “дал сигнал”, а `EntryScannerJob` увидел, что текущее состояние рынка подходит под `ENTRY condition` активной стратегии.

---

## 4.3. DealOpeningService

`DealOpeningService` отвечает за атомарное создание `Deal`.

Он не принимает торговое решение о входе.

Решение о том, что условия входа подходят, принимает `EntryScannerJob` через проверку `StrategyStep ENTRY` / `GRID_ENTRY`.

`DealOpeningService` получает от `EntryScannerJob` уже выбранные данные:

* `instrumentId`;
* `strategyDetailId`;
* `marketPhase`;
* направление сделки, если оно уже определено;
* причину создания сделки / entry context, если нужно для аудита.

`DealOpeningService` делает:

1. Выполняет финальную защитную проверку, что по инструменту всё ещё нет активной сделки.
2. Создаёт `Deal`.
3. Ставит `Deal.Status = PRECHECK`.
4. Сохраняет pinned-связи сделки с инструментом, `StrategyDetail` и фазой рынка.
5. Возвращает созданную сделку.

Не делает:

* не ищет активную стратегию;
* не выбирает `StrategyDetail`;
* не анализирует индикаторы;
* не проверяет `ENTRY condition`;
* не создаёт order;
* не создаёт algo-order;
* не ходит на биржу;
* не запускает FSM.

Важно:

> Создание `Deal` — часть жизненного цикла сделки.
>
> Но создание `Deal` не является частью FSM.
>
> FSM сопровождает уже созданную сделку.

---

## 4.4. DealOrchestratorJob

`DealOrchestratorJob` сопровождает уже созданные сделки.

Он делает:

1. Находит активные `Deal`.
2. Для каждой сделки загружает `DealContext`.
3. Запускает `DealStateMachine`.
4. Получает `TransitionResult`.
5. Передаёт команды в `ServiceCommandExecutor`.
6. Перезагружает `DealContext` после выполнения команд.
7. Сохраняет новый статус сделки.

Он не делает:

* не считает индикаторы;
* не ищет новые входы;
* не ходит на биржу напрямую;
* не считает цены вручную;
* не исполняет REST-запросы сам.

---

## 4.5. DealStateMachine

`DealStateMachine` управляет статусами сделки.

Она делает:

* выбирает handler по текущему `Deal.Status`;
* запускает входные проверки handler'а;
* выполняет рабочую логику этапа;
* проверяет условия стратегии, если этап допускает strategy steps;
* выбирает допустимые `StrategyAction`;
* возвращает команды и новый статус, если переход разрешён.

FSM не делает:

* не создаёт `Deal`;
* не рассчитывает индикаторы;
* не собирает live-цену;
* не исполняет команды;
* не вызывает биржу;
* не строит аудит.

Подробности по каждому FSM-статусу см. в документе:

```text
FSM этапы сделки
```

## 4.6. StrategyActionCalculator

`StrategyActionCalculator` рассчитывает runtime-параметры для выбранного действия стратегии.

Он получает:

```text
StrategyAction + DealContext
```

`DealContext` даёт калькулятору факты сделки:

* `Deal`;
* `Instrument`;
* `StrategyDetail`;
* `BalanceContainer`;
* `PositionContext`;
* `Order`;
* `AlgoOrder`;
* `DealActionState`.

После этого `StrategyActionCalculator` собирает свежий `CalculationContext` через сервисы:

* `MarketPriceDataService`;
* `InstrumentExternalRulesService`;
* `IndicatorService`;
* `MarketStructureService`;
* `MarketPhaseService`;
* `BalanceService`, если нужно обновить баланс перед risk-check.

`StrategyActionCalculator` делает:

1. Собирает свежий `CalculationContext`.
2. Получает актуальные внешние правила инструмента через `InstrumentExternalRulesService`.
3. Получает актуальные рыночные данные `MarketPriceData`, если они нужны выбранному action.
4. Получает готовые `IndicatorValue`, если action / condition / SL требует индикаторы.
5. Получает готовые `MarketStructure`, если action / condition / SL требует рыночные уровни.
6. Получает актуальную `MarketPhase`, если это нужно для проверки условия.
7. Вызывает `PriceCalculator`.
8. Вызывает `SizeCalculator`.
9. Вызывает `RiskCalculator`.
10. Возвращает готовые параметры для `ServiceCommand`.

Важно:

> `CalculationContext` не хранится в `DealContext`.
>
> `DealContext` — это факты сделки для FSM.
>
> `CalculationContext` — это свежий runtime-контекст для расчёта конкретного `StrategyAction`.

Причина:

```text
DealContext собрали
  -> прошло несколько секунд
  -> цена / ATR / фаза / структура могли измениться
  -> перед созданием команды нужно пересчитать параметры по свежим данным
```

Подробности см. в документе:

```text
Калькуляторы действий стратегии
```

# 5. Deal

`Deal` — корневая runtime-сущность сделки.

Она фиксирует, что система начала сопровождать конкретный торговый сценарий по выбранному инструменту и pinned `StrategyDetail`.

```java
public class Deal extends Auditable {

    /**
     * Технический ID сделки.
     */
    private Long id;

    /**
     * Безопасный внешний / межсервисный идентификатор сделки.
     */
    private String internalId;

    /**
     * Инструмент сделки.
     */
    private Long instrumentId;

    /**
     * Pinned detail стратегии, по которой создана сделка.
     */
    private Long strategyDetailId;

    /**
     * Фаза рынка, по которой была выбрана StrategyDetail при создании сделки.
     */
    private Long marketPhaseId;

    /**
     * Текущий статус сделки в FSM.
     */
    private Status status;

    /**
     * Направление сделки: LONG / SHORT.
     */
    private StrategyTradeDirection direction;

    /**
     * Причина закрытия сделки, если сделка уже закрывается или закрыта.
     */
    private CloseReason closeReason;

    /**
     * Время открытия сделки в нашей системе.
     */
    private OffsetDateTime openedAt;

    /**
     * Время закрытия сделки в нашей системе.
     */
    private OffsetDateTime closedAt;

    public enum Status {

        /**
         * Сделка создана, но entry order ещё не создан / не отправлен.
         */
        PRECHECK,

        /**
         * Entry order создан или отправлен, ждём подтверждения входа.
         */
        ENTRY_SUBMITTED,

        /**
         * Вход подтверждён: entry order финализирован, позиция открыта.
         */
        ENTRY_FINALIZED,

        /**
         * Основная standalone-защита создана и временная attached-защита безопасно снята или больше не нужна.
         */
        PROTECTION_SWITCHED,

        /**
```

# 6. DealContext

`DealContext` — это контекст FSM.

Он отвечает на вопрос:

> Что сейчас известно о сделке?

`DealContext` содержит факты сделки и runtime-состояние, которое нужно FSM для принятия решений по этапам сделки.

Он не должен превращаться в универсальный контейнер всех свежих рыночных данных.

Для критичных расчётов цены, размера, риска и внешних правил инструмента `StrategyActionCalculator` собирает свежий `CalculationContext`.

```java
public class DealContext {

   /**
    * Сделка, которую сейчас сопровождает FSM.
    */
   private Deal deal;

   /**
    * Торговый инструмент сделки.
    */
   private Instrument instrument;

   /**
    * Деталь стратегии, по которой была создана сделка.
    *
    * Это pinned-конфигурация сделки.
    */
   private StrategyDetail strategyDetail;

   /**
    * Контейнер баланса аккаунта.
    */
   private BalanceContainer balanceContainer;

   /**
    * Состояние позиций по инструменту сделки.
    */
   private PositionContext positionContext;

   /**
    * Ordinary orders, связанные со сделкой.
    *
    * Attached protection хранится внутри Order,
    * поэтому отдельное поле AttachedProtection в DealContext не нужно.
    */
   private List<Order> orders;

   /**
    * Algo-orders, связанные со сделкой.
    */
   private List<AlgoOrder> algoOrders;

   /**
    * Runtime-состояние выполнения actions стратегии.
    */
   private List<DealActionState> actionStates;
}
```

## 6.2. Что специально не входит в DealContext

В `DealContext` не включаем как обязательные поля:

```text
Strategy целиком
InstrumentExternalRules
MarketPriceData
IndicatorValue
MarketStructure
MarketPhase как свежий runtime-result
AttachedProtection отдельным полем
```

Пояснения:

* `Strategy` целиком не нужна, потому что сделка работает по pinned `StrategyDetail`.
* `InstrumentExternalRules` получает `StrategyActionCalculator` прямо перед расчётом.
* `MarketPriceData`, `IndicatorValue`, `MarketStructure`, `MarketPhase` для расчётов собираются в свежий `CalculationContext`.
* `AttachedProtection` не нужен отдельным полем, потому что это вложенная часть `Order`.

Важно:

> FSM принимает решения по фактам из `DealContext`, а не только по `Deal.status`.
>
> Калькуляторы принимают решения по свежему `CalculationContext`, собранному в runtime.

# 8. DealActionState — кратко

`DealActionState` — runtime-состояние выполнения действия стратегии.

Это не аудит.

Это операционная проекция, которая нужна FSM для восстановления после рестарта.

Зачем нужен `DealActionState`:

* `Order`, `AlgoOrder`, `Position` остаются чистыми биржевыми сущностями;
* в них не храним `strategyActionId`;
* в них не храним `role / level` стратегии;
* связь `StrategyAction -> runtime entity` хранится отдельно;
* FSM после рестарта понимает, какие actions уже материализованы, а какие ещё нет.

Краткая связка:

```text
StrategyAction.id
  -> DealActionState.strategyActionId
     -> RuntimeTarget
        -> entityType
        -> entityId
```

# 10. Восстановление после рестарта

FSM не должна помнить, на каком действии упал процесс.

После рестарта она заново собирает:

* `DealContext`;
* `DealActionState`;
* runtime-сущности;
* exchange snapshots.

Пример:

```text
StrategyStep GRID_ENTRY:
  action key = grid-entry-long-1
  action key = grid-entry-long-2
  action key = grid-entry-short-3
  action key = grid-entry-short-4
```

При сохранении стратегии эти `key` резолвятся во внутренние `strategyActionId`.

До рестарта создали 2 order.

После рестарта:

```text
DealActionState(strategyActionId для grid-entry-long-1)
  -> target.entityId = order1
  -> status = CREATED

DealActionState(strategyActionId для grid-entry-long-2)
  -> target.entityId = order2
  -> status = SUBMITTED

DealActionState(strategyActionId для grid-entry-short-3)
  -> отсутствует

DealActionState(strategyActionId для grid-entry-short-4)
  -> отсутствует
```

FSM делает:

```text
grid-entry-long-1 -> submit / refresh
grid-entry-long-2 -> refresh
grid-entry-short-3 -> create
grid-entry-short-4 -> create
```

Для `AMEND` / `CANCEL`:

```text
cancel-grid-entry-long-1
  -> targetActionKey = grid-entry-long-1
  -> при сохранении стратегии targetActionKey резолвится в target StrategyAction
  -> найти DealActionState(dealId, target StrategyAction.id)
  -> получить RuntimeTarget(entityType = ORDER, entityId = order1)
  -> создать CANCEL_ORDER(orderId = order1)
```

Важно:

> Runtime-логика FSM не строится по аудиту.
>
> Для восстановления используется `DealActionState`, а аудит остаётся журналом фактов.

Подробные recovery-сценарии по каждому статусу сделки описаны в документе:

```text

```

# 11. AnomalyJob и kill-switch

`AnomalyJob` не сопровождает сделки по FSM.

Он ищет глобальные нарушения инвариантов:

* сущность есть на бирже, но нет в БД;
* больше одной позиции на инструмент;
* активный риск без защиты;
* чужие live orders по инструменту;
* live algo-orders без связи со сделкой;
* превышение глобального плеча;
* нарушение isolated margin;
* признаки borrow / debt.

Если аномалия критична, может быть инициирован kill-switch.

`DealOrchestratorJob` и `AnomalyJob` не должны смешиваться:

```text
DealOrchestratorJob
  -> ведёт известные Deal по FSM

AnomalyJob
  -> ищет глобальные нарушения системных инвариантов
```

Подробности по kill-switch и сервисным командам см. в документе:


# 12. Торговые ограничения проекта

Фиксируем:

* OKX SWAP/FUTURES контур;
* торговля только своими средствами;
* без margin borrow;
* без loan/debt логики;
* isolated margin;
* плечо не выше разрешённого стратегией и глобальной risk policy;
* плечо не выше биржевого лимита из `InstrumentExternalRules`;
* не более одной позиции на инструмент;
* максимум одна активная сделка на инструмент, если будущая политика явно не разрешит иначе.
