# Статусы торговых сущностей

## 1. Назначение документа

Документ описывает, как система трактует статусы торговых сущностей и как эти статусы влияют на runtime-логику торгового движка.

Главная цель — чтобы все компоненты одинаково понимали:

* какая сущность ещё участвует в сопровождении сделки;
* какая сущность уже завершена;
* какая сущность создаёт или может создать live risk;
* какие сущности нужно обновлять через refresh;
* какие сущности нужно чистить в `EXIT_PENDING`, `ERROR`, `ErrorHandler`, `KillSwitch`;
* какие сущности считать anomaly;
* как внешние статусы биржи переводятся в доменные статусы.

Документ является основным источником истины по статусам торговых сущностей.

Связанные документы:

* `Strategy.md` — подробная модель стратегии, `StrategyDetail`, `StrategyAction`, pinned `StrategyDetail`.
* `Жизненный цикл сделки.md` — общий flow сделки.
* `FSM этапы сделки.md` — FSM-статусы сделки и handlers.
* `Сервисные команды.md` — runtime-команды и правила их исполнения.
* `Оценка рисков.md` — risk-layer и блокировки риска.
* `Открытые вопросы по движку.md` — нерешённые вопросы, если они появятся.

---

## 2. Область действия

В документ входят торговые сущности, которые влияют на:

* разрешение или запрет новых сделок;
* сопровождение открытых сделок;
* live risk;
* cleanup;
* recovery после рестарта;
* refresh/search/history facts;
* anomaly detection;
* safety-flow.

Основные сущности:

* `Exchange` / `ExchangeAccount`;
* `Instrument`;
* `Strategy`;
* `Deal`;
* `DealActionState`;
* `Order`;
* `AlgoOrder`;
* `Position`;
* `BalanceContainer`.

Документ не заменяет подробные документы по стратегиям, жизненному циклу сделки, сервисным командам и аудиту. Он фиксирует только статусную семантику и её влияние на runtime.

---

## 3. Общий принцип

Система не должна использовать внешние статусы биржи напрямую в FSM, handlers, `DealContextService`, `AnomalyJob` или `KillSwitch`.

Правильная цепочка:

```text
exchange snapshot / external status
-> exchange-specific resolver
-> domain status
-> Active entity / Closed entity / Live risk semantics
-> runtime decision
```

То есть сначала внешний статус конкретной биржи переводится в доменный статус. После этого весь торговый движок работает только с доменными статусами и доменными признаками.

---

## 4. Основные термины

### 4.1. Domain status

`Domain status` — статус сущности в доменной модели приложения.

Примеры:

* `Order.Status`;
* `AlgoOrder.Status`;
* `Position.Status`;
* `Deal.Status`;
* `DealActionState.Status`;
* `Strategy.Status`;
* `Exchange.Status`;
* `Instrument.Status`.

Доменный статус не должен быть прямой копией строки из API биржи.

---

### 4.2. External status

`External status` — статус, который пришёл от биржи.

Примеры для OKX:

* `live`;
* `partially_filled`;
* `filled`;
* `canceled`;
* `effective`;
* `order_failed`;
* `pause`.

Эти значения зависят от биржи и не должны использоваться в бизнес-логике напрямую.

---

### 4.3. Active entity

`Active entity` — сущность, которую локальная система ещё считает участвующей в runtime-процессе.

Это может означать, что сущность:

* требует refresh;
* требует recovery;
* может участвовать в cleanup;
* может влиять на live risk;
* ещё не достигла доменного финального состояния.

Важно:

* `Active entity` — это локальная доменная семантика.
* Она не заменяет биржевую истину.
* Биржевая истина проверяется через refresh/search/history facts.

---

### 4.4. Closed entity

`Closed entity` — сущность, которая в домене переведена в финальное завершённое состояние.

Закрытие не означает удаление записи из БД.

Закрытая сущность может оставаться в БД и использоваться для:

* диагностики;
* восстановления истории;
* расчёта итогов;
* аудита;
* `relatedInactive` snapshot.

---

### 4.5. Live on exchange

`Live on exchange` — сущность на бирже ещё может повлиять на рынок, позицию или риск.

Примеры:

* открытая позиция с ненулевым размером;
* order в состоянии, где он ещё может исполниться;
* algo-order, который ещё может сработать.

---

### 4.6. Closed on exchange

`Closed on exchange` — биржа больше не считает сущность живой.

Примеры:

* order исполнен или отменён;
* algo-order сработал, отменён или завершился ошибкой;
* позиция отсутствует в snapshot или имеет размер `0`.

---

### 4.7. Live risk

`Live risk` — вычисляемое понятие, а не отдельный статус в таблице.

Live risk есть, если сущность или группа сущностей может:

* оставить открытую рыночную позицию;
* создать новую позицию;
* увеличить позицию;
* закрыть или частично закрыть позицию неожиданно для текущего FSM-состояния;
* конфликтовать с cleanup / safety-flow.

Примеры live risk:

* активная `Position`;
* live `Order`, который может исполниться;
* live `AlgoOrder`, который может сработать;
* неизвестная live-сущность на бирже, которой нет в БД.

`reduceOnly` order/algo обычно не увеличивает позицию, но всё равно может влиять на сделку и cleanup. Поэтому он может считаться live-сущностью и должен участвовать в refresh/cleanup.

---

### 4.8. relatedInactive

`relatedInactive` — ограниченный набор уже неактивных сущностей, связанных с текущей сделкой или инструментом.

Это не вся история по инструменту.

`relatedInactive` нужен для:

* расследования;
* recovery;
* anomaly report;
* объяснения, почему FSM принял решение.

`relatedInactive` не должен использоваться как action target для обычного cleanup.

---

## 5. Resolver внешних статусов

### 5.1. Общая идея

Для каждой runtime-сущности должен быть отдельный resolver внешнего статуса.

Рекомендуемое разделение:

* `OrderExternalStatusResolver`;
* `AlgoOrderExternalStatusResolver`;
* `PositionExternalStatusResolver`.

Для каждой биржи должна быть своя реализация:

* `OkxOrderExternalStatusResolver`;
* `OkxAlgoOrderExternalStatusResolver`;
* `OkxPositionExternalStatusResolver`;
* аналогичные реализации для других бирж.

---

### 5.2. Ответственность resolver

Resolver отвечает только за преобразование:

```text
external snapshot / external status -> domain status
```

Resolver не должен:

* сохранять сущность в БД;
* принимать FSM-решения;
* запускать cleanup;
* запускать kill-switch;
* закрывать сделку;
* создавать anomaly report напрямую.

---

### 5.3. Refresh-flow со статусным resolver

Базовый алгоритм refresh:

```text
1. Вызвали refresh.
2. Получили snapshot с биржи.
3. Передали snapshot и exchangeCode в resolver конкретной сущности.
4. Resolver вернул доменный статус.
5. Refresh-service обновил доменную сущность по snapshot.
6. Refresh-service проставил status, который вернул resolver.
7. Refresh-service сохранил сущность в БД.
```

Обновление полей сущности и сохранение в БД делает refresh/service layer, а не resolver.

---

### 5.4. Неизвестный внешний статус

Если resolver получил внешний статус, который он не умеет преобразовать в доменный статус, он должен бросить typed controlled exception.

Рекомендуемый тип:

```java
public class UnknownExternalStatusException extends RuntimeException {

    private final ExchangeCode exchangeCode;
    private final RuntimeEntityType entityType;
    private final String rawStatus;
    private final String externalEntityId;
}
```

Не нужно молча маппить неизвестный статус в `UNKNOWN`.

Причина: если бот не понимает статус биржи, он не может безопасно определить:

* сущность live или closed;
* есть live risk или нет;
* можно ли продолжать FSM;
* можно ли закрыть сделку штатно;
* нужно ли чистить сущность.

---

## 6. Unknown external status policy

Если возник `UnknownExternalStatusException`, применяется safety-critical реакция.

Выбранная политика:

```text
Unknown external status
-> UnknownExternalStatusException
-> текущий Deal переводится в ERROR
-> запускается ErrorHandler / safety-flow
-> Exchange переводится в HOLD
-> новые сделки на этой бирже запрещены до ручного разбора
```

### 6.1. Deal-level реакция

Если неизвестный внешний статус относится к сущности конкретной сделки:

* текущий `Deal` переводится в `ERROR`;
* обычный FSM-flow прекращается;
* далее работает `ErrorHandler` / safety-flow.

`ERROR` не является штатным финальным закрытием сделки. Это runtime-статус, из которого система должна безопасно убрать live risk или оставить сделку для ручного разбора.

---

### 6.2. Exchange-level реакция

Биржа / exchange account переводится в `HOLD`.

Смысл `Exchange HOLD`:

* остановить новые сделки на этой бирже;
* остановить normal trading-flow;
* не дать системе продолжать торговать, пока mapping внешних статусов не разобран вручную.

`Exchange HOLD` не должен блокировать safety/read операции.

---

### 6.3. Что блокирует Exchange HOLD

`Exchange HOLD` блокирует команды normal trading-flow, которые могут создать новый риск или продолжить торговое управление:

```text
SUBMIT_ORDER
SUBMIT_ALGO_ORDER
AMEND_ORDER
AMEND_ALGO_ORDER
```

Также блокируются:

* новые `ENTRY`;
* новые `GRID_ENTRY`;
* новые normal-flow TP/SL/trailing actions;
* pyramid / scaling actions;
* любые действия, которые могут увеличить или изменить торговое намерение не в рамках safety-flow.

---

### 6.4. Что разрешает Exchange HOLD

`Exchange HOLD` разрешает read/safety операции:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
SEARCH by client id
HISTORY lookup
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
KillSwitch / safety-flow
```

Короткое правило:

```text
Exchange HOLD запрещает trading-flow,
но разрешает safety-flow.
```

---

## 7. Управляющие торговые сущности

## 7.1. Exchange / ExchangeAccount

`Exchange` или `ExchangeAccount` отражает возможность торговать на конкретной бирже или аккаунте биржи.

Рекомендуемая семантика статусов:

### ACTIVE

Биржа доступна для normal trading-flow.

Разрешены:

* создание новых сделок;
* submit команд;
* amend команд;
* refresh;
* cancel;
* close;
* safety-flow.

### HOLD

Биржа поставлена на паузу по safety-причине.

Новые сделки запрещены.

Normal trading-flow запрещён.

Safety/read операции разрешены.

Типовые причины:

* неизвестный внешний статус;
* критическое расхождение с биржей;
* подозрение на изменение API semantics;
* ручная остановка торговли на бирже;
* глобальная anomaly по бирже.

### DISABLED

Биржа отключена полностью.

Используется для конфигурационного отключения биржи или аккаунта.

На первом этапе можно трактовать как запрет новых сделок. Разрешение safety/read операций зависит от причины отключения и должно задаваться отдельно.

---

## 7.2. Instrument

`Instrument` отражает возможность торговать конкретным инструментом, например `ETH-USDT-SWAP`.

Рекомендуемая семантика статусов:

### ACTIVE

Инструмент доступен для торговли, если остальные gatekeeper-условия также выполнены:

* `Exchange` не в `HOLD`;
* strategy разрешает новые сделки;
* risk-layer не блокирует;
* market data актуальны или step допускает работу с устаревшими данными;
* инструмент live на бирже;
* соблюдены ограничения маржи, плеча и размера.

### HOLD

Новые сделки по инструменту запрещены.

Safety/read операции по инструменту разрешены.

Типовые причины:

* anomaly по инструменту;
* больше одной позиции на инструмент;
* неизвестные live orders/algo-orders на инструменте;
* превышение допустимого плеча;
* ручная пауза торговли по инструменту.

### DISABLED

Инструмент отключён в системе.

Новые сделки запрещены.

Подробная политика read/safety операций зависит от причины отключения.

---

## 7.3. Strategy

`Strategy.Status` не является статусом runtime-сущности сделки, но напрямую влияет на возможность создания новых сделок и на режим сопровождения уже открытых сделок.

Подробная модель `Strategy`, `StrategyDetail`, `StrategyAction` и pinned `StrategyDetail` описана в документе `Strategy.md`.

### ACTIVE

`Strategy.ACTIVE` разрешает создание новых сделок по инструменту, если остальные gatekeeper-условия также выполнены:

* `Exchange` не в `HOLD`;
* `Instrument` разрешён;
* risk-layer не блокирует;
* market data достаточно актуальны или step допускает работу с ними;
* выбран подходящий `StrategyDetail`;
* входные условия стратегии выполнены.

### INACTIVE

`Strategy.INACTIVE` блокирует только создание новых сделок.

Уже открытые сделки продолжают сопровождаться по pinned `StrategyDetail`.

`INACTIVE` не должен ломать runtime FSM уже открытых сделок.

### DELETED

`Strategy.DELETED` блокирует создание новых сделок.

Уже открытые сделки не бросаются. Они переводятся в graceful shutdown / безопасное завершение по pinned `StrategyDetail` и правилам FSM.

---

## 8. Runtime-сущности сделки

## 8.1. Deal

`Deal` — агрегат сопровождения сделки.

У `Deal` нет прямого состояния на бирже. Его биржевая реальность выводится через связанные сущности:

* `Position`;
* `Order`;
* `AlgoOrder`;
* fills/history facts.

### Active Deal

`Deal` считается active, если он не находится в terminal-статусе.

Terminal-статусы:

```text
CLOSED
EMERGENCY_CLOSED
```

`ERROR` не считается terminal-статусом.

`ERROR` — это runtime-статус для `ErrorHandler` / safety-flow.

### Terminal Deal

`Deal` считается terminal, если:

* он штатно завершён как `CLOSED`;
* или аварийно завершён как `EMERGENCY_CLOSED`.

Terminal Deal не должен иметь FSM handler.

### Deal live risk

`Deal` имеет live risk, если через связанные сущности есть хотя бы одно:

* active `Position`;
* live `Order`;
* live `AlgoOrder`;
* unknown external live-сущность на бирже;
* расхождение, из-за которого невозможно доказать отсутствие live risk.

---

## 8.2. DealActionState

`DealActionState` — persisted runtime-state конкретного `StrategyAction` внутри сделки.

Он нужен для:

* идемпотентности;
* recovery после рестарта;
* понимания, какой action уже создан/отправлен/завершён;
* безопасного retry;
* связи strategy action с runtime target.

`DealActionState` является главным persisted runtime-state для strategy action.

`ServiceCommand` не хранится в БД как pending command.

### Active DealActionState

`DealActionState` считается active, если action ещё не достиг финального состояния и может требовать:

* submit;
* refresh;
* retry;
* cancel;
* recovery;
* проверки результата.

### Completed DealActionState

Action считается успешно завершённым, если его terminal status = `COMPLETED`.

`ACK` от биржи не является truth.

После ACK action может перейти в промежуточное состояние, но финальный факт подтверждается только через refresh/search/history facts.

### Failed DealActionState

`FAILED` означает, что конкретный action больше не может быть продолжен штатно.

Если failure влияет на live risk или безопасность сделки, `Deal` должен перейти в `ERROR`, а дальше работает `ErrorHandler` / safety-flow.

---

## 8.3. Order

Подробная модель ordinary order и attached protection описана в документе `Order.md`.

`Order` — обычный биржевой ордер, связанный со сделкой.

### Active Order

`Order` считается active entity, если доменный статус означает, что ордер ещё не финализирован и может требовать refresh/recovery/cleanup.

Active statuses:

```text
CREATED
PENDING
ACTIVE
PARTIALLY_COMPLETED
```

На уровне биржи order считается live, если он ещё может исполниться или висит на бирже.

Для OKX внешние live-состояния ordinary order обычно:

```text
live
partially_filled
```

Но FSM и handlers не должны использовать эти строки напрямую. Они должны работать с доменным статусом после `OrderExternalStatusResolver`.

### Closed Order

`Order` считается closed entity, если доменный статус означает финал.

Closed statuses:

```text
COMPLETED
CANCELED
ERROR
```

Для OKX внешние terminal-состояния ordinary order обычно:

```text
filled
canceled
mmp_canceled
```

Closed order остаётся в БД и может использоваться для:

* расчёта результата;
* fills reconciliation;
* history;
* relatedInactive;
* диагностики.

### Order live risk

Order может создавать live risk, если:

* он live на бирже;
* он может исполниться;
* он может открыть, увеличить, уменьшить или закрыть позицию;
* он может конфликтовать с текущим cleanup/safety-flow.

`reduceOnly=true` не означает, что order можно игнорировать. Такой order не должен увеличивать позицию, но он может повлиять на закрытие позиции и cleanup.

### Attached protection

`AttachedAlgoOrder` — attached protection внутри parent `Order`.

Она не является standalone `AlgoOrder` нашей системы и не материализуется автоматически в standalone `AlgoOrder`, даже если биржа возвращает attached/algo identifiers.

Active-like statuses attached protection:

```text
CREATED
PENDING
ACTIVE
```

Terminal statuses attached protection:

```text
COMPLETED
CANCELED
ERROR
```

Если attached protection отсутствует в одном `OrderExternalSnapshot.attachedAlgoOrders`, это не считается финальным фактом. Решение зависит от статуса parent `Order` и runtime facts; подробная policy описана в `Order.md`.

---

## 8.4. AlgoOrder

`AlgoOrder` — биржевой algo-ордер: TP, SL, OCO, trailing, trigger и похожие механики.

### Active AlgoOrder

`AlgoOrder` считается active entity, если доменный статус означает, что он ещё может сработать или повлиять на позицию.

Для OKX внешние active-состояния algo-order обычно:

```text
live
pause
```

### Closed AlgoOrder

`AlgoOrder` считается closed entity, если он завершён на бирже и доменный статус отражает финал.

Для OKX внешние terminal/history-состояния algo-order обычно:

```text
effective
canceled
order_failed
partially_failed
```

### AlgoOrder live risk

AlgoOrder создаёт live risk, если:

* он ещё может сработать;
* он может создать ordinary order;
* он может закрыть или изменить позицию;
* он является защитным SL/TP/trailing и влияет на risk state сделки.

Защитный SL — это live risk в широком смысле, потому что он влияет на позицию и должен учитываться в cleanup/recovery.

---

## 8.5. Position

`Position` — открытая позиция по инструменту.

### Active Position

Position считается active entity, если:

```text
Position.Status = ACTIVE
AND position size != 0
```

На бирже позиция считается live, если:

```text
позиция присутствует в exchange snapshot
AND pos != 0
```

### Closed Position

Position считается closed entity, если:

* доменный статус переведён в закрытое состояние;
* сохранён `closeReason`;
* биржа подтверждает отсутствие позиции или `pos = 0`.

На бирже позиция считается закрытой, если:

```text
позиция отсутствует в snapshot
OR pos = 0
```

### Position live risk

Active position почти всегда означает live risk.

Пока позиция открыта, сделка не может считаться штатно закрытой.

---

## 8.6. BalanceContainer

`BalanceContainer` — snapshot баланса и маржинального состояния.

Баланс не имеет semantics active/closed как `Order`, `AlgoOrder` или `Position`.

Для баланса важны:

* актуальность snapshot;
* принадлежность exchange account;
* корректность equity/margin/frozen values;
* использование в risk validation;
* возможность refresh.

`REFRESH_BALANCE` должен фиксироваться в истории исполнения команд, но баланс не является управляемой торговой сущностью как order/algo/position.

---

## 9. Cleanup rules

## 9.1. EXIT_PENDING

`ExitPendingHandler` отвечает за финальную проверку штатного закрытия сделки.

Перед переводом `Deal` в `CLOSED` должно быть доказано:

* позиция закрыта на бирже;
* active position в домене закрыта;
* known live orders отсутствуют или отменены;
* known live algo-orders отсутствуют или отменены;
* order history обновлена;
* algo-order history обновлена;
* fills подтянуты и сопоставлены;
* нет known live risk по сделке;
* нет неизвестных live-сущностей на бирже, связанных с инструментом/сделкой.

Если после refresh остались известные сделке live `Order` / `AlgoOrder`, они отменяются отдельными командами:

```text
CANCEL_ORDER
CANCEL_ALGO_ORDER
```

Если обнаружены неизвестные live-сущности на бирже, это anomaly/safety-flow, а не штатный cleanup сделки.

---

## 9.2. ErrorHandler

`ErrorHandler` работает после перевода `Deal` в `ERROR`.

Цель `ErrorHandler` — безопасно убрать или локализовать live risk.

Типовые действия:

* refresh positions;
* refresh pending orders;
* refresh algo orders;
* refresh order history;
* refresh algo-order history;
* refresh fills;
* cancel known live orders;
* cancel known live algo-orders;
* close active position;
* при необходимости вызвать KillSwitch / safety-flow.

Если live risk успешно убран и это подтверждено refresh/search/history facts, сделка может перейти в `EMERGENCY_CLOSED`.

`ERROR -> CLOSED` запрещён.

---

## 9.3. KillSwitch

`KillSwitch` используется для аварийного снятия риска.

Он должен работать с live-сущностями:

* active positions;
* live orders;
* live algo-orders.

`KillSwitch` не должен пытаться чистить всю историю по инструменту.

Для report/snapshot можно дополнительно включать `relatedInactive`, но action-state должен работать только с live risk.

---

## 10. Anomaly rules

`AnomalyJob` ищет не штатные runtime-ситуации, а нарушения базовых инвариантов системы.

Типовые anomaly cases:

* live order есть на бирже, но нет соответствующей runtime-сущности в БД;
* live algo-order есть на бирже, но нет соответствующей runtime-сущности в БД;
* active position есть на бирже, но нет известной active position в БД;
* больше одной позиции на инструмент, если система допускает максимум одну;
* DB entity closed, но exchange entity всё ещё live;
* unknown external status;
* нарушен режим isolated margin;
* плечо выше глобального лимита x10;
* найден чужой live risk на инструменте;
* после cleanup остались неизвестные live хвосты.

AnomalyJob не должен вести сделку по FSM. Он фиксирует anomaly/safety report и может инициировать safety-flow по правилам системы.

---

## 11. Component impact matrix

| Компонент | Как влияет документ |
|---|---|
| `RefreshExecutor` | Использует resolver внешних статусов, обновляет сущность по snapshot, проставляет доменный статус, сохраняет в БД. Не содержит hardcode внешних статусов биржи. |
| `DealContextService` | Собирает active entities и limited `relatedInactive`, чтобы FSM видел runtime truth, а не всю историю. |
| `ExitPendingHandler` | Проверяет отсутствие live risk перед переводом `Deal` в `CLOSED`. Чистит только известные live хвосты. |
| `ErrorHandler` | После `Deal.ERROR` запускает safety-flow и работает до устранения live risk или ручного разбора. |
| `AnomalyJob` | Сравнивает exchange live facts с доменными active entities. Неизвестные или чужие live-сущности трактует как anomaly. |
| `KillSwitch` | Работает только с live risk: active positions, live orders, live algo-orders. Не чистит историю. |
| `EntryScannerJob` | Не создаёт новые сделки, если `Exchange` в `HOLD`, `Instrument` в `HOLD/DISABLED`, `Strategy` не разрешает entry или risk-layer блокирует. |
| `DealOpeningService` | Перед созданием candidate `Deal` проверяет gatekeeper-статусы: exchange, instrument, strategy, risk. |
| `ServiceCommandExecutor` | При `Exchange HOLD` блокирует normal trading commands, но разрешает safety/read commands. |

## 12. Минимальные правила для кода

### 12.1. Не размазывать live/closed проверки

Для каждой runtime-сущности должны быть явные методы или semantic helpers.

Примеры:

```java
order.isActiveEntity();
order.isClosedEntity();
order.hasLiveRisk();

algoOrder.isActiveEntity();
algoOrder.isClosedEntity();
algoOrder.hasLiveRisk();

position.isActiveEntity();
position.isClosedEntity();
position.hasLiveRisk();
```

Нельзя в разных сервисах вручную писать разные списки статусов.

---

### 12.2. Внешние статусы только в resolver

FSM, handlers, `DealContextService`, `AnomalyJob`, `KillSwitch` не должны знать, что у OKX есть строки `live`, `partially_filled`, `effective` и т.д.

Эти строки должны жить только в exchange-specific resolver / adapter layer.

---

### 12.3. Unknown external status всегда safety-critical

Неизвестный внешний статус не должен маппиться молча.

Правило:

```text
unknown external status
-> UnknownExternalStatusException
-> Deal ERROR
-> Exchange HOLD
-> manual investigation
```

---

### 12.4. ACK не является truth

ACK от биржи означает только то, что запрос принят или обработан на уровне API.

Финальная истина подтверждается только через:

* refresh;
* search by client id;
* order details;
* order history;
* algo-order details;
* algo-order history;
* fills;
* position snapshot.

---

## 13. Короткий итог

Документ фиксирует две ключевые идеи:

```text
1. Внешние статусы биржи сначала переводятся в доменные статусы через exchange-specific resolver.
2. Доменный статус определяет Active entity / Closed entity / Live risk и влияет на runtime-логику системы.
```

Основное правило безопасности:

```text
Если бот не понимает внешний статус биржи,
он не должен продолжать торговлю.

Текущая сделка уходит в ERROR,
биржа уходит в HOLD,
новые сделки запрещены до ручного разбора.
```
