# Статусы торговых сущностей

## 1. Назначение документа

Документ описывает, как система трактует статусы торговых сущностей и как эти статусы влияют на runtime-логику торгового движка.

Главная цель — чтобы все компоненты одинаково понимали:

* какая сущность ещё участвует в сопровождении сделки;
* какая сущность уже завершена;
* какая сущность создаёт или может создать live risk;
* какие сущности нужно обновлять через refresh;
* какие сущности нужно чистить в `EXIT_PENDING`, `ERROR`, `ErrorHandler`, `KillSwitch`;
* какие сущности считать anomaly;
* как внешние статусы биржи переводятся в доменные статусы.

Документ является основным источником истины по статусам торговых сущностей.

Связанные документы:

* `Strategy.md` — подробная модель стратегии, `StrategyDetail`, `StrategyAction`, pinned `StrategyDetail`.
* `Жизненный цикл сделки.md` — общий flow сделки.
* `FSM этапы сделки.md` — FSM-статусы сделки и handlers.
* `Сервисные команды.md` — runtime-команды и правила их исполнения.
* `Оценка рисков.md` — risk-layer и блокировки риска.
* `Position.md` — доменная модель позиции, live-risk semantics и refresh policy.
* `OKX_Position_mapping.md` — exchange-specific mapping позиции для OKX.
* `Открытые вопросы по движку.md` — нерешённые вопросы, если они появятся.

---

## 2. Область действия

В документ входят торговые сущности, которые влияют на:

* разрешение или запрет новых сделок;
* сопровождение открытых сделок;
* live risk;
* cleanup;
* recovery после рестарта;
* refresh/search/history facts;
* anomaly detection;
* safety-flow.

Основные сущности:

* `Exchange` / `ExchangeAccount`;
* `Instrument`;
* `Strategy`;
* `Deal`;
* `DealActionState`;
* `Order`;
* `AlgoOrder`;
* `Position`;
* `BalanceContainer`.

Документ не заменяет подробные документы по стратегиям, жизненному циклу сделки, сервисным командам и аудиту. Он фиксирует только статусную семантику и её влияние на runtime.

---

## 3. Общий принцип

Система не должна использовать внешние статусы биржи напрямую в FSM, handlers, `DealContextService`, `AnomalyJob` или `KillSwitch`.

Правильная цепочка:

```text
exchange snapshot / external status
-> exchange-specific resolver
-> domain status
-> Active entity / Closed entity / Live risk semantics
-> runtime decision
```

То есть сначала внешний статус конкретной биржи переводится в доменный статус. После этого весь торговый движок работает только с доменными статусами и доменными признаками.

---

## 4. Основные термины

### 4.1. Domain status

`Domain status` — статус сущности в доменной модели приложения.

Примеры:

* `Order.Status`;
* `AlgoOrder.Status`;
* `Position.Status`;
* `Deal.Status`;
* `DealActionState.Status`;
* `Strategy.Status`;
* `Exchange.Status`;
* `Instrument.Status`.

Доменный статус не должен быть прямой копией строки из API биржи.

---

### 4.2. External status

`External status` — статус, который пришёл от биржи.

Примеры для OKX:

* `live`;
* `partially_filled`;
* `filled`;
* `canceled`;
* `effective`;
* `order_failed`;
* `pause`.

Эти значения зависят от биржи и не должны использоваться в бизнес-логике напрямую.

---

### 4.3. Active entity

`Active entity` — сущность, которую локальная система ещё считает участвующей в runtime-процессе.

Это может означать, что сущность:

* требует refresh;
* требует recovery;
* может участвовать в cleanup;
* может влиять на live risk;
* ещё не достигла доменного финального состояния.

Важно:

* `Active entity` — это локальная доменная семантика.
* Она не заменяет биржевую истину.
* Биржевая истина проверяется через refresh/search/history facts.

---

### 4.4. Closed entity

`Closed entity` — сущность, которая в домене переведена в финальное завершённое состояние.

Закрытие не означает удаление записи из БД.

Закрытая сущность может оставаться в БД и использоваться для:

* диагностики;
* восстановления истории;
* расчёта итогов;
* аудита;
* `relatedInactive` snapshot.

---

### 4.5. Live on exchange

`Live on exchange` — сущность на бирже ещё может повлиять на рынок, позицию или риск.

Примеры:

* открытая позиция с ненулевым размером;
* order в состоянии, где он ещё может исполниться;
* algo-order, который ещё может сработать.

---

### 4.6. Closed on exchange

`Closed on exchange` — биржа больше не считает сущность живой.

Примеры:

* order исполнен или отменён;
* algo-order сработал, отменён или завершился ошибкой;
* позиция отсутствует в актуальном position snapshot по инструменту.

Для `Position` есть важное уточнение:

```text
snapshot == null
  -> позиции на бирже нет
  -> closed on exchange

snapshot != null
  -> биржа всё ещё возвращает position record
  -> position существует на бирже
```

Если `snapshot != null`, но размер позиции равен `0`, это не normal `CLOSED` для доменной `Position`.
Такая позиция считается active exchange record без live market risk и требует cleanup / retry / anomaly-разбора по контексту.


### 4.7. Live risk

`Live risk` — вычисляемое понятие, а не отдельный статус в таблице.

Live risk есть, если сущность или группа сущностей может:

* оставить открытую рыночную позицию;
* создать новую позицию;
* увеличить позицию;
* закрыть или частично закрыть позицию неожиданно для текущего FSM-состояния;
* конфликтовать с cleanup / safety-flow.

Примеры live risk:

* активная `Position`;
* live `Order`, который может исполниться;
* live `AlgoOrder`, который может сработать;
* неизвестная live-сущность на бирже, которой нет в БД.

`reduceOnly` order/algo обычно не увеличивает позицию, но всё равно может влиять на сделку и cleanup. Поэтому он может считаться live-сущностью и должен участвовать в refresh/cleanup.

---

### 4.8. relatedInactive

`relatedInactive` — ограниченный набор уже неактивных сущностей, связанных с текущей сделкой или инструментом.

Это не вся история по инструменту.

`relatedInactive` нужен для:

* расследования;
* recovery;
* anomaly report;
* объяснения, почему FSM принял решение.

`relatedInactive` не должен использоваться как action target для обычного cleanup.

---

## 5. Resolver внешних статусов

### 5.1. Общая идея

Для каждой runtime-сущности должен быть отдельный resolver внешнего статуса или внешнего факта.

Рекомендуемое разделение:

* `OrderExternalStatusResolver`;
* `AlgoOrderExternalStatusResolver`;
* `PositionStatusResolver`.

Для каждой биржи должна быть своя реализация:

* `OkxOrderExternalStatusResolver`;
* `OkxAlgoOrderExternalStatusResolver`;
* `OkxPositionStatusResolver`;
* аналогичные реализации для других бирж.

Для `Order` / `AlgoOrder` resolver обычно работает с внешним статусом биржи.
Для `Position` resolver работает не со строковым external status, а с фактом наличия позиции:

```text
PositionExternalSnapshot / null -> PositionStatusResolveResult
```


### 5.2. Ответственность resolver

Resolver отвечает только за преобразование:

```text
external snapshot / external status / external fact -> domain status + optional closeReason candidate
```

Целевой контракт resolver'а для runtime-сущностей — result-object:

```java
public class EntityStatusResolveResult {

    /** Доменный статус сущности после интерпретации exchange fact. */
    private EntityStatus status;

    /**
     * Кандидат причины финализации / problem-state.
     * Может быть null, если причина не следует из внешнего факта.
     */
    private EntityCloseReason closeReason;
}
```

Resolver не должен:

* сохранять сущность в БД;
* принимать FSM-решения;
* запускать cleanup;
* запускать kill-switch;
* закрывать сделку;
* создавать anomaly report напрямую.

Refresh / executor layer применяет результат resolver'а к доменной сущности.
Если `closeReason` уже заполнен, executor не должен его перетирать.


### 5.3. Refresh-flow со статусным resolver

Базовый алгоритм refresh:

```text
1. Вызвали refresh.
2. Получили snapshot / null / external status с биржи.
3. Передали внешний факт и exchangeCode в resolver конкретной сущности.
4. Resolver вернул result-object: status + optional closeReason candidate.
5. Refresh-service обновил доменную сущность по snapshot, если snapshot есть.
6. Refresh-service применил status, который вернул resolver.
7. Refresh-service заполнил closeReason candidate только если текущий closeReason == null.
8. Refresh-service сохранил сущность в БД.
```

Обновление полей сущности и сохранение в БД делает refresh/service layer, а не resolver.

Для `Position` обычный `REFRESH_POSITION` не получает `requestedCloseReason`, потому что refresh сам по себе не означает намерение закрыть позицию.
`requestedCloseReason` появляется в explicit close-flow, например в команде `CLOSE_POSITION`.


### 5.4. Неизвестный или проблемный внешний статус

Если resolver получил внешний статус, который он не умеет безопасно преобразовать в доменный статус, он должен бросить typed controlled exception.

Целевой тип:

```text
ExternalStatusException(reasonCode = UNKNOWN_EXTERNAL_STATUS)
```

Если внешний статус известен, но сам означает problem-state, resolver тоже бросает `ExternalStatusException`, но с более точным `reasonCode`.

Примеры:

```text
unknown external status -> ExternalStatusException(reasonCode = UNKNOWN_EXTERNAL_STATUS)
order_failed            -> ExternalStatusException(reasonCode = ORDER_FAILED)
partially_failed        -> ExternalStatusException(reasonCode = PARTIALLY_FAILED)
```

Не нужно молча маппить неизвестный статус в `UNKNOWN`.

Причина: если бот не понимает статус биржи, он не может безопасно определить:

* сущность live или closed;
* есть live risk или нет;
* можно ли продолжать FSM;
* можно ли закрыть сделку штатно;
* нужно ли чистить сущность.

## 6. External exchange exception policy

Controlled exchange exceptions используются для ситуаций, когда внешний факт уже получен или должен был быть найден, но система не может безопасно продолжить normal runtime-flow.

Базовые типы:

```text
ExternalStatusException
ExternalInvariantViolationException
ExternalNotFoundException
```

### 6.1. ExternalStatusException

Кто бросает:

```text
StatusResolver конкретной сущности и биржи
```

Примеры:

```text
OrderExternalStatusResolver
AlgoOrderExternalStatusResolver
PositionExternalStatusResolver
```

Когда:

```text
внешний статус получен, но неизвестен;
или внешний статус известен, но означает problem-state.
```

Примеры `reasonCode`:

```text
UNKNOWN_EXTERNAL_STATUS
ORDER_FAILED
PARTIALLY_FAILED
```

Runtime-реакция:

```text
entity -> ERROR
closeReason = reasonCode
Deal -> ERROR
Exchange -> HOLD по severity / safetyImpact
```

### 6.2. ExternalInvariantViolationException

Кто бросает:

```text
ClientService / exchange adapter-layer
```

Когда:

```text
response получен, но нарушает ожидаемый exchange invariant.
```

Примеры:

```text
tdMode != isolated
posSide != net
side != expected direction
ordType != expected conditionType mapping
reduceOnly != expected positionReducingOnly
```

Runtime-реакция:

```text
entity -> ERROR
closeReason = EXCHANGE_INVARIANT_VIOLATION
Deal -> ERROR
Exchange -> HOLD
```

### 6.3. ExternalNotFoundException

Кто бросает:

```text
RefreshExecutor / recovery-search boundary
```

Когда:

```text
после полного evidence-cycle по релевантным источникам сущность не найдена
и её финал нельзя безопасно объяснить.
```

Важно:

```text
ExternalNotFoundException нельзя бросать после одного пустого response.
```

Для `Order` / `AlgoOrder` последний `null` после полного evidence-cycle может быть problem-flow, если финал сущности нельзя безопасно объяснить.

Для `Position` политика другая:

```text
успешный GET /account/positions по instrument
и отсутствие позиции в response
  -> нормальный closed-on-exchange факт
  -> ClientService возвращает null
  -> PositionStatusResolver возвращает CLOSED + EXTERNAL_CLOSE candidate
```

То есть отсутствие позиции в актуальном snapshot по инструменту не является `ExternalNotFoundException`.

Runtime-реакция для настоящего not-found problem-flow:

```text
entity -> ERROR
closeReason = MISSING_AFTER_REFRESH
Deal -> ERROR
Exchange -> HOLD
```


### 6.4. Deal-level реакция

Если controlled exchange exception относится к сущности конкретной сделки:

* текущий `Deal` переводится в `ERROR`;
* обычный FSM-flow прекращается;
* далее работает `ErrorHandler` / safety-flow.

`ERROR` не является штатным финальным закрытием сделки. Это runtime-статус, из которого система должна безопасно убрать live risk или оставить сделку для ручного разбора.

---

### 6.5. Exchange-level реакция

Биржа / exchange account переводится в `HOLD`, если ошибка означает, что normal trading-flow на этой бирже больше нельзя считать безопасным.

Смысл `Exchange HOLD`:

* остановить новые сделки на этой бирже;
* остановить normal trading-flow;
* не дать системе продолжать торговать, пока mapping / invariant / integration problem не разобран вручную.

`Exchange HOLD` не должен блокировать safety/read операции.

---

### 6.6. Что блокирует Exchange HOLD

`Exchange HOLD` блокирует команды normal trading-flow, которые могут создать новый риск или продолжить торговое управление:

```text
SUBMIT_ORDER
SUBMIT_ALGO_ORDER
AMEND_ORDER
AMEND_ALGO_ORDER
```

Также блокируются:

* новые `ENTRY`;
* новые `GRID_ENTRY`;
* новые normal-flow TP/SL/trailing actions;
* pyramid / scaling actions;
* любые действия, которые могут увеличить или изменить торговое намерение не в рамках safety-flow.

---

### 6.7. Что разрешает Exchange HOLD

`Exchange HOLD` разрешает read/safety операции:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
SEARCH by client id
HISTORY lookup
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
KillSwitch / safety-flow
```

Короткое правило:

```text
Exchange HOLD запрещает trading-flow,
но разрешает safety-flow.
```


### 6.8. RiskValidator и cleanup / safety / risk-reducing flow

`RiskValidator` применяется к actions, которые создают новый runtime-риск, увеличивают риск или ослабляют контроль риска.

Обычно такие actions материализуются через:

```text
CREATE_ORDER
AMEND_ORDER
CREATE_ALGO_ORDER
AMEND_ALGO_ORDER
```

Но сам `ServiceCommandType` не является достаточным критерием.
Если `Order` / `AlgoOrder` используется для reduce-only partial exit, это exit-flow, а не RiskValidator-flow.

`RiskValidator` не применяется к exit / cleanup / safety / risk-reducing flow:

```text
reduce-only partial exit через Order / AlgoOrder
CANCEL_ORDER
CANCEL_ALGO_ORDER
CLOSE_POSITION
EXECUTE_KILL_SWITCH
```

Для этих действий выполняются только minimal domain / exchange safety checks и invariant checks.

Минимальные проверки:

```text
entity существует;
entity относится к нужной сделке / инструменту;
есть необходимые internal/external identifiers;
для reduce-only partial exit действие действительно уменьшает позицию;
для reduce-only partial exit размер не превышает текущую позицию;
для CLOSE_POSITION закрывается вся позиция, не partial;
если entity уже terminal, система верит refresh/search/history facts;
команда не противоречит текущему known exchange state.
```

Причина:

```text
Reduce-only partial exit / CANCEL_* / CLOSE_POSITION / EXECUTE_KILL_SWITCH не создают новый торговый риск.
Они убирают, уменьшают или локализуют уже существующий риск.
```

Поэтому risk-layer не должен блокировать safety-flow, `ErrorHandler`, `KillSwitch` или штатный cleanup сделки.

## 7. Управляющие торговые сущности

## 7.1. Exchange / ExchangeAccount

`Exchange` или `ExchangeAccount` отражает возможность торговать на конкретной бирже или аккаунте биржи.

Рекомендуемая семантика статусов:

### ACTIVE

Биржа доступна для normal trading-flow.

Разрешены:

* создание новых сделок;
* submit команд;
* amend команд;
* refresh;
* cancel;
* close;
* safety-flow.

### HOLD

Биржа поставлена на паузу по safety-причине.

Новые сделки запрещены.

Normal trading-flow запрещён.

Safety/read операции разрешены.

Типовые причины:

* неизвестный внешний статус;
* критическое расхождение с биржей;
* подозрение на изменение API semantics;
* ручная остановка торговли на бирже;
* глобальная anomaly по бирже.

### DISABLED

Биржа отключена полностью.

Используется для конфигурационного отключения биржи или аккаунта.

На первом этапе можно трактовать как запрет новых сделок. Разрешение safety/read операций зависит от причины отключения и должно задаваться отдельно.

---

## 7.2. Instrument

`Instrument` отражает возможность торговать конкретным инструментом, например `ETH-USDT-SWAP`.

Рекомендуемая семантика статусов:

### ACTIVE

Инструмент доступен для торговли, если остальные gatekeeper-условия также выполнены:

* `Exchange` не в `HOLD`;
* strategy разрешает новые сделки;
* risk-layer не блокирует;
* market data актуальны или step допускает работу с устаревшими данными;
* инструмент live на бирже;
* соблюдены ограничения маржи, плеча и размера.

### HOLD

Новые сделки по инструменту запрещены.

Safety/read операции по инструменту разрешены.

Типовые причины:

* anomaly по инструменту;
* больше одной позиции на инструмент;
* неизвестные live orders/algo-orders на инструменте;
* превышение допустимого плеча;
* ручная пауза торговли по инструменту.

### DISABLED

Инструмент отключён в системе.

Новые сделки запрещены.

Подробная политика read/safety операций зависит от причины отключения.

---

## 7.3. Strategy

`Strategy.Status` не является статусом runtime-сущности сделки, но напрямую влияет на возможность создания новых сделок и на режим сопровождения уже открытых сделок.

Подробная модель `Strategy`, `StrategyDetail`, `StrategyAction` и pinned `StrategyDetail` описана в документе `Strategy.md`.

### ACTIVE

`Strategy.ACTIVE` разрешает создание новых сделок по инструменту, если остальные gatekeeper-условия также выполнены:

* `Exchange` не в `HOLD`;
* `Instrument` разрешён;
* risk-layer не блокирует;
* market data достаточно актуальны или step допускает работу с ними;
* выбран подходящий `StrategyDetail`;
* входные условия стратегии выполнены.

### INACTIVE

`Strategy.INACTIVE` блокирует только создание новых сделок.

Уже открытые сделки продолжают сопровождаться по pinned `StrategyDetail`.

`INACTIVE` не должен ломать runtime FSM уже открытых сделок.

### DELETED

`Strategy.DELETED` блокирует создание новых сделок.

Уже открытые сделки не бросаются. Они переводятся в graceful shutdown / безопасное завершение по pinned `StrategyDetail` и правилам FSM.

---

## 8. Runtime-сущности сделки

## 8.1. Deal

`Deal` — агрегат сопровождения сделки.

У `Deal` нет прямого состояния на бирже. Его биржевая реальность выводится через связанные сущности:

* `Position`;
* `Order`;
* `AlgoOrder`;
* fills/history facts.

### Active Deal

`Deal` считается active, если он не находится в terminal-статусе.

Terminal-статусы:

```text
CLOSED
EMERGENCY_CLOSED
```

`ERROR` не считается terminal-статусом.

`ERROR` — это runtime-статус для `ErrorHandler` / safety-flow.

### Terminal Deal

`Deal` считается terminal, если:

* он штатно завершён как `CLOSED`;
* или аварийно завершён как `EMERGENCY_CLOSED`.

Terminal Deal не должен иметь FSM handler.

### Deal live risk

`Deal` имеет live risk, если через связанные сущности есть хотя бы одно:

* active `Position` с live risk;
* live `Order`;
* live `AlgoOrder`;
* unknown external live-сущность на бирже;
* расхождение, из-за которого невозможно доказать отсутствие live risk.

---

## 8.2. DealActionState

`DealActionState` — persisted runtime-state конкретного `StrategyAction` внутри сделки.

Он нужен для:

* идемпотентности;
* recovery после рестарта;
* понимания, какой action уже создан/отправлен/завершён;
* безопасного retry;
* связи strategy action с runtime target.

`DealActionState` является главным persisted runtime-state для strategy action.

`ServiceCommand` не хранится в БД как pending command.

### Active DealActionState

`DealActionState` считается active, если action ещё не достиг финального состояния и может требовать:

* submit;
* refresh;
* retry;
* cancel;
* recovery;
* проверки результата.

### Completed DealActionState

Action считается успешно завершённым, если его terminal status = `COMPLETED`.

`ACK` от биржи не является truth.

После ACK action может перейти в промежуточное состояние, но финальный факт подтверждается только через refresh/search/history facts.

### Failed DealActionState

`FAILED` означает, что конкретный action больше не может быть продолжен штатно.

Если failure влияет на live risk или безопасность сделки, `Deal` должен перейти в `ERROR`, а дальше работает `ErrorHandler` / safety-flow.

---

## 8.3. Order

Подробная модель ordinary order и attached protection описана в документе `Order.md`.

`Order` — обычный биржевой ордер, связанный со сделкой.

### Active Order

`Order` считается active entity, если доменный статус означает, что ордер ещё не финализирован и может требовать refresh/recovery/cleanup.

Active statuses:

```text
CREATED
PENDING
ACTIVE
PARTIALLY_COMPLETED
```

На уровне биржи order считается live, если он ещё может исполниться или висит на бирже.

Для OKX внешние live-состояния ordinary order обычно:

```text
live
partially_filled
```

Но FSM и handlers не должны использовать эти строки напрямую. Они должны работать с доменным статусом после `OrderExternalStatusResolver`.

### Closed Order

`Order` считается closed entity, если доменный статус означает финал.

Closed statuses:

```text
COMPLETED
CANCELED
ERROR
```

Для OKX внешние terminal-состояния ordinary order обычно:

```text
filled
canceled
mmp_canceled
```

Closed order остаётся в БД и может использоваться для:

* расчёта результата;
* fills reconciliation;
* history;
* relatedInactive;
* диагностики.

### Order live risk

Order может создавать live risk, если:

* он live на бирже;
* он может исполниться;
* он может открыть, увеличить, уменьшить или закрыть позицию;
* он может конфликтовать с текущим cleanup/safety-flow.

`reduceOnly=true` не означает, что order можно игнорировать. Такой order не должен увеличивать позицию, но он может повлиять на закрытие позиции и cleanup.

### Attached protection

`AttachedAlgoOrder` — attached protection внутри parent `Order`.

Она не является standalone `AlgoOrder` нашей системы и не материализуется автоматически в standalone `AlgoOrder`, даже если биржа возвращает attached/algo identifiers.

Active-like statuses attached protection:

```text
CREATED
PENDING
ACTIVE
```

Terminal statuses attached protection:

```text
COMPLETED
CANCELED
ERROR
```

Если attached protection отсутствует в одном `OrderExternalSnapshot.attachedAlgoOrders`, это не считается финальным фактом. Решение зависит от статуса parent `Order` и runtime facts; подробная policy описана в `Order.md`.

---

## 8.4. AlgoOrder

`AlgoOrder` — standalone биржевой algo-order: TP, SL, OCO, trailing и похожие механики.

Подробная доменная модель standalone `AlgoOrder` описана в документе `AlgoOrder.md`.

### Active AlgoOrder

`AlgoOrder` считается active entity, если доменный статус означает, что он ещё может сработать, требует refresh/recovery/cleanup или может повлиять на позицию.

Runtime-live статусы:

```text
CREATED
PENDING
ACTIVE
PARTIALLY_COMPLETED
```

Семантика:

```text
CREATED
  локальный intent создан, на бирже ещё не подтверждён.

PENDING
  submit/amend/cancel был или мог быть выполнен, нужен refresh/search/history.

ACTIVE
  algo-order активен на бирже и может сработать.

PARTIALLY_COMPLETED
  algo-order частично сработал на бирже;
  это exchange-driven recovery status, а не целевой flow стратегии.
```

Для OKX внешние runtime-live / recovery состояния standalone algo-order:

```text
live
pause
partially_effective
```

Важно:

```text
live / pause
  -> обычные active-like external states.

partially_effective
  -> не обычный active-state,
  -> это recovery-state,
  -> маппится в PARTIALLY_COMPLETED,
  -> требует добора фактов и решения FSM.
```

Mapping:

```text
live                -> ACTIVE
pause               -> ACTIVE
partially_effective -> PARTIALLY_COMPLETED
```

`pause` считается active external status: algo-order существует на бирже и может влиять на risk / cleanup.

`partially_effective` не является штатной целью стратегии и требует recovery/facts cycle.

### Closed AlgoOrder

`AlgoOrder` считается closed entity, если доменный статус означает финал или problem-final для самой сущности.

Terminal / problem-final статусы:

```text
COMPLETED
CANCELED
ERROR
```

Семантика:

```text
COMPLETED
  algo-order штатно сработал.

CANCELED
  algo-order отменён.

ERROR
  problem-final для entity;
  дальше работает Deal.ERROR / safety-flow.
```

Для OKX внешние terminal/problem состояния standalone algo-order:

```text
effective
canceled
order_failed
partially_failed
```

Mapping:

```text
effective       -> COMPLETED / TRIGGERED
canceled        -> CANCELED / closeReason из cancel intent
order_failed    -> ExternalStatusException(reasonCode = ORDER_FAILED)
partially_failed -> ExternalStatusException(reasonCode = PARTIALLY_FAILED)
unknown         -> ExternalStatusException(reasonCode = UNKNOWN_EXTERNAL_STATUS)
```

`partially_failed` считается problem-state: часть сценария могла успеть выполниться, но биржа сообщает частичный сбой.

### AlgoOrder live risk

AlgoOrder создаёт live risk, если:

* он ещё может сработать;
* он может создать ordinary order;
* он может закрыть или изменить позицию;
* он является защитным SL/TP/trailing и влияет на risk state сделки;
* его состояние не может быть безопасно интерпретировано.

Защитный SL — это live risk в широком смысле, потому что он влияет на позицию и должен учитываться в cleanup/recovery.

---

## 8.5. Position

Подробная доменная модель позиции описана в документе `Position.md`.
Exchange-specific mapping для OKX описан в документе `OKX_Position_mapping.md`.

`Position` — runtime-сущность позиции внутри `Deal`.

Главные правила:

* `Position` принадлежит `Deal` через `dealId`;
* `Position` не хранит `instrumentId` / `exchangeId`;
* `Instrument` и `Exchange` собираются в `DealContext` на каждой итерации FSM;
* локальная `Position` создаётся и обновляется только через `REFRESH_POSITION`;
* `Position` отвечает за live-risk состояние позиции, а не за итоговый PnL сделки.

### Position.Status

Минимальный набор статусов:

```text
ACTIVE
CLOSED
ERROR
```

Семантика:

```text
ACTIVE
  позиция существует на бирже / сопровождается системой.

CLOSED
  position snapshot по инструменту больше не возвращает позицию.

ERROR
  problem-state: exchange facts нельзя безопасно использовать
  или нарушены exchange/domain invariants.
```

Не используются отдельные статусы:

```text
CREATED
PENDING
OPENING
CLOSING
PARTIALLY_CLOSED
```

Причины:

* `Position` не создаётся локально до биржи;
* `Position` материализуется через `REFRESH_POSITION`;
* ACK `close-position` не является runtime truth;
* частичное уменьшение позиции — это `ACTIVE` с обновлённым `externalSize`, а не отдельный статус.

### Active Position

Position считается active entity в домене, если:

```text
Position.Status = ACTIVE
```

Это означает, что биржа всё ещё возвращает position record или позиция сопровождается системой.

### Position live risk

Live risk по позиции считается отдельно:

```text
Position.Status = ACTIVE
AND Position.externalSize > 0
```

Если:

```text
Position.Status = ACTIVE
AND Position.externalSize = 0
```

то:

```text
position record есть на бирже,
но live market risk по размеру позиции нет.
```

Это cleanup / anomaly / retry case, а не normal `CLOSED`, пока биржа продолжает возвращать snapshot.

### Closed Position

Position считается closed entity в домене, если:

```text
Position.Status = CLOSED
```

Для `Position` нормальный closed-on-exchange факт:

```text
GET /account/positions по instrument успешно выполнен
AND position snapshot не найден
```

Тогда `ClientService` возвращает `null`, а `PositionStatusResolver` возвращает:

```text
status = CLOSED
closeReason candidate = EXTERNAL_CLOSE
```

Если position snapshot найден, даже с `externalSize = 0`, позиция остаётся `ACTIVE`.

### Position.CloseReason

`Position.CloseReason` описывает механизм / тип закрытия позиции, а не бизнес-причину сделки.

Значения:

```text
CLOSED_BY_STRATEGY
KILL_SWITCH
MANUAL_CLOSE
EXTERNAL_CLOSE
EXCHANGE_INVARIANT_VIOLATION
UNKNOWN
```

Семантика:

```text
CLOSED_BY_STRATEGY
  бот сам инициировал штатное закрытие позиции как действие стратегии.

KILL_SWITCH
  позиция закрыта аварийным safety-flow / kill-switch.

MANUAL_CLOSE
  пользователь вручную инициировал закрытие.

EXTERNAL_CLOSE
  позиция закрылась на стороне биржи без текущей команды close-position:
  SL / TP / trailing / liquidation / ADL / иной exchange-side event.

EXCHANGE_INVARIANT_VIOLATION
  problem reason для Position.ERROR.

UNKNOWN
  fallback, если причину безопасно определить не удалось.
```

`Position.CloseReason` не дублирует `Deal.CloseReason`.
Например:

```text
Position.CloseReason = EXTERNAL_CLOSE
Deal.CloseReason = STOP_LOSS / TAKE_PROFIT / LIQUIDATION / UNKNOWN
```

### PositionStatusResolver

`PositionStatusResolver` возвращает result-object:

```java
public class PositionStatusResolveResult {

    /** Доменный статус позиции. */
    private Position.Status status;

    /** Candidate причины. Executor применяет его только если closeReason ещё null. */
    private Position.CloseReason closeReason;
}
```

Правила:

```text
snapshot == null
  -> CLOSED + EXTERNAL_CLOSE

snapshot != null
  -> ACTIVE + null
```

Если `snapshot.externalSize == 0`:

```text
status = ACTIVE
live risk = false
```

Refresh executor:

* всегда применяет `status` из resolver result;
* обновляет external-поля из snapshot, если snapshot есть;
* заполняет `closeReason` только если текущий `Position.closeReason == null`;
* не перетирает ранее установленный `closeReason`.

### REFRESH_POSITION policy

Для OKX `REFRESH_POSITION` делает один логический exchange-запрос:

```text
GET /api/v5/account/positions?instType=SWAP&instId=<instrumentExternalId>
```

Политика:

```text
snapshot найден
  -> ClientService возвращает PositionExternalSnapshot

snapshot не найден
  -> ClientService возвращает null

API / сеть / temporary exchange error
  -> retry / exception policy
```

Для OKX не ищем дополнительно по `posId`, потому что цель `REFRESH_POSITION` — доказать наличие или отсутствие live position по инструменту.

Если локальной `Position` ещё нет и refresh вернул `null`, новую `CLOSED Position` не создаём.
Если локальной `Position` ещё нет и refresh нашёл exchange position в рамках active Deal flow, executor создаёт локальную `Position` и привязывает её к `Deal`.

### CLOSE_POSITION semantics

`CLOSE_POSITION` подчиняется общему правилу `CLOSE` / `CANCEL` commands:

```text
ACK от биржи не является runtime truth.
```

`ClosePositionExecutor`:

* выполняет только полное закрытие позиции;
* не выполняет partial close;
* не вызывает `RiskValidator`;
* выполняет minimal domain / exchange safety checks;
* после ACK не переводит `Position` в `CLOSED`.

После `CLOSE_POSITION` для подтверждения закрытия позиции требуется `REFRESH_POSITION`.

### Position и fills / PnL

`Position` не используется для итогового PnL сделки.

`Position` хранит только данные, нужные для сопровождения live-risk позиции:

* наличие / отсутствие позиции;
* размер;
* направление;
* среднюю цену входа;
* mark price;
* liquidation price;
* margin;
* unrealized PnL.

`REFRESH_FILLS` используется в финализации сделки для итогового подсчёта profit / loss.
`Deal.resultProfit` считается на основании фактов исполнений, собранных через `REFRESH_FILLS`.

### Position и DealContext

`DealContext` по позиции содержит одну текущую `Position` сделки, если она уже материализована.

Не нужны:

* `relatedPositions` — в рамках одной `Deal` допускается максимум одна `Position`;
* `exchangePositionFact` — exchange facts сначала применяются refresh-командами к БД, затем `DealContext` собирает уже обновлённые runtime-сущности.

Отсутствие локальной `Position` допустимо в `ENTRY_SUBMITTED` до успешного `REFRESH_POSITION`.

Если exchange position есть, но нет active `Deal`, который объясняет её появление, это зона `AnomalyJob` / safety-flow.


## 8.6. BalanceContainer

`BalanceContainer` — snapshot баланса и маржинального состояния.

Баланс не имеет semantics active/closed как `Order`, `AlgoOrder` или `Position`.

Для баланса важны:

* актуальность snapshot;
* принадлежность exchange account;
* корректность equity/margin/frozen values;
* использование в risk validation;
* возможность refresh.

`REFRESH_BALANCE` должен фиксироваться в истории исполнения команд, но баланс не является управляемой торговой сущностью как order/algo/position.

## 9. Cleanup rules

## 9.1. EXIT_PENDING

`ExitPendingHandler` отвечает за финальную проверку штатного закрытия сделки.

Перед переводом `Deal` в `CLOSED` должно быть доказано:

* `REFRESH_POSITION` подтвердил отсутствие позиции на бирже;
* active position в домене переведена в `CLOSED`;
* known live orders отсутствуют или отменены;
* known live algo-orders отсутствуют или отменены;
* order history обновлена;
* algo-order history обновлена;
* fills подтянуты и сопоставлены;
* нет known live risk по сделке;
* нет неизвестных live-сущностей на бирже, связанных с инструментом/сделкой.

Если после refresh остались известные сделке live `Order` / `AlgoOrder`, они отменяются отдельными командами:

```text
CANCEL_ORDER
CANCEL_ALGO_ORDER
```

Если обнаружены неизвестные live-сущности на бирже, это anomaly/safety-flow, а не штатный cleanup сделки.

---

## 9.2. ErrorHandler

`ErrorHandler` работает после перевода `Deal` в `ERROR`.

Цель `ErrorHandler` — безопасно убрать или локализовать live risk.

Типовые действия:

* refresh positions;
* refresh pending orders;
* refresh algo orders;
* refresh order history;
* refresh algo-order history;
* refresh fills;
* cancel known live orders;
* cancel known live algo-orders;
* close active position;
* при необходимости вызвать KillSwitch / safety-flow.

Если live risk успешно убран и это подтверждено refresh/search/history facts, сделка может перейти в `EMERGENCY_CLOSED`.

`ERROR -> CLOSED` запрещён.

---

## 9.3. KillSwitch

`KillSwitch` используется для аварийного снятия риска.

Он должен работать с live-сущностями:

* active positions;
* live orders;
* live algo-orders.

`KillSwitch` не должен пытаться чистить всю историю по инструменту.

Для report/snapshot можно дополнительно включать `relatedInactive`, но action-state должен работать только с live risk.

---

## 10. Anomaly rules

`AnomalyJob` ищет не штатные runtime-ситуации, а нарушения базовых инвариантов системы.

Типовые anomaly cases:

* live order есть на бирже, но нет соответствующей runtime-сущности в БД;
* live algo-order есть на бирже, но нет соответствующей runtime-сущности в БД;
* active position есть на бирже, но нет active `Deal`, который объясняет её появление;
* terminal `Deal` имеет live position;
* больше одной позиции на инструмент, если система допускает максимум одну;
* DB entity closed, но exchange entity всё ещё live;
* unknown external status;
* нарушен режим isolated margin;
* плечо выше глобального лимита x10;
* найден чужой live risk на инструменте;
* после cleanup остались неизвестные live хвосты.

Важное исключение для `Position`:

```text
entry order исполнился на бирже
-> exchange position уже появилась
-> локальной Position ещё нет
-> следующий REFRESH_POSITION создаёт Position и привязывает её к Deal
```

Это не anomaly, если есть active `Deal` и известный entry order / entry flow, который объясняет появление позиции.

AnomalyJob не должен вести сделку по FSM. Он фиксирует anomaly/safety report и может инициировать safety-flow по правилам системы.


## 11. Component impact matrix

| Компонент | Как влияет документ |
|---|---|
| `RefreshExecutor` | Использует resolver внешних статусов, обновляет сущность по snapshot, проставляет доменный статус, сохраняет в БД. Не содержит hardcode внешних статусов биржи. |
| `DealContextService` | Собирает active entities и limited `relatedInactive`, чтобы FSM видел runtime truth, а не всю историю. |
| `ExitPendingHandler` | Проверяет отсутствие live risk перед переводом `Deal` в `CLOSED`. Чистит только известные live хвосты. |
| `ErrorHandler` | После `Deal.ERROR` запускает safety-flow и работает до устранения live risk или ручного разбора. |
| `AnomalyJob` | Сравнивает exchange live facts с доменными active entities. Неизвестные или чужие live-сущности трактует как anomaly. |
| `KillSwitch` | Работает только с live risk: active positions, live orders, live algo-orders. Не чистит историю. |
| `EntryScannerJob` | Не создаёт новые сделки, если `Exchange` в `HOLD`, `Instrument` в `HOLD/DISABLED`, `Strategy` не разрешает entry или risk-layer блокирует. |
| `DealOpeningService` | Перед созданием candidate `Deal` проверяет gatekeeper-статусы: exchange, instrument, strategy, risk. |
| `ServiceCommandExecutor` | При `Exchange HOLD` блокирует normal trading commands, но разрешает safety/read commands. Reduce-only partial exit / `CANCEL_*` / `CLOSE_POSITION` / `EXECUTE_KILL_SWITCH` не проходят через `RiskValidator`; для них применяются minimal domain / exchange safety checks и invariant checks. |

## 12. Минимальные правила для кода

### 12.1. Не размазывать live/closed проверки

Для каждой runtime-сущности должны быть явные методы или semantic helpers.

Примеры:

```java
order.isActiveEntity();
order.isClosedEntity();
order.hasLiveRisk();

algoOrder.isActiveEntity();
algoOrder.isClosedEntity();
algoOrder.hasLiveRisk();

position.isActiveEntity();
position.isClosedEntity();
position.hasLiveRisk();
```

Нельзя в разных сервисах вручную писать разные списки статусов.

---

### 12.2. Внешние статусы только в resolver

FSM, handlers, `DealContextService`, `AnomalyJob`, `KillSwitch` не должны знать, что у OKX есть строки `live`, `partially_filled`, `effective` и т.д.

Эти строки должны жить только в exchange-specific resolver / adapter layer.

---

### 12.3. Неизвестный внешний статус всегда safety-critical

Неизвестный внешний статус не должен маппиться молча.

Правило:

```text
unknown external status
-> ExternalStatusException(reasonCode = UNKNOWN_EXTERNAL_STATUS)
-> Deal ERROR
-> Exchange HOLD
-> manual investigation
```

---

### 12.4. ACK не является truth

ACK от биржи означает только то, что запрос принят или обработан на уровне API.

Финальная истина подтверждается только через:

* refresh;
* search by client id;
* order details;
* order history;
* algo-order details;
* algo-order history;
* fills;
* position snapshot.

---

## 13. Короткий итог

Документ фиксирует две ключевые идеи:

```text
1. Внешние статусы биржи сначала переводятся в доменные статусы через exchange-specific resolver.
2. Доменный статус определяет Active entity / Closed entity / Live risk и влияет на runtime-логику системы.
```

Основное правило безопасности:

```text
Если бот не понимает внешний статус биржи,
он не должен продолжать торговлю.

Текущая сделка уходит в ERROR,
биржа уходит в HOLD,
новые сделки запрещены до ручного разбора.
```
