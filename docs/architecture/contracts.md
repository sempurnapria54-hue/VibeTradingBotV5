# Контракты между сервисами

## На какой вопрос отвечает этот файл

Как сервисы обращаются друг к другу.

## Два канала

| Канал | Когда | Свойства |
|---|---|---|
| REST, синхронно | срочное: ордер к коннектору, чтение фич для решения, чтение для интерфейса | вверх по ярусам не идёт (`services.md`); разрешён поимённо строкой §«Синхронные вызовы»; таймаут и бюджет повторов у вызывающего; идемпотентность по ключу запроса |
| Kafka, события | несрочное и факты: исполнения, активации, смены членств, аномалии, всё для аудита и статистики | конверт — §«Конверт события» ниже; ключ партиции — `tenantId`; потребитель дедуплицирует по `eventId` |

Формы событий и запросов — классы артефакта `domain-model`
(`services.md`); реестр схем не заводится, пока все производители и
потребители живут в одном монорепозитории. Условие возврата — внешний
потребитель событий.

## Синхронные вызовы

| От | К | Что |
|---|---|---|
| `bff` | `auth` | членства и роли (кэшируется, сброс по событию) |
| `bff` | `strategies`, `trading-core`, `market-data`, `audit-statistics` | чтение и команды пользователя в контексте тенанта |
| `trading-core` | `connector-<биржа>` | команды площадке и добыча факта — перечень операций и их форма в `docs/components/IntegrationService.md` §«Входной контракт» |
| `market-data` | `connector-<биржа>` | публичные чтения площадки: листинг и правила инструментов, свечи, срезы стакана, тикер, открытый интерес, funding |
| `trading-core` | `auth` | **реестр биржевых счетов тенанта: перечень и состояние регистрации.** Ядро обязано знать, какие счета существуют, — иначе ни одного прохода не начнёт; события `ExchangeAccountRegistered` производителя пока не имеет (`.claude/work/backlog.md`), и синхронное чтение — единственная тропа. Вызов внутриярусный и на тропе **снятия** риска не лежит: teardown идёт через коннектор по уже известному идентификатору счёта |
| `trading-core` | `market-data` | фичи на момент решения; листинг и биржевые правила инструментов |
| `strategies` | `market-data` | история для бэктеста, пакетным чтением |
| `strategies` | `trading-core` | проверка при валидации: существует ли счёт и инструмент в контексте тенанта |

Никакой вызов не идёт из интеграции в домен и из домена в периметр.

**Замещения заявки в перечне операций коннектора нет, и это не пропуск.**
Замещение — **доменная** операция, и собирает её ядро из двух
площадочных команд: новая заявка плюс отмена старой
(`docs/rules/replace-not-amend.md`). У площадки есть контракт `amend`, но
им мы не пользуемся: двойственность amend/replace дала бы разный разбор
одних и тех же фактов. Коннектор поэтому знает «выставить» и «отменить»,
а «заменить» не знает вовсе.

**Эта таблица — источник сетевой политики.** `NetworkPolicy` кластера
строится по ней парой на строку при запрете по умолчанию
(`platform.md` §Безопасность); пара, которой здесь нет, в кластере
запрещена. Отсюда порядок: сначала строка сюда, потом политика.

## События

| Событие | Производитель | Потребители |
|---|---|---|
| `ExecutionObserved` (заявка, algo-заявка, позиция, средства — факт с площадки) | коннектор | `trading-core`, аудит |
| `OrderDecided`, `DealOpened`, `DealClosed`, `SignalDetected`, `SignalOutcomeRecorded`, `HoldRaised`, `HoldReleased`, `AnomalyReported` | `trading-core` (через outbox) | аудит, статистика, `bff` (живые данные) |
| `StrategyActivated` (с неизменяемым снимком определения), `StrategyDeactivated`, `StrategyDeleted`, `BacktestCompleted` | `strategies` | `trading-core`, аудит, `bff` |
| `MembershipChanged`, `ExchangeAccountRegistered`, `ExchangeKeysRotated`, `TenantSuspended` | `auth` | `bff`, коннекторы (сброс кэша ключей), `trading-core` (остановка набора риска при приостановке тенанта), аудит |
| `InstrumentListed`, `InstrumentRulesChanged`, `FeaturesUpdated` | `market-data` | `trading-core`, аудит |

Перечень открыт: событие заводится по потребности шага, не превентивно.

**Класс события заводит шаг его производителя, конверт — шаг
`domain-model`.** Правило то же, что у тем: носитель без производителя не
заводится. `domain-model` поставляет конверт и перечни, из которых
события собираются; содержимое каждого события — форма, которую знает
только тот, кто его порождает, и она приезжает вместе с ним.

**У каждого класса события назван писатель, и он же писатель решения.**
Требование «решение и его событие одной транзакцией»
(`data-ownership.md` §«Outbox и доставка») исполнимо ровно тогда, когда
запись outbox делает **тот код, который пишет решение**: посредник
атомарности не добавляет, а прячет. Отсюда таблица — она и есть дом
привязки «класс события → писатель → момент».

| Класс | Писатель | Момент |
|---|---|---|
| `OrderDecided` | `docs/components/CreateOrderExecutor.md` | транзакция заведения строки заявки — та, что присваивает её клиентский идентификатор |
| `DealOpened` | `docs/components/DealOpeningService.md` | транзакция создания сделки, обе тропы (вход по объявлению и восстановительная) |
| `DealClosed` | `docs/components/MarkDealClosedExecutor.md` и `docs/components/MarkDealEmergencyClosedExecutor.md` | транзакция терминального ребра; писателей два, потому что терминалов два |
| `HoldRaised`, `HoldReleased` | `docs/components/HoldService.md` | транзакция, которой ступень объекта поднята либо снята |
| `AnomalyReported` | сервис отчёта аномалии (`docs/models/domain/other/AnomalyReport.md` — дом дедупа) | транзакция заведения строки отчёта; при поглощении дедупом строки нет — и события тоже |
| `SignalDetected`, `SignalOutcomeRecorded` | приезжают со своим предметом — фаза 4 (`signal-strategy-allocator.md`) | — |

**Содержимое несёт идентичности и то, чего потребитель не дочитает сам.**
Потребитель события — аудит, статистика и `bff` — своей базы ядра не
имеет и синхронно его не читает (ярусы запрещают восходящий вызов).
Поэтому в содержимом: `internalId` предмета и его контекста (счёт,
инструмент, сделка, стратегия — там, где применимо), значения, ради
которых событие и заведено (исход терминала, ступень и код причины,
класс и код отчёта), и **ничего производного**: число, выводимое из
присланных, второй раз не едет.

**Названное ограничение: потребителей у пяти классов ещё нет.** Аудит и
статистика — шаг 10, `bff` — шаг 9; до них форма проверяется чтением, а
не прогоном. Условие снятия — первый построенный потребитель; версия
формы (`version` конверта) для того и заведена, чтобы её правка не ломала
уже написанное.

## Конверт события

**Дом формы.** Конверт один на все события; поля ниже — его полный
состав. Класс конверта поставляет `domain-model` (`services.md`).

| Поле | Тип | Что несёт |
|---|---|---|
| `eventId` | `String` | Идентичность события. Потребитель дедуплицирует по нему таблицей inbox; повтор доставки безопасен по построению (`docs/rules/idempotency-via-unique.md`) |
| `tenantId` | `String` | Тенант-владелец. Он же ключ партиции: даёт порядок событий внутри тенанта и делает будущее разделение ядра вопросом числа реплик (`data-ownership.md`) |
| `occurredAt` | `OffsetDateTime` | Момент **происшествия**, не публикации. Время UTC (`docs/rules/time-utc.md`) |
| `version` | `Integer` | Версия формы события. Растёт, когда меняется состав полей содержимого; потребитель старой версии обязан оставаться рабочим |
| `traceContext` | `String` | Контекст трассировки в форме W3C `traceparent`. Несущее поле: без него цепочка разбора инцидента обрывается на границе Kafka, а платформа объявляет трассировку сквозной (`platform.md` §Наблюдаемость) |

**Пустой `traceContext` законен и означает «трассировки не было», а не
«потеряна».** Достижимое состояние: производитель, у которого
инструментирование ещё не подключено, — а `domain-model` выпускается
раньше всех сервисов, то есть раньше любой настройки OpenTelemetry.
Различение обязательно: потребитель, читающий пустоту как потерю, поднял
бы аномалию на штатном состоянии.

**Почему контекст едет конвертом, а не заголовками сообщения.** Конверт
и есть объявленная форма события, а заголовки принадлежат транспорту,
которого доменная библиотека не знает по построению. Отвергнуто:
заголовки Kafka (часть формы уехала бы в транспорт, и `domain-model`
перестал бы быть единственным носителем формы) и отказ от сквозного
трейса с восстановлением связи по `eventId` в логах (ручное сшивание —
ровно то, против чего заведена сквозная трассировка).

**Событие → тема.** Тема одна на **производителя и род события**, а не
одна на тип события и не одна на всех: `<производитель>.<род>`, где род —
`facts` (события-происшествия) либо `state` (события-состояния, чья
истина есть последнее значение по ключу). Род определяет и форму
хранения темы (`data-ownership.md` §«Outbox и доставка»), поэтому смешение
родов в одной теме запрещено: компакция темы фактов теряет факты.
**Сами темы заводит шаг сервиса-производителя** вместе с сервисом —
темы без производителя не бывает; шаг платформы разворачивает брокер и
правило, а не перечень.

## Идемпотентность и повтор

- **Ордер.** Ядро пишет решение об ордере и событие одной транзакцией;
  `clientOrderId` выводится из идентификатора решения. Повтор команды
  после обрыва несёт тот же `clientOrderId`, и площадка второго ордера
  не создаёт — маркер источника остаётся
  (`docs/integrations/okx/rules/client-id-marker.md`).
- **Событие.** Повторная доставка отсекается inbox-таблицей потребителя.
- **REST.** Мутирующий запрос несёт ключ идемпотентности; повтор с тем
  же ключом возвращает первый результат.
- **Саги — хореографией.** Открытие сделки: решение ядра → команда
  коннектору → факт исполнения событием → ядро ведёт сделку по факту.
  Компенсаций нет: шаг либо идемпотентно повторяется, либо переводит
  сделку в объявленное состояние ошибки с холдом
  (`docs/rules/error-handling-policy.md`). Состояние после рестарта
  выводится из фактов, не из очереди (`docs/rules/command-lifecycle.md`).

## Контекст тенанта в вызове

1. Провайдер идентичности выдаёт пользователю токен с идентичностью.
2. `bff` проверяет подпись токена локально по ключам провайдера, без
   вызова `auth`; резолвит членство и роль в выбранном тенанте у `auth`
   с кэшем и сбросом по `MembershipChanged`.
3. `bff` вызывает домен с токеном пользователя и заголовками контекста
   (тенант, роль); домен проверяет подпись токена сам и сверяет
   контекст с собственным кэшем членств `auth`.
4. Сервис проверяет право операции по роли на каждом вызове; отказ —
   единый error-DTO (`docs/rules/error-handling-policy.md`), запись
   отказа остаётся (`docs/models/domain/other/AccessDenial.md`).

Межсервисные вызовы без пользователя (ядро → коннектор, реле outbox) идут
под сервисной идентичностью кластера, ограниченной сетевыми политиками;
контекст тенанта они несут явно в запросе.

## Живые данные в браузер

`bff` подписан на темы событий и раздаёт их в браузер через SSE
(по умолчанию) или WebSocket, фильтруя по тенанту сессии. Состояния
`bff` не держит: переподключение — повторная подписка с последнего
смещения, которое сообщает клиент.
