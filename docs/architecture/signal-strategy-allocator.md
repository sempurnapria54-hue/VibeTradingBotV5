# Сигнал, стратегия, аллокатор

## На какой вопрос отвечает этот файл

Как сигнал, стратегия и аллокатор делят между собой решение о входе.

## Три роли

| Роль | Кто | Вход | Выход |
|---|---|---|---|
| детектор | правило из библиотеки `strategy-engine`, параметризованное стратегией | инструмент, фичи рыночных данных на момент | **сигнал** |
| стратегия | определение-данные, исполняемое движком | сигнал | намерение: входить ли, какими траншами, где защита, как вести |
| аллокатор | модуль `trading-core` | очередь намерений, риск-бюджет тенанта, живая экспозиция | кому из намерений достаётся капитал |

Сегодня первые две роли слиты в условии входа стратегии
(`docs/components/EntryScannerJob.md`): сканер проверяет условие и создаёт
сделку. Целевая форма разводит их, чтобы шов «детектор → сигнал» был
местом, куда встаёт модель, а сигнал — записью, по которой решение
объяснимо задним числом.

## Сигнал

Сигнал — объект первого класса, персистентная запись `trading-core`:

| Поле | Смысл |
|---|---|
| тенант, стратегия, биржевой счёт, инструмент | адресат и контекст |
| детектор и его параметры | что сработало |
| направление | сторона намерения |
| сила | оценка детектора в его собственной шкале, с названием шкалы |
| ожидаемый край | ожидание детектора о преимуществе входа; пусто, если детектор его не оценивает |
| снимок фич | значения операндов детектора на момент срабатывания, как есть — point-in-time, без пересчёта задним числом |
| биржевой момент | по часам источника (`docs/rules/time-utc.md`) |

Сигнал пишется **всегда**, включая случаи, когда до входа не дошло. Это
следствие П3: решение «не вошли» должно быть объяснимо так же, как «вошли».

## Исход сигнала

У каждого сигнала один исход, записанный тем, кто его определил:

| Исход | Кто пишет | Когда |
|---|---|---|
| `TAKEN` | аллокатор, той же транзакцией, что создание сделки | капитал выдан, сделка создана; несёт ссылку на сделку |
| `REJECTED_BY_BUDGET` | аллокатор | риск-бюджета тенанта не хватило |
| `REJECTED_BY_POLICY` | аллокатор либо риск-гейт | потолок одновременного риска, холд счёта или инструмента, активная сделка по инструменту |
| `REJECTED_BY_RANK` | аллокатор | уступил сигналу с бо́льшим приоритетом в том же окне |
| `STALE` | аллокатор | данные входа устарели до решения (`docs/rules/market-data-freshness.md`) |
| `SHADOW` | движок в теневом режиме | стратегия в тени, капитал не выдаётся; результат ведёт симулированный коннектор |

Результат сделки присоединяется к исходу `TAKEN` по её терминалу через
ссылку на сделку; отдельного поля результата у сигнала нет — второй
носитель одного числа.

Пара «сигнал → исход → результат» и есть обучающая выборка: правила-
детекторы генерируют её, ничего сверх записи не делая.

## Стратегия — определение, не код

Стратегия — параметризованные данные (`docs/models/domain/aggregate/Strategy.md`):
какие детекторы с какими параметрами, что делать с сигналом, транши,
защита, ведение, выход. Исполняет её движок; ни у одной стратегии нет
собственного кода. Отсюда: бэктест и живая торговля исполняют одно и то же
определение одним и тем же движком, и гейт проверяет ровно то, что будет
торговать.

Жизненный цикл: черновик → валидация → бэктест → активация человеком.
Черновик заводит либо человек, либо советник; для движка источник
черновика неразличим (`reserved-extension-points.md`).

**Теневой режим** — статус стратегии рядом с живым: движок исполняет её
на живых данных, ордера уходят в симулированный коннектор из
`strategy-engine`, сигналы и исходы `SHADOW` пишутся штатно. Тень не
трогает риск-бюджет и не создаёт сделок на площадке.

## Аллокатор

Работает, когда намерений больше, чем бюджета или чем допускает потолок
одновременного риска тенанта.

1. Собирает окно намерений (сигналы, по которым стратегия решила входить)
   по тенанту.
2. Ранжирует по приоритету. Ранг — функция от силы сигнала, ожидаемого
   края, приоритета стратегии и заполненности бюджета; **веса и пороги —
   параметры без назначенного значения**: их даёт бэктест, а до него
   пустое место означает «ранжирование по порядку поступления», и это
   названо в записи исхода.
3. Раздаёт риск-бюджет тенанта сверху вниз, пока не исчерпан бюджет либо
   потолок одновременной суммы; остальным пишет исход отказа.
4. Каждое выданное намерение проходит риск-гейт как сегодня
   (`docs/processes/risk-evaluation.md`): аллокатор распределяет, гейт
   проверяет действие. Аллокатор не подменяет гейт и гейтом не является.

Аллокатор и риск-гейт — модули ядра; их операнды меняются в каждой
транзакции ядра, и снаружи их не прочитать согласованно
(`services.md`).

## Уровни риска

Лимиты на сделку остаются как есть (`docs/rules/risk-policy.md`). Сверх
них тенант получает **потолок одновременной суммы принятого риска** по
всем живым сделкам всех его счетов — операнд аллокатора и гейта. Число —
риск-аппетит держателя тенанта, пустое место отказывает.
