# Задание для Codex — зафиксировать и реализовать правила статусов `AttachedAlgoOrder`

## Цель задачи

Нужно реализовать и зафиксировать в коде lifecycle `AttachedAlgoOrder`, чтобы:

* `RefreshAttachedAlgoOrderExecutor`
* `RefreshAlgoOrderExecutor`
* доменная модель
* persistence слой

одинаково трактовали переходы статусов.

Codex не должен сам придумывать допустимые переходы.

---

# 1. Какие статусы считаются корректными

Используем только:

* `CREATED`
* `ATTACHED`
* `ACTIVE`
* `CLOSED`
* `FAILED`

Не добавлять новые статусы в рамках этой задачи без отдельного согласования.

---

# 2. Какие переходы разрешены

## Основной путь

* `CREATED -> ATTACHED`
* `ATTACHED -> ACTIVE`
* `ACTIVE -> CLOSED`

## Допустимые альтернативы

* `CREATED -> ATTACHED -> CLOSED`
* `CREATED -> FAILED`
* `CREATED -> ATTACHED -> FAILED`
* `ATTACHED -> ACTIVE -> FAILED`

---

# 3. Какие переходы запрещены

Нельзя:

* `CREATED -> ACTIVE`
* `ACTIVE -> ATTACHED`
* `CLOSED -> ACTIVE`
* `CLOSED -> ATTACHED`
* `FAILED -> ACTIVE`
* `FAILED -> ATTACHED`

Если protection создаётся заново после terminal state — это должна быть новая сущность, а не “оживление” старой.

---

# 4. Кто какие статусы имеет право выставлять

## `RefreshAttachedAlgoOrderExecutor`

Может выставлять:

* `ATTACHED`
* `FAILED`
* `CLOSED` — только при достаточном доказательстве на order-snapshot стадии

Не должен выставлять:

* `ACTIVE`

## `RefreshAlgoOrderExecutor`

Может выставлять:

* `ACTIVE`
* `CLOSED`
* `FAILED`

Не должен выставлять:

* `CREATED`
* новый `ATTACHED`

---

# 5. Важное правило по `CLOSED`

Codex должен зафиксировать в логике следующее правило:

НЕЛЬЗЯ переводить `AttachedAlgoOrder` в `CLOSED` только потому, что child пропал из позднего order snapshot после fill
родительского `Order`.

Почему:

* protection может уже жить в algo-layer;
* отсутствие в order snapshot после fill не доказывает final close.

В таком кейсе child должен остаться в `ATTACHED` и быть подхвачен `REFRESH_ALGO_ORDERS`.

Это обязательное правило.

---

# 6. Где нужно зафиксировать правила

## 6.1. В доменной модели `AttachedAlgoOrder`

Нужно добавить доменные helper methods, если их ещё нет.

Рекомендуемо:

```java
boolean isActiveLike()

boolean isTerminal()

boolean canTransitionTo(Status targetStatus)

void toAttached()

void toActive()

void toClose()

void toFail()
```

Если naming в проекте другой — сохранить стиль проекта, но смысл должен остаться тем же.

## 6.2. В executors

`RefreshAttachedAlgoOrderExecutor` и `RefreshAlgoOrderExecutor` должны использовать эти правила, а не дублировать их
if-else кашей по месту.

---

# 7. Что нужно сделать в `RefreshAttachedAlgoOrderExecutor`

Codex должен реализовать так, чтобы:

* child из `CREATED` мог перейти в `ATTACHED`
* child из `CREATED` или `ATTACHED` мог перейти в `FAILED`, если есть failure proof
* child мог перейти в `CLOSED` только если есть достаточное доказательство на order-snapshot стадии
* child не переводился в `ACTIVE` в этом executor

---

# 8. Что нужно сделать в `RefreshAlgoOrderExecutor`

Codex должен реализовать так, чтобы:

* child в `ATTACHED` мог перейти в `ACTIVE`, если algo endpoints подтверждают live algo
* child в `ATTACHED` или `ACTIVE` мог перейти в `CLOSED`, если algo history доказывает final close
* child в `ATTACHED` или `ACTIVE` мог перейти в `FAILED`, если algo history доказывает failure
* ambiguous / not found cases не превращались в silent `CLOSED`

---

# 9. Persistence правило

Каждая смена статуса `AttachedAlgoOrder` должна сразу сохраняться в БД.

Нельзя держать lifecycle child только внутри текущего вызова executor.

---

# 10. Что вернуть по задаче

Нужно вернуть:

1. обновлённую доменную модель `AttachedAlgoOrder`
2. доменные helper methods для lifecycle
3. точечные изменения `RefreshAttachedAlgoOrderExecutor`
4. точечные изменения `RefreshAlgoOrderExecutor`
5. при необходимости — unit-level helper code для transition checks

Без лишнего рефакторинга unrelated-кода.
