# Codex tasks — refresh commands

## Как запускать

Эти задачи лучше отдавать **последовательно**, а не одной большой пачкой.

Порядок:

1. `AttachedAlgoOrder` lifecycle rules
2. `REFRESH_PENDING_ORDERS`
3. `REFRESH_ALGO_ORDERS`
4. `REFRESH_POSITIONS`

Важно:

* работать в рамках уже существующей архитектуры проекта;
* команды реализуются через **Executor**-классы;
* сложная логика синка — через отдельный `*SyncService`;
* сложные статусные переходы — через отдельный `*StatusResolver`;
* не складывать orchestration-логику в толстые service-классы;
* соблюдать `AGENTS.md` и `Code style.md`.

---

## Общие правила для всех задач

Обязательные архитектурные ограничения:

* команды реализуются через отдельные executors;
* `ServiceCommandExecutor` только маршрутизирует команду в нужный executor;
* `TradeRuleValidator` только валидирует инварианты и при нарушении запускает anomaly / kill-switch сценарий;
* `KillSwitchService` не должен вызывать refresh executors;
* refresh executors не должны напрямую запускать kill-switch;
* если найдено нарушение, normal flow команды должен прерываться через `TradeRuleViolationException`;
* ordinary order layer, attached child layer и algo layer должны быть разделены.

Обязательные кодовые ограничения:

* не использовать множественные объявления переменных через запятую;
* всегда ставить фигурные скобки;
* использовать `Objects.isNull(...)` / `Objects.nonNull(...)`;
* для коллекций использовать `CollectionUtils.isEmpty(...)` / `CollectionUtils.isNotEmpty(...)`;
* по возможности использовать `BooleanUtils.isTrue(...)` / `BooleanUtils.isFalse(...)`;
* использовать только константы из `OkxTimeframes`;
* не нормализовать timeframe в lower-case.

Ограничение по scope:

* не делать unrelated refactoring;
* менять только то, что нужно для задачи;
* если подходящий класс уже есть, дорабатывать его, а не создавать дубль.

Формат результата по каждой задаче:

1. Что сделано
2. Какие файлы изменены
3. Какие команды запуска были выполнены
4. Что прошло / не прошло
5. Что осталось рискованным или недопроверенным

# TASK 1 — AttachedAlgoOrder lifecycle rules

## Цель

Реализовать и зафиксировать lifecycle `AttachedAlgoOrder`, чтобы:

* доменная модель;
* `RefreshAttachedAlgoOrderExecutor`;
* `RefreshAlgoOrderExecutor`;
* persistence слой

одинаково трактовали переходы статусов.

## Использовать только такие статусы

* `CREATED`
* `ATTACHED`
* `ACTIVE`
* `CLOSED`
* `FAILED`

Не добавлять новые статусы.

## Разрешённые переходы

Основной путь:

* `CREATED -> ATTACHED`
* `ATTACHED -> ACTIVE`
* `ACTIVE -> CLOSED`

Допустимые альтернативы:

* `CREATED -> ATTACHED -> CLOSED`
* `CREATED -> FAILED`
* `CREATED -> ATTACHED -> FAILED`
* `ATTACHED -> ACTIVE -> FAILED`

## Запрещённые переходы

* `CREATED -> ACTIVE`
* `ACTIVE -> ATTACHED`
* `CLOSED -> ACTIVE`
* `CLOSED -> ATTACHED`
* `FAILED -> ACTIVE`
* `FAILED -> ATTACHED`

## Кто какие статусы может выставлять

### `RefreshAttachedAlgoOrderExecutor`

Может выставлять:

* `ATTACHED`
* `FAILED`
* `CLOSED` — только при достаточном доказательстве на order-snapshot стадии

Не должен выставлять:

* `ACTIVE`

### `RefreshAlgoOrderExecutor`

Может выставлять:

* `ACTIVE`
* `CLOSED`
* `FAILED`

Не должен выставлять:

* `CREATED`
* `ATTACHED`

## Критически важное правило

Нельзя переводить `AttachedAlgoOrder` в `CLOSED` только потому, что child пропал из позднего order snapshot после fill родительского `Order`.

В таком кейсе child должен остаться в `ATTACHED` и быть подхвачен командой `REFRESH_ALGO_ORDERS`.

## Что сделать

1. Обновить доменную модель `AttachedAlgoOrder`
2. Добавить helper methods lifecycle-уровня
3. Использовать lifecycle-правила в `RefreshAttachedAlgoOrderExecutor`
4. Использовать lifecycle-правила в `RefreshAlgoOrderExecutor`
5. Не дублировать transition logic разрозненными if-else по месту

## Рекомендуемые helper methods

Если naming проекта допускает, ожидается смысл такого набора:

* `boolean isActiveLike()`
* `boolean isTerminal()`
* `boolean canTransitionTo(Status targetStatus)`
* `void toAttached()`
* `void toActive()`
* `void toClose()`
* `void toFail()`

Если в проекте уже есть другой стиль naming — сохранить стиль проекта, но смысл оставить тем же.

## DoD

* lifecycle `AttachedAlgoOrder` зафиксирован в доменной модели;
* illegal transitions не допускаются;
* `RefreshAttachedAlgoOrderExecutor` не ставит `ACTIVE`;
* `RefreshAlgoOrderExecutor` не создаёт новый `ATTACHED`;
* ambiguous / missing state не превращается в silent `CLOSED`.

# TASK 2 — Implement REFRESH_PENDING_ORDERS

## Цель

Реализовать `REFRESH_PENDING_ORDERS` как отдельную сервисную команду **ordinary order truth layer**.

Команда должна сопровождать:

* ordinary `Order`;
* `AttachedAlgoOrder` только на стадии child-sync из order snapshot.

Команда **не должна** выполнять algo-truth refresh.

## Какие классы должны получиться

Минимально ожидаются:

1. `RefreshOrderExecutor`
2. `OrderStatusResolver`
3. `RefreshAttachedAlgoOrderExecutor`
4. `TradeRuleValidator.validateRefreshPendingOrders(...)`
5. при необходимости `OrderRefreshService` **или** `OrderSyncService`
6. при необходимости `AttachedAlgoOrderDataService` / repository methods
7. точечные изменения `ServiceCommandExecutor`

Если подходящие классы уже существуют — доработать их.

## Нейминг

Использовать именно:

* `RefreshOrderExecutor`
* `OrderStatusResolver`
* `RefreshAttachedAlgoOrderExecutor`
* `execute(...)`
* `resolveStatus(...)`
* `validateRefreshPendingOrders(...)`
* `refreshAttachedAlgoOrders(...)` — допустимое имя публичного метода child executor

Для sync-слоя выбрать только одно имя:

* либо `OrderRefreshService`
* либо `OrderSyncService`

## Границы ответственности

### `RefreshOrderExecutor`

Должен:

1. вызвать `GET /api/v5/trade/orders-pending`
2. прочитать local live `Order` по `instrumentId + LIVE_ORDER_STATUSES`
3. вызвать `TradeRuleValidator.validateRefreshPendingOrders(...)`
4. обновить matched ordinary orders
5. восстановить final state missing ordinary orders через:

    * `GET /trade/order`
    * `GET /trade/orders-history`
    * `GET /trade/orders-history-archive`
6. на каждом order snapshot вызвать `RefreshAttachedAlgoOrderExecutor`

Не должен:

* ходить в algo endpoints;
* запускать kill-switch напрямую;
* создавать anomaly report напрямую;
* вручную размазывать order status resolution по нескольким местам.

### `OrderStatusResolver`

Должен:

* переводить `OrderExternalSnapshot` в доменный `Order.Status`

Не должен:

* сохранять order;
* ходить на биржу;
* вызывать validator.

### `RefreshAttachedAlgoOrderExecutor`

Должен:

1. принять `Order` и `OrderExternalSnapshot`
2. прочитать existing `AttachedAlgoOrder` по `orderId`
3. извлечь attached data из order snapshot
4. сопоставить child entities
5. создать / обновить / закрыть / зафейлить `AttachedAlgoOrder`
6. каждое изменение сразу сохранять в БД

Не должен:

* ходить в algo endpoints;
* запускать validator ordinary order команды;
* запускать kill-switch;
* обновлять parent `Order`.

### `TradeRuleValidator.validateRefreshPendingOrders(...)`

Должен проверить:

* нет дублей во внешнем pending snapshot по `ordId` / `clOrdId`;
* нет дублей во внутреннем live наборе по `externalId` / `internalId`;
* каждый внешний pending order однозначно сопоставляется с одним local live order;
* все local live orders относятся к текущему инструменту.

При нарушении должен:

1. создать initial `AnomalyReport`
2. записать before snapshots
3. при необходимости блокировать инструмент
4. вызвать `KillSwitchService`
5. получить after snapshots
6. обновить report
7. выбросить `TradeRuleViolationException`

## Критические правила

### Missing-from-pending order

Если local live order пропал из pending snapshot, нельзя делать silent `CLOSED`.
Нужно восстанавливать final state через:

1. `GET /trade/order`
2. если не помогло — `GET /trade/orders-history`
3. если не помогло — `GET /trade/orders-history-archive`

Если не найдено нигде — это unsafe state, а не happy-path close.

### Attached child

Нельзя закрывать `AttachedAlgoOrder` только потому, что он пропал из позднего order snapshot после fill родителя.

## Persistence требования

Нужны методы уровня:

* `List<Order> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)`
* `Order save(Order order)`
* `List<AttachedAlgoOrder> findAllByOrderId(Long orderId)`
* `AttachedAlgoOrder save(AttachedAlgoOrder attachedAlgoOrder)`

Если проектный стиль требует repository + data service — использовать этот стиль.

## Правка `ServiceCommandExecutor`

Команда должна маршрутизироваться так:

* `REFRESH_PENDING_ORDERS -> refreshOrderExecutor.execute(exchange, instrument, dealId)`

Не вызывать `RefreshAttachedAlgoOrderExecutor` напрямую из `ServiceCommandExecutor`.

## DoD

* ordinary order truth layer живёт отдельно;
* `RefreshOrderExecutor` реализован как отдельный executor;
* `OrderStatusResolver` централизует order status mapping;
* `RefreshAttachedAlgoOrderExecutor` работает только на order-snapshot truth;
* missing-from-pending order не закрывается вслепую;
* attached child не закрывается агрессивно без доказательства;
* команда не лезет в algo endpoints.

# TASK 3 — Implement REFRESH_ALGO_ORDERS

## Цель

Реализовать `REFRESH_ALGO_ORDERS` как отдельную сервисную команду **algo truth layer**.

Команда должна сопровождать:

* `AlgoOrder`;
* `AttachedAlgoOrder`, которые уже вышли из ordinary order snapshot-контура и должны подтверждаться через algo endpoints.

Команда не должна заниматься ordinary `Order`.

## Какие классы должны получиться

Минимально ожидаются:

1. `RefreshAlgoOrderExecutor`
2. `TradeRuleValidator.validateRefreshAlgoOrders(...)`
3. при необходимости `AlgoOrderRefreshService` **или** `AlgoOrderSyncService`
4. при необходимости `AlgoOrderDataService` / repository methods
5. при необходимости `AttachedAlgoOrderDataService` / repository methods для algo-layer выборки
6. точечные изменения `ServiceCommandExecutor`

## Нейминг

Использовать:

* `RefreshAlgoOrderExecutor`
* `execute(...)`
* `validateRefreshAlgoOrders(...)`

Для sync-слоя выбрать только одно:

* либо `AlgoOrderRefreshService`
* либо `AlgoOrderSyncService`

## Границы ответственности

### `RefreshAlgoOrderExecutor`

Должен:

1. собрать внешний live algo snapshot через `GET /api/v5/trade/orders-algo-pending`
2. прочитать local live `AlgoOrder`
3. прочитать `AttachedAlgoOrder`, которые уже в algo-layer
4. вызвать `TradeRuleValidator.validateRefreshAlgoOrders(...)`
5. обновить matched live algo сущности
6. восстановить final state missing algo сущностей через:

    * `GET /api/v5/trade/order-algo`
    * `GET /api/v5/trade/orders-algo-history`
7. сразу сохранять изменения в БД

Не должен:

* читать `orders-pending`;
* читать `trade/order`;
* вызывать `RefreshAttachedAlgoOrderExecutor`;
* обновлять parent `Order`;
* запускать kill-switch напрямую.

### `TradeRuleValidator.validateRefreshAlgoOrders(...)`

Должен проверить:

* нет дублей во внешнем live algo snapshot по `algoId` / `algoClOrdId`;
* нет дублей среди local live `AlgoOrder` по `externalId` / `internalId`;
* нет дублей среди `AttachedAlgoOrder`, попавших в algo-layer, по `externalAttachedId` / `externalId` / `internalId`;
* каждый внешний live algo однозначно сопоставляется с одной local algo-сущностью;
* все local algo-сущности принадлежат текущему инструменту.

При нарушении — полный anomaly / kill-switch flow через validator.

## Как собирать live algo snapshot

Так как `orders-algo-pending` фильтруется по `ordType`, executor должен:

1. собрать набор ordType из local live `AlgoOrder` и `AttachedAlgoOrder` algo-layer;
2. пройтись по ordType;
3. получить все live algo snapshots по instrument;
4. дедуплицировать итоговый внешний snapshot.

Минимально поддержать ordType:

* `conditional`
* `oco`
* `trigger`
* `move_order_stop`

## Какие `AttachedAlgoOrder` попадают в эту команду

Только child в статусах:

* `ATTACHED`
* `ACTIVE`

`CREATED` сюда попадать не должен.

## Как восстанавливать final algo state

Для local algo сущности, отсутствующей во внешнем live algo snapshot:

1. вызвать `GET /trade/order-algo`
2. если не помог — вызвать `GET /trade/orders-algo-history`

Если history показывает:

* `effective` -> final state, обычно `CLOSED`
* `canceled` -> `CLOSED`
* `order_failed` -> `FAILED`

Если algo не найден ни в detail, ни в history — не делать silent `CLOSED`.

## Какие статусы child можно ставить здесь

### `ACTIVE`

Если algo detail / pending algo snapshot подтвердили live algo.

### `CLOSED`

Если algo history доказал final close / cancel / effective completion.

### `FAILED`

Если algo history показал `order_failed` или equivalent failure proof.

Нельзя возвращать child обратно в ordinary-order stage.

## Persistence требования

Нужны методы уровня:

* `List<AlgoOrder> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)`
* `AlgoOrder save(AlgoOrder algoOrder)`
* `List<AttachedAlgoOrder> findAllByStatuses(Set<String> statuses)` или эквивалент с ограничением по инструменту
* `AttachedAlgoOrder save(AttachedAlgoOrder attachedAlgoOrder)`

Важно: выборка должна быть ограничена текущим инструментом.

## Правка `ServiceCommandExecutor`

Команда должна маршрутизироваться так:

* `REFRESH_ALGO_ORDERS -> refreshAlgoOrderExecutor.execute(exchange, instrument, dealId)`

## DoD

* algo truth layer живёт отдельно от ordinary order layer;
* `AttachedAlgoOrder` после ordinary stage корректно подхватывается algo-командой;
* live algo подтверждается через `orders-algo-pending`;
* final algo state восстанавливается через `order-algo -> orders-algo-history`;
* missing algo сущность не закрывается вслепую;
* команда не использует `RefreshAttachedAlgoOrderExecutor`.

# TASK 4 — Implement REFRESH_POSITIONS

## Цель

Реализовать `REFRESH_POSITIONS` как отдельную sync-команду по инструменту через отдельный executor.

Это обычная sync-команда, но при нарушении торговых инвариантов она должна аварийно прерываться через `TradeRuleValidator`.

## Какие классы должны получиться

Минимально ожидаются:

1. `RefreshPositionExecutor`
2. при необходимости `PositionStatusResolver`
3. `TradeRuleValidator.validatePositions(...)` или эквивалентный отдельный validator method в проектном стиле
4. при необходимости `PositionSyncService`
5. точечные изменения `ServiceCommandExecutor`

## Границы ответственности

### `RefreshPositionExecutor`

Должен:

1. прочитать внешние позиции по инструменту
2. прочитать внутренние релевантные активные позиции по инструменту
3. передать данные в `TradeRuleValidator`
4. если validator ничего не выявил — выполнить обычный sync
5. сохранить изменения в БД

Не должен:

* сам создавать `AnomalyReport`;
* сам вызывать `KillSwitchService`;
* сам принимать решения FSM;
* сам менять `DealContext`.

### Обычный sync

Сценарии:

1. позиция есть на бирже и есть в БД -> обновить существующую позицию;
2. позиция есть на бирже, но в БД её нет -> создать новую позицию и привязать к инструменту и при необходимости к `dealId`;
3. на бирже позиции нет, но в БД есть активная позиция -> закрыть локальную активную позицию доменным статусом;
4. на бирже позиции нет и в БД нет активной позиции -> ничего не делать.

### Status resolving

Резолв внешнего статуса позиции в доменный статус должен делать executor или отдельный resolver/sync component.
FSM не должна знать внешние статусы биржи.

## Validator

`TradeRuleValidator` должен:

* проверять инварианты по внешним и внутренним позициям;
* при нарушении полностью обрабатывать anomaly / kill-switch flow;
* после этого выбрасывать `TradeRuleViolationException`.

## Правка `ServiceCommandExecutor`

Команда должна маршрутизироваться так:

* `REFRESH_POSITIONS -> refreshPositionExecutor.execute(exchange, instrument, dealId)`

## DoD

* `REFRESH_POSITIONS` живёт в отдельном executor;
* executor делает только sync use-case;
* validator остаётся единственной точкой anomaly / kill-switch сценария;
* команда не создаёт циклических зависимостей с kill-switch flow;
* обычный sync позиций реализован по инструменту и живым статусам.
