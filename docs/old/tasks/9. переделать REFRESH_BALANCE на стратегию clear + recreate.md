# Задание для Codex — переделать REFRESH_BALANCE на стратегию clear + recreate

## Цель

Нужно переделать реализацию `REFRESH_BALANCE`.

Сейчас логика идёт в сторону поиска существующих `Balance` по валюте и частичного обновления.

Нужно заменить это на более простую и честную snapshot-стратегию:

* контейнер баланса обновляется как snapshot аккаунта;
* вложенные `Balance` не reconcile-ятся по одной валюте;
* старые balances контейнера полностью очищаются;
* новый список balances полностью создаётся заново из текущего внешнего snapshot.

То есть целевая стратегия:

**clear current balances -> create new balances from external snapshot -> save container as aggregate**

---

## Почему так нужно

Для текущего проекта это лучше, потому что:

* валют немного;
* `Balance` — это snapshot, а не долгоживущая бизнес-сущность;
* не нужен сложный reconcile по валютам;
* не нужно занулять отсутствующие валюты;
* проще и понятнее поддерживать консистентность контейнера.

Идея такая:

* внешний snapshot с биржи является источником правды;
* внутренний список balances должен полностью соответствовать ему.

---

## Что нужно изменить концептуально

## 1. Контейнер — главный агрегат

`BalanceContainer` должен быть главным агрегатом snapshot аккаунта.

Он хранит:

* `exchangeId`
* агрегированные поля аккаунта (`totalEquity`, `unrealizedProfit`, и т.д.)
* список `balances`

Именно контейнер должен сохраняться как единое целое.

---

## 2. Балансы по валютам нужно пересоздавать полностью

Не нужно делать:

* `findByExchangeIdAndCurrency(...)`
* точечный upsert каждого `Balance`
* зануление отсутствующих валют

Нужно делать так:

* загрузили или создали контейнер;
* обновили container fields из snapshot;
* удалили текущие `balances` контейнера;
* из `BalanceContainerExternalSnapshot.balanceExternalSnapshots` создали новый список `Balance`;
* положили новый список в контейнер;
* сохранили контейнер.

---

## 3. Нужна полноценная связь в persistence

Чтобы стратегия `clear + recreate` работала нормально, persistence-модель должна быть построена как агрегатная связь:

### `BalanceContainerEntity`

* `@OneToMany(mappedBy = "balanceContainer", cascade = CascadeType.ALL, orphanRemoval = true)`

### `BalanceEntity`

* `@ManyToOne(fetch = FetchType.LAZY)`
* `@JoinColumn(name = "balance_container_id", nullable = false)`

### Важно

Нужно именно `orphanRemoval = true`, чтобы старые balances контейнера удалялись при замене списка.

---

## 4. Сохранять нужно контейнер, а не balances по одному

После перехода на эту стратегию не нужно отдельно делать:

* `balanceDataService.save(balance)` для каждой валюты

Нужно:

* собрать новый список balances внутри контейнера
* сохранить **только контейнер**

То есть aggregate persistence должен работать через:

* `BalanceContainerDataService.save(balanceContainer)`

---

## Что нужно реализовать

## 1. Обновить `RefreshBalanceExecutor`

Нужно переделать executor так, чтобы он:

1. получал `BalanceContainerExternalSnapshot` через client service;
2. находил контейнер по `exchangeId` **с balances через fetch**;
3. если контейнера нет — создавал его через `BalanceContainerFactory`;
4. обновлял container fields через `BalanceContainerMapper`;
5. создавал новый список `Balance` из snapshot через `BalanceFactory` + `BalanceMapper`;
6. полностью заменял balances контейнера новым списком;
7. сохранял контейнер как агрегат.

---

## 2. Убрать reconcile по валюте

Из executor нужно убрать логику:

* `resolveOrCreateBalance(...)`
* поиск одного balance по currency
* зануление отсутствующих валют
* отдельное сохранение balance по одному

Это больше не нужно.

---

## 3. Добавить доменные методы в контейнер

В `BalanceContainer` нужны явные методы для работы со списком balances.

Минимально ожидается:

```java
public void clearBalances()

public void addBalance(Balance balance)

public void replaceBalances(List<Balance> balances)
```

Предпочтительно использовать именно:

```java
replaceBalances(...)
```

чтобы executor не возился вручную с внутренним списком.

---

## 4. Добавить фабрики

Нужно использовать:

* `BalanceContainerFactory`
* `BalanceFactory`

### `BalanceContainerFactory`

Создаёт новый контейнер с начальными дефолтными значениями.

### `BalanceFactory`

Создаёт новый `Balance` по:

* `exchangeId`
* `currency`

Если в доменной модели ещё есть `balanceContainerId`, можно временно оставить, но при полноценной ORM-связи в
persistence главное — чтобы mapper корректно связывал entity-родителя и entity-ребёнка.

---

## 5. Mapper-логика

### Для контейнера

`BalanceContainerMapper` должен уметь обновлять контейнер из `BalanceContainerExternalSnapshot`.

### Для валютного balance

`BalanceMapper` должен уметь обновлять новый `Balance` из `BalanceExternalSnapshot`.

### Важно

Executor не должен вручную раскладывать поля balances и контейнера.

---

## 6. Repository / data service

### Репозиторий контейнера

Нужен fetch-метод с balances:

```java

@Query("""
        select distinct bc
        from BalanceContainerEntity bc
        left join fetch bc.balances b
        where bc.exchangeId = :exchangeId
        """)
Optional<BalanceContainerEntity> findByExchangeIdWithBalances(@Param("exchangeId") Long exchangeId);
```

Поле `bc.balances` должно совпадать с реальным именем коллекции в entity.

### Data service

Нужен метод уровня data service:

```java
Optional<BalanceContainer> findByExchangeIdWithBalances(Long exchangeId)
```

---

## 7. ServiceCommandExecutor

Если команда `REFRESH_BALANCE` ещё не переведена на executor, нужно убедиться, что:

```java
REFRESH_BALANCE ->refreshBalanceExecutor.

execute(exchange)
```

---

## Что не нужно делать

На этом этапе НЕ нужно:

* делать reconcile по валютам;
* занулять отсутствующие balances;
* отдельно удалять balances вручную через repository;
* добавлять `TradeRuleValidator`;
* добавлять `KillSwitchService`;
* привязывать balance к `instrumentId`;
* строить историю изменений баланса.

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## Что вернуть

Нужно вернуть:

1. обновлённый `RefreshBalanceExecutor`
2. обновлённый `BalanceContainer`
3. обновлённые persistence entity для контейнера и balance со связью
4. fetch-метод в `BalanceContainerRepository`
5. метод `findByExchangeIdWithBalances(...)` в data service
6. при необходимости — `BalanceFactory` и `BalanceContainerFactory`
7. при необходимости — точечные правки mapper-ов

Без лишнего рефакторинга unrelated-кода.

---

## Ожидаемый результат

После выполнения задачи должно быть так:

* `REFRESH_BALANCE` получает `BalanceContainerExternalSnapshot`
* контейнер находится или создаётся по `exchangeId`
* старые balances контейнера полностью очищаются
* новый список balances полностью создаётся из текущего snapshot
* контейнер сохраняется как единый агрегат
* внутренний snapshot полностью соответствует внешнему snapshot биржи
