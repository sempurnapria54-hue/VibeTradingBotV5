# Задание для Codex — реализовать KillSwitchService

## Цель

Нужно реализовать `KillSwitchService` как сервис **полного аварийного снятия риска по инструменту**.

На этом этапе kill-switch должен:

* закрыть всё живое по инструменту на бирже;
* обновить локальные сущности в БД;
* повторно прочитать состояние;
* вернуть результат выполнения kill-switch.

Он будет использоваться из `TradeRuleValidator` при обнаружении критичной аномалии.

---

## Архитектурные правила

### 1. Kill-switch выполняется по инструменту

Kill-switch должен работать **в разрезе инструмента**, а не одной сделки.

Если по инструменту обнаружена критичная аномалия, нужно зачистить **все живые сущности по инструменту**.

### 2. KillSwitchService не принимает решение об аномалии

Он не должен:

* определять, есть аномалия или нет;
* определять `severity`;
* определять `code` аномалии;
* создавать `AnomalyReport`;
* решать, продолжать обычный sync или нет.

Это уже ответственность `TradeRuleValidator`.

### 3. KillSwitchService — только исполнитель аварийного сценария

Он должен:

* снять риск на бирже;
* привести БД в согласованное аварийное состояние;
* вернуть итоговый результат.

---

## Что нужно реализовать

### 1. Метод `executeKillSwitch(...)`

Рекомендуемая сигнатура:

```java
public KillSwitchResult executeKillSwitch(Exchange exchange,
                                          Instrument instrument,
                                          Long dealId,
                                          String reasonCode)
```

Если `dealId` в текущей реализации не нужен, его можно пока использовать только для аудита или оставить как параметр на
будущее.

Но основной уровень выполнения — **по инструменту**.

---

### 2. Новый результат `KillSwitchResult`

Создать доменную модель результата.

Минимальные поля:

* `boolean success`
* `String internalAfter`
* `String externalAfter`
* `String message`

Обязательно добавить комментарии над полями.

Смысл:

* `success` — успешно ли снят риск полностью;
* `internalAfter` — внутренний слепок состояния после kill-switch;
* `externalAfter` — внешний слепок состояния после kill-switch;
* `message` — пояснение ошибки или результата.

---

## Полный flow метода

### Шаг 1. Прочитать текущее состояние по инструменту

Из БД нужно вычитать:

* активные позиции по инструменту;
* живые обычные ордера по инструменту;
* живые algo-ордера по инструменту;
* при необходимости статус инструмента.

С биржи нужно вычитать:

* открытые позиции по инструменту;
* pending обычные ордера по инструменту;
* active/pending algo-ордера по инструменту.

Это нужно для понимания, что именно надо зачистить.

---

### Шаг 2. Заблокировать инструмент для новых торговых действий

Если в проекте уже есть механизм блокировки инструмента через его статус, нужно использовать его.

Смысл:

* после запуска kill-switch новый happy-path по инструменту не должен стартовать.

Если готового механизма пока нет, оставить явный TODO, но сам контракт kill-switch проектировать уже с расчётом на такую
блокировку.

---

### Шаг 3. Отменить все pending обычные ордера на бирже

Нужно отменить все живые обычные ордера по инструменту.

Если уже есть соответствующие методы в `OrderService` или клиентском слое — использовать их.

Не изобретать новый параллельный способ, если в проекте уже есть стандартный сервисный путь.

---

### Шаг 4. Отменить все active/pending algo-ордера на бирже

Нужно отменить все живые algo-ордера по инструменту.

Если уже есть соответствующие методы в `AlgoOrderService` или клиентском слое — использовать их.

---

### Шаг 5. Закрыть все открытые позиции на бирже

Если по инструменту есть открытая позиция, её нужно аварийно закрыть.

Политику закрытия брать из текущих проектных соглашений.

Итог должен быть один:

* после kill-switch по инструменту не должно остаться открытой позиции.

---

### Шаг 6. Обновить локальные сущности в БД

После действий на бирже нужно привести БД в согласованное состояние.

Нужно обновить:

* позиции;
* обычные ордера;
* algo-ордера.

Требования:

* не удалять записи;
* использовать понятные аварийные статусы / close reasons;
* не оставлять живые сущности в подвешенном состоянии.

---

### Шаг 7. Повторно вычитать состояние

После выполнения kill-switch нужно заново вычитать состояние по инструменту.

#### Из БД:

* позиции;
* обычные ордера;
* algo-ордера;
* при необходимости статус инструмента.

#### С биржи:

* позиции;
* обычные ордера;
* algo-ордера.

Из этого состояния нужно собрать:

* `internalAfter`
* `externalAfter`

---

### Шаг 8. Определить success

`success = true`, если одновременно выполняются условия:

* на бирже нет открытых позиций по инструменту;
* на бирже нет pending обычных ордеров по инструменту;
* на бирже нет active/pending algo-ордеров по инструменту;
* в БД нет активной позиции по инструменту;
* в БД нет живых pending обычных ордеров по инструменту;
* в БД нет живых active/pending algo-ордеров по инструменту.

Если хотя бы одно условие не выполнено:

* `success = false`
* `message` должен содержать пояснение.

---

## Что должно войти в after-снимки

### `internalAfter`

Минимально должен содержать:

* инструмент;
* статус инструмента;
* позиции по инструменту;
* обычные ордера по инструменту;
* algo-ордера по инструменту.

### `externalAfter`

Минимально должен содержать:

* внешний идентификатор инструмента;
* позиции по инструменту;
* обычные ордера по инструменту;
* algo-ордера по инструменту.

Важно:

* это должны быть **полные слепки по инструменту**;
* не только тех сущностей, которые сервис случайно тронул в процессе.

---

## Какие слои можно затрагивать

Если нужно, допускается использовать существующие:

* `PositionService`
* `OrderService`
* `AlgoOrderService`
* data service слои
* клиентский слой биржи

Но важно не сломать границы ответственности.

KillSwitchService может оркестрировать аварийную зачистку, но не должен забирать на себя логику `TradeRuleValidator` и
`AnomalyService`.

---

## Что не нужно делать сейчас

На этом этапе НЕ нужно:

* реализовывать новый механизм определения аномалии;
* переносить в kill-switch логику формирования `AnomalyReport`;
* менять FSM;
* делать отдельную job;
* проектировать универсальный kill-switch на всё подряд вне контекста инструмента.

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## Что вернуть

Нужно вернуть:

1. `KillSwitchService` с методом `executeKillSwitch(...)`
2. `KillSwitchResult`
3. при необходимости — минимальные изменения в зависимых сервисах/контрактах
4. helper-методы внутри `KillSwitchService`

Без лишних рефакторингов.

---

## Ожидаемый результат

После реализации должно работать так:

* kill-switch вызывается по инструменту;
* все живые позиции / ордера / algo-ордера по инструменту зачищаются;
* БД приводится в аварийно-согласованное состояние;
* собираются полные after-снимки по инструменту;
* возвращается `KillSwitchResult`, по которому `TradeRuleValidator` сможет обновить `AnomalyReport`.
