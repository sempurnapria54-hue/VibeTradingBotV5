# Задание для Codex — TradeRuleValidator (каркас + интеграция с REFRESH_POSITIONS)

## Цель

Нужно реализовать **каркас** `TradeRuleValidator` и встроить его в flow команды `REFRESH_POSITIONS`.

На этом этапе validator должен:

* получить данные от `PositionService`;
* проверить базовые инварианты по позициям;
* при нарушении вызвать **заглушку** в `KillSwitchService`;
* остановить обычный sync через исключение.

Полную интеграцию с `AnomalyService` пока можно не делать.

---

## Что уже зафиксировано архитектурно

### 1. `TradeRuleValidator` — отдельный сервис

Он не является частью FSM.

Он не выполняет обычный sync.

Он только проверяет торговые правила и при нарушении запускает аварийный сценарий.

### 2. `PositionService` остаётся хозяином команды `REFRESH_POSITIONS`

Flow должен быть таким:

* `PositionService` читает snapshot с биржи;
* `PositionService` читает текущее состояние из БД;
* `PositionService` передаёт данные в `TradeRuleValidator.validatePositions(...)`;
* если validator не выявил нарушение — `PositionService` делает обычный sync;
* если validator выявил нарушение — обычный sync не продолжается.

### 3. `KillSwitchService`

На этом этапе `TradeRuleValidator` должен вызывать только **метод-заглушку** в `KillSwitchService`.

Без реальной аварийной логики.

---

## Что нужно реализовать

### 1. Новый сервис `TradeRuleValidator`

Создать сервис `TradeRuleValidator`.

На этом этапе в нём нужен как минимум метод:

```java
public void validatePositions(Exchange exchange,
                              Instrument instrument,
                              Long dealId,
                              List<PositionExternalSnapshot> externalSnapshots,
                              List<Position> domainPositions)
```

Если `dealId` в текущей реализации не нужен, допускается оставить его как nullable-параметр или не использовать внутри
метода.

Но сигнатуру лучше сразу сделать с `dealId`, если он потенциально нужен для аварийного сценария.

---

### 2. Базовые проверки для `validatePositions(...)`

Сейчас достаточно реализовать минимум:

#### Проверка 1. На бирже более одной позиции по инструменту

Это нарушение.

#### Проверка 2. В БД более одной активной позиции по инструменту

Это нарушение.

Если нарушения нет — метод просто завершается без действий.

Если нарушение есть — validator должен:

* определить код аномалии;
* определить критичность;
* вызвать заглушку `KillSwitchService`;
* бросить исключение, чтобы обычный sync не продолжался.

---

### 3. Код и severity

Пока можно захардкодить минимальный набор.

Для описанных нарушений использовать:

* `code = "OVERHEAD_POSITIONS_COUNT"`
* `severity = CRITICAL`

Лучше вынести это в helper-методы:

* `resolvePositionsCode(...)`
* `resolvePositionsSeverity(...)`

Даже если пока логика простая.

---

### 4. Исключение

Создать отдельное доменное исключение, например:

* `TradeRuleViolationException`

Оно должно использоваться для остановки обычного sync после того, как validator уже вызвал аварийную реакцию.

---

### 5. Заглушка в `KillSwitchService`

Добавить в `KillSwitchService` временный метод-заглушку.

Например:

```java
public void executeTradeRuleViolationStub(Exchange exchange,
                                          Instrument instrument,
                                          Long dealId,
                                          String code)
```

Требования:

* метод пока ничего не закрывает реально;
* можно оставить логирование или TODO;
* но вызов должен быть реальным и явным.

Важно:

* не делать пока внутри этого метода реальный kill-switch;
* это только точка расширения.

---

### 6. Интеграция в `PositionService`

Нужно обновить `PositionService`, чтобы он:

* после чтения snapshot с биржи и позиций из БД;
* вызывал `TradeRuleValidator.validatePositions(...)`;
* только после успешной проверки продолжал обычный sync.

Примерный flow:

```text
1. Прочитать externalSnapshots
2. Прочитать domainPositions
3. Вызвать tradeRuleValidator.validatePositions(...)
4. Если исключения нет — продолжить sync
5. Если exception есть — обычный sync прекратить
```

---

## Что не нужно делать сейчас

На этом этапе НЕ нужно:

* реализовывать полную интеграцию с `AnomalyService`;
* реализовывать полноценный `AnomalyReport` flow;
* проверять ордера и algo-ордера;
* делать универсальный router по всем командам;
* реализовывать реальный kill-switch;
* менять FSM или handler'ы.

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только новые классы и точечные изменения.

---

## Рекомендованная структура

### `TradeRuleValidator`

Ожидаются:

* `validatePositions(...)`
* private helper-методы для проверок
* private helper-методы для code / severity
* private helper-метод для запуска аварийной реакции

### `TradeRuleViolationException`

Отдельный exception-класс.

### `KillSwitchService`

Добавить только временный stub-method.

### `PositionService`

Добавить вызов validator перед обычным sync.

---

## Что вернуть

Нужно вернуть:

1. `TradeRuleValidator`
2. `TradeRuleViolationException`
3. временный stub-method в `KillSwitchService`
4. точечные изменения в `PositionService` для интеграции validator

Без лишних рефакторингов.

---

## Ожидаемый результат

После реализации должно работать так:

* `PositionService` читает данные;
* `TradeRuleValidator` проверяет позиции;
* если всё ок — sync продолжается;
* если найдена аномалия — validator вызывает stub в `KillSwitchService` и останавливает flow исключением.
