# Задание для Codex — реализовать команду REFRESH_ALGO_ORDERS

## Цель задачи

Нужно реализовать `REFRESH_ALGO_ORDERS` как отдельную сервисную команду algo truth layer.

Эта команда должна сопровождать:

* `AlgoOrder`
* `AttachedAlgoOrder`, которые уже вышли из ordinary order snapshot-контура и должны подтверждаться через algo endpoints

Команда не должна заниматься ordinary `Order` и не должна использовать `RefreshAttachedAlgoOrderExecutor`.

---

# 1. Какие классы должны получиться

Минимально ожидаются:

1. `RefreshAlgoOrderExecutor`
2. `TradeRuleValidator.validateRefreshAlgoOrders(...)`
3. при необходимости `AlgoOrderRefreshService` или `AlgoOrderSyncService`
4. при необходимости `AlgoOrderDataService` / repository methods
5. при необходимости `AttachedAlgoOrderDataService` / repository methods для algo-layer выборки
6. точечные изменения `ServiceCommandExecutor`

Если подходящие классы уже есть — доработать существующие.

---

# 2. Какой нейминг использовать

Использовать именно такой нейминг:

## Классы

* `RefreshAlgoOrderExecutor`

## Методы

* `execute(...)`
* `validateRefreshAlgoOrders(...)`

## Sync слой

Выбрать **одно** имя и использовать последовательно:

* либо `AlgoOrderRefreshService`
* либо `AlgoOrderSyncService`

Не использовать оба имени одновременно.

---

# 3. Зоны ответственности по классам

## 3.1. `RefreshAlgoOrderExecutor`

### Что должен делать

1. собрать внешний live algo snapshot через `orders-algo-pending`
2. прочитать local live `AlgoOrder`
3. прочитать `AttachedAlgoOrder`, которые уже в algo-layer
4. вызвать `TradeRuleValidator.validateRefreshAlgoOrders(...)`
5. если validator не выбросил исключение:

    * обновить matched live algo сущности
    * восстановить final state missing algo сущностей через `order-algo -> orders-algo-history`
    * сохранить изменения в БД

### Что НЕ должен делать

* не читать `orders-pending`
* не читать `trade/order`
* не вызывать `RefreshAttachedAlgoOrderExecutor`
* не обновлять parent `Order`
* не запускать kill-switch напрямую
* не создавать anomaly report напрямую

---

## 3.2. `TradeRuleValidator`

### Что должен делать

Иметь отдельный метод:

```java
validateRefreshAlgoOrders(exchange,
                          instrument,
                          dealId,
                          externalLiveAlgoSnapshots,
                          internalLiveAlgoOrders,
                          internalAttachedAlgoOrders)
```

### Что обязан проверить

#### Правило A. Нет дублей во внешнем live algo snapshot

Проверить отсутствие дублей по:

* `algoId`
* `algoClOrdId`

#### Правило B. Нет дублей среди local live `AlgoOrder`

Проверить отсутствие дублей по:

* `externalId`
* `internalId`

#### Правило C. Нет дублей среди `AttachedAlgoOrder`, попавших в algo-layer

Проверить отсутствие дублей по:

* `externalAttachedId`
* `externalId`
* `internalId`

#### Правило D. Каждый внешний live algo однозначно сопоставляется с одной local algo-сущностью

Порядок matching:

1. `externalId` (`algoId`)
2. `internalId` (`algoClOrdId`)
3. для attached child допускается `externalAttachedId`, если это проектно используется как основной внешний attached
   identifier

Если внешний algo не сопоставился или сопоставился неоднозначно — это anomaly.

#### Правило E. Все local algo-сущности принадлежат текущему инструменту

### Что делает validator при нарушении

1. создаёт initial `AnomalyReport`
2. пишет `internal_before` / `external_before`
3. при необходимости блокирует инструмент через `InstrumentService`
4. вызывает `KillSwitchService`
5. получает after snapshots
6. обновляет `AnomalyReport`
7. выбрасывает `TradeRuleViolationException`

### Что НЕ делает validator

* не обновляет algo сущности в happy path
* не сопровождает ordinary `Order`
* не использует ordinary order endpoints

---

# 4. Что именно должно происходить в `RefreshAlgoOrderExecutor`

## Шаг 1. Собрать внешний live algo snapshot

Основной внешний источник правды:

* `GET /api/v5/trade/orders-algo-pending`

### Как собирать snapshot

Так как endpoint фильтруется по `ordType`, executor должен:

1. собрать набор ordType из local live `AlgoOrder` и `AttachedAlgoOrder` algo-layer
2. пройтись по ordType
3. получить все live algo snapshots по instrument
4. дедуплицировать итоговый внешний snapshot

Использовать ordType минимум из набора:

* `conditional`
* `oco`
* `trigger`
* `move_order_stop`

Но реально лучше строить набор исходя из local data + project defaults.

## Шаг 2. Прочитать local algo-сущности

### Из БД читать:

* live `AlgoOrder`
* `AttachedAlgoOrder` в статусах `ATTACHED` и `ACTIVE`

`CREATED` сюда попадать не должен.

## Шаг 3. Вызвать validator

* `tradeRuleValidator.validateRefreshAlgoOrders(...)`

Если validator выбросил исключение — normal flow прекращается.

## Шаг 4. Обновить matched live algo сущности

Для каждого external live algo:

* найти local entity (`AlgoOrder` или `AttachedAlgoOrder`)
* применить snapshot
* поставить `ACTIVE`, если algo подтверждён live
* сохранить

## Шаг 5. Для local algo сущностей, отсутствующих в live algo snapshot, восстановить final state

### 5.1. Вызвать `GET /trade/order-algo`

Искать:

* по `algoId`
* если нет `algoId`, то по `algoClOrdId`

Если detail найден:

* обновить entity
* если algo still live/pause -> `ACTIVE`
* если есть достаточное final proof -> final status
* сохранить

### 5.2. Если detail не помог — вызвать `GET /trade/orders-algo-history`

Если history показывает:

* `effective` -> final status, обычно `CLOSED`
* `canceled` -> `CLOSED`
* `order_failed` -> `FAILED`

Сохранить в БД.

### 5.3. Если algo не найден ни в detail, ни в history

Не делать silent `CLOSED`.
Это unresolved algo state.

Это либо retryable state, либо anomaly / exception — по принятой общей политике проекта. Но не silent close.

---

# 5. Что нужно делать с `AttachedAlgoOrder` внутри этой команды

## 5.1. Какие child entities сюда попадают

Сюда попадают только `AttachedAlgoOrder`, которые уже требуют algo-truth refresh.

Минимально это child в статусах:

* `ATTACHED`
* `ACTIVE`

## 5.2. Какие статусы child можно выставлять здесь

### `ACTIVE`

Если algo detail / pending algo snapshot подтвердили live algo.

### `CLOSED`

Если algo history доказал final close / cancel / effective completion.

### `FAILED`

Если algo history показал `order_failed` или equivalent failure proof.

## 5.3. Чего делать нельзя

Нельзя возвращать child обратно в ordinary-order stage.

Нельзя использовать `RefreshAttachedAlgoOrderExecutor` внутри этой команды.

`RefreshAttachedAlgoOrderExecutor` относится только к child-sync из order snapshot.

---

# 6. Persistence требования

## 6.1. Для `AlgoOrder`

Нужны методы уровня:

```java
List<AlgoOrder> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)

AlgoOrder save(AlgoOrder algoOrder)
```

## 6.2. Для `AttachedAlgoOrder`

Нужны методы уровня:

```java
List<AttachedAlgoOrder> findAllByStatuses(Set<String> statuses)

// или лучше по instrument/deal через join/accessor, если модель это позволяет
AttachedAlgoOrder save(AttachedAlgoOrder attachedAlgoOrder)
```

Важно: выборка должна быть ограничена текущим инструментом.

Если для этого нужен join через order/deal — реализовать в проектном стиле.

---

# 7. Что нужно сделать в `ServiceCommandExecutor`

Команда должна быть маршрутизирована как:

```java
REFRESH_ALGO_ORDERS ->refreshAlgoOrderExecutor.

execute(exchange, instrument, dealId)
```

Не вызывать `RefreshAttachedAlgoOrderExecutor` напрямую из `ServiceCommandExecutor`.

---

# 8. Что нельзя делать в этой задаче

Нельзя:

* реализовывать ordinary order refresh здесь
* использовать `orders-pending`
* использовать `trade/order`
* использовать `RefreshAttachedAlgoOrderExecutor`
* закрывать missing algo сущность без `order-algo` / `orders-algo-history`
* тихо создавать local algo сущность из неизвестного внешнего live algo
* обновлять parent `Order`

---

# 9. Что вернуть по задаче

Нужно вернуть:

1. `RefreshAlgoOrderExecutor`
2. `TradeRuleValidator.validateRefreshAlgoOrders(...)`
3. при необходимости — `AlgoOrderRefreshService` или `AlgoOrderSyncService`
4. при необходимости — `AlgoOrderDataService` / repository methods
5. при необходимости — `AttachedAlgoOrderDataService` / repository methods для algo-layer выборки
6. точечные правки `ServiceCommandExecutor`
7. при необходимости — точечные изменения мапперов

Без лишнего рефакторинга unrelated-кода.

---

# 10. Ожидаемый результат

После реализации должно быть так:

* algo truth layer живёт отдельно от ordinary order layer
* `AttachedAlgoOrder` после ordinary stage корректно подхватывается algo-командой
* live algo подтверждается через `orders-algo-pending`
* final algo state восстанавливается через `order-algo -> orders-algo-history`
* missing algo сущность не закрывается вслепую
* любые изменения `AlgoOrder` и `AttachedAlgoOrder` сразу пишутся в БД
