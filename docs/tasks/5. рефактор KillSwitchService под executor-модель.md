# Задание для Codex — рефактор KillSwitchService под executor-модель

## Цель

Нужно переработать `KillSwitchService` под новую архитектуру.

Сейчас `KillSwitchService` слишком много делает сам:

* сам вызывает биржу для разных сущностей;
* сам руками обновляет локальные статусы;
* сам работает одновременно и как orchestrator, и как исполнитель действий.

Нужно привести его к новой модели:

* `KillSwitchService` = orchestrator аварийного сценария по инструменту;
* конкретные действия над сущностями выполняют отдельные executors;
* чтение action-state идёт только по живым статусам;
* полные after-снимки по инструменту собираются отдельно;
* не должно появиться циклических зависимостей.

---

## Архитектурный контекст

### Главная цепочка

На примере `REFRESH_POSITIONS`:

```text
ServiceCommandExecutor
  -> RefreshPositionExecutor
     -> TradeRuleValidator
        -> AnomalyService
        -> KillSwitchService
           -> ClosePositionExecutor
           -> CancelOrderExecutor
           -> CancelAlgoOrderExecutor
           -> DealEmergencyFinalizer
```

Важно:

* `KillSwitchService` вызывается из `TradeRuleValidator`;
* `KillSwitchService` не должен вызывать refresh-executors;
* `KillSwitchService` не должен вызывать фасады, если это создаёт цикл обратно в refresh-flow.

---

## Что нужно исправить концептуально

### 1. `readState(...)` в текущем виде неправильный

Сейчас он читает внутренние сущности просто по `instrumentId` без фильтра по статусам.

Это плохо, потому что:

* со временем по инструменту накопится много исторических записей;
* для action-сценария kill-switch нам не нужны все сущности подряд;
* мы рискуем тащить в аварийные действия неактуальные записи.

Нужно разделить чтение состояний на два типа.

#### `readActionState(...)`

Используется для реальных аварийных действий.

Должен читать только **живые / actionable** сущности.

#### `readReportSnapshot(...)`

Используется для after-снимка в `KillSwitchResult` и затем в `AnomalyReport`.

Должен собирать **полный релевантный срез по инструменту**, а не только action-state.

---

### 2. `KillSwitchService` не должен руками закрывать сущности

Сейчас внутри него есть логика вроде:

* руками переводить `Position` в закрытое состояние;
* руками ставить `Order.Status.CLOSED`;
* руками ставить `AlgoOrder.Status.CLOSED`.

Это нужно убрать.

`KillSwitchService` должен вызывать отдельные executors, а они уже:

* ходят на биржу;
* обновляют локальные доменные модели;
* сохраняют изменения в БД.

---

### 3. Нужно избежать циклических зависимостей

Нельзя получить цикл вида:

```text
RefreshPositionExecutor -> TradeRuleValidator -> KillSwitchService -> PositionService -> RefreshPositionExecutor
```

Поэтому `KillSwitchService` не должен зависеть от refresh-компонентов.

Он должен зависеть только от отдельных аварийных executors.

---

## Что нужно реализовать

### 1. Обновить `KillSwitchService`

Он должен остаться orchestrator'ом и содержать основной метод:

```java
public KillSwitchResult executeKillSwitch(Exchange exchange,
                                          Instrument instrument,
                                          Long dealId,
                                          String reasonCode)
```

Но внутри него больше не должно быть ручного закрытия сущностей.

Он должен делать следующее.

---

## Новый flow `executeKillSwitch(...)`

### Шаг 1. Собрать action-state

Нужно прочитать только **живые** сущности по инструменту.

#### Из БД:

* активные позиции;
* живые обычные ордера;
* живые algo-ордера.

#### С биржи:

* открытые позиции;
* pending обычные ордера;
* active/pending algo-ордера.

Для этого создать отдельный метод, например:

```java
private StateSnapshot readActionState(ClientService clientService, Instrument instrument)
```

Важно:

* чтение из БД должно быть по `instrumentId + live statuses`, а не просто по `instrumentId`;
* нельзя тащить всю историю по инструменту.

---

### Шаг 2. Заблокировать инструмент

Если в проекте есть статус инструмента для запрета торговли, его нужно обновить здесь.

Если уже есть стандартный способ блокировки — использовать его.

---

### Шаг 3. Отменить живые обычные ордера

Не руками внутри `KillSwitchService`, а через отдельный executor:

* `CancelOrderExecutor`

Он сам должен:

* отменить ордера на бирже;
* обновить локальные ордера в БД.

---

### Шаг 4. Отменить живые algo-ордера

Через:

* `CancelAlgoOrderExecutor`

Он сам должен:

* отменить algo-ордера на бирже;
* обновить локальные algo-ордера в БД.

---

### Шаг 5. Закрыть живые позиции

Через:

* `ClosePositionExecutor`

Он сам должен:

* закрыть позиции на бирже;
* обновить локальные позиции в БД.

---

### Шаг 6. Аварийно завершить сделки по инструменту

Если по инструменту есть живая сделка, её нужно перевести в правильное аварийное состояние.

Для этого добавить отдельный executor, например:

* `DealEmergencyFinalizer`

Он должен:

* найти активные сделки по инструменту;
* перевести их в нужный terminal статус;
* выставить корректный close reason.

---

### Шаг 7. Собрать полный after-снимок по инструменту

После выполнения всех аварийных действий нужно собрать **полный релевантный snapshot по инструменту**.

Для этого нужен отдельный метод, например:

```java
private StateSnapshot readReportSnapshot(ClientService clientService, Instrument instrument)
```

Важно:

* этот snapshot используется не для действий, а для отчёта;
* он должен быть богаче, чем action-state.

---

### Шаг 8. Построить `KillSwitchResult`

`KillSwitchResult` должен содержать:

* `success`
* `internalAfter`
* `externalAfter`
* `message`

`success = true`, если:

* на бирже нет открытых позиций по инструменту;
* на бирже нет pending обычных ордеров;
* на бирже нет active/pending algo-ордеров;
* в БД нет активных позиций;
* в БД нет живых обычных ордеров;
* в БД нет живых algo-ордеров;
* связанные сделки переведены в нужное аварийное состояние.

---

## Что нужно сделать со `StateSnapshot`

Текущую модель можно оставить, но нужно уточнить её использование:

### Для `readActionState(...)`

Она содержит только живые/actionable сущности.

### Для `readReportSnapshot(...)`

Она может содержать полный релевантный срез по инструменту.

Если удобно, можно:

* либо оставить одну модель `StateSnapshot`;
* либо ввести две разные модели.

Но важно, чтобы код явно различал:

* snapshot для действий;
* snapshot для отчёта.

---

## Какие новые executors нужно создать

Минимально ожидаются:

### 1. `ClosePositionExecutor`

Отвечает за аварийное закрытие позиций по инструменту.

### 2. `CancelOrderExecutor`

Отвечает за аварийную отмену живых обычных ордеров по инструменту.

### 3. `CancelAlgoOrderExecutor`

Отвечает за аварийную отмену живых algo-ордеров по инструменту.

### 4. `DealEmergencyFinalizer`

Отвечает за перевод живых сделок по инструменту в нужное аварийное состояние.

---

## Требования к чтению из БД

Нельзя использовать методы вида:

```java
findByInstrumentId(...)
```

для action-state без фильтра по статусам.

Нужно использовать чтение вида:

* `findAllByInstrumentIdAndStatuses(...)`
* или аналогичный метод по instrument + live statuses
* для сделок — только активные / не terminal

То есть чтение для kill-switch должно быть строго ограничено живыми сущностями.

### Что нужно добавить в repository / data service слой

Если нужных методов сейчас нет, их нужно добавить.

Минимально ожидаются методы для action-state.

#### Position

Repository / data service должны уметь читать только живые позиции по инструменту.

Ожидаемый контракт, например:

```java
List<PositionEntity> findAllByInstrumentIdAndStatusIn(Long instrumentId, Collection<String> statuses)
```

или на domain/data service уровне:

```java
List<Position> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)
```

Для позиций в action-state обычно нужен только live-статус, например `ACTIVE`.

#### Order

Repository / data service должны уметь читать только живые обычные ордера по инструменту.

Например:

```java
List<OrderEntity> findAllByInstrumentIdAndStatusIn(Long instrumentId, Collection<String> statuses)
```

или на domain/data service уровне:

```java
List<Order> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)
```

Нужно использовать именно те доменные статусы, которые в проекте считаются live.

#### AlgoOrder

Repository / data service должны уметь читать только живые algo-ордера по инструменту.

Например:

```java
List<AlgoOrderEntity> findAllByInstrumentIdAndStatusIn(Long instrumentId, Collection<String> statuses)
```

или на domain/data service уровне:

```java
List<AlgoOrder> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)
```

Нужно использовать именно те доменные статусы, которые в проекте считаются live.

#### Deal

Для аварийного завершения сделок по инструменту нужен метод чтения только живых / не terminal сделок.

Например:

```java
List<DealEntity> findAllByInstrumentIdAndStatusIn(Long instrumentId, Collection<String> statuses)
```

или на domain/data service уровне:

```java
List<Deal> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)
```

Здесь должны использоваться только не terminal статусы сделки.

### Что важно по live-status спискам

Не хардкодить списки статусов хаотично в каждом месте.

Нужно, чтобы для каждой сущности был понятный источник истины:

* либо helper-метод в executor/service;
* либо отдельный util;
* либо метод самой сущности вроде `isLive()` для единичной проверки и рядом централизованный список для repository
  query.

То есть Codex должен не просто добавить query-методы, а ещё аккуратно определить, какие именно статусы считаются live
для:

* `Position`
* `Order`
* `AlgoOrder`
* `Deal`

Если эти правила уже есть в проекте — использовать их.

Если их нет — добавить минимально необходимую централизованную реализацию, не размазывая строки статусов по коду.

## Что не нужно делать

На этом этапе НЕ нужно:

* переделывать `TradeRuleValidator`;
* менять FSM;
* менять `AnomalyReport` модель;
* переносить в `KillSwitchService` поиск аномалии;
* вызывать refresh-executors из kill-switch.

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

## Что вернуть

Нужно вернуть:

1. обновлённый `KillSwitchService`
2. новые executors:

    * `ClosePositionExecutor`
    * `CancelOrderExecutor`
    * `CancelAlgoOrderExecutor`
    * `DealEmergencyFinalizer`
3. при необходимости — точечные изменения в data service / repository методах для чтения по live statuses
4. при необходимости — уточнённую модель `StateSnapshot`
5. при необходимости — точечные изменения в `KillSwitchResult` использовании

Без лишних рефакторингов.

---

## Ожидаемый результат

После рефактора должно работать так:

* `KillSwitchService` больше не закрывает сущности руками;
* он читает action-state только по живым статусам;
* он оркестрирует аварийные executors;
* executors сами обновляют локальные доменные модели;
* после этого собирается полный after-snapshot по инструменту;
* возвращается корректный `KillSwitchResult`.
