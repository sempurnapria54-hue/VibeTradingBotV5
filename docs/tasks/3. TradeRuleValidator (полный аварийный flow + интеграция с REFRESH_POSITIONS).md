# Задание для Codex — TradeRuleValidator (полный аварийный flow + интеграция с REFRESH_POSITIONS)

## Цель

Нужно реализовать `TradeRuleValidator` и встроить его в flow команды `REFRESH_POSITIONS`.

На этом этапе validator должен:

* получить данные от `PositionService`;
* проверить базовые инварианты по позициям;
* при нарушении **сразу выполнить полный аварийный сценарий**;
* после аварийного сценария выбросить доменное исключение, чтобы обычный sync не продолжался.

---

## Что уже зафиксировано архитектурно

### 1. `TradeRuleValidator` — отдельный сервис

Он:

* не является частью FSM;
* не выполняет обычный sync;
* не обновляет `DealContext`;
* отвечает за проверку правил и аварийный flow при нарушении.

### 2. `PositionService` остаётся хозяином команды `REFRESH_POSITIONS`

Flow должен быть таким:

* `PositionService` читает snapshot с биржи;
* `PositionService` читает текущее состояние из БД;
* `PositionService` передаёт данные в `TradeRuleValidator.validatePositions(...)`;
* если validator не выявил нарушение — `PositionService` делает обычный sync;
* если validator выявил нарушение — обычный sync не продолжается.

### 3. `TradeRuleValidator` сам выполняет полный аварийный сценарий

При нарушении validator должен:

1. создать `AnomalyReport`;
2. перевести его в `IN_PROGRESS`;
3. вызвать полноценный `KillSwitchService`;
4. собрать `internalAfter` и `externalAfter`;
5. поставить `KILL_SWITCH_EXECUTED` и затем `COMPLETED`, если всё успешно;
6. либо поставить `ERROR`, если что-то пошло не так;
7. после этого выбросить `TradeRuleViolationException`.

### 4. `AnomalyJob` — это recovery-механизм

Она не является основным обработчиком аномалий.

Она нужна только для случаев, когда процесс оборвался на середине.

---

## Что нужно реализовать

### 1. Новый сервис `TradeRuleValidator`

Создать сервис `TradeRuleValidator`.

На этом этапе в нём нужен как минимум метод:

```java
public void validatePositions(Exchange exchange,
                              Instrument instrument,
                              Long dealId,
                              List<PositionExternalSnapshot> externalSnapshots,
                              List<Position> domainPositions)
```

`dealId` можно пока использовать только там, где это действительно нужно.

---

### 2. Базовые проверки для `validatePositions(...)`

Сейчас достаточно реализовать минимум:

#### Проверка 1. На бирже более одной позиции по инструменту

Это нарушение.

#### Проверка 2. В БД более одной активной позиции по инструменту

Это нарушение.

Если нарушения нет — метод просто завершается без побочных действий.

Если нарушение есть — запускается полный аварийный flow.

---

### 3. Код и severity

Пока можно захардкодить минимальный набор.

Для описанных нарушений использовать:

* `code = "OVERHEAD_POSITIONS_COUNT"`
* `severity = CRITICAL`

Лучше вынести это в helper-методы:

* `resolvePositionsCode(...)`
* `resolvePositionsSeverity(...)`

---

### 4. Полный аварийный flow внутри validator

При нарушении validator должен сделать следующее.

#### Шаг 1. Собрать before-снимки

Подготовить:

* `internalBefore`
* `externalBefore`

На первом этапе допускается простая сериализация в JSON-строки или заглушки/TODO, если готовой сериализации пока нет.

#### Шаг 2. Создать `AnomalyReport`

Через `AnomalyService.create(...)` создать репорт со статусом `CREATED`.

#### Шаг 3. Перевести его в `IN_PROGRESS`

Через `AnomalyService.markInProgress(...)`.

#### Шаг 4. Вызвать полноценный `KillSwitchService`

Нужен **не stub**, а реальный основной метод `KillSwitchService`.

Если реальный kill-switch пока не реализован целиком, допускается временно вызвать существующий основной метод-заглушку,
но через тот контракт, который позже станет боевым.

#### Шаг 5. Собрать after-снимки

После kill-switch повторно собрать:

* `internalAfter`
* `externalAfter`

#### Шаг 6. Обновить статус репорта

Если аварийный сценарий завершился успешно:

* сначала `AnomalyService.markKillSwitchExecuted(...)`
* затем `AnomalyService.complete(...)`

Если в процессе произошла ошибка:

* вызвать `AnomalyService.markError(...)`
* передать текст ошибки в `message`

#### Шаг 7. Прервать обычный sync

После завершения аварийного сценария validator должен **всегда** выбрасывать `TradeRuleViolationException`.

Это осознанное прерывание обычного flow, а не неожиданная техошибка.

---

### 5. Исключение

Создать отдельное доменное исключение:

* `TradeRuleViolationException`

Оно должно использоваться для остановки обычного sync после полной обработки аномалии.

---

### 6. Интеграция в `PositionService`

Нужно обновить `PositionService`, чтобы он:

* после чтения snapshot с биржи и позиций из БД;
* вызывал `TradeRuleValidator.validatePositions(...)`;
* только после успешной проверки продолжал обычный sync.

Примерный flow:

```text
1. Прочитать externalSnapshots
2. Прочитать domainPositions
3. Вызвать tradeRuleValidator.validatePositions(...)
4. Если исключения нет — продолжить sync
5. Если exception есть — обычный sync прекратить
```

Важно:

* `PositionService` не должен ловить и подавлять `TradeRuleViolationException`
* исключение должно подниматься выше и останавливать команду

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных
* всегда ставить фигурные скобки
* писать чистый Spring / DDD код
* не генерировать лишний код
* если можно — возвращать только новые классы и точечные изменения

## Рекомендованная структура

### `TradeRuleValidator`

Ожидаются:

* `validatePositions(...)`
* private helper-методы для проверок
* private helper-методы для `code` / `severity`
* private helper-методы для before/after snapshot
* private helper-метод для полного аварийного flow

### `TradeRuleViolationException`

Отдельный exception-класс.

### `PositionService`

Точечные изменения для вызова validator перед обычным sync.

### `KillSwitchService`

Использовать основной метод аварийного закрытия по инструменту.

### `AnomalyService`

Использовать существующие методы перевода репорта по статусам.

Нужно вернуть:

1. `TradeRuleValidator`
2. `TradeRuleViolationException`
3. точечные изменения в `PositionService`
4. при необходимости — минимальные изменения в `KillSwitchService` контракте
5. при необходимости — минимальные изменения в `AnomalyService` использовании

Без лишних рефакторингов.

---

## Ожидаемый результат

После реализации должно работать так:

* `PositionService` читает данные;
* `TradeRuleValidator` проверяет позиции;
* если всё ок — sync продолжается;
* если найдена аномалия — validator полностью обрабатывает её через `AnomalyService` и `KillSwitchService`;
* после этого validator выбрасывает `TradeRuleViolationException`;
* обычный sync прекращается.
