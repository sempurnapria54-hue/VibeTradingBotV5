# REFRESH_ORDER + ATTACHED_ALGO + ALGO — полный процесс и зоны ответственности

## Цель

Эта дока фиксирует целевую архитектуру сопровождения обычного ордера (`Order`), его прикреплённых защит (
`AttachedAlgoOrder`) и самостоятельных algo-ордеров (`AlgoOrder`).

Нужно жёстко разделить три слоя:

1. `RefreshOrderExecutor`
2. `RefreshAttachedAlgoOrderExecutor`
3. `RefreshAlgoOrderExecutor`

И зафиксировать:

* какой слой из какого источника правды читает;
* какой слой что именно обновляет;
* какой слой когда сохраняет изменения в БД;
* как живёт `AttachedAlgoOrder` между order snapshot и algo snapshot;
* какие методы биржи вызываются и в какой последовательности.

---

# 1. Главная идея

`AttachedAlgoOrder` нельзя оставлять просто полем внутри `Order` без собственного цикла сопровождения.

Но и нельзя сразу считать его полноценным `AlgoOrder`.

Поэтому целевая модель такая:

## Слой A. Ordinary order refresh

Источник правды:

* `GET /api/v5/trade/orders-pending`
* `GET /api/v5/trade/order`
* `GET /api/v5/trade/orders-history`
* `GET /api/v5/trade/orders-history-archive`

Этот слой отвечает за обычный `Order` и за дочерний snapshot attached-защит внутри snapshot ордера.

## Слой B. Attached child refresh

Источник правды:

* `attachAlgoClOrdId`
* top-level attached TP/SL поля ордера
* `attachAlgoOrds[]` внутри snapshot обычного ордера

Этот слой отвечает за `AttachedAlgoOrder` как за дочернюю сущность `Order`.

## Слой C. Algo refresh

Источник правды:

* `GET /api/v5/trade/order-algo`
* `GET /api/v5/trade/orders-algo-pending`
* `GET /api/v5/trade/orders-algo-history`

Этот слой отвечает за уже активный / самостоятельный algo lifecycle.

---

# 2. Сущности и их роли

## Order

Обычный биржевой ордер.

Живёт в ordinary-order контуре.

## AttachedAlgoOrder

Дочерняя сущность обычного ордера.

Нужна для сопровождения attached TP/SL, которые биржа возвращает прямо в order snapshot (`attachAlgoOrds[]`,
`attachAlgoClOrdId`, `tp/sl fields`).

Это не просто DTO-поле. Это полноценная доменная сущность, которую нужно хранить и обновлять в БД при каждом значимом
изменении.

## AlgoOrder

Отдельный самостоятельный algo-ордер.

Живёт в собственном algo-refresh контуре.

---

# 3. Какие команды / executors есть в системе

## 3.1. `RefreshOrderExecutor`

Это отдельный executor для сопровождения обычных order'ов.

Он:

* читает external ordinary order snapshots;
* читает local live orders;
* вызывает `TradeRuleValidator`;
* обновляет matched `Order`;
* восстанавливает финальное состояние missing-from-pending order'ов;
* для каждого обработанного order snapshot вызывает `RefreshAttachedAlgoOrderExecutor`.

## 3.2. `RefreshAttachedAlgoOrderExecutor`

Это дочерний executor order-слоя.

Он **не является отдельной сервисной командой FSM**.

Он вызывается из `RefreshOrderExecutor` и работает на одном order + одном external order snapshot.

Он:

* извлекает attached protection из snapshot обычного ордера;
* синхронизирует `AttachedAlgoOrder` в БД;
* переводит attached child в нужный статус;
* сохраняет изменения сразу.

## 3.3. `RefreshAlgoOrderExecutor`

Это отдельный executor algo-контура.

Он:

* читает live `AlgoOrder`;
* читает `AttachedAlgoOrder`, которые уже дошли до состояния, когда их надо сопровождать как algo;
* ходит в algo endpoints;
* доводит lifecycle до `ACTIVE / CLOSED / FAILED`.

Это отдельный слой и отдельный use-case.

---

# 4. Откуда какой слой берёт правду

## 4.1. `RefreshOrderExecutor`

### Методы биржи

1. `GET /api/v5/trade/orders-pending`
2. `GET /api/v5/trade/order`
3. `GET /api/v5/trade/orders-history`
4. `GET /api/v5/trade/orders-history-archive`

### Почему

`orders-pending` показывает только незавершённые ordinary orders (`live`, `partially_filled`).
Если local live order исчез из pending snapshot, это не значит автоматически `CLOSED`.
Нужно восстановить его финальный state через detail/history/archive.

---

## 4.2. `RefreshAttachedAlgoOrderExecutor`

### Источник правды

Только snapshot обычного ордера, который уже получил `RefreshOrderExecutor`.

То есть он работает по данным из:

* `attachAlgoClOrdId`
* `tpTriggerPx`, `tpTriggerPxType`, `tpOrdPx`
* `slTriggerPx`, `slTriggerPxType`, `slOrdPx`
* `attachAlgoOrds[]`

Он сам на биржу не ходит.

---

## 4.3. `RefreshAlgoOrderExecutor`

### Методы биржи

1. `GET /api/v5/trade/order-algo`
2. `GET /api/v5/trade/orders-algo-pending`
3. `GET /api/v5/trade/orders-algo-history`

### Почему

Это отдельные источники правды именно для algo lifecycle.

`RefreshAttachedAlgoOrderExecutor` не должен тянуть в себя algo endpoints.

---

# 5. Какой lifecycle у AttachedAlgoOrder

Нужно использовать lifecycle `AttachedAlgoOrder`, а не пытаться описывать всё через флаги внутри `Order`.

Рекомендуемая логика статусов:

## `CREATED`

Локальная дочерняя сущность создана, но биржа ещё не подтвердила attached protection.

Пример:

* локально создали entry order с attached SL;
* в БД уже есть `AttachedAlgoOrder`, но внешнего подтверждения ещё нет.

## `ATTACHED`

Attached protection подтверждён в snapshot обычного ордера.

Это значит:

* мы видим attached protection внутри `trade/order`, `orders-pending`, `orders-history` или `orders-history-archive`;
* protection существует как часть order snapshot;
* но мы ещё не считаем его подтверждённым самостоятельным algo lifecycle.

## `ACTIVE`

Protection уже подтверждён как live algo через algo endpoints.

Это значит:

* есть подтверждение из `order-algo` или `orders-algo-pending`;
* attached protection уже живёт в algo-контуре.

## `CLOSED`

Protection завершён и больше не активен.

Примеры:

* order cancelled и attached protection снят;
* attached protection удалили amend'ом;
* protection был снят при `PROTECTION_SWITCHED`;
* algo history показывает final non-live state.

## `FAILED`

Protection не удалось создать/подтвердить.

Примеры:

* в attached snapshot пришёл `failCode/failReason`;
* algo history показывает `order_failed`;
* подтверждение protection не удалось получить, и проектно это считается ошибкой.

---

# 6. Как `RefreshOrderExecutor` должен работать по шагам

## Шаг 1. Прочитать внешний pending snapshot ordinary orders

Вызываем:

* `GET /api/v5/trade/orders-pending`

По инструменту:

* `instType=SWAP`
* `instId=<instrumentExternalId>`
* `state=live,partially_filled`

---

## Шаг 2. Прочитать local live orders

Из БД читаем только live ordinary orders по инструменту.

---

## Шаг 3. Проверить инварианты команды

Вызываем:

* `TradeRuleValidator.validateRefreshOrders(...)`

Validator работает только с ordinary orders этой команды.

Если validator находит нарушение:

* normal flow прекращается;
* запускается anomaly / kill-switch flow.

---

## Шаг 4. Обновить matched ordinary orders

Для каждого order из pending snapshot:

* находим local `Order`;
* обновляем его;
* резолвим доменный статус через `OrderStatusResolver`;
* сохраняем `Order`;
* передаём `(Order, OrderExternalSnapshot)` в `RefreshAttachedAlgoOrderExecutor`.

---

## Шаг 5. Обработать local live orders, которых нет в pending snapshot

Для каждого missing-from-pending local live `Order`:

### 5.1. Вызвать `GET /api/v5/trade/order`

Ищем по:

* `ordId`
* или `clOrdId`

Если найден snapshot:

* обновляем `Order`;
* резолвим статус через `OrderStatusResolver`;
* сохраняем;
* вызываем `RefreshAttachedAlgoOrderExecutor` на этом final snapshot.

### 5.2. Если detail не помог — вызвать `GET /api/v5/trade/orders-history`

Если нашли order:

* обновляем `Order`;
* резолвим final status;
* сохраняем;
* вызываем `RefreshAttachedAlgoOrderExecutor`.

### 5.3. Если recent history не помог — вызвать `GET /api/v5/trade/orders-history-archive`

Если нашли order:

* обновляем `Order`;
* резолвим final status;
* сохраняем;
* вызываем `RefreshAttachedAlgoOrderExecutor`.

### 5.4. Если нигде не нашли

Это unsafe state.

Такой кейс не должен заканчиваться тихим `order.toClose(...)` по умолчанию.
Это уже аномалия восстановления final state.

---

# 7. Как `RefreshAttachedAlgoOrderExecutor` должен работать

## Вход

Он получает:

* `Order order`
* `OrderExternalSnapshot snapshot`

Он не читает биржу сам.

## Что он должен сделать

1. Найти все существующие `AttachedAlgoOrder` по `orderId`.
2. Извлечь attached data из snapshot order.
3. Сопоставить внешний attached snapshot с локальными children.
4. Создать/обновить/закрыть/зафейлить `AttachedAlgoOrder`.
5. Сразу сохранить все изменения в БД.

---

## Какие поля он должен читать из order snapshot

Минимально:

* `attachAlgoClOrdId`
* `attachAlgoOrds[]`
* top-level `tp/sl` поля
* при наличии `attachAlgoId` из `attachAlgoOrds[]`
* `failCode/failReason`, если биржа их вернула внутри attached объекта

---

## Как сопоставлять AttachedAlgoOrder

Рекомендуемый порядок matching:

1. `externalAttachedId`
2. `externalId`
3. `internalId`
4. fallback по `type`, если по модели на order допустим только один child этого типа

Где:

* `externalAttachedId` = `attachAlgoId` из attached order snapshot
* `internalId` = `attachAlgoClOrdId`
* `externalId` = основной algoId, если позже этот child подтверждён через algo endpoints

---

## Когда создавать новый AttachedAlgoOrder

Нужно создавать новый child, если:

* в external order snapshot есть attached protection;
* а local child по нему не найден.

Новый child должен сразу получить:

* `orderId`
* `internalId`
* `externalAttachedId`
* `type`
* trigger prices / size / external type, если доступны
* initial status

И сразу сохраняться в БД.

---

## Когда ставить статус `ATTACHED`

Ставим `ATTACHED`, если:

* attached protection найден в order snapshot;
* нет признаков failure;
* нет ещё подтверждения самостоятельного algo lifecycle.

Это основной happy-path статус после sync из order snapshot.

---

## Когда ставить статус `FAILED`

Ставим `FAILED`, если:

* attached snapshot содержит `failCode` или `failReason`;
* данные protection противоречивы и проектно это трактуется как ошибка;
* external protection явно не смог быть создан/подтверждён.

---

## Когда ставить статус `CLOSED` внутри attached refresh

Нужно быть осторожным.

### Можно закрыть child сразу

Если:

* parent order cancelled/finalized таким образом, что attached protection точно больше не должен существовать;
* или текущий order snapshot явно показывает, что attached protection был удалён;
* или attached ранее был только order-level, а теперь order final и attached empty, и проектно это трактуется как
  удаление.

### Нельзя закрывать child только потому, что он пропал из одного order snapshot после fill

Потому что после исполнения parent order protection может уже жить в algo-контуре.

То есть отсутствие attached в order snapshot после финализации parent order **не является достаточным доказательством**,
что child уже `CLOSED`.

В таком кейсе child должен остаться в промежуточном статусе (`ATTACHED`) и быть передан дальше в
`RefreshAlgoOrderExecutor`.

Это ключевое правило.

---

# 8. Как `RefreshAlgoOrderExecutor` должен работать

## Что он читает из БД

Нужно читать:

* live ordinary `AlgoOrder`
* `AttachedAlgoOrder` в статусах, которые уже требуют algo-подтверждения

Рекомендуемо:

* `ATTACHED`
* `ACTIVE`

---

## Как он работает для AttachedAlgoOrder

Для каждого attached child, который дошёл до algo-слоя:

### Шаг 1. Попробовать `GET /api/v5/trade/order-algo`

Искать:

* сначала по `externalId`, если он уже есть;
* иначе по `internalId` как `algoClOrdId`, если модель так договорится использовать это поле;
* при необходимости можно передавать `instId`.

Если найден live algo:

* обновляем child;
* ставим `ACTIVE`;
* сохраняем в БД.

### Шаг 2. Если detail не помог — посмотреть `GET /api/v5/trade/orders-algo-pending`

Ищем live algo orders по инструменту и ordType.

Если нашли соответствующий protection:

* обновляем child;
* ставим `ACTIVE`;
* сохраняем.

### Шаг 3. Если pending не помог — посмотреть `GET /api/v5/trade/orders-algo-history`

Ищем по:

* `algoId`, если есть;
* иначе по типу + инструменту + состояниям истории.

Если history показывает:

* `effective` -> child уже final, обычно `CLOSED`
* `canceled` -> `CLOSED`
* `order_failed` -> `FAILED`

И сразу сохраняем.

### Шаг 4. Если не нашли нигде

Тогда child остаётся unresolved.

Нельзя молча переводить его в `CLOSED` без доказательства.
Это либо retryable состояние, либо отдельная аномалия — зависит от общей политики проекта.

---

# 9. Кто должен сохранять AttachedAlgoOrder в БД

Каждое значимое изменение `AttachedAlgoOrder` должно быть сразу записано в БД.

Это обязательное правило.

То есть:

* создан child -> save
* изменился trigger / identifiers / status -> save
* child закрыт -> save
* child зафейлился -> save
* child подтверждён как active algo -> save

Нельзя держать lifecycle child только “в памяти до конца команды”.

---

# 10. Кто за что отвечает

## `RefreshOrderExecutor`

Отвечает только за обычный order flow и вызов child refresh.

Не должен:

* сам вести полный lifecycle attached child вручную;
* сам ходить в algo endpoints;
* сам решать, как подтверждать algo-level attached state.

## `RefreshAttachedAlgoOrderExecutor`

Отвечает только за sync attached child из order snapshot.

Не должен:

* сам читать algo endpoints;
* сам запускать kill-switch;
* сам выполнять validator ordinary order команды.

## `RefreshAlgoOrderExecutor`

Отвечает только за algo truth layer.

Не должен:

* обновлять parent ordinary order;
* создавать anomaly report ordinary order flow;
* заниматься ordinary order matching.

## `OrderStatusResolver`

Отвечает только за перевод external ordinary order status -> domain `Order.Status`.

Не сохраняет в БД.

Не ходит на биржу.

---

# 11. Какой порядок вызовов в orchestrator

Целевая последовательность такая:

```text
REFRESH_PENDING_ORDERS
  -> RefreshOrderExecutor
     -> RefreshAttachedAlgoOrderExecutor

REFRESH_ALGO_ORDERS
  -> RefreshAlgoOrderExecutor
```

То есть `RefreshAlgoOrderExecutor` — это не вложенный deep-call из order refresh.
Это следующий отдельный orchestration step.

Так меньше циклических зависимостей и чище ответственность.

---

# 12. Короткий итог

Нужно строить систему так:

1. `RefreshOrderExecutor` сопровождает ordinary orders.
2. Он же на каждом order snapshot вызывает `RefreshAttachedAlgoOrderExecutor`.
3. `RefreshAttachedAlgoOrderExecutor` ведёт child `AttachedAlgoOrder` как отдельную доменную сущность и сразу пишет её в
   БД.
4. Если child дошёл до состояния, где нужен algo truth layer, дальше его подхватывает `RefreshAlgoOrderExecutor`.
5. `RefreshAlgoOrderExecutor` подтверждает `ACTIVE / CLOSED / FAILED` через algo endpoints.
6. Нельзя закрывать attached child просто потому, что он пропал из order snapshot после финализации parent order.

Это и есть целевое разделение ordinary order flow, attached child flow и algo flow.
