# Задание для Codex — полностью переписать REFRESH_PENDING_ORDERS с нуля

## Цель

Нужно полностью переписать реализацию `REFRESH_PENDING_ORDERS`.

Текущая версия недостаточно надёжна, потому что она трактует исчезновение order из `orders-pending` слишком грубо.

Новая реализация должна строиться на таком принципе:

* `orders-pending` показывает только незавершённые order'ы;
* если order пропал из pending snapshot, это значит только, что он **больше не pending**;
* его финальное состояние нужно дополнительно восстановить через другие endpoint'ы биржи.

---

## Что нужно сделать архитектурно

### Главный flow

Нужна такая цепочка:

```text
ServiceCommandExecutor
  -> RefreshPendingOrdersExecutor
     -> TradeRuleValidator
        -> anomaly / kill-switch flow, если найдено нарушение
     -> sync pending orders
     -> resolve final state for orders missing from pending snapshot
```

Важно:

* `RefreshPendingOrdersExecutor` не должен сам запускать kill-switch;
* `TradeRuleValidator` остаётся единственной точкой запуска anomaly / kill-switch flow;
* восстановление финального состояния order — это часть order refresh логики.

---

## Что нужно переписать

## 1. Полностью пересобрать `RefreshPendingOrdersExecutor`

Новая сигнатура use-case должна быть такой:

```java
public void execute(Exchange exchange, Instrument instrument, Long dealId)
```

Executor должен:

1. получить pending snapshot с биржи;
2. получить live orders из БД;
3. передать оба набора в `TradeRuleValidator`;
4. если validator не выбросил исключение — выполнить обычный sync pending orders;
5. для локальных live orders, которых нет в pending snapshot, отдельно восстановить финальное состояние.

---

## 2. Не закрывать order вслепую

Из новой реализации нужно убрать логику вида:

```java
missing in
orders-pending ->

setStatus(CLOSED)
```

Так делать нельзя.

Если локальный live order не найден в pending snapshot, это означает только, что order больше не pending.

Нужно выяснить, что с ним реально стало.

---

## 3. Добавить отдельный resolver финального состояния order

Нужно выделить отдельный компонент, например:

* `OrderFinalStateResolver`
* или `OrderExternalStateResolver`

### Его ответственность

Для order, который пропал из pending snapshot, он должен попытаться восстановить реальное состояние через:

#### Шаг 1. `GET /trade/order`

Точечный detail запрос по:

* `ordId`, если есть `externalId`
* иначе по `clOrdId` / `internalId`, если это согласовано с моделью

#### Шаг 2. `GET /trade/orders-history`

Если detail не помог — искать в recent history.

#### Шаг 3. `GET /trade/orders-history-archive`

Если recent history не помог — искать в archive history.

### Результат resolver'а

Он должен вернуть либо:

* найденный `OrderExternalSnapshot` / эквивалентный финальный snapshot
* либо специальный результат “ничего не найдено”

---

## 4. Использовать реальные биржевые endpoint'ы

В новой реализации нужно опираться на следующие источники:

### Pending snapshot

* `GET /trade/orders-pending`

### Detail по конкретному order

* `GET /trade/order`

### История за последние 7 дней

* `GET /trade/orders-history`

### Архив за последние ~3 месяца

* `GET /trade/orders-history-archive`

То есть missing-from-pending order должен проверяться именно этой цепочкой.

---

## 5. Обычный sync pending orders

Для order'ов, которые есть во внешнем pending snapshot:

### Сценарий A. Order уже есть в БД

* найти локальный order;
* обновить его из pending snapshot;
* резолвить доменный статус;
* сохранить.

### Сценарий B. Order есть на бирже, но в БД его нет

* создать новый локальный `Order`;
* привязать к instrument;
* при необходимости привязать к `dealId`;
* обновить из snapshot;
* сохранить.

Если в проекте уже идёте в сторону factory — использовать factory, а не raw `new Order()`.

---

## 6. Восстановление финального состояния missing order

Для каждого локального live order, который не встретился в pending snapshot:

### Попробовать detail endpoint

Сначала обратиться к `GET /trade/order`.

Если нашли order:

* обновить локальный order;
* резолвить доменный статус;
* сохранить.

### Если detail не помог — recent history

Сопоставить по `externalId` или `clOrdId`.

Если нашли:

* обновить локальный order;
* резолвить финальный статус;
* сохранить.

### Если recent history не помог — archive history

Сопоставить по `externalId` или `clOrdId`.

Если нашли:

* обновить локальный order;
* резолвить финальный статус;
* сохранить.

### Только если вообще ничего не найдено

Разрешается fallback-поведение, но оно должно быть отдельным и осознанным правилом.

Не использовать автоматический `CLOSED` по умолчанию без попытки восстановить state.

---

## 7. Логика сопоставления order'ов

Нужно использовать устойчивое сопоставление.

Предпочтительный порядок:

* сначала `externalId`
* затем `internalId` / `clOrdId`

Не строить matching по косвенным полям.

---

## 8. Резолв доменного статуса

Нужно централизовать резолв доменного статуса из внешнего snapshot.

Это должен быть единый helper/service order-слоя, например:

```java
private Order.Status resolveOrderStatus(OrderExternalSnapshot snapshot)
```

Он должен одинаково применяться:

* для pending snapshot;
* для detail snapshot;
* для history snapshot.

Минимально нужно различать:

* `live` -> `PENDING`
* `partially_filled` -> `PARTIALLY_COMPLETED`
* `filled` -> `COMPLETED`
* `canceled` -> `CLOSED`

Если в модели есть более точные статусы / причины — использовать их.

---

## 9. Persistence слой

Нужны:

* чтение live orders по `instrumentId + live statuses`
* `save(...)`
* при необходимости поиск по `externalId`
* при необходимости поиск по `internalId`

Если нужных методов сейчас нет — добавить точечно.

---

## 10. Что не нужно делать

На этом этапе НЕ нужно:

* переписывать `KillSwitchService`
* трогать algo-order flow
* трогать balance flow
* тянуть fills в эту же задачу
* менять FSM

Нужно именно качественно переписать refresh flow обычных pending orders.

## Ожидаемый результат

После переписывания должно быть так:

* pending orders синкаются корректно;
* order, исчезнувший из pending snapshot, не закрывается вслепую;
* для missing order сначала восстанавливается реальное состояние через:

    * detail
    * recent history
    * archive history
* только после этого локальный order корректно финализируется.
