# Задание для Codex — реализовать команду REFRESH_PENDING_ORDERS

## Цель

Нужно реализовать следующую команду: `REFRESH_PENDING_ORDERS`.

Это обычная sync-команда по инструменту для обычных незавершённых ордеров (`Order`).

Команда должна:

* получить pending orders с биржи;
* прочитать живые локальные `Order` по инструменту;
* передать оба набора данных в `TradeRuleValidator`;
* если validator ничего не выявил — синхронизировать локальные orders;
* если validator выявил нарушение — прервать обычный sync через anomaly / kill-switch flow.

---

## Архитектурный ориентир

Правильная цепочка должна быть такой:

```text
Handler
  -> ServiceCommandExecutor
     -> RefreshPendingOrdersExecutor
        -> TradeRuleValidator
           -> AnomalyService
           -> KillSwitchService
              -> CancelOrderExecutor
              -> CancelAlgoOrderExecutor
              -> ClosePositionExecutor
              -> DealEmergencyFinalizer
        -> обычный sync orders, если validator ничего не выявил
```

Важно:

* executor сам не вызывает `KillSwitchService`;
* executor сам не создаёт `AnomalyReport`;
* обычный sync продолжается только если validator не выбросил исключение.

---

## Что нужно реализовать

## 1. Создать `RefreshPendingOrdersExecutor`

Нужен отдельный executor, например:

```java
public class RefreshPendingOrdersExecutor {

    public void execute(Exchange exchange, Instrument instrument, Long dealId) {
    }
}
```

Если в проекте принято другое имя пакета/класса — использовать проектный стиль, но use-case должен быть отдельным
executor'ом.

---

## 2. Обновить `ServiceCommandExecutor`

Команда:

```java
REFRESH_PENDING_ORDERS
```

должна вызывать:

```java
refreshPendingOrdersExecutor.execute(exchange, instrument, deal.getId())
```

Если сейчас вызывается старый `orderService.refreshPendingOrders(...)` — заменить на executor flow.

---

## 3. Получить внешний pending snapshot

Внутри executor нужно получить pending orders с биржи по инструменту через уже существующий client layer.

Источник правды — pending snapshot биржи.

Ожидаемый результат:

* `List<OrderExternalSnapshot>`

---

## 4. Прочитать внутренние live orders

Из БД нужно прочитать только живые обычные ордера по инструменту.

Нельзя читать всю историю по `instrumentId` без фильтра по статусам.

Если нужного метода ещё нет, добавить в repository/data service слой.

Минимально нужен метод уровня:

```java
List<Order> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)
```

Где `statuses` — это live-статусы `Order`.

---

## 5. Передать данные в `TradeRuleValidator`

Executor не должен сам определять аномалию.

Он должен вызвать validator и передать туда:

* `exchange`
* `instrument`
* `dealId`
* внешние pending orders
* внутренние live orders

Если validator выбрасывает `TradeRuleViolationException`, executor не продолжает обычный sync.

---

## 6. Реализовать обычный sync orders

Если validator не выбросил исключение, executor должен синхронизировать локальные `Order` с биржевым pending snapshot.

Нужно поддержать базовые сценарии.

### Сценарий A. Order есть и на бирже, и в БД

Нужно:

* найти соответствующий локальный order;
* обновить его из snapshot;
* резолвить доменный статус;
* сохранить.

### Сценарий B. Order есть на бирже, но в БД его нет

Нужно:

* создать новый локальный `Order`;
* привязать его к инструменту;
* при необходимости привязать к `dealId`;
* обновить поля из snapshot;
* сохранить.

### Сценарий C. Order отсутствует на бирже, но локально ещё живой

Нужно:

* перевести локальный order в финальный/закрытый статус;
* при необходимости проставить причину;
* сохранить.

### Сценарий D. Нет ни внешних pending orders, ни внутренних live orders

Ничего не делать.

---

## 7. Логика сопоставления orders

Для sync нужно устойчивое сопоставление внешних и внутренних orders.

Предпочтительный порядок:

* по `externalId`
* если внешнего id нет — по `internalId` / `clOrdId`, если это уже принято в проекте

Не строить сопоставление по косвенным данным.

Если нужен helper-метод — добавить его в executor или в отдельный sync helper.

---

## 8. Резолв статусов

Нужно явно определить, кто резолвит доменный статус `Order` из внешнего snapshot.

Это должен делать order refresh layer, а не FSM.

То есть в executor допустим helper-метод вида:

```java
private Order.Status resolveOrderStatus(OrderExternalSnapshot snapshot)
```

Если в проекте уже есть/планируется отдельный order sync service — можно делегировать туда.

---

## 9. Создание новых orders

Если order есть на бирже, а в БД нет, создание лучше делать не raw `new Order()` в executor, а через factory / helper,
если в проекте уже идёте в эту сторону.

То есть:

* либо `OrderFactory.createFromPendingSnapshot(...)`
* либо создать пустой `Order` через factory и затем обновить его из snapshot

Если order factory ещё нет, допустим минимальный локальный вариант, но без лишнего мусора.

---

## 10. Mapping слой

Нужно использовать текущий mapper-стиль проекта.

Если уже есть `OrderMapper` с update method из external snapshot в domain model, использовать его.

Если не хватает отдельных методов для pending refresh — доработать mapper минимально необходимым образом.

Executor не должен руками раскладывать десятки полей order snapshot, если для этого уже есть mapper.

---

## 11. Persistence слой

Нужны:

* чтение live orders по `instrumentId + statuses`
* при необходимости поиск order по `externalId`
* при необходимости поиск order по `internalId`
* обычный `save(...)`

Если каких-то методов сейчас нет, добавить их точечно.

---

## 12. Что не нужно делать

На этом этапе НЕ нужно:

* переписывать `TradeRuleValidator`
* переписывать `KillSwitchService`
* трогать algo-orders
* трогать balance flow
* тащить в `REFRESH_PENDING_ORDERS` историю fills
* тащить историю orders archive глубже, чем нужно для pending sync
* менять FSM

Это именно команда refresh обычных pending orders.

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## Что вернуть

Нужно вернуть:

1. `RefreshPendingOrdersExecutor`
2. обновлённый `ServiceCommandExecutor`
3. при необходимости — repository/data service методы чтения live orders
4. при необходимости — точечные доработки `OrderMapper`
5. при необходимости — factory/helper для создания нового `Order` из snapshot

Без лишнего рефакторинга unrelated-кода.

---

## Ожидаемый результат

После реализации должно быть так:

* `ServiceCommandExecutor` вызывает `RefreshPendingOrdersExecutor`
* executor читает pending orders с биржи и live orders из БД
* executor передаёт оба набора в `TradeRuleValidator`
* если validator ничего не выявил — локальные `Order` синхронизируются с pending snapshot биржи
* если validator находит нарушение — anomaly / kill-switch flow прерывает обычный sync
