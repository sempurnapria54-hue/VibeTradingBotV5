# Задание для Codex — реализовать команду REFRESH_PENDING_ORDERS

## Цель задачи

Нужно реализовать `REFRESH_PENDING_ORDERS` как отдельную сервисную команду ordinary order truth layer.

Эта команда должна сопровождать:

* ordinary `Order`
* `AttachedAlgoOrder` только на стадии child-sync из order snapshot

И не должна выполнять algo-truth refresh.

---

# 1. Какие классы должны получиться

Минимально ожидаются:

1. `RefreshOrderExecutor`
2. `OrderStatusResolver`
3. `RefreshAttachedAlgoOrderExecutor`
4. `TradeRuleValidator.validateRefreshPendingOrders(...)`
5. при необходимости `OrderRefreshService` или `OrderSyncService`
6. при необходимости `AttachedAlgoOrderDataService` / repository методы
7. точечные изменения `ServiceCommandExecutor`

Если в проекте уже есть похожие классы — доработать существующие, а не плодить дубли.

---

# 2. Какой нейминг использовать

Использовать именно такой нейминг:

## Классы

* `RefreshOrderExecutor`
* `OrderStatusResolver`
* `RefreshAttachedAlgoOrderExecutor`

## Методы

* `execute(...)` — для executors
* `resolveStatus(...)` — для `OrderStatusResolver`
* `validateRefreshPendingOrders(...)` — для validator метода
* `refreshAttachedAlgoOrders(...)` — допустимое имя публичного метода child executor

## Sync слой

Выбрать **одно** имя и использовать последовательно:

* либо `OrderRefreshService`
* либо `OrderSyncService`

Не использовать оба названия одновременно.

---

# 3. Зоны ответственности по классам

## 3.1. `RefreshOrderExecutor`

### Что должен делать

1. вызвать `GET /api/v5/trade/orders-pending`
2. прочитать live local `Order` по `instrumentId + LIVE_ORDER_STATUSES`
3. вызвать `TradeRuleValidator.validateRefreshPendingOrders(...)`
4. если validator не выбросил исключение:

    * обновить matched ordinary orders
    * восстановить final state missing ordinary orders через `trade/order -> orders-history -> orders-history-archive`
    * на каждом полученном order snapshot вызвать `RefreshAttachedAlgoOrderExecutor`

### Что НЕ должен делать

* не ходить в algo endpoints
* не запускать kill-switch напрямую
* не создавать anomaly report напрямую
* не содержать полный child lifecycle attached protection внутри себя
* не резолвить order status switch/if вручную в нескольких местах

---

## 3.2. `OrderStatusResolver`

### Что должен делать

Переводить `OrderExternalSnapshot` в доменный `Order.Status`.

### Ожидаемый метод

Например:

```java
Order.Status resolveStatus(OrderExternalSnapshot snapshot)
```

Если нужно, можно добавить source context, но без побочных эффектов.

### Что НЕ должен делать

* не сохранять order
* не ходить на биржу
* не вызывать validator
* не содержать IO

---

## 3.3. `RefreshAttachedAlgoOrderExecutor`

### Что должен делать

Это child-sync слой attached protection из order snapshot.

Он должен:

1. принять `Order` и `OrderExternalSnapshot`
2. прочитать existing `AttachedAlgoOrder` по `orderId`
3. извлечь attached data из order snapshot
4. сопоставить child entities
5. создать/обновить/закрыть/зафейлить `AttachedAlgoOrder`
6. каждое изменение сразу сохранять в БД

### Что НЕ должен делать

* не ходить в algo endpoints
* не запускать validator ordinary order команды
* не запускать kill-switch
* не обновлять parent `Order`

### Важное правило

`RefreshAttachedAlgoOrderExecutor` — это не отдельная FSM-команда.
Он вызывается только из `RefreshOrderExecutor`.

---

## 3.4. `TradeRuleValidator`

### Что должен делать

Иметь отдельный метод:

```java
validateRefreshPendingOrders(exchange,
                             instrument,
                             dealId,
                             externalPendingOrders,
                             internalLiveOrders)
```

### Что обязан проверить

#### Правило A. Нет дублей во внешнем pending snapshot

Проверить отсутствие дублей по:

* `ordId`
* `clOrdId`

#### Правило B. Нет дублей во внутреннем live наборе

Проверить отсутствие дублей по:

* `externalId`
* `internalId`

#### Правило C. Каждый внешний pending order однозначно сопоставляется с одним local live order

Порядок matching:

1. `externalId`
2. `internalId`

Если внешнему pending order не найден local live order, это anomaly.

#### Правило D. Все local live orders принадлежат текущему инструменту

### Что делает validator при нарушении

1. создаёт initial `AnomalyReport`
2. пишет `internal_before` / `external_before`
3. при необходимости через `InstrumentService` блокирует инструмент
4. вызывает `KillSwitchService`
5. получает after snapshots
6. обновляет `AnomalyReport`
7. выбрасывает `TradeRuleViolationException`

### Что НЕ делает validator

* не обновляет order в happy path
* не сопровождает attached child lifecycle
* не ходит в algo endpoints

---

# 4. Что именно должно происходить в `RefreshOrderExecutor`

## Шаг 1

Получить external pending snapshot:

* `clientService.getActiveOrdersByInstrument(instrument)`

Это вызов `GET /api/v5/trade/orders-pending` по instrument.

## Шаг 2

Получить internal live orders:

* `orderDataService.findAllByInstrumentIdAndStatuses(instrument.getId(), LIVE_ORDER_STATUSES)`

## Шаг 3

Вызвать validator:

* `tradeRuleValidator.validateRefreshPendingOrders(...)`

Если validator выбросил исключение — normal flow прекращается.

## Шаг 4

Для каждого matched external pending order:

* применить snapshot к local `Order`
* статус получить через `OrderStatusResolver`
* сохранить order
* вызвать `RefreshAttachedAlgoOrderExecutor`

## Шаг 5

Для каждого local live order, отсутствующего в pending snapshot:

### 5.1. Вызвать `GET /trade/order`

Искать по `ordId`, иначе по `clOrdId`.

### 5.2. Если detail не помог — `GET /trade/orders-history`

### 5.3. Если history не помог — `GET /trade/orders-history-archive`

### 5.4. Если order найден

* применить snapshot
* резолвить status через `OrderStatusResolver`
* сохранить order
* вызвать `RefreshAttachedAlgoOrderExecutor`

### 5.5. Если order не найден нигде

Не делать silent `CLOSED`.
Это unsafe state.

Либо anomaly, либо отдельное recovery exception — по принятой общей политике проекта.

---

# 5. Что должно происходить в `RefreshAttachedAlgoOrderExecutor`

## 5.1. Источник правды

Только order snapshot.

Он должен использовать:

* `attachAlgoClOrdId`
* top-level `tp/sl` fields
* `attachAlgoOrds[]`
* `attachAlgoId`
* `failCode`
* `failReason`

## 5.2. Matching rules

Порядок matching:

1. `externalAttachedId`
2. `externalId`
3. `internalId`
4. fallback по типу, если для order допустим только один child такого типа

## 5.3. Что должен уметь

* создавать новый `AttachedAlgoOrder`
* обновлять существующий
* ставить `ATTACHED`
* ставить `FAILED`, если snapshot явно показывает failure
* ставить `CLOSED` только если есть достаточное доказательство

## 5.4. Что НЕЛЬЗЯ делать

Нельзя закрывать child только потому, что он пропал из позднего order snapshot после fill родительского order.

В таком случае child должен быть сохранён и потом подхвачен командой `REFRESH_ALGO_ORDERS`.

## 5.5. Persistence правило

Каждое изменение `AttachedAlgoOrder` сразу писать в БД.

---

# 6. Persistence требования

## 6.1. Для ordinary orders

Нужны методы уровня:

```java
List<Order> findAllByInstrumentIdAndStatuses(Long instrumentId, Set<String> statuses)

Order save(Order order)
```

## 6.2. Для attached children

Нужны методы уровня:

```java
List<AttachedAlgoOrder> findAllByOrderId(Long orderId)

AttachedAlgoOrder save(AttachedAlgoOrder attachedAlgoOrder)
```

Если проектный стиль требует repository + data service — сохранить этот стиль.

---

# 7. Что нужно сделать в `ServiceCommandExecutor`

Команда должна быть маршрутизирована как:

```java
REFRESH_PENDING_ORDERS ->refreshOrderExecutor.

execute(exchange, instrument, dealId)
```

Не звать `RefreshAttachedAlgoOrderExecutor` напрямую из `ServiceCommandExecutor`.

---

# 8. Что нельзя делать в этой задаче

Нельзя:

* тащить algo endpoints в `RefreshAttachedAlgoOrderExecutor`
* реализовывать `REFRESH_ALGO_ORDERS` внутри этой задачи
* молча создавать local order для неизвестного внешнего pending order
* молча закрывать missing-from-pending order
* молча закрывать attached child после исчезновения из позднего order snapshot
* делать один giant-class вместо выделенных границ

---

# 9. Что вернуть по задаче

Нужно вернуть:

1. `RefreshOrderExecutor`
2. `OrderStatusResolver`
3. `RefreshAttachedAlgoOrderExecutor`
4. `TradeRuleValidator.validateRefreshPendingOrders(...)`
5. при необходимости — `OrderRefreshService` или `OrderSyncService`
6. при необходимости — `AttachedAlgoOrderDataService` / repository methods
7. точечные правки `ServiceCommandExecutor`
8. при необходимости — точечные изменения мапперов

Без лишнего рефакторинга unrelated-кода.

---

# 10. Ожидаемый результат

После реализации должно быть так:

* ordinary order truth layer работает отдельно
* attached protection child-sync происходит внутри ordinary order команды
* любые изменения `AttachedAlgoOrder` сразу пишутся в БД
* missing-from-pending order не закрывается вслепую
* attached child не закрывается агрессивно без доказательства
* команда не лезет в algo endpoints
