# Задание для Codex — реализовать команду REFRESH_BALANCE

## Цель

Нужно реализовать следующую команду: `REFRESH_BALANCE`.

Это обычная sync-команда уровня биржи.

Её задача:

* получить актуальный balance snapshot с биржи;
* привести локальные `Balance` записи в актуальное состояние;
* сохранить их в БД.

На текущем этапе сюда **не** нужно притягивать:

* `TradeRuleValidator`
* `AnomalyService`
* `KillSwitchService`

---

## Что уже зафиксировано архитектурно

### 1. Команда должна выполняться через отдельный executor

Нужен отдельный класс:

* `RefreshBalanceExecutor`

Фасадный `BalanceService` может существовать как обёртка/точка входа, но use-case команды должен жить именно в executor.

### 2. Уровень команды — биржа

Баланс хранится не по инструменту и не по сделке.

Ключ хранения:

* `exchangeId`
* `currency`

### 3. Команда — это обычный snapshot sync

Никакого anomaly flow на текущем этапе сюда не нужно добавлять.

---

## Что нужно реализовать

## 1. `RefreshBalanceExecutor`

Создать отдельный executor:

```java
public class RefreshBalanceExecutor {

    public void execute(Exchange exchange) {
    }
}
```

Если у тебя в проекте принято возвращать что-то ещё — допустимо, но базовый use-case должен быть именно таким.

---

## 2. Вызов из `ServiceCommandExecutor`

Обновить `ServiceCommandExecutor`, чтобы команда:

```java
REFRESH_BALANCE
```

вызывала:

```java
refreshBalanceExecutor.execute(exchange)
```

А не старый direct-вызов в фасадный сервис, если он ещё остался.

---

## 3. Получение внешнего snapshot

Внутри `RefreshBalanceExecutor` нужно получить актуальный внешний snapshot:

```java
BalanceContainerExternalSnapshot externalSnapshot = clientService.getBalanceContainer(exchange)
```

Использовать уже существующий client layer.

---

## 4. Разложение snapshot по валютам

Если `BalanceContainerExternalSnapshot` содержит набор балансов по валютам, executor должен пройтись по каждой валюте
отдельно.

Рабочая единица обновления — это один баланс по одной валюте.

---

## 5. Upsert по `exchangeId + currency`

Для каждой валюты нужно:

### Сценарий A. Запись уже существует

Найти существующую `Balance` запись по:

* `exchangeId`
* `currency`

Затем обновить её через mapper / доменный update.

### Сценарий B. Записи нет

Создать новую `Balance` запись:

* привязать к `exchangeId`
* записать `currency`
* применить внешний snapshot
* сохранить

Важно:

* не создавать дубликаты;
* повторный запуск должен быть идемпотентным.

---

## 6. Какие слои должны участвовать

Ожидаемая структура:

### Executor

* `RefreshBalanceExecutor`

### Фасад / доменный сервис

* `BalanceService` — если нужен как удобный слой, можно использовать

### Persistence

* `BalanceDataService`
* `BalanceRepository`

### Mapping

* `BalanceMapper`

---

## 7. Что должно быть в persistence слое

Если нужных методов ещё нет, добавить.

Минимально нужен метод чтения существующей записи по:

* `exchangeId`
* `currency`

Например на repository/data service уровне:

```java
Optional<Balance> findByExchangeIdAndCurrency(Long exchangeId, String currency)
```

Если в проекте уже есть аналогичный метод — использовать его.

Также нужен обычный `save(...)`.

---

## 8. Что должно быть в модели `Balance`

Если balance-модель ещё не доведена до конца, её нужно привести к уже согласованной форме.

Минимально ожидаются поля:

* `id`
* `exchangeId`
* `currency`
* `available`
* `frozen`
* `total`
* `externalUpdatedAt`
* audit поля

Если чего-то из этого ещё нет — добавить по примеру остальных сущностей проекта.

Важно:

* баланс должен быть привязан к бирже;
* уникальность должна держаться на `exchangeId + currency`.

---

## 9. Что должно быть в mapping

Если уже есть `BalanceMapper`, его нужно использовать.

Предпочтительный стиль:

* не раскладывать все поля вручную в executor;
* использовать mapper update method, чтобы обновлять доменную модель из external snapshot.

Если mapper ещё не покрывает нужный сценарий — доработать его минимально необходимым образом.

---

## 10. Как обрабатывать пустой snapshot

Если внешний snapshot пустой или в нём нет валют:

* не падать без необходимости;
* корректно завершить команду;
* при необходимости залогировать отсутствие данных.

Не нужно в этой задаче придумывать anomaly flow для пустого баланса.

---

## 11. Что не нужно делать

На этом этапе НЕ нужно:

* добавлять `TradeRuleValidator`
* добавлять `KillSwitchService`
* вводить `AnomalyReport`
* привязывать balance к `instrumentId`
* делать историю изменений баланса
* переписывать FSM под баланс

Это простой snapshot-sync use-case.

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## Что вернуть

Нужно вернуть:

1. `RefreshBalanceExecutor`
2. обновлённый `ServiceCommandExecutor`
3. при необходимости — `BalanceDataService` / `BalanceRepository` методы
4. при необходимости — доработки `BalanceMapper`
5. при необходимости — минимальные правки `BalanceService`

Без лишнего рефакторинга unrelated-кода.

---

## Ожидаемый результат

После реализации должно быть так:

* `ServiceCommandExecutor` вызывает `RefreshBalanceExecutor`
* executor получает внешний balance snapshot по бирже
* по каждой валюте находит или создаёт локальную `Balance` запись
* обновляет запись через mapper / доменную модель
* сохраняет её в БД
* повторный запуск не создаёт дубликаты

---

На всякий случай смотри документацию в `docs/context` и `docs/models/domain`.
