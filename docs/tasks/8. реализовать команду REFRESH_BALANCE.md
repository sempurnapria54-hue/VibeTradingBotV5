# Задание для Codex — реализовать REFRESH_BALANCE с контейнером баланса

## Цель

Нужно реализовать команду `REFRESH_BALANCE` с учётом того, что баланс приходит с биржи **не как один плоский объект**, а
как **контейнер snapshot аккаунта**, внутри которого лежат:

* агрегированные значения по аккаунту;
* список балансов по валютам.

Сейчас недостаточно синхронизировать только `Balance` по валютам.

Нужно **прокинуть контейнер во все нужные слои** и синхронизировать:

1. верхний snapshot аккаунта по бирже;
2. вложенные balances по валютам.

---

## Что видно по текущим моделям

Уже есть внешние snapshot модели:

### `BalanceContainerExternalSnapshot`

Содержит:

* `exchangeId`
* `totalEquity`
* `unrealizedProfit`
* `List<BalanceExternalSnapshot>` fileciteturn24file1

### `BalanceExternalSnapshot`

Содержит per-currency snapshot:

* `currency`
* `cashBalance`
* `availableBalance`
* `equity`
* `frozenBalance`
* `unrealizedProfit` fileciteturn24file0

### `Balance`

Сейчас хранит только per-currency доменную модель:

* `exchangeId`
* `currency`
* `available`
* `frozen`
* `total`
* `externalUpdatedAt` fileciteturn24file2

### Главный вывод

Сейчас в домене и persistence не хватает **контейнера баланса**.

Именно его и нужно добавить и прокинуть через слои.

---

## Что нужно реализовать концептуально

Нужно поддержать две связанные сущности:

### 1. `BalanceContainer`

Это snapshot аккаунта по бирже.

Он должен хранить агрегированные значения верхнего уровня, например:

* `exchangeId`
* `totalEquity`
* `unrealizedProfit`
* audit поля
* при необходимости `externalUpdatedAt`

### 2. `Balance`

Это snapshot по одной валюте внутри контейнера.

Он должен остаться отдельной сущностью, но теперь должен логически жить как часть контейнера snapshot аккаунта.

---

## Важное архитектурное правило

`REFRESH_BALANCE` должен обновлять **контейнер и вложенные balances вместе**.

То есть flow такой:

* получить `BalanceContainerExternalSnapshot` с биржи;
* найти или создать внутренний `BalanceContainer` по `exchangeId`;
* обновить поля контейнера;
* пройтись по `balanceExternalSnapshots`;
* найти или создать внутренние `Balance` по `exchangeId + currency`;
* обновить валютные balances;
* сохранить всё согласованно.

---

## Что нужно добавить

## 1. Доменная модель контейнера

Добавить новую доменную модель, например:

```java
public class BalanceContainer extends Auditable {

    private Long id;
    private Long exchangeId;
    private BigDecimal totalEquity;
    private BigDecimal unrealizedProfit;
    private OffsetDateTime externalUpdatedAt;
    private List<Balance> balances;
}
```

Если в проекте принят другой стиль именования — использовать его, но идея должна быть именно такая.

### Важно

* контейнер принадлежит бирже;
* один контейнер = один актуальный snapshot аккаунта по бирже;
* balances по валютам являются его содержимым.

---

## 2. Persistence слой для контейнера

Нужно добавить persistence-модель контейнера, repository и data service.

Минимально нужно:

* `BalanceContainerEntity`
* `BalanceContainerRepository`
* `BalanceContainerDataService`

### Ключевая уникальность

Контейнер должен однозначно находиться по:

* `exchangeId`

То есть логика такая:

* одна биржа → один актуальный контейнер snapshot

Если в проекте требуется явный уникальный индекс — заложить это.

---

## 3. Связь `Balance` с контейнером

Сейчас `Balance` знает только `exchangeId`.

Нужно решить и реализовать связь с контейнером.

Предпочтительный вариант:

* `Balance` получает ссылку на контейнер, например `balanceContainerId`
* при этом ключ идемпотентности по-прежнему может оставаться `exchangeId + currency`

То есть контейнер становится родителем snapshot, а `Balance` — его дочерней записью по валюте.

### Важно

Не ломать существующую бизнес-логику, если где-то уже используется `exchangeId + currency`.

Но контейнер должен появиться в модели явно, а не только как мысль.

---

## 4. Mapping слой

Нужно добавить и/или доработать mapper'ы:

### Для контейнера

* внешний `BalanceContainerExternalSnapshot` → доменная модель `BalanceContainer`
* update existing container from external snapshot

### Для валютных balances

* внешний `BalanceExternalSnapshot` → доменная модель `Balance`
* update existing balance from external snapshot

### Важно

Не раскладывать всё вручную в executor, если можно сделать через mapper update methods.

---

## 5. Executor команды

Нужен отдельный executor:

* `RefreshBalanceExecutor`

### Его задача

1. получить `BalanceContainerExternalSnapshot` через client service;
2. найти или создать внутренний `BalanceContainer` по `exchangeId`;
3. обновить контейнер из external snapshot;
4. синхронизировать вложенные `Balance` по валютам;
5. сохранить контейнер и balances.

---

## 6. Обновить `ServiceCommandExecutor`

Команда:

```java
REFRESH_BALANCE
```

должна вызывать:

```java
refreshBalanceExecutor.execute(exchange)
```

Если сейчас ещё идёт вызов старого `balanceService.refreshBalance(exchange)` — заменить на executor flow.

---

## 7. Как искать контейнер

Нужен метод чтения контейнера по `exchangeId`, например:

```java
Optional<BalanceContainer> findByExchangeId(Long exchangeId)
```

Если контейнера нет:

* создать новый;
* заполнить `exchangeId`;
* применить snapshot;
* сохранить.

---

## 8. Как искать валютный balance

Нужен метод чтения balance по:

* `exchangeId`
* `currency`

Например:

```java
Optional<Balance> findByExchangeIdAndCurrency(Long exchangeId, String currency)
```

Если записи нет:

* создать новый `Balance`;
* привязать к `exchangeId`;
* привязать к контейнеру;
* применить snapshot;
* сохранить.

---

## 9. Какие поля обновлять

### В контейнере

Минимально:

* `totalEquity`
* `unrealizedProfit`
* `externalUpdatedAt` (если это поле будет в модели)

### В balance по валюте

Минимально:

* `available`
* `frozen`
* `total`
* при необходимости `equity`
* при необходимости `unrealizedProfit`
* `externalUpdatedAt`

### Важно

Посмотри на текущие snapshot модели и не потеряй поля, которые уже есть во внешнем слепке.

---

## 10. Как трактовать `BalanceContainerExternalSnapshot`

Это главный внешний snapshot аккаунта.

То есть в коде не надо “обходить контейнер как будто его нет”.

Нужно относиться к нему как к полноценной модели:

* контейнер обновляется сам;
* его дочерние balances обновляются отдельно.

---

## 11. Что не нужно делать

На этом этапе НЕ нужно:

* добавлять `TradeRuleValidator`
* добавлять `KillSwitchService`
* добавлять `AnomalyReport`
* делать историю изменений баланса
* привязывать баланс к `instrumentId`
* менять FSM под баланс

Это по-прежнему обычная snapshot-sync команда, просто теперь с полноценным контейнером.

---

## 12. Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## 13. Что вернуть

Нужно вернуть:

1. доменную модель `BalanceContainer`
2. persistence-модель / repository / data service для контейнера
3. обновлённую модель `Balance` при необходимости связи с контейнером
4. mapper для контейнера
5. доработанный mapper для `Balance`
6. `RefreshBalanceExecutor`
7. обновлённый `ServiceCommandExecutor`
8. при необходимости — точечные правки `BalanceService`

Без лишнего рефакторинга unrelated-кода.

---

## Ожидаемый результат

После реализации должно быть так:

* команда `REFRESH_BALANCE` работает через `RefreshBalanceExecutor`
* внешний `BalanceContainerExternalSnapshot` больше не игнорируется
* в домене и persistence есть полноценный `BalanceContainer`
* контейнер обновляется по `exchangeId`
* вложенные `Balance` обновляются по `exchangeId + currency`
* контейнер и balances сохраняются согласованно
* повторный запуск не создаёт дубликатов
