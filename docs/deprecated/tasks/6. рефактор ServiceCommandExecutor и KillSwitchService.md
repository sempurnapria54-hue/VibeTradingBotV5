# Задание для Codex — рефактор ServiceCommandExecutor и KillSwitchService

## Цель

Нужно привести код к уже согласованной архитектуре.

Сейчас есть несколько проблем:

* `ServiceCommandExecutor` всё ещё вызывает фасадные сервисы старого типа вместо отдельных refresh-executors;
* `KillSwitchService` частично уже переведён на executor-модель, но всё ещё содержит лишнюю и неправильно размещённую
  логику;
* блокировка инструмента делается не через `InstrumentService`, а напрямую через data service;
* чтение внешних algo-ордеров находится в `KillSwitchService`, хотя это не его ответственность;
* report snapshot в `KillSwitchService` слишком грубый и тащит слишком много данных без чёткой структуры.

Нужно это исправить точечно, без лишнего рефакторинга всего проекта.

---

## Главный архитектурный ориентир

Правильная цепочка для `REFRESH_POSITIONS` должна быть такой:

```text
Handler
  -> ServiceCommandExecutor
     -> RefreshPositionExecutor
        -> TradeRuleValidator
           -> AnomalyService
           -> KillSwitchService
              -> ClosePositionExecutor
              -> CancelOrderExecutor
              -> CancelAlgoOrderExecutor
              -> DealEmergencyFinalizer
```

Важно:

* `ServiceCommandExecutor` должен вызывать **executor**, а не фасадный `PositionService`;
* `RefreshPositionExecutor` должен вызывать `TradeRuleValidator`;
* `TradeRuleValidator` должен вызывать `KillSwitchService`;
* `KillSwitchService` должен вызывать аварийные executors;
* `KillSwitchService` не должен вызывать refresh-executors и не должен содержать лишнюю snapshot-логику, не относящуюся
  к его роли.

---

## Что нужно сделать

## 1. Перевести `ServiceCommandExecutor` на executor-модель

### Сейчас плохо

В `ServiceCommandExecutor` всё ещё вызывается старый фасадный сервис:

```java
case REFRESH_POSITIONS ->positionService.

refreshPositions(exchange, instrument, deal);
```

Это не соответствует согласованной архитектуре.

### Нужно

`ServiceCommandExecutor` должен зависеть от отдельных executors для refresh-команд.

Минимально для текущего этапа:

* `RefreshPositionExecutor`
* при необходимости позже аналогично:

    * `RefreshBalanceExecutor`
    * `RefreshPendingOrdersExecutor`

### Для текущей задачи обязательно

Нужно заменить выполнение команды `REFRESH_POSITIONS` на вызов:

```java
refreshPositionExecutor.execute(exchange, instrument, deal.getId())
```

или аналогичную сигнатуру, если в проекте уже есть другой согласованный контракт.

### Важно

Не передавать весь `Deal`, если нужен только `dealId`.

---

## 2. Убрать блокировку инструмента из data-service стиля

### Сейчас плохо

Сейчас в `KillSwitchService` есть логика вида:

```java
private void blockInstrument(Instrument instrument, String reasonCode)
```

и внутри прямой вызов через `InstrumentDataService`.

Это не соответствует договорённости.

### Нужно

Блокировка инструмента должна идти через `InstrumentService`.

То есть `KillSwitchService` не должен напрямую сохранять инструмент через data service.

### Что сделать

* убрать прямую зависимость `KillSwitchService` от `InstrumentDataService` для блокировки;
* внедрить `InstrumentService`;
* через него перевести инструмент в нужный статус;
* если в `InstrumentService` ещё нет подходящего метода — добавить минимально необходимый метод, без лишнего
  рефакторинга.

### Важно

Блокировка инструмента должна оставаться частью kill-switch flow, но не через data service напрямую.

---

## 3. Убрать из `KillSwitchService` логику чтения внешних algo-ордеров

### Сейчас плохо

В `KillSwitchService` есть метод:

```java
private List<AlgoOrderExternalSnapshot> getExternalAlgoOrders(ClientService clientService,
                                                              Instrument instrument,
                                                              List<AlgoOrder> internalAlgoOrders)
```

Это лишняя ответственность для kill-switch orchestration сервиса.

Ты не должен оставлять в `KillSwitchService` такую логику поиска внешних algo-ордеров по типам.

### Нужно

Эту ответственность надо вынести.

Подходящий вариант для текущего этапа:

* вынести в отдельный helper / reader / resolver компонент, связанный со snapshot чтением;
* либо в отдельный сервис, который отвечает за сбор внешнего snapshot по инструменту;
* либо в компонент уровня `StateSnapshotReader`, если ты захочешь минимальный структурный рефакторинг.

### Важно

`KillSwitchService` должен вызывать уже готовый reader/collector, а не сам собирать внешний algo snapshot по типам.

---

## 4. Разделить snapshot для действий и snapshot для отчёта

### Сейчас проблема

Даже если `readActionState(...)` уже читает живые сущности по статусам, `readReportSnapshot(...)` всё ещё в слишком
сыром виде.

Кроме того, внутри `KillSwitchService` не должно быть ощущения, что один и тот же snapshot используется и для действий,
и для отчёта без различия смыслов.

### Нужно

Явно разделить:

#### `readActionState(...)`

Используется для аварийных действий.

Читает только **живые** сущности.

#### `readReportSnapshot(...)`

Используется для полного after-снимка по инструменту.

Должен строить **релевантный отчётный snapshot**, а не бездумно тянуть всё подряд без структуры.

### Важно

Для action-state нельзя читать всё по `instrumentId` без фильтра по статусам.

Для report snapshot пока допустимо использовать более широкий срез, но:

* он должен быть осмысленным;
* не тащить бесконечную историю;
* лучше разделять данные на `active` и `relatedInactive`, если это уже можно аккуратно сделать.

Если это пока слишком много для одного шага, то хотя бы:

* оставить action-state строго по live statuses;
* а report snapshot вынести в отдельный reader/helper, чтобы `KillSwitchService` не содержал эту логику сам.

---

## 5. Оставить `KillSwitchService` только orchestrator'ом

### Должно быть

`KillSwitchService` должен:

* собрать action-state;
* заблокировать инструмент через `InstrumentService`;
* вызвать:

    * `CancelOrderExecutor`
    * `CancelAlgoOrderExecutor`
    * `ClosePositionExecutor`
    * `DealEmergencyFinalizer`
* собрать after-state;
* проверить успех;
* вернуть `KillSwitchResult`.

### Не должно быть

В `KillSwitchService` не должно остаться:

* ручного изменения статусов сущностей;
* прямой блокировки инструмента через data service;
* ручной логики поиска внешних algo-ордеров по типам;
* вызова фасадного `PositionService` / refresh-сервисов.

---

## 6. Проверить циклические зависимости

После рефакторинга не должно появиться циклов типа:

```text
RefreshPositionExecutor -> TradeRuleValidator -> KillSwitchService -> PositionService -> RefreshPositionExecutor
```

### Нужно

Проверить, что:

* `KillSwitchService` не зависит от `RefreshPositionExecutor`
* `KillSwitchService` не зависит от refresh-фасадов, если они ведут обратно в validator-flow
* аварийные executors не ведут обратно в `TradeRuleValidator`

Если для этого нужно чуть скорректировать зависимости — сделать минимально необходимую правку.

---

## 7. Репозиторные / data service методы

Если для action-state сейчас не хватает методов чтения только по живым статусам — добавить их.

Минимально нужно уметь читать по:

* `instrumentId + live statuses` для `Position`
* `instrumentId + live statuses` для `Order`
* `instrumentId + live statuses` для `AlgoOrder`
* `instrumentId + non-terminal statuses` для `Deal`

Если эти методы уже есть — использовать их.

Не использовать для action-state чтение вида:

```java
findByInstrumentId(...)
```

без фильтра по статусам.

---

## 8. Что вернуть

Нужно вернуть:

1. обновлённый `ServiceCommandExecutor`
2. обновлённый `KillSwitchService`
3. новый/вынесенный reader/helper для внешних algo-ордеров и/или snapshot чтения
4. при необходимости — минимальные изменения в `InstrumentService`
5. при необходимости — минимальные изменения в repository/data service методах
6. при необходимости — точечные изменения в зависимостях executors

Без лишнего рефакторинга unrelated-кода.

---

## Что не нужно делать

На этом этапе НЕ нужно:

* переписывать весь state machine слой;
* менять `TradeRuleValidator` полностью;
* делать большой рефактор `AnomalyReport`;
* перепроектировать весь snapshot формат до идеала, если можно ограничиться выносом ответственности и корректным
  action-state.

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## Ожидаемый результат

После выполнения задачи должно быть так:

* `ServiceCommandExecutor` вызывает `RefreshPositionExecutor`, а не старый `PositionService.refreshPositions(...)`;
* `KillSwitchService` блокирует инструмент через `InstrumentService`;
* `KillSwitchService` не содержит в себе ручной логики поиска внешних algo-ордеров;
* `KillSwitchService` остаётся orchestrator'ом аварийного сценария;
* action-state читается только по живым статусам;
* циклические зависимости не появляются.
