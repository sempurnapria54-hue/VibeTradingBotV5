# AnomalyReport

- **Статус:** актуальная спецификация.
- **Источник:** мигрирован из `docs/deprecated/models/domain/AnomalyReport — модель и правила формирования репорта.md` согласно ADR-0001.

## Цель

`AnomalyReport` — это отдельная доменная сущность для фиксации, сопровождения и аудита аномалий, обнаруженных при
сравнении локального состояния системы и фактического состояния на бирже.

Отчёт нужен для того, чтобы:

* сохранить снимки состояния **до** обработки аномалии;
* сохранить снимки состояния **после** обработки аномалии;
* пережить рестарт приложения и продолжить обработку;
* разделять критичные и некритичные инциденты;
* хранить техническую ошибку обработки, если сама обработка завершилась неуспешно.

---

## Общий принцип

`AnomalyReport` не участвует в happy-path сопровождении сделки.

Он используется только в контуре обработки аномалий:

* обычные sync-сервисы читают данные биржи и БД;
* `TradeRuleValidator` проверяет торговые инварианты;
* при нарушении правил запускаются:

    * `KillSwitchService` — аварийное снятие риска;
    * `AnomalyService` — создание и обновление `AnomalyReport`.

`AnomalyReport` — это не валидатор и не команда. Это журналируемый объект расследования и обработки инцидента.

## Domain model

```java
public class AnomalyReport extends Auditable {

    /**
     * Внутренний идентификатор отчёта об аномалии.
     */
    private Long id;

    /**
     * Межсервисный идентификатор отчёта об аномалии.
     */
    private String internalId;

    /**
     * Идентификатор биржи, на которой обнаружена аномалия.
     * Обязательное поле.
     */
    private Long exchangeId;

    /**
     * Идентификатор инструмента, к которому относится аномалия.
     * Может быть null, если инструмент не удалось однозначно определить.
     */
    private Long instrumentId;

    /**
     * Текущий статус обработки аномалии.
     * Нужен для продолжения обработки после рестарта.
     */
    private Status status;

    /**
     * Критичность аномалии.
     * Определяет дальнейшую политику после аварийной обработки.
     */
    private Severity severity;

    /**
     * Машинно-читаемый код аномалии.
     */
    private String code;

    /**
     * Текст непредвиденной ошибки обработки.
     * Обычно заполняется вместе со статусом ERROR.
     */
    private String message;

    /**
     * Снимок локального состояния до обработки аномалии.
     * Хранится в json/jsonb.
     */
    private String internalBefore;

    /**
     * Снимок внешнего состояния до обработки аномалии.
     * Хранится в json/jsonb.
     */
    private String externalBefore;

    /**
     * Снимок локального состояния после обработки аномалии.
     * Хранится в json/jsonb.
     */
    private String internalAfter;

    /**
     * Снимок внешнего состояния после обработки аномалии.
     * Хранится в json/jsonb.
     */
    private String externalAfter;
}
```

## Enum: Status

```java
public enum Status {

    /**
     * Отчёт создан, обработка ещё не началась.
     */
    CREATED,

    /**
     * Обработка аномалии началась, но ещё не завершена.
     */
    IN_PROGRESS,

    /**
     * Kill-switch уже выполнен, но итоговая фиксация репорта ещё не завершена.
     */
    KILL_SWITCH_EXECUTED,

    /**
     * Обработка аномалии завершена полностью.
     */
    COMPLETED,

    /**
     * Во время обработки аномалии произошла непредвиденная ошибка.
     */
    ERROR
}
```

## Enum: Severity

```java
public enum Severity {

    /**
     * Критичная аномалия.
     * После обработки торговля по инструменту должна оставаться запрещённой
     * до ручного разбора.
     */
    CRITICAL,

    /**
     * Некритичная аномалия.
     * После kill-switch торговля по инструменту может быть снова разрешена.
     */
    NON_CRITICAL
}
```

## Обязательные правила модели

### 1. Привязка к бирже обязательна

Каждая аномалия всегда относится к конкретной бирже.

Поэтому `exchangeId` — обязательное поле.

### 2. Привязка к инструменту необязательна

Аномалия может относиться:

* к известному инструменту;
* к внешней сущности, для которой локальный `instrumentId` не определён.

Поэтому `instrumentId` nullable.

### 3. Отчёт должен переживать рестарт

Если приложение упало во время обработки аномалии, job должна иметь возможность найти незавершённый отчёт и продолжить
обработку.

Для этого у отчёта есть собственный `status`.

### 4. Критичность не смешивается с кодом

`severity` отвечает за уровень опасности.

`code` отвечает за конкретный тип аномалии.

Это разные измерения.

### 5. `message` — это техническое поле

`message` не является бизнес-описанием аномалии.

Это поле используется только для хранения текста непредвиденной ошибки обработки, обычно вместе со статусом `ERROR`.

## Смысл json-полей

### `internalBefore`

Содержит активные сущности из БД до обработки аномалии.

Примеры:

* активные `Deal`;
* активные `Position`;
* pending `Order`;
* pending/active `AlgoOrder`;
* статус инструмента;
* связанные служебные идентификаторы.

### `externalBefore`

Содержит найденные на бирже сущности до обработки аномалии.

Примеры:

* активные позиции;
* pending orders;
* active algo orders;
* сущности, найденные по идентификаторам из БД;
* неизвестные внешние сущности.

### `internalAfter`

Содержит локальное состояние после выполнения аварийного сценария.

Примеры:

* позиции закрыты;
* ордера отменены;
* algo-ордера сняты;
* статус инструмента обновлён;
* итоговые статусы сущностей зафиксированы в БД.

### `externalAfter`

Содержит состояние биржи после выполнения аварийного сценария.

Примеры:

* открытых позиций нет;
* pending orders нет;
* active algo orders нет;
* либо видно, что часть риска снять не удалось.

## Правила формирования репорта

### Шаг 1. Создание репорта

Когда `TradeRuleValidator` выявил нарушение инварианта:

* создаётся `AnomalyReport`;
* заполняются:

    * `exchangeId`;
    * `instrumentId` при наличии;
    * `severity`;
    * `code`;
    * `internalBefore`;
    * `externalBefore`;
    * `status = CREATED`.

### Шаг 2. Начало обработки

Перед запуском аварийного сценария:

* `status = IN_PROGRESS`.

### Шаг 3. Выполнение kill-switch

После успешного выполнения `KillSwitchService`:

* `status = KILL_SWITCH_EXECUTED`.

### Шаг 4. Сбор финальных снимков

После повторного чтения БД и биржи:

* заполняются `internalAfter` и `externalAfter`.

### Шаг 5. Завершение обработки

Когда обработка полностью завершена:

* `status = COMPLETED`.

### Шаг 6. Ошибка обработки

Если во время обработки аномалии произошла непредвиденная ошибка:

* `status = ERROR`;
* `message` содержит текст ошибки;
* уже собранные snapshot-поля не теряются.

---

## Правила продолжения после рестарта

Job должна уметь поднимать незавершённые отчёты и дорабатывать их.

Ожидаемое поведение:

* `CREATED` — можно начинать обработку;
* `IN_PROGRESS` — можно продолжать аварийный сценарий;
* `KILL_SWITCH_EXECUTED` — нужно собрать `internalAfter` и `externalAfter`, затем завершить отчёт;
* `COMPLETED` — повторно не обрабатывать;
* `ERROR` — повторная обработка только по отдельной политике.

---

## Что не нужно включать в модель

В `AnomalyReport` специально не включаем:

* `dealId`;
* `tradingBlocked`;
* отдельные boolean-флаги по шагам.

Причины:

* нужный контекст сделки должен попадать в `internalBefore` и `internalAfter`;
* блокировка торговли живёт в статусе инструмента;
* прогресс обработки уже отражён через `status`.

---

## Короткий итог

`AnomalyReport` — это отдельная доменная сущность сопровождения инцидента, которая:

* фиксирует состояние до и после обработки;
* переживает рестарт приложения;
* разделяет критичные и некритичные аномалии;
* хранит техническую ошибку обработки;
* служит источником правды для расследования и повторного анализа.
