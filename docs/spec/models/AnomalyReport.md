# AnomalyReport

`AnomalyReport` — это доменная модель для фиксации, сопровождения и
аудита аномалий, обнаруженных при сравнении локального состояния
системы и фактического состояния на бирже. Это не валидатор и не
команда, а журналируемый объект расследования и обработки инцидента.

## Поля

| Имя | Тип | Обязательно | Описание |
|---|---|---|---|
| id | Long | да | Внутренний идентификатор отчёта. |
| internalId | String | да | Межсервисный идентификатор отчёта. |
| exchangeId | Long | да | Идентификатор биржи, на которой обнаружена аномалия. |
| instrumentId | Long | нет | Идентификатор инструмента; `null`, если инструмент не удалось однозначно определить. |
| status | Status | да | Текущий статус обработки аномалии; см. таблицу значений ниже. |
| severity | Severity | да | Критичность аномалии; см. таблицу значений ниже. |
| code | String | да | Машинно-читаемый код аномалии. |
| message | String | нет | Текст непредвиденной ошибки обработки; заполняется при `status = ERROR`. |
| internalBefore | String (jsonb) | нет | Снимок локального состояния до обработки аномалии. |
| externalBefore | String (jsonb) | нет | Снимок внешнего состояния (биржа) до обработки аномалии. |
| internalAfter | String (jsonb) | нет | Снимок локального состояния после обработки аномалии. |
| externalAfter | String (jsonb) | нет | Снимок внешнего состояния (биржа) после обработки аномалии. |

Модель наследует поля аудита от базового класса `Auditable`.

## Значения Status

| Значение | Смысл |
|---|---|
| CREATED | Отчёт создан, обработка ещё не началась. |
| IN_PROGRESS | Обработка аномалии началась, но ещё не завершена. |
| KILL_SWITCH_EXECUTED | Kill-switch уже выполнен, но итоговая фиксация репорта ещё не завершена. |
| COMPLETED | Обработка аномалии завершена полностью. |
| ERROR | Во время обработки аномалии произошла непредвиденная ошибка. |

## Значения Severity

| Значение | Смысл |
|---|---|
| CRITICAL | Критичная аномалия. После обработки торговля по инструменту должна оставаться запрещённой до ручного разбора. |
| NON_CRITICAL | Некритичная аномалия. После kill-switch торговля по инструменту может быть снова разрешена. |

## Инварианты структуры

- `exchangeId` обязателен — каждая аномалия всегда относится к
  конкретной бирже.
- `instrumentId` nullable — аномалия может относиться к внешней
  сущности, для которой локальный инструмент не определён.
- `severity` и `code` — независимые измерения: `severity` определяет
  уровень опасности, `code` — конкретный тип аномалии.
- `message` заполняется только одновременно с `status = ERROR` и
  содержит текст непредвиденной ошибки обработки; это техническое
  поле, не бизнес-описание аномалии.

## Связи

- **Exchange** — биржа, на которой обнаружена аномалия (`exchangeId`).
- **Instrument** — инструмент, к которому относится аномалия
  (`instrumentId`, опционально).

## Персистентность

Четыре поля `internalBefore` / `externalBefore` / `internalAfter` /
`externalAfter` хранятся в jsonb. Это нетривиальный маппинг: в один
столбец попадают разнородные доменные объекты — перечень ниже.

**Локальные снимки (`internalBefore`, `internalAfter`).** Содержат
доменные модели из БД:

- активные `Deal`;
- активные `Position`;
- pending `Order`;
- pending / active `AlgoOrder`;
- статус инструмента;
- связанные служебные идентификаторы.

**Внешние снимки (`externalBefore`, `externalAfter`).** Содержат
данные, прочитанные с биржи:

- активные позиции;
- pending orders;
- active algo orders;
- сущности, найденные по идентификаторам из БД;
- orphan-сущности (найденные на бирже без соответствия в БД).

Конкретная сериализация (формат, версионирование) — отдельная задача,
см. backlog «Стандарт описания персистентности доменных моделей».

## Не включаемые поля

| Поле | Почему не включается |
|---|---|
| `dealId` | Контекст сделки попадает в `internalBefore` / `internalAfter`. |
| `tradingBlocked` | Блокировка торговли живёт в статусе инструмента. |
| Boolean-флаги по шагам обработки | Прогресс обработки отражён через `status`. |
