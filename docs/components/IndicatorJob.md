# IndicatorJob

## На какой вопрос отвечает этот файл

Кто считает технические индикаторы.

## Что делает

Заранее считает объявленные значения по закрытым свечам и сохраняет их
под идентичностью вычисления:

- читает **заказанные идентичности** из реестра;
- по таймфрейму идентичности берёт группы сбора, готовые отдать историю;
- читает окно закрытых свечей группы;
- считает значения;
- **сохраняет только значения после зоны прогрева**;
- пересчёт идемпотентен;
- заглядывания вперёд не допускает.

## Обходятся идентичности вычисления, а не настройки стратегий

Настроек стратегий джоба не читает: они живут в базе **другого
сервиса**, и ходить в неё market-data не может и не должен. Строка
результата принадлежит идентичности вычисления, а не заказчику
(`docs/models/domain/other/IndicatorValue.md`).

## Инструменты приносит сбор, а не заказ

Идентичность называет, **что** считать; по каким инструментам — отвечают
уже собранные группы её таймфрейма. Так одна заказанная «ATR(14) на 1H»
покрывает весь листинг, у которого этот таймфрейм собирается, — то, чего
требуют детекторы советника
(`docs/architecture/market-data-collection.md` — дом требований к сбору). Требовать отдельного заказа на каждый инструмент значило бы
завести N заказов ради одного вопроса к рынку.

## Прогрев

Величина прогрева в значении не хранится: джоба сама пропускает зону
разгона и сохраняет только пригодные для торговли значения.

Эффективный прогрев — объявленный автором override либо выведенный из
типа и периода (`docs/rules/strategy-condition-contract.md`); объявляется
он параметрами идентичности, а не настройкой стратегии.

## Границы

- Решения о входе не принимает, сделок и заявок не создаёт.
- Фазу рынка напрямую не считает.
- Свежесть не проверяет: её меряет читатель по своему сроку
  (`docs/rules/market-data-freshness.md`).
- Идентичностей не заводит: их заводит команда требования
  (`docs/architecture/market-data-collection.md`).
