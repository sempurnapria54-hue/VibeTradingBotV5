# IndicatorJob

## На какой вопрос отвечает этот файл

Кто считает технические индикаторы (компонент-job): что делает, что не
делает, как обращается с warmup и идемпотентностью.

## Назначение

`IndicatorJob` заранее считает технические индикаторы (EMA, RSI, MACD,
Stochastic, Bollinger Bands, OBV, ATR) и сохраняет их как
`IndicatorValue` (см. `docs/models/domain/other/IndicatorValue.md`). Настройки —
`StrategyIndicatorSetting`; данные — закрытые свечи; результат —
`IndicatorValue`.

## Делает

- читает стратегии **всех статусов кроме `DELETED`** и их
  `StrategyIndicatorSetting` (открытые сделки `INACTIVE`-стратегий
  сопровождаются по pinned detail и тоже читают индикаторы; `CREATED` —
  для warmup-готовности к активации; перечень — как в правиле свежести,
  `docs/rules/market-data-freshness.md`);
- читает закрытые свечи;
- считает значения индикаторов;
- сохраняет только значения после warmup-зоны;
- обеспечивает идемпотентный пересчёт;
- не допускает look-ahead.

## Не делает

- не принимает решение о входе;
- не создаёт сделку / ордера;
- не сопровождает сделку;
- не считает фазу рынка напрямую.

## Warmup

`warmup` в `IndicatorValue` не хранится. `IndicatorJob` сам пропускает
warmup-зону и сохраняет только значения, пригодные для live-логики
(например, при `period = 50` свечи 1–50 — разгон, значение не
сохраняется; со свечи 51+ — сохраняется). Для консервативных индикаторов
warmup можно увеличить внутри алгоритма — это ответственность
`IndicatorJob`. Объявленная глубина прогрева (эффективный `warmup` в
`IndicatorParams`, `docs/models/domain/aggregate/Strategy.md`
§IndicatorParams) — вход для глубины загрузки свечей
(`docs/processes/candle-loading.md`); здесь — runtime-пропуск
разгонной зоны при расчёте.

## Идемпотентность

Считает по закрытым свечам, не использует future data, сохраняет результат
с уникальностью `UNIQUE(instrument_id, strategy_indicator_setting_id,
candle_timestamp)` (ключ по настройке-владельцу — owner-ключевание, см.
`docs/decisions/market-data-result-identity-keying.md`), при повторном
запуске дублей не создаёт. Реестра конфигураций и дедупа по `config_id`
больше нет — каждая настройка-владелец считается под себя. Для
`DELETED`-стратегий новые значения не считает.

**Checkpoint — производный, отдельного состояния нет.** «Докуда
посчитано» = `max(candle_timestamp)` по таблице результатов для
(`instrument_id` + `strategy_indicator_setting_id`); «докуда считать» =
время закрытия последней закрытой свечи в группе (инструмент +
`timeframe`). На тике job берёт `max` → досчитывает от него по закрытым
свечам. Отдельная persisted checkpoint-модель не заводится (дубль данных,
рассинхрон на рестарте в середине пачки).
