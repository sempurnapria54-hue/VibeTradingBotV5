# SystemActionExecutor

## На какой вопрос отвечает этот файл

Кто выдаёт следующую команду системного действия за проход.

## Контракт

```java
Optional<ServiceCommand> next(SystemActionType type, DealContext dealContext, DealTranche tranche);
Optional<ServiceCommand> next(SystemActionType type, DealContext dealContext, DealTranche tranche,
                              ServiceCommandType link, ServiceCommandPayload payload);
void reviseLiveExecutions(DealContext dealContext);
```

**Транш — операнд обеих форм `next`, а не опущенная деталь.** Ключ живого
потраншевого исполнения включает транш и номер его эпизода
(`docs/models/domain/other/DealActionState.md` §Инварианты), и
консолидация входа адресует **транш**, а не сделку: N траншей сетки дают N
законных живых исполнений одного типа. У агрегатного действия транш пуст,
и это пустота-уровень, а не пропуск операнда.

**Вторая форма называет звено ЯВНО.** Применяется к добыче: сущность, чей
факт понадобился, называет вызывающая сторона — она прочитала durable-факт
надобности, и повторять этот разбор здесь значило бы завести второго
носителя одного решения.

**Точек входа три, и последняя стои́т особняком.** Обе формы `next`
отвечают про **одно названное** действие; ревизия проходит по **всем**
живым системным исполнениям сделки.
Вторая нужна потому, что закрытие неактуального исполнения по определению
происходит там, где действие больше **никто не называет**, — то есть
первая точка входа до него не доходит.

- ожидающее повтора исполнение отдаёт команду только по наступлении
  времени следующей попытки, и перевзводится в запланированное: звено
  заново выводится из фактов;
- завершённые и отказавшие строки терминальны; новая надобность — новая
  строка.

**Статус исполнения сервис сам не пишет** — его двигают исполнители
команд и учёт повторов. **Два исключения, оба про актуальность, а не про
исход звена:** перевзвод ожидающего повтора и закрытие исполнения,
ставшего неактуальным. Оба выводятся из тех же фактов, из которых
выводится стадия.

## Стадия выводится из подтверждённого факта

Общее требование: факт **durable**, читается из базы, а не из памяти
прохода. Звено, пишущее в сделку, двигает исполнение **той же
транзакцией** — иначе вывод из фактов ломается на рестарте.

**Подтверждённый факт звена — это добытый факт самой команды.** Команда
добычи ходит к источнику столько раз, сколько нужно, и останавливается,
когда факт добыт; **факт не добыт — звено не завершено** и повторяется по
бюджету действия. Промежуточные записи, сделанные по пути, завершением не
являются.

## Состав цикла добычи

Звенья — добывающие команды по известным сущностям сделки: позиция,
заявки, условные заявки, баланс, движения средств.

**Состав цикла един для всех троп; разводится гейт звена.** Звено добычи
движений эмитится только на выходной тропе.

Все дискриминаторы — durable-факты самой сделки, читаемые из контекста
прохода. Консолидация входа адресует **транш**: подтверждается его вход,
и статус пишется ему; терминалы и число — уровня сделки.

## Финализация

| Действие | Звенья |
|---|---|
| консолидация входа транша | подтверждение его входа; завершение пишет статус транша той же транзакцией |
| штатный терминал | расчёт числа, затем терминальное ребро |
| аварийная тропа | ребро в ошибку и аварийный терминал — **два отдельных исполнения** |

**Терминальная команда эмитится только по терминальному исходу добычи.**
Без числа звено не завершается; исчерпание бюджета добычи уводит на
ошибочную тропу.

**Тропа «неисчислимо» — только аварийный контур.**

## Дочистка звеном не является

Отмена заявок и закрытие позиции эмитируются обработчиком напрямую, без
анкера действия: это риск-снижающие операции, и иерархии создания
торгового намерения они не подчинены.
