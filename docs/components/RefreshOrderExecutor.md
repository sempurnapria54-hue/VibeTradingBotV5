# RefreshOrderExecutor

## На какой вопрос отвечает этот файл

Кто исполняет добычу состояния обычной заявки.

## Что делает

Проходит цикл добычи **внутри одной команды**, с обрывом на первом
успешном источнике:

```text
цикл 1 — заявка:
  по идентификатору (внешнему, иначе по клиентскому)
  → ожидающие
  → история
  → архив истории
  терминал исчерпания: MISSING_AFTER_REFRESH

цикл 2 — материализованная встроенная защита
  (только у ТЕРМИНАЛЬНОГО родителя: TERMINAL_FILLED, TERMINAL_FILL_UNKNOWN):
  живые УСЛОВНЫЕ по инструменту, матч по клиентскому идентификатору
  → история условных заявок
  терминал исчерпания: вторая ступень исхода (PROTECTION_LOST / ANALYSE_HISTORY)
```

Обновляет заявку и её статус через резолвер; при необходимости двигает
строку исполнения.

**Второй цикл — исполнитель исхода `SEARCH_MORE` у ТЕРМИНАЛЬНОГО
родителя.** Первый адресует обычные заявки; встроенная защита,
материализованная источником самостоятельной живой **условной** заявкой
(терминальный родитель с непустым либо недобытым наливом —
`docs/lifecycles/Order.md`), ни в одном из них не находится. Без второго
цикла исход `SEARCH_MORE` называл поиск, которого не делал никто: цикл
заканчивался «не найдена», защита читалась снятой, а покрытие
недосчитывалось — разрешающая ошибка, уводящая штатную сделку в биржевую
ступень 2 по ложному факту.

**Гейт запуска — класс родителя, а не исход первой ступени.** Исход
`SEARCH_MORE` производят **два** класса, и смысл у него разный:
у `LIVE` — «вывода по одному снапшоту не делаем, наблюдаем дальше»
(родитель ещё жив, защита ещё в его теле, материализовать её нечему);
у `TERMINAL_FILLED` / `TERMINAL_FILL_UNKNOWN` — «ищи материализованную
запись». Запуск цикла на живом родителе искал бы того, чего по
построению нет, а его исчерпание давало бы вторую ступень
`PROTECTION_LOST` на живой защите — сделка в `ERROR` и биржевая ступень 2
по ложному факту, ровно та ошибка, против которой цикл и заведён.
Поэтому гейт — терминальность родителя.

**Запрос идёт по инструменту, а совпадение ищется в ответе.** Фильтра по
клиентскому идентификатору у эндпоинта условных заявок нет
(`docs/integrations/okx/contracts/algo-order.md`), поэтому источник
запрашивается по инструменту и типу, а найденная запись сверяется с
`attachAlgoClOrdId` родителя по полю ответа. Эндпоинт, параметры и
маппинг записи в снапшот встроенной защиты — `docs/models/mapping/Order.md`,
раздел evidence-cycle.

**Метрики исполнения приходят готовыми из этой же добычи** — накопленный
филл, средняя цена, комиссия; отдельной команды по сделкам исполнения
нет.

**Терминал выносит сам:** не найдена после **полного** цикла —
контролируемое исключение и причина «не найдена после добычи». Пустой
ответ одного источника основанием не является.

## Пересчёт чисел риска

Наблюдение исполнения или терминального статуса ноги входа меняет
операнды, поэтому исполнитель **той же транзакцией пересчитывает все
четыре числа риска целиком**.

Формулы — `docs/spec/deal-risk-numbers.json`.

**Пересчёт гейтится признаком полноты графа.** Признак `graphComplete`
читается готовым с контекста прохода (`docs/components/models/DealContext.md`);
ложен — числа не пишутся и звено не завершается. Правило, перечень
писателей и их триггеры — дом четырёх чисел риска
(`docs/models/domain/aggregate/Deal.md`); здесь оно не пересказывается.

## Границы

Сделку целиком не сопровождает; добыча позиции — отдельная команда.
