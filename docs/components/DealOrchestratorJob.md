# DealOrchestratorJob

## На какой вопрос отвечает этот файл

Кто сопровождает уже созданные сделки (компонент-job): цикл работы,
операционная оболочка (CRON / выключатель / фасад / выборка),
concurrency-guard, границы.

## Назначение

`DealOrchestratorJob` сопровождает уже созданные `Deal`, прогоняя их
через FSM. Цикл (один проход):

1. находит сделки в работе (критерии выборки — ниже);
2. **энфорсит холд инструмента** (см.): активные сделки
   инструментов в `TRADE_BLOCKED` уводятся в `ERROR`;
3. для каждой загружает `DealContext` (`DealContextService`);
4. **ревизует живые SYSTEM-исполнения** — зовёт
   `SystemActionExecutor.reviseLiveExecutions(dealContext)` **один раз за
   проход, до передачи управления handler'у**, своей транзакцией: строки,
   чьё действие стало неактуальным, закрываются `SKIPPED`. Строки уже
   загружены в `DealContext.actionStates`, отдельного запроса нет.
   Предикат неактуальности и довод — `docs/components/SystemActionExecutor.md`;
5. запускает `DealStateMachine` (см. `docs/components/DealStateMachine.md`);
6. получает `DealTransition` (команды + опц. целевой статус);
7. передаёт команды в `ServiceCommandExecutor`, прерывая цикл при первом
   неуспешном результате (остальные команды перехода в этом проходе не
   гонятся — handler разберёт FAILED-якорь на следующем тике). **Здесь же —
   перехват исключения исполнителя:** оркестратор зовёт `HoldService`,
   передавая радиус и силу реакции **по типу перехваченного исключения**
   — отображение «тип → реакция» установлено inspection'ом и живёт в
   `docs/components/HoldService.md`; контракт броска — ниже;
8. применяет переход: сохраняет новый статус сделки (если задан).

**Номер шага цикла — не адрес: ссылаться на шаг следует именем**. Вставка шага в середину сдвигает нумерацию у всех
цитирующих, а найти их грепом по «шаг N» нельзя — номер у каждого свой.
Это уже случалось дважды (ввод ревизии живых SYSTEM-исполнений четвёртым
пунктом сдвинул диспетчеризацию с 6 на 7, и два носителя отстали),
поэтому внешние ссылки называют шаг — «диспетчеризация команд», «ревизия
живых SYSTEM-исполнений», — а номер приводят только рядом с именем.

## Перехват реакции: выделенный обработчик до общего (H1 `DOCS_CHECK_15`)

Оркестратор — единственная точка, где реакция на отказ исполнителя
резолвится и поднимается. Чтобы это было исполнимо, нужны **два**
обработчика, и порядок между ними — часть спецификации:

- **выделенный** `catch` вокруг **шага 7** (диспетчеризация команд) ловит
  **поимённо** `ControlledExchangeException` и
  `RetryBudgetExhaustedException` — оба бросаются только
  `ServiceCommandExecutor`'ом и только после того, как строка исполнения
  переведена в `FAILED` (`docs/components/ServiceCommandExecutor.md`). Обработчик резолвит класс реакции по типу, зовёт
  `HoldService` и **затем** уводит сделку ошибочной тропой — блокировка и
  разбор live risk не конкурируют, у каждой своя ветка;
- **общий** `catch (RuntimeException)` — execution boundary прохода
  (`RuntimeErrorCode`, `docs/rules/runtime-error-classification.md`):
  ловит **всё остальное** — сборку `DealContext`, прогон FSM, применение
  перехода — и уводит сделку в `ERROR` без радиусной реакции. Стоит
  **после** выделенного.

**Оба `catch` пишут `Deal.status = ERROR` прямой записью, звена не
эмитируя** — карв-аут «троп перехвата»
(`docs/processes/fsm-execution-layering.md`). Эмиссия действия из обработчика исключения
не вводится: на этой тропе нужен гарантированный перевод, а не ещё одна
точка отказа. Анкер попыток аварийной тропы от этого не теряется — его
несёт **второе** исполнение `FINALIZE_DEAL_ERROR_ACTION`, которое
затребует `ErrorHandler`.

**Почему порядок обязателен.** Если бы бросок исполнителя ловил только
общий обработчик, каждый отказ команды (включая ретраябельные) уводил бы
сделку в `ERROR` мимо FSM и ломал семантику `RETRY_PENDING`; а холд не
поднимался бы вовсе. Обратная ошибка — триггерить реакцию по
**возвращённому** неуспешному результату — обесценивает бюджет попыток на
первом таймауте (`docs/components/HoldService.md`).

## Enforcement холда

**Оркестратор — точка enforcement жёсткого холда**:

- `Instrument.Status.TRADE_BLOCKED` (и каскадно
  `Exchange.Status.TRADE_BLOCKED`) → **каждая** активная сделка held-scope
  уводится в `ERROR` с `shutdownReason = RISK_POLICY` (для биржевого
  каскада — `EXCHANGE_HOLD`), дальше её разбирает `ErrorHandler` (teardown
  live risk);
  - **Ребро пишет петля прямой записью — это карв-аут, а не обход
    канона**. Enforcement — **троп перехвата**, а не
    решения: сделка уводится внешним обстоятельством, и требование
    материализовать строку исполнения ввело бы точку отказа там, где
    нужен гарантированный перевод. Строку `FINALIZE_DEAL_ERROR_ACTION`
    на этой тропе заводит **второе** исполнение — `ErrorHandler` после
    доказанного снятия live risk;
- `Exchange.HOLD` (мягкий холд, ступень 1 — статус вводится на
  `CODE`) оркестратором **не перехватывается**: активные сделки не
  трогаются и ведутся штатным FSM **в полном объёме** — ремодел защиты,
  управление, закрытие (командного блок-сета у ступени нет). Каскадный
  перехват — только у `Exchange.TRADE_BLOCKED` (ступень 2,
  `docs/rules/exchange-hold.md`);
- `Instrument.Status.ENTRY_BLOCKED` **не перехватывается** — мягкий класс
  запрещает только **новые входы**, а живые сделки доживают под своим стопом
  и ведутся штатным FSM. Запрет входов даёт выборка `EntryScannerJob`
  (`findByStatus(ACTIVE)`), не оркестратор. Это несущее требование шага 7:
  перехват мягкого класса воскресил бы снятую kill-switch-политику.

Свежий runtime-граф сделки перечитывается из БД в начале следующего прохода
(`DealContextService.build`), не внутри текущего.

Это также execution boundary, на которой ловятся unexpected exceptions
(`RuntimeErrorCode`, см. `docs/rules/runtime-error-classification.md`).

## Операционная оболочка (конвенция джоб)

По `.claude/rules/codestyle.md`:

- **CRON из конфига** + булев **`enabled`** (`@ConfigurationProperties`):
  при `false` запланированный и ручной тик ничего не делают. Частота тика —
  **провизорное число** (бэктест/наблюдения), в конфиге, не хардкод.
- **Ручной триггер вне расписания** — асинхронно через **фасад**
  (`@Async`), не блокируя HTTP-ответ; фасад отвечает только за **запуск**
  (чистый запуск → `202`; отказ запуска, вкл. «уже бежит» → `409`, см.
  `docs/rules/error-handling-policy.md`).
- Тело тика вынесено в приватный `run`; метод `@Scheduled` проверяет
  `enabled` и делегирует.

## Concurrency-guard (D-M1)

Перекрытие проходов (затянувшийся тик + ручной триггер параллельно
расписанию) → двойной `SUBMIT` (деньги-дубль). **D-M1** — жёсткий гейт
`DONE` шага 6 (`.claude/work/roadmap/phase-1.md`): петлю нельзя включать,
пока не закрыт.

Механизм в фазе 1 — **in-process `JobExecutionGuard`** (общая джоб-конвенция,): под одну блокировку по имени джобы заходят **и таймерный, и ручной**
запуск. Это сериализует проходы → перекрывающий запуск пропускается,
**per-deal-коллизий нет**, отдельная per-deal-защита (`@Version` / row-lock на
`DealActionState`) не нужна. В фазе 1 один экземпляр монолита — межэкземплярной
конкуренции нет, in-process guard безопасен и достаточен.

**Мультиинстанс — форвард фазы 3.** С несколькими экземплярами монолита
in-memory guard небезопасен; тогда D-M1 закрывается **БД advisory-замком на
весь проход на одном соединении** (был реализован как `OrchestratorPassLock`,
снят из фазы 1 2026-07-01 как преждевременный — код в git-истории). Возврат —
на шаге распила на мультиинстанс.

**Цена** — последовательная обработка сделок без параллели; принято для
фазы 1, revisit при масштабе.

## Критерии выборки (что берёт проход)

- **активные `Deal`** (не в terminal status `CLOSED`/`EMERGENCY_CLOSED`,
  `docs/lifecycles/Deal.md`);
- **подхват ожидающих повтора — не вторая ось выборки, а предикат
  продвижения.** Проход **сделко-ориентирован**: отдельной выборки по
  таблицам исполнений не существует, и индекса под due-for-retry не
  вводится. Сделка со строкой `DealActionState` (любого вида)
  в `RETRY_PENDING` **уже попадает** в выборку по `Deal.status` — она не
  терминальна; «наступил ли `nextRetryAt`» проверяется **над уже
  загруженными** строками, до срока повтор не берётся
  (`docs/components/RetryPolicyService.md`);
- потенциально большая выборка — ограниченным окном/порядком, не
  безлимитным чтением (`.claude/rules/codestyle.md` данных).

## Не делает

Не считает индикаторы, не ищет новые входы (это `EntryScannerJob`), не
ходит на биржу напрямую, не считает цены, не исполняет REST сам. Не
смешивается с `AnomalyJob`: orchestrator ведёт известные `Deal` по FSM,
`AnomalyJob` ищет глобальные нарушения инвариантов (см.
`docs/components/AnomalyJob.md`).
