# AnomalyJob

## На какой вопрос отвечает этот файл

Кто ищет нарушения базовых инвариантов системы (компонент-job): что
ищет, чем не является.

## Назначение

`AnomalyJob` ищет не штатные runtime-ситуации, а нарушения базовых
инвариантов — сравнивает exchange live facts с доменными active
entities. Фиксирует anomaly/safety report (`AnomalyReport`, см.
`docs/models/domain/other/AnomalyReport.md`) и может инициировать safety-flow по
правилам системы. Сделку по FSM **не** ведёт.

**Блокировку ставит не сам — зовёт `HoldService`**,
передавая радиус и силу реакции по классификации аномалии
(`docs/components/HoldService.md`). Это один из детекторов холда; перечень
зовущих сервис **открыт**, и собственного пути к
статусу scope джоба не заводит — идемпотентность и эскалацию держит
сервис.

## Типовые anomaly-кейсы

- live `Order`/`AlgoOrder` есть на бирже, но нет соответствующей
  runtime-сущности в БД;
- active position на бирже без active `Deal`, объясняющего её появление;
- terminal `Deal` имеет live position;
- больше одной позиции на инструмент (при максимуме одной);
- DB entity closed, но exchange entity всё ещё live;
- unknown external status; нарушен isolated margin; плечо выше
  биржевого максимума (`externalMaxLeverage`); чужой live risk на
  инструменте; после cleanup остались неизвестные live-хвосты;
- **инвариант «ликвидация за стопом» нарушен у ведомой позиции** — см.
  ниже.

## Переоценка инварианта «ликвидация за стопом» (H18 `DOCS_CHECK_10`)

**Требование:** инвариант «ликвидация за стопом»
проверяется **не только на входе**. `RiskValidator` вызывается лишь для
risk-creating/increasing/weakening действий
(`docs/rules/risk-validator-scope.md`), поэтому у позиции, которую просто
ведут, инвариант не переоценивался никогда — при том что
`Position.externalLiquidationPrice` рефрешится и хранится, а на
изолированной марже funding-списания подъедают маржу и двигают цену
ликвидации к марку по мере удержания. Стоп может перестать быть первым на
пути, а на нём стоит вся конструкция «worst-case сделки = убыток на стопе»
(`docs/rules/risk-policy.md`).

**Проверку ведёт `AnomalyJob`** — это сравнение живого биржевого факта
(`externalLiquidationPrice`, актуальная защита) с доменным инвариантом,
то есть ровно его назначение.

**Реакция — не только фиксация.** Нарушение у ведомой позиции ведёт к
**перестановке защиты или контролируемому выходу**, а не к одному лишь
`AnomalyReport`: зафиксированная аномалия оставила бы позицию с
некорректным worst-case. Это исключение из «сделку по FSM не ведёт» —
`AnomalyJob` не ведёт сделку, но инициирует safety-flow по правилам
системы , и здесь правило именно такое.

## Исключение (не anomaly)

Entry order исполнился → exchange position появилась → локальной
`Position` ещё нет → следующий `REFRESH_POSITION_COMMAND` создаёт `Position` и
привязывает к `Deal`. Это не anomaly при наличии active `Deal` и
известного entry flow.

## Состояние носителей

**Док есть, кода нет.** `AnomalyJob` в `src/` не материализован (среди
`@Scheduled`-джоб его нет); материализация — **шаг 8** роадмапа. Все
клаузы этого дока и ссылки на него из правил
(`docs/rules/trading-constraints.md` — энфорсмент «одна
позиция на инструмент», «чужой live risk»;
`docs/rules/risk-policy.md` — переоценка
инварианта ликвидации) сформулированы **целевым временем**.

Пометка записана по итогу инвентаря периодических джоб: без неё клауза «детектит `AnomalyJob`» читается как
описание работающего механизма, и проверяющая линза либо принимает его на
веру, либо поднимает как «механизма нет» — оба исхода неверны.

## Смежное

Зона «live risk после terminal / позиция без active Deal» делит границу с
`ReconciliationJob` (в этой миграции не материализован — только название,
backlog п.7). Полный safety/kill-switch кластер — backlog п.7.

Счётчик **серии неудач по инструменту поверх сделок** — не здесь: его
ведёт отдельная джоба `TradeGuardJob`. Границу проводит вопрос: `AnomalyJob` сравнивает
**текущее** состояние с инвариантом, `TradeGuardJob` считает **историю
исходов** по инструменту.
