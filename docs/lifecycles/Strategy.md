# Strategy lifecycle

## На какой вопрос отвечает этот файл

Через какие состояния проходит `Strategy`.

Структура модели — в `docs/models/domain/aggregate/Strategy.md`.

## Природа статуса

`Strategy.Status` описывает **административное** состояние стратегии и
задаёт жизненный цикл всех вложенных immutable-настроек. Он **не**
описывает runtime-свежесть рыночных данных: устаревшие свечи /
индикаторы / структура / фаза рынка статус не меняют (свежесть — `MarketDataExpirationChecker` +
`StrategyStep.marketDataExpiredSetting`).

## Статусы

- **`CREATED`** — стратегия создана, но ещё не введена в активное
  использование. **Это и есть черновик**: отдельного статуса под него не
  заводится — состояние одно, и второе имя ему было бы вторым носителем
  (`.claude/rules/design-simplicity.md`). Кто автор черновика — человек
  через поверхность или модуль-советник внутри `strategies`, — отвечает
  `createdBy` (`docs/models/domain/other/Auditable.md` §«Область значений
  актора»): его два класса, «имя принципала» и «собственный проход», и
  есть это различение. Отдельного поля источника нет и не заводится, пока
  советника нет: место резервируется швом, а не колонкой
  (`docs/architecture/reserved-extension-points.md` §«Принцип
  резервирования»).
- **`ACTIVE`** — единственная активная стратегия **пары «биржевой счёт,
  инструмент»** (`docs/architecture/tenant-and-exchange.md` §«Торговая
  строка называет счёт, и радиусы читаются от него»). Новые сделки по
  этой паре могут создаваться только по активной стратегии (если данные не устарели, условия входа выполнены, risk/
  invariant checks пройдены). `ACTIVE` — это административное
  **разрешение** к работе, **не** гарантия, что прямо сейчас можно
  открыть сделку.
- **`INACTIVE`** — стратегия существует, но временно не участвует в
  создании новых сделок. **Блокирует только новые сделки**; уже
  открытые сделки продолжают сопровождаться по pinned
  `StrategyDetail` (`Deal.strategyDetailId`).
- **`DELETED`** — логически удалённая. Новые расчёты и сделки по ней
  не запускаются; уже открытые сделки **обработчик активной сделки**
  выходными проверками уводит в координированный выход, записывая
  `Deal.shutdownReason = STRATEGY_DELETED` той же транзакцией
  (`docs/components/DealActiveHandler.md`; дом события —
  `docs/lifecycles/Deal.md`).

## Эффекты на сделки (сводка)

```text
CREATED  -> не используется для новых сделок
ACTIVE   -> разрешает новые сделки (при прочих условиях)
INACTIVE -> новые сделки блокируются; открытые живут по pinned detail
DELETED  -> новые сделки блокируются; открытые -> graceful shutdown
```

`Strategy.INACTIVE`/`DELETED` — единственная связь статуса с runtime
(блокировка новых / graceful shutdown). Runtime-проверка статуса при
поиске входа выполняется в `EntryScannerJob`; реакция открытых сделок
— в FSM/lifecycle Deal (компоненты — форвард-заметки). Здесь —
статусная семантика, которой владеет сама `Strategy`.

## Допустимые переходы (материализовано на `CODE` шага 2)

```text
CREATED  -> ACTIVE | DELETED
ACTIVE   -> INACTIVE | DELETED
INACTIVE -> ACTIVE | DELETED
DELETED  -> (терминальный)
```

`CREATED → INACTIVE` не допускается (деактивировать можно только
введённую в работу стратегию); `CREATED` руками через API не
ставится — только системой при создании. Допустимость перехода
проверяет сама модель (`Strategy.canTransitionTo`); активация
дополнительно держит инвариант «одна `ACTIVE` на **паре** счёт ×
инструмент» (проверка приложения + частичный UNIQUE-индекс в БД) — радиус
пары, а не инструмента, потому что инструмент принадлежит площадке и у
двух счетов одной площадки он один (дом радиуса —
`docs/architecture/tenant-and-exchange.md`).

**Прочие предусловия активации живут в доме валидации**
(`docs/rules/strategy-validation.md` §«Что проверяется на активации»):
допустимость перехода и инвариант единственности — не весь набор.

**Поверхность перехода принадлежит владельцу определений.** Она живёт у
`strategies` и адресуется по его префиксу
(`PUT /api/v1/strategies/{internalId}/status`); путь `PUT
/api/strategies/{internalId}/status` без префикса сервиса — поверхность
**донора**, и он исчезает вместе с ним
(`docs/rules/api-access-policy.md` §«Вся поверхность закрыта; открытое —
перечислено»).

## Кто управляет

**Целевой актор активации — гейт трек-рекорда, не человек.** Определение
любого автора проходит валидацию, бэктест вне выборки и обязательный
теневой период, и активирует его набранный на этом пути трек-рекорд
(`docs/concept.md` §«Машине открывает торговлю гейт, а не доверие»; состав
гейта — `docs/architecture/signal-strategy-allocator.md` §«Активирует гейт,
а не человек»).

**До фазы 4 активирует держатель, и это разведочный режим с названным
условием выхода.** Гейт меняет **актора** тропы, а не саму тропу
(`docs/architecture/reserved-extension-points.md` §«Советник — автономный
управляющий»): переходы, их предусловия и события остаются теми же, у
`PUT`-перехода меняется только то, кто его инициирует. Условие выхода —
построенный гейт (фаза 4).

**Что режим не даёт.** Определение получает живые деньги без бэктеста вне
выборки, без теневого периода и без порога выживаемости — то есть без всех
трёх условий, каждое из которых дом гейта объявляет незаменимым другими.
Смягчение названо и проверяемо: субъект поверхности один — держатель
(`docs/rules/api-access-policy.md` §«Принципал один — посылка фазы 1»), то
есть активация до фазы 4 есть решение владельца капитала о собственных
деньгах, а не автоматический ход. Риск-политика при этом не ослаблена
ничем: гейт риска стои́т после любого намерения
(`docs/rules/risk-policy.md`).

Переходы статуса — административное действие (создание/активация/
деактивация/логическое удаление стратегии). Расчётные jobs
(`IndicatorJob`/`MarketStructureJob`) `Strategy.Status` **не** меняют
(фаза job'ом не считается — вычисляется на лету,
`docs/models/domain/other/MarketPhase.md`). Immutability стратегии (см.
`docs/models/domain/aggregate/Strategy.md`) означает, что правила не
редактируются — меняется только статус контейнера.
