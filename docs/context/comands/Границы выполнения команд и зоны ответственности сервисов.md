# Границы выполнения команд и зоны ответственности сервисов

## Цель

Эта дока фиксирует, какой сервис за что отвечает при выполнении сервисных команд в orchestrator/state machine
архитектуре.

Главная задача — не смешивать:

* sync фактов;
* проверку правил;
* аварийную реакцию;
* формирование отчётов;
* переходы FSM.

---

## Общий принцип

### Handler

Handler принимает решение по стадии сделки.

Он:

* анализирует `DealContext`;
* возвращает `TransitionResult`;
* указывает список `ServiceCommandType`.

Handler не должен:

* ходить на биржу;
* писать в БД напрямую;
* вызывать kill-switch;
* формировать anomaly report.

### ServiceCommandExecutor

Executor только маршрутизирует команды в нужные сервисы.

Он:

* получает `DealContext`;
* достаёт из него только нужные данные;
* вызывает соответствующий сервис.

Executor не должен:

* принимать торговые решения;
* валидировать торговые правила;
* сам мутировать статус сделки.

### Orchestrator

Orchestrator управляет циклом.

Он:

* загружает `DealContext`;
* вызывает FSM;
* передаёт команды в executor;
* после выполнения команд заново загружает `DealContext`.

Orchestrator не должен:

* сам решать, какая защита нужна;
* сам резолвить внешние статусы;
* сам выполнять sync сущностей.

---

## Главный принцип разделения

### Sync-сервисы

Sync-сервисы отвечают только за синхронизацию фактов биржи и БД.

Примеры:

* `PositionService`
* `OrderService`
* `AlgoOrderService`
* `BalanceService`

### Validator

`TradeRuleValidator` отвечает за проверку торговых инвариантов.

Он сравнивает:

* внешние данные с биржи;
* внутренние данные из БД.

И решает:

* всё нормально;
* найдено нарушение.

### Аварийная реакция

`KillSwitchService` отвечает только за аварийное снятие риска.

### Отчёт об инциденте

`AnomalyService` отвечает только за создание и обновление `AnomalyReport`.

### FSM

FSM работает только с уже готовыми нормализованными фактами.

Она не знает про внешние статусы биржи и не валидирует технические инварианты sync-операций.

---

## Кто за что отвечает

## 1. PositionService

### Отвечает за:

* чтение snapshot позиций с биржи;
* чтение позиций из БД;
* передачу обоих наборов данных в `TradeRuleValidator`;
* обычный sync позиций, если validator не выявил нарушение;
* создание / обновление / закрытие позиций в БД;
* резолв внешнего статуса позиции в доменный статус.

### Не отвечает за:

* формирование `AnomalyReport`;
* выполнение kill-switch;
* блокировку торговли;
* переходы FSM;
* изменение `DealContext` напрямую.

---

## 2. OrderService

### Отвечает за:

* создание entry order;
* refresh entry order;
* refresh pending orders;
* sync обычных ордеров между биржей и БД;
* резолв внешних статусов ордеров в доменные статусы.

### Не отвечает за:

* принятие решения о стадии сделки;
* вызов kill-switch напрямую;
* формирование `AnomalyReport`.

---

## 3. AlgoOrderService

### Отвечает за:

* создание main protection;
* refresh active algo orders;
* cancel attached protection;
* amend main protection;
* sync algo-ордеров между биржей и БД;
* резолв внешних статусов algo-ордеров в доменные статусы.

### Не отвечает за:

* стратегические решения по сделке;
* формирование anomaly report;
* блокировку торговли.

---

## 4. BalanceService

### Отвечает за:

* чтение snapshot баланса с биржи;
* чтение балансов из БД;
* обновление или создание балансов в БД;
* хранение баланса как локального snapshot по бирже.

### Не отвечает за:

* торговые решения;
* anomaly report;
* kill-switch.

---

## 5. TradeRuleValidator

### Отвечает за:

* проверку торговых инвариантов;
* сравнение данных биржи и БД;
* принятие решения, является ли найденное состояние допустимым;
* запуск аварийного сценария при нарушении правил;
* вызов `KillSwitchService`;
* вызов `AnomalyService`;
* остановку обычного sync после нарушения.

### Не отвечает за:

* обычный sync сущностей;
* обновление `DealContext`;
* переходы FSM.

### Важный принцип

Validator — это точка принятия решения о нарушении правил.

Именно он решает:

* продолжать обычный sync;
* либо перевести выполнение в аварийный сценарий.

---

## 6. KillSwitchService

### Отвечает за:

* аварийное снятие риска по инструменту;
* закрытие позиций;
* отмену обычных ордеров;
* отмену algo-ордеров;
* приведение инструмента в безопасное состояние.

### Не отвечает за:

* проверку правил;
* формирование отчёта об аномалии;
* sync happy-path сущностей.

---

## 7. AnomalyService

### Отвечает за:

* создание `AnomalyReport`;
* обновление его статусов;
* сохранение snapshot до и после аварийной обработки;
* фиксацию ошибки обработки через `message` и статус `ERROR`.

### Не отвечает за:

* торговые решения;
* sync позиций, ордеров и баланса;
* kill-switch.

---

## 8. DealContextService

### Отвечает за:

* полную сборку `DealContext` после выполнения команд;
* загрузку `Deal`, `Exchange`, `Instrument`;
* загрузку `Order`, `Position`, `AlgoOrder`;
* загрузку `MarketPhase`, `Strategy`, `StrategyDetails`.

### Не отвечает за:

* изменение сущностей;
* выполнение команд;
* валидацию торговых правил.

---

## 9. DealStateMachine / Handlers

### Отвечают за:

* анализ доменных фактов;
* определение следующего шага процесса;
* выбор команд;
* переходы по статусам сделки.

### Не отвечают за:

* резолв внешних статусов биржи;
* sync данных;
* anomaly report;
* kill-switch.

---

## Как должен выглядеть правильный flow команды

### Пример: REFRESH_POSITIONS

```text
1. Handler вернул REFRESH_POSITIONS
2. Executor вызвал PositionService
3. PositionService:
   - прочитал внешние позиции
   - прочитал внутренние позиции
   - передал данные в TradeRuleValidator
4. Если validator ничего не выявил:
   - PositionService выполнил обычный sync
5. Если validator выявил нарушение:
   - TradeRuleValidator вызвал KillSwitchService
   - TradeRuleValidator вызвал AnomalyService
   - обычный sync был остановлен
6. Orchestrator заново пересобрал DealContext
```

---

## Границы по входным данным

### Что можно передавать в sync-сервисы

Лучше передавать только минимально нужные данные:

* `Exchange`
* `Instrument`
* при необходимости `Long dealId`

### Что не нужно передавать в sync-сервисы

Не нужно передавать:

* `DealContext`
* весь `Deal`, если нужен только `dealId`

Причина:

* чем уже контракт сервиса, тем чище архитектура;
* меньше лишней связанности со state machine слоем.

---

## Кто резолвит статусы

Резолв внешних статусов в доменные статусы делают именно sync-сервисы:

* `OrderService`
* `PositionService`
* `AlgoOrderService`

FSM не должна знать значения внешних статусов биржи.

FSM работает только с доменными фактами:

* активна позиция или нет;
* финализирован ордер или нет;
* есть основная защита или нет.

---

## Что считается нарушением архитектуры

Нарушением считаются ситуации, когда:

* `PositionService` сам вызывает `KillSwitchService` без validator;
* `AnomalyService` сам принимает торговое решение;
* handler напрямую ходит на биржу;
* executor начинает валидировать бизнес-правила;
* FSM начинает знать внешние статусы биржи;
* sync-сервис напрямую меняет `DealContext`.

---

## Короткий итог

Правильное разделение такое:

* **sync-сервисы** — читают биржу и БД, синкают факты;
* **TradeRuleValidator** — проверяет правила и решает, допустимо ли состояние;
* **KillSwitchService** — выполняет аварийную реакцию;
* **AnomalyService** — фиксирует и сопровождает `AnomalyReport`;
* **FSM/handlers** — управляют жизненным циклом сделки, но не знают деталей sync и аварийной обработки.
