# Команда REFRESH_POSITIONS — полное описание

## Цель

Команда `REFRESH_POSITIONS` нужна для синхронизации фактического состояния позиций по инструменту между биржей и
локальной БД.

Это **не торговое решение** и **не аварийный сценарий**.

Команда должна:

* прочитать фактические позиции на бирже по инструменту;
* прочитать текущие позиции из БД по инструменту;
* передать оба набора данных в проверку торговых инвариантов;
* если инварианты не нарушены — выполнить обычный sync;
* если инварианты нарушены — не продолжать обычный sync.

---

## Где используется

Команда `REFRESH_POSITIONS` возвращается state machine как сервисная команда.

Её исполняет `ServiceCommandExecutor`, который вызывает `PositionService`.

Примерно так:

* handler решил, что нужно обновить позиции;
* executor вызвал `PositionService.refreshPositions(...)`;
* сервис обновил состояние в БД;
* orchestrator затем заново пересобрал `DealContext`.

Важно:

* `REFRESH_POSITIONS` не обновляет `DealContext` напрямую;
* после выполнения команды контекст перечитывается отдельно.

---

## Входные данные

Для выполнения команды нужны:

* `Exchange exchange`
* `Instrument instrument`
* `Long dealId` — только если при создании новой позиции требуется обязательная привязка к сделке

Если новая позиция может существовать только вместе с `dealId`, то лучше передавать именно `dealId`, а не весь `Deal`.

Плохо:

```java
refreshPositions(Exchange exchange, Instrument instrument, Deal deal)
```

Хорошо:

```java
refreshPositions(Exchange exchange, Instrument instrument, Long dealId)
```

---

## Общий flow выполнения

### Шаг 1. Прочитать данные с биржи

`PositionService` должен запросить позиции по инструменту у клиентского сервиса биржи.

На этом этапе нужно получить snapshot позиций по конкретному инструменту.

Ожидаемый результат:

* список внешних snapshot-позиций;
* либо пустой список, если открытых позиций нет.

### Шаг 2. Прочитать данные из БД

`PositionService` должен загрузить из БД текущее состояние позиций по инструменту.

Обычно интересуют:

* активные позиции;
* либо последняя известная позиция по инструменту, если активной уже нет.

### Шаг 3. Передать данные в `TradeRuleValidator`

`PositionService` не должен сам принимать решение о наличии торговой аномалии.

Он должен передать в `TradeRuleValidator`:

* `exchange`
* `instrument`
* внешние позиции с биржи
* внутренние позиции из БД

`TradeRuleValidator` проверяет инварианты.

Если всё нормально — возвращается управление в `PositionService`.

Если найдено нарушение — validator сам запускает нужные сервисы:

* `KillSwitchService`
* `AnomalyService`

После этого validator должен остановить обычный sync, например через исключение.

### Шаг 4. Выполнить обычный sync

Если validator не обнаружил критичного нарушения и не прервал flow, `PositionService` выполняет обычную синхронизацию.

### Шаг 5. Сохранить изменения в БД

Все изменения по позициям должны быть сохранены в БД.

### Шаг 6. Перечитать контекст

После завершения команды orchestrator отдельно перезагружает `DealContext`.

## Что считается обычным sync

### Сценарий 1. Позиция есть на бирже и есть в БД

Нужно:

* обновить существующую позицию в БД;
* обновить поля из snapshot;
* отдельно резолвить доменный статус позиции.

### Сценарий 2. Позиция есть на бирже, но в БД её нет

Нужно:

* создать новую позицию;
* привязать её к инструменту;
* при необходимости привязать к `dealId`;
* заполнить поля из snapshot;
* сохранить в БД.

Важно:

* позиция создаётся биржей, не нами;
* локальная система только отражает этот факт.

### Сценарий 3. На бирже позиции нет, но в БД позиция есть

Нужно:

* обновить существующую позицию в БД;
* перевести её в доменный закрытый статус;
* сохранить в БД.

Важно:

* не удалять запись;
* не игнорировать исчезновение позиции;
* это тоже sync, а не удаление.

### Сценарий 4. На бирже позиции нет и в БД позиции нет

Ничего не делать.

Это штатный сценарий.

---

## Кто создаёт позицию

Позиция — это сущность, инициатором которой является биржа.

Это значит:

* локальная система не создаёт позицию как бизнес-решение;
* локальная система создаёт запись о позиции только потому, что увидела её на бирже.

Это ключевое отличие от `Order`, который инициируется системой.

---

## Резолв статуса позиции

Резолв внешнего статуса в доменный статус должен происходить в `PositionService`.

Для этого нужен отдельный helper-метод, например:

```java
private Position.Status resolvePositionStatus(PositionExternalSnapshot snapshot)
```

State machine не должна знать внешние статусы биржи.

FSM работает только с уже нормализованными доменными статусами.

---

## Что не должен делать PositionService внутри REFRESH_POSITIONS

`PositionService` не должен:

* сам формировать `AnomalyReport`;
* сам выполнять kill-switch;
* сам принимать решение о критичности аномалии;
* сам менять `DealContext`;
* сам принимать решения FSM;
* сам блокировать торговлю по инструменту.

Он только:

* читает данные;
* передаёт их в validator;
* при нормальном результате делает sync;
* сохраняет данные в БД.

---

## Роль TradeRuleValidator в этом flow

`TradeRuleValidator` — точка проверки торговых инвариантов перед обычным sync.

Он должен:

* сравнить внешние и внутренние данные;
* определить, есть ли нарушение правил;
* при нарушении:

    * вызвать `KillSwitchService`;
    * вызвать `AnomalyService`;
    * остановить обычный sync.

Таким образом:

* `PositionService` остаётся use-case сервисом команды;
* `TradeRuleValidator` отвечает за правила;
* `KillSwitchService` отвечает за аварийную реакцию;
* `AnomalyService` отвечает за отчёт об инциденте.

---

## Ожидаемая сигнатура

Рекомендуемая сигнатура:

```java
public void refreshPositions(Exchange exchange, Instrument instrument, Long dealId)
```

Если в проекте допускается создание позиции без `dealId`, можно оставить вариант без него.

Но если для новой позиции обязательна связь со сделкой, лучше явно передавать именно `dealId`, а не весь `Deal`.

---

## Пример упрощённого flow

```text
1. PositionService читает позиции с биржи по instrument
2. PositionService читает позиции из БД по instrument
3. PositionService передаёт оба набора данных в TradeRuleValidator
4. Если validator выявил нарушение:
   - запускаются KillSwitchService и AnomalyService
   - обычный sync останавливается
5. Если validator ничего не выявил:
   - PositionService создаёт / обновляет / закрывает позиции в БД
6. Orchestrator потом заново грузит DealContext
```

## Инварианты команды

### До выполнения

* известна биржа;
* известен инструмент;
* есть доступ к биржевому клиенту;
* есть доступ к persistence-слою.

### После успешного выполнения

* локальная БД отражает актуальное состояние позиций по инструменту;
* если позиция есть на бирже — она существует в БД в актуальном виде;
* если позиция исчезла на бирже — в БД она переведена в закрытый статус;
* `DealContext` может быть безопасно пересобран.

### После аварийного сценария

* обычный sync не продолжается;
* аварийная реакция и отчёт об аномалии уже запущены через validator.

---

## Короткий итог

`REFRESH_POSITIONS` — это команда синхронизации фактических позиций по инструменту.

Она:

* читает биржу и БД;
* прогоняет данные через `TradeRuleValidator`;
* если всё нормально — синкает позиции;
* если есть нарушение — не продолжает обычный sync.

Это не торговое решение, не kill-switch и не отчёт об аномалии.
