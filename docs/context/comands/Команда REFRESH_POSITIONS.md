# Команда REFRESH_POSITIONS — executor flow

## Цель

Команда `REFRESH_POSITIONS` нужна для синхронизации фактического состояния позиций по инструменту между биржей и
локальной БД.

Это обычная sync-команда.

Но если в процессе проверки найдено нарушение торговых инвариантов, команда должна быть аварийно прервана через
`TradeRuleValidator`.

---

## Кто выполняет команду

Команда должна выполняться не через `PositionService.refreshPositions(...)`, а через отдельный executor:

* `ServiceCommandExecutor`
* `RefreshPositionExecutor`

Фасадный `PositionService` может существовать как удобная точка входа, но реальный use-case `REFRESH_POSITIONS` должен
жить в отдельном executor.

---

## Правильная цепочка вызовов

```text
Handler
  -> ServiceCommandExecutor
     -> RefreshPositionExecutor
        -> TradeRuleValidator
           -> AnomalyService
           -> KillSwitchService
              -> ClosePositionExecutor
        -> обычный sync, если validator ничего не выявил
```

Важно:

* `RefreshPositionExecutor` не должен напрямую вызывать `KillSwitchService`;
* `KillSwitchService` не должен вызывать `RefreshPositionExecutor`.

---

## Входные данные

Для `RefreshPositionExecutor` нужны:

* `Exchange exchange`
* `Instrument instrument`
* `Long dealId` — если при создании новой позиции обязательна привязка к сделке

Если новая позиция обязана быть связана со сделкой, лучше передавать именно `dealId`, а не весь `Deal`.

---

## Общий flow выполнения

### Шаг 1. Прочитать внешние позиции

`RefreshPositionExecutor` должен запросить у клиентского сервиса биржи позиции по инструменту.

Ожидаемый результат:

* список `PositionExternalSnapshot`;
* либо пустой список, если открытых позиций нет.

### Шаг 2. Прочитать внутренние позиции

`RefreshPositionExecutor` должен загрузить из БД **только релевантные для sync** позиции по инструменту.

Для обычного sync нельзя читать все позиции по инструменту без фильтра, потому что исторических записей со временем
станет слишком много.

Для операционного refresh нужны:

* активные позиции по инструменту;
* либо ограниченный и явный набор последних релевантных записей, если это требуется договорённостью.

Базовое правило:

* для действий читаем **по инструменту + по живым статусам**;
* полный исторический срез не используется для операционного refresh.

### Шаг 3. Передать данные в `TradeRuleValidator`

`RefreshPositionExecutor` не должен сам принимать решение о наличии аномалии.

Он должен передать в `TradeRuleValidator.validatePositions(...)`:

* `exchange`
* `instrument`
* `dealId`
* внешние позиции
* внутренние позиции

Если validator ничего не выявил — управление возвращается в executor.

Если validator выявил нарушение — он сам:

* создаёт и ведёт `AnomalyReport`;
* выполняет полный аварийный сценарий через `KillSwitchService`;
* выбрасывает `TradeRuleViolationException`.

После этого обычный refresh не продолжается.

### Шаг 4. Выполнить обычный sync

Если validator не выбросил исключение, `RefreshPositionExecutor` выполняет sync.

### Шаг 5. Сохранить изменения в БД

Все изменения по позициям должны быть сохранены в БД.

### Шаг 6. Перечитать `DealContext`

После завершения команды orchestrator отдельно перезагружает `DealContext`.

---

## Что считается обычным sync

### Сценарий 1. Позиция есть на бирже и есть в БД

Нужно:

* обновить существующую позицию в БД;
* обновить поля из snapshot;
* отдельно резолвить доменный статус позиции.

### Сценарий 2. Позиция есть на бирже, но в БД её нет

Нужно:

* создать новую позицию;
* привязать её к инструменту;
* при необходимости привязать к `dealId`;
* заполнить поля из snapshot;
* сохранить в БД.

Важно:

* позиция создаётся биржей, не нами;
* локальная система только отражает этот факт.

### Сценарий 3. На бирже позиции нет, но в БД есть активная позиция

Нужно:

* обновить существующую позицию в БД;
* перевести её в доменный закрытый статус;
* сохранить в БД.

### Сценарий 4. На бирже позиции нет и в БД нет активной позиции

Ничего не делать.

---

## Что не должен делать RefreshPositionExecutor

`RefreshPositionExecutor` не должен:

* сам создавать `AnomalyReport`;
* сам вызывать `KillSwitchService`;
* сам определять критичность;
* сам менять `DealContext`;
* сам принимать решения FSM.

Он только:

* читает данные;
* вызывает validator;
* при нормальном результате делает sync;
* сохраняет данные в БД.

---

## Кто резолвит статус позиции

Резолв внешнего статуса позиции в доменный статус делает именно `RefreshPositionExecutor` или используемый им
sync-компонент.

Пример helper-метода:

```java
private Position.Status resolvePositionStatus(PositionExternalSnapshot snapshot)
```

FSM не должна знать внешние статусы биржи.

---

## Как команда должна завершаться при аномалии

Если найдено нарушение:

* `TradeRuleValidator` полностью обрабатывает аномалию;
* обычный sync не продолжается;
* команда прерывается через `TradeRuleViolationException`.

Это осознанное прерывание flow, а не неожиданная техническая ошибка.

---

## Короткий итог

`REFRESH_POSITIONS` должен выполняться через `RefreshPositionExecutor`.

Он:

* читает внешние и внутренние позиции;
* передаёт их в `TradeRuleValidator`;
* если всё нормально — синкает позиции;
* если найдено нарушение — validator полностью обрабатывает аномалию и прерывает команду исключением.
