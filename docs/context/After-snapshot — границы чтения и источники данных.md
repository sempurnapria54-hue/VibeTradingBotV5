# After-snapshot — границы чтения и источники данных

## Цель

Эта дока уточняет, откуда именно должен собираться `afterSnapshot` после kill-switch и где проходят границы между:

* активными сущностями;
* связанными неактивными сущностями;
* внутренними и внешними источниками.

---

## Главный принцип

`afterSnapshot` не должен быть:

* просто дампом всей истории по `instrumentId`;
* и не должен быть только голым active-state.

Он должен быть расследовательским snapshot'ом по инструменту.

---

## Внутренние данные

### Active

Берём из БД по:

* `instrumentId + live statuses`

Это то, что реально ещё осталось живым после kill-switch.

### RelatedInactive

Берём ограниченно.

Приоритетные источники:

1. сущности из `beforeSnapshot`, которые после kill-switch стали неактивными;
2. живая/последняя сделка по инструменту;
3. ограниченный набор последних завершённых сущностей, если он нужен для расследования.

Не нужно читать весь архив по инструменту.

---

## Внешние данные

### Active

Берём из обычных active endpoints биржи:

* позиции по инструменту;
* active/pending orders;
* active/pending algo-orders.

Если биржа по этим endpoints отдаёт только живые сущности — это нормально.

### RelatedInactive

На первом этапе допустимо не собирать полноценно.

Если позже понадобится, можно добирать:

* через history endpoints;
* через точечный поиск по внешним id из `beforeSnapshot`.

---

## Практическое правило на сейчас

### Что обязательно сделать

* перестать читать всё по `instrumentId` для after-report как бесконечную историю;
* разделить snapshot на `active` и `relatedInactive` хотя бы на внутренней стороне;
* внешнюю сторону оставить сначала в виде active-state, если history endpoints пока не хочется подключать.

### Что можно отложить

* полноценный внешний `relatedInactive`
* сложную snapshot-модель по всем видам исторических сущностей

---

## Короткий итог

На текущем этапе хороший after-snapshot — это:

* внутренний `active + relatedInactive`
* внешний хотя бы `active`, а дальше при необходимости расширяется

Такой подход уже сильно лучше, чем просто `findByInstrumentId(...)` по всем сущностям без границ.
