# KillSwitchService — полное описание метода аварийного закрытия по инструменту

## Цель

`KillSwitchService` — это сервис полного аварийного снятия риска по инструменту.

Он нужен для ситуаций, когда normal flow сопровождения сделки больше нельзя считать безопасным.

Примеры:

* обнаружена торговая аномалия;
* нарушены базовые инварианты по инструменту;
* найдено критичное расхождение между биржей и БД;
* требуется аварийно зачистить все живые сущности по инструменту.

`KillSwitchService` не принимает решение, есть аномалия или нет.

Он только исполняет аварийный сценарий.

---

## Главное назначение

Метод `executeKillSwitch(...)` должен привести инструмент в безопасное состояние.

Под безопасным состоянием понимается:

* на бирже нет открытых позиций по инструменту;
* на бирже нет pending обычных ордеров по инструменту;
* на бирже нет active/pending algo-ордеров по инструменту;
* в локальной БД нет живых сущностей, которые выглядят как продолжающийся торговый процесс по инструменту.

---

## Граница ответственности

### `KillSwitchService` отвечает за:

* отмену обычных ордеров по инструменту;
* отмену algo-ордеров по инструменту;
* аварийное закрытие позиции по инструменту;
* обновление локальных сущностей в БД после аварийного сценария;
* финальную верификацию результата;
* формирование результата выполнения kill-switch.

### `KillSwitchService` не отвечает за:

* поиск аномалии;
* принятие решения о критичности;
* создание `AnomalyReport`;
* перевод `AnomalyReport` по статусам;
* продолжение или остановку обычного sync.

Это ответственность `TradeRuleValidator` и `AnomalyService`.

---

## На каком уровне выполняется kill-switch

Kill-switch выполняется **по инструменту**, а не по одной сделке.

Это принципиально важно.

Если по инструменту обнаружена критичная аномалия, нужно зачистить **все живые сущности по инструменту**, а не только
те, которые удобно привязать к одной конкретной сделке.

---

## Рекомендуемая сигнатура

Предпочтительная сигнатура:

```java
public KillSwitchResult executeKillSwitch(Exchange exchange,
                                          Instrument instrument,
                                          Long dealId,
                                          String reasonCode)
```

### Пояснение параметров

#### `Exchange exchange`

Нужен для выбора корректного клиента биржи и работы с нужным торговым аккаунтом.

#### `Instrument instrument`

Ключевой объект, потому что kill-switch выполняется именно по инструменту.

#### `Long dealId`

Nullable-параметр.

Может пригодиться:

* для аудита;
* для связи с текущей сделкой;
* для локального поиска связанных сущностей.

Но kill-switch не должен ограничиваться только этой сделкой.

#### `String reasonCode`

Машинно-читаемый код причины, по которой сработал kill-switch.

Примеры:

* `OVERHEAD_POSITIONS_COUNT`
* `POSITION_STATE_MISMATCH`
* `UNKNOWN_PENDING_ORDER`

`reasonCode` нужен для логирования и аудита.

---

## Почему метод должен возвращать результат

Метод не должен быть `void`.

Он должен вернуть отдельный объект результата, например `KillSwitchResult`.

Это нужно, чтобы вызывающий код, например `TradeRuleValidator`, мог:

* понять, kill-switch завершился успешно или нет;
* получить `internalAfter`;
* получить `externalAfter`;
* решить, ставить `COMPLETED` или `ERROR` в `AnomalyReport`.

---

## Рекомендуемая модель результата

```java
public class KillSwitchResult {

    /**
     * Успешно ли завершился kill-switch.
     */
    private boolean success;

    /**
     * Внутренний снимок состояния после kill-switch.
     */
    private String internalAfter;

    /**
     * Внешний снимок состояния после kill-switch.
     */
    private String externalAfter;

    /**
     * Текст ошибки или пояснение результата.
     */
    private String message;
}
```

На первом этапе можно сделать и более простую модель, но идея должна быть именно такой.

---

## Что значит “закрыть всё по инструменту”

### На бирже нужно зачистить:

* все открытые позиции по инструменту;
* все pending обычные ордера по инструменту;
* все active/pending algo-ордера по инструменту;
* при необходимости attached-защиты, если они ещё существуют как управляемые сущности.

### В БД нужно зачистить:

* все активные позиции по инструменту;
* все живые обычные ордера по инструменту;
* все живые algo-ордера по инструменту;
* при необходимости обновить статус инструмента, если политика блокировки живёт там.

---

## Полный flow метода executeKillSwitch(...)

### Шаг 1. Прочитать текущее состояние до действий

Перед выполнением аварийного сценария сервис должен вычитать всё релевантное состояние по инструменту.

#### Из БД:

* активные позиции;
* живые обычные ордера;
* живые algo-ордера;
* при необходимости статус инструмента.

#### С биржи:

* открытые позиции по инструменту;
* pending обычные ордера по инструменту;
* active/pending algo-ордера по инструменту.

Это состояние не обязательно возвращать наружу как отдельный результат kill-switch, потому что before-снимки обычно уже
собраны раньше в `TradeRuleValidator`.

Но внутри метода эти данные нужны для понимания, что именно нужно снимать.

---

### Шаг 2. Заблокировать инструмент для новых торговых действий

Если в проекте блокировка торговли живёт в статусе инструмента, то в самом начале kill-switch инструмент нужно перевести
в запрещённое состояние.

Смысл:

* никакой параллельный happy-path не должен успеть снова открыть риск;
* сопровождающие команды не должны продолжать нормальную работу по инструменту.

Если блокировка инструмента реализуется в другом месте, это нужно явно учесть, но в любом случае kill-switch должен
работать так, как будто инструмент уже выведен из normal flow.

---

### Шаг 3. Отменить обычные ордера на бирже

Нужно отменить все pending обычные ордера по инструменту.

Смысл:

* убрать висящие входы;
* убрать потенциальные доборы;
* убрать хвосты, которые могут снова создать риск.

---

### Шаг 4. Отменить algo-ордера на бирже

Нужно отменить все active/pending algo-ордера по инструменту.

Смысл:

* убрать устаревшие SL/TP/trailing;
* убрать всё, что может остаться висеть после закрытия позиции;
* привести защитный слой в предсказуемое состояние.

---

### Шаг 5. Закрыть позицию на бирже

Если по инструменту есть открытая позиция, её нужно аварийно закрыть.

Политика закрытия зависит от проекта, но итог должен быть один:

* после kill-switch по инструменту не должно остаться открытой позиции.

---

### Шаг 6. Обновить локальные сущности в БД

После действий на бирже нужно синхронизировать БД.

Нужно обновить:

* позиции;
* обычные ордера;
* algo-ордера.

Это должны быть именно понятные аварийные статусы и причины завершения.

Примеры:

* позиция → аварийно закрыта;
* обычный ордер → отменён / закрыт;
* algo-ордер → отменён / закрыт.

Важно:

* не удалять записи;
* не оставлять живые сущности в подвешенном состоянии.

---

### Шаг 7. Повторно прочитать состояние после действий

После выполнения kill-switch сервис обязан заново вычитать состояние по инструменту.

#### На бирже ожидается:

* нет открытых позиций;
* нет pending обычных ордеров;
* нет active/pending algo-ордеров.

#### В БД ожидается:

* нет активной позиции;
* нет живых pending обычных ордеров;
* нет живых active/pending algo-ордеров.

Именно эти данные должны лечь в `internalAfter` и `externalAfter`.

---

### Шаг 8. Сформировать `KillSwitchResult`

Если после повторной проверки всё зачистилось успешно:

* `success = true`
* возвращаются `internalAfter` и `externalAfter`

Если что-то осталось или произошла ошибка:

* `success = false`
* `message` содержит описание ошибки или остаточного риска
* `internalAfter` и `externalAfter` всё равно возвращаются по возможности

---

## Что должно входить в after-снимки

### `internalAfter`

Минимально должен содержать:

* инструмент;
* статус инструмента;
* позиции по инструменту;
* обычные ордера по инструменту;
* algo-ордера по инструменту.

### `externalAfter`

Минимально должен содержать:

* внешний идентификатор инструмента;
* позиции по инструменту;
* обычные ордера по инструменту;
* algo-ордера по инструменту.

---

## Что важно про before/after слепки

В `AnomalyReport` должны лежать **полные слепки по инструменту**, а не только “то, что validator сейчас проверял”.

То есть:

* `internalBefore` — всё релевантное внутреннее состояние по инструменту до kill-switch;
* `externalBefore` — всё релевантное внешнее состояние по инструменту до kill-switch;
* `internalAfter` — всё релевантное внутреннее состояние по инструменту после kill-switch;
* `externalAfter` — всё релевантное внешнее состояние по инструменту после kill-switch.

Смысл этих слепков:

* понять, что именно было по инструменту до аварии;
* понять, что именно осталось после аварийного сценария;
* доказать, что kill-switch реально зачистил всё по инструменту;
* либо показать, что зачистить полностью не удалось.

---

## Что считается успешным kill-switch

Kill-switch считается успешным, если одновременно выполняются условия:

* на бирже нет открытой позиции по инструменту;
* на бирже нет pending обычных ордеров по инструменту;
* на бирже нет active/pending algo-ордеров по инструменту;
* в БД нет живой активной позиции по инструменту;
* в БД нет живых pending обычных ордеров по инструменту;
* в БД нет живых active/pending algo-ордеров по инструменту.

Если хотя бы одно из этих условий не выполнено, kill-switch не считается полностью успешным.

---

## Что не должен делать KillSwitchService

`KillSwitchService` не должен:

* определять, есть аномалия или нет;
* создавать `AnomalyReport`;
* определять `severity`;
* определять `code` аномалии;
* решать, продолжать обычный sync или нет.

Это всё ответственность `TradeRuleValidator`.

---

## Взаимодействие с другими сервисами

### `TradeRuleValidator`

Вызывает `KillSwitchService`, получает `KillSwitchResult`, затем:

* обновляет `AnomalyReport`;
* ставит `KILL_SWITCH_EXECUTED` и `COMPLETED` или `ERROR`;
* выбрасывает `TradeRuleViolationException`.

### `AnomalyService`

Не вызывает kill-switch сам.

Он только ведёт `AnomalyReport`.

### `AnomalyJob`

Если процесс оборвался на середине, job может повторно вызвать kill-switch или дожать обработку в зависимости от
текущего статуса `AnomalyReport`.

---

## Короткий итог

`KillSwitchService.executeKillSwitch(...)` — это метод полного аварийного снятия риска по инструменту.

Он должен:

* зачистить всё живое по инструменту на бирже;
* синхронизировать и зачистить локальные сущности в БД;
* повторно проверить результат;
* вернуть `KillSwitchResult` с итоговым after-снимком по инструменту.

Он не ищет аномалии и не принимает решение о критичности.

Он только исполняет аварийный сценарий максимально полно и предсказуемо.
