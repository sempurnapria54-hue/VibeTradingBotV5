# Report after-snapshot — стратегия рефакторинга

## Цель

Эта дока фиксирует, как должен быть устроен `readAfterSnapshot(...)` для аварийного сценария.

Сейчас основная проблема в том, что after-snapshot слишком грубо читается по `instrumentId` и потенциально тащит всю
историю сущностей по инструменту.

Нужно сделать snapshot полезным для расследования и при этом не превращать его в бесконечный дамп.

---

## Главный принцип

After-snapshot для `AnomalyReport` должен быть:

* достаточно полным для расследования;
* достаточно ограниченным, чтобы не тащить всю историю по инструменту.

То есть нужен не подход:

* “читать вообще всё по `instrumentId`”,

а подход:

* `active`
* `relatedInactive`

---

## Что такое `active`

`active` — это все живые сущности по инструменту после выполнения kill-switch.

Смысл:

* показать, что реально ещё осталось живым;
* показать, зачистился ли риск полностью.

Для `active` нужны:

* активные позиции;
* живые обычные ордера;
* живые algo-ордера;
* живые сделки.

Если kill-switch успешен, этот раздел должен быть пустым или почти пустым.

---

## Что такое `relatedInactive`

`relatedInactive` — это ограниченный набор уже неактивных, но релевантных сущностей по инструменту, которые нужны для
расследования.

Смысл:

* показать, что именно стало финальным состоянием после аварийного сценария;
* не тащить всю историческую ленту по инструменту.

Примеры:

* только что закрытая позиция;
* только что отменённые ордера;
* только что отменённые algo-ордера;
* только что аварийно завершённая сделка.

---

## Почему нельзя читать просто всё по `instrumentId`

Если читать всё по инструменту без ограничений, очень быстро получим:

* огромные JSON в `AnomalyReport`;
* мусор из старых сделок и старых ордеров;
* плохую читаемость расследования;
* тяжёлые запросы и ненужную нагрузку.

Такой snapshot перестанет быть полезным.

---

## Рекомендуемая структура after-snapshot

### Internal after

```json
{
  "instrument": {},
  "active": {
    "positions": [],
    "orders": [],
    "algoOrders": [],
    "deals": []
  },
  "relatedInactive": {
    "positions": [],
    "orders": [],
    "algoOrders": [],
    "deals": []
  }
}
```

### External after

```json
{
  "instrumentExternalId": "...",
  "active": {
    "positions": [],
    "orders": [],
    "algoOrders": []
  },
  "relatedInactive": {
    "positions": [],
    "orders": [],
    "algoOrders": []
  }
}
```

---

## Что важно для `externalAfter`

Если биржевые endpoints по своей природе возвращают только активные сущности, это нормально для секции `active`.

Но для `relatedInactive`, если это потребуется позже, можно использовать:

* данные, найденные по внешним id из внутреннего before-state;
* отдельные history endpoints;
* либо оставить эту секцию пустой на первом этапе.

То есть на первом этапе допустимо:

* `externalAfter.active` — заполняется из обычных active endpoints;
* `externalAfter.relatedInactive` — пусто или минимально.

---

## Как собирать `relatedInactive` внутри БД

`relatedInactive` не должен означать:

* все старые неактивные сущности по инструменту.

Нужен ограниченный набор, например:

* сущности, которые были живыми в `beforeSnapshot`, а после kill-switch стали неактивными;
* сущности, связанные с текущим `dealId`, если это полезно;
* последняя релевантная завершённая сделка по инструменту.

То есть `relatedInactive` — это именно хвост расследования, а не история за всё время.

---

## Как разделить чтение технически

### `readBeforeSnapshot(...)`

Пока может оставаться сфокусированным на активных/live сущностях, если именно это нужно для проверки и kill-switch.

### `readAfterSnapshot(...)`

Нужно переработать так, чтобы он собирал:

* `active`
* `relatedInactive`

Если это слишком много для одной модели `StateSnapshot`, можно:

* либо расширить `StateSnapshot`;
* либо ввести отдельную report-модель snapshot.

---

## Минимальный acceptable шаг

Если пока не хочется проектировать сложную snapshot-модель, то минимально допустимо:

* оставить `active` как есть;
* ограничить `relatedInactive` только сущностями из `beforeSnapshot`, которые стали неактивными после kill-switch.

Это уже будет сильно лучше, чем просто читать всё по `instrumentId`.

---

## Короткий итог

`readAfterSnapshot(...)` нужно рефакторить не в сторону “читать всё”, а в сторону:

* `active`
* `relatedInactive`

Это даст:

* полезный after-report;
* контролируемый объём snapshot;
* понятную картину того, что именно осталось живым и что именно было аварийно завершено.
