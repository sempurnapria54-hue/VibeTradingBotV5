# TradeRuleValidator — модель, роль и flow

## Цель

`TradeRuleValidator` — это отдельный сервис проверки торговых инвариантов перед выполнением обычного sync.

Он нужен для того, чтобы отделить:

* обычную синхронизацию фактов биржи и БД;
* проверку допустимости состояния;
* запуск аварийного сценария при нарушении правил.

`TradeRuleValidator` не является частью FSM и не заменяет sync-сервисы.

---

## Главное назначение

`TradeRuleValidator` отвечает на вопрос:

> допустимо ли текущее состояние системы, или уже обнаружена торговая аномалия?

Если состояние допустимо, validator просто возвращает управление назад в sync-сервис.

Если состояние недопустимо, validator:

* определяет код аномалии;
* определяет критичность;
* запускает аварийный сценарий через `KillSwitchService`;
* инициирует фиксацию аномалии через `AnomalyService`;
* останавливает обычный flow, например через исключение.

---

## Почему validator нужен отдельно

Без `TradeRuleValidator` sync-сервисы начинают смешивать в себе слишком много обязанностей:

* читать биржу;
* читать БД;
* проверять инварианты;
* решать, аномалия это или нет;
* выполнять аварийную реакцию;
* формировать отчёт.

Это делает сервисы тяжёлыми и плохо тестируемыми.

С отдельным validator получается чистое разделение:

* sync-сервис читает данные;
* validator проверяет правила;
* `KillSwitchService` снимает риск;
* `AnomalyService` пишет репорт.

---

## Место в архитектуре

### Sync-сервис

Например, `PositionService`:

* читает snapshot с биржи;
* читает текущее состояние из БД;
* передаёт оба набора данных в `TradeRuleValidator`;
* если validator не выявил нарушение — делает обычный sync.

### TradeRuleValidator

* анализирует входные данные;
* проверяет инварианты;
* при нарушении запускает аварийный сценарий и останавливает обычный sync.

### KillSwitchService

* выполняет аварийное снятие риска.

### AnomalyService

* формирует и сопровождает `AnomalyReport`.

### FSM / handlers

* вообще не знают деталей validator;
* получают уже итоговые доменные факты после sync.

---

## Что validator должен уметь проверять

`TradeRuleValidator` должен уметь делать разные проверки для разных команд.

На уровне концепции у него есть отдельные направления проверки:

* проверка позиций;
* проверка обычных ордеров;
* проверка algo-ордеров;
* при необходимости в будущем — комплексная проверка по инструменту.

Не нужно делать один giant-method на всё сразу.

Лучше иметь отдельные методы:

* `validatePositions(...)`
* `validateOrders(...)`
* `validateAlgoOrders(...)`

А если понадобится единая точка маршрутизации — можно добавить отдельный фасадный метод.

---

## Первое применение: REFRESH_POSITIONS

На первом этапе validator нужен для команды `REFRESH_POSITIONS`.

Flow такой:

```text
1. PositionService читает позиции с биржи по instrument
2. PositionService читает позиции из БД по instrument
3. PositionService передаёт данные в TradeRuleValidator.validatePositions(...)
4. Если validator ничего не выявил:
   - PositionService делает обычный sync
5. Если validator выявил нарушение:
   - запускается kill-switch
   - формируется anomaly-report
   - обычный sync прекращается
```

---

## Какие данные получает validator

Validator должен принимать не `DealContext`, а только минимально нужные данные для проверки.

Для проверки позиций это обычно:

* `Exchange exchange`
* `Instrument instrument`
* `Long dealId` — если нужен для аварийного сценария
* `List<PositionExternalSnapshot> externalSnapshots`
* `List<Position> domainPositions`

Если `dealId` не нужен для конкретной проверки — лучше не передавать.

Главное правило:

* никаких лишних зависимостей от FSM;
* никаких запросов к `DealContext`;
* только необходимые данные.

---

## Что считается результатом проверки

### Сценарий 1. Всё ок

Validator не делает побочных действий.

Он просто возвращает управление обратно в sync-сервис.

### Сценарий 2. Найдено нарушение

Validator:

* классифицирует нарушение;
* выбирает `code`;
* выбирает `severity`;
* запускает аварийный сценарий;
* формирует `AnomalyReport`;
* останавливает обычный sync.

Остановка обычного sync может быть сделана через отдельное доменное исключение.

---

## Что validator должен запускать при нарушении

### 1. KillSwitchService

Validator вызывает `KillSwitchService`, чтобы перевести инструмент в безопасное состояние.

Пока на первом этапе допускается вызов заглушки.

### 2. AnomalyService

Validator вызывает `AnomalyService`, чтобы создать и затем сопровождать `AnomalyReport`.

На первом этапе допустимо реализовать только минимальную фиксацию репорта или оставить интеграцию как следующий шаг.

---

## Что validator не должен делать

`TradeRuleValidator` не должен:

* выполнять обычный sync позиций/ордеров;
* менять `DealContext`;
* принимать решения FSM;
* напрямую обновлять статусы сделки;
* резолвить внешние биржевые статусы в доменные — это делает соответствующий sync-сервис;
* превращаться в универсальный монолитный orchestrator.

---

## Примеры проверок для позиций

На уровне `REFRESH_POSITIONS` validator может проверять такие инварианты:

* на бирже по инструменту не более одной открытой позиции;
* в БД по инструменту не более одной активной позиции;
* внешнее и внутреннее состояние не противоречат базовым правилам;
* нет критичного расхождения, которое требует аварийной остановки.

Примеры кодов аномалий:

* `OVERHEAD_POSITIONS_COUNT`
* `UNKNOWN_POSITION`
* `POSITION_STATE_MISMATCH`

Точный набор кодов можно расширять позже.

## Как лучше организовать класс

На первом этапе лучше сделать один сервис `TradeRuleValidator` с отдельными методами по направлениям.

Примерно так:

```java
public class TradeRuleValidator {

    public void validatePositions(...) {
    }

    public void validateOrders(...) {
    }

    public void validateAlgoOrders(...) {
    }
}
```

Внутри допустимо использовать private helper-методы:

* `checkExternalPositionsCount(...)`
* `checkInternalPositionsCount(...)`
* `handleViolation(...)`
* `resolveSeverity(...)`
* `resolveCode(...)`

---

## Поведение при нарушении

Если найдено нарушение, обычный sync не должен продолжаться.

Поэтому лучший контракт такой:

* validator либо успешно завершает метод;
* либо запускает аварийный сценарий и бросает исключение.

Это делает поведение предсказуемым.

---

## Исключение

Рекомендуется отдельное доменное исключение, например:

* `TradeRuleViolationException`

Смысл:

* validator обнаружил нарушение;
* аварийный сценарий уже запущен;
* обычный sync надо прекратить.

---

## Взаимодействие с KillSwitchService

На первом этапе допустимо, чтобы validator вызывал только заглушку в `KillSwitchService`.

Например:

* `executeForTradeRuleViolation(...)`
* `executeStub(...)`

Это позволит встроить validator в flow уже сейчас, а потом нарастить реальную аварийную логику.

---

## Взаимодействие с AnomalyService

На первом этапе возможны два режима:

### Вариант A

Сразу создавать `AnomalyReport` внутри validator.

### Вариант B

Пока оставить только вызов kill-switch заглушки, а интеграцию с `AnomalyService` сделать следующим шагом.

Для первого каркаса допустим вариант B, если цель — быстро встроить validator в flow `REFRESH_POSITIONS`.

---

## Короткий итог

`TradeRuleValidator` — это точка проверки торговых инвариантов перед sync-операцией.

Он:

* получает внешние и внутренние данные;
* проверяет правила;
* если всё ок — возвращает управление sync-сервису;
* если не ок — запускает аварийный сценарий и останавливает обычный flow.

Это отдельный сервис правил, а не часть FSM и не часть обычной синхронизации.
