# Ключевание результатов расчёта рыночных данных по идентичности

## На какой вопрос отвечает этот файл

Почему результаты расчёта рыночных данных (`IndicatorValue`,
`MarketStructure`) ключуются по идентичности считаемого, а не по
настройке стратегии, которая его запросила, и почему `MarketPhase` —
осознанное исключение (ключ по контейнеру).

## Контекст

Ревизия Н3 (`GAPS_CLOSE_3`, `docs/decisions/strategy-tree-persistence.md`)
перевела листовые настройки (`StrategyIndicatorSetting`,
`StrategyMarketStructureSetting`) в JSONB внутри контейнера — отдельной
реляционной строки/`id` у них больше нет. Downstream-модели результатов
расчёта ключевались по настройке через её `id`:

- `IndicatorValue` (Фаза 3) — `UNIQUE(instrument_id,
  strategy_indicator_setting_id, …)`;
- `MarketStructure` (Фаза 4) — `UNIQUE(instrument_id,
  strategy_market_structure_setting_id, …)`.

После ревизии `*_setting_id` ссылаться не на что. Следствие шло как
открытый downstream-вопрос при закрытии `GAPS_CLOSE_3`; здесь
фиксируется решённое **направление** (точная схема — при реализации
кластеров).

## Принятое решение

Результаты расчёта ключуются по **идентичности считаемого** — тип +
`timeframe` + canonical-`params` (математические параметры расчёта), а
**не** по настройке стратегии. Индикатор / структура считается **раз на
инструмент** для данной идентичности и **шарится** всеми настройками,
которые его просят, — хоть из `Strategy.marketPhaseSetting`, хоть из
`StrategyDetail`. Ссылка на настройку (`strategy_indicator_setting_id` /
`strategy_market_structure_setting_id`) из результата **убирается**.

Это и снимает следствие ревизии Н3: результату больше не нужен
реляционный `id` настройки — он ключуется собственной идентичностью.

**Почему так.** Одна и та же конфигурация (тип + `timeframe` + params),
запрошенная из разных настроек, даёт идентичный результат расчёта —
дублировать вычисление и хранение по каждой настройке бессмысленно.
Шаринг по идентичности экономит расчёт и хранение и согласуется с тем,
что настройка иммутабельна и адресуется по `key`, а не по `id`.

**Отвергнутая альтернатива.** По-настройке ключевание (текущее
`UNIQUE(…, *_setting_id, …)`) — привязывает результат к `id` настройки
(которого при JSONB-хранении нет) и дублирует идентичный расчёт на
каждую настройку, ссылающуюся на ту же конфигурацию.

## Схема идентичности (реестр конфигураций)

Идентичность считаемого материализуется **реестром конфигураций** —
отдельной таблицей на тип результата (`indicator_configs` для
`IndicatorValue`, `market_structure_configs` для `MarketStructure`):

- **Строка реестра** = уникальная конфигурация расчёта (тип +
  `timeframe` + canonical-`params`) с собственным `id`. `UNIQUE` по
  канонической форме (тип + `timeframe` + canonical-`params`) гарантирует
  одну строку на конфигурацию.
- **Канонизация `params`** (стабильная сериализация для сравнения)
  считается **один раз — при регистрации конфигурации** в реестре, а не
  на каждом результате.
- **Результаты ссылаются на реестр** по `config_id` (FK). Ключ
  результата: `UNIQUE(instrument_id, config_id, candle_timestamp)` для
  `IndicatorValue`; `UNIQUE(instrument_id, config_id, window_end_at)` для
  `MarketStructure`. Так «считается раз на инструмент и шарится»
  выражено структурно: одна конфигурация — одна строка реестра — один
  ряд результатов, на который смотрят все настройки.
- **Свежесть** при этом остаётся per-настройка: `expirationDuration` —
  атрибут запрашивающей настройки, не конфигурации; результат шарится,
  а свежесть `MarketDataExpirationChecker` оценивает под каждую
  запрашивающую настройку в runtime (состояние свежести не хранится, см.
  `docs/rules/market-data-freshness.md`).

**Почему реестр** (а не inline-идентичность колонками на результате или
hash-колонка): структурно повторяет смысл решения — конфигурация это
самостоятельная сущность шаринга; FK компактен, канонизация считается
раз, а не в каждом значении; читаемо (в отличие от hash, у которого ещё
и теоретический риск коллизий). Согласуется с
`docs/rules/persistence-representation.md`: реестр — сущность, на которую
ссылаются FK из нескольких мест → реляционная строка по букве правила
(не «часть одного владельца»). Совпадает с границей владения
(`docs/rules/trading-configuration-ownership.md`): универсальная формула
расчёта — у системы, её параметры — у стратегии; реестр держит
параметризованную конфигурацию, которую система делит между стратегиями.

**Отвергнутые схемы.** Inline-идентичность (`type` / `timeframe` /
`params_canonical` колонками прямо на результате + `UNIQUE` по ним) —
канонизация и сравнение в каждом значении, широкий ключ. Hash-колон­ка
(`UNIQUE(instrument_id, identity_hash, timestamp)`) — компактно, но
идентичность нечитаема и есть риск коллизий.

## Исключение — `MarketPhase` (ключ по контейнеру)

`MarketPhase` ключуется **контейнером (per-strategy)** —
`UNIQUE(instrument_id, strategy_market_phase_setting_id, candle_timestamp)`,
а **не** по идентичности считаемого, как индикатор / структура. Это
**осознанное исключение** из правила шаринга-по-идентичности, не
молчаливое отступление.

**Основание исключения:**

- настройки фазы **специфичны для стратегии** — правила определения фазы
  авторские (`phaseRules`, см.
  `docs/decisions/market-phase-conditional-classification.md`), не
  сводятся к общей конфигурации `тип + timeframe + params` с единым
  `config_id`; общего «считаемого», которое стоило бы шарить между
  стратегиями, нет;
- фаза тянет **меньше данных**, чем индикатор / структура, — выигрыш
  шаринга по идентичности не оправдывает усложнение (реестр конфигураций
  + резолв общей строки).

Контейнер `StrategyMarketPhaseSetting` имеет реляционную строку/`id`
(ревизия Н3 коснулась только листовых настроек), поэтому ключ по
контейнеру технически доступен. Свежесть фазы оценивается на чтение под
запрашивающую настройку — единым механизмом со шаримыми результатами, без
хранимого состояния свежести (`docs/rules/market-data-freshness.md`).

## Границы и отложенное

- **Схема выбрана здесь** (реестр конфигураций). На `CODE` остаётся
  механика: конкретная стабильная сериализация `params` для канонической
  формы и форма регистрации конфигурации в реестре (lookup-or-insert при
  первом запросе).
- При реализации **проверить**, что прежнее по-настройке ключевание
  ничем не держалось (нет потребителя, которому нужен именно
  `*_setting_id`).
- Доки `IndicatorValue` / `MarketStructure` и job-доки `IndicatorJob` /
  `MarketStructureJob` приведены к реестру на `GAPS_CLOSE_3` (поле
  `setting` → `config_id`, `UNIQUE(…, *_setting_id, …)` →
  `UNIQUE(…, config_id, …)`); ранее они несли старый по-настройке ключ.
- **Структура — тип-компонент сингулярен** (сверено на Н3, гейт `CODE`).
  Вид расчёта структуры один (`MarketStructureResolver` выводит `Type` как
  **выход**), поэтому идентичность конфигурации структуры сводится к
  `timeframe` + canonical-`params` — type-дискриминатора в ней нет (в
  отличие от `IndicatorValue`, где `Type` различает виды индикаторов).
  Per-настроечный `structureType` удалён из `StrategyMarketStructureSetting`
  (тип — результат, не вход; в идентичности не участвовал) — ключевание
  структуры консистентно.
- **`MarketPhase` — осознанное исключение** (ключ по контейнеру, не по
  идентичности): основание зафиксировано в §Исключение — `MarketPhase`
  (специфичность авторских правил фазы + меньший объём данных). Ревизия
  Н3 его не затронула — листовых настроек касалась, не контейнера.
