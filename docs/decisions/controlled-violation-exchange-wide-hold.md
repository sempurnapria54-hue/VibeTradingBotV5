# Controlled-violation → безусловный L4 холд биржи

## На какой вопрос отвечает этот файл

Почему контролируемая биржевая ошибка на одной сделке поднимает
безусловный L4-холд всей биржи (доминируя над L3), а не реакцию,
соразмерную видимому радиусу факта.

> **Частично superseded лестницей (2026-08-26,
> `docs/decisions/exchange-safety-ladder.md`).** Сохранено: эскалация
> безусловна, scope — вся биржа, доминирование над инструмент-L3,
> принцип «радиус неизвестен → тормозим широко». Пересмотрено: состав
> реакции — controlled-эксепшн ставит `Exchange.HOLD` (заморозка, без
> flatten); kill-switch flatten перенесён на ступень 2
> (`Exchange.TRADE_BLOCKED`, живой риск без защиты). Актуальное правило
> — `docs/rules/exchange-hold.md`; ниже — историческое обоснование
> в терминах прежней одноступенчатой реакции.

## Контекст

Реактивный контур холдов шага 6 классифицировал триггеры по уровню:
бесстоповая risk-creating позиция постфактум = **L3** (инструмент);
controlled-violation = **L4** (биржа). В коде
(`DealFsmSupport.controlledViolationHold`) L4 поднимается, если среди
retry-anchor'ов сделки (action- **или** finalization-states) есть хоть
одна ошибка класса `VALIDATION_ERROR`, а по
`ServiceCommandExecutor.classify` `VALIDATION_ERROR` ⟺ **любой**
`ControlledExchangeException` — то есть все три категории
(`ExternalStatusException`, `ExternalInvariantViolationException`,
`ExternalNotFoundException`). Этот L4 **безусловно доминирует над L3**
(`markErrorStopless`: при наличии controlled-violation L3-сигнал
бесстоповой позиции вытесняется L4). Реакция L4 =
`KillSwitchService.fireExchange` (flatten всех активных сделок биржи) +
`Exchange.TRADE_BLOCKED` (каскадная блокировка входов по всем
инструментам).

Это поведение было введено в коде, но **отсутствовало в утверждённом
дизайне** — поднято на валидацию как **HOLD-Q1**. Развилка: радиус
реакции (вся площадка) может быть несоразмерен радиусу факта (одна
сущность одной сделки); и для `ExternalStatusException` офдок
(`controlled-exchange-exceptions.md`) писал условный квалификатор
«Exchange → HOLD **по severity / safetyImpact**», который код единообразно
терял.

## Принятое решение (вариант 1)

**Controlled-violation = безусловный L4 (биржевой) холд, доминирует над
L3.** Эскалация **единообразна и безусловна для всех трёх категорий**
`ControlledExchangeException` — один controlled-эксепшн на одной сделке
→ flatten всей биржи + `Exchange.TRADE_BLOCKED`. Условный квалификатор
«по severity / safetyImpact» из офдока для `ExternalStatusException`
**снимается**: квалификатора нет, эскалация безусловна.

**Поведение кода не меняется** — оно уже реализует (1). Это решение
утверждает текущее поведение как **намеренную риск-политику** (хвост
`trading-specialist` / `solution-designer`), а не правит код.

## Принцип (переиспользуемый)

Решение опирается на принцип, который должен направлять **будущие
развилки того же класса** (соразмерность реакции vs неизвестный радиус в
незрелой фазе):

> Контролируемая биржевая ошибка (любая из трёх категорий
> `ControlledExchangeException`) — сигнал **недоверенной /
> недопроработанной интеграции**. Раз интеграция понята не до конца,
> **истинный радиус поражения неизвестен**, и оценивать его по одной
> видимой сущности самонадеянно: за единичным видимым фактом может стоять
> системная проблема посылок адаптера, маржи, режима счёта. Пока
> интеграции нельзя доверять — **тормозим консервативно (вся биржа)**.
> Соразмерность «реакция = видимый радиус факта» применима только к
> **доверенной, дозревшей** интеграции; в незрелой фазе цена ложного
> широкого холда (остановка площадки до ручного разбора) ниже цены
> ложного узкого (неснятый системный риск).

Этот принцип — рассуждение, а не разовое обоснование: на развилке того
же класса (насколько широко тормозить на единичный «контролируемый»
сигнал в незрелой интеграции) по умолчанию выбираем консервативную
широкую реакцию, пока интеграция не признана зрелой.

## Рассмотренные альтернативы

- **(2) Различить три категории.** `ExternalStatusException` → условно по
  severity/safetyImpact (как в офдоке: L3/лог); только
  инвариант-нарушение / not-after-refresh → L4. Снимает потерю
  квалификатора. **Отвергнута:** опирается на доверие к тому, что
  «статус локализован на сущности», — ровно то, чего незрелая интеграция
  не гарантирует (принцип выше).
- **(3) L4 не доминирует L3 безусловно — скоуп по радиусу.** Нарушение
  биржевого инварианта (cross-маржа, posSide, ordType) = L4;
  локализованный на инструменте статус/not-found = L3 (логика §8.C
  дизайна холдов: радиус поражения определяет уровень). **Отвергнута:**
  предполагает, что радиус поражения известен из видимого факта;
  в незрелой интеграции он неизвестен.
- **Крен CC (на валидацию) был (2)+(3)** — единообразная эскалация всех
  категорий выглядела шире риск-радиуса факта. **Отклонён владельцем
  риск-семантики** в пользу (1): консервативный тормоз под неизвестный
  радиус важнее соразмерности, пока интеграция не дозрела. Поведение в
  коде CC не менял — оставлял на валидацию; владелец утвердил (1).

## Расхождение с внутренним доком — выровнено

Прежняя редакция `controlled-exchange-exceptions.md` для
`ExternalStatusException` писала «Deal → ERROR; Exchange → HOLD **по
severity / safetyImpact**» (условно); для
`ExternalInvariantViolationException` / `ExternalNotFoundException` —
«Exchange → HOLD» без расшифровки «HOLD» как «flatten всей биржи».
Решением (1) условный квалификатор **снят** — эскалация безусловна для всех
трёх категорий, а «HOLD» = flatten всей биржи + `Exchange.TRADE_BLOCKED`.

**Выравнивание выполнено** (H18, `GAPS_CLOSE_6`):
`docs/rules/controlled-exchange-exceptions.md` несёт §«Эскалация —
безусловный L4 (все три категории)» с ровно этой формулировкой. Клауза
«выравнивание делается на `SYNC_DOCS_FROM_CODE`» устарела и снята — работа
уже сделана, задачи на `SYNC` по этому пункту нет.
