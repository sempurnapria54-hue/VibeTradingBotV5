# Материализация и валидация стратегии

## На какой вопрос отвечает этот файл

Как материализуется «одна реализация» стратегии (через Strategy API
полным жизненным циклом) и каков scope валидатора в шаге 2 (линия реза
create = структура / activate = готовность-к-запуску).

## Контекст

«Одна реализация» (scope шага 2 по Э1 — полное заполненное дерево
`Strategy`) — как материализуется (API создания / сид / фикстура) и
входит ли в шаг 2 компонент-валидатор. Пробел зафиксирован эскалацией
Э5 на `DOCS_CHECK_2`, открыт как STRAT-Q3; решён здесь.

## Принятое решение

### A. Материализация — Strategy API полным жизненным циклом

- `POST` — создать; `GET` — получить; `PUT` — activate / inactivate /
  delete (смена статуса, не физическое удаление).
- Это REST-поверхность над уже задокументированным lifecycle
  стратегии (enforcement `INACTIVE`/`DELETED`, проверка в
  `EntryScannerJob`; `docs/lifecycles/Strategy.md`) — не новая
  механика.
- Дом API — **шаг 2** (отдельного шага под Strategy API в роадмапе
  нет).
- Инвариант: одна `ACTIVE` на инструмент.
- «Одна реализация» = одна полная стратегия, заведённая через `POST`
  (полный JSON, как в `Strategy API examples`).

### B. Валидатор — минимальный в шаге 2, семантика действий отложена

Линия реза: **create = структура, activate = готовность-к-запуску.**

- На **create (400)** — структурно-ссылочная валидация, которой шаг 2
  владеет: валидный JSON; существование ключей индикаторов, на которые
  ссылаются правила; уникальность `key`; разрешённые enum; валидность
  комбинаций операндов; sanity `warmup`-override (не меньше
  производимого минимума).
- Правила **семантики действий** (`targetActionKey`,
  `CLOSE_FULL`/partial-exit) — отложены до шагов, где их сущности
  дозревают (команды — шаг 4, сделки — шаг 7), и/или на **activate
  (422)** как «готова к запуску».
- Конкретные правила валидности комбинаций операндов — часть
  инкрементального per-`ruleType` контракта (см.
  `docs/decisions/strategy-condition-authoring-contract.md`).

**Рационал.** Шаг 2 владеет моделью стратегии и её самодостаточными
инвариантами — их и проверяем сейчас; семантика действий зависит от
незрелой на этом шаге модели команд/сделок/FSM, валидировать её сейчас
= против незрелого.

## Следствия

- 12-пунктная валидация (`docs/models/domain/aggregate/Strategy.md`
  §key / targetActionKey и валидация) расщепляется по линии
  create/activate: структурно-ссылочные пункты (наличие/уникальность
  `key`, разрешённость ссылок в рамках detail) — на create в шаге 2;
  пункты семантики действий — отложены (шаги 4/7 и/или activate).
- Сам компонент-валидатор и Strategy API — артефакты под-шага `CODE`
  шага 2; backlog п.8 в части валидатора/материализации закрыт по
  scope (остаётся открытым — воспроизведение `Strategy API examples`
  как файла знания).
- Закрывает эскалацию **Э5** (`GAPS_CLOSE_2`) и вопрос **STRAT-Q3**.
