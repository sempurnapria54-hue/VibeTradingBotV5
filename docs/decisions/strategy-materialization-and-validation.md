# Материализация и валидация стратегии

## На какой вопрос отвечает этот файл

Как материализуется «одна реализация» стратегии (через Strategy API
полным жизненным циклом) и каков scope валидатора в шаге 2 (линия реза
create = структура / activate = готовность-к-запуску).

## Контекст

«Одна реализация» (scope шага 2 по Э1 — полное заполненное дерево
`Strategy`) — как материализуется (API создания / сид / фикстура) и
входит ли в шаг 2 компонент-валидатор. Пробел зафиксирован эскалацией
Э5 на `DOCS_CHECK_2`, открыт как STRAT-Q3; решён здесь.

## Принятое решение

### A. Материализация — Strategy API полным жизненным циклом

- `POST` — создать; `GET` — получить; `PUT` — activate / inactivate /
  delete (смена статуса, не физическое удаление). Форма (`CODE`
  шага 2): `POST /api/strategies`, `GET /api/strategies/{internalId}`,
  `PUT /api/strategies/{internalId}/status` с телом `{status}`;
  `CREATED` руками не ставится (400); недопустимый переход lifecycle и
  вторая `ACTIVE` на инструменте — 422 (`UNPROCESSABLE_CONTENT`).
- Это REST-поверхность над уже задокументированным lifecycle
  стратегии (enforcement `INACTIVE`/`DELETED`, проверка в
  `EntryScannerJob`; `docs/lifecycles/Strategy.md`) — не новая
  механика.
- Дом API — **шаг 2** (отдельного шага под Strategy API в роадмапе
  нет).
- Инвариант: одна `ACTIVE` на инструмент.
- «Одна реализация» = одна полная стратегия, заведённая через `POST`
  (полный JSON, как в `Strategy API examples`).

### B. Валидатор — минимальный в шаге 2, семантика действий отложена

Линия реза: **create = структура, activate = готовность-к-запуску.**

- На **create (400)** — структурно-ссылочная валидация, которой шаг 2
  владеет: валидный JSON; существование ключей индикаторов, на которые
  ссылаются правила; уникальность `key`; разрешённые enum; валидность
  комбинаций операндов; sanity `warmup`-override (не меньше
  производимого минимума — на шаге 2 упрощённый floor по типу,
  настоящий derive у реализаций индикаторов шага 3). Туда же (`CODE`
  шага 2): ровно одна деталь на каждый `MarketPhase.Type` (неторгуемая
  фаза — явная `NO_TRADE`-деталь); матрица политика×фаза
  (`PhaseEntryPolicy.isAllowedFor`); парс ISO-8601 duration;
  `attachedProtection` обязательна для `ENTRY_ATTACHED_STOP_LOSS`;
  ссылки `indicatorKey`/`structureKey`/`targetActionKey` — в рамках
  своей детали. Исполнитель — `StrategyCreateRequestValidator`
  (api-слой) + Bean Validation per-field границ.
- **Числовые торговые поля** (`riskPerActionPercent`,
  `targetRiskRewardRatio`, `allocationPercents`, `distancePercents`,
  …) на create ограничиваются только **структурно**: невозможные
  значения (отрицательный риск; доля вне [0; 100] там, где поле —
  доля) → 400. **Торгово-суждённые диапазоны** («ганслингерский»
  `riskPerActionPercent > 3%` и прочие разумно-но-легальные пороги) на
  create **не проверяются** — это семантика готовности к запуску,
  относится к **activate (422)**, отложенной до шагов 4/7
  (ТР2 `DOCS_CHECK_8`, 2026-06-05). Оговорка «там, где поле — доля»
  существенна: не каждое `*Percents`-поле ограничено сотней
  (`ATR_PERCENT`-кодировка `150 = 1.5 ATR` легальна) — границы
  структурной возможности задаются per-поле.
- **Исключение из «торгово-суждённое — не на create»: одновременный
  лимит риска** (`RISK-Q3-A`, шаг 7; расширено C9 `DOCS_CHECK_21`). На
  create проверяются **два** неравенства, у каждого свой реджект:

  ```text
  1) strategySimultaneousRiskPerDealPercent ≤ globalSimultaneousRiskPerDealPercent
         иначе — STRATEGY_SIMULTANEOUS_RISK_ABOVE_GLOBAL

  2) N_overlap × riskPerActionPercent ≤ strategySimultaneousRiskPerDealPercent
         иначе — STRATEGY_SIMULTANEOUS_RISK_UNSATISFIABLE
  ```

  Первое — инвариант вложенности потолков: максимум стратегии
  (**поле детали**) не выше глобального (**конфиг**). Второе —
  выполнимость объявленного веера ног.

  **`N_overlap` — по структуре пересечений, не по одному шагу.**
  Прежняя редакция сравнивала с лимитом пакет **каждого шага по
  отдельности** (`n_risk_creating(step)`) и тем молча полагала, что ноги
  разных шагов одновременно не живут; шаги сопровождения наращивают
  позицию, не снимая ног предыдущих. `N_overlap` — максимальная мощность
  множества risk-creating действий, способных быть живыми одновременно:
  пакет одного шага целиком (он исполняется целиком) **плюс** действия
  соседних шагов, ноги которых поздний шаг не снимает явным действием
  отмены/выхода; повторные срабатывания одного шага статически не
  суммируются (их закрывает динамический преконтроль). Правило
  построения множества — `docs/decisions/per-trade-risk-policy.md`
  §«Валидация — в двух точках», здесь не пересказывается.

  **Почему это create, а не activate:** проверка не суждённая, а
  арифметическая — она сравнивает объявленный веер ног с числами,
  известными до запуска, и её нарушение означает пакет, который
  **никогда** не исполнится целиком, ни при каком рынке. Принять такую
  стратегию значило бы позволить ей молча исполняться частично.
  Оговорка «числовые торговые поля на create ограничиваются только
  структурно» этим не отменяется: проверяется не величина поля, а
  выполнимость конфигурации.

- **Второе исключение из «торгово-суждённое — не на create»: ценовая
  база триггера защиты** (C5 `DOCS_CHECK_22`, решение держателя,
  вариант (a)). На create отвергается
  `StopLossSettings.triggerPriceType ∈ {LAST, INDEX}` — реджект
  `STRATEGY_TRIGGER_PRICE_TYPE_NOT_MARK`, 400.

  **Почему create, а не рантайм.** Guard «ликвидация за стопом»
  сравнивает уровень стопа с ценой ликвидации, которую источник считает
  по `mark`; при иной базе триггера сравнение идёт между **разными**
  базами и требует запаса, чья величина ещё не измерена. Пока она не
  измерена, единственная развязка без провизорного числа в риск-контуре
  — не принимать конфигурацию вовсе. Проверка, как и обе предыдущие, не
  суждённая, а **структурная**: сравнивается объявленное значение поля с
  множеством поддержанных, а не «разумность» величины.

  **Ограничение временное и его снятие обеспечено.** Дом —
  `docs/rules/risk-creating-entry-protection.md` §«Ценовая база триггера
  защиты объявляется стратегией и доезжает до биржи»; условие снятия —
  измеренный базис `last` ↔ `mark` (кейс `MG9.5`), снятие — сервисной
  операцией, якорь со стороны события — `.claude/work/backlog.md`
  §«Снятие ограничения `MARK`-only — по измеренному базису».

- **Третье исключение из «торгово-суждённое — не на create»: полнота
  покрытия защиты** (C1 `DOCS_CHECK_23`, решение держателя). Сумма
  `closeFractionPercents` **защитных** действий шага `MAIN_PROTECTION`
  **с `actionType = CREATE`** обязана составлять **100**; иначе реджект
  `STRATEGY_PROTECTION_COVERAGE_INCOMPLETE`, 400.

  **Операнд суммы задан двумя конъюнктами** (A3 `DOCS_CHECK_24`), и без
  них проверка неисполнима:
  - **защитное действие** — `conditionType` из закрытого перечня защит
    (`STOP_LOSS`, `PARTIAL_STOP_LOSS`, `OCO_FULL`, `TRAILING_PERCENTS`,
    `TRAILING_VALUE`); дом перечня —
    `docs/rules/risk-creating-entry-protection.md` §Правило. `TAKE_PROFIT`
    и `PARTIAL_TAKE_PROFIT` несут `closeFractionPercents` наравне с
    защитами, но убыток не ограничивают;
  - **`actionType = CREATE`** — `REPLACE`/`CANCEL`-действия того же шага
    описывают ремодел, а не исходный набор.

  **Почему create, а не рантайм.** Проверка, как и три предыдущие, не
  суждённая, а **арифметическая**: доли объявлены в процентах позиции и
  известны до запуска, а их недобор означает конфигурацию, которая
  оставит часть позиции без стопа **при любом рынке**. Принять такую
  стратегию значило бы позволить ей нарушать инвариант «живого риска без
  защиты быть не должно» штатным исполнением. Дробность набора при этом
  **не ограничивается** — лестница частичных стопов легальна и нужна
  грид-стратегиям фазы 1.

  **Класса ложного отказа не порождает — но держится на селекторе.**
  Без первого конъюнкта легальная конфигурация «`STOP_LOSS` 100 +
  `TAKE_PROFIT` 100» в одном шаге давала бы сумму 200 и реджект верной
  стратегии; без второго ту же сумму раздувал бы объявленный ремодел.
  Прежняя редакция объявляла отсутствие ложных отказов **безусловно**, не
  назвав операнда суммы вовсе (A3 `DOCS_CHECK_24`).

  **Дом инварианта** — `docs/rules/risk-creating-entry-protection.md`
  §«Предикат покрытия и точки его проверки»; здесь — только create-половина.

  **Реджекты названы, а не безымянны** (C9 `DOCS_CHECK_21`; расширено
  C5 `DOCS_CHECK_22` и C1 `DOCS_CHECK_23` — реджектов стало **четыре**:
  `STRATEGY_SIMULTANEOUS_RISK_ABOVE_GLOBAL`,
  `STRATEGY_SIMULTANEOUS_RISK_UNSATISFIABLE`,
  `STRATEGY_TRIGGER_PRICE_TYPE_NOT_MARK`,
  `STRATEGY_PROTECTION_COVERAGE_INCOMPLETE`). Все четыре проверки отдают
  400 через общий error-DTO
  (`docs/rules/error-handling-policy.md`), но несут **стабильный
  идентификатор причины** в сообщении: иначе отказ «поактный лимит 3 %
  при потолке 1 %» читается как отказ непонятно чего — связка
  «глобальный потолок ограничивает поактный лимит сверху» из имён полей
  не выводится. Идентификаторы живут при валидаторе
  (`StrategyCreateRequestValidator`); выравнивание набора кодов реджекта
  на внешней поверхности — общий хвост
  (`.claude/work/backlog.md` §Ретро-ревью).
- Правила **семантики действий** (`targetActionKey`, partial-exit) —
  отложены до шагов, где их сущности
  дозревают (команды — шаг 4, сделки — шаг 7), и/или на **activate
  (422)** как «готова к запуску».
- Конкретные правила валидности комбинаций операндов — часть
  инкрементального per-`ruleType` контракта (см.
  `docs/decisions/strategy-condition-authoring-contract.md`).

**Рационал.** Шаг 2 владеет моделью стратегии и её самодостаточными
инвариантами — их и проверяем сейчас; семантика действий зависит от
незрелой на этом шаге модели команд/сделок/FSM, валидировать её сейчас
= против незрелого.

## Следствия

- 11-пунктная валидация (`docs/models/domain/aggregate/Strategy.md`
  §key / targetActionKey и валидация) расщепляется по линии
  create/activate: структурно-ссылочные пункты (наличие/уникальность
  `key`, разрешённость ссылок в рамках detail) — на create в шаге 2;
  пункты семантики действий — отложены (шаги 4/7 и/или activate).
- Сам компонент-валидатор и Strategy API — артефакты под-шага `CODE`
  шага 2; **созданы на `CODE` (2026-06-05)**: `StrategyController`,
  `StrategyCreateRequestValidator`, `StrategyService` /
  `StrategyDataService`. «Одна реализация» заавторена
  (`src/main/resources/strategy-examples/trend-following-ema.json`,
  касание `trading-specialist` по СТ-1). Backlog п.8 в части
  валидатора/материализации закрыт по
  scope (остаётся открытым — воспроизведение `Strategy API examples`
  как файла знания).
- Закрывает эскалацию **Э5** (`GAPS_CLOSE_2`) и вопрос **STRAT-Q3**.
- Уточнение границы create для числовых торговых полей (структурный
  sanity vs торгово-суждённые пороги) закрывает находку **ТР2**
  `DOCS_CHECK_8` (`GAPS_CLOSE_8`, 2026-06-05).
