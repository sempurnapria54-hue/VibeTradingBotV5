# Граница «команда ↔ действие»: атомарные команды, системные действия, тождество исполнения

## На какой вопрос отвечает этот файл

Почему командный слой устроен как «атомарные команды + системные
действия-последовательности над ними», а не иначе.

## Контекст

`DOCS_CHECK_8` шага 7 показал: у составной последовательности handler'а
(добыча фактов → финализация → терминал) нет first-class-носителя — нет
строки, счётчика попыток и ключа идемпотентности (узел 3: системные
`REFRESH_*` эмитились без анкера, `applyFailureAccounting` — no-op;
узел 4: у ретрая финализации не было пути к числу). Пользователь принял
направление: команды атомарны, составное — на уровне действия, счётчик
попыток один, системные действия материализуются строками. Развилка
проработана `solution-designer` в 4 валидации
(`.claude/work/history/` — трейл; провенанс ниже).

## Решения

### 1. Критерий атомарности команды — «одна ответственность за состояние»

Команда атомарна ⟺ выполняются все три клаузы:

1. **Один владелец исхода** — ровно одна сущность, чьё состояние команда
   обязана привести к факту; остальное — чтение входа либо журнал.
2. **Повтор с нуля безопасен** — повторное исполнение приводит владельца
   к тому же состоянию.
3. **Нет внутреннего гейта на подтверждение собственной записи** — внутри
   команды нет ожидания, пока биржа подтвердит результат записи этого же
   исполнения; чтение чужих/прежних фактов (evidence-cycle, search) клаузу
   не нарушает.

Клауза 3 выводит запрет «команды внутри команды» из свойства: ожидание
подтверждения своей записи и есть то, что требует нового прохода петли.
Прогон по целевому реестру (17): **составных команд нет**, включая
`FINALIZE_DEAL_*`/`MARK_DEAL_*` (на биржу не ходят, пишут одну сущность —
`Deal`). Канон — `docs/rules/command-lifecycle.md`.

### 2. Составное — системное действие (последовательность, не команда)

Составная последовательность живёт этажом выше команд и получает
first-class-носитель: **системное действие** — действие без
`StrategyAction`, чей per-pass исполнитель выбирает следующую команду по
подтверждённым фактам, а строка состояния несёт попытки и идемпотентность.
Системных действий **четыре**:

| Действие | Состав (звенья) |
|---|---|
| `REFRESH_DEAL_CONTEXT_ACTION` | добывающие `REFRESH_*`-команды (добыча фактов с биржи; без `CANCEL_*`/`CLOSE_POSITION_COMMAND` и без `FINALIZE_*`/`MARK_*`) |
| `FINALIZE_DEAL_ENTRY_ACTION` | `FINALIZE_DEAL_ENTRY_COMMAND` |
| `FINALIZE_DEAL_EXIT_ACTION` | `FINALIZE_DEAL_EXIT_COMMAND` → `MARK_DEAL_CLOSED_COMMAND` |
| `FINALIZE_DEAL_ERROR_ACTION` | `MARK_DEAL_ERROR_COMMAND` / `MARK_DEAL_EMERGENCY_CLOSED_COMMAND` (два исполнения: вход в `ERROR`; терминал) |

Границы — **по природе звена**, не по тропе (добыча повторяется на всех
тропах). **Cleanup** (`CANCEL_*`/`CLOSE_POSITION_COMMAND` как дочистка)
остаётся вне действий: его серия неудач уже считается на инструмент-scope
(`docs/rules/instrument-hold.md` §«Серия неудач»), второй deal-scoped
счётчик дал бы двойной учёт. **Kill-switch действием не материализуется**:
звеньев-команд у него нет (teardown — прямые вызовы `IntegrationService`),
наблюдаемость исполнения закрыта `AnomalyReport`
(`docs/components/SafetyHoldCoordinator.md`); он остаётся аварийным
side-executor'ом вне слоёв (`docs/decisions/fsm-execution-layering.md`).
Служебная сборка объекта `DealContext` перед проходом FSM действием **не
материализуется** (между проходами переживать нечего) — действием
является только добыча наружу.

### 3. Носитель — общая таблица состояний, строка = исполнение

`DealFinalizationState` **упразднена**; обе разновидности действий живут в
`deal_action_states`:

- nullable `strategy_action_id` + non-null дискриминатор
  `action_kind (STRATEGY | SYSTEM)` + non-null `system_action_type` у
  SYSTEM-строк;
- **строка = исполнение** (не действие): идентичность — суррогатный `id`;
  уникальность — **частичная, по живым статусам, с целью в ключе**
  (`docs/models/domain/other/DealActionState.md` §Инварианты). Действие
  стратегии исполняется в сделке **многократно** (грид: повторное
  срабатывание узла, одноимённые узлы, параллельные ноги) — прежний ключ
  `UNIQUE(deal_id, strategy_action_id)` был дефектен уже на шаге 4;
- строки исполнений **копятся** (`COMPLETED` жёстко терминален,
  слот-переиспользования нет); политика очистки — **отложена к фазе 3**
  (см. §Отложено);
- `RuntimeTarget` выходит из jsonb в колонки — его поля стали операндами
  ключа (`docs/rules/persistence-representation.md`).

### 4. Ретрай: бюджет на исполнение, предел per command, стадия из фактов

- **Счётчик (β)** — сквозной бюджет отказов на исполнение действия, без
  обнуления при продвижении стадии; перекоса нет — добыча и завершение
  разнесены по разным действиям.
- **Предел** — per command из конфига (`service-command-retry`, ключ —
  `ServiceCommandType`); клауза «предел — по типу текущей команды, счётчик
  — по исполнению действия» записана в
  `docs/components/RetryPolicyService.md`.
- **Стадия исполнения выводится из подтверждённых фактов** на каждом
  проходе; явного поля стадии, курсора звеньев и флага «рестарт с нуля»
  нет. Что считается подтверждённым фактом звена — определено per action
  (`docs/components/SystemActionExecutor.md`).

### 5. Транзакционная клауза записи в `Deal` (обобщение N7)

**Звено, чей исход — запись в `Deal` (число, консолидация, статусное
ребро), делает эту запись в одной транзакции с durable-продвижением
исполнения своего действия.** Экземпляры: `resultProfit` + завершение
звена финализации (N7); `ENTRY_FINALIZED` + завершение
`FINALIZE_DEAL_ENTRY_ACTION` (валидация 4 — закрывает окно повтора
консолидации); терминальные `MARK_*_COMMAND` (статус + продвижение).
Следствие для слоения: handler'ы **гейтят эмиссию** завершающего звена
своими проверками, само статусное ребро пишет звено — это уже действующий
паттерн терминалов, `ENTRY_FINALIZED` присоединяется к ряду.

### 6. Именование уровней — систематический суффикс

Команды — `*_COMMAND`, действия — `*_ACTION`; основа имени может
совпадать (`FINALIZE_DEAL_ENTRY_COMMAND` / `FINALIZE_DEAL_ENTRY_ACTION`).
Правило разведения уровней — `.claude/rules/naming.md` §«Разведение
уровней абстракции». Распространяется и на `StrategyActionType`
(`CREATE_ACTION`/`REPLACE_ACTION`/`CANCEL_ACTION`): потребителей
Strategy API вне репозитория нет — миграция значений
`strategy_actions.action_type` без плана совместимости; групповые маски в
прозе (`REFRESH_*`, `MARK_*`) остаются короткими.

### 7. Окно линковки bills — собственные поля `Deal` (узел 1)

Границы окна — `Deal.billsWindowBegin` / `Deal.billsWindowEnd`, заполняет
наблюдатель факта; из `Position.externalModifiedAt` окно больше не
реконструируется (колонка перестаёт быть двузначной). `billsWindowEnd`
пуст (факт закрытия не добыт) → **привязка ждёт**; исчерпание попыток
добычи → ошибочная тропа + холд инструмента. **Названная цена:** после
терминала линковка запрещена (слот освобождён) ⇒ неподобранные bills не
подберутся никогда — разбивка неполна, сверка даёт `AnomalyReport`,
сделка попадает в `EMERGENCY_CLOSED`-корзину (смещение R-выборки —
торговый хвост узла 2).

### 8. Исход финализации при пустых фактах (узел 4) — вариант (а)

Действие **не завершается без числа**: добыча ретраится бюджетом
`REFRESH_DEAL_CONTEXT_ACTION`, `FINALIZE_DEAL_EXIT_COMMAND` эмитится
только по терминальному исходу добычи и не завершается без числа;
исчерпание уводит сделку ошибочной тропой + холд инструмента. Асимметрия
с аварийной тропой сохранена (`docs/decisions/pnl-finalization-mechanics.md`
§5a): на аварийном терминале жёсткий отказ чтения = «недоступно», терминал
ставится.

### 9. Реакция на исчерпание попыток добычи — действующее правило (временно)

Отказ добычи по живой сделке остаётся **управление-сайд** серией: холд +
kill-switch + `AnomalyReport`, `TRADE_BLOCKED`. Третий (мягкий) класс
триггера не вводится. **Довод — этап отладки** (важно вовремя узнавать о
непредвиденном поведении), и он **истекает с окончанием отладки**; довод
о радиусе ущерба (`docs/rules/error-handling-policy.md`) остаётся и
указывает в другую сторону (посттерминальная добыча обесценивает число и
отчётность, не управление риском). **Горизонт пересмотра — установившийся
режим** (`docs/rules/instrument-hold.md` §«Серия неудач»). Без условия
пересмотра решение читалось бы как принципиальный выбор реакции.

## Альтернативы (отвергнуты)

- **Снять `FINALIZE_DEAL_*` из реестра команд** (буквальное прочтение) —
  действие, пишущее `Deal` само, минует `CommandExecutor` и лишает запись
  retry-анкера.
- **Синтетические строки `strategy_actions` под системные действия** —
  фиктивные узлы в авторском дереве стратегии.
- **Две таблицы** (обобщить `DealFinalizationState`) — расходится с
  принятым направлением; довод прежнего решения «не размывать инвариант»
  пересмотрен: сам инвариант оказался дефектным (многократные исполнения).
- **`KILL_SWITCH_ACTION` как пятое действие** (принималось, отменено на
  валидации 3) — звеньев-команд нет, наблюдаемость уже закрыта
  `AnomalyReport`, deal-scoped строка конфликтует со scope-уровневым
  радиусом.
- **«Строка-слот» с переиспользованием** — `COMPLETED` переставал быть
  терминальным; отклонено, строки копятся, очистка — фаза 3.
- **Журнал срабатываний условий как ключ исполнения** — история не
  источник runtime-логики (`docs/rules/audit-not-runtime-source.md`).

## Отложено

- **Политика очистки накопленных строк исполнений** — фаза 3 (ретеншен —
  цена за границей фазы, названа при принятии «копить»).
- **Метка подтверждения звена добычи** (`REFRESH_DEAL_CONTEXT_ACTION`:
  refresh не меняет данных, если факт не изменился) — гейтится узлом 7
  `DOCS_CHECK_8` (измеритель свежести), решается вместе с ним.
