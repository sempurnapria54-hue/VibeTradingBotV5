# Инкременты концепции производных рыночных данных, въехавшие на CODE (D1-D3 + fork-A)

## На какой вопрос отвечает этот файл

Почему операнд индикатора получил адресный компонент, почему ER-порог
тренда и толеранс кластеризации уровней структуры вынесены в параметры
(и почему их значения провизорны), и почему `MarketStructureResolver`
потребляет готовые каталожные ER/ATR, а не пересчитывает их.

## Контекст

Концепция производных рыночных данных шага 3 (индикаторы +
`MarketStructure` + `MarketPhase`) была доведена до чистого
`DOCS_CHECK_7` **до** написания кода (docs-first,
`.claude/processes/roadmap-step-execution.md`). На под-шаге `CODE`
по этой концепции вскрылись четыре развилки, которые потребовали
содержательного решения сверх утверждённого концепта. Они зафиксированы
здесь батчем — рациональ (the WHY), на который ссылаются синканные доки.

D1 — концепт/контракт-инкремент (новая семантика контракта операнда):
по §6a процесса он миновал концепт-гейт (въехал на CODE) и **подлежит
пост-хок концепт-гейту** (`concept-review` по синканным докам до `DONE`).
D2/D3/fork-A — параметризация и довод проводки уже принятого концепта
(не новая контрактная семантика).

**Провизорность порогов.** Численные пороги, появившиеся в D2/D3,
помечены в доках как провизорные: канонические значения калибруются на
бэктест-гейте фазы 2 (открытый вопрос STRUCT-Q1), числом в канон не
зашиваются. В коде остаются провизорные дефолты резолвера — чтобы расчёт
был определён до калибровки.

## D1 — адресный компонент индикатора-операнда

**Решение.** Операнд индикатора (`StrategyConditionOperand`, источник
`INDICATOR`) получает адресный компонент `indicatorComponent:
IndicatorComponent`: какую часть многокомпонентного индикатора сравнивать.
- MACD — `MACD_LINE` / `SIGNAL_LINE` / `HISTOGRAM`;
- Stochastic — `STOCH_K` / `STOCH_D`;
- Bollinger — `UPPER_BAND` / `MIDDLE_BAND` / `LOWER_BAND` / `BANDWIDTH` /
  `PERCENT_B`.

Контракт авторинга (create-валидация, 400): компонент **обязателен** для
многокомпонентных типов (MACD / Stochastic / Bollinger), **запрещён** для
одно-компонентных (EMA / RSI / ATR / OBV / `EFFICIENCY_RATIO`), и
проверяется на совместимость компонента с типом индикатора. Допустимость
«тип → компоненты» — единый справочник (`util.IndicatorComponents`),
общая опора create-валидации и evaluator'а.

**Почему.** Абсолютное сравнение многокомпонентного индикатора в ценовых
единицах (MACD-линия) с `CONSTANT` масштаб-зависимо межинструментно
(BTC vs ETH) — тот же класс нестабильности, что у голого OBV
(`docs/decisions/volume-condition-semantics.md`). Адресный компонент даёт
автору сравнивать осмысленную часть индикатора (зеркало OBV-принципа
относительных/нормированных форм: `BANDWIDTH`, `PERCENT_B`, `HISTOGRAM` —
производные/нормированные компоненты).

**Отвергнутая альтернатива.** Минимальный точечный запрет
MACD-абсолюта (как у OBV). Выбран полный адресный компонент ради
консистентности грамматики: проблема масштаб-зависимости общая для всех
многокомпонентных индикаторов, а не специфична для MACD; точечный запрет
оставил бы Stochastic/Bollinger неадресуемыми. Свёрнут в шаг 3 (не отложен
на будущую фазу), т.к. без него `INDICATOR_COMPARE` над многокомпонентным
индикатором недоопределён (непонятно, какую часть сравнивать).

## D2 — ER-порог тренда

**Решение.** Бинарный порог ER (тренд vs диапазон) вынесен в
`MarketStructureParams.trendEfficiencyThreshold`: `ER ≥ порога` →
тренд-сила, иначе — нет. Значение — хвост пользователя (per-настройка),
калибруется на бэктест-гейте фазы 2; провизорный дефолт резолвера 0.30
(числом в канон не зашивается).

**Почему.** Канон-якоря у бинарной отсечки ER нет — корпус использует ER
**континуально** (KAMA-style сглаживание скоростью, Kaufman гл. 1
«Measuring Noise», гл. 17). Бинарный порог — допустимое инженерное
упрощение под **дискретный** классификатор структуры (выход
`RANGE`/`UPTREND`/`DOWNTREND`/`UNKNOWN` дискретен, континуальная мера на
выходе не нужна).

**Отвергнутая альтернатива.** Континуальный редизайн ER (адаптивная
скорость в духе KAMA внутри резолвера) — не оправдан: дискретный выход
структуры не требует континуального входа, усложнение без продуктовой
отдачи на этом шаге.

## D3 — толеранс кластеризации уровней

**Решение.** Толеранс группировки пивотов в ценовой уровень —
**ATR-относительный**: `толеранс = k · ATR`, где `k =
MarketStructureParams.levelToleranceAtrMultiplier` (значение — на
бэктест-гейт фазы 2; провизорный дефолт резолвера 0.5). Когда каталожный
ATR недоступен (вход `atrKey` не объявлен) — **fallback** на долю цены
(провизорная константа резолвера).

**Почему.** Фиксированный процент-толеранс непереносим между
инструментами и режимами (волатильность-зависим): на спокойном
инструменте слишком широк, на волатильном — слишком узок.
ATR-относительный толеранс сам адаптируется к текущей волатильности и
задействует уже считаемый каталожный ATR (без отдельной меры разброса).

**Отвергнутая альтернатива.** Фиксированный процент от цены как основной
толеранс — оставлен только как fallback на случай необъявленного ATR, не
как основной механизм.

## fork-A — резолвер потребляет каталожные ER + ATR

**Решение.** `MarketStructureResolver` потребляет **готовые** каталожные
ER (дискриминатор тренд/шум) и ATR (пол толеранса уровней, D3), а не
пересчитывает их. Привязка — «мягкие» ссылки по `key` на индикаторные
настройки **стратегии** (strategy-scope после ревизии трек D —
прежде были настройки того же контейнера):
`StrategyMarketStructureSetting.efficiencyRatioKey` / `atrKey` (ключи
`StrategyIndicatorSetting` стратегии). ER-прокси
(внутренний нетто-ход / суммарный ход окна) резолвер считает **только
когда ER-вход не объявлен** (`efficiencyRatioKey` null); ATR-fallback на
долю цены — когда `atrKey` null.

**Объявлено, но не готово / устарело → консервативный `UNKNOWN`.** Если
ключ ER/ATR объявлен, но значение не готово (нет рассчитанного
`IndicatorValue` / устарело) — `MarketStructureJob` сохраняет
консервативный `UNKNOWN`-результат окна (не proxy, не падение): объявив
вход, автор выразил намерение на нём считать; молча подменять прокси —
исказить замысел, а падать на тике производных данных нельзя. Это
поведение живёт в **job** (он резолвит скаляр из каталога и решает
готовность); резолвер получает уже готовый скаляр ER/ATR либо null.

**Почему.** Консистентность с уже зафиксированным каноном — резолвер
потребляет готовые каталожные индикаторы, не дублирует расчёт
(`docs/decisions/efficiency-ratio-as-catalog-indicator.md` §3 — единый
источник ER, без второго вычисления). Закрывает запаркованное расхождение
проводки (где берётся ER/ATR резолвера); низкий риск, **не новый концепт**
— довод проводки fork A.

**Следствие.** Разрешение структуры зависит от готовности объявленного
ER/ATR-входа: пока вход не прогрет/устарел, структура консервативно
`UNKNOWN` (согласуется с матрицей `UNKNOWN → NO_TRADE`).

## Краевой случай идентичности (STRUCT-Q2) — закрыт реверсом ключевания

**Был:** `config_id` не различал `efficiencyRatioKey` / `atrKey`.
Идентичность конфигурации структуры = `timeframe` + canonical-`params`;
soft-ссылки `efficiencyRatioKey` / `atrKey` жили на
`StrategyMarketStructureSetting`, в идентичность не входили. Две настройки
структуры с одинаковыми `timeframe + params`, но разными ER/ATR-входами
резолвились в **один** `config_id`, делили один ряд результатов и дедуп по
`instrumentId:configId` (`MarketStructureJob`) — «первый писатель
выигрывает» молча, нарушая инвариант шаринга.

**Закрыт (трек D, 2026-06-10).** Реестры конфигураций и шаринг убраны;
результаты ключуются **настройкой-владельцем**
(`docs/decisions/market-data-result-identity-keying.md`). Каждая настройка
структуры (со своими `efficiencyRatioKey` / `atrKey`) пишет в **свою**
строку под своим `strategy_market_structure_setting_id` —
разделяемого ряда, на котором возникала коллизия, больше нет. Краевой
случай снят **по построению**, без отдельного гарда (прежний интерим B —
запрет на create-валидации — не нужен). STRUCT-Q2 закрыт. Soft-ключи
`efficiencyRatioKey` / `atrKey` (fork-A) при этом сохраняются — резолвер
по-прежнему потребляет готовые ER/ATR-входы; в идентичность они входить
перестали вместе с самой идентичностью.
