# Смена модели источника поглощается native-слоем

## На какой вопрос отвечает этот файл

Как мы обходимся с известным заранее изменением модели источника
(переименование / замена поля).

## Контекст

Источник объявляет изменение формы ответа **заранее, с датами
выкатки**. Триггер-кейс (прогон интегратора 2026-07-14, пробел H1
`GAPS_CLOSE_3` шага 7): OKX переименовывает `feeGroup[].elpMaker` →
`feeGroup[].rpiMaker` (ELP→RPI rebranding) — demo **2026-07-21**, прод
**2026-07-28**, параллельные имена до **2026-10-31**; прод-переключение
попадает **внутрь горизонта шага 7**
(`docs/integrations/okx/contracts/trade-fee.md` §«Прочие ремарки офдока»).

Вопрос шире одного поля и одного источника: любое объявленное заранее
переименование/замену ставит одна и та же развилка — **где** изменение
поглощается и **по какому признаку** выбирается поле. Ответ нужен общим
правилом, иначе каждый следующий ребрендинг решается заново и по-разному.

## Решение

**Известное заранее изменение модели источника поглощается native-слоем;
домен видит одно стабильное имя; резолв — по заполненности, не по дате.**

- **Место поглощения — native-слой** (слой, чья работа — знать форму
  источника: native-DTO + маппер в `*ExternalSnapshot`, внутри
  `IntegrationService`/adapter). `docs/rules/raw-exchange-dto-boundary.md`
  уже говорит, что сырой DTO за adapter не выходит; отсюда следствие:
  **и смена формы источника за adapter выходить не должна**. Домен о
  переименовании не знает.
- **Механика, когда поле used:** в native-модели — **два поля** (старое и
  новое), в доменной/снапшотной — **одно** универсальное имя, нейтральное
  к ребрендингу. Резолв — **по заполненности**: какое из двух пришло
  непустым, то и берём.
- **Дата — не переключатель, а максимум страховка.** Дата в конфиге
  допустима **только** на случай, если оба поля придут разом (тогда
  конфиг говорит, какое считать авторитетным). Ветвление
  «до даты читаем старое / после — новое» не строим.
- **Когда поле unused — механику не строить вовсе.** Достаточно
  **корректно назвать** поле в unused-перечне native-дока (оба имени +
  даты), чтобы следующий заход не принял новое имя за новое поле. Ни
  двух полей, ни резолва, ни конфига: инфраструктура под изменение,
  которое ничего у нас не питает, — это код, заведённый превентивно
  (`.claude/rules/codestyle.md` §«Неиспользуемый код»: поля и методы
  заводим по потребности).
- **Переоценка при смене used/unused.** Правило крепится к статусу поля,
  а не к разовому вердикту: поле, ставшее used до завершения окна
  параллельных имён, получает механику двух полей по общему правилу.

## Почему по заполненности, а не по дате

**Резолв по заполненности самокорректируется при сдвиге сроков.** Сроки
выкатки биржа двигает регулярно, и мы узнаём об этом последними — из
перевыкачки офдока или, хуже, из аномалии на сверке. Заполненность —
**наблюдаемый факт входящего ответа**: сдвинули выкатку на месяц —
непустым продолжает приходить старое поле, код читает старое, ничего не
делаем; выкатили раньше — код читает новое, ничего не делаем.

Захардкоженная дата — **утверждение о будущем поведении внешней системы,
которое мы не контролируем**. Оно ложно ровно в тот момент, когда система
ведёт себя иначе, чем мы записали, и цена ошибки платится молча: код
читает поле, которого ещё (или уже) нет, и получает пустоту вместо
ставки.

Отсюда и роль даты как страховки: она отвечает на вопрос, на который
заполненность ответить не может, — **какое из двух непустых полей
авторитетно**. Это единственный случай, где дата что-то решает.

## Отвергнутые альтернативы

- **Переключение по дате из конфига** (до даты — старое поле, после —
  новое). Отвергнуто: ломается при сдвиге выкатки — а сдвиг это норма, не
  исключение. Требует ручного вмешательства **в срок**, о котором мы
  узнаём постфактум; между фактическим сдвигом и нашей правкой конфига
  поле читается неверно. Заполненность даёт тот же результат без
  календаря и без вмешательства.
- **Реагировать постфактум, когда сломается.** Отвергнуто: превращает
  **известное заранее** изменение в инцидент. Для used-поля это тихий
  `null` вместо значения — ровно та болезнь, что вскрыта в H1
  (молчаливый выпад: величина не приходит, никто не падает, число
  портится). Мы знаем дату за недели до выкатки — платить за это
  инцидентом незачем.
- **Протащить оба имени в домен** (домен знает про `elpMaker` и
  `rpiMaker` и выбирает сам). Отвергнуто: форма источника протекает в
  домен — прямое нарушение `docs/rules/raw-exchange-dto-boundary.md`
  (наружу выходит нормализованный снапшот, не форма источника). Домен
  начинает знать про **календарь ребрендингов биржи**; при втором
  источнике с другим именем того же смысла протечка умножается.

## Кейс-иллюстрация — `elpMaker` → `rpiMaker`

Разрешён по ветке **unused → механику не строим**: ставку мы резолвим из
`feeGroup[].taker`/`maker`, а `elpMaker` — ставка ELP/RPI-программы, в
которой мы **не состоим** (инвариант organic-base-rates,
`docs/integrations/okx/contracts/trade-fee.md`). Поле отброшено на
маппинге ⇒ два поля, резолв и конфиг не заводятся; оба имени и даты
зафиксированы в unused-перечне
`docs/models/integrations/okx/OkxTradeFeeResponse.md`.

Условие пересмотра — то же, что у organic-base-rates: **вход в
ELP/RPI-программу делает поле used** → механика двух полей по общему
правилу выше.
