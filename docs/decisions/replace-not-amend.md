# REPLACE вместо AMEND: единый путь ремоделирования

## На какой вопрос отвечает этот файл

Почему домен не амендит сущности на бирже, а ремоделирует их
единственным путём REPLACE (новая сущность + отмена старой), и как
REPLACE устроен (форма, identity, порядок ног, валидация).

## Контекст

Находка К-1/Т-1 (`DOCS_CHECK_4` шага 4): концепция предлагала
амендный путь ремодела trailing, неисполнимый на OKX (И-3:
`amend-algos` — только Stop/Trigger; advance-семья не амендится).
Вместо узкого запрета пользователь расширил развилку: запретить
AMEND как доменную операцию целиком. Проработка —
`.claude/work/history/2026-06-11-phase-1-step-4-concept-review/phase-1-step-4-k1-replace-design.md`;
валидация пользователем 2026-06-11 — чистая (принято без правки по
существу).

Продуктовые вводные: планируются другие биржи — amend
биржеспецифичен (матрица «что амендуемо» различается даже между
типами сущностей одной OKX), replace (place + cancel) поддерживают
все; REPLACE-only проще поддерживать и аудировать; двойственность
amend/replace порождает разный разбор кейсов по биржам; решение —
сейчас, не переделывать потом.

## Решение

1. **AMEND уходит из доменного словаря целиком** — для всех типов
   (ордера и algo). `AMEND_ORDER` / `AMEND_ALGO_ORDER` сняты из
   `ServiceCommandType` (19 → 17); амендные executors и payload'ы
   (`AmendOrderExecutor`, `AmendAlgoOrderExecutor`) удалены;
   амендного request-mapping в домене нет. Биржевые amend-контракты
   остаются задокументированными как поверхность
   (`docs/integrations/okx/contracts/order.md` §Amend,
   `algo-order.md` §Amend) с пометкой «доменом не используется».
2. **REPLACE — операция словаря стратегии, не команда:**
   `StrategyActionType: CREATE / REPLACE / CANCEL`.
   REPLACE-действие задаёт полное новое желаемое состояние (палитра
   как у CREATE) и исполняется **оркестрацией существующих атомарных
   команд** (`CREATE_*`/`SUBMIT_*`/`REFRESH_*`/`CANCEL_*`);
   отдельного `ServiceCommandType.REPLACE` нет. Секвенс ног — FSM по
   **фактам** (не ACK), «одна актуальная команда за проход»;
   recovery — штатный (`DealActionState` + exchange facts).
3. **Порядок ног — по риск-классу действия** (из
   `positionReducingOnly`, новых полей нет):
   - **protective** (reduce-only): place-new → подтверждение фактом
     → cancel-old. Окна без защиты нет; перекрытие двух reduce-only
     защит безопасно по построению (reduce-only не увеличивает
     позицию; при сработке обеих на гэпе вторая закрывает остаток
     либо отклоняется; conditional/trigger algo маржу не морозят).
     Обобщение принятого паттерна `ProtectionSwitchedHandler`.
   - **entry** (не reduce-only): cancel-old → подтверждение
     терминала (fill-race по фактам: исполнен → ремодел неактуален;
     частично — пересчёт остатка) → place-new. Перекрытие двойного
     риска исключено.
4. **Identity и аудит:** новая сущность с новым `internalId` (вся
   submit-retry дисциплина по stable client id сохраняется);
   `replacesInternalId` на новой — указатель на предшественника
   (append-only цепочка, обратная ссылка выводится запросом);
   старая — `Status = CANCELED`,
   `closeReason = REPLACED_BY_STRATEGY` (у `AlgoOrder` значение уже
   существовало; у `Order` добавлено симметрично). След ремодела —
   неизменяемая цепочка сущностей, без мутации параметров на месте.
5. **Резолюция цели по цепочке:** REPLACE/CANCEL через
   `targetActionKey` ссылаются на CREATE-action; рантайм резолвит
   актуальную сущность как последнее звено цепочки замещений.
   Валидация стратегии: правила 4/6/7 переписаны на REPLACE.
6. **Риск-контроль ремодела — на place-ноге** новой сущности
   (`docs/rules/risk-validator-scope.md`); cancel-нога — снятие
   риска, не валидируется risk-policy.

## Оплаченные цены (осознанно)

- **Rate limit:** две ноги вместо одного вызова — но в **разных**
  вёдрах OKX (place и cancel — отдельные лимиты), а аккаунт-уровневый
  fill-ratio-лимит считает place и amend одинаково (cancel
  бесплатен). Для свечного каденса бота нематериально.
- **Очередь лимиток:** теряется место в очереди (но смена цены
  теряет его и при amend; сохранение — только краевой amend
  size-down). Классу стратегии (свечной тренд-фоллоинг от уровней)
  нерелевантно; корпус тезисов о приоритете очереди не несёт
  (помечено «предполагаю» в проработке).
- **Две операции там, где OKX дал бы одну** (ordinary, Stop/Trigger
  algo) — цена универсальности; окно закрыто порядком ног.

## Отвергнутые альтернативы

- **(а) Узкий запрет амендного пути только для TRAILING_*** (крен
  `DOCS_CHECK_4`): минимальная правка, но дуальность остаётся
  навсегда — матрица амендуемости по биржам/типам течёт в
  домен/валидацию; окно-менеджмент всё равно строится (trailing);
  две ветки ремодела в поддержке и аудите.
- **(б) Трансляция AMEND → replace-flow в оркестрации** (AMEND
  остаётся словарём, исполняется как replace): словарь обещает то,
  чего не делает; дуальность семантики сохраняется на уровне
  авторинга.
- **(в) Оставить amend как есть** (биржа отказывает на advance):
  торгово слепо — ремодел защиты молча не происходит.
- **(г-1) REPLACE как `ServiceCommandType`** (executor с двумя
  write-ногами): ломает «одна команда — одна простая операция» и
  гранулярность «одна команда — одна сущность»; безопасный порядок
  ног требует подтверждения фактом → внутри executor'а это либо
  ACK-секвенс (нарушение «ACK не runtime truth»), либо дубль
  submit/cancel/refresh-дисциплин. Прецедент F1 (мульти-вызов внутри
  команды) — read-цикл одной сущности, не две write-операции.

## Следствия

- Биржевая амендная асимметрия (И-3) перестала касаться домена;
  К-1/Т-1 закрыты этим решением (`GAPS_CLOSE_3`).
- Precheck/AnomalyJob (шаги 6/8, смежно CMD-Q4) должны распознавать
  легитимное окно двойной reduce-only защиты во время REPLACE
  (намерение видно из `DealActionState`/цепочки
  `replacesInternalId`) — не флагать аномалией.
- Представление последовательности ног в фабрике (вывод из фактов
  vs явные фазы) и эджи partial-fill — детали `CODE` шага 4.
- `ORDER_AMEND_PRICE` → `ORDER_REPLACE_PRICE`
  (`CalculatedPrice.StrategyPricePurpose`).
