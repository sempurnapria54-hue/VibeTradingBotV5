# Оценка рисков (risk-evaluation)

## На какой вопрос отвечает этот файл

Как устроен процесс оценки риска.

## Назначение

Risk-layer отвечает на вопрос: можно ли выполнить уже рассчитанное
действие при текущем состоянии сделки, позиции, баланса, инструмента и
биржи. Не выбирает стратегию, не проверяет сигнал, не исполняет команды.
Процесс — точка композиции, вызывается из
`docs/processes/deal-management.md`.

## Поток (risk-creating / risk-increasing action)

```text
FSM handler
  -> выбрал StrategyStep, проверил условие, выбрал StrategyAction
  -> StrategyActionCalculator -> CalculatedPrice / CalculatedSize
  -> RiskValidator -> RiskValidationResult
  -> RiskBlockResolver -> RiskBlockAction (если BLOCKED)
  -> StrategyActionOrchestrator -> одна актуальная ServiceCommand, если разрешено
```

Компоненты: `docs/components/RiskValidator.md`,
`docs/components/RiskBlockResolver.md`. RVO: `RiskValidationResult`,
`RiskCheckResult`, `RiskBlockAction` (см. `docs/components/models/`).

## Когда вызывается

См. `docs/rules/risk-validator-scope.md`: только для risk-creating /
risk-increasing / risk-weakening actions; не для refresh/search/history,
cleanup/safety, finalization и reduce-only partial exit. Перед
risk-sensitive action handler обеспечивает fresh `BalanceContainer`; при
absent/stale — добыча звеном `REFRESH_BALANCE_COMMAND` через
`REFRESH_DEAL_CONTEXT_ACTION` (handler добывающие `REFRESH_*` напрямую не
эмитит, `docs/components/SystemActionExecutor.md`) и новый проход FSM (на
этой итерации `RiskValidator` не вызывается).

## Реакция на результат

```text
транш в PRECHECK + BLOCKED + живого риска у него ещё нет
  -> терминал транша CLOSED, closeReason = RISK_CONTROL   # не авария
     (сделка закрывается, когда так закрылись все её транши)

транш в ENTRY_SUBMITTED / ENTRY_FINALIZED / PROTECTION_SWITCHED / MANAGING + BLOCKED
  (для risk-creating / risk-weakening action)
  -> ребро в ERROR **сделки** -> ErrorHandler / safety-flow
     (ошибочного статуса у транша нет)

WARNING  -> action не блокируется; фиксируется в логах / истории
ALLOWED  -> StrategyActionOrchestrator создаёт команду
```

### Отказ по неполноте графа реакцию не делит со схемой

**`DEAL_GRAPH_INCOMPLETE` — не вердикт риск-политики.** Он говорит, что
операндов не предъявлено, а не что риск не позволил: граф сделки пришёл
в проход неполным (`docs/spec/deal-context-load.json`, `graphComplete`).
Поэтому схема выше к нему не применяется ни одной строкой, и в терминал
транша `CLOSED` с причиной `RISK_CONTROL` он не уводит **ни на какой
стадии**: на всех идёт тропа ошибки сделки.

Довод — П3, а не тяжесть повода. Причина закрытия — признак отбора для
разбора по данным; подписав дефект предъявления контекста причиной
риск-контроля, разбор перестаёт отличать «риск не позволил» от «контекст
не загрузился», а именно это различие П3 и требует держать в данных.
Направление ошибки у обеих веток консервативное (входа нет в любом
случае), поэтому вопрос стоит не о безопасности, а о читаемости следа —
и решается в пользу различимости.

### Карв-аут исчерпанного бюджета сделки

**Перечень карв-аута — единственный носитель членства; проза ниже несёт
только доводы.** В `ERROR` не уводят:

| Код | Почему не признак рассогласования |
|---|---|
| `RISK_PER_DEAL_CUMULATIVE_EXCEEDED` | исчерпанный бюджет сделки — ожидаемый исход легитимной стратегии |
| `RISK_PER_DEAL_SIMULTANEOUS_EXCEEDED` | то же; либо операнд слева вырос фактом исполнения |
| `RISK_PER_DEAL_SIMULTANEOUS_GLOBAL_EXCEEDED` | потолок изменила система — повод внутренний |
| `DEAL_NOTIONAL_EXCEEDED` | то же; проскок входа поднимает нотинал живого эпизода |
| `STOP_DISTANCE_BELOW_FLOOR` | реджект приходится на place-ногу либо на транш без живого риска |
| `STOP_LOSS_INVALID_SIDE` | то же: у place-ноги защиты старая защита остаётся живой; у входа в полосе у безубытка (`docs/rules/risk-policy.md` §«Порядок рубежей — по порядку прохода») вход не состоялся и живого риска у транша нет |
| `STOP_LOSS_TOO_CLOSE_TO_LIQUIDATION` | guard ликвидации на открывающем входе не гоняется, поэтому реджект — тоже place-нога защиты при живой позиции |
| `PROTECTION_LADDER_STEP_BELOW_MIN_SIZE` | реджект защитного действия; прежняя защита жива по тому же построению |
| `PROTECTION_COVERAGE_REDUCED` | реджект защитного `REPLACE` на place-ноге: покрытие сохраняется |
| `LOSS_LIMIT_NOT_CONFIGURED` | незаданное число конфигурации — повод внутренний |
| `BALANCE_NOT_ENOUGH` | нехватка свободных средств на очередную ступень сетки — ожидаемый исход легитимной стратегии, а не расхождение учёта |
| `RISK_CREATING_UNDER_COLLAPSE` | энфорсер, сработавший по назначению: сделка уже в координированном выходе |
| `INSTRUMENT_SAFETY_HOLD` | энфорсер, сработавший по назначению: блок-сет стоящей safety-ступени отверг действие блокируемого класса — действие не исполняется, сделка остаётся в статусе и доживает под своей защитой; возобновление — снятием ступени (`docs/rules/instrument-hold.md` §Enforcement). Увод в `ERROR` превращал бы мягкую ступень в жёсткую через аварийный контур — отмену самого разведения ступеней |

**Родовых доводов по группам кодов здесь нет.** Три кода баланса
разведены: `BALANCE_NOT_ENOUGH` — норма и в карв-ауте;
`BALANCE_INVALID` — рассогласование учёта, `BALANCE_NOT_FRESH` —
недобытый операнд, оба ведут в `ERROR`.

**Почему глобальный и сделочный коды тоже в карв-ауте.** Достижимы они
двумя тропами, и **ни одна не является признаком рассогласования**:
потолок изменила **система** после приёма стратегии — повод внутренний;
либо операнд слева вырос **фактом исполнения** — нотинал живого эпизода
считается по фактической средней цене, и проскок входа поднимает его выше
одобренного преконтролем плановой. Вторая тропа приводит к отказу на
действии, которое риска не создаёт вовсе (ослабление защиты с нулевыми
слагаемыми акта, `docs/rules/risk-policy.md`), — то есть контроль
срабатывает на **уже принятой** экспозиции, а не на новом решении. Обе
развязки одинаково не дают превысить потолок (действие не исполняется),
но маршрутизация в `ERROR` дополнительно **создаёт исполнение по рынку**
там, где риск уже был под контролем: `ErrorHandler` снял бы живой риск
защищённой позиции с корректно стоящим стопом, а исход попал бы в
`closeOutcome = NORMAL_EXIT` и в `R`-выборку неотличимо от торгового
решения — то есть ужесточение конфига загрязняло бы распределение `R`.

Исчерпанный бюджет сделки — ожидаемый
исход легитимной стратегии, а не рассогласование состояния: действие
**не исполняется**, сделка остаётся в текущем статусе и ведётся до
выхода имеющимися траншами. Ребро в `ERROR` означало бы, что нормальная работа
стратегии флагается как авария — и стоило бы teardown живого риска там,
где риск под контролем.

**`STOP_DISTANCE_BELOW_FLOOR` — в том же карв-ауте, и довод разный на
трёх ветвях.** Реджект уровня, стоящего ближе round-trip комиссии
(`docs/rules/risk-policy.md`), не является
признаком рассогласования ни на одной из них, но механизм сохранности
живого риска у каждой свой:

- **перенос уровня** (защитный `REPLACE`) — реджект приходится на
  **place-ногу**: старая защита остаётся живой, покрытие сохраняется;
- **первичная защитная заявка** после входа — жива встроенная защита
  входа, которая покрывает транш до подтверждения основной
  (`docs/rules/live-risk-protection.md`);
- **вход в `PRECHECK`** — живого риска у транша ещё нет вовсе, и развязка
  та же, что у прочих `BLOCKED` на этой стадии: терминал транша `CLOSED`,
  не авария (схема выше).

Уводить сделку в `ERROR` на любой из трёх значило бы рвать живой риск
там, где он под контролем.

**`LOSS_LIMIT_NOT_CONFIGURED` — тоже в карв-ауте.** Незаданное число
конфигурации — повод **внутренний** (тот же класс, что ужесточение
потолка системой): живой риск сделки при этом под контролем, а
маршрутизация в `ERROR` создавала бы исполнение по рынку и загрязняла
`R`-выборку исходом, к торговому решению не относящимся.

**Довод `PROTECTION_COVERAGE_REDUCED`.** Реджект защитного действия, оставляющего покрытие ниже
живой экспозиции, — не признак рассогласования, а **сработавший
контроль**: реджект приходится на **place-ногу** защитного `REPLACE`
(place-new → подтверждение → cancel-old), поэтому старая защита остаётся
живой и покрытие сохраняется; уводить сделку в `ERROR` значило бы рвать
живой риск там, где он под контролем. Дом предиката —
`docs/rules/live-risk-protection.md`.

**Довод `RISK_CREATING_UNDER_COLLAPSE` сильнее прочих.** Реджект набора риска в окне сворачивания
(`docs/rules/exit-teardown-order.md`) есть **сработавший по назначению
энфорсер**: сделка уже в координированном выходе, её позиция ведётся под
живой защитой, а объявленный стратегией шаг добора или замещения с
увеличением просто не исполняется. Увод в `ERROR` здесь превращал бы
**штатный выход в аварийный контур**: сделка, идущая к штатному терминалу,
получала бы teardown по рынку — ровно та цена, которой карв-аут
обосновывает свои исключения. Тропа не краевая: она достижима на каждом
координированном выходе сеточной сделки, у которой хоть один транш в
сопровождении несёт объявленный шаг добора.

Карв-аут не новый по конструкции: тот же ряд, что «транш в `PRECHECK` без
живого риска ⇒ его терминал `CLOSED`, не авария» (схема выше). Ось
разведения одна — **является ли реджект признаком рассогласования**.
Коды, которых в перечне нет, ведут в `ERROR`, и каждый — по своему
классу: `RISK_PER_ACTION_EXCEEDED` (сайзинг обязан был уложить действие в
поактный потолок — расхождение расчёта), `RISK_CREATING_ENTRY_WITHOUT_STOP`
(акт создаёт непокрытый риск), шесть кодов контура и инструмента,
`BALANCE_INVALID` и `BALANCE_NOT_FRESH`, `FEE_RATE_UNAVAILABLE`,
`DEAL_GRAPH_INCOMPLETE`, `CALCULATED_ACTION_INVALID`, три кода размера,
`TAKE_PROFIT_INVALID_SIDE` и три инварианта частичного выхода. Общее у
них одно: живой риск **не** под контролем либо состояние рассогласовано, и
teardown там не лишний, а необходимый.

### Отказ расчёта по стороне уровня — отказ шага, не авария

**Контролируемая ошибка расчёта `STOP_LEVEL_NOT_ON_LOSS_SIDE_FOR_SIZING`
сделку в `ERROR` не уводит.** Она приходит на входной тропе первой —
преконтроль вызывается после сайзинга
(`docs/processes/strategy-action-calculation.md`), — и ось у неё та же,
что у карв-аута выше: **является ли отказ признаком рассогласования**.
Не является: уровень уехал на прибыльную сторону от растущей рыночной
структуры, живой риск транша при этом под контролем либо его нет вовсе
(вход в `PRECHECK`). Исход — **шаг не исполняется**, транш и сделка
остаются в своих статусах; повтор придёт следующим проходом, когда
структура даст уровень на убыточной стороне.

**Тип ошибки — `PERMANENT`, а исход — исключение из общего разбора**, где
`PERMANENT` ведёт к отказу строки исполнения и ребру сделки в `ERROR`.
Тип и исход разведены намеренно: тип говорит, повторяется ли **вычисление**
(нет — операнд не «пока недоступен», он неверен), исход — что делать со
**сделкой**. Исключение названо здесь, а не в доке расчёта, потому что ось
разведения риск-оценочная и живёт в этом процессе; дом самой охраны
знаменателя — `docs/rules/risk-policy.md`.

**Статус здесь никто не присваивает.** Схема называет **исход**, а не
писателя: терминал сделки `CLOSED` пишет звено `MARK_DEAL_CLOSED_COMMAND`
(`docs/components/MarkDealClosedExecutor.md`), ребро в `ERROR` — по
карв-ауту природы тропы: решение handler'а ⇒ звено
`MARK_DEAL_ERROR_COMMAND`, перехват ⇒ прямая запись петлёй
(`docs/processes/fsm-execution-layering.md`). Прежняя запись «`Deal.status = ERROR`»
присваиванием выражала писателя, которого на этой тропе нет.

`RISK_CONTROL` отличается от `ENTRY_CONDITION_EXPIRED`: первое — вход
запрещён risk-policy до live risk; второе — входное условие стало false.
Отдельный `ENTRY_RISK_BLOCKED` не используется. Реакция на BLOCKED как
статусная механика — `docs/lifecycles/Deal.md`.

## Несколько actions в одном StrategyStep

Actions выполняются последовательно, **по одному за проход** (порядок и
темп — `docs/components/StrategyActionOrchestrator.md` §«Порядок выбора
действия», здесь они не пересказываются); для каждого — свежий
`CalculationContext` → расчёт → (risk-validation либо minimal
safety/invariant checks) → одна актуальная команда. «Последовательно» здесь
о **порядке**, не о темпе: пакет шага исчерпывается за несколько проходов,
и до его исчерпания шаг остаётся допустимым
(`docs/rules/strategy-step-once-per-episode.md`). Если любое
risk-creating действие step заблокировано — остальные actions step не
выполняются; реакция на сам блок берётся схемой реакции выше и здесь не
пересказывается. Если exit /
cleanup / safety действие не прошло minimal checks — step останавливается,
flow уходит в recovery / ERROR / safety по контексту.

## Границы с ошибками

`CalculationError` (не смогли безопасно рассчитать) ≠ `RiskValidationResult`
(рассчитали, проверили по policy) ≠ unexpected exception
(`RuntimeErrorCode`, см. `docs/rules/runtime-error-classification.md`).
`CalculatedRiskMetrics` из calculator-layer не передаётся — risk-layer сам
считает нужные метрики.
