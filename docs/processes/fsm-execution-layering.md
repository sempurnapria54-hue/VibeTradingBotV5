# Слои исполнения сделки

## На какой вопрос отвечает этот файл

Как разложены слои исполнения сделки от петли до биржевого вызова.

## Слои

```text
DealOrchestratorJob   петля по активным сделкам; по статусу выбирает handler сделки
  Handler сделки (ACTIVE, EXIT_PENDING, ERROR) три роли: условия входа, работа, условия перехода
    DealTrancheStateMachine     прогон FSM каждого нетерминального транша
                                — у ACTIVE и EXIT_PENDING; у ERROR не гоняется
      Handler транша (на статус транша) те же три роли
        StrategyActionOrchestrator  гейтит повтор и маршрутизирует по типу действия
          StrategyActionExecutor    per-pass: следующая команда действия за проход
            CommandExecutor         одна атомарная команда
    StrategyActionOrchestrator  шаги уровня сделки: EXIT, FAIL_SAFE
    SystemActionExecutor        per-pass эмиттер системных действий
      CommandExecutor           одна атомарная команда
  KillSwitch                    сбоку: аварийный исполнитель вне слоёв
```

## Кто прогоняет FSM транша — дом ответа

**Два обработчика сделки из трёх прогоняют FSM траншей, третий — нет.**

| Обработчик сделки | FSM траншей | Почему |
|---|---|---|
| `DealActiveHandler` (`ACTIVE`) | **гоняет** | штатная работа сделки и есть работа её траншей |
| `DealExitPendingHandler` (`EXIT_PENDING`) | **гоняет** | каскад выхода — это и есть прогон каждого нетерминального транша своим выходом; без него выходная проверка «все транши терминальны» не наступает никогда, и координированный выход не завершается (`docs/components/DealExitPendingHandler.md`) |
| `ErrorHandler` (`ERROR`) | **не гоняет** | набор риска остановлен по всем траншам сразу, разрешены только safety, восстановление и проверка фактов; терминальность траншей на этой тропе не требуется — аварийное ребро её не гейтит (`docs/components/ErrorHandler.md`) |

**Почему ответ записан здесь, а не в компонент-доках.** Это стыковая
истина: её читают обе стороны — машина сделки и машина транша — и ещё
три носителя. Пока она жила в каждом по-своему, четыре носителя
утверждали «гоняет **обработчик активной сделки**» (то есть только он),
два — «гоняют все три», а `ErrorHandler` прямо отрицал прогон у себя;
каждая формулировка была верна наполовину, и ни одна не была верна
целиком. Дом стыкового решения — не док деталей
(`.claude/rules/carrier-levels.md`); из носителей уровня «как разложены
слои исполнения» этот файл и есть тот, чей вопрос совпадает с вопросом
решения.

**Цена ошибки была направленной.** Прочтение «гоняет только обработчик
активной сделки» останавливает координированный выход: транши не
доходят до терминала, выходная проверка не сходится, сделка висит в
`EXIT_PENDING` с живой позицией. Прочтение «гоняют все три» запускает
машину транша в ошибочном состоянии — там, где риск может быть живым, а
торговля заблокирована.

Зависимости направлены сверху вниз: handler знает про оркестраторы и
исполнителей; `CommandExecutor` про вызывающих не знает. Уровень транша
вставлен между петлёй и оркестратором действий и той же вертикали не
нарушает: транш видит только своих соседей.

**Ошибочное состояние — только у сделки.** У транша ошибочного статуса
нет: отказ, который нельзя разобрать на месте, поднимается на уровень
сделки, и ребро в ошибку пишется там (`docs/lifecycles/Deal.md`).

## Handler — три роли

- **условия входа** — предусловия работы этого прохода. Не выполнены ⇒
  переход либо остаться;
- **работа** — через оркестраторы исполняет применимые действия
  стратегии и системные действия;
- **условия перехода** — по условиям стратегии и подтверждённым фактам
  решает следующий статус.

**Статусные рёбра, являющиеся исходом системного действия, пишет звено, а
не handler:** терминалы и подтверждение входа. Handler своими проверками
**гейтит эмиссию** завершающего звена, ребро едет в транзакции его
завершения.

## Ребро в `ERROR`: два механизма по природе тропы

| Природа тропы | Кто пишет ребро |
|---|---|
| **решение** — handler по подтверждённым фактам решил, что сделка идёт в `ERROR` | звено `MARK_DEAL_ERROR_COMMAND`; handler гейтит эмиссию |
| **перехват** — сделка уводится в `ERROR` внешним обстоятельством: enforcement холда, контролируемое исключение, граница исполнения прохода | петля прямой записью статуса, без действия и без анкера |

**Причину закрытия ни одна из двух троп не пишет.** `ERROR` — не терминал:
итоговая бизнес-причина определяется на ребре в аварийный терминал, и её
пишет там аварийный обработчик. У тропы перехвата обработчика нет вовсе,
поэтому назначить ей писателя причины было бы некому — это и есть довод, по
которому правило писателя причины называет рёбра, а не события (дом —
`docs/lifecycles/Deal.md`).

## Порядок выбора действия в пакете шага

Пакет шага исполняется целиком; за проход — одно действие.

**Порядок выбора — по риск-классу: устанавливающие защиту раньше
снимающих** (`docs/rules/live-risk-protection.md`). Действие, чьё
предусловие не выполнено, не начинает исполнения: строка исполнения не
заводится, бюджет попыток не расходуется, шаг остаётся неисполненным до
следующего прохода.

## Kill-switch стоит вне слоёв

Kill-switch — аварийный исполнитель, действием стратегии не
материализуется и петле не подчинён. Причина — в
`docs/rules/execution-hierarchy.md`: то, что снимает риск, не должно быть
остановимо тем, что ограничивает его набор.
