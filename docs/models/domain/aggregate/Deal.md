# Deal

## На какой вопрос отвечает этот файл

Что это за сущность `Deal`.

## Назначение

`Deal` — **агрегат торгового сценария по инструменту**: он координирует
транши, держит слот инструмента, владеет биржевыми эпизодами позиции и
отчётностью сделки. Собственного входа у него нет — вход, защита и выход
живут в траншах (`docs/models/domain/aggregate/DealTranche.md`).

`Deal` **не биржевая сущность**: внешнего идентификатора и внешнего
статуса у неё нет.

`Deal` **не отвечает** за сырые ответы биржи, историю команд, историю
изменений сущностей, подробный контекст входа, детали риск-проверок,
свежие рыночные данные и полную финансовую отчётность.

## Структура

| Поле | Тип | Назначение |
|---|---|---|
| `id` | `Long` | Внутренний идентификатор в БД. |
| `internalId` | `String` | Внешний идентификатор для API, логов, таймлайна. |
| `instrumentId` | `Long` | Инструмент. |
| `strategyDetailId` | `Long` | Закреплённая деталь стратегии: открытая сделка ведётся по ней, даже если стратегия изменилась или стала неактивной. **Пусто ровно у восстановленной сделки**: её заводит не выбор входа, и выбирать было нечего. |
| `status` | `Status` | Статус FSM агрегата. |
| `direction` | `StrategyTradeDirection` | Ожидаемое направление; направление позиции обязано ему соответствовать. **Одно на все транши**: в нетто-режиме разнонаправленных траншей не существует. |
| `entryReason` | `EntryReason` | Причина заведения сделки. FSM не управляет. |
| `entryMarketPhase` | `MarketPhase.Type` | **Фаза рынка при входе сделки. Write-once**, пишет `DealOpeningService` на тропе входа по объявлению той же транзакцией, что заводит сделку. Темпоральный операнд предиката смены тренда: своей истории у фазы нет, сравнивать текущую не с чем без этого поля. **Пусто ровно у восстановленной сделки** — входа по объявлению у неё не было, шагов и условий тоже. Форма предиката — `docs/spec/market-phase-condition.json`. |
| `shutdownReason` | `ShutdownReason` | Причина запущенного graceful shutdown. `closeReason` не заменяет. |
| `closeReason` | `CloseReason` | Итоговая бизнес-причина завершения **сделки**; у транша своя. |
| `plannedRiskAmount` | `BigDecimal` | **Риск, принятый сделкой на входах (`R`)** — заявленный риск живых и исполнившихся входных заявок всех траншей плюс налитая доля выбывших; формула — `docs/spec/deal-risk-numbers.json` §`dealPlannedRisk`. Знаменатель R-мультипликатора. Производная проекция, пересчитывается целиком. |
| `incurredRiskAmount` | `BigDecimal` | **Взятый на входе риск** — сколько из заявленного встало под удар. Измеритель разрыва «заявлено ↔ взято»; частичным выходом не уменьшается. Производная проекция. |
| `currentRiskAmount` | `BigDecimal` | **Неотработанная доля взятого на входе риска.** Уменьшается частичным выходом, при полном — ноль. Риском «под ударом сейчас» не является: уровня стопа формула не содержит. Производная проекция. |
| `protectionRelievedRiskAmount` | `BigDecimal` | **Риск, снятый защитой** — насколько действующий стоп уменьшил взятый риск. Наблюдение, не операнд потолков. Знак не клэмпится. Производная проекция. |
| `plannedRiskCurrency` | `String` | Валюта всех чисел риска сделки. Источник — расчётная валюта инструмента; у всех траншей она одна. Пишет `CreateOrderExecutor` при входном действии. |
| `plannedRiskEquityBase` | `BigDecimal` | **База риска на момент сайзинга.** **Write-once**: фиксируется первым сайзингом сделки — первым, каким бы траншем он ни делался. Потребители — знаменатель фактического процента риска в отчётности и база кумулятивного потолка. Пусто = сайзинга не было (позиция создана вне приложения). |
| `resultProfit` | `BigDecimal` | Итоговый результат сделки. |
| `resultProfitCurrency` | `String` | Валюта результата. Источник — расчётная валюта инструмента. |
| `billsWindowBegin` | `OffsetDateTime` | **Нижняя граница окна линковки движений.** Единственный писатель — `SubmitOrderExecutor`, по времени создания первой отправленной входной заявки сделки, каким бы траншем она ни ставилась. Write-once. |
| `billsWindowEnd` | `OffsetDateTime` | **Верхняя граница окна линковки.** Пишет наблюдатель факта закрытия эпизода, **монотонно вперёд**. Пусто = закрытие не добыто ни у одного эпизода. |
| `billsFetchedThrough` | `OffsetDateTime` | **До какого момента движения добыты.** Пишет `RefreshBillsExecutor`, **монотонно вперёд**. Единственный durable-факт «добыча выполнялась»: пусто = не добывали, а не «добыли, движений нет». |
| `closeOutcome` | `CloseOutcome` | Торговый исход закрытия — признак отбора для отчёта. |
| `reconciliationStatus` | `ReconciliationStatus` | Исход сверки разбивки — признак отбора. Свойство числа, а не членства: сделка остаётся в популяции при любом значении. |
| `breakdownIncomplete` | `BreakdownCompleteness` | Полнота разбивки — признак отбора. |
| `riskBenchmarkAvailability` | `RiskBenchmarkAvailability` | Почему знаменатель `R` пуст или непуст — признак отбора. |
| `tranches` | `List<DealTranche>` | **Транши сделки.** Материализуются при создании: по объявлениям детали, каждый в своём `PRECHECK`, — а у восстановленной сделки один, без объявления и сразу в сопровождении. |
| `positions` | `List<Position>` | **Эпизоды позиции**: одна биржевая позиция — одна строка. Живой эпизод не более одного; закрытые остаются. Предикат модели `livePosition` отдаёт живой либо пусто. |

**Заявок и условных заявок у агрегата нет:** они принадлежат траншам.
Читатель, которому нужны все заявки сделки, собирает их обходом траншей.

Все признаки отбора пусты до терминала; пусто у них означает «признак
неприменим» — тропа закрытия без входа.

## Енумы

**`Status`** — `ACTIVE`, `EXIT_PENDING`, `CLOSED`, `ERROR`,
`EMERGENCY_CLOSED`. Значения и переходы — `docs/lifecycles/Deal.md`.

**`EntryReason`** — `STRATEGY` и `RECOVERY`: по значению на каждую тропу
создания сделки. Оба пишет `DealOpeningService` при создании — значением
той тропы, которой он вызван (`docs/components/DealOpeningService.md`):

| Значение | Тропа создания | Кто зовёт и когда |
|---|---|---|
| `STRATEGY` | вход по стратегии | `EntryScannerJob`, когда сработало условие входа |
| `RECOVERY` | восстановление уже живого риска, созданного вне приложения | `AnomalyJob`, когда нашёл активную позицию, которую не объясняет ни одна сделка |

**Третьего значения нет, и пустого — тоже.** Причина известна тому, кто
сделку заводит: пустота означала бы, что создатель не знал, зачем создаёт,
а второй ярлык той же тропы разошёлся бы с первым — и предикат
`positionObserved` (`docs/spec/deal-context-load.json`), стоящий на
`RECOVERY`, перестал бы исчерпывать популяцию сделок, заведённых вокруг
наблюдённой позиции: сделка с другим ярлыком прошла бы с пустыми
эпизодами.

Живёт на агрегате, а не на транше: у восстановленной сделки объявленных
траншей нет вовсе.

**`ShutdownReason`** — `STRATEGY_DELETED`, `MARKET_DATA_EXPIRED`,
`MANUAL_STOP`, `RISK_POLICY`, `EXCHANGE_HOLD` (производится каскадом
биржевой ступени 2; мягкий холд сделок не гасит), `UNKNOWN`. Пишется
только при реальном запуске graceful shutdown.

**`CloseReason`** — `ENTRY_CONDITION_EXPIRED`, `STRATEGY_EXIT`,
`TAKE_PROFIT`, `STOP_LOSS` (включая трейлинг), `TIME_STOP`,
`RISK_CONTROL`, `EMERGENCY_CLOSE`, `UNKNOWN`. `MANUAL_CLOSE` снят —
`docs/rules/manual-halt.md`. Описывает
бизнес-причину, а не технический механизм закрытия. Енум общий с траншем:
причина закрытия транша выражается теми же значениями.

**`CloseOutcome`** — торговый исход закрытия:

| Значение | Что означает |
|---|---|
| `NORMAL_EXIT` | позицию закрыли мы либо биржевое событие вне ликвидационного контура |
| `LIQUIDATION` | принудительное закрытие по марже |
| `FORCED_REDUCTION` | принудительное сокращение |
| `UNDETERMINED` | торговый исход **не установлен** — значение, а не пустота: сделка остаётся в популяции и счётна отдельной корзиной |

**Производителей у `UNDETERMINED` несколько, и перечисляет их правило
резолва** — `docs/models/mapping/PositionCloseResult.md`, дом отображения
сырого типа закрытия в это значение. Здесь перечень не дублируется:
значение отвечает «исход не установлен», а чем именно он не установлен —
вопрос резолва.

Отличается от `closeReason` намеренно: тот — бизнес-причина завершения
сделки, этот — рыночный факт того, кто и почему закрыл позицию. На
`closeReason` фильтровать нечем: одно значение переиспользовано двумя
тропами, а ликвидация в нём не выражается вовсе.

**`ReconciliationStatus`** — `NOT_RUN` (сверка **не была обязана**),
`MATCHED` (общее расхождение в пределах допуска), `MISMATCHED` (сверх
допуска). Третьего значения нет: различение «были обязаны и не
посчитали» несёт терминальный статус, а не признак.

**`RiskBenchmarkAvailability`** — `AVAILABLE` (знаменатель определён),
`NOT_APPLICABLE` (входа не было, поэтому знаменателя нет **по
построению** — нормальная популяция, не аномалия), `MISSING` (вход был, а
знаменателя нет — аномалия с отчётом).

**`MISSING` производит отчёт аномалии, и состав отчёта — здесь.**

| Что | Значение |
|---|---|
| машинный код причины | `RISK_BENCHMARK_MISSING` |
| радиус | инструмент сделки |
| природа факта | событие — своя строка на каждую такую сделку, а не держащееся состояние |
| критичность | некритичный: kill-switch не гоняется |
| момент | после коммита терминала; терминал отчётом не блокируется |
| писатель | тот же, кто пишет значение (таблица троп ниже) |

**Отчёт есть только у `MISSING`.** Оно означает «вход был, а знаменателя
`R` нет» — популяцию, у которой знаменатель потерян при состоявшемся
входе; без отчёта она не всплывает ни в одном сигнале, и «не проверяли»
перестаёт отличаться от «проверили, всё в порядке» (`docs/concept.md` §П1). `AVAILABLE` и `NOT_APPLICABLE` — нормальные исходы, отчёта не
производят.

**Значение определяет факт входа, а не тропа и не терминал.** Правило
тотально: `!hadEntry` ⇒ `NOT_APPLICABLE`; иначе `AVAILABLE` либо
`MISSING` по факту знаменателя. Форма — `docs/spec/deal-lifecycle.json`
§`benchmarkAvailabilityOnTerminal`. Отсюда `NOT_APPLICABLE` пишется на
**любом** терминале, включая **аварийный у не вошедшей сделки**: из
ошибочного состояния другого ребра нет, и приписывать этой популяции
аномалию было бы ложным ярлыком на полностью нормальном исходе.

**Тропа определяет только писателя**, и перечень собран по произведению
двух осей — «штатный / аварийный терминал» × «вход был / не был»:

| Тропа | Писатель |
|---|---|
| штатная, вход был | `FinalizeDealExitExecutor` |
| аварийная, вход был | `MarkDealEmergencyClosedExecutor` |
| любая, входа не было | терминал, применивший ребро: `MarkDealClosedExecutor` либо `MarkDealEmergencyClosedExecutor` |

Троп три, компонентов-писателей три, и совпадения счётов между ними нет:
аварийный терминал стои́т на **двух** тропах из трёх, а финализация выхода
— на одной. Разведение писателей по тропам и состав того, что каждый
пишет, — `docs/lifecycles/Deal.md`.

**`BreakdownCompleteness`** — `COMPLETE` (возраст нижней границы окна на
момент добычи не превышает глубины доступности движений),
`INCOMPLETE_BY_WINDOW` (превышает), `NOT_ASSESSED` (сравнение не
выполнялось: добыча движений не выполнялась — единственный триггер).

## Экспозиция сделки и сверка с биржей

**Экспозиция сделки — сумма экспозиций её траншей**, а экспозиция транша
— производная его собственных заявок **и приписанного ему закрывающего
исполнения уровня сделки**
(`docs/models/domain/aggregate/DealTranche.md`). Отдельным полем не
хранится.

```text
Σ экспозиций траншей  =  Position.externalSize живого эпизода
```

**Равенство — инвариант, а не наблюдение к сведению.** Расхождение
означает живой риск, который модель не приписывает ни одному траншу:
внешнее закрытие, чужая позиция, ошибка вывода.

**Ступень реакции — биржевая ступень 2**, сворачивание
(`docs/rules/exchange-hold.md`), в обе стороны расхождения:

- **сумма меньше нетто-размера** — экспозиция, не приписанная ни одному
  траншу. Покрытие считается потраншево, поэтому неатрибутированная
  экспозиция по построению **не покрыта**, а живой риск без покрытия и
  есть второй триггер ступени 2;
- **сумма больше нетто-размера** — часть нашей экспозиции закрыта не
  нами. Это первый триггер той же ступени: сущность не там, где мы её
  ожидали. **В окне сворачивания сделки эта сторона не срабатывает,
  пока нетто-размер не превосходит Σ gross-экспозиций:** недостача уходит
  в четвёртое слагаемое экспозиции транша (правило сопоставления) и до
  сверки не доживает — вместе с нашим закрытием там поглощается и чужая
  активность в обе стороны. Сверх границы поглощать нечем, и сверка
  срабатывает даже в окне. Это названное ограничение с названными
  удержаниями и названной границей, оно живёт у дома правила
  (`docs/models/domain/aggregate/DealTranche.md`); **вне окна** обе стороны сверки работают без оговорок, и
  окно узкое: координированный выход либо ошибочное состояние при уже
  плоской позиции.

**Ребро — каскад ступени 2**, а не отдельное решение обработчика:
сворачивание уводит активные сделки биржи в ошибочное состояние своим
составом. Обнаружить расхождение могут двое — входная проверка активной
сделки в проходе и `AnomalyJob` вне прохода, — но ступень у них одна;
нового носителя реакции инвариант не вводит.

**Обе стороны опасны одинаково**, потому что обе означают одно: наш счёт
экспозиции разошёлся с биржей, и посылка «мы знаем, чем рискуем»
перестала держаться.

## Итоговый результат сделки

**`resultProfit` — сумма net по эпизодам плюс слагаемое чужой валюты.**
Форма — одним экземпляром в `docs/spec/deal-result.json`: там формула,
предикат области чужой валюты, условие доступности числа и примеры. Здесь
— то, что формулой не выражается.

- **Net берётся готовым** из записи закрытия каждого эпизода
  (`Position.externalRealizedProfit`), посчитан биржей и номинирован в
  расчётной валюте.
- **Сумма — производная проекция, пересчитываемая целиком:**
  инкрементального накопления нет, повторное наблюдение не задваивает
  число.
- **Число недоступно, а не занижено**, когда не добыта запись закрытия
  любого эпизода, **либо** разбивка движений не добыта или предъявлена не
  целиком, **либо** движение вне расчётной валюты ждёт курса. Во всех трёх
  случаях итог не публикуется и финализация выхода не завершается.
  **Ожидание конечно:** оно живёт в бюджете попыток исполнения добычи, а
  по исчерпании бюджета сделка уходит ошибочной тропой к аварийному
  терминалу — разбор держателя наступает **после** него, а не вместо
  него. Пропуск слагаемого и публикация итога без него запрещены — это
  было бы благоприятное умолчание (`docs/concept.md` §П1). Дом ожидания
  — `docs/rules/pnl-reconciliation.md`.
- **Ветвление «закрытие без входа» берёт признак у дома** —
  `docs/rules/deal-without-operations.md`; здесь он не переопределяется.
  Durable-резолв признака — `docs/spec/deal-context-load.json`
  §`positionObserved`.
- **Ноль допустим только как результат расчёта**, не как молчаливый
  запасной вариант; на тропе закрытия без входа ноль и есть расчёт.

**Результат потраншево не разбивается — и это названное ограничение.**
Нетто-режим отдаёт реализованный net на эпизод, а не на транш; доменная
атрибуция закрытий была бы накопителем, зависящим от порядка событий.
Отсюда R-мультипликатор — метрика сделки, а не транша.

**Расчёт и запись — писателей три, и перечень закрыт.**

| Писатель | Когда пишет число | Когда пишет валюту |
|---|---|---|
| `FinalizeDealExitExecutor` | штатная тропа: вычисляет и пишет в одной транзакции с продвижением своего исполнения, поэтому durable-носитель числа есть само поле | той же транзакцией |
| `MarkDealClosedExecutor` | числа не пишет — непустоту **ассертит** и ставит терминал; исключение — тропы закрытия **без входа**, где пишет ноль сам | на тропе без входа — той же транзакцией, что и ноль |
| `MarkDealEmergencyClosedExecutor` | аварийная тропа: best-effort по доступности — пишет, когда числа ещё нет, и не трогает, когда оно уже стои́т (`docs/components/MarkDealEmergencyClosedExecutor.md`) | той же транзакцией, что и число, по тому же правилу |

**Третий писатель прежде назван не был**, хотя число на аварийной тропе
пишет именно он: перечень объявлял двоих, и правило записи валюты,
объявленное **единым на все тропы**, на аварийной оставалось без актора.
Пустая клетка означала бы, что вошедшая сделка уходит в аварийный терминал
с числом без валюты — а контракт штатного терминала валюту требует, и
разойтись эти два ребра не вправе.

**Валюта результата — один авторитет:** расчётная валюта инструмента.
Валюта, пришедшая от биржи, — проверяемый признак, а не источник. Правило
записи одно на все тропы (`docs/lifecycles/Deal.md`); писатель на каждой — из таблицы выше.

**Категорийная разбивка в `Deal` не хранится** — она строки
`DealCashFlow`. Сверка суммы разбивки с net — `docs/rules/pnl-reconciliation.md`.

## Четыре числа риска

Все четыре — **производные проекций заявок всех траншей**, а не
накопители, и пересчитываются целиком одной транзакцией тем писателем,
который меняет операнд. Группировка по траншам их не сдвигает: область
отбора — входные заявки сделки, чьи бы транши их ни держали.

| Число | Отвечает на вопрос | Роль |
|---|---|---|
| `plannedRiskAmount` | под какой риск сайзились | знаменатель `R` и операнд кумулятивного потолка |
| `incurredRiskAmount` | сколько из заявленного встало под удар | наблюдение |
| `currentRiskAmount` | сколько взятого ещё не отработано | сопровождение |
| `protectionRelievedRiskAmount` | насколько защита уменьшила взятый риск | наблюдение, диагностика запертой прибыли |

**Формулы и предикаты отбора слагаемых — `docs/spec/deal-risk-numbers.json`.**

### Писатели четвёрки и их триггеры

Перечень закрытый: писателем четвёрки является тот и только тот
исполнитель, чья транзакция меняет операнд хотя бы одного из четырёх
чисел. Каждый пересчитывает **все четыре** целиком, а не своё —
частичный пересчёт оставлял бы соседние числа посчитанными по прежнему
графу.

| Писатель | Триггер — что он меняет | Операнд четвёрки |
|---|---|---|
| `docs/components/CreateOrderExecutor.md` | заводит ногу входа с её встроенной защитой | множество входных ног и уровень действующей защиты |
| `docs/components/RefreshOrderExecutor.md` | наблюдает филл либо терминальный статус ноги | доля ноги (полная заявленная против налитой) |
| `docs/components/RefreshPositionExecutor.md` | наблюдает размер живого эпизода и смену эпизода | множитель живого слагаемого |
| `docs/components/CreateAlgoOrderExecutor.md` | ставит отдельную условную защиту | уровень действующей защиты |
| `docs/components/RefreshAlgoOrderExecutor.md` | наблюдает состояние условной заявки | уровень действующей защиты |

**Кого в перечне нет и почему.** Отмена — обычной заявки и
условной — операнда не меняет: живость ноги и защиты резолвится
статусом, а снятие статус не финализирует — его двигает наблюдённый
факт (`docs/lifecycles/Order.md`, `docs/lifecycles/AlgoOrder.md`).
Обе команды записывают намерение, и пересчёт на нём был бы
пересчётом по намерению; критерий здесь симметричен для обоих классов
заявки. Создание — другое дело и в перечне стоит: созданная заявка
уже живая (`docs/spec/order-lifecycle.json`,
`docs/spec/algo-order-lifecycle.json`), то есть строка входит в
агрегат той же транзакцией, без внешнего факта.

База риска сайзинга, валюта риска и шесть чисел планового риска
ноги — write-once снимки, а не производные графа: они пишутся
одним ходом при заведении ноги и пересчёту не подлежат.

**Пересчёт запрещён на неполном графе, и это обязанность каждого
писателя перечня.** Числа считаются по ногам, защитам и эпизодам, взятым
из контекста прохода; если контекст предъявил граф не целиком, пересчёт
дал бы **заниженное** `plannedRiskAmount` — то есть ослабленный
кумулятивный потолок (`docs/rules/risk-policy.md`), ошибку в разрешающую
сторону. Поэтому:

- **что читает писатель** — готовый признак полноты графа на контексте
  прохода (`docs/components/models/DealContext.md`); величина и её
  конъюнкты — `docs/spec/deal-context-load.json`, `graphComplete`.
  Признак читается готовым и не пересобирается: иначе каждый писатель
  обязан был бы знать объём загрузки;
- **что делает при ложном признаке** — не пишет чисел и **не завершает
  своё звено**; прежние значения на сделке остаются нетронутыми, повтор
  идёт по бюджету попыток строки исполнения
  (`docs/models/domain/other/DealActionState.md`). Исчерпание бюджета —
  штатная ошибочная тропа действия, а не тихое продолжение с прежними
  числами;
- **чем правило проверяется** — оно исполнимо, а не только записано:
  `docs/spec/deal-context-load.json` несёт решающее правило
  (`riskNumbersRecomputed`), значение, которое окажется в колонке
  (`plannedRiskWritten`), три исхода звена (`recomputeLinkCompletes`,
  `recomputeWaitContinues`, `recomputeErrorPathRequired`) и направление
  ошибки при неполноте (`riskNumbersAnswerDistorted`). Форма здесь не
  переписывается;
- **почему признак именно графа, а не контекста целиком** — строки
  разбивки движений ни в один из четырёх операндов не входят, а их
  выборка берётся окном с потолком. Гейт по полноте контекста целиком
  остановил бы ведение живого риска у долгой сделки из-за длины её
  истории движений — цена, которой ни одно из четырёх чисел не требует.

**Читатель четвёрки, принимающий разрешающее решение, гейтится тем же
признаком.** Единственный такой читатель — преконтроль риска
(`docs/components/RiskValidator.md`): он берёт `plannedRiskAmount`
операндом кумулятивного потолка, а остальные операнды потолков считает
по тому же графу в точке проверки. Неполный граф занизил бы и то и
другое, поэтому преконтроль на нём отказывает, а не разрешает.
**Это тоже исполнимо, а не только записано:** `docs/spec/risk-limits.json`
берёт полноту графа операндом с указателем на дом признака, и три операнда
потолков, считаемые по графу (`dealRiskTaken`, `liveRiskNow`,
`dealNotional`), на неполном пусты — стоящие на них неравенства отказывают
вычислением. Форма признака здесь не переписывается.
Читатели, разрешающих решений не принимающие (отчётность, диагностика
разрыва «заявлено ↔ взято»), гейта не требуют.

Ключевые свойства, из которых формулы выведены:

- **Отбор идёт по бизнес-типу заявки, а доля — по её состоянию:** живая
  и исполнившаяся входят заявленным риском целиком, выбывшая (снятая,
  `ERROR`) — только **налитой долей**. Довод «снятая заявка не стояла»
  верен для её **неисполненной** доли и неверен для налитой: за налитую
  сделка рисковала и продолжает рисковать. Перевыставление входа
  знаменатель не раздувает (неисполненная доля выбывшей ноги в него не
  входит) и не обнуляет.
- **Различие заявленного и взятого — в доле, а не в множестве:** оба
  числа отбирают одни и те же входные ноги, но `plannedRiskAmount` берёт
  у живой и исполнившейся **полный заявленный** риск, а
  `incurredRiskAmount` — только **налитую долю**. Отсюда взятое не
  превышает заявленного, а разрыв между ними и есть неисполненная доля
  заявленного риска живых и исполнившихся ног. На **выбывшей** ноге два
  числа совпадают: заявленное берёт с неё ту же налитую долю — отбор идёт
  по бизнес-типу заявки, а доля по её состоянию.
  Частично исполнившаяся и затем снятая заявка из заявленного **не
  выходит** — она отдаёт в него свою налитую долю. Собственный конъюнкт
  взятого риска `accumulatedFillSize > 0` говорит то же прямо: нет
  филла — нет и взятого.
- **Отбор идёт по наблюдённому состоянию, а не по намерению:** пока
  отмена не подтверждена фактом, заявка считается живой.
- **Пара «снятое защитой» считается по заявкам живого эпизода:**
  уменьшаемое пожизненно, а вычитаемое разбирается по действующей
  защите, и без эпизодного конъюнкта покрытия половин расходились бы.
- **Уровень действующей защиты резолвится по траншу:** наименее
  благоприятный среди всех его действующих защит; класс носителя отбор
  не сужает. Форма — `docs/spec/protection-coverage.json`, величина
  `trancheStopCurrent`. Уровень **на всю позицию** — другая величина того
  же дома (`stopCurrentLive`), и она операнд сделочных потолков, а не
  этих четырёх чисел: на сетке из нескольких траншей это разные числа
  (`docs/rules/risk-policy.md`). Защиты нет вовсе — поле пусто целиком, а
  не ноль.

**Знак не клэмпится:** стоп за безубытком даёт отрицательный риск при
действующем стопе и снятое защитой больше взятого; ослабление защиты
уменьшает поле вплоть до отрицательного. Клэмп убил бы ровно ту
информацию, ради которой пара чисел заведена.

**Операнды потолков риска — не эти поля**, а производные графа в точке
проверки (`docs/rules/risk-policy.md`). Потолки — агрегатные: транши их
не множат.

## Окно линковки движений

Границ **две, и роли у них разные**:

- **`billsWindowEnd`** — порог **доказанного покрытия**: до какого
  момента наблюдался факт закрытия. Монотонна вперёд, потому что число
  наблюдений равно числу закрывшихся эпизодов, и граница обязана
  накрывать движения всех;
- **`billsFetchedThrough`** — **прогресс добычи**: до какого момента
  движения фактически вычитаны. Тоже монотонна вперёд, потому что
  фиксирует прогресс, а не однократно наблюдённый факт.

**У нижней границы один писатель колонки** — отправка первой входной
заявки сделки: момент первого обращения к бирже по этой сделке
единственный, и второго кандидата **на запись** нет. Транш, поставивший
её, роли не играет: граница — свойство сделки.

**Операнд чтения при этом двухместный, и это не противоречие.**
Писатель отвечает на вопрос «что попадает в колонку», операнд — на
вопрос «от чего считать окно **сейчас**». Они расходятся ровно на одной
тропе: у сделки, заведённой восстановлением существующего живого риска,
входной заявки не отправлялось никогда, колонка пуста навсегда, а
движения у неё есть. Поэтому при пустой колонке нижняя граница берётся
**биржевым моментом создания сделки** — подстановкой **внутри
исполнителя**, не записью в колонку
(`docs/components/RefreshBillsExecutor.md`).

**Различитель провенанса стои́т на пустоте колонки:** «граница добыта»
и «граница подставлена» различимы всегда, потому что подстановка колонку
не трогает. Без суррогата восстановленная сделка осталась бы без окна —
то есть без разбивки движений вовсе, и это было бы благоприятное
умолчание.

Границы — **собственные поля сделки**, а не сборка из чужих строк:
окно не зависит от того, какие движения уже добыты. Суррогат этого не
нарушает — он берётся из поля аудита той же сделки
(`docs/models/domain/other/Auditable.md`), а не из чужой сущности.

## Runtime-граф

`Deal` содержит `tranches` и `positions`; заявки и условные заявки висят
на траншах. Живой риск сделки вычисляем, отдельным полем не хранится.

**Закрытые эпизоды из графа не выводятся:** по ним считается результат и
правые операнды пар сверки. «Текущая позиция» — предикат `livePosition`,
а не отдельное поле.

**В граф не входят и в `Deal` не хранятся:** строки исполнения, биржа,
инструмент, деталь стратегии, баланс, сырые факты биржи, контекст
расчёта, рыночные данные, аудит, ожидающие команды. Также не хранятся
идентификатор фазы входа (выводится через деталь стратегии) и торговые
моменты времени (через заявки, позиции и аудит).

**У восстановленной сделки фазы входа нет вовсе** — не «не хранится, но
выводима», а не существует: детали она не закрепляет, и выбора фазы на её
тропе не было. Читатель, которому фаза нужна, обязан различать эти два
случая: невыводимость здесь — свойство тропы, а не потеря операнда.

## Персистентность

Таблица `deals`, наследует поля аудита. Транши, runtime-граф и разбивка
движений — отдельные таблицы по `deal_id`, не каскадные коллекции этой
строки.

**`NOT NULL`:** `internal_id`, `instrument_id`, `status`, `direction`,
`entry_reason`.

**Nullable:** `strategy_detail_id`, `entry_market_phase`,
`shutdown_reason`, `close_reason`, все
четыре числа риска, `planned_risk_currency`, `planned_risk_equity_base`,
`result_profit`, `result_profit_currency`, `bills_window_begin`,
`bills_window_end`, `bills_fetched_through`, `close_outcome`,
`reconciliation_status`, `breakdown_incomplete`,
`risk_benchmark_availability`.

**`entry_market_phase` пуст по тому же основанию, что и
`strategy_detail_id`:** фазу входа наблюдает вход по объявлению, а у
восстановительной тропы его нет. Обе колонки пусты ровно у
восстановленной сделки, и предикат смены тренда у неё не вычисляется —
условий она не имеет.

**`strategy_detail_id` пуст, а `entry_reason` — нет, и основание у обоих
одно.** Деталь выбирает вход; у восстановительной тропы выбора входа нет,
а на инструменте без активной стратегии выбирать не из чего вовсе —
поэтому колонка пуста ровно у восстановленной сделки и непуста у всякой
другой. Причину же знает всякий создатель: обе тропы называют её сами, и
пустой она не бывает. С траншем симметрия полная — `strategy_tranche_id`
пуст у восстановленного транша по тому же основанию
(`docs/models/domain/aggregate/DealTranche.md`).

**`external_created_at` обязателен по существу, но колонкой не
ограничен.** Обе тропы создания пишут его всегда, а у восстановленной
сделки он к тому же единственный операнд нижней границы окна линковки.
Ограничением он тем не менее не закреплён, и это названный выбор, а не
пропуск: на его пустоте стои́т живой предикат резолвимости границы
(`docs/spec/cash-flow-linkage.json`), и `NOT NULL` обнулил бы его ложную
ветвь вместе с наблюдаемостью дефектного писателя. Развилка — у владельца
окна линковки, там же, где вопрос о самой границе.

**Биекция «пусто ⟺ `RECOVERY`» обеспечена ограничением, а не текстом:**
`check ((strategy_detail_id is null) = (entry_reason = 'RECOVERY'))`.
Снятие `NOT NULL` убрало у колонки единственную защиту, и заменять её
соглашением нельзя: на этой биекции стои́т ветвление читателей, а
разошедшаяся пара молча даёт сделку без детали и без объяснения, откуда
она такая. Довод «таблицы пусты» здесь неприменим — он снимает бэкфилл, а
не ограничение.

**Обязанность заполнения на восстановительной тропе названа у писателя** —
`docs/components/DealOpeningService.md` даёт перечень «чем заполняется
каждое обязательное поле восстановленной сделки».

**`entry_step_type` в `deals` нет** — колонка уехала на транш вместе с
входом.

**Типы:** денежные величины — `numeric(36,18)`; строковые и енум-колонки
— `varchar(64)`; временные отметки — `timestamptz`. Енумы хранятся
именем значения.

**Существующая `result_profit_currency` — `varchar(16)`**, и это
названная несимметрия: единая норма длин действует на вводимые колонки,
а шестнадцати символов хватает любому тикеру валюты.

**Write-once обеспечивается условным обновлением, а не запретом на
запись:** строка создаётся раньше, чем наблюдается факт.

| Колонка | Guard |
|---|---|
| `bills_window_begin` | `where bills_window_begin is null` |
| `planned_risk_equity_base` | `where planned_risk_equity_base is null` — охраняет не конкуренцию писателей, а вторую и последующие входные заявки, чьими бы траншами они ни ставились |
| `bills_window_end` | `where bills_window_end is null or bills_window_end <:uTime` — монотонность, не write-once |
| `bills_fetched_through` | `where bills_fetched_through is null or bills_fetched_through <:tSource` — монотонность |

`internal_id` неизменен после создания.

**Ключи и индексы:**

- **`uk_deal_active_instrument`** — частичный уникальный индекс по
  инструменту среди нетерминальных статусов. Инвариант «одна незакрытая
  сделка на инструмент» на уровне БД, как страховка к гейту приложения.
  `ERROR` считается активным: такая сделка слот держит. **Слот держит
  агрегат, не транш.**
- **`ix_deal_status_close_outcome`** — выборка отчёта по терминалу и
  торговому исходу. Её префикс обслуживает и горячую выборку активных
  сделок, поэтому отдельного индекса по статусу нет.
- **`ix_deal_instrument_status`** — гейт входа по инструменту.

**Конкурентная вставка** новой сделки, нарушающая уникальный ключ,
ловится как безобидный пропуск: гонку между проходами закрывает
инвариант БД, приложение её не эскалирует.

## Границы

- **Строка исполнения не поле `Deal`:** это отдельная persisted-запись
  исполнения действия. Связь — от транша к строкам исполнения, от них к
  runtime-цели.
- **Контекст прохода не часть модели:** он добавляет биржу, инструмент,
  закреплённую деталь стратегии (у восстановленной сделки её нет — и это
  не недогруз), последний баланс и список строк исполнения.
- **Собственного входа у агрегата нет:** он не ставит заявок и не снимает
  их. Единственное закрывающее действие уровня сделки — полное закрытие
  нетто-экспозиции, и оно законно, только когда выходят все транши
  (`docs/rules/exit-teardown-order.md`).
