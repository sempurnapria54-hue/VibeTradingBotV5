# Deal

## На какой вопрос отвечает этот файл

Что это за торговая модель `Deal` (lifecycle root и runtime graph
сделки): структура, енумы, runtime graph, итоговый PnL.

Статусы и переходы — в `docs/lifecycles/Deal.md`. Полная редакция с
историей решений и снятыми формулировками — архив
`.claude/work/history/2026-08-26-policy-home-split/Deal-full.md`.

## Назначение

`Deal` — lifecycle root и runtime graph торговой сделки. Фиксирует,
что система начала сопровождать торговый сценарий по конкретному
`Instrument`, по pinned `StrategyDetail`, в ожидаемом направлении,
с FSM-статусом, причиной создания, причиной завершения и итоговым
profit/loss.

`Deal` **не** является биржевой сущностью: нет external id, нет
external status, OKX mapping-документ не нужен. `Deal` **не**
отвечает за: сырые exchange responses, историю команд, историю
изменений сущностей, подробный entry context, risk-check details,
свежие market/calculation data, raw fills archive, полную финансовую
отчётность.

## Структура

Java-класс `com.example.tradingbot.domain.model.aggregate.deal.Deal`,
расширяет `Auditable`.

|---|---|---|
| `id` | `Long` | Внутренний идентификатор в БД. |
| `internalId` | `String` | Безопасный внешний/межсервисный id (API, логи, timeline). |
| `instrumentId` | `Long` | Инструмент (полный `Instrument` — в `DealContext`). |
| `strategyDetailId` | `Long` | Pinned `StrategyDetail`: даже если `Strategy` изменится / станет INACTIVE / DELETED, открытая сделка ведётся по этой pinned-версии. |
| `status` | `Status` | FSM-статус (см. lifecycle). |
| `direction` | `StrategyTradeDirection` | Expected direction (`LONG`/`SHORT`), фиксируется при создании; `Position.direction` должен ему соответствовать. |
| `entryReason` | `EntryReason` | Короткая причина создания (не управляет FSM). |
| `entryStepType` | `EntryStepType` | Тип entry-step (`ENTRY`/`GRID_ENTRY`/null; не управляет FSM). |
| `shutdownReason` | `ShutdownReason` | Причина graceful shutdown / controlled close (если запущен). Не заменяет `closeReason`. |
| `closeReason` | `CloseReason` | Итоговая бизнес-причина завершения. |
| `plannedRiskAmount` | `BigDecimal` | **Заявленный плановый риск сделки (`R`)** — **сумма** плановых рисков её **живых и исполнившихся** ног входа (`Order.plannedRiskAmount`); снятые ноги не входят. **Знаменатель R-мультипликатора** (§«Плановый риск», §«Предикат отбора слагаемых»). Не write-once: производная проекция ног, пересчитывается целиком. |
| `incurredRiskAmount` | `BigDecimal` | **Взятый риск сделки (на входе)** — сколько из заявленного встало под удар: Σ по ногам входа `plannedRiskAmount_i × (accumulatedFillSize_i / plannedSizeContracts_i)`. Не знаменатель — измеритель разрыва «заявлено ↔ взято». **Частичным выходом не уменьшается** (§«Взятый риск»). Не write-once, производная проекция. |
| `currentRiskAmount` | `BigDecimal` | **Неотработанная доля взятого на входе риска**: `incurredRiskAmount × (livePosition().externalSize / Σ accumulatedFillSize_i)`. Уменьшается частичным выходом, при полном — ноль. **Риском «под ударом сейчас» не является** — уровня стопа формула не содержит. Потребитель — **сопровождение**, не отчёт. Не write-once, производная проекция. |
| `protectionRelievedRiskAmount` | `BigDecimal` | **Риск, снятый защитой** — насколько актуальный стоп уменьшил взятый риск: `incurredRiskAmount − riskAtCurrentStop` (закрытая форма вычитаемого — §«Форма вычитаемого»). Пересчитывают писатели защиты (`CreateOrderExecutor` — встроенная защита ноги входа; `CreateAlgoOrderExecutor` / place-нога `REPLACE` — standalone). Величину «риск под ударом» несёт эта пара чисел, а не `currentRiskAmount` в одиночку. Знак не клэмпится. Не write-once, производная проекция. |
| `plannedRiskCurrency` | `String` | Валюта планового риска — **одна на все четыре числа** (та же, что у `resultProfitCurrency` — иначе отношение не считается). Источник у писателя — **расчётная валюта инструмента** (`Instrument.externalSettlementCurrency`, `docs/decisions/instrument-currencies-home.md`); у всех ног сделки она одна. Пишет `CreateOrderExecutor` при входном действии. |
| `plannedRiskEquityBase` | `BigDecimal` | **База процента риска на момент сайзинга** — `BalanceContainer.externalAvailableEquity`, по которому `SizeCalculator` считал бюджет первой ноги входа сделки. **Write-once**: база фиксируется первым сайзингом и под сделкой не двигается. Валюта — `plannedRiskCurrency` (отдельной колонки нет). Два потребителя: знаменатель фактического процента риска в отчётности и **база потолка риска на сделку** (§«Потолок риска на сделку»). Пусто = сделка вокруг позиции, созданной вне приложения (сайзинга не было). |
| `resultProfit` | `BigDecimal` | Итоговый PnL (см. ниже). |
| `resultProfitCurrency` | `String` | Валюта результата (для `ETH-USDT-SWAP` обычно `USDT`). Источник — **расчётная валюта инструмента**; валюта от биржи — проверяемый признак, не источник (§«Валюта результата: один авторитет»). |
| `billsWindowBegin` | `OffsetDateTime` | **Нижняя граница окна линковки bills** — собственное поле сделки; пишет **единственный** писатель `SubmitOrderExecutor` (`Order.externalCreatedAt` первой отправленной ноги; §«Окно линковки bills»). |
| `billsWindowEnd` | `OffsetDateTime` | **Верхняя граница окна линковки bills** — заполняет наблюдатель факта закрытия (вторая нога `REFRESH_POSITION_COMMAND`), **монотонно вперёд**: каждый следующий закрывшийся эпизод двигает границу к `uTime` своей записи закрытия. Пусто = факт закрытия не добыт **ни у одного** эпизода. Порог доказанного покрытия окна (§«Верхних границ две»). |
| `billsFetchedThrough` | `OffsetDateTime` | **До какого момента движения добыты** — верхняя граница последнего успешно вычитанного диапазона; пишет `RefreshBillsExecutor` своей транзакцией, **монотонно вперёд**. Единственный durable-факт «добыча движений выполнялась»: пусто = не добывали (а не «добыли, движений нет»). Операнд завершения bills-звена и обязанности сверки (§«Добыча движений — durable-факт»). |
| `closeOutcome` | `CloseOutcome` | **Торговый исход закрытия** — признак отбора для отчёта. Пишет финализация (штатная и аварийная) из `Position.externalCloseType`; техническая тропа FSM на значение не влияет. Пусто = признак **неприменим** (тропа закрытия без входа); `UNDETERMINED` = операнд не добыт (§«Признаки отбора для отчёта»). |
| `reconciliationStatus` | `ReconciliationStatus` | **Статус сверки разбивки** — признак отбора для отчёта. Свойство числа, а не членства: сделка остаётся в популяции при любом значении. Пусто = признак неприменим (тропа закрытия без входа). |
| `breakdownIncomplete` | `BreakdownCompleteness` | **Полнота разбивки** — сделка длиннее окна доступности движений конвейера добычи. Отделяет «сверка звенит по дефекту» от «звенит по построению»; `NOT_ASSESSED` = сравнение не выполнялось. Пусто = признак неприменим (тропа закрытия без входа). |
| `riskBenchmarkAvailability` | `RiskBenchmarkAvailability` | **Почему знаменатель `R` пуст или непуст** — признак отбора, разводит две природы пустоты `plannedRiskAmount`. Пишут финализация (штатная и аварийная) и — для `NOT_APPLICABLE` на тропах закрытия без входа — `MarkDealClosedExecutor`; пусто до терминала. |
| `orders` | `List<Order>` | Ordinary orders сделки (attached protection — внутри `Order`). |
| `algoOrders` | `List<AlgoOrder>` | Standalone algo-orders сделки. |
| `positions` | `List<Position>` | **Эпизоды позиции сделки** (одна биржевая позиция = один `posId` = одна строка). Живой эпизод — ≤1; закрытые остаются (`docs/decisions/multi-episode-deal.md`). Доменный предикат `livePosition()` отдаёт живой либо пусто. |

`Deal.direction` имеет тип `StrategyTradeDirection` (енум `Strategy`,
`docs/models/domain/aggregate/Strategy.md`).

## Енумы

- **`Status`**: `PRECHECK`, `ENTRY_SUBMITTED`, `ENTRY_FINALIZED`,
  `PROTECTION_SWITCHED`, `MANAGING`, `EXIT_PENDING`, `CLOSED`,
  `ERROR`, `EMERGENCY_CLOSED`. Описывает бизнес-этап сделки, **не**
  статус `Order`/`AlgoOrder`/`Position`/command execution/exchange
  ACK. Значения, группы, переходы — в `docs/lifecycles/Deal.md`.
- **`EntryReason`**: `STRATEGY` (создана `EntryScannerJob` по
  условиям), `MANUAL`, `RECOVERY` (восстановление существующего
  runtime risk), `UNKNOWN` (fallback, не для normal flow).
- **`EntryStepType`**: `ENTRY`, `GRID_ENTRY` (или null, если создана
  не через strategy entry-step). Комбинации с `entryReason` — в
  lifecycle/справке. Подробный entry context — в аудите, не в `Deal`.
- **`ShutdownReason`**: `STRATEGY_DELETED`, `MARKET_DATA_EXPIRED`
  (только если policy решила завершать сделку controlled-exit, не
  при любом stale), `MANUAL_STOP`, `RISK_POLICY`, `EXCHANGE_HOLD`
  (производится **каскадом ступени 2** биржевой лестницы —
  `Exchange.TRADE_BLOCKED`/`DISABLED`; ступень 1 `Exchange.HOLD` —
  мягкий холд, сделки не гасит и их сопровождение не ограничивает —
  `docs/rules/exchange-hold.md`), `UNKNOWN`.
  Заполняется только при реальном запуске graceful shutdown (см.
  lifecycle).
- **`CloseReason`**: `ENTRY_CONDITION_EXPIRED` (candidate закрыт в
  PRECHECK до live risk), `STRATEGY_EXIT`, `TAKE_PROFIT`,
  `STOP_LOSS` (включая fixed и trailing SL; конкретный механизм — в
  `Order`/`AlgoOrder`/`DealActionState`/audit), `TIME_STOP`,
  `RISK_CONTROL` (штатное risk-control завершение, включая risk-block
  в PRECHECK), `MANUAL_CLOSE`, `EMERGENCY_CLOSE` (только для
  `EMERGENCY_CLOSED`), `UNKNOWN`. Не используются:
  `ENTRY_RISK_BLOCKED`, `TRAILING_STOP`. Описывает бизнес-причину, не
  технический механизм закрытия позиции.
- **`CloseOutcome`** — **торговый** исход закрытия, ось отбора для
  отчёта:
  - `NORMAL_EXIT` — позицию закрыли мы (стоп, тейк, стратегийный выход,
    ручное закрытие) либо биржевое событие вне ликвидационного контура
    (`externalCloseType` `1`–`2`);
  - `LIQUIDATION` — позицию принудительно закрыла биржа по марже
    (`3`–`4`);
  - `FORCED_REDUCTION` — принудительное сокращение (ADL) (`5`–`6`);
  - `UNDETERMINED` — исход **не определён: операнд не добыт** (запись
    с `type` вне `1..6` не проходит границу интеграции и до признака
    не доезжает). Значение, а не пустота: сделка остаётся в популяции
    и счётна отдельной корзиной. Пустой `closeOutcome` означает
    другое — признак **неприменим** (тропа закрытия без входа).

  Отличается от `CloseReason` намеренно: `closeReason` —
  **бизнес-причина** завершения сделки, `closeOutcome` — **рыночный
  факт** того, кто и почему закрыл позицию. На `closeReason`
  фильтровать нечем: `ENTRY_CONDITION_EXPIRED` переиспользована двумя
  тропами, а ликвидация в нём не выражается вовсе.
- **`ReconciliationStatus`** — исход контроля целостности разбивки
  (дом сверки — `docs/rules/pnl-reconciliation.md`):
  - `NOT_RUN` — сверка **не была обязана** и не выполнялась: не
    выполнен хотя бы один конъюнкт обязанности — запись закрытия не
    добыта, окно не закрыто **либо движения не добывались**
    (`Deal.billsFetchedThrough` пуст). Последний случай — штатная
    аварийная тропа: bills-звено на ней не эмитится вовсе, поэтому
    «запись закрытия добыта» обязанности **не создаёт** (A2
    `DOCS_CHECK_19`; прежняя редакция «на ветви с добытой записью
    сверка гоняется» опиралась на чужой операнд и снята);
  - `MATCHED` — **общее расхождение по сделке** (`Δ = Σ|Δᵢ|` по
    четырём парам) в пределах epsilon — допуск один на сделку,
    пер-парных якорей нет;
  - `MISMATCHED` — общее расхождение сверх epsilon; **какие** пары
    разошлись — состав отчёта, не предиката.

  **Третьего значения нет — решение держателя.** Различение «были
  обязаны и не посчитали» несёт **терминальный статус**
  (`CLOSED` ↔ `EMERGENCY_CLOSED`), а не значение признака: случая
  «были обязаны, операнда допуска не нашлось» не существует —
  нерезолвимый операнд до финализатора не доезжает, его ловит
  детектирующий контур отказом операции (§«Обнаружение
  рассогласования пары носителей»). `NOT_RUN` внутри
  `EMERGENCY_CLOSED` несёт **один** смысл: сверка не была обязана.
- **`RiskBenchmarkAvailability`** — **почему знаменатель `R` пуст или
  непуст**, поле `riskBenchmarkAvailability`:
  - `AVAILABLE` — `plannedRiskAmount` непуст: знаменатель определён;
  - `NOT_APPLICABLE` — входа **не было по построению**: три тропы закрытия
    без входа (`PRECHECK`-истечение, риск-блок, отмена неисполненного
    входа без движения средств — `docs/rules/deal-without-operations.md`).
    Нормальная популяция, аномалией не является;
  - `MISSING` — **операции были, знаменателя нет**: ни одна нога входа
    планового риска не несёт при состоявшихся операциях (позиция создана
    вне приложения). Аномалия; сопровождается `AnomalyReport`
    `PLANNED_RISK_MISSING` (§«Операции были, а `R` пуст»).

  **Писателей три, и третий — исполнитель закрытия** (решение
  держателя): `AVAILABLE` / `MISSING` пишут два финализатора,
  **`NOT_APPLICABLE` — `MarkDealClosedExecutor` той же транзакцией**
  на тропах закрытия без входа (финализатор выхода там не работает).
  Пусто — до терминала. Признак этим выведен из-под клейма «признаки
  на тропах закрытия без входа не пишутся»: иначе популяция «входа не
  было по построению» не адресуется значением одного поля, ради чего
  признак и заводился.
- **`BreakdownCompleteness`** — полнота разбивки, поле
  `breakdownIncomplete`:
  - `COMPLETE` — **возраст нижней границы окна на момент добычи** не
    превышает глубины доступности движений;
  - `INCOMPLETE_BY_WINDOW` — превышает: часть строк недобываема
    выбранным конвейером добычи;
  - `NOT_ASSESSED` — сравнение **не выполнялось**: нижняя граница окна
    не добыта либо добыча движений не выполнялась. Не то же, что
    `COMPLETE`: «не проверяли» и «проверили, всё в порядке» разведены
    (`docs/rules/absent-value-semantics.md`).

`entryReason`/`entryStepType` не управляют FSM. `shutdownReason`
(почему перевели в graceful shutdown — не значит, что закрылась) и
`closeReason` (итоговая причина завершения) — разные поля.

## Итоговый PnL (resultProfit)

Первоисточник правила — здесь (`Deal` владеет полем,
`.claude/decisions/rule-source-of-truth.md`); источник данных числа и
разбивки — `docs/decisions/result-profit-source.md`:

- **Число** `resultProfit` = **Σ net realized P&L по эпизодам сделки**,
  каждый берётся **готовым** из positions-history
  (`realizedPnl = pnl + fee + fundingFee + liqPenalty`, посчитан биржей;
  слагаемое живёт полем `Position.externalRealizedProfit` своей строки),
  **плюс cross-ccy-слагаемое** Σ(`amount` ×
  `appliedRate`) по строкам `DealCashFlow`, у которых **`rateStatus =
  APPLIED` и тип вне списка исключений биржи и категория — экономическая
  (не `OTHER`)** — предикат области **конъюнктивный**, полный, не
  сокращение.
  - **Почему сумма, а не число последнего эпизода** (решение держателя,
    `docs/decisions/multi-episode-deal.md`): сделка многоэпизодна —
    внутри неё позиция может схлопнуться и открыться заново. Числитель
    обязан покрывать те же ноги, что и знаменатель `R`, иначе
    R-мультипликаторы систематически сжаты [Tharp гл.6 с.144-146; Vince
    гл.1 с.17].
  - **Сумма — производная проекция, пересчитываемая целиком** по
    строкам эпизодов; инкрементального накопления нет, поэтому
    повторное наблюдение не задваивает число (командная идемпотентность
    `REFRESH_*` сохраняется).
  - **Пустое слагаемое не подставляется нулём.** Эпизод, чьё положение
    закрытия не добыто, делает сумму **недоступной**, а не заниженной:
    поведение — по терминальному контракту (чистая тропа ждёт и ретраит,
    аварийная даёт `null` «неисчислимо»). Биржевой net считается в settle-ccy и издержку вне неё не
  содержит — без слагаемого число завышалось бы молча
  (`docs/decisions/pnl-finalization-mechanics.md` реш.5,
  `docs/models/mapping/DealCashFlow.md` §«Число — в settle-ccy»). **Не**
  через fills/`TradeFill` и **не** через `BalanceContainer` diff;
  `REFRESH_BALANCE_COMMAND` после выхода нужен для актуального account
  snapshot, не для PnL сделки.
- **Категорийная разбивка** (торговая комиссия / funding / rebate /
  ликвидационный штраф) — из bills (`DealCashFlow`); сумма bills-flows
  сверяется с net из positions-history — состав сверки, epsilon и
  реакция на расхождение — дом `docs/rules/pnl-reconciliation.md`.
  В `Deal` разбивка не хранится (см. ниже).
- **Формула одна на обе тропы.** `EMERGENCY_CLOSED` best-effort **по
  доступности** числа, а не по его составу: когда net доступен,
  аварийный терминал применяет то же cross-ccy-слагаемое
  (`docs/components/MarkDealEmergencyClosedExecutor.md` §«Состав
  числа») — иначе направленное смещение вверх в и так смещённой
  корзине.
- Для **чистого** terminal `CLOSED` `resultProfit` и
  `resultProfitCurrency` обязательны; для аварийного `EMERGENCY_CLOSED`
  число — **best-effort**: net доступен — та же формула, иначе
  `resultProfit = null` c маркером «неисчислимо» (**не ноль**, отличимо
  от нуля; `docs/lifecycles/Deal.md` §«Терминальный контракт
  финализации»).
- `resultProfit = 0` допустим только как **результат расчёта** (net вышел
  нулевым), **не** как молчаливый fallback при ошибке. Если временно
  нельзя посчитать — добыча и финализация ретраятся бюджетом своих
  **системных действий** (`REFRESH_DEAL_CONTEXT_ACTION` /
  `FINALIZE_DEAL_EXIT_ACTION`,
  `docs/models/domain/other/DealActionState.md`); при исчерпании сделка
  уходит ошибочной тропой к терминалу — всегда доходит до терминала, не
  зависает живым риском.
- **Расчёт и запись.** Число вычисляет и **пишет прямо на `Deal`**
  `FinalizeDealExitExecutor` (Σ **`Position.externalRealizedProfit`** по
  эпизодам — положений закрытия, приземлённых второй ногой
  `REFRESH_POSITION_COMMAND`, — плюс разбивка из `DealCashFlow` +
  сверка; в одной транзакции с продвижением своего исполнения —
  durable-носитель числа = само поле `Deal`, рестарт-safe).
  `MarkDealClosedExecutor` **ассертит** непустоту и ставит терминал
  `CLOSED` (число не пишет). Механика —
  `docs/decisions/pnl-finalization-mechanics.md` реш.2.

## Валюта результата: один авторитет

**Авторитет — расчётная валюта инструмента** (решение пользователя;
дом — поля самого `Instrument` (`externalSettlementCurrency`),
`docs/decisions/instrument-currencies-home.md`).

- **Один источник на оба поля.** `resultProfitCurrency` и
  `plannedRiskCurrency` берутся из **одного** места — иначе требование
  «валюты обязаны совпадать» ничем не обеспечено. Авторитетом назначен
  носитель, который у обоих полей уже общий, известен **до входа** и от
  исхода сделки не зависит.
- **Валюта от биржи — проверяемый признак, не источник.**
  `Position.externalResultCurrency` сверяется с расчётной валютой
  инструмента; не совпало → `AnomalyReport` `RESULT_CURRENCY_MISMATCH`
  (`severity = NON_CRITICAL`, ставит финализатор —
  `docs/components/FinalizeDealExitExecutor.md`). **Расчёт не
  блокируется:** число считается и записывается, терминал проходит.
- **Почему пометка, а не controlled error на границе.** Валидация
  `PositionCloseResult` требует лишь «`ccy` заполнен и парсится»;
  усиление до отказа оставило бы сделку без терминала. Проверка живёт
  **после** приземления факта, где отказывать уже не нужно.

### Ветка «операнд пуст»

Расчётную валюту — поле самой сущности `Instrument` — пишет **тропа
заведения инструмента** (`docs/decisions/instrument-currencies-home.md`
§«Писатель — тропа заведения»). Ветка достижима, когда валюта **не
резолвилась при заведении** (ответ источника неполон), и на популяции
«позиция создана вне приложения» (риск-преконтроль там не работал).
Принцип — **реджект там, где риск ещё не взят; пометка там, где
отказывать нельзя** (образец — `FEE_RATE_UNAVAILABLE`,
`docs/components/models/RiskCheckResult.md`):

| Точка | Операнд пуст ⇒ |
|---|---|
| Вход (`RiskValidator` — точка реджекта; писатель значения — `CreateOrderExecutor`, той же транзакцией) | **реджект** `SETTLE_CURRENCY_UNAVAILABLE` — сделка не открывается. Подставить `USDT` «по контуру» нельзя: подставленное число, выглядящее фактом |
| Запись движения (`RefreshBillsExecutor`, cross-ccy guard) | строка **персистится и линкуется**, guard не выполняется, `appliedRate` не считается; `AnomalyReport` `SETTLE_CURRENCY_UNAVAILABLE`. Строка становится **должником догона** — валюта резолвится ближайшим тиком синка, после чего guard исполним (B3 `DOCS_CHECK_18`) |
| Финализация (`resultProfitCurrency`) | берётся `Position.externalResultCurrency` как единственный доступный факт + `AnomalyReport` `SETTLE_CURRENCY_UNAVAILABLE`. **Явная деградация с пометкой**, не второй молчаливый источник |

Реджект на входе делает две нижние ветки практически недостижимыми для
сделок, открытых **нашим** входом: они остаются для сделок вокруг
позиции, созданной вне приложения.

## Плановый риск (`R`)

**`plannedRiskAmount` — знаменатель R-мультипликатора.** Шаг 7 персистит
числитель (`resultProfit`) и обязан персистить знаменатель: без него
отношение «сколько R заработала сделка» не считается [Tharp гл.6
с.144-146].

- **Что это за число — сумма по ногам входа** (решение пользователя).
  Слагаемое хранится **на ноге** (`Order.plannedRiskAmount`) и есть
  убыток на **её** стопе, посчитанный при постановке **этой** ноги, —
  та же величина, которую считает `RiskValidator`
  (`|entry − stop| × contracts × ctVal + commissions`,
  `docs/decisions/per-trade-risk-policy.md` §«Закрытая форма
  сайзинга»). Прогнозная комиссия **входит** — иначе знаменатель
  отличался бы от величины, под которую подбирался размер. На `Deal`
  живёт **Σ по живым и исполнившимся ногам входа** — предикат отбора
  записан ниже.
- **Почему сумма, а не снимок первой ноги.** Многоногий вход (сетка,
  добор) — рабочий режим фазы 1; снимок первой ноги занижал бы
  знаменатель кратно числу ног, растягивая R-мультипликаторы и ломая
  единство распределения; побочно портился бы `BiggestLoss` [Vince
  гл.1 с.17]. Тождество омиссионного члена epsilon верно **поногово**
  (`docs/models/domain/core/Order.md` §«Плановый риск и его
  операнды»).
- **Кто и когда пишет.** Исполнитель `CREATE_ORDER_COMMAND` входного
  действия (`docs/components/CreateOrderExecutor.md`) — в одной
  транзакции с созданием сущности входа: пишет слагаемое на ногу **и**
  пересчитывает сумму на `Deal`. Риск-преконтроль и создание идут
  **одним проходом** (`docs/rules/risk-validator-scope.md`), поэтому
  durable-слота между проходами не нужно. Сумма — **производная, но
  персистируемая**: фильтр и отчёт обязаны быть выразимы запросом без
  join'а по `orders` (§«Признаки отбора для отчёта»).
- **Чем доезжает — полями `CreateOrderCommandPayload`.** Числа входного
  действия едут payload'ом — тем же путём, что цена и размер: **шесть**
  операндов тождества риска (`plannedRiskAmount`, `plannedRiskCurrency`,
  `plannedEntryPrice`, `plannedSizeContracts`, `plannedContractValue`,
  `plannedStopPrice`) **плюс седьмое** — измеритель
  `liquidationDistanceRatio` — **плюс восьмое**, база процента
  `plannedRiskEquityBase` (§«База процента риска»). Счёт держит место
  истины payload'а
  (`docs/components/CreateOrderExecutor.md` §`CreateOrderCommandPayload`);
  здесь — указатель, а не второй перечень (устаревший счёт «четыре» снят
  B4 `DOCS_CHECK_18`).
- **Write-once живёт на ноге; сумма на сделке — не write-once.**
  Слагаемое `Order.plannedRiskAmount` пишется при постановке своей
  ноги и **не переписывается**: трейлинг двигает стоп, но риск ноги —
  риск **на её входе**, бенчмарк измерения [Tharp гл.9 с.234-236].
  Поле `Deal` при этом двигается, потому что состав слагаемых растёт:
  новая нога добавляет новый принятый на входе риск. На уровне сделки
  `R` = «суммарный риск, под который сайзились её входы». Отдельного
  числа «риск первой ноги» не заводится — у него нет потребителя.

### База процента риска (`plannedRiskEquityBase`)

**Знаменатель, по которому считался бюджет сайзинга, персистируется**
(C4 `DOCS_CHECK_20`, решение держателя). Значение —
`BalanceContainer.externalAvailableEquity` на момент сайзинга **первой**
ноги входа сделки; пишет `CreateOrderExecutor` той же транзакцией,
что шесть чисел, **write-once** (guard §Персистентность).

- **Почему поле, а не реконструкция.** Из `plannedRiskAmount` база не
  восстановима: размер округляется к шагу лота, и фактический риск ноги
  меньше бюджета на неизвестную величину; `BalanceContainer` —
  replace-семантика (`docs/models/domain/core/BalanceContainer.md`),
  прежнего значения не хранит. Без поля «сколько процентов депозита
  реально стояло под ударом» неисчислимо ни на одной сделке.
- **Почему write-once на сделке, а не на каждой ноге.** У числа два
  потребителя, и обоим нужна **одна** база на сделку: знаменатель
  фактического процента риска в отчётности и база потолка риска на
  сделку (§ниже). Плавающая база двигала бы потолок под сделкой —
  контроль, меняющий собственный порог по ходу, эквивалентен
  погашенному.
- **Пустое значение законно и означает «сайзинга не было»**: сделка
  вокруг позиции, созданной вне приложения. Та же популяция, что у
  пустого `plannedRiskAmount`
  (`Deal.riskBenchmarkAvailability = MISSING` + журнальный
  `PLANNED_RISK_MISSING`); второго признака не заводится.
- **Окно ввода — миграция шага 7.** Позже колонка потребовала бы
  миграции на непустой таблице, а наблюдения за прошедшие сделки были
  бы потеряны безвозвратно.

### Потолок риска на сделку (`RISK-Q3` закрыт)

**Лимит риска двухуровневый** (C6 `DOCS_CHECK_20`, решение держателя;
дом формулировки и разбор — `docs/decisions/per-trade-risk-policy.md`
§«Лимит риска двухуровневый»). Здесь — только роль поля:
**носитель накопленного риска сделки — сам `plannedRiskAmount`**, второго
числа не заводится. Преконтроль потолка сравнивает `plannedRiskAmount +
риск нового акта` с `riskPerDealPercent × plannedRiskEquityBase`.

**Клейм «риск на сделку не превышает лимит» был ложным** до этого
закрытия: лимит применялся поактно, а Σ по ногам его превышала
без единого контроля. Клейм восстановлен в истинности не переписыванием
текста, а вводом второго уровня контроля.

### Предикат отбора слагаемых

При REPLACE входной ноги (штатный режим,
`docs/decisions/replace-not-amend.md`) в таблице остаются **две** строки
с непустым `planned_risk_amount` — отменённая и замещающая, — поэтому
фразы «ноги входа» для отбора недостаточно. **Предикат — бизнес-тип,
состояние ноги и страховочный конъюнкт:**

```text
слагаемые Deal.plannedRiskAmount =
  строки orders сделки, у которых
    type ∈ {ENTRY, ENTRY_ATTACHED_STOP_LOSS}       — бизнес-тип
    И status ∈ isLive() ∪ {COMPLETED}              — живая либо исполнившаяся
    И planned_risk_amount НЕПУСТ                   — страховка (цена ниже)
```

**Отбирает бизнес-тип** (решение держателя). Из трёх согласованных форм
(`docs/models/domain/core/Order.md` §«Предикат "нога входа"») предикатом
назначен **`Type`**: он называет роль ноги прямо и живёт в той же
строке, что и слагаемое. `positionReducingOnly` остаётся **намерением**,
уходящим на биржу, предикатом отбора не служит.

**Снятая нога не считается вовсе** (решение держателя). Второй конъюнкт
стоит на **состоянии** ноги, а не на причине её снятия: входят живые
(`CREATED` / `PENDING` / `ACTIVE` / `PARTIALLY_COMPLETED`,
`Order.isLive()`) и исполнившиеся (`COMPLETED`); всякая снятая
(`CANCELED`) выпадает независимо от `closeReason`. Замещённая нога
выходит **тем же конъюнктом** (REPLACE снимает ногу с терминальным
`CANCELED`) — отдельного вычитания и обхода цепочки
`replacesInternalId` не требуется.

- **Почему отозванный риск не в знаменателе.** Снятая заявка не стояла
  — за неё сделка не рисковала; оставить её — раздуть знаменатель
  кратно числу перевыставлений.
- **Частично исполнившаяся и затем снятая нога** из **заявленного**
  выходит тоже; взятый ею риск учитывает второе число (§«Взятый риск»)
  исполненной долей — **и для этого у второго числа свой предикат**, без
  конъюнкта по статусу (§«Предикат взятого риска»). Прежняя редакция
  обещала это поведение, отбирая слагаемые «тем же предикатом», который
  снятую ногу как раз исключал (T1 `DOCS_CHECK_18`).
- **Нога в `ERROR` в сумму не входит** — не живая и не исполнившаяся;
  её исполненная доля остаётся во взятом риске. Сделка с такой ногой
  идёт safety-каскадом и в отчёт попадает помеченной.
- **Отбор идёт по наблюдённому состоянию, не по намерению.** Пока
  отмена не подтверждена refresh'ем
  (`docs/rules/ack-not-runtime-truth.md`), нога остаётся в сумме;
  сумма пересчитывается **целиком** тем же исполнителем, который
  проставит терминальный статус
  (`docs/components/CancelOrderExecutor.md`).

**Третий конъюнкт — страховка.** Непустота `planned_risk_amount` —
производная первых двух форм (у reduce-only-ноги преконтроль не
гоняется, колонка пуста по построению); пока инвариант
`Type = REDUCE_ONLY ⇔ positionReducingOnly = true` держится, конъюнкт
исход не меняет. Он стоит на случай нарушения инварианта — чтобы в
сумму не попало слагаемое-пустота. Цена: предикат гасит рассогласование
пары **молча, в обе стороны**, поэтому обнаружение живёт отдельным
механизмом (§ниже), а реакция на обнаруженное — **отказ операции**, не
пометка.

Побочно той же конструкцией снят дефект селекции защиты: снятая нога в
сумму не входит — её `stop_i` не запрашивается, и чисто закрывшаяся
сделка с attached-SL отменённой ноги в `ERROR` не уходит.

### Обнаружение рассогласования пары носителей (`Type` ↔ `positionReducingOnly`)

Предикат отбора нарушение инварианта **гасит** (§выше), поэтому носитель
обнаружения отдельный, и он не один:

| Контур | Где стоит | Что делает |
|---|---|---|
| **Превентивный** | валидация состава шага стратегии (дельта `CODE`, `.claude/work/backlog.md` §Шаг 7) | не выпускает действие с `orderType = REDUCE_ONLY` при `positionReducingOnly = false` либо наоборот. Закрывает штатный путь появления пары |
| **Детектирующий** | те же три исполнителя, что пересчитывают суммы (`CreateOrderExecutor`, `RefreshOrderExecutor`, `CancelOrderExecutor`) | при пересчёте сверяет пару на ногах сделки **до** применения предиката отбора: расхождение становится фактом, а не молчаливым исключением ноги |

Одного превентивного мало: он закрывает путь появления пары
**приложением** и ничего не говорит о строках, попавших в таблицу иначе
(правка данных, миграция, нога до ввода валидации).

**Реакция детектирующего контура — отказ операции** (решение
держателя). Обнаружив рассогласование, исполнитель пересчёта бросает
исключение non-retryable-класса (`VALIDATION_ERROR`,
`docs/components/ServiceCommandExecutor.md`), строка исполнения уходит
в `FAILED`, сделка — **ошибочной тропой** (`ERROR` → `ErrorHandler`),
а перехваченное оркестратором исчерпание бюджета даёт **полный холд
инструмента** (`docs/rules/instrument-hold.md` §«Форма реакции на
исчерпание бюджета попыток»). Журнального кода не заводится:
реактивную запись производит последовательность холда
(`RETRY_BUDGET_EXHAUSTED`). Цена принята держателем: реакция
несоразмерна ущербу (торговля по инструменту встаёт до ручного
разбора), но искажённый знаменатель не должен накапливаться, пока
причину не разобрали.

**Реакция одна на оба направления** рассогласования: «тип входной,
числа нет» и «тип reduce-only, число есть» — один и тот же отказ;
какой стороной нарушен инвариант — вопрос разбора, не реакции.

### Взятый риск — второе число (`incurredRiskAmount`)

Решение пользователя: **два разных поля** — заявленный (заполняется при
создании ноги) и фактически взятый (обновляется по исполнению ног).

| Поле | Что измеряет | Момент | Предикат / формула |
|---|---|---|---|
| `plannedRiskAmount` | **заявленный** риск — бенчмарк, «риск, под который сайзились» | вход | Σ `Order.plannedRiskAmount` по **живым и исполнившимся** ногам входа (§«Предикат отбора слагаемых», предикат **заявленного**) |
| **`incurredRiskAmount`** | **взятый** риск — сколько из заявленного встало под удар | вход | Σ по ногам входа, отобранным предикатом **взятого** (§ниже): `plannedRiskAmount_i × (accumulatedFillSize_i / plannedSizeContracts_i)`; слагаемое ноги с `plannedSizeContracts_i = 0` — **ноль**, не деление |
| **`currentRiskAmount`** | **неотработанная доля** взятого на входе риска | сейчас | `incurredRiskAmount × (livePosition().externalSize / Σ accumulatedFillSize_i по тому же предикату взятого)`; живого эпизода нет ⇒ числитель **ноль**; слагаемых нет ⇒ поле **пусто**; слагаемые есть, а `Σ accumulatedFillSize_i = 0` ⇒ поле **ноль** (риск заведомо ещё не взят — значение по проверенному факту, `docs/rules/absent-value-semantics.md`) |
| **`protectionRelievedRiskAmount`** | **риск, снятый защитой** — насколько актуальный стоп уменьшил взятый риск | сейчас | `incurredRiskAmount − riskAtCurrentStop` (закрытая форма вычитаемого — §«Форма вычитаемого»); действующей защиты нет ⇒ поле **пусто** |

#### Предикат взятого риска — свой, без конъюнкта по статусу

**Второе и третье числа отбирают ноги своим предикатом** (T1
`DOCS_CHECK_18`):

```text
слагаемые incurredRiskAmount / знаменателя currentRiskAmount =
  строки orders сделки, у которых
    type ∈ {ENTRY, ENTRY_ATTACHED_STOP_LOSS}   — бизнес-тип
    И accumulated_fill_size > 0                — риск фактически взят
    И planned_risk_amount НЕПУСТ               — страховка (та же, что у заявленного)
```

**Почему не «тот же предикат, что у заявленного».** Конъюнкт
`status ∈ isLive() ∪ {COMPLETED}` исключает **`CANCELED`**, то есть ровно
ту ногу, ради которой второе число и заведено: частично исполнившуюся и
затем снятую. Её порождает самая частая тропа — перевыставление входа
(`docs/decisions/replace-not-amend.md` §Решение п.3: cancel-old →
place-new) и teardown частично налитой ноги. Счётные последствия
прежнего предиката, обе — направленные:

- **разрыв «заявлено ↔ взято» не измеряется** там, где он и возникает:
  филлы снятой ноги выпадают из обоих чисел;
- **третье число ломается арифметически:** `livePosition().externalSize`
  содержит филлы снятой ноги, а знаменатель `Σ accumulatedFillSize_i` —
  нет ⇒ отношение > 1, и «неотработанная доля» превышает взятый риск.

**Что это не меняет.** Знаменатель `R` (`plannedRiskAmount`) свой
предикат сохраняет: снятая заявка не стояла — за неё сделка не
рисковала, и раздувать бенчмарк перевыставлениями нельзя (§«Предикат
отбора слагаемых»). Два предиката вместо одного — названная цена;
довод «разведение по двум полям делает предикат простым» ослаблен, но
альтернатива (один предикат) сохраняет неверный торговый исход.
Конъюнкт `accumulated_fill_size > 0` делает предикат взятого
самонесущим: нога без филлов слагаемого не даёт независимо от статуса.

#### Форма вычитаемого `protectionRelievedRiskAmount`

**`riskAtCurrentStop` — та же закрытая форма, что у планового риска, с
подстановкой действующего стопа** (T2 `DOCS_CHECK_18`):

```text
riskAtCurrentStop = Σ по ногам предиката взятого:
    ( signedStopDistance × accumulatedFillSize_i × plannedContractValue_i
      + комиссионный член_i )

где signedStopDistance =
    LONG  : plannedEntryPrice_i − stopCurrent_i
    SHORT : stopCurrent_i − plannedEntryPrice_i
```

— тождественно `plannedRiskAmount_i` (`docs/decisions/
per-trade-risk-policy.md` §«Закрытая форма сайзинга») с двумя заменами:
`stop_i → stopCurrent_i` и `plannedSizeContracts_i → accumulatedFillSize_i`.

**Дистанция — знаковая по направлению сделки, не модуль** (C2
`DOCS_CHECK_19`). Модуль в закрытой форме сайзинга корректен, потому что
**на входе** стоп всегда неблагоприятен; за безубытком это перестаёт
быть верным. Прежняя редакция несла `|plannedEntryPrice_i − stopCurrent_i|`
и рядом обещала `riskAtCurrentStop < 0` при стопе за безубытком — с
модулем это недостижимо, а поведение выходило обратным заявленному: при
`entry = 100` стоп `110` (заперт +1R) давал ту же величину, что стоп `90`
(исходный риск), а дальше монотонность инвертировалась, и **трейлинг в
прибыли читался как ослабление защиты** — то есть поле алиасило два
противоположных состояния. Операнд направления уже есть —
`Deal.direction`.

Три операнда, которых форма прежде не называла, названы:

- **комиссионный член входит** — как и в уменьшаемом. Иначе при
  **недвинутом** стопе поле выдавало бы ≈ двойную комиссию > 0, то есть
  «защита сняла риск», которого она не снимала.

  **Форма члена задана явно** (B9 `DOCS_CHECK_20`) — та же, что в
  закрытой форме сайзинга, с теми же двумя заменами:

  ```text
  комиссионный член_i = rate_i × (plannedEntryPrice_i + stopCurrent_i)
                        × accumulatedFillSize_i × plannedContractValue_i
  ```

  - **`stopCurrent_i`, а не `plannedStopPrice_i`, стои́т и в комиссионном
    члене.** Прочтений было два — пересчитывать член по действующему
    стопу или заморозить его на плановом, — и клейм «при недвинутом
    стопе поле равно нулю **точно**» верен только при первом: при
    втором член перестаёт быть той же функцией, что в уменьшаемом, и
    разность даёт остаток, пропорциональный сдвигу. Прочтение выбрано
    первое, и клейм тем самым восстановлен в точности: при
    `stopCurrent_i = plannedStopPrice_i` выражение тождественно
    `plannedRiskAmount_i × (accumulatedFillSize_i /
    plannedSizeContracts_i)`, то есть слагаемому `incurredRiskAmount`,
    и разность равна нулю **алгебраически**, а не приближённо.
  - **`rate_i` нового поля не требует** — она выводится из шести
    persisted-чисел обращением закрытой формы сайзинга
    (`docs/decisions/per-trade-risk-policy.md` §«Закрытая форма
    сайзинга»):

    ```text
    rate_i = ( plannedRiskAmount_i
               / (plannedContractValue_i × plannedSizeContracts_i)
               − |plannedEntryPrice_i − plannedStopPrice_i| )
             / (plannedEntryPrice_i + plannedStopPrice_i)
    ```

    Все операнды write-once на ноге и охвачены инвариантом «шесть или
    ни одного», поэтому величина воспроизводима на любой момент жизни
    сделки и **не зависит** от текущей ставки в навесе — это ровно
    та ставка, под которую нога сайзилась. Знаменатель положителен
    (цены положительны), вырожденной ветки нет;
- **размер — поногово `accumulatedFillSize_i`**, не
  `livePosition().externalSize`: во втором случае эффект скейл-аута
  считался бы дважды (он уже учтён третьим числом);
- **знак не клэмпится.** Стоп за безубытком даёт `riskAtCurrentStop < 0`
  и `protectionRelievedRiskAmount > incurredRiskAmount`; ослабление
  защиты (risk-weakening `REPLACE`) даёт **уменьшение** поля вплоть до
  отрицательного. Клэмп в нуле убил бы ровно ту информацию, ради которой
  пара чисел заведена (§ниже, «Чего сумма не покрывает»).

**Операнд трейлинга — `condition.trailing.externalPrice`, не
`AlgoOrder.externalPrice`** (B2 `DOCS_CHECK_20`). Плоское
`AlgoOrder.externalPrice` — это `actualPx`, **фактическая цена
срабатывания**: у живой трейлинговой защиты оно пусто, а после
срабатывания несёт цену исполнения, а не уровень стопа
(`docs/models/domain/core/AlgoOrder.md` §«Поля фактического
срабатывания», верифицировано по `AlgoOrderMapper.java`). Прежняя
редакция называла плоское поле, поясняя его как `moveTriggerPx`, — то
есть реализация по месту истины давала бы **постоянно пустое**
`protection_relieved_risk_amount` на всём трейлинговом классе.

**Операнд поногово — `stopCurrent_i`, а не один на сделку** (C2
`DOCS_CHECK_20`). Действующая защита резолвится **для каждой ноги
отдельно**, по приоритету:

| Приоритет | Что защищает ногу `i` | Операнд `stopCurrent_i` |
|---|---|---|
| 1 | **своя attached-защита ноги жива** (`Order.attachedAlgoOrders[*].isActiveLike()`) | `attachedAlgoOrders[*].stopLossTriggerPrice` этой ноги |
| 2 | attached снята, действует **standalone** `AlgoOrder`, `conditionType ∈ {STOP_LOSS, OCO_FULL, PARTIAL_STOP_LOSS}` | `condition.trigger.stopLoss.value` новейшей живой standalone-защиты |
| 3 | attached снята, действует **standalone-трейлинг** (`conditionType ∈ {TRAILING_PERCENTS, TRAILING_VALUE}`) | **`AlgoOrder.condition.trailing.externalPrice`** (`moveTriggerPx`) новейшей живой standalone-защиты |
| 4 | живой защиты у сделки нет вовсе | `protectionRelievedRiskAmount` **пусто** целиком — ратифицированная ветка (§«Взятый риск», строка четвёртого числа), не подстановка нуля |

**Частичного случая «часть ног без защиты» не бывает по инварианту.**
Risk-creating вход не выпускается без встроенной защиты
(`docs/rules/risk-creating-entry-protection.md`), а standalone-защита
покрывает позицию целиком — то есть нога теряет свою attached только
тогда, когда её роль принимает standalone. Приоритет 1→3 разбирает
именно эту передачу, а строка 4 срабатывает **на всей сделке сразу**.

- **Почему поногово.** Один `stopCurrent` на все ноги неверен ровно в
  том окне, ради которого пара чисел заведена: доборная нога живёт со
  **своей** attached-защитой от филла до подтверждения пересчитанной
  основной (`docs/rules/risk-creating-entry-protection.md` §«Защита
  доборной ноги снимается после пересчёта основной»), и в это время у
  разных ног действуют **разные** уровни. Подстановка одного —
  новейшего, то есть более благоприятного — уровня всем ногам
  **завышает** `riskAtCurrentStop` защиты и тем самым **занижает живой
  риск**: направление ошибки — в благоприятную сторону, что запрещено
  `docs/rules/absent-value-semantics.md`.
- **Эпизоды разводятся тем же приоритетом.** Ноги закрывшегося эпизода
  своей attached-защиты уже не имеют, а standalone-защита сделки
  относится к живому эпизоду — то есть слагаемые старых ног попадают в
  строку 4 и слагаемого не дают. Отдельного механизма разведения по
  эпизодам не вводится.

- **У трейлинга `condition.trigger` не существует по инварианту**
  `trigger XOR trailing` (`docs/models/domain/core/AlgoOrder.md`
  §Condition-модель), поэтому прежняя редакция — «операнд =
  `condition.trigger.stopLoss.value` действующей защиты» — на всём классе
  трейлинговых конфигураций либо оставляла поле пустым (читалось как
  «действующей защиты нет» при живой защите), либо считала по
  attached-защите, которая к этому моменту штатно снята. Класс — тот
  самый, где стоп **непрерывно** снижает риск, то есть ровно тот, ради
  которого пара чисел заведена.
- **`Trailing.externalPrice` рыночной котировкой не является** — это
  состояние **нашей заявки** на бирже, добываемое тем же
  evidence-cycle, что и статусы; запрет «событийная проекция не должна
  стать функцией времени» (§выше) его не покрывает. Отвергнут
  `Trailing.activationPrice`: после активации он систематически
  **завышает** `riskAtCurrentStop`, то есть направленно занижает снятый
  защитой риск, и смещение растёт вместе с ходом в прибыль.
- **Переходное окно двойной защиты не держится один проход** (C2
  `DOCS_CHECK_20`; клейм снят). У окна два источника, и оба длиннее
  прохода: `REPLACE` идёт **place-new → подтверждённый факт →
  cancel-old** (`docs/decisions/replace-not-amend.md`), то есть обе
  заявки живы минимум до следующего наблюдения; attached-защита
  доборной ноги живёт **от её филла до подтверждения пересчитанной
  основной** — отдельным шагом стратегии
  (`PROTECTION_ADJUSTMENT`), то есть неопределённо долго
  (`docs/components/ManagingHandler.md` §«Допустимые StrategyStep»).
- **Поногового приоритета окну достаточно.** Пока attached ноги жива,
  её нога считается по ней (строка 1) — независимо от того, сколько
  standalone-заявок в этот момент живо; когда attached снята, нога
  переходит на новейшую живую standalone (строки 2-3). «Новейшая» здесь
  безопасна: `REPLACE` ставит новую **до** снятия старой, и пока новая
  не подтверждена, она в графе не живая.

- **Величину «риск под ударом» несёт пара чисел, а не третье поле в
  одиночку** (решение держателя): стоп двигается (безубыток, трейлинг,
  risk-weakening replace), а формула третьего числа уровня стопа не
  содержит — обещанную величину несёт `protectionRelievedRiskAmount`
  у **писателя защиты**. Ввод рыночной цены/стопа прямо в формулу
  отвергнут: событийная проекция стала бы функцией времени.
- **Вырожденные операнды разведены явно.** Страховочный конъюнкт
  непустоты распространяется на **все три** формулы: без него
  `null`-слагаемое отравляет сумму там, где инвариант «шесть или ни
  одного» не удержался. Две природы вырожденного знаменателя третьего
  числа: **слагаемых нет** (пусто) и **слагаемые есть, филлов нет**
  (ноль — риск ещё не взят). Вторая ветка достижима:
  `accumulated_fill_size` в `V6` nullable, а `Position` может быть
  `ACTIVE` при `externalSize = 0`
  (`docs/models/domain/core/Position.md` §Live risk).
- **Знаменатель R-мультипликатора остаётся заявленным** (решение
  пользователя; бенчмарк `docs/decisions/per-trade-risk-policy.md`
  §Асимметрия не переоткрывается). Второе поле — измеритель разрыва
  «заявлено ↔ взято», не замена бенчмарка.
- **`incurredRiskAmount` частичным выходом не уменьшается**: риск был
  понесён на входе, и исход отрезка реализовался; уменьшение задним
  числом делало бы R-мультипликаторы сделок со скейл-аутом
  несравнимыми с прямыми [Tharp гл.6 с.144-146].
- **`currentRiskAmount` уменьшается** и при полном выходе — ноль.
  Потребитель — **сопровождение**: у закрытой сделки он нулевой по
  построению и в выборку `R` не входит. **Операндом лимита он так и не
  стал** (`RISK-Q3` закрыт `GAPS_CLOSE_20`: потолок сделки проверяется
  по `plannedRiskAmount`, вариант «расходуемый ресурс» отвергнут), то
  есть ограничение ниже остаётся принятым, а не отложенным.
  - **Названное ограничение: доля считается по размеру, а не по
    риск-плотности** (C4 `DOCS_CHECK_19`). Формула верна точно, только
    когда все слагаемые ноги несут одинаковый риск на контракт. При
    grid-входе с общим стопом дистанции ног разные: нога A — 10
    контрактов и риск 100, нога B — 10 контрактов и риск 300; после
    полной отработки A формула даёт `400 × 10/20 = 200`, тогда как
    неотработанный риск — 300. Направление ошибки — **занижение живого
    риска**, то есть в сторону, разрешающую больше экспозиции [Vince
    гл.1 с.13,25; Tharp гл.12: превышение оптимума хуже недобора].
    Тот же механизм на многоэпизодной сделке: знаменатель копит филлы
    **закрытых** эпизодов.
  - **Почему приближение принято для фазы 1.** Точная форма требует
    риск-взвешивания по ногам **живого эпизода**, то есть привязки ноги
    к эпизоду — колонки на `orders`, которой нет; плюс при неттинге
    отнесение частичного выхода к конкретным ногам произвольно (FIFO —
    соглашение, не факт). Пока число читает только сопровождение,
    приближение дешевле колонки.
  - **Условие пересмотра названо и не наступило:** приближение стало бы
    недопустимым, если бы число стало операндом **лимита** — оно
    ошибается в разрешающую сторону. `RISK-Q3` закрыт **иначе**
    (потолок проверяется по `plannedRiskAmount`, не по
    `currentRiskAmount`), поэтому ограничение остаётся принятым.
    Оно **другое**, чем «формула не содержит уровня стопа»
    (§выше): то про стоп, это про состав слагаемых.
- **Что второе число чинит.** Неисполненная нога слагаемое в
  заявленном сохраняет, во взятом даёт **ноль**; разрыв «заявлено ↔
  взято» — персистированное поле, а не реконструкция постфактум
  (искажение направленное — занижение правого хвоста `R` [Tharp гл.6
  с.144-146, с.158-159]).
- **Все четыре — производные проекции, пересчитываемые целиком.**
  Инкрементального накопления нет: значение всегда равно формуле по
  текущему состоянию — пересчёт идемпотентен и от порядка не зависит
  (операнд четвёртого числа — уровень стопа — событийный, не
  рыночный). Пересчитывает **тот исполнитель, который меняет операнд**,
  своей же транзакцией:

  **Правило одно: кто меняет любой операнд — пересчитывает все четыре
  числа целиком, своей же транзакцией** (B3 `DOCS_CHECK_19`). Отдельного
  разделения «кто какое число пишет» нет — оно и порождало расхождение
  между местом истины и компонент-доками.

  | Триггер | Исполнитель | Какой операнд меняется |
  |---|---|---|
  | создана новая нога входа (со своей встроенной защитой) | `CreateOrderExecutor` | состав слагаемых **и** действующая защита (attached SL ноги) |
  | наблюдены исполнение / терминальный статус ноги **входа** | `RefreshOrderExecutor` | `accumulatedFillSize`, статус ноги |
  | нога входа отменена / замещена | `CancelOrderExecutor` | статус ноги |
  | **наблюдена позиция** — живая либо из истории | `RefreshPositionExecutor` | размер живого эпизода |
  | **поставлена / замещена standalone-защита** | `CreateAlgoOrderExecutor`, place-нога `REPLACE` | действующая защита |
  | **наблюдён алго-ордер** (в т. ч. сдвиг трейлинга биржей, терминальный статус защиты) | `RefreshAlgoOrderExecutor` | уровень действующей защиты (`condition.trailing.externalPrice` у трейлинга); её исчезновение без замещения |
  | **защита отменена** | `CancelAlgoOrderExecutor` | действующая защита исчезла либо сменилась |

  - **Почему «все четыре», а не по одному полю.** Числа объявлены
    производными проекциями, чьё значение «всегда равно формуле по
    текущему состоянию»; разделение писателей делало значение функцией
    **порядка событий**, а не состояния: после наблюдения филла ноги
    (`incurredRiskAmount` сдвинулся) инвариант `currentRiskAmount =
    incurredRiskAmount × (size / Σ fills)` был бы нарушен до следующего
    наблюдения позиции. Пересчёт целиком идемпотентен и от порядка не
    зависит — цена уже уплачена тем, что вырожденные ветки знаменателя
    описаны выше и обрабатываемы у любого писателя.
  - **Клейм «ветка вырожденного знаменателя недостижима» снят** вместе с
    разделением: она **обрабатываема** (слагаемых нет ⇒ пусто; слагаемые
    есть, филлов нет ⇒ ноль), и это записано.
  - **Два новых писателя — следствие C3 и A7:** `RefreshAlgoOrderExecutor`
    нужен, потому что трейлинг двигает **биржа**, и без наблюдения
    операнд четвёртого числа не обновляется вовсе;
    `CancelAlgoOrderExecutor` — потому что объявленное «действующей
    защиты нет ⇒ поле пусто» не имело писателя: таблица перечисляла
    только события **появления** операнда, а троп исчезновения три
    (teardown выхода, kill-switch, `PROTECTION_LOST` после рефреша).
    Асимметрия с `CancelOrderExecutor`, который пересчёт нёс, снята.

  **Reduce-only-нога состав слагаемых не двигает** — она не входит в
  множество; её исполнение меняет размер живого эпизода и через него —
  `currentRiskAmount`.

  **Наблюдение позиции** не ограничено live-ногой: `REFRESH_POSITION_COMMAND` при
  not-found эскалирует на `positions-history` и материализует позицию
  из записи закрытия (`docs/components/RefreshPositionExecutor.md`
  §«Evidence-cycle: live → positions-history»). Известное ограничение
  (позиция вокруг чужого риска — операнда нижней границы окна нет)
  остаётся: у такой сделки третье число не появляется, и это записано,
  а не замаскировано суррогатом.

  Персистируются все четыре (а не считаются запросом): фильтр и отчёт
  обязаны быть выразимы запросом **без join'а** по `orders`
  (§«Признаки отбора для отчёта»).

  **У третьего и четвёртого чисел читателя в фазе 1 нет — и это принято
  записью, а не выведено** (B4 `DOCS_CHECK_19`). Прежняя атрибуция «их
  читает сопровождение в проходе оркестратора» ни одним доком
  сопровождения не подтверждалась: грепом по `docs/` оба поля
  встречаются только у самой модели и у пяти **писателей**. Довод
  персиста назван честно — **однородность набора и наблюдаемость**, а
  не потребитель.

  - **Почему это исключение из «поле заводится вместе с потребителем»**
    (codestyle §«Неиспользуемый код») названо, а не замаскировано: тем
    же правилом проект **вывел** `triggerPx` и `openAvgPx` из
    used-набора, и молчаливая несимметрия воспроизводила бы находку
    каждым прогоном.
  - **Что делает исключение допустимым:** оба числа — производные
    проекции уже персистируемых операндов, их запись не стоит ни
    запроса к источнику, ни отдельного прохода; цена ввода —
    две колонки на пустой таблице, цена **ввода потом** — миграция с
    данными и потеря наблюдений за период до ввода.
  - **Назначенный потребитель — сопровождение и наблюдения.**
    Кандидат «риск-бюджет как расходуемый ресурс» отпал: `RISK-Q3`
    закрыт двухуровневым лимитом по `plannedRiskAmount`
    (`docs/decisions/per-trade-risk-policy.md` §«Лимит риска
    двухуровневый»). Числа накапливают наблюдения; отдельного
    «включателя» не заводится, исключение из «поле заводится вместе с
    потребителем» остаётся принятым с той же ценой.
- **Валюта одна на все четыре числа** — `plannedRiskCurrency`
  (расчётная валюта инструмента); вторая валютная колонка не заводится.
- **Чего сумма не покрывает — названо.** Риск, выросший **без новой
  ноги** (risk-weakening replace — разрешённый класс,
  `docs/rules/risk-validator-scope.md`), в `R` не входит: замещается
  не нога, а защита. Движение наблюдаемо с обратным знаком — как
  **уменьшение `protectionRelievedRiskAmount`**; реально понесённый
  `R` с учётом ослабления защиты — на шаге ожидаемости. Посылка
  «ослабление защиты конфигурируемо стратегиями фазы 1» не проверена
  (владелец — `trading-specialist`).
- **`R` — риск заявленный, не взятый; операнды сравнения персистятся
  рядом.** Число считается по **заявленной** цене входа и
  **заявленному** размеру; расхождение с фактом систематическое по
  обеим осям (проскок входа; частичное исполнение), поэтому вместе с
  `R` персистятся **`plannedEntryPrice`** (reference-цена входа; для
  market-входа — `ORDER_MARKET_REFERENCE_PRICE` калькулятора, на биржу
  не отправляемая) и **`plannedSizeContracts`** (заявленный размер).
  - **Дом операндов — нога входа, и это `Order`**: при многоногом
    входе операндов несколько, а держать риск и его операнды на разных
    уровнях значило бы разорвать связывающее их тождество.
  - **Входной тропы алго-ордером не существует** (inspection по коду:
    все значения `AlgoOrder.ConditionType` — protective/closing);
    вход — ordinary `Order` (`ENTRY` / `ENTRY_ATTACHED_STOP_LOSS`),
    поэтому колонки `planned_entry_price` / `planned_size_contracts`
    живут **только в `orders`**
    (`docs/models/domain/core/Order.md` §Персистентность). Условие
    возврата вопроса — `docs/models/domain/core/AlgoOrder.md`
    §Назначение.
  - **Знаменатель `R` на `Deal` остаётся — но как сумма, а не как
    единственный носитель**: у ноги — принятый ею риск (write-once), у
    сделки — принятый суммарно (поддерживается актуальной).
  - **Поправка живёт в аналитике, не в поле.** `plannedRiskAmount`
    остаётся числом, под которое подбирался размер; разрыв наблюдаем
    по persisted-данным: (`avgPx` − `plannedEntryPrice`),
    (`accFillSz` − `plannedSizeContracts`) [Kaufman гл.21 PDF
    с.1913-1914]. Поправка на проскок **выхода** отложена
    (`docs/decisions/per-trade-risk-policy.md` §«Без поправки на
    проскок»).
- **Почему не реконструкция.** Формально `R` восстановим через
  REPLACE-цепочку + `avgPx`/`accFillSz` + `ctVal` — но это join через
  три носителя, прогнозная комиссия в него не входит, и получается не
  то число, под которое сайзились.
- **Смежный вопрос был про лимит, не про знаменатель, и он закрыт.**
  Правило агрегации **лимита** — двухуровневый лимит
  (`docs/decisions/per-trade-risk-policy.md` §«Лимит риска
  двухуровневый», закрытие `RISK-Q3`); состав знаменателя он не
  меняет. Открытым остаётся только **число** потолка (`RISK-Q3-A`,
  риск-аппетит держателя) и **портфельный** радиус — форвард.

Детальный breakdown (fees, fundingFee, gross/netProfit, entry/exit
fills, average prices, partial exits) в `Deal` не хранится: число берётся
готовым из positions-history, категорийная разбивка живёт как
`DealCashFlow` (bills), пофилловая детализация — вне фазы 1 (persisted
`TradeFill` не вводится).

## Рамка R-выборки

**Выборки как хранимого объекта не существует** (решение пользователя).
Отбор сделок для отчёта — **параметры эндпоинта**, который дёргает
фронт; фильтры суть значения полей сделки. **Сделка пишется всегда**,
независимо от терминала, и **из популяции ничего не выводится**: нет ни
«выведена из R-выборки», ни «исключена как непроверенная» — есть
значения признаков, по которым потребитель отчёта фильтрует сам.

Довод против выборки-множества с предикатом членства: членство по
технической тропе FSM раскалывало бы сделки с одинаковым рыночным
исходом на разные популяции, а левый хвост распределения (ликвидации —
худшие исходы) усекался бы, делая `BiggestLoss` ненаблюдаемым и
систематически завышая ожидаемость.

### Признаки отбора для отчёта

**Каждый фильтруемый признак — поле сделки, а не вывод на лету.**
Признак, вычисляемый запросом «по дороге», фильтром эндпоинта быть не
может: его нельзя ни проиндексировать, ни воспроизвести, ни объяснить
в отчёте.

| Признак | Поле | Значения |
|---|---|---|
| Торговый исход закрытия | `closeOutcome` | `NORMAL_EXIT` / `LIQUIDATION` / `FORCED_REDUCTION` / `UNDETERMINED` |
| Статус сверки разбивки | `reconciliationStatus` | `NOT_RUN` / `MATCHED` / `MISMATCHED` |
| Структурная неполнота разбивки | `breakdownIncomplete` | `COMPLETE` / `INCOMPLETE_BY_WINDOW` / `NOT_ASSESSED` |
| Природа пустоты знаменателя `R` | `riskBenchmarkAvailability` | `AVAILABLE` / `NOT_APPLICABLE` / `MISSING` |

- **`closeOutcome` — торговый факт, не техническая тропа.** Пишется
  финализацией (штатной и аварийной) из `Position.externalCloseType`
  (`docs/models/domain/core/Position.md`): `1,2` — штатный выход;
  `3,4` — ликвидация; `5,6` — ADL; **операнд пуст — `UNDETERMINED`**.
  - **Эпизод-источник назван: строка с `max(externalModifiedAt)`** (A6
    `DOCS_CHECK_19`). У многоэпизодной сделки `externalCloseType` несут
    несколько строк, и «последний» до сих пор нигде не был определён
    операндом. Берётся `externalModifiedAt` (`uTime` записи закрытия) —
    тот же операнд, которым `RefreshPositionExecutor` выбирает
    «последнюю запись» для `billsWindowEnd`; второго носителя
    хронологии не заводится. `externalCreatedAt` (`cTime`) не годится:
    у эпизода, схлопнувшегося и переоткрывшегося между тиками, порядок
    заведения строк не совпадает с порядком закрытий.
  Ликвидация чистой тропой `EXIT_PENDING → CLOSED` и ликвидация через
  `ERROR → EMERGENCY_CLOSED` получают **одно и то же** значение —
  путь-зависимости нет.
- **`reconciliationStatus` — свойство числа, а не членства.** `NOT_RUN`
  — сверка не была обязана (аварийный терминал с пустым окном
  движений); `MISMATCHED` — расхождение сверх epsilon; сделка остаётся
  в популяции при любом значении. Состав сверки, epsilon, реакция —
  дом `docs/rules/pnl-reconciliation.md`.
- **Неполнота разбивки — она же неполнота числа, и она уводит
  терминал** (решение держателя). Источник неполноты у разбивки и у
  `resultProfit` общий (cross-ccy-слагаемое суммируется по тем же
  строкам), усечение направленное — число завышается, — поэтому такая
  сделка чистого `CLOSED` не получает. Предикат — **перечнем значений,
  без неявного «иначе»** (Г1 + B3 `DOCS_CHECK_18`):

  ```text
  breakdownIncomplete ∈ {INCOMPLETE_BY_WINDOW, NOT_ASSESSED}
  ИЛИ ∃ прилинкованная строка DealCashFlow с
        rateStatus ∈ {RATE_UNAVAILABLE, SETTLE_CURRENCY_UNAVAILABLE}
  ```

  Истина ⇒ **ошибочная тропа** к `EMERGENCY_CLOSED`; исполняет предикат
  выходная проверка `ExitPendingHandler`
  (`docs/components/FinalizeDealExitExecutor.md` §«Неполное число — не
  чистый терминал», `docs/components/ExitPendingHandler.md` §«Выходные
  проверки»). Пятого признака (полноты числителя) не заводится —
  предикат собран из существующих фактов.
- **`breakdownIncomplete` — структурная, а не дефектная неполнота.**
  Окно добычи конечно со стороны источника, горизонт удержания сделки
  не ограничен; у сделки длиннее окна часть строк недобываема
  **выбранным конвейером добычи** (`7d` → `bills-archive` `3m`;
  deep-архив в конвейер не входит). Признак отделяет «сверка звенит по
  дефекту» от «звенит по построению».

**Значение при недобытом операнде — явное, не благоприятное** (правило
— `docs/rules/absent-value-semantics.md`): «не проверяли» обязано
отличаться от «проверили, всё в порядке»:

| Признак | Операнд не добыт | Значение | Сигнал |
|---|---|---|---|
| `closeOutcome` | `Position.externalCloseType` пуст (записи нет) | `UNDETERMINED` | журнальный `AnomalyReport` (`kind = EVENT`) |
| `breakdownIncomplete` | `billsWindowBegin` пуст **либо** `billsFetchedThrough` пуст (добыча движений не выполнялась) | `NOT_ASSESSED` | журнальный `AnomalyReport` (`kind = EVENT`) |
| `reconciliationStatus` | **строки нет** — операнд допуска резолвится всегда, нерезолвимый до признака не доезжает | — | — |

- **`UNDETERMINED` — не «сделки не было» и не «штатный выход»:** сделка
  с недобытым фактом закрытия не попадает в благоприятную корзину под
  чужим ярлыком; счётность — `group by close_outcome`.
- **Недостача обязательного поля источника — нарушение контракта
  интеграции, и обнаруживается оно на границе.** Обязательные поля
  добытой записи (`type` внутри `1..6`, правые операнды четырёх пар,
  `realizedPnl`, `ccy`, резолвимый `direction`) проверяются **в слое
  интеграции**; нарушение — `ExternalInvariantViolationException`
  (`docs/models/mapping/PositionCloseResult.md` §«Контракт записи
  проверяется здесь»). Реакция — **биржевая ступень 2
  `Exchange.TRADE_BLOCKED`** (kill-switch flatten), поднимается общим контуром
  перехвата **параллельно** ошибочному терминалу сделки — ветки не
  конкурируют (`docs/rules/exchange-hold.md` §«Что переводит в
  TRADE_BLOCKED», п.1).
  **Следствие для признака:** до финализатора запись с `type` вне
  перечня не доезжает, поэтому `UNDETERMINED` несёт один смысл —
  **записи нет вовсе**; биржевой реакции этот случай не вызывает.
- **Обязанная и невыполненная сверка ⇒ ошибочный терминал.** Принцип
  формулируется через **обязанность**: наступила и не исполнена ⇒
  ошибочный терминал; «должны были и посчитали» ⇒ успешный терминал
  (`MATCHED`/`MISMATCHED`); «не должны были» ⇒ успешный терминал
  (`NOT_RUN`). **Операнд «должны были посчитать»** — составной
  durable-предикат: записи закрытия добыты у **всех** эпизодов
  (`Position.externalRealizedProfit` непуст на каждой строке — поле
  обязательно на границе, его непустота ⟺ запись добыта), окно движений
  закрыто (`Deal.billsWindowEnd` непуст) **и движения добывались**
  (`Deal.billsFetchedThrough` непуст — A2 `DOCS_CHECK_19`). Третий
  конъюнкт несущий: на аварийной тропе bills-звено не эмитится вовсе, и
  без него обязанность считалась бы наступившей там, где сверять нечего
  (`docs/components/SystemActionExecutor.md` §«Состав конкретного
  цикла»). Живого случая «были
  обязаны, операнда допуска не нашлось» нет: оба операнда допуска
  персистятся write-once на ноге по инварианту «шесть или ни одного»
  (`docs/components/FinalizeDealExitExecutor.md` §epsilon); нарушение
  инварианта ловит детектирующий контур **отказом операции**
  (§«Обнаружение рассогласования пары носителей»). Биржевой холд по
  этому классу **не поднимается**: недостача наша, радиус ущерба
  локализован сделкой.
- **`breakdownIncomplete` — енум из трёх значений, не `Boolean`.**
  `Boolean` + `NULL` дал бы трёхзначную логику, где «разбивка полна» и
  «не оценивалась» неразличимы для потребителя, не пишущего
  `IS NULL`. **Аварийный терминал считает признак тем же сравнением,
  что штатный** (не подставляет `INCOMPLETE_BY_WINDOW` безусловно):
  «заведомо неполна» — свойство разбивки, а не результат измерения.

**Тропы закрытия без входа — признаки неприменимы, и пустота есть их
значение.** На тропах, где терминал `CLOSED` ставится в обход
финализации (истечение условия входа в `PRECHECK`, риск-блок
`RISK_CONTROL` в `PRECHECK`, отмена неисполненного входа из
`ENTRY_SUBMITTED`), события, о котором признак, не было: позиция не
открывалась, разбивку сверять не с чем. Пустота однозначна
(`docs/rules/absent-value-semantics.md` §«Разграничение — по тропе, а
не по полю»). `MARK_DEAL_CLOSED_COMMAND` пишет ноль, валюту и терминал;
три признака (`closeOutcome`, `reconciliationStatus`,
`breakdownIncomplete`) оставляет пустыми — это их ратифицированное
значение, а не пропуск. Четвёртый (`riskBenchmarkAvailability`) из-под
клейма выведен: `NOT_APPLICABLE` пишет `MarkDealClosedExecutor` той же
транзакцией (§Енумы).

**Принудительный эпизод внутри сделки отдельным полем `Deal` не
выражается.** `closeOutcome` — проекция **последнего** закрытия
источника; сделка, где принудительное сокращение произошло в середине, а
последним закрытием было наше, числится `NORMAL_EXIT`. Факт **полной**
ликвидации / принудительного закрытия несёт **`closeOutcome`
(`LIQUIDATION` / `FORCED_REDUCTION`) — единственный носитель уровня
сделки, на любой тропе**: маршрутизирующего правила «закрытие позиции
биржей доводит сделку до `EMERGENCY_CLOSED`» не существует — ликвидация
штатно проходит и чистой тропой, и `closeOutcome` пишется на обеих.

**Прежняя названная цена — «частичный принудительный эпизод, за которым
последовал наш выход, отдельно не счётен» — снята многоэпизодностью**
(`docs/decisions/multi-episode-deal.md`): у эпизода **есть своя строка**
`positions` со своим `external_close_type`, и такой эпизод счётен
запросом по строкам. Ограничение осталось только на уровне **поля
сделки**: одно поле — один исход, и это последний. Кейс, где эпизод не
получает строки (принудительное **сокращение** без схлопывания в ноль:
`posId` тот же, позиция уменьшилась), остаётся неотличимым по строкам —
его след ловят категория `LIQ_PENALTY` в разбивке и предусловие `CODE`
п. 10.

**След эпизода — посылка, а не факт.** «След частичного эпизода
остаётся строками `LIQ_PENALTY` и покрыт четвёртой парой сверки» —
посылка: при ADL штраф не обязателен, частичный ADL может не оставить
следа вовсе [Tharp гл.6 с.158-159]; корпус объявляет ADL пробелом
(`microstructure.md` §9). Проверка посылки — в реестре предусловий
`CODE` (`docs/decisions/pnl-finalization-mechanics.md` §«Предусловия
`CODE`», п. 10): фикстура §AG1 на реальном ответе источника — даёт ли
`type` `5,6` записи категории `LIQ_PENALTY` в bills.

**Конструкция фильтров живёт на стороне API и фронта**, в модели шага 7
её нет: модель обязана лишь **нести признаки полями**, чтобы фильтр был
выразим запросом.

**Что остаётся верным из прежней рамки:**

- **Сделка без состоявшихся операций — не исход системы.** Признак —
  `docs/rules/deal-without-operations.md` (там же составной предикат
  по тропам). **Отдельным полем он не материализуется**; назначенного
  операнда отбора у отчёта нет (`closeReason` две тропы не различает,
  терминальный `status` фазу закрытия не хранит) — **определение
  популяции за потребителем отчёта, решается на шаге фронта** по полям
  сделки и её дочерних сущностей. Несостоявшиеся входы — ось «частота
  возможностей», не распределение R [Tharp гл.6 с.130-133];
  **счётчик частоты покрывает только входы, дошедшие до создания
  `Deal`** — пропуски на уровне скана — форвард фазы 3
  (`docs/decisions/pnl-finalization-mechanics.md` §«Форвард-фокус»).
- **Неисчислимые (`resultProfit = null`) считаются поштучно.**
  `RESULT_PROFIT_UNAVAILABLE` — отчёт природы `kind = EVENT`, анкера
  не имеет и по разным сделкам одного инструмента не схлопывается
  (`docs/models/domain/other/AnomalyReport.md` §Енумы, `Kind`).
  Счётность обеспечена структурно, а не соглашением.

**Разрешимость выборки при пропускной способности контура фазы 1**
(один инструмент, одна активная сделка) — **форвард на фазу 3** вместе
с осью упущенных возможностей
(`docs/decisions/pnl-finalization-mechanics.md` §«Форвард-фокус»).

### Операции были, а `R` пуст

Обратный случай к «есть `R`, но операций не было»: числитель есть,
знаменателя нет. Достижим **только** для позиций, созданных **вне
приложения** (решение пользователя): наш риск-преконтроль пишет
`plannedRiskAmount` на каждом входном действии, поэтому сделка,
рождённая нашим входом, без знаменателя не бывает. Остаются
`EntryReason.RECOVERY` / `MANUAL` / `UNKNOWN` — сделки вокруг чужой
позиции.

Пустота суммы означает: **ни одна нога входа планового риска не несёт**
(§«Предикат отбора слагаемых»). Пустая сумма и сумма-ноль различимы:
слагаемых нет ⇒ поле пусто (не `ZERO`) — подстановка нуля запрещена
(`docs/rules/absent-value-semantics.md`).

**Две природы пустоты разведены признаком, а не оставлены потребителю**
(решение пользователя): признак — енум **`riskBenchmarkAvailability`**
(§Енумы). Отвергнутая альтернатива — операнд отбора конъюнкцией
`planned_risk_amount is null AND close_outcome is not null` — колонки
не добавляет, но фильтр отчёта обязан быть выразим значением одного
поля (§«Признаки отбора для отчёта»).

- **Это аномалия, а не рабочий режим.** Реакция — **жёсткий выход**:
  контур фазы 1 позициями извне не управляет, и попытка вести такую
  сделку означала бы риск, размер которого система не назначала.
- **Такие сделки обязаны быть счётными.** Популяция
  outcome-коррелирована по построению (чужие позиции всплывают из
  рестартов и аварий) — молчаливая омиссия воспроизводила бы смещение.
  Счёт — журнальным отчётом `kind = EVENT` (`PLANNED_RISK_MISSING`).
  Из популяции сделка **не выводится**: пустой `plannedRiskAmount` —
  свойство строки, по которому потребитель отчёта фильтрует сам.
- **Детализация — шаг 8** (`AnomalyJob`): код отчёта, момент детекции
  и форма жёсткого выхода. Шаг 7 фиксирует популяцию, реакцию и
  требование счётности.

Провенанс числа и довод «`null` ≠ ноль» — `docs/decisions/
pnl-finalization-mechanics.md` реш.3.

## Окно линковки bills (`billsWindowBegin` / `billsWindowEnd`)

Границы окна, по которому `RefreshBillsExecutor` матчит движения к
сделке, — **собственные поля `Deal`**; из чужих колонок
(`Position.externalModifiedAt`) окно **не реконструируется** — та
колонка писалась обеими ногами `REFRESH_POSITION_COMMAND` и предиката
«запись закрытия добыта» не выражала. Заполняет **наблюдатель факта**;
монотонность у границ **разная** и следует из того, что каждая
наблюдает:

- `billsWindowBegin` — **`Order.externalCreatedAt` первой отправленной
  ноги сделки; писатель один — `SubmitOrderExecutor`, всегда при
  постановке** (решение пользователя; §«Почему у нижней границы один
  писатель»). **Write-once**: первая нога у сделки одна, наблюдение
  однократно.
- `billsWindowEnd` — `uTime` записи закрытия positions-history; пишет
  **вторая нога** `REFRESH_POSITION_COMMAND` в одной транзакции с
  полями положения закрытия на `Position`. Писатель один, но
  **наблюдений столько, сколько эпизодов**: значение двигается
  **монотонно вперёд** (§«Верхняя граница монотонна, а не write-once»).

### Верхних границ две, и у них разные роли

Развилка `FEE-Q2` закрыта решением держателя: **величины две, и обе
законны**.

| Величина | Чем является | Носитель | Кто потребитель |
|---|---|---|---|
| **подвижная** | **серверное время источника** на момент запроса (`GET /public/time`, A8 `DOCS_CHECK_20`) | не персистится как граница — оседает в `billsFetchedThrough` | верхняя граница **запроса к источнику**; линковку ограничивает не отметка, а нетерминальность `Deal`: `RefreshBillsExecutor` тянет `[billsWindowBegin, t_source]` и линкует добытое сразу |
| **неподвижная** | `uTime` записи закрытия **позднейшего закрывшегося** эпизода | `Deal.billsWindowEnd` (монотонно вперёд) | предикат **обязанности сверки**, **один из двух** операндов признака полноты, порог **доказанного покрытия** окна |

**Что это даёт.** Добыча не ждёт записи закрытия: окно запроса
определено всегда, добыча идёт на любом проходе — без гейта эмиссии.

**Линковка идёт по подвижной границе** (C1 `DOCS_CHECK_19`):
`deal_cash_flows.deal_id` проставляется **при сохранении**, предикат —
`ts ≥ billsWindowBegin` при нетерминальном `Deal`.

- **Почему не по неподвижной.** Неподвижная граница — `uTime` записи
  закрытия, а движения этого закрытия приходят в конвейер bills
  **позже** этого момента (лаг конвейера — `docs/integrations/okx/
  contracts/account-bills.md`). Линковка «по закрытому окну» поэтому
  либо ждёт неопределённое время, либо теряет хвост: предикат `ts ≤
  billsWindowEnd` отсекает ровно те строки, ради которых окно и
  открывалось. Довод не зависит от монотонности границы — он верен и
  для одноэпизодной сделки. **Многоэпизодность его усиливает:** пока
  граница двигается, «окно закрыто» — состояние, которое до терминала
  не наступает вовсе, и линковка, ожидающая его, не выполняется
  никогда.
- **Точность сверху обеспечивает не граница, а инвариант слота.** Пока
  сделка не терминализована, она **единственная** активная на
  инструменте (`uk_deal_active_instrument`), поэтому открытая сверху
  линковка чужого не подберёт — довод ратифицирован
  (`docs/models/domain/other/DealCashFlow.md` §«Линковка к `Deal`»).
- **Провизорной линковки по-прежнему нет** — значит нет и отлинковки:
  строка, залинкованная к единственной активной сделке инструмента,
  принадлежит ей окончательно. Монотонная политика перезаписи не
  нарушается.
- **Побочно снята названная цена** прежней редакции: движения,
  пришедшие после закрытия позиции, но до терминала сделки, больше не
  остаются несвязанными — они принадлежат экономике этой сделки и
  линкуются к ней. Форвард-слот шага 8 сужается до движений аккаунта
  **вне** периода жизни сделок.

**Цена посчитана — двойная не линковка, а добыча:**

- **перекрывающиеся перезапросы:** каждый проход тянет диапазон заново
  до `now`; лишних строк нет (дедуп по
  `UNIQUE(exchange_id, external_bill_id)`), но растут трафик и число
  страниц — плата за завершимость звена;
- **операнд `breakdownIncomplete` — составной: верхняя отметка есть
  позднейший из двух моментов** (решение держателя):

  ```text
  max(billsFetchedThrough, billsWindowEnd) − billsWindowBegin
                                             против глубины конвейера
  ```

  Недобываемость строки определяется её давностью — отсюда возраст
  нижней границы; **позднейший** из двух моментов делает операнд
  монотонным и не зависящим от тропы. Цена — один лишний конъюнкт.
  **Оба операнда — биржевые якоря** (A8 `DOCS_CHECK_20`): `public/time`
  прохода добычи и `uTime` записи закрытия; системных часов в формуле
  нет (`docs/rules/time-utc.md` §«Два временных домена, и смешивать их
  запрещено»).
  `Deal.billsWindowEnd` остаётся операндом **обязанности сверки** — и
  одним из двух операндов признака полноты; ветка «добыча не
  выполнялась» (пустота нижней границы = отсутствие разбивки)
  сохраняется.

**Почему подвижная не персистится.** Она не факт, а параметр запроса:
что именно добыто, видно по самим строкам и их `ts`. Колонки под неё
не заводится.

### Верхняя граница монотонна, а не write-once

**`billsWindowEnd` двигается вперёд с каждым закрывшимся эпизодом**
(A1 `DOCS_CHECK_20`). Формула писателя — та, что уже записана в
исполнителе: нога 2 `REFRESH_POSITION_COMMAND` идёт по **каждой**
строке `Position` сделки, добывшей запись закрытия, и ставит
`billsWindowEnd = uTime` **последней** записи
(`docs/components/RefreshPositionExecutor.md` §«Нога 2»).

**Почему не write-once.** Write-once сажает границу на **первый**
закрывшийся эпизод. Тогда предикат завершения bills-звена
(`billsFetchedThrough ≥ billsWindowEnd`) становится истинным **до**
закрытия последнего эпизода: движения второго и последующих эпизодов
ещё не пришли, а покрытие уже «доказано». Число уходит в чистый
`CLOSED` **заниженным** — то есть попадает не в ветку «недоступно», а
в ветку «посчитано верно», что прямо запрещено
`docs/rules/absent-value-semantics.md` §«Благоприятное значение по
умолчанию запрещено».

**Инвариант.** `billsWindowEnd` есть верхняя отметка **всей** сделки,
не отдельного эпизода: окно `[billsWindowBegin, billsWindowEnd]`
обязано накрывать движения всех эпизодов. Второй носитель (граница
эпизода) **не заводится** — различения «граница эпизода против границы
сделки» ни один потребитель не запрашивает, а четыре потребителя
границы (завершение bills-звена, завершение
`REFRESH_POSITION_COMMAND`, обязанность сверки, верхняя отметка
`breakdownIncomplete`) читают её **на финализации**, когда двигаться
уже нечему.

**Что монотонность НЕ меняет.** Все четыре потребителя читают границу
одним и тем же способом; guard писателя — тот же условный `UPDATE`,
только условие другое (§Персистентность). Новых мест чтения ноль.

### Добыча движений — durable-факт, а не память прохода

**`billsFetchedThrough` — носитель факта «движения добыты до момента
T»** (A1 + A2 `DOCS_CHECK_19`). Пишет `RefreshBillsExecutor` своей
транзакцией при успешно вычитанном диапазоне: `billsFetchedThrough =
верхняя граница запроса этого прохода`, монотонно вперёд.

**Верхняя граница запроса — биржевой якорь, не системные часы** (A8
`DOCS_CHECK_20`, решение держателя). Значение берётся из `GET
/api/v5/public/time` прохода
(`docs/integrations/okx/contracts/server-time.md`), а не из `now()`
наших часов: оно сравнивается с `billsWindowEnd` (биржевой `uTime`) в
предикате завершения звена, а границы биржевых окон сравниваются только
с биржевыми таймстампами (`docs/rules/time-utc.md` §«Два временных
домена, и смешивать их запрещено»). Собственной метки у события «мы
вычитали диапазон» нет — законно пустой набор движений не даёт ни одной
строки, — поэтому применяется ветка «при нужде `public/time`».

- **Цена — один публичный запрос на проход звена.** Эндпоинт без
  подписи, вне приватного лимита; ответ используется дважды —
  как `end` запроса bills и как записываемое значение
  `billsFetchedThrough`.
- **Отказ `public/time` — отказ звена**, а не повод подставить
  системное время: подставленный операнд выглядел бы фактом, не будучи
  им (`docs/rules/absent-value-semantics.md`). Учёт отказа — обычный,
  по бюджету исполнения.

**Зачем понадобился.** У bills-звена не было **ни одного** durable
операнда завершения: строки `DealCashFlow` не кодируют вычитанный
диапазон, верхняя граница запроса подвижна каждым проходом, собственной
метки звено не несло. Единственное звено цикла, чью стадию нельзя было
вывести из БД — вопреки общему требованию «факт durable, читается из
БД, не память прохода» (`docs/components/SystemActionExecutor.md`
§«Вывод стадии»). Отсюда два следствия на **штатной** тропе: стадия
действия по звену не выводима (звено повторяется до исчерпания бюджета —
ложный `FAILED` + холд инструмента на нормальном выходе), и предикат
«движения добывались» подменялся чужим фактом — `billsWindowEnd`,
который пишет наблюдатель **закрытия позиции**, а не добыча.

**Два предиката, которые поле закрывает:**

```text
bills-звено завершено ⟺ billsWindowEnd непуст И billsFetchedThrough ≥ billsWindowEnd
движения добывались   ⟺ billsFetchedThrough непуст
```

- **Р7 не переоткрывается.** Р7 `GAPS_CLOSE_16` снял **гейт эмиссии** по
  окну: добыча не ждёт записи закрытия и идёт каждым проходом — это
  остаётся в силе. Здесь речь о другом — о **завершении** звена: оно
  означает **доказанное покрытие**, а не «мы что-то вычитали».
  Недостижимого условия завершения при этом не возникает: тот же
  `billsWindowEnd` уже гейтит завершение соседнего звена
  (`REFRESH_POSITION_COMMAND` — «`Position.status = CLOSED` плюс непустое
  положение закрытия»), то есть действие и так не завершается без него.
- **Ложного «добыли, движений нет» больше нет.** Пустой набор движений —
  тоже добытый факт: `billsFetchedThrough` пишется независимо от того,
  вернул ли источник строки. Прежний кандидат-операнд «непустота
  прилинкованной коллекции» этих двух состояний не различал.
- **Догон курса получает горизонт.** Пока покрытие не доказано, звено
  повторяется, то есть должники `rateStatus` получают новую попытку
  каждым проходом выходной тропы — механика догона
  (`docs/components/RefreshBillsExecutor.md` §«Политика отказа котировки
  и догон») перестаёт зависеть от того, сколько раз handler завёл
  исполнение.
- **Монотонность, а не write-once:** значение двигается вперёд каждым
  успешным проходом. Guard — `where bills_fetched_through is null or
  bills_fetched_through < :tSource`, где `:tSource` — серверное время
  источника прохода (A8 `DOCS_CHECK_20`).

### Почему у нижней границы один писатель

Поле write-once, а при нескольких писателях потребовалось бы правило
разрешения конкуренции, которого нет. Писатель назначен один,
безусловно: `Deal.billsWindowBegin = Order.externalCreatedAt` первой
отправленной ноги (`docs/components/SubmitOrderExecutor.md` §«Нижняя
граница окна линковки bills»). Ни live-нога, ни нога 2
`REFRESH_POSITION_COMMAND` этого поля не касаются.

- **Зависимости от рантайм-факта нет:** `externalCreatedAt` ордера не
  позже комиссии его же исполнения (комиссия входа возникает при
  филле, филл — не раньше постановки), значит окно накрывает entry-fee
  при любом ответе источника.
- **Более широкое окно безопасно:** лишних движений оно не
  захватывает — активная сделка на инструмент одна (тот же инвариант
  слота, что держит верхнюю границу).
- **Ограничение подтропы «позиция создана вне приложения»:**
  отправленной ноги нет — нет и операнда границы; та же подтропа уже
  не адресуема по временной оси запроса positions-history
  (`docs/components/RefreshPositionExecutor.md` §«Известное
  ограничение»). Выбор писателя её достижимости не меняет.

**Механизм write-once — условный `UPDATE`, не `updatable = false`.**
Строка `deals` существует раньше значения (границы окна приходят позже
наблюдением факта), поэтому JPA-запрет обновления сделал бы поле
незаписываемым вовсе; это отличает `deals.bills_window_*` от
`orders.planned_*`, которые садятся той же вставкой, что и строка
(`docs/models/domain/core/Order.md` §Персистентность). Guard — условие
`where bills_window_begin is null` в обновлении; при единственном
писателе он охраняет не конкуренцию писателей, а повторную постановку
ног той же сделки.

`billsWindowEnd` пуст (факт закрытия не добыт) → **завершения
bills-звена нет**, окно не закрывается; исчерпание бюджета добычи →
ошибочная тропа + холд инструмента. **Линковку это не блокирует** —
она идёт по подвижной границе при сохранении (§«Верхних границ две»).
**Цена решения:** после терминала линковка запрещена
(`docs/models/domain/other/DealCashFlow.md` §«Линковка к `Deal`») ⇒
движения, не пришедшие в конвейер до терминала, не подберутся никогда —
разбивка неполна, сверка даёт `AnomalyReport` при, возможно, верном
числе.

## Runtime graph

`Deal` содержит runtime graph: `orders` (см.
`docs/models/domain/core/Order.md`), `algoOrders` (см.
`docs/models/domain/core/AlgoOrder.md`), `positions` (см.
`docs/models/domain/core/Position.md` — **строки эпизодов**, живая ≤1).
Live risk сделки — вычисляемо (см. lifecycle), отдельным boolean-полем не
хранится.

**Закрытые эпизоды из графа не выводятся** (`docs/decisions/
multi-episode-deal.md`): по ним считается `resultProfit` и правые
операнды четырёх пар сверки, поэтому «граф сделки» без них был бы
клеймом полноты, опровергаемым собственным финализатором. «Текущая
позиция» — предикат модели `livePosition()`, не отдельное поле.

В runtime graph **не** входят и в `Deal` не хранятся:
`DealActionState`, `Exchange`, `Instrument`, `StrategyDetail`,
`BalanceContainer`, `TradeFill` archive (persisted `TradeFill` в
проекте не вводится), raw exchange facts, `CalculationContext`,
`MarketPriceData`, `IndicatorValue`, `MarketStructure`, `MarketPhase`
runtime data, audit/history, pending `ServiceCommand`. Также не
хранятся `marketPhaseId` (фаза входа выводится через
`StrategyDetail.marketPhaseType`), `openedAt`/`closedAt`/`errorAt`
(даты записи — `Auditable`; торговые моменты — через
`Order`/`Position`/audit). Окно линковки bills из чужих носителей не
собирается — его границы суть собственные поля сделки (§«Окно линковки
bills»; `docs/models/domain/other/DealCashFlow.md` §«Линковка к
`Deal`»).

## Персистентность

Хранится в БД (entity `DealEntity`, таблица `deals`), наследует
audit-поля (`AuditableEntity`). Runtime graph (`orders`/`algoOrders`/
`positions`) — отдельные таблицы по `deal_id`, не cascade-коллекции этой
строки. Категорийная разбивка P&L (`DealCashFlow`) — тоже **отдельная
таблица `deal_cash_flows` по `deal_id`** (не поле `Deal`; число
`resultProfit`/`resultProfitCurrency` — поля `Deal`, разбивка — строки
`deal_cash_flows`; `docs/models/domain/other/DealCashFlow.md`).
Ограничения схемы:

- `id` — identity (autoincrement).
- `internal_id`, `instrument_id`, `strategy_detail_id`, `status`,
  `direction` — `NOT NULL`; `entry_reason`, `entry_step_type`,
  `shutdown_reason`, `close_reason`, `planned_risk_amount`,
  `incurred_risk_amount`, `current_risk_amount`,
  `protection_relieved_risk_amount`, `planned_risk_currency`,
  `planned_risk_equity_base`,
  `result_profit`, `result_profit_currency`, `bills_window_begin`,
  `bills_window_end`, `bills_fetched_through`, `close_outcome`,
  `reconciliation_status`,
  `breakdown_incomplete`, `risk_benchmark_availability` — nullable
  (`planned_risk_*` / `incurred_risk_amount` / `current_risk_amount`
  пусты до постановки входа, `protection_relieved_risk_amount` — до
  постановки защиты; `bills_window_*` — до наблюдения фактов
  открытия/закрытия; признаки отбора — до финализации).
- **Колонки шага 7 — `ALTER`, в `V6`/`V9` их нет** (типы — по общему
  правилу `docs/rules/persistence-representation.md` §«Строковые
  колонки»): `planned_risk_amount` (`numeric(36,18)` — **заявленная**
  сумма плановых рисков живых и исполнившихся ног входа; не
  write-once), **`incurred_risk_amount`** (`numeric(36,18)` — **взятый
  на входе** риск; не write-once), **`current_risk_amount`**
  (`numeric(36,18)` — **неотработанная доля** взятого на входе риска;
  не write-once), **`protection_relieved_risk_amount`**
  (`numeric(36,18)` — **риск, снятый защитой**; не write-once),
  `planned_risk_currency` (`varchar(64)` — одна на все четыре числа;
  **несимметрия с существующей `result_profit_currency` (`varchar(16)`,
  `V6`) названа и ретрофита не требует** — B8 `DOCS_CHECK_18`: единая
  норма длин действует на **вводимые** колонки
  (`docs/rules/persistence-representation.md` §«Строковые колонки:
  длины»), а `varchar(16)` вмещает любой тикер валюты, поэтому
  расширение существующей колонки было бы правкой без потребителя),
  **`planned_risk_equity_base`** (`numeric(36,18)` — база процента риска
  на момент сайзинга; **write-once**, C4 `DOCS_CHECK_20`),
  `bills_window_begin`, `bills_window_end`, **`bills_fetched_through`**
  (все три `timestamptz`; третья — монотонная вперёд, до какого момента
  добыты движения; A1 + A2 `DOCS_CHECK_19`) **плюс
  признаки отбора для отчёта** — `close_outcome` (`varchar(64)`),
  `reconciliation_status` (`varchar(64)`), `breakdown_incomplete`
  (`varchar(64)` — енум `BreakdownCompleteness`, не `boolean`: третье
  состояние «не оценивалось» заведено значением),
  **`risk_benchmark_availability`** (`varchar(64)` — енум
  `RiskBenchmarkAvailability`) — добавляются миграцией шага 7.
  **Длины строковых колонок — единая норма `varchar(64)`**
  (`docs/rules/persistence-representation.md` §«Строковые колонки:
  длины»). Полная schema-дельта шага —
  `docs/decisions/pnl-finalization-mechanics.md` §«Schema-дельта шага 7». Перечень
  здесь — **место истины** схемы сущности
  (`docs/rules/persistence-representation.md` §«Место истины схемы»).
- **Индекс отбора для отчёта — `ix_deal_status_close_outcome`** по
  (`status`, `close_outcome`): выборка отчёта фильтрует по терминалу и
  торговому исходу, без индекса растёт линейно по истории закрытых
  сделок. Остальные признаки низкоселективны и в индекс не идут.
  **Прежний `ix_deal_status` дропается той же миграцией**: (`status`) —
  префикс нового индекса, выборку активных сделок он обслуживает; вторая
  структура на непрунимой таблице платится стоимостью записи без
  выигрыша чтения. **Имя названо здесь** (B5 `DOCS_CHECK_18`): место
  истины схемы `deals` — этот раздел, а три соседних индекса названы
  поимённо; на имя ссылается
  `docs/models/domain/other/DealActionState.md` §«Поисковые индексы»
  (довод «отбор идёт префиксом этого индекса»).
- `internal_id` — `updatable = false` (неизменен после создания).
- **`bills_window_begin` — write-once условным `UPDATE`, не
  `updatable = false`**: строка `deals` создаётся раньше, чем
  наблюдается факт границы. Guard — `where bills_window_begin is null`
  в обновлении. Разбор — §«Почему у нижней границы один писатель».
- **`planned_risk_equity_base` — write-once тем же механизмом**: guard
  `where planned_risk_equity_base is null`. Строка `deals` создаётся
  раньше первого сайзинга, поэтому `updatable = false` сделал бы колонку
  незаписываемой; guard охраняет не конкуренцию писателей (он один —
  `CreateOrderExecutor`), а вторую и последующие ноги входа: базу
  задаёт **первый** сайзинг сделки (§«База процента риска»).
- **`bills_window_end` — не write-once, а монотонное вперёд**: guard
  `where bills_window_end is null or bills_window_end < :uTime`. Число
  наблюдений равно числу закрывшихся эпизодов, и граница обязана
  накрывать движения всех (§«Верхняя граница монотонна, а не
  write-once»). Форма guard'а — та же, что у `bills_fetched_through`;
  разница только в операнде.
- **`bills_fetched_through` — не write-once, а монотонное вперёд**:
  guard `where bills_fetched_through is null or bills_fetched_through
  < :tSource` (`:tSource` — серверное время источника прохода). Поле по
  природе движется — оно фиксирует прогресс добычи, а не однократно
  наблюдённый факт (§«Добыча движений — durable-факт»).
- Enum-поля (`status`, `direction`, `entry_reason`, `entry_step_type`,
  `shutdown_reason`, `close_reason`, `close_outcome`,
  `reconciliation_status`, `breakdown_incomplete`,
  `risk_benchmark_availability`) хранятся строкой (имя enum); enum —
  только в домене (codestyle: enum'ы — в доменном слое).

Ключевые индексы/constraints (миграция
`V9__create_deal_finalization_states.sql`):

- **`uk_deal_active_instrument`** — частичный уникальный индекс
  `on deals (instrument_id) where status not in ('CLOSED',
  'EMERGENCY_CLOSED')`. DB-уровень инварианта «одна незакрытая сделка
  на инструмент» — **defense-in-depth** к app-gatekeeper'у
  (`EntryScannerJob`/`DealOpeningService`; см.
  `docs/rules/trading-constraints.md`). Предикат «активная/незакрытая»
  = любой `Status` **кроме** `CLOSED` и `EMERGENCY_CLOSED`:
  `PRECHECK`, `ENTRY_SUBMITTED`, `ENTRY_FINALIZED`,
  `PROTECTION_SWITCHED`, `MANAGING`, `EXIT_PENDING` **и `ERROR`**
  считаются активными — сделка в `ERROR` всё ещё блокирует новую
  сделку по инструменту, пока не дойдёт до терминала.
- **`ix_deal_status`** `on deals (status)` — support-индекс под горячую
  выборку активных сделок за проход оркестратора
  (`DealOrchestratorJob`). **Снимается миграцией шага 7**: его роль
  принимает префикс индекса отбора (`status`, `close_outcome`).
- **`ix_deal_instrument_status`** `on deals (instrument_id, status)` —
  support-индекс под gatekeeper входа по инструменту
  (`EntryScannerJob`/`DealOpeningService`). Таблица `deals` не пруним —
  индексы по `status`/`instrument_id` держат выборку активных дешёвой
  по мере роста истории закрытых сделок.
- **Benign insert-race:** вставку новой сделки `EntryScannerJob` делает
  в try/catch — конкурентная вставка, нарушающая
  `uk_deal_active_instrument`, ловится как benign skip (лог по
  инструменту, не фатальная ошибка прохода). Гонку между двумя
  проходами закрывает DB-инвариант, приложение её не эскалирует.

## Границы с DealActionState / DealContext

- `DealActionState` **не** поле `Deal`: persisted строка **исполнения
  действия** (оба вида — STRATEGY и SYSTEM; recovery/retry/idempotency,
  для STRATEGY — связь `StrategyAction → runtime target`). Связь:
  `Deal.id → DealActionState.dealId → strategyActionId | systemActionType
  → (targetEntityType, targetEntityId)`.
- `DealContext` **не** часть модели `Deal`: процессный runtime-context
  одного прохода FSM (добавляет `Exchange`, `Instrument`, pinned
  `StrategyDetail`, последний persisted `BalanceContainer`, список строк
  исполнений).

Полные модели — `docs/models/domain/other/DealActionState.md`,
`docs/components/models/DealContext.md`; FSM-handlers (материализованы) —
`docs/components/` (`PrecheckHandler` … `ErrorHandler`,
`.claude/decisions/fsm-handler-as-component.md`); правила сборки —
`docs/processes/deal-management.md`.
