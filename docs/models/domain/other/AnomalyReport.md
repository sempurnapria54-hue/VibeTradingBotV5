# AnomalyReport

## На какой вопрос отвечает этот файл

Что это за модель `AnomalyReport`: структура, енумы, инварианты,
персистентность.

Статусы и переходы — в `docs/lifecycles/AnomalyReport.md`.

## Назначение

`AnomalyReport` — доменная модель для фиксации, сопровождения и
аудита аномалий, обнаруженных при сравнении локального состояния
системы и фактического состояния на бирже. Это **не** валидатор и
**не** команда, а журналируемый объект расследования и обработки
инцидента (поэтому — `docs/models/domain/other/`, а не `core`: модель не про
бизнес-цикл сделки, а про аудит/расследование инцидента, см.
`.claude/decisions/models-core-vs-other.md`).

## Структура

Java-модель, наследует поля аудита от `Auditable`.

| Поле | Тип | Обязательно | Назначение |
|---|---|---|---|
| `id` | `Long` | да | Внутренний идентификатор отчёта. |
| `internalId` | `String` | да | Межсервисный идентификатор отчёта. |
| `exchangeId` | `Long` | да | Биржа, на которой обнаружена аномалия. |
| `instrumentId` | `Long` | нет | Инструмент; `null`, если однозначно не определён. |
| `scope` | `HoldScope` | да | **Радиус** инцидента: `INSTRUMENT` / `INSTRUMENT_GROUP` / `EXCHANGE`; снимает неоднозначность `instrumentId = null`. Ярлыки уровня (L3/L4) с енума сняты — уровень живёт в error-политике, одному уровню отвечают разные радиусы (H6 `GAPS_CLOSE_5`, реконсилировано здесь H4 `GAPS_CLOSE_6`). Общий enum с `HoldSignal` (дом — `docs/components/models/HoldSignal.md`). |
| `status` | `Status` | да | Текущий статус обработки (см. lifecycle). |
| `severity` | `Severity` | да | Критичность аномалии. |

| `externalAfter` | `String` (jsonb) | нет | Снимок внешнего состояния (биржа) после обработки. |

## Енумы

### `Status`
`CREATED`, `IN_PROGRESS`, `KILL_SWITCH_EXECUTED`, `COMPLETED`,
`ERROR`. Значения, переходы и какие поля заполняются на каждом шаге —
в `docs/lifecycles/AnomalyReport.md`.

### `Severity`

**Одна сущность, две тропы обработки; разводит их `severity`** (H6,
`GAPS_CLOSE_6`). Отдельной «журнальной» сущности не заводим: аудит-аномалия
и инцидент реактивной обработки — один объект расследования, различается
**поведение**, а не онтология.

- `CRITICAL` — критичная аномалия: реактивный контур **гоняет kill-switch**
  (`docs/components/SafetyHoldCoordinator.md`), отчёт проходит
  `KILL_SWITCH_EXECUTED` и терминализуется только по подтверждённому
  снятию риска.
- `NON_CRITICAL` — некритичная: kill-switch **не гоняется**, процесс
  завершается **штатно** (`CREATED → COMPLETED` для журнальной аномалии,
  либо через `IN_PROGRESS`, если обработка есть). Типичные производители —
  сверка bills↔net и cross-ccy на финализации, несвежесть ставки/ключа
  группы, пометка «неисчислимо» на аварийном терминале.

**Severity не задаёт блокировку торговли.** Она отвечает **только** на
«отрабатывает ли kill-switch». Блокировку задаёт **состав реакции**
error-политики (`docs/rules/error-handling-policy.md` §«Перечень scope и
реакций»), а несёт её **статус scope** (`Instrument.Status.TRADE_BLOCKED` /
`ENTRY_BLOCKED`, `docs/rules/instrument-hold.md` §Enforcement). Прежняя
формулировка («`CRITICAL` → торговля остаётся запрещённой; `NON_CRITICAL` →
после kill-switch может быть разрешена») выводила блокировку из severity и
описывала обе ветки в kill-switch-терминах — снята: `NON_CRITICAL`-тропа
kill-switch не проходит вовсе, а мягкий холд ставится при
`NON_CRITICAL`-аномалии и снимается вручную.

## Инварианты структуры

- `exchangeId` обязателен — каждая аномалия относится к конкретной
  бирже.
- `instrumentId` nullable — аномалия может относиться к внешней
  сущности, для которой локальный инструмент не определён.
- `scope` (`HoldScope`: `INSTRUMENT` / `INSTRUMENT_GROUP` / `EXCHANGE`)
  явно кодирует **радиус** инцидента и снимает неоднозначность
  `instrumentId = null` — которая **трёхзначна**: биржа-широкий радиус vs
  радиус комиссионной группы vs неопределённый инструмент. Ровно поэтому
  групповой радиус получил своё значение енума, а не выражается через
  `INSTRUMENT` + перечень в слепке (H4, `GAPS_CLOSE_6`). Enum общий с
  `HoldSignal` (сигнал из прохода) — дом енума
  `docs/components/models/HoldSignal.md`.
- **Одна аномалия — один отчёт на факт, не на инструмент.** Инцидент
  «строка ставки / ключ группы протухли» относится к **группе**: отчёт
  один, `scope = INSTRUMENT_GROUP`, `instrumentId = null`, идентификация
  группы — в `code` и слепке. N отчётов на N инструментов группы
  задваивали бы один факт.
- **Анкер идемпотентности — незакрытый отчёт по ключу (`exchangeId`,
  `instrumentId`, `scope`, `severity`)** (H15 `DOCS_CHECK_9`, решение
  пользователя; ревизует тройку H19 `GAPS_CLOSE_7` — прежний ключ включал
  `code` и «ключ группы», которого в колонках нет, и потому был
  **невыразим на схеме**). Производитель заводит отчёт, только если по
  этому ключу **нет отчёта в незавершённом статусе**
  (`CREATED`/`IN_PROGRESS`/`KILL_SWITCH_EXECUTED`); иначе факт уже
  зафиксирован и расследуется.
  - **Выражается на уровне БД** — частичный уникальный индекс по
    незакрытым статусам (§Персистентность): все операнды ключа — уже
    существующие колонки, **отдельная колонка-якорь не нужна**. Это
    снимает исходную находку (app-проверка «существует ли уже» против
    правила «уникальность — на уровне БД»,
    `docs/rules/idempotency-via-unique.md`).
  - **Что это закрывает.** У мягкой тропы условие «возраст факта > порога»
    остаётся истинным **до ручного снятия холда**
    (`docs/rules/instrument-hold.md` §Снятие), а синк тикает раз в час ⇒ без
    анкера инвариант «один отчёт на факт» нарушался бы каждым тиком, и
    журнал расследования тонул бы в копиях. У реактивной тропы анкер уже
    есть — «scope уже в `TRADE_BLOCKED`»
    (`docs/components/SafetyHoldCoordinator.md`); мягкая осталась без
    парного.
  - **Почему не «анкер = факт перехода статуса».** При радиусе «аккаунт»
    переходов N (по числу инструментов контура), а факт — один; анкер на
    переходе снова дал бы N отчётов. Ключ со `scope` держит инвариант
    **при любом радиусе** — это и есть довод выбора.
  - **Почему не «отчёт при постановке + периодическое ещё-держится».**
    Периодическое напоминание — это уже мониторинг, отдельная ось; вводить
    его ради идемпотентности значит решать не ту задачу. Если напоминание
    понадобится, оно ляжет поверх анкера, а не вместо него.
  - **Хвост — как scope влияет на перекрытие** (два незакрытых факта
    разных `code` на одном ключе; `instrumentId = null` у групповых
    радиусов в частичном уникальном индексе) — отнесён к **следующему
    шагу** (шаг 8, AnomalyJob; `.claude/work/backlog.md` §Шаг 8).
- `severity` и `code` — независимые измерения: `severity` —
  уровень опасности, `code` — конкретный тип аномалии.
- `message` заполняется только одновременно с `status = ERROR`,
  содержит текст непредвиденной ошибки обработки (техническое поле,
  не бизнес-описание аномалии).

## Производящая поверхность и коды шага 7

**Поверхность создания — две, по природе производителя** (H23,
`GAPS_CLOSE_7`). Существующая точка входа рассчитана только на реактивную
тропу: она принимает `DealContext` (откуда берёт `instrumentId`) и жёстко
ставит `Severity.CRITICAL`. Производители шага 7 в неё не проходят:
сверка/cross-ccy/«неисчислимо» дают `NON_CRITICAL`, а у
`InstrumentExternalRulesSyncJob` `DealContext` **нет вовсе** — он работает
вне сделки.

| Поверхность | Кто зовёт | Что задаёт |
|---|---|---|
| Реактивная (существующая) | `SafetyHoldCoordinator`, `AnomalyJob` | `DealContext` + `HoldSignal`; `severity = CRITICAL` |
| Журнальная (вводится шагом 7) | `FinalizeDealExitExecutor`, `RefreshBillsExecutor`, `MarkDealEmergencyClosedExecutor`, `InstrumentExternalRulesSyncJob` | `exchangeId`, `scope`, опц. `instrumentId`, `code`, `severity = NON_CRITICAL`, слепки |

Журнальная поверхность **не требует `DealContext`** и severity не
захардкоживает — иначе `INSTRUMENT_GROUP`-радиус (несвежесть) выразить
нечем: у него нет ни сделки, ни одного инструмента. `HoldSignal`-фабрик под
`INSTRUMENT_GROUP` не заводится: сигнал — объект **реактивного** прохода
над сделкой, а журнальная тропа проходом не порождена.

**Реестр кодов шага 7** (`code` обязателен — до сих пор ни одного значения
для `NON_CRITICAL` объявлено не было):

| `code` | Производитель | Факт | `scope` |
|---|---|---|---|
| `PNL_RECONCILIATION_MISMATCH` | `FinalizeDealExitExecutor` | Σ`amount` строк расчётной валюты разошлась с net сверх epsilon | `INSTRUMENT` |
| `SETTLE_CURRENCY_VIOLATION` | `RefreshBillsExecutor` | движение в валюте, отличной от расчётной валюты инструмента | `INSTRUMENT` |
| `RESULT_PROFIT_UNAVAILABLE` | `MarkDealEmergencyClosedExecutor` | число на аварийном терминале «неисчислимо» (`null`) | `INSTRUMENT` |
| `FEE_RATE_STALE` | `InstrumentExternalRulesSyncJob` | возраст строки ставки группы > порога | `INSTRUMENT_GROUP` |
| `FEE_GROUP_KEY_STALE` | `InstrumentExternalRulesSyncJob` | возраст ключа группы на инструменте > порога | `INSTRUMENT_GROUP` / `EXCHANGE` (по радиусу отказа) |

В ключ анкера идемпотентности `code` **не входит** (H15 `DOCS_CHECK_9`
— ключ собран из колонок: `exchangeId`, `instrumentId`, `scope`,
`severity`; §Инварианты структуры): повторный тик по тому же факту
нового отчёта не заводит; перекрытие разных `code` на одном ключе —
хвост следующего шага.

## Связи

- **Exchange** — биржа, на которой обнаружена аномалия (`exchangeId`).
- **Instrument** — инструмент аномалии (`instrumentId`, опционально).

## Персистентность

**Анкер идемпотентности — на уровне БД** (H15 `DOCS_CHECK_9`):
частичный уникальный индекс по (`exchange_id`, `instrument_id`,
`scope`, `severity`) `where status in ('CREATED', 'IN_PROGRESS',
'KILL_SWITCH_EXECUTED')` — «не более одного незакрытого отчёта на факт»;
отдельной колонки-якоря нет, операнды ключа — существующие колонки
(`docs/rules/idempotency-via-unique.md`,
`docs/rules/persistence-representation.md`). Индекс — миграцией шага 7
(в `V10` его нет). Семантика NULL `instrument_id` у групповых радиусов и
перекрытие разных `code` на одном ключе — хвост следующего шага
(§Инварианты структуры).

Четыре поля `internalBefore` / `externalBefore` / `internalAfter` /
`externalAfter` хранятся в jsonb; в один столбец попадают разнородные
доменные объекты.

- **Локальные снимки** (`internalBefore`, `internalAfter`) —
  доменные модели из БД: активные `Deal`; активные `Position`;
  pending `Order`; pending/active `AlgoOrder`; статус инструмента;
  связанные служебные идентификаторы.
- **Внешние снимки** (`externalBefore`, `externalAfter`) — данные с
  биржи: активные позиции; pending orders; active algo orders;
  сущности, найденные по идентификаторам из БД; orphan-сущности
  (найденные на бирже без соответствия в БД).

Конкретная сериализация (формат, версионирование) — отдельная задача
(стандарт описания персистентности доменных моделей; форвард-заметка
в task-вопросах).

## Чего не хранит

- `dealId` — контекст сделки попадает в `internalBefore`/
  `internalAfter`.
- `tradingBlocked` — блокировка торговли живёт в статусе инструмента.
- Boolean-флаги по шагам обработки — прогресс отражён через `status`.
