# DealActionState

## На какой вопрос отвечает этот файл

Что это за модель `DealActionState` — строка исполнения действия.

## Назначение

`DealActionState` — операционная запись **одного исполнения действия** в
рамках транша (для системных действий уровня сделки — в рамках сделки).
Отвечает на вопрос «на каком шаге это исполнение и какую runtime-сущность
оно затрагивает». Несёт идемпотентность, восстановление и бюджет попыток.

**Строка = исполнение, не действие.** Действие стратегии исполняется
многократно — переоткрытый эпизод транша, одно объявление,
материализованное N траншами сетки, параллельные заявки в полёте;
системные действия повторяются циклами добычи. Идентичность исполнения —
суррогатный ключ.

**Повторного срабатывания шага на одном эпизоде среди этих троп нет:**
шаг стратегии применяется на эпизоде транша однократно, и признаком
«применён» служат ровно эти строки, отобранные **номером эпизода**
(`trancheEpisodeSeq`) и статусом (дом правила —
`docs/rules/strategy-step-once-per-episode.md`). Многократность здесь —
про **разные** эпизоды, транши и попытки, не про повтор той же ступени
лестницы.

Строки исполнений **копятся**: завершённое состояние жёстко терминально,
слот не переиспользуется.

`DealActionState` — **единственный держатель связи «действие стратегии —
runtime-сущность»**: заявки и позиции ссылок на действие не хранят.

**Строка исполнения защитного действия служит обязательством
покрытия** — durable-фактом «мы сейчас это устанавливаем»
(`docs/rules/live-risk-protection.md`).

## Структура

Наследует состояние повторов и поля аудита.

| Поле | Тип | Обязательно | Назначение |
|---|---|---|---|
| `id` | `Long` | да | Идентичность исполнения. |
| `dealId` | `Long` | да | Сделка-агрегат. |
| `dealTrancheId` | `Long` | у **потраншевых** — и стратегийных, и системных | Транш, чьё действие исполняется. Пусто у исполнений **уровня сделки**, и они бывают обоих родов: у системных — агрегатный тип действия, у стратегийных — узел агрегатной поверхности (`EXIT` и `FAIL_SAFE` уровня сделки, `docs/models/domain/aggregate/Strategy.md`). Дискриминатор «пусто законно» — **уровень объявления**, а не род строки: тип системного действия либо уровень узла стратегии. |
| `actionKind` | `ActionKind` | да | Вид действия. **В схему не персистится** — вид кодируется таблицей. |
| `strategyActionId` | `Long` | у стратегийных | Узел стратегии, чьё исполнение отслеживается. |
| `systemActionType` | `SystemActionType` | у системных | Тип системного действия. |
| `targetEntityType` | `TargetEntityType` | нет | Тип runtime-сущности. Колонка, а не JSONB: операнд ключа уникальности. |
| `targetEntityId` | `Long` | нет | Идентификатор этой сущности; пусто, пока она не создана. |
| `trancheEpisodeSeq` | `Integer` | у потраншевых | Номер эпизода транша на момент заведения строки (`DealTranche.episodeSeq`). Пишет тот, кто заводит строку, той же транзакцией. Операнд области «эпизод»: без него строки прошлого эпизода неотличимы от строк текущего, потому что переоткрытие идёт **тем же** траншем и `dealTrancheId` не меняется. |
| `status` | `DealActionStateStatus` | да | Статус исполнения. |

**Поля повторов:** счётчик попыток, снимок предела, время следующей
попытки, последняя ошибка.

**Счётчик — сквозной бюджет отказов одного исполнения**, без обнуления
при продвижении стадии; **предел** читается живьём по типу текущей
команды.

**Стадия исполнения выводится из подтверждённых фактов и полем не
хранится:** явная стадия дублировала бы факты и протухала на рестарте.
Курсора пройденных звеньев нет.

## Енумы

**`ActionKind`** — `STRATEGY`, `SYSTEM`.

**`SystemActionType`:**

| Значение | Что делает |
|---|---|
| `REFRESH_DEAL_CONTEXT_ACTION` | добыча свежих фактов с биржи; дочистка звеном не является |
| `FINALIZE_DEAL_ENTRY_ACTION` | консолидация результата входа **транша**; завершение пишет статус подтверждённого входа транша той же транзакцией. **Потраншевое** — единственное системное действие с непустым траншем |
| `FINALIZE_DEAL_EXIT_ACTION` | число и чистый терминал |
| `FINALIZE_DEAL_ERROR_ACTION` | аварийная тропа; вход в ошибку и терминал — два отдельных исполнения |

**`DealActionStateStatus`:**

| Значение | Что означает |
|---|---|
| `PLANNED` | исполнение выбрано, команды ещё не было |
| `CREATED` | локальная сущность создана, цель заполнена |
| `SUBMITTED` | отправлено на биржу, факт не подтверждён |
| `COMPLETED` | доведено, факты подтверждены. **Жёстко терминален** |
| `RETRY_PENDING` | звено упало на повторяемой ошибке, ждёт следующей попытки |
| `FAILED` | бюджет исчерпан либо ошибка неповторяема |
| `SKIPPED` | исполнение стало неактуальным |

**`CREATED` и `SUBMITTED` проходят не все.** Оба значения говорят о
внешнем следе — заведённой локальной сущности и отправке наружу. Звенья
трёх действий финализации ни того ни другого не производят и завершаются
прямым ребром из `PLANNED`; значения от этого не становятся лишними —
через них идут стратегийные исполнения и добыча
(`docs/lifecycles/DealActionState.md`).

**Мимо `CREATED` и `SUBMITTED` идут и неуспешные исходы этих звеньев.**
Упав или не завершившись, локальное звено уходит из `PLANNED` в
`RETRY_PENDING`, а по исчерпании бюджета — в `FAILED`: те же два значения,
что у прочих звеньев, и тот же счётчик попыток строки. Отдельного статуса
под «звено ждёт операнда» не заводится — ожидание от отказа отличает
бюджет.

**`TargetEntityType`** — `ORDER`, `ALGO_ORDER`, `POSITION`, `DEAL`
(цель системных действий), `BALANCE`, `NONE`.

## Замещение: две ноги, одна запись на ногу

Замещающее действие исполняется как надмножество создания: нога порождает
**новую** сущность с указателем на замещаемую, плюс отмена старой. Новых
статусов не требуется — следующая команда выводится из фактов.

Порядок ног — по риск-классу (`docs/rules/replace-not-amend.md`).
Замещаемая сущность резолвится по цепочке замещений от целевого действия.

## Инварианты

**Стратегийные и системные исполнения хранятся в двух таблицах**, у
каждой свои ключи: в стратегийной ссылка на узел обязательна, в
системной — тип системного действия. Общей таблицы с nullable-ссылкой и
частичными индексами по виду нет — вместе с nullable-колонкой исчезает и
неоднозначность ключа.

**Инвариант — про колонку рода действия, не про колонку транша.**
`deal_tranche_id` nullable в обеих таблицах, и это не тот же класс:
пустота там означает объявленный **уровень** действия (сделка вместо
транша), а не «неизвестно, какого рода строка». Различитель уровня
существует и обязателен в своей строке — тип системного действия либо
уровень узла стратегии, — поэтому «пусто законно» и «пусто по недосмотру»
различимы, а ключ однозначен.

**Ключи частичные, по живым статусам** — «уникальность среди живых»
(`docs/rules/idempotency-via-unique.md`). Завершённые строки ключ не
держат. У каждого ключа есть имя.

**Транш входит в состав ключа обеих таблиц — и стратегийной, и
системной, — ровно настолько, насколько действие потраншевое.** Одно
объявление действия, материализованное N траншами сетки, даёт N законных
живых исполнений; без транша в ключе они конфликтовали бы между собой, а
с ним уникальность остаётся ровно там, где нужна, — внутри одного транша.

**У системной таблицы.** `FINALIZE_DEAL_ENTRY_ACTION` консолидирует вход
**транша** и пишет его статус, поэтому N траншей сетки, консолидирующих
вход одновременно, дают N законных живых исполнений одного типа — ключ
`(deal_id, deal_tranche_id, system_action_type)`. Три остальных типа
агрегатные: у них транш пуст, и ключ вырождается в
`(deal_id, system_action_type)`.

**У стратегийной таблицы — симметрично.** Шаг стратегии принадлежит
траншу, кроме узкой агрегатной поверхности (`EXIT` и `FAIL_SAFE` уровня
сделки — `docs/models/domain/aggregate/Strategy.md`). У потраншевого шага
ключ — `(deal_id, deal_tranche_id, strategy_action_id)`; у агрегатного
транша нет ни одного, и ключ вырождается в
`(deal_id, strategy_action_id)`. Выбирать «носителем» один транш из N
нельзя: действие выхода — утверждение обо **всех** траншах сразу
(`docs/components/ExitActionExecutor.md`), и приписка его первому
попавшемуся дала бы правилу сопоставления закрытого объёма ложный якорь.

**Частичный ключ строится по живым статусам во всех четырёх случаях;
пустой транш в уникальности агрегатных исполнений участвует как пустой,
а не как разделитель.** Оговорка не косметическая: в Postgres `NULL` в
уникальном индексе не конфликтует сам с собой, поэтому индекс, собранный
буквально по трём колонкам, пропустил бы два живых исполнения одного
агрегатного действия. Форма индекса для агрегатных строк — по двум
колонкам с условием пустоты третьей, а не по трём.
