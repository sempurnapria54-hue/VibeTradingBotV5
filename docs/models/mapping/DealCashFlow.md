# DealCashFlow — mapping bills → домен

## На какой вопрос отвечает этот файл

Как OKX bill-записи ложатся на доменную `DealCashFlow`, как из `type`/`subType`
резолвится `CashFlowCategory`, какие поля валидируются.

## Mapping-flow

```text
bills REST -> raw OkxAccountBillResponse -> IntegrationService validation
  -> DealCashFlowMapper.integrationToSnapshot
  -> DealCashFlowExternalSnapshot (транзитный, за границу выходит он)
  -> RefreshBillsExecutor (резолв category / exchangeId / appliedRate /
     rateStatus / deal_id)
  -> DealCashFlowMapper.snapshotToDomain -> DealCashFlow (persist)
```

### `DealCashFlowExternalSnapshot` (транзитный)

Граничный объект цепочки bills. Как `TradeFeeRateExternalSnapshot` и
`PositionCloseResultExternalSnapshot`, **отдельного дока не требует** — нет
самостоятельного persisted содержания; состав фиксируется здесь:

| Snapshot field | Тип | Источник (OKX bill) |
|---|---|---|
| `externalBillId` | `String` | `billId` |
| `amount` | `BigDecimal` | `balChg` |
| `externalFee` | `BigDecimal` | `fee` |
| `ccy` | `String` | `ccy` |
| `externalType` | `String` | `type` |
| `externalSubType` | `String` | `subType` |
| `externalOrderId` | `String` | `ordId` |
| `externalInstrumentId` | `String` | `instId` |
| `externalCreatedAt` | `OffsetDateTime` | `ts` (epoch millis) |

**Чего в снапшоте нет и почему.** `category`, `exchangeId`, `appliedRate`,
`rateStatus`, `dealId` **и три координатных поля ссылки на свечу курса** — не факты **этого** ответа источника: их
производит вызывающий (резолвер категории, писатель, пересчёт курса,
матчинг к сделке; координаты свечи заполняет тот же пересчёт, из ответа
свечного эндпоинта). Именно
поэтому доменная модель за границу adapter'а выходить не может: её
обязательные поля (`exchangeId`, `category`, `rateStatus` — `NOT NULL` в
схеме) на этой точке ещё не заполнены, и наружу уходила бы недозаполненная
сущность.

**Многострочность и пагинация.** Метод границы возвращает
`List<DealCashFlowExternalSnapshot>` — прецедент списка снапшотов на
границе уже есть (`IntegrationService`); курсор пагинации `7d → 3m`
остаётся **внутри** команды и границу не пересекает
(`docs/components/RefreshBillsExecutor.md`).

Raw OKX DTO не выходит за пределы `IntegrationService` / adapter-layer
(`docs/rules/raw-exchange-dto-boundary.md`). Наполняется командой
`REFRESH_BILLS_COMMAND` (`RefreshBillsExecutor`): пагинация bills (7d → 3m archive)
внутри команды, матчинг к сделке и проставление `deal_id` — при сохранении
(`docs/models/domain/other/DealCashFlow.md` к `Deal`).

## OKX bill-поле → `DealCashFlow`-поле

| OKX field | DealCashFlow field |
|---|---|
| `balChg` | `amount` (строка → `BigDecimal`) |
| `fee` | `externalFee` (строка → `BigDecimal`; знаковая комиссионная компонента) |
| `ccy` | `ccy` |
| `ts` | `externalCreatedAt` (epoch millis → `OffsetDateTime`; конвенция `Auditable`, H25) |
| `billId` | `externalBillId` |
| `type` | `externalType` |
| `subType` | `externalSubType` |
| `ordId` | `externalOrderId` |
| `instId` | `externalInstrumentId` |

`category` **не** маппится напрямую — резолвится из `type`/`subType` (см.
ниже). `deal_id` проставляется матчингом, не маппером. `appliedRate` и
`rateStatus` источник не несёт вовсе — их проставляет
`RefreshBillsExecutor` при пересчёте cross-ccy-строки , маппер к ним не причастен. `exchangeId` — не поле источника:
его знает писатель, как знает синк `TradeFeeRate`.

**`instId` пишется в поле, а не только фильтрует**. Обоснование
опирается на **действующую** тропу линковки, а не на отложенную:

- **`instId` — ось предиката отбора при сохранении.** Линковка идёт по
  подвижной границе (`deal_id` проставляется при сохранении, предикат —
  `ts ≥ billsWindowBegin` при нетерминальном `Deal`;
  `docs/models/domain/aggregate/Deal.md`). Ответ
  `/account/bills` — **аккаунт-широкий**: он несёт движения всех
  инструментов аккаунта, и без инструментной оси предикат подобрал бы
  движение чужого инструмента, попавшее в то же временное окно.

### Разделение ролей `balChg` и `fee`

Два поля отвечают на **разные вопросы** и не подменяют друг друга:

- **`balChg` → `amount`** — вопрос «сходится ли сумма»: Σ`amount` сверяется с
  net из positions-history. Верен при **любой** гранулярности bills (Σ`balChg`
  = net независимо от того, комбинирует источник pnl и комиссию в одну запись
  или эмитит их раздельно).
- **`fee` → `externalFee`** — вопрос «сколько комиссии»: комиссионная
  компонента записи, взятая **явно**, а не выведенная из знака `balChg`.
  Комиссия сделки = Σ`externalFee` по её торговым движениям (область
  суммирования —).

**Под-случай, который посылку ломает — «fee-эхо».** Если источник эмитит
комиссию **отдельной** записью и **дублирует** её число информационным
полем `fee` на соседней pnl-записи (`balChg` = pnl без комиссии, но
`fee = −f` присутствует), то `f` попадает в Σ`externalFee` дважды, а
realized-слагаемое считается как `pnl − (−f) = pnl + f` вместо `pnl`.
Σ`amount` при этом **сходится** — сверка такой дефект **не видит**.
Фактическое поведение источника — рантайм-вопрос.5
(`.claude/tests/source-api/okx/plan.md`), его вопросник расширен
инспекцией `fee` **на pnl-записи**, а не только на fee-записи. Гейтом не
является: прогон.5/AG3.5 и так запланирован **до** `CODE`.

**Почему число комиссии — из native `fee`.** Вывод
комиссии из знака `balChg` верен только при гранулярности «отдельная
fee-запись на событие». При **комбинированной** записи (`balChg = pnl + fee`)
он кладёт весь `pnl + fee` в одну корзину: комиссия недосчитана, realized pnl
пересчитан — разбивка (единственный смысл `DealCashFlow`) искажена. Native
`fee` даёт компоненту **явно**, а не выведенной из знака. Суперсет безопасен
для **суммы-сверки** и **realized-слагаемого** при любой гранулярности —
**при условии, что пустой `externalFee` в разности трактуется нулём**. Для **суммы комиссии** суперсет безопасен
не был и не стал.
Фактическая гранулярность — рантайм-вопрос
(`.claude/tests/source-api/okx/plan.md` **.5**; фикстура общая с.5);
на маппинг ответ не влияет.
*Суперсет — про **число**; **категорию** он не определяет — она резолвится по
типу операции (, H9).*

### Знак `externalFee` — сырой, нормализации нет

`externalFee` переносится **со знаком источника** (минус = комиссия, плюс =
ребейт), без `× −1` и без `abs`. Это **сознательная асимметрия** с прогнозной
ставкой `TradeFeeRate`, где знак снимается при маппинге
(`docs/models/domain/other/TradeFeeRate.md`, H2):

- **ставка** — прогноз, попадающий в **формулу риска** (`+ commissions`); там
  нужна проектная нормаль «издержка», иначе знак источника молча ломает
  сайзинг;
- **`externalFee`** — **факт** движения, участвующий в **арифметике
  композиции**: realized-слагаемое = `amount` − `externalFee` даёт
  `(pnl + fee) − fee = pnl` **только** на знаковом `fee`. Нормализуй его — и
  разложение комбинированной записи сломается.

Разные роли — разные конвенции. Помечено явно, чтобы следующий проход не
«выровнял» одно по другому: одинаковыми они выглядят только по имени.

**Компонента, не отдельная строка.** `fee` едет **полем на той же строке**, а
не синтетической второй `DealCashFlow`: ключ идемпотентности —
`UNIQUE(exchange_id, external_bill_id)` (одна строка на bill-запись,
`docs/models/domain/other/DealCashFlow.md`), а разложение
комбинированной записи на две строки и задвоило бы её в Σ`amount` (сломав
сверку), и не имело бы второго `billId` под ключ. Отсюда же следствие: при
комбинированной записи realized-pnl-слагаемое разбивки = `amount` −
`externalFee` (native `pnl` отдельным носителем не требуется —
`docs/models/integrations/okx/OkxAccountBillResponse.md`).

## Резолв категории

**Ось резолва — тип операции, а не знак числа**.
`CashFlowCategory` резолвится **только** из `type`/`subType` bill-записи:
категория отвечает на вопрос «**что это было за событие**», а на него отвечает
источник своим типом операции — не арифметика знака.

| Что за событие (`type`/`subType`) | Категория |
|---|---|
| funding-платёж: `subType` `173` (expense) / `174` (income) | `FUNDING` |
| торговое движение (исполнение ордера, закрытие/частичное закрытие позиции) | `REALIZED_PNL` |
| отдельная запись списания торговой комиссии | `TRADE_FEE` |
| отдельная запись возврата/скидки комиссии | `REBATE` |
| запись ликвидационного штрафа | `LIQ_PENALTY` |
| не отнесённое к перечисленному | `OTHER` |

`LIQ_PENALTY`: само число `liqPenalty` в net берётся из positions-history (не
bills); в `DealCashFlow` категория попадает **как факт bill-записи
ликвидации**, если она присутствует в окне.

**Резолв категории — в вызывающем коде, не в маппере** (codestyle:
маппер делает только перенос данных, доменных решений — интерпретации
`type`/`subType` в категорию — не принимает). Актуальный перечень
`type`/`subType` — справочник OKX (`GET /api/v5/account/subtypes`,
`docs/integrations/okx/contracts/account-bills.md`), **не хардкод**: конкретные
числовые значения `type` в этот док не переписываются, кроме funding-подтипов
`173`/`174`, на которых завязана отдельная ветка.

**Носитель отображения — тот же per-exchange `@ConfigurationProperties`,
что у списка исключений**. Таблица выше отвечает на
вопрос «**что** считать какой категорией» на языке событий; **чем** это
выражается в значениях источника — конфигурируемое отображение
`type`/`subType` → `CashFlowCategory`, живущее рядом со списком исключений
, с непустым
стартовым набором в конфиге по умолчанию.

- **Почему тот же носитель, а не второй.** Обе таблицы — про **значения
  источника**, обе меняются по мере наблюдения за биржей и обе обязаны
  править́ся **без релиза**; ключ по бирже нужен обеим. Заводить второй
  носитель того же класса запрещает `.claude/rules/design-simplicity.md`.
- **Поведение при новом `type` не меняется:** значение, которого нет в
  отображении, попадает в `OTHER` и **звенит** `UNCLASSIFIED_CASH_FLOW` —
  ровно как задумано списком-от-противного. Отображение — не allow-list
  экономики (её границу по-прежнему задают **исключения**), а
  расшифровка «какое событие стоит за значением».
- **Содержание отображения для OKX — хэнд-офф `integrator`**, предусловие
  `CODE` п. 16 (`docs/rules/pnl-reconciliation.md`). Грунт
  добывается тем же кейсом `AG6`, что и список исключений; наблюдение
  прошлого прогона содержания не сохранило — см.
  `.claude/work/backlog.md`.

## Область суммирования — задаётся явно

Категория задаёт не только атрибуцию, но и **что по чему складывать**. **Шесть** сумм, шесть разных областей. **Области адресуются именами, не номерами**: порядковая адресация («четвёртая область») отстаёт при
каждом пересчёте реестра, имя — нет; номера остаются только у **пар**
сверки, чей состав фиксирован тождеством net'а:

| Сумма | Область | Зачем |
|---|---|---|
| комиссия сделки = Σ`externalFee` | строки **торговых** категорий (`REALIZED_PNL` / `TRADE_FEE` / `REBATE`) **в settle-ccy**, за вычетом **исключённых типов**  | левый операнд **второй** пары сверки (против `fee`) |
| realized-pnl-слагаемое = Σ(`amount` − `externalFee`) | **только** строки `REALIZED_PNL` **в settle-ccy**, за вычетом **исключённых типов**  | левый операнд **первой** пары (против `pnl`) |
| funding-слагаемое = Σ`amount` | **только** строки `FUNDING` **в settle-ccy**, за вычетом **исключённых типов**  | левый операнд **третьей** пары (против `−externalFundingCost`) |
| штраф-слагаемое = Σ`amount` | **только** строки `LIQ_PENALTY` **в settle-ccy**, за вычетом **исключённых типов**  | левый операнд **четвёртой** пары |
| cross-ccy-слагаемое = Σ(`amount` × `appliedRate`) | строки, у которых **`rateStatus = APPLIED`** **и** тип **вне списка исключений** **и** категория **экономическая** (не `OTHER`) | довнести в число издержку, уплаченную вне settle-ccy |
| композиционный член допуска = Σ`\|amount\|` | строки **в settle-ccy**, **вне списка исключений** **и** категории **экономической** (не `OTHER`) — то есть **объединение областей четырёх пар** | правая часть относительного члена `epsilon` (`docs/rules/pnl-reconciliation.md` — дом политики). Однородность покрытия с левой частью (`Δ = Σ\|Δᵢ\|` по четырём парам) — сам довод выбора области |

**Общей Σ`amount` по всей разбивке в реестре больше нет**. Суммарная сверка с net заменена четырьмя раздельными
парами ещё решением, которое их вводило, а четвёртая пара довела покрытие
до полного состава net'а (`realizedPnl = pnl + fee + fundingFee +
liqPenalty`); отдельная сумма по всей разбивке ничего сверх них не
проверяет, а её область шире net'а на строки, которых в net'е нет.

**Cross-ccy-область — единственная, которая число
формирует, а не проверяет**, поэтому её предикат ограничен так же строго,
как у проверяющих: одного `rateStatus` мало. Любая
прилинкованная строка в чужой валюте вне экономики сделки (перевод,
движение маржи, нераспознанный тип в корзине `OTHER`) при полученной
котировке иначе попала бы прямо в числитель `R` — и не была бы поймана ни
одной парой, потому что в settle-ccy её нет по построению.

**Валютная оговорка на первых четырёх суммах — несущая, не педантизм**
(H5). Складывать `amount` разных валют нельзя: сумма перестала бы быть числом
в одной валюте, а сверка — сверкой. Поэтому чужая `ccy` вынесена в
**отдельную cross-ccy-область** и входит в число только после пересчёта
.

**`FUNDING`-строки исключены** из комиссионной и realized-pnl областей — и
это несущее уточнение, а
не педантизм. Формула «realized-pnl-слагаемое = `amount` − `externalFee`»
 без области суммирования применялась бы **ко всем**
строкам и **втянула бы funding в realized pnl**: funding-движение несёт
`amount` и не несёт `externalFee` ⇒ его сумма целиком попала бы в
realized-слагаемое. Funding — **holding-cost**, живёт своей категорией и в
realized pnl не входит (разделяющий довод — `per-trade-risk-policy.md`, N13). Своя область у него **есть** — funding-область реестра,
левый операнд третьей пары; то же у `LIQ_PENALTY`.

**Категории и области соответствуют один-к-одному не полностью, и это
намеренно:** `REALIZED_PNL` участвует в двух областях (в своём слагаемом
целиком и комиссионной частью — в комиссионной сумме), потому что несёт
оба факта одной строкой. Сверка от этого не двоится: слагаемые считаются
по разным полям (`amount` − `externalFee` против `externalFee`).

### Область сверки задаётся списком **исключений** по бирже (H14 `DOCS_CHECK_10`)

**Проблема.** Предикат линковки — «`ts` ∈ окно» + «`instId` == инструмент
сделки»; `type` в запрос не идёт вовсе, а `OTHER` — принимающая корзина,
которая **входит** в сумму-сверку. Какие движения принадлежат экономике
сделки, не было определено. Для isolated-маржи на SWAP это не гипотетика:
движения маржи по позиции несут `instId` и сопоставимы по величине с самой
позицией; native-док прямо свидетельствует, что bills несут не только
торговые движения (`posBalChg`, `posBal`, `from`/`to` — в отброшенных).
Посторонние движения раздувают Σ`|amount|`, поднимают собственный допуск
сверки и глушат настоящие пропуски — контроль, срабатывающий на каждой
сделке, эквивалентен погашенному.

**Решение пользователя: линковать всё, область сверки задать явно — списком
того, что *исключается*, конфигурируемым по бирже.**

- **Линковка не сужается.** Все движения по окну + `instId` персистятся и
  получают `deal_id` — принцип «запись не теряется», ради которого убрали
  фильтр `ccy`, сохранён.
- **Область сверки = все залинкованные строки settle-ccy минус
  исключённые типы.** Список исключений — перечень `type`/`subType`
  источника, **не принадлежащих экономике сделки** (переводы между
  счетами, добавление/снятие маржи и т. п.).
- **Список — от противного, и это несущее свойство.** Allow-list
  (перечислить включаемое) отвергнут: он фиксирует числовые `type`
  источника, чего док запретил, и **новый тип от биржи выпадал бы молча**
  — болезнь мёртвого `ccy`-фильтра. При списке исключений новый тип по
  умолчанию **попадает в расчёт**, и если он посторонний, обнаруживается
  сам — через непустую корзину `OTHER`.
- **Непустой `OTHER` сам по себе даёт `AnomalyReport`** — код
  `UNCLASSIFIED_CASH_FLOW` (`severity = NON_CRITICAL`, ставит финализатор;
  `docs/models/domain/other/AnomalyReport.md`). Корзина
  «прочее» перестаёт быть молчаливой: она либо пуста, либо звенит.
- **Конфигурируется по бирже.** Перечень посторонних типов — свойство
  источника, не системы: у другой биржи он другой.
  **Дом конфига — `@ConfigurationProperties` per-exchange**. Перечень меняется **без релиза**:
  состав посторонних `type`/`subType` уточняется по мере наблюдения за
  источником, и при неполном списке контроль целостности числа искажён —
  ждать релиза под каждое уточнение нельзя. Ключ — по бирже, чтобы вторая
  площадка не наследовала чужой список; **непустой стартовый набор лежит в
  конфиге по умолчанию** (иначе предусловие п. 2 не выполняется при первом
  запуске). Названная цена: значение живёт вне репозитория и не
  версионируется вместе с кодом. Отвергнуты константы adapter'а (правка
  требует релиза) и реляционный носитель на `exchanges` (связность
  максимальная — состав области сверки становится данными). Разбор и
  строка не-схемной дельты —
  `docs/rules/pnl-reconciliation.md`
  п. 12 и.
  > **Хэнд-офф `integrator` остаётся — но только по содержанию:** чем
  > перечень наполняется для OKX (предусловие `CODE` п. 2,
  > `.claude/work/backlog.md` 7). Структурная половина вопроса
  > закрыта.

**Что это меняет у epsilon.** Исключённые типы не входят в Σ`|amount|` ⇒
допуск больше не раздувается посторонним оборотом (сцепление с H15 —).

## Validation (структурная, до маппинга)

В `IntegrationService` OKX:

- **`billId` присутствует** — половина ключа дедупа/идемпотентности; движение
  без `billId` не сохраняется.
- **`ccy` присутствует** — обязательно, иначе cross-ccy движение теряется
  молча при сверке (`pnl-finalization-mechanics.md` реш.5).
- **`ts` присутствует и парсится**: обязательность `externalCreatedAt` обеспечивается
  **здесь, на границе разбора**, а не `NOT NULL`-колонкой — audit-колонки
  приходят из общего `AuditableEntity`, часть наследников которого
  БД-first, поэтому `NOT NULL` на них невозможен в принципе. Пустой `ts`
  делает строку невыбираемой оконным предикатом и молча выпадающей из
  суммы-сверки — класс отказа, ради наблюдаемости которого введён
  омиссионный член epsilon; поэтому запись с отсутствующим или
  непарсящимся `ts` до персиста не доходит.
- **`type` присутствует** — `external_type`
  объявлен `NOT NULL` и служит осью резолва `category` (тоже
  `NOT NULL`), а конвенции «пустое значение по природе поля» у bills, в
  отличие от positions-history, нет. Без проверки на границе пустой
  `type` давал бы не контролируемый реджект, а падение вставки на
  constraint **внутри транзакции звена**. Достижимость низкая (OKX
  штатно отдаёт `type`), но ровно то же верно для `billId` и `ccy`,
  которые валидируются с явно названными доводами.
- **`balChg` parseable numeric** — числа приходят строками, `amount`
  парсится в `BigDecimal`; пустая/непарсящаяся строка недопустима.

## Сверка и cross-ccy

**Сверка — раздельная по категориям**. Суммы разбивки **по строкам settle-ccy вне списка
исключений** сверяются с **четырьмя** числами той же записи positions-history:

| Слагаемое разбивки | Против числа биржи |
|---|---|
| Σ(`amount` − `externalFee`) по `REALIZED_PNL` | `pnl` |
| Σ`externalFee` по торговым категориям | `fee` |
| Σ`amount` по `FUNDING` | `−externalFundingCost` |
| Σ`amount` по `LIQ_PENALTY` | `externalLiquidationPenalty` |

**Правые операнды всех четырёх пар суммируются по эпизодам сделки**
(`docs/models/domain/aggregate/Deal.md`): у многоэпизодной сделки записей
закрытия столько, сколько эпизодов, а окно линковки bills накрывает их
все — иначе левая и правая стороны сверки имели бы разное покрытие и
сверка звенела бы по построению.

**Исход расхождения и его допуск — дом `docs/rules/pnl-reconciliation.md`.**
Здесь фиксируется только разделение писателей: аномалию по валюте ставит
**`REFRESH_BILLS_COMMAND` на записи** (там же, где движение
пересчитывается), сверку сумм — финализатор.

**Сверка не выполняется** (предикат обязанности из трёх конъюнктов не
выполнен — дом `docs/rules/pnl-reconciliation.md`) ⇒
`Deal.reconciliationStatus = NOT_RUN`. Это **признак числа, а не вывод
сделки из популяции**: сделка пишется всегда, фильтрует по признаку
потребитель отчёта (`docs/models/domain/aggregate/Deal.md`).

**Сделка длиннее глубины архивной выдачи** (конвейер `bills` 7d →
`bills-archive` 3m) ⇒ `Deal.breakdownIncomplete = INCOMPLETE_BY_WINDOW`. У такой сделки часть строк
недобываема **выбранным конвейером добычи**, поэтому сверка звенела
бы **детерминированно**, а не по дефекту — а контроль, срабатывающий на
каждом объекте своей популяции, эквивалентен погашенному. Признак отделяет
две причины срабатывания; из популяции сделка не выводится.

- **Epsilon, его форма и реакция на расхождение — дом
  `docs/rules/pnl-reconciliation.md`** (,). Здесь — только то, что специфично маппингу: **какие
  четыре пары** собираются из bill-полей и против каких чисел записи
  закрытия сравниваются (таблица выше). Формула допуска, разбор «пол
  вынесен наружу», провизорность величин и снятые редакции в этом файле
  **не пересказываются**.
- **Cross-ccy — нарушение инварианта, не режим:** комиссии платятся только в
  settle-ccy (`docs/rules/trading-constraints.md` комиссии).

### Guard оживлён: `ccy` не фильтрует, а проверяется (H5, `GAPS_CLOSE_6`)

- **`ccy` убран из query** (`docs/integrations/okx/contracts/account-bills.md`) — записи чужой валюты доезжают;
- **`ccy` убран из критериев матчинга** — матчинг по окну + `instId`
  (`docs/models/domain/other/DealCashFlow.md`);
- **ветка на записи:** `ccy == расчётная валюта инструмента` → штатно; иначе →
  **персист + линковка + пересчёт + `AnomalyReport`**. Запись сохраняется и
  получает `deal_id` наравне с остальными — она факт сделки, просто в чужой
  валюте.

### Операнд сравнения — расчётная валюта инструмента (H4, `GAPS_CLOSE_7`)

**Сравнивать с `Deal.resultProfitCurrency` нельзя** — на момент записи
движения это поле **пусто**: его пишет `FINALIZE_DEAL_EXIT_COMMAND`, то есть **после**
прохода `REFRESH_BILLS_COMMAND` (`docs/models/domain/aggregate/Deal.md` — колонка nullable;
`docs/rules/pnl-reconciliation.md` реш.2). Предикат сравнивал бы с
`null` — cross-ccy guard снова был бы мёртв, ровно тем же отказом, который чинил.

**Операнд — расчётная валюта инструмента (settle-ccy).** Это свойство
инструмента, а не результата сделки: оно известно до входа, не зависит от
исхода и от того, доехала ли сделка до финализации. Проверка валюты перестаёт
зависеть от факта закрытия.

### Число — в settle-ccy; чужая валюта пересчитывается сразу

`Deal.resultProfit` = net из positions-history **+ cross-ccy-слагаемое**
Σ(`amount` × `appliedRate`) **по строкам cross-ccy-области** —
`rateStatus = APPLIED` **и** тип вне списка исключений **и** категория
экономическая (конъюнкция целиком —; «по строкам
чужой `ccy`» как предикат **снято** — оно затягивает в произведение строки с
пустым `appliedRate`). Довод: биржевой net считается **в settle-ccy** и
издержку, уплаченную вне её, **не содержит** — без этого слагаемого число
завышало бы результат ровно на её величину, и завышало бы молча
(`docs/rules/trading-constraints.md`). Пометка аномалией
фиксирует **факт** нарушения инварианта, но смещения числа не устраняет — тот
же урок, что и на null-drop (H6, `pnl-finalization-mechanics.md` реш.3).

**Момент курса — операция, не её обработка и не закрытие сделки**. Механика:

- нарушающее движение **сохраняется и пересчитывается сразу**, на записи —
  тем же проходом `REFRESH_BILLS_COMMAND`, который его добыл;
- курс берётся **из свечи на момент операции** — секундного разрешения при
  доступности, с деградацией к более грубому; исход попытки фиксируется
  признаком `rateStatus`, а **взятая свеча** (пара котировки, таймфрейм —
  он же разрешение, — открытие интервала) — **ссылкой на строке**;
- применённый курс **фиксируется полем** `DealCashFlow.appliedRate`
  (заполнен только при `rateStatus = APPLIED`). Число, полученное
  расчётом по внешней котировке, обязано быть **воспроизводимым**: без
  записанного курса эквивалент постфактум не восстановить. Тот же принцип, по
  которому отвергнут fallback-ставки — подставленное число не должно выглядеть
  фактом, не будучи проверяемым.

Отсюда cross-ccy-слагаемое = Σ(`amount` × `appliedRate`) по строкам
cross-ccy-области (конъюнктивный предикат —) —
величина детерминирована самим движением и при пересчёте не дрейфует.
