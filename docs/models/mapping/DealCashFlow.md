# DealCashFlow — mapping bills → домен

## На какой вопрос отвечает этот файл

Как OKX bill-записи ложатся на доменную `DealCashFlow`, как из `type`/`subType`
резолвится `CashFlowCategory`, какие поля валидируются.

## Контекст

Mapping-слой для `DealCashFlow`. Доменная модель —
`docs/models/domain/other/DealCashFlow.md`. Native bill-поля —
`docs/models/integrations/okx/OkxAccountBillResponse.md`. Контракт endpoint'ов
и поток применения — `docs/integrations/okx/contracts/account-bills.md`.
Сквозные правила — `docs/rules/raw-exchange-dto-boundary.md`, codestyle
§Маппинг.

`DealCashFlow` — носитель **разбивки** результата (не первоисточник числа):
заголовочное `Deal.resultProfit` = net из positions-history, а сумма flows —
независимая **сверка** (`docs/decisions/result-profit-source.md`,
`docs/decisions/pnl-finalization-mechanics.md`).

Текущие источники: **OKX**.

## Mapping-flow

```text
bills REST -> raw OkxAccountBillResponse -> IntegrationService validation
  -> DealCashFlowMapper -> DealCashFlow (persist)
```

Raw OKX DTO не выходит за пределы `IntegrationService` / adapter-layer
(`docs/rules/raw-exchange-dto-boundary.md`). Наполняется командой
`REFRESH_BILLS_COMMAND` (`RefreshBillsExecutor`): пагинация bills (7d → 3m archive)
внутри команды, матчинг к сделке и проставление `deal_id` — при сохранении
(`docs/models/domain/other/DealCashFlow.md` §Линковка к `Deal`).

## OKX bill-поле → `DealCashFlow`-поле

| OKX field | DealCashFlow field |
|---|---|
| `balChg` | `amount` (строка → `BigDecimal`) |
| `fee` | `externalFee` (строка → `BigDecimal`; знаковая комиссионная компонента) |
| `ccy` | `ccy` |
| `ts` | `externalCreatedAt` (epoch millis → `OffsetDateTime`; конвенция `Auditable`, H25) |
| `billId` | `externalBillId` |
| `type` | `externalType` |
| `subType` | `externalSubType` |
| `ordId` | `externalOrderId` |
| `instId` | `externalInstrumentId` (сырой; H11 `DOCS_CHECK_11`) |

`category` **не** маппится напрямую — резолвится из `type`/`subType` (см.
ниже). `deal_id` проставляется матчингом, не маппером. `appliedRate` и
`rateStatus` источник не несёт вовсе — их проставляет
`RefreshBillsExecutor` при пересчёте cross-ccy-строки (§«Число — в
settle-ccy»), маппер к ним не причастен. `exchangeId` — не поле источника:
его знает писатель, как знает синк `TradeFeeRate`.

**`instId` теперь пишется в поле, а не только фильтрует** (H11
`DOCS_CHECK_11`). Пока линковка шла в момент чтения ответа, инструмент был
нужен только как критерий матчинга. Но ратифицирована и **отложенная**
тропа — «следующее исполнение звена при непустом `billsWindowEnd`
проставляет `deal_id` **уже сохранённым** строкам окна, а не только вновь
прочитанным» (`docs/components/RefreshBillsExecutor.md`), а множество
«уже сохранённых строк окна» адресуемо только колонками строки. Без
инструментной колонки документированный предикат «окно + `instId`» над
persisted-строками **невыразим** — выразимо только «окно» по времени.
Опереться на «в контуре один инструмент» нельзя: это ратифицированное
ограничение фазы 1, снимаемое явно, и опора на него делает предикат молча
неверным при снятии (тот же довод, которым отвергнут матч по голому
`groupId`). Дополнительный резон: модель сама называет долгоживущий
`deal_id = null` форвард-слотом под движения аккаунта вне сделки (шаг 8) —
строки чужой природы заведомо появятся в тех же временных окнах.

### Разделение ролей `balChg` и `fee`

Два поля отвечают на **разные вопросы** и не подменяют друг друга:

- **`balChg` → `amount`** — вопрос «сходится ли сумма»: Σ`amount` сверяется с
  net из positions-history. Верен при **любой** гранулярности bills (Σ`balChg`
  = net независимо от того, комбинирует источник pnl и комиссию в одну запись
  или эмитит их раздельно).
- **`fee` → `externalFee`** — вопрос «сколько комиссии»: комиссионная
  компонента записи, взятая **явно**, а не выведенная из знака `balChg`.
  Комиссия сделки = Σ`externalFee` по её торговым движениям (область
  суммирования — §«Область суммирования»).

**Посылка-инвариант, на которой стоят обе формулы** (H10, `GAPS_CLOSE_6`;
прежде подразумевалась, не была записана): **`fee` — компонента `amount`
той же записи**, то есть `balChg` уже включает `fee`. Отсюда и
`realized = amount − externalFee`, и «комиссия = Σ`externalFee`» без риска
двойного счёта.

**Под-случай, который посылку ломает — «fee-эхо».** Если источник эмитит
комиссию **отдельной** записью и **дублирует** её число информационным
полем `fee` на соседней pnl-записи (`balChg` = pnl без комиссии, но
`fee = −f` присутствует), то `f` попадает в Σ`externalFee` дважды, а
realized-слагаемое считается как `pnl − (−f) = pnl + f` вместо `pnl`.
Σ`amount` при этом **сходится** — сверка такой дефект **не видит**.
Фактическое поведение источника — рантайм-вопрос §AG3.5
(`.claude/tests/source-api/okx/plan.md`), его вопросник расширен
инспекцией `fee` **на pnl-записи**, а не только на fee-записи. Гейтом не
является: прогон §AG1.5/AG3.5 и так запланирован **до** `CODE`.

**Почему число комиссии — из native `fee` (шаг 7, `GAPS_CLOSE_3`, H2).** Вывод
комиссии из знака `balChg` верен только при гранулярности «отдельная
fee-запись на событие». При **комбинированной** записи (`balChg = pnl + fee`)
он кладёт весь `pnl + fee` в одну корзину: комиссия недосчитана, realized pnl
пересчитан — разбивка (единственный смысл `DealCashFlow`) искажена. Native
`fee` даёт компоненту **явно**, а не выведенной из знака. Суперсет безопасен
для **суммы-сверки** и **realized-слагаемого** при любой гранулярности; для
**суммы комиссии** — нет (§«Число комиссии», H15 `GAPS_CLOSE_5`).
Фактическая гранулярность — рантайм-вопрос
(`.claude/tests/source-api/okx/plan.md` **§AG3.5**; фикстура общая с §AG1.5);
на маппинг ответ не влияет.
*Суперсет — про **число**; **категорию** он не определяет — она резолвится по
типу операции (§«Резолв категории», H9).*

### Знак `externalFee` — сырой, нормализации нет

`externalFee` переносится **со знаком источника** (минус = комиссия, плюс =
ребейт), без `× −1` и без `abs`. Это **сознательная асимметрия** с прогнозной
ставкой `TradeFeeRate`, где знак снимается при маппинге
(`docs/models/domain/other/TradeFeeRate.md` §«Знак ставки», H2):

- **ставка** — прогноз, попадающий в **формулу риска** (`+ commissions`); там
  нужна проектная нормаль «издержка», иначе знак источника молча ломает
  сайзинг;
- **`externalFee`** — **факт** движения, участвующий в **арифметике
  композиции**: realized-слагаемое = `amount` − `externalFee` даёт
  `(pnl + fee) − fee = pnl` **только** на знаковом `fee`. Нормализуй его — и
  разложение комбинированной записи сломается.

Разные роли — разные конвенции. Помечено явно, чтобы следующий проход не
«выровнял» одно по другому: одинаковыми они выглядят только по имени.

**Компонента, не отдельная строка.** `fee` едет **полем на той же строке**, а
не синтетической второй `DealCashFlow`: ключ идемпотентности —
`UNIQUE(external_bill_id)` (одна строка на bill-запись,
`docs/models/domain/other/DealCashFlow.md` §Персистентность), а разложение
комбинированной записи на две строки и задвоило бы её в Σ`amount` (сломав
сверку), и не имело бы второго `billId` под ключ. Отсюда же следствие: при
комбинированной записи realized-pnl-слагаемое разбивки = `amount` −
`externalFee` (native `pnl` отдельным носителем не требуется —
`docs/models/integrations/okx/OkxAccountBillResponse.md` §«Не используется»).

## Резолв категории

**Ось резолва — тип операции, а не знак числа** (H9, `GAPS_CLOSE_4`).
`CashFlowCategory` резолвится **только** из `type`/`subType` bill-записи:
категория отвечает на вопрос «**что это было за событие**», а на него отвечает
источник своим типом операции — не арифметика знака.

| Что за событие (`type`/`subType`) | Категория |
|---|---|
| funding-платёж: `subType` `173` (expense) / `174` (income) | `FUNDING` |
| торговое движение (исполнение ордера, закрытие/частичное закрытие позиции) | `REALIZED_PNL` |
| отдельная запись списания торговой комиссии | `TRADE_FEE` |
| отдельная запись возврата/скидки комиссии | `REBATE` |
| запись ликвидационного штрафа | `LIQ_PENALTY` |
| не отнесённое к перечисленному | `OTHER` |

`LIQ_PENALTY`: само число `liqPenalty` в net берётся из positions-history (не
bills); в `DealCashFlow` категория попадает **как факт bill-записи
ликвидации**, если она присутствует в окне.

**Резолв категории — в вызывающем коде, не в маппере** (codestyle §Маппинг:
маппер делает только перенос данных, доменных решений — интерпретации
`type`/`subType` в категорию — не принимает). Актуальный перечень
`type`/`subType` — справочник OKX (`GET /api/v5/account/subtypes`,
`docs/integrations/okx/contracts/account-bills.md`), **не хардкод**: конкретные
числовые значения `type` в этот док не переписываются, кроме funding-подтипов
`173`/`174`, на которых завязана отдельная ветка.

### Почему не по знаку `externalFee` (что закрывает H9)

Промежуточная редакция (`GAPS_CLOSE_3`, правка H2) резолвила ветку
комиссия/rebate **по знаку `externalFee`**: минус → `TRADE_FEE`, плюс →
`REBATE`. Лид-ины при этом остались правильными (`DealCashFlow.md` §Структура,
поле `category`: «резолвится из `type`/`subType`»), а механизм разошёлся с
ними. Знаковая ось ломалась трижды:

1. **Нет приоритета правил.** Комбинированная запись (`balChg = pnl + fee`)
   матчила одновременно «`externalFee` минус → `TRADE_FEE`» и «реализованный
   pnl → `REALIZED_PNL`». При комбинированной гранулярности комиссия есть у
   **каждой** закрывающей записи ⇒ всё уходило в `TRADE_FEE`, а `REALIZED_PNL`
   **не назначался никогда** — категорийная ось (единственный смысл
   `DealCashFlow`) вырождалась.
2. **Нет ветки нуля.** Тест «минус/плюс» не покрывал `externalFee` = 0.
3. **Ось не та.** Знак `fee` отвечает на «сколько и в какую сторону», а не на
   «что за событие»: комбинированная торговая запись с комиссией — это
   **торговое движение** с комиссионной компонентой, а не «событие комиссии».

Резолв по типу операции снимает все три: у комбинированной записи **один**
`type` (торговое движение) → категория `REALIZED_PNL`, а комиссия едет
компонентой `externalFee` на той же строке. Приоритет не нужен — правило одно.

**`externalFee` = 0 — определённая ветка** (H9). Ноль означает «торговое
движение **без** комиссионной компоненты» (промо нулевой комиссии, maker-ребейт
0 и т. п.). На категорию не влияет — она уже пришла из `type`/`subType`; в
Σ`externalFee` вносит ноль. Отличается от `null` (поля в записи нет вовсе —
§Validation): `null` = «комиссионной компоненты у события не бывает»
(например funding), `0` = «бывает, и она нулевая». Для сумм разницы нет, для
разбора инцидента — есть.

**Число комиссии: claim гранулярность-независимости ограничен** (H15,
`GAPS_CLOSE_5`). Гранулярность-независимы **Σ`amount`** (Σ`balChg` = net
при любой гранулярности) и **realized-слагаемое**. Для **комиссии сделки =
Σ`externalFee`** claim не держится: при раздельной гранулярности, если
самостоятельная fee-запись несёт число в `balChg`, а поля `fee` — нет
(`externalFee = null` по правилу «комиссионной компоненты у события не
бывает», `docs/models/domain/other/DealCashFlow.md` §Структура), комиссия
выпадает из разбивки целиком — при том что Σ`amount` и realized-слагаемое
сходятся, и сверка этого не видит. Что фактически несёт `fee` на
самостоятельной `TRADE_FEE`/`REBATE`-записи — факт источника, из доков не
выводимый: рантайм-вопрос **§AG3.5** (прогон уже запланирован до `CODE`). H9
чинил **присвоение категории**; этот пункт ограничивает claim о **числе**.

## Область суммирования — задаётся явно

Категория задаёт не только атрибуцию, но и **что по чему складывать** (H9,
`GAPS_CLOSE_4`). **Четыре** суммы, четыре разные области (счёт выровнен —
H27, `GAPS_CLOSE_7`; четвёртая добавлена H5 `GAPS_CLOSE_6`, а лид-ин остался
от трёхстрочной редакции):

| Сумма | Область | Зачем |
|---|---|---|
| Σ`amount` | строки сделки **в settle-ccy**, за вычетом **исключённых типов** (§ниже) | сумма-сверка с net из positions-history |
| комиссия сделки = Σ`externalFee` | строки **торговых** категорий (`REALIZED_PNL` / `TRADE_FEE` / `REBATE`) **в settle-ccy** | «сколько комиссии» |
| realized-pnl-слагаемое = Σ(`amount` − `externalFee`) | **только** строки `REALIZED_PNL` **в settle-ccy** | разложение net на слагаемые |
| cross-ccy-слагаемое = Σ(`amount` × `appliedRate`) | строки с **`rateStatus = APPLIED`** | довнести в число издержку, уплаченную вне settle-ccy (H5 `GAPS_CLOSE_6`; операнд и курс — H4 `GAPS_CLOSE_7`; предикат — H9 `DOCS_CHECK_11`) |

**Четвёртая область ключуется признаком состояния курса, а не `ccy`** (H9
`DOCS_CHECK_11`). Прежняя формулировка («строки, у которых `ccy` ≠
расчётной валюты») затягивала в произведение строки с `appliedRate = null`
— а `null` в произведении даёт не «слагаемое не вносится», а NPE либо
`NULL` всей суммы. Пустым `appliedRate` бывает по **трём** причинам
(пересчёт не нужен; котировка не получена; расчётная валюта не
резолвится), и различить их по `ccy` нельзя: две последние — как раз
cross-ccy строки. Явный признак `rateStatus` делает предикат выразимым и
одновременно даёт адресуемое множество должников догона курса
(`docs/models/domain/other/DealCashFlow.md` §Енум `RateStatus`;
`docs/components/RefreshBillsExecutor.md` §«Политика отказа котировки и
догон»).

**Валютная оговорка на первых трёх суммах — несущая, не педантизм**
(H5). Складывать `amount` разных валют нельзя: сумма перестала бы быть числом
в одной валюте, а сверка — сверкой. Поэтому чужая `ccy` вынесена в
**отдельную** (четвёртую) область и входит в число только после пересчёта
(§«Число — в settle-ccy»).

**`FUNDING`-строки исключены** из двух последних — и это несущее уточнение, а
не педантизм. Формула «realized-pnl-слагаемое = `amount` − `externalFee`»
(§«Разделение ролей») без области суммирования применялась бы **ко всем**
строкам и **втянула бы funding в realized pnl**: funding-движение несёт
`amount` и не несёт `externalFee` ⇒ его сумма целиком попала бы в
realized-слагаемое. Funding — **holding-cost**, живёт своей категорией и в
realized pnl не входит (разделяющий довод — `per-trade-risk-policy.md` §«Учёт
комиссий», N13).

Σ`amount` при этом идёт по строкам **всех** экономических категорий,
включая `FUNDING`: она сверяется с net, а net из positions-history funding
**содержит** (`realizedPnl = pnl + fee + fundingFee + liqPenalty`,
`docs/decisions/result-profit-source.md`). Разные области у сверки и у
разбивки — не рассогласование, а разные вопросы.

### Область сверки задаётся списком **исключений** по бирже (H14 `DOCS_CHECK_10`)

**Проблема.** Предикат линковки — «`ts` ∈ окно» + «`instId` == инструмент
сделки»; `type` в запрос не идёт вовсе, а `OTHER` — принимающая корзина,
которая **входит** в сумму-сверку. Какие движения принадлежат экономике
сделки, не было определено. Для isolated-маржи на SWAP это не гипотетика:
движения маржи по позиции несут `instId` и сопоставимы по величине с самой
позицией; native-док прямо свидетельствует, что bills несут не только
торговые движения (`posBalChg`, `posBal`, `from`/`to` — в отброшенных).
Посторонние движения раздувают Σ`|amount|`, поднимают собственный допуск
сверки и глушат настоящие пропуски — контроль, срабатывающий на каждой
сделке, эквивалентен погашенному.

**Решение пользователя: линковать всё, область сверки задать явно — списком
того, что *исключается*, конфигурируемым по бирже.**

- **Линковка не сужается.** Все движения по окну + `instId` персистятся и
  получают `deal_id` — принцип «запись не теряется», ради которого убрали
  фильтр `ccy`, сохранён.
- **Область сверки = все залинкованные строки settle-ccy минус
  исключённые типы.** Список исключений — перечень `type`/`subType`
  источника, **не принадлежащих экономике сделки** (переводы между
  счетами, добавление/снятие маржи и т. п.).
- **Список — от противного, и это несущее свойство.** Allow-list
  (перечислить включаемое) отвергнут: он фиксирует числовые `type`
  источника, чего док запретил, и **новый тип от биржи выпадал бы молча**
  — болезнь мёртвого `ccy`-фильтра. При списке исключений новый тип по
  умолчанию **попадает в расчёт**, и если он посторонний, обнаруживается
  сам — через непустую корзину `OTHER`.
- **Непустой `OTHER` сам по себе даёт `AnomalyReport`** — код
  `UNCLASSIFIED_CASH_FLOW` (`severity = NON_CRITICAL`, ставит финализатор;
  `docs/models/domain/other/AnomalyReport.md` §«Реестр кодов»). Корзина
  «прочее» перестаёт быть молчаливой: она либо пуста, либо звенит.
- **Конфигурируется по бирже.** Перечень посторонних типов — свойство
  источника, не системы: у другой биржи он другой.
  > **Хэнд-офф `integrator`:** носитель этого конфига — новый; определить,
  > **где он живёт** и **кто его правит при добавлении биржи**
  > (`.claude/work/backlog.md` §Шаг 7).

- **Непустой список — предусловие `CODE`** (H10 `DOCS_CHECK_11`, решение
  пользователя). Прежняя редакция отгружала контроль с заведомо пустым
  списком («честный старт: посторонние типы проявятся через `OTHER`»).
  Это защитимо как **процедура разведки**, но не как **режим работы**:
  при пустом списке на каждой сделке одновременно Σ|amount| раздут
  маржинальными движениями (композиционный член epsilon завышен),
  Σ`amount` не сходится с net (`PNL_RECONCILIATION_MISMATCH`) и корзина
  `OTHER` непуста (`UNCLASSIFIED_CASH_FLOW`) — то есть контроль
  целостности числа отгружается погашенным, а на нём стоит вся R-выборка.
  - **Условие выхода и его носитель названы:** перечень `type`/`subType`,
    не принадлежащих экономике сделки, наполняется **рантайм-прогоном
    источника** (`.claude/tests/source-api/okx/plan.md`), и до его
    непустоты шаг не переходит на `CODE` — тем же механизмом, каким к
    `CODE` уже привязан инвариант агрегации positions-history. Новых
    фикстур это не добавляет: прогон уже запланирован, привязывается
    только срок.
  - **Отвергнут вариант «сверять только распознанные экономические
    категории», оставив `OTHER` чистым детектором** (решение
    пользователя): он снимает зависимость от конфига, но несёт риск при
    добавлении **новых типов на бирже** — новый экономический тип попал
    бы в `OTHER` и выпал из суммы, то есть ровно «новый тип выпадает
    молча», против чего и выбран список исключений.
  - **Находка держится в обе стороны, и прогон разрешает которую.** Если
    маржинальные движения в окне есть — контроль был бы мёртв с первого
    дня; если их нет — ложна посылка, на которой построена машинерия
    списка исключений. Пустой список не выясняет, какая ветка истинна.

**Что это меняет у epsilon.** Исключённые типы не входят в Σ`|amount|` ⇒
допуск больше не раздувается посторонним оборотом (сцепление с H15 —
§«Сверка и cross-ccy»).

## Validation (структурная, до маппинга)

В `IntegrationService` OKX:

- **`billId` присутствует** — половина ключа дедупа/идемпотентности
  (`UNIQUE(exchange_id, external_bill_id)`, H13 `DOCS_CHECK_11`); движение
  без `billId` не сохраняется.
- **`ccy` присутствует** — обязательно, иначе cross-ccy движение теряется
  молча при сверке (`pnl-finalization-mechanics.md` реш.5).
- **`ts` присутствует и парсится** (H12 `DOCS_CHECK_11`, решение
  пользователя): обязательность `externalCreatedAt` обеспечивается
  **здесь, на границе разбора**, а не `NOT NULL`-колонкой — audit-колонки
  приходят из общего `AuditableEntity`, часть наследников которого
  БД-first, поэтому `NOT NULL` на них невозможен в принципе. Пустой `ts`
  делает строку невыбираемой оконным предикатом и молча выпадающей из
  суммы-сверки — класс отказа, ради наблюдаемости которого введён
  омиссионный член epsilon; поэтому запись с отсутствующим или
  непарсящимся `ts` до персиста не доходит.
- **`balChg` parseable numeric** — числа приходят строками, `amount`
  парсится в `BigDecimal`; пустая/непарсящаяся строка недопустима.
- **`fee` parseable numeric, если присутствует** — `externalFee` парсится в
  `BigDecimal`; пусто → `null` (движение без комиссионной компоненты, например
  funding). Непарсящаяся непустая строка недопустима.
- На controlled error (`code != "0"`, parse, invariant) — exception в adapter
  (`docs/rules/controlled-exchange-exceptions.md`).

## Сверка и cross-ccy

Сумма `DealCashFlow.amount` **по строкам settle-ccy** сверяется с net из
positions-history. Расхождение **сверх epsilon** и наличие cross-ccy-движения
(`ccy` ≠ расчётной валюты инструмента) → `AnomalyReport` (audit-аномалия,
`severity = NON_CRITICAL`, **не** блок финализации;
`docs/decisions/pnl-finalization-mechanics.md` реш.5). Аномалию по валюте
ставит **`REFRESH_BILLS_COMMAND` на записи** (там же, где движение пересчитывается),
сверку суммы — финализатор.

- **Epsilon — двухчастный, срабатывает меньший, но пол — общий** (H15
  `DOCS_CHECK_10`; форма исправлена H8 `DOCS_CHECK_11`):
  `max( 0.01 settle-ccy, min( 0.5% × Σ|amount|, k × ожидаемая комиссия
  сделки ) )`. Первый член охраняет ошибку **композиции разбивки** — её
  масштаб задают валовые потоки, а не их итог (H7, `GAPS_CLOSE_3`);
  второй — **омиссию** (выпадение entry-fee за границу окна,
  неподобранные движения после терминала): такие отказы фиксированного
  размера, оборотом не масштабируются, и один относительный член делал
  их ненаблюдаемыми именно на сделках с большим |R|. Величины
  (`0.01`/`0.5%`/`k`) — **провизорны** (калибровка —
  пользователь/бэктест), структура теста и якоря — нет. Разбор —
  `docs/decisions/pnl-finalization-mechanics.md` реш.5 §epsilon.
  - **Пол вынесен наружу** (решение пользователя). Прежняя форма
    `min( max(0.01, …), … )` держала пол **внутри** одного из кандидатов,
    и `min` его снимал: при `k × ожидаемая комиссия < 0.01` итоговый
    допуск уходил ниже величины, признанной неотличимой от округления.
    Пол — не член сравнения, а **шум-флор**: он принадлежит итоговому
    допуску, а не одному из кандидатов. Ни одного нового операнда и ни
    одной новой константы правка не вводит.
  - Там, где ожидаемая комиссия сама меньше `0.01`, допуск шире
    омиссионного члена — но её абсолютная величина в этом режиме порядка
    шума, а альтернатива (систематический `PNL_RECONCILIATION_MISMATCH`
    на мелких сделках) обесценивала бы `EVENT`-журнал, на счётности
    которого стоит рамка R-выборки.
- **Cross-ccy — нарушение инварианта, не режим:** комиссии платятся только в
  settle-ccy (`docs/rules/trading-constraints.md` §Валюта комиссии).

### Guard оживлён: `ccy` не фильтрует, а проверяется (H5, `GAPS_CLOSE_6`)

Прежняя редакция объявляла «движение с чужой `ccy` не отбрасывается молча», но
**отсекала его дважды раньше guard'а**: `ccy=USDT` стоял в query запроса bills,
и `ccy` входил в предикат линковки. Нарушающая запись не приходила в ответ ⇒
строки не возникало ⇒ guard не срабатывал **никогда**; расхождение сверки тоже
не возникало (чужая издержка не входит ни в биржевой net, ни в Σ USDT-строк),
то есть нарушение было невидимо полностью. Теперь:

- **`ccy` убран из query** (`docs/integrations/okx/contracts/account-bills.md`
  §Использование) — записи чужой валюты доезжают;
- **`ccy` убран из критериев матчинга** — матчинг по окну + `instId`
  (`docs/models/domain/other/DealCashFlow.md` §«Линковка к `Deal`»);
- **ветка на записи:** `ccy == расчётная валюта инструмента` → штатно; иначе →
  **персист + линковка + пересчёт + `AnomalyReport`**. Запись сохраняется и
  получает `deal_id` наравне с остальными — она факт сделки, просто в чужой
  валюте.

### Операнд сравнения — расчётная валюта инструмента (H4, `GAPS_CLOSE_7`)

**Сравнивать с `Deal.resultProfitCurrency` нельзя** — на момент записи
движения это поле **пусто**: его пишет `FINALIZE_DEAL_EXIT_COMMAND`, то есть **после**
прохода `REFRESH_BILLS_COMMAND` (`docs/models/domain/aggregate/Deal.md`
§Персистентность — колонка nullable;
`docs/decisions/pnl-finalization-mechanics.md` реш.2). Предикат сравнивал бы с
`null` — cross-ccy guard снова был бы мёртв, ровно тем же отказом, который
`GAPS_CLOSE_6` чинил.

**Операнд — расчётная валюта инструмента (settle-ccy).** Это свойство
инструмента, а не результата сделки: оно известно до входа, не зависит от
исхода и от того, доехала ли сделка до финализации. Проверка валюты перестаёт
зависеть от факта закрытия.

> **Носитель расчётной валюты — определён** (H12 `DOCS_CHECK_9`, решение
> пользователя): валюты инструмента (settle/base/quote) **персистятся в
> `Instrument`** — поле `externalSettlementCurrency`, читаемое с
> `DealContext.instrument` (H6 `DOCS_CHECK_11`,
> `docs/decisions/instrument-currencies-home.md`,
> `docs/models/domain/core/Instrument.md` §«Валюты инструмента»).
> `CCY-Q2` **закрыт** — имена полей окончательные, навес на валюты не
> претендует.

### Число — в settle-ccy; чужая валюта пересчитывается сразу

`Deal.resultProfit` = net из positions-history **+ settle-ccy-эквивалент
движений чужой `ccy`**. Довод: биржевой net считается **в settle-ccy** и
издержку, уплаченную вне её, **не содержит** — без этого слагаемого число
завышало бы результат ровно на её величину, и завышало бы молча
(`docs/rules/trading-constraints.md` §«Валюта комиссии»). Пометка аномалией
фиксирует **факт** нарушения инварианта, но смещения числа не устраняет — тот
же урок, что и на null-drop (H6, `pnl-finalization-mechanics.md` реш.3).

**Момент курса — обработка движения, не закрытие сделки** (H4,
`GAPS_CLOSE_7`; уточняет редакцию `GAPS_CLOSE_6` «по курсу на момент
закрытия», которая теперь снята — редакция одна). Механика:

- нарушающее движение **сохраняется и пересчитывается сразу**, на записи —
  тем же проходом `REFRESH_BILLS_COMMAND`, который его добыл;
- курс берётся **отдельным вызовом биржи на момент обработки**;
- применённый курс **фиксируется полем** `DealCashFlow.appliedRate` (`null`
  для строк расчётной валюты — пересчёт им не нужен). Число, полученное
  расчётом по внешней котировке, обязано быть **воспроизводимым**: без
  записанного курса эквивалент постфактум не восстановить. Тот же принцип, по
  которому отвергнут fallback-ставки — подставленное число не должно выглядеть
  фактом, не будучи проверяемым.

Отсюда cross-ccy-слагаемое = Σ(`amount` × `appliedRate`) — величина
детерминирована в момент записи и при пересчёте не дрейфует.

**CCY-Q1 закрыт** этим решением (`GAPS_CLOSE_7`): момент курса — обработка,
источник — живой вызов биржи, применённый курс хранится. Отвергнут
исторический бар по `uTime`: бар давал бы **темпоральную точность**
(курс на момент события источника), а записанный `appliedRate` даёт
**воспроизводимость применённого** — разные свойства (оси довода
разведены, H18 `DOCS_CHECK_9`); для ветки-нарушения-инварианта
темпоральная точность самостоятельной ценности не несёт, а бар стоил бы
ещё одного read-пути.
