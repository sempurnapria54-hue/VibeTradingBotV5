# Стартовый этап: setup и стратегия

Это резюме первого стратегического чата по проекту VibeTradingBotV5. Документ зафиксирован для будущих сессий — чтобы концепция работы и её обоснования не зависели от того, сохранилась ли история конкретного чата.

**Дата:** 2026-05-14
**Этап:** Initial setup
**Результат:** заложена инфраструктура работы с Claude, проведён первичный аудит проекта, согласована модель миграции документации.

---

## Контекст на момент старта

Проект VibeTradingBotV5 — алгоритмический торговый бот для криптобирж (на старте — OKX, далее планируются другие). Стек: Java 21, Spring Boot 3, PostgreSQL, Flyway, MapStruct, Spring Cloud Vault.

К моменту начала работы с Claude:
- Кодовая база ~357 Java-файлов, ~20к строк.
- Большой объём документации в разных папках: `codex/`, `docs/domain/`, `docs/api/`, `docs/context/`, `docs/planning/`, `docs/deprecated/`.
- Документация и код частично рассинхронизированы.
- Тесты отсутствуют (0 файлов в `src/test/java`).
- `@EnableScheduling` есть, но ни одного `@Scheduled` — фоновые job'ы не реализованы.
- Проект начинался с другой нейросетью; ТЗ и код не приведены к единой картине.

## Принятые концептуальные решения

### 1. Двухсессионная модель работы

- **Чат с Claude (claude.ai)** — стратегические обсуждения, проектирование, ревью.
- **Claude Code** — все изменения файлов в репозитории.
- Знания из чата переносятся в репозиторий через **черновики** (Вариант 3): я выдаю готовый текст артефакта, человек передаёт его в Claude Code с задачей "адаптируй под актуальное состояние и сохрани".

### 2. Иерархия источников правды

Установлена строгая иерархия. От высшего приоритета к низшему:

1. `docs/spec/` — целевая спецификация (будет наполняться).
2. `docs/domain/`, `docs/api/` — текущие живые источники для тем, не перенесённых в spec.
3. Код, ADR, conventions.
4. Прочие `docs/`.
5. Архивы (`context/`, `deprecated/`, любые `old/`, `archive/`) — только справка.

Конфликты разрешаются по приоритету. Конфликты внутри одного уровня фиксируются в ADR.

### 3. Поэтапная миграция документации

Старые документы **не удаляются**, а постепенно мигрируют в `docs/spec/`. При полной миграции темы — старый файл помечается `[MIGRATED → docs/spec/...]` на первой строке и теряет статус источника правды.

### 4. Принцип связного обновления документации

Любое изменение модели, процесса или концепции **автоматически** влечёт проверку и обновление всех связанных документов. Это базовое поведение, не отдельный сценарий. Knowledge Curator проверяет это в конце каждой сессии.

### 5. Структура артефактов знаний

Чёткое разделение по жанрам:
- **ADR** (`docs/adr/`) — **почему** выбрали именно так, с альтернативами. Append-only.
- **Спецификация** (`docs/spec/`, `docs/domain/`) — **как устроено** сейчас. Живая, мутирует.
- **Скилл** (`.claude/skills/`) — **как делать на практике**. Активируется по триггеру в `description`.
- **Промпт агента** (`.claude/agents/`) — роль с KPI и проверками.
- **CLAUDE.md** — оглавление и общие конвенции.
- **pipeline-evolution-log.md** — история изменений самого пайплайна работы.

### 6. Стартовая команда агентов

Подняты пять ролей:
- `architect` — структура, абстракции, layering.
- `domain-expert` — доменная модель, инварианты, FSM.
- `risk-engineer` — системные/технические риски (failure modes, race conditions).
- `trading-risk-officer` — финансовый смысл решений.
- `knowledge-curator` — фиксация знаний, проверка связных обновлений.

Каждый агент имеет:
- Чёткий KPI.
- Систематические категории проверок.
- Adversarial requirement (искать конкретные проблемы перед одобрением).
- Явно выделенные зоны (что НЕ делает).
- Инструкции по knowledge capture.

### 8. Project в claude.ai

### 9. Технические правила Claude Code

- Default model: Opus для нетривиальной работы.
- Claude Code **не коммитит** сам — оставляет в working tree.
- Claude Code **делает `git add`** на изменённые/созданные файлы (auto-staging).
- Связные документы обновляются в одной сессии, не "потом".
- Knowledge Curator вызывается в конце сессии.

## Что было решено НЕ делать

Решения по умолчанию, явно проговорённые:

- **Не создавать многоагентность в рантайме (внутри бота)** на этом этапе. Возможно, после MVP в проде.
- **Не строить весь пайплайн заранее.** Стартовать с минимально достаточной конфигурацией, наращивать по реальной потребности.
- **Не делать "дискуссию" между агентами** в работе по умолчанию. Использовать конвейерную схему (один за другим), дискуссии — только в исключительных случаях, когда стоимость многоагентного диалога оправдана.
- **Не помечать сразу старые доки как deprecated.** Они остаются на месте; маркировка `[MIGRATED]` ставится только при полной миграции темы в `docs/spec/`.
- **Не делать отдельный сценарий "обновление спецификации".** Это базовое поведение (связное обновление), применимое во всех сценариях.

## Результаты первичного аудита

Проведён аудит проекта в Claude Code. Главные находки:

### Критические расхождения

1. **Конфликт reconcile-моделей.** В коде и docs/context работает AnomalyReport, а codex/stage/05 v3 описывает SynchronizeExecutionEnvironmentReport. Нужно решение, оформляемое первым ADR.

2. **Раздвоение планирования.** `codex/stage/` описывает внешнюю оболочку (proxy, persistence, vault), `docs/domain/` — глубокую модель (FSM, Strategy, Calculation). Линии не сведены.

3. **Forward recovery / Deal status после рестарта.** В `docs/context/` описан механизм через DealContext, но DealContextService в коде не подтверждён.

4. **Нет ни одного scheduled job.** `@EnableScheduling` есть, `@Scheduled` отсутствует. Бот сейчас работает только как REST-прокси.

### Высокие расхождения

- **RestTemplate вместо RestClient** — нарушение Tech Radar.
- **Полное отсутствие тестов** при сложной FSM + executor-схеме.
- **ServiceCommandType** обобщён и не отражает доменные команды из docs.
- **AGENTS.md** упоминает immutable-параметры, которых нет в коде / Strategy.md.

### Средние

- Висячие ссылки в Main.md, Code style.md, Stage 06.
- Дубль файлов: `vault_local.md` и `vault-local.md`.
- `docs/deprecated/` не отделён барьером.

### Структурные решения по итогам аудита

- `codex/stage/`, `codex/tasks/`, `codex/Main.md` — удалены.
- `codex/CodeStyle.md`, `codex/TechRadar.md` — переезжают в `docs/conventions/` (с доработкой).
- `docs/context/` — переезжает в `docs/domain/rules/` (при миграции).
- Старые `docs/deprecated/`, фрагменты `docs/planning/` — остаются в исходных папках, но как приоритет 5.

## Как использовать этот документ

Этот файл — **навигационный**. Он не дублирует CLAUDE.md или working-with-claude.md, а описывает **исторический контекст**: что было решено, почему, в каком состоянии стартовали.

Используется:
- Когда нужно понять, **почему** установлена текущая концепция.
- Когда новая сессия Claude (в чате или в Claude Code) вводится в контекст проекта — этот документ даёт быстрый обзор стартовых решений.
- При ретроспективе — для сверки, как далеко проект ушёл от изначального состояния.

Не редактируется задним числом. Эволюция концепции отражается в `pipeline-evolution-log.md`, а не здесь.
