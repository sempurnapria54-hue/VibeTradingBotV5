# Жизненный цикл сервисной команды

## На какой вопрос отвечает этот файл

Какое у нас правило жизненного цикла `ServiceCommand`: критерий
атомарности, `CREATE → SUBMIT → REFRESH`, «не persisted queue», одна
команда за проход.

## Правило

- **`ServiceCommand` — runtime object, не persisted entity и не durable
  queue.** Pending-команды в БД не хранятся. После рестарта pending
  `ServiceCommand` как очередь не восстанавливаются: FSM заново определяет
  нужную атомарную команду по актуальным `DealContext`, строкам исполнений
  (`DealActionState`), runtime graph и exchange facts.
- **Критерий атомарности — «одна ответственность за состояние».** Команда
  атомарна ⟺ выполняются все три клаузы
  (`docs/decisions/command-action-boundary.md` §1):
  1. **один владелец исхода** — ровно одна сущность, чьё состояние команда
     обязана привести к факту (остальное — чтение входа либо журнал:
     `AnomalyReport`, аудит);
  2. **повтор с нуля безопасен** — повторное исполнение приводит владельца
     к тому же состоянию;
  3. **нет внутреннего гейта на подтверждение собственной записи** —
     внутри команды нет ожидания, пока биржа подтвердит результат записи
     этого же исполнения; чтение чужих/прежних фактов (evidence-cycle,
     search по client id) клаузу не нарушает.
- **`CREATE_* → SUBMIT_* → REFRESH_*` — это lifecycle, а не пакет.** Для
  создаваемых на бирже сущностей: `CREATE_*` создаёт локальную сущность в
  БД (на биржу не ходит, сущность + строка исполнения одной транзакцией);
  `SUBMIT_*` отправляет или восстанавливает факт отправки по stable client
  id (`internalId → clOrdId`/`algoClOrdId`); `REFRESH_*` подтверждает
  фактическое состояние. FSM двигает статус сделки только после
  подтверждения фактов.
- **Одна актуальная команда за проход.** Всю цепочку заранее никто не
  создаёт: за один проход FSM/handler — одно актуальное исполнение и одна
  актуальная команда, выбранная по свежим фактам. Strategy-команды эмитит
  per-type `StrategyActionExecutor` под диспетчером
  `StrategyActionOrchestrator`; команды системных действий (добыча,
  финализация) — `SystemActionExecutor`
  (`docs/components/SystemActionExecutor.md`).
- **Составное — системное действие, не команда.** Последовательность
  команд (добыча фактов, финализация, аварийное завершение) — **системное
  действие** со строкой исполнения (попытки + идемпотентность), которое
  per-pass ведёт `SystemActionExecutor` по подтверждённым фактам;
  handler'ы добывающие `REFRESH_*` напрямую не эмитят
  (`docs/decisions/command-action-boundary.md` §2). Прочие составные
  процессы (graceful shutdown, protection switch, **REPLACE-ремодел** —
  амендных команд нет, `docs/decisions/replace-not-amend.md`, порядок ног
  по риск-классу, секвенс по фактам; safety-flow) раскладываются на
  атомарные команды и переходы FSM.
- **Атомарность не означает «один HTTP-запрос».** Refresh-команда может
  обойти несколько эндпоинтов биржи **внутри себя**, и сама вынести
  терминал (`MISSING_AFTER_REFRESH`), если исчерпанный цикл и есть его
  основание — клаузу 3 нарушает только ожидание подтверждения
  **собственной** записи. FSM секвенсит *команды*, не эндпоинты внутри
  refresh-команды (см. `docs/decisions/refresh-evidence-cycle-ownership.md`).
  - **Принцип обхода — общий для класса `REFRESH_*`, не свойство отдельной
    команды.** Команда рефреша **ходит к источнику столькими запросами,
    сколько нужно, и останавливается, когда добыла искомый факт**. Отсюда
    три следствия, применимые к **любой** refresh-команде — существующей и
    будущей:
    1. **Предикат остановки — «факт добыт», не «эндпоинт опрошен».** Обход
       обрывается на первом запросе, вернувшем искомое; полный обход — только
       когда факт не найден нигде. Лестница эндпоинтов (live → pending →
       history → archive; live → positions-history; пагинация 7d → архив;
       уточняющий запрос за курсом и т. п.) — **деталь конкретной команды**,
       описывается в её компонент-доке и в реестр правил не выносится.
    2. **Факт не добыт ⇒ команда не завершена.** Отсутствие искомого — не
       успешное завершение с пустым результатом: команда не рапортует
       «сделано», а повторяется по бюджету своего действия. Промежуточные
       записи, сделанные по пути, завершением не являются.
    3. **Исчерпанный цикл — самостоятельный исход, и он расходует бюджет
       наравне с отказом** (H8 `DOCS_CHECK_14`, решение пользователя).
       Когда все запросы пройдены и факта нет, это **легитимный исход**
       («не найдено» / «число недоступно»), который команда выносит сама —
       но `attemptCount` действия он **инкрементирует**: бюджет попыток —
       единственный механизм, которым «повторяется по бюджету» (следствие
       2) может закончиться, и без расхода `RETRY_PENDING → FAILED` на
       легитимно-пустой ветке не наступал бы никогда — действие не могло
       бы завершиться, сделка вечно удерживала бы слот инструмента
       **молча**. Прежняя клауза «не инкрементирует счётчик отказов»
       **ограничена** классами, где отрицательный ответ **сам является
       терминалом команды** (`REFRESH_ORDER_COMMAND` →
       `MISSING_AFTER_REFRESH`) — там повторов нет и считать нечего.
       Принятая цена названа явно: «факт источника не появился» на
       исчерпании неотличим от «интеграция сломана» — политика этапа
       отладки, а не новая. Учёт ведёт единственная ветка
       (`docs/components/ServiceCommandExecutor.md` §«Контракт броска»).
       **Аварийная тропа сделки исключением не является** (H3
       `DOCS_CHECK_15`, решение пользователя): при `Deal.status = ERROR`
       отказ канала добычи расходует бюджет так же, и `FAILED` строки
       служит durable-носителем исхода «недоступно», разрешающим эмиссию
       терминала. Прежняя оговорка «на аварийной тропе счётчик не растёт»
       **отменена** — без расхода бюджета у исхода не было носителя вовсе,
       и сделка зависала в `ERROR`. Отличается там только **бросок**:
       радиусная реакция по отказу канала не поднимается.
  - **Следствие для стадии составного действия.** «Звено сделано» выводится
    из **добытого факта** (durable-состояние сущности-владельца либо метка
    времени, отданная самим источником), а не из значения-дельты и не из
    памяти прохода: если факт не изменился, звено просто повторится
    безвредно. Отдельной метки «команда отработала» класс не требует
    (`docs/decisions/command-action-boundary.md` §5 — стадия из фактов,
    курсора звеньев нет).
  - **«Команда внутри команды» не допускается — следствие клаузы 3.**
    Вложенная команда не имеет ни своего прохода FSM, ни канала возврата
    данных (`ServiceCommandExecutionResult` несёт только
    `success`/`errorCode`/`message`,
    `docs/components/ServiceCommandExecutor.md`). Если факту нужно доехать
    до потребителя — он едет **durable-носителем** (строка сущности), а
    добыча оформляется ногой цикла своей команды. Кейс, на котором граница
    проведена, — положение закрытия позиции (H1/H3 `GAPS_CLOSE_7`).
- **ACK не runtime truth** — факт подтверждается refresh/search/history
  (см. `docs/rules/ack-not-runtime-truth.md`).
