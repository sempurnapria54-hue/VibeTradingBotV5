# Представление сущностей в БД: реляционный каркас + JSONB-навес

## На какой вопрос отвечает этот файл

Какое у нас правило представления сущности (и её частей) в БД.

## Правило

- **Реляционно** (своя таблица/строка с `id`, связи через FK)
  хранятся:
  - **структурный каркас** сущности/агрегата — узлы-контейнеры и
    каркасные узлы дерева (пример — дерево `Strategy`: `Strategy`,
    `StrategyMarketPhaseSetting`, `StrategyDetail`, `StrategyStep`,
    `StrategyAction`);
  - сущности, на которые **ссылаются FK из нескольких мест**.
- **Всё навешанное на каркас** (`params`, операнды и прочие части,
  принадлежащие одному владельцу) — **JSONB**: в строке реляционного
  владельца либо внутри JSON владельца, если тот сам хранится JSONB.
  **Число полей значения не имеет** — критерия «больше N полей →
  таблица» нет; структурированность части сама по себе не делает её
  реляционной.
  - **Исключение — листовые настройки рыночных данных.**
    `StrategyIndicatorSetting` / `StrategyMarketStructureSetting`
    хранятся **реляционными строками** (а не JSONB-навесом), потому что
    на них ссылается жёсткой FK результат расчёта
    (`IndicatorValue` / `MarketStructure`), а у JSONB-листа нет цели FK.
    Это попадает под «сущности, на которые ссылаются FK». Обоснование и
    форма (strategy-scope, `UNIQUE(strategy_id, key)`, одна типизированная
    FK результата) — `docs/decisions/strategy-tree-persistence.md`
    §Ревизия — настройки в собственные строки,
    `docs/decisions/market-data-result-identity-keying.md`. Их `params` при
    этом остаются JSONB-колонкой на строке настройки.
- **`params`** — всегда JSONB в строке/JSON владельца; в коде
  десериализуется в конкретный подтип. Прямых ссылок на `params`
  в БД нет — доступ только через сущность-владельца.
- **Полиморфный JSONB** (payload с подтипами) — дискриминатор
  подтипа живёт **на владельце** (соседнее поле-тип) и в payload
  **не дублируется**; маппинг — Jackson `EXTERNAL_PROPERTY`.
  Поле-тип владельца — единственный источник тега. Механика
  (проверено на `CODE` шага 2): на поле-типе владельца —
  `@JsonProperty(access = WRITE_ONLY)` (иначе при сериализации ключ
  пишется дважды — bean-полем и внешним тегом), на payload-поле —
  `@JsonTypeInfo(..., visible = true)` (при чтении тег заполняет и
  поле владельца).

## Запрет полиморфных ключей

Полиморфных первичных ключей и полиморфных ссылок-владельцев в проекте
**нет**. Где у ссылки несколько возможных таблиц-целей (развилка
адресации владельца) — выражаем её **типизированными FK и/или `UNIQUE`**,
а не парой «`owner_kind` + `owner_id`» (дискриминатор-тип владельца +
нетипизированный id).

- Если целевых таблиц несколько и развилка реальна — отдельная
  типизированная FK на каждую (nullable + `CHECK`/`UNIQUE` по смыслу),
  либо переосмысление владения так, чтобы цель стала одна.
- Предпочтительно сводить адресацию к **одной** типизированной FK (как
  у owner-ключевания результатов рыночных данных: результат → одна
  таблица настройки, `docs/decisions/market-data-result-identity-keying.md`).

**Почему.** `owner_kind + owner_id` рвёт ссылочную целостность (БД не
проверяет FK по полиморфному id), мешает join'ам и индексам, прячет
реальный граф владения. Типизированная FK сохраняет целостность и читаемость
схемы. Заявлено как общепроектное ограничение (трек D, 2026-06-10).

## Почему

- Мотив реляционности — FK-целостность и структурные связи. Там,
  где жёстких FK-ссылок нет (навешанное адресуется по логическому
  ключу или читается только вместе с владельцем), реляционная
  строка не несёт пользы — только лишние таблицы, join'ы и
  inheritance-маппинг.
- Счётчик полей — ложный критерий: он измеряет размер, а не
  характер связей. Представление определяет то, ссылаются ли на
  часть извне, а не то, сколько в ней полей.
- Дубль дискриминатора (на владельце и в payload) — риск
  рассинхрона («настройка говорит EMA, params — RSI»);
  единственный источник тега его исключает.

## Первоисточник и смежное

Правило сквозное — обобщение разбора персистентности дерева
`Strategy` (`docs/decisions/strategy-tree-persistence.md` — первое
применение, детальное обоснование и отвергнутые альтернативы на
конкретной схеме). Конкретная схема сущности фиксируется в её
модели (`docs/models/...` §Персистентность). Для новой сущности
правило — дефолт; осознанное исключение фиксируется decision'ом.
