# Иерархия исполнения торговли

## На какой вопрос отвечает этот файл

Какова иерархия уровней исполнения торговли (стратегия → условия и
действия → `StrategyAction` → команды → биржевые вызовы).

## Правило (решение держателя, 2026-08-26)

Торговля исполняется по фиксированной иерархии уровней:

1. **Торговля идёт по стратегии.** Вне стратегии торговых решений нет
   (`docs/models/domain/aggregate/Strategy.md`).
2. **В стратегии — условия и действия.** Стратегия описывает, *когда*
   (условия) и *что* (действия) делать
   (`docs/decisions/strategy-condition-authoring-contract.md`,
   `docs/processes/strategy-action-calculation.md`).
3. **При выполнении условий исполняется `StrategyAction`** — единица
   исполнения уровня стратегии
   (`docs/components/StrategyActionOrchestrator.md`,
   `docs/components/StrategyActionExecutor.md`).
4. **`StrategyAction` может состоять из нескольких команд**
   (`ServiceCommand`). Всю цепочку заранее никто не создаёт: за один
   проход FSM эмитится одна актуальная атомарная команда по свежим
   фактам (`docs/rules/command-lifecycle.md`,
   `docs/decisions/command-action-boundary.md`).
5. **Команда рефреша данных вправе в рамках одной команды несколько
   раз сходить на биржу в разные эндпоинты, пока не получит данные.**
   Атомарность команды не означает «один HTTP-запрос»; FSM секвенсит
   команды, не эндпоинты внутри refresh-команды
   (`docs/rules/command-lifecycle.md` §«Атомарность не означает „один
   HTTP-запрос“», `docs/decisions/refresh-evidence-cycle-ownership.md`).

Каждый уровень виден только соседнему: стратегия не знает про команды,
команда не знает про условия стратегии; биржевые вызовы — деталь
конкретной команды.

## Что не входит в иерархию

- **Системные действия** (добыча фактов, финализация, аварийное
  завершение) — та же командная механика уровней 4-5, но вне стратегии:
  их ведёт `SystemActionExecutor` по строкам исполнения
  (`docs/decisions/command-action-boundary.md` §2).
- **Kill-switch** — аварийный self-contained teardown вне реестра
  команд, не подчинён петле и иерархии
  (`docs/decisions/action-orchestration-vs-command.md`).
- **Cleanup/safety-команды handler'ов** — риск-снижающие дочистки
  (`CANCEL_*`, `CLOSE_POSITION_COMMAND`), эмитируемые handler'ом
  напрямую, без анкера действия: teardown условия-перехода
  (`ExitPendingHandler`), аварийное снятие риска (`ErrorHandler`),
  реакция сопровождения (`AnomalyJob`). Сознательно вне действий
  (`docs/decisions/fsm-execution-layering.md`): иерархия управляет
  **созданием торгового намерения**, снятие риска ей не подчинено.
