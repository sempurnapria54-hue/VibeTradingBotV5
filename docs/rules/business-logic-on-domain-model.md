# Бизнес-логика — на доменной модели

## На какой вопрос отвечает этот файл

Какое правило системы определяет, где выполняется бизнес-логика
относительно слоёв моделей.

## Правило

Бизнес-логика всегда выполняется на доменной модели. Поток:

```text
вход из внешнего слоя
  → mapping в domain (см. docs/models/mapping/)
    → выполнение бизнес-логики на domain
      → при необходимости mapping обратно (domain → request / persistence / rest)
```

- На моделях слоёв `integrations/{name}` (нативные DTO источника),
  `externalSnapshot` (нормализованный граничный объект),
  `persistence` (хранимые проекции), `rest` (наш API) бизнес-логика
  **не выполняется**. Эти модели — носители данных слоя, без
  поведения сделки.
- Валидация на не-доменных слоях допустима только в рамках
  «структурной/protocol-валидации» этого слоя (например, проверка
  обязательных полей DTO источника в `ClientService`), не как
  бизнес-логика.
- Перенос ответственности из non-domain слоёв в `domain` — основной
  механизм поддержания инвариантов: status-резолвинг, выбор
  следующего действия, расчёт risk/PnL, validation against
  invariants — всё на domain.

## Где применяется

Сквозное правило: для всех потоков данных всех сущностей.
Первоисточник — здесь (сквозной слой, см.
`.claude/decisions/rule-source-of-truth.md`).

## Связанные правила

- `docs/rules/raw-exchange-dto-boundary.md` — raw DTO источника не
  выходит за adapter-layer; то, что выходит — нормализованный
  snapshot, не носитель бизнес-логики.
- `docs/rules/ack-not-runtime-truth.md` — ACK операции источника не
  меняет доменный статус; статус ставит domain после refresh.
- `docs/rules/external-status-resolution.md` — резолвинг сырого
  статуса источника в `Domain.Status` — пограничная операция, после
  неё работа идёт на domain.

моделей) — фиксирует слои и место `mapping/`.
