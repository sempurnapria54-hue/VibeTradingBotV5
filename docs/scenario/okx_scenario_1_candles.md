# OKX API — Сценарий 1: свечи (Market Candles) — бизнес‑кейсы и правила

> Цель сценария 1: получать свечи (candles) по инструменту и таймфреймам, уметь строить непрерывное окно данных для анализа/сигналов и корректно обрабатывать «края» истории (начало/конец), дневные свечи и пропуски.

---

## 1) Используемые эндпоинты

### 1.1. Последние свечи (актуальные)
- **GET** `/api/v5/market/candles`
- Назначение: получить последние свечи (обычно **от новых к старым**).

### 1.2. Исторические свечи (углубление «в прошлое»)
- **GET** `/api/v5/market/history-candles`
- Назначение: постранично уходить в историю (обычно с меньшими лимитами и более строгими rate limits).

---

## 2) Формат данных свечи

Каждая свеча приходит как массив из **9 строковых полей**:

`[ts, o, h, l, c, vol, volCcy, volCcyQuote, confirm]`

- `ts` — Unix timestamp **в миллисекундах** (UTC), **начало** свечи
- `o/h/l/c` — Open/High/Low/Close
- `confirm`:
  - `"1"` — свеча **закрыта**
  - `"0"` — свеча **ещё формируется** (незакрытая)

---

## 3) Бизнес‑правила для анализа

### Правило R1 — анализируем только закрытые свечи
Для индикаторов/сигналов/кворума используем **только свечи с `confirm="1"`**.
Незакрытые (`confirm="0"`) можно использовать лишь для «live‑оценки» (без принятия финального решения).

### Правило R2 — работаем во времени UTC
Храним timestamps в UTC (миллисекунды). Любые локальные преобразования — только для UI/отчётов.

### Правило R3 — одинаковая шкала времени на всех слоях
- На входе из API: `ts` (ms UTC)
- В домене/БД: timestamp в UTC (ms или timestamptz — главное единообразие)
- В аналитике: UTC

---

## 4) Кейсы «начало» и «конец» доступных данных

### Кейс A: разные TF стартуют с разных дат
Пример:
- `1D` свечи есть с **21 декабря**
- `1H/15m/1m...` есть с **28 декабря**

**Решение (coverage_start):**
- Для каждого TF вычисляем `coverage_start(tf)` — дату начала **непрерывного хвоста** (см. раздел 5)
- Глобальное начало для стратегии, которая использует набор TF:
  - `global_start = max(coverage_start(tf))` по всем используемым TF

Итог в примере:
- `global_start = 28 декабря` (потому что иначе MTF‑логика не сможет строить признаки на всех TF)

### Кейс B: конец «разный», потому что часть свечей открыта
- В `market/candles` и иногда на других TF верхняя свеча может быть `confirm="0"`
- Для анализа конец считается как **последняя закрытая свеча**

**Решение (coverage_end):**
- Для каждого TF: `coverage_end(tf) = max(ts where confirm="1")`

Два режима:
1) **Strict оффлайн (все TF закрыты):**
   - `global_end = min(coverage_end(tf))` по всем TF
2) **Live режим (базовый TF закрыт, HTF берём «последний закрытый»):**
   - `global_end = coverage_end(base_tf)`
   - HTF‑контекст: всегда «последний закрытый бар» на HTF

## 5) Пропуски свечей (дыры) и целостность данных

### Предпосылка
В БД есть уникальность по (instrument, timeframe, tsUTC) — **дубликатов не будет**.

### 5.1. Быстрый smoke‑check через COUNT
Идея: если ряд непрерывный между min_ts и max_ts, то
`expected = (max_ts - min_ts) / tfMs + 1`
и должно быть `count == expected`.

**Важно:** считать только по закрытым свечам (confirm=1) и в рамках «сеточного» шага TF.

Доп. защита от «смещения сетки»:
- проверяем, что все `ts` лежат на одной сетке:
  - `ts % tfMs` одинаков для всего ряда
  - (особенно актуально для дневок)

Если `count == expected` **и** сетка выровнена → дыр нет.

### 5.2. Если дырки есть: поиск и докачка по рекурсии (divide & conquer)
Цикл:
1) **Общий COUNT‑чек**
2) Если дырки есть → **поиск дыр сегментацией** (бинарный/рекурсивный подход)
3) **Докачка** найденных сегментов через `history-candles`
4) Повторить общий COUNT‑чек
5) Повторять, пока `count == expected` (или пока не сработает stop‑условие)

#### Как работает рекурсивный поиск дыр
Для сегмента `[L..R]`:
- `expectedLR = (R-L)/tfMs + 1`
- `cntLR = countCandles(L..R)`
- если `cntLR == expectedLR` → сегмент «целый», дальше не делим
- иначе если сегмент малый (порог) → считаем «дырным» и отдаём на докачку
- иначе делим на `[L..M]` и `[M+tfMs..R]` и продолжаем

**Пороги (пример):**
- 1m: 6–24 часа
- 15m: 1–7 дней
- 1H: 7–30 дней
- 1D: 90–180 дней

### 5.3. Stop‑условия, чтобы цикл не был бесконечным
Обязательные стопы:
- Лимит итераций (например, 10 на TF)
- Прогресс: после докачки `count` должен увеличиться; если нет — фиксируем «невозможно восстановить»
- Если API возвращает пусто (история закончилась) — пересчитываем min_ts/coverage_start (см. раздел 6)

## 6) Как определить «самое начало истории»

Есть два практичных способа.

### Способ 1 (простой): идти назад, пока API не начнёт отдавать пусто
1) Берём текущую «нижнюю границу» `after = min_ts_из_последней_пачки`
2) Запрашиваем `history-candles` с `after`
3) Если ответ пустой → **ниже истории нет**, значит начало истории лежит в предыдущей пачке

Плюсы: просто, понятно.
Минусы: может быть много итераций, если история длинная.

### Способ 2 (быстрый): бинарный поиск по времени «есть ли что-то раньше X»
Используем тест “пусто/не пусто”:
- `history-candles?after=X`
  - если **не пусто**, значит есть свечи раньше X → история начинается раньше X
  - если **пусто**, значит свечей раньше X нет → история начинается позже/в районе X

Дальше бинпоиском сужаем диапазон, а затем докачиваем «приближаясь» к началу.

Плюсы: быстрее на длинной истории.
Минусы: сложнее, нужна аккуратная логика границ и шага `tfMs`.

## 7) Дневные свечи (1D) и «границы дня»

У OKX дневные свечи могут быть «привязаны» к разным границам дня (например, по UTC+8).

Практическое правило для проекта:
- Мы храним `ts` как UTC и **не пытаемся «переинтерпретировать»** границы дня на стороне бота.
- Если стратегии важно «календарное начало суток по UTC», это делается отдельным mapping‑слоем (и отдельно тестируется).

Для смешанного MTF это критично:
- «1D в UTC+8» будет иметь `ts` = 16:00 UTC предыдущего календарного дня (зимой для Европы это часто 18:00 по Хельсинки).
- Это нормально, пока всё хранится и сравнивается в UTC, и пока соблюдается правило `confirm="1"`.

---

## 8) Рекомендации по логам и метрикам

Для каждого (instrument, timeframe) логировать:
- `min_ts_confirmed`, `max_ts_confirmed`
- `count_confirmed`
- `expected_count`
- `aligned_to_grid` (да/нет)
- `gap_segments_found` (сколько сегментов рекурсией)
- `downloaded_candles` (сколько докачали)
- `iterations_used` (сколько циклов)

Это позволяет быстро объяснить:
- почему `global_start` именно такой
- где были дырки и как они были восстановлены

---

## 9) Чек‑лист готовности данных для стратегии (MTF)

1) Для каждого TF:
   - ряд закрытых свечей непрерывен (COUNT==expected)
   - timestamps на одной сетке (alignment)
2) `global_start` посчитан как max по TF
3) `global_end` выбран по режиму (strict или live)
4) Сигналы/индикаторы используют только `confirm="1"`

---
