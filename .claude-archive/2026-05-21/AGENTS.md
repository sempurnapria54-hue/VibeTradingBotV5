# AGENTS.md

## Назначение

Этот файл задаёт правила работы для Codex в проекте торгового бота.
Главная цель: вносить изменения безопасно, без поломки уже согласованной архитектуры, доменной модели и проектных инвариантов.

---

## 1. Контекст проекта

Проект — торговый бот под **OKX v5 API**.
Основной инструмент: **ETH-USDT-SWAP**.

Технический стек проекта:

* Java 21
* Spring Boot 3.x
* Spring Data JPA / Hibernate
* PostgreSQL
* Maven
* Lombok
* MapStruct
* Kafka — в проекте/экосистеме используется, но не в каждой задаче

Ключевые бизнес-ограничения проекта:

* торгуем только через **OKX**;
* основной инструмент — **ETH-USDT-SWAP**;
* плечо — **не выше x10**;
* использовать только **isolated margin**;
* риск на сделку — не больше **1% депозита**;
* допускается **не более одной позиции на один инструмент**;
* у пользователя может быть несколько открытых позиций по разным инструментам, но **не более одной на один инструмент**.

Важно:

* на OKX для `SWAP/FUTURES` поле `sz` задаётся **в контрактах**, а не в USDT;
* если логика оперирует суммой в USDT, нужно сначала получать спецификацию инструмента (`ctVal`, `lotSz`, `minSz`) и текущую цену, затем конвертировать USDT → контракты.

## 2. Общие принципы работы Codex

### 2.1. Не придумывай архитектуру заново

В проекте уже зафиксированы доменные договорённости. Их нельзя молча переопределять.
Если задача конфликтует с ними, нужно следовать этим правилам, а не предлагать альтернативную архитектуру по умолчанию.

### 2.2. Меняй только то, что нужно для задачи

Запрещено делать попутный рефакторинг широкого охвата без прямой необходимости.
Нельзя:

* массово переименовывать классы/пакеты;
* менять уже согласованные доменные термины;
* переносить слои между пакетами без запроса;
* переписывать рабочие сервисы «под свой стиль», если это не требуется задачей.

### 2.3. Соблюдай текущий стиль проекта

Новый код должен быть похож на уже существующий код проекта, особенно на сервисы уровня `HistoryService` и связанные прикладные сервисы.

### 2.4. Не ломай идемпотентность и воспроизводимость

Если изменение касается вычислений, параметров, оркестрации, сигналов, индикаторов, ордеров, позиций, снапшотов, журналирования или FSM — решение должно сохранять идемпотентность.

## 3. Архитектурные правила

## 3.1. Слои ответственности

Использовать стандартное разделение:

* **Controller** — только REST-вход/выход, простое преобразование DTO;
* **Service** — прикладная и доменная логика;
* **Client / ClientService** — вызовы внешнего API OKX и маппинг внешних DTO;
* **Repository** — только доступ к БД;
* **Mapper** — преобразование моделей через MapStruct;
* **Domain model / persistence model** — не смешивать с transport DTO.

Нельзя запихивать в controller:

* бизнес-логику;
* orchestration;
* прямую работу с репозиториями;
* расчёты по торговой логике.

---

## 3.2. Истина в торговом процессе

Для live-логики и сопровождения сделок истина раскладывается так:

* факты по бирже — из OKX snapshot/WS;
* факты в системе — из `DealContext` и связанных сущностей;
* после рестарта истиной для FSM является не только `Deal.status`, а **факты из DealContext**.

Нельзя строить recovery только по одному полю статуса сделки.

---

## 3.3. Разделение job-контуров

### ReconciliationJob = AnomalyJob

Эта job:

* ищет **глобальные аномалии** системы;
* не ведёт сделку по FSM;
* не является основным контуром сопровождения сделки.

Типовые аномалии:

* сущность есть на бирже, но нет в БД;
* более одной позиции на инструмент;
* превышение глобального плеча;
* нарушение базовых инвариантов системы.

Результат работы:

* формирование `AnomalyReport` со snapshot-слепками;
* при критике — блокировка инструмента и запуск kill-switch.

### DealOrchestratorJob

Это **единственный** контур, который сопровождает известные сделки и двигает `Deal.Status` по FSM.

Нельзя переносить логику сопровождения сделки в ReconciliationJob.

---

## 3.4. FSM, executors, resolvers и сервисные команды

FSM использует универсальные события:

* `CHECK_ENTRY_INVARIANTS`
* `PROCESS`
* `CHECK_EXIT_INVARIANTS`
* `RETRY`
* `FAIL`

Команды FSM должны быть **сервисными**, а не низкоуровнево-биржевыми.

При этом в проекте есть важное дополнительное правило реализации:

* команды и операционные действия обычно оформляются через отдельные **Executor**-классы;
* типовой стиль: `CloseAlgoOrderExecutor`, `RefreshAlgoOrderExecutor`, `RefreshBalanceExecutor` и т.д.;
* если логика простая и точечная — использовать executor;
* если логика синхронизации сложная, многошаговая или агрегирует несколько источников — допустимо и желательно выносить её в отдельный **SyncService**, например `AlgoOrderSyncService`;
* если нужно определить сложный статусный переход, резолв внешнего статуса или mapping нескольких факторов в итоговый статус — использовать отдельный **Resolver**-класс, например `OrderStatusResolver`.

Предпочтительное разделение ответственности:

* **Executor** — выполняет конкретное прикладное действие/команду/refresh-шаг;
* **SyncService** — координирует сложный sync/reconcile/merge сценарий;
* **Resolver** — принимает решение о статусе, переходе или классификации;
* **Service** — доменный API и точка входа для прикладной логики, но не место для разрастания всей orchestration-логики подряд.

Нельзя превращать FSM в набор прямых вызовов OKX client из каждого состояния.
Нельзя также складывать сложную sync-логику и статусные переходы в один «толстый» service, если в проекте для этого уместнее executor/resolver/sync-service.

## 3.5. DealContext

`DealContextService` сам собирает `DealContext` из:

* `Deal`
* `Order`
* `Position`
* `AlgoOrder`
* `MarketPhase`
* `Strategy`
* `StrategyDetails`

Нельзя таскать огромный полу-сырой context через весь код без необходимости.
Нужно передавать в сервисы только реально нужные параметры.

---

## 3.6. Active / Closed semantics

Для каждой сущности нужно различать:

* **active in DB**
* **active on exchange**
* **closed in domain**
* **closed on exchange**

Это особенно важно для:

* `Position`
* `Order`
* `AlgoOrder`
* `Deal`

Правила:

* operational flow работает только с **active/live** сущностями;
* snapshot для аномалий может включать и `relatedInactive`, но это не вся история подряд;
* нельзя вручную раскидывать списки live/final статусов по десяткам сервисов — нужно использовать централизованные правила/методы.

Смысловой источник: сущность должна считаться живой только если она реально ещё влияет на риск, исполнение или сопровождение.

---

## 3.7. Параметры конфигураций immutable

В проекте **не используем `params_hash` как основной идентификатор конфигурации**.

Вместо этого используются immutable-таблицы параметров:

* `indicator_params`
* `signal_params`
* `quorum_params`
* `risk_params`
* `exchange_params`

Обязательное правило:

1. Канонизировать входной конфиг в `canonical_json`.
2. Найти запись по уникальности.
3. Если найдена — использовать существующий id.
4. Если нет — создать новую immutable-запись.
5. Все вычисленные сущности должны ссылаться на неё через FK.

Нельзя:

* обновлять старые строки параметров;
* идентифицировать конфигурацию только json-строкой в прикладной логике;
* возвращаться к старой схеме с `params_hash` как основной сущностью идентификации.

## 3.8. Свечи и таймфреймы

### Таймфреймы OKX чувствительны к регистру

Это критичное правило.
Нужно всегда использовать константы из `com.example.tradingbot.util.OkxTimeframes`.

Нельзя:

* нормализовать таймфреймы в lower-case;
* сравнивать таймфреймы «по смыслу»;
* подставлять строковые литералы вроде `"1d"`, `"1h"`, `"1m"`, если в проекте уже есть константы.

Использовать только значения в формате OKX, например:

* `ONE_MINUTE`
* `THREE_MINUTES`
* `FIVE_MINUTES`
* `FIFTEEN_MINUTES`
* `ONE_HOUR`
* `FOUR_HOURS`
* `ONE_DAY`

### Свечные данные

Правила:

* всё время хранить в **UTC**;
* не допускать look-ahead;
* идти по свечам строго **old → new**;
* существующие таблицы `candles` и `history_group` не ломать;
* для истории и докачки соблюдать текущую модель загрузки и целостности.

## 3.9. Индикаторы, сигналы, решения

Текущий фокус проекта: **indicator features / backfill features**.

Это значит:

* сейчас приоритетно считать и докачивать **значения индикаторов**;
* сигналы и решения — отдельные этапы и отдельные задачи;
* не нужно самовольно расширять задачу на полный trading flow, если пользователь просил только features.

Особенно важно:

* **features не имеют horizons**;
* horizons относятся к **signals/evaluation**;
* при работе с features не нужно тащить в код лишнюю сигнальную/кворумную логику, если задача про расчёт индикаторов.

## 3.10. Торговые инварианты

Нельзя нарушать следующие проектные правила:

* только **isolated margin**;
* фактическое плечо не выше **10x**;
* не более **одной позиции на инструмент**;
* `CancelUnknownOrders=true` — это **production policy**, а не тестовый флаг;
* при защитной логике нельзя оставлять активные «хвосты» без контроля;
* attached/protective/algo-ордера должны сопровождаться согласованно с FSM и refresh-flow.

## 3.4.1. Практическое правило выбора между Executor / SyncService / Resolver

Если задача про одно конкретное действие, refresh-шаг или command execution — предпочитать **Executor**.

Примеры:

* обновить локальный snapshot ордера;
* закрыть algo-order;
* обновить баланс;
* синхронизировать один тип сущности простым сценарием.

Если задача требует:

* нескольких шагов синка;
* чтения нескольких источников;
* merge локального и внешнего состояния;
* отдельной стратегии reconcile;
  то лучше использовать **SyncService**.

Если задача сводится к тому, чтобы:

* определить итоговый статус;
* классифицировать закрытие;
* вычислить переход между статусами;
* скрыть сложную матрицу условий;
  то лучше использовать **Resolver**.

Это правило нужно соблюдать при проектировании новых частей live-flow.

## 5. Стиль кода

## 5.1. Обязательные правила оформления

### Дополнительные строгие правила по style-guide

* для null-check использовать только `Objects.isNull(x)` и `Objects.nonNull(x)`;
* не использовать `== null` и `!= null`;
* для сравнения объектов и строк использовать `Objects.equals(a, b)`;
* избегать прямых отрицаний в условиях, где это можно выразить через утилиты;
* для boolean-проверок по возможности использовать `BooleanUtils.isTrue(...)` и `BooleanUtils.isFalse(...)`;
* для коллекций не писать парные проверки вида `collection != null && !collection.isEmpty()`;
* вместо этого использовать `CollectionUtils` — локальный utility проекта, если он уже есть в модуле; иначе библиотечный `CollectionUtils` из Apache Commons Collections;
* это правило распространяется не только на коллекции, но и в целом на типовые парные guard-checks: если в проекте уже есть безопасный utility-метод, предпочтительно использовать его вместо ручной составной проверки.

Примеры:

Плохо:

```java
if (collection != null && !collection.isEmpty()) {
    ...
}
```

Хорошо:

```java
if (CollectionUtils.isNotEmpty(collection)) {
    ...
}
```

Плохо:

```java
if (data != null) {
    ...
}
```

Хорошо:

```java
if (Objects.nonNull(data)) {
    ...
}
```

Плохо:

```java
if (!flag) {
    ...
}
```

Хорошо:

```java
if (BooleanUtils.isFalse(flag)) {
    ...
}
```

### Не объявлять несколько переменных в одной строке

Плохо:

```java
int a = 1, b = 2;
```

Хорошо:

```java
int a = 1;
int b = 2;
```

### Всегда ставить фигурные скобки

Плохо:

```java
if (condition)
    return;
```

Хорошо:

```java
if (condition) {
    return;
}
```

Это правило распространяется на:

* `if`
* `else`
* `for`
* `while`
* `do while`
* `switch` ветки, где это уместно

## 5.5. Null-safety и проверки

При работе с внешними snapshot / DTO / API-ответами:

* явно проверять null там, где данные реально могут отсутствовать;
* использовать `Objects.isNull(...)` / `Objects.nonNull(...)`;
* для коллекций использовать `CollectionUtils.isEmpty(...)` / `CollectionUtils.isNotEmpty(...)` вместо ручных null+empty проверок;
* если в модуле есть локальный `CollectionUtils`, предпочитать его; если нет — использовать библиотечный Apache Commons Collections;
* для типовых boolean-веток по возможности использовать `BooleanUtils.isTrue(...)` / `BooleanUtils.isFalse(...)`;
* не плодить лишние Optional-цепочки, если в проекте принят обычный imperative-style;
* не удалять защитные проверки только ради «красоты» кода.

## 6. Правила для работы с OKX API

### 6.1. Размер в ордерах SWAP

Для `SWAP` размер `sz` — это **контракты**.
Нельзя трактовать `sz` как USDT.

### 6.2. Подтверждение факта действия

Для операций create/amend/cancel/close-position/algo:

* REST-ответ OKX часто означает только `ack`, а не финальное подтверждение;
* финальный факт должен подтверждаться через последующий snapshot / detail endpoint / WS событие.

### 6.3. Позиции

По инструменту допускается не более одной позиции.
Любая логика, которая может создать вторую позицию на тот же инструмент, считается нарушением проектного инварианта.

### 6.4. Защитные ордера

При сопровождении сделки нужно различать:

* attached protection;
* отдельные algo-orders;
* активные и уже финализированные защиты.

Нельзя оставлять защитную логику в «полу-согласованном» состоянии.

---

## 7. Правила для БД и миграций

Если задача требует изменений БД:

* изменения должны быть минимальными и обратимыми по смыслу;
* нельзя ломать существующие таблицы и уникальные ограничения без прямого запроса;
* если добавляется новая таблица параметров/сущность/индекс — нужно объяснить, зачем это нужно;
* если меняется уникальность или инварианты — нужно отдельно подсветить риск.

Особенно осторожно с:

* `candles`
* `history_group`
* таблицами параметров
* таблицами, где завязана идемпотентность
* таблицами, связанными с order/deal/position/algo lifecycle

### Быстрая проверка без интеграционных тестов

```bash
./mvnw test
```

или

```bash
mvn test
```

### Запуск одного набора тестов

```bash
./mvnw -Dtest=ClassNameTest test
```

### Запуск одного тестового метода

```bash
./mvnw -Dtest=ClassNameTest#methodName test
```

### Сборка без тестов

Использовать только если задача не требует тестового прогона или тесты в окружении заведомо не стартуют:

```bash
./mvnw -DskipTests package
```

### Запуск приложения локально

Обычно:

```bash
./mvnw spring-boot:run
```

Если для локального запуска нужны внешние зависимости, Codex должен сначала проверить конфиги `application.properties` / `application.yml`, профили, переменные окружения и доступность БД.

### Важно

Нельзя писать в результате, что сборка/тесты прошли, если они реально не запускались.
Нельзя выдумывать результат команд.

---

## 9. Как оформлять результат работы

После выполнения задачи результат нужно оформлять коротко и по делу.

### Обязательный формат ответа

1. **Что сделано**

    * короткий список реальных изменений;
    * без воды и без пересказа всей архитектуры.

2. **Какие файлы изменены**

    * перечислить только реально изменённые файлы.

3. **Что важно проверить руками**

    * только реальные риски, edge-cases, миграции, интеграционные места.

4. **Какие команды запускались**

    * перечислить фактически выполненные команды.

5. **Результат команд**

    * прошло / не прошло;
    * если не прошло — честно указать, где и почему.

### Если тесты не запускались

Нужно явно писать:

* что тесты не запускались;
* почему не запускались, если причина есть.

### Если есть ограничения

Нужно явно писать:

* чего не удалось сделать;
* что осталось недопроверенным;
* где есть риск.

---

## 10. Что Codex должен проверять перед изменениями

Перед тем как писать код, нужно проверить:

* не конфликтует ли решение с текущими архитектурными правилами;
* не ломает ли решение инварианты торговли;
* не меняет ли случайно live-flow там, где задача локальная;
* не затрагивает ли immutable-конфигурации и ключи идемпотентности;
* не ломает ли регистр и формат таймфреймов OKX;
* не использует ли строковый timeframe вместо `OkxTimeframes`;
* не открывает ли возможность второй позиции на инструмент;
* не начинает ли трактовать `sz` для SWAP как USDT.

---

## 11. Что делать, если задача неоднозначна

Если в коде есть несколько вариантов, выбирать тот, который:

* минимально меняет существующую архитектуру;
* лучше сохраняет идемпотентность;
* лучше соответствует уже обсуждённым правилам проекта;
* ближе к текущему стилю кода.

По умолчанию не нужно:

* вводить новые абстракции ради красоты;
* делать «универсальные framework-like решения»;
* расширять скоуп задачи без запроса.

---

## 12. Короткий чек-лист перед коммитом

Перед завершением задачи убедись, что:

* используются правильные `OkxTimeframes` константы;
* нет lower-case нормализации таймфреймов;
* нет множественных объявлений переменных в одной строке;
* у всех `if` есть фигурные скобки;
* не сломан live/deal/anomaly split;
* не нарушена immutable-модель параметров;
* не нарушены trade invariants;
* не добавлена вторая позиция на инструмент;
* `SWAP sz` трактуется как контракты;
* результат описан честно, без выдуманных запусков и тестов.

---

## 13. Приоритеты, если правила конфликтуют

При конфликте ориентироваться в таком порядке:

1. Сохранность торговых инвариантов и безопасности.
2. Согласованная архитектура проекта.
3. Идемпотентность и воспроизводимость.
4. Совместимость с существующим кодом.
5. Локальный стиль конкретного модуля.
6. Общие предпочтения по «красоте» кода.

---

## 14. Итог для Codex

Работай как инженер, который дорабатывает уже согласованную систему, а не проектирует её заново.

Главное:

* не ломай инварианты;
* не переизобретай архитектуру;
* соблюдай стиль пользователя;
* меняй только нужное;
* честно показывай, что реально проверено, а что нет.
