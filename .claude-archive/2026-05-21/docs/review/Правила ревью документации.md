# Правила ревью документации

> Статус документа: методологическая дока по ревью и стандартизации документации.
>
> Документ описывает алгоритм ревью, зоны ответственности групп документов, правила миграции решений и правила работы с формулировками.
>
> Документ не хранит результаты конкретного ревью. Конкретные переносы решений фиксируются в рабочем документе `Миграция решений по документации.md`.

---

# 1. Цель ревью

Ревью документации нужно, чтобы привести документы проекта к состоянию, в котором:

* каждый документ имеет понятную зону ответственности;
* принятые решения и инварианты находятся в правильных смысловых разделах;
* временные Q/A-разделы не остаются в финальных документах как источник истины;
* связанные документы не противоречат друг другу;
* термины, статусы, команды и runtime-семантика используются одинаково;
* документация понятна человеку;
* документация пригодна для последующей оценки объёма, декомпозиции и постановки задач Codex.

Главная цель ревью — не сократить документацию любой ценой, а сделать её точной, согласованной и пригодной для реализации без разночтений.

---

# 2. Что не хранится в этом документе

Этот документ не является журналом найденных проблем и не хранит результаты конкретного ревью.

В нём не фиксируются:

* найденные проблемы по конкретным файлам;
* рекомендации по конкретным правкам;
* список TODO;
* временные архитектурные решения;
* Codex-задачи;
* результаты миграции решений.

Конкретные переносы решений, которые нельзя потерять при чистке документов, фиксируются в рабочем документе:

```text
Миграция решений по документации.md
```

Если в ходе ревью появляется новое постоянное правило проверки документации, оно добавляется в этот документ.

---

# 3. Группы документов и зоны ответственности

## 3.1. Модели

Документы моделей описывают доменную сущность.

В них должны находиться:

* назначение сущности;
* runtime-смысл сущности;
* поля;
* статусы;
* причины финализации / закрытия / problem-state;
* инварианты сущности;
* active / closed / live-risk semantics, если применимо;
* связи с другими сущностями;
* правила создания и обновления внутри домена;
* правила, которые защищают целостность самой сущности.

Модельный документ может ссылаться на процессы, command-layer, mapping или API, но не должен подробно описывать чужую логику.

Примеры модельных документов:

```text
Deal.md
Order.md
AlgoOrder.md
Position.md
BalanceContainer.md
Strategy.md
```

## 3.2. Процессы / lifecycle

Процессные документы описывают порядок работы системы.

В них должны находиться:

* цель процесса;
* кто запускает процесс;
* какие компоненты участвуют;
* какие этапы проходит процесс;
* какие переходы возможны;
* какие факты нужны для перехода дальше;
* как работает retry / recovery / restart;
* как связаны модели, команды, калькуляторы, risk-layer и exchange facts;
* где проходит граница между normal-flow, cleanup-flow, safety-flow и anomaly-flow.

Процессный документ может ссылаться на модели, но не должен подробно дублировать поля сущностей.

Примеры процессных документов:

```text
01. Жизненный цикл сделки.md
FSM этапы сделки.md
Расчёт индикаторов и рыночных данных.md
```

## 3.3. Service commands / executors

Документы command-layer описывают атомарные runtime-команды и правила их исполнения.

В них должны находиться:

* какие `ServiceCommandType` существуют;
* кто создаёт команду;
* кто исполняет команду;
* что делает executor;
* что является ACK;
* что является runtime truth;
* как работает `CREATE -> SUBMIT -> REFRESH`;
* как обновляется `DealActionState`;
* как работает retry policy;
* какие команды относятся к trading-flow, cleanup-flow, safety-flow и read-only refresh-flow.

Command-layer не должен принимать торговые решения и не должен подменять FSM.

Пример документа:

```text
Сервисные команды.md
```

## 3.4. Exchange mapping

Mapping-документы описывают связь внешней биржи с доменной моделью.

В них должны находиться:

* какие exchange endpoints используются;
* какие request fields нужны;
* какие response fields используются;
* какие поля валидируются в client / adapter-layer;
* какие поля попадают в external snapshot;
* как external snapshot обновляет доменную модель;
* как external status / external fact превращается в domain status;
* какие exchange-specific constants используются;
* что является ACK;
* что требует refresh / search / history confirmation.

Mapping-документ не должен заменять доменную модель и не должен становиться источником истины по внутренней FSM-логике.

Примеры mapping-документов:

```text
OKX_Order_mapping.md
OKX_AlgoOrder_mapping.md
OKX_Position_mapping.md
OKX_Balance_mapping.md
```

## 3.5. API

API-документы описывают внешний контракт сервиса.

В них должны находиться:

* endpoint;
* request;
* response;
* сценарии использования;
* ошибки;
* ограничения вызова;
* примеры запросов и ответов.

API-документ не должен становиться источником истины по внутренней FSM, domain model, exchange mapping или risk-policy.

# 4. Индивидуальная зона ответственности документа

Каждый финальный документ должен иметь короткий раздел:

```text
## Зона ответственности документа
```

В этом разделе указывается:

* что именно описывает файл;
* какие решения должны находиться в этом файле;
* какие соседние темы вынесены в другие документы;
* какие документы являются связанными источниками.

Если в документе найдено правило чужой зоны ответственности, оно должно быть:

* перенесено в правильный документ;
* заменено ссылкой на правильный документ;
* или зафиксировано в миграционном backlog, если перенос требует аккуратной проверки.

Пример формулировки:

```markdown
## Зона ответственности документа

Этот документ описывает доменную модель `Position`: назначение, runtime-смысл, поля, статусы, live-risk semantics, инварианты и правила обновления позиции внутри системы.

Exchange-specific mapping позиции для OKX описан в `OKX_Position_mapping.md`.

Участие позиции в общем lifecycle сделки описано в `01. Жизненный цикл сделки.md` и `FSM этапы сделки.md`.
```

Отрицания в разделе зоны ответственности допустимы, если они помогают провести границу между документами.

---

# 5. Что проверяем при ревью

## 5.1. Согласованность

Проверяем:

* одинаково ли называются сущности;
* одинаково ли трактуются статусы;
* одинаково ли используются команды;
* нет ли разных source of truth по одной теме;
* не противоречат ли документы друг другу;
* не описан ли один flow по-разному в разных местах;
* не используются ли старые названия рядом с новыми;
* не осталось ли legacy-решений, которые противоречат текущей архитектуре.

## 5.2. Зоны ответственности

Проверяем:

* лежит ли решение в правильном документе;
* не описывает ли модель чужой процесс;
* не описывает ли процесс поля модели слишком подробно;
* не описывает ли mapping внутреннюю бизнес-логику;
* не описывает ли API внутреннюю FSM-логику;
* не принимает ли command-layer решения, которые должны быть в FSM;
* не принимает ли calculator-layer решения, которые должны быть в risk-layer;
* не принимает ли risk-layer решения, которые должны быть в handler / FSM.

## 5.3. Принятые решения

Проверяем:

* перенесены ли решения из Q/A-разделов в смысловые разделы;
* не остались ли разделы вида `Ответы на вопросы Q1-Q8` как источник истины;
* не потеряны ли инварианты;
* не продублированы ли решения в нескольких местах с разными формулировками;
* не лежит ли решение в документе, который не отвечает за эту область.

## 5.4. Формулировки

Проверяем:

* можно ли заменить лишнее отрицание позитивным описанием ответственности;
* важные запреты оформлены как инварианты;
* правила чужой зоны ответственности перенесены в правильный документ;
* дубли заменены ссылками;
* длинные исторические объяснения заменены текущими правилами;
* формулировки понятны без знания всей истории обсуждений.

# 6. Правила работы с отрицаниями

Отрицания не удаляются механически.

Цель ревью — сохранить смысл решения, но поместить его в правильный документ и правильный раздел.

## 6.1. Лишнее отрицание

Если отрицание просто повторяет границу ответственности, его нужно заменить позитивным описанием.

Плохо:

```text
Position не является копией exchange response.
```

Лучше:

```text
Position хранит runtime-данные, необходимые для сопровождения live-risk позиции.
```

## 6.2. Важный запрет

Если отрицание защищает архитектурное правило, оно остаётся как инвариант.

Пример:

```text
Direct partial close позиции запрещён. Partial exit выполняется через reduce-only Order / AlgoOrder actions.
```

Такое правило нельзя удалять ради красоты текста.

Его нужно оформить как инвариант в документе, который отвечает за соответствующую область.

## 6.3. Чужая ответственность

Если отрицание описывает ответственность другого процесса или сущности, смысл переносится в правильный документ.

Пример:

```text
Position не используется для итогового расчёта PnL сделки.
```

В документе `Position.md` достаточно описать, что `Position` отражает live-risk состояние позиции.

Правило расчёта итогового результата сделки должно находиться в документе, который отвечает за финализацию сделки / `REFRESH_FILLS` / `Deal.resultProfit`.

## 6.4. Граница документа

Отрицание допустимо в разделе `Зона ответственности документа`, если оно помогает понять, какие темы вынесены в соседние документы.

Пример:

```text
Этот документ не описывает OKX-specific mapping позиции; он зафиксирован в `OKX_Position_mapping.md`.
```

# 7. Алгоритм ревью

## 7.1. Выбрать группу документов

Ревью проводится по связанной группе документов, а не по случайному набору файлов.

Для торгового движка допустимо ревьюить весь runtime-контур, но проходы должны быть разделены:

```text
1. Карта ответственности.
2. Сквозная проверка инвариантов.
3. Миграция решений и точечная правка.
```

## 7.2. Определить зоны ответственности

Перед содержательным ревью нужно определить:

* какую область покрывает каждый документ;
* какие решения должны жить в этом документе;
* какие темы должны быть вынесены в соседние документы;
* какой документ является source of truth по каждой сквозной теме.

## 7.3. Прочитать документы без правок

На первом чтении документы не правятся.

Цель — понять текущую картину и найти:

* противоречия;
* дубли;
* устаревшие решения;
* временные Q/A-разделы;
* чужие ответственности;
* лишние отрицания;
* неявные инварианты;
* правила, лежащие не в том файле.

## 7.4. Классифицировать найденные проблемы

Каждую найденную проблему нужно отнести к одному из типов:

```text
1. Оставить здесь и переписать.
2. Перенести в другой документ.
3. Удалить как дубль.
4. Оставить как явный инвариант.
5. Вынести в миграционный backlog.
6. Обсудить отдельно.
```

## 7.5. Согласовать спорные моменты

Если изменение очевидное и безопасное, его можно применить сразу.

Если есть архитектурный выбор, сначала нужно обсудить и согласовать решение.

До явного согласования спорное решение не считается зафиксированным.

## 7.6. Применить правку или создать запись в миграции

После согласования результат ревью должен стать одним из действий:

* правка в документе;
* перенос решения в правильный документ;
* удаление дубля;
* оформление правила как инварианта;
* запись в `Миграция решений по документации.md`;
* открытый вопрос для отдельного обсуждения.

Отдельный список рекомендаций после ревью не ведётся.

## 7.7. Проверить сохранность смысла

После правки нужно проверить:

* не потеряно ли принятое решение;
* не удалён ли важный инвариант;
* не появился ли новый конфликт;
* не осталась ли старая Q/A-формулировка как второй источник истины;
* корректно ли стоят ссылки на связанные документы.

## 7.8. Обновить правила ревью при необходимости

Если в процессе ревью обнаружена повторяющаяся проблема, нужно обновить этот документ.

Пример:

```text
Решения из Q/A-разделов не оставлять в финальной доке. Их нужно переносить в смысловые разделы.
```

---

# 8. Когда использовать миграционный backlog

Запись в `Миграция решений по документации.md` создаётся, если:

* решение важно и его нельзя потерять;
* решение сейчас лежит не в том документе;
* решение нужно перенести в несколько документов;
* перед переносом нужно согласование;
* старый блок можно удалить только после проверки, что смысл перенесён;
* есть риск, что при быстрой правке будет потеряна часть смысла.

Если правка очевидная, локальная и безопасная, её можно внести сразу без записи в backlog.

## 8.1. Рекомендуемый формат миграционной записи

```markdown
| Статус | Текущее место | Смысл решения | Проблема | Куда перенести | Новая формулировка / действие |
|---|---|---|---|---|---|
| TODO | `Position.md`, раздел X | Position хранит только live-risk данные | Часть правила относится к Deal finalization | `Position.md` + `01. Жизненный цикл сделки.md` | В `Position.md` оставить назначение; расчёт PnL перенести в Deal finalization |
```

## 8.2. Статусы миграции

```text
TODO
IN_PROGRESS
MIGRATED
REMOVED
SKIPPED
```

Где:

* `TODO` — перенос ещё не начат;
* `IN_PROGRESS` — перенос выполняется;
* `MIGRATED` — смысл перенесён в правильное место;
* `REMOVED` — старый дубль удалён;
* `SKIPPED` — перенос не нужен, причина должна быть понятна из комментария.

После завершения миграции backlog может быть очищен или удалён.

---

# 9. Результат ревью

Ревью должно завершаться конкретным действием, а не списком рекомендаций.

Допустимые результаты:

* документ исправлен;
* решение перенесено в правильный документ;
* дубль удалён;
* инвариант сохранён в правильном разделе;
* создана запись в миграционном backlog;
* открыт вопрос для обсуждения;
* обновлены правила ревью.

Недопустимый результат:

```text
оставить отдельный список рекомендаций без применения и без миграционного backlog
```

Причина:

```text
Так появляется дополнительный слой документации, который быстро устаревает и размывает источник истины.
```

---

# 10. Финальная проверка после правок

После правки документов нужно проверить:

* каждый документ описывает свою зону ответственности;
* source of truth по теме понятен;
* связанные документы не противоречат друг другу;
* принятые решения не потеряны;
* временные Q/A-разделы удалены после переноса смысла;
* важные запреты сохранены как инварианты;
* лишние отрицания заменены позитивным описанием ответственности;
* правила чужой зоны ответственности перенесены или заменены ссылкой;
* ссылки ведут на конкретные документы;
* документация остаётся пригодной для оценки объёма и дальнейшей декомпозиции.

---

# 11. Сквозные темы для ревью торгового движка

При ревью движка нужно отдельно проверить сквозные темы, которые проходят через несколько документов:

```text
1. Кто создаёт Deal.
2. Кто создаёт и обновляет Position.
3. Как работает CREATE -> SUBMIT -> REFRESH.
4. Что является ACK, а что runtime truth.
5. Где вызывается RiskValidator.
6. Как работает partial exit.
7. Как работает CLOSE_POSITION.
8. Как считается live risk.
9. Как работает Balance freshness.
10. Как работает recovery после restart.
11. Как работают external status resolvers.
12. Как работают ERROR / EMERGENCY_CLOSED / safety-flow.
13. Где считается Deal.resultProfit.
14. Где живут exchange-specific constants.
15. Что является source of truth по статусам.
```

Для каждой сквозной темы должен быть понятен основной документ-источник и документы, которые только ссылаются на него.

---

# 12. Короткое правило

```text
Ревью документации = проверить ответственность, согласованность и сохранность решений.

Результат ревью = правка документа, перенос решения, запись в миграции или открытый вопрос.

Рекомендации после ревью отдельно не храним.
```
