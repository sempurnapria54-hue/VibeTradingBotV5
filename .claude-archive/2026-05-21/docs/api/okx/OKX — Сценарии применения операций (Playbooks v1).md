# OKX — Сценарии применения операций (Playbooks v1)

Ниже — практические сценарии, **как комбинировать операции из твоей таблицы**, включая обязательные проверки, WS/REST
фоллбеки и кейсы «даунтайм/обрыв связи».

> Общая идея: **команду отправили → подтверждение получили → состояние сверили**.
> WS даёт быстрые события, но **в спорных ситуациях финально подтверждаем через REST snapshot + историю (orders/fills)
**.

---

## 0) Базовые правила (общие для всех сценариев)

### 0.1 Источники «правды» (простое правило)

1. **WS private** (`orders/positions/account`) — быстрые изменения в реальном времени.
2. **REST snapshot** (`positions`, `orders-pending`, `order`) — текущее состояние «прямо сейчас».
3. **REST история** (`orders-history`, `fills`) — что реально произошло, если WS был недоступен.

### 0.2 Идемпотентность

* Для создания ордера всегда используем свой `clOrdId` (client order id) — это ключ идемпотентности.
* Для algo (TP/SL/Trailing) — свой `algoClOrdId`.

### 0.3 Обязательные проверки после торговой команды

* **После create/amend/cancel**: либо дождаться события WS `orders`, либо сделать `GET /trade/order` (точечно) для
  финального статуса.
* **После close-position**: проверить `GET /account/positions` (нет позиции) + при необходимости `GET /trade/fills` (
  есть сделка закрытия).
* **После create/cancel algo**: дождаться WS по algo-каналу (если используешь) или сделать REST-check по algo (если у
  тебя есть такой запрос в наборе).

### 0.4 CancelUnknownOrders=true (твоя политика)

Если приложение при старте/восстановлении находит на бирже ордера, которых нет в БД/журнале стратегии — **снимаем** (
cancel) и логируем.

---

## 1) S0 — Холодный старт / рестарт приложения (синхронизация окружения)

**Цель:** восстановить истину «что сейчас на бирже» и привести БД к консистентному состоянию.

**Шаги:**

1. `GET /account/balanceExternalSnapshot?ccy=USDT` — понять доступные средства.
2. `GET /account/positions?instId=...` — получить позиции по инструменту.
3. `GET /trade/orders-pending?instId=...` — получить висящие ордера.
4. (Опционально) `GET /trade/fills` (последние 3 дня) — чтобы быстро закрыть «дыру» по факту исполнения во время
   даунтайма.
5. Применить политику:

    * если позиция есть → переходим в режим «управление позицией».
    * если позиции нет, но есть ордера → решаем: (a) продолжаем стратегию, (b) cancel unknown orders.

**Финальная проверка:** БД отражает текущее состояние биржи (позиция/ордера) + проставлены статусы.

---

## 2) S1 — Открыть позицию маркетом + сразу поставить SL/TP

**Цель:** быстро войти в рынок и **сразу** защититься стопом.

**Шаги:**

1. Подготовка входа:

    * `GET /public/instruments?...` — есть `Instrument` + `dynamicSpec` (tick/lot/min).
    * Цена: WS `tickers` (основной) или REST `GET /market/ticker` (fallback).
    * Рассчитать `sz` (контракты) с учётом `lotSz/minSz`.
2. `POST /trade/order` (market) — отправили entry.
3. Подтверждение entry:

    * ждать WS `orders` (filled/partially_filled) **или** `GET /trade/order`.
4. Убедиться, что позиция появилась:

    * ждать WS `positions` **или** `GET /account/positions`.
5. Поставить защиту:

    * Вариант A (предпочтительный): `POST /trade/order-algo` — выставить SL (и TP) как algo (TP/SL/Trailing).
    * Вариант B: если твой create order поддерживает attach TP/SL — можно прикрепить сразу при создании (тогда шаг 5
      идёт вместе с шагом 2).
6. Подтверждение SL/TP:

    * дождаться WS по algo-каналу (если подключён) или проверить через REST по algo (если используешь).

**Критический момент:** если вход уже исполнен, а SL ещё не успели поставить — это окно риска. Поэтому:

* либо ставим attach TP/SL сразу при create,
* либо ставим algo сразу после подтверждения fill.

---

## 3) S2 — Открыть позицию лимиткой (ордер висит) + управление ордером

**Шаги:**

1. Подготовка как в S1 (spec + ticker + расчёт размера).
2. `POST /trade/order` (limit).
3. Подтверждение создания:

    * WS `orders` (state=live) или `GET /trade/order`.
4. Ордер висит — дальше 3 варианта:

    * A) **Ждём исполнения**: просто мониторим WS `orders`.
    * B) **Двигаем цену**: `POST /trade/amend-order` → затем проверка (WS или `GET /trade/order`).
    * C) **Отменяем**: `POST /trade/cancel-order` → затем проверка.
5. Если ордер исполнился (filled/partially_filled) → переходим к постановке SL/TP как в S1.

**Кейс partial fill:**

* Если ордер частично исполнился, позиция уже существует.
* SL/TP лучше ставить **на фактический размер позиции** (см. `positions`) либо выставлять защиту на рассчитанную долю.

---

## 4) S3 — «Двигаем SL по трейлингу вручную» (твоя стратегия)

**Цель:** каждые N секунд/тиков подтягивать SL вслед за ценой.

**Предусловие:** позиция открыта.

**Петля управления (в рантайме):**

1. Источник цены: WS `tickers` (или свечи WS `candle...` если ты привязываешь SL к свечам).
2. Стратегия рассчитывает новый уровень SL:

    * например: `newSL = max(oldSL, lastPrice - X%)` для long.
3. Обновление SL:

    * Вариант A: если SL — это algo trailing/stop, то чаще делается через **отменить старый algo + создать новый** (если
      биржа не поддерживает amend конкретного типа).
    * Вариант B: если биржа позволяет amend algo (зависит от типа) — используешь amend.
4. Подтверждение: WS algo-канал или REST проверка.

**Защита от флуда:**

* Добавь debounce: не обновлять SL чаще чем раз в X секунд и только если изменение > tickSz * K.

---

## 5) S4 — Цена дошла до «расчётного TP»: что делать?

Ты писал, что хочешь не фиксировать TP, а «дать прибыли течь» и закрываться по стопу.

Варианты:

* **Вариант A (трендовый):**

    * TP не ставим вообще.
    * Ведём позицию только трейлинг-SL (algo trailing или твой ручной обновляемый SL).
    * Когда цена растёт — SL подтягиваем.
* **Вариант B (комбинированный):**

    * Ставим частичный TP (например TP1) + трейлинг-SL на остаток.
    * Тогда нужен механизм частичных закрытий (отдельный reduce-only ордер) и пересчёт SL на остаток.

**Технически:**

* Тейк как algo — `POST /trade/order-algo`.
* Частичный тейк — отдельный ордер `POST /trade/order` reduce-only.
* После частичного закрытия — проверяем позицию `positions` и при необходимости корректируем SL.

---

## 6) S5 — Аварийно закрыть позицию маркетом (safety-кнопка)

**Команда:** `POST /trade/close-position`.

**Почему нужна проверка:** close-position — это команда, но финальный факт закрытия зависит от исполнения.

**Шаги:**

1. Отправили `close-position`.
2. Ждём подтверждение:

    * WS `positions` (позиция стала 0 / исчезла) и/или WS `orders` (появились закрывающие сделки).
3. **Обязательная проверка через REST:**

    * `GET /account/positions?instId=...` — позиции нет (или размер 0).
4. Если позиция всё ещё есть:

    * повторить close-position (с защитой от бесконечных повторов)
    * или выставить reduce-only market ордер на остаток (если close-position по какой-то причине не сработал).
5. После закрытия:

    * отменить все algo по инструменту (SL/TP/Trailing), чтобы не осталось «висящих» защитных ордеров.
    * `GET /trade/orders-pending?instId=...` — убедиться, что нет ордеров.

---

## 7) S6 — Отмена ордера (обычная) + проверка

**Шаги:**

1. `POST /trade/cancel-order`.
2. Подтверждение:

    * WS `orders` → state=canceled
    * или `GET /trade/order`.
3. Если REST показывает, что ордер уже filled/partially_filled:

    * значит отмена не успела → переходим к управлению позицией (S1/S3) или закрытию.

---

## 8) S7 — Даунтайм/обрыв связи: «что произошло, пока нас не было?»

**Цель:** восстановить события и финальные статусы.

**Шаги восстановления:**

1. Snapshot (как S0): balanceExternalSnapshot + positions + orders-pending.
2. Найти «расхождения»:

    * В БД ордер был live, а на бирже его нет → значит он либо filled, либо canceled.
3. Восстановить финал:

    * `GET /trade/orders-history` (если укладываемся в 7 дней)
    * если старше → `GET /trade/orders-history-archive`
    * `GET /trade/fills` (или `fills-history`) — фактические исполнения.
4. Обновить БД:

    * Ордеру поставить финальный статус.
    * Если были fills → обновить позицию/закрытие позиции.

**Главная мысль:**

* **fills** = «что реально исполнилось».
* **orders-history** = «финальный статус ордера, даже если он отменён без сделок».

---

## 9) S8 — WS упал в рантайме (но приложение живо)

**Шаги:**

1. Переключаемся на временный REST polling:

    * `GET /trade/orders-pending` (реже)
    * `GET /account/positions` (реже)
    * `GET /market/ticker` (чаще, если нужна цена)
2. Когда WS восстановился:

    * делаем snapshot (S0-lite) и убеждаемся, что всё консистентно.

---

## 10) S9 — Повторная отправка create/amend/cancel (ретраи) и «непонятный результат»

**Проблема:** запрос мог уйти на биржу, но ответ не дошёл.

**Правильный алгоритм:**

1. Повторяем запрос (retry) ограниченное число раз.
2. Если ретраи закончились — **не гадаем**, а проверяем:

    * Для create: `GET /trade/order` по `clOrdId` или `GET /trade/orders-pending`.
    * Для amend/cancel: `GET /trade/order` по `ordId/clOrdId`.
3. Только после проверки принимаем решение: повторить/считать успехом/зафиксировать ошибку.

---

## 11) S10 — Открыли позицию, но SL/TP не выставился (или выставился частично)

**Шаги:**

1. Позиция есть (positions).
2. Проверяем наличие активных algo защит:

    * через WS algo-канал или REST по algo.
3. Если защит нет:

    * немедленно выставляем SL (минимум) через `order-algo`.
4. Если часть защит есть (например SL есть, TP нет):

    * решаем по стратегии: ставим недостающую или отключаем TP и ведём трейлингом.

---

## 12) S11 — Закрыли позицию, но остались ордера/алго

**Почему так бывает:**

* SL/TP/Trailing могут жить отдельно и не всегда автоматически исчезают.

**Шаги:**

1. Закрыли позицию (S5) и убедились через `positions`.
2. `GET /trade/orders-pending` — если есть ордера → cancel.
3. `POST /trade/cancel-algos` — снять все algo по инструменту.
4. Финально проверить, что:

    * `positions` пусто
    * `orders-pending` пусто

---

## 13) S12 — Поставить SL сразу при входе vs после входа

* Если биржа позволяет «attach» TP/SL прямо в create order — это лучший вариант (меньше окно риска).
* Если нет — ставим сразу после подтверждения fill.

Практический компромисс:

* Для market-entry: сначала entry → сразу SL-algo.
* Для limit-entry: можно заранее приготовить SL-algo, но аккуратно — он не должен сработать до появления позиции.

---

## 14) S13 — Расчёт размера ордера (USDT → контракты) и валидация

**Шаги:**

1. `Instrument.dynamicSpec` → `lotSz/minSz/tickSz`.
2. Цена (ticker).
3. Конвертация USDT → контракты.
4. Округление:

    * размер округляем вниз по `lotSz`.
    * если < `minSz` → не торгуем.
5. Перед отправкой ордера можно дополнительно проверить лимиты `maxMktSz/maxLmtSz`.

---

## 15) S14 — Проверка лимитов и «неожиданный отказ биржи»

Если биржа вернула ошибку (code/msg):

1. Сохраняем `lastRequestId/lastAttemptAt/lastCreateResultCode/Message` в доменной сущности.
2. В зависимости от ошибки:

    * ошибки сети/таймауты → retry + verify (S9).
    * «некорректный размер/шаг» → обновить spec (`public/instruments`) и пересчитать.
    * «недостаточно маржи/лимит» → проверить balanceExternalSnapshot/positions и уменьшить риск.

---

## 16) Карта «какие проверки к какой операции» (очень коротко)

* **create order** → проверить `orders` (WS) или `GET /trade/order`, затем `positions`.
* **amend order** → проверить `GET /trade/order`.
* **cancel order** → проверить `GET /trade/order` или `orders-pending`.
* **create algo (SL/TP/Trailing)** → проверить algo-статус (WS/REST).
* **cancel algo** → проверить, что algo исчез/стал canceled.
* **close-position** → обязательно `GET /account/positions` + при необходимости `fills`.

* Или расписать отдельно «main flow» (BPMN/Activity) именно для управления ордерами/позициями с защитой от рестарта.
