# Active / Closed semantics по сущностям

## Цель

Эта дока фиксирует:

* что считается **активной сущностью в БД**;
* что считается **активной сущностью на бирже**;
* что значит **закрытие сущности**;
* какие правила должны использовать refresh-flow, kill-switch и anomaly snapshots.

Без такого соглашения дальше невозможно стабильно проектировать:

* `Refresh*Executor`;
* `TradeRuleValidator`;
* `KillSwitchService`;
* `AnomalyReport`.

---

## Общий принцип

Нужно различать:

* **active in DB** — сущность ещё участвует в живом торговом процессе или риске;
* **active on exchange** — сущность на бирже ещё может повлиять на риск / исполнение / состояние инструмента;
* **closed in domain** — локальная система считает сущность завершённой;
* **closed on exchange** — на бирже сущность больше не живая.

Это не всегда одно и то же, поэтому правила должны быть зафиксированы отдельно для каждой сущности.

---

## 1. Position

### Active in DB

Позиция считается активной в БД, если одновременно:

* `Position.Status = ACTIVE`
* размер позиции больше 0

То есть одной только записи недостаточно — позиция должна реально отражать живой риск.

### Active on exchange

Позиция считается активной на бирже, если:

* позиция присутствует в ответе биржи по инструменту;
* и её размер не равен 0.

### Closed on exchange

Позиция считается закрытой на бирже, если:

* позиция отсутствует в ответе по инструменту;
* либо возвращается размер 0.

### Closed in domain

Позиция считается закрытой в домене, если:

* статус переведён из `ACTIVE` в финальный закрытый статус;
* сохранён корректный `closeReason`.

### Что значит закрытие позиции

Закрытие позиции — это не удаление записи, а перевод в завершённое состояние с понятной причиной.

---

## 2. Order

### Active in DB

Обычный ордер считается активным в БД, если он находится в одном из live-статусов.

Рекомендуемое правило:

* использовать единый доменный метод вроде `order.isLive()`

То есть refresh и kill-switch не должны вручную угадывать список статусов каждый раз.

### Active on exchange

Обычный ордер считается активным на бирже, если его внешний статус означает, что ордер ещё живой:

* он ещё может исполниться;
* он ещё висит на бирже;
* он ещё не финализирован.

Для OKX это должно быть зафиксировано отдельно в mapping-правилах внешнего статуса → доменный статус.

### Closed on exchange

Ордер считается закрытым на бирже, если он больше не находится в live-состоянии:

* исполнен;
* отменён;
* завершён иначе.

### Closed in domain

Ордер считается закрытым в домене, если его статус переведён в финальное состояние.

Важно:

* если в доменной модели есть более точные финальные статусы, лучше использовать их;
* не сводить всё к безликому `CLOSED`, если можно точнее различить финал.

---

## 3. AlgoOrder

### Active in DB

Algo-ордер считается активным в БД, если он находится в одном из live-статусов.

Рекомендуемое правило:

* использовать единый доменный метод вроде `algoOrder.isLive()`

### Active on exchange

Algo-ордер считается активным на бирже, если его внешний статус означает, что он:

* действует;
* ожидает срабатывания;
* ещё может повлиять на рынок или защиту позиции.

### Closed on exchange

Algo-ордер считается закрытым на бирже, если он больше не находится в live/pending состоянии:

* отменён;
* исполнен;
* завершён иначе.

### Closed in domain

Algo-ордер считается закрытым в домене, если его статус переведён в финальное завершённое состояние.

---

## 4. Deal

### Active in DB

Сделка считается активной в домене, если она не находится в terminal-состоянии.

То есть:

* не `CLOSED`
* не `ERROR`

### Active on exchange

У сделки как агрегата нет прямого состояния на бирже.

Сделка отражается через связанные сущности:

* позицию;
* ордера;
* algo-ордера.

Поэтому для неё active на бирже — это derived-понятие через живые биржевые сущности.

### Closed in domain

Сделка считается закрытой в домене, если:

* перешла в `CLOSED` как нормальный финал;
* либо в `ERROR` как аварийный финал.

### Что важно для kill-switch

Если kill-switch сработал по инструменту и по этому инструменту есть живая сделка, её нужно перевести в правильный
terminal статус.

Обычно это:

* `Deal.Status.ERROR`
* корректный `closeReason`, например аварийный

---

## 5. Balance

Баланс не имеет semantics active / closed как position или order.

Это snapshot сущность.

Для него важны:

* актуальность snapshot;
* принадлежность бирже;
* корректное обновление полей.

---

## Как использовать эти semantics в коде

## Для refresh executors

Нужно работать только с **active / live** сущностями.

Например:

* `RefreshPositionExecutor` читает активные позиции;
* `RefreshPendingOrdersExecutor` читает живые ордера;
* `RefreshAlgoOrdersExecutor` читает живые algo-ордера.

Нельзя для операционных действий читать всё по инструменту без фильтра по статусам.

---

## Для kill-switch

### Action-state

Для реальных действий kill-switch должен работать только с живыми сущностями:

* active positions
* live orders
* live algo-orders

### Report snapshot

Для `AnomalyReport` нужен более широкий срез:

* `active`
* `relatedInactive`

То есть можно разделять snapshot примерно так:

```json
{
  "instrument": {},
  "active": {
    "positions": [],
    "orders": [],
    "algoOrders": [],
    "deals": []
  },
  "relatedInactive": {
    "positions": [],
    "orders": [],
    "algoOrders": [],
    "deals": []
  }
}
```

Важно:

* `relatedInactive` — это не вся история по инструменту;
* это только ограниченный полезный хвост, который нужен для расследования.

---

## Что должно быть зафиксировано отдельно в коде

Нужно, чтобы для каждой сущности были явные правила в одном месте:

* какие доменные статусы считаются live;
* какие внешние статусы считаются live;
* какие статусы означают финал;
* какой mapping внешнего статуса в доменный статус используется.

Это лучше не разносить по десяткам сервисов вручную.

---

## Короткий итог

Нужно жёстко разделить:

* **active in DB**;
* **active on exchange**;
* **closed in domain**;
* **closed on exchange**.

Для `Position`, `Order`, `AlgoOrder`, `Deal` эти semantics должны быть явно зафиксированы.

Операционные refresh / kill-switch действия работают только с active/live сущностями.

`AnomalyReport` хранит более широкий snapshot по инструменту: `active` + `relatedInactive`.
