# Команда REFRESH_BALANCE — executor flow

## Цель

Команда `REFRESH_BALANCE` нужна для синхронизации актуального баланса биржи в локальную БД.

Это обычная sync-команда.

На текущем этапе её задача простая:

* прочитать актуальный баланс на бирже;
* привести доменную модель `Balance` в актуальное состояние;
* сохранить snapshot в БД.

---

## Главное отличие от позиций / ордеров / algo-ордеров

Баланс — это не торговая сущность жизненного цикла сделки.

Баланс не является:

* открытой позицией;
* ордером;
* algo-ордером;
* отдельным шагом FSM.

Баланс — это snapshot состояния средств по бирже.

Поэтому:

* у `REFRESH_BALANCE` нет сложного state-machine поведения;
* у `REFRESH_BALANCE` нет своего kill-switch сценария;
* у `REFRESH_BALANCE` на текущем этапе не нужен `TradeRuleValidator`.

---

## Уровень команды

`REFRESH_BALANCE` — это команда уровня **биржи**, а не инструмента.

Хотя команда может исполняться в контексте сделки, сам баланс привязан не к инструменту, а к бирже.

То есть ключ хранения такой:

* `exchangeId`
* `currency`

Не:

* `instrumentId`
* не `dealId`

---

## Кто выполняет команду

Команда должна выполняться через отдельный executor:

* `ServiceCommandExecutor`
* `RefreshBalanceExecutor`

Фасадный `BalanceService` может существовать как удобная точка входа, но use-case команды должен жить в
`RefreshBalanceExecutor`.

---

## Правильная цепочка вызовов

```text
Handler
  -> ServiceCommandExecutor
     -> RefreshBalanceExecutor
        -> ClientService.getBalanceContainer(exchange)
        -> обычный sync balance snapshot в БД
```

Важно:

* `REFRESH_BALANCE` не должен идти через `TradeRuleValidator`;
* `REFRESH_BALANCE` не должен вызывать `KillSwitchService`;
* `REFRESH_BALANCE` не должен менять `DealContext` напрямую.

После выполнения команды orchestrator при необходимости заново читает `DealContext`.

---

## Входные данные

Для выполнения команды нужен:

* `Exchange exchange`

На текущем этапе `instrument` и `dealId` для refresh balance не нужны.

Рекомендуемая сигнатура:

```java
public void execute(Exchange exchange)
```

---

## Источник данных

Источник правды для команды — внешний snapshot баланса с биржи.

Ожидаемый flow такой:

* клиентский слой запрашивает баланс на бирже;
* получает контейнер внешнего snapshot;
* executor преобразует / применяет snapshot к локальным `Balance` сущностям;
* локальные записи сохраняются в БД.

---

## Как хранить баланс

Баланс должен храниться как snapshot по бирже и валюте.

Ключевая уникальность:

* `exchangeId`
* `currency`

Например:

* OKX + USDT
* OKX + BTC
* OKX + ETH

Каждая такая запись — отдельная сущность `Balance`.

---

## Какой expected flow внутри executor

### Шаг 1. Получить внешний snapshot баланса

Через клиентский сервис биржи:

```java
BalanceContainerExternalSnapshot externalSnapshot = clientService.getBalanceContainer(exchange)
```

Если snapshot пустой — это отдельный case обработки, но на первом этапе можно трактовать это как отсутствие данных и
просто ничего не обновлять либо логировать.

### Шаг 2. Разложить контейнер по валютам

Если контейнер содержит несколько балансов по валютам, executor должен пройтись по ним поштучно.

То есть working unit — это одна валюта внутри контейнера.

### Шаг 3. Найти существующую запись в БД

По ключу:

* `exchangeId`
* `currency`

### Шаг 4. Применить внешний snapshot

Если запись существует:

* обновить поля доменной модели через mapper / доменный update method.

Если записи нет:

* создать новую `Balance`;
* заполнить обязательные поля;
* применить snapshot;
* сохранить.

### Шаг 5. Сохранить изменения

Каждый баланс должен быть сохранён в БД.

---

## Что значит “обновить баланс”

Обновление баланса — это не частичный patch и не журнал операций.

Это refresh snapshot.

То есть локальная запись должна отражать актуальное состояние, которое пришло с биржи на момент запроса.

Например, должны обновляться поля вроде:

* `available`
* `frozen`
* `total`
* `externalUpdatedAt`
* при необходимости другие поля snapshot

---

## Что делать, если запись не найдена

Если баланс по валюте и бирже ещё не существует в БД:

* создать новую запись;
* привязать её к `exchangeId`;
* записать валюту;
* применить snapshot;
* сохранить.

Это нормальный сценарий.

---

## Что не должен делать RefreshBalanceExecutor

`RefreshBalanceExecutor` не должен:

* валидировать торговые правила;
* запускать anomaly flow;
* блокировать инструмент;
* вызывать kill-switch;
* принимать решения FSM;
* работать с позициями, ордерами и algo-ордерами.

Это чистый snapshot-sync use-case.

---

## Какой слой должен резолвить внешний snapshot

Предпочтительная модель:

* client layer получает `BalanceContainerExternalSnapshot`;
* executor или `BalanceService` применяет его к доменной модели;
* mapper обновляет поля доменной сущности.

То есть не нужно вручную раскладывать десятки полей в executor, если уже есть mapper-стиль проекта.

* `BalanceService`

* `BalanceDataService`

* `BalanceMapper`

---

## Поведение при повторном запуске

Команда должна быть идемпотентной:

* повторный вызов просто обновляет те же balance snapshot записи;
* дубликаты не должны появляться;
* upsert идёт по `exchangeId + currency`.

---

## Инварианты команды

### До выполнения

* известна биржа;
* настроен клиент биржи;
* доступен persistence-слой.

### После успешного выполнения

* локальная БД отражает актуальный snapshot баланса по бирже;
* по каждой валюте есть актуальная запись;
* повторный запуск не создаёт дубликатов.

---

## Короткий итог

`REFRESH_BALANCE` — это обычная sync-команда уровня биржи.

Она:

* получает внешний balance snapshot;
* обновляет или создаёт локальные `Balance` записи по `exchangeId + currency`;
* сохраняет их в БД;
* не участвует в kill-switch / anomaly / validator flow на текущем этапе.
