# Аварийные executors — семантика статусов и причин

## Цель

Эта дока фиксирует, как должны завершать сущности аварийные executors.

Сейчас проблема в том, что executors слишком примитивны:

* просто ставят `CLOSED`;
* не фиксируют причину;
* не используют явные доменные переходы.

Для kill-switch этого недостаточно.

---

## Общий принцип

Аварийный executor не должен делать “глухой setStatus(...)”.

Он должен:

* использовать доменный переход;
* фиксировать понятную причину завершения;
* сохранять итоговую сущность в корректном финальном состоянии.

---

## 1. ClosePositionExecutor

### Что правильно

Для позиции уже есть нормальная идея:

* использовать доменный переход типа `toClose(...)`
* передавать `CloseReason.EMERGENCY_CLOSE`

### Что это значит

Позиция должна завершаться не просто как “закрыта”, а как:

* аварийно закрыта;
* с понятной причиной.

Это хороший пример для остальных сущностей.

---

## 2. CancelOrderExecutor

### Текущая проблема

Сейчас executor просто делает:

* `order.setStatus(CLOSED)`

Это слишком грубо.

### Что нужно

Нужен доменный переход для обычного ордера, который явно означает:

* ордер отменён kill-switch сценарием;
* это не нормальное завершение по happy-path.

Примеры направлений:

* `toCanceledByKillSwitch()`
* `toClose(Order.CloseReason.KILL_SWITCH)`
* либо другой согласованный доменный метод

Главное:

* не raw `setStatus(...)`
* причина должна быть явной.

---

## 3. CancelAlgoOrderExecutor

### Текущая проблема

Сейчас executor просто делает:

* `algoOrder.setStatus(CLOSED)`

Это тоже слишком грубо.

### Что нужно

Нужен доменный переход, который явно означает:

* algo-ордер отменён аварийным сценарием;
* это kill-switch, а не обычная бизнес-логика.

Примеры направлений:

* `toCanceledByKillSwitch()`
* `toClose(AlgoOrder.CloseReason.KILL_SWITCH)`
* либо другой согласованный доменный метод

Главное — зафиксировать причину аварийного завершения.

---

## 4. DealEmergencyFinalizer

### Что нужно

Если по инструменту есть живая сделка, она должна быть переведена в terminal аварийное состояние.

Ожидаемая семантика:

* `Deal.Status.ERROR`
* `Deal.CloseReason.EMERGENCY_STOP`

Лучше тоже использовать доменный переход, а не raw set полей.

Пример направления:

* `deal.toError(Deal.CloseReason.EMERGENCY_STOP)`
* либо другой согласованный метод

---

## Почему это важно

Если оставить примитивные `setStatus(...)`, то потом будет сложно:

* различать happy-path и аварийный финал;
* расследовать закрытие;
* корректно строить отчёты;
* развивать доменную модель дальше.

Нормальный kill-switch должен оставлять после себя понятную доменную картину.

---

## Что должно быть у каждой сущности

Для каждой сущности нужно зафиксировать:

* какой финальный статус ставится при kill-switch;
* какая причина используется;
* какой доменный метод выполняет этот переход.

То есть для:

* `Position`
* `Order`
* `AlgoOrder`
* `Deal`

должны быть явные правила аварийного финала.

---

## Минимальный допустимый шаг

Если прямо сейчас в модели ещё нет всех нужных доменных методов, допустимо:

* сначала добавить эти методы;
* затем перевести executors на них.

Но нельзя оставлять надолго примитивный стиль:

* `setStatus(CLOSED)`
* без причины
* без явной семантики

---

## Короткий итог

Аварийные executors должны завершать сущности не “как-нибудь”, а через явные доменные переходы с понятной причиной.

Для kill-switch это критично.

Идея такая:

* позиция → аварийно закрыта;
* обычный ордер → отменён kill-switch;
* algo-ордер → отменён kill-switch;
* сделка → `ERROR` + `EMERGENCY_STOP`.
