# KillSwitchService — оркестрация аварийного сценария по инструменту

## Цель

`KillSwitchService` — это сервис полного аварийного снятия риска по инструменту.

Он нужен для ситуаций, когда обычный flow больше нельзя считать безопасным.

Но в новой архитектуре он не должен руками закрывать сущности внутри себя.

Он должен **оркестрировать** аварийный сценарий через специализированные executors.

---

## Главное назначение

`executeKillSwitch(...)` должен привести инструмент в безопасное состояние.

Под безопасным состоянием понимается:

* на бирже нет открытых позиций по инструменту;
* на бирже нет pending обычных ордеров по инструменту;
* на бирже нет active/pending algo-ордеров по инструменту;
* в БД нет живых сущностей, выглядящих как продолжающийся торговый процесс по инструменту.

---

## Роль в архитектуре

`KillSwitchService` — не валидатор и не sync-сервис.

Он:

* собирает initial action-state;
* блокирует инструмент;
* вызывает аварийные executors;
* собирает after-state;
* проверяет, всё ли зачистилось;
* возвращает `KillSwitchResult`.

Он не должен:

* определять, есть аномалия или нет;
* создавать `AnomalyReport`;
* руками менять статусы позиций, ордеров и algo-ордеров внутри себя;
* вызывать refresh-executors.

---

## Рекомендуемая сигнатура

```java
public KillSwitchResult executeKillSwitch(Exchange exchange,
                                          Instrument instrument,
                                          Long dealId,
                                          String reasonCode)
```

Kill-switch выполняется **по инструменту**, а не по одной сделке.

`dealId` используется только как дополнительный контекст.

---

## Какие executors должен вызывать KillSwitchService

### Для позиции

* `ClosePositionExecutor`

### Для обычных ордеров

* `CancelOrderExecutor`

### Для algo-ордеров

* `CancelAlgoOrderExecutor`

### Для сделки

* `DealEmergencyFinalizer` или аналогичный executor

### Для инструмента

* `InstrumentBlockExecutor` или аналогичная логика блокировки

---

## Почему так лучше

Если `KillSwitchService` сам начинает:

* отменять ордера;
* закрывать позиции;
* руками менять доменные статусы;

то он становится слишком толстым и дублирует логику специализированных сервисов.

Кроме того, так легче получить циклические зависимости.

Правильнее:

* каждый executor делает свою часть;
* сам вызывает биржу;
* сам обновляет локальное состояние своей сущности;
* `KillSwitchService` остаётся оркестратором.

---

## Какие состояния должен читать KillSwitchService

### 1. Action-state

Нужен для реальных действий.

Для него нужно читать только **живые / actionable** сущности.

#### Из БД:

* активные позиции;
* живые обычные ордера;
* живые algo-ордера.

#### С биржи:

* открытые позиции;
* pending обычные ордера;
* active/pending algo-ордера.

Важно:

* нельзя читать просто всё по инструменту без фильтра по статусам;
* исторических сущностей со временем станет слишком много.

### 2. Report snapshot

Нужен для after-снимка.

Это уже полный релевантный срез по инструменту для `AnomalyReport`.

Он может включать:

* active сущности;
* related inactive сущности;
* статус инструмента;
* связанные сделки.

## Полный flow executeKillSwitch(...)

### Шаг 1. Собрать action-state до действий

Нужно вычитать:

* живые внутренние позиции, ордера, algo-ордера;
* живые внешние позиции, ордера, algo-ордера.

Это состояние используется именно для принятия аварийных действий.

---

### Шаг 2. Заблокировать инструмент

Нужно перевести инструмент в состояние, при котором по нему нельзя продолжать новые торговые действия.

Это должно произойти до аварийных executors.

---

### Шаг 3. Отменить все живые обычные ордера

Через `CancelOrderExecutor`.

Executor сам:

* снимает ордера на бирже;
* обновляет локальные статусы;
* сохраняет изменения в БД.

---

### Шаг 4. Отменить все живые algo-ордера

Через `CancelAlgoOrderExecutor`.

Executor сам:

* снимает algo-ордера на бирже;
* обновляет локальные статусы;
* сохраняет изменения в БД.

---

### Шаг 5. Закрыть все открытые позиции

Через `ClosePositionExecutor`.

Executor сам:

* закрывает позицию на бирже;
* обновляет локальную позицию в БД;
* сохраняет close reason / статус.

---

### Шаг 6. Аварийно завершить сделки по инструменту

Если по инструменту есть живая сделка, её нужно перевести в нужное аварийное состояние.

Например:

* `Deal.Status.ERROR`
* соответствующий `closeReason`

Это должен делать отдельный executor, а не `KillSwitchService` руками.

---

### Шаг 7. Собрать after-state

После завершения всех executors нужно заново прочитать полное состояние по инструменту.

Из этого состояния формируются:

* `internalAfter`
* `externalAfter`

Это должны быть **полные слепки по инструменту**, а не только action-state.

---

### Шаг 8. Проверить успешность

Kill-switch считается успешным, если одновременно:

* на бирже нет открытых позиций;
* на бирже нет pending обычных ордеров;
* на бирже нет active/pending algo-ордеров;
* в БД нет активной позиции;
* в БД нет живых обычных ордеров;
* в БД нет живых algo-ордеров;
* связанные сделки переведены в нужное аварийное состояние.

---

### Шаг 9. Вернуть `KillSwitchResult`

Результат должен содержать:

* `success`
* `internalAfter`
* `externalAfter`
* `message`

Этот результат используется `TradeRuleValidator` для завершения `AnomalyReport`.

---

## Что важно про слепки

В `AnomalyReport` должны лежать **полные слепки по инструменту**:

* `internalBefore`
* `externalBefore`
* `internalAfter`
* `externalAfter`

Причём имеет смысл делить их на:

* `active`
* `relatedInactive`

Потому что для расследования полезно видеть:

* что было живым по инструменту;
* какие связанные уже неактивные сущности тоже участвовали в картине.

Но для action-state kill-switch должен работать только с живыми сущностями.

---

## Что не должен делать KillSwitchService

`KillSwitchService` не должен:

* вычитывать все сущности по инструменту без фильтра по статусам для операционных действий;
* руками обновлять локальные статусы сущностей;
* звать refresh-executors;
* звать `TradeRuleValidator`;
* создавать `AnomalyReport`.

---

## Короткий итог

Новая роль `KillSwitchService` такая:

* это оркестратор аварийного сценария по инструменту;
* он собирает action-state;
* блокирует инструмент;
* вызывает специализированные аварийные executors;
* собирает полный after-snapshot;
* возвращает `KillSwitchResult`.

Он не должен дублировать логику закрытия сущностей внутри себя.
