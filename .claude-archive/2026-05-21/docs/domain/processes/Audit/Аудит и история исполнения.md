# 1. Главная идея

Аудит и история исполнения нужны для объяснения прошлого:

* почему была создана сделка;
* какая стратегия и какой action привели к действию;
* какая runtime-команда выполнялась;
* какая runtime-сущность была создана или изменена;
* чем закончилась попытка исполнения;
* были ли ошибки и retry;
* какие факты подтвердили финальное состояние.

Главное правило:

> Аудит не является источником runtime-логики FSM.
>
> FSM не должна читать историю, чтобы решить, что делать дальше.

Для runtime-восстановления используется:

```text
DealContext
DealActionState
Order / AlgoOrder / Position / BalanceContainer
exchange snapshots
refresh/search/history facts
```

Для объяснения прошлого будет использоваться история исполнения команд и история изменений сущностей, но их финальные модели проектируются отдельно.

---

# 2. Инварианты аудита

* `Order`, `AlgoOrder`, `Position` не хранят `strategyActionId`, `strategyActionKey`, role или level стратегии.
* Runtime-связь `StrategyAction -> runtime entity` хранится в `DealActionState`.
* `DealActionState` — operational state для FSM, а не аудит.
* `ServiceCommand` — runtime object, а не persisted command queue.
* История исполнения команд не должна становиться durable queue.
* История изменения сущностей не должна заменять `DealActionState`.
* Подробный entry context хранится в истории, а не в `Deal`.
* `shutdownReason` должен быть виден в timeline сделки, но не заменяет `closeReason`.
* `CLOSED` и `EMERGENCY_CLOSED` должны различаться в отчётах: штатный terminal-финал и аварийный terminal-финал.
* `ENTRY_CONDITION_EXPIRED` должен отображаться как нормальное закрытие candidate Deal без live risk, а не как авария.
* Direct partial close позиции запрещён. Partial exit должен быть объясним через `Order / AlgoOrder`, fills/history/refresh и `DealActionState`.
* `REFRESH_BALANCE` должен попадать в историю исполнения команд, потому что баланс влияет на risk decisions.

---

# 3. Что аудит не должен делать

Аудит не должен:

* управлять FSM;
* быть источником решения, какие команды создать;
* заменять `DealActionState`;
* быть единственным источником восстановления после рестарта;
* хранить operational-lock состояние;
* быть command queue.

Runtime-логика не должна зависеть от чтения исторических таблиц.

---

# 4. Что аудит должен объяснять

Аудит должен помогать человеку понять:

* почему появился `Deal`;
* какой `entryReason` и `entryStepType` были у сделки;
* почему был запущен graceful shutdown;
* почему сделка попала в `ERROR`;
* как был выполнен safety-flow / kill-switch;
* почему сделка стала `EMERGENCY_CLOSED`;
* какие команды выполнялись;
* какие команды были retryable / failed / skipped;
* какие refresh/search/history facts подтвердили состояние;
* как partial exit был материализован через `Order / AlgoOrder`;
* почему `DealActionState` перешёл в `COMPLETED`, `FAILED`, `SKIPPED` или `RETRY_PENDING`.

# 6. Текущий статус

Зафиксировано точно:

* аудит не источник runtime-логики FSM;
* `Order`, `AlgoOrder`, `Position` не хранят `strategyActionId`;
* связь action стратегии с runtime-сущностью для FSM хранится в `DealActionState`;
* `ServiceCommand` не является persisted queue;
* `REFRESH_BALANCE` должен попадать в историю исполнения команд;
* модели истории команд и сущностей ещё не финализированы;
* flow записи истории ещё не финализирован.


# 7. Дополнение после Q2–Q8

Этот раздел добавлен без финализации моделей истории и без изменения базовых правил аудита.

## 7.1. Risk-layer в аудите

Risk-layer подробно описывается в документе `Оценка рисков`.

В будущей истории исполнения желательно уметь объяснить:

```text
какой RiskCheckCode был получен;
какой RiskCheckSeverity был у результата;
какое решение вернул RiskBlockResolver;
какой handler принял runtime-решение после RiskBlockAction;
почему action был разрешён, пропущен, отложен или заблокирован.
```

Для `BLOCKED` risk result нужно различать два больших сценария:

```text
PRECHECK, live risk ещё не создан
  -> candidate Deal закрывается без ERROR;
  -> closeReason может быть ENTRY_RISK_BLOCKED или другое согласованное значение risk-layer.

ENTRY_SUBMITTED / ENTRY_FINALIZED / PROTECTION_SWITCHED / MANAGING / EXIT_PENDING
  -> Deal переводится в ERROR;
  -> дальше работает ErrorHandler / safety-flow.
```

Аудит должен объяснять не только сам факт блокировки, но и почему handler выбрал конкретную реакцию.

## 7.2. Ошибки расчёта и unexpected exceptions

После Q3 и Q8 нужно различать:

```text
CalculationError
  -> controlled ошибка расчёта;
  -> например нет свежего ATR, не удалось рассчитать size, controlled validation case.

Unexpected exception
  -> ошибка вне нормального расчётного результата;
  -> ловится на границе DealOrchestratorJob / FSM execution boundary.
```

Для unexpected exceptions используются базовые коды:

```text
INTERNAL_ERROR
EXCHANGE_ERROR
VALIDATION_ERROR
```

Смысл для аудита:

```text
INTERNAL_ERROR
  -> баг приложения, NPE, mapper, неожиданное состояние, внутренняя техническая проблема.

EXCHANGE_ERROR
  -> timeout, connection reset, gateway/API error, ошибка клиента биржи,
     не удалось надёжно завершить exchange operation.

VALIDATION_ERROR
  -> нарушение инварианта / валидации, которое не должно было попасть в runtime.
```

`EXCHANGE_ERROR` может быть retryable.

`INTERNAL_ERROR` и `VALIDATION_ERROR` по умолчанию non-retryable.

## 7.3. Уточнение по UNKNOWN_RESULT / EXCHANGE_TIMEOUT

В старых формулировках открытых вопросов мог встречаться пункт:

```text
UNKNOWN_RESULT / EXCHANGE_TIMEOUT
```

После Q6 это нужно читать так:

```text
UNKNOWN_RESULT не используем.
EXCHANGE_TIMEOUT отдельно не используем.
Используем единый код EXCHANGE_ERROR.
```

Для timeline это означает:

```text
показываем EXCHANGE_ERROR как проблему взаимодействия с биржей;
не строим отдельную runtime-семантику UNKNOWN_RESULT;
ACK от биржи не является truth;
финальный факт подтверждается refresh/search/history.
```

## 7.4. CLOSE_POSITION, autoCxl и refresh-контур

После Q5 в аудите нужно будет объяснять flow полного закрытия позиции.

Доменная команда:

```text
CLOSE_POSITION
```

не содержит `autoCxl` / `autoCancelOrders` в payload.

Если конкретный exchange-adapter для OKX проставит `autoCxl=true`, это техническая exchange-specific деталь.

Доменная логика не должна считать, что auto-cancel гарантированно убрал все хвосты.

После `CLOSE_POSITION` в timeline должны быть видны refresh-команды:

```text
REFRESH_POSITION
REFRESH_PENDING_ORDERS
REFRESH_ALGO_ORDERS
REFRESH_ORDER_HISTORY
REFRESH_ALGO_ORDER_HISTORY
REFRESH_FILLS
```

Если после refresh остались известные сделке live `Order` / `AlgoOrder`, они отменяются отдельными командами:

```text
CANCEL_ORDER
CANCEL_ALGO_ORDER
```

Если найдены неизвестные / чужие хвосты на бирже, это anomaly / safety-flow, а не штатный cleanup сделки.

## 7.5. REFRESH_FILLS

`REFRESH_FILLS` — runtime read-only команда.

На текущем этапе `Fill` как отдельную persisted entity не храним.

`RefreshFillsExecutor` должен:

```text
загрузить fills;
сопоставить их с известными Order / AlgoOrder / Position facts;
обновить вложенные runtime-сущности;
не обновлять Deal напрямую.
```

`Deal` обновляет FSM handler по фактам вложенных сущностей.

Для будущего аудита открытым остаётся вопрос:

```text
храним ли raw fills / normalized fills в истории;
или фиксируем только итоговые изменения Order / AlgoOrder / Position.
```

## 7.6. ServiceCommand runtime object и история исполнения

`ServiceCommand` остаётся runtime object.

История исполнения команд, если будет создана, не должна становиться durable command queue.

Для аудита это значит:

```text
можно хранить факт попытки исполнения runtime ServiceCommand;
можно хранить command payload snapshot;
можно хранить result/error snapshot;
но runtime recovery не должен читать историю как источник pending-команд.
```

Источник runtime recovery остаётся:

```text
DealContext
DealActionState
Order / AlgoOrder / Position / BalanceContainer
exchange facts
refresh/search/history facts
```

# 8. Открытые вопросы после Q2–Q8

Эта секция не заменяет раздел `5. Открытые вопросы`, а уточняет, какие вопросы остаются актуальными после Q2–Q8.

## 8.1. Snapshot format

Остаётся открытым формат snapshot'ов для:

```text
command execution history;
entity history;
AnomalyReport;
KillSwitch report;
SynchronizeExecutionEnvironmentReport.
```

Нужно решить:

```text
храним internal domain snapshot;
храним external raw snapshot;
храним оба;
храним before/after;
храним diff или полный snapshot;
маскируем ли поля;
как группируем refresh-driven изменения.
```

## 8.2. Timeline grouping

Остаётся открытым, как показывать человеку цепочки:

```text
CREATE -> SUBMIT -> REFRESH;
CLOSE_POSITION -> refresh contour -> cleanup;
retry attempts;
EXCHANGE_ERROR;
REFRESH_FILLS;
partial exit через Order / AlgoOrder / fills;
ERROR -> EMERGENCY_CLOSED.
```

## 8.3. История risk и calculation decisions

Нужно решить, будут ли отдельные записи для:

```text
RiskCheckResult;
RiskBlockAction;
CalculationError;
controlled skipped action;
temporary calculation retry;
unexpected exception.
```

Пока это не финализируется.
