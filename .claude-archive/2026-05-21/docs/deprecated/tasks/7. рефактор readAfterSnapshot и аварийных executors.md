# Задание для Codex — рефактор readAfterSnapshot и аварийных executors

## Цель

Нужно сделать два связанных улучшения:

1. переработать `readAfterSnapshot(...)`, чтобы он перестал тащить неограниченную историю по `instrumentId`;
2. улучшить аварийные executors, чтобы они завершали сущности через осмысленные доменные переходы, а не через
   примитивные `setStatus(CLOSED)`.

Нужно сделать это без большого разрушительного рефакторинга.

---

## Контекст

Сейчас архитектура уже стала лучше:

* `TradeRuleValidator` ведёт anomaly flow;
* `KillSwitchService` стал orchestrator'ом;
* `beforeSnapshot` собирается отдельно;
* есть отдельные аварийные executors.

Но остаются две проблемы:

### Проблема 1. `readAfterSnapshot(...)`

Сейчас after-snapshot потенциально читает слишком много по `instrumentId` и со временем может разрастись в мусорный
дамп.

### Проблема 2. Аварийные executors слишком примитивны

Сейчас некоторые executors просто делают:

* `setStatus(CLOSED)`

Это слишком грубо и не фиксирует явную причину kill-switch завершения.

---

## Часть 1 — рефактор `readAfterSnapshot(...)`

### Что нужно изменить концептуально

After-snapshot не должен быть:

* всей историей по инструменту;
* и не должен быть только голым active-state.

Нужно перейти к модели:

* `active`
* `relatedInactive`

### Что значит `active`

Это все живые сущности по инструменту после kill-switch.

### Что значит `relatedInactive`

Это ограниченный набор уже завершённых сущностей, которые нужны для расследования именно этого аварийного сценария.

---

### Что сделать технически

Нужно переработать чтение after-snapshot так, чтобы:

* для внутренней части он не тянул всё подряд по `instrumentId`;
* использовал хотя бы ограниченный набор данных;
* был пригоден для расследования.

Минимально acceptable вариант:

* `active` читается как сейчас по live statuses;
* `relatedInactive` строится из сущностей из `beforeSnapshot`, которые после kill-switch перестали быть живыми;
* плюс при необходимости добавляется текущая/последняя аварийно завершённая `Deal`.

То есть не нужно тащить весь архив по инструменту.

---

### Что допускается на первом этапе

Для внешней части after-snapshot допустимо оставить:

* только `active` через существующие биржевые active endpoints

Если history endpoints для внешних сущностей пока не хочется подключать — это нормально.

Но внутренняя часть должна стать аккуратнее.

---

### Что вернуть по этой части

Нужно вернуть:

* обновлённый подход в `StateSnapshotReader.readAfterSnapshot(...)`
* при необходимости — расширенную модель `StateSnapshot`
* при необходимости — helper для построения `relatedInactive`
* при необходимости — небольшие изменения в `JsonUtils`, чтобы snapshot сериализовался в новой структуре

---

## Часть 2 — рефактор аварийных executors

### Что сейчас плохо

Сейчас некоторые executors завершают сущности слишком примитивно.

Примеры нежелательного стиля:

* `order.setStatus(CLOSED)`
* `algoOrder.setStatus(CLOSED)`

Так делать не нужно.

---

### Что нужно

Каждый аварийный executor должен использовать осмысленный доменный переход.

#### Position

Для позиции уже есть хороший стиль:

* `toClose(EMERGENCY_CLOSE)`

Это правильный ориентир.

#### Order

Нужно уйти от raw `setStatus(CLOSED)` и перейти к явному доменному переходу.

Направление:

* `toCanceledByKillSwitch()`
* или `toClose(Order.CloseReason.KILL_SWITCH)`
* или другой согласованный метод

Главное:

* причина должна быть явной
* переход должен быть доменным

#### AlgoOrder

То же самое.

Нужно уйти от raw `setStatus(CLOSED)` и перейти к доменному переходу.

Направление:

* `toCanceledByKillSwitch()`
* или `toClose(AlgoOrder.CloseReason.KILL_SWITCH)`
* или другой согласованный метод

#### Deal

Если ещё не приведено к доменному переходу — тоже желательно уйти от простого набора полей и использовать осмысленный
аварийный переход.

---

## Что делать, если доменных методов пока нет

Если в модели ещё нет нужных доменных методов, их нужно добавить минимально необходимым образом.

То есть:

* сначала добавить доменный переход;
* потом перевести executor на него.

Нельзя надолго оставлять примитивное `setStatus(...)` без причины.

---

## Какие классы вероятнее всего затронутся

По этой задаче могут затронуться:

* `StateSnapshotReader`
* `StateSnapshot`
* `JsonUtils`
* `CancelOrderExecutor`
* `CancelAlgoOrderExecutor`
* `ClosePositionExecutor` (если нужно только выровнять стиль — минимально)
* `DealEmergencyFinalizer`
* domain модели `Order`, `AlgoOrder`, `Deal` — если не хватает доменных методов перехода

---

## Что не нужно делать

На этом этапе НЕ нужно:

* переписывать весь `TradeRuleValidator`
* менять FSM
* менять отдельную команду `EXECUTE_KILL_SWITCH`
* полностью проектировать идеальную внешнюю history-модель snapshot
* делать большой рефактор unrelated сущностей

---

## Code style

Следовать стилю проекта:

* не использовать множественные объявления переменных;
* всегда ставить фигурные скобки;
* чистый Spring / DDD стиль;
* не генерировать лишний код;
* если можно — возвращать только нужные новые классы и точечные изменения.

---

## Ожидаемый результат

После выполнения задачи должно быть так:

* `readAfterSnapshot(...)` больше не тянет бездумно всю историю по `instrumentId`;
* after-snapshot становится расследовательским, а не мусорным;
* аварийные executors не делают примитивных `setStatus(CLOSED)` без причины;
* завершение `Order`, `AlgoOrder`, `Deal` становится доменно осмысленным;
* kill-switch оставляет после себя понятную и читаемую картину в `AnomalyReport`.
