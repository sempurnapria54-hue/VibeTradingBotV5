# ADR-0008: Журнал open-questions

**Статус:** Proposed
**Дата:** 2026-05-15
**Контекст:** Стратегия миграции `docs/domain/` в `docs/spec/`. Новый артефакт для фиксации концептуальных и рабочих вопросов проекта.
**Связанные ADR:** ADR-0002 (стандарт документа `docs/spec/`), ADR-0003 (разделение `docs/` и `.claude/`), ADR-0006 (принципы спецификации), ADR-0007 (структура `docs/spec/`), ADR-0009 (стратегия миграции).

## Context

В проекте есть `.claude/planning/backlog.md` — список рабочих задач, единый по ADR-0003. Backlog отвечает на вопрос «что делать».

В legacy `docs/domain/` накопились две группы открытых вопросов:

- **Встроенные open-questions** в model/process документах: четыре документа имеют собственные блоки open-questions (`Аудит и история исполнения.md`, `Сервисные команды.md`, `FSM этапы сделки.md`, `Жизненный цикл сделки.md`).
- **Корневой документ-список** `docs/domain/Открытые вопросы по движку.md` — 13 пронумерованных формальных вопросов про runtime-движок.

ADR-0002 (стандарт документа `docs/spec/`) уже зафиксировал: spec-документы не содержат встроенных открытых вопросов. Поэтому при миграции legacy → spec встаёт вопрос: куда переносить эти ~30+ открытых вопросов?

Backlog не подходит как единый ответ:

- Не все вопросы — рабочие задачи. Концептуальные вопросы (с альтернативами и последствиями) — кандидаты на ADR, не на пункт backlog.
- Не каждый вопрос вообще требует действия. Некоторые могут оказаться устаревшими, некоторые — некорректно сформулированными.
- Backlog как «список задач» теряет фокус, если в него попадает 30+ концептуальных вопросов.

Плюс: в ходе обычной работы над проектом (не миграционной) тоже возникают концептуальные вопросы. Сейчас они теряются в истории чата или попадают в backlog как неоднородные пункты.

ADR-0008 фиксирует **новый артефакт** — журнал open-questions — со своей структурой, статусами, классификацией. Журнал отвечает на вопрос «какие концептуальные и рабочие вопросы зафиксированы», в отличие от backlog'а («что делать»).

ADR-0008 описывает **структуру и правила работы с журналом**. Применение журнала при миграции — в ADR-0009.

## Decision

Семь подразделов.

### 1. Артефакт и расположение

Создаётся новый файл: **`.claude/questions/open-questions.md`** — журнал открытых вопросов проекта.

- Тип артефакта: append-only по структуре (закрытые вопросы не удаляются, переходят в раздел «Closed»), живой по содержанию (вопросы могут перемещаться между статусами, к ним добавляются заметки).
- Назначение: единый каталог концептуальных и рабочих вопросов проекта.
- Природа: рабочий артефакт, не source-of-truth по системе (spec — для системы; журнал — для незакрытых вопросов о системе).

Папка `.claude/questions/` — новая. Создаётся при создании журнала. В будущем папка может содержать тематические подфайлы (если один файл станет слишком большим), но стартует с одного файла.

Расположение в `.claude/`, не в `docs/` — по ADR-0003: журнал относится к **работе над проектом** (рабочий артефакт процесса), не к **продуктовой документации**.

### 2. Структура entry

Каждый вопрос — отдельный entry с 11 полями:

| Поле | Тип | Описание |
|---|---|---|
| `id` | строка | Стабильный идентификатор вида `Q-NNN`. Не меняется при перемещении entry между разделами. Используется для ссылок из ADR/spec/backlog. |
| `title` | строка (1 строка) | Краткое название вопроса. Для оглавления и ссылок. |
| `formulation` | текст | Буквальная формулировка вопроса. |
| `source` | текст | Откуда взялся вопрос: legacy-документ + раздел (для миграционных), либо «обсуждение от YYYY-MM-DD», либо «текущая работа над X». |
| `added` | дата | Дата заведения entry. |
| `status` | enum | Один из: `Added`, `In-progress`, `Resolved`. См. §3. |
| `classification` | enum | Один из. См. §4. Присваивается при добавлении entry; может уточниться при разборе, но не остаётся пустой. |
| `context` | текст (1-3 абзаца) | Контекст вокруг вопроса. Чтобы при ревью не нужно было лезть в исходный документ. |
| `related` | список | Другие Q-N, связанные с этим (если есть). Помогает видеть кластеры вопросов. |
| `notes` | список | Append-only датированные заметки по ходу разбора. Не редактируются после добавления. |
| `resolution` | текст | Заполняется при переходе в `Resolved`. Содержит: где решён вопрос (ADR-NNNN / spec-документ + раздел / коммит) или явное обоснование устаревания. |

### 3. Статусы

Три статуса:

- **`Added`** — заведён в журнал. Классифицирован при добавлении. Не в активной работе.
- **`In-progress`** — взят в ревью или разбор. Это сигнал, что вопрос сейчас обсуждается в сессии или серии сессий, не забыт.
- **`Resolved`** — финальный. Указано, где решён вопрос (см. поле `resolution`). При переходе в этот статус — entry перемещается из основного раздела в раздел «Closed».

Перемещение между разделами «Open» и «Closed» — при переходе в `Resolved`. До этого entry остаётся в основном разделе независимо от статуса.

### 4. Классификация

Семь значений. Классификация описывает **природу вопроса** и сразу намечает его судьбу.

**Вопросы, требующие решения:**

- **`concept`** — концептуальный пробел. Вопрос требует решения с альтернативами и последствиями. Типичная судьба: разбор в чате → принятие ADR. Пример: «как именно работает kill-switch при orphan-Position».

- **`missing-model`** — отсутствует модель или структура. Не описано, как должна выглядеть. Типичная судьба: разбор в чате → описание в существующем или новом spec-документе. Пример: «структура DealActionState».

- **`contradiction`** — противоречие между источниками. Один документ говорит одно, другой — другое. Типичная судьба: разбор в чате → выбор стороны или примирение через новое решение. Пример: «в FSM этапы.md и в Сервисные команды.md разная последовательность переходов Order».

**Рабочая задача:**

- **`structural`** — техническое уточнение «как лучше структурировать». Не концептуальное, нужно просто решить и сделать. Типичная судьба: разбор в чате → пункт в backlog или прямое исполнение. Пример: «в каком разделе Strategy.md описывать StrategyMarketStructureSetting».

**Кандидаты на устаревание:**

- **`legacy-bug`** — замеченная ошибка или некорректная формулировка в legacy. Типичная судьба: ревью → подтверждение устаревания → `Resolved` с обоснованием. Пример: «устаревшее упоминание переименованного класса».

- **`obsolete-by-decision`** — вопрос уже решён где-то (ADR / spec / коммит), но был зафиксирован параллельно в legacy. Типичная судьба: подтверждение со ссылкой на решение → `Resolved`.

- **`obsolete-by-context`** — контекст вопроса исчез из системы (модель/процесс/концепция больше не существует или замещены). Типичная судьба: подтверждение со ссылкой на решение, устранившее контекст → `Resolved`.

### 5. Условия устаревания

Вопрос помечается классификацией obsolete-* или legacy-bug при добавлении в журнал, но **финальное удаление** (переход в `Resolved` с пустым результирующим действием в системе) требует обоснования. Допустимые обоснования — три условия:

**Условие 1: содержательное решение зафиксировано.**

Должна быть **явная ссылка** на ADR / раздел spec-документа / коммит, где этот вопрос **закрыт по существу**. Не «похожая тема обсуждалась», а буквально: ссылка отвечает на вопрос. Перечитывание вопроса и ссылки должно показать, что вопрос исчерпан.

**Условие 2: контекст вопроса исчез.**

Вопрос относился к модели/процессу/концепции, которой больше не существует в проекте. Требуется ссылка на решение (ADR / коммит / commit-message), которое устранило контекст.

**Условие 3: вопрос некорректно сформулирован.**

Вопрос основан на ложной премиссе или ошибочной формулировке. Требуется явное обоснование: что именно ошибочно. Не «вопрос непонятный», а «вопрос предполагал, что X, но в системе X не существует».

Если ни одно условие не выполнено — вопрос **не устарел**. Default-действие: остаётся в журнале со статусом `Added` или `In-progress`, ждёт разбора.

### 6. Связь с другими артефактами

**С backlog.**

Backlog содержит **задачи на разбор** групп Q-N, не сами вопросы. Например:

> `[ ] Разобрать concept-вопросы из кластера C1 (Q-007, Q-009, Q-012).`

При закрытии задачи на разбор — задача уходит в «Закрытые» backlog, соответствующие Q-N в журнале получают финальный статус `Resolved`.

**С Knowledge Curator.**

Knowledge Curator при обнаружении изменения статуса Q-N на `Resolved` выполняет проверку:

1. Текстовый поиск в `docs/spec/` всех упоминаний этого Q-N (через grep по `Q-NNN`).
2. Для каждого найденного места — проверка, что соответствующий раздел spec-документа **обновлён** в соответствии с полем `resolution`.
3. Если найдено упоминание, но обновления не сделано (раздел всё ещё содержит «см. Q-NNN» как заглушку) — автоматически создаётся пункт в backlog:

> `[ ] Q-NNN закрыт. Обновить разделы spec-документов с inline-ссылкой: <путь>, <путь>.`

Это **дополнение к существующему промпту Knowledge Curator**, не новый агент.

**С inline-ссылками в spec-документах.**

В spec-документах разрешена **только одна форма** пометки незавершённости — короткая inline-ссылка вида «см. Q-NNN» в местах, где описание неполно из-за нерешённого вопроса. Сам вопрос — в журнале, не в spec.

Пример:

> Поле `closeReason` — назначение и допустимые значения уточняются (см. Q-007).

или короче:

> Поле `closeReason` — см. Q-007.

Запрещено: формулировка вопроса в теле spec, развёрнутые обсуждения, TODO-комментарии.

Чек-лист Сценария 7 в playbook (создание/обновление документа спецификации) уточняется: «Нет встроенных открытых вопросов как самостоятельных формулировок. Допустима inline-ссылка «см. Q-NNN»».

### 7. Шаблон и скилл

**Шаблон:** `.claude/templates/documents/open-questions-journal.md` — шаблон самого журнала. Применяется один раз при создании файла журнала. Содержит:

- Шапку с описанием назначения файла.
- Разделы «Open» и «Closed».
- Блок «Как пользоваться» — короткая инструкция.
- Пример заполненного entry как живая инструкция, остающаяся в файле.

Шаблон **не для entry** в отдельности; шаблонизация одного entry — раздел «Пример entry» внутри шаблона журнала.

`templates/documents/README.md` дополняется новой строкой в общей таблице.

**Скилл:** `.claude/skills/open-questions-workflow/SKILL.md` — операционная процедура работы с журналом. Активируется при работе с `.claude/questions/open-questions.md`. Что делает:

- При добавлении entry — проверяет полноту полей, генерирует следующий `Q-N` на основе максимального существующего.
- При смене статуса — проверяет, что для перехода в `Resolved` заполнено поле `resolution` со ссылкой.
- При закрытии — переносит entry из «Open» в «Closed», не теряя историю.
- Проверяет связные обновления: если в backlog была задача со ссылкой на Q-N, и Q-N перешёл в `Resolved` — задача в backlog должна быть отмечена закрытой.

Скилл — параллель `spec-document-workflow` для жанра журнала.

## Alternatives

**По расположению журнала:**

- *`.claude/planning/`* — рядом с backlog. Отброшен. Backlog — про задачи, журнал — про вопросы. Это два разных жанра, объединение в одной папке размывает границу.
- *`.claude/notes/`* — рабочие заметки. Отброшен. Notes — расходный материал для одной сессии. Журнал — постоянный артефакт, переживает сессии и должен быть видимым.
- *`docs/`* — рядом с продуктовой документацией. Отброшен. По ADR-0003 рабочие артефакты процесса работы с Claude — в `.claude/`. Журнал не описывает систему, описывает открытые вопросы по системе — это процесс работы.
- *Выбран: новая папка `.claude/questions/`.*

**По размеру файла:**

- *Несколько тематических файлов с самого начала (по подсистемам или по кластерам миграции).* Отброшен. На старте — преждевременная сегментация. Размер первой партии (~30-50 Q-N после миграции легаси) укладывается в один файл. При росте — можно разделить тематически в той же папке.
- *Один файл навсегда.* Не отброшен жёстко, но и не зафиксирован. Решение откладывается до момента, когда один файл станет неудобным. В этом ADR — стартуем с одного файла.

**По размеру набора статусов:**

- *Расширенный набор (Open / Classified / In-progress / Closed-by-ADR / Closed-by-spec / Closed-as-obsolete / Closed-merged).* Отброшен как избыточный. Различие «как именно закрыт» сохраняется в поле `resolution`, не нужно отдельного статуса.
- *Минималистичный набор (Open / Closed).* Отброшен. Отсутствие промежуточного `In-progress` теряет важный сигнал «сейчас в работе, не забыт».
- *Выбран: три статуса (Added / In-progress / Resolved).*

**По размеру набора классификаций:**

- *Меньший набор (концептуальный / рабочий / устаревший — 3 значения).* Отброшен. Слишком грубо. Не различает missing-model (нужно дописать) и contradiction (нужно выбрать); устаревший не различает причин (это влияет на условие обоснования).
- *Больший набор (отдельные значения для каждой причины устаревания + ADR-кандидат vs ADR-предложение, и т.д.).* Отброшен как избыточный. Различия второго порядка можно зафиксировать в `notes` или `resolution`.
- *Выбран: семь значений, покрывающих природу вопроса и сразу намечающих его судьбу.*

**По связи с backlog:**

- *Сами Q-N как пункты backlog.* Отброшен (см. Context).
- *Полное разделение: backlog не знает про журнал, журнал не знает про backlog.* Отброшен. Задачи на разбор групп Q-N — естественная роль backlog (это работа). Без связи теряется механизм планирования разбора.
- *Выбран: журнал хранит вопросы, backlog содержит задачи на разбор групп Q-N со ссылками. Knowledge Curator автоматизирует синхронизацию при закрытии Q-N со ссылками в spec.*

## Consequences

### Артефакты, которые создаются

- `.claude/questions/open-questions.md` — журнал. Создаётся как заготовка по шаблону, без entry на старте. По ходу миграции (см. ADR-0009) пополняется Q-N.
- `.claude/questions/` — новая папка.
- `.claude/templates/documents/open-questions-journal.md` — шаблон.
- `.claude/skills/open-questions-workflow/SKILL.md` — скилл.

### Артефакты, которые обновляются

- `.claude/templates/documents/README.md` — добавляется новая строка в таблице шаблонов: для шаблона журнала.
- `.claude/agents/knowledge-curator.md` — добавляется логика автозавода задач в backlog при закрытии Q-N с висящими inline-ссылками в `docs/spec/`.
- `.claude/flow/playbook.md` — в чек-листе Сценария 7 уточняется правило про inline-ссылки «см. Q-NNN».
- `.claude/working-with-claude.md` — упоминание журнала как одного из артефактов знаний.

### Применение журнала при миграции

Процедура использования журнала при миграции каждого документа из `docs/domain/` (выписать open-questions, классифицировать, добавить Q-N, обработать inline-ссылки в новых spec-документах) — описана в ADR-0009.

### Что не меняется

- Backlog (`.claude/planning/backlog.md`) — продолжает быть **единым** по ADR-0003. Журнал не делит backlog по типам; они **дополняют** друг друга.
- ADR-0002 (стандарт документа `docs/spec/`) — без изменений. Уточняется только чек-лист сценария 7 в playbook (правило inline-ссылок).
- Существующие ADR (0001-0005) — не затрагиваются.

### Связь с другими ADR

- **ADR-0002.** Чек-лист сценария 7 в playbook уточняется (правило inline-ссылок «см. Q-NNN»). Сам стандарт документа из ADR-0002 не меняется.
- **ADR-0003** (разделение `docs/` и `.claude/`). Журнал в `.claude/questions/` следует ADR-0003: рабочий артефакт процесса работы → в `.claude/`.
- **ADR-0006** (принципы спецификации). Концептуальные вопросы по применению принципов ADR-0006 при миграции попадают в журнал как `concept`-классификация.
- **ADR-0007** (структура `docs/spec/`). Inline-ссылки «см. Q-NNN» появляются в документах `docs/spec/` в соответствии с правилами этого ADR.
- **ADR-0009** (стратегия миграции). Описывает операционный план применения журнала при миграции.
