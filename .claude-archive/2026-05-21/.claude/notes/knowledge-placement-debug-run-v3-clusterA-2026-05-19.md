### Фрагмент 2 corpus: 12 крупных файлов смешивают вопросы намеренно — это рабочая практика, не ошибка

**Источник:** corpus-отчёт, раздел «Фрагмент 2: 12 крупных файлов
смешивают вопросы намеренно — это рабочая практика, не ошибка»
(первоисточник — `artifact-question-mapping-2026-05-18.md`, раздел
«Смешанные»).

**Цитата:**

> «12 крупных файлов смешивают вопросы намеренно (хабы, snapshot,
> скиллы). Это не ошибка — это рабочая практика. Приём
> "вопросы-маркеры" должен либо разрешить намеренные смеси (через
> подразделы-маркеры внутри файла), либо нарезать хабы на части.»

**Результат применения скилла v3:**

```
Классификация:
- Измерение: PIPELINE
- Основные категории: L-ADR + L-CONV PIPELINE
  (Шаг 1(б): обоснование с альтернативой (нарезать vs разрешить
  смеси) → L-ADR; правило применения (как помечать смешанные
  разделы) → L-CONV PIPELINE. Два связных артефакта.)
- Основной вопрос:
  - L-ADR: «почему намеренные смеси легитимны, а не нарезаются на
    отдельные файлы?»
  - L-CONV PIPELINE: «как разметить разделы файла, когда они
    отвечают на разные характеристические вопросы?»
- Тег: precedent (правило выходит за один кейс — задаёт основу
  для всех хабов/snapshot/скиллов).

Место хранения:
- Целевой файл (L-ADR): [планируется: ADR-PIPELINE про
  «намеренные смеси и разметка вопросов внутри файла»].
- Целевой файл (L-CONV PIPELINE): Шаг 2(ж) — конвенция отсутствует
  (см. ниже).
- Промежуточное хранение: strategy-summary v7 + corpus-нота.

Связные обновления:
- `CLAUDE.md` — сам по себе намеренная смесь (M-NAV + L-CONV +
  M-PIPE по таблице corpus-ноты). Кандидат на первую разметку.
- Скилл `knowledge-placement` — неявно предполагает «один
  фрагмент — одно место»; нужно учесть «фрагмент → раздел
  внутри смешанного файла» в Шаге 2.
- Конфликт с ADR-0002 §3 (жанровая чистота) — только для PRODUCT
  spec; для PIPELINE-артефактов жанровая чистота не фиксирована.
  Новое правило не отменяет ADR-0002.

Развилка конвенции (Шаг 2(ж)):
- Категория классифицирована: L-CONV PIPELINE.
- Конвенция размещения для случая «семантическая пометка раздела
  внутри смешанного файла как ответа на конкретный
  характеристический вопрос» отсутствует. Это не файл и не
  каталог, а **режим разметки** существующего артефакта.
- Развилка системная (повторится на всех 12 смешанных файлах
  из corpus-ноты + на будущих хабах/snapshot/скиллах) → нести
  в «Открытые расширения карты».
- Варианты решения конвенции:
  (а) разметка через подзаголовок-маркер («## L-CONV: …», «##
      M-NAV: …») в каждом разделе смешанного файла;
  (б) frontmatter-поле `mixed: true` + таблица соответствия
      «раздел → вопрос-маркер» в шапке файла;
  (в) внешний индекс-файл (например,
      `.claude/conventions/mixed-files-index.md`), мапящий
      «файл:раздел → вопрос-маркер»;
  (г) нарезка хабов на части (отказ от смесей) — альтернатива,
      опровергаемая самим фрагментом.

Открытые расширения карты:
- «Семантическая разметка внутри файла» как механизм не
  покрыта Шагом 2(б)–(е) (это не новый каталог и не новая
  ячейка). Шаг 2(ж) фиксирует развилку, не закрывает её.
```

**Сравнение с v2:**

- **Что изменилось.** v2 заканчивала на «Открытые расширения
  карты: разметка вопросов-маркеров внутри файла как механизм
  — не файл и не каталог; Шаг 2(д) формально не покрывает». v3
  через Шаг 2(ж) даёт **именованный** статус развилке —
  «конвенция размещения отсутствует», и поле «Развилка
  конвенции» в выходном формате содержит явный список вариантов
  решения. Шаг 4(д) применён: формулировка как
  «решение об общем правиле», не «куда положить этот
  фрагмент».
- **Адресует ли правка v3 буксование.** Да. v2-сигнал к v3 на
  этом фрагменте: «случай "фрагмент → раздел разметки внутри
  смешанного файла" не формализован». v3 формализует его через
  (ж)+(д)+поле «Развилка конвенции».
- **Побочные эффекты.** Категории/тег идентичны v2. Появилась
  явная развилка системного характера → в «Открытые расширения
  карты», как предусмотрено Шагом 4(д) в v3.

### Фрагмент 13 corpus: append-only — policy редактирования артефакта, не invariant модели или поведения

**Источник:** corpus-отчёт, раздел «Фрагмент 13» (первоисточник —
`pipeline-spec-fitting-2026-05-18.md`, метамодель 5).

**Цитата:**

> «Append-only как принцип на уровне всего документа. Это не
> "инвариант структуры" (структура полей) и не "инвариант
> поведения" (FSM модели) — это **policy** редактирования
> артефакта. Ближе к convention о работе с артефактом, чем к
> свойству самой модели. Текущий шаблон lifecycle принимает
> append-only как инвариант поведения, но это натяжка.»

**Результат применения скилла v3:**

```
Классификация:
- Измерение: PIPELINE
- Основные категории: L-CONV PIPELINE + L-ADR
  (Шаг 1(б): обоснование «append-only — policy, не invariant»
  → L-ADR; само правило «правила редактирования живут в
  convention» → L-CONV PIPELINE.)
- Основной вопрос:
  - L-ADR: «почему append-only классифицируется как L-CONV
    PIPELINE (policy), а не как L-SPEC PIPELINE invariant у
    метамодели ADR?»
- Тег: precedent (расщепление «свойство артефакта vs правило
  работы с артефактом» применимо ко многим случаям).
- Связь с v2-фрагментом 11 (append-only временно): фрагмент 11
  v2 — про **временное отключение** правила; этот фрагмент —
  про **классификацию слоя**, где правило живёт.

Место хранения:
- Целевой файл (L-ADR): [планируется: ADR-PIPELINE про
  классификацию append-only как L-CONV].
- Целевой файл (L-CONV PIPELINE): Шаг 2(ж) — конвенция
  отсутствует (см. ниже).
- Промежуточное хранение: strategy-summary v7 + corpus-нота.

Связные обновления:
- Конфликт с ADR-0008 (open-questions-journal) — фиксирует
  append-only для `notes` как invariant entry. Это локальный
  invariant поля, не documentation-wide policy — не противоречит.
- `.claude/working-with-claude.md` раздел «ADR — правила»
  содержит формулировку «ADR append-only»; место правила.
- `.claude/adr/README.md` — содержит правила работы с ADR;
  кандидат на L-SKILL/L-CONV расщепление.
- Связь с v2-фрагментом 11: temporary-rule (append-only
  отключается на Этапе 1) опирается на это правило.

Развилка конвенции (Шаг 2(ж)):
- Категория классифицирована: L-CONV PIPELINE (policy
  редактирования) + L-ADR (обоснование классификации).
- Конвенция размещения для случая «policy редактирования
  как пометка существующего журнала-артефакта (ADR-журнал,
  Q-N-журнал)» отсутствует — **дословно первый пример из
  Шага 2(ж) v3** («append-only как policy для существующего
  журнала»).
- Развилка системная (применима ко всем policy-правилам:
  append-only, write-once, immutable-after-status-X) → нести
  в «Открытые расширения карты».
- Варианты решения конвенции:
  (а) policy живёт в `.claude/conventions/<артефакт>-policy.md`
      (по одному файлу на тип артефакта: `adr-policy.md`,
      `q-journal-policy.md`);
  (б) policy живёт как раздел в L-SPEC PIPELINE метамодели
      артефакта (если L-SPEC PIPELINE появится), отдельный от
```
