# Playbook: как я работаю на этом проекте

Операционная инструкция для **человека** (тебя). Содержит сценарии — типовые рабочие циклы, которые ты выполняешь, переходя между чатом с Claude и Claude Code.

Это **не справочник для Claude**. Это твоя памятка. Открываешь, когда не уверен, что делать дальше.

Для концептуальных основ — см. `working-with-claude.md`. Для архитектурных решений — `adr/`. Для истории изменений пайплайна — `pipeline-evolution-log.md`.

---

## Базовые роли

- **Я (человек)** — продукт-овнер, постановщик задач, принимающий решения, ревьюер.
- **Claude в чате (claude.ai)** — стратегический собеседник: проектирование, обсуждение, ревью.
- **Claude Code** — исполнитель: чтение и изменение файлов, работа с git, запуск тестов.
- **Субагенты в Claude Code** — специализированные роли (architect, risk-engineer и т.д.), вызываются из основной сессии Claude Code.

## Чат vs Claude Code — когда что

| Задача | Инструмент |
|---|---|
| Обсудить новый дизайн или решение | Чат |
| Понять, какой вариант лучше | Чат |
| Получить второе мнение по результатам Claude Code | Чат |
| Прочитать или изменить файл в проекте | Claude Code |
| Запустить тесты, посмотреть git diff | Claude Code |
| Реализовать обсуждённое в чате | Claude Code |
| Доработать промпт агента или скилл | Чат для решения, Claude Code для исполнения |
| Мелкая правка текста документа | Claude Code напрямую |
| Содержательное обсуждение чего-либо | Чат |
| Структурный анализ нескольких файлов (инвентарь, классификация, кросс-проверка) | Claude Code |

Правило: **думаешь — чат, делаешь — Claude Code**.

## Гигиена работы

- **Один чат — одна задача / этап.** Не превращай чат в "всё про проект".
- **Все чаты — внутри Проекта в claude.ai.** Тогда они видят прикреплённые файлы.
- **Claude Code: одна сессия — одна задача.** `/clear` между подзадачами, `/exit` после задачи.
- **Claude Code не коммитит сам.** Коммитишь ты через IDEA после ревью.
- **При значимых изменениях файлов, прикреплённых к Project Knowledge** — обнови их в Project Knowledge (через интерфейс claude.ai).

## Сценарий 1. Архитектурное решение → ADR

**Когда:** возникла развилка с альтернативами. Решение значимое (трудно отменить, влияет на несколько мест).

**Цепочка:**

1. **Открой чат** в Проекте. Опиши контекст и развилку.
2. **Обсудите альтернативы.** Я раскладываю варианты, за/против, применимость, литературу. Ты задаёшь вопросы, оспариваешь, уточняешь.
3. **Прими решение** в чате.
4. **Получи пакет:**
   - Черновик ADR (полный текст).
   - Список затронутых документов спецификации.
   - Указание, требуется ли обновление Project Knowledge.
   - Запись для `pipeline-evolution-log.md` — **только если решение меняет сам пайплайн работы**, иначе не пишется.
5. **Перейди в Claude Code** (новая сессия). Передай пакет с задачей:
   - Сверить черновик с актуальным состоянием репо.
   - Сохранить ADR в `.claude/adr/` со следующим свободным номером.
   - Обновить затронутые спецификации (связное обновление!).
   - Обновить `.claude/adr/README.md` (индекс).
   - Не коммитить.
6. **Ревью** изменений в IDEA. Особое внимание — на спецификации.
7. **Коммит** через IDEA.
8. **Если затронут файл из Project Knowledge** — обнови его в claude.ai.

**Подводные камни:**

- ADR создан, спецификации забыты → главный риск. Knowledge Curator должен ловить, но проверяй и сам.
- Спецификация расходится с ADR → разруливается новым ADR (Supersedes), не правкой старого.
- Точечная правка спецификации ломает логику документа → перечитай весь файл, не только изменённый раздел.

## Сценарий 2. Доработка существующего агента

**Когда:** агент работает не идеально (слишком многословный, упускает важное, лезет не в свою зону, и т.п.).

**Цепочка:**

1. **Накопи наблюдения.** Веди `.claude/notes/agent-issues.md`. Конкретные кейсы, не общие "что-то не так".
2. **Открой чат.** Опиши проблему, приложи наблюдения, прикрепи текущий файл агента к сообщению.
3. **Обсудите диагноз и правки.** Несколько итераций, если нужно.
4. **Получи пакет:**
   - Финальный полный текст агента (не diff).
   - Запись для `pipeline-evolution-log.md`.
   - Тест-кейсы для проверки.
5. **Перейди в Claude Code.** Передай задачу:
   - Заменить содержимое `.claude/agents/<name>.md`.
   - Добавить запись в лог.
   - Не коммитить.
6. **Ревью** в IDEA.
7. **Тест** — запусти агента в Claude Code на 2-3 тест-кейсах. Сравни с прежним поведением.
8. **Коммит** через IDEA.
9. **Обнови `agent-issues.md`** — отметь адресованные наблюдения.

**Подводные камни:**

- Правка ломает то, что раньше работало → тест обязателен на критичных агентах.
- Слишком частые правки одного агента → это не доработка, нужен пересмотр (мета-чат).
- Промпт расходится с `working-with-claude.md` → если правка намеренная, обнови концепцию.

## Сценарий 3. Создание нового агента

**Когда:** появилась повторяющаяся задача, которую существующие агенты не закрывают; новая зона ответственности.

**Перед началом ответь себе:**
- Какую конкретную проблему решает? (Не "хочу агента X", а "задача Y не закрывается".)
- Почему существующие не справляются?
- Какие конкретные задачи будет получать?
- Чем будет отличаться от существующих?
- С кем будут пересечения?

Если на 2+ вопроса нет внятного ответа — агент не нужен, нужна доработка или скилл.

**Цепочка:**

1. **Чат: обсудить целесообразность.** Возможный исход — "не создаём, делаем скилл" или "не создаём, дорабатываем существующего".
2. **Чат: проектирование.** Имя, description (триггер), KPI, чек-лист категорий, adversarial requirement, инструменты, модель, зоны разграничения.
3. **Чат: проверка на эхо-камеру** — чем новый агент содержательно отличается от существующих.
4. **Получи пакет:**
   - Полный файл агента.
   - Запись для лога.
   - Тест-кейсы (минимум 3: в зоне, вне зоны, пограничный).
   - Опционально — упоминание в `working-with-claude.md` (если файл активно используется как справка).
5. **Claude Code:** создать файл, проверить коллизии, добавить лог.
6. **Ревью + тест на 2-3 кейсах. Обязательный шаг.**
7. **Коммит.**
8. **Обнови Project Knowledge**, если правился `working-with-claude.md`.

**Подводные камни:**

- "На всякий случай" → не создавать без минимум одной реальной задачи.
- Слишком узкая специализация → лучше скилл.
- Перекрытие зон → в description явно указать "NOT for ...".
- Слабый промпт (5 строк) → недостаточно. Хороший промпт — 50-150 строк.
- Забытый тест → главный риск: несколько недель работаешь с плохим агентом.
- Накопление неиспользуемых агентов → разбирать на ретроспективе.

## Сценарий 4. Доработка существующего скилла

**Когда:** новое знание, скилл устарел, шумит / не подгружается, разросся.

**Цепочка:**

1. **Накопи наблюдения.** `.claude/notes/skill-issues.md`.
2. **Чат: открыть.** Прикрепи затронутые файлы скилла (не все подряд).
3. **Обсудите.** Тип правки:
   - Добавление в файл — текст для вставки.
   - Правка `description` — критично, влияет на триггерное поведение.
   - Полная замена файла.
   - Рефакторинг (несколько файлов).
4. **Получи пакет:** правки + запись в лог.
5. **Claude Code:** передай с инструкцией **сверить с актуальным состоянием** (важно для развивающихся скиллов).
6. **Ревью** в IDEA.
7. **Тест** — обязателен, если правил `description` или делал рефакторинг. Проверь триггеры: подгружается / не подгружается на ожидаемых задачах.
8. **Коммит.**
9. **Обнови заметки.**

**Подводные камни:**

- `description` — самая частая ошибка. Слишком широко → шум. Слишком узко → не подгружается. Формула: "Use **when** [сценарии]. Covers [...]. **NOT for** [исключения]."
- Скилл-свалка → раз в 5 правок ревизия.
- Дублирование со спецификацией / ADR → скилл это "как делать", не "что есть" и не "почему решили".
- Тяжёлый SKILL.md → если больше 2-3 страниц, рефакторить (вынести тяжёлое в отдельные файлы).

## Сценарий 5. Создание нового скилла

**Когда:** новая интеграция, переиспользуемое знание, повторяющаяся процедура, материал из книги / статьи.

**Перед началом ответь:**
- Какую задачу скилл решает?
- Когда активируется (триггер)?
- Какие материалы будут?
- Что **не** относится к этому скиллу?

**Цепочка:**

1. **Чат: целесообразность.** Может, это часть существующего скилла? Раздел в CLAUDE.md? ADR? Спецификация?
2. **Чат: проектирование.** Имя, структура папки (минимальная / с ресурсами / с примерами), `description`, содержание SKILL.md.
3. **Получи пакет:**
   - Файлы скилла (SKILL.md + опционально дополнительные).
   - Запись в лог.
   - Тест-кейсы (в зоне, вне зоны, пограничный).
4. **Claude Code:** создать с проверками коллизий с другими скиллами.
5. **Ревью.**
6. **Тест триггеров. Обязательный шаг.**
7. **Коммит.**

**Подводные камни:**

- Скилл, который никогда не активируется → плохой `description`. Проверять регулярно.
- Скилл-свалка с самого начала → стартовать с минимально жизнеспособного.
- Скилл вместо ADR → ADR это "что и почему решили", скилл это "как применять".
- Скилл вместо спецификации → спецификация это "как устроено", скилл это "процедура работы".
- Слишком общий скилл → должен закрывать конкретную область / процедуру.
- Тяжёлый SKILL.md → прогрессивное раскрытие: SKILL.md лёгкий, ресурсы рядом.
- "На будущее" → не создавать без минимум одной страницы реального контента.

## Сценарий 6. Ретроспектива пайплайна

**Когда:** раз в месяц / квартал, после большого этапа, при накоплении мелких раздражителей, при ощущении "что-то стало неудобно".

**Цепочка:**

1. **Подготовка (10-15 мин).** Собери материал:
   - `pipeline-evolution-log.md` за период.
   - `agent-issues.md`, `skill-issues.md`.
   - Новые ADR за период.
   - Свои воспоминания: что раздражало, что работало, что хотелось бы.

   Запиши short summary.

2. **Чат: открой новый, под ретроспективу.** Приложи summary и материалы.

3. **Структурированное обсуждение.** Темы:
   - Команда агентов (использование, качество, пересечения).
   - Скиллы (триггеры, использование, устаревание).
   - Процессы / сценарии (что выполнялось, где была боль).
   - Документация (устаревание, пробелы, разрастание).
   - Концепция (нужны ли фундаментальные правки).

4. **Получи приоритизированный список действий.** Срочные / важные / опциональные. Цель — **3-5 ценных** изменений, не 15.

5. **Выполни список по одному.** Каждый пункт — отдельная сессия Claude Code, по соответствующему сценарию (2/3/4/5/правка документа).

6. **После всех пунктов** — общая запись в `pipeline-evolution-log.md`.

7. **Опционально** — сохрани резюме ретроспективы в `docs/retrospectives/YYYY-MM.md`, если решишь вести историю.

**Подводные камни:**

- Косметический обзор без подготовки → обязательная подготовка.
- Откладывание ретроспектив → по календарю, не по ощущению "созрели".
- Слишком амбициозный список → не более 3-5 пунктов.
- Лог как wish list → в лог только сделанное, не запланированное.
- Наладка инструмента вместо работы → если изменений в пайплайне больше, чем содержательной работы, снизь частоту ретро.
- Фундаментальный пересмотр на обычной ретро → выноси в отдельный мета-чат.

## Сценарий 7. Создание или обновление документа спецификации

**Когда:** появилась тема для документа в `docs/spec/` — новая или
мигрируемая из `docs/domain/`. Или существующий spec-документ требует
обновления.

**Цепочка:**

1. **Чат: определить жанр.** Это model / lifecycle / process / integration
   mapping / reference / invariant? Согласовать с ADR-0002.
2. **Чат: проектирование документа.** Получить от меня:
   - Полный текст документа (готовый к сохранению).
   - Какие связные документы затрагиваются, если есть.
   - Какие пункты backlog закрываются / появляются.
3. **Claude Code:** скилл `spec-document-workflow` активируется
   автоматически. Он направляет:
   - Скопировать шаблон из `.claude/templates/documents/<имя>.md`
     в целевой путь (для создания) или прочитать существующий
     документ (для обновления). Соответствие жанра имени шаблона:
     `models → model.md`, `lifecycle → lifecycle.md`,
     `processes → process.md`, `integrations → integration-mapping.md`,
     `references → reference.md`, `invariants → invariant.md`.
   - Заполнить шаблон полученным содержанием.
   - Проверить связные обновления (другие spec-документы, ADR, backlog).
   - Пройтись по чек-листу (входит в скилл).
4. **Ревью** в IDEA по чек-листу ниже.
5. **Knowledge-curator** в конце сессии (общая проверка).
6. **Коммит** через IDEA.
7. **Project Knowledge** — если затронут прикреплённый файл.

**Чек-лист ревью документа спецификации:**

- [ ] Frontmatter заполнен (`status`, `last_review`, `related_adrs`).
- [ ] Файл лежит в правильной папке для своего жанра.
- [ ] Имя файла соответствует правилам (PascalCase для классов,
      kebab-case иначе).
- [ ] Нет Java-сниппетов (для `models/` и `lifecycle/`).
- [ ] Структура моделей — таблицей полей, не Java-кодом.
- [ ] Кросс-ссылки — markdown-link с относительным путём, не inline-code.
- [ ] Нет addenda-разделов («Дополнение после ...»).
- [ ] Нет встроенных открытых вопросов (они в `.claude/planning/backlog.md`).
- [ ] Размер документа ≤1000 строк (если больше — есть запись в backlog).
- [ ] Связные документы обновлены (другие spec-документы, ADR, backlog).

**Подводные камни:**

- Документ смешивает жанры → разнести по соответствующим папкам, не
  совмещать.
- Дублирование с другим документом → заменить на ссылку.
- Java-сниппет «для наглядности» → таблица полей, не Java.
- «Дополнение после...» как способ внести правку → нет, правится тело
  документа.

## Сценарий 8. Проверка консистентности Project Knowledge в конце сессии

**Когда:** сессия (в чате claude.ai) внесла **содержательное** изменение,
требующее обновления Project Knowledge. Это любая сессия, которая:
- Приняла новый ADR.
- Обновила концепцию (working-with-claude.md, project-instructions.md).
- Создала новую версию snapshot (strategy-summary-vN).
- Изменила состав файлов в PK (добавила / удалила прикрепления).
- Обновила содержимое любого файла из списка PK содержательно (не
  опечатка).

Опечатки и минорные правки текста — без триггера.

**Принцип:** «кто менял — тот и проверяет». Глубокую проверку делает
**тот же чат**, который проектировал изменения. Новый чат не имеет
контекста ожиданий и не может корректно сверить.

**Цепочка:**

1. **После применения изменений** (через Claude Code) — человек
   обновляет PK в claude.ai вручную: удаляет старые версии файлов,
   загружает актуальные.

2. **Возвращается в исходный чат** (тот, в котором проектировались
   изменения).

3. **Запрашивает у Claude глубокую проверку:** "проведи глубокую
   проверку Project Knowledge после применённых изменений".

4. **Claude формирует набор проверок под то, что менялось.**
   Например:
   - Принят ADR-NNNN → проверка индекса; проверка наличия ADR в
     `.claude/adr/`; проверка ключевых разделов внутри ADR.
   - Обновлена концепция → проверка цитат ключевых положений в
     `working-with-claude.md`.
   - Новый snapshot vN → проверка даты и упомянутых ADR в шапке.
   - Изменился состав PK → перепроверка ожидаемого списка в
     `working-with-claude.md` и сверка с реальным PK.
   - Изменён playbook (новые сценарии) → проверка наличия их в
     `playbook.md`.

5. **Claude выдаёт отчёт по каждой проверке:** ОК / РАСХОЖДЕНИЕ /
   НЕ ПРИМЕНИМО.

6. **При расхождениях:** перечисление, что человеку нужно поправить
   в claude.ai. Сессия **не закрывается**, пока расхождения не
   устранены.

7. **При полном ОК:** сессия закрывается. Промпт для следующего чата
   готовится без проверочной части (она уже сделана).

**Подводные камни:**

- **Глубокая проверка в новом чате (не в том, который менял).** Новый
  чат не знает, какими были ожидания. Получится "формальная" проверка,
  пропускающая расхождения. **Принципиально нужен исходный чат.**

- **Забыл провести в финале сессии.** Тогда следующий чат начнёт
  с лёгкой пред-проверки, и она может выявить базовое расхождение
  (если состав не сошёлся). Но содержательные расхождения внутри
  файлов могут пройти незамеченными до первой реальной проблемы.
  Профилактика: knowledge-curator (агент) напоминает в финале
  сессии.

- **Тривиальные изменения, не требующие глубокой проверки.** Не
  заводить процедуру ради опечатки — критерий "содержательное"
  работает осознанно.

- **PK не обновлён человеком к моменту запроса проверки.** Claude
  должен явно спросить: "PK уже обновлён в claude.ai?" — и не
  начинать проверку до утвердительного ответа.

**Связь с другими сценариями.** Сценарий 8 — финальный этап для
сценариев 1, 3, 5, 7 (создание ADR, агента, скилла, документа
спецификации), если в них что-то затронуло PK. Запуск Сценария 8
в этих случаях фиксируется в чек-листе соответствующего сценария
(см. чек-листы выше).

## Сценарий 10. Итеративная доводка инфраструктуры через dry-run

**Когда:** доводка крупной инфраструктуры (миграционной или иной), 
где нужен систематический замер пробелов в правилах. Применяется, 
когда пакет ADR в Proposed и сопровождается набором скиллов/агентов/
шаблонов, которые нужно протестировать как целое перед переходом 
ADR в Accepted.

**Принцип режима** — пакет Proposed-ADR во время итерации считается 
стабильным снапшотом (as-if-Accepted, см. working-with-claude.md, 
раздел про ADR). Тестируем на каждой итерации **то, что 
собираемся принять**, а не движущуюся мишень.

**Цепочка одной итерации (V_N):**

1. **Запуск dry-run прогона в Claude Code.** Прогон выбранного 
   кейса (legacy-документа, кластера, миграционной задачи) через 
   текущее состояние инфраструктуры. Кк не пишет файлы в `docs/spec/` 
   — только составляет план, фиксирует решения, заводит Q-N. 
   Артефакт: `.claude/notes/migration-dryrun-<context>-<date>.md`.

2. **Анализ отчёта отдельной сессией кк.** Прочитать отчёт, 
   классифицировать каждый замеченный пробел (A — алгоритм миграции 
   не покрывает случай, B — правило в скилле/агенте отсутствует 
   или неполно, C — конфликт между артефактами, D — терминологическое 
   расхождение, E — структурный пробел в ADR). Артефакт: 
   `.claude/notes/migration-dryrun-analysis-<context>-<date>.md`.

3. **Группировка пунктов анализа в пакеты.** Связанные правки 
   (один смысловой блок: например, всё про MODELS.md как реестр, 
   или всё про парный lifecycle для status-моделей) — в один пакет. 
   Приоритет: **B → A повторные → A одиночные → C → E → D**. 
   Каждый пакет получает короткое имя и список пунктов из анализа.

4. **Обработка пакетов по очереди.** Один пакет — две сессии: 
   отдельная сессия чата для формулировки правок (обсуждение, 
   принятие решений, написание текста), отдельная сессия (или 
   микро-сессии) кк для применения. Слишком объёмный пакет 
   разбивается на микро-сессии для качества — лучше три фокусных 
   сессии, чем одна расфокусированная.

5. **Правки тела Proposed-ADR — в журнал, не в тела.** Журнал — 
   `.claude/notes/adr-drafts/adr-fixes-iteration-N.md`. Формат — 
   старая формулировка / новая формулировка / источник в анализе. 
   Журнал ведётся в течение всей итерации, тела ADR не правятся 
   по ходу.

6. **Финальная сессия итерации.** Применяет накопленный журнал 
   правок к телам ADR разом, удаляет журнал, создаёт следующий 
   snapshot стратегии (`strategy-summary-vN+1.md`), записывает 
   итог итерации в `pipeline-evolution-log.md` (одна запись на 
   всю итерацию). После финальной сессии — обновление Project 
   Knowledge человеком (см. Сценарий 8).

7. **Следующий dry-run (V_{N+1}) при необходимости.** Если 
   обновлённая инфраструктура нашла значимое в новом прогоне — 
   старт следующей итерации. Итерации идут до **насыщения** — 
   когда тест перестаёт находить значимые пробелы.

**Подводные камни:**

- **Слишком объёмные пакеты.** Соблазн — взять всё, что относится 
  к одной теме, и обработать одной сессией. Качество падает. 
  Разделять на микро-сессии по подтемам.
- **Правки Proposed-ADR сразу.** Соблазн — «маленькая правка, 
  применим сразу». Нарушает стабильность снапшота: следующий 
  замер тестирует уже не то, что собираемся принять. Все правки 
  ADR — через журнал, без исключений.
- **Пропуск финальной сессии.** Если итерация закончилась, а 
  журнал правок не применён, snapshot не создан — следующая 
  итерация стартует на смешанном состоянии (часть правок 
  применена, часть нет). Финальная сессия — обязательный этап, 
  не опциональный.
- **Слишком много итераций.** Если 3-4 итерации подряд не дают 
  насыщения (каждый прогон находит сопоставимое по объёму), 
  проблема не в инфраструктуре — она в концепции пакета ADR. 
  Сигнал к содержательному пересмотру (мета-чат), а не к 
  очередной итерации.
- **Правки инфраструктуры в журнал.** Правки скиллов, агентов, 
  шаблонов **не** идут в журнал ADR. Они применяются сразу, в 
  той же сессии. Журнал — только для тел Proposed-ADR.

**Связь с другими сценариями:**

- Сценарий 1 (создание ADR) — финальный переход пакета ADR из 
  Proposed в Accepted после насыщения цикла. Делается отдельной 
  сессией, не в рамках финальной сессии итерации.
- Сценарий 8 (проверка консистентности Project Knowledge) — 
  выполняется в конце финальной сессии итерации, если затронуты 
  файлы из PK (snapshot v_{N+1}, working-with-claude.md, playbook.md 
  и т.п.).
- Сценарий 2/3/4/5 (доработка/создание агентов и скиллов) — 
  применяются внутри обработки пакетов, как нужно.

## Принцип связного обновления (напоминание)

Любое изменение модели, процесса, концепции — **автоматически** влечёт проверку связных документов. Это не отдельный сценарий, а базовое правило, применяемое во всех сценариях выше.

Knowledge Curator проверяет это в конце каждой сессии. Пропуск связного обновления = незавершённая работа.
