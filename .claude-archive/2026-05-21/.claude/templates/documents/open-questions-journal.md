# Журнал open-questions

Каталог концептуальных и рабочих вопросов проекта. Артефакт фиксирует открытые вопросы — концептуальные пробелы, отсутствующие модели, противоречия, кандидатов на устаревание — со ссылкой на источник и судьбу каждого.

Журнал — рабочий артефакт процесса работы над проектом. Не источник правды о системе (для этого — `docs/spec/`), а источник правды о том, **какие вопросы по системе ещё не закрыты**.

Полные правила работы с журналом — ADR-0008 (`.claude/adr/0008-open-questions-journal.md`).

## Как пользоваться

**Добавление нового entry.**

1. Открой раздел «Open» ниже.
2. Скопируй блок «Пример entry» (Q-EXAMPLE) как заготовку.
3. Присвой новый `id` — следующий по порядку `Q-NNN` после максимального существующего (включая Closed). Пример сохраняет фиксированный id `Q-EXAMPLE` и не считается.
4. Заполни все поля шапки и текстовые секции. Если природа вопроса при добавлении неясна — `classification: unclassified`. Это допустимо; при разборе переклассифицируется.
5. Если есть связанные Q-N — перечисли их в `Related`.

**Изменение entry.**

- `status` — меняется один раз: Added → Resolved.
- `notes` — append-only. Новые заметки датируются и добавляются в конец списка. Существующие не редактируются.
- `resolution` — заполняется один раз при переходе в Resolved.
- `classification`, `title`, `formulation`, `context`, `related` — могут уточняться по ходу разбора без удаления истории. При reclassification — в `notes` добавляется датированная заметка с причиной.

**Закрытие entry.**

При переходе `status` в `Resolved`:

1. Убедись, что `classification` ≠ `unclassified` (если ещё `unclassified` — сначала переклассифицируй).
2. Заполни `Resolution`: ссылка на ADR / раздел spec-документа / коммит, где вопрос закрыт по существу, либо обоснование устаревания по одному из трёх условий (см. ADR-0008 §5).
3. Перемести entry из раздела «Open» в раздел «Closed» (id и ссылки на entry сохраняются — они стабильные).
4. Проверь связь с backlog: если на этот Q-N ссылалась задача в `.claude/planning/backlog.md` — отметь её закрытой.
5. Knowledge Curator при следующей сверке проверит inline-ссылки «см. Q-NNN» в `docs/spec/`; при висящих ссылках автоматически заведёт пункт в backlog.

**Ссылки на entry.**

- Из ADR / spec / backlog — по `id` (`Q-NNN`).
- В spec-документах — короткая inline-ссылка «см. Q-NNN» в конце предложения или в скобках. Сам вопрос — в журнале, не в spec.

**Formulation.**

Буквальная формулировка вопроса. Одно или несколько предложений. То, на что нужно ответить.

**Context.**

Контекст вокруг вопроса. Один-три абзаца. Цель — чтобы при ревью или возвращении к entry через месяц не нужно было лезть в исходный legacy-документ или восстанавливать обсуждение из чата. Что обсуждалось, какие альтернативы упоминались, какие соображения за и против — кратко.

**Notes.**

- [YYYY-MM-DD] Датированная заметка. Заметки добавляются в конец, существующие не редактируются. Сюда уходит: «вопрос взят в активный разбор», «переклассифицирован из X в Y по причине Z», промежуточные соображения по ходу разбора.

**Resolution.**

— (заполняется при переходе в Resolved: ссылка на ADR / spec-документ / коммит или обоснование устаревания)
