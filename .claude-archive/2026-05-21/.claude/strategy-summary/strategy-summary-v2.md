## Принятые концептуальные решения

Из v1 без изменений:

1. **Двухсессионная модель работы.** Чат для мышления, Claude Code для исполнения, перенос через черновики.
2. **Иерархия источников правды.** `docs/spec/` → `docs/domain/`+`docs/api/` → код+ADR+conventions → прочие `docs/` → архивы. Конфликты внутри уровня — ADR.
3. **Поэтапная миграция документации.** Маркер `[MIGRATED → ...]` на первой строке старого документа.
4. **Принцип связного обновления.** Любое изменение модели/процесса/концепции автоматически влечёт проверку и обновление связанных документов. Knowledge Curator проверяет в конце сессии.
5. **Claude Code не коммитит.** Все изменения в working tree, коммитит человек через IDEA. Auto-staging через `git add`.

Новые решения, накопленные с v1:

6. **Стандарт документа `docs/spec/`** (ADR-0002). Шесть жанровых каталогов с шаблонами в `_templates/`. Правило «один факт — одно место». Frontmatter обязателен. Никаких Java-сниппетов, addenda, встроенных открытых вопросов. Контроль на трёх уровнях: шаблоны / скилл `spec-document-workflow` / ревью человека.

7. **Модель reconcile через AnomalyReport** (ADR-0001). FSM сделки и AnomalyJob — два потребителя kill-switch. `KillSwitchExecutor` — единая точка исполнения. Orphan-сущности — блокирующие аномалии без kill-switch.

8. **Разделение `docs/` vs `.claude/`** (ADR-0003). Граница по природе артефакта, не по теме содержания. `docs/` — продуктовая документация (что бот собой представляет). `.claude/` — работа над проектом через Claude (рабочие артефакты, процесс, конфигурация). Все ADR и backlog — в `.claude/`. Закреплён детальный алгоритм работы с ADR (два типа примечаний, поведение при рефакторингах).

9. **Версионированные снимки.** Новый паттерн — документы класса «снимок состояния на момент времени» не редактируются задним числом, эволюция через новые версии (`-v1`, `-v2`, ...) в одной подпапке. Применён к этому документу (`strategy-summary-v1` → `strategy-summary-v2`).

10. **Backlog как синхронизация связного обновления** (фиксация в working-with-claude.md от 2026-05-14). Закрытие пункта работой → перемещение в «Закрытые» с датой и ссылкой; новый открытый вопрос в ходе работы → сразу в backlog, не в чате.

11. **Терминология: «доменная модель» вместо «entity».** «Entity» нагружено JPA-аннотацией, создаёт двусмысленность между доменной моделью и персистентной сущностью. Не все доменные модели проекта персистентны.

## Что было решено НЕ делать (из v1, актуально)

- Не создавать многоагентность в рантайме (внутри бота) на этом этапе.
- Не строить весь пайплайн заранее — наращивать по реальной потребности.
- Не делать «дискуссию» между агентами по умолчанию — конвейерная схема.
- Не помечать старые доки как deprecated сразу — маркировка `[MIGRATED]` только при полной миграции темы в `docs/spec/`.
- Не делать отдельный сценарий «обновление спецификации» — это базовое поведение (связное обновление).

Новое решение НЕ делать (из ADR-0003):

- Не разделять backlog на продуктовый и пайплайновый. Один общий список.
- Не разделять ADR по жанру решения. Все ADR — в одном месте.
- Не обновлять ссылки внутри принятого ADR при переезде целевых файлов. Append-only, технические примечания вместо правок.

## Как использовать этот документ

Снимок — навигационный и контекстный. Используется:
- Чтобы понять, **в каком состоянии** проект на 2026-05-15.
- Чтобы новая сессия видела текущую картину без перечитывания всех ADR и пайплайн-лога.
- При ретроспективе — для сверки, как далеко проект ушёл от v1.

Не редактируется задним числом. Если состояние изменилось значимо — создаётся `strategy-summary-v3.md` со ссылкой на этот документ и кратким описанием, что нового.

История эволюции пайплайна — в `../pipeline-evolution-log.md` (хронологический детальный лог). История архитектурных решений — в `../adr/`.
