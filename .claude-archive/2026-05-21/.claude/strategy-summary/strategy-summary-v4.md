## Принятые концептуальные решения

Из v3 без изменений — все 15 пунктов (двухсессионная модель, иерархия
источников правды, поэтапная миграция, связное обновление, no-commit
от Claude Code, стандарт `docs/spec/`, ADR-0001 reconcile, ADR-0003
разделение `docs/`/`.claude/`, версионированные снимки, backlog как
синхронизация, терминология «доменная модель», принципы спецификации,
структура `docs/spec/`, журнал open-questions, стратегия миграции).

Новые решения, накопленные в этом цикле ревью:

16. **Принцип 6 (внесён в `working-with-claude.md` после Принципа 5).** Документация —
    источник истины, код подтягивается. Доменная документация описывает
    целевое состояние; код реализует постепенно. При миграции legacy
    дока — источник истины; documented-only модели мигрируются как
    валидные spec-документы; code-only классы упоминаются как роли
    в process-документах, не как модели.

17. **Правило формата общения в чате (внесено в
    `project-instructions.md` как принцип 13).** При обсуждении содержательных решений
    Claude использует формат: короткое описание вопроса (контекст из
    жизни, не через ссылки на параграфы) → список вариантов → короткая
    рекомендация → ждать выбор пользователя.

18. **Процедурное: пакет ADR принимается разом, не по одному.** До
    завершения Этапа 4 все ADR пакета — Proposed; индекс
    `.claude/adr/README.md` не обновляется частично. Это страхует
    от ситуации, когда часть пакета принята, а потом по результатам
    стресс-теста нужно поправить уже принятые ADR.

19. **Открытые концептуальные вопросы заводятся естественно при
    миграции, не предзаводятся.** Природа моделей (core vs runtime),
    структура отсутствующих моделей и т.п. — Q-N появляются в журнале
    из материала legacy при миграции соответствующего кластера, не
    создаются заранее по плану.

## Состав пакета ADR-0006..0009

### ADR-0006: Принципы спецификации (Proposed)

Четыре принципа организации содержания spec-документов:
1. Один бизнес-объект — один model-документ; вложенные модели — разделами. Деление на core/runtime.
2. Локальные vs кросс-модельные инварианты (операционализированный тест).
3. Статусные таксономии: внутри model-документов; двухуровневый резолвер биржевых статусов.
4. Addenda при миграции — вмерживаются в основной текст, нерешённые остатки уходят в журнал.

### ADR-0007: Структура `docs/spec/` (Proposed)

Подкаталоговая структура:
- `models/core/` и `models/runtime/`.
- `integrations/<exchange>/{models,mapping}/` — для фазы 2.
- `lifecycle/`, `processes/`, `invariants/`, `references/`.
- Глоссарий — в корне `docs/` (исключение из жанровой структуры).
- `docs/api/` остаётся самостоятельным жанром.

### ADR-0008: Журнал open-questions (Proposed)

Новый артефакт `.claude/questions/open-questions.md`. Структура entry
(11 полей), статусы (Added/Resolved), классификация (7 содержательных
+ 1 служебная `unclassified`), три условия устаревания. Шаблон и скилл
`open-questions-workflow` создаются на Этапе 4.

### ADR-0009: Стратегия миграции `docs/domain/` (Proposed)

Шесть последовательных фаз миграции:
1. Миграция домена (8 кластеров).
2. Миграция OKX-маппингов.
3. Обработка корневого backlog движка.
4. Реорганизация `docs/api/`.
5. Цикл ревью.
6. Упразднение legacy.

Восемь кластеров фазы 1, единица миграции — двухуровневая
(кластер + spec-документ), пять hard gates готовности, синтаксис
забегающей ссылки, принцип качества миграции (батчинг, не сокращение
скоупа), процедура работы с open-questions, скилл
`spec-cluster-migration` + Сценарий 9 в playbook.

## Что решено НЕ делать (расширение из v3)

Из v3 без изменений. Добавляется:

- **Не предзаводить Q-N в журнале по плану миграции.** Q-N появляются
  естественно при работе с конкретным legacy-материалом (по ADR-0008 §4).
- **Не принимать пакет ADR по одному.** Все четыре ADR пакета
  принимаются разом после завершения Этапа 4.
- **Не заводить отдельных backlog-пунктов на разведку persistence
  конкретных моделей** (DealActionState, MarketPriceData) — это вопросы,
  которые встанут естественно при миграции C1/C7/C6.
