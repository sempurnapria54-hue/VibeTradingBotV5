# spec-document-migration

Процедура миграции одного legacy-документа из `docs/domain/`,
`docs/deprecated/` или любой другой pre-spec локации в `docs/spec/`.
**Единица миграции — один legacy-файл.** Содержание разбирается по
упомянутым в нём сущностям; каждая сущность получает либо своё
место в `docs/spec/`, либо Q-N в журнале.

## Когда активируется

- Перенос документа из `docs/domain/` в `docs/spec/`.
- Перенос документа из `docs/deprecated/` в `docs/spec/`.
- Любая миграция, где исходник вне `docs/spec/`, цель — внутри
  `docs/spec/`, и содержание требует переработки.

## Когда НЕ активируется

- Создание нового документа сразу в `docs/spec/` без legacy-предка —
  это [`spec-document-workflow`](../spec-document-workflow/SKILL.md).
- Редактирование существующего документа в `docs/spec/` — тоже
  `spec-document-workflow`.
- Физическое перемещение файла (`git mv`) без переработки содержания —
  это refactor, не миграция.

## Базовая модель работы

Алгоритм по одному legacy-документу:

1. **Прочитать целиком.** Никаких правок до полного прочтения.
2. **Разобрать упоминания сущностей.** Для каждого имени,
   появляющегося в тексте, определить тип по тестам из раздела
   «Определение типа сущности при миграции» (модель / процесс /
   invariant / integration / reference / реализационный класс /
   значение).
3. **Реализационные классы и значения — не отдельные документы.**
   `Executor`, `Repository`, `Mapper`, `Service`, `Configuration`,
   `Factory`, `Handler` и подобные — упоминаются как роли в
   документах соответствующих жанров. Имена-значения (`CreateOrder`
   как имя сервисной команды, имена статусов в тексте, имена кодов
   аномалий) — упоминаются в разделе «Виды ...» или в перечне
   значений внутри документа модели-носителя.
4. **Доменные сущности — содержательное описание vs только
   упоминание.**
   - Если в legacy есть содержательное описание (поля, поведение,
     роль, любая структурная информация) — создать или дополнить
     целевой документ в `docs/spec/`. В созданный документ кладётся
     только то содержание, которое было в legacy.
   - Если в legacy — только упоминание имени без описания — завести
     Q-N в журнале с classification `missing-model` /
     `missing-process` / `missing-invariant` (по типу сущности).
5. **Пограничные случаи** (не ясно, модель это, процесс или
   invariant; не ясно, доменная это сущность или реализационный
   класс) — завести Q-N с classification `concept`. Решение
   молча не принимается.
6. **При создании целевого документа** — открыть журнал, закрыть
   соответствующие Q-N по этой сущности (если они там есть),
   обновить ссылки в документах, которые упоминали эту сущность
   прозаически. См. раздел «Закрытие Q-N при создании модели».
7. **Когда все упоминания в legacy разнесены** (содержательные —
   в целевые документы, без описания — в Q-N) — проставить
   MIGRATED-маркер на legacy-файл, перейти к следующему документу.

**Заглушка — валидное состояние документа.** Документ в
`docs/spec/`, у которого заполнено только то, что было в legacy
(хотя бы определение и связи), а остальные разделы шаблона
помечены «описание появится при миграции содержательного
источника» — нормальное промежуточное состояние. Документ
существует, зарегистрирован в `docs/spec/MODELS.md`, ссылки на
него ставятся как обычные markdown-ссылки. Заглушка отличается
от полного отсутствия документа: отсутствующая сущность — это
Q-N в журнале, не markdown-ссылка на несуществующий файл.

Состояния документа:

- **Заглушка с обвязкой** — заполнено определение и связи, нет
  структурных полей. Сопровождается открытым Q-N
  `missing-<тип>` по содержательной части.
- **Заполнен по существу, не по всему шаблону** — норма, Q-N
  нет.
- **Полностью заполнен** — идеал.

Q-N резолвится по конкретному содержательному пробелу, не по
полноте документа в целом.

## Процедура

### Шаг 1. Анализ исходника

Прочитать legacy-документ целиком. Составить инвентарь
упоминаемых сущностей: имя → тип (по тестам ниже) →
содержательное описание в legacy есть/нет → целевой документ
(если содержание есть) или Q-N (если нет).

Параллельно прочитать:

- ADR в `.claude/adr/`, на которые ссылается исходник или
  которые касаются предметной области документа.
- Шаблоны жанров из `.claude/templates/documents/`, релевантные
  ожидаемым целевым документам.
- `.claude/planning/backlog.md` — для проверки затронутых
  пунктов.
- `.claude/questions/open-questions.md` — для проверки
  существующих Q-N по предмету документа.
- `docs/conventions/terminology.md` — для применения замен.
- `.claude/planning/migration-tracker.md` — для понимания
  статуса кластера и документа.
- Существующие документы в `docs/spec/`, которые могут быть
  дополнены результатами миграции или содержать прозаические
  упоминания мигрируемых сущностей.

На этом шаге **ничего не правится**. Инвентарь и план — в чат
пользователю.

### Шаг 2. Разрешение пограничных случаев в чате

Пограничные случаи (классификация неясна, разделение по жанрам
неоднозначно, граница «доменная сущность vs реализационный
класс» не очевидна) — обсуждаются с пользователем. Решения
фиксируются в чате, в файлах не отражаются. По итогам —
обновлённый план: имя → тип → место.

Часть пограничных случаев пользователь может оставить
неразрешёнными — тогда в исполнении они уйдут в Q-N с
classification `concept`.

### Шаг 3. Исполнение

Для каждой сущности по плану:

- **Содержательное описание есть, целевой документ ещё не
  существует** — создать документ из шаблона жанра, перенести
  содержание, проставить frontmatter. Если миграция создаёт
  заглушку (содержания мало) — заполнить определение и связи,
  остальные разделы оставить с пометкой о появлении при
  содержательной миграции.
- **Содержательное описание есть, документ уже существует** —
  дополнить существующий документ (раздел или поле), не
  создавать второй файл на ту же сущность.
- **Содержательного описания нет, есть только упоминание** —
  завести Q-N через скилл
  [`open-questions-workflow`](../open-questions-workflow/SKILL.md)
  с classification, соответствующей типу сущности
  (`missing-model` / `missing-process` / `missing-invariant`).
- **Пограничный случай, оставленный неразрешённым** — Q-N с
  classification `concept`.

По всем созданным/дополненным документам — выполнить связное
обновление (раздел «Закрытие Q-N при создании модели»).

Другие связные обновления:

- Закрыть/обновить пункты `.claude/planning/backlog.md`,
  связанные с миграцией.
- Обновить `.claude/planning/migration-tracker.md`: статус
  legacy-документа (`done` или `in-progress`), перечень
  созданных/дополненных целевых spec-документов.
- Обновить `docs/spec/MODELS.md`: новые model-документы
  (включая заглушки) регистрируются ссылкой; заглушки в реестре
  заменяются ссылками — через скилл
  [`spec-models-registry`](../spec-models-registry/SKILL.md).
- Проставить MIGRATED-маркер на legacy — когда все упоминания
  разнесены (см. раздел «MIGRATED-маркер на исходнике»).

После исполнения — активируется `spec-document-workflow` для
финального чек-листа на каждом созданном/дополненном целевом
документе.

### Шаг 4. Ревью пользователем

Пользователь получает сводку и тексты целевых документов.
Сверка по инвентарю — каждое упоминание из legacy нашло либо
место в целевом документе, либо Q-N в журнале, либо явное
вычёркивание с обоснованием (дубль ADR / реализационный класс /
значение). Точечные правки — отдельной итерацией.

## Определение типа сущности при миграции

Триггер применения теста — упоминание имени в legacy, которому
нужен какой-то ответ (документ или Q-N). Тест применяется к
**каждому** встреченному имени. `docs/spec/MODELS.md` не
является гейтом принятия решения — реестр **отражает** уже
созданные model-документы, а не разрешает их создание.

### Тесты по типу

**Модель** — все четыре признака:

- Имеет независимый жизненный цикл (создаётся, изменяется,
  удаляется вне контекста другого объекта).
- Имеет identity (стабильный идентификатор).
- Может быть субъектом операций: загрузить, провалидировать,
  сохранить, передать.
- Имеет смысл в отрыве от других моделей.

Если все четыре — да: это бизнес-модель, ей нужен
model-документ в `docs/spec/models/` (core или runtime — по
природе).

**Реализационный класс** — нет identity, существование привязано
к чему-то другому (команде, операции, контейнеру), смысла в
отрыве нет. Типичные имена: `Executor`, `Repository`, `Mapper`,
`Service`, `Configuration`, `Factory`, `Handler`, `Resolver`,
`Validator`, `Builder`, `Listener`. В `docs/spec/` отдельным
документом **не появляются**. Упоминаются как роли внутри
документов соответствующих жанров: «`OrderRepository` загружает
по id» — в process-документе; «триггерит `KillSwitchExecutor`» —
в lifecycle-документе.

**Значение** — имя, идентифицирующее экземпляр другой модели.
Пример: `CreateOrder` — это значение, экземпляр `ServiceCommand`
с конкретными параметрами. Не отдельная модель. Упоминается в
разделе «Виды команд» документа `ServiceCommand`, или в перечне
значений enum у модели-носителя. Имена статусов (`CREATED`,
`LIVE`, `COMPLETED`), имена кодов аномалий — тоже значения.

**Процесс** — осмысленный набор шагов исполнения с входом и
выходом, имеет триггер. Может быть job, executor-flow,
оркестратор. Примеры: `CreateOrder` (как процесс, отличный от
одноимённой команды-значения), `MarketPhaseJob`,
`DealOrchestrator`. Документ в `docs/spec/processes/`.

**Invariant** — правило, пересекающее несколько моделей или
процессов. Не принадлежит одной модели. Примеры:
`status-resolution`, `freshness`, `evidence-cycle`,
`kill-switch`. Документ в `docs/spec/invariants/`.

**Integration mapping** — описание соответствия внешней DTO
биржи и доменной модели. Документ в
`docs/spec/integrations/<exchange>/`.

**Reference** — стабильный архитектурный паттерн или справочная
информация, общая для нескольких документов: каталог исключений,
mapping-pattern, data-flow. Документ в `docs/spec/references/`.

### Граничные ситуации

- **Имя совпадает с реализационным классом, но в legacy есть
  содержательная роль.** Пример: `RiskValidator` упоминается в
  legacy с описанием роли. Это всё равно реализационный класс —
  описание роли остаётся в process- или lifecycle-документе
  модели, к которой класс относится. Отдельного документа не
  получает.
- **Имя похоже на модель, но это контейнер без identity.**
  Пример: `BalanceContainer` — если содержит несколько `Balance`
  без собственного id. Рассмотреть как aggregate root модели
  `Balance` (см. тест identity и lifecycle). Решение —
  пограничный случай, Q-N с classification `concept`.
- **Имя нового invariant или процесса без содержательного
  описания.** Q-N с classification `missing-invariant` /
  `missing-process`. Имя фиксируется как кандидат, документ
  не создаётся.

### Что НЕ делается

- Не сверяться с `docs/spec/MODELS.md` для решения, является
  ли имя моделью — реестр не гейт, а отражение.
- Не создавать пустых документов для имён без содержательного
  описания — для этого Q-N.
- Не создавать документов на реализационные классы и значения.

## Работа с упоминаниями неполных сущностей: заглушки и Q-N

Legacy-документ часто упоминает сущность, для которой нет полного
описания — потому что её содержательный источник в другом
legacy-файле, или потому что описание разнесено по нескольким
местам.

- **Если у сущности есть хоть какое-то содержание в текущем
  legacy** (определение, поля, поведение) — создаётся документ в
  `docs/spec/`. Может быть заглушка (только определение и
  связи), может быть частично заполненный документ. Состояние
  «заглушка» — не ошибка, а начальное состояние, в которое
  потом дольёт следующая миграция. Документ регистрируется в
  `docs/spec/MODELS.md` сразу.
- **Если у сущности нет ни одного содержательного упоминания**
  (только имя в чужом тексте) — заводится Q-N с classification
  `missing-<тип>`. Документ не создаётся. Текст, упоминавший
  имя, оформляется прозаически (не markdown-ссылкой на
  несуществующий файл): «связана с <Имя> через ...».
- **При следующей миграции**, доносящей содержание этой
  сущности, Q-N закрывается с резолюцией, ссылающейся на
  созданный документ; прозаические упоминания заменяются на
  markdown-ссылки (связное обновление — см. ниже).

Markdown-ссылки на ещё не созданные документы — запрещены.
Документ-заглушка существует — ссылка на него нормальная.
Документа нет — прозаическое имя плюс Q-N.

## Закрытие Q-N при создании модели

При создании или дополнении целевого spec-документа кк
выполняет связное обновление в той же сессии:

1. **Открыть журнал** `.claude/questions/open-questions.md` и
   найти все открытые Q-N, относящиеся к создаваемой/дополняемой
   сущности (по имени модели/процесса/invariant).
   Учитываются Q-N с classification `missing-model`,
   `missing-process`, `missing-invariant`, `concept` — все,
   где субъект совпадает.
2. **Закрыть найденные Q-N** через скилл
   [`open-questions-workflow`](../open-questions-workflow/SKILL.md)
   с резолюцией: ссылка на созданный документ + короткое
   объяснение, что вопрос разрешён появлением документа.
3. **Найти и обновить прозаические упоминания.** В существующих
   `docs/spec/`-документах могут быть прозаические упоминания
   создаваемой сущности (текст вида «связана с <Имя> через ...»
   без markdown-ссылки), оставленные, когда документа ещё не
   было. После создания документа эти упоминания заменяются на
   обычные markdown-ссылки. Поиск — grep по имени модели в
   `docs/spec/`.
4. **Обновить `docs/spec/MODELS.md`.** Если создан новый
   model-документ — добавить запись в реестр; если ранее в
   реестре была заглушка-описание без файла — заменить её на
   ссылку. Правила — в скилле
   [`spec-models-registry`](../spec-models-registry/SKILL.md).

Откладывание связного обновления «на потом» создаёт расхождение
между журналом, реестром и фактическим состоянием `docs/spec/`.

## MIGRATED-маркер на исходнике

Когда все упоминания в legacy-документе разнесены —
содержательные в целевые документы (созданные или дополненные),
без описания в Q-N — на первую строку исходника ставится маркер:

```markdown
> **[MIGRATED → <путь1>, <путь2>, ...]** — этот документ больше не источник правды.
```

Если миграция распределила содержание по нескольким целевым
документам — в маркере перечисляются все целевые документы.

Сам файл исходника не удаляется — остаётся в legacy-локации с
маркером.

**Открытые Q-N не блокируют MIGRATED-маркер.** Q-N, заведённые
в ходе миграции (`missing-model`, `concept` и т.п.), относятся
к **сущности**, не к legacy-документу. Legacy-документ свою
задачу выполнил: всё его содержание либо разнесено по целевым
документам, либо явно помечено как пробел в журнале. Маркер
ставится. Q-N остаётся открытым до тех пор, пока сущность не
получит содержательное описание из другого источника.

**Маркер для shared-файлов.** Если legacy-документ распадается
по нескольким миграционным сессиям (фрагменты файла относятся к
разным кластерам или разным сессиям) — MIGRATED-маркер ставится
только когда **все** фрагменты файла разнесены. До этого момента
в трекере статус документа `in-progress`, в перечне целевых
spec-документов накапливаются ссылки по мере миграции каждого
фрагмента.

## Терминологические замены при миграции

При переработке исходника в целевой spec-документ — применяются
канонические термины проекта по
[`docs/conventions/terminology.md`](../../../docs/conventions/terminology.md).
Известные замены:

| Термин в legacy | Канонический термин |
|---|---|
| entity, сущность, domain object | доменная модель |
| persisted (рус.) | хранимое |
| orphan, orphan-сущность, orphan order/position | domain-only или external-only (уточнить, какой тип) |
| (упоминание core vs runtime через persistent/transient JPA) | core vs runtime |

Применение:

- Прямые замены (entity → доменная модель; persisted → хранимое)
  делаются автоматически при переработке.
- Замены с уточнением (orphan → domain-only / external-only) —
  требуют разбора контекста. Если из контекста ясно, какой тип
  имеется в виду — заменить конкретным термином. Если неясно —
  завести Q-N с classification `concept`.
- Список замен растёт по мере добавления соглашений в
  `terminology.md`. При работе сверять с актуальной версией
  файла.

## Подводные камни

**1. «Сразу написать целевой документ» без анализа.** Запрещено.
Без прохода по упоминаниям с тестами теряются граничные случаи
(контейнер, который выглядит моделью; реализационный класс,
описанный как сущность; имена-значения, оформленные как модели).

**2. Создание пустого документа вместо Q-N.** Соблазн — создать
файл-каркас под упоминаемое имя, пусть будет. Запрещено: пустой
файл создаёт впечатление, что сущность описана. Если содержания
нет — это Q-N с classification `missing-<тип>`, не документ.

**3. Markdown-ссылка на несуществующий документ.** Запрещено:
ссылка обещает читателю, что цель есть. Если документа нет —
прозаическое упоминание имени плюс Q-N в журнале.

**4. Откладывание закрытия Q-N «на потом».** При создании
документа Q-N о соответствующей сущности должны быть закрыты в
этой же сессии. Отложенное закрытие создаёт расхождение между
журналом, реестром и фактическим состоянием `docs/spec/`.

**5. Парный «migrated-from»-маркер в целевом документе.**
Запрещено. Связь — только через `related_adrs` в frontmatter и
односторонний маркер на исходнике.

**6. Спор о жанре «по удобству».** Жанровое разделение
принципиально. Аргумент удобства неприемлем — применяется тест
типа сущности.

**7. Удаление содержания «потому что в ADR уже сказано».**
Прежде чем удалить блок legacy с обоснованием «дубль ADR» —
проверить, что ADR действительно содержит это утверждение, а
не смежное. Дубли удаляются осмысленно, не по созвучию.

**8. Игнорирование терминологических замен.** Канонические
термины применяются всегда, в том числе в формулировках Q-N.

**9. Сверка с MODELS.md как с гейтом.** Соблазн — «этого имени
нет в MODELS.md, значит модели нет, заведу Q-N». Запрещено:
тест типа применяется к содержанию, не к реестру. Реестр —
отражение, не гейт.

## Связанные документы и скиллы

- [`spec-document-workflow`](../spec-document-workflow/SKILL.md) —
  активируется на целевых документах после исполнения миграции
  (финальный чек-лист).

  оркестратор миграции набора legacy-документов; вызывает этот
  скилл для каждого документа кластера.

  ведение журнала; используется при заведении и закрытии Q-N.

  обновление `docs/spec/MODELS.md` при создании model-документов
  (включая заглушки).
- `.claude/adr/0002-spec-document-standard.md` — стандарт
  документа (фон, не операционная инструкция; конкретные правила
  стандарта проверяет `spec-document-workflow`).
- `.claude/templates/documents/` — шаблоны жанров.
- `.claude/planning/backlog.md` — открытые пункты, закрываемые
  миграцией.
- `.claude/planning/migration-tracker.md` — статус миграции по
  документам и кластерам.
- `.claude/questions/open-questions.md` — журнал Q-N.
- `docs/conventions/terminology.md` — канонические термины.
- `docs/spec/MODELS.md` — реестр канонических имён бизнес-моделей.
